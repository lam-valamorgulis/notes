Idea to Production

Someone decided what to build. Now put it in front of real users, and keep it working.

What this course is for. Twenty-four weeks. One invented product called Speck. At the end, Speck is live, tested, deployed by a pipeline, watched by alarms, and you have broken it on purpose and fixed it. Read MISSION.md for the full mission, and RESOURCES.md for every source used.

The big picture

Most software that never ships was written. The code existed. What was missing was everything around it.

This course teaches the everything-around-it. It starts at the moment the decision is already made — someone said build this — and stops when strangers depend on it. The half before that moment, finding a problem worth solving and cutting it to an MVP, is a different course: Founding Engineer. The two do not repeat each other.

The work happens in four Stages, and the order is not decoration. It is the order in which mistakes get expensive.

Stage 1, Decide. Before any code, you write it down. A design doc forces the argument to happen while it is still cheap — on a page, not in a schema. Then you cut the work into vertical slices: thin pieces that go all the way through the system and reach production. The first slice is a walking skeleton. It does almost nothing, and it is deployed. That is the point.

Stage 2, Shape. Now you make the three decisions that are painful to undo. The data model, because you will rewrite the front end twice and keep the schema. The contract at the edge — Speck puts a <script> tag on other people's websites, and you can never break it. And config, so the same build runs in every environment with no code change.

Stage 3, Deliver. This Stage answers one question: how does a change get from your laptop to a user, safely, today? Four habits do it. Small batches merged to one trunk. A test strategy that one person can keep alive. A deployment pipeline where each stage buys more confidence. And the habit that makes the rest boring: release is not deploy. You ship the code turned off, turn it on with a flag, and change the database in steps where old and new code both work.

Stage 4, Operate. Live software fails. The question is whether you find out from a graph or from a customer. You learn the four golden signals, one SLO, the security baseline that matters for a multi-tenant product, and what to do in the first ten minutes of an incident. Then you break Speck on purpose and write the postmortem.

Twelve core ideas, one per two weeks. Everything else waits in the depth queue.

The product: Speck

Every task in every Lesson is done on the same product. Speck is a hosted feedback widget. A site owner pastes one <script> tag. Visitors leave a short note. The owner reads the notes in a dashboard.

Speck stays the same for all 24 weeks on purpose. The schema you design in week 5 is the table you migrate in week 17, with rows in it. A fresh toy project per Lesson would hide exactly the problems this course exists to teach.

Speck hasSo the course must teach
A public write endpoint anyone can callRate limits, abuse, CORS, input validation
Many site owners in one databaseAccess control — OWASP's number one risk
A script tag on other people's sitesA public contract you can never break
A daily digest emailBackground jobs, retries, doing a thing exactly once
Growth from 10 rows to 10 millionSchema change with users on the table
A dashboard behind a loginSessions, secrets, config per environment

The 24 weeks

One core Lesson per two weeks. Each block also names its depth Lessons and the one artefact it must produce. Each Stage ends with a gate — a sentence that must be true before the next Stage starts. The same list, printable, is in the build order.

Stage 1 — Decide

Weeks 1–4. The cheapest place to be wrong is on a page.

Weeks 1–2 Lesson written

Write it down before you build it

The argument you avoid now becomes a rewrite later.

  • 0001 The design doc core — context, goals, non-goals, alternatives considered. A code review before there is code.
  • 0013 Non-goals: the section that saves the project depth — writing down what you refuse to build.
  • 0014 Reviewing someone else's design doc depth — the five questions that find the hole.

Artefact: docs/0001-speck.md — a real design doc for Speck, naming one option you rejected and why.

Weeks 3–4 next

Cut it into slices that reach production

Not all the database, then all the API, then all the UI.

  • 0002 Vertical slices and the walking skeleton core — the thinnest slice that goes through every layer and deploys.
  • 0015 Elephant Carpaccio: finding 15 slices where you saw 3 depth — the slicing drill.
  • 0016 Slice zero is a deploy, not a login screen depth — why the skeleton starts at the end.

Artefact: Speck deployed, doing one nearly useless thing end to end, on a real URL.

Gate 1: a design doc exists, someone else read it, and it names an option you rejected. If it does not, Stage 2 does not start.

Stage 2 — Shape

Weeks 5–10. Three decisions that are painful to undo later.

Weeks 5–6

The data model outlives the code

You will rewrite the front end twice and keep the schema.

  • 0003 The data model outlives the code core — model the nouns and the rules before the screens.
  • 0017 Choosing the boring stack, once depth — you get about three novel choices.
  • 0018 Tenant id: the column you cannot add later depth — where multi-tenancy lives.

Artefact: Speck's schema as a migration file, with the tenant boundary in it from the first line.

Weeks 7–8

The contract at the edge

Speck's script tag lives on other people's sites. It can never break.

  • 0004 The contract at the edge core — design the API first, and know exactly what counts as a breaking change.
  • 0019 Errors are part of the contract depth — a changed error shape breaks clients too.
  • 0020 A CI check that fails on a breaking change depth — the rule, enforced by a machine.

Artefact: openapi.yaml for Speck, plus a written breaking-change policy you can point at.

Weeks 9–10

Same build, every environment

One artefact. Different config. No code change.

  • 0005 Config from the environment core — the twelve-factor rules that survived fifteen years, and the ones that did not.
  • 0021 Secrets: the smallest safe version depth — for one person, with no vault.
  • 0022 One command to run Speck on a new laptop depth — dev and production, close together.

Artefact: a README a stranger can follow in 30 minutes.

Gate 2: schema, public API and config are written down, and someone who has never seen Speck runs it in 30 minutes.

Stage 3 — Deliver

Weeks 11–18. How a change gets to a user today, not next month.

Weeks 11–12

Small batches, one trunk

Long branches are unmerged risk sitting in a corner.

  • 0006 Trunk-based development and small batches core — merge at least once a day, three or fewer live branches.
  • 0023 Code review when there is nobody to review depth — the one-person substitutes.
  • 0024 Commit messages that still help in a year depth — the why, not the what.

Artefact: two weeks of Speck commits where no branch lived longer than one day.

Weeks 13–14

Tests one person can maintain

A slow flaky suite gets switched off, and then protects nothing.

  • 0007 A test strategy one person can maintain core — many fast, some medium, very few slow.
  • 0025 Test the boundary, not the mock depth — the test that passes while the code is broken.
  • 0026 Flaky tests are worse than no tests depth — quarantine, then fix or delete.

Artefact: a suite that runs in under 90 seconds and blocks a bad merge.

Weeks 15–16

The pipeline that ships

Each stage buys confidence, and each stage costs time.

  • 0008 The deployment pipeline core — build once, promote the same artefact, deploy on green.
  • 0027 What each stage is allowed to cost depth — the time budget per stage.
  • 0028 The pipeline is code too depth — reviewed, versioned, testable.

Artefact: a merge to trunk that reaches production with nobody touching a server.

Weeks 17–18

Release is not deploy

The habit that makes shipping boring.

  • 0009 Release is not deploy — flags and expand/contract core — ship it off, turn it on later, and change the schema in three safe steps.
  • 0029 The four kinds of flag, and which ones you must delete depth — release, experiment, ops, permission.
  • 0030 Backfill a million rows without a lock depth — batches, and how to resume.

Artefact: one column added and one dropped on a live Speck table, with no downtime, plus one release rolled back on purpose.

Gate 3: a commit reaches production untouched by hand, and you have rolled a release back on purpose.

Stage 4 — Operate

Weeks 19–24. Find out from a graph, not from a customer.

Weeks 19–20

Is it alive?

"Is it healthy?" answered with a number, not a feeling.

  • 0010 The four golden signals and one SLO core — latency, traffic, errors, saturation, then one promise to users.
  • 0031 Logs, metrics, traces: what each one is for depth — three tools, three questions.
  • 0032 An alert that does not need a human is a bug depth — why most alerting is noise.

Artefact: a dashboard with four signals, and exactly one alert that reaches your phone.

Weeks 21–22

The security baseline

For a multi-tenant product, access control is the whole game.

  • 0011 The security baseline — OWASP Top 10:2025 core — the ten, and the two that actually apply to Speck today.
  • 0033 Multi-tenant access control, tested depth — a test that fails if tenant A reads tenant B.
  • 0034 Rate limiting a public endpoint depth — the write endpoint anyone can call.

Artefact: a failing-then-passing test proving one tenant cannot read another's feedback.

Weeks 23–24

When it breaks

Roll back first. Diagnose second. Blame nobody.

  • 0012 When it breaks — rollback, incident, postmortem core — the first ten minutes, and the four DORA metrics as the scoreboard.
  • 0035 The runbook one person can follow at 3am depth — written for a tired version of you.
  • 0036 The four DORA metrics on one page depth — measure the pipeline, not the people.

Artefact: a deliberate outage, an alert received, a rollback done, and a written blameless postmortem.

Gate 4: Speck was broken on purpose, the phone rang, and the postmortem exists. That is the end of the course.

The depth queue — the other 80%

None of this is deleted. All of it waits. Every item here is real work that a production system eventually needs, and none of it helps until the twelve core items are solid. The one exception is you asking for one — then we do it, and the Lesson says which core item got skipped.

  • Caching and the CDN depth Where to cache, and the two hard problems: naming and throwing away.
  • Queues, retries and doing a thing exactly once depth Speck's digest email is the example. Idempotency keys.
  • Containers, and when Kubernetes is wrong depth One deployable unit is correct for a product with no users.
  • Infrastructure as code depth Rebuilding the whole environment from a file.
  • Auth in depth: sessions, tokens, OAuth depth What each one actually protects against.
  • Taking money: payments and webhooks depth The webhook that arrives twice, and the one that never arrives.
  • Scaling the database depth Indexes, read replicas, and the point where sharding starts.
  • Distributed tracing and OpenTelemetry depth Following one request across services, when there are services.
  • Load testing and capacity depth Finding the number where it falls over, before a user does.
  • Supply chain security depth OWASP A03:2025. Pinning, SBOMs, and the dependency that changed under you.
  • Deleting user data properly depth Retention, backups, and "deleted" meaning deleted.
  • Disaster recovery you have actually rehearsed depth A backup nobody restored is a guess, not a backup.
  • Cost: the bill as a design constraint depth The query that costs more than the feature earns.
  • Experiments and A/B tests depth Experiment flags, and why most results are noise.
  • Blue-green and canary in detail depth Beyond the one-machine version taught in Lesson 0009.
  • Contract testing between services depth Useful the day Speck stops being one deployable unit.
  • Performance budgets on the front end depth Speck's widget runs on other people's pages. Size is a promise.
  • Handing the code to engineer number two depth What has to be written down before someone else can help.
