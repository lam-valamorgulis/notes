Reference · terms

Glossary

Every term this course uses, in plain words. If a Lesson says it, it is here.

The rule. A term is introduced once in plain words, then the real name is used from then on. The real name never gets softened into a description, because the real name is the thing you have to type, search for, and say to another engineer.
Two kinds of entry Entries marked sourced come from the resource named. Entries marked ours are this course's own wording, and you should not quote them as if a book said them.

Stage 1 — Decide

TermIn plain wordsWhere it comes from
Design doc A document written before the code. It says what you are building, what you are deliberately not building, how it will work, and which other options you rejected. sourced — Design Docs at Google
Non-goal A thing the design could reasonably do, and will not. Written down, so nobody argues about it later. Not the same as "we forgot". sourced — same
Alternatives considered The section listing other designs you thought about, and why you did not pick them. The section that proves the choice was a choice. sourced — same
Cross-cutting concerns The things every part of a design touches: security, privacy, being able to see what it is doing. sourced — same
ADR (Architecture Decision Record) A short note recording one decision and its reason. Smaller than a design doc. Written when the decision is made, never edited after. sourced — widely used; see SWE at Google, ch. 10 on docs as code
Vertical slice A thin piece of work that goes through every layer — screen, server, database — and produces something a user can see. sourced — agile practice; see walking skeleton
Horizontal layer The opposite. Building all the database, then all the API, then all the UI. Nothing works until the last one is done. ours — the plain contrast term
Walking skeleton The thinnest slice of real function that you can build, deploy and test end to end, automatically. It does almost nothing. It is deployed. sourced — Alistair Cockburn, via Blodgett
Elephant Carpaccio An exercise where a team learns to cut one feature into 15–20 slices, when they first only saw 3. sourced — Cockburn / Kniberg workshop

Stage 2 — Shape

TermIn plain wordsWhere it comes from
Data model The nouns your system stores and the rules connecting them. In Speck: site, visitor note, owner, plan. sourced — Designing Data-Intensive Applications
Schema The data model as the database actually holds it: tables, columns, types, constraints. standard term
Migration A file that changes the schema, versioned with the code, run in order. Never a change typed by hand into the live database. standard term
Multi-tenant One running system serving many separate customers, whose data must never mix. Speck is multi-tenant from day one. standard term
Tenant id The column saying which customer a row belongs to. Cheap on day one. Very expensive to add to a full table later. ours — the "cannot add later" framing is this course's
Contract The promise your system makes to something outside it: the shape of a request, the shape of a reply, the errors it can return. standard term
OpenAPI A file format describing an HTTP API — every path, parameter and response — that both humans and tools can read. standard — OpenAPI Initiative
Breaking change A change where a client that worked before now fails, without the client changing at all. Removing a field. Renaming one. Making an optional field required. Tightening authentication. sourced — Speakeasy
Additive change A change old clients survive: a new optional field, a new endpoint, a new value in a list they can ignore. sourced — same
Deprecation Marking part of an API as "going away", while it still works, so clients have time to move. OpenAPI 3.1 has a keyword for it. sourced — same
Twelve-factor app Twelve rules for building software that runs the same way everywhere. The ones that matter most here: config comes from the environment, dev and production stay close, logs are just a stream of text. sourced — 12factor.net
Config Everything that differs between one environment and another: database address, API keys, feature switches. Never in the code. sourced — 12factor, factor III
Environment One place the software runs: your laptop, staging, production. Same build, different config. standard term
Dev/prod parity Keeping your laptop and production as similar as you can, so a bug shows up before users find it. sourced — 12factor, factor X
Build artefact The one packaged thing your pipeline produces and then promotes through every environment. Built once, never rebuilt per environment. sourced — Deployment Pipeline
Innovation token An imaginary budget of about three novel technology choices. Spend them where they win. Everything else should be boring and well known. sourced — Choose Boring Technology

Stage 3 — Deliver

TermIn plain wordsWhere it comes from
Trunk The one main branch everyone merges into. Often called main. sourced — trunkbaseddevelopment.com
Trunk-based development Everyone merges small changes into trunk at least once a day. Branches live hours, not weeks. sourced — DORA
Batch size How much change goes out at once. Small batches fail small and are easy to undo. Large batches fail large. sourced — Accelerate
Continuous integration (CI) Trunk-based development plus fast automated tests running on every change, so trunk always works. sourced — DORA
Continuous delivery (CD) Every change that passes the pipeline could go to production at any moment. A human still chooses when. sourced — Humble & Farley
Continuous deployment The same, but no human chooses. Passing the pipeline is the decision. Different from continuous delivery, and often confused with it. sourced — same
Deployment pipeline An ordered set of stages a change must pass. Each stage buys more confidence and costs more time. First failure stops everything. sourced — Fowler
Unit test Tests one small piece on its own. Runs in milliseconds. Points straight at the broken line. sourced — Practical Test Pyramid
Integration test Tests that two real things work together — your code and a real database, for example. Slower, and catches what unit tests cannot. sourced — same
End-to-end test Drives the whole system like a user does. Most realistic, slowest, and most likely to fail for no reason. sourced — same
Test pyramid The shape of a good suite: many unit tests, fewer integration tests, very few end-to-end tests. sourced — Mike Cohn, then Fowler, then Vocke
Flaky test A test that passes and fails on the same code. Worse than no test, because it teaches you to ignore red. standard term
Test double A stand-in for a real thing in a test. A mock is one kind. Too many doubles means you test your fakes, not your system. sourced — Vocke
Deploy Putting new code onto the servers. A technical event. Users may not notice at all. sourced — Feature Toggles
Release Turning a feature on for users. A product event. Separating this from deploy is the key habit of Stage 3. sourced — same
Feature flag / feature toggle A switch that turns a code path on or off without deploying again. sourced — same
Release toggle A flag hiding unfinished work. Short-lived. Must be deleted after the release. sourced — same
Ops toggle A flag that turns an expensive feature off under load. Long-lived on purpose. sourced — same
Experiment toggle A flag that sends different users down different paths, to compare them. sourced — same
Permission toggle A flag that turns features on per customer or per plan. Lives forever. sourced — same
Dark launch Deploying code that runs, but whose result nobody sees yet. standard term
Canary release Sending a small share of traffic to the new version first, and watching before sending the rest. standard term
Blue-green deployment Two identical environments. Traffic switches from one to the other, and switches straight back if it goes wrong. standard term
Rollback Returning to the previous version. The first move in an incident, before understanding anything. sourced — Google Incident Management
Expand and contract Changing a schema in three steps so old and new code both work: expand — add the new thing; migrate — write to both and backfill; contract — drop the old thing. Also called parallel change. sourced — Wellhausen
Backfill Filling a new column with values for rows that already exist. Done in batches, in the background, restartable. standard term
Zero downtime Changing the running system without any request failing. What expand and contract exists to make possible. standard term

Stage 4 — Operate

TermIn plain wordsWhere it comes from
Monitoring Watching numbers you decided to watch in advance. sourced — SRE Book, ch. 6
Observability Being able to answer a question you did not think of in advance, without shipping new code to find out. standard term, contrasted with monitoring
Four golden signals Latency — how long a request takes. Traffic — how much demand there is. Errors — how many requests fail. Saturation — how full the system is. If you can watch only four numbers, watch these. sourced — SRE Book, ch. 6
SLI (Service Level Indicator) One measured number. "The share of requests that returned in under 300 milliseconds." sourced — SRE Book
SLO (Service Level Objective) The target for that number. "99% of requests in under 300 milliseconds, measured over 30 days." An internal promise. sourced — SRE Book
SLA (Service Level Agreement) A promise to a customer with money attached if you break it. Speck does not need one yet. sourced — SRE Book
Error budget The failure your SLO allows. A 99% SLO permits 1% failure. Spend it on shipping. When it runs out, stop shipping and fix things. sourced — SRE Book
Alert / page A message that wakes a human. The rule: if a human does not have to think about it, it should not be a page. sourced — SRE Book, ch. 6
Runbook A written list of steps for a known failure. Written for a tired person at 3am, not for you at your best. sourced — SRE Workbook
Incident A live problem affecting users. It has a start, a person in charge, and an end. sourced — Google Incident Management
Postmortem A written record after an incident: what happened, when, why, and what changes so it does not happen again. sourced — SRE Workbook
Blameless Assuming everyone involved acted sensibly on the information they had. You fix the system that let it happen, not the person. sourced — same
Deployment frequency DORA metric 1. How often you deploy to production. sourced — Four Keys
Change lead time DORA metric 2. From commit to running in production. sourced — same
Change failure rate DORA metric 3. The share of deploys that needed a fix afterwards. sourced — same
Failed deployment recovery time DORA metric 4. How long from broken to working. Older sources call it MTTR or time to restore service. sourced — same
OWASP Top 10 The ten most critical web application security risks, agreed by a wide group and updated every few years. Current version: 2025. sourced — OWASP Top 10:2025
Broken access control (A01:2025) A user reaching data or actions that are not theirs. Number one on the list. For Speck, the whole game. SSRF now sits inside this category. sourced — same
IDOR The most common form of it: changing an id in a URL and getting someone else's data. standard term, a kind of A01
Security misconfiguration (A02:2025) Default passwords, open buckets, debug mode left on. Moved up from fifth place in 2021. sourced — OWASP Top 10:2025
Software supply chain failures (A03:2025) New category in 2025. The risk arrives through your dependencies and your build system, not your code. sourced — same
Mishandling of exceptional conditions (A10:2025) New category in 2025. Errors handled badly, failing into an unsafe state. sourced — same
ASVS OWASP's checklist version of the same knowledge, at three levels. Level 1 is the right target for a product like Speck. sourced — OWASP ASVS
CORS The browser rule deciding which websites may call your API from a page. Central to Speck, because its widget runs on other people's sites. standard web platform term
Rate limiting Refusing requests above a set speed, per caller. The first defence for a public write endpoint. standard term

Course words

These are this course's own words. No source uses them this way.

WordWhat it means here
SpeckThe invented product every Lesson builds: a hosted feedback widget.
StageOne of the four parts of the course — Decide, Shape, Deliver, Operate. Not the same as a pipeline stage.
GateOne sentence that must be true before the next Stage starts. Pass or fail, no middle.
ArtefactThe thing that exists at the end of a two-week block. A file, a deploy, an alarm, a document.
Core / depthCore is the 20% taught first. Depth is everything else, queued, not deleted.
ScarA block-03 item in a Lesson: a real way this idea fails in production.
Two pairs people mix up Deploy and release are not the same thing, and Stage 3 depends on the difference. Pipeline stage and course Stage are also different — this page capitalises the course one.
