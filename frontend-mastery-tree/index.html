The end state is domain expertise: explain from first principles · predict an unseen case · say what the design gives up · debug with no ready answer online · judge someone else's work. Every lesson names which of those five it moves. Full statement in MISSION.md.

The story of the tree

Everything a browser does for your users rests on three layers of physics. A single-threaded engine runs your code one call at a time — the call stack, the boxes its variables live in, the boxes that outlive the call, and the loop that feeds it one task at a time (Stratum 1 · Language & Runtime, 32 cores). Because that loop will not paint until its microtasks are drained and cannot be interrupted, the way you spend a millisecond is the way the storefront feels.

That code exists to change pixels, and pixels come out of a fixed pipeline: parse — style — layout, paint, composite — with a 16.67 ms budget per frame (Stratum 2 · Rendering, 26 cores). Miss the budget and you have a metric with a name the client can read: LCP, CLS, INP. And nothing arrives to run or render at all except over a network you must treat as slow, flaky and expensive — where a new domain costs half a second before it is any use, the cheapest request is the one that never happens, and a careless retry can double a customer's order (Stratum 3 · Network & Delivery, 26 cores).

On top of that physics sits every framework you will ever use. Reactivity, component models, state, routing, rendering strategies, build systems — these are not magic; they are engineering answers to Strata 1–3 (Stratum 4 · Architecture, 30 cores). Once an app works, four constraint layers separate it from one you can ship: it must work for every human (Stratum 5 · Platform & Users, 20 cores), survive hostile input (Stratum 6 · Security, 12 cores), be testable, observable and debuggable by a team (Stratum 7 · Engineering Practice, 17 cores), and integrate probabilistic AI services without wrecking determinism, cost or trust (Stratum 8 · AI Integration, 12 cores).

The order of work is core-first inside depth-first. Of the 84 cores in Chapters 1–3, twenty-one carry most of the real-world value. Those twenty-one are taught first and taught deeply. The other sixty-three are not deleted — they are queued below, and they wait.

Chapter 1 — Language & Runtime 9 core lessons

Branch: Execution model (6 cores) → Event loop (5) → Memory (6) → Async primitives (6) → Type system (6) → Engine optimization (3). Nine are core; the rest are queued.

  • 0001 · The call stack & execution context core
    One call = one context; push, pause, pop, resume. Stack traces as photos of the stack.
  • 0002 · The scope chain & lexical environment core
    Where variables live, and how a name is resolved by walking fixed, write-time outer references.
  • 0003 · Closures — captured environment, not copied values core
    Derived, not memorised: the frame is popped, the box is not. Shared, never copied. One box per call.
  • 0004 · this binding: call-site, bind, arrow capture core
    A hidden argument the call site fills in. An arrow has no slot, which is why bind is ignored.
  • 0005 · The task queue & one task per tick core
    Run-to-completion, derived from the one-stack rule. Why setTimeout(fn, 0) promises almost nothing.
  • 0006 · The microtask queue drains to empty before render core
    Two queues, two rules. Why a spinner added before await Promise.resolve() never appears.
  • 0007 · Long tasks, starvation & input delay core
    Input delay + processing + presentation. Where the 50 ms line comes from, and starvation with nothing to blame.
  • 0008 · The promise state machine & resolution procedure core
    Three states, two one-way transitions, once. And why fetch does not reject on a 422.
  • 0009 · Leak shapes: detached DOM, listeners, timers, closures core
    Reachable, not used. Four ropes, one rule, and the three-snapshot hunt that finds the line to change.

Chapter 2 — Rendering Pipeline 7 core lessons

Branch: Parse (4 cores) → Style (4) → Layout (8) → Paint & composite (5) → Frame budget (5). Seven are core.

  • 0010 · CSSOM construction & render-blocking CSS core
    Two lanes into one render tree. Why the browser refuses to paint early, and what each fix costs.
  • 0011 · Parser-blocking scripts vs defer, async, module core
    Both download early — they differ in whether order survives. Includes the Liquid script_tag trap.
  • 0012 · Cascade, specificity, inheritance & layers core
    Five ordered steps; specificity is step four. Why unlayered app CSS beats your carefully layered theme.
  • 0013 · Which properties trigger layout, paint or composite core
    One rule generates the whole table. And what a compositor layer actually costs in memory.
  • 0014 · Layout thrashing & forced synchronous layout core
    Same work, same result, different line order — five to twenty times faster.
  • 0015 · The 16.67 ms frame budget core
    The deadline is set by the screen. The exact frame order, and where rAF sits in it.
  • 0016 · LCP, CLS, INP — definition and measurement core
    Three failure modes, three numbers. LCP's four sub-parts, and why lab and field can both be right.

Chapter 3 — Network & Delivery 5 core lessons

Branch: Protocol (6 cores) → Caching (5) → Service worker (4) → Client storage (3) → Request discipline (5) → Real-time (3). Five are core.

  • 0017 · DNS, TCP and TLS — what a request costs in round trips core
    Latency, not bandwidth. Slow start. Why every third-party domain is a fresh three-round-trip bill.
  • 0018 · Cache-Control & immutable assets core
    A one-year lifetime is safe exactly when the URL changes with the content — plus what you do and do not control on Shopify.
  • 0019 · Resource hints: preconnect, preload, prefetch, fetchpriority core
    Each hint moves a different block. If you cannot name the block, delete the hint.
  • 0020 · Waterfall vs parallel — reading the Network panel core
    A staircase is a discovery problem, never a network problem. Which Timing row blames whom.
  • 0021 · Retry with exponential backoff and jitter core
    Backoff protects the server; jitter protects it from your other clients. And why a timeout is not a failure.
