Event loop, timing & promises — cheat sheet

The compressed core of lessons 0005–0008. If you can reproduce the two tables below from memory, you can answer any output-ordering question asked in an interview.

The one turn lessons 0005 · 0006 · 0015

1. run ONE task (script, click handler, setTimeout callback) 2. drain ALL microtasks (.then, await continuations, queueMicrotask, MutationObserver) ...including microtasks queued DURING the drain — "to empty" is literal 3. handle input 4. run requestAnimationFrame callbacks 5. recalculate style, then layout 6. deliver ResizeObserver / IntersectionObserver records 7. paint, composite <-- the FIRST moment the user sees anything 8. if time remains, requestIdleCallback -> back to 1 everything before step 7 is invisible. a microtask runs before the frame; a task runs after it. that single sentence answers most ordering questions.

Task vs microtask lesson 0006

Task (macrotask)Microtask
How many per turnexactly oneall of them, until empty
Queued while runningwaits for a later turnruns in this checkpoint
Can a frame happen betweenyesno
SourcessetTimeout, DOM events, messages, network events.then/.catch/.finally, every await continuation, queueMicrotask, MutationObserver
Failure modea long task delays the next frame and any queued inputan endless chain freezes the tab with no long task to blame
The yield that actually works await Promise.resolve() stays in the same turn — no paint. await new Promise(r => setTimeout(r, 0)) reaches the task queue and ends the turn — a paint can happen. Awaiting a real fetch also ends the turn, which is why the same code can show a spinner on a cold load and not on a cached one.

Ordering drills — derive, do not memorise

Timers: the bare facts lesson 0005

BeliefReality
"setTimeout(fn, 0) runs now"queues a task, eligible after ≥ 0 ms, after every microtask and every task already queued
"0 means 0"clamped to about 4 ms after ~5 levels of nesting; background tabs throttled much harder
"I can be interrupted if it matters"never. Run-to-completion. You must end your own task
"chunking makes it responsive"only a loop that yields; a loop that schedules 30 chunks up front is starvation with a clean long-task report

Interaction cost lessons 0007 · 0016

INP = input delay + processing + presentation delay (queued behind (your (style, layout, other work) handler) paint) long task >= 50ms <- derived: ~100ms response budget minus the worst-case wait INP good <= 200ms at the 75th percentile of REAL users most slow interactions are INPUT DELAY, from scripts you did not write. measure which of the three is biggest BEFORE fixing anything. always throttle CPU 4x — that is the customer's phone.

Promise state machine lesson 0008

RuleWhy it exists
Three states, two one-way transitions, oncea callback could be called twice; a promise cannot settle twice
A second resolve/reject is silently ignoredno error, no warning — silence is the mechanism
The outcome is kepta handler attached later still receives it, unlike an event you missed
Handlers always async, even when settledone behaviour to reason about instead of two — predictability bought with a tick
.then returns a new promisevalue → fulfil · throw → reject · promise → adopt (2 extra ticks) · no handler → pass through
fetch rejects only on network failure404 and 422 are fulfilled promises. Check response.ok yourself
The two that cost money A chain with no .catch turns a real failure into a console warning nobody reads. And fetch not rejecting on a bad status means a 422 error body gets rendered as if it were data — an empty cart in front of a customer.
