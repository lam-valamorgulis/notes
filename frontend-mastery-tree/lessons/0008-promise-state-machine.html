The promise state machine & resolution procedure

A promise is not "async syntax". It is a tiny state machine with three states, two one-way transitions and one hard guarantee — and every rule about await, chaining and error handling is a consequence of those.

core Domain expertise: moves ability #3 (say what the design gives up) and ability #4 (debug with no ready answer) — a swallowed rejection in a cart request is invisible until you know where the state went.

The win: after ~35 minutes you can say what a promise guarantees that a callback cannot, explain why handlers are always asynchronous, and find the exact line where an error in an AJAX cart chain disappeared.

1. The three problems callbacks could not solve

Before promises, an async operation took a callback. Three things went wrong constantly, and each one is a rule the promise had to invent:

Callback problemThe rule promises answer it with
The callback ran twice (a retry fired the old one too)state changes once, and only from pending
The callback never ran, or ran with both an error and a valueexactly one of two outcomes: a value or a reason
You could not attach a handler after the operation finishedthe result is kept, so a late handler still gets it

Put those three together and you are forced into a state machine. There must be a "not finished yet" state (pending), two terminal states (fulfilled, rejected), and the transitions must be one-way and once-only. The word for "no longer pending" is settled. This is not a design opinion — it is what the three requirements above leave you with, and the spec writes it out at ECMA-262 § Promise Objects.

2. Why handlers are always asynchronous

Here is a rule that looks like an inconvenience and is actually a safety guarantee. Even when a promise is already settled, .then does not call your function immediately — it queues it as a microtask (lesson 0006): 

const p = Promise.resolve('done');   // already fulfilled
p.then(v => console.log('handler', v));
console.log('after .then');
// → after .then, then handler done

Ask why, from first principles. If .then ran the handler synchronously when the value was ready, then the same function would sometimes run before the next line and sometimes after — depending on cache timing you do not control. Every caller would have to defend against both. The platform removes the choice: always later, never now. One behaviour to reason about instead of two.

Say it this way

A promise gives up the chance to be fast in the easy case, to be predictable in every case. That is the trade, and naming it is ability #3.

3. then returns a new promise — so errors have a path

.then does not return the same promise; it returns a new one, whose state is decided by what your handler did. Four rules, all derivable from "the new promise needs a state":

  • Handler returns a plain value → the new promise fulfils with it.
  • Handler throws → the new promise rejects with the thrown thing. This is why try/catch-style flow works across a chain.
  • Handler returns a promise → the new promise adopts it: it waits, then takes the same outcome. This step is the resolution procedure, and it costs two extra microtask ticks — a bare fact worth verifying by hand, in the live-coding step below.
  • No handler of the right kind → the state passes through to the next link. That is why one .catch at the end can catch a rejection from any earlier step.
fetch('/cart/add.js', { method: 'POST', body })
  .then(r => r.json())            // throws on bad JSON → rejects the NEXT promise
  .then(cart => render(cart))     // skipped entirely if the step above rejected
  .catch(err => showError(err));  // one place to land, for either step
Trap — the silent one, and it is everywhere in theme code

Two mistakes hide a real failure from you completely:

1. A chain with no .catch. The rejection has nowhere to go and becomes an unhandled rejection — a console warning many people never look at, with no visible break in the UI.

2. fetch does not reject on 404 or 500. It rejects only on a network failure. A 422 from a cart endpoint is a perfectly fulfilled promise, so your .then runs happily with an error body and renders nonsense. You must check response.ok yourself. That is a platform decision, not a promise rule.

4. Explain it back Feynman check

Part 1 · Plain words — no jargon at all

A promise is a small box with a label. At first the label says "waiting". Later, exactly once, someone writes on it either "here is the answer" or "here is what went wrong" — and after that the label can never be changed again. Because the box keeps what was written, you can come and read it whenever you like, even long after. And when you ask the box to tell you, it always tells you a moment later, never in the same breath — so it behaves the same way whether the answer arrived an hour ago or has not arrived yet.

Part 2 · One analogy, and where the analogy breaks

The analogy. A parcel tracking page. It says "in transit", then one day it says "delivered" or "lost". You can check it whenever you want and it still tells you the outcome. Nobody can change "delivered" back to "in transit".

Where it breaks. Tracking pages update themselves and you can refresh to see progress. A promise has no progress: there is nothing between "waiting" and the final answer — no percentage, no partial value, no cancel button. If you need progress or cancellation you need something else (a stream, or AbortController). Pretending a promise can report progress is a design mistake, not a missing feature.

Part 3 · The sticking point

Two, and they cost real money. First: people think fetch rejects when the server returns an error. It does not — 404 and 500 are successful promises with an unhappy body, so an unchecked response.ok is a silent bug in a live cart. Second: people say ".then returns the promise". It returns a new promise, which is the only reason a throw in step two can be caught in step five. Say "new promise" out loud and the whole error model becomes obvious.

Part 4 · Teach it back to me

Two or three sentences to a junior who asks: "my .then ran even though the server said 422, and the page showed an empty cart. Isn't .catch supposed to handle that?" Explain what the promise actually promised, and what it never promised. Then send it to me. I am checking that you separate the request succeeded from the server was happy — a distinction most candidates blur.

5. Point at it: read the state yourself gate #3

  1. The state, in the Console. Run const p = new Promise(r => setTimeout(() => r(42), 3000)); p; — the Console prints Promise {<pending>}. Wait three seconds, type p again: Promise {<fulfilled>: 42}. The state machine, on screen, with no library.
  2. Once-only, proven. Run const q = new Promise((res, rej) => { res('first'); res('second'); rej('nope'); }); q.then(console.log); — it logs first. No error, no warning. Silence is the mechanism: later transitions are ignored.
  3. The unhandled rejection. Run Promise.reject(new Error('boom')) with no .catch. Read the exact console wording — Uncaught (in promise). That is the message you will now recognise in a client's console instead of scrolling past it.
  4. Async stack traces. In Sources, break inside a .then handler and look at the Call Stack pane: DevTools shows the async frames that queued it, separated by a marker. You are reading across microtask boundaries — the pane is stitching two turns of lesson 0005's loop together for you.
Work drill — do this on a real theme

A theme's AJAX add-to-cart does fetch('/cart/add.js', …).then(r => r.json()).then(cart => renderDrawer(cart)) with no .catch. A customer adds a sold-out variant. Shopify replies 422 with a JSON body { description: "…is not available" }. The drawer opens showing zero items, and the console shows one warning nobody noticed.

Before flipping the recall cards: name the exact promise state after the fetch, say which line first behaves wrongly, and say which line produced the warning. Then the interviewer's follow-up: write the minimum correct version, and explain why adding a .catch alone would not fix this bug.

6. Live coding session

Type it, predict it, break it

Open a scratch file. Type this by hand and predict the two lines' order before running:

const p = Promise.resolve('ready');
p.then(v => console.log('handler', v));
console.log('sync line');

Now the interleaving question — write your prediction down, all four letters, before running:

Promise.resolve().then(() => console.log('a')).then(() => console.log('b'));
Promise.resolve().then(() => console.log('c')).then(() => console.log('d'));

The answer is a c b d, and you can derive it from lesson 0006 alone: the checkpoint drains what is queued, and each .then only queues its successor once its own handler has run.

Now measure the resolution procedure's cost yourself — this is the bare fact from section 3, made observable. Predict which chain finishes first:

Promise.resolve()
  .then(() => Promise.resolve('PROMISE-RETURNING'))
  .then(v => console.log(v));

Promise.resolve()
  .then(() => console.log('plain 1'))
  .then(() => console.log('plain 2'))
  .then(() => console.log('plain 3'));

All three plain lines print before PROMISE-RETURNING, even though its chain is shorter — adopting a returned promise costs two extra ticks. Verify it rather than believing either of us.

Break it the production way. Point a fetch at a URL that returns a 404 and see for yourself:

fetch('/this-path-does-not-exist.js')
  .then(r => { console.log('then ran, ok =', r.ok, r.status); return r.json(); })
  .then(d => console.log('parsed', d))
  .catch(e => console.log('caught', e.message));

Predict first: does .catch fire because of the 404, or because of something else? Run it. The .then runs with ok = false, and the .catch only fires later, when the HTML error page fails to parse as JSON. That gap — a real failure reported as a parse error — is the bug in the drill.

Remember this
  • Three states — pending, fulfilled, rejected — two transitions, one-way and once. "Settled" means no longer pending.
  • A second resolve or reject is silently ignored. No error, no warning.
  • The outcome is kept, so a handler attached later still receives it — unlike an event, which is gone if you missed it.
  • Handlers always run as microtasks, even on an already-settled promise: predictability bought with a tick.
  • .then returns a new promise. Return a value → fulfil; throw → reject; return a promise → adopt it (two extra ticks); no matching handler → pass through.
  • fetch rejects only on network failure. A 404 or 422 is a fulfilled promise — check response.ok yourself.
  • A chain with no .catch turns a real failure into a console warning nobody reads.

If you remember one thing: a promise guarantees the request finished, never that the answer was good.
