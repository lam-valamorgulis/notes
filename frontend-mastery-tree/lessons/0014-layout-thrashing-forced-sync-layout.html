Stratum 2 · Rendering Pipeline · Layout · Lesson 0014

Layout thrashing & forced synchronous layout

The browser saves you work by doing layout once, at the end. Reading one innocent property in the wrong place cancels that saving — and doing it in a loop turns one layout into twenty-four.

core Domain expertise: moves ability #4 (debug with no ready answer) — this bug has no error message, no stack trace, and a name most developers never learn.

The win: after ~35 minutes you can spot the read-write loop in any file, find the "Forced reflow" warning in a profile, and make the same feature five to twenty times faster by moving lines rather than rewriting logic.

1. Why the browser is lazy on purpose

Suppose you change six styles in one task. Laying out after each change would be six layouts for one visible result. So the browser batches: it marks the affected boxes dirty, keeps running your code, and does style and layout once, at the end of the task — the render step from lesson 0005's diagram. That is why a hundred DOM writes in a loop can still be cheap.

Now break it. Your code asks for a number that depends on geometry: 

el.style.width = '300px';           // marks layout dirty — no layout yet
const h = el.offsetHeight;          // you asked. the answer must be CORRECT.

The browser cannot hand you a stale number, and it cannot predict one. So it stops, performs the whole pending layout right now, mid-JavaScript, and returns the true value. That is a forced synchronous layout. Once per task it is a fair price. Inside a loop it is a disaster: 

cards.forEach(card => {
  const h = tallest.offsetHeight;   // READ  → forces layout, because...
  card.style.height = h + 'px';     // WRITE → ...this dirtied it again last iteration
});

Twenty-four cards, twenty-four full layouts in a single task. Nothing is wrong with either line. The order is wrong. That pattern is layout thrashing.

2. What counts as a read

Any property or method whose answer depends on geometry will force a pending layout. The ones you will actually meet in theme code:

CategoryExamples
Box metricsoffsetTop, offsetLeft, offsetWidth, offsetHeight, clientWidth, clientHeight
RectsgetBoundingClientRect(), getClientRects()
ScrollscrollTop, scrollLeft, scrollWidth, scrollHeight, scrollIntoView()
Computed stylegetComputedStyle(el) then reading a layout-dependent property
WindowinnerWidth/innerHeight in some cases, scrollY, focus()

Full, engine-specific list: Paul Irish — What forces layout / reflow. The point is not the list. The point is the question: does this line ask for a number that depends on where boxes are?

Trap — a read is only expensive if layout is dirty Reading offsetHeight a thousand times with no writes in between costs one layout, not a thousand: after the first read, layout is clean and the rest are cheap lookups. So "never read offsetHeight" is the wrong lesson. The expensive thing is a write followed by a read, repeatedly. Chase the alternation, not the property.

3. The three ways to fix it

  1. Batch: all reads, then all writes. The default fix, and usually enough. 
    const heights = cards.map(c => c.offsetHeight);        // one layout, at the first read
cards.forEach((c, i) => c.style.height = heights[i] + 'px');  // writes only
  2. Let the platform tell you instead of asking. ResizeObserver and IntersectionObserver deliver geometry after layout has already run, so there is nothing to force. Replacing a scroll handler that reads getBoundingClientRect() with an IntersectionObserver removes the whole class of problem — and this is the single most common real fix in a Shopify theme.
  3. Avoid needing the number. Equal-height cards want CSS grid, not measured heights. Sticky headers want position: sticky, not a scroll listener. A layout you never read cannot be forced.

4. Explain it back Feynman check

Part 1 · Plain words — no jargon at all

The browser saves effort by waiting: you can change many things, and it works out the new positions once, at the end. But the moment your code asks "how tall is this?", it cannot give an old answer — so it stops and works out every position immediately, then answers. Ask, change something, ask again, change again, and you have made it do that full calculation once for every item in your list, instead of once for the whole list.

Part 2 · One analogy, and where the analogy breaks

The analogy. A stocktake. Your colleague is happy to count the whole warehouse once at the end of the day. But every time you ask "how many of item 12 right now?", they must stop and recount everything, because you moved things since the last count. Ask after every single move and the day is gone.

Where it breaks. A person would get annoyed, or guess, or say "roughly forty". The browser never guesses and never complains — it silently does the full recount, every time, and your page just feels slow with no error anywhere. That silence is why this bug survives in codebases for years.

Part 3 · The sticking point

People take away "reading offsetHeight is slow" and then write anxious code that avoids reads while keeping the alternation. Wrong lesson. A read is cheap when layout is clean; the cost comes from write → read → write → read. Second sticking point: assuming this is about the number of DOM operations. It is not — a thousand writes in a row are fine. It is about how many times you force the browser to settle up.

Part 4 · Teach it back to me

Two or three sentences to a junior whose equal-height-cards function takes 180 ms on a collection page. Explain what the browser is being forced to do, why moving two lines fixes it, and how they can prove the fix. Then send it to me — I am checking that you say "because a write came before the read", not "because reading is slow".

5. Point at it: the browser will name this one for you gate #3

  1. The warning nobody reads. Chrome logs "Forced reflow while executing JavaScript took Nms" to the Console when the cost is large enough. Search a client's console for "reflow" before you do anything else — it is a free diagnosis.
  2. The profile, unmistakable. DevTools → Performance → record the interaction. Thrashing looks like a picket fence: many short purple Layout bars in one task. Click one and the summary shows a red warning triangle with "Forced reflow is a likely performance bottleneck", and — the useful part — a link to the exact line of your code that caused it.
  3. Count them. Note the number of Layout entries inside the task before your fix and after. Going from 24 to 1 is the evidence to put in the pull request, and it is gate #3 for this core.
  4. Measure the wall-clock too. Wrap the function in performance.mark/performance.measure, or just performance.now() either side, with CPU throttled 4×. A number the client can read beats a screenshot of a flame chart.
Work drill — do this on a real theme

A collection page has 24 product cards. To align the "Add to cart" buttons, equalise() loops the cards: it reads card.querySelector('.title').offsetHeight, then sets card.querySelector('.title').style.minHeight, then reads the card's own offsetHeight and writes it back to a wrapper. It runs on load, on resize, and after every filter change. The console shows three "Forced reflow" warnings per filter click.

Before flipping the recall cards: count how many forced layouts one call performs, name the exact alternation causing it, and give the batched rewrite. Then the interviewer's follow-up: the resize handler makes it worse — what two separate problems does resize add, and how would you fix each?

6. Live coding session

Type it, predict it, break it

One file. Type it by hand — this is a measurement exercise, so the numbers are the output:

<!doctype html>
<style>.card { width: 200px; padding: 8px; border: 1px solid #ccc; margin: 4px }</style>
<div id="grid"></div>
<script>
  grid.innerHTML = '<div class="card">card</div>'.repeat(500);
  const cards = [...document.querySelectorAll('.card')];

  function thrash() {
    const t = performance.now();
    cards.forEach(c => { c.style.height = (c.offsetHeight + 1) + 'px'; });
    return Math.round(performance.now() - t);
  }

  function batched() {
    const t = performance.now();
    const hs = cards.map(c => c.offsetHeight);          // all reads
    cards.forEach((c, i) => { c.style.height = (hs[i] + 1) + 'px'; }); // all writes
    return Math.round(performance.now() - t);
  }

  console.log('thrash', thrash(), 'ms');
  console.log('batched', batched(), 'ms');
</script>

Predict before running: which is faster, and by roughly what factor? Write your guess down. Then run it with CPU throttled 4× and compare. Most people guess "a bit faster" and are wrong by an order of magnitude.

Now see it, not just measure it. Record a Performance profile while calling thrash() and count the purple Layout bars. Then profile batched(). Find the "Forced reflow" warning triangle and click through to the line it blames — your own c.offsetHeight.

Break the fix on purpose. Add one write into the middle of the read loop:

    const hs = cards.map(c => { c.style.opacity = '1'; return c.offsetHeight; });

Predict: does opacity — a composite-only property from lesson 0013 — dirty layout and bring the thrashing back? Run it and find out. The answer teaches you that "cheap property" and "does not invalidate layout" are two different questions, and it is the most useful surprise in this lesson.

Remember this
  • The browser batches style and layout to the end of the task. That is why many writes in a row are cheap.
  • Reading a geometry property while layout is dirty forces the pending layout immediately, mid-JavaScript.
  • Layout thrashing = write → read → write → read in a loop. N items become N full layouts in one task.
  • A read is cheap when layout is clean. Chase the alternation, not the property.
  • Fix one: all reads, then all writes. Usually a five-line diff.
  • Fix two: let the platform hand you geometry after layout — ResizeObserver, IntersectionObserver.
  • Fix three: do not need the number — CSS grid instead of measured heights, position: sticky instead of a scroll listener.
  • Chrome names it for you: a Console "Forced reflow" warning, and a red triangle on the Layout entry that links to your line.

If you remember one thing: never read geometry inside a loop that also writes styles.
