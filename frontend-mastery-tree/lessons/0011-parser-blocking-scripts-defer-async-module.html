Parser-blocking scripts vs defer, async and module

Lesson 0010 ended with a script that stopped the page being read at all. This lesson explains why the parser has no choice, and what each of the four attributes actually changes — which is one of the cheapest performance wins in any theme.

core Domain expertise: moves ability #2 (predict an unseen case) and ability #5 (judge someone else's work) — reviewing a <head> is a skill, and this is the mechanism you review it with.

The win: after ~30 minutes you can read any script tag and say when it downloads, when it runs, and in what order relative to its neighbours — and you can defend the one case where async is wrong even though it sounds fastest.

1. Why the parser must stop

The parser is building the DOM in document order. Then it meets a <script>. Ask what the script is allowed to do at that moment. It can call document.write('<div>') and insert markup at that exact position. It can read the DOM built so far. It can move nodes.

So the parser cannot continue past a classic script and hope, because the script may change the very bytes it would read next. There is no safe way to run the two at once. It must stop, wait for the script (downloading it if needed), run it to completion — remember run-to-completion from lesson 0005, this is the same one thread — and then resume. That is what parser-blocking means, and it follows from document.write existing at all (HTML Standard § script attributes).

Every one of the four modes below is a way of promising the parser "I will not do that", so it can keep going.

Two extra facts that decide real arguments:

  • The preload scanner. While the parser is blocked, a second, lighter reader scans ahead for URLs and starts downloading them. That is why defer and async can download in parallel at all — and why resources hidden from the scanner (built by JavaScript, or reached through @import) are so much slower.
  • async is only correct for code that depends on nothing and that nothing depends on. Analytics, yes. Your theme's slider, no — it will sometimes run before the DOM it needs exists, and the failure is intermittent, which is the worst kind.
Trap — the Shopify one Liquid's script_tag filter renders a plain classic script: {{ 'theme.js' | asset_url | script_tag }} becomes a parser-blocking tag with no defer. Write the tag by hand instead — <script src="{{ 'theme.js' | asset_url }}" defer></script> — and you have removed a blocker in one line. Then check what the apps injected: app script tags are frequently classic, and each one is a full stop in the middle of your <head>.

3. Why defer is almost always the right default

Line the requirements up and only one option survives. Your theme code usually needs the DOM to exist, needs to run in a predictable order relative to other files, and must not delay the first frame. defer gives all three. async gives up order. Classic gives up the first frame. Putting a classic script at the end of <body> — the old advice — is strictly worse than defer in the head, because the head version starts downloading much earlier while still executing late. 

<!-- in the head: downloads early, runs late, keeps order -->
<script src="{{ 'vendor.js' | asset_url }}" defer></script>
<script src="{{ 'theme.js'  | asset_url }}" defer></script>
<!-- vendor.js is guaranteed to run before theme.js -->

One consequence to keep in mind: defer scripts run before DOMContentLoaded fires. So a defer script that itself waits for DOMContentLoaded still works — the event has not happened yet. That is a common worry and it is unfounded.

4. Explain it back Feynman check

Part 1 · Plain words — no jargon at all

The browser reads your page from top to bottom, building it as it goes. When it hits a piece of code, it has to stop reading — because that code is allowed to write new page content right there, and the browser cannot read and be rewritten at the same time. So it waits, fetches the code, runs it, and only then carries on reading. Unless you add a word that promises the code will not do that. Then the browser fetches it in the background and reads on.

Part 2 · One analogy, and where the analogy breaks

The analogy. Reading a recipe aloud to someone cooking. At step 5 the recipe says "call the author and ask what to do next; they may add a step here". You must stop reading, make the call, hear the answer, and only then continue — because the answer might change step 6. defer is the author promising in advance: "my note only matters at the end, keep reading".

Where it breaks. A reader could skim ahead while on the phone, and in fact the browser does — the preload scanner runs ahead and starts fetching things it spots. But that skim only finds addresses written plainly in the page. Anything a script builds at runtime is invisible to it, so the skim cannot save you from work you hid.

Part 3 · The sticking point

People treat async as "the fast one" and defer as "the slow one". Wrong axis. Both download at the same time; they differ in when they run and whether order holds. async is a race, and a race is the wrong shape for code with dependencies. The second sticking point: thinking a classic script at the bottom of <body> is equivalent to defer. It is not — it starts its download much later, so it finishes later, for exactly the same benefit.

Part 4 · Teach it back to me

Two or three sentences reviewing a teammate's pull request that adds async to the theme's main script "because it is faster". Say what will break, why it will break intermittently, and what to write instead. Then send it to me — this is ability #5, and "intermittently" is the word I am looking for.

5. Point at it: see the stall and the order gate #3

  1. The stall, in one picture. DevTools → Performance → record a reload of any storefront. Find the long Parse HTML block on the Main track and look for Evaluate Script entries nested inside it. A script running inside the parse block is a parser-blocking script, drawn as such.
  2. Who blocks whom. Network → enable the Waterfall column and hover a script's bar. Read Queueing and Stalled: a classic script found late shows a long queue; a defer script found early shows an early start and a late effect.
  3. Order, proven. Add console.log to two defer scripts and reload ten times: the order never changes. Switch both to async and reload ten times with throttling on: the order changes. Watching it flip is gate #3 for this core, and it is also the argument you will use in code review.
  4. Audit the theme you actually ship. Run document.querySelectorAll('script[src]:not([defer]):not([async])') in the Console of a real storefront and read the list. Every entry is a full stop in the parse. Most of them will not be yours.
Work drill — do this on a real theme

A client's theme.liquid head has, in order: a classic vendor.js (140 KB), {{ 'theme.js' | asset_url | script_tag }}, an async analytics tag, and a chat widget script with no attributes. The product page's slider "sometimes does not initialise on mobile, maybe one load in ten".

Before flipping the recall cards: say which tags delay the DOM, then explain the one-in-ten slider failure — being precise about which mode causes an intermittent failure and why the odds change on mobile. Then the interviewer's follow-up: you cannot edit the chat widget's tag because an app injects it. What are your options, and what does each cost?

6. Live coding session

Type it, predict it, break it

Create three files. First, two tiny scripts, typed by hand:

// a.js
console.log('A ran', Math.round(performance.now()),
  'body children:', document.body ? document.body.children.length : 'no body');

// b.js  (same two lines, with B)

Then the page:

<!doctype html>
<script src="a.js"></script>
<script src="b.js"></script>
<body>
  <p>one</p><p>two</p><p>three</p>
</body>

Predict before running: what does each script report for body children? Serve it with python3 -m http.server and check. Both say "no body" — they ran before the body existed, because they blocked the parser at the point they appear.

Now add defer to both and predict the two numbers before reloading. Both report 3: parsing finished first. Same files, same order, completely different world.

Now make the order break. Switch both to async, set Network throttling to Slow 4G, and reload eight or nine times, watching the console order.

<script src="a.js" async></script>
<script src="b.js" async></script>

Predict first: will B ever print before A? Make b.js much smaller than a.js to load the dice, and you will see it flip. You have just reproduced an intermittent bug on purpose — the most valuable thing in this session, because it is the failure you will be asked to explain one day with no reproduction steps.

Remember this
  • A classic script must stop the parser because it may write markup at its own position. Everything else is a promise not to.
  • defer: parallel download, runs after parsing, in document order, before DOMContentLoaded. The right default.
  • async: parallel download, runs the moment it arrives, order is a race. Correct only for code with no dependencies in either direction.
  • type="module": deferred by default, plus its own import graph. Adding async makes it behave like async.
  • The preload scanner reads ahead while the parser is blocked — which is why parallel downloads happen, and why URLs built by JavaScript are slow.
  • Liquid's script_tag filter emits a blocking script. Write the tag by hand with defer.
  • A classic script at the end of <body> is worse than defer in the head: same late execution, much later download.

If you remember one thing: defer and async both download early — they differ in whether order survives.
