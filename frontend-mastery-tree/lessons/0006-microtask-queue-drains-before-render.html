Stratum 1 · Language & Runtime · Event loop · Lesson 0006

The microtask queue drains to empty before render

Lesson 0005 gave the browser one queue and one rule. That is not enough to make promises safe — so there is a second queue with a much stronger rule. Almost every "await should have let it paint" bug lives in the gap between them.

core Domain expertise: moves ability #2 (predict an unseen case) and ability #5 (judge someone else's work) — this is the mechanism that decides whether a code review comment about await is right or wrong.

The win: after ~35 minutes you can order any mix of synchronous code, setTimeout, .then and await with no doubt, and you can explain why a loading spinner added right before await sometimes never appears on screen.

1. Why one queue was not enough

A promise chain is meant to read as one logical operation: fetch(…).then(parse).then(render). Ask the question this lesson exists to answer: what if each .then step were an ordinary task?

Then a click, a timer, and a frame could all run between two steps of your chain. The user could see the page painted after parse but before render — a half-finished operation, on screen, in front of a customer. That is exactly the failure that run-to-completion was invented to prevent, leaking back in through the side door.

So the platform adds a second queue with a stronger promise. After the current task ends, the loop performs a microtask checkpoint: it runs microtasks until the queue is empty — including microtasks queued by those microtasks — and only then may it render or take the next task (MDN — Microtask guide, HTML Standard § event loops).

2. The canonical ordering question

Every senior interview in this branch asks a version of this. Read it, cover the answer, and predict: 

console.log('script start');
setTimeout(() => console.log('setTimeout'), 0);
Promise.resolve()
  .then(() => console.log('promise 1'))
  .then(() => console.log('promise 2'));
console.log('script end');
script start
script end
promise 1
promise 2
setTimeout

Derive it, do not memorise it. The script is one task, so both synchronous lines print first. The stack empties, so the checkpoint runs: promise 1 runs, and its .then queues promise 2 as a new microtask — which the checkpoint must also drain, because it drains to empty. Only then is the timer's task eligible. Change nothing about the code and the order can never change; this is not a race.

3. await is a microtask, and that is the bug

An await splits a function in two. Everything after it becomes a continuation that is queued as a microtask when the awaited promise settles. So: 

btn.classList.add('is-loading');   // DOM changed — not painted yet
await Promise.resolve();           // yields to the MICROTASK queue only
filterNineHundredProducts();       // runs in the same turn, still before any paint
btn.classList.remove('is-loading');

The spinner never appears. Not "sometimes" — never. The class was added, then the continuation ran, then the class was removed, and the render box in the diagram was reached only after all of it. The user's screen never held the loading state for a single frame.

Trap — the one that gets past code review "I added await so the browser can breathe" is wrong when you await an already-settled promise. Awaiting a real fetch does let a frame in, because the continuation cannot run until the network task arrives — the turn genuinely ends. To yield on purpose you must reach the task queue: await new Promise(r => setTimeout(r, 0)), or scheduler.yield() where it exists, or two nested requestAnimationFrame calls if what you need is "after the next paint".

4. The failure mode this queue creates

A stronger rule buys a stronger failure. A long task delays the next frame; an endless microtask chain never lets a frame happen at all: 

function spin() { queueMicrotask(spin); }
spin();   // the checkpoint can never reach "empty"

The tab is now unrecoverable, and the Performance panel shows no long task to blame — because from the loop's point of view the checkpoint simply has not finished. That is microtask starvation, its own core in the depth queue. Knowing it exists is enough today; the point is that "drains to empty" is a promise the platform keeps even when it is fatal.

5. Explain it back Feynman check

Part 1 · Plain words — no jargon at all

The worker takes one job from the main line and finishes it. Before it is allowed to look up at the shop again, it must clear a small tray of follow-up notes on its desk — and if clearing a note creates another note, that one goes in the same tray and must be cleared too. Only when the tray is completely empty does the worker look up, update the display board, and call the next customer. Anything you write while the tray is being cleared is not on the board yet. Nobody outside can see it.

Part 2 · One analogy, and where the analogy breaks

The analogy. Sending an email. The main line is your inbox — one message at a time. The tray is the set of "before I send this, also do X" notes attached to the message you are already handling. You finish all of them before the message goes out, so nobody ever receives a half-written email.

Where it breaks. With email you could always give up and send it half done. Here you cannot: the tray must reach empty, and a note is allowed to add another note forever. That is not a bug in the analogy, it is a real property with a real consequence — an endless chain of notes freezes the shop with no long task to point at.

Part 3 · The sticking point

The mistake is treating await and setTimeout as two flavours of "later". They are different queues with different rules, and only one of them permits a paint. Say it precisely: a microtask runs before the next frame; a task runs after it. The second sticking point is thinking the drain is "just the microtasks that were already there". It is not — anything queued during the drain joins the same drain. That is why promise 2 beats setTimeout even though setTimeout was queued first.

Part 4 · Teach it back to me

Two or three sentences to a teammate who wrote "I added await Promise.resolve() before the heavy loop so the spinner shows" in a pull request. Explain why the spinner still will not show, and what to write instead — without using the words "microtask" or "macrotask" until you have defined them in plain words. Then send it to me. This is ability #5 in one paragraph: judging someone else's work in mechanism terms.

6. Point at it: prove the ordering in two places gate #3

  1. Console, 20 seconds. Paste the section-2 snippet. The output order is fixed, every time, on every machine — a determinism you can lean on in an interview.
  2. Performance panel. Record while running a promise chain. Inside a single Task bar you will find a child entry named Run Microtasks. Read what that nesting is telling you: the microtasks are inside the task's own bar, not after it — the drain is part of the same turn.
  3. The paint test. Run this in the Console of any page: document.body.style.background='red'; await Promise.resolve(); const e=Date.now()+1500; while(Date.now()<e){}; document.body.style.background=''; — predict first, then run. You should never see red. Now replace await Promise.resolve() with await new Promise(r => setTimeout(r, 0)) and run again: red for a second and a half. Same code shape, different queue, visible difference. That is gate #3 for this core.
Work drill — do this on a real theme

A theme's "Add to cart" button does: add the class is-loading, await a helper that resolves immediately from a client-side cache, rebuild the cart drawer HTML for 400 ms of synchronous work, then remove the class. QC's ticket: "no loading state on repeat adds, but it works the first time".

Before flipping the recall cards: explain why the first add shows the spinner and the repeat add does not — the code path is identical. Then the interviewer's follow-up: give the smallest change that makes the spinner appear in both cases, and say what you would measure afterwards to prove it worked.

7. Live coding session

Type it, predict it, break it

Open a scratch file. Type it by hand, and write your predicted output on paper before running:

console.log('1');
setTimeout(() => console.log('2'), 0);
queueMicrotask(() => {
  console.log('3');
  queueMicrotask(() => console.log('4'));
});
Promise.resolve().then(() => console.log('5'));
console.log('6');

The answer is 1 6 3 5 4 2. If you got the 4 before the 2, you have the "drains to empty" rule. If you put 4 after 2, re-read section 1 before continuing.

Now the await version of the same idea:

async function run() {
  console.log('a');
  await null;                // awaiting a non-promise still queues a microtask
  console.log('b');
}
run();
console.log('c');

Predict, then run: a c b. Everything after await is a continuation, and a continuation is a microtask — even when there was nothing real to wait for.

Break it in the way that matters visually. On any page, in a scratch file loaded in the browser:

const box = document.body;
box.style.outline = '8px solid red';
await Promise.resolve();              // wrong queue
const end = Date.now() + 1200;
while (Date.now() < end) {}
box.style.outline = '';

Predict: do you see red? Run it. Then change one line to await new Promise(r => setTimeout(r, 0)); and run again. Watching the red appear the second time is the moment this lesson stops being theory.

Remember this
  • Two queues, two rules: one task per turn, but all microtasks, until the queue is empty.
  • A microtask queued during the drain joins the same drain. A task queued during a task waits for a later turn.
  • The checkpoint happens before the render step, so nothing done in a microtask is on screen yet.
  • Microtask sources: .then/.catch/.finally, every await continuation, queueMicrotask, MutationObserver.
  • await on an already-settled value does not let the browser paint. To yield, reach the task queue: await new Promise(r => setTimeout(r, 0)).
  • An endless microtask chain freezes the tab with no long task to blame — a stronger rule buys a nastier failure.

If you remember one thing: a microtask runs before the next frame, a task runs after it — so only a task lets the user see anything.
