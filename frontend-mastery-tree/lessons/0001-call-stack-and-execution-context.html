The call stack & execution context

Before anything renders, fetches, or reacts, one machine runs your code one call at a time. This is that machine.

The win: after ~30 minutes you can read any stack trace — in an interview or in a broken Shopify theme — and say exactly what the engine was doing at that moment, and why.

1. What the engine creates when a function runs

Every time JavaScript starts running a piece of code — the whole script, or one function call — the engine creates an execution context. Plain words: a small record that tracks one running call. Per the MDN execution model, that record holds three things you should be able to name cold:

  • Where it is in the code — the exact statement being evaluated, so the engine can resume there after a nested call returns.
  • Its variables — the arguments and local variables of this particular call (the spec calls this the variable bindings; we will meet its full form, the lexical environment, in the next lesson).
  • Its this value — set at the call site (its own lesson later in this branch).

The formal definition lives in the spec: ECMA-262 § Execution Contexts. You do not need to memorize the spec fields — you need the model: one call = one context. Call the same function three times, you get three separate contexts, each with its own variables. This one fact is why recursion works at all.

2. The stack: contexts pile up, last in, first out

Contexts live on the call stack. Calling a function pushes a new context on top; return (or reaching the end) pops it off, and the engine resumes the context underneath, exactly where it left off. Watch a cart-money helper run: 

function penny(price) {
  return Math.round(price * 100);   // cents as an integer — no float drift
}
function lineTotal(price, qty) {
  return penny(price) * qty;
}
const total = lineTotal(4.99, 3);   // → 1497

The key discipline: at t3, lineTotal is not gone — it is paused, its context still holding price, qty, and the exact spot to resume (… * qty). That "resume exactly where it stopped" behavior is the whole reason the record exists.

3. One stack, one thread — and the two ways it fails

JavaScript has one call stack per agent (per tab, roughly — MDN). Two consequences:

  • Blocking. While any context is on the stack, nothing else runs — no clicks, no rendering. A slow synchronous loop in a theme's theme.js freezes the whole storefront until the stack empties. (How the browser schedules work around this is the event loop — two lessons ahead.)
  • Stack overflow. The stack has a size limit. A function that keeps calling itself with no exit condition pushes contexts until the engine throws RangeError: Maximum call stack size exceeded.
Trap A stack overflow (too many nested calls — a stack problem) is not an out-of-memory error (too much data alive — a heap problem, Memory branch, three lessons of its own). Interviewers love this distinction; keep the two failure stories separate.

4. Point at it: the stack in DevTools gate #3

A stack trace is just a photo of the call stack at the moment something threw. Two places to see the real thing today:

  1. Paused, live: DevTools → Sources → set a breakpoint inside any function (or type debugger;) → trigger it. The Call Stack pane on the right is this lesson's diagram, live: top entry = running context, entries below = paused callers. Click a lower frame — you can inspect that call's variables, because its context is still alive on the stack.
  2. Post-mortem: any red console error. Read it top-down: line 1 is where it threw, each line below is the caller that was paused, all the way to the stack floor.

Remember this
  • One function call = one execution context: where it is in the code, its own variables, its this.
  • Contexts live on the call stack: push on call, pop on return — last in, first out.
  • A caller is not gone while a callee runs — it is paused, and resumes exactly where it stopped.
  • One stack per tab: while anything is on it, nothing else runs — no clicks, no paint.
  • Unbounded recursion → RangeError: Maximum call stack size exceeded; a repeating pair of names in the trace is the loop.
  • A stack trace is a photo of the stack at throw time; DevTools' Call Stack pane is the live version.

If you remember one thing: the stack is a pile of paused calls — the top one runs, every one below is waiting to resume where it stopped.
