Closures — captured environment, not copied values

Lesson 0001 said a frame is thrown away when a function returns. Lesson 0002 said a function's box has an arrow to the box around it. Those two rules cannot both be true — and the way the engine resolves the conflict is the closure.

core Domain expertise: moves ability #1 (explain from first principles) and ability #3 (say what the design gives up) — a closure is not a feature that was added, it is a consequence you can derive.

The win: after ~35 minutes you can derive closures instead of remembering them, predict whether two functions share one variable or get one each, and name the exact price the language pays for this — the price you will meet again as a memory leak in lesson 0009.

1. The contradiction that forces closures to exist

Two rules we already accepted, in order:

  • From 0001: when a function returns, its frame is popped off the call stack. Gone.
  • From 0002: a function's lexical environment holds an arrow to the environment that surrounded it in the source — fixed at creation, never changed.

Now write four lines that put the two rules against each other: 

function makeCounter() {
  let count = 0;                       // lives in makeCounter's box
  return function inc() { return ++count; };
}
const next = makeCounter();            // makeCounter has RETURNED
console.log(next(), next());           // → 1 2

makeCounter has returned. Rule one says its frame is gone. But inc's arrow points at makeCounter's box, and inc is still alive in next. So either the arrow now points at nothing — and next() should crash — or the box outlived the frame. It printed 1 2, so the box outlived the frame. There is no third option.

The engine can do this because the frame and the box are not the same thing and do not live in the same place. Frames live on the stack, sized and freed in strict order. Environments live on the heap, freed only when nothing can reach them any more (that reachability rule is its own core, lesson 0009). A returned function is something that can reach its box. So the box is kept.

Say it this way

A closure is not a feature someone added to JavaScript. It is what you are left with when lexical arrows and heap reachability are both true at the same time.

2. Captured means shared, not copied

This is the sentence in the lesson title, and it is where most wrong answers come from. inc does not hold the number 0. It holds the arrow to the box. Every read of count walks that arrow and reads whatever is in the box right now. So two functions created in the same box are talking about the same variable: 

function makeCounter() {
  let count = 0;
  return {
    inc: () => ++count,
    dec: () => --count,
    read: () => count
  };
}
const c = makeCounter();
c.inc(); c.inc(); c.dec();
console.log(c.read());   // → 1

Three separate functions, one box, one count. If capture were a copy, each would have its own 0 and read() would print 0 forever. Per MDN — Closures, the function keeps a reference to its lexical environment, not a snapshot of its values.

3. One box per call — which is why counters are independent

A new box is created every time the outer function runs, not every time it is written. So: 

const a = makeCounter();
const b = makeCounter();
a.inc(); a.inc();
console.log(a.read(), b.read());   // → 2 0

Two calls, two boxes, two independent count variables. This single rule — one box per execution, shared by everything created inside that execution — answers both classic puzzles:

Code shapeHow many boxesResult
for (var i …) + 3 callbacksone — var binds to the whole functionall three read the same i, already 3
for (let i …) + 3 callbacksthree — a fresh block box per iterationeach callback reads its own i: 0 1 2
makeCounter() called twicetwo — one per callindependent counters

Lesson 0002 already showed the var/let loop. Nothing new was needed to explain it — that is the sign the model is right.

4. What the design gives up

Every mechanism trades something away, and being able to name the trade is what separates a senior answer from a correct one. Closures buy you private state with no classes and no ceremony. The price:

  • Memory you did not ask for. As long as the function is reachable, its whole box is reachable. Attach a handler that closes over a big object, never remove the handler, and that object stays for the life of the page. This is the leak shape in lesson 0009 — and it is the same rule, not a new one.
  • Surprise sharing. Two functions in one box look independent in the source and are not. Bugs of the form "why did the second card's button change the first card's total" are almost always one box where you assumed two.
  • Harder to reason about later. The state is invisible: there is no property to log. You have to know which box a function came from.
One engine detail — a bare fact, not a derivation V8 does not necessarily keep every variable of the outer function alive: it allocates a context object for the bindings the inner functions actually reference. So an unused huge array in the outer scope may be collected. Treat this as an optimisation you can observe in a heap snapshot, never as a guarantee to design around — the spec promises you the whole environment. Check it in DevTools rather than trusting either of us: Fix memory problems.

5. Explain it back Feynman check

Part 1 · Plain words — no jargon at all

A function is born inside a box of names. When the function is passed somewhere else and used later, it still knows its box. Not a photocopy of the box — the box itself. So if anything changes a name in that box, the function sees the new value, because it looks in the box every time. And the box cannot be thrown away while the function is still around, because the function would have nowhere to look.

Part 2 · One analogy, and where the analogy breaks

The analogy. A shared kitchen notebook. Two cooks were trained in the same kitchen and both know where the notebook is kept. One writes "salt: 2" in it; the other reads "2". They are not carrying copies — they walk to the same notebook. A new kitchen, opened later, gets its own notebook, and cooks trained there cannot see the first one.

Where it breaks. A cook can decide to stop using the notebook, and the notebook can be thrown out. Here it is the other way round: the notebook is thrown out only when the last cook who knows about it is gone, and the cook has no way to let go of it. You do not choose to keep the box; keeping the function keeps the box. That reversal is the whole memory story of lesson 0009.

Part 3 · The sticking point

The wrong mental model is "the function remembers the value it saw when it was created". People say this with confidence and then cannot explain why var in a loop prints 3, 3, 3. The right model is "the function remembers where to look". Test yourself with one question: if capture were a copy, could two arrow functions in the same box ever disagree about count? No — and they never do, because there is one box. Second sticking point: a box is made per call, not per function-definition-in-the-source.

Part 4 · Teach it back to me

Two or three sentences to a junior who asks: "I made two counters with the same factory function. Why don't they share the number, when you told me closures share things?" You must use the word "call" and you must not use the word "instance". Then send it to me — the gap I am looking for is whether you separate one box per call from one box shared inside a call.

6. Point at it: the Closure scope in DevTools gate #3

You never have to believe any of this. Chrome names it on screen:

  1. Paste the makeCounter code into the Console, then run const c = makeCounter().
  2. DevTools → Sources → set a breakpoint inside inc → call c.inc().
  3. The Scope pane shows Local, then an entry literally labelled Closure (makeCounter) holding count. That entry is box #1 from the diagram — still in the heap, long after the frame was popped. Expand it and watch count change as you call c.inc() again.
  4. Now the memory side: Memory panel → Heap snapshot → search for the string in your closed-over data. The Retainers section names the function that is holding it. That is the leak-hunting move you will use for real in lesson 0009.
Work drill — do this on a real theme

A product grid renders 24 cards. The theme's quantity-stepper.js loops over the cards, and inside the loop it does var input = card.querySelector('.qty'); and then attaches a click handler that reads input.value. QC reports that the plus button on every card changes the quantity of the last card only.

Before flipping the recall cards: how many boxes exist here, which one do all 24 handlers point at, and what is the smallest one-word change that fixes it? Second question, the one an interviewer will ask next: after the fix, how many boxes are alive, and what does each one keep in memory?

7. Live coding session

Type it, predict it, break it

Open a scratch file. Type this by hand — do not copy-paste, the typing is part of the exercise:

function makeCounter() {
  let count = 0;
  return {
    inc: () => ++count,
    read: () => count
  };
}
const a = makeCounter();
const b = makeCounter();
a.inc(); a.inc(); b.inc();
console.log(a.read(), b.read());

Predict on paper first: two numbers, in order. Then run it.

Now break it on purpose — move count out of the function, one line up:

let count = 0;                // now in the global box, not per call
function makeCounter() {
  return { inc: () => ++count, read: () => count };
}

Predict again before running: what do the two numbers become, and why? Then run it. You have just converted "one box per call" into "one box for the whole program" by moving a single line — that is the entire mechanism, demonstrated in one edit.

Third round, the memory one. Replace the counter's body with something big and watch it survive:

function hold() {
  const big = new Array(1e6).fill('x');   // ~ a few MB
  return () => big.length;                // the arrow keeps `big` reachable
}
window.keep = hold();                     // now nothing can free it

Take a heap snapshot, then run window.keep = null, force garbage collection (the bin icon), take a second snapshot, and compare. You have just watched a closure hold and release a few megabytes on purpose.

8. Prove it

The gate — only now touch the tracker Open the tree tracker and mark closures — captured environment, not copied values done only if all three held, from memory: (1) you explained, in plain English with no jargon, why a returned function can still read the outer variable — the teach-back in section 5; (2) you predicted 2 0 and then the broken version's output before running either; (3) you saw the Closure (makeCounter) entry in the Scope pane with your own eyes. Two out of three is zero out of three.

Remember this
  • A closure = a function plus the lexical environment (box) it was created in. Not a feature — a consequence of lexical arrows + heap reachability.
  • Frames live on the stack and are popped on return; environments live on the heap and survive while anything can reach them.
  • Captured means shared, not copied. The function holds the arrow, so it always reads the current value.
  • One box per call. Two calls to the same factory give two independent boxes; everything created inside one call shares that one box.
  • The price: keeping the function keeps the whole box — that is the memory-leak shape in lesson 0009, not a separate rule.
  • DevTools names it out loud: the Scope pane's Closure (fnName) entry is the surviving box.

If you remember one thing: a closure remembers where to look, never what it saw.
