Cascade, specificity, inheritance & layers

Many rules match one element and set the same property. Exactly one wins. Almost everyone believes specificity decides that — specificity is step four of five, and the steps above it are the ones that decide real arguments.

core Domain expertise: moves ability #2 (predict an unseen case) and ability #5 (judge someone else's work) — this is the mechanism behind every !important in a theme, and behind whether adding one is right.

The win: after ~35 minutes you can look at two conflicting rules and name the winner and the step that decided it, in one sentence — and you can say why adding !important to beat an app's CSS is sometimes the correct engineering answer and sometimes debt.

1. Why a total ordering has to exist

An element has one computed value per property. Two rules that both say color cannot both apply. So the engine needs a rule that always produces exactly one winner — no ties, no "it depends", no randomness, or the same page would render differently twice.

That is what the cascade is: a sequence of tie-breakers applied in a fixed order, ending in one that can never tie. Per MDN — CSS cascade and CSS Cascade 5:

2. Specificity is three numbers, not one

Specificity is a triple: (ids, classes/attributes/pseudo-classes, types/pseudo-elements), compared left to right like a version number. The columns do not carry:

SelectorSpecificityBeats
#cart1-0-0everything below
.drawer.is-open0-2-0.drawer, and any number of types
.drawer0-1-0ul li a span b i (0-0-6) — eleven types would still lose
a:hover0-1-1a
[data-open="true"]0-1-0same weight as a class
:where(.a, #b)0-0-0nothing — always loses on step 4
:is(.a, #b)1-0-0takes its most specific argument
* , :root vs html0-0-0 / 0-1-0 / 0-0-1:root is a pseudo-class, so it outranks html

A style attribute (style="color:red") is not part of this triple at all — it is handled earlier, and only an !important declaration can beat it.

Trap — what !important really is !important does not make a rule "more specific". It moves the declaration into a different bucket at step 1, which is checked before layers and long before specificity. That is why a single .btn { color: red !important } beats #page #main .btn.primary. And when two !important author declarations collide, you are back to steps 3, 4 and 5 between them — which is how an !important arms race starts.

3. Layers, and the trap that matters for app CSS

@layer gives you step 3: an explicit ordering that beats specificity entirely. Declare the order once and a later layer wins no matter how weak its selectors are: 

@layer reset, theme, sections, utilities;

@layer sections { .card .title { font-size: 1rem } }   // 0-2-0
@layer utilities { .text-lg { font-size: 2rem } }      // 0-1-0, and it WINS

Two rules about layers you must be able to state, because they decide whether layering a theme is safe:

  • Unlayered normal declarations beat every layer. Anything outside a layer is treated as the last, strongest layer. So if you move your theme CSS into layers and an app injects unlayered CSS, the app now wins by default — the opposite of what people expect when they reach for layers.
  • For !important, layer order is reversed. An !important declaration in an earlier layer beats one in a later layer. That is deliberate: it lets a base layer defend a rule it truly must keep.

4. Inheritance is a different mechanism

The cascade only runs where a declaration exists for that element and property. When nothing matched, inheritance asks the parent — but only for inherited properties (color, font-*, line-height, visibility). Non-inherited ones (display, padding, border, background) fall back to their initial value instead.

So "why is my heading blue when I never set it" is a cascade question, and "why is my heading blue when nothing matches it" is an inheritance question. Different mechanism, different place to look. The four keywords let you steer it: inherit (take the parent's), initial (the property's spec default), unset (inherit if inherited, else initial), revert (go back to what the previous origin said, usually the browser's own stylesheet).

5. Explain it back Feynman check

Part 1 · Plain words — no jargon at all

Several style rules can want to set the same thing on the same element, and only one can win. So the browser runs down a fixed checklist of questions and stops at the first one that separates them: did anyone mark theirs as urgent? · which group was declared to matter more? · which selector is more precise? · which was written last? The last question can never tie, so there is always exactly one winner. Most people only know the "more precise" question, which is why they argue about the wrong thing.

Part 2 · One analogy, and where the analogy breaks

The analogy. A dress code with a chain of authority. A legally required rule beats the company handbook, which beats your team's convention, which beats "whatever the last email said". You do not compare the wording of two rules until you know they came from the same level.

Where it breaks. In a real organisation, a very detailed team rule can sometimes override a vague company one. Here it never can: a weak rule in a stronger bucket beats an extremely precise rule in a weaker one, always. And one twist no organisation has — for urgent rules the group order runs backwards, so the base group defends itself against the ones above it.

Part 3 · The sticking point

Two, and both cost real hours. First: treating specificity as a single number. It is three numbers compared left to right, so one class beats any number of element selectors — 0-1-0 versus 0-0-11 is not close. Second: believing !important is "very specific". It is a different step, checked earlier, which is exactly why it wins so easily and why two of them collapse back into an ordinary specificity fight. If you can say "different bucket, not bigger number" you will never mis-diagnose one again.

Part 4 · Teach it back to me

Two or three sentences reviewing a pull request that adds !important to five theme rules to beat a review app's stylesheet. Say what the author actually did in cascade terms, when that is the right call, and what will happen in six months. Then send it to me — I am looking for you to defend !important as a legitimate tool and name its cost, rather than calling it bad practice.

6. Point at it: the Styles pane is the cascade gate #3

  1. Read the winner. DevTools → Elements → select a node. The Styles pane lists every matching rule in cascade order, strongest at the top, with losing declarations struck through. Hover a struck declaration and DevTools tells you what beat it.
  2. Find the true source. The Computed tab shows the final value per property; expand one and it names the exact rule and file that won. This is the fastest way to answer "where is this coming from" in a theme with app CSS in it.
  3. See inheritance separately. Scroll to the bottom of the Styles pane: the Inherited from sections are a different mechanism, not more matching rules. Notice that only inherited properties appear there.
  4. Prove the layer rule yourself. In the Styles pane, layered rules are grouped under their @layer name. Add an unlayered rule with a weaker selector and watch it win — the surprising half of section 3, in front of you. That is gate #3 for this core.
Work drill — do this on a real theme

A product page's Add to cart button must be #1F6C8C. The theme sets .product-form .btn { background: #1F6C8C }. A subscriptions app injects <style>.btn { background: #333 !important }</style> late in the body. A previous developer "fixed" it with #MainContent .product-form .btn { background: #1F6C8C }, which did not work, and then with inline style="background:#1F6C8C" on the Liquid element, which did.

Before flipping the recall cards: explain, step by step, why the very specific selector lost and why the inline style also lost until — actually check this — did it? State what happens between an inline style and an !important app rule, and give the fix you would ship. Then the interviewer's follow-up: how would you make this class of conflict cheap to fix for the next twenty tickets, and what does your approach give up?

7. Live coding session

Type it, predict it, break it

One HTML file, typed by hand. Predict the colour after each block before you reload.

<!doctype html>
<style>
  ul li a span      { color: green }   /* 0-0-4 */
  .label            { color: red }     /* 0-1-0 */
</style>
<ul><li><a href="#"><span class="label">Which colour?</span></a></li></ul>

Red. Four element selectors cannot out-vote one class, because the columns never carry.

Round two — the buckets. Add this and predict again:

  #page .label    { color: blue }               /* 1-1-0 */
  span            { color: orange !important }  /* 0-0-1, different bucket */

Orange. Say the reason out loud before you reload: importance is step 1, specificity is step 4.

Round three — layers, including the surprise. Predict all three states:

@layer base, overrides;
@layer base      { .label { color: teal } }
@layer overrides { span   { color: purple } }   /* weaker selector, later layer → wins */
.label { color: black }                          /* UNLAYERED → beats both layers */

Then break it the way an app would: put the unlayered rule in a second <style> block with a deliberately weak selector, and confirm it still wins over your carefully layered theme. That is the exact reason layering a Shopify theme needs a decision, not a habit.

Round four — inheritance versus cascade. Predict what each child shows:

<div style="color: crimson; padding: 20px">
  <p>inherits colour?</p>
  <p style="color: inherit">same thing, explicitly</p>
  <p style="padding: inherit">inherits padding?</p>
</div>

Colour inherits with no help. Padding does not inherit by default but can be told to. Seeing those two behave differently is the whole point of section 4.

Remember this
  • Five ordered steps: origin & importance → context → layer order → specificity → order of appearance. The first step that separates two rules decides.
  • Specificity is three numbers compared left to right. One class (0-1-0) beats any number of element selectors.
  • !important is a different bucket at step 1, not a bigger number. Two of them fall back to steps 3–5 between themselves.
  • Unlayered normal declarations beat every layer — so layering your theme hands the win to unlayered app CSS.
  • For !important, layer order reverses: an earlier layer wins.
  • Inheritance is not the cascade. It only fills in where nothing matched, and only for inherited properties.
  • :where() is 0-0-0; :is() takes its most specific argument. Use them to choose your own weight.

If you remember one thing: find out which step separates the two rules before you touch either selector.
