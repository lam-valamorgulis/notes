Stratum 2 · Rendering Pipeline · Frame budget · Lesson 0015

The 16.67 ms frame budget

Every lesson in Chapter 2 has described work. This one gives that work a deadline — and the deadline is set by hardware, not by the browser, so it is not negotiable.

core Domain expertise: moves ability #2 (predict an unseen case) and ability #3 (say what the design gives up) — a budget turns "this feels janky" into arithmetic you can do before writing the code.

The win: after ~35 minutes you can say how much time a smooth animation actually has, name every piece of work competing for it, place requestAnimationFrame in the frame exactly, and calculate how many frames a 300 ms task destroys.

1. Where the number comes from

A 60 Hz screen refreshes 60 times per second. One second divided by 60 is 16.67 ms. To show something new at a refresh, every piece of work for that frame must be finished before it. Miss it, and the screen shows the previous frame again — a dropped frame, which the eye reads as a stutter.

So the real rule is not "16.67 ms". It is one refresh interval. A 120 Hz phone gives you 8.3 ms; a 90 Hz tablet 11.1 ms. Quoting 16.67 as a law rather than as the 60 Hz case is a small tell in an interview.

And you do not get all of it. The browser needs part of the interval for its own bookkeeping and for compositing, so the practical guidance is to keep your work — script plus the style and layout it causes — near 10 ms. Everything below is how that 10 ms gets spent.

2. What happens inside one frame, in order

The browser's per-frame sequence — the spec calls it "update the rendering" — is worth knowing precisely, because where your callback sits decides whether your work lands in this frame or the next:

  1. Run one task (lesson 0005), then drain microtasks (lesson 0006).
  2. Handle pending input events.
  3. Run requestAnimationFrame callbacks — just before style and layout.
  4. Recalculate style, then layout.
  5. Deliver ResizeObserver and IntersectionObserver records (after layout, which is exactly why they cost you no forced layout — lesson 0014).
  6. Paint, then composite.
  7. If time is left over, run requestIdleCallback callbacks.
CallbackRunsUse it for
requestAnimationFrameonce per frame, before style/layoutvisual writes, per-frame animation steps
setTimeout(fn, 0)a task, whenever the loop gets to ityielding, not animating — it has no relationship to the frame
requestIdleCallbackleftover time, may be skipped for many framesnon-visual, non-urgent work: analytics, prefetch, cleanup
ResizeObserver / IntersectionObserverafter layout, before paintreading geometry for free
Trap — requestAnimationFrame is not a speed-up Putting slow work inside rAF does not make it fit the budget; it guarantees the work lands inside the frame, where it now delays style, layout and paint directly. rAF is for scheduling visual writes at the right moment, and for throttling scroll or resize handlers to at most one run per frame. If the work itself is 8 ms, rAF just makes it 8 ms of your 10.

4. Explain it back Feynman check

Part 1 · Plain words — no jargon at all

The screen redraws itself about sixty times a second, on a fixed rhythm nobody can change. For each redraw the browser must have a finished picture ready in time — about sixteen thousandths of a second. If it is not ready, the screen simply shows the old picture again, and the movement looks broken. So all the work for one step of an animation has to fit inside that gap: reacting to the finger, running your code, working out positions, colouring in, and sticking it together.

Part 2 · One analogy, and where the analogy breaks

The analogy. A hand-drawn flip-book being filmed at a fixed rate. The camera clicks every sixteen milliseconds whether or not your next page is drawn. Miss it and the camera photographs the previous page twice — the motion jerks. You cannot ask the camera to wait.

Where it breaks. A flip-book artist can draw ahead and build a buffer. The browser mostly cannot: the next frame usually depends on state that only exists now — the current scroll position, the finger's position, the latest data. The one real exception is a composited animation, where the compositor can keep moving an already-drawn page without you. That exception is why transform is not just a preference.

Part 3 · The sticking point

People treat requestAnimationFrame as a performance fix. It is a timing tool. It says "run this at the right point in the frame", not "make this cheap" — and code inside it is competing for the same 10 ms as everything else, now with less room to recover. The second sticking point: quoting 16.67 ms as if it were a law of the web. It is the 60 Hz case. The real statement is "one refresh interval", and plenty of phones refresh faster than that, which makes the budget smaller, not larger.

Part 4 · Teach it back to me

Two or three sentences to a designer who asks for a scroll-linked animation that fades and moves twelve elements at once. Explain the budget in everyday words, say which version of their idea fits and which does not, and offer the compromise. No jargon: not "composite", not "frame budget", until you have said it plainly. Then send it to me — the skill here is saying "yes, with this constraint" rather than "no".

5. Point at it: read the frames track gate #3

  1. Live, in one number. DevTools → Command Menu → "Show Rendering" → Frame rendering stats. An overlay shows the frame rate and the count of dropped frames. Throttle the CPU 4× and interact — the number you care about is the one under throttling.
  2. Per frame, in a profile. Performance → record an animation. The Frames track draws one block per frame; hover for its duration. Frames that missed the deadline are marked, and clicking one selects exactly the work that overran.
  3. Where the time went. With a frame selected, read the Summary donut: scripting, rendering (style plus layout), painting, system. That split tells you which of Chapter 2's lessons to apply — script means chunk it, rendering means lesson 0013 or 0014, painting means fewer or smaller paints.
  4. Prove where rAF sits. Log inside a rAF callback and inside a ResizeObserver. The observer always reports after the rAF of the same frame, because layout happened in between. Seeing that order confirms section 2 with two console.log calls, and it is gate #3 for this core.
Work drill — do this on a real theme

A theme has a scroll-linked hero: on every scroll event it reads window.scrollY, reads getBoundingClientRect() on four elements, then writes top and opacity on each. On a mid-range Android, Frame rendering stats shows 22 fps while scrolling and a rising dropped-frame count.

Before flipping the recall cards: work out roughly how many times per second that handler runs versus how many frames exist, name every budget item it is spending, and give the version you would ship. Then the interviewer's follow-up: after your fix the scroll is smooth but the effect lags the finger by about one frame — explain why, and say whether you would accept it.

6. Live coding session

Type it, predict it, break it

One file. Type it by hand — this is a stopwatch for frames:

<!doctype html>
<div id="out" style="font:14px monospace"></div>
<button id="load">Add 25ms of work per frame</button>
<script>
  let last = performance.now(), heavy = false, worst = 0;
  load.onclick = () => heavy = !heavy;

  function frame(now) {
    const delta = now - last; last = now;
    if (delta > worst) worst = delta;
    out.textContent = `frame gap ${delta.toFixed(1)}ms · worst ${worst.toFixed(1)}ms`;
    if (heavy) { const end = performance.now() + 25; while (performance.now() < end) {} }
    requestAnimationFrame(frame);
  }
  requestAnimationFrame(frame);
</script>

Predict before clicking: what is the frame gap at rest, and what will it become with 25 ms of work added? Then click. At rest it hovers near 16.7 (or 8.3 on a 120 Hz screen). With the work it jumps to roughly 33 — one frame's worth of overrun costs a whole extra frame, because the next refresh has already been missed.

Now prove the ordering in section 2. Add this and predict which of the three lines logs first:

  const box = document.body;
  new ResizeObserver(() => console.log('3 · observer, after layout')).observe(box);
  requestAnimationFrame(() => console.log('2 · rAF, before style'));
  queueMicrotask(() => console.log('1 · microtask, before the frame work'));
  box.style.padding = '30px';   // dirty layout so the observer fires

Predict the order, then read the console. You have just verified the frame anatomy from lesson 0006 through to this lesson with four lines.

Third round — the honest fix. Write a scroll handler the wrong way and then the right way:

  // wrong: work per scroll event, and a forced layout inside it
  addEventListener('scroll', () => { document.body.style.setProperty('--y', scrollY + 'px'); });

  // right: at most one write per frame
  let queued = false;
  addEventListener('scroll', () => {
    if (queued) return;
    queued = true;
    requestAnimationFrame(() => { document.body.style.setProperty('--y', scrollY + 'px'); queued = false; });
  });

Predict what changes and what does not: the number of writes drops to one per frame, the total scroll work drops, and the effect is now at most one frame behind the finger. That last part is the trade — name it out loud before you accept it.

Remember this
  • The deadline is one refresh interval: 16.67 ms at 60 Hz, 8.3 ms at 120 Hz. Hardware sets it, not the browser.
  • Miss it and the screen repeats the previous frame — a dropped frame, seen as a stutter.
  • You get roughly 10 ms for script plus the style and layout it causes; the browser needs the rest.
  • Frame order: task → microtasks → input → rAF → style → layout → observers → paint → composite → idle callbacks.
  • rAF is a timing tool, not a speed-up. Use it to write visuals once per frame and to throttle scroll and resize handlers.
  • Observers deliver after layout, which is why they hand you geometry with no forced layout.
  • A 300 ms task drops about 18 frames at 60 Hz. Do this arithmetic before writing the animation, not after the complaint.

If you remember one thing: the frame deadline is set by the screen — your only choice is what you fit inside it.
