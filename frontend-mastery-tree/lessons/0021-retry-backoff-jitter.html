Retry with exponential backoff and jitter

The last core of Chapter 3. Every other lesson made a request faster; this one decides what happens when it fails — and a careless retry is the one front-end mistake that can take a store down instead of just making it slow.

core Domain expertise: moves ability #3 (say what the design gives up) and ability #4 (debug with no ready answer) — "the customer was charged twice" starts here.

The win: after ~35 minutes you can write a retry that helps instead of harming, say which HTTP statuses may be retried and which must never be, and explain why a retried add-to-cart can double a customer's order.

1. Why retrying at all, and why not immediately

Mobile networks fail transiently: a handover between towers, a dropped packet, a server restarting behind a load balancer. A large share of failures succeed on a second attempt seconds later. So retrying is right. The question is when.

Reason it through. A request failed. The most likely cause of a 503 or a timeout is that the server is already struggling. Now imagine ten thousand storefront visitors whose requests all failed in the same second:

  • Retry immediately → ten thousand extra requests arrive at a server that could not handle the first ten thousand. You have doubled the load at the exact worst moment. This is a retry storm, and it turns a wobble into an outage.
  • Retry on a fixed timer — say every 2 seconds → the failures were synchronised, so the retries are synchronised too. You have built a pulse: a spike every two seconds, forever, which prevents recovery instead of waiting for it.
  • Exponential backoff — 1 s, 2 s, 4 s, 8 s → each round gives the server exponentially more room. Load falls away instead of piling on.
  • Backoff plus jitter — randomise each delay → the clients are no longer in lockstep, so the retries arrive spread out rather than as a wave (AWS Builders' Library).

Backoff protects the server. Jitter protects it from your other clients. You need both, and they solve different problems — that distinction is the interview answer.

2. What may be retried — and what must never be

OutcomeRetry?Why
Network error, fetch rejectedyesthe request may never have reached the server
408, 425, 429, 500, 502, 503, 504yestransient or explicitly "try later" — and for 429/503, obey Retry-After instead of your own maths
400, 401, 403, 404, 422nothe request itself is wrong. Retrying gets the same answer more expensively
A timeout on a non-idempotent requestonly with protectionyou do not know whether the server did the work. See below
Trap — the one that costs money

POST /cart/add.js times out. Did the item go in the cart? You cannot tell. A timeout means you stopped waiting, not that nothing happened. Retry blindly and the customer may get two of the item — or on a payment-adjacent endpoint, be charged twice.

Three defences, in order of strength: (1) an idempotency key — send a unique id with the request so the server can recognise a repeat and return the first result, which requires server cooperation; (2) reconcile — after a timeout, re-read the state (GET /cart.js) and only act on what it says; (3) ask the user — show a failure and a manual retry button, which is honest and often the right product decision. On a Shopify storefront you rarely control the endpoint, so (2) and (3) are the realistic ones.

3. A retry you could actually ship

const RETRYABLE = new Set([408, 425, 429, 500, 502, 503, 504]);

async function request(url, opts = {}, { attempts = 4, base = 500, cap = 8000, timeout = 10000 } = {}) {
  for (let n = 0; n < attempts; n++) {
    const ac = new AbortController();
    const timer = setTimeout(() => ac.abort(), timeout);   // never hang forever
    try {
      const res = await fetch(url, { ...opts, signal: ac.signal });
      if (res.ok) return res;
      if (!RETRYABLE.has(res.status) || n === attempts - 1) {
        throw new HttpError(res.status, res);               // 422 must not be retried
      }
      const after = Number(res.headers.get('Retry-After'));  // the server may tell you
      await wait(after ? after * 1000 : backoff(n, base, cap));
    } catch (err) {
      if (err.name !== 'AbortError' && !(err instanceof TypeError)) throw err;  // not a transport failure
      if (n === attempts - 1) throw err;
      await wait(backoff(n, base, cap));
    } finally {
      clearTimeout(timer);
    }
  }
}

const backoff = (n, base, cap) => Math.random() * Math.min(cap, base * 2 ** n);  // full jitter
const wait = ms => new Promise(r => setTimeout(r, ms));

Every line is one decision from this lesson: a timeout so nothing hangs (using AbortController — the cancellation a promise could not give you in lesson 0008), a status allow-list, Retry-After taking priority over your own maths, full jitter, a cap, and a bounded attempt count. Note what is missing on purpose: this helper does not retry POSTs safely. That decision belongs to the caller, who knows whether the endpoint is idempotent.

The other half is the interface A retry that takes 15 seconds while the button sits there doing nothing is a worse experience than a fast failure. Show the state — a disabled button with "Retrying…" — keep the total bounded to a few seconds for anything a customer is waiting on, and always leave a manual retry. Silent retries are for background work, never for a tap.

4. Explain it back Feynman check

Part 1 · Plain words — no jargon at all

When a request fails, trying again usually works, because most failures are brief. But the most likely reason it failed is that the other side is overloaded — so trying again straight away makes things worse. So you wait, and each time you fail you wait about twice as long. And because thousands of people's requests failed at the same moment, you also add a random amount to your wait, so everyone does not come back at once and knock the server over again.

Part 2 · One analogy, and where the analogy breaks

The analogy. A busy phone line. If you redial the instant it is engaged, you are part of the reason it stays engaged. Waiting longer each time helps, and waiting a random amount helps more, because otherwise everyone who got the engaged tone at 10:00 redials together at 10:02.

Where it breaks. A phone call either connects or it does not, and you know which. A network request can succeed without you hearing about it — the server did the work and the answer got lost. Redialling is harmless; retrying an order is not. That gap is the whole idempotency problem, and no amount of good backoff maths addresses it.

Part 3 · The sticking point

Two. First: believing a timeout means nothing happened. It means you stopped waiting — the server may have completed the work. Anyone who internalises this writes different code around carts and payments for the rest of their career. Second: retrying everything. A 422 is the server telling you the request is wrong; retrying it four times just says the same wrong thing four times, more slowly, while showing the customer a spinner. Retry transport failures and explicit try-later statuses, nothing else.

Part 4 · Teach it back to me

Two or three sentences to a teammate whose pull request adds "retry 5 times, every 500 ms" to the theme's add-to-cart call. Name both bugs — the load one and the correctness one — and say what you would ship instead. Then send it to me. If your answer only mentions backoff, you missed the expensive half.

5. Point at it: make failures happen on purpose gate #3

  1. Offline and back. Network panel → throttling dropdown → Offline. Trigger your request, watch it reject, then switch back to Slow 4G and watch the retry succeed. Every retry attempt appears as its own row, so you can literally count them and read the gaps between their start times.
  2. Verify the jitter. Log Date.now() before each attempt and check the gaps are growing and uneven. Two runs producing identical delays means you wrote backoff without jitter — the most common half-done version.
  3. Block one URL. Right-click a request → Block request URL, then reload. This is the cheapest way to see what your UI does when one endpoint fails while everything else works — and it is where you discover the spinner that never stops. Gate #3 for this core is doing this on your own theme's cart request and watching the interface, not just the console.
  4. Prove the timeout. Point a request at a slow endpoint and confirm your AbortController fires. A retry helper with no timeout will sit forever on a connection that never answers, and no amount of attempts configuration saves you.
Work drill — do this on a real theme

A theme's add-to-cart posts to /cart/add.js. On flaky mobile connections, support receives occasional reports of "I added one and got two". You find that a previous developer wrapped the call in a retry: 3 attempts, 400 ms apart, retrying on any failure including a timeout, with no request timeout of its own and no user-visible state.

Before flipping the recall cards: list every distinct defect in that description — there are at least four — and say which one causes the duplicate line items. Then the interviewer's follow-up: you cannot add an idempotency key because you do not own the endpoint. Describe exactly what you would ship, including what the customer sees.

6. Live coding session

Type it, predict it, break it

Type this by hand. It is a failing endpoint plus a retry, so you can watch the delays:

python3 - <<'PY'
from http.server import SimpleHTTPRequestHandler, HTTPServer
n = {'count': 0}
class H(SimpleHTTPRequestHandler):
    def do_GET(self):
        if self.path == '/flaky':
            n['count'] += 1
            code = 200 if n['count'] % 4 == 0 else 503   # fails 3 times, then works
            self.send_response(code)
            self.send_header('Access-Control-Allow-Origin', '*')
            self.end_headers(); self.wfile.write(b'attempt %d' % n['count']); return
        super().do_GET()
HTTPServer(('', 8000), H).serve_forever()
PY

Now the client, in the Console of http://localhost:8000:

const wait = ms => new Promise(r => setTimeout(r, ms));

async function go(jitter) {
  const t0 = Date.now();
  for (let n = 0; n < 5; n++) {
    const res = await fetch('/flaky');
    console.log(`attempt ${n + 1} at +${Date.now() - t0}ms → ${res.status}`);
    if (res.ok) return;
    const interval = Math.min(8000, 500 * 2 ** n);
    await wait(jitter ? Math.random() * interval : interval);
  }
}
await go(false);   // backoff only

Predict before running: write down the five timestamps you expect with jitter = false. Then run it. You should see roughly +0, +500, +1500, +3500 — the doubling, exactly as designed.

Now run await go(true) three times and predict how the timestamps differ between runs. With jitter they change every run; without it they are identical. Now picture ten thousand browsers running the first version at the same moment — that is the retry storm, and you have just seen why it happens.

Break it the expensive way. Change the endpoint to a POST that appends a line to a file, make it sleep 3 seconds before responding, and give your client a 1-second timeout so it always gives up and retries:

  // server: time.sleep(3) then append to a list; client: AbortController with 1000ms

Predict how many lines end up in the file after "one" click. Then look. Every attempt succeeded on the server and every one looked like a failure to you — that is the duplicate cart item, reproduced on your own machine. Nothing about backoff or jitter would have prevented it.

Remember this
  • Retrying is right — most failures are brief. Retrying immediately is wrong, because the likeliest cause is an overloaded server.
  • Exponential backoff protects the server. Jitter protects it from your other clients being in lockstep. You need both.
  • Full jitter: delay = random(0, min(cap, base × 2^attempt)). Always cap the delay and bound the attempts.
  • Retry transport failures and 408/425/429/5xx. Never retry 400, 401, 403, 404, 422.
  • Obey Retry-After when the server sends it — it beats your own arithmetic.
  • A timeout means you stopped waiting, not that nothing happened. Retrying a non-idempotent request can double an order.
  • Without an idempotency key, the honest options are reconcile (re-read the state) or ask the user.
  • Every request needs a timeout (AbortController), and every retry a visible state. Silent retries are for background work only.

If you remember one thing: good backoff maths never makes an unsafe retry safe.
