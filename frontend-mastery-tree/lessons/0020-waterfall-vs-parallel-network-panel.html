Stratum 3 · Network & Delivery · Request discipline · Lesson 0020

Waterfall vs parallel — reading the Network panel

Every other lesson in Chapter 3 gave you a cause. This one is the diagnosis: the shape of a waterfall tells you the dependency structure of your page, and a staircase is always a bug.

core Domain expertise: moves ability #4 (debug with no ready answer) and ability #5 (judge someone else's work) — reading a waterfall out loud in front of a client is the single most useful network skill you can have.

The win: after ~35 minutes you can open a storefront's Network panel and say, in under a minute, which requests are on a dependency chain, which are waiting on a queue, which are waiting on the server, and which of those is actually your problem.

1. Two shapes, and only one of them is fine

The browser fetches in parallel whenever it can. So if requests appear one after another, stepping down and to the right, something prevented parallelism — each URL was only discovered after the previous response arrived. That staircase costs the full setup and download of every step, one after another.

The usual causes of a staircase, in the order you should check them:

CauseTellFix
A script that fetches another scriptthe Initiator column names a .js file, not the documentput the real URL in the markup, or preload it (lesson 0019)
@import in CSSa stylesheet whose initiator is another stylesheetreplace with a <link> (lesson 0010)
Redirect chainstatus 301/302 rows, each a full round triplink to the final URL; never link to a redirect in a template
Font inside a stylesheetfont starts only after the CSS is parsed and matchedpreload with crossorigin (lesson 0019)
Image src set by JavaScriptimage initiator is a script; the preload scanner never saw itreal src in the HTML, and fetchpriority if it is the LCP element

2. The timing rows, and what each one blames

Click any request, open Timing, and read down. Each row points at a different team:

RowLong meansWhose problem
Queueing / Stalledwaiting for a connection or behind higher-priority requestsyours — too many requests, or bad priorities
DNS, Initial connection, SSLa new origin's setup costyours — origin count (lesson 0017)
Waiting (TTFB)the server is thinkingthe platform, the app, or Liquid — not front-end
Content Downloadbytes, or TCP slow start on a fresh connectionyours — size, format, compression

This table is what makes you useful in a meeting. "The 900 ms is Waiting, on the server, on a request our theme does not control" is a completely different ticket from "the 900 ms is Content Download of an unoptimised hero image". Both look like "the site is slow" without the panel.

Trap — the Initiator column is the answer to most questions It is off-screen by default on narrow windows and almost nobody enables it. Right-click the table header, tick Initiator, and every mystery request now names the file and line that caused it. Nine out of ten "where is this request coming from" questions end there — including "which app is loading this".

3. What to check, in order, on a storefront you have never seen

  1. Set the conditions first. Disable cache, throttle to Slow 4G, CPU 4×. An un-throttled waterfall on office wifi hides everything in Chapter 3.
  2. Count. The footer shows requests, transferred bytes and load times. Note them; they are the before-numbers for whatever you do next.
  3. Look at the shape. Any staircase? Follow it with the Initiator column.
  4. Sort by Time, then by Size. The two lists are usually different, and the difference tells you whether you have a latency problem or a bytes problem.
  5. Group by domain. Enable the Domain column and sort. That is your origin count from lesson 0017, and it is usually the biggest number nobody has looked at.
  6. Check the Priority column against what matters: the LCP image should not be below a chat widget (lesson 0019).
  7. Filter 304 — round trips that returned nothing (lesson 0018).

4. Explain it back Feynman check

Part 1 · Plain words — no jargon at all

The panel draws one bar per file, positioned by when it started and how long it took. If the bars all start together, the browser knew about everything at once and fetched them side by side — good. If they form a staircase, each file was only discovered after the one above it had arrived, so the waits happened one after another instead of at the same time. And when you click a single bar, it splits the wait into parts, which tells you whether you were queuing, connecting, waiting for the server to think, or downloading.

Part 2 · One analogy, and where the analogy breaks

The analogy. Sending four people to fetch four things. If you hand out all four lists at the door, they go at once and you wait for the slowest. If each list is hidden inside the previous person's bag, they go one at a time and you wait for all four.

Where it breaks. You can send a hundred people; the browser cannot. There is a limit on parallel connections per origin — around six on HTTP/1.1 — so beyond that, requests queue even when every URL was known from the start. That is why the Queueing row exists and why "make it all parallel" has a ceiling.

Part 3 · The sticking point

People read the total and stop. The total tells you there is a problem; the shape tells you the kind, and the Timing rows tell you the owner. Second sticking point: blaming the network for a staircase. A staircase is a discovery problem — the fix is in your markup or your CSS, not in your hosting. Third: judging any of this without throttling, which makes every one of Chapter 3's mechanisms invisible.

Part 4 · Teach it back to me

Two or three sentences to a project manager who forwards a client email saying "the site is slow" with a screenshot of the Network panel. Explain what you can and cannot tell from that screenshot, and name the one extra thing you need. Then send it to me — the skill is asking for the right missing information instead of guessing from a picture.

5. Point at it: read a real waterfall out loud gate #3

  1. Open any storefront you did not build. Network panel, cache disabled, Slow 4G, CPU 4×, reload.
  2. Enable the columns that matter: right-click the header row and tick Initiator, Priority, Protocol, Domain.
  3. Narrate it, out loud, in this order: how many requests, how many origins, is there a staircase, what is the slowest single request, and which Timing row dominates it. If you cannot do all five in a minute, do it again on another site until you can. That fluency is gate #3 for this core.
  4. Export the evidence: right-click → Save all as HAR. A HAR file is the honest attachment for a ticket — it survives, and anyone can reload it into their own panel.
Work drill — do this on a real theme

On Slow 4G a product page takes 6.1 s to load. The waterfall shows: the document at 400 ms TTFB; then a block of theme CSS and JS, all parallel, finishing by 1.4 s; then a four-step staircase — app-loader.js → bundle.js → config.json → reviews.css — ending at 4.9 s; and finally the hero image, starting at 5.0 s and finishing at 6.0 s, whose Initiator column names slider.js. Of the six seconds, only 900 ms is Content Download in total.

Before flipping the recall cards: name each of the two problems in mechanism terms, say which one you would fix first and why, and say what "only 900 ms is Content Download" tells you about the whole page. Then the interviewer's follow-up: the merchant's developer replies that the site is slow "because Shopify's servers are slow" — using only this waterfall, how do you answer, and what would you concede?

6. Live coding session

Type it, predict it, break it

Build a staircase on purpose. Four files, typed by hand:

<!-- index.html -->
<!doctype html>
<script src="a.js"></script>

// a.js
const s = document.createElement('script'); s.src = 'b.js'; document.head.append(s);

// b.js
fetch('data.json').then(r => r.json()).then(d => console.log('done', d));

// data.json
{ "ok": true }

Serve it, throttle to Slow 4G, disable the cache, reload with the Network panel open. Predict first: will the four bars form a block or a staircase, and what will the Initiator column say for each? Then look. Every URL was hidden inside the previous response, so nothing could be discovered early — including by the preload scanner from lesson 0011.

Now flatten it and predict the new total before reloading:

<!doctype html>
<link rel="preload" as="fetch" href="data.json" crossorigin>
<script src="a.js" defer></script>
<script src="b.js" defer></script>

All three now start together, and the total drops to roughly the slowest one plus a little. Same bytes, same files, one third of the wall clock — because you changed when things were discovered, not how fast the network is.

Third round — make the Timing rows tell you different stories. Add a slow endpoint to your server and fetch it:

python3 - <<'PY'
from http.server import SimpleHTTPRequestHandler, HTTPServer
import time
class H(SimpleHTTPRequestHandler):
    def do_GET(self):
        if self.path == '/slow':
            time.sleep(1.5)                      # server thinking time
            self.send_response(200); self.send_header('Content-Type','text/plain')
            self.end_headers(); self.wfile.write(b'ok'); return
        super().do_GET()
HTTPServer(('', 8000), H).serve_forever()
PY

Fetch /slow and a large static file, and predict which Timing row dominates each: Waiting (TTFB) for the first, Content Download for the second. Being able to tell those two apart at a glance is what stops you optimising images when the problem is a server.

7. Prove it

The gate — only now touch the tracker Open the tree tracker and mark waterfall vs parallel: reading the Network panel done only if all three held, from memory: (1) you answered the "site is slow, here is a screenshot" email — the teach-back in section 4; (2) you predicted the staircase and its initiators, and predicted which Timing row would dominate each of the two requests; (3) you narrated a real storefront's waterfall — requests, origins, shape, slowest request, dominant row — in about a minute. Two out of three is zero out of three.

Remember this
  • Bars starting together = the browser knew all the URLs. A staircase = each URL was discovered only after the previous response.
  • A staircase is a discovery problem, not a network problem. The fix is in your markup or CSS.
  • The Initiator column answers "where is this request coming from" — enable it, it is off by default.
  • Timing rows blame different owners: Queueing/Stalled = your request count and priorities · DNS/connection/SSL = origin count · Waiting (TTFB) = the server · Content Download = bytes and slow start.
  • Parallelism has a ceiling: roughly six connections per origin on HTTP/1.1, which is what Queueing is showing you.
  • Always: cache disabled, Slow 4G, CPU 4×. Without throttling, Chapter 3 is invisible.
  • Sort by Time and by Size separately — the difference says latency problem or bytes problem.
  • Attach a HAR file to the ticket, not a screenshot.

If you remember one thing: read the shape first, then the timing rows — the total tells you nothing about the cause.
