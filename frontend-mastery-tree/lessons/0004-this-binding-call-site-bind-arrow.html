Stratum 1 · Language & Runtime · Execution model · Lesson 0004

this binding: call-site, bind, arrow capture

Lessons 0002 and 0003 built one rule: names are resolved by where the code was written. this is the one thing in the language that breaks that rule — and an arrow function is what happens when you take the break away.

core Domain expertise: moves ability #2 (predict an unseen case) and ability #4 (debug with no ready answer) — "this is undefined" is the single most common runtime error in hand-written theme JavaScript.

The win: after ~30 minutes you can look at any call expression — including one buried in addEventListener — and say what this will be, before running it. And you can explain why an arrow function fixes it without saying the word "magic".

1. The problem this was invented to solve

You have one behaviour and many objects that need it. Written the honest way, the object goes in as an argument: 

function total(cart) { return cart.items.length; }
total(cartA); total(cartB);

That works, and it is explicit. But you want to attach the behaviour to the object, so the caller can write cartA.total(). The function now has to receive the object without it appearing in the argument list. So the language passes a hidden extra argument, and gives it a name: this.

Once you accept that this is a hidden argument, one question decides everything: who fills it in? Not the place the function was written — the writer does not know which cart you will use. The only place that knows is the call site: the exact expression that performs the call. That is the whole mechanism, and per MDN — this it is decided fresh on every single call.

Say it this way

A variable name asks "where was I written?". this asks "how was I called?". Two different questions, two different answers, one line apart in the same function.

2. The five call shapes, in the order the engine checks them

There are only five ways a call can look, and each one fills the hidden argument differently. Read the chart top to bottom and stop at the first "yes" — that is genuinely how to answer any interview question on this topic.

Rule 4 is where the bugs live, because the dot can be lost. The dot is part of the call expression, not part of the function. Take the function out of the object and the dot is gone: 

const cart = {
  items: ['tee', 'cap'],
  count() { return this.items.length; }
};

cart.count();                    // → 2  — rule 4, this = cart
const c = cart.count;
c();                             // → TypeError  — rule 5, this = undefined
setTimeout(cart.count, 0);       // → TypeError  — same thing, one day later
Trap setTimeout(cart.count, 0) looks like it "passes the method". It passes the function value and throws the dot away. Later, the timer calls it bare — rule 5. This is the same bug as button.addEventListener('click', this.open), which is the most common broken line in hand-written theme JavaScript. One exception worth knowing: for a normal function used as a DOM listener, the browser calls it with this set to the element the listener is attached to — so you get the button, not your object. Silent wrong answer instead of an error, which is worse.

3. Why an arrow function fixes it — and it is not a new rule

An arrow function does not have its own this. Not "it copies the outer one" — it simply has no slot. So when the body of an arrow function mentions this, the engine does what it does for any name it cannot find locally: it follows the outer reference from lesson 0002, one step at a time, until it finds a this. 

class CartDrawer {
  constructor(el) {
    this.el = el;
    // arrow: no own this → the one found outward is the instance
    el.addEventListener('click', () => this.open());
    // method reference: dot lost → this becomes the element
    el.addEventListener('click', this.open);
  }
  open() { this.el.classList.add('is-open'); }
}

Two consequences fall out of "no slot", and both are exam questions:

  • bind cannot change an arrow's this. There is nothing to bind. arrow.call(x) silently ignores x.
  • An arrow is the wrong tool for a method that needs a receiver. Write obj = { fn: () => this.x } and this is whatever surrounded the object literal — almost never the object.

The third fix is older and still fine: this.open = this.open.bind(this) in the constructor. It builds a new function whose hidden argument is pinned forever. Cost: one extra function object per instance, and a name that now means something different from the prototype method with the same name.

4. Explain it back Feynman check

Part 1 · Plain words — no jargon at all

When you call a function, the language quietly hands it one extra thing: "the object you are working on". Who decides what that object is? Not the person who wrote the function. The person who makes the call, by the shape of the call they write. Put something before the dot and that thing is handed over. Call the function with nothing before it and nothing is handed over. Arrow functions refuse to accept this extra thing at all, so when they need it they borrow it from the code around them.

Part 2 · One analogy, and where the analogy breaks

The analogy. A form that says "sign here on behalf of ______". The form is the function; the blank is this. The person who hands you the form fills in the blank, not the person who printed it. Hand over the same form with a different name in the blank and the same words now bind a different company.

Where it breaks. A paper form keeps whatever was written in the blank. This blank is wiped and refilled on every single call — the same function can be "on behalf of" a different object one line later. And an arrow function is a form with no blank printed on it at all; asking it who it represents makes it look at the letterhead of the page it was printed on.

Part 3 · The sticking point

Everyone learns "this is the object the method belongs to" and it is wrong. A function does not belong to an object; it is a value stored in a property. The dot is part of the call, and the moment you store the function somewhere else — a variable, setTimeout, addEventListener, an array of callbacks — the dot is gone and rule 5 applies. The second sticking point: people say an arrow "binds this to the outer scope". It binds nothing. It has no slot, so ordinary name lookup runs. Say it the second way and the follow-up question ("can you bind an arrow?") answers itself.

Part 4 · Teach it back to me

Two or three sentences to a junior who asks: "my addEventListener('click', this.open) throws Cannot read properties of undefined, but () => this.open() works. What is the difference?" You may not use the words "context" or "scope" without defining them first. Then send it to me — I am checking whether you explain the arrow as no slot rather than as copied this.

5. Point at it: watch the slot change in DevTools gate #3

  1. Paste the cart object from section 2 into the Console.
  2. DevTools → Sources → breakpoint on the return line inside count.
  3. Call cart.count(). In the Scope pane, look at Local: there is an entry named this, and it is the cart object.
  4. Resume, then run const c = cart.count; c();. Same breakpoint, same function, same line — and this in the Scope pane is now undefined. Nothing about the function changed. Only the call changed. That is gate #3 for this core, in about forty seconds.
  5. Bonus, for the arrow rule: breakpoint inside an arrow function and notice there is no this entry in Local at all — DevTools shows it under the outer scope instead. The absence is the mechanism.
Work drill — do this on a real theme

A theme's cart-drawer.js has a class with open() and close(). The constructor does this.overlay.addEventListener('click', this.close). Clicking the overlay does not close the drawer, and the console shows no error at all.

Before flipping the recall cards: why is there no error, what is this inside close at that moment, and which two fixes would work? Then the interviewer's follow-up: which fix would you choose if the same handler must later be removed with removeEventListener, and why does that rule out one of them?

6. Live coding session

Type it, predict it, break it

Open a scratch file. Type this by hand:

const cart = {
  items: ['tee', 'cap'],
  count() { return this.items.length; }
};
console.log(cart.count());

Predict, then run. Now add three lines and predict each one before running it — write the three answers on paper first:

const c = cart.count;
console.log(c());                      // a
console.log(c.call(cart));             // b
console.log(c.call({ items: [1,2,3] })); // c

Line (c) is the one that teaches the most: the same function, given an object it has never seen, works fine — because this was never about ownership.

Now break it in the way that hurts in production. Write the listener bug on purpose:

const box = document.createElement('div');
document.body.append(box);
const widget = {
  name: 'drawer',
  hello() { console.log('hello from', this.name); }
};
box.addEventListener('click', widget.hello);   // predict the output
box.click();

Predict before running: an error, or a wrong answer? Then run it. You should see hello from undefined — no exception, because for a normal function the DOM set this to the div, which simply has no name. Fix it two ways (an arrow wrapper, then .bind) and confirm both.

Remember this
  • this is a hidden extra argument, filled in by the call site, fresh on every call.
  • Five shapes, checked in order: arrow (no slot) → new → call/apply/bind → dot → bare.
  • The dot belongs to the call, not to the function. Store the function elsewhere and the dot is lost.
  • An arrow function has no this of its own, so ordinary scope-chain lookup finds the outer one. Nothing is copied; bind has no effect.
  • A normal function used as a DOM listener gets this = the element — a silent wrong answer, not an error.
  • bind returns a new function object, so the bound version cannot be removed with removeEventListener unless you kept a reference to it.

If you remember one thing: names ask where they were written; this asks how it was called.
