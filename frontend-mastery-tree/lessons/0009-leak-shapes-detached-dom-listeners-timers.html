Leak shapes: detached DOM, listeners, timers, closures

The garbage collector does not free what you have stopped using. It frees what you can no longer reach. Every memory leak you will ever debug is one accidental rope — and there are only four common ropes.

core Domain expertise: moves ability #4 (debug a problem with no ready answer) — the last core of Chapter 1, and the one that pays for itself the first time a client says "the site gets slower the longer I browse".

The win: after ~40 minutes you can take a heap snapshot, find a detached DOM subtree, name the exact line holding it, and say which of the four shapes it is — without guessing.

1. Reachability, not usage

Start from the engine's position. It cannot know what your code will use next; that would need to predict the future. It can only know what your code can still get to. So it defines a set of roots — things that are alive by definition — and keeps everything reachable from them:

  • the global object and its properties (window, anything you hung off it);
  • every frame currently on the call stack, and its variables (lesson 0001);
  • things the platform itself holds: the live document tree, registered event listeners, pending timers, in-flight requests.

Then it does mark-and-sweep: walk every rope from every root, mark what you touch, free the rest. The consequence is the sentence that fixes leaks: a leak is not "memory that is unused" — it is memory you no longer want that is still reachable. The bug is never in the collector. The bug is a rope you forgot.

And now lesson 0003 pays off directly. A closure keeps its whole box alive, so a rope to a function is a rope to everything that function could see. Nothing new to learn; the same rule, applied to memory.

2. The four shapes

ShapeThe ropeWhat it keepsThe fix
Detached DOMa variable, array or Map still referencing a removed nodethe node and its whole subtreenull the reference when you remove the node; key caches with WeakMap
ListenersaddEventListener on a long-lived target (window, document) whose handler closes over your componentthe handler's box → the component → its DOMremoveEventListener with the same reference, or one AbortController per instance
TimerssetInterval never cleared (a pending timer is a root)the callback's box, foreverclearInterval on teardown; prefer rAF loops that stop themselves
Closuresany surviving function created in a big scopeevery binding its box holdskeep boxes small; do not close over a whole component when you need one id
Trap — the listener myth "Event listeners always leak" is false, and believing it wastes hours. If the target node and the handler both become unreachable together, the collector takes both — no removeEventListener needed. The leak happens when the target outlives the component: window, document, or a node you kept a reference to. So the question is never "did I remove the listener?" but "what is the listener attached to, and how long does that thing live?"

3. The shape that bites Shopify themes specifically

Theme sections are re-rendered by the theme editor and by the Section Rendering API. Each re-render calls your init again on fresh markup — and if init attaches to something long-lived, every re-render adds a new rope while the old markup is thrown away: 

// leaks once per section re-render
function init(section) {
  const slides = section.querySelectorAll('.slide');
  window.addEventListener('resize', () => layout(slides));   // window outlives the section
  setInterval(() => advance(slides), 4000);                  // a pending timer is a root
}
document.addEventListener('shopify:section:load', e => init(e.target));
// one controller per instance — one line cuts every rope
function init(section) {
  const slides = section.querySelectorAll('.slide');
  const ac = new AbortController();
  window.addEventListener('resize', () => layout(slides), { signal: ac.signal });
  const id = setInterval(() => advance(slides), 4000);
  section.addEventListener('shopify:section:unload', () => {
    ac.abort();            // removes every listener registered with this signal
    clearInterval(id);     // the timer root goes away
  }, { once: true });
}

AbortController as a listener remover: MDN — AbortController. It is the same object used to cancel a fetch, which is the cancellation a promise could not give you in lesson 0008.

4. Explain it back Feynman check

Part 1 · Plain words — no jargon at all

The browser cleans up by asking one question about every object: can I still get to it? It starts from a few places it knows are in use, follows every rope, and throws away whatever it never touched. It never asks "do you still want this". So a thing you stopped caring about stays in memory as long as one rope still reaches it — and ropes are easy to leave behind: a name you forgot to clear, a timer still ticking, a handler still listening on something that lives as long as the page.

Part 2 · One analogy, and where the analogy breaks

The analogy. A warehouse clear-out. The team walks in from the loading doors, follows every labelled path, and marks every crate it can reach. Anything unmarked gets thrown out — including crates that are perfectly full, if no path leads to them. A crate you no longer want survives simply because one old path still points at it.

Where it breaks. A warehouse manager can look at a crate and decide it is junk. The collector cannot: it has no opinion about value, only about paths. And unlike a warehouse, here removing a crate from the shop floor — taking a node out of the page — does not remove any path to it. That single mismatch is the whole detached-DOM bug.

Part 3 · The sticking point

Two, and they are the reason leak hunts go in circles. First: people think element.remove() frees the element. It only unlinks it from the document; if any JavaScript still references it, the node and its entire subtree stay. Second: people believe every listener must be removed by hand. Not true — if the target dies with the handler, both are collected. What matters is how long the target lives. Ask that question and you will stop removing listeners that never leaked while missing the one on window that does.

Part 4 · Teach it back to me

Two or three sentences to a junior who asks: "I called drawer.remove(), so why does the Memory panel still show 400 detached nodes after ten opens?" You may not use the words "garbage collection" or "reference" without explaining them plainly first. Then send it to me — I am checking that you say reachable rather than used, because that one word swap is what makes the fix findable.

5. Point at it: find the rope in a heap snapshot gate #3

  1. See the trend first. DevTools → Performance monitor (Command Menu → "Show Performance monitor"). Watch JS heap size and DOM Nodes while you open and close a drawer ten times. A staircase that never comes back down is a leak; a sawtooth is healthy.
  2. The three-snapshot technique. Memory → Heap snapshot. Take snapshot 1. Do the action ten times. Take snapshot 2. Do it ten more times. Take snapshot 3. Then compare 3 against 2 with the Comparison view: whatever keeps growing between two identical rounds is the leak, and everything that merely appeared once is noise. Documented in Chrome DevTools — Fix memory problems.
  3. Name the shape. In a snapshot, type Detached into the class filter. Each Detached HTMLDivElement is a removed node still held. Select one and read the Retainers pane at the bottom — it names the object and the property holding it, and often the file and line. That retainer chain is the rope in the diagram.
  4. Confirm the timer shape. With the leak reproduced, run for (let i = 1; i < 9999; i++) clearInterval(i) in the Console, force garbage collection with the bin icon, and re-snapshot. If the detached nodes disappear, a pending timer was the root — a crude test, and it answers the question in ten seconds.
Work drill — do this on a real theme

A client reports the storefront "gets sluggish after browsing for a while", worst on collection pages with infinite scroll. You watch the Performance monitor: DOM Nodes climbs from 1,800 to 14,000 over five minutes of scrolling and never drops, and JS heap follows it. A snapshot comparison shows thousands of Detached HTMLImageElement entries, and the Retainers pane keeps naming an array called observedCards inside the lazy-loading module.

Before flipping the recall cards: name the shape, explain why the images were detached but not freed, and give the fix. Then the interviewer's follow-up: the module needs to remember which cards it has already handled — how do you keep that memory without keeping the nodes alive?

6. Live coding session

Type it, predict it, break it

Open a scratch HTML file. Type this leak by hand — you are building the bug on purpose:

const kept = [];
function openDrawer() {
  const el = document.createElement('div');
  el.innerHTML = '<p>row</p>'.repeat(400);
  document.body.append(el);
  kept.push(el);                      // the rope
  setTimeout(() => el.remove(), 50);  // unlinked, but still reachable
}
for (let i = 0; i < 10; i++) openDrawer();

Predict first: after the timeouts run, how many detached nodes will a snapshot show? Then check: Memory → Heap snapshot → filter Detached. Read the Retainers pane and find kept by name. Seeing your own variable named in DevTools is the moment this becomes a skill instead of a warning.

Now fix it and prove the fix. Change one line — kept.push(el) becomes nothing, or clear the array in the timeout — force garbage collection with the bin icon, snapshot again, and confirm the detached count is zero. Same page, same 4,000 nodes created, no leak.

Third round: the listener shape. Predict which of these two leaks, then test both:

// A
const a = document.createElement('button');
a.addEventListener('click', () => console.log('a'));
document.body.append(a); a.remove();

// B
const b = document.createElement('button');
window.addEventListener('resize', () => b.focus());
document.body.append(b); b.remove();

A does not leak: the button and its handler became unreachable together. B leaks: window is a root, it holds the handler, the handler's box holds b. Now fix B with an AbortController and confirm the detached button disappears. If you can explain the difference between A and B out loud, you have this core.

The gate — only now touch the tracker Open the tree tracker and mark leak shapes: detached DOM, listeners, timers, closures done only if all three held, from memory: (1) you explained "reachable, not used" in plain words — the teach-back in section 4; (2) you predicted which of A and B leaks, before testing; (3) you found a Detached element in a real heap snapshot and read its retainer chain. Remember this
  • The collector frees what is unreachable, never what is "unused". A leak is something you no longer want with a rope still attached.
  • Roots: globals, the call stack, and platform-held things — the live document, registered listeners, pending timers, in-flight requests.
  • element.remove() unlinks a node from the page. It frees nothing if JavaScript still references it — and one held node keeps its whole subtree.
  • Four shapes: detached DOM, listeners on long-lived targets, uncleared timers, closures over too much. All four are the same rule.
  • Listeners do not always leak. Ask how long the target lives, not "did I remove it".
  • A closure keeps its whole box (lesson 0003), so a rope to a function is a rope to everything it could see.
  • Method: Performance monitor for the trend, three snapshots for the culprit, Retainers for the line to change.

If you remember one thing: ask "what still points at this?", never "why has this not been freed?"
