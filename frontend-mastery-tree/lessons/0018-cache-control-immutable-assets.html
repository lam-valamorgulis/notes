Stratum 3 · Network & Delivery · Caching · Lesson 0018

Cache-Control & immutable assets

Lesson 0017 made a request cheaper. This lesson makes it not happen. The difference between "fresh" and "revalidate" is one round trip on every page view — and most sites give it away by accident.

core Domain expertise: moves ability #3 (say what the design gives up) and ability #5 (judge someone else's work) — reading a response header and saying whether it is right is a five-second senior skill.

The win: after ~35 minutes you can read a Cache-Control header and say exactly what the browser will do on the next page view, explain why a one-year lifetime is safer than a one-hour one, and check what your own storefront is actually sending instead of assuming.

1. Two questions, three outcomes

When the browser needs a URL it already has a copy of, it asks two questions in order. Everything about HTTP caching falls out of them:

  1. Is my copy still fresh? — decided locally, from the response's freshness lifetime. If yes: use it. Zero network. Zero round trips. The best possible outcome, and the only one that is actually free.
  2. If not fresh, has it changed? — a conditional request carrying the validator the server gave you (If-None-Match with the ETag, or If-Modified-Since). The server may answer 304 Not Modified with no body. Cheap in bytes — and still a full round trip.

That second point is the one people miss. A 304 feels like a cache hit and costs like a request. On a 150 ms mobile connection, forty revalidations is six seconds of waiting to be told nothing changed (MDN — HTTP caching).

2. The directives you will actually meet

Trap — no-cache does not mean "do not cache" no-cache means "cache it, but check with me every time". The directive that means "do not keep this at all" is no-store. Getting these backwards produces two different bugs: a needless round trip on every asset, or a customer's cart contents sitting in a shared cache. Say the long form out loud — "no-cache is always revalidate" — until it is automatic.

3. Why a one-year lifetime is the safe choice

The instinct is that a long lifetime is risky: what if you need to change the file? Follow the reasoning through and the instinct inverts.

If correctness comes from the header, you are always trading staleness against round trips, and there is no good number: an hour is both too long to ship a fix and too short to avoid the traffic. If correctness comes from the URL — theme.a91f3c.js, or a version query parameter that changes with the content — then the old URL can never be wrong, because new content lives at a new URL. A year is safe, and immutable stops even the reload-triggered revalidation.

HTML → no-cache (or a short max-age) + ETag ... it names the asset URLs hashed asset → max-age=31536000, immutable ... its URL changes when it changes cart / account→ no-store, private ... never in a shared cache

This is the whole strategy, and it is three lines. Everything else is a variation.

4. What you control on a Shopify theme — and what you do not

Be precise here, because the usual advice assumes you own the server. On a Shopify storefront you generally do not set these headers: Shopify's CDN decides them for theme assets and for storefront HTML. What you do control:

  • Which URL you ask for. Using {{ 'theme.js' | asset_url }} gives you the platform's versioned URL. Hand-writing a URL, or adding your own cache-busting parameter, can defeat a cache that was working.
  • Whether the request happens at all. Lessons 0010, 0011 and 0017 — fewer origins, fewer files.
  • Your own fetch calls. The cache option ('default', 'no-store', 'reload', 'force-cache') decides how a cart or section request uses the cache. Sending no-store on a Section Rendering request that could have been cached is a real, self-inflicted round trip.
  • Third-party assets. You cannot change their headers, but you can read them, and "this app's script sends no-cache so it costs a round trip on every page view" is a concrete line for a report.
Verify, do not trust — including this page Header behaviour on any platform changes over time. Do not quote a value from a blog post or from this lesson: open the Network panel on the storefront you are actually working on, click the asset, and read its real Cache-Control. The habit of checking is the transferable skill; the specific values are not.

5. Explain it back Feynman check

Part 1 · Plain words — no jargon at all

The browser keeps copies of files it has already downloaded. Each copy comes with a note from the server saying how long it can be trusted. If the time has not run out, the browser just uses its copy and asks nobody — instant. If the time has run out, it still has to ask "has this changed?", and even a "no, it has not" answer takes a full trip to the server and back. So the best thing you can do is make copies trustworthy for a very long time, and change the file's name whenever its contents change.

Part 2 · One analogy, and where the analogy breaks

The analogy. A printed price list with a date on it. Inside its valid period the shop assistant quotes from it directly. Once the date passes, they have to phone head office — and phoning to hear "prices unchanged" takes just as long as phoning to get new prices.

Where it breaks. A shop can decide to trust an old list a bit longer, or eyeball it, or ask a colleague. The browser cannot improvise: it follows the note exactly. And there is a move the paper analogy has no equivalent for — printing a new list with a new title so the old one can never be mistaken for current. That is fingerprinted URLs, and it is what makes a one-year lifetime safe rather than reckless.

Part 3 · The sticking point

Two, and they are opposite mistakes. First: reading no-cache as "do not cache". It means "always check first" — the never-store directive is no-store. Second: believing a 304 is free. It carries no body, so it looks free in the Size column, and it costs a whole round trip, so it is not. Forty of them on a phone is seconds. The mental model that fixes both: ask whether the browser had to talk to the server at all, not how many bytes came back.

Part 4 · Teach it back to me

Two or three sentences to a teammate who says: "I set max-age to five minutes on our assets so customers always get the latest version". Explain what they actually bought and what it cost, and what to do instead. No jargon: not "revalidation", not "fingerprinting", until you have said each plainly. Then send it to me — I want to see you name the round trip.

6. Point at it: read the real headers gate #3

  1. Cache hits, in one column. DevTools → Network, cache enabled, and navigate between two pages of a storefront. Read the Size column: (disk cache) and (memory cache) are the free green box from the diagram. A byte count means the network was used.
  2. Find the round trips that returned nothing. Filter the Status column for 304. Every one is a full round trip spent hearing "unchanged". Count them and multiply by a mobile RTT — that number belongs in your report.
  3. Read one asset's headers properly. Click a theme asset → Headers → Response headers. Note its Cache-Control, its ETag, and whether immutable is present. Then do the same for the HTML document, and for one third-party script. Three headers, three different strategies — writing them down is gate #3 for this core.
  4. Prove the fetch option matters. In the Console, run the same request twice: await fetch('/cart.js'); await fetch('/cart.js', { cache: 'no-store' }); and compare the two entries in the Network panel. Same URL, different cache behaviour, decided entirely by your own code.
Work drill — do this on a real theme

On a client storefront, a page-to-page navigation shows 38 requests: 9 return 200 with bytes, 24 are 304, and 5 come from disk cache. The 24 revalidations are all from one review app's origin, whose script and CSS carry Cache-Control: no-cache. The site's own theme assets are the 5 disk-cache hits. Mobile RTT in the field is about 170 ms.

Before flipping the recall cards: work out what the 24 revalidations cost per page view, explain why the app's choice is not automatically wrong, and say what you would put in the report. Then the interviewer's follow-up: the merchant asks you to "cache the app's files harder". Can you? What can you actually do, and what would you refuse to do?

7. Live coding session

Type it, predict it, break it

Type this small server by hand — it is the only way to control headers on your own machine:

python3 - <<'PY'
from http.server import SimpleHTTPRequestHandler, HTTPServer
class H(SimpleHTTPRequestHandler):
    def end_headers(self):
        if self.path.endswith('fresh.js'):
            self.send_header('Cache-Control', 'max-age=600')
        if self.path.endswith('check.js'):
            self.send_header('Cache-Control', 'no-cache')
        if self.path.endswith('never.js'):
            self.send_header('Cache-Control', 'no-store')
        super().end_headers()
HTTPServer(('', 8000), H).serve_forever()
PY

Create fresh.js, check.js, never.js (any one-line content) and an index.html that loads all three. Then open http://localhost:8000 with the Network panel open and cache enabled.

Predict before your second reload: for each of the three files, will you see a byte count, a 304, or (disk cache)? Write all three down. Then reload and check.

Expected: fresh.js from cache with no request, check.js a 304, never.js a full 200 every time. Three headers, three completely different network costs, same file size.

Now throttle to Slow 4G and reload again, watching the timings. Predict which one's cost grows the most. The 304 is the interesting case: still no bytes, and now clearly expensive — the point of section 1, measured.

Break the fingerprinting idea on purpose. Change fresh.js's contents on disk and reload without clearing the cache. Predict: does the browser pick up your change? It does not, for ten minutes — which is exactly the behaviour that makes a long max-age dangerous without a content-based URL, and safe with one. Then rename it to fresh.v2.js, update the HTML, and watch it load immediately.

Remember this
  • Two questions: is it fresh? (free if yes) and has it changed? (a full round trip, even for a 304).
  • A 304 has no body and still costs one RTT. Judge caching by whether the browser talked to the server, not by bytes.
  • no-cache = "store it, always revalidate". no-store = "never keep it". Do not swap them.
  • Correctness should come from the URL, not the header: fingerprinted assets get max-age=31536000, immutable.
  • Three-line strategy: HTML no-cache + ETag; hashed assets a year plus immutable; personal data no-store, private.
  • private keeps a response out of shared caches; s-maxage gives CDNs their own shorter lifetime.
  • On a Shopify theme you usually do not own these headers — you own which URL you request, whether you request it, and your fetch cache option.
  • Always read the real header in the Network panel. Never quote one from memory, including from this lesson.

If you remember one thing: a long lifetime is safe exactly when the URL changes with the content.
