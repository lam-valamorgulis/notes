The scope chain & lexical environment

Lesson 0001 said an execution context holds "the call's own variables." This lesson opens that box: where variables actually live, and how the engine finds one when your code just writes its name.

The win: after ~30 minutes you can predict, with no doubt, whether a name inside a nested function resolves to a local, an outer, or the global variable — and explain why a classic var-in-a-loop bug happens, before we even reach closures.

1. What a lexical environment actually is

Every time a function runs, or a block ({ } after if, for, or on its own) executes, the engine creates a lexical environment. Plain words: a small record of the names declared right here, plus one link back to the record it sits inside. Per the ECMA-262 spec on lexical environments, that record has exactly two parts you should be able to name cold:

  • An environment record — the bindings declared in this exact function or block: parameters, let/const/function declarations for a block, or the full set of locals for a function.
  • A reference to the outer environment — the lexical environment of whatever code textually contains this one, fixed the moment this environment is created.

That word lexical is the whole lesson: the outer reference is decided by where the code sits on the page, not by who called it. This is different from this (lesson 0001's teaser, its own lesson later) — this is decided at the call site; the outer environment reference is decided at write time and never changes. A function called from ten different places still has exactly one, fixed outer environment.

One thing to keep separate from execution contexts Lesson 0001's execution context and this lesson's lexical environment are not two competing ideas — every execution context has a lexical environment as one of its fields. The context is the whole running-call record; the lexical environment is specifically the part that answers "what variables can this code see, and in what order."

2. The scope chain: how the engine finds a name

When your code reads an identifier, the engine does not know instantly where it lives. It searches:

  1. Look in the current lexical environment's own record. Found it? Done.
  2. Not found? Follow the outer reference to the next environment out, and look there.
  3. Repeat until found, or until the global environment is reached and still nothing turns up — then, and only then, ReferenceError: x is not defined.

This walk — environment, outer, outer's outer, … up to global — is the scope chain. It is not a separate structure the engine builds specially; it is just the outer references, followed one at a time. 

const storeName = "Anchor & Co";        // lives in the global environment

function makeGreeter(customerName) {
  const greeting = "Welcome";            // lives in makeGreeter's environment
  function greet() {
    console.log(`${greeting}, ${customerName}, to ${storeName}`);
  }
  return greet;
}

const greetLam = makeGreeter("Lam");
greetLam();   // → "Welcome, Lam, to Anchor & Co"

3. Shadowing: same name, chain stops at the first match

If an inner environment declares a binding with the same name as one further out, the inner one wins for any code inside it — the chain lookup stops at the first match, it does not keep going to "check" the outer one. The outer binding still exists; it is simply shadowed, unreachable by that name from inside.

Trap Shadowing is not a bug by itself — reusing item, i, or error as a parameter name in a nested function is completely legal. The bug shows up when you meant to read the outer one and forgot the inner one shadows it. Interviewers ask this by nesting the same name three levels deep and asking which value logs — walk the chain from the innermost environment outward, stop at the first match, done.

4. Point at it: the Scope pane in DevTools gate #3

The scope chain is not an abstraction you have to imagine — Chrome shows it to you, live, with the exact same layering as the diagram above:

  1. Open the greeter example (or your own theme code) and set a breakpoint inside the innermost function.
  2. DevTools → Sources, paused. The Scope pane on the right lists Local (the current environment's own bindings), then Closure (functionName) for each outer function environment, then Script and Global — read top to bottom, it is the scope chain.
  3. Expand each level. A name you did not expect to see at the Local level, but do see under a Closure level further down, is shadowing or an outer reference doing its job — exactly what section 2 and 3 just described.
Work drill — do this on a real theme

A Shopify theme's product-card.js has a module-level let selectedVariant = null; at the top, and further down a function renderCard(selectedVariant) that takes a parameter with the exact same name.

Before flipping the last recall card below: inside renderCard, which selectedVariant does every line of that function see — the module-level one or the parameter? What does that tell you about the bug where changing the module-level variable elsewhere in the file seems to have "no effect" inside this function?

5. Live coding session

Type it, predict it, break it

Open a scratch file. Type this without copying, using var for the loop counter:

for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}

Predict on paper, before running: what three numbers print, and in what order? Run it and check.

Now change only the keyword — let instead of var — and predict again before running:

for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}

Same loop, same callback, different output. Pause inside the arrow function with a breakpoint for both versions and compare the Scope pane: with var there is one shared environment holding one i, already 3 by the time any callback runs. With let, for creates a new block environment per iteration, so each callback's outer reference points at a different environment, each holding its own i.

6. Explain it back Feynman check

Teach it to a junior — no jargon

Say or write this out loud: a junior on your team asks "why did my three setTimeout callbacks all log 3 instead of 0, 1, 2, and why does changing var to let fix it?" You may not use the word "closure" — that word is next lesson's; explain it using only "environment," "binding," and "outer reference."

Cover, from first principles: what a lexical environment holds, why var puts its binding in one place shared by the whole loop while let makes a fresh block environment each turn, and why "fresh environment per turn" is exactly what makes the three callbacks see three different values.

If your explanation needs the listener to already know what a closure is, you borrowed next lesson's answer instead of explaining this lesson's mechanism — the "different box per iteration" fact stands on its own, before you ever ask what a callback does with that box later.

7. Prove it

The gate — only now touch the tracker Open the tree tracker and mark scope chain / lexical environment done only if all three held, from memory: (1) you explained, in plain English with no jargon, what a lexical environment holds and how the scope chain walks outward (the explain-it-back exercise above); (2) you predicted both the var and let loop outputs before running them; (3) you compared the Scope pane between the two versions in DevTools. Two out of three is zero out of three.

Anything unclear — why the outer reference never changes, how block environments differ from function environments, how this shows up in your theme code? Ask me. I am your teacher; that is what this session is for.

Remember this
  • A lexical environment = an environment record (its own bindings) + a reference to the outer environment, fixed at creation time — by where the code is written, not who calls it.
  • The scope chain is just those outer references, followed one at a time: look here, then outer, then outer's outer, until found or until ReferenceError.
  • Shadowing: an inner binding with the same name as an outer one wins for code inside it; the chain stops at the first match. The outer binding is not gone, just unreachable by that name from there.
  • var binds to the nearest function (or global) environment; let/const bind to the nearest block environment — a for (let …) loop creates a fresh block environment every single iteration.
  • DevTools' Scope pane, paused on a breakpoint, is the scope chain rendered as UI: Local → Closure(fn) → … → Script → Global, top to bottom.

If you remember one thing: every name lookup walks outward through fixed, write-time links until it finds a match — never inward, never sideways, never by who called you.
