Stratum 1 · Language & Runtime · Event loop · Lesson 0007

Long tasks, starvation & input delay

The two previous lessons were mechanism. This one turns them into a number you can put in front of a client — and into the metric Google now ranks you on.

core Domain expertise: moves ability #4 (debug with no ready answer) and ability #5 (judge someone else's work) — "the site feels slow" is not a bug report until you can split it into these three parts.

The win: after ~35 minutes you can take "the button feels laggy", split it into input delay, processing and presentation, measure each in DevTools, and say which of the three your fix would change — before writing the fix.

1. Deriving input delay from run-to-completion

Lesson 0005 proved a task cannot be interrupted. Now put a user in the picture. A customer taps Add to cart at a moment nobody controls — the middle of some other task. Three things must happen, in this order, and none of them can overlap:

  1. Input delay. The tap waits in the queue until the running task ends and the microtask checkpoint is done. Your code has not run yet. Nothing is on screen yet.
  2. Processing. Your handler runs — all of it, plus every microtask it queues.
  3. Presentation delay. The browser still has to do style, layout, paint and composite before the customer can see the result.

Add them up and you have what the user actually felt. That sum has an official name: INP — Interaction to Next Paint (web.dev — INP). It is measured to the next paint precisely because a handler that finishes fast but paints late still feels slow, and the customer cannot tell the difference.

2. Where the 50 ms rule comes from

A long task is a task that occupies the main thread for 50 ms or more. That number is not arbitrary, and being able to derive it is a small senior-signal in an interview.

Research-based guidance says a response should land within about 100 ms to feel instant. A tap arrives at a random point inside whatever task is running, so on average it waits half that task, and in the worst case almost all of it. If every task stays under 50 ms, the worst-case wait is under 50 ms — leaving the other 50 ms of the budget for your handler and the paint. Over 50 ms and the arithmetic stops working, so that is where the browser draws the line and flags it.

3. Starvation: the failure with nothing to blame

Now the case that defeats most audits. Nothing here is a long task, and the page is still unusable: 

for (const section of sections) {
  setTimeout(() => renderSection(section), 0);   // 40ms each, 30 sections
}

Thirty tasks of 40 ms. Every one is under the 50 ms line, so DevTools flags nothing. But the queue never empties for 1.2 seconds, and a tap that arrives at the start of it waits behind all thirty. This is starvation: the thread is not held by one greedy task, it is held by a crowd of polite ones. Chunking work into "small" pieces and queueing them all at once does not fix responsiveness — it only hides the evidence.

Trap Splitting a long task into smaller tasks helps only if the browser is actually allowed to breathe between them. Queue them all up front and you have starvation with a clean long-task report. Queue the next chunk only after yielding — and ideally check whether input is waiting first — and you have responsiveness. The pattern that works is a loop that yields, not a loop that schedules. 
async function renderAll(sections) {
  for (const s of sections) {
    renderSection(s);
    // end the task so a queued tap can be served before the next chunk
    await new Promise(r => setTimeout(r, 0));
  }
}

Remember lesson 0006: it must be a task yield. await Promise.resolve() here would change nothing at all — same turn, same starvation, no paint.

4. Explain it back Feynman check

Part 1 · Plain words — no jargon at all

When someone taps a button, three separate waits happen one after another. First, the browser is busy with something it cannot put down, so the tap sits in line. Second, your code for that button runs. Third, the browser redraws the screen so the person can see what changed. The person feels all three as one delay. Most of the time the first wait is the biggest, and it has nothing to do with the button.

Part 2 · One analogy, and where the analogy breaks

The analogy. A doctor's waiting room. Your appointment feels slow if the doctor was already mid-appointment when you arrived (waiting), if your own appointment is long (processing), or if you then queue at reception to get the paperwork (presentation). Complaining that the doctor is slow when you actually waited 20 minutes in the corridor misses the real problem.

Where it breaks. A waiting room lets you see the queue and lets urgent cases jump ahead. The browser has no triage: your tap cannot be prioritised over the analytics script that got there first, and the person cannot see that a queue exists — which is exactly why they tap again, adding another appointment to the same queue.

Part 3 · The sticking point

The sticking point is assuming slow interaction means slow handler. Very often the handler is 20 ms and the interaction is 400 ms, because 350 ms of it was input delay caused by code you did not write. If you optimise the handler you will move the number by 5%, tell the client you fixed it, and be wrong. Second sticking point: believing "I split it into small chunks" is the same as "the browser can respond between chunks". It is not — see starvation. A queue of thirty polite tasks blocks a tap exactly as well as one rude one.

Part 4 · Teach it back to me

Two or three sentences to a client who says: "your developers made the button faster but it still feels slow". Explain the three waits in everyday words, say which one you measured, and say what you would change next. No jargon: not "main thread", not "task", not "INP", until you have said it plainly first. Then send it to me. Being able to say this to a non-technical stakeholder is most of what "senior" means in a client agency.

5. Point at it: measure all three parts gate #3

  1. Long tasks, visually. DevTools → Performance → record while you interact. Grey Task bars with a red corner are long tasks. Enable the Interactions track: each interaction is drawn as a bar split into exactly the three parts from the diagram.
  2. The number, in the Console. Paste this and then click around — it prints every interaction over 40 ms with its duration, using PerformanceObserver: 
    new PerformanceObserver(list => {
  for (const e of list.getEntries()) {
    console.log(e.name, Math.round(e.duration) + 'ms',
      'delay:', Math.round(e.processingStart - e.startTime) + 'ms');
  }
}).observe({ type: 'event', durationThreshold: 40, buffered: true });
    The delay figure is input delay — the part your handler cannot influence.
  3. Blame it correctly. Click a long task in the flame chart and read the Bottom-Up tab: it names the script file. If the top entry is a chat widget or a reviews app, your handler was never the problem, and the fix is a loading decision, not a code change.
  4. Throttle the CPU to 4× slower before you conclude anything. A mid-range Android phone is roughly there, and it is the device most storefront customers are using.
Work drill — do this on a real theme

A client complains that the Add to cart button on a product page takes "about half a second" to respond on mobile. You record a profile with 4× CPU throttling. Your handler shows 45 ms of processing. Directly before it sits a 300 ms task whose Bottom-Up view names a reviews app script, and after your handler there is a 90 ms render.

Before flipping the recall cards: give the INP figure, name which part dominates, and say what you would propose — including what you would refuse to spend the client's hours on. Then the interviewer's follow-up: the client says the reviews app cannot be removed. What are your remaining options, in order of cost?

6. Live coding session

Type it, predict it, break it

Make a scratch HTML file with one button, and type this by hand:

<button id="b">Tap me</button>
<script>
  b.addEventListener('click', () => {
    console.log('handler ran at', Math.round(performance.now()));
  });
  function block(ms) {
    const end = performance.now() + ms;
    while (performance.now() < end) {}
  }
  setInterval(() => block(300), 350);      // a rude neighbour
</script>

Predict first: if you tap at a random moment, what is the range of possible waits before handler ran appears? Then tap ten times and watch the timestamps. You are measuring input delay by hand.

Now the starvation version. Replace the setInterval line with thirty small tasks queued at once:

  for (let i = 0; i < 30; i++) setTimeout(() => block(40), 0);

Predict: does DevTools flag a long task? Does your tap still wait about a second? Record a profile and check both answers. Seeing "no long tasks" next to a one-second delay is the lesson.

Then fix it properly — a loop that yields instead of a loop that schedules:

  (async () => {
    for (let i = 0; i < 30; i++) {
      block(40);
      await new Promise(r => setTimeout(r, 0));
    }
  })();

Tap during it and compare the timestamps with the previous run. Same total work, very different feel — and now change that one yield to await Promise.resolve() and watch the improvement disappear completely. That contrast is lesson 0006 and this lesson in one experiment.

7. Prove it

The gate — only now touch the tracker Open the tree tracker and mark long tasks, starvation, input delay done only if all three held, from memory: (1) you explained the three waits to a non-technical person — the teach-back in section 4; (2) you predicted the input-delay range before tapping, and predicted that the thirty-task version would show no long task; (3) you read a real interaction's delay figure, either from the Interactions track or from the PerformanceObserver snippet. Two out of three is zero out of three.

Remember this
  • Every interaction is three waits: input delay (queued behind other work) + processing (your handler) + presentation delay (style, layout, paint).
  • INP measures all three, to the next paint. Good is ≤ 200 ms at the 75th percentile of real users.
  • A long task is ≥ 50 ms. The number comes from the ~100 ms response budget minus the worst-case wait.
  • Most slow interactions are input delay, often caused by scripts you did not write. Optimising your handler then moves almost nothing.
  • Starvation: thirty 40 ms tasks block a tap as well as one 1.2 s task, and DevTools flags nothing.
  • Chunking works only with a loop that yields, not a loop that schedules — and the yield must reach the task queue.
  • Never conclude anything without 4× CPU throttling; that is the customer's phone.

If you remember one thing: measure which of the three waits is biggest before you fix anything — most teams optimise the smallest one.
