The task queue & one task per tick

Lesson 0001 left a hole: if nothing else can run while the stack has anything on it, how does a click ever get handled? This lesson fills the hole — and the answer explains almost every "why is my page frozen" ticket you will ever get.

core Domain expertise: moves ability #1 (explain from first principles) and ability #2 (predict an unseen case) — output ordering questions are unpredictable until this model is exact, then they are trivial.

The win: after ~30 minutes you can say what setTimeout(fn, 0) really promises, predict the order of any mix of synchronous code and timers, and explain to a client why "the button did nothing for two seconds" is not a slow button.

1. Deriving the loop from the one-stack rule

Start from what we already proved. There is one call stack per tab, and while anything is on it nothing else runs (lesson 0001). Now add an obvious fact: a user can click while your code is running. Both cannot be true unless something outside the stack is holding the click until the stack is free.

So there must be a queue, and something that feeds it into the stack. Next question: when is it allowed to feed? Two options, and only one of them can work:

  • Interrupt the running code — pause a half-finished function, run the click handler, resume. This would let a handler observe an object halfway through being updated. Every function in the language would have to be written as if it could be frozen between any two lines. Nobody could write correct code.
  • Wait until the stack is empty — let the current work finish completely, then take the next item. No function can ever be observed mid-update. This is the choice the platform made, and the HTML Standard § event loops writes it down as the processing model.

That is the event loop: pick one task from a task queue, run it until the stack is empty, then look again. The guarantee has a name — run-to-completion — and everything else in this lesson is a consequence of it.

2. What setTimeout(fn, 0) actually promises

Read the name honestly: setTimeout does not run anything. It queues a task, and the delay is a minimum wait before the task becomes eligible. So the real promise is:

What people think it meansWhat it means
"run this in 0 ms""queue a task; it may run after ≥0 ms, once the current task ends and the queue reaches it"
"run this next""run this after every microtask, and after any task already queued ahead of it"
"a way to go faster""a way to yield — to end the current task so the browser can render or handle input"

Two bare facts to keep, both mandated rather than derivable — mark them as facts, not logic. Nested timers are clamped to a minimum of about 4 ms after five levels of nesting, and timers in background tabs are throttled much harder. Do not build timing on setTimeout; use it to yield. 

console.log('1');
setTimeout(() => console.log('2'), 0);
console.log('3');
// → 1  3  2   — the script is itself one task, and it runs to completion first
Say it this way

The whole script is one task. A timer callback is a different task. There is no way for the second to start until the first has completely finished — not "usually", never.

3. The consequence you will be paid to understand

If one task must run to completion, then a task that takes 2 seconds blocks everything for 2 seconds: clicks, scrolling, animation, paint. The click is not lost — it is sitting in the queue, waiting its turn. The user sees a dead page and clicks again, which queues a second task behind the first. 

btn.addEventListener('click', () => {
  const end = Date.now() + 2000;
  while (Date.now() < end) {}          // one task, two seconds
  render();                             // the user sees nothing until here
});

This is the mechanism behind the words "long task" and "input delay", which are their own core (lesson 0007) and the basis of the INP metric (lesson 0016). Note what the fix cannot be: there is no way to ask the browser to interrupt you. You must end your task — split the work and yield — and that is only possible because you understand the loop.

4. Explain it back Feynman check

Part 1 · Plain words — no jargon at all

The browser has one worker and a waiting line of jobs. The worker takes the first job and finishes it completely. It will not put a job down half done, not even for a moment, because a half-done job could leave things in a broken state. Only when its hands are empty does it look at the line again. Your click is a job in that line. If the job the worker is holding takes two seconds, your click waits two seconds — it was never lost, it was queued.

Part 2 · One analogy, and where the analogy breaks

The analogy. A single cashier at a shop with one queue. Each customer is served completely before the next is called. A customer with a huge trolley does not get interrupted so that someone with one item can pay.

Where it breaks. A real cashier can say "one moment" and call a colleague, and a real customer can give up and leave. Neither is possible here: there is exactly one cashier and no second till, and a queued click cannot withdraw itself. Worse, the customer being served is allowed to add new items to their own trolley forever — which is how one bad loop freezes a page permanently. The only cure is that the code itself chooses to stop and rejoin the queue later.

Part 3 · The sticking point

The mistake is reading setTimeout(fn, 0) as "run now, in parallel". Nothing in a browser tab runs in parallel with your JavaScript (workers aside, which have their own stack and their own loop). Zero means "as soon as possible", and "possible" starts only when your current task has finished. The second sticking point is believing the browser can interrupt a long function if it really needs to. It cannot. Every "make it responsive" technique — chunking, await, requestIdleCallback, scheduler.yield — is a way of voluntarily ending your task early. Nothing more.

Part 4 · Teach it back to me

Two or three sentences to a client-facing project manager who asks: "why does the page ignore my clicks for two seconds after I press Add to cart, and then do all of them at once?" No jargon at all — you may not use "thread", "task" or "queue" without explaining it in everyday words first. Then send it to me. This one is also the exact answer that wins a senior interview, because most candidates explain it to the interviewer and not to the client.

5. Point at it: tasks in the Performance panel gate #3

  1. Open any storefront. DevTools → Performance → record for a few seconds while you interact, then stop.
  2. In the flame chart, the grey bars on the Main track labelled Task are literally the unit from this lesson. Click one: the summary names its duration and its cause (Event: click, Timer Fired, Parse HTML).
  3. Any task over 50 ms gets a red triangle and the label Long task. That red corner is the browser telling you a user's click had to wait. Hover to see by how much.
  4. Now prove run-to-completion by hand. In the Console: setTimeout(() => console.log('timer'), 0); const e = Date.now() + 1000; while (Date.now() < e) {}; console.log('sync done'); — the timer was eligible after 0 ms and still printed second. That output is the mechanism.
Work drill — do this on a real theme

A theme's collection page filters 900 products in JavaScript on every checkbox change. QC writes: "after ticking a filter the page hangs for about a second, and if I tick three filters quickly nothing happens for three seconds and then it jumps to the final state."

Before flipping the recall cards: explain the three-second version in terms of tasks and the queue, and say why the intermediate states were never painted. Then the interviewer's follow-up: name two mechanically different fixes — one that keeps all the work on the main thread, one that does not — and say what each gives up.

6. Live coding session

Type it, predict it, break it

Open a scratch file. Type this by hand and write the expected output on paper before running:

console.log('A');
setTimeout(() => console.log('B'), 0);
setTimeout(() => console.log('C'), 100);
console.log('D');

Then a harder one. Predict all four lines, in order, before running:

console.log('1');
setTimeout(() => {
  console.log('2');
  setTimeout(() => console.log('3'), 0);
  console.log('4');
}, 0);
console.log('5');

If you predicted 1 5 2 4 3 you have the model. If you predicted 1 5 2 3 4 you are still treating a nested setTimeout as "run now" — re-read section 2 before continuing.

Now break the page on purpose. In the Console on any page:

document.body.addEventListener('click', () => console.log('click at', Date.now()));
const end = Date.now() + 3000;
console.log('blocking from', Date.now());
while (Date.now() < end) {}            // click the page NOW, several times
console.log('unblocked at', Date.now());

Click the page four or five times while it is frozen. Predict first: are the clicks lost, or do they all arrive afterwards? Read the timestamps — they show the clicks queued during the block and ran after it. You have just measured input delay with two console.log calls.

Remember this
  • One stack, one thread — so queued work can only start when the stack is empty. That is the event loop.
  • Run-to-completion: a task is never interrupted mid-way. Chosen deliberately, so no function can be observed half-updated.
  • The whole script is one task. A timer callback, a click handler, a message event are separate tasks.
  • setTimeout(fn, 0) means "queue a task, eligible after ≥0 ms" — never "run now" and never "run next".
  • A 2-second task blocks clicks, scroll and paint for 2 seconds. The clicks are queued, not lost, then run in a burst.
  • You cannot be interrupted. Every responsiveness technique is a way to end your own task early.
  • Nested timers are clamped to about 4 ms, and background tabs are throttled harder — bare facts, not logic.

If you remember one thing: the browser cannot take the work out of your hands — you have to put it down.
