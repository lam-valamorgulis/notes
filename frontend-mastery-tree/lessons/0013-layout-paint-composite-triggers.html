Stratum 2 · Rendering Pipeline · Layout & paint · Lesson 0013

Which properties trigger layout, paint or composite

"Animate transform, not left" is advice you have read. This lesson is the reason, and the reason is not a trick — it is which stages of the pipeline the browser is forced to redo.

core Domain expertise: moves ability #3 (say what the design gives up) and ability #4 (debug with no ready answer) — a janky menu is not "a slow phone", it is a property choice you can name.

The win: after ~35 minutes you can look at any CSS animation or JavaScript style change and say which pipeline stages it costs, prove it with paint flashing, and explain why will-change on forty elements is a memory bug rather than an optimisation.

1. One rule generates the whole table

Lesson 0010 gave the pipeline: style → layout → paint → composite. Each stage consumes the output of the one before it. So there is only one rule to learn:

The rule: a change invalidates the earliest stage it affects, and every stage after that must run again. Nothing else about this topic needs memorising.

Now derive the three cases by asking what actually changed:

  • Changed the geometry — width, height, padding, margin, top, font-size, adding a node? Boxes move, so layout must run, then paint, then composite. And layout is not local: a box that grows can push its siblings and reflow its ancestors.
  • Changed only appearance — background-color, color, box-shadow, border-radius, outline? Every box is exactly where it was, so layout is skipped, but the pixels are wrong: paint, then composite.
  • Changed only where an already-painted picture goes — transform, opacity on a composited layer? The layout is unchanged and the painted texture is unchanged. Only the composite step runs, and it can happen on the compositor thread — off the main thread, so it survives a busy main thread (web.dev — Animations guide).

3. Layers: what "composited" costs

transform can skip paint only if the element has its own compositor layer — its own already-painted texture that the compositor can move around. The browser promotes an element to a layer for reasons including a 3D transform, will-change: transform, video, canvas, and some position: fixed cases.

Layers are not free. Each one is a texture held in memory and uploaded to the GPU. Promote forty product cards and you have bought forty textures to make one hover animation smooth — this is layer explosion, and on a mid-range phone it can be slower overall than the thing you were fixing (web.dev).

Trap — will-change is a hint, not a fix will-change: transform tells the browser "prepare a layer, I am about to move this". Two rules follow. Add it shortly before the animation and remove it after — a permanent will-change in a stylesheet is a permanent memory cost for an animation that may never run. And it is never a repair for animating left: the layer does not remove the layout, it only holds the painted result. Wrong property, wrong stage, no rescue.

4. Explain it back Feynman check

Part 1 · Plain words — no jargon at all

Putting a page on screen has three jobs, in order: work out where every box sits, fill in the colours, then stick the finished pieces together. If you change something about size or position, all three jobs have to be done again. If you only change a colour, the first job can be skipped. And if you only slide or fade something that was already drawn, both of the first two jobs can be skipped — the browser just moves the picture it already has, which is why that kind of movement stays smooth even when the page is busy.

Part 2 · One analogy, and where the analogy breaks

The analogy. A printed poster on a magnetic board. Changing the size of one poster means re-planning the whole board, reprinting, and re-sticking. Changing its colour means reprinting that one poster and re-sticking it. Sliding it two centimetres means only moving the magnet — nothing is re-planned and nothing is reprinted.

Where it breaks. Magnets are free; layers are not. Every poster you make individually movable costs a sheet of memory that stays used, and a phone has far less of it than a laptop. Also, the board never re-plans itself by accident — a real page can be forced to re-plan in the middle of your code just because you asked how tall something is, which is the next lesson.

Part 3 · The sticking point

People remember the conclusion — "use transform" — and lose the reason, so they cannot handle a new case. The reason is which stage is invalidated first. Get that and you can classify a property you have never seen in one question: does it change geometry, or only colour, or only where an existing picture sits? Second sticking point: believing will-change makes slow things fast. It only prepares a layer. Animate height with will-change: height and you still run layout every frame — plus you now pay for a layer.

Part 4 · Teach it back to me

Two or three sentences to a junior who says: "the mega-menu animation is janky on mobile so I added will-change: max-height and it did not help". Explain what they measured, what they changed, and what to change instead. Then send it to me — I want the words "which stage" in your answer.

5. Point at it: make the browser show you gate #3

  1. Paint flashing. DevTools → Command Menu → "Show Rendering" → tick Paint flashing. Green rectangles appear wherever the browser repaints. Hover a card, open a menu, scroll. An animation that flashes green on every frame is repainting every frame; a transform animation on a layer flashes once and then stops.
  2. Layer borders and the layer count. Same panel, tick Layer borders. Then open the Layers panel: it lists every compositor layer with an estimated memory size and the reason it was promoted. Read that reason column — it is the fastest way to find a stray will-change.
  3. Name the stages in a profile. Performance → record an interaction. The Main track shows Recalculate Style, Layout, Paint and Composite Layers as separate entries. Animate left, record, and count the Layout entries per frame. Then animate transform, record again, and watch them disappear. That before-and-after is gate #3 for this core.
  4. Frame rate honestly. Rendering panel → Frame rendering stats, with CPU throttled 4×. Judge smoothness on the throttled number, never on your laptop's.
Work drill — do this on a real theme

A theme's mega-menu opens by animating max-height from 0 to 800px over 300 ms. On a mid-range Android it visibly stutters. A previous developer added will-change: max-height to the panel and will-change: transform to all 32 nav links, which did not help and made scrolling slightly worse.

Before flipping the recall cards: name the stage the original animation pays on every frame, explain why both will-change additions were wrong — for two different reasons — and give the animation you would ship instead. Then the interviewer's follow-up: your replacement animates transform, but the menu must still push the page content down when open. How do you reconcile those, and what do you give up?

6. Live coding session

Type it, predict it, break it

One file. Type it by hand, and turn on Paint flashing before you run anything.

<!doctype html>
<style>
  .box { position: absolute; top: 40px; width: 80px; height: 80px; background: #1F6C8C }
  .slow { animation: moveLeft 2s infinite alternate }
  .fast { animation: moveTx   2s infinite alternate; top: 160px }
  @keyframes moveLeft { from { left: 0 }                 to { left: 300px } }
  @keyframes moveTx   { from { transform: translateX(0) } to { transform: translateX(300px) } }
</style>
<div class="box slow"></div>
<div class="box fast"></div>

Predict before running: which box flashes green every frame, and which one flashes once? Then record a Performance profile of five seconds and count Layout entries. The two boxes move identically on screen and cost completely different amounts.

Now prove the composite claim. Add a button that blocks the main thread for two seconds:

<button onclick="const e=Date.now()+2000; while(Date.now()<e){}">Block 2s</button>

Predict first: during the freeze, do both boxes stop, or only one? Click it and watch. The transform box keeps sliding because its animation runs on the compositor thread; the left box freezes with the main thread. This single experiment explains more than any article — and it connects straight back to lesson 0005.

Third round — the layer cost. Generate a page with 300 promoted elements and watch the Layers panel:

document.body.innerHTML = Array.from({length: 300}, (_, i) =>
  `<div style="will-change:transform;width:40px;height:40px;background:#C86A08;display:inline-block"></div>`
).join('');

Predict, then check the Layers panel's memory estimate and scroll the page. Then remove will-change:transform and compare. You have just measured the price of the "optimisation" people paste everywhere.

Remember this
  • One rule: a change invalidates the earliest stage it affects, and every later stage reruns.
  • Geometry (width, top, padding, font-size) → layout + paint + composite. Layout can spread to siblings and ancestors.
  • Appearance only (background, color, box-shadow) → paint + composite.
  • transform and opacity on a composited layer → composite only, and it runs off the main thread.
  • That last point is why a transform animation keeps moving while JavaScript is blocked, and a left animation freezes.
  • Layers cost GPU memory. Layer explosion from scattered will-change can be slower than the jank it was meant to fix.
  • will-change prepares a layer — it never removes a layout. Add it just before, remove it after.

If you remember one thing: ask which stage the change invalidates, not whether the property is "fast".
