Month 4 · Lesson 3

Dependencies & the stale closure

The dependency array is not a setting — it is a claim about what your effect reads. This is what happens when the claim is false, and the four honest ways to shorten the list.

Your win today: you can explain why a setInterval inside a component logs stale state, fix it three different ways, and say which fix fits which situation. This is the single most asked React interview question after "what is a key".

Lesson 1 said the dependency array answers a question. This lesson is about what happens when you answer it wrong — and it is never a small bug. It is the kind that survives three code reviews, cannot be reproduced on demand, and gets blamed on React.

First principle — an effect is a closure over one render

Month 1 taught you that state is a snapshot: each render gets its own count, frozen for that render. An effect is written inside that render, so it captures that render's values. Forever.

function Ticker() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1);      // which count? The one from the render that made this interval.
    }, 1000);
    return () => clearInterval(id);
  }, []);                       // ✕ the lie: this effect DOES read count

  return <h1>{count}</h1>;
}

Run it and the counter goes 0 → 1 → and stops. Not slow, not flickering — stuck at 1, forever, while the interval keeps firing every second.

Trace it once by hand and you will never be confused by it again:

The last step surprises people: why does it stop at 1 instead of flickering? Because setCount(0 + 1) keeps passing the same value, and React skips re-rendering when the new state equals the old. The interval is still running. It is just doing nothing, every second, forever.

Reactive values — what must go in the array

A value is reactive if it can be different on a later render. That is the whole rule:

ValueReactive?Goes in the array?
A propYesYes
A state variableYesYes
Anything calculated from them during renderYesYes
A function declared inside the componentYes — a new identity every renderYes, and that is usually a signal to move it inside the effect
A prop that is a functionYesYes — see the removal recipes below
A const outside the component (module scope)No — it cannot changeNo
The setter from useState (setCount)No — React guarantees a stable identityNo (the lint rule knows this)
A ref object from useRefNo — the same object every renderNo. And never list ref.current.
An imported module, window, documentNoNo

So the array is mechanical, not a judgement call: list every reactive value the effect body reads. Which is exactly what the lint rule checks for you.

The lint rule is a fact-checker, not a style rule

react-hooks/exhaustive-deps, from eslint-plugin-react-hooks, compares the values your effect reads against the values you declared. When it warns, it has found a false statement in your code.

// The line that causes more "impossible" bugs than any other in React:
useEffect(() => {
  doSomethingWith(roomId, userId);
  // eslint-disable-next-line react-hooks/exhaustive-deps
}, [roomId]);      // ✕ userId is read but not declared — now it can never update
Never suppress it A suppressed dependency warning becomes a bug report months later, with a title like "sometimes the chat shows the previous user's messages". You cannot fix a dependency array by deleting from it — you fix it by changing the code so the effect no longer reads that value. Four ways to do that follow. If none of them applies, the honest answer is that the effect really does depend on it, and re-running is correct.

Four honest ways to shorten the list

1. Use the updater form, so you do not read the state at all

useEffect(() => {
  const id = setInterval(() => {
    setCount(c => c + 1);    // ✓ asks React for the latest value; reads nothing from render
  }, 1000);
  return () => clearInterval(id);
}, []);                      // ✓ now [] is TRUE — the effect reads nothing reactive

The counter now runs forever, and the interval is created once. This is the best fix whenever all you need is "the previous value" — and it is why Month 1 taught setCount(c => c + 1) before you had a use for it.

2. Move the value inside the effect

// ✕ The object is created fresh every render, so the identity always differs…
function ChatRoom({ roomId }: { roomId: string }) {
  const [message, setMessage] = useState('');
  const options = { serverUrl: 'wss://…', roomId };   // new object every keystroke

  useEffect(() => {
    const c = createConnection(options);
    c.connect();
    return () => c.disconnect();
  }, [options]);   // …so the chat reconnects on every letter you type. Object.is again.
}

// ✓ Create it inside. Now the effect depends on a string, not on an identity.
useEffect(() => {
  const options = { serverUrl: 'wss://…', roomId };
  const c = createConnection(options);
  c.connect();
  return () => c.disconnect();
}, [roomId]);

This is the most common real-world version of the bug, and the symptom is memorable: typing in the message box drops your connection. Objects, arrays and functions created during render are new identities every time, so they can never be stable dependencies. Depend on the primitives inside them instead.

3. Split one effect into two

// ✕ One effect doing two unrelated jobs, so each job re-runs for the other's reasons
useEffect(() => {
  const c = createConnection(roomId);
  c.connect();
  logVisit(roomId, theme);       // changing the theme now reconnects the socket
  return () => c.disconnect();
}, [roomId, theme]);

// ✓ Two effects, two lifecycles, two honest arrays
useEffect(() => {
  const c = createConnection(roomId);
  c.connect();
  return () => c.disconnect();
}, [roomId]);

useEffect(() => {
  logVisit(roomId, theme);
}, [roomId, theme]);

One effect should sync one thing. If you can describe an effect only with the word "and", it should be two.

4. useEffectEvent — read the latest value without reacting to it

Sometimes an effect must read a value but must not restart when it changes. The docs' own example: a timer that ticks every second, with an adjustable step.

// ✕ Updater form is not enough — the step must be the LATEST one
useEffect(() => {
  const id = setInterval(() => setCount(c => c + increment), 1000);
  return () => clearInterval(id);
}, [increment]);
// Correct, but it destroys and recreates the interval every time the step
// changes — so the user's tick timing jumps. The array is honest; the
// re-synchronising is the problem.
// ✓ Separate the event part from the effect part
import { useState, useEffect, useEffectEvent } from 'react';

export default function Timer() {
  const [count, setCount] = useState(0);
  const [increment, setIncrement] = useState(1);

  const onTick = useEffectEvent(() => {
    setCount(c => c + increment);   // always sees the latest increment
  });

  useEffect(() => {
    const id = setInterval(() => onTick(), 1000);
    return () => clearInterval(id);
  }, []);   // ✓ truly reads nothing reactive — Effect Events are excluded from deps
}

An Effect Event behaves like an event handler that lives inside your effect: it always sees the latest props and state, and it is excluded from dependency arrays by design. The mental split is worth saying out loud: the effect decides when, the Effect Event decides what with the latest data.

Version note — check before you type it useEffectEvent is stable from React 19.2; before that it existed as experimental_useEffectEvent. Run npm ls react. On React 18 the hand-rolled equivalent is a ref that you keep up to date, which is what libraries did for years: 
const incrementRef = useRef(increment);
useEffect(() => { incrementRef.current = increment; }, [increment]);

useEffect(() => {
  const id = setInterval(() => setCount(c => c + incrementRef.current), 1000);
  return () => clearInterval(id);
}, []);   // a ref object is not reactive, so [] is honest here too
Two rules for Effect Events Only call them from inside effects — not during render, and not as a prop passed to a child. And do not reach for one to silence a dependency you actually want to react to: if the socket should reconnect when the room changes, roomId belongs in the array.

An effect has its own lifecycle — not the component's

The old mental model was "mount, update, unmount". Drop it. A component mounts once, but an effect can start and stop many times while that component stays on screen.

Component lifecycleEffect lifecycle
Mounts, updates, unmounts.Starts syncing, stops syncing. That is all it does.
Happens once, then once at the end.Can happen twenty times for one mount — once per dependency change.
"Run this on mount" is a thing you say.There is no "on mount". There is only "start syncing, because these values say so".
You think about the component's history.You think about one start/stop pair in isolation — which is why it is testable in your head.

This is why the reading test for an effect is a single question: can I describe one start and its matching stop, without knowing anything about what happened before? If yes, the effect is correct however many times it runs.

Build it for real — three dependency bugs, then three fixes

All three go in one small app so you can feel the difference between them. Keep the console open.

src/Ticker.tsx — bug 1: the classic frozen counter

import { useEffect, useState } from 'react';

export function Ticker() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    console.log('interval created');
    const id = setInterval(() => {
      console.log('tick — this closure thinks count is', count);
      setCount(count + 1);            // ✕ reads a stale count
    }, 1000);
    return () => clearInterval(id);
  }, []);                             // ✕ the lie

  return <h2>Count: {count}</h2>;
}

The console is the lesson: interval created appears once, and then every tick logs count is 0 while the screen shows 1. Two facts in one log line — the interval is alive, and it is living in the past.

src/Ticker.tsx — fix 1: stop reading the state

useEffect(() => {
  const id = setInterval(() => setCount(c => c + 1), 1000);
  return () => clearInterval(id);
}, []);    // ✓ honest: nothing reactive is read

src/StepTicker.tsx — bug 2: the fix that restarts your timer

import { useEffect, useState } from 'react';

export function StepTicker() {
  const [count, setCount] = useState(0);
  const [increment, setIncrement] = useState(1);

  useEffect(() => {
    console.log('interval created with step', increment);
    const id = setInterval(() => setCount(c => c + increment), 1000);
    return () => clearInterval(id);
  }, [increment]);   // honest — but watch what it costs

  return (
    <section>
      <h2>Count: {count}</h2>
      <button type="button" onClick={() => setIncrement(i => i + 1)}>
        step +1 (now {increment})
      </button>
    </section>
  );
}

Click the step button quickly, several times. Every click logs a new interval created, and the count barely moves — because each new interval starts its one-second wait from zero. The dependency array is correct and the behaviour is still wrong. That is the exact situation useEffectEvent exists for.

src/StepTicker.tsx — fix 2: the effect owns the timing, the event owns the data

import { useEffect, useEffectEvent, useState } from 'react';   // React 19.2+

export function StepTicker() {
  const [count, setCount] = useState(0);
  const [increment, setIncrement] = useState(1);

  const onTick = useEffectEvent(() => {
    setCount(c => c + increment);     // latest increment, no re-sync
  });

  useEffect(() => {
    console.log('interval created');  // now logs exactly once
    const id = setInterval(() => onTick(), 1000);
    return () => clearInterval(id);
  }, []);

  // …same JSX
}

src/ChatRoom.tsx — bug 3: typing disconnects the chat

import { useEffect, useState } from 'react';
import { createConnection } from './chat';   // the fake connection from Lesson 1

export function ChatRoom({ roomId }: { roomId: string }) {
  const [message, setMessage] = useState('');

  const options = { serverUrl: 'wss://example.test/chat', roomId };   // ✕ new object per render

  useEffect(() => {
    const c = createConnection(options.serverUrl, options.roomId);
    c.connect();
    return () => c.disconnect();
  }, [options]);   // ✕ compared by identity, so it changes every render

  return (
    <input value={message} onChange={e => setMessage(e.target.value)} placeholder="Message…" />
  );
}

Type "hello" and read the console: five disconnect/connect pairs, one per letter. In a real app that is five socket handshakes, a burst of "user joined" events, and a support ticket that says "the chat is flaky when I type fast".

src/ChatRoom.tsx — fix 3: depend on the value, not on the identity

const SERVER_URL = 'wss://example.test/chat';   // outside the component: not reactive

export function ChatRoom({ roomId }: { roomId: string }) {
  const [message, setMessage] = useState('');

  useEffect(() => {
    const c = createConnection(SERVER_URL, roomId);   // options built inside, if needed
    c.connect();
    return () => c.disconnect();
  }, [roomId]);   // ✓ a string — stable across keystrokes

  // …same JSX. Now typing does nothing to the connection.
}

Extend it — three reps

  1. Make the interval delay adjustable as well as the step. Then decide, out loud, which of the two belongs in the dependency array and which belongs in an Effect Event. (The delay must re-create the interval — that is a real re-sync. The step must not.)
  2. Add a onMessage function prop to ChatRoom and call it from inside the effect. The lint rule will demand it as a dependency, and an inline arrow in the parent will make it a new identity every render. Fix it with an Effect Event, and explain why useCallback in the parent is the worse answer here.
  3. Break it deliberately. Put // eslint-disable-next-line react-hooks/exhaustive-deps above one of your fixed arrays and remove a dependency. Write down the exact user-visible symptom before you run it, then check whether you predicted it. That prediction skill is what code review is.

Practice: read the situation, pick the move

Scenario

A bug report says: "the dashboard sometimes shows data for the team I was looking at before." You find one effect that fetches team data. Its array is [teamId] and the lint rule is happy. Inside, it calls a onLoaded(data) prop and reads a filters object built during render — but a colleague already "fixed" that by adding // eslint-disable-next-line two months ago, so filters and onLoaded are not in the array.

Work out, in order: which value is stale, why the symptom is intermittent rather than constant, and which of the four removal recipes applies to filters and which to onLoaded. Then say what you would delete first.

Remember this · the Feynman summary
  • An effect is a closure over one render. It keeps that render's props and state — so a long-lived interval or listener keeps old values forever.
  • A stale closure freezes, it does not flicker. setCount(0 + 1) sends the same value every time, so React stops re-rendering and the timer runs on quietly.
  • The array is a claim, not a setting: "these are the reactive values I read." Reactive = props, state, and anything computed from them.
  • Not reactive: module constants, useState setters, ref objects, imports, window. Never list ref.current.
  • react-hooks/exhaustive-deps is a fact-checker. Suppressing it is how you write a bug that survives three reviews.
  • You cannot remove a dependency by deleting it — you change the code so the effect stops reading it. Four ways: the updater form, move the value inside, split the effect in two, or use an Effect Event.
  • Objects, arrays and functions built during render are new identities every render, so they can never be stable dependencies. Depend on the primitives inside them.
  • An honest array can still be wrong behaviour: [increment] recreates the interval. useEffectEvent lets the effect keep the timing while the event reads the latest data. Stable since React 19.2; the ref pattern is the React 18 stand-in.
  • Call Effect Events only from inside effects — never during render, never as a prop.
  • An effect's lifecycle is start syncing / stop syncing, not mount / unmount. One mount, many start-stop pairs. Judge one pair in isolation.
  • Real use case (built & run): a counter frozen at 1 by a stale closure, a timer that restarted itself on every step change, and a chat that disconnected on every keystroke because of one object literal — all three fixed with a different recipe.

If you remember one thing: the dependency array is a promise about what your effect reads — keep it true by changing the code, never by shortening the list.
