Events & controlled inputs

How a keystroke becomes state — and why React wants to own the value of every input.

Your win today: you'll be able to (1) wire up any event with a correctly typed handler, (2) explain controlled vs uncontrolled inputs and say which one you'd pick and why, and (3) drive a whole form from one piece of state. This is the month where React stops being read-only and starts taking input.

Month 1 ended with a card you could click. That is one event and one number. A real app takes typing, and typing is where beginners lose the plot. The screen has its own idea of what is in the text box. React has its own idea. When those two disagree, you get the classic bug: "I type and nothing appears."

This lesson fixes that for good, from first principles.

First principle — an event is a message, state is the memory

The browser tells you something happened. It tells you once. A click, a keypress, a change — each one is a message that arrives, gets handled, and is gone.

Now put that next to UI = f(state). The screen shows state. So an event that does not end in a state update changes nothing that anyone can see.

The job of every event handler

An event handler has one real job: turn a moment into memory. Read what the user did, then put it in state. The handler is the door; state is the room.

Passing a handler — the shape that always works

You pass the function itself. React calls it later, when the event happens.

function DeleteButton() {
  function handleClick() {
    console.log('clicked');
  }

  return <button onClick={handleClick}>Delete</button>;   // no parentheses
}

When you need to pass an argument, wrap it in an inline arrow function. That arrow is the thing React calls; your real function runs inside it.

// WRONG — this calls handleDelete during render, on every render
<button onClick={handleDelete(task.id)}>✕</button>

// RIGHT — React calls the arrow on click, the arrow calls your function
<button onClick={() => handleDelete(task.id)}>✕</button>
Why the wrong one is so bad onClick={handleDelete(task.id)} runs during render and passes the return value to onClick. If handleDelete sets state, that render sets state, which causes a render, which sets state again. You get an infinite loop, and the error message rarely points at this line.

Typing events — let TypeScript do it for you

Every React handler receives one argument: the event object. It is a React SyntheticEvent — a thin wrapper over the native event, with the same API in every browser.

Here is the part people over-work. If you write the handler inline in JSX, TypeScript already knows the type. You annotate nothing.

// e is inferred as React.ChangeEvent<HTMLInputElement> — no annotation needed
<input value={query} onChange={(e) => setQuery(e.target.value)} />

You only write the type when you pull the handler out of the JSX, because then there is no context to infer from:

function handleChange(e: React.ChangeEvent<HTMLInputElement>) {
  setQuery(e.target.value);
}

function handleSubmit(e: React.FormEvent<HTMLFormElement>) {
  e.preventDefault();
  // ...
}

function handleClick(e: React.MouseEvent<HTMLButtonElement>) {
  // ...
}
You are handlingTypeThe value you want
Text input, textarea, selectReact.ChangeEvent<HTMLInputElement>e.target.value — always a string
CheckboxReact.ChangeEvent<HTMLInputElement>e.target.checked — a boolean
Form submitReact.FormEvent<HTMLFormElement>nothing — call e.preventDefault()
ClickReact.MouseEvent<HTMLButtonElement>e.currentTarget, or nothing at all
KeyboardReact.KeyboardEvent<HTMLInputElement>e.key — e.g. 'Enter', 'Escape'
One trap worth naming now A number input still gives you a string. e.target.value for <input type="number" /> is "42", not 42. Convert on the way into state: setAge(Number(e.target.value)). TypeScript will not catch this for you, because the string type is correct — it is your meaning that is wrong.

The form, and why preventDefault exists

A submit button inside a <form> makes the browser reload the page and send the data itself. That is the default behaviour from before JavaScript existed. In a React app you want to keep the page and handle the data yourself.

<form onSubmit={handleSubmit}>
  <input value={title} onChange={(e) => setTitle(e.target.value)} />
  <button type="submit">Add</button>
</form>

Use a real <form> with onSubmit, not a button with onClick. You get two things free: Enter submits, and screen readers announce it as a form. That is accessibility you did not have to write.

Bubbling — the bug in every clickable row

A React event travels up the tree. Click the ✕ inside a row, and the ✕'s handler runs, then the row's handler runs, then the row's parent's, and so on.

That is why this delete button also opens the task you just deleted:

<li onClick={() => openTask(task.id)}>
  {task.title}
  <button onClick={() => deleteTask(task.id)}>✕</button>   // deletes AND opens
</li>

The fix is to stop the message travelling further:

<button onClick={(e) => { e.stopPropagation(); deleteTask(task.id); }}>✕</button>
MethodWhat it stopsUse it when
e.preventDefault()The browser's built-in action (form reload, link navigation)Form submit, custom link behaviour
e.stopPropagation()The event reaching parent handlersA button inside a clickable card or row

They are not the same thing, and interviewers like the difference. One stops the browser. The other stops the tree.

Controlled inputs — the heart of this lesson

Now the big idea. An <input> in the DOM has its own memory. You type, and the DOM element stores your text on its own, with no help from React. That is a second source of truth, sitting right next to your state.

React gives you two choices about that.

UncontrolledControlled
Who owns the valueThe DOM elementYour React state
What you writedefaultValue="hi"value={text} onChange={...}
To read itLater, with a ref or the form dataIt is already in state, right now
Re-renders while typingNoYes — one per keystroke
Can you react to each keystroke?NoYes — filter, validate, format, disable

A controlled input is one where the value you see is computed from state on every render:

const [query, setQuery] = useState('');

<input
  value={query}                                   // state decides what is shown
  onChange={(e) => setQuery(e.target.value)}      // typing updates state
/>

Once you see step 4, the famous bug explains itself. Write value={query} and forget onChange, and the input becomes read-only:

// BROKEN — you can type, but nothing appears
<input value={query} />

You press a key. Nothing updates state. React re-renders sooner or later and writes query — still '' — back into the input. Your keystroke is erased by the very next render. React even warns you in the console about it.

The other half of the same bug value={undefined} makes an input uncontrolled. So value={user.name} where name is missing gives you an input that works fine — until data arrives and React flips it to controlled, wiping what the user typed. Use value={user.name ?? ''}. An input's value should never be null or undefined.

When uncontrolled is the right answer

Controlled is the default in this course, because it makes state the single source of truth. But uncontrolled is not a mistake — it is a trade.

  • File inputs must be uncontrolled. <input type="file" /> has a read-only value, for security. You cannot set it from state.
  • Big forms. Controlled means one re-render per keystroke. On a 40-field form that starts to cost. Month 9 covers form libraries that keep values out of React state on purpose.
  • Fire-and-forget forms. If you only need the values at submit time and nothing reacts to typing, uncontrolled is less code.

The question to ask is simple: does anything need to react to each keystroke? Live filtering, character counters, "password too short", a disabled submit button — all yes. Then you need controlled.

Many fields, one piece of state

Five inputs do not need five useState calls. Group fields that travel together into one object, and use the input's name to decide which key to update.

interface ProfileForm {
  name: string;
  email: string;
  role: 'dev' | 'design' | 'pm';
  available: boolean;
}

const [form, setForm] = useState<ProfileForm>({
  name: '', email: '', role: 'dev', available: true,
});

function handleChange(e: React.ChangeEvent<HTMLInputElement>) {
  const { name, value, type, checked } = e.target;
  setForm(prev => ({
    ...prev,                                    // keep every other field
    [name]: type === 'checkbox' ? checked : value,   // replace one field
  }));
}

Then every field shares one handler:

<input name="name"  value={form.name}  onChange={handleChange} />
<input name="email" value={form.email} onChange={handleChange} />
<input name="available" type="checkbox" checked={form.available} onChange={handleChange} />

Two details in that setForm line matter, and both come from Month 1.

  1. prev => — the new value is built from the old value, so use the updater form.
  2. ...prev — you build a new object instead of editing the old one. React compares references to decide whether anything changed. Next lesson is entirely about this rule.
Note the extra parentheses setForm(prev => ({ ...prev })) wraps the object in (). Without them, JavaScript reads { as the start of a function body, not an object. It is a silent, confusing error — and now you know why the parentheses are there.

Build it for real — a team search bar

Three controlled inputs of three different kinds, filtering one list. This is the smallest build that uses everything above. In your Vite project, replace src/App.tsx:

src/App.tsx

import { useState } from 'react';

type Role = 'all' | 'dev' | 'design' | 'pm';

interface Member {
  id: number;
  name: string;
  role: Exclude<Role, 'all'>;
  available: boolean;
}

const TEAM: Member[] = [
  { id: 1, name: 'Mai Nguyen',   role: 'dev',    available: true  },
  { id: 2, name: 'Tomas Rehak',  role: 'design', available: false },
  { id: 3, name: 'Aisha Bello',  role: 'dev',    available: false },
  { id: 4, name: 'Jun Park',     role: 'pm',     available: true  },
  { id: 5, name: 'Elena Rossi',  role: 'design', available: true  },
];

export default function TeamSearch() {
  // three controlled inputs → three pieces of state
  const [query, setQuery] = useState('');
  const [role, setRole] = useState<Role>('all');
  const [onlyAvailable, setOnlyAvailable] = useState(false);

  // DERIVED, not stored — recomputed on every render from the state above
  const visible = TEAM.filter(m => {
    const matchesQuery = m.name.toLowerCase().includes(query.trim().toLowerCase());
    const matchesRole = role === 'all' || m.role === role;
    const matchesAvailability = !onlyAvailable || m.available;
    return matchesQuery && matchesRole && matchesAvailability;
  });

  return (
    <section>
      <h1>Find a teammate</h1>

      <input
        type="search"
        placeholder="Search by name…"
        value={query}
        onChange={(e) => setQuery(e.target.value)}
      />

      <select value={role} onChange={(e) => setRole(e.target.value as Role)}>
        <option value="all">All roles</option>
        <option value="dev">Engineering</option>
        <option value="design">Design</option>
        <option value="pm">Product</option>
      </select>

      <label>
        <input
          type="checkbox"
          checked={onlyAvailable}
          onChange={(e) => setOnlyAvailable(e.target.checked)}
        />
        Available only
      </label>

      <p>{visible.length} of {TEAM.length} people</p>

      {visible.length === 0 ? (
        <p>No one matches. Try clearing a filter.</p>
      ) : (
        <ul>
          {visible.map(m => (
            <li key={m.id}>
              <b>{m.name}</b> — {m.role} {m.available ? '· free' : '· busy'}
            </li>
          ))}
        </ul>
      )}
    </section>
  );
}

Run npm run dev and prove each idea to yourself:

  1. Type in the search box. The list narrows on every keystroke. That is only possible because the input is controlled — the value reaches state immediately.
  2. Delete the onChange on the search input. Typing stops working, and the console warns you. Put it back. You have now caused and fixed the bug on purpose.
  3. Look at what is not in state. There is no visibleMembers state and no count state. Both are derived during render. Storing them would give you two truths to keep in sync.
  4. Note the as Role cast on the select. The DOM only knows strings, so e.target.value is string. You are telling TypeScript what you know and it cannot: those four option values are the only ones possible.
Try one more thing Change the checkbox to use e.target.value instead of e.target.checked. TypeScript stays quiet, and the filter breaks in a strange way — value for a checkbox is the literal string "on". A truthy string is not a boolean answer to "is it ticked?".

Remember this · the Feynman summary
  • An event is a message; state is the memory. A handler's job is to read what happened and put it in state. No state update means nothing visible changes.
  • Pass the function, don't call it: onClick={fn}, and onClick={() => fn(id)} when you need an argument.
  • Inline handlers are typed for free. Only annotate when you extract the handler — React.ChangeEvent<HTMLInputElement>, React.FormEvent<HTMLFormElement>, React.MouseEvent<HTMLButtonElement>.
  • preventDefault stops the browser (form reload, link navigation). stopPropagation stops the tree (parent handlers). Different problems.
  • Controlled input = value + onChange. The text on screen comes from state, not from your typing. Drop onChange and the input goes read-only, because the next render writes the old state back.
  • Never let an input's value be undefined or null — use value={x ?? ''}, or the input silently flips between controlled and uncontrolled.
  • Uncontrolled is a valid trade for file inputs (required), very large forms, and forms where nothing reacts to typing.
  • Group related fields in one object and update with setForm(prev => ({ ...prev, [name]: value })) — updater form plus a new object.
  • Real use case (built & run): a team search bar — text, select, and checkbox inputs, all controlled, with the filtered list and the count derived rather than stored.

If you remember one thing: in a controlled input, the user does not change the text on screen — the user changes state, and state changes the text.
