WebRTC & media in React

A camera stream is a handle to hardware, not a value. React can't diff it, shouldn't own it — but has to display it. Here's the pattern.

Your win today: you'll be able to (1) put a live camera or screen-share on screen in React without leaks (no camera LED left burning), (2) wrap an imperative call engine in a provider so React renders its truth instead of guessing, and (3) answer the video-call interview questions with patterns from a real product — a virtual-office collaboration app, our case-study codebase, whose React call stack this lesson is drawn from.

Lesson 5's rule was: the socket is a side effect, its messages are state. Media pushes that rule further. A MediaStream is a live handle to your camera and microphone — it can't be serialized, can't be diffed, and "rendering" it means wiring it into a <video> element imperatively. React's two escape hatches — refs and effects — are the entire toolkit here.

First principle — displaying a stream needs a ref

There is no <video src={stream}>. A live stream attaches to a media element through a DOM property, srcObject — and reaching a DOM node from React is exactly what refs are for:

function VideoTile({ stream, muted = false }: { stream: MediaStream; muted?: boolean }) {
  const videoRef = useRef<HTMLVideoElement>(null);

  useEffect(() => {
    const el = videoRef.current;
    if (!el) return;
    el.srcObject = stream;                    // the imperative attach — no JSX prop exists for this
    return () => { el.srcObject = null; };    // detach on unmount / stream change
  }, [stream]);

  return <video ref={videoRef} autoPlay playsInline muted={muted} />;
}

Three attributes carry real meaning: autoPlay (a live call can't wait for a play button), playsInline (iOS otherwise hijacks the video into fullscreen), and muted for your own preview — you would hear yourself, and browsers only allow autoplay-with-audio on muted elements anyway. The case-study app's createVideoElement helper does these exact steps imperatively; in React, the ref + effect pair is the same code in its proper home.

Acquiring hardware — the effect that must clean up

function CameraPreview({ deviceId }: { deviceId: string }) {
  const [stream, setStream] = useState<MediaStream | null>(null);

  useEffect(() => {
    let cancelled = false;
    navigator.mediaDevices
      .getUserMedia({ video: { deviceId: { exact: deviceId } } })  // exact: THIS camera (cf. the case-study app's settings modal)
      .then(s => {
        if (cancelled) { s.getTracks().forEach(t => t.stop()); return; }  // arrived after unmount → release immediately
        setStream(s);
      });
    return () => {
      cancelled = true;
      setStream(prev => { prev?.getTracks().forEach(t => t.stop()); return null; });
    };
  }, [deviceId]);

  return stream ? <VideoTile stream={stream} muted /> : <p>Starting camera…</p>;
}
Trap — the camera LED that never turns off track.stop() is what physically releases the device — the LED, the OS indicator, the hardware lock. Detaching srcObject or unmounting the component does not do it. Two classic leaks: forgetting cleanup entirely, and the subtler one handled above — getUserMedia is async, so the stream can resolve after unmount; without the cancelled check you stop nothing and the LED burns forever. Users notice this bug more than any other you will ever ship.

Note the division of labor: stream is in useState here — but as an opaque handle whose identity triggers re-render ("we have a stream now"), never as data you map over or spread. The moment you're tempted to put it in a store, JSON-log it, or send it anywhere — stop; it's hardware, not data.

The engine pattern — a call is a machine, React is its dashboard

A real call involves signaling, transports, producers, consumers, reconnect timers — a stateful machine with a lifetime much longer than any component. The case-study app's engine is a framework-free EventEmitter class of 2,000+ lines (xms_client.js) that knows nothing about React; the React layer (VoiceCallProvider) wraps it. This separation is the single most important design decision in the whole domain:

// ── the engine: plain TypeScript, no React (simplified case-study shape) ──
class CallEngine extends EventTarget {
  peers = new Map<string, Peer>();          // each Peer holds its MediaStream
  micPaused = false;

  async join(roomId: string) { /* signaling handshake, transports, produce */ }
  toggleMic() {
    this.micPaused = !this.micPaused;        // pause the producer + tell the server —
    this.dispatchEvent(new Event('change')); // uplink actually stops (not track.enabled!)
  }
  leave() { /* close producers, consumers, transports */ }
}
export const engine = new CallEngine();      // module singleton, like lesson 5's socket
// ── the bridge: React subscribes to the machine ──────────────────────
function useCallState() {
  return useSyncExternalStore(
    (onChange) => {                                        // subscribe
      engine.addEventListener('change', onChange);
      return () => engine.removeEventListener('change', onChange);
    },
    () => engine.snapshot()                                // read: { peers: [...], micPaused } — a plain object
  );
}

function MicButton() {
  const { micPaused } = useCallState();                    // truth comes FROM the engine…
  return (
    <button onClick={() => engine.toggleMic()}>           // …commands go TO the engine
      {micPaused ? '🔇 Unmute' : '🎙 Mute'}
    </button>
  );
}

Commands flow down (engine.toggleMic()), state flows up (events → snapshot → render). The button holds no state of its own — and that's the point:

Trap — the mute button that lies The junior version: const [muted, setMuted] = useState(false) in the button, toggled on click. Now there are two copies of the truth — the component's boolean and the engine's actual producer — and they drift: the engine can mute without you (server-side moderation, device unplugged, reconnect restoring state), and the button smiles "🎙 on" while the mic is dead. The case-study app reads mute state from producer.paused — the object that actually knows. UI state that mirrors an external system must be derived from it, never duplicated.
The architecture, in one line

The engine owns the call; React renders a snapshot of it. Same shape as lesson 5 — singleton + subscription + state — just with a bigger machine on the other side of the border.

Rendering peers — Month 1's keys, with faces

function VideoGrid() {
  const { peers } = useCallState();          // Peer[] from the engine's Map
  return (
    <div className="grid">
      {peers.map(peer => (
        <VideoTile key={peer.userId} stream={peer.stream} />   // key = identity, NOT index
      ))}
    </div>
  );
}

Why the key matters more than usual here: in a real room the peer list churns — the case-study app shows video for only the 3 loudest speakers and swaps who's in that window as the conversation moves. With key={peer.userId}, React moves the existing <video> elements and only mounts tiles for genuinely new speakers. With key={index}, a swap re-attaches every stream to the wrong element — a heavy, visible glitch (video flashes black) instead of a free reorder. Reconciliation (Lesson 3) stops being abstract the day each list item owns a hardware pipeline.

Two UX details that separate real products

  • Screen share ends outside your UI. getDisplayMedia shows a browser-owned "Stop sharing" bar, and users click that, not your button. The track fires ended — the engine listens (track.onended), runs the same cleanup as your stop button, and emits a change event so React updates. Miss it and your UI says "sharing" while nothing flows. (The case-study app wires exactly this on the producer's trackended.)
  • Devices come and go mid-call. Headsets unplug; permissions change in browser settings. The case-study app's useDeviceManager subscribes to navigator.mediaDevices.ondevicechange and navigator.permissions.query({ name: 'camera' }).onchange — both are effects with cleanup, both end in setState, and the device dropdown is again just UI = f(devices). When the active mic disappears, it auto-selects a replacement rather than leaving the call silent.
Drill — the settings preview

Build the camera-settings panel: a dropdown of cameras and a live preview of the selected one (the case-study app has exactly this modal). Requirements: switching cameras must release the old one (LED off), closing the panel must release everything, and the preview must be silent.

Remember this
  • A MediaStream is a hardware handle, not data: attach it with a ref via el.srcObject; hold it in state only as an opaque identity.
  • track.stop() releases the device — unmounting does not. Guard the async gap: a stream that resolves after unmount must be stopped on arrival.
  • Local preview: autoPlay playsInline muted — each word load-bearing.
  • Engine pattern: the call lives in a framework-free singleton class; React subscribes (useSyncExternalStore or events→state) and renders a snapshot. Commands down, events up.
  • Never duplicate external truth: the mute button reads the engine's state (producer.paused), it doesn't keep its own boolean.
  • Peer grids churn — key={userId} makes reorders free; key={index} re-attaches every stream on every swap.
  • Handle the exits you don't own: the browser's "Stop sharing" bar (track.onended) and devices unplugging mid-call (ondevicechange).

If you remember one thing: the engine owns the call and React renders its snapshot — refs to attach hardware to the DOM, effects to acquire and release it, and no component ever keeping a private copy of the truth.
