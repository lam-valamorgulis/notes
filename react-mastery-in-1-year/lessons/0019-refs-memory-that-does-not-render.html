Refs — memory that does not cause a render

State is memory React watches. A ref is memory React ignores. Choosing the wrong one is how you get a component that is either wasteful or haunted.

Your win today: a two-second rule for deciding between useState and useRef, a stopwatch you can write from memory with no leaking interval, and the one rule that stops a ref from making your screen lie.

Month 4 was about talking to the outside world. Every one of those effects needed a value that the user never sees: a timer id, an AbortController, a socket. We stored them in plain local variables inside the effect, which worked because they died with the effect.

This month those values have to outlive the effect. A stopwatch is started by a button and stopped by another button — two separate handlers, one shared timer id. That is memory. And it is memory of a kind we have not had yet.

First principle — a component needs two kinds of memory

Start from what you already know. A component function runs from the top on every render. So a plain let inside it is not memory at all — it is born and dies with one render.

function Stopwatch() {
  let intervalId = null;        // ✕ back to null on every single render

  function handleStart() {
    intervalId = setInterval(tick, 10);
  }
  function handleStop() {
    clearInterval(intervalId);  // ✕ always null here — the timer never stops
  }
}

Moving it up to module scope makes it survive, and creates a worse bug: now every <Stopwatch /> on the page shares one box.

let intervalId = null;          // ✕ shared by every instance of the component

function Stopwatch() { /* ... */ }

So the thing we need is a box that is per component instance and kept between renders. React already has exactly one of those: state. But state has a second job bolted onto it — writing to it schedules a render. And a timer id is not on screen. Re-rendering because it changed is pure waste, and if an effect depends on it you get the loop from lesson 15.

That is the whole reason refs exist. Two kinds of memory, split by one question: does the screen need to follow this value?

React docs · Referencing Values with Refs "When you want a component to remember some information, but you don't want that information to trigger new renders, you can use a ref." … "Like state, refs are retained by React between re-renders. However, setting state re-renders a component. Changing a ref does not!"

A ref is a state variable without a setter

This is the sentence that makes refs stop feeling magical. The React docs spell it out — useRef could be written on top of useState:

React docs · Deep Dive: How does useRef work inside? "Although both useState and useRef are provided by React, in principle useRef could be implemented on top of useState. You can imagine that inside of React, useRef is implemented like this:" 
// Inside of React
function useRef(initialValue) {
  const [ref, unused] = useState({ current: initialValue });
  return ref;
}
"React provides a built-in version of useRef because it is common enough in practice. But you can think of it as a regular state variable without a setter. If you're familiar with object-oriented programming, refs might remind you of instance fields — but instead of this.something you write somethingRef.current."

Three consequences fall straight out of that code, and each one shows up in real work:

  1. The object is the same object on every render. It is held in state and never replaced. That is why a ref object is not a reactive value and never belongs in a dependency array — the fact you memorised in lesson 17.
  2. The value lives in .current, and it is yours to mutate. The box is stable; the contents are not. This is the one place in React where mutation is normal and correct.
  3. Writing .current tells React nothing. No render, no Object.is comparison, no batching, no queue. It is a plain JavaScript assignment to a plain JavaScript object.

The table to be able to draw from memory

Straight from the docs, because in an interview this is asked almost word for word:

useRef(initialValue) returns { current: initialValue }useState(initialValue) returns the current value and a setter ([value, setValue])

And the practical version — the one you actually run in your head while typing:

Look at the last row. "Unless it changes appearance" is not hedging — it is the rule doing its job. The same fact can belong in either lane depending on whether the screen reads it.

The one rule: never read or write a ref during render

Render must be a pure calculation of the screen from props and state (lesson 15). A ref is a value React does not track, so touching it during render breaks that promise in both directions: write to it and you have made rendering do something; read from it and your output depends on a value React never compared.

React docs · useRef caveats "Do not write or read ref.current during rendering, except for initialization. This makes your component's behavior unpredictable." … "You can read or write refs from event handlers or effects instead." … "If you have to read or write something during rendering, use state instead."

The exception is worth memorising, because it is the standard way to create one expensive object per component:

function Video() {
  const playerRef = useRef(null);
  if (playerRef.current === null) {
    playerRef.current = new VideoPlayer();   // ✓ allowed: runs once, always the same result
  }
  // ...
}
React docs · Avoiding recreating the ref contents "Normally, writing or reading ref.current during render is not allowed. However, it's fine in this case because the result is always the same, and the condition only executes during initialization so it's fully predictable."

Why not useRef(new VideoPlayer())? Because that argument is evaluated on every render and then thrown away on all but the first. With a cheap value like null or 0 nobody cares. With a constructor that opens a connection, you have just opened one per render.

Build it for real — part 1: make the screen lie

Before the correct build, spend four minutes proving to yourself what "React is not told" means. Create a component with a counter kept in a ref.

src/RefLie.tsx

import { useRef, useState } from 'react';

export function RefLie() {
  const countRef = useRef(0);
  const [note, setNote] = useState('');

  function handleClick() {
    countRef.current = countRef.current + 1;
    console.log('the ref really is', countRef.current);   // the value is correct
  }

  return (
    <section>
      <button onClick={handleClick}>Clicked {countRef.current} times</button>
      <input value={note} onChange={e => setNote(e.target.value)} placeholder="type anything" />
    </section>
  );
}

Click the button five times. The console counts to 5. The button still says 0. Now type one letter in the input — the button jumps to 5.

Nothing here is broken and nothing is racing. The ref was correct the entire time. What was wrong was asking the screen to display a value React was never told about. The letter you typed set state, which caused a render, and that render happened to read the ref again.

The symptom to recognise "The value updates, but only when I click something else." Nine times out of ten that is a value that should be in state, being kept in a ref — or an object being mutated instead of replaced, which is the same mistake wearing lesson 8's clothes. Both are "React was never told".

Build it for real — part 2: a stopwatch with no leaks

Now the real thing, and the canonical use of a ref. Two buttons, two handlers, one shared timer id that the screen never sees.

Plan the state first, the habit from Month 3:

ValueLaneWhy
startTimestateThe elapsed time is computed from it, and the elapsed time is on screen.
nowstateUpdated ten times a second in order to redraw. Re-rendering is the point.
secondsPassedneither — derived(now - startTime) / 1000. Derive, don't store.
intervalRefrefWritten by Start, read by Stop, never drawn. A render would be waste.

src/Stopwatch.tsx

import { useEffect, useRef, useState } from 'react';

export function Stopwatch() {
  const [startTime, setStartTime] = useState<number | null>(null);
  const [now, setNow] = useState<number | null>(null);
  const intervalRef = useRef<ReturnType<typeof setInterval> | null>(null);

  function handleStart() {
    setStartTime(Date.now());
    setNow(Date.now());

    if (intervalRef.current !== null) clearInterval(intervalRef.current);
    intervalRef.current = setInterval(() => {
      setNow(Date.now());          // the only reason this component re-renders
    }, 10);
  }

  function handleStop() {
    if (intervalRef.current !== null) {
      clearInterval(intervalRef.current);
      intervalRef.current = null;  // ✓ leave the box in an honest state
    }
  }

  // The component being removed is not a user action, so it is not a handler's job.
  useEffect(() => {
    return () => {
      if (intervalRef.current !== null) clearInterval(intervalRef.current);
    };
  }, []);

  let secondsPassed = 0;
  if (startTime !== null && now !== null) {
    secondsPassed = (now - startTime) / 1000;
  }

  return (
    <section>
      <h1>Time passed: {secondsPassed.toFixed(3)}</h1>
      <button onClick={handleStart}>Start</button>
      <button onClick={handleStop}>Stop</button>
    </section>
  );
}

Four things in that file are worth saying out loud, because each is a decision and not a detail.

1. The timer is started by a click, so it lives in a handler

This is the lesson-16 question, answered: the interval exists because the user pressed Start, not because the component is on screen. So it does not belong in an effect. The cleanup effect at the bottom is the other half of the same answer — unmounting is not a user action, so that is effect work.

This is the pair to memorise A timer started by an event: create it in the handler, keep the id in a ref, and clear it in an unmount-only cleanup. A timer that exists because the component is on screen: create it in an effect and clear it in that effect's cleanup — no ref needed, because a local variable already survives long enough.

2. The docs' version of this example leaks, and yours should not

The React docs show this stopwatch without the cleanup effect, which is fine in a sandbox that never unmounts. In a real app, start the stopwatch and navigate away: the interval keeps firing, calling setNow on a component that is gone. React 18 and later will not warn you about this — the old "can't perform a state update on an unmounted component" warning was removed as a false alarm — so nothing on your screen tells you it is happening. It is a real leak all the same: the callback holds the component's closure alive, and on a page that mounts the stopwatch many times you accumulate timers.

3. The TypeScript type of a timer id is not number

In the browser setInterval returns a number. But if @types/node is anywhere in your project — and with Vite it is — TypeScript may resolve the Node overload, which returns a Timeout object. Two honest fixes:

// Option A — let TypeScript work it out. Correct in both environments.
const intervalRef = useRef<ReturnType<typeof setInterval> | null>(null);

// Option B — say explicitly that you mean the browser's timer.
const intervalRef = useRef<number | null>(null);
intervalRef.current = window.setInterval(tick, 10);   // window.setInterval returns number

Do not reach for as any or NodeJS.Timeout. Both are people guessing at the wrong environment.

4. Strict Mode creates every ref twice

React docs · useRef caveats "In Strict Mode, React will call your component function twice in order to help you find accidental impurities. This is development-only behavior and does not affect production. Each ref object will be created twice, but one of the versions will be discarded. If your component function is pure (as it should be), this should not affect the behavior."

Read the last sentence as a test you can run. If your component behaves differently in Strict Mode, the ref is not the problem — you are doing something during render that should not be there.

The six real jobs of a ref

The docs describe refs as an escape hatch for "rare situations", and the list really is short. If your ref is not doing one of these six jobs, look again.

#JobTypical shape
1Timer and animation ids — setTimeout, setInterval, requestAnimationFrame.useRef<ReturnType<typeof setTimeout> | null>(null)
2Cancellation handles — an AbortController that must survive past the function that made it.useRef<AbortController | null>(null)
3DOM nodes — the whole of the next lesson.useRef<HTMLInputElement>(null)
4The latest-value box — read fresh data from a long-lived callback without re-subscribing.a ref updated in an effect on every commit
5Facts about the past — the previous value, "has this already run", "is the user mid-drag".useRef(value) / useRef(false)
6One expensive object per component — an observer, a parser, a player, a cache.the if (ref.current === null) initialisation above

Job 4 in code — the latest-value box

You met this in lesson 17 as the React 18 stand-in for useEffectEvent. Now you can see why it works: a ref is not reactive, so reading it inside a long-lived callback never restarts anything.

const onMessageRef = useRef(onMessage);

useEffect(() => {
  onMessageRef.current = onMessage;   // no dependency array: keep it fresh on every commit
});

useEffect(() => {
  const socket = createConnection(roomId);
  socket.on('message', msg => onMessageRef.current(msg));  // always the latest fn
  return () => socket.disconnect();
}, [roomId]);                          // ✓ honest, and does not react to onMessage

On React 19.2 and later, prefer useEffectEvent — it says the intent out loud. Keep this pattern for older versions and for reading the latest value from something that is not an effect at all, such as a DOM listener you attached yourself.

Job 5 in code — and the trap inside it

const prevQueryRef = useRef(query);

useEffect(() => {
  prevQueryRef.current = query;        // after the commit, so during render it is the OLD value
});

This is genuinely useful for logging, analytics, and "did this change?" decisions inside effects. But notice what you must not do with it: read it during render to draw something. That breaks the one rule, and it is also subtly wrong — the ref is updated after the commit, so a render triggered by something else will see a "previous" value that is now the current one.

If the screen needs the previous value Use the tool from lesson 16 instead: keep the previous value in state and adjust it during render (if (items !== prevItems) { setPrevItems(items); … }). A ref is for facts your code needs. State is for facts the screen needs. The word "previous" does not decide the lane; the reader does.

Extend it — three reps

  1. Add laps. A Lap button pushes the current secondsPassed into a list. Decide the lane before you type: the list is drawn, so it is state — and it must be replaced, not pushed into (lesson 8). Then ask why the lap count needs no separate state at all.
  2. Survive a reload. On Start, write startTime to localStorage; on mount, read it back and resume. Note which parts are handler work and which are effect work, and that the resumed elapsed time comes from Date.now() arithmetic rather than from a count of ticks.
  3. Break it on purpose. Move now from state into a ref. Predict the exact symptom in writing first, then run it. You should get a clock frozen at 0.000 that suddenly displays the truth the moment you press Stop — because handleStop does not re-render either, but pressing a button that calls setState anywhere would.

Practice: read the situation, pick the move

Scenario

A colleague opens a pull request titled "reduce re-renders". It changes three things in a form component: const [isSaving, setIsSaving] = useState(false) becomes const isSavingRef = useRef(false); the submit button now reads disabled={isSavingRef.current}; and a new const validationErrorsRef = useRef<string[]>([]) replaces the errors state, with the error list rendered from validationErrorsRef.current. The PR description says "these values do not need to trigger renders". Locally, the author says it works.

Work out, in order: which of the three changes are wrong and by what rule; the exact user-visible symptom of each; why it can look fine when clicked slowly by the author; and whether any value in this component legitimately belongs in a ref. Then write the one-sentence review comment you would actually leave.

Remember this · the Feynman summary
  • A component needs two kinds of memory. A local let dies with the render; a module variable is shared by every instance. Refs and state are the two per-instance boxes React keeps.
  • State is memory React watches. A ref is memory React ignores. Setting state re-renders; changing a ref does not.
  • One question picks the lane: does the user read this value on the screen? Yes → state. No → ref.
  • A ref is a state variable without a setter. useRef could be built on useState({current: value}) and never calling the setter — which is why the object identity is stable forever.
  • A ref that the screen reads is a screen that lies, and it lies quietly until an unrelated render happens to reveal the truth.
  • Never read or write ref.current during render. Handlers and effects only. The single exception is one-time initialisation: if (ref.current === null) ref.current = new Thing().
  • useRef(new Thing()) builds the thing on every render and throws it away. Pass null and initialise inside the guard.
  • The six jobs: timer ids, cancellation handles, DOM nodes, the latest-value box, facts about the past, and one expensive object per component.
  • Timer started by a click → handler + a ref for the id + an unmount cleanup. Timer that exists because the component is on screen → effect + its own cleanup, no ref needed.
  • A timer id is not typed number when @types/node is present. Use ReturnType<typeof setInterval>, or window.setInterval and number.
  • Strict Mode creates each ref twice and discards one. If that changes your behaviour, your render is impure.
  • Real use case (built & run): a ref counter that showed 0 after five clicks, then a stopwatch where the interval id is a ref, the elapsed time is derived, and the interval is cleared both by the Stop button and on the way out.

If you remember one thing: put a value in a ref when the screen must not follow it — and the moment the screen needs it, that value was always state.
