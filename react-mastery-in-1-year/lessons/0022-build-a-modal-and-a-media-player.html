Month 5 · Lesson 4 · The real build

Build it — a click-outside modal & a custom media player

Two features that look like UI work and are really ownership work: who owns focus, and who owns the truth about whether the video is playing.

Your win today: a modal that closes on Escape and on an outside click, moves focus in, traps it, and gives it back — and a media player whose buttons never disagree with the video, even when the user drives it with the native controls. Plus the two sentences that get you through the "build a modal, live" interview task.

This is the month's headline build, and the most requested live-coding task that involves refs. Both halves are the same lesson wearing different clothes: something outside React already has state, and your job is to command it without lying about it.

Part A — a modal is eight requirements, not one component

Most people build the first row of this table and stop. The rest is what separates a modal from a floating div.

#RequirementTool
1It appears above everything, whatever its parent's overflow or z-index.createPortal
2Assistive tech knows it is a dialog and what it is called.role="dialog", aria-modal="true", aria-labelledby
3Escape closes it.a keydown effect
4Clicking outside closes it.a pointerdown effect + node.contains()
5Focus moves into it when it opens.a ref + focus()
6Tab cannot escape while it is open.onKeyDown on the panel + a focusable-elements query
7Focus returns to whatever opened it.document.activeElement saved in a ref, restored in the cleanup
8The page behind does not scroll.document.body.style.overflow in an effect, restored in the cleanup

Read the right-hand column again. Requirements 3, 4, 7 and 8 are all setup / cleanup pairs — Month 4's shape. Requirements 5 and 6 are non-destructive DOM commands — lesson 20's safe column. You already have every tool. What is new is the discipline of not forgetting six of the eight.

Stage 1 — the version everybody writes first

src/Modal.tsx — stage 1, five bugs

type Props = { open: boolean; onClose: () => void; children: React.ReactNode };

export function Modal({ open, onClose, children }: Props) {
  if (!open) return null;

  return (
    <div className="overlay" onClick={onClose}>
      <div className="panel" onClick={e => e.stopPropagation()}>
        {children}
        <button onClick={onClose}>Close</button>
      </div>
    </div>
  );
}
BugHow to see it in ten seconds
1. Escape does nothing.Open it and press Escape. Every other dialog on the web closes; this one does not.
2. Focus never moves.Open it and press Tab. You are tabbing through the page behind the modal, invisibly.
3. Focus never comes back.Close it with the Close button and press Tab. You are at the top of the document, not at the button you clicked.
4. Select text and release outside → it closes.Drag to select a sentence in the panel and let go over the dark area. click fires on the common ancestor, so the modal closes and takes your selection with it.
5. The page behind scrolls.Scroll with the wheel over the overlay. On a long page, the content moves behind the dialog.

Bug 4 is the interesting one, because stopPropagation looks like it handles the inside/outside question and does not. A click event fires on the nearest common ancestor of where the pointer went down and where it came up. Press inside, release outside, and the "click" belongs to the overlay. The user's own text selection closed the dialog.

Stage 2 — a portal and the right roles

import { createPortal } from 'react-dom';

export function Modal({ open, onClose, title, children }: Props) {
  if (!open) return null;

  return createPortal(
    <div className="overlay">
      <div
        className="panel"
        ref={panelRef}
        role="dialog"
        aria-modal="true"
        aria-labelledby="modal-title"
        tabIndex={-1}          // so stage 5 can move focus onto the panel itself
        onKeyDown={handleKeyDown}
      >
        <h2 id="modal-title">{title}</h2>
        {children}
      </div>
    </div>,
    document.body,
  );
}

Why a portal. A modal nested inside a card with overflow: hidden gets clipped; inside a transformed ancestor, position: fixed stops meaning "the viewport"; and any ancestor z-index can trap it below a sticky header. Rendering into document.body removes all three problems at once. Events still bubble through your React tree, which is the part people expect to break and it does not — onClose handlers, context, and state all keep working exactly as if the JSX were where you wrote it.

Stage 3 — Escape

useEffect(() => {
  if (!open) return;

  function handleKeyDown(event: KeyboardEvent) {
    if (event.key === 'Escape') onClose();
  }

  document.addEventListener('keydown', handleKeyDown);
  return () => document.removeEventListener('keydown', handleKeyDown);
}, [open, onClose]);

Two decisions in five lines. if (!open) return keeps the effect honest — no listener exists while the modal is closed, which is better than one listener that checks a flag. And onClose is in the dependency array because it is a function prop, so the array is a true statement (lesson 17). If the parent passes an inline arrow the effect re-subscribes on every parent render; that is cheap here, and if it ever is not, the fix is an Effect Event, not a shorter array.

Stage 4 — clicking outside, without the text-selection bug

const panelRef = useRef<HTMLDivElement>(null);

useEffect(() => {
  if (!open) return;

  function handlePointerDown(event: PointerEvent) {
    const panel = panelRef.current;
    if (panel !== null && !panel.contains(event.target as Node)) {
      onClose();
    }
  }

  document.addEventListener('pointerdown', handlePointerDown);
  return () => document.removeEventListener('pointerdown', handlePointerDown);
}, [open, onClose]);
ApproachVerdict
onClick on the overlay + stopPropagation on the panelSimple, and wrong for drag-select. Also breaks if any child stops propagation itself.
click listener on document + contains()Same drag-select problem — click is reported on the common ancestor — plus a real risk of closing on the very click that opened it.
pointerdown on document + contains()What to use. It asks the right question ("did the press start outside?"), and the press that opened the modal happened before this listener existed.
The "it closes the instant I open it" bug If you listen for click on document, the same click that opened the modal can still be travelling up the tree when your listener is attached — so it is seen as an outside click and the modal shuts immediately. Whether it happens depends on exactly when React commits and runs the effect, which is a terrible thing for a feature to depend on. Listening for pointerdown removes the question entirely, because the press that opened the dialog finished before the listener existed. Guard flags and setTimeout(…, 0) both "work" and both are the wrong answer.

One more detail worth knowing: panel.contains(event.target) is what makes the portal safe. The panel is in document.body, so a click inside it is genuinely inside that DOM subtree — a check based on the React tree would have to be much cleverer for no gain.

Stage 5 — focus in, focus trapped, focus back

const restoreFocusRef = useRef<HTMLElement | null>(null);

useEffect(() => {
  if (!open) return;

  restoreFocusRef.current = document.activeElement as HTMLElement | null;
  panelRef.current?.focus();          // the panel has tabIndex={-1} so it can receive focus

  return () => {
    restoreFocusRef.current?.focus(); // ✓ give it back on the way out
  };
}, [open]);

And the trap itself. Keep it on the panel with onKeyDown — a JSX prop, because one exists (lesson 21's rule) — rather than another document listener:

const FOCUSABLE = 'a[href], button:not([disabled]), input:not([disabled]), select, textarea, [tabindex]:not([tabindex="-1"])';

function handleKeyDown(event: React.KeyboardEvent<HTMLDivElement>) {
  if (event.key !== 'Tab') return;

  const panel = panelRef.current;
  if (panel === null) return;

  const items = Array.from(panel.querySelectorAll<HTMLElement>(FOCUSABLE));
  if (items.length === 0) return;

  const first = items[0];
  const last = items[items.length - 1];

  if (!event.shiftKey && document.activeElement === last) {
    event.preventDefault();
    first.focus();                    // wrap forwards
  } else if (event.shiftKey && document.activeElement === first) {
    event.preventDefault();
    last.focus();                     // wrap backwards
  }
}

Query the focusable elements at the moment Tab is pressed, not once when the modal opens. A dialog's contents change — a validation error appears, a button becomes enabled — and a list captured at open time sends focus to a node that is no longer there.

Stage 6 — stop the page behind from scrolling

useEffect(() => {
  if (!open) return;

  const previous = document.body.style.overflow;
  document.body.style.overflow = 'hidden';
  return () => {
    document.body.style.overflow = previous;   // ✓ restore, don't assume it was ''
  };
}, [open]);

This is a legitimate manual DOM change, and it is worth knowing exactly why: document.body is not rendered by React, so React has no reason to touch its inline style. That is precisely the carve-out the docs allow. Saving and restoring the previous value rather than setting '' is what makes it safe to nest — two modals, or a modal inside a drawer, and the last cleanup puts back what was really there.

The honest alternative: the browser already has a modal

Everything above is worth building once, because it teaches refs, portals, and setup/cleanup pairs at the same time. But you should know what you are competing with. A native <dialog> opened with showModal() gives you the top layer, the focus move, the focus trap, Escape, and a styleable backdrop — for free.

export function NativeModal({ open, onClose, title, children }: Props) {
  const dialogRef = useRef<HTMLDialogElement>(null);

  // The dialog's open/closed state lives in the DOM, so this is a sync — an effect.
  useEffect(() => {
    const dialog = dialogRef.current;
    if (dialog === null) return;

    if (open && !dialog.open) dialog.showModal();
    if (!open && dialog.open) dialog.close();
  }, [open]);

  return (
    <dialog ref={dialogRef} onClose={onClose} aria-labelledby="modal-title">
      <h2 id="modal-title">{title}</h2>
      {children}
    </dialog>
  );
}

Look at what that effect is: "make the DOM's state match my prop" — the definition of an effect from lesson 15, with two guards because showModal() on an already-open dialog throws. The onClose prop of <dialog> is the element's own close event, so Escape and close() both flow back into React through one path.

What to actually ship Use <dialog> when it fits, and a maintained library (React Aria, Radix, Headless UI) when the design needs more — nested dialogs, animated exits, scroll containers inside. Full accessible dialog behaviour includes cases this lesson does not cover, such as making the rest of the page inert for screen readers. Build the hand-rolled version to understand it; do not defend it in a code review as better than the platform.

Part B — a media player, and two versions of the truth

Now the second half, and a different flavour of the same problem. A <video> element is a state machine that exists whether or not React is watching: it knows if it is playing, where the playhead is, how long the media runs, whether it is muted. Your React component wants to draw all of that.

So there are two copies of the truth, and the whole design is deciding which one wins.

DirectionHowExamples
Commands down — you tell the element to do somethingImperatively, through a ref, inside an event handlerplay(), pause(), currentTime = 30, volume = 0.5, playbackRate = 1.5
Truth up — the element tells you what happenedMedia events → setState, so the screen can draw itonPlay, onPause, onTimeUpdate, onLoadedMetadata, onEnded, onVolumeChange

Stage 1 — the wrong version, and why it breaks in the demo

const [isPlaying, setIsPlaying] = useState(false);

useEffect(() => {
  if (isPlaying) videoRef.current?.play();     // ✕ React state pretends to be the truth
  else videoRef.current?.pause();
}, [isPlaying]);

<button onClick={() => setIsPlaying(p => !p)}>{isPlaying ? 'Pause' : 'Play'}</button>

It works when you only ever use your own button. Then reality arrives:

What the user doesWhat breaks
Uses the browser's own controls, or the media keys on the keyboardThe video pauses, your isPlaying stays true, and the button now says "Pause" over a paused video. Pressing it does nothing, because the effect's state did not change.
Loads the page and the browser blocks autoplayplay() returns a rejected promise (NotAllowedError) that nobody handled. Your state says playing; nothing is playing; the console has an unhandled rejection.
Clicks Play then Pause quicklypause() interrupts the pending play() promise, which rejects with AbortError: "The play() request was interrupted by a call to pause()".
Lets the video reach the endThe element pauses itself. Your button still says "Pause". Clicking it calls pause() on an already-paused video and nothing happens — the classic "the play button is dead" report.

All four are one mistake: you made a mirror the source of truth. The element is going to change state without asking you, so any design that assumes otherwise has to be wrong eventually.

Stage 2 — commands in handlers, truth from events

src/formatTime.ts

export function formatTime(seconds: number): string {
  if (!Number.isFinite(seconds)) return '--:--';   // duration is NaN before metadata loads
  const total = Math.floor(seconds);
  const mm = String(Math.floor(total / 60)).padStart(2, '0');
  const ss = String(total % 60).padStart(2, '0');
  return `${mm}:${ss}`;
}

src/Player.tsx — stage 2

import { useRef, useState } from 'react';
import { formatTime } from './formatTime';

export function Player({ src }: { src: string }) {
  const videoRef = useRef<HTMLVideoElement>(null);

  // All three are MIRRORS of the element, updated only by its events.
  const [isPlaying, setIsPlaying] = useState(false);
  const [currentTime, setCurrentTime] = useState(0);
  const [duration, setDuration] = useState(NaN);

  async function handleToggle() {
    const video = videoRef.current;
    if (video === null) return;

    if (video.paused) {              // ✓ ask the element, never our own state
      try {
        await video.play();          // ✓ a promise: it can be refused
      } catch (error) {
        if ((error as DOMException).name !== 'AbortError') {
          console.warn('play was refused', error);   // autoplay policy, missing file…
        }
      }
    } else {
      video.pause();
    }
    // Note what is NOT here: no setIsPlaying. The play/pause events do that.
  }

  return (
    <section>
      <video
        ref={videoRef}
        src={src}
        playsInline
        onPlay={() => setIsPlaying(true)}
        onPause={() => setIsPlaying(false)}
        onEnded={() => setIsPlaying(false)}
        onTimeUpdate={e => setCurrentTime(e.currentTarget.currentTime)}
        onLoadedMetadata={e => setDuration(e.currentTarget.duration)}
        style={{ width: '100%' }}
      />

      <button onClick={handleToggle} aria-label={isPlaying ? 'Pause' : 'Play'}>
        {isPlaying ? '❙❙' : '▶'}
      </button>

      <output>{formatTime(currentTime)} / {formatTime(duration)}</output>
    </section>
  );
}

Test it the way the last version failed. Right-click the video, turn on the native controls, and play from there — your button flips to pause on its own, because the element told it to. Let the video end and the button goes back to "Play". Nothing you wrote handles those cases specifically; they work because there is only one truth and React is reading it.

Use the JSX props, not addEventListener Every media event has a React prop, so there is no effect and no cleanup to forget — React attaches and removes them with the element (lesson 21's rule). Reach for addEventListener on the node only for the handful of media events React has no prop for, and then it is an effect with a cleanup like any other.

Stage 3 — the seek bar, and the fight with the playhead

A range input showing currentTime is easy. The bug appears when the user drags it: timeupdate keeps firing four to sixty times a second and keeps resetting the thumb under their finger.

const [scrubTime, setScrubTime] = useState<number | null>(null);   // null = not scrubbing

const shownTime = scrubTime ?? currentTime;   // derived: one line instead of a branch everywhere

<input
  type="range"
  min={0}
  max={Number.isFinite(duration) ? duration : 0}
  step={0.1}
  value={shownTime}
  aria-label="Seek"
  onChange={e => setScrubTime(e.currentTarget.valueAsNumber)}   // while dragging: UI only
  onPointerUp={() => commitScrub()}
  onKeyUp={() => commitScrub()}
  onBlur={() => commitScrub()}
/>

function commitScrub() {
  const video = videoRef.current;
  if (video === null || scrubTime === null) return;
  video.currentTime = scrubTime;     // ✓ the command, sent once, at the end
  setScrubTime(null);                // hand control back to timeupdate
}

Three decisions to be able to defend:

  • Why scrubTime is state, not a ref. The thumb's position is drawn from it. Lesson 19's question answers itself.
  • Why null rather than a separate isScrubbing boolean. Two states that must agree are a chance for them to disagree — Month 3's "no contradictions in state". One nullable value cannot contradict itself.
  • Why the command is sent on release, not on every move. Setting currentTime makes the element seek, which decodes frames and fires more events. Sixty seeks per second is how you make a video player stutter. If you want the picture to follow the drag, seek on move but throttle it — and then say out loud that you chose to pay for it.

Stage 4 — a player handle the parent can use

The last piece ties lesson 20 back in. A page with several players needs "pause everyone else when this one starts". Do not expose the <video> — expose three verbs:

export type PlayerHandle = {
  play: () => Promise<void>;
  pause: () => void;
  seek: (seconds: number) => void;
};

type Props = { src: string; onStarted?: () => void; ref?: React.Ref<PlayerHandle> };

export function Player({ src, onStarted, ref }: Props) {
  const videoRef = useRef<HTMLVideoElement>(null);

  useImperativeHandle(ref, () => ({
    play: async () => { await videoRef.current?.play(); },
    pause: () => { videoRef.current?.pause(); },
    seek: (seconds: number) => {
      if (videoRef.current !== null) videoRef.current.currentTime = seconds;
    },
  }));

  // …onPlay={() => { setIsPlaying(true); onStarted?.(); }}
}

The parent keeps a Map of player handles — the pattern from lesson 20 — and on onStarted it pauses every other one. Three verbs the DOM already has, and no way for a future teammate to reach in and set src behind the component's back.

Look at what is not here

Same exercise as last month — the absences are the plan, not oversights.

  • No custom hooks. The modal has four effects that obviously want to be useOnEscape, useClickOutside, useFocusTrap and useScrollLock. Extracting them is Month 6, on purpose: you can only judge a good hook boundary once you have seen the effects written out.
  • No memo, no useCallback. The player re-renders on every timeupdate — several times a second. That is fine here and it is exactly the kind of measured decision Months 6 and 11 are about.
  • No animation. An animated exit means the modal must stay mounted after open becomes false, which is a real design problem the platform now helps with. Later.
  • No global modal state. Every modal here is controlled by its parent's useState. "Open a dialog from anywhere" needs Context (Month 6) or a route (Month 8).
  • No streaming, captions, or analytics. A real player adds HLS, text tracks, and playback telemetry. All three sit on top of what you just built without changing it.

Extend it — four reps

  1. Volume and mute. Add a volume slider and a mute button. Decide which direction each piece of information travels, and use onVolumeChange so the native controls stay in agreement. Then say why volume is a command and a mirror.
  2. Keyboard shortcuts. Space toggles play, arrows seek five seconds. Put them on the player container with onKeyDown and tabIndex={0} — not on document — then explain the difference to yourself in one sentence.
  3. Confirm-before-close. Give the modal an onRequestClose that can refuse — for a form with unsaved changes. Notice that the Escape effect and the outside-click effect now both go through one function, which is a hint about where a custom hook's boundary belongs.
  4. Rebuild the modal on <dialog>. Delete six of your eight requirements and check what still works. Write down what you lost and what you gained. That list is the honest answer to "why not just use the platform?" in a code review.

Practice: read the situation, pick the move

Scenario

You are given a design review for a "quick preview" feature: clicking a thumbnail in a grid opens a modal with a video player inside it. The developer's plan is: a previewOpen boolean in the grid component; the modal rendered inline (no portal) inside the clicked card, since "it is position: fixed anyway"; the player receiving an autoPlay prop and an isPlaying state that an effect pushes into the element; Escape handled with a keydown listener added in the card's onClick; and the outside click handled by an onClick on the overlay. They also mention the grid has overflow: hidden on each card and a sticky toolbar with z-index: 10.

Work out, in order: which two of those decisions produce a visibly broken feature and why the card's own CSS is enough to prove it; which one is a listener that will never be removed; what will break the first time a user pauses with the native controls; and which single change fixes the most problems at once. Then write the three-line review comment you would leave.

Remember this · the Feynman summary
  • A modal is eight requirements: portal, dialog roles, Escape, outside click, focus in, focus trapped, focus restored, background locked. Four of them are setup/cleanup pairs; two are DOM commands.
  • Portal it into document.body so no ancestor's overflow, transform or z-index can clip or bury it. React events still bubble through your component tree.
  • Use pointerdown for outside clicks, not click. A click is reported on the common ancestor of press and release, so drag-selecting text closes the dialog — and a document click listener can even catch the click that opened it.
  • Save document.activeElement in a ref on open and focus it in the cleanup. Nobody notices this until they use a keyboard, and then it is the first thing they notice.
  • Query focusable elements at the moment Tab is pressed, not once at open — a dialog's contents change while it is open.
  • Restore the previous body.style.overflow instead of setting '', so nesting still works. Touching document.body by hand is safe precisely because React does not render it.
  • The platform has a modal. <dialog> + showModal() gives the top layer, focus handling, the trap and Escape for free; syncing it to a prop is a two-guard effect. Build your own to learn, ship the platform or a library.
  • A <video> is a state machine outside React. Commands go down through a ref inside handlers; the truth comes up through media events into state. React state is a mirror, never the source.
  • Never branch on your mirror. Ask video.paused, not !isPlaying — otherwise the native controls, the end of the file, and blocked autoplay all leave you out of sync.
  • play() returns a promise that can be refused — NotAllowedError for autoplay policy, AbortError when a pause() interrupts it. Await it in a try/catch and ignore AbortError.
  • A scrub is one command at the end, not sixty per second. Keep the dragged value in nullable state, draw scrubTime ?? currentTime, and set currentTime on release.
  • Real use case (built & run): a modal that went from five bugs to eight satisfied requirements, and a player whose button stayed correct when the video was driven from the native controls or ran to the end.

If you remember one thing: when something outside React already has state — focus, or a video — your job is to command it and mirror it, never to keep a second copy of the truth.
