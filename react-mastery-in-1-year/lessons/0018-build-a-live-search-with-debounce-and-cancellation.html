Build it — a live search with debounce & cancellation

One search box, three separate problems, three separate tools — and a race condition you can reproduce on demand instead of hoping it never happens.

Your win today: a search box that can never show results for the wrong query, built from an effect you can write from memory — plus the sentence that ends the argument in a code review: "aborting the request is not enough, and here is why."

This is the month's headline build and the most common React interview task that involves an effect. It looks like one feature. It is three problems wearing one coat, and people who have not separated them fix the wrong one.

Three problems, not one

#The problemWhat the user seesThe tool
1Too many requests. One per keystroke.Nothing, at first — then rate-limit errors, a slow app, and an angry backend team.Debounce: a setTimeout in the effect, cleared in the cleanup.
2Responses arrive out of order. The reply for rea lands after the reply for react.Results that do not match the box. The worst kind of bug: correct code, wrong screen, not reproducible on demand.An ignore flag, set in the cleanup.
3Work nobody wants is still running.Wasted bandwidth and battery; a spinner that outlives its query.AbortController — abort() in the cleanup.

Problems 2 and 3 look like the same thing and are not. This is the single most important paragraph in the lesson, and it comes straight from the React documentation:

React docs · Synchronizing with Effects "In addition to ignoring the result of an outdated API call, you can also use AbortController to cancel the requests that are no longer needed. However, by itself this is not enough to protect against race conditions. More asynchronous steps could be chained after the fetch, so using an explicit flag like ignore is the most reliable way to fix this type of problem."

Read that twice. Abort is an optimisation. The flag is the correctness fix. Plenty of production code has only the abort, which is why "sometimes it shows the wrong results" is such a common bug report.

Why the race happens — a timeline

The stale closure from Lesson 3 is the mechanism that makes this work. Each effect run captures its own ignore variable, so "was this run superseded?" is answered per run, with no shared bookkeeping and no ids to compare.

The state plan first

Month 3 habit: decide what is state before typing. Run the three questions over everything on the screen.

That last row is new this month and worth saying out loud: not everything a component remembers is state. A timer id and an AbortController exist only so the cleanup can undo the setup. Nothing on screen depends on them, so storing them in state would cause renders for nothing.

Build it for real — stage by stage

New Vite + React + TS project. We build the naive version first, prove it broken, then fix one problem per stage.

The fake API — engineered so the race happens every time

A real backend hides the race behind normal luck. This one makes shorter queries slower, so typing fast always produces an out-of-order pair. That turns a heisenbug into a demo.

src/types.ts

export interface SearchItem {
  id: string;
  name: string;
  kind: string;
}

export type Status = 'idle' | 'loading' | 'done' | 'error';

src/api.ts

import type { SearchItem } from './types';

const CATALOG: SearchItem[] = [
  { id: '1', name: 'react',          kind: 'library'   },
  { id: '2', name: 'react-dom',      kind: 'library'   },
  { id: '3', name: 'react-router',   kind: 'library'   },
  { id: '4', name: 'reactive-forms', kind: 'library'   },
  { id: '5', name: 'readline',       kind: 'node core' },
  { id: '6', name: 'realm',          kind: 'database'  },
  { id: '7', name: 'redux',          kind: 'library'   },
  { id: '8', name: 'rehype',         kind: 'tool'      },
];

// Shorter query ⇒ longer delay. This guarantees the race instead of hoping for it.
function delayFor(query: string) {
  return Math.max(150, 1100 - query.length * 180);
}

export function searchApi(query: string, signal: AbortSignal): Promise<SearchItem[]> {
  const ms = delayFor(query);
  console.log(`→ request "${query}" (will take ${ms}ms)`);

  return new Promise((resolve, reject) => {
    const timer = setTimeout(() => {
      console.log(`← response "${query}"`);
      resolve(CATALOG.filter(item => item.name.includes(query.toLowerCase())));
    }, ms);

    // Behave like fetch does: reject with an AbortError when cancelled.
    signal.addEventListener('abort', () => {
      clearTimeout(timer);
      console.log(`✕ aborted "${query}"`);
      reject(new DOMException(`Aborted "${query}"`, 'AbortError'));
    });
  });
}

Stage 1 — the naive version, and the bug on screen

src/LiveSearch.tsx — stage 1

import { useEffect, useState } from 'react';
import { searchApi } from './api';
import type { SearchItem } from './types';

export function LiveSearch() {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState<SearchItem[]>([]);

  useEffect(() => {
    if (query === '') return;

    // ✕ No flag, no abort, no debounce. One request per keystroke,
    //   and whichever answer arrives last wins.
    searchApi(query, new AbortController().signal).then(setResults);
  }, [query]);

  return (
    <section>
      <input value={query} onChange={e => setQuery(e.target.value)} placeholder="Search…" />
      <p>query: <b>{query || '—'}</b></p>
      <ul>
        {results.map(item => (
          <li key={item.id}>{item.name} <small>{item.kind}</small></li>
        ))}
      </ul>
    </section>
  );
}

Type "react" at a normal speed. The console shows five requests, and the responses come back in the wrong order. On screen you end up with the results for r or re while the box says react — a list containing redux and realm for a query that cannot match them.

Stop here and appreciate the shape of this bug. No exception, no red console, no failing test. Only a screen that lies.

Stage 2 — the correctness fix: one ignore flag per run

useEffect(() => {
  if (query === '') {
    setResults([]);
    return;
  }

  let ignore = false;                    // ✓ local to THIS run of the effect

  searchApi(query, new AbortController().signal).then(data => {
    if (!ignore) setResults(data);       // only the run that is still current may write
  });

  return () => {
    ignore = true;                       // this run has been superseded — disown it
  };
}, [query]);

Type "react" again. The console still shows five requests and still shows them answering out of order — and the screen is now always correct, because four of those five runs were disowned before their answers arrived.

Why this is not "cancel" Nothing was cancelled. The old requests all completed and their .then callbacks all ran — each one checked its own ignore, found true, and did nothing. Correctness first, efficiency second: fixing the screen and fixing the waste are two different jobs.

Stage 3 — fewer requests: debounce inside the effect

A debounce is "wait until the typing stops". In React that is a timer, which is a classic setup/cleanup pair — so it belongs in the same effect, not in a separate mechanism.

const DEBOUNCE_MS = 300;   // module scope: a constant, not a dependency

useEffect(() => {
  if (query === '') {
    setResults([]);
    return;
  }

  let ignore = false;

  const timer = setTimeout(() => {                 // ✓ the wait
    searchApi(query, new AbortController().signal).then(data => {
      if (!ignore) setResults(data);
    });
  }, DEBOUNCE_MS);

  return () => {
    ignore = true;
    clearTimeout(timer);                           // ✓ a keystroke cancels the pending wait
  };
}, [query]);

Now type "react" quickly and read the console: one request, for react. Each keystroke re-runs the effect, and the cleanup clears the previous timer before it ever fires. The debounce is not a special library — it is the cleanup doing what cleanups do.

Why the timer must live inside the effect A tempting alternative is a separate "debounced value" kept in state, updated by its own effect. That works, but it costs an extra render and a second copy of the query. Keeping the timer inside the fetching effect means one source of truth (query) and one lifecycle to reason about. And keep the delay in module scope — a value declared in the component body would be reactive, and would restart the debounce on every render.

Stage 4 — stop the wasted work: AbortController

useEffect(() => {
  if (query === '') {
    setResults([]);
    return;
  }

  let ignore = false;
  const controller = new AbortController();        // ✓ one per run

  const timer = setTimeout(() => {
    searchApi(query, controller.signal)
      .then(data => {
        if (!ignore) setResults(data);
      })
      .catch((err: unknown) => {
        // An abort is not a failure. Never show it to the user.
        if (err instanceof Error && err.name === 'AbortError') return;
        if (!ignore) console.error(err);
      });
  }, DEBOUNCE_MS);

  return () => {
    ignore = true;
    controller.abort();                            // ✓ drop work nobody wants
    clearTimeout(timer);
  };
}, [query]);

Three lines of cleanup, one per problem: ignore for correctness, abort for waste, clearTimeout for the pending wait. That trio is the thing to be able to type from memory.

A myth worth retiring You may read that the flag exists to avoid "setState on an unmounted component". That warning was removed in React 18 — setting state after unmount is a harmless no-op, not a leak. The flag is not about unmounting at all; it is about ordering. Two live requests, two answers, and only the latest one has the right to write.

src/LiveSearch.tsx — the finished owner

import { useEffect, useRef, useState } from 'react';
import { searchApi } from './api';
import { SearchInput } from './SearchInput';
import { ResultList } from './ResultList';
import type { SearchItem, Status } from './types';

const DEBOUNCE_MS = 300;

export function LiveSearch() {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState<SearchItem[]>([]);
  const [status, setStatus] = useState<Status>('idle');
  const [errorText, setErrorText] = useState('');

  // Not state: changing it must never cause a render. Refs are Month 5;
  // this is the one honest use of one here — a box that survives renders.
  const cache = useRef(new Map<string, SearchItem[]>());

  useEffect(() => {
    const trimmed = query.trim().toLowerCase();

    if (trimmed === '') {
      setResults([]);
      setStatus('idle');
      return;                                // no cleanup needed: nothing was started
    }

    const cached = cache.current.get(trimmed);
    if (cached) {
      setResults(cached);                     // instant, and no request at all
      setStatus('done');
      return;
    }

    let ignore = false;
    const controller = new AbortController();
    setStatus('loading');                     // old results stay visible underneath

    const timer = setTimeout(() => {
      searchApi(trimmed, controller.signal)
        .then(data => {
          cache.current.set(trimmed, data);
          if (ignore) return;                 // superseded — the cache still keeps the data
          setResults(data);
          setStatus('done');
        })
        .catch((err: unknown) => {
          if (err instanceof Error && err.name === 'AbortError') return;
          if (ignore) return;
          setErrorText(err instanceof Error ? err.message : 'Search failed');
          setStatus('error');
        });
    }, DEBOUNCE_MS);

    return () => {
      ignore = true;
      controller.abort();
      clearTimeout(timer);
    };
  }, [query]);                                // the only reactive value read: query

  // Everything below is derived — no extra state.
  const isBusy = status === 'loading';
  const isEmpty = status === 'done' && results.length === 0;

  return (
    <section style={{ fontFamily: 'system-ui', maxWidth: 460 }}>
      <SearchInput value={query} onChange={setQuery} busy={isBusy} />

      {status === 'idle'  && <p>Type to search.</p>}
      {isBusy             && <p>Searching…</p>}
      {status === 'error' && <p role="alert">Something went wrong: {errorText}</p>}
      {isEmpty            && <p>No packages match “{query.trim()}”.</p>}

      {results.length > 0 && (
        <>
          <p><b>{results.length}</b> result{results.length === 1 ? '' : 's'}</p>
          <ResultList items={results} />
        </>
      )}
    </section>
  );
}

Point it at a real API

Swap the fake for a real endpoint to see that nothing about the shape changes:

export async function searchApi(query: string, signal: AbortSignal): Promise<SearchItem[]> {
  const res = await fetch(
    `https://api.github.com/search/repositories?q=${encodeURIComponent(query)}&per_page=8`,
    { signal },                              // ← the whole integration is this one option
  );
  if (!res.ok) throw new Error(`GitHub said ${res.status}`);

  const json = await res.json();
  return json.items.map((r: { id: number; full_name: string; language: string | null }) => ({
    id: String(r.id),
    name: r.full_name,
    kind: r.language ?? 'unknown',
  }));
}

Two honest notes. First, GitHub's search endpoint has a low rate limit without a token — roughly ten searches a minute — so the debounce is not a nicety here, it is what keeps the feature working; remove it and you will earn a 403 within seconds of typing. Second, this is where the shape of the problem starts to outgrow a hand-written effect.

Look at what is not here

The effect above is about twenty-five lines and every one of them earns its place. Now consider what a real product also wants:

The app also needsBy hand
Two components searching the same queryTwo identical requests, unless you build request de-duplication.
Retry once on a network blipYour own retry loop, with backoff, inside the effect.
Cache that expiresTimestamps in the Map, and a policy for when data is too old.
Refetch when the tab regains focusAnother effect, another listener, another cleanup.
Show cached data instantly, refresh behind itThe "stale while revalidating" logic, by hand, per screen.
Pagination that keeps the previous page visibleMore state, and careful ordering rules.
The same data shared by five screensLift it, or a store — and now cache invalidation is your problem.

Every one of those is solvable, and every one of them is the same code in every app. That is exactly why server state gets its own library — TanStack Query in Month 7. You are not learning this effect so you can hand-write it forever. You are learning it so that when the library does it for you, you know precisely which problem each of its options solves — and so you can still write it by hand in an interview, on a whiteboard, with the race condition explained.

Extend it — four reps, without looking

  1. Keyboard navigation. Arrow keys move a highlighted index, Enter selects. Ask the state question first: is highlightedIndex state? (Yes — the user produces it, and it cannot be computed. But reset it whenever results changes, and prefer doing that during render over an effect.)
  2. A minimum query length. Do not search until two characters. One condition, in one place — and notice that the early return means no request, no timer, and no cleanup.
  3. Cancel on demand. Add a "Stop" button. It cannot reach the effect's controller, and that is the lesson: the effect owns its own cancellation. The clean version sets state — for example clearing the query — and lets the cleanup do the aborting.
  4. Expire the cache. Store { data, at } and treat entries older than thirty seconds as missing. Then say out loud what you have just started building, and why Month 7 exists.

Practice: read the situation, pick the move

Scenario

A colleague reviews your pull request and asks for three changes. One: "the ignore flag is redundant now that you call controller.abort() — delete it." Two: "move the debounce into a useDebouncedValue hook that keeps the delayed query in its own state, so the fetch effect gets simpler." Three: "the cache should be in state, not a ref, because it is data the component uses."

Answer each one as you would in the review. One is flatly wrong and would ship a bug, one is a reasonable idea with a real trade-off, and one is wrong for a reason worth naming precisely. Say which is which, and quote the documentation for the first.

Remember this · the Feynman summary
  • One search box, three problems: too many requests (debounce), answers arriving out of order (the ignore flag), and wasted work (AbortController). Different tools, different reasons.
  • The flag is the correctness fix; the abort is an optimisation. The docs are explicit: abort alone does not protect against race conditions, because more async steps can be chained after the fetch.
  • Each effect run owns its own ignore — a closure per query. React runs the old cleanup before the new setup, so an outdated run is disowned before its answer lands.
  • The cleanup is three lines: ignore = true, controller.abort(), clearTimeout(timer). Learn to type it without thinking.
  • A debounce is just a timer in the effect, cleared by the cleanup. No library needed, and no second copy of the query.
  • An abort is not an error. Return early on err.name === 'AbortError' or you will show failures for requests you cancelled yourself.
  • The flag is not about unmounting. The "setState on an unmounted component" warning was removed in React 18. This is about ordering.
  • Status as a union — 'idle' | 'loading' | 'done' | 'error' — so "loading and error at the same time" cannot happen.
  • Not everything a component remembers is state. A timer id and a controller live in the closure; the cache lives in a ref, because nothing on screen re-renders when it changes.
  • Keep the old results visible while loading. Setting status without clearing results is stale-while-revalidate, by hand.
  • Make the race deterministic to learn from it: a fake API where shorter queries are slower turns an unreproducible bug into a demo.
  • This is why server-state libraries exist. De-duplication, retries, expiry, refetch-on-focus and shared cache are the same code in every app — Month 7.
  • Real use case (built & run): a debounced live search with per-run cancellation, an in-memory cache, a union status, an error path that ignores aborts, and a race condition reproduced on purpose and then made impossible.

If you remember one thing: with two requests in flight, only the newest one has the right to write to state — and the cleanup is where you take that right away from the old one.
