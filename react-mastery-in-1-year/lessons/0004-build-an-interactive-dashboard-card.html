Type it out yourself in your Vite + TypeScript project (don't copy-paste — the muscle memory is the point), run it, then read the walkthrough that maps every line back to the concept it uses.

The plan — decompose before you code

Senior React starts with the same question every time: what are the components, and who owns the state? Our card is one owner and three helpers:

  • ProjectCard — the container. It owns the state (the task list) and holds the functions that change it.
  • StatBadge — pure display. Takes props, shows a number. No state, no events.
  • TaskItem — one row. Shows a task; when clicked, calls a function its parent gave it (events up).
  • AddTaskForm — a small controlled input that reports a new task's text to the parent.

The state lives in ProjectCard because it's the lowest component that both displays the tasks and needs to change them — everyone else just receives what they need through props. This "put state at the lowest common owner" instinct is the whole of Month 3 ("Thinking in React"); you're meeting it early, in practice.

Build it for real — the full component

Replace src/App.tsx with the following. It's long, but every piece is something you've already met — read the comments as you type.

src/App.tsx

import { useState } from 'react';

// One shared data shape, used everywhere below. This is our single source of truth's element type.
type Task = { id: number; text: string; done: boolean };

// ---------- 1. StatBadge: pure display. Props in, UI out. No state. ----------
function StatBadge({ label, value }: { label: string; value: string }) {
  return (
    <span className="badge">
      <strong>{value}</strong> {label}
    </span>
  );
}

// ---------- 2. TaskItem: one row. Reports clicks UP via callback props. ----------
type TaskItemProps = {
  task: Task;
  onToggle: (id: number) => void;
  onDelete: (id: number) => void;
};

function TaskItem({ task, onToggle, onDelete }: TaskItemProps) {
  return (
    <li>
      <label>
        <input
          type="checkbox"
          checked={task.done}
          onChange={() => onToggle(task.id)}
        />
        <span style={{ textDecoration: task.done ? 'line-through' : 'none' }}>
          {task.text}
        </span>
      </label>
      <button onClick={() => onDelete(task.id)} aria-label="Delete task">✕</button>
    </li>
  );
}

// ---------- 3. AddTaskForm: a controlled input that hands new text to the parent. ----------
function AddTaskForm({ onAdd }: { onAdd: (text: string) => void }) {
  const [text, setText] = useState('');

  function handleSubmit(e: React.FormEvent) {
    e.preventDefault();              // stop the browser reloading the page
    const trimmed = text.trim();
    if (!trimmed) return;            // ignore empty input
    onAdd(trimmed);                  // event up: tell the parent
    setText('');                     // clear the box
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        value={text}                              // controlled: the input shows state...
        onChange={(e) => setText(e.target.value)}  // ...and state follows the input
        placeholder="Add a task…"
      />
      <button type="submit">Add</button>
    </form>
  );
}

// ---------- 4. ProjectCard: the owner. Holds state + the functions that change it. ----------
export default function ProjectCard() {
  const [tasks, setTasks] = useState<Task[]>([
    { id: 1, text: 'Set up Vite + TypeScript', done: true },
    { id: 2, text: 'Understand UI = f(state)', done: true },
    { id: 3, text: 'Build the dashboard card', done: false },
  ]);

  // DERIVED values — computed from state during render, never stored as separate state.
  const doneCount = tasks.filter((t) => t.done).length;
  const total = tasks.length;
  const percent = total === 0 ? 0 : Math.round((doneCount / total) * 100);
  const allDone = total > 0 && doneCount === total;

  // State updaters — all IMMUTABLE (build a new array, never mutate the old one).
  function addTask(text: string) {
    setTasks((prev) => [...prev, { id: Date.now(), text, done: false }]);
  }
  function toggleTask(id: number) {
    setTasks((prev) =>
      prev.map((t) => (t.id === id ? { ...t, done: !t.done } : t))
    );
  }
  function deleteTask(id: number) {
    setTasks((prev) => prev.filter((t) => t.id !== id));
  }

  return (
    <article className="card">
      <header>
        <h2>Learn React — Month 1</h2>
        {allDone && <span className="pill">✓ Complete</span>}
      </header>

      <div className="stats">
        <StatBadge label="done" value={`${doneCount}/${total}`} />
        <StatBadge label="complete" value={`${percent}%`} />
      </div>

      {total === 0 ? (
        <p>No tasks yet — add your first one below.</p>
      ) : (
        <ul>
          {tasks.map((task) => (
            <TaskItem
              key={task.id}          // stable identity from the data — never the index
              task={task}
              onToggle={toggleTask}
              onDelete={deleteTask}
            />
          ))}
        </ul>
      )}

      <AddTaskForm onAdd={addTask} />
    </article>
  );
}

Run npm run dev. Add a task, check some off, delete one, delete them all to see the empty state, then complete every task to see the "✓ Complete" pill appear. It's small, but it's a real interactive component — and you wrote all of it.

The senior habit hiding in here Notice we never stored doneCount or percent in state. They're derived from tasks every render. A beginner adds a useState for the count and then fights to keep it in sync (the exact bug React exists to kill). The rule: if you can compute it from existing state, don't store it. Fewer sources of truth, fewer bugs.

Extend it — three reps to make it yours

Building confidence means changing code you understand. Try these without looking anything up:

  1. Add a filter. A row of "All / Active / Done" buttons. Store the current filter in state, and derive the visible list from tasks + filter. (No new task state — just a filter value.)
  2. Add "clear completed." One button that removes every done task. It's a one-line filter update.
  3. Guard the pill. Delete all tasks — does "✓ Complete" wrongly appear on an empty list? Check why allDone already handles it (total > 0 && …), and say out loud what would break if you removed that guard.

Remember this · the Feynman summary
  • Start every build by decomposing: what are the components, and who owns each piece of state? Put state at the lowest common owner.
  • One owner, many display children. ProjectCard holds the task list; StatBadge, TaskItem, and AddTaskForm receive what they need through props.
  • Data down, events up. Children get data as props and report changes by calling callback props (onToggle, onAdd) — they never touch the parent's state directly.
  • Derive, don't store. doneCount, percent, and allDone are computed from tasks each render — no extra state to keep in sync.
  • Update immutably: [...prev, x], .map, .filter build new arrays; the updater form setTasks(prev => …) uses the latest value.
  • Keys from data (key={task.id}) keep state attached to the right row.
  • Real use case (built & run): an interactive project card with add / toggle / delete, live derived stats, and empty + complete states — every Month-1 idea working together, typed end to end.

If you remember one thing: a React feature is a tree of small functions sharing one source of truth — data flows down as props, changes flow up as callbacks.
