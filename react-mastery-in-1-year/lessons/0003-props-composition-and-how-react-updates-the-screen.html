Month 1 · Lesson 3 · The render model

Props, composition & how React updates the screen

One-way data flow, building big UIs from small parts, and the diff that turns your descriptions into pixels.

Your win today: you'll be able to (1) compose a real interface from small typed components with one-way data flow, (2) render lists and conditionals correctly, and (3) explain reconciliation and why keys matter — the questions that separate "I've used React" from "I understand React." You'll also cause, then fix, the most famous keys bug on purpose.

You now have the two data channels: props (passed down from a parent) and state (a component's own memory). This lesson is about assembling many components into one UI, and then the deep part — what React does with all those returned descriptions to update the actual page.

Props flow one way — down

Data in React travels in exactly one direction: from parent to child, through props. A parent chooses what to pass; a child reads its props but must never change them. This is called one-way data flow, and it's the reason React apps are predictable: to find why a value is what it is, you only ever look upward, at whoever passed it.

type PriceTagProps = {
  label: string;
  cents: number;
};

function PriceTag({ label, cents }: PriceTagProps) {
  // derive display data from props during render — no state needed
  const dollars = (cents / 100).toFixed(2);
  return <span>{label}: ${dollars}</span>;
}
Props are read-only Never write props.cents = 0 or push into a prop array. A child that needs to change data doesn't mutate props — it calls a function its parent passed down (a callback prop like onChange). "Data down, events up." We'll use that pattern in the build.

Composition — big UIs from small parts

You don't build a page as one giant component. You build small, focused components and nest them. A component can render other components, exactly like calling smaller functions from a bigger one. The special prop children lets a component wrap arbitrary content handed to it:

import type { ReactNode } from 'react';

// A reusable "card" shell. Whatever you nest inside becomes `children`.
function Card({ title, children }: { title: string; children: ReactNode }) {
  return (
    <section className="card">
      <h2>{title}</h2>
      {children}
    </section>
  );
}

// Using it — the <p> and <PriceTag/> are passed in as children:
function App() {
  return (
    <Card title="Wireless Mouse">
      <p>Ergonomic, 2-year battery.</p>
      <PriceTag label="Now" cents={2999} />
    </Card>
  );
}

ReactNode is the TypeScript type for "anything React can render" — JSX, a string, a number, an array of these, or nothing. It's the type you'll use for children constantly. Composition is how you keep components small and reusable: Card knows nothing about prices, and PriceTag knows nothing about cards.

Conditional rendering — UI is just expressions

Because JSX is JavaScript, "show this sometimes" is just an expression. Three common shapes:

{isLoggedIn ? <Dashboard /> : <LoginButton />}   // ternary: one or the other

{hasError && <p className="error">Something broke</p>}  // &&: show only when true

if (!user) return <Spinner />;   // early return from the component
The && gotcha that ships to production {count && <Badge/>} looks fine — until count is 0. 0 && ... evaluates to 0, and React renders the number 0 on screen. Guard with a real boolean: {count > 0 && <Badge/>}. (React renders false, null, and undefined as nothing — but 0 is a number, so it shows.)

Rendering lists — and the key that everything hinges on

To turn an array of data into an array of elements, you use .map() — plain JavaScript inside JSX:

type Task = { id: string; text: string };

function TaskList({ tasks }: { tasks: Task[] }) {
  return (
    <ul>
      {tasks.map(task => (
        <li key={task.id}>{task.text}</li>   // key = stable identity of THIS item
      ))}
    </ul>
  );
}

The key prop is not decoration and it is not for you — it's a message to React's diffing algorithm: "this element corresponds to this item of data across renders." To understand why that matters, we need to open up what React does after your component returns.

The deep part — render, commit & reconciliation

Each time state or props change, React does its work in two phases:

  • Render phase. React calls your components and builds the new tree of element descriptions. This is pure computation — nothing on screen changes yet. (This is why your component must be a pure function of its props and state: React may call it more than once, and does exactly this in development to help you catch impurities.)
  • Commit phase. React compares the new tree to the previous one, works out the smallest set of real-DOM edits, and applies them. Only now does the screen change.

That comparison is reconciliation, and it follows two simple rules:

  1. Same position, same element type → keep the DOM node. React updates only the props that changed and keeps the node's identity (and its state, and what you typed into it). A <div> that stays a <div> is reused.
  2. Different type → tear it down and rebuild. A <div> that becomes a <section> throws away the old subtree (and its state) and builds a fresh one.

For lists, "position" is ambiguous — items get added, removed, and reordered. So React needs you to tell it identity, and that's the key. With keys, React matches elements by key (item identity). Without keys, it falls back to matching by index (position) — and that's where the classic bug lives.

Build it for real — cause the keys bug, then fix it

Reading about the keys bug is forgettable; watching it happen is not. Build this list where each row has its own uncontrolled input, then add an item to the front.

src/App.tsx

import { useState } from 'react';

type Task = { id: number; text: string };

export default function App() {
  const [tasks, setTasks] = useState<Task[]>([
    { id: 1, text: 'Learn props' },
    { id: 2, text: 'Learn keys' },
  ]);

  function addToTop() {
    const id = Date.now();
    // immutable update: build a NEW array, newest first
    setTasks(prev => [{ id, text: 'NEW task' }, ...prev]);
  }

  return (
    <div>
      <button onClick={addToTop}>Add to top</button>
      <ul>
        {tasks.map((task, index) => (
          // BUG version: key={index}. Type a note in each row, then click "Add to top".
          <li key={index}>
            {task.text} <input placeholder="your note" />
          </li>
        ))}
      </ul>
    </div>
  );
}

Run it. Type "hello" into the first row's input, then click Add to top. Watch closely: the new row appears at the top, but your "hello" text stays in the first position — it did not move down with the "Learn props" task it belonged to. The input's state stuck to slot 0, because with key={index} the new item is index 0, so React reused the existing top DOM node and just changed the label. The label moved; the input value didn't.

Now change one character — key={index} to key={task.id} — and repeat. This time "hello" rides down with its task, and the empty new input appears on top, exactly as a human expects. Same list, one attribute, correct vs corrupted UI. You just felt reconciliation with your own hands.

The keys rules that follow A key must be (1) stable — the same item gets the same key every render; (2) unique among siblings; and (3) come from your data's identity (a database id, a UUID), never the array index — unless the list is static and never reorders, inserts, or deletes. When in doubt, give your data real ids.

Remember this · the Feynman summary
  • Props flow one way — down. A parent passes props; a child reads them and never mutates them. To change data, a child calls a callback prop ("data down, events up").
  • Composition: build big UIs from small components by nesting them; the children prop (typed ReactNode) lets a component wrap arbitrary content.
  • Conditional rendering is just expressions: ternary, &&, or early return. Guard && against 0 ({count > 0 && ...}), because React renders the number 0.
  • Lists: .map() data to elements; give each a key.
  • Two phases: render (call components, build the new element tree — pure, nothing on screen yet) then commit (apply the minimal DOM edits).
  • Reconciliation: same position + same type → keep the DOM node and its state; different type → tear down and rebuild.
  • Keys give list items identity. With keys React matches by item; without them it matches by index, so reordering/inserting sticks state to the wrong item. Keys must be stable, unique, and from your data — not the array index.
  • Real use case (built & run): a list where key={index} leaves typed input on the wrong row after inserting at the top, and key={task.id} fixes it — reconciliation, felt.

If you remember one thing: a key tells React which item an element is, so state and DOM follow the right item when the list changes.
