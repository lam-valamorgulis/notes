Month 3 · Lesson 4 · The real build

Build it — the filterable product table

All five steps, end to end, on the exercise React itself uses — with search, an in-stock filter, sortable columns, grouping, and a selected row.

Your win today: the whole method in one app you can rebuild from a blank folder in about thirty minutes — and, more useful in an interview, the ability to talk through the five steps while your hands are typing.

This is the classic React exercise, and it is classic for a reason: it contains every decision that matters. What is a component, what is state, who owns it, and what is just a computation.

We build a bigger version than the docs do. Same five steps, four more features: sorting, grouping that survives sorting, a selected row with a detail panel, and a live count with a real empty state.

Step 1 — the component tree

The features: search by name, show only in-stock items, sort by name or price in either direction, keep products grouped under their category, click a row to see its details, and show "N of M" with an empty state.

Seven components, and every one of them is a function of a slice of the data. Two of them exist because the data repeats, one because a column heading now has behaviour of its own.

Step 2 — the static version

Already done in Lesson 1, and this is the payoff for doing it: the markup, the grouping and the price formatting are known to work, so every bug from here is a state bug. Keep the files you built.

Four pieces of state for a table this size. Seven derived values. That ratio is what "thinking in React" buys you — and each derived value you refuse to store is a bug that cannot happen.

Step 4 — where each piece lives

StateWho renders from itOwner
filterTextSearchBar shows it · the filter uses itFilterableProductTable

All four land in the same component, because every one of them has readers on both sides of the tree. That is not laziness — it is what the procedure returned. No child owns anything.

Step 5 — the callbacks going up

Prop on the childTypeWhat the owner does with it
onFilterTextChange(next: string) => voidsetFilterText directly.
onInStockOnlyChange(next: boolean) => voidsetInStockOnly directly.
onSortChange(key: SortKey) => voidhandleSortChange — same column flips direction, new column starts ascending.
onSelect(id: string) => voidhandleSelect — clicking the selected row clears it.
onClear() => voidsetSelectedId(null).

Notice onSortChange takes a column, not a whole sort object. The child says "the user clicked Price"; the owner decides what that means. That is the division of labour you want everywhere: children report facts, owners make decisions.

src/SortHeader.tsx — a column title with behaviour

import type { Sort, SortKey } from './types';

interface SortHeaderProps {
  label: string;
  sortKey: SortKey;
  sort: Sort;                              // the current sort, to draw the arrow
  onSortChange: (key: SortKey) => void;    // reports a click, decides nothing
}

export function SortHeader({ label, sortKey, sort, onSortChange }: SortHeaderProps) {
  const isActive = sort.key === sortKey;                    // derived, not state
  const arrow = isActive ? (sort.dir === 'asc' ? ' ↑' : ' ↓') : '';

  return (
    <th
      aria-sort={isActive ? (sort.dir === 'asc' ? 'ascending' : 'descending') : 'none'}
    >
      <button type="button" onClick={() => onSortChange(sortKey)}>
        {label}{arrow}
      </button>
    </th>
  );
}

src/ProductTable.tsx — draws what it is given

import { Fragment } from 'react';
import type { Product, Sort, SortKey } from './types';
import { ProductRow } from './ProductRow';
import { ProductCategoryRow } from './ProductCategoryRow';
import { SortHeader } from './SortHeader';

export interface Group {
  category: string;
  items: Product[];
}

interface ProductTableProps {
  groups: Group[];                         // already filtered, sorted and grouped
  sort: Sort;
  selectedId: string | null;
  onSortChange: (key: SortKey) => void;
  onSelect: (id: string) => void;
}

export function ProductTable({
  groups, sort, selectedId, onSortChange, onSelect,
}: ProductTableProps) {
  return (
    <table>
      <thead>
        <tr>
          <SortHeader label="Name"  sortKey="name"  sort={sort} onSortChange={onSortChange} />
          <SortHeader label="Price" sortKey="price" sort={sort} onSortChange={onSortChange} />
        </tr>
      </thead>
      <tbody>
        {groups.length === 0 && (
          <tr><td colSpan={2}>Nothing matches those filters.</td></tr>
        )}
        {groups.map(group => (
          // A fragment per group keeps the <tbody> flat and the keys stable.
          <Fragment key={group.category}>
            <ProductCategoryRow category={group.category} />
            {group.items.map(product => (
              <ProductRow
                key={product.id}
                product={product}
                isSelected={product.id === selectedId}
                onSelect={onSelect}
              />
            ))}
          </Fragment>
        ))}
      </tbody>
    </table>
  );
}
Two small things in that file The fragment needs a real import. The short form <>…</> cannot take a key, and a list of groups needs one — so import Fragment by name and write <Fragment key=…>. It groups the heading row and its product rows without adding a DOM element, which matters inside a <tbody>, where a stray <div> is invalid HTML. And the empty state lives here, not in the owner: the table knows it drew nothing, and one groups.length === 0 is cheaper than a second branch upstairs.

src/FilterableProductTable.tsx — the owner, and the only interesting file

import { useState } from 'react';
import type { Product, Sort, SortKey } from './types';
import { SearchBar } from './SearchBar';
import { ProductTable, type Group } from './ProductTable';
import { ProductDetail } from './ProductDetail';

export function FilterableProductTable({ products }: { products: Product[] }) {
  // ── the four pieces of state, and nothing else ──
  const [filterText, setFilterText] = useState('');
  const [inStockOnly, setInStockOnly] = useState(false);
  const [sort, setSort] = useState<Sort>({ key: 'name', dir: 'asc' });
  const [selectedId, setSelectedId] = useState<string | null>(null);

  // ── derived: 1 · filter ──
  const needle = filterText.trim().toLowerCase();
  const matching = products.filter(p =>
    p.name.toLowerCase().includes(needle) && (!inStockOnly || p.inStock)
  );

  // ── derived: 2 · sort a COPY (sort() mutates in place) ──
  const sorted = [...matching].sort((a, b) => {
    const result = sort.key === 'name'
      ? a.name.localeCompare(b.name)
      : a.price - b.price;
    return sort.dir === 'asc' ? result : -result;
  });

  // ── derived: 3 · group by category, categories A→Z ──
  const byCategory = new Map<string, Product[]>();   // local: born and dies this render
  for (const product of sorted) {
    const bucket = byCategory.get(product.category);
    if (bucket) bucket.push(product);
    else byCategory.set(product.category, [product]);
  }
  const groups: Group[] = [...byCategory.entries()]
    .sort(([a], [b]) => a.localeCompare(b))
    .map(([category, items]) => ({ category, items }));

  // ── derived: 4 · the selected product, looked up fresh ──
  const selected = products.find(p => p.id === selectedId) ?? null;

  // ── the two decisions the owner makes ──
  function handleSortChange(key: SortKey) {
    setSort(prev =>
      prev.key === key
        ? { key, dir: prev.dir === 'asc' ? 'desc' : 'asc' }   // same column: flip
        : { key, dir: 'asc' }                                  // new column: start up
    );
  }

  function handleSelect(id: string) {
    setSelectedId(prev => (prev === id ? null : id));           // click again to clear
  }

  return (
    <div>
      <SearchBar
        filterText={filterText}
        inStockOnly={inStockOnly}
        onFilterTextChange={setFilterText}
        onInStockOnlyChange={setInStockOnly}
      />
      <p>Showing {matching.length} of {products.length}</p>
      <ProductTable
        groups={groups}
        sort={sort}
        selectedId={selectedId}
        onSortChange={handleSortChange}
        onSelect={handleSelect}
      />
      <ProductDetail product={selected} onClear={() => setSelectedId(null)} />
    </div>
  );
}

SearchBar.tsx is exactly the file from Lesson 3 — it never changes, because it never owned anything.

Why the grouping had to change

Lesson 1 grouped rows with a running lastCategory variable. That worked because the data arrived already grouped. Add sorting and it breaks: sorting by price interleaves fruits and nuts, so the same category appears again and again, each time it comes back around.

The fix is to make the grouping explicit — bucket the rows into a Map, then render one group at a time. Same pattern as before: a derived value that used to be free is now a computation, so write the computation.

Sorting inside groups, not across them Because we group after sorting and then order the categories A→Z, the sort applies within each category. That is almost always what a user of a grouped table expects: "sort by price" means "cheapest first inside each group", not "throw the grouping away". If you want the other behaviour, the sort has to move to the group level — a good exercise, and a good question to ask a designer before you build it.

Look at what is not here No useEffect. No useMemo. No useReducer. No state library. A sortable, groupable, filterable, selectable table needs none of them, because every visible value is either state the user set or a computation over it. If this table held ten thousand rows, useMemo would cache the pipeline — a Month 6 change, made after measuring, and it would still not turn any derived value into state.

Extend it — four reps, without looking

  1. Clear all filters. One button in the owner that resets three states. It needs no new state — and the search box empties itself, because it renders the value it is given.
  2. Multiple selection. Swap selectedId: string | null for selectedIds: Set<string>. Remember that a Set in state must be replaced, not mutated: setSelectedIds(prev => { const next = new Set(prev); next.has(id) ? next.delete(id) : next.add(id); return next; }). Then ProductDetail becomes a summary — count and total price, both derived.
  3. A price range filter. { min, max } in one state variable, because the two inputs are one fact. Add it to the filter step only; everything downstream keeps working, which is the reward for the pipeline shape.
  4. Sort by category, then name. Add 'category' to SortKey, and make the comparator fall back to name when the primary values tie. Watch TypeScript point at the exact switch you forgot to extend.

Harder, and the real interview follow-up: put filterText and sort in the URL so a filtered view can be shared as a link. You cannot do it yet — that is Month 8 — but say out loud which file would change. If your answer is "only the owner", your component boundaries are right.

Practice: read the situation, pick the move

Scenario

A teammate reviews this build and asks for three changes. One: "move the filtering into ProductTable, the parent is doing too much." Two: "store groups in state so we don't rebuild the Map every render." Three: "ProductRow should own isSelected itself so a click doesn't re-render the whole table."

Answer each one as you would in the review — what you agree with, what you refuse, and what evidence would change your mind. One of the three is a reasonable idea with a real trade-off; the other two would create bugs. Say which is which.

Remember this · the Feynman summary
  • The five steps, in order: tree → static version → minimal state → owner → inverse data flow. Say them while you type.
  • Four pieces of state ran this whole table: filterText, inStockOnly, sort, selectedId. Seven other values were derived.
  • Group what always changes together: sort: { key, dir }, because a header click sets both.
  • Store the id, look up the object: selectedId plus find — so renames and deletes cannot leave a stale copy behind.
  • The derived pipeline is the app: filter → sort a copy → group → draw. One new filter = one new line in one file.
  • Copy before you sort. sort() mutates, and React compares identity.
  • Children report, owners decide. onSortChange(key) reports a column; the owner works out the direction.
  • Every child is controlled and owns nothing, so the owner can reset, restore, or later read the state from the URL without touching them.
  • Keys are identity: product.id for rows, group.category for fragments — and <> cannot take a key, so use <Fragment key=…>.
  • Grouping had to become explicit once sorting existed: the running lastCategory trick only works on pre-grouped data.
  • No effect, no memo, no library — none of it is needed when every visible value is state or a computation over state.
  • Real use case (built & run): a seven-component product table with live search, an in-stock filter, sortable columns, category grouping, a selected row with a detail panel, a live count and an empty state.

If you remember one thing: the five steps turn "build this design" into four small decisions about state — and the rest is typing.
