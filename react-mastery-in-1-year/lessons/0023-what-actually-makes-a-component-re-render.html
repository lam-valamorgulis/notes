What actually makes a component re-render

Almost everyone answers this wrong, and the wrong answer is why teams sprinkle memo everywhere and get nothing back. React does not look at your props to decide whether to run your component.

Your win today: you can point at any component in a tree and say, in one sentence, why it just re-rendered — and you can fix the two most common over-rendering problems with zero memoisation, using only where you put state and where you create JSX.

You have spent five months learning to make the screen correct. This month is about making it correct and cheap, and about sharing state across a whole app without threading it through twelve components. Both of those subjects rest on one piece of machinery you have used all year without naming precisely: what causes a component function to run again.

First principle — there are exactly two reasons

Not three, not "props changed". The docs are blunt about it.

React docs · Render and Commit "There are two reasons for a component to render:
1. It's the component's initial render.
2. The component's (or one of its ancestors') state has been updated."

Read reason 2 again, slowly. Or one of its ancestors'. Not "its props changed". Not "the data it uses changed". If state updates anywhere at or above you, you run again — even if you take no props at all, even if nothing you display has changed by one pixel.

And it does not stop at you:

React docs · Render and Commit "This process is recursive: if the updated component returns some other component, React will render that component next, and if that component also returns something, it will render that component next, and so on. The process will continue until there are no more nested components and React knows exactly what should be displayed on screen."

So the default is not "React renders what changed". The default is React re-renders the whole subtree below the state that changed, and then works out which DOM nodes actually need touching. Two different steps, and people collapse them into one word — which is where the confusion starts.

The complete list of triggers

Learn this table. It is the whole answer to "why did this render", and it is a very common interview question because it separates people who have read the docs from people who have read blog posts.

TriggerWhat it isCan you stop it?
Initial renderThe component is mounting for the first time.No — and you would not want to.
Its own state changedA useState setter or a useReducer dispatch ran with a different value.Only by not changing it. memo does nothing here.
An ancestor re-renderedThe default recursive behaviour. Your props may be identical; you still run.Yes — memo, or better, structure (see below).
A context it reads changedThe provider above it got a value that is not Object.is-equal to the last one.No. Documented: memo does not stop this.
An external store it subscribes to changeduseSyncExternalStore — a store outside React told React the snapshot changed.Only with a narrower selector.
Its key changedNot a re-render at all — React unmounts the old component and mounts a fresh one, with fresh state.Yes, by keeping the key stable (lesson 3, lesson 9).

"A prop changed" is not on that list, and cannot be. A prop is a value your parent computed while rendering. For it to change, your parent must have rendered. So "props changed" is always downstream of one of the real triggers.

Say this in an interview

"A component re-renders because it is mounting, because its own state changed, because an ancestor re-rendered, or because a context or external store it subscribes to changed. Props changing is a symptom of the third one, not a cause."

Four myths, and what is actually true

MythThe truth
"React re-renders a child when its props change."React re-renders a child when the parent re-renders, full stop. It does not compare props first — unless you wrapped the child in memo, which is opt-in.
"A re-render means the DOM was updated."No. "React only changes the DOM nodes if there's a difference between renders." A re-render that produces identical output writes nothing to the DOM.
"Re-renders are slow, so I must stop them."Most re-renders are a function call and a shallow comparison. They become slow in bulk (hundreds of rows), or when your component body does real work. Measure before you assume.
"memo makes a component stop re-rendering."memo only skips renders caused by a re-rendering parent. Its own state and any context it reads still re-render it — both documented caveats.

Render is not paint — the two-step you keep collapsing

You have known this since Month 1, but here it earns money. One "update" is really three separate costs, and the fixes for each are different.

StepCostWhat makes it expensive
RenderYour component function runs. React builds a description of the UI.Real work in the body: sorting 5,000 rows, formatting dates in a loop, building objects.
ReconcileReact compares the new description with the old one.The number of elements. 20 nodes is free; 20,000 is not.
Commit + paintReact writes only the differences to the DOM; the browser draws.Actual DOM changes and layout. Zero differences means zero DOM work.

This is why "my app re-renders too much" is rarely the real problem, and why the fix is almost never a blanket memo. The real problem is usually a lot of components re-rendering or one component doing something expensive during render. Two different diseases.

The bail-out you get for free

Setting state to the value it already has is not a re-render. React checks first.

React docs · useState "If the new value you provide is identical to the current state, as determined by an Object.is comparison, React will skip re-rendering the component and its children. This is an optimization. Although in some cases React may still need to call your component before skipping the children, it shouldn't affect your code."

Two useful consequences. First, a "select the same tab again" click costs nothing — you do not need to guard it yourself. Second, the escape hatch in that quote ("may still need to call your component") explains a thing that confuses people: you can see one extra log after clicking, and then silence. React called your function to find out whether the result changed, then dropped it. Your children and your effects did not run.

The trap that hides behind this Object.is, not deep equality. setUser({...user}) with identical contents is always a different object, so it always re-renders. This is the same identity rule from lesson 8 — it decides mutation bugs there and re-render counts here.

One event, one render — batching

React docs · useState "React batches state updates. It updates the screen after all the event handlers have run and have called their set functions. This prevents multiple re-renders during a single event."

So this handler causes one re-render, not three:

function handleSubmit() {
  setStatus('saving');   // no render yet
  setError(null);        // no render yet
  setAttempts(a => a + 1);
}                        // handler ends → React renders once with all three applied

Which means "how many setStates did I call" is not a useful measure of anything. Since React 18 this batching also covers updates inside promises, timeouts and native event handlers — the old "outside React events are not batched" behaviour is gone.

Build it for real — a render counter you can trust

You cannot reason about re-renders you cannot see. Before touching any optimisation, build the instrument. And notice that there are two different things to count.

src/debug/useRenderLog.ts

import { useEffect, useRef } from 'react';

// Counts COMMITS: renders that actually reached the DOM.
// An effect with no dependency array runs after every commit.
export function useCommitCount(label: string) {
  const count = useRef(0);
  useEffect(() => {
    count.current += 1;
    console.log(`[commit] ${label}: ${count.current}`);
  });
}

And the cruder, more revealing one — a log in the component body:

function Legend() {
  console.count('render Legend');   // counts RENDER CALLS
  return <p>Totals include tax</p>;
}
console.count in the bodyuseCommitCount (effect)
CountsEvery time React called your function.Every time the result was committed.
Sees a bailed-out renderYes — this is how you catch the "extra call" from the quote above.No.
Strict Mode in devDoubles the number. Halve it in your head.Not doubled by the extra render, but the first mount runs setup twice.
Honest?No — logging in render breaks purity. Instrumentation only, delete it after.Yes. An effect is the legal place for a side effect.

Now the app under test. One input, one heavy list, and a legend that takes no props at all.

src/App.tsx — stage 1, the version that feels laggy

import { useState } from 'react';

const ROWS = Array.from({ length: 2000 }, (_, i) => ({ id: i, name: `Item ${i}` }));

function Legend() {
  console.count('render Legend');
  return <p className="legend">Showing every matching item.</p>;
}

function Row({ name }: { name: string }) {
  return <li>{name}</li>;
}

export default function App() {
  const [query, setQuery] = useState('');
  console.count('render App');

  const visible = ROWS.filter(r => r.name.includes(query));

  return (
    <div>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <Legend />
      <ul>{visible.map(r => <Row key={r.id} name={r.name} />)}</ul>
    </div>
  );
}

Type five characters and read the console. render App five times — correct and unavoidable, the input's value lives there. render Legend five times — and Legend has no props and no state. That is trigger 3 in the table, doing exactly what it is documented to do. And 2,000 Row calls per keystroke, which is where the lag actually comes from.

Fix 1 — move the state down

Ask the question from Month 3 again, but for a different reason. Last time: who needs to read this state? Now: what is the smallest subtree that needs to re-render when it changes?

The input's query is read by the filter, so it cannot move below the list. But look at the shape again — if the filtering belongs to the list, then the input and the list are one feature and the rest of the page is not.

src/App.tsx — stage 2, the state moved into its own component

function SearchableList() {
  const [query, setQuery] = useState('');
  const visible = ROWS.filter(r => r.name.includes(query));
  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <ul>{visible.map(r => <Row key={r.id} name={r.name} />)}</ul>
    </>
  );
}

export default function App() {
  console.count('render App');
  return (
    <div>
      <Header />
      <SearchableList />
      <Legend />
      <Footer />
    </div>
  );
}

Now type five characters. render App: once. render Legend: once. Header and Footer: once. The keystroke no longer reaches them, because they are no longer below the state that changed. No memo. No useCallback. You moved a useState down one level.

This is the single highest-value re-render fix in React, and it is free. It is also the third of Month 3's ownership moves seen from a new angle: invent a component just to hold state — lesson 13 sold it as "it keeps App small and names the feature", and it turns out to also be the performance fix.

React docs · memo — how to make memoisation unnecessary "Prefer local state and don't lift state up any further than necessary."

Fix 2 — pass the expensive part as children

Sometimes you cannot move the state down, because the state genuinely belongs to a wrapper — a sidebar's open/closed flag, a tab index, a hover state on a container. The wrapper re-renders, and everything inside it goes with it.

The problem

function Layout() {
  const [open, setOpen] = useState(false);
  return (
    <div className={open ? 'wide' : 'narrow'}>
      <button onClick={() => setOpen(!open)}>Toggle</button>
      <ExpensiveReport />   // re-renders on every toggle. Why? It is below the state.
    </div>
  );
}

The fix — the element is created one level up

function Layout({ children }: { children: React.ReactNode }) {
  const [open, setOpen] = useState(false);
  return (
    <div className={open ? 'wide' : 'narrow'}>
      <button onClick={() => setOpen(!open)}>Toggle</button>
      {children}          // the SAME element object as last render
    </div>
  );
}

function Page() {
  return (
    <Layout>
      <ExpensiveReport />   // created HERE, by a component that did not re-render
    </Layout>
  );
}

Why this works, precisely. <ExpensiveReport /> is an object created by whoever wrote that JSX. When Layout re-renders because of its own state, it does not run Page — so children is literally the same object it was last time. React sees an identical element and can reuse the whole subtree. The element became a value that Layout holds, and holding a value is not the same as creating one.

React docs · memo — how to make memoisation unnecessary "When a component wraps other components, let it accept JSX as children. This way, when the wrapper updates its own state, React knows that children don't need re-rendering."

You have already used this without knowing why it was fast: it is the children pattern from lesson 3, and the reason a well-built <Modal> or <Card> does not slow the page down.

The order to try things in

OrderMoveCost to you
1Move the state down into the smallest component that needs it.Free. Usually makes the code clearer too.
2Take the expensive subtree as children so a stateful wrapper cannot re-create it.Free. Usually makes the component more reusable.
3Stop the render from being expensive: fewer elements on screen, no heavy work in the body.Real work, but it fixes the actual disease.
4memo / useMemo / useCallback.Ongoing maintenance, easy to get wrong, silently useless if one prop leaks. Lesson 25.

Moves 1 and 2 do not just skip work — they make the wasted render impossible. Move 4 lets the render be requested and then declines it, which means it still costs a comparison and still breaks the moment someone adds an inline arrow function. Prefer impossible to declined.

Seeing it without console.count

Install React Developer Tools, open the Components tab, click the gear, and tick "Highlight updates when components render". Now every render draws a box around the component. Type in the stage-1 app and the whole page flashes; type in the stage-2 app and only the list does. This is the fastest way to answer "is this a re-render problem at all?" — and the honest answer is often no.

The Profiler tab is the next step: record an interaction, and it shows you each committed render, how long it took, and — in the "Why did this render?" panel, if you enable it — which of the triggers fired. Two notes so the numbers do not lie to you: Strict Mode double-renders in development, and development builds are slower than production. Use it to compare before and after, not to quote absolute milliseconds.

Practice: read the situation, pick the move

Scenario

A teammate opens a pull request titled "fix performance". A dashboard page has one search input at the top and eleven cards below it, and typing feels sticky. Their change wraps all eleven cards in React.memo, wraps every handler in useCallback, and adds useMemo around a rows.length expression. Typing is still sticky. In the same file you notice that the search input's state lives in the page component, that one card renders a 3,000-row table, and that each card is passed config={{ dense: true }} inline.

Work out, in order: why every one of the eleven memo wrappers is doing nothing at all right now; which single change would remove the stickiness for ten of the eleven cards; why the eleventh card needs a different kind of fix; and what you would say in the review that is more useful than "revert this".

Remember this · the Feynman summary
  • Two reasons to render: the initial render, and state updating in this component or one of its ancestors. That is the whole rule.
  • Rendering is recursive. When a component re-renders, React re-renders everything below it by default — props identical or not, props absent or not.
  • "Props changed" is never the cause. A prop can only change because an ancestor re-rendered, so it is the symptom.
  • The other two triggers are context and external stores: a context value that is not Object.is-equal, or a useSyncExternalStore snapshot that changed.
  • A key change is not a re-render — it is an unmount and a fresh mount, with fresh state. That is why it works as a reset.
  • Render is not paint. React only changes DOM nodes when there is a difference between renders, so a re-render with identical output writes nothing.
  • Setting state to the same value bails out (Object.is) — children and effects are skipped, though React may still call your function once to find out.
  • One event is one render. React batches all the setters in a handler, so counting setState calls tells you nothing.
  • Count two different things: console.count in the body counts render calls (and reveals bail-outs); an effect with no dependency array counts commits. Body logging is instrumentation you delete.
  • Fix 1, free: move the state down into the smallest component that needs it. A keystroke cannot re-render what is not below it.
  • Fix 2, free: take the expensive subtree as children. The element was created by a component that did not re-render, so it is the same object and React reuses the subtree.
  • Try structure before memoisation. Moves 1 and 2 make the wasted render impossible; memo only declines it, and one inline object voids the whole thing.
  • Real use case (built & run): a 2,000-row list where five keystrokes re-rendered a props-less Legend five times — then once, after one useState moved down a level.

If you remember one thing: React does not ask "did the props change?" — it asks "did state change at or above me?", and the cheapest fix is always to move the state, not to memoise the child.
