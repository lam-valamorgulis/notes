Month 6 · Lesson 2

Context — sharing state through the tree

Props are a wire between two components. Context is a broadcast to a whole subtree. It removes the plumbing — it does not remove the owner, and it does not make anything global.

Your win today: a typed provider that any depth of the tree can read, plus the two facts that make the difference between a provider that is fine and a provider that re-renders your entire app on every keystroke — and the sentence about memo and context that most candidates get wrong.

Every month so far has taught you to lift state to the nearest common parent. That rule is correct and it eventually hurts: the nearest common parent of "the theme toggle in the header" and "the border colour of a table cell nine levels down" is the root of your app, and now eleven components pass a theme prop they never read.

The problem, precisely

<App theme={theme}>
  <Layout theme={theme}>              // does not use it
    <Content theme={theme}>           // does not use it
      <Panel theme={theme}>           // does not use it
        <Table theme={theme}>         // does not use it
          <Cell theme={theme} />      // ← the one component that needed it

This is prop drilling. It is not a crime — the props are explicit and easy to trace — but four of those six components now break when you rename the prop, and none of them care about themes.

React docs · Passing Data Deeply with Context — before you use context "Start by passing props. If your components are not trivial, it's not unusual to pass a dozen props down through a dozen components. It makes it very clear which components use which data."

"Extract components and pass JSX as children to them. If you pass data through many layers of intermediate components that don't use that data, you may have forgotten to extract some components. Instead of <Layout posts={posts} />, use <Layout><Posts posts={posts} /></Layout>."

"If neither approach works well for you, consider context."

Notice that the second alternative is the same move as lesson 23's free performance fix. That is not a coincidence: a component that only forwards data is usually a component that should have taken children instead. Try that first, every time. Context is the third option.

First principle — context is a broadcast, not a variable

A context is not storage. It holds nothing. What it gives you is a channel: a provider puts a value on the channel for everything inside it, and any descendant can tune in without the components in between knowing the channel exists.

Which means three things people get wrong:

People assumeActually
Context is global state.The state still lives in a normal component with a normal useState. Context only changes how it is read. Render two providers and you have two independent states.
Context replaces lifting state up.It replaces the passing, not the owning. You still choose an owner, and choosing badly still hurts (lesson 13).
Context is a state manager.There are no selectors. A consumer subscribes to the whole value — it cannot say "only wake me when user.name changes". That single limitation drives the rest of this lesson.

The three steps, typed

src/theme/ThemeContext.ts — step 1, create

import { createContext } from 'react';

export type Theme = 'light' | 'dark';

// The argument is the DEFAULT: what a reader gets when there is
// no provider above it. Pick a value that is actually correct alone.
export const ThemeContext = createContext<Theme>('light');

src/theme/ThemeProvider.tsx — step 3, provide

import { useState } from 'react';
import { ThemeContext, type Theme } from './ThemeContext';

export function ThemeProvider({ children }: { children: React.ReactNode }) {
  const [theme, setTheme] = useState<Theme>('light');
  return (
    <ThemeContext value={theme}>      // React 19 form
      <button onClick={() => setTheme(t => (t === 'light' ? 'dark' : 'light'))}>
        Toggle
      </button>
      {children}
    </ThemeContext>
  );
}

src/Cell.tsx — step 2, read

import { useContext } from 'react';
import { ThemeContext } from './theme/ThemeContext';

export function Cell({ label }: { label: string }) {
  const theme = useContext(ThemeContext);   // no props needed
  return <td className={theme}>{label}</td>;
}

Note the shape of the provider: it takes children and puts state around it. That is the same identity trick from lesson 23 — the tree inside children was created by whoever rendered <ThemeProvider>, so a state change inside the provider re-renders the provider itself but React can reuse the children subtree, except for the parts that read this context. The provider being a wrapper is what keeps this cheap.

React 19 · Context as a provider "In React 19, you can render <Context> as a provider instead of <Context.Provider>" … "New Context providers can use <Context> and we will be publishing a codemod to convert existing providers. In future versions we will deprecate <Context.Provider>."

So both of these are correct today, and the first is the form to write in new code:

<ThemeContext value={theme}>{children}</ThemeContext>          // React 19+
<ThemeContext.Provider value={theme}>{children}</ThemeContext.Provider>  // still works

The TypeScript decision: a real default, or no default at all

createContext forces you to answer a question you might not have thought about: what should a component get if nobody provided a value? There are two honest answers and one dishonest one.

ApproachWhen it is right
createContext<Theme>('light')There is a sensible standalone value. A <Cell> with no ThemeProvider above it rendering in light mode is fine.
createContext<Auth | null>(null) + a hook that throwsThere is no sensible default. "The current user" outside a provider is a bug, and you want the error at the point of use.
createContext({} as Auth)Never. It makes TypeScript stop complaining and turns a missing provider into undefined is not a function in production instead of a clear error.

src/auth/AuthContext.ts — the no-default pattern, and your first custom hook

import { createContext, useContext } from 'react';

export type User = { id: string; name: string };
export type AuthValue = { user: User | null; login: (n: string) => void; logout: () => void };

const AuthContext = createContext<AuthValue | null>(null);
export { AuthContext };

export function useAuth(): AuthValue {
  const value = useContext(AuthContext);
  if (value === null) {
    throw new Error('useAuth must be used inside <AuthProvider>');
  }
  return value;                       // TS now knows it is AuthValue, not AuthValue | null
}

Three wins in nine lines, and they are the reason this pattern is everywhere in real codebases:

  1. Every consumer stops writing if (!auth) return null. The null check happens once, in the hook.
  2. The error names the fix. "must be used inside <AuthProvider>" is a better bug report than a crash nine frames deep.
  3. The context object never leaves the module if you do not export it — so no component can read it raw and skip the check.

Lesson 26 turns this into the standard shape for a feature. For now, notice what it is: a function whose name starts with use, which calls a hook. That is the entire definition of a custom hook.

Reading context conditionally — use

useContext obeys the rules of hooks: top level only, no early returns above it. React 19 adds an escape hatch.

React 19 · reading context with use "You can also read context with use, allowing you to read Context conditionally such as after early returns." 
import {use} from 'react';
import ThemeContext from './ThemeContext'

function Heading({children}) {
  if (children == null) {
    return null;
  }

  // This would not work with useContext
  // because of the early return.
  const theme = use(ThemeContext);
  return (
    <h1 style={{color: theme.color}}>
      {children}
    </h1>
  );
}

Use it when you genuinely have an early return above the read. Do not use it to justify a component with six conditional context reads — that is a component that wants splitting.

The fact that decides everything: when do consumers re-render?

React docs · useContext "React automatically re-renders all the children that use a particular context starting from the provider that receives a different value. The previous and the next values are compared with the Object.is comparison."

"React automatically re-renders all the children that use a particular context starting from the provider that receives a different value. Skipping re-renders with memo does not prevent the children receiving fresh context values."

Read the second quote twice. This is lesson 23's fourth trigger, and it is the one memo cannot touch. A memo-wrapped component with unchanged props will still re-render if it reads a context whose value changed — and it has to, or it would show stale data.

The bug you will ship at least once

The moment your context holds more than one thing, you write this:

src/auth/AuthProvider.tsx — the broken version

export function AuthProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<User | null>(null);

  function login(name: string) { setUser({ id: crypto.randomUUID(), name }); }
  function logout() { setUser(null); }

  // 🔴 A brand-new object on EVERY render of AuthProvider.
  // 🔴 login and logout are brand-new functions too.
  return (
    <AuthContext value={{ user, login, logout }}>
      {children}
    </AuthContext>
  );
}

The symptom. Any state change in AuthProvider — or in anything above it — produces a new value object. Object.is says "different". Every single useAuth() consumer in the app re-renders, no matter how deep, no matter that user is the identical object it was before. Wrap them in memo and nothing improves, because of the caveat you just read.

The nasty version of this is a provider that holds two unrelated things. Put user and a notifications array in the same context, and every arriving notification re-renders every component that only wanted the user's name.

Fix A — stabilise the value

React docs · useContext — optimizing re-renders when passing objects and functions 
import { useCallback, useMemo } from 'react';

function MyApp() {
  const [currentUser, setCurrentUser] = useState(null);

  const login = useCallback((response) => {
    storeCredentials(response.credentials);
    setCurrentUser(response.user);
  }, []);

  const contextValue = useMemo(() => ({
    currentUser,
    login
  }), [currentUser, login]);

  return (
    <AuthContext value={contextValue}>
      <Page />
    </AuthContext>
  );
}
"As a result of this change, Page will not need to re-render unless currentUser has changed."

Typed, in our file:

export function AuthProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<User | null>(null);

  const login = useCallback((name: string) => {
    setUser({ id: crypto.randomUUID(), name });
  }, []);                                  // [] is honest: it uses only the setter

  const logout = useCallback(() => setUser(null), []);

  const value = useMemo<AuthValue>(
    () => ({ user, login, logout }),
    [user, login, logout],
  );

  return <AuthContext value={value}>{children}</AuthContext>;
}

Two details that matter. The dependency arrays are honest — login genuinely uses nothing but setUser, which is stable (lesson 17's not-reactive list), so [] is a fact, not a shortcut. And value now only changes when user changes, which is exactly what a consumer means by "something happened".

This is the one place memoising is not optional Lesson 25 will argue that most useMemo is noise. A context value is the exception. Here the memo does not save a few microseconds — it decides how many components in your app re-render, and there is no structural alternative that gets you the same result. Memoise context values by default.

Fix B — split the context in two

Fix A still wakes every consumer when user changes, including the components that only ever call logout() and never read user. That is the missing-selector limitation biting. The answer is to stop putting both on the same channel.

// two contexts, two channels
const AuthContext = createContext<User | null>(null);
const AuthActionsContext = createContext<AuthActions | null>(null);

export function AuthProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<User | null>(null);

  const actions = useMemo<AuthActions>(() => ({
    login: (name: string) => setUser({ id: crypto.randomUUID(), name }),
    logout: () => setUser(null),
  }), []);                       // [] — actions never change, for the app's whole life

  return (
    <AuthActionsContext value={actions}>
      <AuthContext value={user}>{children}</AuthContext>
    </AuthActionsContext>
  );
}

Now a <LogoutButton> calls useAuthActions(), reads a value that never changes for the lifetime of the app, and therefore never re-renders when a user logs in. A <Greeting> calls useAuth() and re-renders only when the user does change. Two channels, two audiences.

Put the actions provider outside the value provider, as above. It never changes, so it never re-renders, so it never even considers re-rendering the tree below it.

Nesting — an inner provider wins

A provider overrides any provider of the same context above it, for its own subtree only. That is a feature, not a quirk.

<ThemeContext value="light">
  <Page />                        // reads "light"
  <ThemeContext value="dark">
    <PromoCard />                 // reads "dark" — a dark card on a light page
  </ThemeContext>
</ThemeContext>

The docs' own example is nicer than a theme: a <Section> reads the current heading level from context and provides level + 1 to its children, so every <Heading> renders the right <h1>–<h6> for how deeply it is nested, with nobody passing a number anywhere. That is context used for something props genuinely cannot express: a value that depends on position in the tree.

The caveat that costs an hour A useContext() call is not affected by a provider returned from the same component. If Section both provides level + 1 and reads the level, it reads the level from above itself. The provider must be above the reader in the tree, not beside it.

When context is the right tool — and when it is not

Use context forWhy it fits
ThemingRead by everything, changed rarely, no sensible prop path.
The current accountRead by many unrelated places; changes a handful of times per session.
RoutingThe current route, and whether a link is active. This is how React Router works inside (Month 8).
Managing statePassing complex state deep, usually with a reducer's dispatch beside it (lesson 26).
Values that depend on depthHeading level, nesting level, a form's field prefix. Props cannot express "where am I".
Do not use context forWhat to do instead
Values that change many times a second — mouse position, scroll offset, a form field being typed into.Keep it local, or use an external store with selectors. Every change wakes every reader.
Data from a server.A server-state library — caching, refetching and invalidation are the actual problem (Month 7).
State two nearby components share.Lift it to the common parent. Context here is a bigger machine for a smaller job.
Avoiding thinking about ownership.Nothing. This is the real failure mode: one giant AppContext that everything reads and everything writes.

Build it for real — a theme provider in three stages

Small app, three components, and a console that tells you the truth. The point is not the theme — it is watching the re-render count change while the visible behaviour stays identical.

src/theme/ThemeProvider.tsx — stage 1, the version with the bug

import { createContext, useContext, useState } from 'react';

export type Theme = 'light' | 'dark';
type ThemeValue = { theme: Theme; toggle: () => void };

const ThemeContext = createContext<ThemeValue | null>(null);

export function useTheme() {
  const v = useContext(ThemeContext);
  if (!v) throw new Error('useTheme must be used inside <ThemeProvider>');
  return v;
}

export function ThemeProvider({ children }: { children: React.ReactNode }) {
  const [theme, setTheme] = useState<Theme>('light');
  const [clicks, setClicks] = useState(0);   // unrelated state, on purpose

  return (
    <ThemeContext value={{ theme, toggle: () => setTheme(t => t === 'light' ? 'dark' : 'light') }}>
      <button onClick={() => setClicks(c => c + 1)}>
        Unrelated clicks: {clicks}
      </button>
      {children}
    </ThemeContext>
  );
}

src/App.tsx

import { memo } from 'react';
import { ThemeProvider, useTheme } from './theme/ThemeProvider';

const Badge = memo(function Badge() {
  console.count('render Badge (memo, reads theme)');
  const { theme } = useTheme();
  return <span>theme: {theme}</span>;
});

const Static = memo(function Static() {
  console.count('render Static (memo, reads nothing)');
  return <p>I never change.</p>;
});

function ToggleButton() {
  console.count('render ToggleButton (actions only)');
  const { toggle } = useTheme();
  return <button onClick={toggle}>Toggle theme</button>;
}

export default function App() {
  return (
    <ThemeProvider>
      <Badge />
      <Static />
      <ToggleButton />
    </ThemeProvider>
  );
}

Click "Unrelated clicks" five times and read the console. Halve everything for Strict Mode, then look at the shape:

ComponentRenders on "unrelated clicks"Why
Badge (memo)Every clickNew value object → context changed → memo cannot help. The documented caveat, live.
ToggleButtonEvery clickReads the same context, and never even looks at theme.
Static (memo)OnceArrived as children, created by App, which did not re-render — and it reads no context.

That last row is the control in the experiment: it proves the provider's children trick is working, so the other two rows are caused by the context value and nothing else.

src/theme/ThemeProvider.tsx — stage 2, memoise the value

const toggle = useCallback(() => {
  setTheme(t => (t === 'light' ? 'dark' : 'light'));
}, []);                                    // updater form → no dependency on theme

const value = useMemo<ThemeValue>(() => ({ theme, toggle }), [theme, toggle]);

return (
  <ThemeContext value={value}>
    <button onClick={() => setClicks(c => c + 1)}>Unrelated clicks: {clicks}</button>
    {children}
  </ThemeContext>
);

Click again. Badge and ToggleButton now log nothing on unrelated clicks, and both log once when you press "Toggle theme". Same behaviour on screen, a fraction of the renders. Note why toggle could keep an empty dependency array: the updater form setTheme(t => ...) means it never reads theme — lesson 17's first removal recipe, paying off again.

src/theme/ThemeProvider.tsx — stage 3, split the channels

const ThemeContext = createContext<Theme>('light');
const ThemeActionsContext = createContext<(() => void) | null>(null);

export function useTheme() { return useContext(ThemeContext); }

export function useToggleTheme() {
  const t = useContext(ThemeActionsContext);
  if (!t) throw new Error('useToggleTheme must be used inside <ThemeProvider>');
  return t;
}

export function ThemeProvider({ children }: { children: React.ReactNode }) {
  const [theme, setTheme] = useState<Theme>('light');
  const toggle = useCallback(() => {
    setTheme(t => (t === 'light' ? 'dark' : 'light'));
  }, []);

  return (
    <ThemeActionsContext value={toggle}>
      <ThemeContext value={theme}>{children}</ThemeContext>
    </ThemeActionsContext>
  );
}

Now press "Toggle theme" ten times. Badge re-renders ten times, correctly — it displays the theme. ToggleButton re-renders zero times, because toggle is the same function it was on the first render and the button does not read the theme at all. No useMemo was needed for the value either, because theme is a string: primitives compare by value under Object.is.

The general shape One context per thing that changes on its own schedule, plus one context for the stable actions. When you get to reducers in lesson 26 this gets even cleaner, because dispatch has a stable identity by design — no useCallback, no useMemo, nothing to get wrong.

Extend it — three reps

  1. Put two unrelated things in one context on purpose. Add a notifications: string[] to the stage-2 value and a button that pushes one every second. Watch Badge re-render once a second while the theme never changes. Then fix it by splitting, and say the rule out loud: one channel per thing that changes on its own schedule.
  2. Delete the throw. Change useTheme to return the raw useContext result, render <Badge /> outside the provider, and read the error you get. Compare it with the error the throwing version gives. This is why the pattern exists.
  3. Build the heading-level provider. A <Section> that reads the level from context and provides level + 1; a <Heading> that renders h1–h6 from it. Nest four deep with no props anywhere. Then try to do the same thing with props and describe what breaks when someone moves one <Section>.

Practice: read the situation, pick the move

Scenario

An app has a single AppContext at the root. Its value is an inline object holding user, theme, cart, toasts, isSidebarOpen, and eight functions to change them. Roughly forty components call useApp(). A product page with a quantity input feels sluggish while typing, and someone has already wrapped every leaf in React.memo with no effect. A junior asks whether the fix is to switch to Redux.

Work out, in order: exactly why the forty consumers re-render on every keystroke; why every memo in the app is powerless against it; the smallest change that fixes the typing lag without touching any consumer; the follow-up refactor you would do next week and how you would slice it; and the honest answer to the Redux question.

Remember this · the Feynman summary
  • Order of attack: props → children → context. A component that only forwards data usually wanted children instead.
  • Context is a broadcast channel, not storage. The state still lives in a component with a normal useState; two providers mean two independent states. Context changes how a value is read, never who owns it.
  • Three steps: createContext with a default, useContext to read, and a provider above the readers. React 19 writes the provider as <Context value={x}>; <Context.Provider> still works and will be deprecated.
  • Pick the default honestly: a real standalone value, or null plus a hook that throws. Never {} as T — it turns a missing provider into a crash somewhere else.
  • Consumers re-render when the value is not Object.is-equal, starting from the provider that got the new value.
  • memo cannot stop a context re-render. Documented, and the caveat interviewers ask about — a memoised component with identical props still re-renders when a context it reads changes.
  • An inline object as value is the classic bug. A new object every render means "changed" is always true, so every consumer in the app wakes up on every provider render.
  • So memoise context values by default — useMemo the object, useCallback the functions. This is the one place memoisation is structural, not a micro-optimisation.
  • Split the channels: one context for the value that changes, one for the stable actions. Action-only components then never re-render at all. With a reducer this is free, because dispatch is already stable.
  • Context has no selectors. A consumer subscribes to the whole value, so putting two unrelated things on one channel makes them wake each other. That limit is why external stores exist.
  • An inner provider overrides an outer one for its subtree — and a useContext call is not affected by a provider returned from the same component.
  • Good fits: theme, current account, routing, deep state with a reducer, and values that depend on depth. Bad fits: anything changing many times a second, server data, and state two nearby components share.
  • Real use case (built & run): a theme provider taken from "every consumer re-renders on an unrelated click" to "the toggle button never re-renders at all", in two changes and with the screen behaving identically.

If you remember one thing: a consumer wakes up when the whole context value changes identity — so the two skills are keeping that identity stable and splitting the value so fewer people care.
