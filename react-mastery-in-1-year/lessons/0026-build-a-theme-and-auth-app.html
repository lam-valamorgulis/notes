Month 6 · Lesson 4 · The real build

Build it — a theme & auth app with reducers and custom hooks

Two features every app has, built so that typing a password does not re-render the header, and so the login rules live in one pure function you can test without React.

Your win today: a typed reducer with a state union that cannot contradict itself, two providers whose action consumers never re-render, six custom hooks — four of which delete sixty lines from lesson 22's modal — and a re-render audit you performed yourself, before and after.

This is the month's headline build and the last lesson of Phase 2. Everything hard is behind you now: effects, refs, timing, context, re-renders. What is left is packaging — how you organise state logic so a feature stays understandable at 300 lines, and how you extract behaviour so the next component gets it for free.

First principle 1 — a reducer is a list of things that can happen

With useState, your handlers describe how state should change. Ten handlers means ten places that know the shape of your state, and a bug can be in any of them.

A reducer flips the direction. Handlers describe what happened; one function decides what that means.

React docs · Extracting State Logic into a Reducer A reducer function "takes two arguments—the current state and an action object—and returns the next state".

"Reducers are named after the reduce() operation performed on arrays." … "React reducers follow the same idea: they take the state so far and the action, and return the next state. In this way, they accumulate actions over time into state."

That analogy is worth taking literally. [1,2,3].reduce((sum, n) => sum + n) folds many numbers into one number. Your component folds many events into one state. The reducer is the folding function, and dispatch is how you hand it the next item.

useStateuseReducer
Code sizeLess code up front.More code initially, but "helps cut down code if many event handlers modify state similarly".
ReadabilityVery easy for simple updates.Better for complex updates; "cleanly separates the how of update logic from the what happened of event handlers".
DebuggingHard to tell where and why state was set wrongly.One console.log in the reducer shows every update and which action caused it.
TestingNeeds a realistic component environment."The reducer is a pure function that can be exported and tested separately in isolation."
PreferenceThe docs' own last row: it is a matter of preference, and you can mix both in one component.

The debugging and testing rows are why this build uses one. Authentication is a feature where the state graph is small but the wrong transition is expensive.

The three rules

  1. Reducers must be pure. "Similar to state updater functions, reducers run during rendering." No requests, no timers, no mutation — return a new object.
  2. Each action describes a single user interaction, even when it changes five fields. The docs' example: a "Reset" button on a five-field form dispatches one reset_form, not five set_fields.
  3. Name the action after what happened, not after how you want state to change. "Choose a name that says what happened!" — sign_in_failed, not set_error.

Rule 3 sounds like style advice. It is not. set_error forces every caller to know that failure means "an error string exists". sign_in_failed lets the reducer decide that failure also clears the password field, stops the spinner, and increments an attempt count — later, without touching a single caller.

First principle 2 — a custom hook shares logic, not state

This is the misconception to kill before you write one. A custom hook is not a store, not a singleton, not a shared variable.

React docs · Reusing Logic with Custom Hooks "Custom Hooks let you share stateful logic but not state itself. Each call to a Hook is completely independent from every other call to the same Hook."

"The code inside your custom Hooks should be pure, like your component's code. Custom Hooks re-run during every re-render of your component and always receive the latest props and state. Think of custom Hooks' code as part of your component's body."

That last line is the mental model: a custom hook is a copy-paste that happens at call time. Two components calling useOnlineStatus() get two separate useStates and two separate effects. They agree only because they read the same outside world.

not because the hook shares anything. To share actual state: one owner + context. That is what this build does for the user.

The naming rules matter too, and they are enforced by the linter:

React docs · Reusing Logic with Custom Hooks "Hook names must start with use followed by a capital letter" … and functions that do not call other Hooks should not use the prefix: a plain getSorted(items) stays a plain function, while useSorted(items) would be misleading.

"Do NOT extract custom Hooks that act as alternatives to the useEffect API itself" — avoid useMount(fn), useEffectOnce(fn), useUpdateEffect(fn). "Keep your custom Hooks focused on concrete high-level use cases": useData(url), useOnlineStatus(), useChatRoom(options).

Test any hook you are about to write against that: useEscapeKey(onEscape) names a concrete thing a user does. useMount(fn) names a React internal and will lie to you the day Strict Mode or Suspense changes the mount sequence.

Step 1 — the state union that cannot contradict itself

src/auth/authReducer.ts

export type User = { id: string; name: string; role: 'admin' | 'member' };

// Month 3's rule, enforced by the type: no isLoading + error at once,
// no user + signed-out at once. Every state below is a real screen.
export type AuthState =
  | { status: 'signed_out' }
  | { status: 'submitting'; name: string }
  | { status: 'signed_in'; user: User }
  | { status: 'failed'; message: string };

// Named after what HAPPENED, never after how state should change.
export type AuthAction =
  | { type: 'sign_in_submitted'; name: string }
  | { type: 'sign_in_succeeded'; user: User }
  | { type: 'sign_in_failed'; message: string }
  | { type: 'signed_out' }
  | { type: 'session_restored'; user: User };

export const initialAuthState: AuthState = { status: 'signed_out' };

export function authReducer(state: AuthState, action: AuthAction): AuthState {
  switch (action.type) {
    case 'sign_in_submitted':
      // The rule lives HERE, not in the component: a second submit
      // while one is in flight is not an error, it is a no-op.
      if (state.status === 'submitting') return state;
      return { status: 'submitting', name: action.name };

    case 'sign_in_succeeded':
      return { status: 'signed_in', user: action.user };

    case 'sign_in_failed':
      return { status: 'failed', message: action.message };

    case 'signed_out':
      return { status: 'signed_out' };

    case 'session_restored':
      if (state.status === 'signed_in') return state;
      return { status: 'signed_in', user: action.user };

    default: {
      // If someone adds an action and forgets a case, THIS line
      // fails to compile. The exhaustiveness check is the whole point.
      const unhandled: never = action;
      return state;
    }
  }
}

Four things in that file are doing real work.

DetailWhat it prevents
A discriminated union for state, keyed on statusReading state.user when the status is 'failed' — TypeScript refuses. This is lesson 12's "no contradictions" rule made unrepresentable rather than merely discouraged.
A discriminated union for actionsDispatching { type: 'sign_in_succeeded' } with no user, or a typo'd type string.
const unhandled: never = actionAdding a sixth action next year and silently forgetting to handle it. The build breaks instead of the app.
Returning state itself for a no-opAn unnecessary re-render — "React will ignore your update if the next state is equal to the previous state, as determined by an Object.is comparison."
The one that looks like a no-op and is not return { ...state } is a different object, so it re-renders. If nothing happened, return the exact same reference. Lesson 8's identity rule, one more time, now deciding render counts.

Step 2 — the fake API, and where async work belongs

src/auth/api.ts

import type { User } from './authReducer';

export async function signInRequest(name: string): Promise<User> {
  await new Promise(r => setTimeout(r, 700));
  if (name.trim().toLowerCase() === 'nobody') {
    throw new Error('No account found for that name.');
  }
  return { id: crypto.randomUUID(), name: name.trim(), role: 'member' };
}

The reducer cannot call this. Reducers run during rendering and must be pure — so the sequence is: dispatch what happened, do the async work outside, dispatch what happened next. Three actions, one reducer, zero impurity.

And note where it does not go: not in a useEffect. Signing in is caused by a user pressing a button, which is Month 4's first door. An effect here would be lesson 16's most common mistake wearing a login form.

Step 3 — the provider, and why dispatch makes this easy

src/auth/AuthProvider.tsx

import { createContext, useContext, useMemo, useReducer, useRef } from 'react';
import { authReducer, initialAuthState, type AuthState } from './authReducer';
import { signInRequest } from './api';

type AuthActions = {
  signIn: (name: string) => Promise<void>;
  signOut: () => void;
};

const AuthStateContext = createContext<AuthState>(initialAuthState);
const AuthActionsContext = createContext<AuthActions | null>(null);

export function useAuth(): AuthState {
  return useContext(AuthStateContext);
}

export function useAuthActions(): AuthActions {
  const actions = useContext(AuthActionsContext);
  if (!actions) throw new Error('useAuthActions must be used inside <AuthProvider>');
  return actions;
}

export function AuthProvider({ children }: { children: React.ReactNode }) {
  const [state, dispatch] = useReducer(authReducer, initialAuthState);

  // A fact about the past that the screen never reads → a ref (lesson 19).
  // Written in a handler, never during render.
  const inFlight = useRef(false);

  const actions = useMemo<AuthActions>(() => ({
    async signIn(name: string) {
      if (inFlight.current) return;
      inFlight.current = true;
      dispatch({ type: 'sign_in_submitted', name });
      try {
        const user = await signInRequest(name);
        dispatch({ type: 'sign_in_succeeded', user });
      } catch (error) {
        dispatch({
          type: 'sign_in_failed',
          message: error instanceof Error ? error.message : 'Sign-in failed.',
        });
      } finally {
        inFlight.current = false;
      }
    },
    signOut() {
      dispatch({ type: 'signed_out' });
    },
  }), []);   // [] is HONEST: dispatch has a stable identity, refs never change

  return (
    <AuthActionsContext value={actions}>
      <AuthStateContext value={state}>{children}</AuthStateContext>
    </AuthActionsContext>
  );
}
React docs · useReducer "The dispatch function has a stable identity, so you will often see it omitted from Effect dependencies. Including it will not cause the Effect to fire."

That one sentence is why the reducer-plus-context pattern is cleaner than the useState version from lesson 24. There, login and logout each needed a useCallback whose dependency array you had to keep honest. Here the actions object closes over nothing that can change — dispatch is stable by design and a ref object never changes identity — so [] is a fact, and AuthActionsContext holds one value for the app's entire life.

Consequence: a sign-out button re-renders zero times when a user signs in. Not "fewer times". Zero.

Why the actions provider is on the outside It never changes, so it never re-renders, so it never even asks whether the tree below it should. Put the stable channel outermost and the volatile one innermost, every time.

Step 4 — useLocalStorage, your first real custom hook

src/lib/useLocalStorage.ts

import { useEffect, useState } from 'react';

export function useLocalStorage<T>(key: string, initial: T) {
  // Lazy initialiser: reads storage ONCE, not on every render (lesson 21).
  const [value, setValue] = useState<T>(() => {
    try {
      const raw = window.localStorage.getItem(key);
      return raw === null ? initial : (JSON.parse(raw) as T);
    } catch {
      return initial;   // corrupt JSON, or storage blocked entirely
    }
  });

  // Writing to storage is a side effect on an outside system → an effect.
  useEffect(() => {
    try {
      window.localStorage.setItem(key, JSON.stringify(value));
    } catch {
      // quota exceeded, or Safari private mode. The app must still work.
    }
  }, [key, value]);

  return [value, setValue] as const;   // as const → a tuple, not (T | setter)[]
}
DecisionWhy
Lazy useState(() => …)Reading localStorage is synchronous disk-backed work. Doing it on every render for no reason is exactly the "expensive body" problem from lesson 25.
Two try/catch blocksStorage throws in real browsers: blocked cookies, private mode, full quota, and hand-edited corrupt JSON. A theme preference must never crash the app.
as const on the returnWithout it TypeScript infers (T | Dispatch<SetStateAction<T>>)[] and destructuring gives you a union. With it you get a real 2-tuple.
Returns the raw setterIt is already stable, and it keeps the hook honest — this hook persists a value, it does not invent an API.
Not done: cross-tab syncA storage event listener would keep two tabs in step. Left out deliberately — it is a different feature, and pretending otherwise would hide a decision.

Now check it against the docs' naming rule. It calls hooks, so the use prefix is correct. It names a concrete use case — persisting one value — not a React lifecycle moment. It passes.

Step 5 — the system theme is an external store

"Follow the OS setting" is not React state. It is a value that lives in the browser and changes without asking. Lesson 16 named the right tool for that shape, and this is it.

src/theme/useSystemTheme.ts

import { useSyncExternalStore } from 'react';

const QUERY = '(prefers-color-scheme: dark)';

// Module scope, so both functions have a stable identity.
// Defined inside the hook they would be new every render → resubscribe every render.
function subscribe(onStoreChange: () => void) {
  const mql = window.matchMedia(QUERY);
  mql.addEventListener('change', onStoreChange);
  return () => mql.removeEventListener('change', onStoreChange);
}

function getSnapshot(): 'light' | 'dark' {
  return window.matchMedia(QUERY).matches ? 'dark' : 'light';
}

function getServerSnapshot(): 'light' | 'dark' {
  return 'light';   // there is no matchMedia on the server (Month 10)
}

export function useSystemTheme() {
  return useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot);
}

Six lines of hook, and it is tear-free: React reads the snapshot at the right moment, so no part of the screen can show light while another shows dark. The useState-plus-useEffect version of this is longer and paints the wrong value on the first frame.

Why the two functions live at module scope is the same identity rule as everywhere else this month: subscribe is compared by useSyncExternalStore, and a fresh function every render means unsubscribe-and-resubscribe every render.

Step 6 — the theme provider, three channels

src/theme/ThemeProvider.tsx

import { createContext, useContext, useEffect } from 'react';
import { useLocalStorage } from '../lib/useLocalStorage';
import { useSystemTheme } from './useSystemTheme';

export type ThemePreference = 'light' | 'dark' | 'system';
export type ResolvedTheme = 'light' | 'dark';

const ThemeContext = createContext<ResolvedTheme>('light');
const PreferenceContext = createContext<ThemePreference>('system');
const SetThemeContext = createContext<((p: ThemePreference) => void) | null>(null);

export const useTheme = () => useContext(ThemeContext);
export const useThemePreference = () => useContext(PreferenceContext);

export function useSetTheme() {
  const set = useContext(SetThemeContext);
  if (!set) throw new Error('useSetTheme must be used inside <ThemeProvider>');
  return set;
}

export function ThemeProvider({ children }: { children: React.ReactNode }) {
  const [preference, setPreference] = useLocalStorage<ThemePreference>('theme', 'system');
  const system = useSystemTheme();

  // DERIVED, not stored. Month 3's rule: the resolved theme is a calculation.
  const resolved: ResolvedTheme = preference === 'system' ? system : preference;

  // The <html> element is outside React → an effect, with the DOM as the target.
  useEffect(() => {
    document.documentElement.dataset.theme = resolved;
  }, [resolved]);

  return (
    <SetThemeContext value={setPreference}>
      <PreferenceContext value={preference}>
        <ThemeContext value={resolved}>{children}</ThemeContext>
      </PreferenceContext>
    </SetThemeContext>
  );
}

Three contexts, and each one has a different audience:

ContextRead byChanges when
ThemeContext ('light' | 'dark')Anything that draws differently in dark mode.The preference changes, or the OS setting changes while on 'system'.
PreferenceContextOnly the theme menu, to show which of the three is selected.The user picks a different option. Not when the OS flips.
SetThemeContextOnly the theme menu's buttons.Never. A useState setter has a stable identity, so no useCallback and no useMemo.

Splitting the preference from the resolved theme is not over-engineering — it is the difference between "the OS went dark at 6pm" waking every button in the app or waking only the components that actually render differently.

And notice there is no useMemo anywhere in this provider. Every value is a string or a stable setter, and primitives compare by value under Object.is. The cheapest way to avoid memoising a context value is to not put an object in it.

Step 7 — four hooks that delete sixty lines

Lesson 22 built a modal with eight requirements and left four of them tangled inside one component. They are four independent behaviours with four independent lifetimes, which is exactly the shape a custom hook is for.

src/hooks/useEscapeKey.ts

import { useEffect, useEffectEvent } from 'react';   // useEffectEvent: React 19.2+

export function useEscapeKey(enabled: boolean, onEscape: () => void) {
  // The handler is not reactive — we do not want a re-subscribe when the
  // caller passes a new arrow function (lesson 17's fourth removal recipe).
  const handleEscape = useEffectEvent(onEscape);

  useEffect(() => {
    if (!enabled) return;
    function onKeyDown(event: KeyboardEvent) {
      if (event.key === 'Escape') handleEscape();
    }
    document.addEventListener('keydown', onKeyDown);
    return () => document.removeEventListener('keydown', onKeyDown);
  }, [enabled]);
}

src/hooks/useOutsideClick.ts

import { useEffect, useEffectEvent, type RefObject } from 'react';

// Generic in T, not just RefObject<HTMLElement | null>: RefObject has a
// mutable `current`, so it is invariant — a RefObject<HTMLDivElement | null>
// would NOT be assignable to RefObject<HTMLElement | null>.
export function useOutsideClick<T extends HTMLElement>(
  ref: RefObject<T | null>,
  enabled: boolean,
  onOutside: () => void,
) {
  const handleOutside = useEffectEvent(onOutside);

  useEffect(() => {
    if (!enabled) return;
    // pointerdown, NOT click — a click fires on the common ancestor of
    // press and release, so drag-selecting text inside the panel and
    // releasing outside it would close the modal (lesson 22).
    function onPointerDown(event: PointerEvent) {
      const node = ref.current;
      if (node && !node.contains(event.target as Node)) handleOutside();
    }
    document.addEventListener('pointerdown', onPointerDown);
    return () => document.removeEventListener('pointerdown', onPointerDown);
  }, [enabled, ref]);
}

src/hooks/useScrollLock.ts

import { useEffect } from 'react';

export function useScrollLock(enabled: boolean) {
  useEffect(() => {
    if (!enabled) return;
    const previous = document.body.style.overflow;   // save what was there
    document.body.style.overflow = 'hidden';
    return () => { document.body.style.overflow = previous; };
  }, [enabled]);
}

src/hooks/useFocusTrap.ts

import { useEffect, type RefObject } from 'react';

const FOCUSABLE = [
  'a[href]', 'button:not([disabled])', 'input:not([disabled])',
  'select:not([disabled])', 'textarea:not([disabled])',
  '[tabindex]:not([tabindex="-1"])',
].join(', ');

export function useFocusTrap<T extends HTMLElement>(
  ref: RefObject<T | null>,
  enabled: boolean,
) {
  useEffect(() => {
    if (!enabled) return;
    const panel = ref.current;    // copy to a local — cleanup runs later (lesson 21)
    if (!panel) return;

    const previouslyFocused = document.activeElement as HTMLElement | null;
    panel.focus();

    function onKeyDown(event: KeyboardEvent) {
      if (event.key !== 'Tab') return;
      // Query at the MOMENT Tab is pressed — the panel's contents
      // can change while it is open (lesson 22).
      const items = Array.from(panel.querySelectorAll<HTMLElement>(FOCUSABLE));
      if (items.length === 0) { event.preventDefault(); return; }
      const first = items[0];
      const last = items[items.length - 1];

      if (event.shiftKey && document.activeElement === first) {
        event.preventDefault();
        last.focus();
      } else if (!event.shiftKey && document.activeElement === last) {
        event.preventDefault();
        first.focus();
      }
    }

    panel.addEventListener('keydown', onKeyDown);
    return () => {
      panel.removeEventListener('keydown', onKeyDown);
      previouslyFocused?.focus();   // give focus back to whatever opened it
    };
  }, [enabled, ref]);
}

src/components/Modal.tsx — the whole of lesson 22's part A, now

import { useRef } from 'react';
import { createPortal } from 'react-dom';
import { useEscapeKey } from '../hooks/useEscapeKey';
import { useOutsideClick } from '../hooks/useOutsideClick';
import { useFocusTrap } from '../hooks/useFocusTrap';
import { useScrollLock } from '../hooks/useScrollLock';

type Props = { open: boolean; onClose: () => void; title: string; children: React.ReactNode };

export function Modal({ open, onClose, title, children }: Props) {
  const panelRef = useRef<HTMLDivElement>(null);

  useEscapeKey(open, onClose);          // requirement 3
  useOutsideClick(panelRef, open, onClose);  // requirement 4
  useFocusTrap(panelRef, open);         // requirements 5, 6, 7
  useScrollLock(open);                  // requirement 8

  if (!open) return null;               // AFTER the hooks — always

  return createPortal(
    <div className="overlay">
      <div
        className="panel"
        ref={panelRef}
        role="dialog"
        aria-modal="true"
        aria-labelledby="modal-title"
        tabIndex={-1}
      >
        <h2 id="modal-title">{title}</h2>
        {children}
      </div>
    </div>,
    document.body,
  );
}

Four lines of behaviour. The component is now about markup, and each behaviour can be read, tested and reused on its own — a dropdown wants useOutsideClick and useEscapeKey but not the trap or the lock, and now it can have exactly those two.

DetailWhy it is like that
Every hook takes enabled as its first argumentHooks cannot be called conditionally. The condition moves inside, as an early return in the effect — which reads as "when closed, sync nothing".
if (!open) return null sits below all four hooksRules of hooks: same calls, same order, every render.
useEffectEvent for the callbacksSo a caller writing onClose={() => setOpen(false)} inline does not tear down and re-add the document listener on every render.
tabIndex={-1} on the panelpanel.focus() does nothing on an element that cannot receive focus.
Names describe user-visible behaviouruseEscapeKey, not useKeydownEffect. The docs' "concrete high-level use cases" rule.
The ref hooks are generic in TRefObject has a mutable current, so it is invariant: a RefObject<HTMLDivElement | null> is not assignable to RefObject<HTMLElement | null>. <T extends HTMLElement> lets T infer from the call site.
The line you must not cross Do not now write useModal(open, onClose) that calls all four. It is tempting and it is a step towards the useMount anti-pattern: a hook whose name describes a bundle of React plumbing rather than one behaviour. Four named behaviours at the call site is documentation. One useModal is a black box, and the first time a dropdown needs three of the four you will fork it.

Step 8 — the screen, and where form state lives

src/components/SignInForm.tsx

import { useState } from 'react';
import { useAuth, useAuthActions } from '../auth/AuthProvider';

export function SignInForm() {
  console.count('render SignInForm');
  const [name, setName] = useState('');       // ← LOCAL. Never in context.
  const state = useAuth();
  const { signIn } = useAuthActions();

  const busy = state.status === 'submitting';

  return (
    <form
      onSubmit={e => { e.preventDefault(); signIn(name); }}
    >
      <input
        value={name}
        onChange={e => setName(e.target.value)}
        disabled={busy}
        placeholder="Your name (try “nobody”)"
      />
      <button disabled={busy || name.trim() === ''}>
        {busy ? 'Signing in…' : 'Sign in'}
      </button>
      {state.status === 'failed' && <p role="alert">{state.message}</p>}
    </form>
  );
}

The most important line in this file is useState(''). A half-typed name is transient state belonging to one component. Putting it in context would re-render every consumer in the app on every keystroke — the exact bug from lesson 24's drill, and the exact thing the docs warn about: "don't keep transient state like forms and whether an item is hovered at the top of your tree or in a global state library."

Step 9 — the re-render audit

Step 10 — test the reducer, with no React at all

src/auth/authReducer.test.ts — Vitest

import { describe, expect, it } from 'vitest';
import { authReducer, initialAuthState } from './authReducer';

describe('authReducer', () => {
  it('moves to submitting when a sign-in is submitted', () => {
    const next = authReducer(initialAuthState, { type: 'sign_in_submitted', name: 'ana' });
    expect(next).toEqual({ status: 'submitting', name: 'ana' });
  });

  it('ignores a second submit while one is in flight', () => {
    const submitting = authReducer(initialAuthState, { type: 'sign_in_submitted', name: 'ana' });
    const again = authReducer(submitting, { type: 'sign_in_submitted', name: 'ben' });
    // toBe, not toEqual: the SAME object means React skips the re-render.
    expect(again).toBe(submitting);
  });

  it('clears the error when a later attempt succeeds', () => {
    const failed = authReducer(initialAuthState, { type: 'sign_in_failed', message: 'nope' });
    const user = { id: '1', name: 'ana', role: 'member' } as const;
    expect(authReducer(failed, { type: 'sign_in_succeeded', user })).toEqual({
      status: 'signed_in', user,
    });
  });
});

No render, no provider, no fake timers, no DOM. Three tests, milliseconds, and they cover the rules that actually matter. This is the docs' testing row made concrete — and it is only possible because the reducer imports nothing from React.

The toBe in the second test is the interesting one: it asserts an identity, and identity is what React uses to decide whether to re-render. A test that says "returns the same object" is a test that says "does not cause a wasted render". Month 9 turns this into a habit.

Strict Mode as a purity test "In Strict Mode, React will call your reducer and initializer functions twice in order to help you find accidental impurities." So if a reducer mutates its argument or increments a module counter, development shows you doubled or corrupted state immediately. Free test coverage for rule 1.

Remember this · the Feynman summary
  • A reducer folds actions into state. It takes the state so far and one action and returns the next state — named after Array.reduce, and it accumulates actions over time into state.
  • Reducers must be pure and they run during rendering: no fetching, no timers, no mutation. The async work happens outside, between two dispatches.
  • One action per user interaction, and name it after what happened — sign_in_failed, not set_error. The name decides how much you can change later without touching callers.
  • A discriminated union makes bad states unrepresentable. Keyed on status, there is no way to hold a user and be signed out, and TypeScript narrows state.user for you.
  • Return state itself for a no-op. React ignores an update when the next state is Object.is-equal to the previous one — so {...state} costs a render and state costs nothing.
  • End the switch with const unhandled: never = action. Adding an action and forgetting a case then breaks the build instead of the app.
  • dispatch has a stable identity, so an actions object built from it can honestly use [] — which is why reducer-plus-context is cleaner than a pile of useCallbacks.
  • Two contexts per feature: the state, and the stable actions. Put the stable one outermost. Action-only components then re-render zero times.
  • Primitives in context need no useMemo. The cheapest way to avoid memoising a context value is to not put an object in it.
  • A custom hook shares stateful logic, not state. Every call gets its own state and its own effects. Two components agree because they read the same source, not because the hook joins them.
  • Name hooks after behaviour, not lifecycle. useEscapeKey, useData(url), useChatRoom(options) — never useMount, useEffectOnce or useUpdateEffect.
  • Pass enabled instead of calling a hook conditionally. The condition becomes an early return inside the effect, which reads as "sync nothing while closed".
  • Transient state stays local. A half-typed name in context re-renders the whole app; in useState it re-renders one component.
  • A pure reducer is testable without React — no render, no provider, no DOM. And expect(next).toBe(prev) is a test that asserts "no wasted render".
  • Real use case (built & run): a theme-plus-auth app where a keystroke touches one component, the sign-out button re-renders zero times on sign-in, the OS going dark does not wake the theme menu, and four extracted hooks replaced sixty lines of modal.

If you remember one thing: a reducer turns "how do I change this state" into "what just happened", and context turns "who do I pass this to" into "who is listening" — the skill is choosing how many channels those listeners need.
