Reaching the DOM with refs

React writes the DOM. A ref is a borrow permit, not a transfer of ownership — and the difference between focusing a node and rewriting one is the difference between a normal feature and a crash.

Your win today: focus, scroll, and measure real DOM nodes on purpose — including a whole list of them — plus the three ways to attach a ref, the React 19 ref-as-a-prop change, and the one-line fix for "my scroll always lags one item behind".

Everything so far has been one-directional: you describe the screen, React writes it. That covers almost everything, and then you hit a wall. There is no prop for focus this input. There is no prop for scroll this row into view, how tall is this element, play this video, or select the text in this field.

Those are not descriptions of a screen. They are commands to a node that already exists. To send one, you need the node itself — and a ref is how React hands it to you.

First principle — you are borrowing, not taking over

React keeps its own picture of what the DOM should be and updates the real DOM to match. When you hold a node in your hand, you are holding something React still believes it owns. So there are two categories of thing you can do with it, and only one of them is safe.

React docs · Best practices for DOM manipulation with refs "Refs are an escape hatch. You should only use them when you have to 'step outside React'. Common examples of this include managing focus, scroll position, or calling browser APIs that React does not expose." … "If you stick to non-destructive actions like focusing and scrolling, you shouldn't encounter any problems. However, if you try to modify the DOM manually, you can risk conflicting with the changes React is making."
React docs · Avoid changing DOM nodes managed by React "Avoid changing DOM nodes managed by React. Modifying, adding children to, or removing children from elements that are managed by React can lead to inconsistent visual results or crashes like above." … "However, this doesn't mean that you can't do it at all. It requires caution. You can safely modify parts of the DOM that React has no reason to update. For example, if some <div> is always empty in the JSX, React won't have a reason to touch its children list. Therefore, it is safe to manually add or remove elements there."

That gives you a clean two-column test you can apply in one second:

Safe — React has no opinion about itDangerous — React owns this
node.focus(), node.blur()node.innerHTML = …
node.scrollIntoView(), reading scrollTopnode.appendChild(…) / removeChild(…) on a node whose children come from JSX
node.getBoundingClientRect() (measuring)node.textContent = … where JSX renders the text
node.select(), setSelectionRange()node.setAttribute('class', …) where JSX sets className
video.play(), audio.pause(), dialog.showModal()node.remove() — the classic crash: React later tries to remove it again
Attaching a listener React has no prop for (animationend on a third-party node)Setting value directly on a controlled input

The right-hand column is not a style objection. React holds a reference to the node it created; if you delete or refill it, React's next update writes into something that no longer matches, and you get either a wrong screen or an exception from the browser.

When is the ref actually filled in?

A ref starts as null and gets its node during the commit phase — after React has rendered and written to the DOM, before any effect runs. That order is the whole reason "read the DOM in an effect, never during render" works.

React docs · Manipulating the DOM with Refs "The useRef Hook returns an object with a single property called current. Initially, myRef.current will be null. When React creates a DOM node for this <div>, React will put a reference to this node into myRef.current. You can then access this DOM node from your event handlers and use the built-in browser APIs defined on it."

The shape you will type a thousand times

import { useRef } from 'react';

export function SearchBox() {
  const inputRef = useRef<HTMLInputElement>(null);

  function handleClear() {
    setQuery('');
    inputRef.current?.focus();      // ✓ optional chaining: .current is typed as possibly null
  }

  return (
    <>
      <input ref={inputRef} value={query} onChange={…} />
      <button onClick={handleClear}>Clear</button>
    </>
  );
}

Two TypeScript notes that save real time:

  • Give the element type, pass null. useRef<HTMLInputElement>(null). The type comes from the tag you are attaching to: HTMLInputElement, HTMLDivElement, HTMLVideoElement, HTMLDialogElement. Hover the JSX tag in your editor if you are unsure — it is not guesswork.
  • .current is nullable and should stay that way. Use ?. or an if guard. Do not write useRef<HTMLInputElement>(null!) to silence it — that is a promise to TypeScript that you cannot keep, and it turns a clear undefined into a crash the first time the element is conditionally rendered.

Callback refs — and the React 19 cleanup

Instead of a ref object, you can pass a function. React calls it with the node when the element is mounted. Since React 19, whatever you return from it is treated as a cleanup function:

React 19 release notes · Cleanup functions for refs "We now support returning a cleanup function from ref callbacks" … "When the component unmounts, React will call the cleanup function returned from the ref callback. This works for DOM refs, refs to class components, and useImperativeHandle." … "Previously, React would call ref functions with null when unmounting the component. If your ref returns a cleanup function, React will now skip this step."

There is a TypeScript trap hidden in that change, and it is worth knowing before it bites you:

React 19 release notes · the implicit-return trap "Due to the introduction of ref cleanup functions, returning anything else from a ref callback will now be rejected by TypeScript. The fix is usually to stop using implicit returns, for example:" 
- <div ref={current => (instance = current)} />
+ <div ref={current => {instance = current}} />
"The original code returned the instance of the HTMLDivElement and TypeScript wouldn't know if this was supposed to be a cleanup function or if you didn't want to return a cleanup function."

So: braces, not parentheses, in a callback ref. One character of arrow-function shorthand is now a type error, and the error message is confusing until you have read the paragraph above.

A list of refs — the Map pattern

You cannot call useRef in a loop; hooks run in a fixed order (that is the rule from Month 1). So for "scroll to row 14 of 200", you keep one ref holding a Map from id to node, and fill it with a callback ref. This is the docs' pattern, typed:

const rowsRef = useRef<Map<string, HTMLLIElement> | null>(null);

function getMap() {
  if (!rowsRef.current) {
    rowsRef.current = new Map();   // lazy init — allowed, always the same result
  }
  return rowsRef.current;
}

function scrollTo(id: string) {
  getMap().get(id)?.scrollIntoView({ behavior: 'smooth', block: 'nearest' });
}

// …in the JSX:
<li
  key={note.id}
  ref={node => {
    const map = getMap();
    map.set(note.id, node!);
    return () => {
      map.delete(note.id);         // ✓ React 19 cleanup: the row left the screen
    };
  }}
>
  {note.title}
</li>
Why the cleanup matters more than it looks Without it, the Map keeps a DOM node for every row that has ever been rendered — a genuine memory leak in a long list, and a source of the strangest bug in this area: scrollTo succeeding on a node that is no longer in the document, so nothing moves and nothing errors.

A ref to your own component

Put a ref on a component you wrote and it does not reach the DOM by itself — your component has to pass it on. In React 19 that is now the boring answer: ref arrives as an ordinary prop.

React 19 release notes · ref as a prop "Starting in React 19, you can now access ref as a prop for function components:" 
function MyInput({placeholder, ref}) {
  return <input placeholder={placeholder} ref={ref} />
}

//...
<MyInput ref={ref} />
"New function components will no longer need forwardRef, and we will be publishing a codemod to automatically update your components to use the new ref prop. In future versions we will deprecate and remove forwardRef."

Typed, in the two versions you will meet in real codebases:

// ── React 19+ — ref is a normal prop ──────────────────────────
type TextFieldProps = {
  label: string;
  value: string;
  onValueChange: (next: string) => void;
  ref?: React.Ref<HTMLInputElement>;
};

export function TextField({ label, value, onValueChange, ref }: TextFieldProps) {
  return (
    <label>
      {label}
      <input ref={ref} value={value} onChange={e => onValueChange(e.target.value)} />
    </label>
  );
}

// ── React 18 — the same thing with forwardRef ─────────────────
export const TextField18 = forwardRef<HTMLInputElement, Omit<TextFieldProps, 'ref'>>(
  function TextField18({ label, value, onValueChange }, ref) {
    return (
      <label>
        {label}
        <input ref={ref} value={value} onChange={e => onValueChange(e.target.value)} />
      </label>
    );
  }
);

Note the shape of the older one: forwardRef exists because ref used to be pulled out of props before your function ever saw it, so it had to be handed back as a second argument. Nothing about it was ever clever. React 19 simply stopped taking it away.

The pitfall the docs flag, and you should quote "Refs are an escape hatch. Manually manipulating another component's DOM nodes can make your code fragile." Exposing a node means every parent can now do anything to it — including the things in the dangerous column. Expose a ref because a real feature needs it (focus, scroll, measure, play), not because it might be handy.

useImperativeHandle — hand out a remote control, not the node

When you want the parent to be able to do exactly one thing, do not give away the element. Give away an object with one method:

import { useRef, useImperativeHandle } from 'react';

export type NoteInputHandle = { focus: () => void };

type Props = { value: string; onValueChange: (next: string) => void; ref?: React.Ref<NoteInputHandle> };

export function NoteInput({ value, onValueChange, ref }: Props) {
  const realInputRef = useRef<HTMLInputElement>(null);

  useImperativeHandle(ref, () => ({
    focus() {
      realInputRef.current?.focus();   // only expose focus, nothing else
    },
  }));

  return <input ref={realInputRef} value={value} onChange={e => onValueChange(e.target.value)} />;
}
React docs · Exposing a subset of the API with an imperative handle "Here, realInputRef inside MyInput holds the actual input DOM node. However, useImperativeHandle instructs React to provide your own special object as the value of a ref to the parent component. So inputRef.current inside the Form component will only have the focus method."

This is the right tool for design-system components and for a media player (next lesson but one). It is the wrong tool when the "handle" grows methods like setValue or submit — at that point you have rebuilt props out of function calls, and the data no longer flows one way.

flushSync — when your scroll lags one item behind

Here is a bug that feels like a React bug and is actually a lesson-2 fact you already know: state updates are queued, so the DOM has not changed yet on the next line.

function handleAdd() {
  setNotes([...notes, newNote]);
  listRef.current.lastChild.scrollIntoView();   // ✕ scrolls to the PREVIOUS last item
}
React docs · Flushing state updates synchronously with flushSync "In React, state updates are queued. Usually, this is what you want. However, here it causes a problem because setTodos does not immediately update the DOM. So the time you scroll the list to its last element, the todo has not yet been added. This is why scrolling always 'lags behind' by one item." … "This will instruct React to update the DOM synchronously right after the code wrapped in flushSync executes. As a result, the last todo will already be in the DOM by the time you try to scroll to it." 
import { flushSync } from 'react-dom';

function handleAdd() {
  flushSync(() => {
    setText('');
    setNotes([...notes, newNote]);
  });
  listRef.current?.lastElementChild?.scrollIntoView({ behavior: 'smooth', block: 'nearest' });
}

flushSync is a real escape hatch: it throws away batching for that update, so React renders and commits in the middle of your handler. Use it when you must read or command the DOM in the same handler that changed it. Do not sprinkle it around — every call is a re-render you have forced the browser to take immediately.

The alternative worth knowing Often you do not need flushSync at all, because "scroll to the thing that just appeared" can be expressed as "when the list changes, scroll to the last row" — which is an effect. Reach for flushSync when the action must finish inside one user event (focus is the common case: browsers only allow focus moves in response to a real interaction on some platforms).

Build it for real — a notes panel that behaves

One small feature, four separate DOM commands. Create the files as you read.

src/types.ts

export type Note = { id: string; title: string; body: string };

Stage 1 — the three bugs, on purpose

src/NotesPanel.tsx — stage 1, broken

import { useRef, useState } from 'react';
import type { Note } from './types';

let nextId = 1;

export function NotesPanel() {
  const [notes, setNotes] = useState<Note[]>([]);
  const [title, setTitle] = useState('');
  const listRef = useRef<HTMLUListElement>(null);

  function handleAdd() {
    if (title.trim() === '') return;
    setNotes([...notes, { id: String(nextId++), title, body: '' }]);
    setTitle('');
    listRef.current!.lastElementChild!.scrollIntoView();   // ✕ bug 1: one behind
    // ✕ bug 2: focus is lost — the user has to click the input again
  }

  return (
    <section>
      <input value={title} onChange={e => setTitle(e.target.value)} />
      <button onClick={handleAdd}>Add note</button>
      <ul ref={listRef} style={{ height: 160, overflowY: 'auto' }}>
        {notes.map(note => (
          <li key={note.id}>{note.title}</li>   // ✕ bug 3: no way to scroll to a specific one
        ))}
      </ul>
    </section>
  );
}

Add six notes with the list scrolled to the bottom. The view always stops one row short of the note you just typed, the input loses focus every time so adding six notes takes twelve interactions, and there is no way to jump to note #2 later. Three separate problems, three separate tools.

Stage 2 — flushSync for "the thing I just added", and focus that stays

import { flushSync } from 'react-dom';

const inputRef = useRef<HTMLInputElement>(null);

function handleAdd() {
  const trimmed = title.trim();
  if (trimmed === '') {
    inputRef.current?.focus();          // ✓ point at the problem, don't just refuse
    return;
  }

  flushSync(() => {
    setNotes([...notes, { id: String(nextId++), title: trimmed, body: '' }]);
    setTitle('');
  });

  // After flushSync the new <li> is really in the DOM.
  listRef.current?.lastElementChild?.scrollIntoView({ behavior: 'smooth', block: 'nearest' });
  inputRef.current?.focus();            // ✓ keep the keyboard where the user is working
}

Both fixes are non-destructive commands from the safe column: scroll and focus. Nothing about the DOM's contents was touched by hand.

Stage 3 — a Map of row refs, so any row can be reached

const rowsRef = useRef<Map<string, HTMLLIElement> | null>(null);

function getRowMap() {
  if (!rowsRef.current) rowsRef.current = new Map();
  return rowsRef.current;
}

function scrollToNote(id: string) {
  getRowMap().get(id)?.scrollIntoView({ behavior: 'smooth', block: 'nearest' });
}

// …in the JSX:
<ul ref={listRef} style={{ height: 160, overflowY: 'auto' }}>
  {notes.map(note => (
    <li
      key={note.id}
      ref={node => {
        const map = getRowMap();
        if (node) map.set(note.id, node);
        return () => { map.delete(note.id); };   // braces, not parentheses
      }}
    >
      {note.title}
    </li>
  ))}
</ul>

<nav>
  {notes.map(note => (
    <button key={note.id} onClick={() => scrollToNote(note.id)}>{note.title}</button>
  ))}
</nav>

Delete a note and watch the Map shrink in the debugger. That is the cleanup earning its place.

Stage 4 — a component that exposes only focus()

Replace the bare <input> with the NoteInput from earlier in the lesson. The parent's ref type changes from HTMLInputElement to NoteInputHandle, and every call site keeps working because the only thing the parent ever did was focus:

const inputRef = useRef<NoteInputHandle>(null);

// …
<NoteInput ref={inputRef} value={title} onValueChange={setTitle} />

Now try to write inputRef.current.value = 'x' in the parent. TypeScript stops you, which is the entire point: the surface is one method wide, so no future teammate can reach through the component and edit its insides.

Extend it — three reps

  1. Select the text instead of just focusing. On "Rename", focus the input and call select() so typing replaces the old title. Then try it with setSelectionRange(0, 0) and feel the difference — this is why "focus" is not one behaviour.
  2. Add a "scroll to first unsaved note" button that finds the id in your data first and only then touches the Map. Say out loud why searching the data is right and querySelectorAll('li')[i] is wrong, even though both work today.
  3. Delete the flushSync and make the scroll work as an effect that depends on notes.length instead. Both versions are defensible; write down the one sentence that decides between them for this feature. (Hint: does anything else in the app add notes?)

Practice: read the situation, pick the move

Scenario

A teammate's chat feature works locally and breaks in production. The code keeps a messagesRef to the scroll container and, in handleSend, does three things: messagesRef.current.insertAdjacentHTML('beforeend', renderBubble(text)) so the message "appears instantly", then setMessages([...messages, msg]), then messagesRef.current.scrollTop = messagesRef.current.scrollHeight. QA reports duplicated bubbles, and sometimes NotFoundError: The object can not be found here in the console. They ask you whether adding flushSync would fix it.

Work out, in order: which of the three lines is the actual defect and by which documented rule; why duplicates appear and why a browser exception can appear from the same cause; whether flushSync helps at all here; and what the two-line correct version looks like. Then decide which of the three DOM touches is legitimate to keep.

Remember this · the Feynman summary
  • A DOM ref is a borrow permit. React still owns the node. Non-destructive commands only: focus, blur, scroll, measure, select, play, pause, showModal.
  • Never rewrite what React renders. Setting innerHTML, adding or removing children, or deleting a node React created gives you a wrong screen or a browser exception. You may safely touch parts of the DOM React has no reason to update.
  • ref.current is null during render and gets its node at commit, before any effect. So read it in handlers and effects, never while rendering.
  • Type it from the tag, keep it nullable: useRef<HTMLInputElement>(null) and ref.current?.focus(). null! is a promise you cannot keep.
  • Three ways to attach: an object ref for one element, a callback ref for many or for appear/disappear work, and a ref prop to reach into a component you wrote.
  • Since React 19 a callback ref can return a cleanup function — and because of that, TypeScript rejects implicit returns. Write { … }, not ( … ).
  • Hooks cannot run in a loop, so a list of refs is one ref holding a Map from id to node, filled and emptied by a callback ref.
  • In React 19 ref is an ordinary prop; forwardRef is the React 18 way and is on its way out.
  • useImperativeHandle hands out a remote control instead of the node. Good for one or two verbs (focus, play); a smell once it grows setters.
  • "My scroll lags one item behind" is not a React bug — state updates are queued, so the DOM has not changed yet. flushSync forces the commit inside your handler; an effect is often the better answer.
  • Never use querySelector where a ref belongs. A ref is scoped, typed, and detached for you.
  • Real use case (built & run): a notes panel that scrolled to the wrong row and lost focus on every add, fixed with flushSync + focus(), a Map of row refs for jump-to-note, and an input that exposes only focus().

If you remember one thing: use a ref to command a node, never to rewrite one — focus and scroll are always safe, and touching what React renders never is.
