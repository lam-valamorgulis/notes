Sharing state between components

Lifting state up, events flowing back, and how to find the one component that should own each piece of data.

Your win today: you'll be able to (1) decide which component should own any piece of state, (2) lift state up with correctly typed callback props, and (3) spot the two classic mistakes — copying props into state, and lifting things that should have stayed local.

You can now hold state and take input. The last piece of Month 2 is the one that makes an app instead of a pile of widgets: two components that need the same data.

First principle — siblings cannot see each other

Props flow one way: down. A component can read what its parent passed and nothing else. It cannot reach sideways into a sibling, and it cannot reach up.

So if two components need the same value, there is exactly one place that value can live: a component above both of them. That is not a workaround. It is the direct consequence of one-way data flow, and it is why you can always answer "who changed this?" in a React app.

The rule

State belongs to the closest component that is above everyone who needs it. Data flows down as props. Events flow back up as function calls.

The problem, concretely

Two panels. Each owns whether it is open:

function Panel({ title, children }: { title: string; children: React.ReactNode }) {
  const [isOpen, setIsOpen] = useState(false);       // local state
  return (
    <section>
      <h3>{title}</h3>
      {isOpen
        ? <p>{children}</p>
        : <button onClick={() => setIsOpen(true)}>Show</button>}
    </section>
  );
}

This works fine — until the requirement arrives: only one panel open at a time. Now Panel A must know about Panel B. It can't. Each panel has its own private isOpen, and neither can see the other's.

No amount of cleverness inside Panel fixes this. The state is in the wrong place.

Lifting state up — three mechanical steps

The fix has a name and a recipe. You do the same three steps every time.

  1. Remove the state from the child. Delete the useState.
  2. Pass the value down from the common parent as a prop.
  3. Pass a function down so the child can ask the parent to change it.
function Panel({ title, isOpen, onShow, children }: {
  title: string;
  isOpen: boolean;                 // 2 · value comes in
  onShow: () => void;              // 3 · a way to ask for a change
  children: React.ReactNode;
}) {
  return (
    <section>
      <h3>{title}</h3>
      {isOpen ? <p>{children}</p> : <button onClick={onShow}>Show</button>}
    </section>
  );
}

function Accordion() {
  // one value describes the whole group — which index is open
  const [openIndex, setOpenIndex] = useState(0);

  return (
    <>
      <Panel title="About"   isOpen={openIndex === 0} onShow={() => setOpenIndex(0)}>
        Etc.
      </Panel>
      <Panel title="Billing" isOpen={openIndex === 1} onShow={() => setOpenIndex(1)}>
        Etc.
      </Panel>
    </>
  );
}

Read what happened to the requirement. "Only one open at a time" is no longer a rule you enforce with code — it is a fact about the state shape. One number cannot describe two open panels. The bug became impossible instead of being fixed.

This is the real prize Choosing the right owner and the right shape removes whole categories of bug. Two booleans need syncing and can disagree; one index cannot. Month 3 is built on this idea.

Data down, events up

The function you pass down is called a callback prop. Two conventions make code readable, and every React codebase uses them:

  • The prop is named onSomething — onSelect, onQueryChange, onDelete.
  • The function in the parent is named handleSomething — handleSelect, handleQueryChange.
// parent
function handleSelect(id: string) { setSelectedId(id); }
<MemberList onSelect={handleSelect} />

// child — the prop type says exactly what the parent will receive
interface MemberListProps {
  members: Member[];
  selectedId: string | null;
  onSelect: (id: string) => void;      // takes an id, returns nothing
}
TypeScript makes the contract explicit onSelect: (id: string) => void is a small piece of documentation the compiler enforces. The child cannot call it wrongly, and the parent cannot accept the wrong shape. Prop types are where TypeScript pays for itself in React.

Controlled and uncontrolled — one level up

You met these words for inputs. They mean the same thing for your own components, and using them out loud marks you as someone who has done this before.

Uncontrolled childControlled child
Who owns the valueThe child, in its own useStateThe parent, passed in as a prop
Parent needsNothingState + a handler
Good forSelf-contained widgets — a tooltip, a local "show more"Anything that must coordinate with something else
CostThe parent cannot influence itMore wiring in the parent

Real component libraries often support both, by making the prop optional and falling back to internal state. You do not need that yet — but that is the pattern you are looking at when a library says a component is "controlled or uncontrolled".

Finding the owner — the procedure

  1. List every component that reads the value. Reads, not writes — writing goes through the callback anyway.
  2. Find their closest common parent. Walk up until one component contains all of them.
  3. Put the state there. Pass the value down, pass a setter or handler down.
  4. If that feels wrong — for instance the common parent is a layout component with no business meaning — put it one level higher, where it makes sense to a human.

Then check the invariant: one piece of information, one owner. If the same fact is stored in two places, they will drift apart, and the bug report will say "sometimes it shows the wrong name".

The classic mistake — copying props into state

This is the highest-value bug in the lesson, because it looks so reasonable:

function PriceTag({ price }: { price: number }) {
  const [value, setValue] = useState(price);   // ✕ a copy of the prop
  return <span>{value}</span>;
}

The parent changes price to 99. The component re-renders. The screen still shows the old number.

Why? Because the argument to useState is the initial value — used once, on the first render of that component, and ignored on every render after. You created a second source of truth, and it froze at birth.

What to do instead Just use the prop. If the value comes from above, read it from above: <span>{price}</span>. If the child genuinely needs to edit it, the state belongs in the parent and the child gets value + onChange. The only case for copying is a deliberately independent draft — for example an edit form pre-filled from the server value — and then you must decide how it resets. Which brings us to key.

Resetting state with key

State does not belong to your function. It belongs to a position in the tree. React keeps state for "the third child of this list" as long as something of the same type stays in that position.

That explains a bug that feels supernatural. You have an edit form with a draft in local state. The user selects a different member — and the form still shows the previous member's text, because from React's view it is the same component in the same position, just with new props.

The fix is one attribute:

// changing the key tells React: this is a DIFFERENT component now
<MemberNote key={selectedId} memberId={selectedId} />

When the key changes, React throws the old component away — state and all — and mounts a fresh one. Same idea as list keys in Month 1: the key is the identity.

Two ways to reset a child's state

Give it a key that changes when the identity changes — clean, declarative, no extra code. Or lift the value up so the parent controls it and can set it back. Reaching for an effect to "sync" props into state is almost always the wrong third option (Month 4 explains why).

When not to lift

  • Only one component reads it? Keep it local. Local state is not a lesser thing — it keeps re-renders small and the component readable and reusable.
  • Passing a prop through four components that do not use it? That is prop drilling. It is a real smell, but the first answer is usually better composition — pass the JSX down instead of the data. If it is genuinely app-wide (theme, current user), that is what Context is for in Month 6.
  • Lifting everything to the top makes one giant component that re-renders on every keystroke. Put state as high as it must go, and no higher.

Build it for real — a filter bar, a list, and a detail panel

Three sibling components, no state of their own, all coordinated by one parent. Replace src/App.tsx:

src/App.tsx

import { useState } from 'react';

interface Member {
  id: string;
  name: string;
  role: string;
}

const TEAM: Member[] = [
  { id: 'm1', name: 'Mai Nguyen',  role: 'Engineering' },
  { id: 'm2', name: 'Tomas Rehak', role: 'Design' },
  { id: 'm3', name: 'Aisha Bello', role: 'Engineering' },
  { id: 'm4', name: 'Jun Park',    role: 'Product' },
];

// ---------- child 1: fully controlled, owns nothing ----------
interface SearchBarProps {
  query: string;
  onQueryChange: (next: string) => void;
}

function SearchBar({ query, onQueryChange }: SearchBarProps) {
  return (
    <input
      type="search"
      placeholder="Filter by name…"
      value={query}
      onChange={(e) => onQueryChange(e.target.value)}
    />
  );
}

// ---------- child 2: reports clicks, decides nothing ----------
interface MemberListProps {
  members: Member[];
  selectedId: string | null;
  onSelect: (id: string) => void;
}

function MemberList({ members, selectedId, onSelect }: MemberListProps) {
  if (members.length === 0) return <p>No one matches that filter.</p>;

  return (
    <ul>
      {members.map(m => (
        <li key={m.id}>
          <button
            onClick={() => onSelect(m.id)}
            aria-current={m.id === selectedId}
          >
            {m.name} — {m.role}
          </button>
        </li>
      ))}
    </ul>
  );
}

// ---------- child 3: has its OWN state on purpose ----------
function MemberNote({ member }: { member: Member }) {
  // A private draft. Nobody else needs it, so it stays local.
  const [note, setNote] = useState('');

  return (
    <div>
      <h2>{member.name}</h2>
      <p>{member.role}</p>
      <textarea
        value={note}
        placeholder={`Private note about ${member.name}…`}
        onChange={(e) => setNote(e.target.value)}
      />
    </div>
  );
}

// ---------- the owner ----------
export default function TeamPage() {
  const [query, setQuery] = useState('');
  const [selectedId, setSelectedId] = useState<string | null>(null);

  // both derived — never stored
  const visible = TEAM.filter(m =>
    m.name.toLowerCase().includes(query.trim().toLowerCase())
  );
  const selected = TEAM.find(m => m.id === selectedId) ?? null;

  return (
    <main>
      <h1>Team</h1>

      <SearchBar query={query} onQueryChange={setQuery} />

      <MemberList
        members={visible}
        selectedId={selectedId}
        onSelect={setSelectedId}
      />

      {selected && (
        /* key = identity. New member → brand-new component → empty note. */
        <MemberNote key={selected.id} member={selected} />
      )}
    </main>
  );
}

Run it, then do these four experiments. Each one proves a claim from this lesson:

  1. Type in the search box. The input, the list, and the empty-state message all move together — because there is only one query, in one place.
  2. Pick a member, type a note, then pick a different member. The note clears. Now delete key={selected.id} and repeat: the old note stays behind. You have just seen that state belongs to a position, not to a component.
  3. Try to make MemberList clear the search box. You cannot — it has no access. That is one-way data flow doing its job. It would have to call a callback the parent gave it.
  4. Ask yourself why note was not lifted. Nothing else reads it. Lifting it would add wiring, add re-renders to the whole page on every keystroke, and buy nothing.
Notice what you passed as a callback onQueryChange={setQuery} passes the state setter straight down. That is fine and common when the child's value is the state. Write a named handleQueryChange when the parent needs to do more than store it — validate, trim, also clear the selection, log it.

Practice: read the situation, pick the move

Scenario

A teammate's <CartTotal total={total} /> shows a stale number. Inside, they wrote const [displayTotal, setDisplayTotal] = useState(total); and render displayTotal. Adding an item updates total in the parent, the child re-renders — and the old number stays on screen.

Name the mistake, say why the re-render does not help, and give the fix.

Remember this · the Feynman summary
  • Siblings cannot see each other. Props flow one way, so shared data must live in a component above everyone who reads it.
  • Lifting state up, three steps: remove the useState from the child · pass the value down as a prop · pass a function down so the child can request a change.
  • Data down, events up. Prop named onSomething, parent function named handleSomething, typed as (arg: T) => void.
  • Controlled child = the parent owns its value. Uncontrolled child = it owns its own. Same words as inputs, one level up.
  • Find the owner by listing every component that reads the value and taking their closest common parent — then move it higher only if that place makes human sense.
  • One fact, one owner. Two copies of the same information will drift apart.
  • Never copy a prop into state — useState(props.x) only uses x on the first render, so later prop changes are ignored. Read the prop, or lift the state.
  • State lives at a position in the tree. Change a component's key to throw its state away and start fresh — the clean way to reset an edit form.
  • Don't lift what only one component reads. Local state keeps re-renders small; prop drilling is answered by composition first, Context (Month 6) second.
  • Real use case (built & run): a search bar, a list, and a detail panel — two children with no state at all, one parent owning query and selectedId, a private local note in the third child, and key resetting it per member.

If you remember one thing: put each piece of state in the closest component above everyone who reads it — then send data down and events up.
