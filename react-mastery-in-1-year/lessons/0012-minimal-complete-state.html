Month 3 · Lesson 2 · Thinking in React

Minimal, complete state

Step 3 of the method: three questions that tell you what is state, and five principles that tell you what shape it should have.

Your win today: you will be able to (1) run three questions over any value and say whether it is state, props, derived, or constant, (2) reshape state so whole classes of bug become impossible, and (3) recognise the four smells — contradictions, redundancy, duplication, deep nesting — in someone else's component in under a minute.

Your static table works. Nothing on the screen reacts yet. Step 3 asks one question about it: what changes?

This is the step that decides how buggy your app will be. Not the components, not the CSS. The state.

First principle — state is memory for what cannot be recomputed

The course rests on UI = f(state). Read it backwards: the state is the input to a function that draws your whole screen. So the state has to be two things at once:

  • Complete — enough to draw every visible pixel. If you cannot reproduce the screen from the state, some truth is hiding in the DOM or in a variable React cannot see.
  • Minimal — nothing that can be worked out from the rest. Every extra value is a second copy of the truth, and copies go stale.
The rule

Keep the smallest set of values from which the entire screen can be rebuilt. Anything you can compute, compute. State is memory, and memory is expensive to keep correct.

This is the same instinct a database engineer has when they normalise tables. One fact, stored once, in one place.

The three questions

React's docs give a test for each value on the screen. Run it out loud — it takes five seconds and it is nearly always right.

Two pieces of state. That is the whole answer to step 3 for this app. Everything else on the screen is a prop, a computation, or a constant.

Props versus state, in one line each Props are the arguments a parent passes in — a component cannot change its own props. State is the component's private memory — it survives between renders, and setting it asks for a new render. If a value is passed in, it is not your state. If you keep a copy of it in state, you now have two truths (see principle 3).

Five principles for the shape of state

Knowing what is state is half the job. The other half is what shape it takes. React's docs list five principles, and each one removes a family of bugs.

1 · Group related state

If two values always change together, they are one value.

// Meh — two setters that must always be called as a pair
const [x, setX] = useState(0);
const [y, setY] = useState(0);

// Better — one fact: "where the pointer is"
const [position, setPosition] = useState({ x: 0, y: 0 });

The test is not "are they related in my head?" — it is "do I ever update one without the other?" If the answer is never, merge them. In Lesson 4 the sort key and the sort direction get merged for exactly this reason: clicking a column header changes both, always.

Careful with the opposite mistake. Search text and the checkbox change independently, so merging them into one filters object buys nothing and makes every update a spread.

2 · Avoid contradictions

Three booleans for one process is three chances to disagree.

// Bug factory — 8 combinations exist, only 4 are legal.
const [isSaving, setIsSaving] = useState(false);
const [isSaved,  setIsSaved]  = useState(false);
const [isError,  setIsError]  = useState(false);
// Forget one reset and the UI shows a spinner AND "Saved!" at once.

// One fact, four legal values, impossible to contradict.
type SaveStatus = 'idle' | 'saving' | 'saved' | 'error';
const [status, setStatus] = useState<SaveStatus>('idle');

const isSaving = status === 'saving';   // derive the booleans back if you like

This is where TypeScript earns its place. A union type does not just document the four states — the compiler refuses 'savin', and a switch over status can be checked for completeness. You cannot write the impossible state, so you cannot ship it.

3 · Avoid redundant state

If you can calculate it during render, calculating it is the implementation.

// Redundant — a third state that has to be maintained
const [first, setFirst] = useState('');
const [last, setLast] = useState('');
const [fullName, setFullName] = useState('');    // goes stale the moment you forget

// Just compute it
const fullName = first + ' ' + last;             // always right, no setter to forget

The special case worth naming: do not mirror props in state.

// Broken: it copies the prop once, then ignores every later value.
function Price({ amount }: { amount: number }) {
  const [value] = useState(amount);   // frozen at the first render
  return <span>{value}</span>;
}

// Correct: read the prop.
function Price({ amount }: { amount: number }) {
  return <span>{amount}</span>;
}

useState(props.x) only reads the argument on the first render of that component. This is the frozen-copy bug from Month 2, Lesson 3, and it is the most common "why is my UI stale?" question on the internet.

4 · Avoid duplication

This one produces the strangest bug reports, so we will run it for real in a minute. The pattern: a list in state, plus the selected item object in state.

// Two copies of the same product. Rename one and they disagree.
const [products, setProducts] = useState(PRODUCTS);
const [selected, setSelected] = useState(PRODUCTS[0]);   // a whole object

// One copy, plus a pointer to it.
const [products, setProducts] = useState(PRODUCTS);
const [selectedId, setSelectedId] = useState<string | null>(null);
const selected = products.find(p => p.id === selectedId) ?? null;   // derived

Store the id, derive the object. The id is a fact that stays true when the object changes; the object is a snapshot that rots. For multiple selection, the same idea with a set of ids: useState<Set<string>>(new Set()).

5 · Avoid deeply nested state

Updating state means copying every level above the change (Month 2, Lesson 2). So a five-level tree means five spreads for one edit — verbose to write and easy to get wrong.

// Nested: to rename one child you rebuild the whole chain above it.
const plan = { id: 0, title: 'Root', children: [
  { id: 1, title: 'Earth', children: [ { id: 2, title: 'Africa', children: [ … ] } ] },
] };

// Flat ("normalised"): one lookup table, ids for edges.
const placesById = {
  0: { id: 0, title: 'Root',   childIds: [1] },
  1: { id: 1, title: 'Earth',  childIds: [2] },
  2: { id: 2, title: 'Africa', childIds: [] },
};
// Renaming node 2 now touches exactly one entry:
setPlaces({ ...placesById, 2: { ...placesById[2], title: 'Afrika' } });

This is database normalisation, and it is what state libraries do for you later. Do not reach for it on day one — flatten when the nesting starts to hurt.

Build it for real — feel the duplication bug, then delete it

Reading about principle 4 does not stick. Watching your own UI lie to you does. Add this file to the project from Lesson 1.

src/StockPanel.tsx — the broken version, on purpose

import { useState } from 'react';
import type { Product } from './types';
import { PRODUCTS } from './data';

export function StockPanel() {
  const [products, setProducts] = useState<Product[]>(PRODUCTS);

  // THE BUG: a second copy of one product, frozen at the moment you clicked.
  const [selected, setSelected] = useState<Product>(PRODUCTS[0]);

  function handleRename(id: string, name: string) {
    setProducts(prev => prev.map(p => (p.id === id ? { ...p, name } : p)));
  }

  return (
    <section>
      <ul>
        {products.map(p => (
          <li key={p.id}>
            <input
              value={p.name}
              onChange={e => handleRename(p.id, e.target.value)}
            />
            <button onClick={() => setSelected(p)}>Pick</button>
          </li>
        ))}
      </ul>
      <p>Picked: <b>{selected.name}</b> — {selected.inStock ? 'in stock' : 'out of stock'}</p>
    </section>
  );
}

Render it (<StockPanel /> in App) and do exactly this:

  1. Click Pick on "Apple". The line at the bottom says Apple.
  2. Now edit Apple's name to "Apricot" in the input.
  3. The list says Apricot. The line at the bottom still says Apple.

Nothing crashed. No warning. The screen simply shows two different truths about one product, and which one you see depends on which component you look at. In a real app this is the bug report "the header shows the old name until I refresh" — and it is unfixable by tweaking components, because the state shape is wrong.

src/StockPanel.tsx — the fix: store the id, derive the object

export function StockPanel() {
  const [products, setProducts] = useState<Product[]>(PRODUCTS);
  const [selectedId, setSelectedId] = useState<string | null>(null);

  // Derived during render — cannot go stale, because it is recomputed.
  const selected = products.find(p => p.id === selectedId) ?? null;

  function handleRename(id: string, name: string) {
    setProducts(prev => prev.map(p => (p.id === id ? { ...p, name } : p)));
  }

  return (
    <section>
      <ul>
        {products.map(p => (
          <li key={p.id}>
            <input value={p.name} onChange={e => handleRename(p.id, e.target.value)} />
            <button onClick={() => setSelectedId(p.id)}>Pick</button>
          </li>
        ))}
      </ul>
      {selected
        ? <p>Picked: <b>{selected.name}</b> — {selected.inStock ? 'in stock' : 'out of stock'}</p>
        : <p>Nothing picked yet.</p>}
    </section>
  );
}

Repeat the three steps. The bottom line now follows the rename, because there is no second copy to fall behind. Two more things the fix bought you, for free:

  • A real "nothing selected" state. string | null made TypeScript force you to handle it. The broken version faked it with PRODUCTS[0].
  • Deleting works. Remove the picked product from the list and the derived selected becomes null on its own. In the broken version the panel would keep showing a product that no longer exists.
The tempting wrong fix Keeping both copies and "syncing" them — update products, then also update selected in every handler that touches it. It works until the next handler, the next developer, or the next feature. You are hand-maintaining an invariant the computer could guarantee. Reaching for useEffect to do that syncing is the same mistake with extra renders; Month 4 covers why.

A one-minute state review

Run these on any component — yours, or one in a pull request.

  1. Can I rebuild the screen from the state alone? If not, some truth is hiding outside React.
  2. Can any two state variables disagree? If yes, they want to be one union type.
  3. Can I delete a state variable and compute it instead? If yes, delete it.
  4. Does any object appear in state twice? If yes, keep one copy and store ids for the rest.
  5. Do updates need three spreads? If yes, the shape is too deep — flatten it.

Practice: read the situation, pick the move

Scenario

A colleague's checkout component holds: items, itemCount, subtotal, couponCode, discountAmount, total, isSubmitting, isSubmitted, errorMessage, and selectedAddress (a whole address object, also present inside user.addresses). QA reports three bugs: the total is sometimes one item behind, editing an address in the profile does not update the checkout summary, and after a failed payment the button shows "Submitting…" and an error at the same time.

Map each bug to one of the five principles, and rewrite the state list. How many state variables do you end up with?

Remember this · the Feynman summary
  • State must be complete and minimal: enough to rebuild the whole screen, and nothing that can be recomputed.
  • Three questions: does it ever change (no → constant) · does it arrive as a prop (yes → not your state) · can you compute it (yes → derived). Three noes means it is state.
  • The product table has exactly two pieces of state — the search text and the checkbox. Rows, groups and counts are all derived.
  • Group related state when you never update one without the other — and only then.
  • Avoid contradictions: three booleans for one process create impossible combinations. One union type — 'idle' | 'saving' | 'saved' | 'error' — makes them unwritable.
  • Avoid redundant state: compute fullName, and never write useState(props.x) — that copy freezes on the first render.
  • Avoid duplication: store selectedId, derive the object with find. Ids stay true; object copies go stale.
  • Avoid deep nesting: flat lookup tables plus ids, because every update copies the whole chain above the change.
  • Syncing two copies by hand is not a fix — neither is an effect. Delete the copy.
  • Real use case (built & run): a stock panel that shows the old product name after a rename, then the same panel storing an id and deriving the object — with a free "nothing selected" state and safe deletes.

If you remember one thing: every extra piece of state is a second version of the truth — keep one, compute the rest.
