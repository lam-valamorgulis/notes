Month 3 · Lesson 1 · Thinking in React

From design to component tree

React's own method, steps 1 and 2: split a design into components, then build it static — props only, no state.

Your win today: you will be able to (1) look at any mockup and name the components before you type, (2) say why each split exists, and (3) build a working static version that renders real data with no state at all.

Months 1 and 2 gave you the parts: state, props, events, lists, immutable updates. But interviews and real work do not start with parts. They start with a picture. Someone hands you a design and says "build this".

That gap is what this month closes. React has an official method for it, and it has five steps. This lesson does the first two.

First principle — a component is a responsibility, not a rectangle

Coming from HTML and CSS, your eye sees boxes. A grey panel, a left column, a header strip. It is tempting to make one component per box.

That instinct is wrong, and here is why. A component is a function from data to UI. So the useful question is not "which rectangles do I see?" but:

The question that produces the tree

Which part of the screen is a function of which part of the data? Each answer is one component. Its job is to turn that slice of data into that slice of screen — and nothing else.

A left column is not a function of anything. It is a layout decision. But "one row of the table" is a function of one product. That is a component.

The method — five steps, and where you learn each one

This is React's own recipe, straight from the official docs. It never changes, whatever the app.

Step 1 — break the design into a component hierarchy

Here is the design we will use all month. A search box, a checkbox, and a table of products grouped by category:

Notice what decided the split: the data. The product list repeats, so ProductRow exists. Products come grouped by category, so ProductCategoryRow exists. There is no LeftColumn, because no piece of data is called a left column.

Three lenses that give the same answer

  1. One job each (the single responsibility principle). If a component both filters a list and formats a price, it has two jobs. Split it.
  2. The shape of the data. Look at the JSON your API returns. A well-shaped data model and a well-shaped component tree usually look the same, because both describe the same problem.
  3. The design's own repeats and names. Designers already grouped things into layers and gave them names. If the design file says "product row", that is a component.

When the three lenses agree, you are done. When they disagree, trust the data model.

How small is too small?

Split it out when…Leave it inline when…

The trap — splitting by visual nesting One component per <div> gives you thirty components that each pass their props straight through. It reads worse than the version you started with, and every prop change now touches four files. Layout markup can stay inside the component that owns the job. Components are units of behaviour and data, not units of markup.

Step 2 — build a static version

A static version renders the data and does nothing else. No useState. No onClick. Every component takes props and returns JSX.

This feels like a waste of a step. It is the opposite. Here is the honest description from the React docs, and it is worth memorising:

Why static first

Building a static version needs a lot of typing and no thinking. Adding interactivity needs a lot of thinking and not much typing. So do them separately. Mixing them is how you end up debugging your layout and your state at the same time.

One rule holds the whole step together: state is only for data that changes over time. A static version has no data that changes yet, so it has no state. If you catch yourself adding useState here, you have skipped ahead to step 3.

In TypeScript, model the data first

Your props types are not decoration. They are the contract between components, and they come from the data model. So type the data first, and the props follow for free.

Build it for real — the static product table

Fresh Vite app if you need one: npm create vite@latest product-table -- --template react-ts. Then create these files in src/, in this order.

src/types.ts — the data model, written once

export interface Product {
  id: string;            // a stable identity — this becomes our key
  name: string;
  category: string;
  price: number;         // a NUMBER, not "$1" — see the note below
  inStock: boolean;
}
Store data, format at the edge The React docs' version of this exercise stores price: "$1" as a string. Do not copy that. A price is a number; the dollar sign is presentation. Store the number, and format it in the component that shows it. If you store "$10" you cannot sort by price, add up a total, or change currency — and Lesson 4 sorts by price.

src/ProductRow.tsx — one product in, one row out

import type { Product } from './types';

const money = new Intl.NumberFormat('en-US', {
  style: 'currency', currency: 'USD',
});                                   // built once, outside the component

export function ProductRow({ product }: { product: Product }) {
  return (
    <tr>
      <td style={{ color: product.inStock ? 'inherit' : 'crimson' }}>
        {product.name}
      </td>
      <td>{money.format(product.price)}</td>
    </tr>
  );
}

One job: turn one product into one row. It does not know about search, categories, or the table around it. That is why you could drop it into a different screen tomorrow.

src/ProductCategoryRow.tsx

export function ProductCategoryRow({ category }: { category: string }) {
  return (
    <tr>
      <th colSpan={2}>{category}</th>
    </tr>
  );
}

src/ProductTable.tsx — the grouping happens here

import type { ReactNode } from 'react';
import type { Product } from './types';
import { ProductRow } from './ProductRow';
import { ProductCategoryRow } from './ProductCategoryRow';

export function ProductTable({ products }: { products: Product[] }) {
  // Build the list of rows before returning. This is still pure:
  // same products in, same rows out, nothing outside is touched.
  const rows: ReactNode[] = [];
  let lastCategory: string | null = null;

  for (const product of products) {
    if (product.category !== lastCategory) {
      rows.push(
        <ProductCategoryRow
          key={product.category}          // category names are unique here
          category={product.category}
        />
      );
      lastCategory = product.category;
    }
    rows.push(<ProductRow key={product.id} product={product} />);
  }

  return (
    <table>
      <thead>
        <tr><th>Name</th><th>Price</th></tr>
      </thead>
      <tbody>{rows}</tbody>
    </table>
  );
}
A loop inside render is allowed — a side effect is not Pushing into a local array you created in the same render is fine. The rule for a render is purity: no touching anything that lives outside the call. A local rows array is born and dies inside this one render, so it breaks nothing. Pushing into an array declared outside the component would be a real bug, because a second render would append to the first render's leftovers.

src/SearchBar.tsx — static on purpose

export function SearchBar() {
  return (
    <form>
      <input type="text" placeholder="Search…" />
      <label>
        <input type="checkbox" /> Only show products in stock
      </label>
    </form>
  );
}

No value, no onChange, no props. You can type in the box and it does nothing to the table — correct for now. This is an uncontrolled input: the DOM holds the text, React does not know it exists. Lesson 3 hands the value to React.

Do not half-do it Writing value="" without onChange would freeze the box and React would warn you in the console. That is the read-only bug from Month 2, Lesson 1. In a static version, pass neither.

src/FilterableProductTable.tsx — the parent that will hold state later

import type { Product } from './types';
import { SearchBar } from './SearchBar';
import { ProductTable } from './ProductTable';

export function FilterableProductTable({ products }: { products: Product[] }) {
  return (
    <div>
      <SearchBar />
      <ProductTable products={products} />
    </div>
  );
}

src/App.tsx

import { PRODUCTS } from './data';
import { FilterableProductTable } from './FilterableProductTable';

export default function App() {
  return <FilterableProductTable products={PRODUCTS} />;
}

Run npm run dev. You should see the whole design, filled with real data, grouped by category, with out-of-stock names in red — and nothing that reacts to you. That is a finished step 2.

What the static version already told you

This is the part people skip, so they never get the payoff. A finished static version answers three questions for free:

QuestionWhere the answer showed up
Is my data model right?Any value you had to invent while writing JSX is missing from the model. Grouping needed category; the red name needed inStock.
What is the contract between components?The props types. ProductTable needs a list; ProductRow needs one product. Written down, checked by the compiler.
What does not change?Everything you rendered without state. Whatever is left over when you ask "what changes?" is the answer to step 3 — next lesson.

Data flowed one way the whole time: App → FilterableProductTable → ProductTable → ProductRow. You built a working app with no state at all. Remember that the next time you reach for a state library on line one.

Practice: read the situation, pick the move

Scenario

A designer hands you a settings page: a left sidebar with three tab names, and a right panel that shows one of three forms. A teammate builds SettingsPage, LeftSidebar, RightPanel, PanelHeader, PanelBody, PanelFooter, and one component per form — ten components. Eight of them take the same three props and pass them straight down.

Say which of those components you would keep and which you would delete, using the data model as your argument. Then say what data model you would ask the backend for.

Remember this · the Feynman summary
  • A component is a responsibility, not a rectangle. Ask which part of the screen is a function of which part of the data.
  • Five steps: tree → static version → minimal state → who owns it → inverse data flow. The order matters more than the speed.
  • Three lenses for splitting: one job each, the shape of the data, the design's own repeats and names. When they disagree, trust the data model.
  • Repeating data creates components. ProductRow and ProductCategoryRow exist because the list repeats and comes grouped.
  • A static version has no state and no handlers — props only. State is for data that changes over time, and nothing changes yet.
  • Static first because it separates typing from thinking: lots of typing and no thinking now, lots of thinking and little typing later.
  • Type the data model first — interface Product — and the props types fall out of it.
  • Store data, format at the edge. price: 1 plus Intl.NumberFormat, never price: "$1".
  • Loops inside render are fine; side effects are not. A local rows array is created and thrown away in the same render.
  • Real use case (built & run): a five-component static product table rendering typed data, grouped by category, out-of-stock names in red — zero state.

If you remember one thing: draw the tree from the data, then build it dead — interactivity is a separate, later decision.
