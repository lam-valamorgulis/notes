WebSockets in React

A socket is not data — it's a living object with a lifecycle. React has exactly two tools for things like that, and useState is not one of them.

Your win today: you'll be able to (1) connect a React app to a WebSocket without leaks, double-connections, or stale UI, (2) explain why the socket lives outside React state while its messages flow into it, and (3) describe the production shape — one app-wide connection, a manager hook, and an event router — used by a real product (a React 18 + TypeScript virtual-office app — our case-study codebase — whose source this lesson is drawn from).

Everything so far in this course renders data: numbers, strings, arrays. A WebSocket is a different kind of thing — a live connection that opens, emits events at random times, breaks, and must be closed. It doesn't render. It doesn't diff. Putting it in useState is a category error. The whole lesson is learning where it does go.

First principle — the naive version, and its three bugs

The obvious first attempt. Read it and find the bugs before I list them:

function Chat() {
  const socket = new WebSocket('wss://api.example.com/ws');   // ① in the component body
  const [messages, setMessages] = useState<string[]>([]);

  socket.onmessage = (e) => {                                  // ② wired during render
    setMessages([...messages, e.data]);                        // ③ reads `messages`
  };

  return <ul>{messages.map((m, i) => <li key={i}>{m}</li>)}</ul>;
}
  1. ① A new socket on every render. The component body re-runs on every state change (Lesson 2). First message arrives → setMessages → re-render → another new WebSocket(...). Each message spawns a connection; you DDoS your own server from one browser tab.
  2. ② No cleanup, ever. Nothing closes the old sockets. Navigate away and they linger.
  3. ③ The stale closure. onmessage captured this render's messages — a snapshot (Lesson 2, same trap, new costume). Every message computes [...messages] from that old snapshot, so the list keeps only the latest message.
The rule, in one line

The socket is a side effect; its messages are state. The connection lives in an effect (or outside React entirely). Only what you want to render — messages, connection status — goes through setState.

The correct small version — effect + cleanup + updater

function Chat() {
  const [messages, setMessages] = useState<string[]>([]);
  const [status, setStatus] = useState<'connecting' | 'open' | 'closed'>('connecting');

  useEffect(() => {
    const socket = new WebSocket('wss://api.example.com/ws'); // created in the effect
    socket.onopen = () => setStatus('open');
    socket.onclose = () => setStatus('closed');
    socket.onmessage = (e) => {
      setMessages(prev => [...prev, e.data]);                 // updater form — no stale snapshot
    };
    return () => socket.close();                              // cleanup: the connection dies with the component
  }, []);                                                     // connect once per mounted component

  return <ul>{messages.map(m => <li key={m.id}>{m.text}</li>)}</ul>;
}

Three fixes in one shape: the socket is created inside useEffect (once per mount, not per render), the cleanup function closes it (React runs cleanup when the component unmounts — and before re-running the effect), and setMessages(prev => …) uses the updater form, so the handler never depends on a snapshot.

Trap — StrictMode connects twice, on purpose In development, React 18's <StrictMode> mounts, unmounts, and re-mounts every component — so your effect runs connect → close → connect. This is not a bug to silence; it is React testing that your cleanup actually works. If double-connect breaks your app (duplicate "user joined" events, two subscriptions), your cleanup is incomplete — fix the cleanup, don't remove StrictMode. The interview version: "StrictMode revealed that my effect wasn't symmetric."

The production shape — one connection, a manager, a router

Now the real-world problem: chat, presence, notifications, and live data all over the app. One socket per component would mean dozens of connections. Every serious app converges on the same architecture — and the case-study app is a textbook example:

// ── network.ts — a MODULE SINGLETON, outside React entirely ──────────
// The case-study app does exactly this: one configured STOMP-over-WebSocket
// client, exported once, shared by chat, presence, calls, everything.
let socket: WebSocket | null = null;
const listeners = new Set<(msg: ServerMessage) => void>();

export function connect(token: string) {
  socket = new WebSocket(`wss://api.example.com/ws?auth=${token}`);
  socket.onmessage = (e) => {
    const msg = JSON.parse(e.data) as ServerMessage;
    listeners.forEach(fn => fn(msg));                // fan out to whoever subscribed
  };
}
export function subscribe(fn: (msg: ServerMessage) => void) {
  listeners.add(fn);
  return () => listeners.delete(fn);                 // unsubscribe = the return value
}
export function send(msg: ClientMessage) { socket?.send(JSON.stringify(msg)); }
// ── useConnection.ts — ONE hook owns the lifecycle (cf. useNetworkManager) ──
export function useConnection(token: string | null) {
  const [status, setStatus] = useState<Status>('offline');
  const attempt = useRef(0);

  useEffect(() => {
    if (!token) return;
    let cancelled = false;

    function open() {
      setStatus('connecting');
      connect(token, {
        onOpen:  () => { attempt.current = 0; setStatus('open'); },
        onClose: () => {                                  // reconnect with exponential backoff
          if (cancelled) return;
          setStatus('reconnecting');
          const delay = Math.min(30_000, 1000 * 2 ** attempt.current++);
          setTimeout(() => { if (!cancelled && navigator.onLine) open(); }, delay);
        },
      });
    }
    open();
    return () => { cancelled = true; disconnect(); };     // symmetric — StrictMode-proof
  }, [token]);

  return status;                                          // 'offline' | 'connecting' | 'open' | 'reconnecting'
}

Three responsibilities, three homes — this is the architecture worth memorizing:

  • The connection is a module singleton — plain TypeScript, no React. It exists once per tab, survives every re-render, and components never touch it directly. (the case-study app: network.ts exports one STOMP client that carries chat, presence, call invites and all call signaling — one connection, four jobs.)
  • The lifecycle — connect on login, reconnect with backoff — lives in one hook, mounted once near the app root (the case-study app: useNetworkManager, which doubles the delay on each failed attempt, caps it, and only retries when navigator.onLine says there's a network to try).
  • The data flows through a router: one onmessage parses each message's type and hands it to the right store or provider (chat store, presence store, call provider). Components read from those stores and re-render on data — never on socket events directly.

And the piece juniors forget: the status is state too. A 'reconnecting' banner is just UI = f(status) — the same one rule from Lesson 1, applied to connection health.

Two production details from the case-study source Heartbeats from a Worker: browsers throttle timers in background tabs, so a setInterval heartbeat silently stops and the server thinks you died. The case-study app configures its heartbeats to run on a Web Worker (workers aren't throttled), keeping the connection alive while the tab is hidden. Filter your own echo: when you broadcast to a room you're in, the server may send your message back to you — the case-study app stamps each frame with a client id and drops its own. If your chat shows every sent message twice, this is why.
Trap — the context that reconnects everyone A tempting refactor: <SocketContext.Provider value={{ socket, status }}>. That object literal is recreated on every render of the provider, so every consumer re-renders every time anything changes — and if consumers key effects on it, they resubscribe constantly. Provide stable things: the singleton's functions (stable by module), plus status as plain state. The socket object itself almost never needs to be in context at all.

Rendering a live feed — the last mile

function useChannel(channel: string) {
  const [items, setItems] = useState<Message[]>([]);
  useEffect(() => {
    return subscribe((msg) => {                       // subscribe returns unsubscribe — perfect cleanup
      if (msg.channel !== channel) return;
      setItems(prev => [...prev.slice(-199), msg]);   // cap the list — unbounded state is a leak too
    });
  }, [channel]);
  return items;
}

Note the two small production habits: the subscription's unsubscribe function is the effect cleanup (change channels → old subscription is removed before the new one starts), and the list is capped — a socket that delivers 10 messages/second grows an uncapped array to 36,000 items an hour, and every one of them re-renders.

Drill — the reconnect banner

Product asks: "when the connection drops, show a yellow 'reconnecting…' bar; when it's back, flash a green 'connected' bar for 2 seconds, then hide it."

Build it as a component consuming useConnection's status. The 2-second "then hide" is the interesting part — which tool runs that timer, and what must its cleanup do if the connection drops again during the 2 seconds? Sketch it before the quiz.

Remember this
  • The socket is a side effect; its messages are state. Connections never go in useState — what renders does.
  • Small version: create in useEffect, close in cleanup, setX(prev => …) in handlers so no snapshot goes stale.
  • StrictMode's double-mount is a test of your cleanup, not a bug. Connect → close → connect must be harmless.
  • Production shape: module singleton (the connection) + one lifecycle hook (connect, backoff, online gating) + event router → stores (components read data, never the socket).
  • Connection status is state too — the reconnect banner is just UI = f(status).
  • Details that bite in production: heartbeats from a Worker (background-tab throttling), filter your own echo, cap live lists, provide stable values in context.

If you remember one thing: React renders data — a WebSocket is not data. Keep the connection outside the render world, and let only its messages and its status cross the border, as state.
