Updating objects & arrays in state

Why React insists you make a new one — and the short list of recipes that covers every case.

Your win today: you'll be able to (1) explain from first principles why editing state in place is invisible to React, (2) write every array and object update immutably without looking it up, and (3) recognise the "it works sometimes" bug that mutation causes — the most confusing bug in early React.

Month 1 said "never mutate state" and promised a full explanation. This is it. This lesson is short on new API and long on one idea, because that one idea is behind a whole family of bugs.

First principle — how React decides whether anything changed

When you call a setter, React has to answer one question: is this new value different from the one I already have? If nothing changed, re-rendering would be wasted work.

For a number or a string, "different" is obvious. 0 is not 1.

For an object or an array, JavaScript does not compare the contents. It compares identity — whether both names point at the same thing in memory. React uses Object.is, which behaves like === here.

const a = [1, 2, 3];
const b = [1, 2, 3];
a === b;            // false — same contents, different objects

const c = a;
c.push(4);
c === a;            // true — one array with two names

Now the consequence. This is the whole lesson in five lines:

function addTask(title: string) {
  tasks.push({ id: crypto.randomUUID(), title });   // edit the SAME array
  setTasks(tasks);                                   // hand React the same array back
}

React compares the value you passed with the value it already holds. They are the same array. Nothing changed, as far as React can tell, so it does not re-render. Your data did change. The screen does not.

The rule, in one line

React notices new objects, not new contents. To tell React something changed, hand it a different object — not the same object with different insides.

Why this bug is so hard to find: it works sometimes

If mutation always did nothing, you would catch it in a minute. It does not always do nothing, and that is what wastes people's afternoons.

Renders are not private. When any state in that component changes, React calls your function again, and your function reads the mutated array — which now has the pushed item in it. So the item appears, late, when something unrelated happens.

// tasks was mutated earlier and never showed up.
// Then the user types one letter in an unrelated search box:
setQuery('a');   // → re-render → the map() now reads the mutated array
                 // → the missing task suddenly appears

The symptoms people report are always the same, and now you can translate them:

  • "It only updates when I click something else." → a mutated array, revealed by an unrelated render.
  • "It works in dev but the count is wrong." → mutation seen twice under StrictMode's double invoke.
  • "My memoised child does not update." → React.memo also compares by identity, so the child sees the same prop and skips the render (Month 6).
The other reasons, briefly Identity comparison is the reason you can feel. There are more: keeping past renders intact is what lets React compare snapshots, power DevTools time travel, make useMemo and React.memo trustworthy, and re-run rendering safely under concurrent features. All of them rest on the same promise — a value you handed React is never edited afterwards.

Treat state as read-only

State is not technically frozen. JavaScript will happily let you push. The rule is a contract you keep, not a lock React puts on the object.

So the working sentence is: once a value is in state, you never edit it — you replace it. Copy what you need, change the copy, hand the copy to the setter.

The array recipes — all of them

There are only four things you do to a list. Learn one line for each and you are done.

filter and map do the heavy lifting, and both already return a new array. That is why "remove" and "update" read so cleanly. Memorise the pair:

  • filter = remove — keep the ones that are not it.
  • map = update — return a changed copy for the matching one, and the original for everyone else.
The two that catch everyone sort() and reverse() mutate in place and return the same array. setList(list.sort(fn)) looks pure and is not — you just edited state and handed back the same identity, so you get a silent no-render. Always copy first: [...list].sort(fn).

The object recipe — spread, then override

One line covers the flat case. Later keys win, so put your change after the spread:

setUser({ ...user, name: 'Mai' });               // copy everything, then replace name
setUser(prev => ({ ...prev, name: 'Mai' }));      // updater form — safer default

Nested objects are where it gets ugly, and the ugliness is honest: a spread is shallow. It copies the top level only. Inner objects are still shared with the old state, so editing one of them is still mutation.

// state: { name: 'Mai', address: { city: 'Hanoi', zip: '100000' } }

// WRONG — the copy shares the same address object
const next = { ...user };
next.address.city = 'Da Nang';    // mutates the old state too

// RIGHT — copy every level you touch, from the top down
setUser(prev => ({
  ...prev,
  address: { ...prev.address, city: 'Da Nang' },
}));
The real lesson of nested spreads When the copying gets painful, that is a signal about your state shape, not a signal that you need a library. Deeply nested state is hard to update because it is hard to reason about. Flatten it, or split it into two pieces of state. Month 3 makes choosing the shape a skill of its own.

Arrays of objects — the shape you will use most

Almost all real state is a list of records. Updating one field of one item combines both recipes: map for the list, spread for the item.

interface Task { id: string; title: string; done: boolean; }
const [tasks, setTasks] = useState<Task[]>([]);

function toggle(id: string) {
  setTasks(prev => prev.map(t =>
    t.id === id ? { ...t, done: !t.done } : t     // new item for the match, same item for the rest
  ));
}

Notice the : t at the end. Untouched items keep their original identity. That is not laziness — it is what lets React (and later React.memo) know those rows did not change.

Local mutation is fine

The rule is about state, not about all objects. An object you just created inside your handler is yours to edit freely, because React has never seen it. Copy first, mutate the copy as much as you like, then set it.

function addMany(titles: string[]) {
  const next = [...tasks];                    // my own fresh array
  for (const title of titles) {
    next.push({ id: crypto.randomUUID(), title, done: false });   // push is fine here
  }
  setTasks(next);                             // a new identity → React re-renders
}

Build it for real — a task board with five immutable updates

One list, one state variable, five operations. Every one of them makes a new array. Replace src/App.tsx:

src/App.tsx

import { useState } from 'react';

interface Task {
  id: string;
  title: string;
  done: boolean;
}

const SEED: Task[] = [
  { id: 'a', title: 'Write the spec',   done: true  },
  { id: 'b', title: 'Review the Figma', done: false },
  { id: 'c', title: 'Ship the banner',  done: false },
];

export default function TaskBoard() {
  const [tasks, setTasks] = useState<Task[]>(SEED);
  const [draft, setDraft] = useState('');

  // 1 · ADD — spread the old list, append the new item
  function addTask(e: React.FormEvent<HTMLFormElement>) {
    e.preventDefault();
    const title = draft.trim();
    if (!title) return;
    setTasks(prev => [...prev, { id: crypto.randomUUID(), title, done: false }]);
    setDraft('');
  }

  // 2 · UPDATE one field of one item — map + spread
  function toggle(id: string) {
    setTasks(prev => prev.map(t => (t.id === id ? { ...t, done: !t.done } : t)));
  }

  // 3 · RENAME — same recipe, different field
  function rename(id: string, title: string) {
    setTasks(prev => prev.map(t => (t.id === id ? { ...t, title } : t)));
  }

  // 4 · REMOVE — filter keeps everything that is not it
  function remove(id: string) {
    setTasks(prev => prev.filter(t => t.id !== id));
  }

  // 5 · REORDER — copy FIRST, then swap inside the copy
  function moveUp(index: number) {
    if (index === 0) return;
    setTasks(prev => {
      const next = [...prev];                              // my own array now
      [next[index - 1], next[index]] = [next[index], next[index - 1]];
      return next;
    });
  }

  const doneCount = tasks.filter(t => t.done).length;      // derived, not stored

  return (
    <section>
      <h1>Task board</h1>
      <p>{doneCount} of {tasks.length} done</p>

      <form onSubmit={addTask}>
        <input
          value={draft}
          placeholder="New task…"
          onChange={(e) => setDraft(e.target.value)}
        />
        <button type="submit">Add</button>
      </form>

      <ul>
        {tasks.map((t, i) => (
          <li key={t.id}>
            <input
              type="checkbox"
              checked={t.done}
              onChange={() => toggle(t.id)}
            />
            <input
              value={t.title}
              onChange={(e) => rename(t.id, e.target.value)}
            />
            <button onClick={() => moveUp(i)} disabled={i === 0}>↑</button>
            <button onClick={() => remove(t.id)}>✕</button>
          </li>
        ))}
      </ul>
    </section>
  );
}

Now run it, and then break it on purpose. This is the important half of the exercise:

  1. Break "add". Replace the body of addTask's setter with tasks.push({ id: crypto.randomUUID(), title, done: false }); setTasks(tasks);. Add a task: nothing appears.
  2. Now type one letter in the input. The missing task appears — because that keystroke caused a re-render, and the render read the mutated array. This is the "it works sometimes" bug, on demand.
  3. Break "reorder". Change moveUp to sort or swap on prev directly. Nothing moves, for exactly the same reason.
  4. Fix both and note what changed: not the logic — only who owns the array you edited.
A word about Immer Libraries like Immer (useImmer) let you write draft.tasks[3].done = true and produce the immutable copy for you. They are legitimate, and React's own docs recommend them for deep state. Learn the plain spread first anyway — if you only know the shortcut, mutation bugs elsewhere in your app will stay invisible to you.

Remember this · the Feynman summary
  • React compares identity, not contents (Object.is). Editing state in place keeps the same identity, so React concludes nothing changed and skips the render.
  • Mutation causes the "works sometimes" bug. Any later render reads the mutated data, so the change shows up late, triggered by something unrelated.
  • Treat state as read-only. Copy what you touch, change the copy, hand the copy to the setter.
  • Array recipes: add [...list, x] · remove list.filter(...) · update list.map(...) · insert slice + spread · sort [...list].sort(fn).
  • filter = remove, map = update. Both already return new arrays.
  • Watch sort and reverse — they mutate in place and return the same array. Copy first. slice is safe, splice spoils.
  • Objects: { ...prev, key: value }. Spread is shallow, so for nested state copy every level you change.
  • Arrays of objects combine both: map the list, spread the one item, return the others untouched so their identity survives.
  • Local mutation is fine on an object you just created. The contract only covers values React is already holding.
  • Painful nesting is a shape problem, not a library problem — flatten the state (Month 3), or reach for Immer knowingly.
  • Real use case (built & run): a task board with add, toggle, rename, remove, and reorder — all immutable — then broken on purpose to watch the stale screen and the late update.

If you remember one thing: React notices a new object, never new contents — so to change state, replace it, don't edit it.
