Month 1 · Lesson 2 · The render model

State & the render loop

The memory that makes UI move — useState and what really happens when you set it.

Your win today: you'll understand (1) why a normal variable can't make the screen update, (2) what useState actually gives you and how to type it, and (3) the exact loop React runs every time you set state — the loop that answers the most common React interview question, "what happens when you call setState?"

Last lesson: UI = f(state), and a component is a function whose props are its arguments. But props are passed down by a parent — a component can't change its own props. So how does a counter go up when you click? The missing ingredient is state: data a component owns and is allowed to change over time.

First principle — why a plain variable fails

The obvious first attempt is a normal variable. It seems reasonable, and it is completely broken. Read it and predict what happens when you click:

function Counter() {
  let count = 0;                       // a plain variable

  function handleClick() {
    count = count + 1;                 // change it
    console.log('count is now', count);
  }

  return <button onClick={handleClick}>Count: {count}</button>;
}

Click it: the console logs 1, 2, 3… but the button still says "Count: 0". Two separate things are broken, and understanding both is the lesson:

  1. Nothing told React to re-render. Changing a variable does not call your function again. React only re-computes the UI when it knows the data changed — and a plain assignment is invisible to it.
  2. Even if it did re-render, the variable resets. Counter is a function; every time React calls it, let count = 0 runs again from scratch. A local variable has no memory between calls.

So we need something that does two jobs at once: remember a value across renders, and tell React to re-render when that value changes. That thing is useState.

What state is, in one line

State is a component's memory. It's a value React keeps for you between renders — and changing it (through React's setter) is what triggers a new render.

useState — the fix, one piece at a time

import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);   // [the value, the setter]

  function handleClick() {
    setCount(count + 1);                    // ask React for a new render with count+1
  }

  return <button onClick={handleClick}>Count: {count}</button>;
}

Read useState(0) literally: "give me a state value starting at 0." It returns an array of exactly two things, and we name them with array destructuring:

  • count — the current value for this render.
  • setCount — the setter. Calling it does not just change a variable; it tells React "the state changed — please render this component again."
TypeScript note — you get typing for free Because you passed 0, TypeScript infers count: number and setCount: (n: number) => void. You don't write the type. You only annotate when the initial value doesn't tell the whole story — e.g. a value that starts empty but will hold a user object: useState<User | null>(null). That angle-bracket type is the one bit of TypeScript syntax you'll use constantly with hooks.

The render loop — what actually happens on setCount

This is the model to burn in. When you call the setter, React runs a precise cycle:

  1. Trigger. setCount(1) tells React: this component's state changed. React schedules a re-render (it doesn't happen on that exact line — more on that below).
  2. Render. React calls Counter() again. This time useState hands back the new value (1), so the returned description says "Count: 1".
  3. Diff. React compares the new description to the previous one and finds the one thing that changed: the button's text.
  4. Commit. React makes that one minimal edit to the real DOM. The screen now says "Count: 1".

Then it waits. You click again, an event fires, you call the setter, and the loop runs once more. That loop is UI = f(state) in motion — data changes, React re-runs f, the screen follows.

The gotcha that reveals the whole model — state is a snapshot

Here's the single experiment that separates people who "use React" from people who understand it. What does this button do after one click?

function handleClick() {
  setCount(count + 1);
  setCount(count + 1);
  setCount(count + 1);
}

Almost everyone guesses +3. It's actually +1. Why? Because count is a fixed value for this render — a snapshot. During this click, count is 0 and stays 0 for the whole function. So all three lines read the same snapshot and say the same thing: "render with 0 + 1." React sees "set to 1" three times → 1.

Read that again, because it's the seed of a hard bug you'll meet in Month 4 (the "stale closure"): the count in your handler is the value from the render that created that handler — not a live pointer to the latest state.

When your next value depends on the previous one, pass a function to the setter instead. React feeds it the latest value and applies each in turn:

function handleClick() {
  setCount(c => c + 1);   // c is the latest value React has
  setCount(c => c + 1);
  setCount(c => c + 1);   // now genuinely +3
}
The rule that follows If the new state is built from the old state, use the updater function form: setX(prev => ...). If it's a brand-new value that doesn't depend on the old one, setX(value) is fine. This one habit prevents a large family of "why is my state one step behind?" bugs.

Two more facts that fall out of "state is a snapshot":

  • State updates are batched. React doesn't re-render on each setter call inside one event — it collects them and renders once, at the end. That's why reading count right after setCount still shows the old value: the new value belongs to the next render.
  • Never mutate state. For objects and arrays, don't change the existing one (arr.push(...)) — create a new one ([...arr, item]) and pass it to the setter. React decides "did it change?" by comparing references; mutating the same object hides the change from React. (Full treatment in Month 2.)

Build it for real — an interactive "like" card

Let's build a small interactive widget with real state and prove the render loop with our own eyes. In your Vite project, replace src/App.tsx:

src/App.tsx

import { useState } from 'react';

export default function LikeCard() {
  // This log runs on EVERY render — watch it fire as you click.
  console.log('LikeCard rendered');

  const [likes, setLikes] = useState(0);
  const [liked, setLiked] = useState(false);

  function toggleLike() {
    // depends on previous state → use the updater form
    setLikes(n => (liked ? n - 1 : n + 1));
    setLiked(l => !l);
  }

  return (
    <article>
      <h2>React from first principles</h2>
      <button onClick={toggleLike}>
        {liked ? '♥ Liked' : '♡ Like'}
      </button>
      <p>{likes} {likes === 1 ? 'person likes' : 'people like'} this</p>
    </article>
  );
}

Run npm run dev, open the browser console, and click. Feel each piece of the model happen:

  1. Every click logs "LikeCard rendered" — proof that setting state re-runs the whole function. That's the render loop, live.
  2. The heart, the count, and the "person/people" wording all update together from a single source of truth (the state). You never wrote a line of DOM code — you described the UI, React synced it.
  3. onClick={toggleLike} passes the function itself, not toggleLike(). If you wrote the parentheses, you'd call it immediately during render (an instant infinite loop of state-setting). Passing the reference lets React call it later, when the click actually happens.
The takeaway you can feel State is memory that survives renders. Setting it re-runs your component. Derived text like "person/people" needs no extra state — it's computed from the state during render. One source of truth, many parts of the UI in sync, zero hand-written DOM updates.

Remember this · the Feynman summary
  • A plain variable can't drive the UI: changing it doesn't tell React to re-render, and it resets to its initial value every time the component runs.
  • State is a component's memory. useState(initial) returns [value, setter]. The value persists across renders; the setter both updates it and tells React to re-render.
  • The render loop: setState → React schedules a render → calls your component again (new state value) → diffs the new description → commits the minimal DOM change.
  • State is a snapshot. Within one render, the state value is fixed — so setCount(count+1) three times only adds 1. Use the updater form setCount(c => c+1) when the next value depends on the previous.
  • Updates are batched (one render per event) and state is never mutated — you pass a new value/object to the setter.
  • TypeScript: the initial value is usually enough to infer the type; annotate with useState<T>() only when it can't be inferred (e.g. starts null).
  • onClick={fn}, not onClick={fn()} — pass the function so React calls it on the event, don't call it during render.
  • Real use case (built & run): a Like card whose heart, count, and wording all update from one state source — and a console.log proving each click re-runs the component.

If you remember one thing: setting state doesn't change a variable — it asks React to render your component again with a new value.
