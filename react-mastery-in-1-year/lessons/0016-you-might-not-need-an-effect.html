Month 4 · Lesson 2

You might not need an effect

Most effects in most codebases should not exist. Here is the full catalogue of the mistake, why each one is slower and buggier, and the one-line replacement for each.

Your win today: you can look at any useEffect and answer "should this exist?" in about five seconds — and delete four of them from a working app without changing what the user sees.

Lesson 1 gave you a door to the outside world. This lesson is about not walking through it for no reason.

The React documentation has a whole page called "You Might Not Need an Effect", and it exists because this is the most common way React code goes wrong. Not a subtle bug — a habit. Something changes, so people reach for an effect to react to it.

The test, in two questions

Is this caused by a specific user action? → event handler. Is this synchronising with a system outside React? → effect. Neither? → it is a calculation, and it belongs in render.

First principle — an effect is a detour

Nothing about an effect makes it a neutral choice. Compare the two timelines for "show a filtered list".

The catalogue

Every row below is a real pattern from real code. The left column is what people write; the right is what it should be.

The habitWhat to do instead
An effect that computes state from props or other stateCompute it during render. No state, no effect.
An effect that caches an expensive calculationuseMemo — after measuring. It caches without making a second truth.
An effect that resets all state when a prop changesGive the component a key. React resets it for you.
An effect that resets some state when a prop changesCompare with the previous prop and set state during render.
An effect that runs shared logic for two handlersA plain function, called from both handlers.
An effect that sends a POST because state changedSend it in the handler that caused it.
A chain of effects, each setting the next valueOne calculation during render, or one handler that sets everything.
An effect with [] for app startup workModule scope — it runs once when the module loads.
An effect that tells the parent about a state changeCall setState and onChange in the same handler.
An effect that pushes data up to the parentLift the state. Data flows down, not up.
An effect that subscribes to a browser or third-party storeuseSyncExternalStore.
An effect that fetches dataThis one is legitimate — but it needs the race fix, and a library does it better. Lesson 4, then Month 7.

Now the six worth writing out, because each one has a bug you will meet.

1. Computing state from props or state

// ✕ Redundant state and an unnecessary effect
function Form({ firstName, lastName }: Props) {
  const [fullName, setFullName] = useState('');

  useEffect(() => {
    setFullName(firstName + ' ' + lastName);
  }, [firstName, lastName]);
  // Renders with the OLD name, paints it, then fixes it. And if a third
  // name field is added and forgotten here, fullName is silently wrong.
}

// ✓ One line, always correct, no frame in between
function Form({ firstName, lastName }: Props) {
  const fullName = firstName + ' ' + lastName;
}

This is Month 3's "minimal state" rule showing up again. If you can calculate it during render, it is not state — and an effect that keeps a copy in sync is just the maintenance bill for storing it.

Expensive? Measure before you cache Wrap the calculation in console.time('filter') / console.timeEnd('filter') and look. Under about 1 ms, do nothing. If it is genuinely slow, useMemo(() => getFiltered(todos, filter), [todos, filter]) caches the result between renders without turning it into state. Same single truth, just remembered.

2. Resetting all state when a prop changes — use a key

// ✕ The effect approach: manual, incomplete, and one render late
function Profile({ userId }: { userId: string }) {
  const [comment, setComment] = useState('');
  const [draftTitle, setDraftTitle] = useState('');

  useEffect(() => {
    setComment('');
    setDraftTitle('');     // every new state you add must be remembered here
  }, [userId]);
}

// ✓ Split the component and hand React an identity
export default function ProfilePage({ userId }: { userId: string }) {
  return <Profile userId={userId} key={userId} />;
}

function Profile({ userId }: { userId: string }) {
  // This and every state below it resets automatically on a key change.
  const [comment, setComment] = useState('');
  const [draftTitle, setDraftTitle] = useState('');
}

You already know why this works — Lesson 9. A different key means a different component to React, so it throws the old state away. The effect version forgets one state variable the day someone adds a third field; the key version cannot.

3. Resetting some state when a prop changes

Sometimes only part of the state should reset. The docs' answer surprises people: set state during render, guarded by a comparison with the previous prop.

function List({ items }: { items: Item[] }) {
  const [isReverse, setIsReverse] = useState(false);
  const [selection, setSelection] = useState<Item | null>(null);

  // Better: adjust the state while rendering
  const [prevItems, setPrevItems] = useState(items);
  if (items !== prevItems) {
    setPrevItems(items);
    setSelection(null);     // isReverse survives; only the selection resets
  }
}

It looks illegal and it is not. React re-renders the component immediately after it exits, before rendering children and before touching the DOM, so nothing is painted in between. That is strictly better than an effect, which paints first and fixes second. It is still the second-best option though — the best is not needing it:

// ✓ Best: calculate everything during rendering
function List({ items }: { items: Item[] }) {
  const [isReverse, setIsReverse] = useState(false);
  const [selectedId, setSelectedId] = useState<string | null>(null);

  // Nothing to reset: if the item is gone, the lookup is null on its own.
  const selection = items.find(item => item.id === selectedId) ?? null;
}

Store the id, look up the object — Month 3, Principle 4. The reset problem vanishes, rather than being handled.

4. Logic shared between event handlers

// ✕ A bug, not just a smell
function ProductPage({ product, addToCart }: Props) {
  useEffect(() => {
    if (product.isInCart) {
      showNotification(`Added ${product.name} to the cart!`);
    }
  }, [product]);
  // Reload the page with something already in the cart and the toast fires
  // again — the user did nothing. Worse in a real app: this shape is how
  // "buy" ends up firing on a page refresh.
}

// ✓ The action caused it, so the handler owns it
function ProductPage({ product, addToCart }: Props) {
  function buyProduct() {
    addToCart(product);
    showNotification(`Added ${product.name} to the cart!`);
  }

  function handleBuyClick()  { buyProduct(); }
  function handleCheckout()  { buyProduct(); navigateTo('/checkout'); }
}

The causation test settles it. The notification happens because the user clicked buy, not because the cart contains something. Effects run whenever the component shows up, including on a refresh — so anything that should happen once per action must not live in one.

5. Chains of effects

// ✕ Four renders, and a chain that is hard to change safely
const [card, setCard] = useState(null);
const [goldCardCount, setGoldCardCount] = useState(0);
const [round, setRound] = useState(1);

useEffect(() => { if (card?.gold) setGoldCardCount(c => c + 1); }, [card]);
useEffect(() => { if (goldCardCount > 3) { setRound(r => r + 1); setGoldCardCount(0); } }, [goldCardCount]);

// ✓ One handler, one pass: the event knows everything already
function handlePlaceCard(nextCard: Card) {
  setCard(nextCard);
  if (nextCard.gold) {
    if (goldCardCount <= 3) {
      setGoldCardCount(goldCardCount + 1);
    } else {
      setGoldCardCount(0);
      setRound(round + 1);
    }
  }
}

Each effect in a chain triggers a render that triggers the next effect. The app is slower, and — worse — you can no longer read the rules in one place. Anything caused by one user action should be decided in one handler.

6. Telling the parent about a change

// ✕ Parent finds out one render late
function Toggle({ onChange }: { onChange: (on: boolean) => void }) {
  const [isOn, setIsOn] = useState(false);
  useEffect(() => { onChange(isOn); }, [isOn, onChange]);
}

// ✓ Both updates in the event that caused them — one render pass
function Toggle({ onChange }: { onChange: (on: boolean) => void }) {
  const [isOn, setIsOn] = useState(false);

  function updateToggle(nextIsOn: boolean) {
    setIsOn(nextIsOn);
    onChange(nextIsOn);
  }

  function handleClick() { updateToggle(!isOn); }
}

And if the parent needs that value anyway — lift it. A fully controlled Toggle that takes isOn and onChange deletes the problem instead of solving it. Data flows down; an effect that pushes data up is a sign the state is in the wrong component.

Two more worth knowing by name

// App startup — not an effect. Module scope runs once, when the module loads.
if (typeof window !== 'undefined') {
  checkAuthToken();
  loadDataFromLocalStorage();
}

function App() { /* … */ }
// Subscribing to something outside React: the purpose-built hook, not an effect
function subscribe(callback: () => void) {
  window.addEventListener('online', callback);
  window.addEventListener('offline', callback);
  return () => {
    window.removeEventListener('online', callback);
    window.removeEventListener('offline', callback);
  };
}

function useOnlineStatus() {
  return useSyncExternalStore(
    subscribe,               // same function identity ⇒ no resubscribe
    () => navigator.onLine,  // value on the client
    () => true,              // value on the server
  );
}

useSyncExternalStore exists because the effect version of a subscription can read a value that changed between render and the effect firing. It is also the hook every state library uses under the hood — which is why it appears again in Month 6.

Build it for real — delete four effects from a working app

This app works. Every feature is correct on screen. It also has four effects that should not exist. Type it, run it, then remove them one at a time and watch the file get shorter.

src/types.ts

export interface Member {
  id: string;
  name: string;
  role: string;
  active: boolean;
}

src/TeamPanel.tsx — the "before". Four effects, four bugs waiting.

import { useEffect, useState } from 'react';
import type { Member } from './types';

interface TeamPanelProps {
  members: Member[];
  onVisibleCountChange: (n: number) => void;
}

export function TeamPanel({ members, onVisibleCountChange }: TeamPanelProps) {
  const [query, setQuery] = useState('');
  const [activeOnly, setActiveOnly] = useState(false);
  const [selectedId, setSelectedId] = useState<string | null>(null);

  // ✕ 1. Derived data stored in state
  const [visible, setVisible] = useState<Member[]>(members);
  useEffect(() => {
    setVisible(
      members.filter(
        m =>
          m.name.toLowerCase().includes(query.toLowerCase()) &&
          (!activeOnly || m.active),
      ),
    );
  }, [members, query, activeOnly]);

  // ✕ 2. A chain: this one waits for the effect above to finish
  const [summary, setSummary] = useState('');
  useEffect(() => {
    setSummary(`Showing ${visible.length} of ${members.length}`);
  }, [visible, members]);

  // ✕ 3. Pushing a value up to the parent, one render late
  useEffect(() => {
    onVisibleCountChange(visible.length);
  }, [visible, onVisibleCountChange]);

  // ✕ 4. Resetting state when a prop changes
  useEffect(() => {
    setSelectedId(null);
  }, [members]);

  const selected = visible.find(m => m.id === selectedId);

  return (
    <section>
      <input value={query} onChange={e => setQuery(e.target.value)} placeholder="Search…" />
      <label>
        <input type="checkbox" checked={activeOnly} onChange={e => setActiveOnly(e.target.checked)} />{' '}
        Active only
      </label>

      <p>{summary}</p>

      <ul>
        {visible.map(m => (
          <li key={m.id} onClick={() => setSelectedId(m.id)}>
            {m.name} — {m.role}
          </li>
        ))}
      </ul>

      {selected && <p>Selected: {selected.name}</p>}
    </section>
  );
}

src/TeamPanel.tsx — the "after". Same features, zero effects.

import { useState } from 'react';
import type { Member } from './types';

interface TeamPanelProps {
  members: Member[];
  onSelect: (id: string | null) => void;   // the parent asked for a fact; give it one on the event
}

export function TeamPanel({ members, onSelect }: TeamPanelProps) {
  const [query, setQuery] = useState('');
  const [activeOnly, setActiveOnly] = useState(false);
  const [selectedId, setSelectedId] = useState<string | null>(null);

  // ✓ 1 + 2. Derived during render: correct on the first frame, always in step.
  const visible = members.filter(
    m =>
      m.name.toLowerCase().includes(query.toLowerCase()) &&
      (!activeOnly || m.active),
  );
  const summary = `Showing ${visible.length} of ${members.length}`;

  // ✓ 4. No reset needed: an id that is gone simply finds nothing.
  const selected = visible.find(m => m.id === selectedId) ?? null;

  // ✓ 3. Told in the event that caused it — one render, no dependency array.
  function handleSelect(id: string) {
    setSelectedId(id);
    onSelect(id);
  }

  return (
    <section>
      <input value={query} onChange={e => setQuery(e.target.value)} placeholder="Search…" />
      <label>
        <input type="checkbox" checked={activeOnly} onChange={e => setActiveOnly(e.target.checked)} />{' '}
        Active only
      </label>

      <p>{summary}</p>

      <ul>
        {visible.map(m => (
          <li key={m.id} onClick={() => handleSelect(m.id)}>
            {m.name} — {m.role}
          </li>
        ))}
      </ul>

      {selected && <p>Selected: {selected.name}</p>}
    </section>
  );
}

Two state variables removed, four effects removed, four dependency arrays that no longer exist to get wrong — and the summary is right on the first paint. Note what replaced effect 3: not another effect, but a change of contract. The parent wanted to know about a selection, so the child reports the event, not the resulting state.

The one effect that stays

Add this to the parent, and be able to defend it:

function App() {
  const [members, setMembers] = useState(INITIAL_MEMBERS);
  const activeCount = members.filter(m => m.active).length;

  // ✓ A real effect: document.title is a system outside React.
  //   Not a calculation, not caused by one user action — it must simply
  //   match what is on the screen, whenever that changes.
  useEffect(() => {
    document.title = `Team (${activeCount} active)`;
  }, [activeCount]);

  // …
}

Run the two questions over it. Caused by a specific user action? No — the tab title must be right however the count changed. Synchronising with something outside React? Yes: the browser tab. So it is an effect, and it needs no cleanup, because the next run overwrites the same single slot.

Extend it — three reps

  1. Persist the filters. Save query and activeOnly to localStorage so a refresh keeps them. Decide first: which part is an effect and which part is not? (Writing is an effect — localStorage is outside React. Reading the initial value is not: pass it to useState as an initial value instead.)
  2. Reset everything for a new team. The parent can now switch between two teams. Reset the whole panel with key={teamId} and delete any code you were tempted to write.
  3. Reset only the checkbox. Keep query, clear activeOnly when the team changes. Use the prevTeamId comparison during render, and say out loud why that beats an effect.

Practice: read the situation, pick the move

Scenario

A pull request adds a feature to a settings form: when the user changes the currency, the totals must update and the change must be saved to the server. The implementation is two effects — one that recalculates totals into state when currency changes, and one that calls saveSettings(currency) when currency changes. Both have correct dependency arrays and the feature works in the demo.

Review it. One of those two effects should be deleted and one should be moved, and there is a specific user-visible bug in the second one that a demo will not show. Name all three things — and say what you would ask the author to test.

Remember this · the Feynman summary
  • Two questions decide everything. Caused by a specific user action → handler. Synchronising with an outside system → effect. Neither → it is a calculation; put it in render.
  • An effect is a detour: render, paint the wrong frame, effect, setState, render, paint again. Calculating during render paints correctly the first time.
  • Storing derived data makes a second truth, and a second truth needs syncing, and syncing is where the bugs live. Delete the copy, not the sync code.
  • Expensive? Measure with console.time, then useMemo — a cache, not a second copy of the truth.
  • Reset all state on a prop change with key, not with an effect that must remember every state variable.
  • Reset some state by comparing the previous prop and setting state during render. React re-renders before painting, so nothing wrong is ever shown.
  • Shared handler logic goes in a plain function, called from both handlers. An effect would fire again on a refresh, when the user did nothing.
  • Chains of effects each cost a render and hide the rules. One handler decides everything the action implies.
  • Never push data up in an effect. Tell the parent in the same handler, or lift the state.
  • Startup work goes in module scope; subscriptions go in useSyncExternalStore; fetching is a real effect that needs the race fix (next lessons).
  • Real use case (built & run): a working team panel with four effects, reduced to zero — plus one document.title effect kept on purpose, with the reason spoken out loud.

If you remember one thing: if no system outside React is involved, an effect is the wrong tool — you are describing a calculation.
