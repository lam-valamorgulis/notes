Where state lives & inverse data flow

Steps 4 and 5: the procedure that finds the one owner of each piece of state, and the callback contract that lets children ask for changes.

Your win today: you will be able to (1) run a three-step procedure that names the owner of any piece of state, (2) design a child's props as a contract — value down, onChange up — with types that do not leak the parent's implementation, and (3) say when to invent a component just to hold state, and when prop drilling has gone too far.

You have the tree, and you know the two things that change. One question is left before the app works: who owns them?

Month 2 taught the mechanics of lifting state up. This lesson turns that into a procedure you can run on a design you have never seen, plus the part nobody teaches — how to design the child's props so it stays reusable.

First principle — one owner, and props only travel down

Props flow one way. A component reads what its parent passed, and nothing else: no reaching sideways to a sibling, no reaching up. That single constraint decides ownership for you.

The rule

A piece of state must live in a component that is above everyone who reads it — and the useful choice is the closest such component. Higher than necessary re-renders more of the app than necessary and hides who changed what.

So "where does state live?" is not taste. It is arithmetic on the tree.

Step 4 — the procedure, three moves

Straight from the React docs. For each piece of state, separately:

  1. List every component that renders something based on it. Reading it to show it counts. Reading it to filter with it counts.
  2. Find their closest common parent — the lowest component that has all of them somewhere beneath it.
  3. Put the state there. Or higher, if something above also needs it. Or, if no existing component is a sensible owner, create a new component just to hold it and place it above the common parent.

The third option people forget — a component whose only job is to hold state

Sometimes the closest common parent is a bad owner. Two panels halfway down a big page need the same value, and their nearest shared ancestor is a 300-line layout component, or App itself.

Putting app-wide plumbing into App is how App becomes a 500-line file that nobody wants to open. The docs' third option is better: create a component that exists only to own that state and wrap the readers in it.

// Before: App owns things it does not care about.
function App() {
  const [filterText, setFilterText] = useState('');
  const [inStockOnly, setInStockOnly] = useState(false);
  return (
    <Layout>
      <SearchBar filterText={filterText} … />
      <ProductTable products={PRODUCTS} filterText={filterText} … />
      <Footer />
    </Layout>
  );
}

// After: one small component owns the feature's state, App just places it.
function App() {
  return (
    <Layout>
      <FilterableProductTable products={PRODUCTS} />   // self-contained
      <Footer />
    </Layout>
  );
}

That new component is not overhead. It is the name of the feature, and it gives you a unit you can move, reuse, and test on its own.

Choose…WhenCost if you get it wrong
The closest common parentThe default. It already exists and it already renders both readers.—
Something higher upA third reader will appear above, or a sibling feature needs the same value.Lifting too high re-renders a large tree on every keystroke and makes ownership hard to find.

Step 5 — inverse data flow

Data goes down. Now the child needs to change something above it. It cannot — so the parent hands it a function, and calling that function is the child's way of asking.

That is the whole of "inverse data flow". Nothing flows up except a function call.

Pass the setter, or pass a handler?

// A · the setter itself — fine when the parent has nothing to add
<SearchBar onFilterTextChange={setFilterText} />

// B · a named handler — when the parent does more than store the value
function handleFilterTextChange(next: string) {
  setFilterText(next);
  setPage(1);                      // a new search starts on page one
}
<SearchBar onFilterTextChange={handleFilterTextChange} />

Start with A. Move to B the moment the parent has a second thing to do. The child never notices the difference, which is the point.

The naming convention, and why it is worth following The prop is named for the event: onFilterTextChange, onSelect, onDelete. The function inside the parent is named for the work: handleFilterTextChange. When you read a component's props you then see its whole API at a glance: values coming in, and on… events going out. React's own DOM components do exactly this.

Type the contract, not the implementation

Here is a TypeScript decision that separates a junior from a senior component API.

// ✕ Leaks how the parent stores the value
interface SearchBarProps {
  onFilterTextChange: React.Dispatch<React.SetStateAction<string>>;
}

// ✓ Says only what the child is allowed to ask for
interface SearchBarProps {
  filterText: string;
  inStockOnly: boolean;
  onFilterTextChange: (next: string) => void;
  onInStockOnlyChange: (next: boolean) => void;
}

Two reasons the second one is better:

  • It keeps the parent free. With Dispatch<SetStateAction<string>> you have promised the child that a useState setter sits behind the prop. Swap the parent to useReducer, add validation, or put the value in the URL later, and the type no longer matches — even though the child's needs never changed.
  • It keeps the child honest. That type also lets the child call onFilterTextChange(prev => prev + '!') — reaching into the parent's previous state. A child should report what happened, not run updates on the owner's data.

(next: string) => void is still satisfied by passing setFilterText directly, so you lose nothing. That is the sweet spot: strict contract, flexible implementation.

The component contract — controlled, uncontrolled, or both

Steps 4 and 5 have a consequence people miss. Once a child takes value + onChange, the child no longer decides where the state lives — and that is what makes it reusable.

ShapePropsWho owns the valueUse when
Controlledvalue + onChangethe parentAnyone else needs to read it, reset it, or react to it. Default for shared UI.
UncontrolleddefaultValue onlythe childNobody outside cares until submit — a simple form field, a search box that only searches on Enter.
Bothvalue? + defaultValue? + onChange?whoever passed propsA library component. More code, so only for components with many users.

<input> is the proof this is a real pattern, not a theory: pass value and React owns it, pass defaultValue and the DOM owns it. Your components can offer the same choice, and the naming is already familiar to every React developer.

The half-controlled trap Taking value as a prop and keeping a copy in state "so typing feels fast" gives you two owners and a race between them. If you accept value, render value. If you want a private draft — an edit form that can be cancelled — say so in the API: take defaultValue, keep your own state, and report the result with onSubmit.

How far down is too far — prop drilling

Passing a prop through three components that do not use it is a smell, not a crime. Try the cheap fixes before the expensive one.

  1. Move the component, not the data. If the middle layer only forwards props, pass the finished JSX instead. The data never travels: 
    // Drilling: Layout does not care about user, but must carry it.
<Layout user={user} />      // → <Sidebar user={user} /> → <UserBadge user={user} />

// Composition: Layout takes a hole to fill. It never sees user.
<Layout sidebar={<UserBadge user={user} />} />
  2. Pass one object instead of six props — <ProductRow product={product} /> rather than name, price, category, inStock. Fewer joints to change when the model changes.
  3. Then Context — for values a whole subtree needs and nobody wants to thread: theme, current user, locale. That is Month 6, together with the re-render cost it brings. Context is a delivery mechanism, not a state manager, and reaching for it to avoid two levels of props usually makes the app harder to follow.

Build it for real — wire the table up

Same project as Lesson 1. Two files change, and the app comes alive.

src/SearchBar.tsx — fully controlled, owns nothing

interface SearchBarProps {
  filterText: string;
  inStockOnly: boolean;
  onFilterTextChange: (next: string) => void;
  onInStockOnlyChange: (next: boolean) => void;
}

export function SearchBar({
  filterText, inStockOnly, onFilterTextChange, onInStockOnlyChange,
}: SearchBarProps) {
  return (
    <form onSubmit={e => e.preventDefault()}>   // nothing to submit: filtering is live
      <input
        type="text"
        placeholder="Search…"
        value={filterText}                       // value comes from above…
        onChange={e => onFilterTextChange(e.target.value)}   // …changes go back up
      />
      <label>
        <input
          type="checkbox"
          checked={inStockOnly}                  // checkboxes use checked, not value
          onChange={e => onInStockOnlyChange(e.target.checked)}
        />{' '}
        Only show products in stock
      </label>
    </form>
  );
}

Read the props type out loud: two values in, two events out, no state. This component works the same whether the owner is a parent, a reducer, or the URL — it cannot tell, and it does not care.

src/FilterableProductTable.tsx — the owner does the deriving

import { useState } from 'react';
import type { Product } from './types';
import { SearchBar } from './SearchBar';
import { ProductTable } from './ProductTable';

export function FilterableProductTable({ products }: { products: Product[] }) {
  // Step 4: both children read these, so they live here.
  const [filterText, setFilterText] = useState('');
  const [inStockOnly, setInStockOnly] = useState(false);

  // Step 3's leftovers: derived during render, never stored.
  const needle = filterText.trim().toLowerCase();
  const visible = products.filter(p =>
    p.name.toLowerCase().includes(needle) && (!inStockOnly || p.inStock)
  );

  return (
    <div>
      <SearchBar
        filterText={filterText}
        inStockOnly={inStockOnly}
        onFilterTextChange={setFilterText}       // the setter fits (next: string) => void
        onInStockOnlyChange={setInStockOnly}
      />
      <p>Showing {visible.length} of {products.length}</p>
      <ProductTable products={visible} />       // the table just draws what it is given
    </div>
  );
}

ProductTable from Lesson 1 does not change at all. It already took a list of products and drew them, and that is still its whole job.

A real design choice — filter in the owner, or in the table? The React docs pass filterText and inStockOnly into ProductTable and filter inside it. Both versions work. Passing the finished list is the better default: ProductTable keeps one job — "draw these rows" — so it can be reused for search results, a category page, or a saved list, and it needs no new prop when a third filter arrives. Filtering inside the table only pays off when the table also owns paging or virtual scrolling and needs the full list itself. Either way, say which one you chose and why — that sentence is what an interviewer is listening for.

Run it. Type "fruit", tick the checkbox, watch the count. Every keystroke goes child → parent → state → render → both children. One direction, one owner, no surprises.

What just became easy

  • A "clear filters" button anywhere in the owner: setFilterText(''); setInStockOnly(false). The search box updates because it renders the value it was given.
  • Deep-linking later. Because SearchBar never owned the text, swapping useState for a URL search param in the owner changes one file (Month 8).
  • Testing. SearchBar takes plain values and plain functions — render it with a spy and assert what it called. No app needed (Month 9).

Remember this · the Feynman summary
  • One-way data flow decides ownership. State must live above everyone who reads it — and the closest such component is the right one.
  • Step 4, three moves: list every component that renders from the value · find their closest common parent · put it there, higher, or in a new component made only to hold it.
  • Inventing a component to own state is a real option — it names the feature and keeps App from collecting everyone's plumbing.
  • Too high is a real cost: bigger re-renders and ownership nobody can find. Do not lift past the closest common parent "just in case".
  • Inverse data flow is just a function call. Pass the setter when the parent adds nothing; pass handleX when it does more.
  • Naming: the prop is the event (onFilterTextChange), the parent's function is the work (handleFilterTextChange).
  • Type the contract, not the implementation: (next: string) => void, never Dispatch<SetStateAction<string>> — the child should not know the parent uses useState.
  • Controlled means the child owns nothing — value + onChange. Never accept value and keep a copy in state as well.
  • Against prop drilling, in order: pass JSX instead of data (composition) · pass one object instead of six props · then Context, in Month 6.
  • Real use case (built & run): the product table wired up — two states in the owner, a stateless controlled SearchBar, a derived visible list, and a live "showing N of M" count.

If you remember one thing: find the closest component above every reader, put the state there, and give the children a function — the tree tells you the answer.
