Measuring, timing & the browser

Some work has to finish before the user sees anything. That single sentence is the whole difference between useEffect and useLayoutEffect — and it decides whether your tooltip flickers.

Your win today: you can measure a real element and reposition it with no visible flicker, watch a size with ResizeObserver, and write a countdown that is still correct after twenty minutes in a background tab — plus the sentence that explains why useLayoutEffect is a last resort and not a better useEffect.

Lesson 20 gave you the node. Now you want to know something about it: how tall is this tooltip, how wide is this container, has this row scrolled into view. Measuring is easy — getBoundingClientRect() and you are done. Doing something with the measurement without the user seeing the before-and-after is the hard part, and it is a timing problem, not a DOM problem.

First principle — there is a moment when the screen is decided

Extend the render loop one more time. You know it up to the commit: React renders, compares, and writes to the DOM. Then two things happen in a fixed order that you can hook into.

StepWhat happensYour hook
renderYour function runs and returns JSX. No DOM exists for this render yet.—
commitReact writes the changes to the real DOM and attaches refs.—
before paintThe DOM is updated but the user has not seen it. React runs layout effects here — and any state you set is rendered and committed before the pixels are drawn.useLayoutEffect
paintThe browser draws the frame. This is the first moment the user sees anything.—
after paintEverything that does not need to beat the frame.useEffect
React docs · useLayoutEffect "useLayoutEffect is a version of useEffect that fires before the browser repaints the screen." … "React guarantees that the code inside useLayoutEffect and any state updates scheduled inside it will be processed before the browser repaints the screen. This lets you render the tooltip, measure it, and re-render the tooltip again without the user noticing the first extra render. In other words, useLayoutEffect blocks the browser from painting."

The flicker, in code

A tooltip that must appear above the target when there is no room below. You cannot know if there is room until you know how tall the tooltip is, and you cannot know that until it is in the DOM. So the first render is always a guess.

function Tooltip() {
  const ref = useRef(null);
  const [tooltipHeight, setTooltipHeight] = useState(0);

  useLayoutEffect(() => {
    const { height } = ref.current.getBoundingClientRect();
    setTooltipHeight(height);
  }, []);

  // ...use tooltipHeight in the rendering logic below...
}

Swap that one word to useEffect and the docs describe exactly what you get: "React will let the browser paint the screen before it processes the state update inside useEffect. As a result, the tooltip flickers."

Notice what is not different: the measurement is identical, the state update is identical, the final screen is identical. The only difference is whether the user sees the intermediate frame. That is why "it works but it flashes" is the signature of a measurement in the wrong hook.

The price, and the two warnings

React docs · Pitfall "useLayoutEffect can hurt performance. Prefer useEffect when possible."

Blocking paint means the browser is sitting idle while your JavaScript runs, and if you set state you have forced a second render into that same gap. On one tooltip nobody notices. On a hundred rows that each measure themselves, you have built a frame budget problem that no amount of memo will fix later.

React docs · useLayoutEffect does nothing on the server "When you or your framework uses server rendering, your React app renders to HTML on the server for the initial render… on the server, there is no layout information."

That one matters from Month 10, when the course moves to Next.js: a component that measures itself cannot produce correct HTML on the server, because there is no layout to measure. The documented options are to use useEffect instead, to mark the component as client-only, or to render the simple version first and swap after hydration.

Measuring is not free

Two facts about the browser that React cannot hide from you:

  1. Reading layout after changing styles forces the browser to compute layout early. getBoundingClientRect(), offsetHeight, scrollTop and friends must return a truthful answer, so the browser stops and recalculates. Do it once and cache it; do it in a loop over 200 rows, alternating with style writes, and you have built the slowest possible version of your feature.
  2. A measurement is a fact about one moment. The value you stored is wrong the instant the window resizes, a font loads, or a sibling grows. If the size can change while the component is on screen, one measurement is not enough — you need to be told when it changes.

Being told is what ResizeObserver is for. It is an outside system, so it is textbook effect work: setup, cleanup, and a dependency that says which node to watch.

import { useLayoutEffect, useRef, useState } from 'react';

type Size = { width: number; height: number };

export function ChartBox() {
  const boxRef = useRef<HTMLDivElement>(null);
  const [size, setSize] = useState<Size>({ width: 0, height: 0 });

  useLayoutEffect(() => {
    const node = boxRef.current;
    if (node === null) return;

    const observer = new ResizeObserver(entries => {
      const entry = entries[0];
      if (entry === undefined) return;
      const { width, height } = entry.contentRect;
      setSize({ width, height });          // React skips the re-render if both are unchanged
    });

    observer.observe(node);                // fires once immediately with the current size
    return () => observer.disconnect();    // ✓ the cleanup half of the pair
  }, []);

  return (
    <div ref={boxRef} style={{ resize: 'both', overflow: 'auto', border: '1px solid' }}>
      <p>{Math.round(size.width)} × {Math.round(size.height)}</p>
    </div>
  );
}

Three details that are easy to get wrong:

  • Copy the node into a local variable at the top of the effect. The cleanup runs later, and boxRef.current may already be null by then. This is the ref version of the stale-closure discipline from lesson 17.
  • observer.observe() fires straight away with the current size, so you do not need a separate first measurement.
  • Never resize the observed element inside its own callback. That is the cause of the console message "ResizeObserver loop completed with undelivered notifications" — you asked to be told about a change, and your reaction caused another change.
Which observer for which question ResizeObserver — "how big is this?" IntersectionObserver — "is this visible?" (lazy loading, infinite scroll, tracking impressions). MutationObserver — "did this subtree change?", which in a React app almost always means you are watching something you should have rendered yourself. All three are the same effect shape: create, observe, disconnect in the cleanup.

Timers, honestly

You have the two failure modes already: a timer with no cleanup leaks, and a timer that reads state directly freezes on one render's values (lesson 17). This lesson adds the third, which nobody warns you about until a user does.

A counter of ticks is not a clock setInterval does not promise to run on time. The callback is queued, so a busy main thread delays it — and in a background tab browsers clamp timers to roughly once per second or slower, and stop requestAnimationFrame entirely. So setSeconds(s => s - 1) once per interval drifts, and after twenty minutes in another tab your countdown can be minutes wrong. The fix is not a better timer. Store the deadline and compute the remaining time from Date.now(); let the timer only decide how often you re-read the clock. 
// ✕ counts ticks — drifts, and loses time in a background tab
useEffect(() => {
  const id = setInterval(() => setSeconds(s => s - 1), 1000);
  return () => clearInterval(id);
}, []);

// ✓ reads the clock — correct no matter when the callback actually runs
useEffect(() => {
  const id = setInterval(() => setNow(Date.now()), 250);
  return () => clearInterval(id);
}, []);

const remainingMs = Math.max(0, deadline - now);   // derive, don't store

The same principle covers "why did my animation stutter": setInterval(…, 16) is not a frame. Use requestAnimationFrame for anything visual, because the browser then calls you when it is actually about to paint, and it stops calling when the tab is hidden.

useEffect(() => {
  let frame = 0;

  function loop() {
    setNow(Date.now());
    frame = requestAnimationFrame(loop);   // re-schedule from inside
  }
  frame = requestAnimationFrame(loop);

  return () => cancelAnimationFrame(frame);
}, []);

Listening to things React does not own

window, document, matchMedia, the network status — none of them have JSX props, so all of them are effects. The shape never changes:

useEffect(() => {
  function handleKeyDown(event: KeyboardEvent) {
    if (event.key === 'Escape') onClose();
  }
  document.addEventListener('keydown', handleKeyDown);
  return () => document.removeEventListener('keydown', handleKeyDown);
}, [onClose]);
RuleReason
Use a JSX prop if one exists. onKeyDown on the element beats addEventListener on the node.React attaches and removes it for you, and it cannot outlive the element.
Remove the same function you added. A new inline arrow in removeEventListener removes nothing.The browser matches listeners by identity.
Keep the handler's dependencies honest, or read the latest value through a ref / Effect Event.A document listener lives across many renders — prime stale-closure territory.

Build it for real — three timing problems

Stage 1 — the tooltip that flips

src/Tooltip.tsx

import { useLayoutEffect, useRef, useState } from 'react';

type Props = { targetRect: { top: number; bottom: number; left: number } | null; children: React.ReactNode };

const GAP = 8;

export function Tooltip({ targetRect, children }: Props) {
  const ref = useRef<HTMLDivElement>(null);
  const [tooltipHeight, setTooltipHeight] = useState(0);

  useLayoutEffect(() => {
    const node = ref.current;
    if (node === null) return;
    const { height } = node.getBoundingClientRect();
    setTooltipHeight(height);            // measured before the user sees anything
  }, [children]);                        // re-measure when the content changes

  let top = 0;
  let left = 0;
  if (targetRect !== null) {
    top = targetRect.bottom + GAP;
    left = targetRect.left;
    if (top + tooltipHeight > window.innerHeight) {
      top = targetRect.top - tooltipHeight - GAP;   // no room below → flip above
    }
  }

  return (
    <div ref={ref} style={{ position: 'fixed', top, left, pointerEvents: 'none' }}>
      {children}
    </div>
  );
}

Run it twice. Hover a target near the bottom of the window and watch closely. With useLayoutEffect the tooltip appears above, once. Change the import to useEffect and the same tooltip appears below for one frame and then jumps. Nothing else in the file changes. Keep both versions open in two tabs — this is the clearest demonstration of "before paint" you will get.

The dependency that catches people [children], not []. A tooltip whose text changes is a tooltip whose height changed, and an empty array means you keep positioning by yesterday's measurement. If the content can also change size without a re-render — a font finishing loading, an image arriving — then a measurement is not enough and you want ResizeObserver.

Stage 2 — a size you can build on

Use the ChartBox effect from earlier, then render something that genuinely depends on the number: a bar chart drawn with width: size.width / data.length, or a label that switches from "compact" to "full" below 320 pixels. The point is to feel the difference between a CSS media query (about the viewport) and a measurement (about this element) — which is the whole reason container queries exist.

Stage 3 — a countdown that survives a background tab

src/Countdown.tsx

import { useEffect, useState } from 'react';

type Props = { deadline: number };   // a timestamp, not a duration

export function Countdown({ deadline }: Props) {
  const [now, setNow] = useState(() => Date.now());

  useEffect(() => {
    const id = setInterval(() => setNow(Date.now()), 250);
    return () => clearInterval(id);
  }, []);

  // Come back from another tab and re-read the clock immediately,
  // instead of waiting for the next throttled tick.
  useEffect(() => {
    function handleVisibility() {
      if (document.visibilityState === 'visible') setNow(Date.now());
    }
    document.addEventListener('visibilitychange', handleVisibility);
    return () => document.removeEventListener('visibilitychange', handleVisibility);
  }, []);

  const remaining = Math.max(0, deadline - now);
  const mm = String(Math.floor(remaining / 60000)).padStart(2, '0');
  const ss = String(Math.floor((remaining % 60000) / 1000)).padStart(2, '0');

  return <time>{mm}:{ss}</time>;
}

The test that proves it. Start a five-minute countdown, switch to another tab for two minutes, come back. The tick-counting version is roughly two minutes behind — sometimes far worse. This version is exact, because the timer never decided the answer; it only decided how often to ask.

Two more things this file quietly gets right. useState(() => Date.now()) uses the lazy initialiser, so the clock is read once rather than on every render. And remaining, mm and ss are derived — the only state is now, which is the smallest complete answer (Month 3's rule).

Extend it — three reps

  1. Make the tooltip flip sideways too. Measure the width as well and mirror it to the left of the target when it would leave the viewport. Then say why both measurements belong in the same layout effect and the same state object.
  2. Add "N items fit" to ChartBox. Divide the observed width by a fixed item width and render only that many. Then resize slowly and watch the render count in the React DevTools profiler — this is the exact place where a measurement-driven layout becomes a performance question (Month 11).
  3. Break the countdown two ways. First replace 250 with 1000 and describe the symptom precisely (it is not "less accurate" — it is a visible pause of up to one second). Then switch to counting ticks and run the background-tab test again, writing down the drift you measure. Numbers you produced yourself are the ones you remember in an interview.

Practice: read the situation, pick the move

Scenario

A colleague reports two problems in the same table component. First, on open, the first row is briefly shown at the top and then the view jumps to the previously selected row — the scroll restoration lives in a useEffect. Second, the header cell widths are computed by a useLayoutEffect inside every <Row>, which each read getBoundingClientRect() and then set a style on themselves; with 400 rows, opening the table freezes for about a second. Their proposed fix is to convert the scroll restoration to useLayoutEffect and to memoise every row with React.memo.

Work out, in order: whether the first half of their fix is right and why; why React.memo will not help the second problem at all; what the per-row layout effects should be replaced with; and which of the two problems you would fix first if you could only ship one today.

Remember this · the Feynman summary
  • The order is render → commit → layout effects → paint → effects. Everything the user must not see has to finish before paint.
  • useLayoutEffect fires before the browser repaints, and any state you set inside it is rendered and committed before the frame is drawn — so the extra render is invisible.
  • useEffect lets the browser paint first. That is why measuring in it makes a tooltip flicker: the wrong frame is real, it is just brief.
  • One test decides it: would the user see a wrong frame if this ran after paint? Yes → layout effect. No → effect.
  • It is a last resort, not a better useEffect. It blocks painting, the docs say it can hurt performance, and it does nothing on the server — which matters the moment you move to Next.js.
  • Measuring forces the browser to compute layout. Measure once and cache; never alternate reads and style writes over a long list.
  • A measurement is a fact about one moment. If the size can change while on screen, use ResizeObserver — observe in the setup, disconnect in the cleanup, and never resize the observed element from its own callback.
  • Copy ref.current into a local variable at the top of an effect, because the cleanup runs later and may find null.
  • Counting ticks is not telling time. Timers are delayed by a busy thread and throttled hard in background tabs. Store the deadline, compute from Date.now(), and let the timer only decide how often you look.
  • requestAnimationFrame for anything the eye follows; it is called right before a paint and stops when the tab is hidden. Always cancelAnimationFrame in the cleanup.
  • Outside listeners are effects: add and remove the same function, prefer a JSX prop when one exists, and prefer useSyncExternalStore for an external store of values.
  • Real use case (built & run): a tooltip that flips above the target with no flicker, a box that reports its own size through ResizeObserver, and a countdown that stayed exact after two minutes in a background tab.

If you remember one thing: useLayoutEffect buys you the frame before the user sees anything — pay for it only when a wrong frame would be visible.
