Month 6 · Lesson 3

memo, useMemo & useCallback — and when they do nothing

Three tools that all do the same thing: compare, and skip. They fail in the same way too — one value that is "always new" and the whole comparison was a waste of time.

Your win today: you can look at a memo in a real codebase and say in five seconds whether it does anything at all — and you can defend, with numbers you measured yourself, the decision not to memoise something.

These three are the most cargo-culted APIs in React. People add them because a review comment said to, remove them because a blog post said to, and almost never measure. Both moves are wrong for the same reason: memoisation is a trade, and you cannot judge a trade you have not priced.

First principle — all three cache, and all three compare with Object.is

Each of these tools does exactly two things: it remembers something from the last render, and it decides whether it may reuse it. The decision is always the same shallow identity check you have met three times already — in lesson 8 for mutation bugs, in lesson 17 for effect dependencies, in lesson 24 for context values.

ToolCachesComparesSkips
memo(Component)The component's rendered output.Every prop, shallowly, with Object.is.The render, when a parent re-rendered but the props are equal.
useMemo(fn, deps)The result of calling fn.The dependency array, item by item.Re-running an expensive calculation.
useCallback(fn, deps)The function itself.The dependency array, item by item.Nothing on its own — it makes something else able to skip.
React docs · useCallback — how is it related to useMemo? "useMemo caches the result of calling your function." … "useCallback caches the function itself. Unlike useMemo, it does not call the function you provide. Instead, it caches the function you provided so that the function itself doesn't change unless its dependencies have changed."

"If you're already familiar with useMemo, you might find it helpful to think of useCallback as this:" 
function useCallback(fn, dependencies) {
  return useMemo(() => fn, dependencies);
}

That four-line definition is worth memorising. useCallback is not a special mechanism — it is useMemo returning a function instead of computing a value. Which also explains something that surprises people:

React docs · useCallback "useCallback does not prevent creating the function. You're always creating a function (and that's fine!), but React ignores it and gives you back a cached function if nothing changed."

So useCallback never saves you the cost of making a function. Making functions is free. What it buys is a stable identity, and identity only matters to something that compares — a memo child, or a dependency array.

The failure mode all three share

The sentence to keep

"Not all memoization is effective: a single value that's 'always new' is enough to break memoization for an entire component."

That is from the docs, and it is the whole lesson in one line. memo compares all the props. One inline arrow function, one object literal, one array.filter(...) written in the JSX, and the comparison fails forever. The component still gets wrapped, the check still runs, and it never once skips a render. A useless memo is not neutral — it is a cost plus a lie. Every future reader believes the child is protected.

memo's four caveats — read them once, quote them forever

React docs · memo — Caveats "React may still re-render it: memoization is a performance optimization, not a guarantee."
"Even when a component is memoized, it will still re-render when its own state changes."
"Even when a component is memoized, it will still re-render when a context that it's using changes."
"Memoization only has to do with props that are passed to the component from its parent."

The first caveat is the one that stops bugs: if your code only works with memo, your code is broken. React reserves the right to render anyway. A component that counts its own renders, or writes to a module variable during render, or assumes an effect will not re-run, will fail the day React decides differently. Memoisation is never allowed to be load-bearing for correctness.

The broken trio you will meet in every codebase

src/RowList.tsx — three memoised children, none of them working

const Row = memo(function Row({ item, onSelect, style }: RowProps) {
  console.count('render Row');
  return <li style={style} onClick={() => onSelect(item.id)}>{item.name}</li>;
});

export function RowList({ items }: { items: Item[] }) {
  const [query, setQuery] = useState('');

  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <ul>
        {items.filter(i => i.name.includes(query)).map(item => (
          <Row
            key={item.id}
            item={item}
            onSelect={(id) => console.log(id)}   // 🔴 new function per row per render
            style={{ padding: 4 }}               // 🔴 new object per row per render
          />
        ))}
      </ul>
    </>
  );
}

Every keystroke: every Row re-renders. The memo ran a comparison for each one, found onSelect different, and rendered anyway. You paid for the gate and walked around it.

src/RowList.tsx — the version where memo earns its keep

const ROW_STYLE = { padding: 4 };          // module scope: created once, ever

export function RowList({ items }: { items: Item[] }) {
  const [query, setQuery] = useState('');

  const handleSelect = useCallback((id: string) => {
    console.log(id);
  }, []);                                  // [] is honest — it closes over nothing

  const visible = useMemo(
    () => items.filter(i => i.name.includes(query)),
    [items, query],
  );

  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <ul>
        {visible.map(item => (
          <Row key={item.id} item={item} onSelect={handleSelect} style={ROW_STYLE} />
        ))}
      </ul>
    </>
  );
}

Three separate leaks, three different plugs, and notice that one of them needed no hook at all. A constant object belongs at module scope. Reaching for useMemo to stabilise a literal that never depends on anything is a hook you will maintain forever for no reason.

The leak that survives a review <Row item={item} /> looks safe, and is — item comes from the items array, so it is the same object each render as long as nobody rebuilds the array. The day someone writes items={data.map(d => ({ ...d, label: d.name }))} in the parent, every item becomes a fresh object and all the memoisation below silently dies. Memoisation is a whole-chain property: it only works if every link holds.

Measure. The docs even tell you how.

Before you memoise a calculation, find out whether it is expensive. The threshold in the docs is lower than most people guess, and so is the typical answer.

React docs · useMemo — how to tell if a calculation is expensive? "In general, unless you're creating or looping over thousands of objects, it's probably not expensive." 
console.time('filter array');
const visibleTodos = filterTodos(todos, tab);
console.timeEnd('filter array');
"You will then see logs like filter array: 0.15ms in your console. If the overall logged time adds up to a significant amount (say, 1ms or more), it might make sense to memoize that calculation."

"useMemo won't make the first render faster. It only helps you skip unnecessary work on updates."

"Keep in mind that your machine is probably faster than your users' so it's a good idea to test the performance with an artificial slowdown." … "measuring performance in development will not give you the most accurate results. (For example, when Strict Mode is on, you will see each component render twice rather than once.)"

Four things to take from that. 1ms is the bar. Thousands of objects is the scale. The first render never gets faster — memoisation is purely about updates. And a number you measured on your laptop in a dev build is not a number: use Chrome's CPU throttling and a production build before you believe it.

The measuring routine

  1. React DevTools → Highlight updates when components render. Perform the interaction. If nothing you care about flashes, stop — there is no problem.
  2. Profiler tab → record the interaction → look at the committed renders and their durations. This tells you which component is slow, which is a different question from which one re-renders often.
  3. console.time around the suspect calculation. Under 1ms, walk away.
  4. Apply one change. Re-measure the same way. If the number did not move, revert it — an optimisation that does not optimise is just code.

Before you memoise — the five documented alternatives

React docs · useMemo & memo — "you can make a lot of memoization unnecessary" "1. When a component visually wraps other components, let it accept JSX as children. This way, when the wrapper component updates its own state, React knows that its children don't need to re-render.
2. Prefer local state and don't lift state up any further than necessary. For example, don't keep transient state like forms and whether an item is hovered at the top of your tree or in a global state library.
3. Keep your rendering logic pure. If re-rendering a component causes a problem or produces some noticeable visual artifact, it's a bug in your component! Fix the bug instead of adding memoization.
4. Avoid unnecessary Effects that update state. Most performance problems in React apps are caused by chains of updates originating from Effects that cause your components to render over and over.
5. Try to remove unnecessary dependencies from your Effects."

You have already built all five. Number 1 and number 2 are lesson 23's two free fixes. Number 3 is Month 1. Numbers 4 and 5 are Month 4 — lessons 16 and 17 in one sentence each. Month 6 does not introduce performance work; it collects it.

And read number 4 again: most performance problems come from effect chains. Not from missing memo. If you spent Month 4 deleting effects, you have already done more for this app's speed than any amount of memoisation will.

When it is worth it

React docs · useMemo — should you add it everywhere? "Optimizing with useMemo is only valuable in a few cases:
• The calculation you're putting in useMemo is noticeably slow, and its dependencies rarely change.
• You pass it as a prop to a component wrapped in memo. You want to skip re-rendering if the value hasn't changed.
• The value you're passing is later used as a dependency of some Hook."

"There is no benefit to wrapping a calculation in useMemo in other cases. There is no significant harm to doing that either, so some teams choose to not think about individual cases, and memoize as much as possible. The downside of this approach is that code becomes less readable."
React docs · memo — should you add it everywhere? "If your app is like a documentation site with coarse interactions (replacing pages/sections), memoization is usually unnecessary. If your app is like a drawing editor with granular interactions (moving shapes), memoization is very helpful."

"memo is only valuable when your component re-renders often with the same exact props, and its re-rendering logic is expensive." … "If there is no perceptible lag when your component re-renders, memo is unnecessary."

That "documentation site versus drawing editor" line is the most useful sentence in the whole subject, because it moves the question from your component to your product. A settings page does not need memoisation. A canvas where dragging a node updates sixty times a second does.

The case that is not a performance optimisation at all

There is one use of useMemo that changes behaviour, and you already met the bug it fixes. Lesson 17, the chat that disconnected on every keystroke:

function ChatRoom({ roomId }: { roomId: string }) {
  const [message, setMessage] = useState('');

  const options = { serverUrl: 'https://localhost:1234', roomId };  // new object every render

  useEffect(() => {
    const conn = createConnection(options);
    conn.connect();
    return () => conn.disconnect();
  }, [options]);                    // honest array, and it fires on every keystroke

Here a memo is not saving milliseconds — it is deciding whether the socket survives typing. The docs' third bullet above covers it ("used as a dependency of some Hook"), and the honest description is: when identity feeds a dependency array, memoisation stops being cosmetic. Lesson 17 gave you two better fixes for this exact case — move the object inside the effect, or pass primitives — and those are still better, because they remove the dependency instead of stabilising it. But when the value must exist outside the effect and must be stable, useMemo is the tool, and it is not optional.

The same is true of a context value (lesson 24), and of an object you build once and reuse:

// Building an Intl formatter is genuinely not free, and it never changes.
const fmt = useMemo(
  () => new Intl.NumberFormat('en-AU', { style: 'currency', currency: 'AUD' }),
  [],
);
But do not use useMemo as storage "React will not throw away the cached value unless there is a specific reason to do that" — and then the docs list several: editing the file in development, the component suspending during the initial mount, and possibly more in future. So if losing the value would be a bug rather than a slowdown, you need useState with a lazy initialiser or a useRef, not useMemo. Lesson 19's rule, restated.

Build it for real — five stages, measured at each one

A list of 4,000 rows, a filter box, and a "selected" highlight. The goal is not to make it fast — it is to find out which of the five changes actually did anything, and to end up with the smallest version that works.

src/data.ts

export type Row = { id: string; name: string; owner: string };

export const ROWS: Row[] = Array.from({ length: 4000 }, (_, i) => ({
  id: String(i),
  name: `Task ${i}`,
  owner: ['ana', 'ben', 'cleo'][i % 3],
}));

Stage 0 — instrument before you touch anything

function RowItem({ row, selected, onSelect }: RowItemProps) {
  console.count('render RowItem');
  return (
    <li onClick={() => onSelect(row.id)} className={selected ? 'sel' : ''}>
      {row.name} — {row.owner}
    </li>
  );
}

export default function TaskList() {
  const [query, setQuery] = useState('');
  const [selectedId, setSelectedId] = useState<string | null>(null);

  console.time('filter');
  const visible = ROWS.filter(r => r.name.includes(query));
  console.timeEnd('filter');

  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <ul>
        {visible.map(row => (
          <RowItem
            key={row.id}
            row={row}
            selected={row.id === selectedId}
            onSelect={setSelectedId}
          />
        ))}
      </ul>
    </>
  );
}

Type one character and read both numbers. The filter timing will almost certainly be well under 1ms — 4,000 string checks is nothing. The render RowItem count jumps by thousands. Write both numbers down. They tell you the diagnosis before you have changed a line: this is a many components problem, not an expensive calculation problem, so the useMemo everyone reaches for first is the wrong tool.

Stage 1 — memo alone (and why nothing improves)

const RowItem = memo(function RowItem({ row, selected, onSelect }: RowItemProps) {
  console.count('render RowItem');
  // …same body…
});

Measure again. The count barely moves. onSelect={setSelectedId} is actually stable — state setters are — but selected={row.id === selectedId} changes for two rows when the selection changes, and row is stable, so the props are mostly equal… and yet the count is still enormous while typing. Why?

Because typing changes visible, so a different set of rows is rendered. memo can skip a row that is rendered again with the same props; it cannot skip a row that is newly mounted because it just entered the filter, and it cannot help with 4,000 elements existing in the first place. That is the real lesson of this stage: memo reduces re-renders, and your problem might be mounts and element count.

Stage 2 — break it on purpose to see the gate fail

<RowItem
  key={row.id}
  row={row}
  selected={row.id === selectedId}
  onSelect={(id) => setSelectedId(id)}      // 🔴 inline arrow
/>

Now click one row. Before this change: two rows re-render (the old selection and the new one). After it: all of them, because every onSelect is a fresh function. Same visible behaviour, thousands of extra renders, and the diff is nine characters. Revert it, and remember the shape — this is the single most common way memoisation is lost in real pull requests.

Stage 3 — useCallback when the handler needs an argument

Passing setSelectedId straight through worked because the signature happened to match. It usually does not:

const handleSelect = useCallback((id: string) => {
  setSelectedId(current => (current === id ? null : id));   // toggle
}, []);                                                     // [] honest: updater form reads no state

The updater form is what keeps the array empty, exactly as in lesson 17. If you had written setSelectedId(selectedId === id ? null : id) you would need [selectedId], the function would change on every selection, and memo would break for every row on every click. The dependency array is a fact — so the way to get a short one is to need less, not to write less.

Stage 4 — the structural fix that makes the rest nearly pointless

function FilterBox({ onCommit }: { onCommit: (q: string) => void }) {
  const [text, setText] = useState('');       // keystrokes live HERE now
  return (
    <input
      value={text}
      onChange={e => { setText(e.target.value); onCommit(e.target.value); }}
    />
  );
}

That alone is not enough — onCommit still lifts the query up. The real move is the one from lesson 23: decide what the smallest subtree is that must react to a keystroke, and put the state there. Two honest options for this app:

OptionWhat it changesCost
Keep query local to a <TaskList> that owns the input and the listNothing outside that component re-renders. Inside, the list still redraws — because it must.Free. This is stage 0 already, if the rest of the page is outside.
Render fewer rows — paginate, or virtualise with @tanstack/react-virtualThirty <li> exist instead of 4,000. Renders, reconciliation and DOM nodes all drop by two orders of magnitude.A dependency and some scroll handling. This is the actual fix.

Measure the virtualised version. The render RowItem count per keystroke goes from thousands to about thirty, and it does so with memo, useMemo and useCallback all removed. That is the honest ending: the winning move was not to skip work more cleverly, it was to have less work.

The React Compiler — and what it does not fix

React docs · React Compiler React Compiler "automatically optimizes your React application by handling memoization for you, eliminating the need for manual useMemo, useCallback, and React.memo." It works at build time by "skipping cascading re-renders" and "skipping expensive calculations".

"React is often fast enough without optimization, but sometimes you need to manually memoize components and values to keep your app responsive. This manual memoization is tedious, easy to get wrong, and adds extra code to maintain. React Compiler does this optimization automatically for you."

"React Compiler is now stable and has been tested extensively in production" — and has "been used in production at companies like Meta", with support for React 17, 18 and 19.

So is this lesson obsolete? No, and the docs are careful about exactly why:

React docs · React Compiler — existing memoisation For new code, "rely on the compiler for memoization and using useMemo/useCallback where needed to achieve precise control". For existing code, "we recommend either leaving existing memoization in place (removing it can change compilation output) or carefully testing before removing the memoization". The hooks remain useful as "escape hatches to provide control over which values are memoized", particularly for effect dependencies.
The compiler fixesThe compiler does not fix
Forgetting useCallback on a handler passed to a memoised child.State living in the wrong component. It cannot move your useState down a level.
An inline object literal as a context value.A context value that genuinely changed — every consumer still wakes, by design.
Recomputing a derived list on every render.4,000 elements on screen. Fewer renders of too many nodes is still too many nodes.
The maintenance cost of hand-written memoisation.Effect chains that cause cascading updates (the docs' "most performance problems").
Human error in dependency arrays for memoisation.Impure components — it requires your code to follow the Rules of React.

The interview line: "The compiler removes hand-written memoisation, not bad state placement." Everything in lesson 23 still applies with the compiler on; only lesson 25's manual work goes away.

Extend it — three reps

  1. Find a useless memo. In any codebase you have, search for memo( and for each hit list the props. Mark every prop that is created during render — an arrow function, an object literal, a .map or .filter, a template string building an array. If any prop is marked, that memo currently does nothing. Report a count, not an opinion.
  2. Prove the 1ms rule to yourself. Wrap the stage-0 filter in console.time and grow ROWS — 4,000, then 40,000, then 400,000. Write down the first size at which the filter crosses 1ms. That number is your personal threshold for "is this expensive", and it is much larger than you expect.
  3. Make a memoisation chain fail from three links away. Keep memo(RowItem), keep useCallback, keep everything — then in the parent of TaskList pass rows={ROWS.map(r => ({ ...r }))}. Watch every row re-render again. Say the rule out loud: memoisation is a property of the whole chain, and any link can break it.

Practice: read the situation, pick the move

Scenario

A pull request adds 34 useCallbacks, 12 useMemos and memo on 19 components across a checkout flow. The description says "reduces re-renders by 60%" with no methodology. Reading it, you find: three of the useMemos wrap items.length; one useMemo had its dependency array trimmed from [items, taxRate] to [items] "because it kept recalculating"; six useCallbacks wrap handlers passed directly to <button onClick>; and one memo is on a component that receives children. Separately, the flow has a useEffect that recalculates a total and writes it to state whenever the cart changes, and a single CheckoutContext whose value is an inline object holding the cart, the shipping form fields, and eleven functions.

Work out, in order: which of the four listed memoisation problems is a correctness bug rather than a waste; why the six useCallbacks on DOM handlers cannot help; what is really causing most of the re-renders in this flow, given the last sentence; the two changes you would ask for instead of all 65; and what you would say about the "60%" claim without being unkind.

Remember this · the Feynman summary
  • All three do the same two things: cache something from the last render, and compare with Object.is to decide whether to reuse it.
  • memo caches output and compares props; useMemo caches a result; useCallback caches a function. useCallback(fn, deps) is just useMemo(() => fn, deps).
  • useCallback does not stop the function being created. Creating functions is free — what you are buying is a stable identity, which only matters to something that compares.
  • One always-new value breaks memoisation for a whole component. An inline arrow, an object literal, a .filter() in the JSX — the gate runs and never closes.
  • memo only knows about props from the parent. Its own state re-renders it, and a context it reads re-renders it. Both documented, both interview questions.
  • Memoisation is never load-bearing. "A performance optimization, not a guarantee" — if the code breaks without it, the code is already broken.
  • Measure with console.time. Under about 1ms, do not memoise. Under thousands of objects, it is probably not expensive. And it never makes the first render faster.
  • Development numbers lie — Strict Mode double-renders and dev builds are slow. Compare before and after, on a throttled CPU, in a production build.
  • Five documented alternatives come first: take JSX as children, keep state local, keep render pure, delete effects that set state, remove effect dependencies. Most performance problems are effect chains, not missing memo.
  • Fewer nodes beats fewer renders. Virtualising 4,000 rows down to thirty beat every hook in the build — and let all of them be deleted.
  • Two places where memoising is structural, not cosmetic: a context value, and a value that feeds a dependency array. There it changes behaviour, not speed.
  • useMemo is not storage. React may throw the cache away, so anything you cannot afford to lose belongs in useState with a lazy initialiser, or a ref.
  • Constants belong at module scope, not in a useMemo with an empty array.
  • React Compiler is stable and automates all three, and the docs say to leave existing memoisation in place or test carefully before removing it. It fixes hand-written memoisation — not state in the wrong place, not too many nodes, not effect chains.
  • Real use case (built & run): a 4,000-row list where the measured filter was under 1ms, a nine-character inline arrow undid every memo, and the change that actually worked deleted all three hooks and rendered thirty rows instead.

If you remember one thing: memoisation only pays when the skipped work is genuinely expensive and every input stays identical — measure the first, and audit the props for the second.
