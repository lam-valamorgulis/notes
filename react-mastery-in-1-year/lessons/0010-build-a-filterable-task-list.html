Month 2 · Lesson 4 · The real build

Build it — a filterable task list

Everything from Month 2 in one small app: controlled inputs, immutable updates, lifted state, typed callbacks, and keys.

Your win today: a working app you can rebuild from memory in about twenty minutes — add, edit, complete, delete, search, and filter. It is the most-asked live-coding exercise in front-end interviews, and every line of it is one of Month 2's ideas doing its job.

Three lessons gave you three habits: state owns every input's value, never edit state in place, and state lives above everyone who reads it. This lesson puts them together, and it starts where every real build should start — on paper, before any code.

The plan — decide the state before you type

The feature list: add a task, tick it off, rename it, delete it, search by text, and filter by All / Active / Done, with a live count.

Now the only question that matters. Every value on that screen is one of three things:

ValueState, derived, or constant?Lives where — and why
The list of tasksState — the source of everythingApp. The list, the counts, and the filters all read it.
Search textState — the user types itApp. The filter bar shows it; the list is filtered by it.
Status filter (all / active / done)State — the user picks itApp, same reason.
The new-task text boxState — but privateTaskForm. Nobody else reads a half-typed title, so it stays local.
"Am I editing this row?" + the edit draftState — but privateTaskRow. One row's edit mode is nobody else's business.
The visible tasksDerivedComputed in App during render from tasks + query + filter.
Active count, done countDerivedComputed from tasks. Storing them would be a second truth to keep in sync.
The three filter labelsConstantA plain array outside the component.

That table is the architecture. Two things fall out of it before you write a line:

  • Three pieces of state in App, because more than one component reads each of them.
  • Two pieces of state kept local, because nobody else reads them. Local state is a deliberate choice here, not laziness.

Build it for real — five small files

Real projects split components into files. Create these inside src/, in this order.

src/types.ts — the shape of the data, in one place

export interface Task {
  id: string;
  title: string;
  done: boolean;
}

export type Status = 'all' | 'active' | 'done';

src/TaskForm.tsx — a controlled input with private state

import { useState } from 'react';

interface TaskFormProps {
  onAdd: (title: string) => void;      // the only thing the parent gives it
}

export function TaskForm({ onAdd }: TaskFormProps) {
  // Local on purpose: nobody else needs a half-typed title.
  const [draft, setDraft] = useState('');

  function handleSubmit(e: React.FormEvent<HTMLFormElement>) {
    e.preventDefault();                // keep the page — don't let the browser submit
    const title = draft.trim();
    if (!title) return;                // guard: no empty tasks
    onAdd(title);                       // report up; App owns the list
    setDraft('');                       // clear the box for the next one
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        value={draft}
        placeholder="What needs doing?"
        onChange={(e) => setDraft(e.target.value)}
        aria-label="New task title"
      />
      <button type="submit" disabled={draft.trim() === ''}>Add</button>
    </form>
  );
}

src/FilterBar.tsx — fully controlled, owns nothing

import type { Status } from './types';

const FILTERS: { value: Status; label: string }[] = [
  { value: 'all',    label: 'All'    },
  { value: 'active', label: 'Active' },
  { value: 'done',   label: 'Done'   },
];

interface FilterBarProps {
  query: string;
  status: Status;
  onQueryChange: (next: string) => void;
  onStatusChange: (next: Status) => void;
}

export function FilterBar({ query, status, onQueryChange, onStatusChange }: FilterBarProps) {
  return (
    <div>
      <input
        type="search"
        value={query}
        placeholder="Search tasks…"
        onChange={(e) => onQueryChange(e.target.value)}
        aria-label="Search tasks"
      />

      {FILTERS.map(f => (
        <button
          key={f.value}
          onClick={() => onStatusChange(f.value)}
          aria-pressed={status === f.value}
        >
          {f.label}
        </button>
      ))}
    </div>
  );
}

src/TaskRow.tsx — the busiest component: two local states, three callbacks

import { useState } from 'react';
import type { Task } from './types';

interface TaskRowProps {
  task: Task;
  onToggle: (id: string) => void;
  onRename: (id: string, title: string) => void;
  onDelete: (id: string) => void;
}

export function TaskRow({ task, onToggle, onRename, onDelete }: TaskRowProps) {
  // Both local: one row's edit mode is nobody else's business.
  const [isEditing, setIsEditing] = useState(false);
  const [draft, setDraft] = useState(task.title);

  function startEditing() {
    setDraft(task.title);      // seed the draft AT THE MOMENT editing starts
    setIsEditing(true);
  }

  function handleSave(e: React.FormEvent<HTMLFormElement>) {
    e.preventDefault();
    const title = draft.trim();
    if (title) onRename(task.id, title);   // App owns the list, so App renames
    setIsEditing(false);
  }

  if (isEditing) {
    return (
      <li>
        <form onSubmit={handleSave}>
          <input
            value={draft}
            onChange={(e) => setDraft(e.target.value)}
            onKeyDown={(e) => { if (e.key === 'Escape') setIsEditing(false); }}
            autoFocus
            aria-label="Edit task title"
          />
          <button type="submit">Save</button>
          <button type="button" onClick={() => setIsEditing(false)}>Cancel</button>
        </form>
      </li>
    );
  }

  return (
    /* clicking the row toggles it — so inner buttons must stop the event */
    <li onClick={() => onToggle(task.id)}>
      <input
        type="checkbox"
        checked={task.done}
        onChange={() => onToggle(task.id)}
        onClick={(e) => e.stopPropagation()}   // else the row toggles it back
        aria-label={`Mark "${task.title}" as done`}
      />
      <span style={{ textDecoration: task.done ? 'line-through' : 'none' }}>
        {task.title}
      </span>
      <button onClick={(e) => { e.stopPropagation(); startEditing(); }}>Edit</button>
      <button onClick={(e) => { e.stopPropagation(); onDelete(task.id); }}>✕</button>
    </li>
  );
}

src/TaskList.tsx — a list, a key, and an empty state

import type { Task } from './types';
import { TaskRow } from './TaskRow';

interface TaskListProps {
  tasks: Task[];
  onToggle: (id: string) => void;
  onRename: (id: string, title: string) => void;
  onDelete: (id: string) => void;
}

export function TaskList({ tasks, onToggle, onRename, onDelete }: TaskListProps) {
  if (tasks.length === 0) {
    return <p>Nothing here. Change the filter, or add a task.</p>;
  }

  return (
    <ul>
      {tasks.map(task => (
        <TaskRow
          key={task.id}            // identity — never the array index
          task={task}
          onToggle={onToggle}
          onRename={onRename}
          onDelete={onDelete}
        />
      ))}
    </ul>
  );
}

src/App.tsx — the owner: all shared state, all immutable updates

import { useState } from 'react';
import type { Status, Task } from './types';
import { TaskForm } from './TaskForm';
import { FilterBar } from './FilterBar';
import { TaskList } from './TaskList';

const SEED: Task[] = [
  { id: 't1', title: 'Read "Updating Arrays in State"', done: true  },
  { id: 't2', title: 'Rebuild this app from memory',    done: false },
  { id: 't3', title: 'Say the immutability answer out loud', done: false },
];

export default function App() {
  // three pieces of shared state — everything else is derived
  const [tasks, setTasks] = useState<Task[]>(SEED);
  const [query, setQuery] = useState('');
  const [status, setStatus] = useState<Status>('all');

  // ---- the four updates. every one makes a NEW array. ----

  function handleAdd(title: string) {
    setTasks(prev => [
      ...prev,
      { id: crypto.randomUUID(), title, done: false },
    ]);
  }

  function handleToggle(id: string) {
    setTasks(prev => prev.map(t =>
      t.id === id ? { ...t, done: !t.done } : t
    ));
  }

  function handleRename(id: string, title: string) {
    setTasks(prev => prev.map(t =>
      t.id === id ? { ...t, title } : t
    ));
  }

  function handleDelete(id: string) {
    setTasks(prev => prev.filter(t => t.id !== id));
  }

  // ---- derived values: recomputed every render, never stored ----

  const needle = query.trim().toLowerCase();

  const visible = tasks.filter(t => {
    const matchesText = t.title.toLowerCase().includes(needle);
    const matchesStatus =
      status === 'all' ? true :
      status === 'done' ? t.done :
      !t.done;
    return matchesText && matchesStatus;
  });

  const doneCount = tasks.filter(t => t.done).length;
  const activeCount = tasks.length - doneCount;

  return (
    <main>
      <h1>Tasks</h1>
      <p>{activeCount} active · {doneCount} done · showing {visible.length}</p>

      <TaskForm onAdd={handleAdd} />

      <FilterBar
        query={query}
        status={status}
        onQueryChange={setQuery}
        onStatusChange={setStatus}
      />

      <TaskList
        tasks={visible}
        onToggle={handleToggle}
        onRename={handleRename}
        onDelete={handleDelete}
      />
    </main>
  );
}

Run npm run dev. It works, and it is about 200 lines with no library beyond React.

The walkthrough — every Month-2 idea, mapped

Read down this table with the code open. This is the part that turns a working app into knowledge you can say out loud.

IdeaWhere it isWhy it had to be that way
Controlled input value={draft} + onChange in TaskForm; value={query} in FilterBar The Add button must disable itself while the box is empty, and the list must filter on every keystroke. Both need the value in state now.
Form, not a click handler <form onSubmit={handleSubmit}> + e.preventDefault() Enter submits, and screen readers announce a form. preventDefault stops the browser reloading the page.
stopPropagation The checkbox, Edit, and ✕ buttons inside TaskRow The row itself is clickable. Without it, deleting also toggles, and the checkbox toggles twice — once for itself, once for the row.
Immutable add [...prev, newTask] push would keep the same array identity, so React would see no change and skip the render.
Immutable update prev.map(t => t.id === id ? { ...t, done: !t.done } : t) map replaces one item and returns the rest untouched — so unchanged rows keep their identity.
Immutable delete prev.filter(t => t.id !== id) filter already returns a new array. splice would mutate.
Updater form Every setter uses prev => Each new list is built from the previous one. The updater form is immune to stale snapshots and to batching.
Lifted state tasks, query, status in App FilterBar shows the query, TaskList is filtered by it, and the header counts read the tasks. More than one reader means it goes to the common parent.
Local state kept local draft in TaskForm; isEditing and draft in TaskRow Nobody else reads them. Lifting them would re-render the whole page on every keystroke and buy nothing.
Typed callback props onAdd: (title: string) => void, onRename: (id: string, title: string) => void The type is the contract between parent and child, enforced by the compiler.
Derived, not stored visible, doneCount, activeCount Anything computable from state must be computed. A stored copy is a second truth that goes stale.
Keys by id key={task.id} in TaskList Rows carry their own local state (edit mode). With an index key, deleting row 1 would hand row 1's state to the old row 2.
A deliberate draft copy setDraft(task.title) inside startEditing This is not the useState(props.x) bug: the draft is re-seeded by an event, so it is never stale when editing begins.
Type-only import import type { Task } from './types' Types vanish at build time. import type says "this is erased", so no runtime import is generated.
Look at what is not here No useEffect. No state library. No useMemo. A filterable list with live search needs none of those, and reaching for them early is the most common way people make React harder than it is. Effects arrive in Month 4 — for talking to the outside world, which this app never does.

Extend it — three reps to make it yours

Do these without looking at the code above. Each one is a small trap.

  1. "Clear completed" button. One line in the parent: setTasks(prev => prev.filter(t => !t.done)). Then make the button disappear when doneCount === 0 — derived, not a new piece of state.
  2. "Toggle all" checkbox. Flip every task to match. setTasks(prev => prev.map(t => ({ ...t, done: nextValue }))). Watch the parentheses around the object — without them the arrow body is read as a block.
  3. Sort A→Z. The trap you were warned about: setTasks(prev => [...prev].sort((a, b) => a.title.localeCompare(b.title))). Write it without the spread first, watch nothing happen, then fix it. Feeling that bug once is worth more than reading it three times.

One more, harder: give each task a priority: 'low' | 'high' and a <select> per row. You will need the as cast on e.target.value, an onClick with stopPropagation, and the map-plus-spread update. If you can do that one unaided, Month 2 is finished.

Practice: read the situation, pick the move

Scenario

A teammate refactors this app "for performance". They add const [visible, setVisible] = useState(tasks) and update it inside every filter handler, so the filtering runs once per change instead of once per render. Search and the filter buttons work. But now renaming a task shows the old title until you touch a filter, and deleting one leaves a ghost row.

Explain what they created, why the symptoms look random, and what you would do instead.

Remember this · the Feynman summary
  • Plan the state before the components. Sort every value on screen into state, derived, or constant — that table is the architecture.
  • Shared state goes up, private state stays down. tasks, query, and status have several readers; a half-typed title and one row's edit mode have none.
  • Children report, parents decide. Rows call onToggle / onRename / onDelete; only App ever changes the list.
  • Four immutable recipes cover a whole CRUD app: add [...prev, x] · update map + spread · delete filter · reorder or sort on a copy.
  • Every setter used the updater form prev =>, because each new list is built from the last one.
  • Derived beats stored. visible, activeCount, and doneCount are recomputed each render — storing them creates a second truth that goes stale.
  • Keys are identity. Rows hold their own state, so an index key would hand a deleted row's edit mode to its neighbour.
  • Seed a draft from an event, never from useState(props.x) — startEditing re-seeds the draft at the moment editing begins.
  • Use a real form with onSubmit and preventDefault, and stopPropagation on buttons inside a clickable row.
  • No effects, no memo, no state library — a filterable searchable list needs none of them.
  • Real use case (built & run): a five-component task app — add, toggle, inline rename, delete, live text search, and a status filter with live counts.

If you remember one thing: decide what is state, what is derived, and who owns it — then the code almost writes itself.
