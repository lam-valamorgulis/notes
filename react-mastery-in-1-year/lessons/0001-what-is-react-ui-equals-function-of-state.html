Month 1 · Lesson 1 · The render model

What is React, really?

The first idea the whole year rests on — your screen is a function of your data.

Your win today: you'll be able to explain, in plain words, (1) what React actually is and what problem it solves, (2) what JSX really is under the surface, and (3) the one equation the rest of the year builds on — UI = f(state). You'll also write your first typed component and understand why you need a build tool at all.
How we learn here We build every idea from first principles — we start from the simplest true thing and add one step at a time, so nothing is magic. Every lesson has a "Build it for real" step where you run actual React code. At the end, the "Remember this" box is a Feynman summary: the whole lesson said again in words simple enough to teach a friend. If you can say that box out loud, you own the lesson. All code is TypeScript, the way real teams write React.

Start from zero — what actually puts things on a screen?

A web page is a tree of objects called the DOM (Document Object Model). Each heading, button, and paragraph is a node in that tree. When you write plain JavaScript, the only way to change what the user sees is to reach into that tree and edit it by hand: create a node, set its text, attach it, remove it later.

That works for a small page. But real apps have data that changes — a counter goes up, a list gets filtered, a form shows an error. Every time the data changes, you are responsible for finding the exact DOM nodes affected and updating each one to match. Here is that job in vanilla JavaScript:

// The data our UI is supposed to reflect:
let count = 0;

const label = document.getElementById('label');
const button = document.getElementById('btn');

button.addEventListener('click', () => {
  count = count + 1;              // 1. change the data
  label.textContent = `Count: ${count}`;   // 2. now MANUALLY sync the DOM to match
});

Notice the trap: there are two things — the data (count) and the screen (label.textContent) — and you must keep them in sync, everywhere, forever. Miss one spot and the screen shows a lie. In a big app with dozens of values feeding dozens of nodes, this hand-syncing is where most UI bugs are born. This style is called imperative: you write the step-by-step instructions to mutate the DOM.

The problem, in one line

Keeping the screen in sync with changing data by hand is the hardest, buggiest part of building a UI — and it gets worse as the app grows.

React's answer — describe, don't mutate

React flips the job around. Instead of writing instructions to change the DOM, you write a function that returns a description of what the UI should look like for the current data. When the data changes, you don't touch the DOM — you just let React call your function again with the new data, and React figures out the minimal DOM changes for you. This style is called declarative: you describe the what, not the how.

That is the whole idea of React in one equation — memorise it, because every hard part later is a consequence of it:

Say this one out loud

UI = f(state). Your interface is the return value of a function of your data. You never edit the screen directly — you change the data, and React re-computes the screen to match.

What a component is — just a function that returns UI

The building block of React is the component: a JavaScript function that takes some data and returns a description of UI. That's it. No class, no magic — a function, in and out.

// A component is a function. Data goes in, a UI description comes out.
function Greeting() {
  return <h1>Hello, React</h1>;
}

The thing that looks like HTML inside the function is JSX. And this is the single most clarifying fact for a beginner: JSX is not HTML, and it is not a string. It is a shorthand the build tool rewrites into a normal function call. These two are exactly the same code:

// What you write (JSX):
<h1 className="title">Hello, React</h1>

// What it compiles to — a plain function call:
React.createElement('h1', { className: 'title' }, 'Hello, React');

And React.createElement(...) just returns a plain JavaScript object — a lightweight description like { type: 'h1', props: { className: 'title', children: 'Hello, React' } }. That object is called a React element. It is not a real DOM node — it's a cheap description of one. Your component returns these descriptions; React reads them and updates the real DOM. So "JSX" is not a mystery: it's function calls that build description objects.

Why this matters Because JSX is just JavaScript expressions, everything you know about JavaScript still works inside it — variables, .map(), ternaries, function calls. There is no new "template language" to learn. When JSX confuses you later, mentally rewrite it as createElement calls and it becomes obvious.

See it yourself — React with zero tooling

To prove a component really is "just a function returning a description," let's run React with no build step at all — straight from a CDN in a single HTML file. Save this as proof.html and open it in a browser:

proof.html

<div id="root"></div>

<script src="https://unpkg.com/react@18/umd/react.development.js"></script>
<script src="https://unpkg.com/react-dom@18/umd/react-dom.development.js"></script>
<script src="https://unpkg.com/@babel/standalone/babel.min.js"></script>

<script type="text/babel">
  function Greeting() {
    return <h1>Hello, React — no build tool</h1>;
  }

  // Ask React to render our component's description into the real DOM:
  const root = ReactDOM.createRoot(document.getElementById('root'));
  root.render(<Greeting />);
</script>

Open it — you see your heading. No install, no terminal. This strips React down to its truth: a function returns a description (<Greeting />), and root.render hands it to React to put on screen. (The @babel/standalone script is what turns JSX into createElement calls in the browser — fine for a demo, far too slow for a real app.)

Why you actually need a build tool — and where TypeScript comes in

That CDN demo works, but no real project ships that way. Two reasons force a proper setup, and the second is why this course is in TypeScript:

  1. Speed & tooling. Compiling JSX in the browser on every load is slow. A build tool (we use Vite) compiles your JSX once, ahead of time, and gives you instant reloads while you code.
  2. TypeScript can't run in a browser at all. A browser has no idea what name: string means. Types are erased at build time — a compiler checks them, then strips them out, leaving plain JavaScript for the browser. So the moment you want types (and you do — they catch a whole class of bugs before you run the code), you need a build step by definition.
The first-principle to hold

TypeScript is a compile-time tool. It never runs in the browser. It reads your types, catches mistakes, then disappears — the browser only ever sees ordinary JavaScript.

So from here on, every example uses a real project. Create one in about ten seconds:

# Scaffold a React + TypeScript app with Vite, then start it:
npm create vite@latest my-app -- --template react-ts
cd my-app
npm install
npm run dev        # open the printed http://localhost:5173

The react-ts template gives you a project where files end in .tsx ("TypeScript + JSX"). That x is the whole reason the extension isn't just .ts: it tells the compiler "this file also contains JSX."

Build it for real — your first typed component

Let's build something with actual data flowing in. In React, the data a component receives from its parent is called props (short for "properties"). A component is a function; props are its arguments. With TypeScript, we describe the shape of those arguments so the compiler catches a wrong or missing prop before the app even runs.

Replace src/App.tsx with this:

src/App.tsx

// 1. Describe the shape of this component's props.
type GreetingProps = {
  name: string;
  role: string;
};

// 2. The component is a function; its argument is the props object.
function Greeting({ name, role }: GreetingProps) {
  return (
    <section>
      <h1>Hello, {name}</h1>
      <p>Your role: {role}</p>
    </section>
  );
}

// 3. The same function, called with different data, produces different UI.
export default function App() {
  return (
    <main>
      <Greeting name="Ada" role="Engineer" />
      <Greeting name="Grace" role="Admiral" />
    </main>
  );
}

Three things to feel here, because they are the mental model:

  • The curly braces {name} in JSX mean "drop the value of this JavaScript expression in right here." JSX is JavaScript, remember.
  • <Greeting name="Ada" role="Engineer" /> is just Greeting({ name: 'Ada', role: 'Engineer' }) in disguise — a function call. Same data in → same UI out. That's UI = f(data) made concrete.
  • Now try to break it: write <Greeting name="Ada" /> (drop role). TypeScript underlines it in red before you even save-and-run — "Property 'role' is missing." That red squiggle is the payoff of typing from day one: the bug is caught at compile time, not by a confused user.
The takeaway you can feel A component is a function. Props are its arguments. Types describe those arguments so mistakes are caught while you type. Change the arguments → the UI changes. You just built UI = f(data) with your own hands.

Right now the "data" is props passed by the parent, so the two greetings never change on their own. The next lesson adds the missing ingredient — state, data a component owns and can change — which turns UI = f(data) into a living, clicking, updating interface.

"What is the Virtual DOM?" — the interview angle

You'll be asked this in week one of any React interview, and a hand-wavy answer costs you. Here's the honest version. Because your components return cheap description objects (React elements), React can keep the latest description in memory — this in-memory tree of elements is nicknamed the Virtual DOM. When your data changes, React builds a fresh description and compares it to the previous one to work out the smallest set of real DOM edits needed. (That comparison is called reconciliation — Lesson 3 goes deep on it.)

The nuance that scores points The Virtual DOM is not "why React is fast" — hand-written DOM updates can be faster. Its real purpose is to let you program declaratively (UI = f(state)) while React handles the tedious, bug-prone DOM syncing for you. React trades a little raw speed for a lot of correctness and developer sanity. Say that, not "the Virtual DOM makes React fast."
