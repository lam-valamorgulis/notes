Month 4 · Lesson 1

Effects & the outside world

Render must stay pure — so anything that touches a network, a timer or the browser needs its own door. useEffect is that door, and cleanup is what keeps it from leaking.

Your win today: you can say what an effect is for in one sentence, write the setup + cleanup pair without thinking, and answer the question that catches most candidates — "why does my effect run twice in development, and why is that good?"

Everything in Months 1–3 stayed inside React. Props came in, state changed, a function returned JSX. Nothing left the building.

Real apps leave the building constantly. They open network requests, subscribe to sockets, start timers, read localStorage, listen for resize, hand a DOM node to a chart library, send analytics. None of that is a calculation. All of it has to happen somewhere.

This lesson is about where. And the answer starts with a rule you already learned, taken seriously.

First principle — render must be pure

A component is a function from props and state to JSX. React reserves the right to call it whenever it likes, twice in a row, or to throw the result away. That is only safe if the function is pure:

  • Same props and state in → same JSX out.
  • It changes nothing outside itself while it runs.

So this is broken, even though it "works" the first time:

function Profile({ userId }: { userId: string }) {
  const [user, setUser] = useState<User | null>(null);

  // ✕ A side effect during render. React may call this function twice,
  //   or call it and throw the result away. Now you have two requests
  //   and a setState in the middle of rendering.
  fetch(`/api/users/${userId}`).then(r => r.json()).then(setUser);

  return <h1>{user?.name}</h1>;
}

The fix is not "do it more carefully". The fix is to move it out of render. React gives you exactly three places for code to live, and knowing which is which is most of this month:

WhereWhat belongs thereCaused byExample
The body of the component (render)Pure calculations from props and state.Nothing — it just describes the screen.const visible = items.filter(…)
An event handlerSide effects caused by a specific user action.A click, a submit, a keystroke.Buying a ticket, sending a message, showing an alert.
An effect (useEffect)Side effects caused by the component being on the screen.Rendering itself.The chat is open, so a connection must exist.
The sentence to remember

An event handler runs because the user did something. An effect runs because the component is on the screen — and its job is to keep an outside system in sync with what the screen says.

That word sync is the whole idea. An effect is not "run this after render". It is: this outside thing should match my current props and state; go make that true, and undo it when it stops being true.

The anatomy — three parts, and one of them is optional

useEffect(() => {
  // 1. SETUP — start syncing with the outside system.
  const connection = createConnection(serverUrl, roomId);
  connection.connect();

  return () => {
    // 2. CLEANUP — stop syncing. Undo exactly what setup did.
    connection.disconnect();
  };
}, [serverUrl, roomId]);
  // 3. DEPENDENCIES — the values this effect reads from render.
  //    Change any of them and React re-syncs: cleanup, then setup again.

The dependency array is the part people treat as a config knob. It is not. It is an answer to a question React asks: "which values from the render does this code read?" Get it wrong and you have lied to React — which is Lesson 3 of this month.

You writeReact re-runs setupUse it for
useEffect(fn) — no arrayAfter every render.Almost never. Usually a mistake, and a common infinite-loop source.
useEffect(fn, [])Once after the first render, then never again while the component stays mounted.Setup that reads nothing from props or state.
useEffect(fn, [a, b])When a or b changed since the last render, compared with Object.is.The normal case.

Notice Object.is again — the same comparison from Lesson 8. A new object or a new array literal is a new identity every render, so [{ id }] in a dependency array re-runs the effect forever. Same rule, new place.

When it actually runs

Extend the render loop you learned in Lesson 2. An effect is not part of rendering. It happens after React has put things on the screen.

One precise note for interviews: useEffect runs after the browser has painted that frame, which is why it never blocks what the user sees. React also has a before paint version, useLayoutEffect, for the rare case where you must measure the DOM and adjust before anyone sees it. That is Month 5.

The infinite loop you will write once

Every React developer writes this exactly once, and then never forgets it:

function TodoList() {
  const [todos, setTodos] = useState<Todo[]>([]);

  useEffect(() => {
    fetch('/api/todos')
      .then(r => r.json())
      .then(setTodos);       // ← sets state…
  });                        // ← …and no dependency array, so it runs after every render

  // render → effect → setState → render → effect → setState → …
  // Your network tab becomes a waterfall. Your API owner finds you.
}

The cycle is worth tracing by hand, because the same shape causes subtler loops later: the effect changes state, the state change causes a render, the render re-runs the effect. The dependency array is what breaks the cycle — here, [], because the effect reads nothing from render.

The same loop in disguise useEffect(() => { setUser(buildUser(data)); }, [data, user]) — the effect sets user, and user is in its own dependency list. It loops for the same reason. If an effect sets a value it also depends on, stop and ask whether that value should be state at all. That question is the whole of Lesson 2 this month.

Cleanup — the half everyone forgets

Cleanup is not a tidy-up nicety for unmount. It is the other half of a pair, and React calls it in two situations:

  1. Before running setup again, because a dependency changed.
  2. When the component is removed from the screen.

So the test for a correct cleanup is simple: if setup ran twice in a row with your cleanup in between, would the world be the same as running it once? If yes, you are done. If no, your cleanup is incomplete.

Setup doesCleanup must doWhat a missing cleanup looks like
connection.connect()connection.disconnect()Ten open sockets after ten room switches; duplicate messages.
window.addEventListener('resize', h)window.removeEventListener('resize', h)Handlers pile up; each resize does the work N times; the component can never be garbage collected.
setInterval(tick, 1000)clearInterval(id)A counter that speeds up every time you change a filter.
observer.observe(node)observer.disconnect()Callbacks firing for nodes that are gone.
fetch(url)Ignore the result, and abort the requestA slow old response overwriting a fresh one. That is Lesson 4's build.
chart = new Chart(node)chart.destroy()Two charts drawn on top of each other.
Show a modal / lock scrollingHide it / unlock scrollingA page that can never scroll again.

Some setups genuinely need no cleanup — document.title = title just gets overwritten by the next run, and a one-off analytics event is meant to fire once per view. But "I don't need cleanup" should be a decision you can defend, not a blank you left.

Why your effect runs twice in development

Wrap your app in <StrictMode> — Vite's React template does this for you — and React deliberately does something strange in development only. From the React documentation:

React docs · useEffect caveats "When Strict Mode is on, React will run one extra development-only setup+cleanup cycle before the first real setup. This is a stress-test that ensures that your cleanup logic 'mirrors' your setup logic and that it stops or undoes whatever the setup is doing. If this causes a problem, implement the cleanup function."

Read the order carefully, because candidates get it backwards. It is setup → cleanup → setup. Not setup twice.

This is a free bug detector. Bugs that would otherwise appear in production the first time a user switches rooms, navigates away and back, or opens the same page twice, appear on your machine on the first load instead.

Symptom under StrictModeWhat it is really telling you
Two connections in the log, one never closedMissing cleanup.
Two network requestsUsually fine and expected in dev — but it also proves you have no protection against two responses racing. Fix the race, not the double-run.
A counter that jumps by 2Your effect mutates something outside instead of syncing it. Setup + cleanup + setup should equal setup.
An animation that plays twiceThe cleanup does not reset the animation to its starting point.
The wrong fix Turning off StrictMode, or guarding with const didRun = useRef(false). Both hide the message instead of reading it. The double-run is not the bug — it is the alarm. In production the setup runs once, and the bug it was warning you about is still there, waiting for the first user who switches tabs.

Build it for real — a room connection that leaks, then does not

New Vite + React + TS project, or a new folder in the one you have. The point is to see the leak in the console, then see cleanup close it, then see StrictMode prove it.

src/chat.ts — a fake outside system, so the log is the whole truth

let openConnections = 0;

export interface Connection {
  connect: () => void;
  disconnect: () => void;
}

export function createConnection(serverUrl: string, roomId: string): Connection {
  // A real one would open a WebSocket. This one only tells the truth about counts.
  return {
    connect() {
      openConnections++;
      console.log(`✅ connect "${roomId}" — open: ${openConnections}`);
    },
    disconnect() {
      openConnections--;
      console.log(`❌ disconnect "${roomId}" — open: ${openConnections}`);
    },
  };
}

src/RoomPanel.tsx — step 1: the version with the leak

import { useEffect } from 'react';
import { createConnection } from './chat';

const SERVER_URL = 'wss://example.test/chat';

export function RoomPanel({ roomId }: { roomId: string }) {
  useEffect(() => {
    const connection = createConnection(SERVER_URL, roomId);
    connection.connect();
    // ✕ No cleanup, and no dependency array either.
  });

  return <h2>Room: {roomId}</h2>;
}

src/App.tsx

import { useState } from 'react';
import { RoomPanel } from './RoomPanel';

const ROOMS = ['general', 'travel', 'music'];

export default function App() {
  const [roomId, setRoomId] = useState('general');
  const [show, setShow] = useState(true);

  return (
    <main style={{ fontFamily: 'system-ui', padding: '2rem', maxWidth: 520 }}>
      <label>
        Room:{' '}
        <select value={roomId} onChange={e => setRoomId(e.target.value)}>
          {ROOMS.map(r => (
            <option key={r} value={r}>{r}</option>
          ))}
        </select>
      </label>

      <button type="button" onClick={() => setShow(s => !s)} style={{ marginLeft: '.6rem' }}>
        {show ? 'Close chat' : 'Open chat'}
      </button>

      {show && <RoomPanel roomId={roomId} />}
      <p style={{ color: '#666' }}>Watch the console, not the screen.</p>
    </main>
  );
}

Run it and read the console. Switch rooms three times, then close and open the chat. The open: number only ever goes up — 1, 2, 3, 4… Every connection you opened is still open, and nothing on screen tells you. This is the shape of a real production leak: invisible, and paid for by someone else's server.

src/RoomPanel.tsx — step 2: setup and cleanup as a pair

import { useEffect } from 'react';
import { createConnection } from './chat';

const SERVER_URL = 'wss://example.test/chat';

export function RoomPanel({ roomId }: { roomId: string }) {
  useEffect(() => {
    const connection = createConnection(SERVER_URL, roomId);   // setup
    connection.connect();

    return () => connection.disconnect();                      // cleanup: undo exactly that
  }, [roomId]);   // re-sync when the room changes — that is the only value it reads

  return <h2>Room: {roomId}</h2>;
}

Now the log tells a story that matches reality. On first mount, with StrictMode on, you see the stress-test:

✅ connect "general" — open: 1
❌ disconnect "general" — open: 0     ← the extra dev-only cleanup
✅ connect "general" — open: 1        ← the real setup

And switching to travel shows a re-sync, in the right order:

❌ disconnect "general" — open: 0     ← old effect cleaned up first
✅ connect "travel" — open: 1         ← then the new one starts

The number never exceeds 1. That is the invariant your cleanup buys, and it is exactly what you would say in a code review: "switch rooms twenty times and there is still one connection."

src/WindowSize.tsx — the same shape on a browser API

import { useEffect, useState } from 'react';

export function WindowSize() {
  const [width, setWidth] = useState(window.innerWidth);

  useEffect(() => {
    function handleResize() {
      setWidth(window.innerWidth);
    }

    window.addEventListener('resize', handleResize);      // setup
    return () => window.removeEventListener('resize', handleResize);  // cleanup
  }, []);   // reads nothing from render — and it really reads nothing, so [] is honest

  return <p>Window width: {width}px</p>;
}

Two very different outside systems — a socket and a browser event — and the same four lines of shape. That is the point of learning effects as syncing rather than as a list of recipes.

Prove the cleanup, don't trust it Break it on purpose: delete the return line from WindowSize, then console.log('resize handler') inside handleResize. Toggle the component off and on five times, then resize the window once. Five logs from one resize — with the component not even on screen. Put the cleanup back and it drops to one.

Extend it — three reps

  1. Show the connection state on screen. Add status: 'connecting' | 'open' in RoomPanel and have the fake connection call a callback. Question to answer as you do it: is status state, or is it derived? (State — it comes from outside, and cannot be computed from props.)
  2. Make the server URL a prop. Then fix the dependency array. If you did not add it, you lied to React — Lesson 3 covers exactly what that lie costs.
  3. Log a page view. useEffect(() => { logVisit(roomId); }, [roomId]). Now argue with yourself: is this really caused by rendering, or by a user action? (Caused by rendering — the visit happens because the room is on screen, no matter how the user got there.)

Practice: read the situation, pick the move

Scenario

A teammate opens a pull request titled "fix: stop effect running twice". The diff adds a useRef(false) guard around the body of every effect in the app, so each one runs only on the very first setup. The PR description says: "React 18 StrictMode runs effects twice, which double-fires our analytics and opens two sockets. This makes dev match production."

You have to reply. Decide: what is actually true in that description, what is false, and what will happen in production if this merges? Name the one change you would accept, and the console evidence you would ask for.

Remember this · the Feynman summary
  • Render must be pure, so side effects need another door. There are only three doors: render (calculations), event handlers (caused by a user), effects (caused by being on screen).
  • An effect is a sync, not a "then". "While this is true, keep that outside thing matching it — and stop when it stops being true."
  • Three parts: setup, an optional cleanup it returns, and a dependency array that answers "which render values do you read?"
  • It runs after commit and after paint, so it is too late to decide what to draw. useLayoutEffect is the before-paint version — Month 5.
  • No dependency array = after every render. An effect that sets state with no array loops forever.
  • Cleanup runs twice over: before every re-run and on unmount. The test — setup, cleanup, setup should leave the world the same as one setup.
  • StrictMode runs an extra setup + cleanup before the first real setup, in development only. Order: setup → cleanup → setup.
  • The double-run is the alarm, not the fire. A useRef guard silences the alarm and ships the leak.
  • Object.is again: a fresh object or array in the dependency array is a new identity every render, so the effect never stops re-running.
  • Real use case (built & run): a room panel that leaked one socket per room switch, then held at exactly one open connection forever — plus a resize listener with the identical setup/cleanup shape.

If you remember one thing: every "start" in an effect needs a "stop" next to it, because the effect will run again — and React will prove that in development before your users prove it in production.
