Webpack, Vite & the build

The job description names both. "Vite is faster" is a slogan. Knowing why it is faster is the answer, and it takes two sentences.

Your win today: you can explain what a bundler does, why Vite's dev server is fast for a structural reason, and give a real answer to "would you migrate us off webpack?"

What a bundler is for

Four jobs. Say them in this order:

JobWhat it means
ResolveTurn import x from './x' and 'react' into real files, following a module graph from the entry point.
TransformTypeScript → JavaScript, JSX → function calls, modern syntax → what your browser targets support, CSS → something the page can use.
Bundle & splitGroup the graph into files the browser downloads well — one per route, vendors separate, so a change to your code does not invalidate the cached React.
OptimiseMinify, tree-shake unused exports, hash filenames for long-term caching, emit source maps.

Why Vite's dev server is fast — the structural reason

Say this, word for word

"In development Vite does not bundle. The browser supports ES modules natively, so Vite serves each file on demand and only transforms what the current page imports. Dependencies get pre-bundled once with esbuild, which is Go and much faster than a JavaScript transform. For production it still bundles, with Rollup — because hundreds of separate requests would be slow on a real network."

Two follow-ups you should be ready for. Why is HMR instant? Because only the changed module needs re-transforming and re-sending — the graph does not have to be rebuilt. Why bundle for production at all? Request overhead, compression that works better over larger files, and control over chunking and caching.

Webpack is not legacy — know why it survives

Webpack still wins atWhy
Module FederationIndependently deployed micro-frontends loading each other's code at runtime. This is webpack's flagship feature and the usual reason a large app stays.
Deeply customised buildsTen years of loaders and plugins for anything unusual.
Large existing configsA working build nobody wants to risk. That is a legitimate engineering answer, not laziness.

A real build worth describing

A large React product this course draws on ran webpack 5 with three choices worth explaining, because each one is a trade-off rather than a default:

ChoiceWhy it was made
esbuild-loader instead of babel-loader or ts-loaderFar faster transforms. The catch: esbuild strips types without checking them, so on its own the build would happily compile broken TypeScript.
fork-ts-checker running tsc in a background workerThat is the answer to the catch. Type checking happens in parallel instead of blocking every rebuild, so you get speed and type errors.
The config split into reusable parts, one per environmentSix environments sharing one base. A single 900-line config file is where build knowledge goes to die.
Why this story works "We used esbuild for speed, which meant no type checking, so we ran tsc in a background worker to get it back" is a complete engineering decision: a trade-off, its consequence, and the mitigation. That structure is worth more than knowing any particular tool.

The five webpack words

WordOne line
entryWhere the module graph starts.
outputWhere files go, and their naming — [contenthash] for long-term caching.
loaderTransforms one file type on the way in (TS, CSS, images).
pluginHooks into the whole build (generating the HTML, extracting CSS, analysing the bundle).
splitChunksDecides how the graph becomes files — vendors separate, so app changes do not invalidate cached React.

Environment variables — the one that catches people

import.meta.env.VITE_API_URL      // Vite: only VITE_-prefixed vars are exposed
process.env.REACT_APP_API_URL     // CRA / webpack conventions
Trap — "we keep the API key in an env var so it's safe" Anything a build inlines into the client bundle is public. Open DevTools and read it. Environment variables in a front-end build are for configuration — which API host, which feature flag — never for secrets. If a secret is needed, a server holds it. Say this clearly; it is a security question hiding inside a tooling question.

"Would you migrate us to Vite?"

The answer that shows judgement

"For a new project, Vite, without hesitating. For an existing one, I'd ask what the pain actually is. If the dev server takes two minutes to start and the team rebuilds fifty times a day, that is worth measuring and worth doing. If the build is fine and the config carries years of edge cases, migrating is risk with no visible benefit to users. And if the app uses Module Federation, that is a real blocker to check before promising anything."

Drill · out loud, 3 minutes

"Our production bundle is 4 MB. What do you do?"

Order matters: measure first with a bundle visualiser → find the biggest offenders (a date library with every locale, a whole icon set, a chart library on the landing page) → route-level code splitting → check that tree shaking is working, which needs ES modules → then compression and caching. Refusing to guess at the start is half the answer.

Remember this
  • A bundler resolves, transforms, bundles/splits, optimises.
  • Vite is fast in dev because it does not bundle — native ESM, on-demand transforms, esbuild pre-bundling.
  • Vite still bundles for production, with Rollup.
  • Webpack survives on Module Federation, deep customisation, and working configs.
  • esbuild is fast because it does not type-check — run tsc in a worker to get checking back.
  • Five words: entry, output, loader, plugin, splitChunks.
  • Front-end env vars are public configuration, never secrets.
  • Migration is a judgement call: measure the pain, check for Module Federation.

If you remember one thing: Vite is fast because it does less work, not because it works harder.
