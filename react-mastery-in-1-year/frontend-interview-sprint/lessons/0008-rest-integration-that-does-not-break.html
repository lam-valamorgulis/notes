REST integration that does not break

"Experience with RESTful API integration" is on the job description. Nobody is asking whether you can call fetch. They are asking what you do when it fails.

Your win today: you can describe the four failure modes of a real API layer — bad status, slow network, expired token, and out-of-order responses — and say what your code does about each one.

The gotcha they open with

const res = await fetch('/api/users/999');   // server replies 404
const data = await res.json();               // no error thrown — you now parse an error body
Trap — fetch does not reject on 4xx or 5xx fetch rejects only on a network failure: DNS, offline, CORS block, aborted. A 404 or a 500 is a successful HTTP exchange as far as fetch is concerned. You must check res.ok yourself. This is the most common React interview gotcha there is, and it is exactly why teams reach for axios — axios rejects on non-2xx by default. 
async function request<T>(url: string, init?: RequestInit): Promise<T> {
  const res = await fetch(url, init);
  if (!res.ok) {
    const body = await res.text();
    throw new ApiError(res.status, body);   // one error shape for the whole app
  }
  return res.json() as Promise<T>;
}

The four failure modes

FailureWhat the user seesWhat your layer does
Bad status (4xx / 5xx)A blank screen, or a crash in .mapCheck res.ok, throw one ApiError type, render an error state.
Slow or dead networkA spinner foreverA timeout via AbortSignal.timeout(), and retry with exponential backoff — only for idempotent requests.
Expired token (401)Silently logged out mid-taskRefresh once, queue the requests that failed while refreshing, replay them, and log out only if the refresh itself fails.
Out-of-order responsesResults that do not match the inputCancel the previous request (AbortController), or ignore stale responses.

The 401 refresh flow — draw this one

This is the highest-value diagram in the lesson, because almost every real app has it and almost no candidate can describe it.

// axios response interceptor — the shape used in real apps
let refreshing: Promise<string> | null = null;

api.interceptors.response.use(undefined, async (error) => {
  const original = error.config;
  if (error.response?.status !== 401 || original._retried) throw error;

  original._retried = true;                       // retry each request at most once
  refreshing ??= refreshToken().finally(() => { refreshing = null; });
  const token = await refreshing;                 // all 401s wait on the SAME promise

  original.headers.Authorization = `Bearer ${token}`;
  return api(original);                           // replay the original request
});
Say the two guards out loud _retried stops an infinite loop when the refreshed token is also rejected. The shared promise stops a refresh stampede. Both are one line, and both are bugs that reach production in real products. If you have shipped this, say so — it is a strong, concrete story.

Retries — and when not to

for (let attempt = 0; attempt < 3; attempt++) {
  try { return await request(url, { signal: AbortSignal.timeout(10_000) }); }
  catch (e) {
    if (e instanceof ApiError && e.status < 500) throw e;   // 4xx: our fault, retrying won't help
    if (attempt === 2) throw e;
    await sleep(2 ** attempt * 300 + Math.random() * 200);  // backoff + jitter
  }
}

Two rules to state: retry only idempotent requests — a repeated GET is harmless, a repeated POST /orders creates two orders — and add jitter, so a thousand clients recovering from an outage do not all retry at the same millisecond and knock the server over again.

If the API supports an idempotency key, a POST becomes safe to retry. Mentioning that key is a senior signal. (Backend tree L02 covers it from the server side.)

CORS, in one breath

Say this

"CORS is a browser rule, not a server error. The browser blocks a cross-origin response unless the server sends the right Access-Control-Allow-* headers. I cannot fix it in the front end — it is fixed on the server, or worked around with a dev proxy. If the request has custom headers or is not a simple method, the browser sends an OPTIONS preflight first."

The trap is answering "I'd add mode: 'no-cors'". That does not fix anything — it makes the response opaque and unreadable.

Drill · out loud, 3 minutes

"Our list page sometimes shows the wrong data after the user switches filters quickly. What is happening and how do you fix it?"

Name the race condition, name both fixes (AbortController and the ignore-stale-response flag), say which you prefer and why, and finish with what a query library would do for free.

Remember this
  • fetch does not reject on 4xx or 5xx. Check res.ok. axios does reject.
  • One ApiError shape for the whole app beats a different error per call site.
  • The 401 flow needs two guards: retry once, and share one refresh promise.
  • Retry only idempotent requests, with backoff and jitter.
  • An idempotency key makes a POST safe to retry.
  • CORS is a browser rule, fixed on the server. no-cors fixes nothing.
  • Out-of-order responses need cancellation, not a bigger spinner.

If you remember one thing: they are not asking whether you can call an API. They are asking what happens when it fails.
