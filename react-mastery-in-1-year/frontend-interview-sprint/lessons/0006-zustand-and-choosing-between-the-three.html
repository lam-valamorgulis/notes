Zustand, and choosing between the three

The job description names Redux, Zustand and Context together. The question behind that list is not "do you know them". It is "can you choose".

Your win today: you can write a Zustand store from memory, explain why it re-renders less than Context, and give a 45-second decision script that picks one of the three for any situation they describe.

Zustand in one sentence

Say this, word for word

"Zustand is a store that lives outside React. Components subscribe to it with a selector, so a component re-renders only when the slice it selected changes. There is no provider and no reducer ceremony."

The whole API

// stores/cartStore.ts
import { create } from 'zustand';

type CartState = {
  items: { id: string; qty: number }[];
  add: (id: string) => void;
  clear: () => void;
};

export const useCartStore = create<CartState>()((set, get) => ({
  items: [],
  add: (id) => set(state => {                // set merges at the top level
    const found = state.items.find(i => i.id === id);
    return found
      ? { items: state.items.map(i => i.id === id ? { ...i, qty: i.qty + 1 } : i) }
      : { items: [...state.items, { id, qty: 1 }] };
  }),
  clear: () => set({ items: [] }),
}));
// Any component. No <Provider> anywhere in the tree.
const count = useCartStore(s => s.items.length);   // ← subscribes to ONE number
const add   = useCartStore(s => s.add);            // actions are stable — never re-render for this

// And outside React — a socket handler, a plain module, a test:
useCartStore.getState().clear();
Three points worth making out loud 1. No provider means no tree wiring and no context nesting. 2. The selector is the performance story — the component subscribes to items.length, so adding an unrelated field to the store re-renders nothing. 3. getState() works outside React, which matters when a WebSocket message or an imperative engine needs to write state.
Trap — the selector that returns a new object useCartStore(s => ({ items: s.items, total: s.total })) re-renders on every store change, exactly like the Redux mistake. Zustand compares the selector result with Object.is. Select two values with two calls, or use useShallow from zustand/react/shallow. Being able to say this about both libraries shows you understand the mechanism rather than the syntax.

Middleware — the two you will be asked about

import { persist, devtools } from 'zustand/middleware';

export const useSettings = create<State>()(
  devtools(                                  // shows up in Redux DevTools
    persist(
      (set) => ({ theme: 'light', setTheme: (t) => set({ theme: t }) }),
      { name: 'settings', partialize: (s) => ({ theme: s.theme }) },   // persist only what matters
    ),
  ),
);

persist writes to localStorage by default and takes a custom storage — IndexedDB, for example, when the state is bigger than a few kilobytes. partialize is the detail that matters in review: persist the user's choices, never the loading flags or the cached responses.

The honest weakness of Zustand — say it before they do Zustand does not enforce discipline. Any component can call set with anything, so on a big team the store drifts into a mutable global object with no story about who changed what. Redux's ceremony is the price of an action log and a single update path. Naming a tool's weakness is one of the fastest ways to sound senior; naming only its strengths sounds like marketing.

The decision script

Drill · learn this shape, 45 seconds

"How do you decide which state management to use?"

Answer in four steps, in this order — the order is the answer:
  • 1. Is it server data? Then none of the three. TanStack Query or RTK Query. Most "global state" turns out to be a cache.
  • 2. Can it stay local? useState in the component that owns it. Lift it only when a second component needs it.
  • 3. Is it shared but slow-changing? Theme, user, locale, feature flags → Context.
  • 4. Is it shared and changes often, or read in slices by many components? → a store. Zustand for a small or medium app or a team that values speed. Redux Toolkit for a large app, many contributors, or when the action log and devtools genuinely earn their cost.

Using several at once is a real answer

Production apps often run more than one. A large real-time collaboration product this course draws on used TanStack Query for server data, Zustand for domain state (with part of it persisted to IndexedDB), a small atom library for shared UI state, and plain Context for the signed-in session. That is a defensible design — each tool holds a different kind of state.

It also has a real cost, and you should name it: a new developer has to learn four mental models, and "where does this value live?" stops being obvious. If you describe a multi-tool setup in an interview, describe the rule that decides which tool holds what. A rule turns it from mess into architecture.

Remember this
  • Zustand is a store outside React with selector subscriptions and no provider.
  • A selector returning a new object re-renders on every change — in Zustand and Redux.
  • getState() works outside React: sockets, engines, tests.
  • persist plus partialize — save the user's choices, never the loading flags.
  • Zustand's weakness is no enforced discipline. Redux's ceremony buys an action log.
  • The decision order: server data → local → slow-changing shared → store.
  • Several tools at once is fine, if you can state the rule that assigns each kind of state.

If you remember one thing: ask "is this really server data?" before you reach for any of the three.

Ask: "give me five scenarios and make me pick the state tool for each." That is exactly how this gets asked.
