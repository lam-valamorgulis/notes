Kata 1 — the debounced search box

The most-asked React live-coding task there is. Set a timer for 25 minutes, share your screen with yourself, and talk the whole time.

Your win today: you can build a search box that debounces, cancels in-flight requests, shows loading, error and empty states, and cleans up on unmount — while narrating each decision. Twice. The second run should be calm.

The brief, exactly as they will give it

The task · 25 minutes on the clock

"Build a search input. As the user types, fetch matching users from /api/users?q=… and show the results. Don't hammer the API."

That is all they will say. Everything else is a decision they are watching you make.

Before you type: 60 seconds of talking

This is the part candidates skip, and it is worth more than the code. Say this out loud:

The opening — say it before your first keystroke

"Let me state my assumptions. I'll debounce the input by about 300 milliseconds so we send one request per pause, not per keystroke. I'll cancel the previous request when a new one starts, so an old slow response can't overwrite a newer one. I'll handle four states: idle, loading, error, and empty results. And I'll clean up on unmount. Is that the scope you want, or would you rather I focus somewhere specific?"

You have now told them you know about race conditions, cleanup, and UX states — before writing a line. If they only have 20 minutes, they will now steer you. That is a good thing.

The three traps they are actually testing

#TrapWhat a weak answer does
1DebounceFires a request per keystroke, or debounces with a setTimeout that is never cleared.
2Race conditionIgnores it. An older, slower response lands last and overwrites the newer results.
3CleanupLeaves the timer and the request running after unmount, then calls setState on a dead component.

Reference solution

Two pieces. A reusable useDebounce, and a component whose effect owns the request.

// useDebounce.ts — a value that lags behind by `delay` ms.
import { useEffect, useState } from 'react';

export function useDebounce<T>(value: T, delay = 300): T {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);   // ← the whole debounce lives in this line
  }, [value, delay]);

  return debounced;
}

Say out loud why that cleanup is the debounce: every keystroke re-runs the effect, and the cleanup cancels the timer the previous keystroke started. Only a pause long enough to survive the delay lets one through.

// UserSearch.tsx
type User = { id: string; name: string };
type Status = 'idle' | 'loading' | 'error' | 'done';

export function UserSearch() {
  const [query, setQuery] = useState('');
  const [users, setUsers] = useState<User[]>([]);
  const [status, setStatus] = useState<Status>('idle');
  const debouncedQuery = useDebounce(query, 300);

  useEffect(() => {
    if (!debouncedQuery.trim()) {          // empty box → no request at all
      setUsers([]); setStatus('idle');
      return;
    }

    const controller = new AbortController();
    setStatus('loading');

    fetch(`/api/users?q=${encodeURIComponent(debouncedQuery)}`, {
      signal: controller.signal,           // ← kills the race condition
    })
      .then(res => {
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        return res.json();
      })
      .then((data: User[]) => { setUsers(data); setStatus('done'); })
      .catch(err => {
        if (err.name === 'AbortError') return;   // we cancelled it — not an error
        setStatus('error');
      });

    return () => controller.abort();       // new query OR unmount → cancel
  }, [debouncedQuery]);

  return (
    <div>
      <label htmlFor="user-search">Search users</label>
      <input
        id="user-search"
        value={query}
        onChange={e => setQuery(e.target.value)}
        aria-busy={status === 'loading'}
      />

      {status === 'loading' && <p>Searching…</p>}
      {status === 'error'   && <p role="alert">Something went wrong. Try again.</p>}
      {status === 'done' && users.length === 0 && <p>No users match “{debouncedQuery}”.</p>}

      <ul>
        {users.map(u => <li key={u.id}>{u.name}</li>)}
      </ul>
    </div>
  );
}
Four small things that read as senior 1. One status union instead of three booleans — isLoading + isError + isEmpty can encode states that cannot exist. 2. encodeURIComponent on user input in a URL. 3. A real <label htmlFor> and role="alert". 4. An empty query sends no request at all. Each one is five seconds of work and each one gets noticed.

What they will ask next

Assume you finish. The follow-up questions are the real interview:

Follow-upThe short answer
"Debounce or throttle?"Debounce waits for a pause — right for search. Throttle guarantees a rate — right for scroll, resize, mouse move.
"Why not just check if the query still matches?"A boolean ignore flag also fixes the display bug, and it is the fix react.dev shows. AbortController is better because it also stops the request on the wire and frees the connection.
"How would you do this in production?"TanStack Query. The query key is ['users', debouncedQuery], and cancellation, caching, dedupe and retry come free. Writing it by hand is the interview version.
"How do you test it?"React Testing Library plus fake timers: type, advance 300ms, assert one call. Then resolve the responses out of order and assert the newest query wins.
"The list is 10,000 rows."Virtualise it — render only the visible window. That is a different problem from fetching, and I would say so.

Remember this
  • Spend the first 60 seconds talking, not typing. State assumptions and ask for scope.
  • The debounce is the clearTimeout in the effect cleanup.
  • AbortController kills the race condition and frees the connection; an ignore flag only fixes the display.
  • Swallow AbortError. It is your own cancellation, not a failure.
  • One status union beats three booleans — impossible states become unrepresentable.
  • Four UI states, always: idle, loading, error, empty.
  • Finish by saying what you would use in production (TanStack Query) and why.

If you remember one thing: they are grading the narration as much as the code.
