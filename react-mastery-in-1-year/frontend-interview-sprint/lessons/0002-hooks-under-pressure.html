Day 1 · Lesson 2 · React, said out loud

Hooks under pressure

Six questions cover most of what anyone asks about hooks. Five of the six are really the same question: what is useEffect actually for?

Your win today: you can say what an effect is for in one sentence, name the four cases where you should delete one, and explain the double-run in Strict Mode without sounding annoyed by it.

The rules, and the reason behind them

Hooks are called at the top level, never inside a condition, loop or nested function. Candidates recite this. Few can say why.

The reason: React does not know your hooks by name. It stores them per component as an ordered list and matches them across renders by call order. Render one calls useState, useState, useEffect — slots 0, 1, 2. If render two skips the first one because of an if, every slot shifts and your effect reads someone else's state.

Say this

"React identifies hooks by call order, not by name. A conditional hook shifts the order, so the state from slot 1 arrives in slot 0. That is why the rule exists."

What an effect is for

Say this, word for word

"An effect synchronises my component with something outside React — the network, the DOM, a socket, a timer, a media device. If nothing outside React is involved, I do not need an effect."

An effect has three parts, and every interview question about effects is really about one of them.

Question 1 — "Why does my effect run twice?"

Strict Mode in development mounts, unmounts and remounts every component once. Your effect runs setup → cleanup → setup.

The answer that scores "It is a test, not a bug." React is checking that my cleanup correctly undoes my setup. If running the effect twice breaks something — a duplicate socket, two API calls, a double-counted analytics event — then my cleanup is incomplete, and that same bug appears in production the moment the component remounts. So the fix is never to disable Strict Mode. The fix is to write the cleanup.

Question 2 — the stale closure

useEffect(() => {
  const id = setInterval(() => {
    setCount(count + 1);   // reads `count` from the render that created this interval
  }, 1000);
  return () => clearInterval(id);
}, []);                     // empty deps → the closure is frozen at count = 0 forever

The counter goes 0 → 1 and stops. The arrow function captured count when it was created. The empty dependency array told React "this setup reads nothing that changes" — which was a lie.

Two honest fixes:

// A. Do not read the value at all — the updater form reads it from React.
setCount(prev => prev + 1);   // deps can honestly stay []

// B. Tell the truth in the deps and let the effect re-subscribe.
}, [count]);                   // interval torn down and recreated each tick
Trap — the disabled lint rule // eslint-disable-next-line react-hooks/exhaustive-deps is the most expensive comment in React. The dependency array is not a control knob for "when should this run". It is a declaration of what the setup function read. Lying about it does not stop the effect reading the value — it only guarantees the value it reads is old.

Question 3 — the four effects you should delete

The You Might Not Need an Effect page is the highest-value page on react.dev for a senior interview. The four cases:

The effectWhy it is wrongDo this instead
Computing derived state (useEffect → setFullName)Two renders instead of one, and a frame where the value is stale.Calculate it during render: const fullName = first + ' ' + last.
Resetting state when a prop changesThe old state is visible for one render before the reset lands.Give the component a key. A new key means a new component with fresh state.
Handling a user action (POST when submitted === true)The effect cannot tell why it ran, so it fires again on a remount.Put it in the event handler. That is what handlers are for.
Chains of effects that set each other's stateOne click causes four renders, and the order is fragile.Calculate what you can during render; do the rest in one handler.
Say this

"If the code reacts to a user action, it belongs in a handler. If it reacts to the component appearing on screen, it belongs in an effect. Most effects I delete were really handlers."

Question 4 — useRef vs useState

useStateuseRef
Changing it re-rendersYesNo
Read during renderYes, alwaysNo — that makes render impure
Use it forAnything the screen showsTimer ids, DOM nodes, previous values, "did I already do this"

One sentence: state is for what the user sees; a ref is for what the component must remember but nobody looks at. Parent-course lesson 19 goes deeper.

Question 5 — custom hooks

A custom hook is any function starting with use that calls other hooks. The property that matters: it shares stateful logic, not state. Two components calling useOnlineStatus() each get their own state. Sharing an actual value still needs one owner plus context.

Good names describe a use case — useDebounce, useChatRoom, useMediaDevices. Bad names describe React's machinery — useMount, useUpdateEffect. The docs tell you not to write those, because a lifecycle-shaped hook hides the question an effect exists to answer: what is this synchronising with?

Drill · 5 minutes, out loud

"My component fetches inside a useEffect and it loops forever. Fix it."

Answer out loud before reading on. A complete answer covers: the effect sets state, the state change re-renders, the re-render re-runs the effect — then names the usual cause, a dependency that is a new object or array on every render, so the Object.is check always says "changed". The fix is to make the dependency stable, not to delete it from the array.

Remember this
  • Hooks are matched by call order — that is the whole reason for the rules.
  • An effect synchronises with something outside React. Nothing outside React → no effect.
  • Three parts: setup, cleanup, dependencies. The deps list is a fact about what setup read.
  • The Strict Mode double-run is a test of your cleanup, not a bug.
  • A stale closure comes from lying in the deps. Fix with the updater form or an honest list.
  • Four effects to delete: derived state, resetting on a prop change, user actions, effect chains.
  • Custom hooks share logic, not state. Name them after a use case, never after a lifecycle.

If you remember one thing: the dependency array is a declaration, not a schedule.
