Kata 2 — the shared store

A shopping cart read by four unrelated components. The classic "show me you can manage state" task. 30 minutes.

Your win today: you can build the same feature three ways — lifted state, Context, and a store — and say in one sentence why you would ship each one.

The brief

The task · 30 minutes on the clock

"There's a product list, a cart badge in the header, a cart drawer, and a checkout button that must disable when the cart is empty. Wire them up."

Four components, three of them nowhere near each other in the tree. That layout is the whole point of the exercise.

Step 0 — the sentence that starts it

Say this before writing anything

"Before I pick a tool: is the cart server state or client state? If the cart lives on the server and syncs across devices, I'd put it in a query cache and mutate through the API. I'll assume it's client-side for this exercise — tell me if that's wrong."

That question alone separates you from most candidates. Then work down the ladder out loud: local → lifted → Context → store.

Version A — lift the state (and see it break)

Put items in App, pass items and addItem down. It works. Now count what you touched: Header and Layout carry props they never read, and App re-renders the whole tree on every add.

Say the trade-off, do not just abandon it: "This is fine for two levels. It stops being fine when a component in the middle has to carry a prop it does not use — that is the signal I move to Context or a store."

Version B — Context, done properly

const CartContext    = createContext<CartItem[] | null>(null);
const CartActionsContext = createContext<CartActions | null>(null);   // split on purpose

export function CartProvider({ children }: { children: ReactNode }) {
  const [items, dispatch] = useReducer(cartReducer, []);

  // dispatch has a stable identity, so this memo is a fact, not a guess
  const actions = useMemo(() => ({
    add:    (id: string) => dispatch({ type: 'added', id }),
    remove: (id: string) => dispatch({ type: 'removed', id }),
  }), []);

  return (
    <CartContext.Provider value={items}>
      <CartActionsContext.Provider value={actions}>{children}</CartActionsContext.Provider>
    </CartContext.Provider>
  );
}

Narrate the split: "The 'Add to cart' buttons only need the actions. Because the actions context value never changes, those buttons re-render zero times when the cart updates." That sentence is worth more than the rest of the file.

The mistake they are watching for value={{ items, add, remove }} — one context, one inline object. Every consumer re-renders on every render of the provider. If you write it this way and then catch it yourself out loud, that is still a good outcome. Catching your own bug reads as experience.

Version C — Zustand

export const useCart = create<CartState>()((set) => ({
  items: [],
  add: (id) => set(s => ({ items: upsert(s.items, id) })),
  remove: (id) => set(s => ({ items: s.items.filter(i => i.id !== id) })),
}));

// Header badge — subscribes to a number, not to the cart
const count = useCart(s => s.items.reduce((n, i) => n + i.qty, 0));

// Add button — subscribes to a function that never changes
const add = useCart(s => s.add);

Point at the two selectors and say: "The badge re-renders when the count changes. The button never re-renders at all. Neither of them needs a provider, and I can also read the cart from a WebSocket handler with useCart.getState()."

The follow-ups

Follow-upThe short answer
"Which would you ship?"Context + reducer if the cart is the only shared state. Zustand once there are three or four such stores, because I stop wiring providers and get selectors.
"How do you persist it across a refresh?"Zustand's persist with partialize, or a small effect writing to localStorage. Persist the items, never the loading flags. Then hydrate carefully — reading storage during render is impure.
"Two tabs are open."localStorage fires a storage event in the other tabs. Subscribe and re-hydrate, or accept last-write-wins and say so. Naming the conflict is the answer.
"How do you test the cart logic?"The reducer is a pure function — test it with no React at all. For the store, call the actions directly and assert on getState().
"What if the cart is on the server?"Then it is server state: a query for reading, a mutation for writing, optimistic update on click, invalidate on success, roll back on failure.

Score yourself

Tick honestly

  • I named the trade-off of lifted state instead of skipping it.
  • I split the value context from the actions context, and said why.
  • My selectors return primitives or stable references — no inline objects.
  • No component re-renders for state it does not read. I can point at each one.
  • I said how I would persist it, and what I would not persist.
  • I said how I would test it.

Remember this
  • Start by asking server state or client state. It reframes the whole task.
  • Work down the ladder out loud: local → lifted → Context → store.
  • Split value and actions contexts. Action-only components then never re-render.
  • dispatch and store actions are stable — that is why the memo is honest.
  • Selectors must return primitives or stable references, in every library.
  • Persist the user's data, never the transient flags.
  • The reducer is pure, so the cart's rules are testable with no React.

If you remember one thing: be able to point at each component and say why it does or does not re-render.
