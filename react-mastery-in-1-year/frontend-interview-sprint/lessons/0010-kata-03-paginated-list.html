Kata 3 — the paginated list

A table with filters, paging, and every state a real screen has. This is the closest kata to the actual job. 30 minutes.

Your win today: you can build a filtered, paged list where every state is handled, the URL survives a refresh, and you can explain why you chose offset paging or cursor paging.

The brief

The task · 30 minutes

"Show a list of survey responses. Let the user filter by status and page through the results. Make it feel good."

"Make it feel good" is the part being graded. It means the states, not the fetching.

Six states, not two

StateWhat the user should see
First loadA skeleton the shape of the table, not a centred spinner. It stops the layout jumping.
Empty (no data at all)"No responses yet" plus the action that creates one.
Empty (filter matched nothing)A different message: "No responses with status Closed" plus a "clear filters" button. Shipping one message for both is the most common miss.
ErrorWhat failed, and a Retry button. Never a raw stack trace.
Changing pageKeep the old rows visible, dim them, disable the buttons. Do not blank the table.
LoadedRows, plus the total, plus which page you are on.
Say this while you build

"I'm keeping the previous page visible while the next one loads, rather than showing a spinner. A table that disappears on every page change feels broken even when it is fast."

Put the filters in the URL

const [params, setParams] = useSearchParams();          // react-router
const status = params.get('status') ?? 'all';
const page   = Number(params.get('page') ?? '1');

const { data, isPending, isError, isFetching, refetch } = useQuery({
  queryKey: ['responses', { status, page }],             // key = the filters
  queryFn: ({ signal }) => fetchResponses({ status, page, signal }),
  placeholderData: (prev) => prev,                       // keep the old page while loading
});
Why the URL, and say it out loud "Filters go in the URL, not in state. Then a refresh keeps the view, the back button works, and a colleague can paste the link into a bug report and land on exactly what I am seeing." Very few candidates say this. It is a product instinct, not a React trick, and it reads as senior.

Offset or cursor?

Offset (?page=3&limit=20)Cursor (?after=abc123)
Jump to page 47YesNo — next and previous only
Correct while data is changingNo — a new row shifts everything and you see a duplicate or a gapYes
Cost at page 10,000The database still counts past all of themFlat
Right forAn admin table where people want page numbersA feed, an infinite scroll, a large dataset

The answer that scores: "Offset because this is an admin table and users want page numbers — but I know it double-counts when rows are being inserted, so for a live feed I would use a cursor." Backend detail is in Backend tree L03.

Accessibility, in four lines

<table>
  <caption className="sr-only">Survey responses, page {page}</caption>
  <thead><tr><th scope="col">Store</th>…</tr></thead>
</table>
<div role="status" aria-live="polite">{isFetching ? 'Loading…' : `${data.total} results`}</div>

A real <table> with <th scope="col">, and one aria-live region announcing the result count. Thirty seconds of work, and it answers "are you familiar with UI/UX best practices?" from the job description with evidence instead of a claim.

The follow-ups

Follow-upThe short answer
"Now 50,000 rows on one page."Virtualise — render only the visible window plus a small buffer. TanStack Virtual or react-window. Note that it breaks Ctrl+F, so it is a trade.
"Add sorting."Sort on the server and put the sort in the URL, so it composes with paging. Client-side sorting only sorts the page you can see, which is a wrong answer users notice.
"The API is slow."Measure first. Then: prefetch the next page on hover, raise staleTime, and ask the backend whether the endpoint can return less per row.
"Two users edit the same row."Last-write-wins unless the API supports a version or ETag. Name the conflict rather than pretending it does not exist.
Tick honestly
  • All six states, including two different empty states.
  • Old rows stay visible while the next page loads.
  • Filters and page live in the URL.
  • Query key contains every filter — no stale results from an old filter.
  • Stable key from the row id.
  • A real table with header scopes and one live region.
  • I said which paging style I chose and why.
Remember this
  • Six states, and two different empty states — no data versus no matches.
  • Keep the previous page visible while loading. A table that blanks feels broken.
  • Filters and page belong in the URL: refresh, back button, shareable link.
  • The query key holds every filter, so an old filter's response can never land.
  • Offset paging for admin tables, cursor paging for feeds and changing data.
  • A real <table>, scope="col", and one aria-live region.
  • Huge lists need virtualisation, and it costs you Ctrl+F.

If you remember one thing: "make it feel good" means the states, not the speed.
