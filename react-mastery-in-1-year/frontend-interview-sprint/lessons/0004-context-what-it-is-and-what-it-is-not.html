Context — what it is, and what it is not

The job description lists "Redux, Zustand, or Context API" as if they were three of the same thing. They are not. Knowing why is a senior answer.

Your win today: you can say in one sentence what Context actually does, name the exact reason it performs badly for fast-changing state, and answer "can Context replace Redux?" without saying "it depends".

The one sentence

Say this, word for word

"Context is a transport, not a store. It solves 'how does this value reach a deep component', not 'where does this value live and how does it change'."

Context has no reducer, no selectors, no middleware, no devtools, no way to update anything. You still need useState or useReducer to hold the value. Context only carries it down.

The shape you write in an interview

// ThemeContext.tsx
type Theme = 'light' | 'dark';
const ThemeContext = createContext<Theme | null>(null);
const SetThemeContext = createContext<((t: Theme) => void) | null>(null);

export function ThemeProvider({ children }: { children: ReactNode }) {
  const [theme, setTheme] = useState<Theme>('light');
  return (
    <ThemeContext.Provider value={theme}>
      <SetThemeContext.Provider value={setTheme}>{children}</SetThemeContext.Provider>
    </ThemeContext.Provider>
  );
}

// A custom hook per context: better errors, and consumers never import the context object.
export function useTheme() {
  const value = useContext(ThemeContext);
  if (value === null) throw new Error('useTheme must be used inside <ThemeProvider>');
  return value;
}
Three details that get noticed 1. Default value null plus a throw — so a missing provider fails loudly at the call site instead of silently using a fake default. 2. A useTheme() hook, not a raw useContext everywhere. 3. Two contexts, value and setter, split on purpose. That last one is the whole performance story.

Why context is slow — the real reason

When a provider's value changes, every component that reads that context re-renders. Not the ones between — the ones that consume. React.memo does not save them, because they are not re-rendering from props; they are subscribed.

And "changes" means Object.is. This is the classic bug:

<AuthContext.Provider value={{ user, login, logout }}>   // ← new object EVERY render

The object literal is a fresh reference each time the provider re-renders, so every consumer in the app re-renders too — even though user never changed. Two fixes, and you should give both:

// Fix A — memoise the value.
const value = useMemo(() => ({ user, login, logout }), [user, login, logout]);

// Fix B — better: split, so no object exists to memoise.
// The setter context never changes value at all: useState setters are stable.
Say this

"Context has no selectors. A consumer subscribes to the whole value, so any change re-renders all of them. That is why I split contexts by how often each part changes, and why fast-changing state does not belong in context."

Remember this
  • Context is a transport, not a store. It carries a value down; it does not hold or change one.
  • It solves prop drilling. The middle components stop carrying props they never use.
  • Any change to the provider value re-renders every consumer. There are no selectors.
  • An inline object as value is a new reference every render — the classic performance bug.
  • Fix by splitting contexts (value vs setter) first, useMemo second.
  • Good for slow-changing values: theme, user, locale, flags. Bad for anything typed or animated.
  • Context + useReducer is a real pattern — it is Context supplying what it lacks.

If you remember one thing: Context answers "how does it get there", not "where does it live".

Ask your teacher: "show me a context that re-renders the whole app, and let me find why."
