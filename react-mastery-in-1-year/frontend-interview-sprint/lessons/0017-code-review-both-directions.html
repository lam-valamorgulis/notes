Day 6 · Lesson 17 · Working with people

Code review, both directions

"Good understanding of Git, agile workflow, and code review practices" is a line in the job description. It is really asking: are you safe to give write access to?

Your win today: you can say what code review is for in one sentence, describe what you look for in order, and answer "what if the reviewer is wrong?" without sounding either weak or difficult.

What review is for

Say this — it is close to Google's own wording

"The purpose of a review is to keep the codebase healthy over time. So the bar is not 'is this perfect' — it is 'does this leave the codebase better than it was'. If it does, I approve it, even when I would have written it differently."

That single idea resolves most review arguments. A reviewer who blocks until the code matches their personal style is slowing the team down; a reviewer who approves anything is not adding value. "Better than before" is the line.

What you look for, in order

Order matters. A comment about naming on a pull request with a race condition in it is noise.

#Look forTypical React example
1CorrectnessMissing effect cleanup; a dependency array that lies; state derived in an effect instead of during render.
2Security & dataUser input in dangerouslySetInnerHTML; a token in localStorage without a reason; a secret in an env var that ships to the client.
3DesignTwo sources of truth for one value; a component with eight props doing three jobs; server data copied into a store.
4TestsIs the risky part covered? A test that only checks the happy path of a form is a false comfort.
5ReadabilityNames that say what, not how. A comment explaining why, where the code cannot.
6StyleShould be automated. If you are commenting on formatting, the project is missing a formatter.

How to write a comment that lands

Label the weight of every comment. This one habit removes most review friction, and describing it in an interview is a strong signal.

PrefixMeansExample
blocking:I cannot approve until this changes"blocking: this effect has no cleanup, so leaving the page keeps the socket open."
question:I might be wrong; help me understand"question: what happens here if the response arrives after unmount?"
suggestion:Better, but your call"suggestion: this could be derived during render instead of held in state."
nit:Trivial, ignore if you like"nit: userList reads better than data2."
praise:Genuinely good — say so"praise: the abort handling here is exactly right."
Trap — reviewing the person "You forgot the cleanup" versus "this effect is missing a cleanup". The second is about code and is easy to act on. The first is about a person and invites defensiveness. Same information, completely different conversation. In a distributed team, where nobody hears your tone, this matters far more than it does in an office.

Receiving a review

  • The pull request is not you. Say it before you open the comments.
  • Do not defend — ask. "Can you say more about the risk you're seeing?" beats "that's not a problem because…". You may be right, and you will find out faster.
  • Answer every comment, even with just "done" or "left as is because X". Silence reads as ignoring.
  • Make the reviewer's job easy. A short description saying what changed and why, and what you are unsure about, gets you better reviews. Reviewing your own diff first catches the embarrassing half.
"What if the reviewer is wrong?"

"I ask first, because they might be seeing something I'm not. If I still disagree after that, I say why with evidence — a link to the docs, a failing test, a profile. If we still disagree, I ask a third person or take it to a quick call, because a comment thread is a bad place for a real design argument. And if it's a preference rather than a correctness issue, I usually just do it their way — being right about a small thing is not worth the friction."

Small pull requests, and why they matter

A 60-line pull request gets a real review. A 2,000-line one gets "LGTM". Reviewers do not scale with size, and everyone knows this from the receiving end.

Say it this way: "I try to keep pull requests small enough to review in fifteen minutes, and I separate refactors from behaviour changes — a diff that moves code and changes it at the same time is impossible to review honestly." That sentence tells an interviewer you have been on both sides.

The Git answers

QuestionShort answer
"Rebase or merge?"Rebase my own feature branch to keep history readable. Never rebase a shared branch — it rewrites history other people have. Squash on merge if the team wants one commit per change.
"How do you write a commit message?"Imperative subject under about 50 characters — "fix stale mute state on remote tracks" — and a body explaining why, because the diff already shows what.
"You pushed a bug to production."Revert first, investigate second. Restoring service is not the same as finding the cause, and doing them in the wrong order makes the outage longer.
"A conflict in a lockfile."Do not hand-merge it. Take one side, re-run the install, commit the regenerated file.
"How do you find when a bug appeared?"git bisect with a script that reproduces it. It is the only Git answer that consistently surprises interviewers.
Drill · out loud, 3 minutes

"A junior developer opens a pull request with the logic in the right place but a poor structure — five components in one file, some duplication, no tests. What do you do?"

A good answer separates this pull request from this developer. Block only on what is genuinely wrong. Make the structure a suggestion, and explain the reason so it is learning rather than an order. Ask for a test on the one risky path, not on everything. Say something true that was good. And if the same pattern appears three times, the answer is a conversation or a written convention — not the same comment three times.

Remember this
  • Review exists to keep the codebase healthy over time — the bar is "better than before", not "perfect".
  • Look in order: correctness → security → design → tests → readability → style.
  • Label every comment: blocking, question, suggestion, nit, praise.
  • Comment on the code, never the person. This matters double when nobody can hear your tone.
  • Receiving: ask before you defend, and reply to every comment.
  • Small pull requests, and never mix a refactor with a behaviour change.
  • Rebase your own branch; never rewrite a shared one.
  • Broken production: revert first, investigate second.

If you remember one thing: the question behind all of this is "are you safe to work with?"

Ask: "give me a pull request to review out loud and grade my comments."
