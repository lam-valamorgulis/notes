Day 1 · Lesson 1 · React, said out loud

The render model, in one sentence

The first ten minutes of the interview decide the rest. They will be spent on this one idea. Own it and everything after it sounds easy.

Your win today: you can answer "what happens when you call setState?" in about 40 seconds, with the three phases named, and you never say the words "the virtual DOM is faster".

The sentence

Say this, word for word

"React re-runs my component function to work out what the screen should be, compares that result with the last one, and changes only the parts of the real DOM that differ."

That is the whole model. Every other React answer is a consequence of it. When you are stuck in an interview, come back to this sentence and reason forward from it out loud. Interviewers grade reasoning, not recall.

Three phases, three names

The official docs split an update into three steps (Render and Commit). Name them. Most candidates say "React re-renders" and stop.

PhaseWho does whatThe interview point
TriggerA state setter is called, or the component mounts.State updates are queued, not applied on the spot.
RenderReact calls your function. It must be pure: same props and state in, same JSX out, no side effects.This is why Strict Mode calls it twice in development — to catch impurity.
CommitReact applies the minimum set of DOM changes.If the output is identical, React touches nothing at all.

State is a snapshot, not a variable

This is the trick question. Almost every interview asks some version of it.

function Counter() {
  const [n, setN] = useState(0);

  function handleClick() {
    setN(n + 1);
    setN(n + 1);
    setN(n + 1);
    console.log(n);   // logs 0 — not 1, not 3
  }

  return <button onClick={handleClick}>{n}</button>;   // goes 0 → 1
}

Why? Because n is a const in this render's scope. It was fixed the moment this render started. All three calls compute 0 + 1. React queues three identical "set to 1" instructions.

The fix is the updater form, which queues a function instead of a value:

setN(prev => prev + 1);
setN(prev => prev + 1);
setN(prev => prev + 1);   // 0 → 3. Each one receives the result of the last.
Say this

"State behaves like a snapshot. Inside one render, the state value never changes — so I use the updater form whenever the next value depends on the previous one."

Batching — and why it exists

React groups all state updates from one event into one re-render. Since React 18 this also covers updates inside promises, timeouts and native handlers ("automatic batching"). Without it, a handler that sets three pieces of state would render three times and the user could see a half-updated screen.

The virtual DOM question — do not fall in

Trap — "the virtual DOM is faster than the DOM" It is not. It is the DOM, plus extra work to decide what to change. Hand-written imperative DOM code, done perfectly, is always faster. What the virtual DOM buys you is a programming model: you describe the end state and stop tracking transitions by hand. The honest senior answer is: "It trades a little speed for a lot of correctness — I never have to remember to undo the previous state." Say that and you separate yourself from every candidate who memorised a blog post.

Keys — the other half of reconciliation

When React compares two renders of a list, it matches children by key, not by position. A key is an identity claim: "this is the same item as before."

{items.map((item, i) => <Row key={item.id} ... />)}   // identity → correct
{items.map((item, i) => <Row key={i} ... />)}         // position → bugs on reorder/delete

With index keys, deleting the first row makes React think every row's data changed — so state that lives inside a row (an open dropdown, a half-typed input, a video element) attaches to the wrong item. That is the concrete failure to describe. Parent-course lesson 3 works through it.

Drill · 3 minutes, out loud

The interviewer says: "I click a button, and my console.log right after setCount still shows the old number. Is that a bug in React?"

Answer it out loud before reading on. A complete answer names the snapshot rule, says where the new value is visible (the next render), and offers the updater form. Bonus: mention that a ref is the escape hatch if you genuinely need the value immediately.

Remember this
  • Three phases: trigger → render → commit. "Re-render" means your function ran, not that the DOM changed.
  • Render must be pure. Strict Mode double-invokes it in development to prove that.
  • State is a snapshot: inside one render the value never changes.
  • Use the updater form setX(prev => ...) when the next value depends on the previous one.
  • React batches all updates from one event into one render — since 18, in async code too.
  • The virtual DOM buys a programming model, not raw speed.
  • Keys are identity. Index keys break reorder and delete.

If you remember one thing: React re-runs my function, compares, and changes only the difference. Every other answer is a consequence of that.
