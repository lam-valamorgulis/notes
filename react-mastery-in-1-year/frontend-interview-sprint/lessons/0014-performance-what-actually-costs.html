Day 5 · Lesson 14 · Making it fast

Performance — what actually costs

"Optimize components for performance, scalability, and reusability" is on the job description. The wrong answer starts with useMemo. The right one starts with a measurement.

Your win today: you can name the three causes of a slow React app, say what memo actually compares, and explain why adding useMemo everywhere makes an app slower.

The sentence that opens every performance answer

Say this first, always

"First I'd measure. The React Profiler tells me which components render and why; the browser's Performance panel tells me whether the time is even going to JavaScript. Optimising before that is guessing."

Candidates who jump straight to useMemo are telling the interviewer they have never profiled anything. The tools, by name: React DevTools Profiler (with "record why each component rendered" enabled), the Chrome Performance panel, and Lighthouse for the load-time picture.

Three causes, in the order you should check them

#CauseThe fix
1Too many components render. One state change wakes half the tree.Move state down, lift content up as children, split contexts, then memo at the boundary.
2One render does too much work. A sort or filter over 10,000 rows on every keystroke.useMemo around the expensive computation — with a real measurement behind it.
3Too much DOM. Five thousand rows, each with handlers.Virtualise. Render the visible window plus a small buffer.

What memo actually does

React.memo wraps a component so React skips re-rendering it when its props are shallow-equal to last time. Shallow means Object.is on each prop. Which is why this is so common:

<MemoisedList items={items} onSelect={() => select(id)} />   // new function every render

The arrow function is a new reference each render, so the shallow compare always fails and memo does nothing but add work. useCallback exists to fix exactly this — and only makes sense when the child is memoised or the function is an effect dependency.

ToolWhat it memoisesOnly worth it when
React.memoA component's rendered outputThe component is expensive and its props are usually stable
useMemoA computed valueThe computation is genuinely costly, or the value is a dependency of something memoised
useCallbackA function's identityIt is passed to a memoised child or listed in a dependency array
Trap — memoising everything Every useMemo and useCallback costs memory and a dependency comparison on every render, and each one is a dependency array that can go stale. Wrapping a component that renders three <div>s in memo makes it slower, not faster. Say this out loud: "Memoisation is a trade, not a free win — I add it where the profiler shows a cost, not by default."

Code splitting

const Analytics = lazy(() => import('./routes/Analytics'));   // its own bundle chunk

<Suspense fallback={<PageSkeleton />}>
  <Analytics />
</Suspense>

Split by route first — it is the biggest win for the least risk. Then split heavy, rarely used components: a rich-text editor, a charting library, a date picker, a PDF viewer. A chart library nobody opens should not be in the first download.

Core Web Vitals — know the three

MetricMeasuresUsual front-end cause
LCP — Largest Contentful PaintWhen the main content appearsA big unoptimised hero image, a render-blocking bundle, a slow API before first paint
INP — Interaction to Next PaintHow fast the page responds to a click or a keypressLong JavaScript tasks blocking the main thread. This replaced FID.
CLS — Cumulative Layout ShiftHow much the layout jumpsImages with no width/height, ads or banners injected above content, late-loading fonts

Knowing that INP replaced FID is a small, current detail that signals you have looked at this recently.

Bundle size

  • Look before you cut. rollup-plugin-visualizer for Vite, webpack-bundle-analyzer for webpack.
  • The usual culprits: moment.js with all its locales, a whole icon set imported as one object, lodash imported as a namespace, a chart library on the landing page.
  • Tree shaking needs ES modules. A CommonJS dependency cannot be shaken, which is why import _ from 'lodash' pulls everything and lodash-es with named imports does not.
Drill · out loud, 4 minutes

"Our dashboard has become slow. Where do you start?"

Structure: define slow (slow to load, or slow to interact? they are different problems) → measure (Profiler for renders, Performance panel for main-thread time, Lighthouse for load) → the three causes in order → structural fixes before memoisation → measure again to prove it. Refusing to guess is the answer.
Already yours — go deeper later L23 · What actually makes a component re-render · L25 · memo, useMemo & useCallback · L24 · Context
Remember this
  • Measure first. Profiler for renders, Performance panel for main-thread time, Lighthouse for load.
  • Three causes: too many renders, too much work per render, too much DOM.
  • Structural fixes beat memoisation: move state down, pass children, split contexts.
  • memo compares props shallowly — an inline function or object defeats it.
  • useCallback only earns its cost with a memoised child or a dependency array.
  • Split by route first, then heavy rare components.
  • LCP, INP, CLS — and INP replaced FID.
  • Tree shaking needs ES modules; measure the bundle before cutting.

If you remember one thing: the fastest render is the one that never happens.
