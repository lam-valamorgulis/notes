Redux Toolkit, so you can teach it

You have used Redux. You cannot explain it. That gap is normal, it is visible in an interview, and it closes in about three hours.

Your win today: you can draw the Redux data flow on a whiteboard from memory, say why each arrow exists, and answer "why not just Context" with a reason, not a preference.

The one sentence

Say this, word for word

"Redux is one predictable container for state. The state is read-only. The only way to change it is to dispatch a plain object describing what happened, and a pure function decides what that means."

Three rules, and every Redux feature exists to serve one of them.

RuleWhat it buys you
One store — a single object tree for the appNo "which copy is right?" There is one.
State is read-only — you never assign to itEvery change went through one door, so every change is loggable and replayable.
Changes come from pure reducers — (state, action) => newStateSame inputs, same output. Testable with no React, no DOM, no network. Time-travel debugging works.

The diagram — draw this, do not describe it

Narrate the loop like this

"A component dispatches an action — a plain object saying what happened, not what to change. The store hands the current state and that action to the reducer. The reducer returns a brand-new state object. The store swaps it in and notifies subscribers. Each component re-reads its slice through a selector and re-renders only if its slice actually changed."

Redux Toolkit is Redux — do not apologise for old Redux

Trap — "Redux has too much boilerplate" That sentence dates you to about 2018. The Redux team's own answer was Redux Toolkit, and RTK is the official way to write Redux today. Hand-written action-type constants, switch statements and combineReducers are legacy. If you say "boilerplate" as a criticism, expect: "have you used Redux Toolkit?" Get in front of it: "I use Redux Toolkit — it removed the boilerplate people used to complain about."

The whole thing, in about 30 lines

// features/cart/cartSlice.ts
import { createSlice, type PayloadAction } from '@reduxjs/toolkit';

type CartState = { items: { id: string; qty: number }[]; status: 'idle' | 'loading' };
const initialState: CartState = { items: [], status: 'idle' };

const cartSlice = createSlice({
  name: 'cart',
  initialState,
  reducers: {
    added(state, action: PayloadAction<string>) {
      const found = state.items.find(i => i.id === action.payload);
      if (found) found.qty += 1;              // looks like mutation — see Immer below
      else state.items.push({ id: action.payload, qty: 1 });
    },
    removed(state, action: PayloadAction<string>) {
      state.items = state.items.filter(i => i.id !== action.payload);
    },
  },
});

export const { added, removed } = cartSlice.actions;   // action creators, generated
export default cartSlice.reducer;

// selectors live next to the slice, so components never reach into the shape
export const selectCartCount = (s: RootState) =>
  s.cart.items.reduce((n, i) => n + i.qty, 0);
// store.ts
import { configureStore } from '@reduxjs/toolkit';
export const store = configureStore({ reducer: { cart: cartReducer } });
export type RootState = ReturnType<typeof store.getState>;

// CartButton.tsx
const count = useSelector(selectCartCount);          // subscribe to ONE derived value
const dispatch = useDispatch();
<button onClick={() => dispatch(added(productId))}>Add ({count})</button>

configureStore is not just a shorter createStore. It turns on the Redux DevTools, adds thunk middleware, and — in development — adds checks that throw if you accidentally mutate state outside a reducer or put something non-serialisable in the store. That is a real answer to "what does RTK give you".

Immer — the part that confuses everyone

In the reducer above, found.qty += 1 looks like mutation, and Redux forbids mutation. Both are true. RTK wraps every reducer in Immer.

Say this

"Immer gives my reducer a draft — a proxy of the state. I write straightforward mutating code against the draft, and Immer records what I touched and produces a new immutable state, sharing every unchanged branch. So the code reads like mutation and the result is still immutable."

Trap — the two Immer rules 1. Either mutate the draft or return a new value — never both in one reducer. 2. Immer only applies inside createSlice / createReducer. Mutating state anywhere else — in a component, a thunk, a selector — is a real bug, and RTK's development middleware will throw to tell you.

Async — thunks

Reducers are pure, so they cannot fetch. Async work goes in a thunk: a function dispatched instead of an object, which the thunk middleware calls with dispatch and getState.

export const loadUser = createAsyncThunk('user/load', async (id: string) => {
  const res = await fetch(`/api/users/${id}`);
  if (!res.ok) throw new Error(String(res.status));
  return res.json();                       // becomes action.payload of user/load/fulfilled
});

extraReducers: (builder) => {
  builder
    .addCase(loadUser.pending,   s => { s.status = 'loading'; })
    .addCase(loadUser.fulfilled, (s, a) => { s.status = 'idle'; s.data = a.payload; })
    .addCase(loadUser.rejected,  (s, a) => { s.status = 'error'; s.error = a.error.message; });
}

One thunk generates three action types — pending, fulfilled, rejected. Naming them is a strong signal that you have actually used it.

The senior addition Follow that with: "though for server data I would reach for RTK Query or TanStack Query instead of thunks — caching, deduplication and invalidation are the hard parts, and hand-rolling them in slices is how stores get bloated." Day 3 covers why.

The re-render bug they may show you

const { items, total } = useSelector(s => ({ items: s.cart.items, total: s.cart.total }));

This re-renders on every dispatched action in the app. useSelector compares the previous and next result with reference equality, and that object literal is new every time it runs. Three fixes, best first:

  • Two separate useSelector calls, each returning a primitive or a stable reference.
  • useSelector(fn, shallowEqual) from react-redux.
  • createSelector from RTK — a memoised selector that returns the same object while its inputs are unchanged. This is also the right tool for a derived value that is expensive to compute.

Remember this
  • Three rules: one store, read-only state, changes only through pure reducers.
  • The flow: dispatch → reducer → new state → selector → render. One direction.
  • An action describes what happened, not what to change. The reducer decides what it means.
  • RTK is Redux today. Never call Redux boilerplate-heavy without naming RTK.
  • Immer lets you write mutating code on a draft and returns new immutable state — only inside createSlice.
  • Async is a thunk: pending, fulfilled, rejected.
  • A selector returning a new object re-renders on every action. Split it, or memoise with createSelector.

If you remember one thing: the UI never writes to the store — it dispatches a fact, and a pure function decides what that fact means.

Say "make me teach Redux back to you". Explaining it out loud is the fastest way to find the hole you cannot see.
