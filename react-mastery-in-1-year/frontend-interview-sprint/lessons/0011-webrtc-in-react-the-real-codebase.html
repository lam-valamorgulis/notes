Day 4 · Lesson 11 · Your strongest material

WebRTC in React — the real codebase

Most candidates have a CRUD app. You shipped video calls, screen share and device management in a React product. This lesson turns that into answers.

Your win today: you can draw the two-network architecture of a video call, explain the four React patterns that make it work, and answer "what would you do differently now?" with three specific, technical answers.

Why this is your best material

A video call breaks every comfortable assumption in React. The data is a live hardware handle, not JSON. The truth lives in an engine outside React. The user's hardware changes while the app runs. Nothing can be solved by adding another useState. If you can talk about this calmly, the interviewer learns more about you in five minutes than a whole CRUD discussion would tell them.

The architecture — two networks, not one

This is the first thing to draw, and the thing most candidates get wrong. A call runs on two separate connections.

Say this, word for word

"A call has two networks. Signalling — a WebSocket — carries who is calling whom, accept, reject, hang up. The media server carries the audio and video. They fail independently, which is why 'they joined but I can't hear them' is a different bug from 'the call never started'."

Mesh, SFU or MCU — the scaling question

TopologyWhat each browser doesBreaks at
Mesh (peer to peer)Sends its stream to every other person. 5 people = 4 uploads each.About 4–6 people. Upload bandwidth dies first, then CPU.
SFU (selective forwarding)Sends once to the server; the server forwards. Still decodes N streams.Dozens. The usual production choice.
MCU (mixing)Sends once, receives one mixed stream. Cheapest for the client.Server CPU cost, and you lose per-person layout control.

Say which one your product used and why: an office product with rooms of a dozen people needs an SFU — mesh cannot carry it, and an MCU takes away per-person video tiles and speaker highlighting. That sentence answers "how would you scale it?" before it is asked. (Backend tree L07 has the server side.)

Where React's job starts and stops

The design rule

"The engine owns the call. React renders a snapshot of it. Commands go down into the engine; state comes back up as events."

The media engine is a long-lived class with sockets, transports, producers, consumers and reconnect timers. Its life is longer than any component's. React must never become a second copy of that truth — it must read it. Now four patterns that make that real.

Pattern 1 — a stream reaches the screen through a ref

There is no <video src={stream}>. A live stream is attached through a DOM property, srcObject, which means a ref and an effect.

function VideoTile({ stream, muted }: { stream: MediaStream | null; muted: boolean }) {
  const ref = useRef<HTMLVideoElement>(null);

  useEffect(() => {
    const el = ref.current;
    if (!el || !stream) return;
    el.srcObject = stream;
    return () => { el.srcObject = null; };   // detach when the stream changes or we unmount
  }, [stream]);

  return <video ref={ref} autoPlay playsInline muted={muted} />;
}

Three attributes carry real meaning, and naming them is a signal you have shipped this: autoPlay because a live call cannot wait for a play button, playsInline because iOS otherwise throws the video into fullscreen, and muted on your own preview so you do not hear yourself — and because browsers only allow unattended autoplay when the element is muted.

Pattern 2 — play() returns a promise, and it rejects

el.onloadeddata = () => {
  el.play().catch(err => {
    // NotAllowedError: autoplay policy — the user has not interacted with the page yet
    setNeedsUserGesture(true);   // show an "Unmute" button and let the click start it
  });
};
Trap — the silent call Browsers block audio playback until the user has interacted with the page. A call that starts from a notification, a deep link, or a background tab hits this, play() rejects with NotAllowedError, and the user sees a frozen video with no sound and no explanation. The production answer has two parts: catch the rejection, and show a button, because only a real user gesture can unblock it. In the case-study code this rejection was caught and logged — the honest version of the story is "we caught it; what I would add now is the recovery UI".

Pattern 3 — reading the engine during render is a bug waiting

The tempting shortcut, and one the real code used:

const localStream = EngineManager.get(callId)?.local_stream ?? null;   // read during render

It works most of the time, and that is the problem. React does not know that value exists, so nothing re-renders when the engine swaps the stream — the component only updates when something else happens to re-render it. With concurrent rendering, two parts of one screen can read that mutable object at different moments and disagree. That is called tearing, and it is exactly the problem useSyncExternalStore was added to solve.

function useLocalStream(callId: string) {
  return useSyncExternalStore(
    (onChange) => {                                     // subscribe
      engine.on('streamchange', onChange);
      return () => engine.off('streamchange', onChange);
    },
    () => engine.get(callId)?.localStream ?? null,       // read a consistent snapshot
  );
}
This is your best senior answer of the whole week "We read the engine's stream directly during render. It worked, but React had no subscription to it, so updates depended on an unrelated re-render — and under concurrent rendering two components could read different values in the same pass. I'd move it to useSyncExternalStore, which exists precisely for reading a mutable external source safely." Naming a real weakness in your own shipped code, with the correct fix, is the strongest thing you can do in a technical interview.

Pattern 4 — the dependency array bug that mutes the wrong person

useEffect(() => {
  if (remoteStream && videoRef.current) {
    videoRef.current.srcObject = remoteStream;
    videoRef.current.muted = micStatus === 'off';   // reads micStatus…
  }
}, [remoteStream, callStatus]);                     // …but micStatus is not in the list

Trace it out loud: the remote user mutes their microphone. micStatus changes. The component re-renders — but the effect does not re-run, because neither remoteStream nor callStatus changed. The element's muted property keeps the value from the last time the effect ran. The mute icon in the UI is correct while the audio behaviour is not.

This is the stale-deps problem in production, on real code, with a user-visible consequence. Two fixes: add micStatus to the array, or better — split it, because attaching a stream and setting a mute flag are two different synchronisations that happen at different times.

Say this

"One effect should synchronise one thing. When I see an effect doing two jobs, the dependency array can only be right for one of them."

The hardware layer — the part nobody prepares for

Devices are not configuration. They are hardware that changes while the app is running. The real product had to handle all of this, and each item is a question you can answer with a story:

SituationWhat the app must do
User unplugs the headset mid-callListen for devicechange, notice the selected device is gone, fall back to another input of the same kind, and tell the user. Doing nothing means silence with no error.
Ten devicechange events in one secondOne Bluetooth device produces a burst. Guard the handler with a lock so the re-enumeration runs once, not ten times racing each other.
Permission changes in the browser UInavigator.permissions.query({name:'camera'}) gives a PermissionStatus with an onchange event. React to a revoke instead of failing on the next call.
Device labels are emptyBefore permission is granted, enumerateDevices returns entries with blank labels — an anti-fingerprinting rule. So you cannot show a useful device picker until the user has granted access once.
The user picked a camera last weekPersist the chosen deviceId, but always verify it still exists on load, because ids change between machines and after some OS updates.
The story to tell "The hardest bug I fixed there was not React. A Bluetooth headset connecting fires a burst of devicechange events, and our handler re-enumerated devices on each one — so several async updates raced and the user could end up on a microphone that no longer existed. We serialised the handler with a lock so only one re-enumeration runs at a time, and made device removal fall back to another input of the same kind." Concrete, technical, and it shows you can debug something that is not in a tutorial.

The cleanup rule

return () => {
  stream.getTracks().forEach(t => t.stop());   // ← this, and only this, releases the hardware
};

track.stop() is what turns the camera light off. Setting srcObject = null, unmounting the component, and leaving the page all fail to do it. Users forgive most bugs; a camera light that stays on after a call is not one of them.

What I would change today — rehearse these three

  1. Read the engine through useSyncExternalStore instead of during render, so React owns the subscription and concurrent rendering cannot tear.
  2. One effect per synchronisation. Attaching a stream, setting mute, and clearing on call end are three concerns; one effect with a shared dependency array was where our stale-mute bug lived.
  3. Handle the autoplay rejection with UI, not a log. Catch NotAllowedError and show an "Unmute" button, because only a user gesture can unblock audio.
Drill · out loud, 5 minutes

"Tell me about the most technically difficult thing you've built."

Ninety seconds, no more. Structure: what the product was → the one hard constraint (React had to render state it did not own) → the design decision (engine owns the call, React renders a snapshot) → one concrete bug and its fix (the device-change race, or the stale mute) → what you would change now. Then stop and let them ask.

  • A call runs on two networks: signalling (WebSocket) and media (SFU). They fail separately.
  • Mesh dies around 5 people; an SFU is the production answer; an MCU trades layout control for client cost.
