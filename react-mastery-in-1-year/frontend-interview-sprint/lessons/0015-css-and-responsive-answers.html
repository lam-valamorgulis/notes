CSS & responsive — the answers

"Implement responsive design and ensure cross-browser compatibility" is a line in the job description. Here are the six questions behind it.

Your win today: you can answer flex-vs-grid in one sentence, explain mobile-first with the technical reason rather than the slogan, and describe how you would organise CSS on a large product.

Q1 — Flexbox or Grid?

Say this, word for word

"Flexbox lays out one dimension — a row or a column — and is content-first: the items decide the sizes. Grid lays out two dimensions at once and is layout-first: I define the tracks and the items fill them. A toolbar is flex. A page layout or a card grid is grid. Real screens use both, nested."

Reach for flex whenReach for grid when
A nav bar, a button row, a form field with an iconA page shell — header, sidebar, main, footer
Items should size themselves to their contentYou want columns to line up across rows
You need space-between along one axisYou want a responsive card grid with no media queries
/* The one-liner responsive grid — no media query anywhere */
.cards {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(16rem, 1fr));
  gap: 1rem;
}

Being able to write that from memory answers "how do you do responsive?" better than any explanation. It reads as: as many 16rem columns as fit, then share the leftover space.

Q2 — Why mobile-first?

The slogan is "design for small screens first". The technical reason is better:

Say this

"With min-width queries, the base styles are the small-screen styles, so a phone downloads and applies the simplest rules and never evaluates the desktop ones. Going the other way means every phone parses a desktop layout and then overrides it. It also matches how CSS works: I add complexity as space appears, instead of undoing it."

.sidebar { display: none; }                        /* base = mobile */

@media (min-width: 48rem) {                        /* add, do not undo */
  .sidebar { display: block; }
}

Breakpoints belong to your content, not to device names. The right answer to "which breakpoints do you use?" is: "Wherever the layout starts to look wrong when I drag the window — I don't target iPhone widths, because those change every year."

Q3 — Container queries

A media query asks about the viewport. A card in a sidebar and the same card in a wide main column get the same answer, which is the wrong answer. A container query asks about the parent:

.card-slot { container-type: inline-size; }

@container (min-width: 24rem) {
  .card { grid-template-columns: 8rem 1fr; }   /* wide enough for an image beside the text */
}

This is the answer that makes a component genuinely reusable, which is the word the job description uses. Baseline in all major browsers since 2023 — safe to name.

Q4 — How do you organise CSS at scale?

They are asking whether you have worked on something big enough for CSS to become a problem. Give the trade-offs, then a choice.

ApproachStrengthCost
CSS ModulesScoped names, plain CSS, zero runtimeDynamic values need CSS variables
CSS-in-JS (Emotion, styled-components)Styles co-located with the component; props drive styles naturallyRuntime cost, a bigger bundle, and awkward with Server Components
TailwindNo naming, no dead CSS, one consistent scaleNoisy markup; needs component extraction to stay readable
Design tokens (CSS custom properties)One source of truth for colour, spacing, radius; themes for freeNeeds discipline — a hard-coded hex defeats it
The senior version of this answer "Whichever we pick matters less than having tokens underneath it. Colour, spacing, radius and typography live as CSS custom properties, and components consume the tokens. That is what makes a dark theme a variable swap instead of a rewrite, and it is what stops the fourteenth shade of grey appearing." That answer is about maintenance, which is what "UI consistency" in the job description means.

Q5 — Specificity and the cascade

Specificity counts three things: ids, classes (and attributes and pseudo-classes), elements. Inline styles beat all of them, and !important beats everything, which is why it is a smell — it is a fight you win once and lose forever.

/* :where() has ZERO specificity — the modern way to write overridable defaults */
:where(.prose) a { color: var(--accent); }   /* any later single class beats this */

/* @layer decides order regardless of specificity */
@layer reset, base, components, utilities;   /* utilities always win, no !important */

Naming :where() and @layer shows you have written CSS recently. Both are widely supported now.

Q6 — Cross-browser compatibility, in 2026

The honest answer is that this question has changed. Say so:

Say this

"The old browser-prefix work is mostly gone — the build handles it. What is left is Safari, which lags on some newer APIs, and mobile viewport behaviour. So I test the real flows in Safari and on a real phone, use @supports for anything genuinely new, and check Baseline support before adopting a feature rather than guessing."

@supports (animation-timeline: scroll()) { /* progressive enhancement, not a polyfill */ }

/* the mobile viewport unit that accounts for the browser chrome */
.sheet { height: 100dvh; }   /* 100vh is famously wrong on mobile Safari */

The accessibility answers — four, and they are cheap

DoWhy it matters in an interview

Drill · out loud, 3 minutes

"How would you make this dashboard work on mobile?"

A complete answer moves through: content priority (what does a phone user actually need first?) → layout (grid shell collapsing to one column; a table becoming stacked cards) → touch (targets around 44px, no hover-only actions) → performance (mobile CPUs are slower, so images and JavaScript cost more) → testing (a real device, not just the DevTools emulator).

Remember this
  • Flex is one dimension and content-first. Grid is two dimensions and layout-first.
  • repeat(auto-fit, minmax(16rem, 1fr)) — a responsive grid with no media query.
  • Mobile-first means min-width: add complexity as space appears, never undo it.
  • Breakpoints come from the content, not from device names.
  • Container queries ask the parent, which is what makes a component truly reusable.
  • Tokens as CSS custom properties matter more than which styling library you pick.
  • :where() has zero specificity; @layer sets order without !important.
  • Four cheap accessibility wins: semantic HTML, visible focus, 4.5:1 contrast, reduced motion.

If you remember one thing: responsive is about content priority, not about breakpoints.

Ask: "give me a layout and make me choose flex or grid, out loud."
