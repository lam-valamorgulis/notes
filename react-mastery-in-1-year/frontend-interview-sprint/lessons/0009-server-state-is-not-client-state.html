Server state is not client state

One idea makes you sound senior faster than anything else this week. Most of what people put in a global store is not state at all — it is a cache.

Your win today: you can name the difference in one sentence, list the four things you re-implement badly when you fetch by hand, and describe an optimistic update including the rollback.

The one sentence

Say this, word for word

"Client state is mine — I own it and it is always correct. Server state is a copy of somebody else's state that was correct when it arrived and may be wrong now. Those need different tools."

Client stateServer state
OwnerThis browser tabThe server. Other users change it.
CorrectnessAlways currentStale the moment it arrives
LifetimeUntil you change itNeeds expiry and refresh
ExamplesTheme, open modal, form draft, selected tabOrders, users, products, permissions
TooluseState, Context, Zustand, ReduxTanStack Query, RTK Query

What you re-implement badly by hand

Everyone can write useEffect + fetch + useState. Here is what that version is missing, and this list is the interview answer:

MissingWhat the user experiences
CachingNavigate away and back — a full spinner again, for data you already had.
DeduplicationThree components need the same user, so three identical requests go out.
Background refetchThe tab sat open for an hour. The numbers are an hour old and nothing says so.
InvalidationYou create an order; the list still shows the old one until a manual refresh.
Race conditionsCovered in lesson 8 — the old response overwrites the new.
Retry and offlineOne flaky request means a permanent error screen.

The API, in the amount you need

const { data, isPending, isError, error } = useQuery({
  queryKey: ['orders', { status, page }],       // the cache key AND the dependency array
  queryFn: ({ signal }) => fetchOrders({ status, page, signal }),
  staleTime: 30_000,                             // 30s of "do not bother refetching"
});

Two things to point out when you show this. The query key is the dependency array — change status and it is a different cache entry, fetched automatically, and the old one stays cached. And the signal handed to queryFn means cancellation is wired for you.

const queryClient = useQueryClient();

const createOrder = useMutation({
  mutationFn: (input: NewOrder) => api.post('/orders', input),
  onSuccess: () => {
    queryClient.invalidateQueries({ queryKey: ['orders'] });   // list refetches itself
  },
});

Optimistic updates — say the rollback

An interviewer asking about optimistic UI is testing whether you remember that it can fail.

useMutation({
  mutationFn: toggleFavourite,
  onMutate: async (id) => {
    await queryClient.cancelQueries({ queryKey: ['items'] });   // stop an in-flight refetch overwriting us
    const previous = queryClient.getQueryData(['items']);       // snapshot for the rollback
    queryClient.setQueryData(['items'], optimisticallyToggle(id));
    return { previous };
  },
  onError: (_err, _id, ctx) => {
    queryClient.setQueryData(['items'], ctx.previous);          // put it back
  },
  onSettled: () => queryClient.invalidateQueries({ queryKey: ['items'] }),  // truth wins
});
Say this

"Optimistic means I write the expected result into the cache before the server answers. Three things make it safe: cancel in-flight refetches, keep a snapshot so I can roll back, and re-validate at the end so the server always has the last word."

The knock-on effect on your store

Once server data lives in a query cache, look at what is left for Redux or Zustand: the theme, the signed-in user, an open modal, a filter selection, a draft form. That is a small store — which is why the modern answer to "do you use Redux?" often is "less than I used to, because most of what used to be in it was server cache." That sentence lands well.

Trap — copying query data into a store useEffect(() => { dispatch(setOrders(data)); }, [data]). Now there are two copies with two lifetimes and no rule about which is right. If a component needs the data, it calls useQuery with the same key — the cache is already shared, and there is no second fetch.
Drill · out loud, 3 minutes

"We already use Redux everywhere. Why should we add another library for data fetching?"

This is a pushback question, and pushing back correctly is the skill. Name what a store does not give you (staleness, background refetch, dedupe, per-query loading and error states), then offer the cheaper path: RTK Query, which ships inside Redux Toolkit — no new library at all. Knowing that option exists is the answer they want.

Remember this
  • Server state is a cache of someone else's state. Client state is yours.
  • Hand-rolled fetching misses caching, dedupe, background refetch, invalidation, cancellation, retry.
  • The query key is the dependency array and the cache key at the same time.
  • staleTime = when to refetch. gcTime = when to forget. Different clocks.
  • Mutate, then invalidate — do not hand-patch a list you do not own.
  • Optimistic update = cancel, snapshot, patch, roll back on error, re-validate at the end.
  • Never copy query data into a store. Two copies, two lifetimes, one bug.

If you remember one thing: most "global state" is a cache, and a cache needs a cache library.

Ask: "quiz me on staleTime vs gcTime and on optimistic rollback." Both are common follow-ups.
