The 52-Week Plan

One page that holds the whole year, one week at a time. Four phases, thirteen modules, fifty-two weeks. Tick a skill when you can do it — not when you have read about it.

How a week works, at ~10 hours: about 2 hours on the lesson, 1 hour on the primary source, and 6–7 hours building the week's thing and running the drill. The build is the point. Reading without building produces someone who can talk about Node and not fix it.

Phase 1 · Weeks 1–13

The runtime

What Node actually is, and how async really works. Everything later stands on this.

Module 1 · Weeks 1–4 · The event loop

W1What Node really is core

Goal: stop calling Node a framework. It is V8 plus libuv plus a standard library — and libuv is where the "never waits" comes from.

Build: a script that proves the two halves are separate — a tight for loop that freezes everything, next to an fs read that does not.

Drill: "Node is single-threaded — so how does it serve 10,000 connections?" Answer in 60 seconds, no notes.

Primary: Introduction to Node.js · libuv design. Lesson: 0001.

W2The JavaScript Node leans on — an audit core

Goal: this is a check, not a course. You already write JavaScript. Confirm the four things Node uses constantly, and move on. If it is easy, this is a short week — that is the intended result.

Build: five small snippets — a closure that holds memory alive, this in four call shapes, a prototype chain, and module scope versus global.

Drill: Given a callback that lost its this, name three fixes and say which one you would ship.

Primary: MDN JavaScript. Lesson: 0002.

W3The event loop, up close core

Goal: know the phase order, and know that microtasks run between phases — not inside one.

Build: a print-order quiz you write yourself — ten files mixing sync, setTimeout, setImmediate, process.nextTick and Promise.then. Predict, then run.

Drill: Whiteboard the print order for sync + setTimeout(fn,0) + setImmediate(fn) + Promise.resolve().then(fn), and justify each position.

Primary: Event Loop, Timers and nextTick; talk — Bert Belder on the event loop. Lesson: 0003.

W4Build — a web server that never blocks core

Goal: turn the theory into a measurement. Prove, with numbers, that one blocking route ruins every other route.

Build: a raw http server with a fast route and a slow route, plus a small latency tester that hits the fast route while the slow one runs. Then make the slow route async and measure again.

Drill: "Your p99 latency jumped and CPU is at 100% on one core. What is your first hypothesis?"

Primary: Don't Block the Event Loop. Lesson: 0004.

Module 2 · Weeks 5–8 · The async model

W5The async ladder core

Goal: move between callbacks, promises and async/await in either direction, without thinking about it.

Build: take one callback-style API and write it three ways — raw callback, hand-built promise, and async/await. Keep all three in one file and compare.

Drill: Convert a three-level callback nest to async/await live, in under five minutes.

Primary: Asynchronous flow control · MDN: Using promises. Lesson: 0005.

W6Async errors and unhandled rejections core

Goal: understand why a try/catch can sit right there and still miss the error. This is the most common silent failure in production Node.

Build: reproduce an unhandled rejection on purpose, three different ways, then catch each one. Add an unhandledRejection handler and watch what it does and does not save.

Drill: "A request sometimes returns 200 with an empty body and nothing is logged." Walk through how you would find it.

Primary: Errors · Node Best Practices §2. Lesson: 0006.

W7Many things at once, with a limit core

Goal: Promise.all over a big array is a way to kill your own service. Learn the combinators, then write the limiter yourself.

Build: your own pLimit in under 40 lines — a queue plus a running count. Then read p-limit and compare.

Drill: Write a concurrency limiter live, from an empty file, in ten minutes.

Primary: MDN: Promise · undici. Lesson: 0007.

W8Build — the concurrent multi-API aggregator core

Goal: put the whole async model into one tool that survives a flaky network.

Build: fetch 500 URLs, 10 at a time, with retry-and-backoff, a per-request timeout, and a final report of what succeeded, what failed, and why.

Drill: "500 URLs, 10 at a time, retries, timeouts" — write it live, no notes. This is a real interview question.

Primary: AbortController. Lesson: 0008.

Module 3 · Weeks 9–12 · Modules, packages, and a real CLI

W9CommonJS versus ESM, and how Node finds a file core

Goal: this is the error message that ruins evenings. Understand resolution well enough to read the error instead of guessing.

Build: one small package that works from both require() and import. Then break the resolution four ways on purpose and write down each error message.

Drill: "ERR_REQUIRE_ESM — explain what happened and give two fixes."

Primary: ESM · CommonJS modules. Lesson: 0009.

W10The process — argv, streams, exit codes core

Goal: a program that behaves properly in a shell. Right stream, right exit code, works in a pipe.

Build: a tool that reads from stdin when piped, reads a file when given a path, writes results to stdout and errors to stderr, and exits non-zero on failure. Test it inside a real pipeline.

Drill: "Your CLI works alone but prints nothing through | head." Name the cause.

Primary: process · util.parseArgs. Lesson: 0010.

W11package.json in full, and publishing depth

Goal: depth, not core — you will do this a few times a year, not weekly. But shipping one package teaches what reading about it cannot.

Build: publish a small scoped package to npm. Scoped, so you can unpublish it without shame.

Drill: "A minor version bump broke our build. Whose fault, and how do you stop it happening again?"

Primary: packages · Publishing a package. Lesson: 0011.

W12Build — ship the CLI core

Goal: one finished, installable tool. Finished means someone else can install it and it does not surprise them.

Build: a bulk file renamer with --dry-run, --help, colour-free output when not a TTY, and a real README. Install it globally and use it on your own files.

Drill: Demo the tool in 90 seconds and name one thing you deliberately left out.

Primary: your own README. Lesson: 0012. Post the tool to r/node for review.

W13Review — the runtime and the async model review

Goal: no new material. Pull weeks 1–12 back out of memory, mixed up on purpose. Retrieval is what makes it stick; re-reading is not.

Do: close every tab. Write, from memory: the loop phases, a concurrency limiter, and a promise wrapper around a callback. Then check.

Community: ask one real question in the Node.js Discord. Not a lurk — a question.

Ask your teacher: "Run mock interview 1."

Phase 2 · Weeks 14–26

The hard core

Streams, servers built from raw sockets, and using more than one thread. The parts people avoid.

Module 4 · Weeks 14–17 · Streams, buffers and backpressure

W14Buffers and binary core

Goal: understand why Node needed its own byte type, and what a string really costs.

Build: read a file byte-range by hand. Decode a multi-byte UTF-8 character split across two chunks — get the mojibake on purpose, then fix it with StringDecoder.

Drill: "Your file upload works for English and corrupts Vietnamese." Name the cause in one sentence.

Primary: buffer. Lesson: 0014.

W15Readable, Writable, and backpressure core

Goal: backpressure is the whole reason streams exist. A fast producer must not be able to drown a slow consumer.

Build: a file copier that ignores the return value of write() and watch memory climb. Then honour it with drain and watch memory stay flat. Two graphs.

Drill: "A worker copying S3 files runs out of memory on big files only." Explain and fix.

Primary: Backpressuring in Streams · stream. Lesson: 0015.

W16Transform streams and pipeline core

Goal: chain stages safely. pipe leaks on error; pipeline is the one you actually use.

Build: a three-stage pipeline — parse, transform, write. Throw from the middle stage on purpose, and prove with pipe that the file handle leaks, then prove with pipeline that it does not.

Drill: "Why is pipeline preferred over pipe?" Answer with the failure it prevents, not with "it is better".

Primary: stream.pipeline. Lesson: 0016.

W17Build — a processor for a file too big for memory core

Goal: constant memory over a multi-GB input. This is the stream lesson that cannot be faked.

Build: generate a 4 GB CSV or log file. Process it — parse, filter, aggregate, write — while resident memory stays flat. Chart the memory over the run.

Drill: "Process a 50 GB log and count errors by hour. Sketch it." Ten minutes, out loud.

Primary: How to use streams. Lesson: 0017.

Module 5 · Weeks 18–21 · Events and servers from scratch

W18EventEmitter — the pattern under everything core

Goal: streams, servers, sockets and processes are all emitters. Learn it once and four things become obvious.

Build: write your own EventEmitter in about 30 lines. Then add a listener in a loop until Node prints the max-listeners warning, and explain what that warning is really telling you.

Drill: "MaxListenersExceededWarning in production." Is it a leak? How do you tell?

Primary: events. Lesson: 0018.

W19Raw TCP with net depth

Goal: depth on purpose. You will rarely write raw TCP. But writing it once is how message framing stops being a mystery.

Build: a TCP chat server. Send two messages fast and watch them arrive glued together. Then fix it with length-prefix framing.

Drill: "Two JSON messages arrived as one string." Explain the cause in 30 seconds.

Primary: net. Lesson: 0019.

W20HTTP from scratch core

Goal: know the request and response lifecycle before a framework hides it. Then a framework bug is readable instead of magic.

Build: a router with no framework — method and path matching, body parsing with a size limit, JSON responses, correct status codes, and keep-alive handled.

Drill: "Write a route handler that streams a large file to the client without buffering it."

Primary: http. Lesson: 0020.

W21Build — the spine API, version 1 core

Goal: the service you will keep for the next 30 weeks starts here. Raw http, no framework, small on purpose.

Build: a REST API on raw http — a handful of resources, in-memory storage for now, real status codes, one consistent error shape. Do not restart this project later.

Drill: Draw your API's request lifecycle on paper — socket to response — in five minutes.

Primary: http · Node Best Practices. Lesson: 0021.

Module 6 · Weeks 22–25 · Concurrency and scale

W22CPU-bound versus I/O-bound core

Goal: know which problem you have before choosing a tool. Most "Node is slow" claims are one CPU-bound function.

Build: measure event-loop delay under an I/O-heavy load and under a CPU-heavy load. Two very different graphs from the same server.

Drill: "Our image-resize endpoint makes the health check fail." Diagnose before touching code.

Primary: Don't Block the Event Loop · libuv design. Lesson: 0022.

W23Worker threads and a worker pool core

Goal: move CPU work off the main thread, and understand what crossing that boundary costs.

Build: your own worker pool — a fixed set of workers, a task queue, and a promise per task. Measure the cost of transferring data versus copying it.

Drill: "When would a worker thread make things slower?" Give a concrete case.

Primary: worker_threads. Lesson: 0023.

W24Child processes and cluster core

Goal: use every core on the machine, and know the difference between a thread and a process here.

Build: cluster the spine API across all cores. Prove every worker is serving. Kill one worker under load and watch it come back with no dropped connections.

Drill: "Sessions work locally and log users out randomly in production." Name the cause.

Primary: cluster · child_process. Lesson: 0024.

W25Build — an image-thumbnail service core

Goal: one service that is genuinely CPU-heavy, made responsive. This is the story you tell in an interview.

Build: upload an image, get thumbnails back. Worker pool for the resizing, cluster for the cores, and a health check that stays green under load. Measure before and after.

Drill: Present the before/after numbers in 90 seconds, and say what you would do next with more time.

Primary: autocannon. Lesson: 0025. Post the repo to r/node for review.

W26Review — the mid-year gate review

Goal: half the year is gone. This week decides whether the second half is built on something solid or on gaps.

Do: from an empty file, rebuild three things from memory — a Transform stream, a worker pool, and a concurrency limiter. No looking.

Gate: if you cannot explain backpressure and worker threads without notes, repeat weeks 14–17 before going on. Feelings do not count here.

Ask your teacher: "Run mock interview 2."

Phase 3 · Weeks 27–39

Production

Turning a program that works into a service that survives real traffic — and proving it with numbers.

Module 7 · Weeks 27–30 · Reliability

W27Signals and graceful shutdown core

Goal: this is the line between a script and a service. A deploy must not drop a single in-flight request.

Build: handle SIGTERM on the spine API — stop accepting, finish in-flight work, close the server, exit. Then send SIGTERM while autocannon is running and prove zero errors.

Drill: "Every deploy produces a spike of 502s." Explain the cause and the fix.

Primary: process signal events. Lesson: 0027.

W28Operational errors versus programmer errors core

Goal: one of these you handle. The other you crash on. Mixing them up is how services corrupt data quietly.

Build: an error taxonomy for the spine API — a base AppError, an operational flag, and a top-level handler that restarts on programmer errors and responds on operational ones.

Drill: "Should you catch uncaughtException and keep running?" Argue both sides, then commit.

Primary: Node Best Practices — Error Handling · errors. Lesson: 0028.

W29Observability — logs you can trace depth

Goal: depth, but the useful kind. A log line you cannot tie to a request is nearly worthless during an incident.

Build: structured JSON logging with pino, a request id carried through every async hop with AsyncLocalStorage, and one diagnostics_channel subscriber.

Drill: "One user reports an error, no stack trace, 40 requests a second." Find it.

Primary: AsyncLocalStorage · diagnostics_channel. Lesson: 0029.

W30Build — harden the spine API core

Goal: attack your own service and make it survive. Numbers, not confidence.

Build: load-test with autocannon, then kill the process mid-load, restart it, run out of memory, and drop the database. Write down what happened each time and fix the worst one.

Drill: "Walk me through what happens to an in-flight request when the pod is killed."

Primary: autocannon. Lesson: 0030.

Module 8 · Weeks 31–34 · Performance and memory

W31Measure first core

Goal: a performance claim with no measurement behind it is an opinion. Learn the tools before touching any code.

Build: profile one slow route on the spine API with --cpu-prof and a Clinic flame graph. Find the hot function. Fix it. Profile again and show both graphs.

Drill: "The service is slow." What are the first three things you measure, in order?

Primary: Profiling a Node.js app · Clinic.js. Lesson: 0031.

W32Memory and heap snapshots core

Goal: find a leak and name the thing that held the reference. This is the debugging skill that has no ready answer online.

Build: plant a leak on purpose — a growing Map, a listener never removed, a closure holding a big buffer. Take two heap snapshots, diff them, and name the retainer for each.

Drill: "RSS grows 40 MB an hour and never comes down." Walk through your investigation.

Primary: Memory diagnostics · V8 docs. Lesson: 0032.

W33The costs you can actually control depth

Goal: depth, and a discipline. Micro-optimisation is mostly a waste — so every change this week must be justified by a measurement.

Build: benchmark three candidate changes — JSON handling, buffer reuse, an in-process cache. Keep only the ones that measured better. Write down the ones you threw away.

Drill: "Is JSON.parse your bottleneck?" Say how you would find out, not whether it is.

Primary: perf_hooks. Lesson: 0033.

W34Build — find and fix a real leak, and write it up core

Goal: the write-up is the deliverable. An engineer who can explain a leak they fixed beats one who fixed it silently.

Build: run the spine API under sustained load for an hour. Find whatever actually leaks or slows down. Fix it. Write a one-page report: symptom, hypothesis, evidence, fix, proof.

Drill: Tell the leak story as an interview answer. Symptom, investigation, fix, proof, lesson.

Primary: your own report. Lesson: 0034.

Module 9 · Weeks 35–38 · Testing, debugging and security

W35node:test — the built-in runner core

Goal: Node ships a test runner now. Use it, and understand what a test is actually proving.

Build: cover the spine API's core paths with node:test — the happy path, the 404, the 409, and the validation failures. Turn on coverage and read it critically.

Drill: "What would you test first on a service you did not write?"

Primary: node:test · Test runner intro. Lesson: 0035.

W36Async tests without flakes core

Goal: a flaky test is worse than no test, because it teaches the team to ignore a red build.

Build: delete every setTimeout from your test suite. Replace waiting with fake timers, mocks, and real signals. Run the suite 50 times and require 50 passes.

Drill: "This test passes locally and fails in CI one time in ten." Name three suspects.

Primary: node:test mocking. Lesson: 0036.

W37The inspector, and hardening your input core

Goal: debug with a real debugger, not console.log. Then attack your own API before somebody else does.

Build: attack the spine API yourself — injection, prototype pollution, an unbounded request body, a ReDoS regex, a path traversal. Fix each one. Debug the fixes with --inspect, not logs.

Drill: "Name three ways a JSON body can hurt a Node service." Then fix all three.

Primary: Security best practices · OWASP Node.js Cheat Sheet. Lesson: 0037.

W38Build — the full suite and the security pass core

Goal: the spine API becomes something you would let a stranger deploy.

Build: a complete test suite that runs in CI, a documented coverage number you can defend, and a written security pass listing what you checked and what you accepted.

Drill: Judge a stranger's Node project out loud. What is wrong, and why does it matter?

Primary: Node Best Practices as a checklist. Lesson: 0038.

W39Review — production readiness review

Goal: pull weeks 27–38 back out cold, and interleave them with phase 1 and 2 material so nothing has quietly rotted.

Do: from memory, write the graceful-shutdown handler and the error taxonomy. Then re-do one week-13 drill and one week-26 drill.

Gate: you should now be able to take a Node service you have never seen and say what will break first. If not, name the gap and spend the week on it.

Ask your teacher: "Run mock interview 3."

Phase 4 · Weeks 40–52

Professional

The data layer, TypeScript, NestJS — then saying all of it out loud under pressure.

Module 10 · Weeks 40–43 · The data layer

W40Postgres — pools, transactions, and N+1 core

Goal: the database is where most Node latency actually lives. Learn the pool before the ORM.

Build: give the spine API real persistence with node-postgres. Turn on query logging, create an N+1 on purpose, see it in the log, then fix it.

Drill: "The API hangs under load but CPU is idle." Name the most likely cause.

Primary: node-postgres. Lesson: 0040.

W41Redis, and the three ways a cache lies core

Goal: caching is easy to add and easy to get subtly wrong. Learn the failure modes with the win.

Build: add Redis caching to the spine API. Then create a stale-read bug on purpose, a thundering-herd on cold start, and an unbounded key growth. Fix all three.

Drill: "Users see old data 30 seconds after saving." Explain and fix.

Primary: Redis developer docs. Lesson: 0041.

W42Background work — queues, retries, idempotency core

Goal: slow work does not belong in a request. Learn the queue, and learn why a retry can charge a customer twice.

Build: move the slowest route to a BullMQ job. Add retries, a dead-letter path, and an idempotency key. Then run the same job twice on purpose and prove nothing broke.

Drill: "A retry sent the email twice." Design the fix in five minutes.

Primary: BullMQ. Lesson: 0042.

W43Build — the spine API with a real data layer core

Goal: Postgres, Redis and a queue in one service, all three under load, all three with a tested failure path.

Build: the full data layer, running together. Then take each dependency down in turn while load is running, and record what the API does each time.

Drill: "Walk me through a request from socket to database and back." Five minutes, whiteboard.

Primary: your own architecture diagram. Lesson: 0043.

Module 11 · Weeks 44–46 · TypeScript for Node

W44The type system you actually need core

Goal: not all of TypeScript. The parts that catch real Node bugs: narrowing, generics, unknown, and discriminated unions.

Build: type the trickiest function in the spine API — the one with an ambiguous return. Then type the error taxonomy from week 28 as a discriminated union.

Drill: "Type a function that returns a user or a not-found error." No any, no throw.

Primary: TypeScript docs. Lesson: 0044.

W45The build setup depth

Goal: depth, and mostly a one-time cost. But a stack trace pointing at compiled JavaScript wastes hours, so it is worth one week.

Build: a working tsconfig.json for Node ESM, tsx for development, a real build for production, and source maps so a stack trace names your .ts line.

Drill: "It compiles but crashes at run time with a module error." Name two causes.

Primary: tsconfig reference · Node + TypeScript. Lesson: 0045.

W46Build — migrate the spine API to TypeScript core

Goal: the whole service, typed, with no any left that you cannot defend.

Build: migrate file by file, keeping the tests green at every step. Keep a list of every place the compiler found a real bug — that list is the argument for TypeScript.

Drill: "Was TypeScript worth it here?" Answer with your bug list, not with an opinion.

Primary: your own migration commits. Lesson: 0046.

Module 12 · Weeks 47–50 · NestJS

W47Modules and dependency injection core

Goal: understand what Nest is for before learning its syntax. DI is the whole point; decorators are packaging.

Build: the same small service twice — once wired by hand, once with Nest's container. Then swap one dependency for a fake in both, and compare how much code moved.

Drill: "Why NestJS and not Express?" Give a real trade-off, not a feature list.

Primary: NestJS providers. Lesson: 0047.

W48Controllers, pipes, guards, interceptors core

Goal: know which of the four to reach for, and in what order Nest runs them.

Build: port the spine API's routes into Nest. Validation in a pipe, auth in a guard, logging in an interceptor, errors in a filter. Nothing in a controller that does not belong there.

Drill: "Where does rate limiting go, and why not in the controller?"

Primary: NestJS docs. Lesson: 0048.

W49Testing and data in Nest core

Goal: DI pays for itself in tests or it does not pay at all. Prove it here.

Build: port the week 35–38 test suite to Nest's testing module. Swap the real database for a fake in one line. Then run the same suite against the real one.

Drill: "Show me a unit test where DI genuinely saved you work."

Primary: NestJS testing. Lesson: 0049.

W50Build — the spine API, rebuilt in NestJS core

Goal: the same service, professionally shaped. Same tests, same load numbers, and an honest verdict on what Nest cost.

Build: the complete rebuild — modules, DI, the data layer, the queue, the tests, graceful shutdown. Load-test it and compare with the week 30 numbers.

Drill: Present the rebuild in five minutes, including one thing you would do differently.

Primary: NestJS docs. Post the repo for community review. Lesson: 0050.

Module 13 · Weeks 51–52 · The interview

W51System design, for Node specifically core

Goal: general system design is everywhere. The Node-specific judgement — when a worker pool, when a separate service, when not Node at all — is rare and is what gets you hired.

Build: design one real system end to end on paper. "Send 1 million notifications an hour." Queues, workers, rate limits, retries, failure modes, and the cost. Then defend every box.

Drill: "Design a service that sends 1M notifications an hour." 45 minutes, whiteboard, out loud.

Primary: your own 12 builds. Ask your teacher for a design round. Lesson: 0051.

W52Review — the final gate review

Goal: the year is over when you can say all of it out loud, under pressure, with no notes. Not when you have read all of it.

Do: a full mock loop — one live-coding round, one debugging round, one system-design round, one "tell me about something you built" round. Recorded, then reviewed.

Final gate: record yourself answering ten questions cold. Watch it back. The gaps you see are next year's syllabus.

Ask your teacher: "Run the final mock loop."
