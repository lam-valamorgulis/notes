Why one service, and not thirty more toys

A toy teaches an idea. It cannot teach the things that only appear over time:

  • Change is expensive. Week 46 migrates this to TypeScript. That only means something if the code was written before you knew it was coming.
  • Numbers need a baseline. Week 30 load-tests it, week 34 fixes a leak, week 50 rebuilds it in NestJS. Each of those compares against this week's numbers. There is nothing to compare a toy to.
  • Decisions have consequences. The error shape you pick today is the one an exception filter has to reproduce in week 48. Choosing badly is part of the lesson.

Decide the error shape now, once

This is the decision with the longest reach. Every route, every middleware, every test and eventually a NestJS exception filter has to agree with it.

{
  "error": {
    "code": "code_taken",                        // stable, machine-readable
    "message": "That short code is already in use.",   // for a human
    "details": { "code": "abc123" }              // optional, structured
  }
}

Three properties, and each earns its place:

  • code is what a client branches on. It must never change, even when the wording does. Rewording a message is a patch; renaming a code is a breaking change.
  • message is for a person reading a log or a screen. It may be reworded freely.
  • details is structured, so a client can show which field was wrong without parsing English.
The mistake this avoids The common shape is { "error": "That short code is already in use." }. It works until a client needs to branch on the failure, and then somebody writes if (err.includes('already in use')). Now your error text is an API, and improving the wording breaks a customer. Give clients something stable to branch on, so the words stay yours.

Status codes, and the one people get wrong

CodeWhenNote
200Read succeeded—
201CreatedMust include a Location header pointing at the new thing.
301 / 302The redirect itself302 here. A 301 is cached by browsers forever, and you cannot take it back.
400The request is malformedBroken JSON, missing field, not a URL.
404No such code—
409The request is valid but conflicts with the current stateThe one people get wrong. See below.
413Body over the limitWeek 20's rule.
500You brokeNever leak a stack trace into it.

400 against 409 is the useful distinction. Ask: could this exact request have succeeded a minute ago? If no, it is a 400: the JSON is broken, or the URL is not a URL. Retrying will never help.

If yes, and it only fails because of what exists now, it is a 409. A client can act on that difference. A 409 means “pick another code”. A 400 means “your request is wrong”.

Choose 302, and know why A 301 is a permanent redirect, and browsers cache it aggressively — sometimes until the user clears their history. Ship a 301 by mistake and you cannot change where that link points, for anyone who has already followed it. 302 gives up a little speed and keeps control. That is the trade, and it is exactly the kind of thing week 21 exists to make you decide deliberately.
Say it in the simplest words — the Feynman check

1 · In plain words Until now you built a new small thing each week and threw it away. From today you build one thing and keep it.

Each later week does not add a feature. It makes the same program survive something it could not survive before: being shut down, being overloaded, losing its database. You cannot practise that on something you built yesterday.

2 · One analogy Learning to drive. You can practise turning, braking and parking separately in an empty car park. But you only learn to drive by keeping one car on one road, in traffic, for a long time.

…and where the analogy breaks A car does not get worse because you drove it badly last month. Your code does. Week 33's version carries every shortcut week 21 took.

That is not a flaw in the exercise — it is the exercise. Living with your own old decision, and paying to change it, is the thing a toy can never teach. The error shape you choose today is the one week 48 must reproduce in a NestJS filter. That holds whether you still like it or not.

The value is not in the code. It is in the baseline. Week 30 measures p99 against this week's p99. Week 34 compares memory against this week's memory. Week 50 compares NestJS against this week's raw http. Rewrite it in week 33 and every one of those comparisons is gone. The ugliness is the data.

Build it for real — the spine, version 1

Raw http, no framework, no database. In-memory storage is correct for this week. Week 24 shows exactly why it stops being correct, and that lesson needs the mistake to exist first.

The routes:

RouteDoesReturns
POST /linksCreate a short code for a URL201 + Location, or 400, or 409
GET /links/:codeRead one link and its click count200 or 404
GET /:codeRedirect, and count the click302 or 404
DELETE /links/:codeRemove it204 or 404
GET /healthLiveness200

Requirements. Every one is a decision you will be asked about later:

  1. One sendError(res, status, code, message, details) helper. Every failure goes through it. No route writes an error body by hand.
  2. A validation step that rejects a non-URL with 400 and a code of invalid_url. Use the URL constructor, not a regular expression.
  3. A duplicate custom code returns 409, not 400. Be able to say why.
  4. The 1 MB body limit from week 20, returning 413.
  5. Every handler ends the response on every path. Prove it — see the check below.
  6. A README.md that says what this service is, and one paragraph headed “What this does not do yet”.

The one helper that matters

function sendError(res, status, code, message, details) {
  if (res.headersSent) return res.destroy();     // week 20 — too late for a clean reply
  const body = JSON.stringify({ error: { code, message, ...(details && { details }) } });
  res.writeHead(status, {
    'content-type': 'application/json',
    'content-length': Buffer.byteLength(body),   // week 14 — bytes, not characters
  });
  res.end(body);
}
