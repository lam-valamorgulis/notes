Testing and data in Nest

Dependency injection pays for itself in tests, or it does not pay at all. Prove it here.

coreWeek 49 of 52. This lesson builds one domain-expert ability: collect the evidence that a design choice paid off. Week 49 in the plan · Glossary

Your win today: a one-line database swap, and the number that says what it costs — 0.33 ms per test. That is the whole bill for the container, and now you can defend it.
Where you are Week 47 claimed the container earns its keep in tests. This week is where that claim gets checked, and where the data layer from weeks 40–43 goes in without infecting the whole codebase.

Start from the problem — why is a fake database hard?

Not because writing a fake is hard. Because of where the real one is named.

// this service can never be tested without Postgres
import { pool } from '../db.js';
class LinkService {
  async resolve(code) { return pool.query('select url from links where code=$1', [code]); }
}

The dependency is not a parameter. It is an import, resolved at module load, before anybody can intervene. To swap it you must intercept the module system. That is where mocking libraries come from, and where test suites go to become unmaintainable.

The whole reason injection helps here

If a dependency arrives as a constructor argument, swapping it needs no cleverness at all. It is just a different argument.

The swap, and the three ways to do it

All three are one line, and they differ in what you hand over. Measured on NestJS 12.0.1:

.overrideProvider(Store).useClass(FakeStore)        // https://fake
.overrideProvider(Store).useValue({ find: async () => … })   // https://stub
.overrideProvider(Store).useFactory({ factory: () => … })    // https://made
StyleUse it when
useClassThe fake has real behaviour worth reusing — an in-memory store.
useValueA stub for one test. Also where a mock.fn from week 36 goes.
useFactoryThe fake needs building, or needs other providers injected into it.

Set against a swap that would otherwise cost one rebuild per level of your graph, that is a bargain — and you can now say so with a number instead of a feeling.

Not everything is that cheap. Compare a unit test with an end-to-end one:

And that 38 ms is the optimistic number The handler measured here does nothing. A real end-to-end test also starts the app, connects to a database, and often resets it between cases. The HTTP is never the expensive part.

So the question is not “is end-to-end slower?” It is “what does it check that a unit test cannot?” The guard, the pipe, the filter, the serialisation, and the wiring itself. That is a real list, and it is why some tests must be end-to-end.

Wiring the data layer without spreading it everywhere

The mistake is letting pg types reach your service. Then every test needs Postgres, and a database change touches files that have nothing to do with data.

Define the dependency in your own words, and inject it by a token:

// the port — no framework, no pg. this is your language.
export interface LinkStore {
  find(code: string): Promise<{ code: string; url: string } | undefined>;
}
export const LINK_STORE = Symbol('LINK_STORE');

// the adapter — the ONLY file that knows Postgres exists
@Injectable() class PgLinkStore implements LinkStore { … }

// the service depends on the interface, never the adapter
@Injectable() class LinkService {
  constructor(@Inject(LINK_STORE) private store: LinkStore) {}
  async resolve(code: string) { return (await this.store.find(code))?.url ?? null; }
}

@Module({ providers: [LinkService, { provide: LINK_STORE, useClass: PgLinkStore }] })
class LinksModule {}

Now the swap is the same one line, and the in-memory version is a real implementation rather than a mock. Measured:

  real adapter : https://from-postgres
  swapped      : https://memory
  missing key  : null
Why a Symbol token, and why implements An interface does not exist at run time, so Nest cannot inject by it — you need a token, and a Symbol cannot collide with anything. And implements LinkStore on both the real adapter and the fake means the compiler keeps them in step. A fake that drifts from the real thing is a test that proves nothing, and week 44's checker is what stops that.

When is an end-to-end test worth its slowness?

When it checks something a unit test structurally cannot:

Worth it end-to-endNot worth it
The guard actually blocks the routeA pure function's branches
The pipe rejects a bad body with 400A calculation with many cases
The filter turns your error into the right statusAnything you can call directly
The wiring is correct — providers resolveA repeat of a unit test, but slower
A real transaction commits and rolls backBehaviour you have already covered

Look at the left column: every row is something that only exists once the pieces are joined together. That is the definition, and it is a short list. A large end-to-end suite is usually a unit-test suite in a slow costume.

Say it in the simplest words — the Feynman check

1 · In plain words A fake database is easy to write. What makes it hard is where the real one is named. If a service imports the database directly, that choice was made when the file loaded, before any test could intervene.

If it arrives as a constructor argument instead, swapping it needs no cleverness. It is just a different argument, and the container makes that one line.

2 · One analogy A socket in a wall. The lamp does not care what is behind it, so you can test the lamp on any supply. If the lamp were soldered to the mains, you could only test it in one building.

…and where the analogy breaks A socket has a physical shape, so a bad plug will not fit. An interface is erased before the program runs. So nothing at run time stops a fake drifting away from the real thing.

That is why both classes say implements LinkStore — the compiler becomes the shape of the socket. It is also why the injection needs a Symbol token. Nest cannot inject by an interface that no longer exists at run time. A fake that has quietly drifted is worse than no test, because it still passes.

3 · The sticking point People assume the container is too slow for tests, or that it is free. Neither. Measured: createTestingModule().compile() costs 0.33 ms, against effectively zero for a plain new.

A thousand tests is a third of a second, once. That is the whole bill, and it is worth saying out loud. “Dependency injection makes tests easier” is an opinion. 0.33 ms for a one-line swap is an argument.

4 · Now you explain it back

In three sentences, explain why importing your database module directly makes a service hard to test. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — port the suite, then prove the claim

Requirements:

  1. Port the week 35–38 tests to Nest's testing module. Same assertions. If an assertion had to change, ask whether the behaviour changed or only the plumbing.
  2. Define ports for Postgres, the cache and the queue — interfaces in your own words, injected by Symbol tokens.
  3. Both the real adapter and the fake say implements. Break one on purpose and confirm the compiler catches the drift.
  4. Swap the database in one line. Then run the identical suite against the real one, changing nothing else.
  5. Time your suite with and without the container. Write the number down. Defend it or drop the container.
  6. Keep end-to-end tests for the short list: the guard blocks, the pipe rejects, the filter maps, a transaction rolls back.
  7. Find one end-to-end test that is really a unit test in a slow costume, and rewrite it.
The drill

“Show me a unit test where dependency injection genuinely saved you work.”

Show the test, then show what it would have looked like without the container — every level of the graph rebuilt by hand. The comparison is the answer. If the two versions look about the same, you have found a place where the container is not earning its keep, and saying that is a better answer than pretending.

Say it like an interviewer just asked

What this lesson left out on purpose Testcontainers — a real Postgres per test run in Docker — is the honest answer for the data layer and worth adopting. @nestjs/typeorm and Prisma integrate an ORM into the container, with the trade-offs from week 40. Transactional tests, where each case rolls back, are a fast way to keep a database suite isolated. Contract tests keep a fake and its real implementation honest at run time, which is the gap the compiler cannot close alone.

Remember this · the 20-second recap
  • A fake is easy; the problem is where the real one is named. An import is decided at load time, before a test can act.
  • A constructor argument needs no cleverness to swap. That is the entire benefit.
  • Three one-line overrides: useClass for real behaviour, useValue for a stub, useFactory when the fake needs building.
  • Measured: 0.33 ms per createTestingModule().compile() — a third of a second across a thousand tests.
  • Define ports in your own words and inject by a Symbol, so only the adapter imports pg.
  • implements on both the real and the fake makes the compiler stop them drifting apart.
  • End-to-end only for what unit tests structurally cannot reach: the guard, the pipe, the filter, the wiring, a real transaction.

If you remember one thing: a drifted fake is worse than no test, because it still passes.
