The inspector, and hardening your input

Attack your own API before somebody else does. Then debug the fixes with a real debugger.

coreWeek 37 of 52. This lesson builds one domain-expert ability: find the input that breaks a service, and say what it costs. Week 37 in the plan · Glossary

Your win today: a 32-character string that freezes your whole server for half a minute. You will measure it, understand why, and fix it in one line.
Where you are Weeks 35 and 36 checked that the spine does what you meant. This week checks what it does when someone means you harm. Those are different questions, and the second one has no test suite by default.

Start from the problem — where does trust end?

Your service has a line around it. Inside the line, you wrote everything. Outside, a stranger did. Every security bug in this lesson is the same mistake: something crossed the line without being checked.

The rule for the boundary

At the edge, reject — do not coerce. Turning bad input into something usable is how bad input gets in. If you cannot say exactly what shape you want, you cannot defend it.

Coercion feels helpful. The user sent a number as a string, so you call Number(). They sent an odd URL, so you clean it up. Each small kindness moves the check from “is this allowed?” to “can I make this work?” Those are opposite questions.

Attack 1 — the URL that is not a URL

The spine stores a URL and later redirects to it. Obvious validation: does it parse? Verified on Node v24.14.0:

new URL('javascript:alert(1)')
  ACCEPTED -> protocol=javascript:
new URL('data:text/html,<script>alert(1)</script>')
  ACCEPTED -> protocol=data:
new URL('file:///etc/passwd')
  ACCEPTED -> protocol=file:
“It parsed” is not validation new URL tells you the string is a well-formed URL. It never says the URL is one you should send a person to. Store javascript:alert(1), redirect a browser to it, and you have published a cross-site scripting attack on your own domain.

The fix is an allow-list of protocols. Not a block-list — you cannot list every scheme an attacker might find.

function isSafeTarget(raw) {
  let u;
  try { u = new URL(raw); } catch { return false; }        // not a URL at all
  return u.protocol === 'http:' || u.protocol === 'https:';
}
  DENY  "javascript:alert(1)"
  DENY  "data:text/html,<script>alert(1)</script>"
  DENY  "file:///etc/passwd"
  allow "https://ok.test/a"

Now the part most write-ups stop before. Run one more input through the same allow-list:

  allow "http://169.254.169.254/latest/meta-data/"
That address is not a website 169.254.169.254 is the cloud metadata endpoint. On many hosts it hands out credentials to anything that asks from inside the machine. It is plain http:, so the protocol allow-list lets it through.

This is the server-side request forgery shape. It only becomes a real hole if your server fetches the URL. A 302 redirect makes the browser fetch it, which is a much smaller problem. The distinction is the whole risk assessment, and it is yours to make and write down.

So the honest position after one fix is this. Protocol closed. Private addresses accepted on purpose, because we redirect rather than fetch. That sentence belongs in your security pass next week. A layer you chose not to add is fine. A layer you did not notice is not.

Attack 2 — prototype pollution

A recursive merge, the kind in every codebase for merging options or settings:

function merge(target, src) {
  for (const k in src) {
    if (typeof src[k] === 'object' && src[k] !== null) {
      target[k] = target[k] || {};
      merge(target[k], src[k]);                  // k can be "__proto__"
    } else target[k] = src[k];
  }
  return target;
}

merge({}, JSON.parse('{"__proto__":{"isAdmin":true}}'));

Measured immediately afterwards:

  after merge, ({}).isAdmin = true
  a brand new unrelated object: {"name":"x"} -> isAdmin = true

Read that twice. Not the merged object. Every object in the process, including ones created later, in code that never heard of this request. Any if (user.isAdmin) anywhere is now true.

Now the detail that tells you where the bug actually is:

const o = JSON.parse('{"__proto__":{"x":1}}');
  ({}).x = undefined
  own properties of the parsed object: [ '__proto__' ]
JSON.parse is not the problem It puts __proto__ in as an ordinary own key. Nothing is polluted yet. The damage happens when your code copies that key onto another object — a merge, an Object.assign, a for...in loop that assigns. So do not go looking for a safer parser. Look at your own assignment code.

Two fixes, and it is worth knowing why the second one works:

// 1 — refuse the dangerous keys, at the boundary
const BAD = ['__proto__', 'constructor', 'prototype'];
if (BAD.includes(k)) continue;

// 2 — merge into an object that has no prototype to pollute
const clean = Object.create(null);
  Object.getPrototypeOf(clean) = null
merge(clean, JSON.parse('{"__proto__":{"isAdmin":true}}'));
  ({}).isAdmin = undefined          <- nothing leaked
  clean own keys = [ '__proto__' ]  <- it became a plain key

With no prototype, __proto__ has no special meaning. It is just a string key holding data. That is the one-line version: an object with no prototype cannot have its prototype poisoned.

Attack 3 — one string, half a minute of downtime

Say you validate a code with a regex. Something innocent, like /^(a+)+$/. Feed it a string that almost matches, and measure. Verified:

Input lengthTime to fail the match
26 characters2,224 ms
28 characters1,760 ms
30 characters6,978 ms
32 characters27,874 ms

Two characters more, four times the wait. That is not a slow function. That is a curve, and the attacker chooses where you sit on it.

Now the part that matters for a server. A heartbeat every 10 ms, running while the regex runs:

const evil = /^(a+)+$/;
let beats = 0;
const timer = setInterval(() => { beats++; }, 10);
// ... then, on the next tick:
evil.test('a'.repeat(30) + '!');

regex took                    : 35893 ms
heartbeats expected during it : 3589
heartbeats that actually ran  : 0
Zero out of 3,589 Not “delayed”. Not “slow”. None ran. For 36 seconds the process did nothing else — no requests served, no health check answered, no shutdown signal handled.

This is week 22 arriving as an attack. Regular expressions run on the main thread, in C++, with no yielding. Your load balancer marks the instance unhealthy and moves the traffic to the next one. There, the attacker sends the same 32 characters.

The cause is backtracking. (a+)+ gives the engine many different ways to split the same run of as. When the string cannot match, it must try all of them before giving up. The number of ways doubles with each added character.

How to spot one before it ships Look for a repeat inside a repeat: (a+)+, (a*)*, (a|aa)+. Then ask the real question — does user input reach this regex? A slow regex on your own constant is a curiosity. The same regex on a request body is an outage.

The fix here is usually not a cleverer regex. It is a length limit before the match, plus a simpler pattern. /^[a-z0-9]{1,32}$/ has no nesting and cannot backtrack this way.

Attack 4 — path traversal, and the fix that is still wrong

Serve a file from a folder. The obvious code:

path.join('/srv/app/public', userInput)

  join("../../etc/passwd") -> /srv/etc/passwd        <- outside the folder
  join("ok.txt")           -> /srv/app/public/ok.txt

path.join resolves .. as part of its job. It is doing exactly what it promises. The mistake is believing it defends anything.

So people write the check. Here is the version that looks right and is not:

const full = path.resolve(ROOT, userInput);
if (full.startsWith(ROOT)) return full;          // looks fine…

  "../public-evil/secrets" -> /srv/app/public-evil/secrets     ACCEPTED
One missing separator /srv/app/public-evil/secrets starts with /srv/app/public. A sibling folder whose name merely begins with your folder's name walks straight through. Compare against ROOT + path.sep: 
if (full.startsWith(ROOT + path.sep)) return full;
  "../public-evil/secrets" -> null    DENIED
  "../../etc/passwd"       -> null    DENIED
  "ok.txt"                 -> /srv/app/public/ok.txt

This is the most useful lesson in the whole week. A fix you did not test is a fix you do not have. Both versions look correct while reading. Only one of them is.

Attack 5 — the body with no end

You already fixed this one in week 20: count bytes as they arrive and destroy the socket past the limit. Check it is still true, because it is the easiest protection to lose in a refactor to a framework.

curl -X POST http://localhost:3000/links \
  -H 'content-type: application/json' \
  --data-binary @<(head -c 5000000 /dev/zero | tr '\0' 'a')
# want: 413, fast, and memory flat while it happens
Never trust content-length It is a claim by the client, not a fact. Count the bytes you actually receive. A client can send a small content-length and then keep sending.

Now debug the fixes with a real debugger

You have five fixes to verify. console.log can do it, badly: edit, restart, read, repeat, then remove the logs and hope you got them all.

node --inspect server.js
Debugger listening on ws://127.0.0.1:9229/c3299a52-21e3-484b-bafa-a6fd9bcea632
For help, see: https://nodejs.org/en/docs/inspector

Open chrome://inspect, or use your editor's Node debugger. Two flags, and the difference matters:

FlagWhat it doesUse it when
--inspectOpens the port, runs normallyThe bug is in a request handler
--inspect-brkOpens the port, pauses before line oneThe bug is in startup or module loading

Verified: with --inspect-brk, a console.log on the first line never printed until a client attached. That is the whole point of it.

The feature worth learning today is the conditional breakpoint. Right-click a line number, choose Edit breakpoint, and give it an expression:

raw.startsWith('javascript:')          // stop only on the attack input
input.length > 24                      // stop only where the regex gets slow
!full.startsWith(ROOT + path.sep)      // stop only when the traversal check denies
Why this beats a log line, specifically A log tells you one value you thought to print. A breakpoint gives you the whole scope — every variable, the call stack, and the ability to run expressions right there. When you do not yet know which value is wrong, printing is guessing and the debugger is looking.
Say it in the simplest words — the Feynman check

1 · In plain words Your service has a line around it. Inside it, you wrote the code. Outside it, a stranger writes the input. Every bug in this lesson is one thing crossing that line unchecked.

So at the edge you reject rather than tidy up. A URL that parses is not a URL you should redirect to. A key called __proto__ is not a key you should copy. A 32-character string is not a string you should run a nested regex over.

2 · One analogy A door with a guest list. You are not judging whether someone looks respectable. You check the name against the list, and if it is not there they do not come in.

…and where the analogy breaks A guest list has one door. Your service has several, and each one lets a different thing through. The protocol list stopped javascript:, and still allowed http://169.254.169.254 — the cloud address that hands out credentials.

So one check is never “secure”. It closes one door. The professional habit is to say out loud which doors are shut, and which you left open on purpose. In the spine's case, we redirect the browser rather than fetch the URL. So that address is somebody else's problem. That is a decision, and it belongs in writing.

3 · The sticking point People look for the dangerous function — a safer JSON parser, a stricter URL class. That is the wrong hunt. JSON.parse does not pollute anything; it stores __proto__ as an ordinary own key.

The damage happens in your own merge, when you copy that key onto a normal object. The dangerous thing is usually plain code you wrote to be helpful, so no library upgrade will save you.

4 · Now you explain it back

In three sentences, explain how a 32-character string can take a server offline. Then say why a length limit fixes it. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — attack the spine, then fix it

Requirements. For each of the five, write the attack first, as a failing test:

  1. A bad scheme. Store javascript:alert(1) and follow the redirect. Then allow-list protocols. Then decide about 169.254.169.254 and write down which way you decided.
  2. Prototype pollution. Find every merge, Object.assign and for...in that touches request data. Pollute through one. Fix it. Prove ({}).isAdmin is undefined after.
  3. A slow regex. Check every regex that user input reaches. Add a length limit before the match. Measure the worst input before and after.
  4. Path traversal, if you serve any file. Write the startsWith(ROOT) version, watch ../public-evil pass, then add path.sep.
  5. An oversized body. Confirm 413 and flat memory, with the 5 MB curl above.
  6. Set one conditional breakpoint that stops only on an attack input. No console.log in this exercise at all.
Write the attack before the fix If you fix first, you never find out whether you were vulnerable, and you never find out whether the fix works. Two of the five fixes in this lesson look correct and are not — the missing path.sep, and the protocol allow-list that still permits the metadata address. Only a test tells them apart.

Remember this · the 20-second recap
  • At the boundary, reject — do not coerce. Coercion turns “is this allowed?” into “can I make this work?”.
  • new URL('javascript:alert(1)') succeeds. Allow-list the protocol — and note it still lets 169.254.169.254 through.
  • JSON.parse does not pollute — __proto__ becomes an own key. Your merge is the bug.
  • Object.create(null) has no prototype to poison. Or refuse __proto__, constructor, prototype.
  • /^(a+)+$/ on 30 characters: 35,893 ms, 0 of 3,589 heartbeats. Limit length before the match.
  • path.resolve then startsWith(ROOT + path.sep). Without path.sep, public-evil passes.
  • --inspect runs; --inspect-brk pauses before line one. Conditional breakpoints stop only on the attack.

If you remember one thing: a fix you did not attack is a fix you do not have.
