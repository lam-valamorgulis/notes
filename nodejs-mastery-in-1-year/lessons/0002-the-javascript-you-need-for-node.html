The JavaScript you actually need for Node

The handful of language ideas that make every Node program readable — closures above all.

Your win today: you'll be able to read almost any Node code without getting lost, and explain the one idea — the closure — that every callback, event handler, and middleware in Node secretly depends on. If Lesson 1 was "what Node is," this is "the language it runs."
Where you are In Lesson 1 you learned Node runs your JavaScript on one thread and hands slow work off with a callback. A callback is just a function — so today we learn exactly enough of the language to understand functions, and the closures that make callbacks work.

The 20% of JavaScript you use 80% of the time

JavaScript is a big language, but Node code leans on a small core again and again. We'll build up just that core, from first principles. Everything else you can learn as you meet it.

Values, and the one gotcha: copies vs links

JavaScript has two families of values, and the difference causes more bugs than anything else for beginners.

  • Primitives — number, string, boolean, null, undefined, bigint, symbol. When you assign or pass one, you get a copy.
  • Objects (including arrays and functions) — when you assign or pass one, you get a link (reference) to the same thing, not a copy.
let a = 5;
let b = a;      // b is a COPY
b = 99;
console.log(a); // 5  — a is untouched

const list1 = [1, 2, 3];
const list2 = list1;   // list2 LINKS to the same array
list2.push(4);
console.log(list1);    // [1, 2, 3, 4]  — both see the change!
Two things that trip everyone 1. const means the variable can't be reassigned — it does not make an object immutable (you can still push to a const array). 2. Always compare with === (checks value and type), never == (does surprising type conversions, e.g. 0 == '' is true).

Functions are values — this is why callbacks exist

In JavaScript a function is just another value. You can store it in a variable, pass it to another function, and return it from a function. That last two are the whole basis of Node's style.

// three ways to make a function — all are just values
function add(a, b) { return a + b; }
const sub = function (a, b) { return a - b; };
const mul = (a, b) => a * b;        // arrow function, short form

// passing a function INTO another function = a callback
setTimeout(() => console.log('runs later'), 100);
[1, 2, 3].forEach((n) => console.log(n));

A callback is nothing more exotic than "a function you hand to someone else, for them to call later." setTimeout, fs.readFile, and every event handler in Node work this way. Which raises the real question of this lesson…

Closures — the idea Node is built on

Here's the puzzle. A callback runs later — often long after the function that created it has finished and returned. So how does it still have access to the variables it needs? The answer is the closure, and it is the single most important JavaScript concept for Node.

Definition · say this out loud

A closure is a function together with the variables it "remembers" from where it was created. The function carries them like a backpack, even after the outer function has returned.

function makeCounter() {
  let count = 0;                 // a private variable
  return function () {
    count = count + 1;           // the inner function REMEMBERS count
    return count;
  };
}

const next = makeCounter();      // makeCounter has now returned...
console.log(next());  // 1
console.log(next());  // 2   ← count survived, because of the closure
console.log(next());  // 3

makeCounter already finished, yet count is still alive and private — the inner function kept it in its backpack. That is a closure. In Node, every asynchronous callback works this way: it runs later, but it still sees your variables because it closed over them.

The classic closure bug (interviewers love this) Using var in a loop shares one variable across every callback: 
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// prints 3 3 3  — all three closures share the SAME i

for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
// prints 0 1 2  — let gives each loop its OWN i

By the time the timers fire, the var loop has already finished and i is 3 — and all three closures point at that same i. let creates a fresh i each turn, so each closure remembers its own. This is closures and the event loop meeting in one tiny example — exactly what you learn next lesson.

this in one minute (and the bug to avoid)

In a normal function, this depends on how the function is called — which surprises people. An arrow function has no this of its own; it uses this from where it was written. The practical rule for now: in callbacks, prefer arrow functions, and you'll sidestep the most common this bug entirely. We'll go deeper only when a real situation needs it.

Build it for real — utilities every Node dev writes

Closures aren't academic — you use them to build small tools constantly. Let's build two that appear in real Node codebases. Save as utils.js and run with node utils.js.

utils.js

// once(fn): run fn only the first time; after that, return the first result.
// Real use: make sure an expensive setup runs exactly once.
function once(fn) {
  let called = false;
  let result;
  return (...args) => {
    if (!called) { called = true; result = fn(...args); }
    return result;
  };
}

const connect = once(() => {
  console.log('opening database connection...');
  return { db: 'connected' };
});

connect();   // logs "opening database connection..."
connect();   // (silent) returns the same cached connection

// memoize(fn): remember past answers so we never recompute them.
function memoize(fn) {
  const cache = new Map();
  return (n) => {
    if (cache.has(n)) return cache.get(n);
    const value = fn(n);
    cache.set(n, value);
    return value;
  };
}

const slowSquare = memoize((n) => { for (let i = 0; i < 1e7; i++) {} return n * n; });
console.log(slowSquare(9));  // slow the first time
console.log(slowSquare(9));  // instant — served from the closure's cache

Both tools work only because the returned function closes over private state (called, result, cache). You just used closures to build real things.

Remember this · the Feynman summary
  • Primitives copy; objects link. Changing a linked object is seen by everyone holding the link. const stops reassignment, not mutation.
  • Always compare with ===, never ==.
  • Functions are values — you can pass them around. A function passed to be called later is a callback.
  • A closure is a function plus the variables it remembers from where it was made — a backpack it keeps even after the outer function returns.
  • Every async callback in Node relies on closures to still see your variables when it finally runs.
  • The var-in-a-loop bug (all callbacks see the final value) is fixed by let, which gives each turn its own variable.

If you remember one thing: a closure is a function that carries a backpack of the variables it was born with — that's what makes callbacks work.
