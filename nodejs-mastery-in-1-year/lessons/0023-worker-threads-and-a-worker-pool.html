Worker threads and a worker pool

Move the heavy thinking off the main thread — and find out what crossing that boundary costs.

coreWeek 23 of 52. This lesson builds one domain-expert ability: say why it was built this way, and what that choice gives up. Week 23 in the plan · Glossary

Your win today: your own worker pool, and the three numbers that decide whether a worker is worth it. Measured: starting one costs 16 ms, a round trip costs 0.025 ms, and copying 50 MB costs 28 ms — or 2 ms if you transfer it instead.
Where you are Week 22 told you how to know the work is CPU-bound. This is the first of the two fixes. Week 24 is the other one.

Start from the problem — one thread cannot be in two places

Your JavaScript runs on one thread. CPU-bound work occupies it. There is no clever way round that inside one thread, so the only real answer is another thread.

But a thread that shares memory brings back everything JavaScript was designed to avoid. Two threads writing one variable, torn reads, locks, deadlocks. Node refused that. So it made a choice:

The design decision

A worker gets its own V8 instance, its own heap and its own event loop. Nothing is shared by default. Data is copied between threads, and you must ask explicitly for anything else.

That single choice explains everything else this week. No shared memory means no locks, no data races and no Mutex in your code. It also means every message has a cost, because copying is not free.

Prove the isolation

Send a worker two things: a plain object, and a SharedArrayBuffer. Change both inside the worker, then look from the main thread.

const shared = new Int32Array(new SharedArrayBuffer(4));
shared[0] = 1;
const plain = { n: 1 };
new Worker(__filename, { workerData: { buf: shared.buffer, plain } });

// inside the worker: set both to 99

The real output (Node v24.14.0):

shared: 99   |   plain: 1

The plain object was copied, so the worker changed its own copy and you never saw it. The SharedArrayBuffer is genuinely the same memory. That is the whole model in one line of output.

The three costs — measure them before you decide

CostMeasuredWhat it means for your design
Starting a worker16 msNever start one per request. Start a pool at boot.
One message round trip0.025 msCheap. Chattiness is not your problem.
Copying 50 MB28 msThis is your problem. Size, not frequency.
Transferring 50 MB2 ms14 times faster — see the trap below.

Read those together and the rule falls out. A worker is worth it when the work is much bigger than the data. Hashing a password — tiny input, 100 ms of CPU — is ideal. Filtering a 50 MB array to return a 50 MB array is not. You pay 56 ms in copying to save nothing.

Transfer is fast because it takes the data away from you postMessage(buf, [buf.buffer]) moves the memory instead of copying it. Verified: 50 MB in 2 ms instead of 28 ms. But afterwards, in the sending thread, buf.length is 0. The buffer is emptied — “detached” — and touching it throws. That is not a bug. It is the price: only one thread may own it, which is exactly what makes locks unnecessary.

Build the pool — a queue and a promise

Starting a worker costs 16 ms, so you start N once and reuse them. A pool is three things: idle workers, a queue of waiting jobs, and a promise per job.

class Pool {
  constructor(file, size = require('node:os').availableParallelism() - 1) {
    this.idle = [];
    this.queue = [];
    for (let i = 0; i < size; i++) this.idle.push(this.spawn(file));
  }

  spawn(file) {
    const w = new Worker(file);
    w.on('error', (err) => this.fail(w, err));         // week 18: never skip this
    w.on('exit', (code) => { if (code !== 0) this.fail(w, new Error('worker died')); });
    return w;
  }

  run(job) {
    return new Promise((resolve, reject) => {
      this.queue.push({ job, resolve, reject });
      this.pump();
    });
  }

  pump() {
    if (!this.queue.length || !this.idle.length) return;
    const worker = this.idle.pop();
    const { job, resolve, reject } = this.queue.shift();
    worker.current = { resolve, reject };
    worker.once('message', (result) => {
      worker.current = null;
      this.idle.push(worker);
      resolve(result);
      this.pump();                                      // take the next job
    });
    worker.postMessage(job);
  }
}

That is the same shape as the concurrency pool from week 7. N runners, a shared queue, one promise per job. The only new part is that the runners are real threads.

The line most people forget fail(w, err) — what happens when a worker dies mid-job. Without it, the caller's promise never settles and never rejects. The request just hangs, forever, with no error anywhere. This is week 20's missing res.end() wearing a different hat: a promise nobody will ever settle. Reject it, and start a replacement worker.
Say it in the simplest words — the Feynman check

1 · In plain words One person cannot do two hard jobs at once. So you hire helpers. But these helpers work in separate rooms, and they cannot see your desk.

To give one a job, you photocopy the papers and send the copy. That works, and it costs time when the pile is thick. So helpers are worth hiring when the thinking is long and the papers are few.

2 · One analogy A translator in a separate office. You post them a document, they work on it alone, and they post the translation back. Nobody edits the same page at the same time, so nothing gets scribbled over.

…and where the analogy breaks A real office could just walk down the corridor and read your copy. These cannot — the separation is total, and it is the point, not a limitation.

There is one exception, and the analogy has no equivalent. A SharedArrayBuffer is literally the same paper on both desks. Nothing is posted and nothing is copied. That is fast. It also brings back the problem the separation removed: two people can write on the same line at once.

3 · The sticking point People think a worker makes things faster. It moves work, and moving work costs money.

Starting one costs 16 ms, and copying 50 MB costs 28 ms. So a worker is slower whenever the data is large and the work is small. The test is not “is this slow?” but “is the thinking much bigger than the papers?” Hashing a password passes. Filtering a big array and returning a big array fails.

4 · Now you explain it back

In two or three sentences, describe a job where a worker thread would make things slower, and say why. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — the pool, and the three costs

Requirements:

  1. A Pool class: fixed size, a job queue, one promise per job.
  2. Handles a worker that dies mid-job — rejects the caller and starts a replacement.
  3. Sizing defaults to os.availableParallelism() - 1. Be able to say why you leave one.
  4. Measure all three costs yourself: startup, round trip, and 50 MB copied against transferred.
  5. Wire it into week 22's /slow-cpu route, and re-run the p99 experiment.

Remember this · the 20-second recap
  • A worker has its own V8, heap and event loop. Nothing is shared by default, so there are no locks.
  • Data is copied. Verified: a plain object came back as 1, a SharedArrayBuffer as 99.
  • Three costs: start 16 ms, round trip 0.025 ms, copy 50 MB 28 ms.
  • Transfer moves 50 MB in 2 ms — and empties the sender's buffer. Only one owner.
  • The rule: a worker pays off when the work is much bigger than the data.
  • Never start a worker per request. Start a pool at boot, size it availableParallelism() - 1.
  • Handle a worker dying mid-job, or the caller's promise never settles and the request hangs.

If you remember one thing: a worker does not make work faster. It moves work, and moving costs 28 ms per 50 MB.
