Month 2 · Lesson 5 · Async model

The async ladder — callbacks, promises, async/await

Three ways to say "do this when it's ready" — and why each one was invented.

Your win today: you'll be able to take any callback-style function and climb it up the ladder to a clean async/await version — and answer the question that trips up most candidates: what does await actually pause? (Hint: not what people think.)
Where you are Month 1 taught you that Node hands slow work to the OS and later gets called back. That "called back" is a callback — the bottom rung of this ladder. This month is about the three ways we handle a value that arrives later, and how to run many of them at once without hurting yourself. This is Lesson 1 of 4.

Start from zero — the one problem all three solve

Ordinary synchronous code returns its answer now:

const x = add(2, 3);   // x is 5 on the very next line

But a file read, a database query, or a network call can't do that — the answer isn't ready for milliseconds or seconds. From Month 1 you know Node refuses to stand still and wait. So async code can't hand you the value; it can only promise to hand it to you later. Every tool in this lesson is just a different grammar for "later."

The idea in one line

Callbacks, promises, and async/await all answer the same question — "the value isn't here yet, so how do I say what to do when it arrives?" — and each was invented to cure the pain of the one before it.

Rung 1 — the callback

The original answer: pass in a function, and Node calls it when the work finishes. Node's built-in style is the error-first callback: the first argument is the error (or null), the second is the result.

const fs = require('fs');

// (err, data) — always check err FIRST.
fs.readFile('data.json', 'utf8', (err, data) => {
  if (err) return console.error('read failed:', err.message);
  console.log('got it:', data);
});
console.log('this prints BEFORE the file is read'); // non-blocking (Month 1)

This works. The trouble starts when one "later" depends on another "later." You end up nesting callbacks inside callbacks — the shape people call the pyramid of doom:

getUser(1, (err, user) => {
  if (err) return done(err);
  getOrders(user.id, (err, orders) => {
    if (err) return done(err);
    getItems(orders[0].id, (err, items) => {
      if (err) return done(err);          // error handling repeated at every level
      done(null, items);                  // the real work, buried three levels deep
    });
  });
});

It drifts to the right, the error checks repeat, and the actual logic is buried. That pain is why the next rung exists.

Rung 2 — the promise

A Promise is an object that stands for a value that will exist later. It is always in exactly one of three states:

  • pending — still working, no value yet;
  • fulfilled — the work succeeded; it now holds a value (you read it with .then);
  • rejected — the work failed; it now holds an error (you read it with .catch).

Once it leaves pending it is settled and can never change again. Because a promise is a real object, you can return it, pass it around, and — crucially — chain it. Each .then returns a new promise, so the pyramid flattens into a straight line:

getUser(1)
  .then((user) => getOrders(user.id))     // return a promise → the next .then waits for it
  .then((orders) => getItems(orders[0].id))
  .then((items) => done(null, items))
  .catch((err) => done(err));              // ONE catch handles a failure at ANY step

Same three steps as the pyramid — but flat, and with a single error handler instead of one per level. That is the whole reason promises were added to the language.

Turn a callback into a promise (a classic live-coding ask)

Most old Node APIs are callback-style; most new code is promise-style. Bridging the two is a common interview task, and there are two ways.

Way 1 — util.promisify wraps any error-first callback function into one that returns a promise:

const fs = require('fs');
const { promisify } = require('util');

const readFile = promisify(fs.readFile);   // now returns a promise
readFile('data.json', 'utf8').then((text) => console.log(text));

Way 2 — build it by hand with the Promise constructor. You get resolve (call on success) and reject (call on failure). This is the version to be able to write from memory:

function readFileP(path) {
  return new Promise((resolve, reject) => {
    fs.readFile(path, 'utf8', (err, data) => {
      if (err) reject(err);      // failure → rejected promise
      else resolve(data);        // success → fulfilled promise
    });
  });
}
You rarely need to do this by hand anymore Node now ships promise versions of most modules — require('fs/promises'), require('dns/promises'), and so on. Reach for those first. But knowing how to wrap a raw callback proves you understand what a promise is, so it's a favourite interview exercise.

Rung 3 — async/await

Promises are flat, but .then chains still read differently from normal code. async/await is syntax sugar over promises that lets you write asynchronous code that reads top-to-bottom like synchronous code.

  • Mark a function async — it now always returns a promise.
  • Inside it, await a promise — you get the fulfilled value directly, as if it were synchronous.
  • Use ordinary try/catch for errors (the next lesson is all about this).
async function loadItems() {
  const user   = await getUser(1);            // unwraps the promise's value
  const orders = await getOrders(user.id);
  const items  = await getItems(orders[0].id);
  return items;                               // resolves loadItems()'s promise
}

Three rungs, same three steps — but this last one reads like the synchronous code you already understand. That's the goal of the whole ladder.

The interview trap — what does await actually pause?

Here is the single most misunderstood point in async Node, and a shaky answer costs you the round.

The trap "await waits for the result, so it blocks the thread while it waits." Wrong. If that were true, await would freeze every other user — and Node would be useless.

The truth: await pauses only the async function it lives in. It does not pause the thread. Under the hood, await somePromise is really somePromise.then(rest_of_the_function) — Node registers "run the rest of this function when the promise settles," then hands the single thread straight back to the event loop, which is free to serve other requests. When the promise settles, your function resumes where it left off.

Say this one out loud

await suspends the current function and returns control to the event loop; it does not block the thread. So awaiting a slow network call lets Node keep serving everyone else — the exact opposite of a synchronous while loop, which captures the thread and freezes everyone.

This is Month 1's golden rule, restated: await on I/O is non-blocking and good; a synchronous CPU loop is blocking and bad. Same one thread, opposite behaviour.

Build it for real — climb the ladder yourself

One small program that shows all three rungs and proves await doesn't block. You need modern Node (node -v ≥ 18 for built-in fetch).

ladder.js

const fs = require('fs');
const { promisify } = require('util');

// Rung 1 → 2: wrap a callback API into a promise by hand.
function readFileP(path) {
  return new Promise((resolve, reject) => {
    fs.readFile(path, 'utf8', (err, data) => (err ? reject(err) : resolve(data)));
  });
}

// Rung 3: async/await reads top-to-bottom.
async function main() {
  // Proof that await does NOT block the thread:
  const timer = setInterval(() => console.log('  ...thread is still free, tick'), 300);

  console.log('fetching a slow URL (about 2s)...');
  const res = await fetch('https://httpbin.org/delay/2');  // suspends main(), frees the loop
  const body = await res.json();
  console.log('got response while the ticks kept printing:', body.url);

  clearInterval(timer);
}

main().catch((err) => console.error('failed:', err.message));

Run node ladder.js. While the fetch is "waiting," the setInterval keeps printing ticks — visible proof that the thread was never blocked during the await. If await froze the thread, the ticks would stop.

Try the rewrite yourself Take the callback pyramid from earlier (three nested fs.readFile calls reading three files in turn) and rewrite it as one async function with three await readFileP(...) lines. Feel how the drift-to-the-right disappears. That rewrite is the skill this lesson tests.

Remember this · the Feynman summary
  • Async code can't return a value now; it can only promise one later. Callbacks, promises, and async/await are three grammars for "later."
  • Callback: pass a function to run when done. Node's style is error-first: (err, data), check err first. Nesting them makes the pyramid of doom.
  • Promise: an object for a future value — pending → fulfilled / rejected, then settled forever. Chaining .then flattens the pyramid and needs only one .catch.
  • Turn a callback into a promise with util.promisify, or by hand with new Promise((resolve, reject) => ...). Prefer built-in fs/promises etc.
  • async/await is sugar over promises: an async function always returns a promise, and await unwraps one so the code reads like synchronous code.
  • The trap: await pauses only the current function and returns control to the event loop — it does not block the thread. Awaiting I/O is non-blocking; a synchronous loop is not.

If you remember one thing: await pauses your function, not the thread — the event loop keeps serving everyone else.
