Async errors & the danger of unhandled rejections

Why a try/catch can miss the error completely — and why a forgotten await can crash your server.

Your win today: you'll know exactly where an async error goes, why an ordinary try/catch often fails to catch it, what an unhandled rejection is, and why modern Node crashes the whole process when one slips through — plus the senior take on why crashing is the right behaviour.
Where you are Lesson 5 climbed the ladder from callbacks to async/await. Every rung has its own way of reporting failure, and getting this wrong is the number-one source of silent bugs and 3am pages in real Node services. Lesson 2 of 4.

Start from zero — why async errors are different

A synchronous error is easy: it is thrown, it travels straight up the call stack, and the nearest try/catch catches it.

try {
  JSON.parse('not json');     // throws synchronously
} catch (err) {
  console.log('caught:', err.message);   // works — same call stack
}

Async work breaks this. By the time the file read or network call fails, the original code has already moved on — the call stack that ran your try is gone. The error appears later, on a fresh stack. So a try/catch wrapped around the start of an async operation catches nothing:

try {
  fs.readFile('missing.txt', (err, data) => {
    // the error arrives HERE, later, on a new stack —
    // the try/catch below already finished and is long gone.
    if (err) throw err;      // this throw escapes into nothing useful
  });
} catch (err) {
  console.log('this NEVER runs');   // the try already returned before the callback fired
}
The idea in one line

A synchronous error travels up the stack to your try/catch. An async error arrives later, after that stack is gone — so each async style has its own channel for reporting failure, and you must use the matching one.

Three rungs, three ways to handle failure

Callbacks — check err first, every time. The error is the first argument. There is nothing to throw to; you handle it inline.

fs.readFile('data.json', 'utf8', (err, data) => {
  if (err) return handle(err);   // the ONLY correct place to see this error
  use(data);
});

Promises — a failure becomes a rejection, caught by .catch. A rejection travels down the chain until something catches it.

getUser(1)
  .then((u) => getOrders(u.id))
  .then(use)
  .catch((err) => handle(err));   // catches a rejection from ANY step above

async/await — try/catch works again. This is a big reason async/await feels nicer: because await turns a rejection back into a thrown error inside your function, the ordinary try/catch catches it — just like synchronous code.

async function load() {
  try {
    const user  = await getUser(1);
    const items = await getItems(user.id);
    return items;
  } catch (err) {
    handle(err);      // catches a rejection from EITHER await
  }
}
The rule of thumb try/catch only catches async errors when you await the thing that can fail. No await, no catch. That single fact explains most "why didn't my try/catch work?" confusion.

The dangerous part — the unhandled rejection

What if a promise rejects and nothing is there to catch it? No .catch, no surrounding try/catch with an await? That is an unhandled promise rejection — and it is the async equivalent of an error nobody caught.

The two most common ways to create one by accident:

// 1) A "floating" promise — called but never awaited and never .catch'd.
sendEmail(user);           // returns a promise; if it rejects, NOBODY is listening

// 2) A missing await, so the try/catch guards nothing.
async function handler() {
  try {
    saveOrder(order);      // forgot await → the try/catch can't catch its rejection
  } catch (err) {
    // never runs; the rejection floats away unhandled
  }
}
What Node does about it — and why it matters Since Node.js v15, an unhandled promise rejection terminates the process by default (it used to only print a warning). So a single forgotten await or missing .catch doesn't just hide a bug — it can crash your entire server. This is a deliberate change: a silent, ignored failure is more dangerous than a loud crash.

Why crashing is the correct behaviour (the senior take)

New engineers reach for a global handler that swallows every error to "keep the server up." That is usually the wrong instinct. If an error reached the top unhandled, your program is now in an unknown state — a half-finished transaction, a corrupted in-memory value, a connection left dangling. Continuing to serve traffic from a broken process gives users wrong answers, which is worse than a clean restart.

The line to memorise

Handle every error where it happens. For the ones that still escape, let the process crash and let your supervisor restart it clean — a fresh, correct process beats a limping, corrupted one. Use the global handlers to log and exit, not to swallow and continue.

The two global safety nets exist for logging and a graceful exit, not for pretending nothing happened:

process.on('unhandledRejection', (reason) => {
  console.error('unhandled rejection:', reason);
  process.exit(1);      // log, then exit so a supervisor restarts us clean
});

process.on('uncaughtException', (err) => {
  console.error('uncaught exception:', err);
  process.exit(1);      // same: last resort, not a way to keep limping
});

We'll wire this into proper graceful shutdown (drain in-flight requests, then exit) in Month 7. For now, the mindset is what matters: catch what you can, crash clean on what you can't.

Build it for real — make an error vanish, then catch it

Feel the danger with your own eyes. Modern Node (≥ v18).

rejection.js

function flaky() {
  // a promise that always rejects after 100ms
  return new Promise((_, reject) =>
    setTimeout(() => reject(new Error('service is down')), 100)
  );
}

// STEP 1: floating call — no await, no .catch. Watch Node crash.
flaky();
console.log('this line runs, then ~100ms later the process CRASHES');

Run node rejection.js. It prints the line, then dies with UnhandledPromiseRejection and a non-zero exit code. That is a one-line bug taking down a server.

Now fix it — three correct ways, any one is enough:

// FIX A: await it inside try/catch
async function main() {
  try {
    await flaky();
  } catch (err) {
    console.log('handled cleanly:', err.message);   // process lives
  }
}
main();

// FIX B: attach a .catch to the floating promise
flaky().catch((err) => console.log('handled:', err.message));

// FIX C (last resort): the global net — LOG then EXIT, never swallow-and-continue
process.on('unhandledRejection', (reason) => {
  console.error('logged for the on-call engineer:', reason.message);
  process.exit(1);
});
The habit that prevents 90% of this Whenever you call a function that returns a promise, ask: "who is awaiting or catching this?" If the answer is "nobody," you have a floating promise. Either await it (inside try/catch) or attach a .catch. Linters have a no-floating-promises rule that flags exactly this.

Remember this · the Feynman summary
  • A synchronous error travels up the stack to try/catch. An async error arrives later, after that stack is gone — so each style has its own failure channel.
  • Callback: check err (the first argument) inline. Promise: a failure is a rejection, caught by .catch. async/await: a rejection is re-thrown inside your function, so try/catch works — but only around an await.
  • An unhandled rejection = a promise rejected with nobody listening. The usual causes are a floating promise (never awaited or caught) and a missing await.
  • Since Node v15, an unhandled rejection crashes the process by default — a one-line mistake can take down the server.
  • Senior take: handle errors where they happen; for the ones that escape, crash clean and restart. Use process.on('unhandledRejection'/'uncaughtException') to log and exit, never to swallow and keep limping.

If you remember one thing: every promise needs an owner — someone who awaits it or .catches it — or Node will crash the process.
