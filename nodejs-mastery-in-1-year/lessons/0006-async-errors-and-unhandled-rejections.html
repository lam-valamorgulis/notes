Async errors & the danger of unhandled rejections

Why a try/catch can miss the error completely — and why a forgotten await can crash your server.

Start from zero — why async errors are different

A synchronous error is easy. It is thrown, travels straight up the call stack, and the nearest try/catch catches it.

try {
  JSON.parse('not json');     // throws synchronously
} catch (err) {
  console.log('caught:', err.message);   // works — same call stack
}

Async work breaks this. By the time the file read or network call fails, the original code has already moved on. The call stack that ran your try is gone, and the error appears later, on a fresh stack. So a try/catch around the start of an async operation catches nothing:

try {
  fs.readFile('missing.txt', (err, data) => {
    // the error arrives HERE, later, on a new stack —
    // the try/catch below already finished and is long gone.
    if (err) throw err;      // this throw escapes into nothing useful
  });
} catch (err) {
  console.log('this NEVER runs');   // the try already returned before the callback fired
}
The idea in one line

A synchronous error travels up the stack to your try/catch. An async error arrives later, after that stack is gone. So each async style has its own channel for reporting failure, and you must use the matching one.

Three rungs, three ways to handle failure

Callbacks — check err first, every time. The error is the first argument. There is nothing to throw to; you handle it inline.

fs.readFile('data.json', 'utf8', (err, data) => {
  if (err) return handle(err);   // the ONLY correct place to see this error
  use(data);
});

Promises — a failure becomes a rejection, caught by .catch. A rejection travels down the chain until something catches it.

getUser(1)
  .then((u) => getOrders(u.id))
  .then(use)
  .catch((err) => handle(err));   // catches a rejection from ANY step above

async/await — try/catch works again. This is a big reason it feels nicer. await turns a rejection back into a thrown error inside your function, so the ordinary try/catch catches it.

async function load() {
  try {
    const user  = await getUser(1);
    const items = await getItems(user.id);
    return items;
  } catch (err) {
    handle(err);      // catches a rejection from EITHER await
  }
}
The rule of thumb try/catch only catches async errors when you await the thing that can fail. No await, no catch. That single fact explains most "why didn't my try/catch work?" confusion.

The dangerous part — the unhandled rejection

What if a promise rejects and nothing is there to catch it? No .catch, no surrounding try/catch with an await? That is an unhandled promise rejection — and it is the async equivalent of an error nobody caught.

The two most common ways to create one by accident:

// 1) A "floating" promise — called but never awaited and never .catch'd.
sendEmail(user);           // returns a promise; if it rejects, NOBODY is listening

// 2) A missing await, so the try/catch guards nothing.
async function handler() {
  try {
    saveOrder(order);      // forgot await → the try/catch can't catch its rejection
  } catch (err) {
    // never runs; the rejection floats away unhandled
  }
}
What Node does about it — and why it matters Since Node.js v15, an unhandled promise rejection terminates the process by default (it used to only print a warning). So a single forgotten await or missing .catch doesn't just hide a bug — it can crash your entire server. This is a deliberate change: a silent, ignored failure is more dangerous than a crash you can see.

Why crashing is the correct behaviour (the senior view)

New engineers use a global handler that hides every error to "keep the server up". That is usually the wrong instinct.

An error that reached the top unhandled leaves your program in an unknown state. A half-finished transaction, a corrupted value, a dangling connection. Serving traffic from a broken process gives users wrong answers, which is worse than a clean restart.

The line to memorise

Handle every error where it happens. For the ones that still escape, let the process crash and let your process manager restart it clean. A fresh, correct process beats a broken one. Use the global handlers to log and exit, not to hide and continue.

The two global safety nets exist for logging and a graceful exit, not for pretending nothing happened:

process.on('unhandledRejection', (reason) => {
  console.error('unhandled rejection:', reason);
  process.exit(1);      // log, then exit so a process manager such as systemd or pm2 restarts us clean
});

process.on('uncaughtException', (err) => {
  console.error('uncaught exception:', err);
  process.exit(1);      // same: last resort, not a way to keep broken
});

We'll wire this into proper graceful shutdown (drain still-running requests, then exit) in week 27. For now, the mindset is what matters: catch what you can, crash clean on what you can't.

Say it in the simplest words — the Feynman check

1 · In plain words A try/catch guards a moment in time, not a piece of code. By the time an asynchronous error actually happens, the try block has already run to the end and gone. There is nothing left standing there to catch anything.

2 · One analogy A try/catch is an umbrella you hold while you walk to the car. It protects you for exactly as long as you hold it up. An async error is rain that falls an hour later, after the umbrella is folded and back in the car.

…and where the analogy breaks An umbrella is yours to hold or drop by choice. This one is not. Writing await inside the try is what keeps the umbrella open across the whole wait. That is precisely what the keyword buys you.

Take the await away and the umbrella snaps shut the same instant. That is why one forgotten keyword is the classic version of this bug.

3 · The sticking point People look at try { doThing() } catch {}, where doThing returns a promise, and believe it is guarded. It is not. The try block finished the moment doThing() handed back its promise. That is before any work was done, and long before anything could fail. One missing await, and a caught error becomes an unhandled rejection that kills the process.

4 · Now you explain it back

Build it for real — make an error vanish, then catch it

See the danger yourself. Modern Node (≥ v18).

rejection.js

function flaky() {
  // a promise that always rejects after 100ms
  return new Promise((_, reject) =>
    setTimeout(() => reject(new Error('service is down')), 100)
  );
}

// STEP 1: floating call — no await, no .catch. Watch Node crash.
flaky();
console.log('this line runs, then ~100ms later the process CRASHES');

Run node rejection.js. It prints the line, then dies with Error: service is down and exit code 1. That is a one-line bug taking down a server. Node only adds the UnhandledPromiseRejection wrapper when the reason is not an Error. Try Promise.reject('a string') and you will see it.

Now fix it — three correct ways, any one is enough:

// FIX A: await it inside try/catch
async function main() {
  try {
    await flaky();
  } catch (err) {
    console.log('handled cleanly:', err.message);   // process lives
  }
}
main();

// FIX B: attach a .catch to the floating promise
flaky().catch((err) => console.log('handled:', err.message));

// FIX C (last resort): the global net — LOG then EXIT, never hide-and-continue
process.on('unhandledRejection', (reason) => {
  console.error('logged for the on-call engineer:', reason.message);
  process.exit(1);
});
The habit that prevents 90% of this Whenever you call a function that returns a promise, ask: "who is awaiting or catching this?" If the answer is "nobody," you have a floating promise. Either await it (inside try/catch) or attach a .catch. ESLint has the rule @typescript-eslint/no-floating-promises that flags exactly this.

Now find the guilty line — the part nobody writes down

Knowing what an unhandled rejection is takes ten minutes. Finding which of your 400 files created it has no ready answer online. That is why this lesson exists.

The crash message often does not name your code at all. The stack starts where the promise rejected, not where it was created and left unowned. Three moves, in order:

  1. Run with node --trace-warnings app.js. It prints a stack for the warning, not just the message.
  2. Register the handler first, and print reason.stack, never reason.message. The message alone hides the file. 
    process.on('unhandledRejection', (reason) => {
  console.error('unhandled rejection:', reason && reason.stack || reason);
  process.exitCode = 1;
});
  3. If the stack still stops inside Node, the promise was created in a callback and the frames are gone. Now search instead of debug: look for calls to async functions with no await and no .catch.
Stop writing them in the first place ESLint has the rule @typescript-eslint/no-floating-promises. It finds exactly this mistake before the code ships, which is cheaper than finding it at 3am. Turn it on once and it keeps working forever.
The honest limit An async stack trace loses frames. That is not a bug you can fix, it is how the call stack works — the original stack was unwound long before the failure. So the skill is not “read the stack better”. It is knowing what the missing frames mean, and switching to search when the trace runs out.

Remember this · the 20-second recap
  • A synchronous error travels up the stack to try/catch. An async error arrives later, after that stack is gone — so each style has its own failure channel.
  • Callback: check err, the first argument, inline. Promise: a failure is a rejection, caught by .catch. async/await: a rejection is re-thrown inside your function, so try/catch works. But only around an await.
  • An unhandled rejection = a promise rejected with nobody listening. The usual causes are a floating promise (never awaited or caught) and a missing await.
  • Since Node v15, an unhandled rejection crashes the process by default — a one-line mistake can take down the server.
  • Senior take: handle errors where they happen; for the ones that escape, crash clean and restart. Use process.on('unhandledRejection'/'uncaughtException') to log and exit, never to hide and keep broken.

If you remember one thing: every promise needs an owner. Someone must await it or .catch it, or Node crashes the process.
