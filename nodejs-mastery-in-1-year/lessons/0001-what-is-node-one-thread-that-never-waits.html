What is Node.js, really?

The first idea the whole year rests on — one thread that never waits.

Your win today: you'll be able to explain, in plain words, (1) what Node.js actually is, (2) why JavaScript — a browser language — runs on a server at all, and (3) the single trick that lets one thread serve thousands of users at once. That trick is the question almost every Node.js interview opens with.
How we learn here We build every idea from first principles — we start from the simplest true thing and add one step at a time, so nothing is magic. Every lesson has a "Build it for real" step where you run actual Node.js code that does a real job — not just theory. At the end, the "Remember this" box is a Feynman summary: the whole lesson said again in words simple enough to teach a friend. If you can say that box out loud, you own the lesson.

Start from zero — what actually runs your code?

A computer's processor (the CPU) understands exactly one thing: machine code — raw numbers. Your JavaScript is just text in a file. So something has to read that text, translate it, and run it. That something is called an engine.

The engine for JavaScript is V8, built by Google for the Chrome browser. V8 is extremely fast, but on its own it only knows the language itself: numbers, strings, objects, functions, loops. It cannot open a file on your disk, listen on a network port, or read the system clock — because inside a browser, those powers are handed to JavaScript by the browser, not by the language.

So here is the whole idea of Node.js in one sentence:

Definition · say this one out loud

Node.js is Google's V8 engine taken out of the browser, bundled with extra abilities written in C++ — reading files, networking, timers, talking to the operating system — so JavaScript can run on a server.

A helper library called libuv (written in C) is the part that actually talks to the operating system and, crucially, gives Node its non-blocking superpower — which is the rest of this lesson. Put simply, a runtime is "the engine that runs your code plus the extra abilities it gives your code." Node.js is a runtime. It is not a language (that's JavaScript) and not a framework (that's things like NestJS, which we build later, that sit on top of Node).

The problem Node.js was built to solve

Imagine you run a website and 10,000 people click it in the same second. Most requests need something slow: read a row from a database, call another company's API, read a file from disk. "Slow" here means a few milliseconds to a few seconds — which, to a CPU that does billions of operations per second, is an eternity of sitting around.

The classic way many languages handle this is one thread per request. A thread is like a worker with its own chunk of memory (often 1–2 MB or more). The trouble: while that worker waits for the database to answer, it just stands there, blocked — using memory and a slot, doing nothing. 10,000 requests waiting on the database means 10,000 workers mostly standing still. You run out of memory and CPU quickly.

The picture to hold in your head

A restaurant with one waiter per table. Each waiter takes your order, then stands frozen at your table until the kitchen finishes cooking. To serve 100 tables you need 100 waiters — 90 of them just standing still. Expensive, and it doesn't scale.

Node.js asked a different question: what if one waiter never stands still?

The one trick — don't wait, get called back

Here is the whole secret, built one step at a time:

  1. Your JavaScript runs on one thread (one worker).
  2. When that code hits something slow (a file, a network call, a database query), Node does not wait for it. Instead it says: "Operating system, please do this. Here's a function to run when you're done" — that function is called a callback.
  3. Node then immediately moves on to the next piece of work. The waiting happens elsewhere — in the operating system, or in libuv's small background thread pool — not on your thread.
  4. When the slow thing finishes, its result is placed on a queue. A loop constantly checks that queue and runs the matching callback. That loop is the event loop.

So the single JavaScript thread is almost never blocked. It is either running a quick piece of your code, or it is free. That is why one thread can keep thousands of slow requests "in flight" at the same time — the slowness overlaps instead of stacking up.

Run it." │ └───────┬──────────────────┬──────────┘ │ hand off slow I/O │ run callback ▼ ▲ when result is ready ┌───────────────────────────────────┐ │ OS kernel + libuv thread pool │ │ (this is what waits) │ └───────────────────────────────────┘
The waiter, finished Node's one waiter takes your order, hands it straight to the kitchen, and immediately serves the next table. When your food is ready, the kitchen rings a bell; the waiter brings it over. One waiter, 100 tables, nobody standing still.

See it yourself — the 3-line proof

This is your first live-coding rep. You need Node installed (check with node -v in a terminal). Create a file, paste this in, and — before you run it — say out loud what order the numbers will print.

app.js

console.log('1  — this runs first');

setTimeout(() => {
  console.log('3  — this runs LAST, even though the delay is 0 ms');
}, 0);

console.log('2  — this runs second');

Run it with node app.js. Did you predict this?

What actually prints:

1  — this runs first
2  — this runs second
3  — this runs LAST, even though the delay is 0 ms

Why? Lines 1 and 2 are ordinary synchronous code — they run top to bottom on the single thread. But setTimeout(fn, 0) does not mean "run now". It means "hand this callback to the timer system; run it later, once the current code has finished." Even with a 0 ms delay, "later" means after the whole main script is done. That gap — between "schedule it" and "run it" — is the event loop. This tiny program is the seed of everything else in Node.js.

Why it matters — blocking vs non-blocking I/O

The same idea shows up the moment you touch a file. Node gives you two versions of many operations — one that blocks, one that doesn't. Read this (you don't have to run it):

const fs = require('fs');

// BLOCKING: the whole thread freezes until the entire file is read.
// While this runs, NO other user can be served.
const data = fs.readFileSync('big.txt');
console.log('got the file — and I was frozen until now');

// NON-BLOCKING: I ask, keep working, and get called back when it's ready.
fs.readFile('big.txt', (err, data) => {
  console.log('got the file — the server kept serving others meanwhile');
});
console.log('this line runs BEFORE the file is ready');

The one thread stops and waits.The one thread keeps going.

Simple to reason about.Needs a callback / promise, but scales.
Fine in a one-off script or at startup.The default inside a running server.
The one rule that follows from this In a Node server, never block the event loop. One slow synchronous call (a ...Sync function, a huge JSON.parse, a heavy loop) freezes every user at once — because they all share that single thread. We will return to this rule again and again.

Build it for real — a server that never freezes

Enough theory — let's apply Node.js to its most common real job: a web server. We'll use Node's built-in http module (no framework yet — that keeps us honest about learning the core first). This server has two routes: /fast answers instantly, and /slow pretends to do a 3-second database query.

server.js

const http = require('http');

const server = http.createServer((req, res) => {
  if (req.url === '/slow') {
    // pretend this is a slow database query (3 seconds)
    setTimeout(() => {
      res.end('slow: done after 3s\n');
    }, 3000);
    return;
  }
  res.end('fast: instant\n');
});

server.listen(3000, () => console.log('listening on http://localhost:3000'));

Now run the experiment — this is the lesson, felt for real:

  1. Start it: node server.js
  2. In one terminal, hit the slow route: curl http://localhost:3000/slow — it hangs for 3 seconds.
  3. While it's still hanging, in a second terminal hit the fast route: curl http://localhost:3000/fast

The fast route answers instantly — even though the slow request is still in flight. One thread, two requests at once, nobody frozen. You just watched "one thread that never waits" actually happen.

Now feel the golden rule break Swap the slow route for a blocking version, run the same experiment, and watch everything freeze: 
// The SAME server, but /slow now blocks the single thread:
if (req.url === '/slow') {
  const end = Date.now() + 3000;
  while (Date.now() < end) {}   // busy-wait — nothing else can run
  res.end('slow: done (but it froze everyone)\n');
  return;
}

Hit /slow, then quickly hit /fast. This time /fast is stuck until the 3 seconds are up. Same one thread — but the while loop never handed control back to the event loop, so every user waited. That is why "never block the event loop" is the most important habit in Node.js.

The takeaway you can feel setTimeout / async I/O = the thread stays free, everyone is served. A synchronous busy loop (or a ...Sync call, or a giant computation) = the thread is captured, everyone waits. Same code shape, opposite outcome — and now you've seen both with your own eyes.

"Is Node single-threaded?" — the interview trap

This is the classic gotcha, and a shaky answer costs you. Both extreme answers are wrong: "yes, completely single-threaded" and "no, a thread per request" both miss the truth. Here is the honest, senior version:

  • Your JavaScript runs on one thread — the main thread, the one with the event loop. Because of that, you don't get the classic data races over your variables that multi-threaded languages fight with.
  • But Node as a whole is not single-threaded. Network I/O is handled by the operating system, and libuv keeps a small background thread pool (default 4) for certain jobs — some file I/O, DNS lookups, crypto, compression.
  • You can add real parallelism when you need it: Worker Threads for CPU-heavy work in true parallel, and the cluster module (or several processes) to use all your CPU cores.
The line to memorise

"Node runs my JavaScript on a single thread, but performs I/O asynchronously using the operating system and a small background thread pool — so one thread can handle thousands of concurrent connections."

Remember this · the Feynman summary
  • Node.js is a runtime: Google's V8 engine taken out of the browser, plus C++ powers (files, network, timers, OS) and the libuv library — so JavaScript runs on a server.
  • It is not a language (that's JavaScript) and not a framework (that's NestJS, later).
  • The problem it solves: a "one thread per request" server wastes memory because most threads just sit blocked, waiting for slow work.
  • Node's trick is non-blocking I/O: hand slow work to the OS / a thread pool, register a callback, and keep the one thread free. The event loop runs the callback when the result is ready.
  • setTimeout(fn, 0) runs after the current code, not now — that gap is the event loop.
  • Interview truth: your JavaScript is single-threaded, but Node's I/O is not — the OS and libuv's thread pool do the waiting, so one thread serves thousands.
  • The golden rule: never block the event loop — one slow synchronous call freezes every user.
  • Real use case (built & run): the classic Node app is a web server — with async I/O it answers a fast request while a slow one is still waiting; with a blocking call it freezes them both.

If you remember one thing: Node.js is one thread that never waits — it hands off the waiting and gets called back.
