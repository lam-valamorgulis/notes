Start from zero — what actually runs your code?

A computer's processor (the CPU) understands exactly one thing: machine code — raw numbers. Your JavaScript is just text in a file. So something has to read that text, translate it, and run it. That something is called an engine.

The engine for JavaScript is V8, built by Google for the Chrome browser. V8 is extremely fast. On its own it only knows the language itself: numbers, strings, objects, functions, loops.

It cannot open a file on your disk, listen on a network port, or read the system clock. Inside a browser, those powers come from the browser, not from the language.

So here is the whole idea of Node.js in one sentence:

Definition · say this one out loud

Node.js is Google's V8 engine taken out of the browser. It comes bundled with extra abilities written in C++: reading files, networking, timers, and talking to the operating system. That is how JavaScript runs on a server.

A helper library called libuv, written in C, is the part that talks to the operating system. It also gives Node its non-blocking superpower, which is the rest of this lesson.

Put simply, a runtime is the engine that runs your code, plus the extra abilities it gives it. Node.js is a runtime. It is not a language — that is JavaScript. It is not a framework either, like NestJS, which sits on top of Node.

The problem Node.js was built to solve

Imagine you run a website and 10,000 people click it in the same second. Most requests need something slow: read a row from a database, call another company's API, read a file from disk. "Slow" here means a few milliseconds to a few seconds. To a CPU doing billions of operations per second, that is a very long time.

The classic way many languages handle this is one thread per request. A thread is like a worker with its own chunk of memory, often 1–2 MB or more.

Here is the trouble. While that worker waits for the database, it just stands there, blocked, using memory and a slot. 10,000 requests waiting means 10,000 workers standing still, and you run out of memory quickly.

The picture to hold in your head

A restaurant with one waiter per table. Each waiter takes your order, then stands frozen at your table until the kitchen finishes cooking. To serve 100 tables you need 100 waiters — 90 of them just standing still. Expensive, and it doesn't scale.

Node.js asked a different question: what if one waiter never stands still?

The one trick — don't wait, get called back

Here is the whole secret, built one step at a time:

  1. Your JavaScript runs on one thread (one worker).
  2. When that code hits something slow (a file, a network call, a database query), Node does not wait for it. Instead it says: "Operating system, please do this. Here's a function to run when you're done" — that function is called a callback.
  3. Node then immediately moves on to the next piece of work. The waiting happens elsewhere — in the operating system, or in libuv's small background thread pool — not on your thread.
  4. When the slow thing finishes, its result is placed on a queue. A loop constantly checks that queue and runs the matching callback. That loop is the event loop.

So the single JavaScript thread is almost never blocked. It is either running a quick piece of your code, or it is free. That is why one thread can keep thousands of slow requests running at once. The slowness overlaps instead of stacking up.

┌─────────────────────────────────────┐ │ EVENT LOOP (↻) │ │ "Anything finished? Any callback │ │ ready to run? Run it." │ └───────┬──────────────────┬──────────┘ │ hand off slow I/O │ run callback ▼ ▲ when result is ready ┌───────────────────────────────────┐ │ OS kernel + libuv thread pool │ │ (this is what waits) │ └───────────────────────────────────┘
The waiter, finished Node's one waiter takes your order, hands it straight to the kitchen, and immediately serves the next table. When your food is ready, the kitchen rings a bell; the waiter brings it over. One waiter, 100 tables, nobody standing still.

See it yourself — the 3-line proof

This is your first live-coding practice. You need Node installed (check with node -v in a terminal). Create a file, paste this in, and — before you run it — say out loud what order the numbers will print.

app.js

console.log('1  — this runs first');

setTimeout(() => {
  console.log('3  — this runs LAST, even though the delay is 0 ms');
}, 0);

console.log('2  — this runs second');

Run it with node app.js. Did you predict this?

What actually prints:

1  — this runs first
2  — this runs second
3  — this runs LAST, even though the delay is 0 ms

Why? Lines 1 and 2 are ordinary synchronous code, running top to bottom on the single thread. But setTimeout(fn, 0) does not mean "run now". It means: hand this callback to the timer system, and run it once the current code has finished.

Even with a 0 ms delay, "later" means after the whole main script is done. That gap, between "schedule it" and "run it", is the event loop. This tiny program is the base for everything else in Node.js.

Why it matters — blocking vs non-blocking I/O

The same idea shows up the moment you touch a file. Node gives you two versions of many operations — one that blocks, one that doesn't. Read this (you don't have to run it):

const fs = require('fs');

// BLOCKING: the whole thread freezes until the entire file is read.
// While this runs, NO other user can be served.
const data = fs.readFileSync('big.txt');
console.log('got the file — and I was frozen until now');

// NON-BLOCKING: I ask, keep working, and get called back when it's ready.
fs.readFile('big.txt', (err, data) => {
  console.log('got the file — the server kept serving others meanwhile');
});
console.log('this line runs BEFORE the file is ready');
Blocking (readFileSync)Non-blocking (readFile + callback)
The one thread stops and waits.The one thread keeps going.
Every other user is frozen too.Everyone else keeps being served.
Simple to reason about.Needs a callback / promise, but scales.
Fine in a one-off script or at startup.The default inside a running server.
The one rule that follows from this In a Node server, never block the event loop. One slow synchronous call (a ...Sync function, a huge JSON.parse, a heavy loop) freezes every user at once — because they all share that single thread. We will return to this rule again and again.
Say it in the simplest words — the Feynman check

1 · In plain words Your program runs one job at a time. When it needs something slow — a file, a database, another website — it does not sit and wait for the answer. It leaves a note that says “call me back when this is ready”, and immediately starts the next job. The waiting is done by somebody else.

2 · One analogy One waiter in a restaurant. He takes your order, hands the slip to the kitchen, and goes straight to the next table. He never stands at the kitchen door watching your food cook. That is why one waiter can look after fifty tables.

…and where the analogy breaks The picture puts many cooks in the kitchen. It is tempting to call those cooks “Node's other threads”. They are not. For network work the kitchen is the operating system, not Node.

Node's own helpers are libuv's thread pool, four by default. They handle file I/O, dns.lookup, some crypto, and zlib compression. That four is a convention chosen by libuv, not a rule you can derive. Change it with UV_THREADPOOL_SIZE.

And the analogy hides the real danger. If the waiter himself starts chopping vegetables, no kitchen anywhere can save the room. That is blocking.

3 · The sticking point People hear “single-threaded” and conclude Node can only do one thing at a time. Two different things are being mixed up.

Your JavaScript runs on one thread, and that part is completely true. The waiting happens in thousands of places at once, and none of it is your JavaScript. “Single-threaded” describes where your code runs, not how much work is running.

Build it for real — prove the two halves are separate

The plan for this week says: show that V8 and libuv are different things. So build the smallest program that proves it. Two jobs that both take about two seconds, running side by side. One is handed away, and one is done by your own thread.

proof.js

const fs = require('node:fs');

// A heartbeat. If the thread is free, this prints every 100 ms.
let ticks = 0;
const beat = setInterval(() => { ticks++; }, 100);

console.time('total');

// Job A — handed to libuv. Our thread does NOT do this work.
fs.readFile(__filename, () => {
  console.log('A finished. heartbeats so far:', ticks);
});

// Job B — done right here, on the one thread that runs your JavaScript.
const end = Date.now() + 2000;
while (Date.now() < end) {}          // two seconds of pure CPU
console.log('B finished. heartbeats so far:', ticks);

setTimeout(() => {
  clearInterval(beat);
  console.timeEnd('total');
  console.log('total heartbeats:', ticks);
}, 2500);

Predict the output before you run it. Write your prediction down — that is the whole exercise. Then run node proof.js.

The real output (Node v24.14.0):

B finished. heartbeats so far: 0
A finished. heartbeats so far: 1
total: 4.503s
total heartbeats: 25
What you will see, and why The heartbeat count is 0 when job B finishes, even though two seconds passed. Twenty heartbeats were due and not one of them ran. The while loop held the single thread, so nothing else — not the timer, not the finished file read — could get a turn. Job A finished first in real time, but its callback had to wait in the queue behind your loop.

That one number is the whole lesson. libuv did job A while your thread was busy. That is the "never waits" half. Your thread doing job B stopped everything. That is the golden rule. Both halves, in one twenty-line file.

You will feel this on a real server in week 4 A heartbeat counter is a toy. In week 4 you build an actual HTTP server and measure the same effect in milliseconds of user-facing latency: ten slow requests finish in about 2 seconds when the work is handed away, and about 20 seconds when it is not. Same idea, real numbers, real users.

"Is Node single-threaded?" — the interview trap

This is the classic trick question, and a weak answer loses you the interview. Both extreme answers are wrong: "yes, completely single-threaded" and "no, a thread per request" both miss the truth. Here is the correct, senior answer:

  • Your JavaScript runs on one thread — the main thread, the one with the event loop. Because of that, you don't get the classic data races over your variables that multi-threaded languages have to deal with.
  • But Node as a whole is not single-threaded. The operating system handles network I/O. And libuv keeps a small background thread pool, 4 by default, for file I/O, DNS lookups, crypto and compression.
  • You can add real parallelism when you need it. Worker Threads run CPU-heavy work in true parallel, and the cluster module uses all your CPU cores.
The line to memorise

"Node runs my JavaScript on a single thread. It performs I/O asynchronously, using the operating system and a small background thread pool. So one thread handles thousands of concurrent connections."

Remember this · the 20-second recap
  • Node.js is a runtime. Google's V8 engine taken out of the browser, plus C++ powers and the libuv library. It is not a language and not a framework.
  • The problem it solves is waste. A thread-per-request server burns memory while most threads sit blocked, waiting.
  • Node's trick is non-blocking I/O. Hand slow work to the OS or a thread pool, register a callback, and keep the one thread free. The event loop runs the callback when the result is ready.
  • setTimeout(fn, 0) runs after the current code, not now — that gap is the event loop.
  • Interview truth: your JavaScript is single-threaded, but Node's I/O is not. The OS and libuv's thread pool do the waiting, so one thread serves thousands.
  • The main rule: never block the event loop — one slow synchronous call freezes every user.
  • Real use case, built and run: a web server. With async I/O it answers a fast request while a slow one waits. With a blocking call it freezes them both.

If you remember one thing: Node.js is one thread that never waits. It hands off the waiting and gets called back.
