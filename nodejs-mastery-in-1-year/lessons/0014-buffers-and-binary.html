Buffers and binary

Why Node needed its own type for bytes — and why cutting a file in half can break a letter.

coreWeek 14 of 52. This lesson builds one domain-expert ability: predict how it behaves in a case you have never seen. Week 14 in the plan · Glossary

Your win today: you will explain what a Buffer is and why it exists. You will also produce a bug that most English-speaking developers never see. It breaks Vietnamese text, and it will break your users' text the day you ship.
Where you are Weeks 1–8 were about time. Weeks 9–12 were about place. Weeks 14–17 are about size: moving data that does not fit in memory. Before you can move bytes, you have to know what a byte is to Node.

Start from the problem — JavaScript had nowhere to put a byte

Node had to read files and sockets. Both give you bytes: whole numbers from 0 to 255.

Browser JavaScript in 2009 had two ways to hold data. Neither one worked.

  • A string is a sequence of UTF-16 code units, not bytes. Putting raw bytes in one corrupts them, because some byte sequences are not valid text at all.
  • An array of numbers works, but each element is a full 64-bit JavaScript value. A one-megabyte file becomes about eight megabytes of objects. All of it sits on the V8 heap, where the garbage collector has to walk it.

So Node added a third thing. Buffer is a fixed-length block of raw bytes, allocated outside the V8 heap. One byte in memory is one byte in the buffer.

Say this out loud

Every byte that enters or leaves a Node process is a Buffer before it is anything else. A string is what you get after deciding how to read those bytes.

It is not a special Node-only type any more. Verified on Node v24.14.0:

Buffer.from('hi') instanceof Uint8Array   // true

Buffer is a subclass of Uint8Array. So anything that takes a typed array takes a Buffer. The extra methods — toString, readInt32BE, subarray — are Node's additions on top.

Bytes are not characters — and this is where it hurts

Here is the fact everything else follows from. In UTF-8, one character is one, two, three or four bytes. English letters are one byte each. Almost nothing else is.

Take a Vietnamese word:

Buffer.from('việt', 'utf8').length   // 6 bytes
'việt'.length                       // 4 characters

Four characters, six bytes. The ệ takes three bytes on its own.

Now cut those six bytes into two chunks, the way a stream does, and turn each chunk into a string:

const full = Buffer.from('việt', 'utf8');
const a = full.subarray(0, 3);
const b = full.subarray(3);

a.toString('utf8') + b.toString('utf8')

The real output (Node v24.14.0):

"vi���t"

The ệ is gone. Three replacement characters sit where it was. Each half of the split character was decoded on its own, and neither half is valid UTF-8.

Why this bug reaches production and never reaches your tests Split an English word anywhere you like and nothing breaks, because every ASCII letter is exactly one byte. So the bug is invisible in English test data. It appears the first time a real user types Vietnamese, Chinese, Arabic, or an emoji — and by then the data is already saved, wrong.

The fix — something has to remember the half-finished character

You cannot decode a chunk on its own. You need something that holds the incomplete bytes back and waits for the rest. Node ships it:

const { StringDecoder } = require('node:string_decoder');
const d = new StringDecoder('utf8');

d.write(a) + d.write(b) + d.end()

The real output:

"việt"

The first write returns "vi" and quietly keeps the one dangling byte. The second write gets the two bytes that finish it, joins all three, and returns "ệt".

The easier fix, most of the time Set the encoding on the stream itself — createReadStream(path, 'utf8'), or stream.setEncoding('utf8'). Node then uses a StringDecoder internally and you never see the problem. Do that whenever you know the data is text. Use StringDecoder by hand when you are assembling chunks yourself.

Two ways to make one, and why there are two

CallWhat it does
Buffer.alloc(n)Gives you n bytes, every one set to zero. Slower, and always safe.
Buffer.allocUnsafe(n)Gives you n bytes and skips the zeroing. Faster. The contents are not guaranteed to be anything.
Buffer.from(x)Copies from a string, an array, or another buffer.
Be precise about allocUnsafe, because the usual warning overstates it You will read that allocUnsafe “shows you old memory”. When I ran it, the bytes came back all zero anyway. The correct statement is narrower and more useful: the contents are undefined. You may not assume they are zero, and Node may hand you memory that a previous part of your own process used.

So the rule is simple. Use allocUnsafe only when you overwrite every byte immediately. If you would ever send it, log it, or return it before filling it, use alloc.

Say it in the simplest words — the Feynman check

1 · In plain words A file is a long line of numbers, each from 0 to 255. Text is those numbers plus an agreement about what they mean.

The agreement is not one number per letter. Some letters need two, three or four numbers in a row. So if you cut the line at a random place, you can cut a letter in half. Half a letter is not a letter at all.

2 · One analogy A train. Each letter is a carriage, and a carriage is built from one to four wagons. English letters are single wagons. ệ is a carriage of three. Cut the train between two wagons of the same carriage, and both pieces are broken.

…and where the analogy breaks On a real train you can see where one carriage ends and the next begins. In a line of bytes you cannot. Nothing separates the carriages.

The only way to know is that UTF-8 marks the first byte of each character differently from the rest. Reading those marks is the whole job. That is exactly what StringDecoder does. It spots a carriage that is not finished, and holds those wagons back until the rest arrive.

3 · The sticking point People believe calling .toString() on each chunk is harmless. For English it is harmless. Every ASCII letter is exactly one byte, so no cut can ever land inside one.

That is the trap. The code is not wrong for some users and right for others. It is wrong for everyone, and only visible when the data is not English. So it passes every test written in English and fails the day a real user types their own name.

4 · Now you explain it back

In two or three sentences, explain why splitting a byte stream can break a character. Then say why this bug almost never shows up in testing. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — break your own text, then fix it

Short week. Two files, twenty minutes, and one result you will not forget.

1 · Break it

const word = 'việt nam';                // or your own name
const bytes = Buffer.from(word, 'utf8');
console.log('characters:', word.length, ' bytes:', bytes.length);

// Cut at every possible position and decode naively.
for (let i = 1; i < bytes.length; i++) {
  const out = bytes.subarray(0, i).toString('utf8')
            + bytes.subarray(i).toString('utf8');
  if (out !== word) console.log(`cut at ${i} ->`, JSON.stringify(out));
}

Count the cut positions that break the word. Then run the same loop over 'viet nam', with no accents. Zero breakages. That difference is the lesson.

2 · Fix it

const { StringDecoder } = require('node:string_decoder');

for (let i = 1; i < bytes.length; i++) {
  const d = new StringDecoder('utf8');       // a fresh one per attempt
  const out = d.write(bytes.subarray(0, i))
            + d.write(bytes.subarray(i))
            + d.end();
  if (out !== word) console.log('STILL BROKEN at', i);
}

Nothing should print. Every cut position now survives.

3 · See it on a real file

node -e "require('fs').writeFileSync('vn.txt','việt nam '.repeat(20000))"
node -e "
  const fs=require('fs');
  let s='';
  const r=fs.createReadStream('vn.txt',{highWaterMark:64});   // tiny chunks on purpose
  r.on('data',c=>{ s+=c.toString('utf8'); });                 // the naive way
  r.on('end',()=>console.log('broken characters:',(s.match(/�/g)||[]).length));
"

Now change createReadStream('vn.txt', {highWaterMark: 64}) to createReadStream('vn.txt', {highWaterMark: 64, encoding: 'utf8'}) and run it again. The count drops to zero, because Node now decodes with a StringDecoder for you.

What to hand in Two numbers: how many characters broke without the encoding, and how many broke with it. Write them next to each other. That pair is worth more than the explanation.

Say it like an interviewer just asked

What this lesson left out on purpose Encodings other than UTF-8 — latin1, base64, hex — are real and are a lookup, not an idea. Reading numbers out of a buffer with readInt32BE and friends belongs with a binary protocol, and this course does not build one. Byte order, big-endian against little-endian, is left out for the same reason. How a stream produces these chunks is week 15 — that is the next lesson, on purpose.

Remember this · the 20-second recap
  • A Buffer is a fixed block of raw bytes, outside the V8 heap. It is a subclass of Uint8Array.
  • Every byte entering or leaving Node is a Buffer first. A string is a decision about those bytes.
  • In UTF-8 a character is 1 to 4 bytes. 'việt' is 4 characters and 6 bytes.
  • Cutting a byte stream can cut a character in half. Decoding the halves gives �.
  • Fix it with StringDecoder, or by setting encoding on the stream and letting Node do it.
  • English hides this bug completely, because every ASCII letter is one byte.
  • allocUnsafe gives undefined contents, not guaranteed-old memory. Use it only when you overwrite every byte at once.

If you remember one thing: a chunk boundary is not a character boundary, and English will never tell you.
