Redis, and the three ways a cache lies

A cache is the easiest big win in this course, and the easiest thing to get subtly wrong.

coreWeek 41 of 52. This lesson builds one domain-expert ability: add speed without adding a lie. Week 41 in the plan · Glossary

Your win today: a cache that does nothing at all for the first hundred requests, and you will see exactly why. Then one line fixes it.
Where you are Week 40 put the spine's data in Postgres and showed where the time goes. A cache removes most of that time. It also introduces the only hard problem in this module: two copies of the truth.

Start from the problem — what have you actually done?

A cache is a second copy of your data, in a faster place. Everything good and everything bad about caching comes from that one sentence.

The trade you just made

You traded correctness for speed, and agreed to manage the gap. The question is never “is the cache correct?” It is “how wrong may it be, and for how long?”

If you cannot answer that second question for a piece of data, you are not ready to cache it. That is also the answer to “what TTL should I use?”, which otherwise gets decided by habit.

Lie 1 — the stale read

The simplest cache, and the bug in it. Measured against PostgreSQL 18.3:

const get = async (code) =>
  cache.has(code) ? cache.get(code) : (cache.set(code, await db(code)), cache.get(code));

  read 1 (fills cache) : https://first.test
  database now holds   : https://SECOND.test      <- somebody did an UPDATE
  read 2 (from cache)  : https://first.test       <- WRONG, and stays wrong forever

Nothing crashed. No error was logged. The service is fast and confidently wrong, and it will stay that way until the process restarts.

There are exactly two ways out, and they are a real choice:

StrategyHow wrong, and for how longCost
TTL — let it expireWrong for up to the TTL, every timeOne line. Nothing to remember.
Invalidate on writeWrong for millisecondsEvery write path must remember. Miss one and it is wrong forever.
BothWrong for milliseconds, and the TTL catches your mistakesThe one to use.
Why “both” is the real answer Invalidation is correct and fragile — it depends on you remembering every write path, including the one added next year by someone who has not read this. A TTL underneath turns “wrong forever” into “wrong for 60 seconds”. It is a safety net for a mistake you will definitely make.

So pick the TTL from the requirement, not from habit. Try this sentence: “users may see a link's old target for up to 60 seconds after an edit”. You can put that in front of a product owner. “300, because that is what we always use” is not.

Lie 2 — the cache that does nothing when you need it most

Cold cache, one popular key, 100 requests arriving together. Measured:

DesignDatabase queriesTime
The cache above10043 ms
With single-flight122 ms
A hundred requests, a hundred queries, and the cache was working correctly Every request checked the cache. Every one missed, because none of the others had finished writing yet. So all hundred went to the database. The cache does not help until the first answer comes back.

This is cache stampede, also called the thundering herd. It happens on cold start, after a deploy, after a Redis restart, and every time a popular key expires. That is exactly when you are least able to absorb it.

The fix is single-flight: remember the in-progress lookup, not just the finished value.

const cache = new Map(), inflight = new Map();

async function get(code) {
  if (cache.has(code)) return cache.get(code);
  if (inflight.has(code)) return inflight.get(code);      // <- the whole fix

  const p = db(code).then(v => {
    cache.set(code, v);
    inflight.delete(code);                                 // or it leaks, week 34
    return v;
  });
  inflight.set(code, p);
  return p;
}

You already know why this works. A promise can have many awaiters, from week 5. The hundredth request does not start a hundredth query — it waits on the first one's promise.

Two details that matter Delete from inflight on failure too, or a single failed lookup poisons that key for the life of the process. And note this map is per process — with cluster from week 24, eight workers means eight queries, not one. That is still a hundredfold improvement, and worth knowing rather than discovering.

The stampede you build on purpose

Now warm 1,000 keys at once — a deploy, or a cache rebuild — all with the same 60-second TTL. Count how many expire in the busiest single second:

TTLBusiest second
Exactly 60 s, every key1,000 expiries
60 s ± 10%100
60 s ± 50%23

Warm them together and they expire together. Your traffic then arrives at the database in a spike, once a minute, forever. One line prevents it:

const ttl = BASE_TTL * (0.5 + Math.random());     // ±50% jitter

A 43-fold reduction in the worst second, from adding randomness. This is the same idea as jittered retry backoff in week 8: anything synchronised becomes a spike.

Lie 3 — the cache that never gives anything back

A cache with no TTL and no eviction is not a cache. It is a leak with a good reputation. Measured:

  500,000 cached links -> 52.5 MB held, forever
  per key              : 110 bytes

52 MB does not sound alarming. That is the problem. It grows quietly, in proportion to traffic rather than to your data. It looks exactly like the leak you hunted in week 34. A cache keyed by something unbounded, like a search query or a request id, has no ceiling at all.

Redis gives you two controls for this, and you should set both:

SET link:abc "https://..." EX 60        # always set a TTL. no exceptions.

# redis.conf — the ceiling, for when a TTL is not enough
maxmemory 512mb
maxmemory-policy allkeys-lru            # evict least-recently-used when full
The default policy is not the one you want Redis defaults to noeviction: when memory is full it refuses writes and returns an error. Your cache stops accepting new entries and starts returning errors on SET, at the worst possible moment. Choose the policy on purpose.

What does your service do when Redis is down?

This must be a tested path, because it is not a rare one. Redis restarts, fails over, and gets network partitions. The same 200 requests, two designs, measured:

DesignFailed requestsDatabase queries
The cache error propagates2000
Catch it, fall through to the database0200

Row 1 is the accident nobody intends: an optional dependency taking down a service that could have answered every request. Row 2 is right, and it has a condition attached.

Degrading only works if the database can take it Falling through means 100% of traffic reaches Postgres, all at once. If your pool is sized for a 90% cache hit rate, you have just handed it ten times its normal load — and week 40 showed exactly what that queue does to response times.

So degrading is not free. It needs a short cache timeout, so a slow Redis does not become a slow request. It also needs you to have decided what happens if the database cannot cope. Load shedding — serving 503 to some traffic — is a legitimate answer.

The sentence to be able to say “Redis is optional for reads and required for nothing. If it is down we serve from Postgres, which we have load-tested at 100% miss rate, and we shed load above N requests per second.” That is a designed answer. “It should still work” is a hope.
Say it in the simplest words — the Feynman check

1 · In plain words A cache is a second copy of your data in a faster place. Every good thing and every bad thing about caching comes from there being two copies.

So the question is never “is the cache correct?” It is “how wrong may it be, and for how long?” If you cannot answer that for a piece of data, you are not ready to cache it. That answer is also your TTL.

2 · One analogy A printed price list at the till. It is much faster than phoning head office. It is also whatever was true when it was printed.

…and where the analogy breaks A printed list is obviously old. You can see the date on it. A cache looks exactly as authoritative as the database, so nothing about a stale answer feels wrong. I measured a read returning https://first.test while the database held https://SECOND.test — no error, no log line, no slowdown.

And a price list has one more difference that matters: when it goes missing, one person walks to the phone. When a cached key expires, a hundred requests walk to the database at the same instant. I measured that too. 100 concurrent requests for one missing key produced 100 queries, because none had finished writing the answer yet.

3 · The sticking point People measure a cache by its hit rate and stop there. A 99% hit rate says nothing about the 1%. That 1% is where all the damage lives: cold start, a deploy, a Redis restart, or a popular key expiring.

Those moments are correlated by design — everything warmed together expires together. Measured: 1,000 keys on an identical 60-second TTL all expire in the same second, forever, once a minute. Adding ±50% jitter brought the worst second down to 23.

4 · Now you explain it back

In three sentences, explain why a cache can produce zero benefit at exactly the moment it is needed most. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — cache the spine, then break it three ways

Requirements. Create each bug on purpose before you fix it:

  1. Cache the code-to-URL lookup in Redis. Measure the hit and miss latency separately.
  2. Create a stale read. Update a link, watch the old target still serve. Then fix it with invalidation and a TTL, and say in one sentence how wrong the cache may now be.
  3. Create a stampede. 100 concurrent requests on a cold key. Count the database queries — you should see about 100. Add single-flight and count again.
  4. Create unbounded growth. Cache with no TTL, drive traffic, watch memory climb. Then set a TTL, maxmemory and allkeys-lru.
  5. Add ±50% jitter to every TTL.
  6. Kill Redis while load is running. The service must keep answering. Write down what happened to latency and to the pool's waitingCount.
  7. Make step 6 an automated test, not a thing you did once.
The drill

“Users say they see old data about 30 seconds after saving.”

Explain the mechanism in two sentences. Then give two fixes with different trade-offs, and say which you would ship and why. “About 30 seconds” is the clue — it is naming something in your configuration.

Remember this · the 20-second recap
  • A cache is a second copy. The question is never “is it correct?” but “how wrong, for how long?” — and that is your TTL.
  • Use invalidation and a TTL. Invalidation is exact but fragile; the TTL is the net under your mistake.
  • Measured: 100 concurrent requests on one cold key → 100 queries. Single-flight → 1.
  • Identical TTLs synchronise. Measured: 1,000 expiries in one second → 23 with ±50% jitter.
  • No TTL and no eviction is a leak: 52.5 MB for 500,000 keys, growing with traffic. Redis defaults to noeviction.
  • When Redis dies, either 200 requests fail or 200 hit the database. Degrading is right only if the database can take it.
  • Hit rate hides all of this. The damage lives in the misses, and misses arrive together.

If you remember one thing: a cache helps least at the moment you need it most.
