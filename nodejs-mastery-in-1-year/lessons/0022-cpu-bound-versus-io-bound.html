CPU-bound versus I/O-bound

Know which problem you have before you choose a tool. Most “Node is slow” claims are one function.

coreWeek 22 of 52. This lesson builds one domain-expert ability: debug a problem that has no ready answer online. Week 22 in the plan · Glossary

Your win today: one number that tells you which kind of slow you have. Measured: under heavy I/O a heartbeat ran 3 ms late. Under one CPU burst, the same heartbeat ran 155 ms late.
Where you are Week 1 gave you the rule: never block the event loop. It never told you how to tell. This week is the measurement, and weeks 23–25 are the two tools you reach for once you know the answer.

Start from the problem — “it is slow” is two different bugs

A request takes two seconds. There are exactly two reasons, and they need opposite fixes:

  • I/O-bound. Your thread is waiting. A database, a network call, a disk read. The CPU is idle. More concurrency helps; more CPU does not.
  • CPU-bound. Your thread is working. Hashing, resizing an image, parsing something huge. More concurrency makes it worse; you need another core.

Guess wrong and your fix makes things worse. Add concurrency to a CPU-bound service and nothing improves. You get the same total work, plus context switching, plus a longer queue.

The question to ask

The question is not “how long did it take?” It is “was my thread free while it took that long?” That is a different measurement. It is the one that decides your fix.

The measurement — how late does a heartbeat run?

Set a timer for every 50 ms and record how late it actually fires. A late timer means the loop could not get to it. That is the definition of blocked.

let worstLate = 0, expected = Date.now() + 50;
setInterval(() => {
  const late = Date.now() - expected;      // how far behind schedule
  if (late > worstLate) worstLate = late;
  expected = Date.now() + 50;
}, 50);

Now run two workloads that both take about a second, and compare.

The real output (Node v24.14.0):

// 40 concurrent file reads — waiting
io   -> worst tick was 3ms late

// one pbkdf2Sync burst — working
cpu  -> worst tick was 155ms late

Fifty times worse. Both took about the same wall-clock time. Only one of them stopped everything else in the process.

The production version of this perf_hooks.monitorEventLoopDelay() gives you the same signal as a histogram, with percentiles, and costs almost nothing to leave running. Export its p99 as a metric. A rising event-loop delay is the earliest warning a Node service gives you — it moves before latency does, because a queued request has not started being slow yet.
Set the resolution below what you want to see monitorEventLoopDelay({ resolution: 10 }) samples every 10 ms, so it cannot report a delay under 10 ms. My first attempt used the default and reported a floor of 10 ms for both workloads, which made them look identical. The heartbeat above has no such floor, which is why this lesson uses it to teach and the histogram to monitor.

Where the work actually happens

Week 1 said libuv does the waiting. It is worth being precise, because the three cases behave differently:

WorkRuns whereBlocks your loop?
Network I/O — sockets, HTTPThe operating system's own event notificationNo. Effectively unlimited concurrency.
File I/O, dns.lookup, some crypto, zliblibuv's thread pool, 4 threads by defaultNo, but only 4 at a time. The 5th waits.
Your JavaScriptThe one main threadYes. Always.
The middle row is the one that surprises people The thread pool has four threads. Fire twenty pbkdf2 calls — the async ones — and four run while sixteen queue. Your event loop stays free, so this is not blocking, but throughput is capped at four whatever the machine has. Raise it with UV_THREADPOOL_SIZE when the profile says so, and not before. That number is a convention, not a law.
Say it in the simplest words — the Feynman check

1 · In plain words There are two ways for a job to take a long time. You are doing something hard, or you are waiting for somebody else.

They look the same from outside — both take two seconds. But if you are waiting, you can start other jobs while you wait. If you are working, you cannot. So the fix for one makes the other worse.

2 · One analogy A cook. Waiting for water to boil is waiting: they can chop vegetables meanwhile. Kneading dough is working: their hands are busy and nothing else gets done. A stopwatch says both took ten minutes.

…and where the analogy breaks A cook can see they are kneading. Your program cannot tell you which one it is doing, and neither can a stopwatch.

That is why this week has a measurement rather than a rule. You cannot ask “how long did it take?” — the two are identical on that question. You have to ask a second, different question: while it was taking that long, could anything else run? A heartbeat answers it. A duration never will.

3 · The sticking point People reach for concurrency whenever something is slow. It is the thing they learned in weeks 5 to 8.

For CPU-bound work it makes things worse. The same total work still happens on the same one core. Now there is scheduling overhead and a longer queue on top. There are three honest answers. Move it to another thread, do less of it, or say Node is the wrong tool here.

4 · Now you explain it back

In two or three sentences, explain why a duration cannot tell you whether work is CPU-bound. Then say what you would measure instead. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — a blocking detector for the spine API

Add the measurement to the spine, then make it fire.

Requirements:

  1. A lag.js module that reports the worst heartbeat lateness over the last ten seconds.
  2. The spine logs a warning to stderr whenever lateness passes 100 ms, naming the route that was running.
  3. A deliberate /slow-cpu route that hashes a password with pbkdf2Sync.
  4. A deliberate /slow-io route that awaits a 1-second timer.
  5. An experiment that hits /health repeatedly while each slow route runs, and records p99.
# the whole experiment, in four commands
node spine.js &
autocannon -c 10 -d 10 http://localhost:3000/health          # baseline p99
curl localhost:3000/slow-io  & autocannon -c 10 -d 5 http://localhost:3000/health
curl localhost:3000/slow-cpu & autocannon -c 10 -d 5 http://localhost:3000/health

Predict the three p99 numbers before you run it. The I/O one should barely move. The CPU one should be visibly worse, and the warning should fire.

What to hand in Three p99 numbers, and the worst lateness for each. Keep them — week 25 fixes the CPU case with a worker pool, and this is the before.

Remember this · the 20-second recap
  • Slow has two causes: waiting (I/O-bound) and working (CPU-bound). They need opposite fixes.
  • Duration cannot tell them apart. Ask instead: was the thread free while it took that long?
  • Measure it as timer lateness. Verified: 3 ms late under I/O, 155 ms under a CPU burst.
  • In production use perf_hooks.monitorEventLoopDelay() and export its p99.
  • Rising event-loop delay is the earliest warning a Node service gives — it moves before latency.
  • Network I/O uses the OS. File, DNS and some crypto use libuv's 4-thread pool. Your JavaScript uses the one thread.
  • Adding concurrency to CPU-bound work makes it worse, not better.

If you remember one thing: one busy core and seven idle ones is a CPU-bound diagnosis. More concurrency is the wrong fix.
