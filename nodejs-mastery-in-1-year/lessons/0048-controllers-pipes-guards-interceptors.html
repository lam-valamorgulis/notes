Controllers, pipes, guards, interceptors

Four places to put code. Knowing which one, and in what order they run, is the whole skill.

coreWeek 48 of 52. This lesson builds one domain-expert ability: put each piece of logic where it will still be right in a year. Week 48 in the plan · Glossary

Your win today: when a guard rejects, exactly two things run. You will see the log line that proves it, and it answers the rate-limiting question for good.
Where you are Week 47 was about how objects get built. This week is about where a request goes once one of them has to handle it.

Start from the problem — what does a request actually need?

Before any framework names, list the jobs. Every HTTP request needs the same four questions answered, and they have a natural order:

QuestionWhenNest calls it
Are you allowed here at all?First — before any workGuard
Wrap this: time it, log it, transform the resultAround everythingInterceptor
Is this input the right shape?Just before the handlerPipe
Do the actual jobThe point of it allHandler
Something threw — turn it into a responseWhenever it goes wrongFilter
Why the order is not arbitrary

Cheap rejections come first. There is no point parsing a body for a request you were going to refuse anyway.

The order, measured

One controller with all five, each pushing its name onto a list. Measured on NestJS 12.0.1:

A. everything passes     : guard → interceptor:before → pipe → handler → interceptor:after
B. guard denies          : guard → filter
C. pipe rejects the body : guard → interceptor:before → pipe → filter

Read line B again. When the guard says no, two things run. The interceptor never started, the pipe never parsed, the handler never existed.

This is the answer to the rate-limiting question Rate limiting goes in a guard, because a guard rejects before anything else costs you anything. Put it in the controller and you have already run the interceptor, parsed and validated the body, and possibly hit the database — for a request you were going to refuse.

Under an attack, that difference is the whole defence. A rate limiter that runs after body parsing is a rate limiter that can be used to exhaust you.

Line C has a subtler lesson. The pipe threw, so the handler never ran — and neither did interceptor:after. An interceptor that logs the response time will log nothing at all for a failed request. That is exactly the traffic you most want to see.

The metrics gap almost everybody ships tap() runs on success only. To measure failures you need tap({ next, error }) or finalize(). Otherwise your latency dashboard silently describes only the requests that worked, and your worst traffic is invisible.

Choosing between them

The decision is nearly always guard versus pipe, and there is a clean test:

Guard or pipe?

A guard answers a yes/no about the request and returns a boolean. A pipe answers a question about one value and returns the value, possibly transformed.

RequirementWhereBecause
Rate limitingGuardReject before anything costs you. Measured: two steps.
Is this token valid?GuardYes/no about the request, and cheap to answer.
Does this user own this link?GuardStill yes/no — though it may need a query.
Is url a string, and a safe scheme?PipeA question about one value, and it returns the parsed value.
Turn :id into a numberPipeA transformation of one value.
Log the request and its durationInterceptorIt wraps the handler — it needs both sides.
Turn an error into a response bodyFilterIt only runs when something threw.
The controller is not one of the options Anything in the table above that ends up in a controller is in the wrong place, and the symptom is always the same: it gets copied into the next controller, then the one after, and one copy is eventually missed. Cross-cutting logic goes in the thing that cuts across.

Your week 28 error taxonomy becomes a filter

You already decided this in week 28: operational errors become a response, programmer errors do not get swallowed. A filter is where that decision lives now.

@Catch()
export class ErrorFilter implements ExceptionFilter {
  catch(err: unknown, host: ArgumentsHost) {
    const res = host.switchToHttp().getResponse();

    if (err instanceof ValidationError)  return res.status(400).json(body('invalid_input', err));
    if (err instanceof NotFoundError)    return res.status(404).json(body('not_found', err));
    if (err instanceof CodeTakenError)   return res.status(409).json(body('code_taken', err));

    // not ours. log it with the request id, and say nothing useful to the client.
    logger.error({ err, requestId: res.locals.requestId });
    return res.status(500).json(body('internal', null));
  }
}
One filter, not one per error A single filter holding the whole taxonomy is a page you can read to know every status code the service can return. Scatter it and that page stops existing, and the 409 you argued for in week 21 quietly becomes a 500 somewhere.

Notice the catch(err: unknown. That is week 44: anything can be thrown, so narrow before you use it.

Say it in the simplest words — the Feynman check

1 · In plain words Every request needs the same few questions answered in the same order. Are you allowed? Is the input the right shape? Do the job. And if something throws, turn it into a response.

Nest gives each question its own place — guard, pipe, handler, filter — with an interceptor wrapped around the whole thing. Putting a question in the wrong place still works, which is why the mistake survives so long.

2 · One analogy Airport security. The ticket check is at the door, the bag scan is at the gate. Both refuse people, but the door is deliberately first, because it is the cheapest place to say no.

…and where the analogy breaks At an airport the cost of checking late is a queue. In a service it is a weapon. If your rate limiter runs after body parsing, an attacker gets you to parse every request before you refuse it.

I measured what a guard rejection actually costs: two steps. Guard, then filter. No interceptor, no parsing, no validation, no query. The same rejection from inside a controller would have run all of it first. That gap is not an optimisation — it is the reason guards exist.

3 · The sticking point People think an interceptor sees everything, because it wraps the handler. It does not. Measured: when the pipe rejected a body, the run was guard → interceptor:before → pipe → filter — the interceptor's after half never ran.

So a logging interceptor using tap() records nothing for failed requests. Your latency dashboard then describes only the traffic that worked. Use tap({ next, error }) or finalize(), or your worst requests stay invisible.

4 · Now you explain it back

In three sentences, explain why rate limiting in a controller is worse than rate limiting in a guard. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

The drill

“Where does rate limiting go, and why not in the controller?”

Answer with the measured sequence, not with “separation of concerns”. Then extend it: where would you put rate limiting that has to be shared across several instances of the service, and what does that add? A guard is the right layer, and one process's memory is the wrong store.

Say it like an interviewer just asked

What this lesson left out on purpose Middleware runs before guards and is the right place for a few things, mostly ones that need the raw request. class-validator and ValidationPipe are how most Nest projects do validation, and worth learning after you have written a pipe by hand. Custom decorators for pulling the current user out of a request are a small, useful pattern. Global versus controller versus method scope changes what applies where. Distributed rate limiting needs shared state, which is a Redis problem, not a Nest one.

Remember this · the 20-second recap
  • Order, measured: guard → interceptor → pipe → handler → interceptor (after). Cheap rejections first.
  • Guard denies → guard, filter. Two steps. No parse, no validation, no query.
  • So rate limiting goes in a guard. In a controller, an attacker makes you do all the work before you refuse.
  • Pipe rejects → guard → interceptor:before → pipe → filter. The interceptor's after never runs.
  • So tap() logs nothing for failures. Use tap({ next, error }) or finalize().
  • Guard = yes/no about the request, returns a boolean. Pipe = a question about one value, returns the value.
  • Week 28's taxonomy goes in one filter, so every status the service can return is on one page.

If you remember one thing: a guard rejection costs two steps. That is not an optimisation — it is why guards exist.
