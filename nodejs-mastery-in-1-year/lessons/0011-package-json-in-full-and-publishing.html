package.json in full, and publishing

Four fields decide whether a stranger can use your code. Then one number decides whether they can trust it.

depthWeek 11 of 52. This lesson builds one domain-expert ability: say why it was built this way, and what that choice gives up. Week 11 in the plan · Glossary

Your win today: you will publish a real package that a stranger can install, and you will be able to defend every field in its package.json. You will also know what a version number actually promises, and the exact place that promise breaks.
Why this week is tagged depth, not core You publish a package a few times a year, not weekly. So this is queued material, and it is honest to say so. It is here anyway for one reason: week 9 showed you exports from the consumer side, where it only blocks you. This week you stand on the other side and see why the author locked it. That change of view is worth a week.

Start from the problem — a stranger has your folder

Your code works. Now someone you have never met has to run it. What do they need that a folder of files does not give them?

Four things, and each one is a field:

  1. A way to refer to it. Not a path — a name. → name
  2. A way to know which file to start at. Your folder has forty. → exports
  3. A way to know what they are allowed to touch. → also exports
  4. A way to know whether an upgrade will break them. → version

That is the whole subject. Everything else in package.json is either settings for other tools or an old field kept for compatibility.

Identity — name and version

Together these are the primary key of the whole ecosystem. Once you publish my-tool@1.0.0, that exact pair is permanent and immutable. You cannot change what it contains, ever. You can only publish a new version.

npm did not make that rule to be strict. It is the only thing that makes a lockfile mean anything. A lockfile — package-lock.json — records the exact version of every package an install chose. It is a record of what ran, not a wish about what should run.

Say 1.0.0 could change under you. Then a lockfile would record a promise nobody keeps. A build that passed on Monday could fail on Tuesday, with no commit in between.

Publish under a scope while you are learning A scoped name like @yourname/word-freq is yours alone, so you cannot collide with an existing package and you will not spend twenty minutes inventing a free name. Scoped packages are private by default, so the first publish needs npm publish --access public.

exports — the door, now from the inside

In week 9 this field blocked you with ERR_PACKAGE_PATH_NOT_EXPORTED. Here is why an author wants that.

Before exports existed, every file in a package was public. Not by intent — by accident, because nothing could stop require('some-pkg/lib/internal/helper'). So the moment anyone did that, the author could never rename helper.js again without breaking a stranger's build. Whole packages froze their internal structure because of files they never meant to publish.

exports is the author drawing a line around what they promise to keep:

{
  "name": "@you/word-freq",
  "version": "1.0.0",
  "exports": {
    ".":          "./src/index.js",     // import '@you/word-freq'
    "./counters": "./src/counters.js"   // import '@you/word-freq/counters'
  }
}

Everything else in src/ is now unreachable, even though it ships. You can rename it, split it, or delete it, and nobody's build breaks.

One package, two module systems

Some of your users write require(). Some write import. You can serve both from one package, because exports accepts conditions:

{
  "exports": {
    ".": {
      "require": "./index.cjs",
      "import":  "./index.mjs"
    }
  }
}

Node picks the branch that matches how it was loaded. Verified on Node v24.14.0:

require('dual').who   // 'CommonJS build'
import { who } from 'dual'   // 'ESM build'
The dual-package hazard Ship both builds and a user can end up with both loaded at once — one through require, one through import. They are two separate module instances. Any module-level state, any instanceof check, any cache is now duplicated and quietly wrong. The safe shapes are: ship ESM only, or keep all state in the CommonJS build and make the ESM file a thin re-export. Shipping two independent implementations is the shape that goes wrong.

files — what actually leaves your machine

files is an allow-list. Anything not listed is not uploaded. Verified: a package with "files": ["index.cjs"] and a SECRET.txt sitting next to it packs 2 files — index.cjs and package.json. The secret never left. You may see 3: npm always adds README, LICENSE and CHANGELOG, and the main file, whatever files says. files cannot exclude those.

Always look before you publish:

npm pack --dry-run

It prints the exact tarball contents without uploading anything. Run it every single time. It costs two seconds and it is the only step between you and a permanently published credential.

main — the field exports replaced

main names one entry file and nothing else. So it answers “where do I start” and it cannot answer “what may you touch”. That is the whole reason it is not enough on its own any more. A package with only main still leaves every other file reachable. That is the freeze described above.

Keep it for consumers on old Node. When both fields are present, exports wins.

bin — turning a file into a command

{ "bin": { "wordfreq": "./cli.js" } }

On install, npm puts wordfreq on the user's PATH. Two things must be true or it fails in a confusing way:

  • The file starts with #!/usr/bin/env node. Without it the shell has no idea it is JavaScript.
  • The file is executable. npm handles this on install, but not when you run it straight from a clone.

Semver — the promise, and where it lies

ChangeBumpWhat you are promising
Fixed a bug1.0.1 patchUpgrade freely. Nothing you use has changed.
Added a feature1.1.0 minorUpgrade freely. Old code still works.
Removed or changed something2.0.0 majorRead the notes. Your code may break.
Where the promise breaks Semver is a claim about intent, not a fact the tooling can check. Nothing verifies it. Three ways a patch release breaks you anyway:
  • The author did not know it was breaking. A bug fix is a behaviour change to anyone who had worked around the bug.
  • You depended on something not in the contract — an internal file, or the exact wording of an error message.
  • A transitive dependency moved. Their patch pulled a new minor of something three levels down.
This is why a lockfile exists. Semver says what an upgrade should be safe to do; the lockfile records what you actually ran. Trust the second one.
Say it in the simplest words — the Feynman check

1 · In plain words Publishing is writing a short contract with people you will never meet. The contract says four things.

  • what your code is called
  • which file to open first
  • which parts they are allowed to touch
  • what the version number promises about the next upgrade

Nothing else in the file matters as much as those four.

2 · One analogy A shop. name is the sign above the door. files is what you actually load into the van — leave the staff room and the safe behind. exports is which doors you unlock for customers. version is the label promising that this month's product works like last month's.

…and where the analogy breaks A shop can rearrange its back rooms any night it likes. You cannot. A stranger builds a habit around any door you leave unlocked, even once. Locking it later is a breaking change. So the lock has to go on before the first customer arrives.

And the label lies more often than a shop label would. Nothing checks a version number. It is one person's honest guess about their own code, and honest people are sometimes wrong.

…and one more thing no shop does A shop is one building. Your package is not. One project can end up with two copies of it open at once — one reached through require, one through import.

Each copy has its own counters and its own private memory. A value set in one is invisible to the other. Nothing in a shop behaves like that. So the dual-package hazard feels impossible, right up until it happens to you.

3 · The sticking point People think files and exports do the same job. Both sound like “what is in my package”.

They are completely different gates. files decides what gets uploaded. exports decides what can be reached from what was uploaded. A file can ship and still be unreachable. That is usually exactly what you want. It ships so the code works. It stays unreachable so you can still rename it.

Get them confused and one of two things happens. You publish your .env. Or you freeze your own folder structure forever.

4 · Now you explain it back

In two or three sentences, explain the difference between files and exports. Then say what goes wrong if you get each one wrong. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — publish something today

Small on purpose. The point is the whole loop, end to end, not the package.

1 · Make it

mkdir -p hello && cd hello        # plain folder name — the scope is added by npm
npm init --scope=@yourname -y
printf 'export const hello = (n) => `hello ${n}`;\n' > index.mjs
printf 'nothing to see\n' > SECRET.txt        # deliberate — see step 3

2 · Write the contract

{
  "name": "@yourname/hello",
  "version": "1.0.0",
  "type": "module",
  "exports": { ".": "./index.mjs" },
  "files": ["index.mjs"]
}

3 · Check the file list — do this before every publish

npm pack --dry-run

Confirm SECRET.txt is not in the list. Then delete the files field and run it again. Watch the secret appear. That difference is the lesson. Put the field back.

4 · Ship it

npm login
npm publish --access public

5 · Be your own user

cd /tmp && mkdir user && cd user && npm init -y
npm install @yourname/hello
node --input-type=module -e "import {hello} from '@yourname/hello'; console.log(hello('world'))"
What to hand in Not the package — the two npm pack --dry-run outputs, with and without files, saved side by side. That pair is the thing you will remember in six months, and it is what stops you publishing a credential one tired evening.
You can undo this, within 72 hours npm unpublish @yourname/hello --force always works in the first 72 hours. After that it still works while three things are true: nothing depends on it, it has under 300 downloads a week, and it has one owner — which a learning package easily meets. What is permanent is the exact name@version pair; that pair can never be published again. The name itself becomes free 24 hours after you remove every version.
Scenario

Your team's internal package ships src/utils/format.js. Nobody documented it, but three services now import it directly. You need to rename the file.

Say what has actually gone wrong here, name the one field that would have prevented it, and say why adding that field now is a major version bump rather than a patch.

Remember this · the 20-second recap
  • A package answers four questions. What is it called? Where do you start? What may be touched, and is upgrading safe?
  • name + version are permanent and immutable once published. That is what makes a lockfile mean anything.
  • exports lists the reachable entry points, so you stay free to rename internals. Its conditions serve require and import from one package — watch the dual-package hazard.
  • files is an allow-list for the upload. Different gate, different job from exports.
  • bin maps a command name to a file, and that file needs #!/usr/bin/env node on its first line.
  • npm pack --dry-run before every publish. It is the only step between you and a published secret.
  • Semver is a promise about intent. Nothing verifies it, so the lockfile is what you actually trust.

If you remember one thing: files decides what is uploaded; exports decides what is reachable. Confusing them either leaks a secret or freezes your folder structure forever.
