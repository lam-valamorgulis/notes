Piece 1 — a timeout you can actually cancel

A slow endpoint is worse than a failing one: it holds a connection open and blocks a pool slot forever. You need to give up after N milliseconds. The modern, correct tool is AbortController — a standard way to cancel an still-running operation. fetch accepts an AbortSignal; when the signal fires, the fetch rejects and the underlying connection is torn down.

Node gives you a one-liner for the common case, AbortSignal.timeout(ms), which aborts automatically after the delay:

async function fetchJson(url, timeoutMs = 3000) {
  const res = await fetch(url, { signal: AbortSignal.timeout(timeoutMs) });
  if (!res.ok) throw new Error(`HTTP ${res.status}`);   // treat 4xx/5xx as failures
  return res.json();
}
Why not just Promise.race a timer? You can race the fetch against a setTimeout reject (Lesson 7) — but that only makes your promise reject; the real request keeps running in the background, still holding a socket. AbortController actually cancels the work. Racing hides the slow call; aborting stops it.

Piece 2 — retry with exponential backoff (and jitter)

Networks fail briefly, and a retry turns a transient failure into a success. But retrying immediately and constantly just adds load to a struggling server.

So you wait longer after each failure — exponential backoff: 200ms, 400ms, 800ms. And you add a little randomness, called jitter, so a thousand clients do not all retry at the same moment.

const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

async function withRetry(fn, { retries = 3, baseMs = 200 } = {}) {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fn();                       // success → return immediately
    } catch (err) {
      if (attempt >= retries) throw err;        // out of tries → give up, propagate
      const backoff = baseMs * 2 ** attempt;    // 200, 400, 800, ...
      const jitter  = Math.random() * backoff;  // spread the herd
      await sleep(backoff + jitter);            // wait, then loop to retry
    }
  }
}
Only retry what's worth retrying Retrying a 404 Not Found or a 400 Bad Request is pointless — the answer won't change, and you've tripled the load for nothing. Retry transient failures: timeouts, connection resets, 429 Too Many Requests, and 5xx. A production withRetry inspects the error and only retries the retryable ones. Keep that nuance in your pocket for the interview.

Piece 3 — the pool that never discards a result

The runner from Lesson 7, with one deliberate change. The worker catches its own error and returns a result object instead of throwing. That gives allSettled behaviour: the pool never fails fast, and we keep every outcome.

// Lesson 7's pool, unchanged. The whole change is inside the worker:
const worker = async (url) => {
  try {
    return { url, ok: true,  data: await fetchWithRetry(url) };
  } catch (err) {
    return { url, ok: false, error: err.message };   // catch, never throw
  }
};

One try/catch is the entire difference. Because the worker never throws, the runner's await never rejects, so Promise.all(pool) can never fail fast. You get allSettled behaviour out of a plain Promise.all, and you sort the outcomes afterwards with results.filter(r => r.ok).

Say it in the simplest words — the Feynman check

1 · In plain words A network call that works perfectly on your laptop behaves differently on a real network. Sometimes it takes forever. Sometimes it fails for no reason. Three habits fix that. Give every call a deadline. If it fails, try again, waiting longer each time. And never have more than a fixed number running at once.

2 · One analogy Three rules for phoning your way down a list of people. Hang up after 30 seconds of ringing. If nobody answers, call back later, and leave a longer gap each time. And never have more than ten phones ringing at once.

…and where the analogy breaks With telephones, calling somebody back costs nothing. With a network call it can cost a great deal. A retry can charge a card twice, or send the same email twice.

Retrying is only safe when repeating the call does no harm. That property has a name, idempotency, and it is the whole subject of week 42. Until then, only retry reads.

3 · The sticking point People add retries and believe they have added safety. Often they have added load. A failing server is usually failing because it is overloaded, and your retry sends it three times the traffic.

Retries rescue a short failure. They make an overload worse. That is why backoff and jitter are not optional extras. Without them, a retry is an attack.

Build it for real — the full aggregator

One file. Modern Node (node -v ≥ 18 for fetch; ≥ 17.3 for AbortSignal.timeout).

aggregator.js

const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

// --- Piece 1: fetch with a real, cancellable timeout ---
async function fetchJson(url, timeoutMs = 3000) {
  const res = await fetch(url, { signal: AbortSignal.timeout(timeoutMs) });
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
}

// --- Piece 2: retry with exponential backoff + jitter ---
async function withRetry(fn, { retries = 3, baseMs = 200 } = {}) {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fn();
    } catch (err) {
      if (attempt >= retries) throw err;
      const backoff = baseMs * 2 ** attempt;
      await sleep(backoff + Math.random() * backoff);
    }
  }
}

// --- Piece 3: the concurrency pool (never fail-fast) ---
async function mapWithConcurrency(items, limit, worker) {
  const results = new Array(items.length);
  let next = 0;
  async function runner() {
    while (next < items.length) {
      const i = next++;
      results[i] = await worker(items[i], i);   // worker never throws (see below)
    }
  }
  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, runner));
  return results;
}

// --- Put it together: fetch many URLs, reliably ---
async function aggregate(urls, { concurrency = 10, timeoutMs = 3000, retries = 3 } = {}) {
  return mapWithConcurrency(urls, concurrency, async (url) => {
    try {
      const data = await withRetry(() => fetchJson(url, timeoutMs), { retries });
      return { url, ok: true, data };
    } catch (err) {
      return { url, ok: false, error: err.message };   // caught → allSettled-style
    }
  });
}

// --- Run it ---
(async () => {
  const urls = [
    'https://httpbin.org/json',
    'https://httpbin.org/delay/1',
    'https://httpbin.org/status/500',    // will fail → retried → reported
    'https://httpbin.org/delay/10',       // will reach the 3s timeout
  ];

  const start = Date.now();
  const results = await aggregate(urls, { concurrency: 2, timeoutMs: 3000, retries: 2 });
  const ok  = results.filter((r) => r.ok);
  const bad = results.filter((r) => !r.ok);

  console.log(`done in ${Date.now() - start}ms — ${ok.length} ok, ${bad.length} failed`);
  bad.forEach((r) => console.log('  failed:', r.url, '→', r.error));
})();

Run node aggregator.js. The good URLs return data. The 500 ones are retried with growing pauses, then reported as failed. The delay/10 URL gives up at the 3-second timeout. All of it with at most 2 requests at once, and no crash. That is the shape of reliable fetching.

The habits this build bakes in

  • Bound everything. Concurrency is bounded (the pool), waiting is bounded (the timeout), retries are bounded (max attempts). Unbounded anything is a production incident that will happen.
  • Handle a failed item quietly; let a real bug throw. A single URL failing is expected data, so it's caught and reported. A programming mistake still throws — you do not hide those (Lesson 6).
  • Cancel, don't just ignore. AbortController stops the real work; a raced timer only hides it.
  • Be a polite client. Backoff + jitter means that when a server is struggling, you send less, not more.
One real habit (full version later) Production aggregators often add a circuit breaker: if one endpoint fails repeatedly, stop calling it for a while instead of retrying every time. The same idea as backoff, at a bigger scale. Know the term; we'll use it when we harden the one API we build from week 21 in Phase 3.

Remember this · the 20-second recap
  • An aggregator calls many sources at once and collects results. The simple Promise.all(urls.map(u => fetch(u))) breaks four ways in production.
  • Timeout: use AbortController or AbortSignal.timeout(ms) to actually cancel a slow request. A raced timer only hides it while the socket stays open.
  • Retry with exponential backoff and jitter: wait longer after each failure, 200·2ⁿ plus randomness. A short failure then recovers without stampeding a struggling server. Only retry transient errors — timeouts, 429, 5xx — never 4xx.
  • Concurrency pool: cap running requests to N so you do not flood. Make the worker catch its own error and return a result object. That is allSettled style, so one failure never discards the batch.
  • The mindset: bound everything — concurrency, waiting, retries. Fail soft on data, loud on bugs. Cancel, do not ignore. Be a polite client.

If you remember one thing: reliable fetching is a bounded pool, a real timeout and backoff retries. Collect every outcome instead of failing fast.
