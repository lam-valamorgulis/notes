What we're building, and why each piece exists

An aggregator fans out to many sources and collects their answers — a price checker hitting 200 suppliers, a dashboard pulling 50 microservices, a link checker verifying 1,000 URLs. The naïve version is one line and three latent production incidents:

const data = await Promise.all(urls.map((u) => fetch(u).then((r) => r.json())));

Piece 1 — a timeout you can actually cancel

A slow endpoint is worse than a failing one: it holds a connection open and blocks a pool slot forever. You need to give up after N milliseconds. The modern, correct tool is AbortController — a standard way to cancel an in-flight operation. fetch accepts an AbortSignal; when the signal fires, the fetch rejects and the underlying connection is torn down.

Node gives you a one-liner for the common case, AbortSignal.timeout(ms), which aborts automatically after the delay:

async function fetchJson(url, timeoutMs = 3000) {
  const res = await fetch(url, { signal: AbortSignal.timeout(timeoutMs) });
  if (!res.ok) throw new Error(`HTTP ${res.status}`);   // treat 4xx/5xx as failures
  return res.json();
}
Why not just Promise.race a timer? You can race the fetch against a setTimeout reject (Lesson 7) — but that only makes your promise reject; the real request keeps running in the background, still holding a socket. AbortController actually cancels the work. Racing hides the slow call; aborting stops it.

Piece 2 — retry with exponential backoff (and jitter)

Networks blip. A retry turns a transient failure into a success. But retrying immediately and constantly just adds load to a struggling server — so you wait longer after each failure (exponential backoff: 200ms, 400ms, 800ms…) and add a little randomness (jitter) so a thousand clients don't all retry in lockstep and create a synchronized stampede.

const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

async function withRetry(fn, { retries = 3, baseMs = 200 } = {}) {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fn();                       // success → return immediately
    } catch (err) {
      if (attempt >= retries) throw err;        // out of tries → give up, propagate
      const backoff = baseMs * 2 ** attempt;    // 200, 400, 800, ...
      const jitter  = Math.random() * backoff;  // spread the herd
      await sleep(backoff + jitter);            // wait, then loop to retry
    }
  }
}
Only retry what's worth retrying Retrying a 404 Not Found or a 400 Bad Request is pointless — the answer won't change, and you've tripled the load for nothing. Retry transient failures: timeouts, connection resets, 429 Too Many Requests, and 5xx. A production withRetry inspects the error and only retries the retryable ones. Keep that nuance in your pocket for the interview.

Piece 3 — the pool that never discards a result

The runner from Lesson 7, with one deliberate change: the worker catches its own error and returns a result object instead of throwing. That gives us allSettled behaviour — the pool never fails-fast, and we keep every outcome, success or failure.

Build it for real — the full aggregator

One file. Modern Node (node -v ≥ 18 for fetch; ≥ 17.3 for AbortSignal.timeout).

aggregator.js

const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

// --- Piece 1: fetch with a real, cancellable timeout ---
async function fetchJson(url, timeoutMs = 3000) {
  const res = await fetch(url, { signal: AbortSignal.timeout(timeoutMs) });
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();
}

// --- Piece 2: retry with exponential backoff + jitter ---
async function withRetry(fn, { retries = 3, baseMs = 200 } = {}) {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fn();
    } catch (err) {
      if (attempt >= retries) throw err;
      const backoff = baseMs * 2 ** attempt;
      await sleep(backoff + Math.random() * backoff);
    }
  }
}

// --- Piece 3: the concurrency pool (never fail-fast) ---
async function mapWithConcurrency(items, limit, worker) {
  const results = new Array(items.length);
  let next = 0;
  async function runner() {
    while (next < items.length) {
      const i = next++;
      results[i] = await worker(items[i], i);   // worker never throws (see below)
    }
  }
  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, runner));
  return results;
}

// --- Put it together: fetch many URLs, resiliently ---
async function aggregate(urls, { concurrency = 10, timeoutMs = 3000, retries = 3 } = {}) {
  return mapWithConcurrency(urls, concurrency, async (url) => {
    try {
      const data = await withRetry(() => fetchJson(url, timeoutMs), { retries });
      return { url, ok: true, data };
    } catch (err) {
      return { url, ok: false, error: err.message };   // caught → allSettled-style
    }
  });
}

// --- Run it ---
(async () => {
  const urls = [
    'https://httpbin.org/json',
    'https://httpbin.org/delay/1',
    'https://httpbin.org/status/500',    // will fail → retried → reported
    'https://httpbin.org/delay/10',       // will hit the 3s timeout
  ];

  const start = Date.now();
  const results = await aggregate(urls, { concurrency: 2, timeoutMs: 3000, retries: 2 });
  const ok  = results.filter((r) => r.ok);
  const bad = results.filter((r) => !r.ok);

  console.log(`done in ${Date.now() - start}ms — ${ok.length} ok, ${bad.length} failed`);
  bad.forEach((r) => console.log('  failed:', r.url, '→', r.error));
})();

Run node aggregator.js. You'll see the good URLs return data, the 500 get retried (with growing pauses) and then reported as failed, and the delay/10 URL give up at the 3-second timeout — all while at most 2 requests run at once, and the program never crashes on a failure. That is the shape of resilient real-world fetching.

The habits this build bakes in

  • Bound everything. Concurrency is bounded (the pool), waiting is bounded (the timeout), retries are bounded (max attempts). Unbounded anything is a production incident waiting to happen.
  • Fail soft on items, loud on bugs. A single URL failing is expected data, so it's caught and reported. A programming mistake still throws — you don't swallow those (Lesson 6).
  • Cancel, don't just ignore. AbortController stops the real work; a raced timer only hides it.
  • Be a polite client. Backoff + jitter means that when a server is struggling, you ease off instead of piling on.
One real habit (full version later) Production aggregators often add a circuit breaker: if one endpoint fails repeatedly, stop calling it for a while instead of retrying every time. Same spirit as backoff, one level up. Know the term; we'll use it when we harden the spine API in Phase 3.

Remember this · the Feynman summary
  • An aggregator fans out to many sources and collects results. The naïve Promise.all(urls.map(fetch)) breaks four ways in production.
  • Timeout: use AbortController / AbortSignal.timeout(ms) to actually cancel a slow request — a raced timer only hides it while the socket stays open.
  • Retry with exponential backoff + jitter: wait longer after each failure (200·2ⁿ) plus randomness, so a blip recovers without stampeding a struggling server. Only retry transient errors (timeouts, 429, 5xx), not 4xx.
  • Concurrency pool: cap in-flight requests to N so you don't flood. Make the worker catch its own error and return a result object → allSettled-style, so one failure never discards the batch.
  • The mindset: bound everything (concurrency, waiting, retries); fail soft on data, loud on bugs; cancel don't ignore; be a polite client.

If you remember one thing: resilient fetching = a bounded pool + a real timeout + backoff retries, collecting every outcome instead of failing fast.
