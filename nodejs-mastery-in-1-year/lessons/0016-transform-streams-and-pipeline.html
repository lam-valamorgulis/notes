Transform streams and pipeline

Chaining stages is easy. Cleaning up when one of them fails is the part that has a right answer.

coreWeek 16 of 52. This lesson builds one domain-expert ability: say why it was built this way, and what that choice gives up. Week 16 in the plan · Glossary

Your win today: you will answer “why pipeline and not pipe?” with a failure you have reproduced, not with “it is better”. You will also write a Transform from scratch, including the part everyone forgets.
Where you are Week 15 was one producer and one consumer. Real work has stages in between: parse, filter, compress, write. This week is how to join them so a failure in the middle does not leave the rest running.

Start from the problem — a stage is both ends at once

You have a readable source and a writable destination. Now you want something in the middle: uppercase every line, or strip a column, or gzip.

What is that middle thing? Ask what it must do:

  • It has to accept chunks. That is a Writable.
  • It has to produce chunks. That is a Readable.

So it is both. Node calls the general case a Duplex. The special case, where the output is made from the input, is a Transform. That is the whole idea. A Transform is a Writable and a Readable stuck together, with your function in the middle.

const { Transform } = require('node:stream');

const upper = new Transform({
  transform(chunk, encoding, callback) {
    callback(null, chunk.toString().toUpperCase());   // error first, then output
  },
});

Backpressure passes straight through it, for free. If the destination says false, the Transform stops pulling, and the source stops being read. The message from week 15 travels the whole chain.

The part everyone forgets — _flush

Some transforms hold data back. A line splitter cannot emit a line until it has seen the newline, so it keeps a remainder. When the input ends, that remainder is still inside.

flush is your last chance to push it out:

const splitLines = new Transform({
  readableObjectMode: true,
  transform(chunk, enc, cb) {
    this.rest = (this.rest || '') + chunk.toString();
    const parts = this.rest.split('\n');
    this.rest = parts.pop();            // keep the unfinished last piece
    for (const line of parts) this.push(line);
    cb();
  },
  flush(cb) {
    if (this.rest) this.push(this.rest);   // the final line, with no newline after it
    cb();
  },
});
Leave out flush and you lose the last record Silently. The file that ends without a trailing newline drops its final row, and nothing errors. It is the same shape of bug as week 14's split character: correct on tidy data, wrong on real data, and invisible until someone counts.

Now the real subject — what happens when a stage fails

pipe is the old way to join two streams. It looks fine:

source.pipe(transform).pipe(destination);

Now make the destination fail, and check whether the source was cleaned up. This is the experiment:

const r = source();                         // a readable
const w = sinkThatErrors();                 // a writable that calls cb(new Error(...))

r.pipe(w);
w.on('error', () => console.log('source destroyed?', r.destroyed));

The real output (Node v24.14.0):

pipe     -> source destroyed? false
pipeline -> source destroyed? true

With pipe, the source is still alive. Its file descriptor is still open. It is still reading. Nothing is consuming what it produces, and nobody will ever close it.

The answer to the interview question

pipe forwards data but not failure. When one stream dies, the others are never told. pipeline exists because that clean-up is the same every time, and everybody got it wrong.

So use pipeline. It takes the stages, plus a callback, and it destroys every stream in the chain when any of them fails:

const { pipeline } = require('node:stream/promises');

await pipeline(
  fs.createReadStream('in.csv'),
  splitLines,
  upper,
  fs.createWriteStream('out.csv'),
);   // throws if any stage fails, and cleans up all of them
Which import to use node:stream gives you the callback version. node:stream/promises gives you the await version. Prefer the promise one — a failed pipeline then throws where you can try/catch it, which is week 6's rule applied here.

A stage does not have to be a stream

pipeline accepts an async generator as a stage. Often that is clearer than a Transform subclass, because the state is just a local variable:

await pipeline(
  Readable.from(['a\n', 'b\n', 'c\n']),
  async function* (source) {
    for await (const chunk of source) yield chunk.toString().toUpperCase();
  },
  async function (sink) {
    for await (const chunk of sink) out.push(chunk);
  },
);
// out.join('') === "A\nB\nC\n"

Verified on Node v24.14.0. The for await loop is the backpressure: nothing is pulled from the source until the body comes round again.

When to use which Use an async generator for one-off logic inside a pipeline — it is shorter and the remainder is a plain variable. Use a Transform class when the stage is reused in several places, or when you need the extra control that flush, destroy and options give you.
Say it in the simplest words — the Feynman check

1 · In plain words You join several machines into a line, and work passes down it. A middle machine is just one that both takes work in and puts work out.

The hard part is not joining them. It is what happens when one machine breaks. The old way told the machine after it, and nobody else. The machines before it kept working, feeding a line that goes nowhere.

2 · One analogy A factory line with a fire alarm. pipe is a line with no alarm at all. If one station stops, the stations behind it keep pushing work onto the floor. pipeline is the same line with one alarm wired to every station.

…and where the analogy breaks In a factory, work piling on the floor is obvious. Somebody shouts. Here nothing is visible: the source keeps its file open, keeps reading, and never finishes.

Nothing crashes and nothing is logged. You find out weeks later, when the process runs out of file descriptors under load. That is a long way from the failure that caused it. The alarm is not for safety. It is because without it, the failure has no symptom at all.

3 · The sticking point People think pipe versus pipeline is a style preference, like var against let. It is not. They behave identically on the happy path and differently on every failure.

So the difference is invisible in every test that passes. It appears only in the case you did not test. That is why “we have always used pipe and it is fine” is not evidence of anything.

4 · Now you explain it back

In two or three sentences, say what pipeline does that pipe does not. Name the failure, not the feature. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — prove the leak, then close it

Save as leak.js and run it twice.

const { Readable, Writable, pipeline } = require('node:stream');
const mode = process.argv[2];                     // 'pipe' or 'pipeline'

const src = () => {
  let i = 0;
  return new Readable({ read() { this.push(i++ < 5 ? `row ${i}\n` : null); } });
};
const sink = () => new Writable({
  write(c, e, cb) { cb(new Error('sink exploded')); },
});

const r = src(), w = sink();

if (mode === 'pipe') {
  r.pipe(w);
  w.on('error', () => setImmediate(() =>
    console.log('pipe     -> source destroyed?', r.destroyed)));
} else {
  pipeline(r, w, () => setImmediate(() =>
    console.log('pipeline -> source destroyed?', r.destroyed)));
}
node leak.js pipe
node leak.js pipeline

Then build the real thing. A three-stage pipeline over a CSV:

  1. Split the byte stream into lines, with a flush for the last one.
  2. Filter — drop rows whose amount is below a threshold.
  3. Write the survivors to a new file.

Then throw from the middle stage on purpose, on row 50. Run it with pipe and with pipeline, and check the output file both times. With pipe you get a half-written file and no error. With pipeline you get an exception you can catch.

What to hand in Two lines of output from leak.js, and a note of what the output file contained after each version of the three-stage run. The second pair matters more — a half-written file that reported success is the failure mode this whole lesson is about.
Scenario

A worker imports uploaded CSVs. Under load it dies with EMFILE: too many open files. The team raises the file-descriptor limit. It survives two weeks, then dies again.

What this lesson left out on purpose Duplex streams where the two sides are unrelated — a socket, for example — are the general case, and Transform is the one you write. compose, which packs several stages into one reusable stream, is worth knowing once you have used pipelines for a while. Remember this · the 20-second recap
  • A middle stage takes chunks in and puts chunks out, so it is a Writable and a Readable at once. Node calls it a Transform.
  • Backpressure passes through a Transform for free. The signal reaches the whole chain.
  • flush is your last chance to push held-back data. Forget it and the final record vanishes silently.
  • pipe forwards data but not failure. Measured: after a sink error the source is destroyed: false.
  • pipeline destroys every stage. Measured: destroyed: true.
  • Prefer node:stream/promises, so a failed pipeline throws where you can catch it.
  • An async generator is a valid stage, and is often clearer than a Transform subclass.

If you remember one thing: pipe and pipeline behave identically until something fails. That is exactly why no passing test can tell them apart.
