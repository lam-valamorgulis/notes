The costs you can actually control

Micro-optimisation is mostly a waste. So every change this week must be justified by a measurement.

depthWeek 33 of 52. This lesson builds one domain-expert ability: throw away your own good idea because the number said no. Week 33 in the plan · Glossary

Your win today: a cache that made the code slower and leaked 200,000 entries. You will find it with your own benchmark, and delete it.
Why this week is marked depth Not because benchmarking is unimportant, but because the answer is usually “do not bother”. The skill worth having is not making code faster. It is being able to tell, honestly, whether you did.

Start from the problem — most benchmarks lie

Week 31 said no claim without a number. This week adds the harder half: most numbers are not evidence. A benchmark without these four things is a story:

RequirementWhat it prevents
Warm-upMeasuring the first, unoptimised pass of the compiler
RepeatsOne unlucky run deciding your architecture
Variance, reportedBelieving a difference smaller than your noise
Enough iterationsTiming the clock instead of the code

Here is the harness. Warm up, repeat, take the median, and print the spread next to it:

function bench(name, fn, { warmup = 5, runs = 15, iters = 200000 } = {}) {
  for (let w = 0; w < warmup; w++) for (let i = 0; i < iters; i++) fn(i);
  const times = [];
  for (let r = 0; r < runs; r++) {
    const t0 = process.hrtime.bigint();
    for (let i = 0; i < iters; i++) fn(i);
    times.push(Number(process.hrtime.bigint() - t0) / 1e6);
  }
  times.sort((a, b) => a - b);
  const median = times[Math.floor(runs / 2)];
  const spread = (times[runs - 1] - times[0]) / median * 100;   // print this. always.
  return { name, median, spread };
}
The rule that makes it honest If the difference is smaller than the spread, there is no difference. Print both, and let that rule decide — not your hope for the change you just spent an afternoon writing.

Watch the verdict change when you add iterations

The same three candidates, twice: 20,000 iterations then 200,000. Measured on Node v24.14.0:

Candidate20k iterations200k iterations
Manual string concat vs JSON.stringify±101% → within noise±25% → 48.6x faster
Buffer.allocUnsafe vs Buffer.alloc±316% → within noise±31% → 1.74x faster
A Map cache over unique keyswithin noisewithin noise, and slower
Look at those spreads ±316%. The slower run took four times as long as the fastest one. Any single number from that batch is meaningless, and if I had printed only a median I would have published a confident, invented fact.

This is why the spread goes next to every result. It is not decoration — on the first run it was the only thing telling me the measurement had failed.

Three candidates, honestly judged

1 · JSON — a real win, with a condition

JSON.stringify every time     42.34 ms  ±3%    (baseline)
pre-stringified, reused        0.85 ms  ±75%   49.6x faster
manual string concat           0.87 ms  ±25%   48.6x faster

Keep it — but read what it actually says. Reusing a pre-built string is 49x faster than building it. That is obvious once stated: not doing work beats doing work. It only applies where the value does not change, like a health-check body or a cached response.

And note the manual concat is the same speed as the pre-built string, not faster. On the first run it looked like the winner at ±101% spread. It was not.

2 · Parsing — no effect at all

JSON.parse                    35.02 ms  ±2%    (baseline)
JSON.parse + destructure      35.82 ms  ±3%    within noise

Throw it away. A change with no measured effect is not neutral — it costs a review, a diff, and the next reader's attention. Delete it and say why.

3 · Buffers — real, and narrow

Buffer.alloc each time        74.99 ms  ±29%   (baseline)
Buffer.allocUnsafe each time  43.03 ms  ±31%   1.74x faster
reuse one shared buffer       12.48 ms  ±74%   6.01x faster
allocUnsafe is 1.74x faster and hands you old memory It skips zeroing, so the buffer contains whatever was there before — possibly another request's data. Safe only if you overwrite every byte before reading any. Use it for a buffer you are about to fill completely, never for one you might read from first.

And the shared buffer is 6x faster and not safe under concurrency. Two requests using it at once corrupt each other. That is exactly the mistake I made in week 15, where a reused buffer made a benchmark lie.

4 · The cache — the one to delete

A Map in front of a small computation. First with three hot keys, then with realistic traffic:

// 3 hot keys — the demo everyone runs
no cache    3.75 ms  ±11%   (baseline)
Map cache   1.85 ms  ±6%    2.03x faster

// 200,000 unique keys — what production actually looks like
no cache    5.30 ms  ±9%    (baseline)
Map cache   7.07 ms  ±38%   within noise — and the median is SLOWER

cache now holds 200000 entries and will never shrink.
This is the result the week exists for Same code, same cache. With three keys it looked like a 2x win. With realistic key variety it bought nothing measurable, and the median was worse — because every miss now costs a lookup, a computation and an insert.

And it kept 200,000 entries forever. So the honest verdict is: no speed benefit, plus a permanent memory cost that grows with traffic. That is week 34's leak, introduced on purpose by an optimisation.

Why the demo lied Three keys means a 100% hit rate after the first three calls. Your benchmark chose the input, and the input decided the answer. Benchmark with the key distribution you actually have, or you are measuring a system nobody runs.

When a cache is a correctness bug, not a speed win

Week 41 covers this for a shared cache. In-process, the same rule applies with an extra trap:

Cache thisNever cache this
A pure function of its inputAnything that reads the clock
A value that changes only on deployAnything scoped to a user, in a process-wide cache
A bounded set of keysAnything keyed by user input — no ceiling
The worst in-process caching bug A process-wide cache holding per-user data. With cluster from week 24, each worker has its own copy, so the bug appears on some requests and not others. It looks like a race condition and it is a cache key that forgot the user.
Say it in the simplest words — the Feynman check

1 · In plain words A benchmark gives you a number whether or not the number means anything. So you print the spread next to it — how far apart the fastest and slowest runs were.

If the difference between two options is smaller than that spread, there is no difference. That holds however much you want one. That rule is the whole discipline.

2 · One analogy Weighing yourself once and concluding you lost weight. You need several weighings, and you need to know how much the scale wobbles, before a change means anything.

…and where the analogy breaks A scale wobbles by about the same amount every time. A benchmark's wobble depends on what you are measuring, and it can be enormous.

I measured a buffer comparison at ±316%. The slowest run took four times as long as the fastest, so any single number from it was worthless. The spread was the only thing telling me so. Ten times the iterations settled it to ±31%, and only then did a real 1.74x difference appear. The first run had found nothing at all.

3 · The sticking point People benchmark the input that shows the result they hoped for, usually without noticing. My Map cache looked 2.03x faster on three hot keys — a 100% hit rate after the first three calls.

On 200,000 unique keys, which is what production looks like, it bought nothing measurable and the median was slower. Every miss now costs a lookup, the computation and an insert. It also kept 200,000 entries forever. The code never changed; the input decided the answer.

4 · Now you explain it back

In three sentences, explain how a cache can be twice as fast in a benchmark and slower in production. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — three candidates, and a rejection list

Requirements:

  1. Write the harness: warm-up, repeats, median, and the spread printed next to every result.
  2. Benchmark three real candidates on the spine. JSON handling, buffer reuse, and one cache.
  3. Run each at two iteration counts. If a verdict changes between them, the smaller run was not a measurement.
  4. Benchmark the cache with your real key distribution, not three keys.
  5. Keep only what beat its own spread. Delete the rest, including the ones you liked.
  6. Write the rejection list: what you tried, what it measured, and why you kept the old code. That list is the deliverable.
  7. Take the winner and check it end to end with autocannon. A 49x win on a function that is 0.1% of a request is a 0.1% win.
Requirement 7 is the one that keeps you honest Every measurement in this lesson is a micro-benchmark. A function being 49x faster tells you nothing about the request until you know what fraction of the request that function was. Week 50 makes the same point from the other side: 4.8 µs was 25% of an empty handler and 0.03% of a real one.
The drill

“Is JSON.parse your bottleneck?”

Do not answer yes or no. Say how you would find out — and the answer is week 31's CPU profile, not a micro-benchmark. A micro-benchmark tells you how fast a function is. A profile tells you whether anyone is calling it enough to matter.

Say it like an interviewer just asked

What this lesson left out on purpose Hidden classes and inline caches in V8 explain why some of these differences exist, and are fascinating and rarely actionable. Object shape consistency is one micro-optimisation that genuinely holds up. --allow-natives-syntax lets you ask V8 whether a function was optimised or deoptimised. Benchmark.js and mitata do the statistics properly and are worth using over a hand-rolled harness. Memory versus speed trades are usually the interesting ones, and almost never appear in a timing benchmark.

Remember this · the 20-second recap
  • A benchmark needs warm-up, repeats, enough iterations, and the spread printed. Three of four is a story.
  • If the difference is smaller than the spread, there is no difference.
  • Measured ±316% on one comparison — ten times the iterations brought it to ±31%. A verdict that changes with the iteration count means the smaller run measured nothing.
  • Measured: a cache was 2.03x faster on 3 keys and slower on 200,000 — and held every entry forever.
  • Your benchmark chooses the input, and the input chooses the answer. Use your real key distribution.
  • allocUnsafe is 1.74x faster and hands you old memory. A shared buffer is 6x faster and unsafe under concurrency.
  • Keep the rejection list. What you threw away, and why, is the actual output of the week.

If you remember one thing: when a benchmark tells you what you hoped to hear, suspect the benchmark first.
