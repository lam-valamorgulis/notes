The type system you actually need

Not all of TypeScript. The four parts that catch real Node bugs.

coreWeek 44 of 52. This lesson builds one domain-expert ability: make a whole class of bug impossible to write. Week 44 in the plan · Glossary

Your win today: six real Node mistakes, caught before you run anything. And one that TypeScript happily lets through — which is the more useful thing to learn.
Where you are The spine works, is tested, is hardened and has a data layer. Nothing this week changes what it does. It changes how many of your mistakes are possible.

Start from the problem — what is a type checker for?

Not documentation, and not autocomplete. Those are side benefits. The real one:

What you are actually buying

A test that runs on every line, in every branch. That includes branches your tests never reach: the error path, the empty array, the missing environment variable.

That is exactly where your test suite is weakest. Week 35 measured a file with 100% branch coverage and 50% function coverage. A type checker does not care what your tests reached.

So learn the parts that catch Node bugs. That is four things, and it is genuinely most of the value.

1 · unknown, and why any is not a type

Two functions doing the same wrong thing. Measured with TypeScript 7.0.2, strict: true:

function withAny(v: any)         { return v.toUpperCase(); }
function withUnknown(v: unknown) { return v.toUpperCase(); }

a.ts(3,43): error TS18046: 'v' is of type 'unknown'.
// one error. the `any` version produced NOTHING AT ALL.
any is not "a value of unknown type" It is “stop checking”. The checker steps aside, and every value derived from it is also unchecked. One any at a boundary quietly disables type safety for everything downstream of it.

unknown says the same thing honestly. I do not know what this is, so you must check before you use it. Same ignorance, opposite consequence.

You meet unknown whether you ask for it or not. Under strict, a caught error is unknown:

try { JSON.parse('{'); } catch (e) { console.log(e.message); }
a.ts(6,50): error TS18046: 'e' is of type 'unknown'.

That is not pedantry. JavaScript can throw anything — a string, a number, undefined. Your catch was assuming, and now it has to check:

catch (e) { console.log(e instanceof Error ? e.message : String(e)); }   // compiles

2 · Discriminated unions — the shape that makes the check compulsory

Your error taxonomy from week 28 is a union. A call either worked or it did not, and the two carry different data.

type Result =
  | { ok: true;  value: string }
  | { ok: false; error: string };

function bad(r: Result) { return r.value; }
a.ts(15,36): error TS2339: Property 'value' does not exist on type 'Result'.
  Property 'value' does not exist on type '{ ok: false; error: string; }'.

Read the second line. It does not say “you might be wrong”. It names the exact case you forgot. Add the check and the types change underneath you:

function render<T>(r: Result<T>): string {
  if (r.ok) return String(r.value);     // r.value exists — TS knows ok is true here
  return r.error.code;                   // r.error exists — and r.value does not
}

That is narrowing: an ordinary if teaching the compiler something. No casts, no assertions. The tag ok is what makes it work, which is why these are called discriminated unions.

Why this beats value?: string An optional field says both fields might be there, in any combination — including neither, and both. A union says exactly two shapes exist. You then cannot construct the impossible state, which is a stronger guarantee than being reminded to check for it.

3 · never — the compiler tells you what you forgot

The job types from week 42, with one case missing from the switch:

type Job = { kind: 'email' } | { kind: 'pdf' } | { kind: 'webhook' };

switch (j.kind) {
  case 'email': return 'e';
  case 'pdf':   return 'p';
  default: { const never: never = j; return never; }
}
b.ts(31,22): error TS2322: Type '{ kind: "webhook"; }' is not assignable to type 'never'.

The error names the case: webhook. Not “a case is missing” — which one.

This is the trick worth stealing today Six months from now somebody adds { kind: 'sms' } to Job. Every switch in the codebase that forgot to handle it fails to compile, and each error names the file, the line, and the case. Without never, those switches quietly fall through to a default and drop the job.

4 · What it catches in real Node code

Five mistakes anyone can make in an afternoon. All measured:

The codeThe error
req.headers['content-length'].lengthTS2532: Object is possibly 'undefined'
const t: string = await readFile('a.txt')TS2322: Type 'NonSharedBuffer' is not assignable to type 'string'
parseInt(process.env.PORT)TS2345: 'string | undefined' is not assignable to 'string'
const f: Link = links.find(…)TS2322: '{…} | undefined' is not assignable to '{…}'
A switch missing a caseTS2322: Type '{ kind: "webhook" }' is not assignable to type 'never'

Every one of these is a real production incident in miniature. A header that is sometimes absent. A Buffer where a string was expected. A missing environment variable in one environment only. A find that returns nothing on an edge case.

Notice the pattern: almost all of them are undefined. That is the single biggest thing strict mode buys you in Node, and it is why strict is not negotiable. Without it, most of this table disappears.

The hole — and it is exactly where your data comes in

Now the measurement that matters more than all of the above. This file compiles with zero errors:

const body = JSON.parse('{"url": 123}');       // JSON.parse returns any
const url: string = body.url;                   // no error
const len: number = url.toUpperCase().length;   // no error
console.log(url.trim());

tsc: 0 errors
at run time: TypeError: b.url.trim is not a function
Zero errors, and it crashes JSON.parse returns any, so the checker steps aside — and it stays aside for url, and for len, and for everything after. The : string annotation is a claim you made, and TypeScript believed you.

This is not a flaw to work around. It is the boundary of what a type checker can do. Types are erased before the program runs, so they cannot check data that arrives while it is running.

So the rule from week 37 comes back with a second reason. Validate at the boundary — every request body, every environment variable, every third-party response. Then the types are true because something checked, not because you asserted.

function toCreateLink(body: unknown): CreateLink {   // unknown, never any
  if (typeof body !== 'object' || body === null) throw new ValidationError('body');
  const { url, code } = body as Record<string, unknown>;
  if (typeof url !== 'string' || !isSafeTarget(url)) throw new ValidationError('url');
  if (code !== undefined && typeof code !== 'string') throw new ValidationError('code');
  return { url, code };                              // now the type is earned
}
Where the type system stops and you start Inside your service the checker is doing real work. At the edge it can do nothing at all. So one validating function per entry point, returning a typed value — and everything past it can be trusted. Libraries like Zod do this for you; the principle is what matters.

Generics — one that is worth it

Generics are where people over-reach. The test is simple: a generic is worth it when the output type depends on the input type. Otherwise it is decoration.

async function withRetry<T>(fn: () => Promise<T>, attempts = 3): Promise<T> {
  let last: unknown;
  for (let i = 0; i < attempts; i++) {
    try { return await fn(); } catch (e) { last = e; }
  }
  throw last;
}

Retry a function returning Link and you get a Link back. Retry one returning number and you get a number. Without the generic the return type is any, and you have just disabled checking at every call site.

The generic that is not doing anything function log<T>(x: T): void gains you nothing — nothing depends on T. If you cannot say which output type a type parameter determines, delete it and use unknown.
Say it in the simplest words — the Feynman check

1 · In plain words A type checker is a test that runs on every line and every branch. That includes branches your tests never reach. The error path, the empty array, the missing environment variable.

It runs before the program does. So it catches a whole class of mistake for free. And it catches them in code nobody thought to test.

2 · One analogy A form that will not submit until every required box is filled. It cannot tell you the address is real. It can guarantee you did not leave it blank.

…and where the analogy breaks A form checks what someone typed. TypeScript checks what you wrote, then it is erased before the program runs. So it can never look at data arriving while the program runs.

I measured this: JSON.parse('{"url":123}'), then const url: string = body.url, compiled with zero errors and crashed with TypeError: b.url.trim is not a function. JSON.parse returns any, the checker stepped aside, and my : string was a claim it simply believed.

3 · The sticking point People read any as “a value whose type I do not know”. It means “stop checking”, and everything derived from it is unchecked too. One any at a boundary turns off type safety for everything downstream.

unknown expresses the same ignorance with the opposite result: you must check before you use it. Measured, the difference is stark — the unknown version produced TS18046, and the any version produced no error at all.

Build it for real — type the hard parts first

Requirements:

  1. strict: true. Everything in this lesson depends on it. Nothing else is negotiable either.
  2. Type the spine's trickiest function — the one with an ambiguous return. Not the easy ones.
  3. Type the week 28 error taxonomy as a discriminated union, and narrow it with a plain if.
  4. Put a never check in the default of every switch over a union. Then add a case to the union and watch what fails.
  5. One validating function per entry point: unknown in, a typed value out. No any at any boundary.
  6. Write one generic that is genuinely worth it, and say which output type its parameter determines.
  7. Grep for any. For each one, delete it or write a one-line comment defending it.
The drill

“Type a function that returns a user or a not-found error. No any, no throw.”

The constraint is the whole question. No throw means the failure must be in the return type, so the caller cannot ignore it. Write it, then write the caller and show that reaching the user without checking does not compile.

Remember this · the 20-second recap
  • A type checker is a test on every line and branch, including the ones your suite never reaches.
  • any means stop checking, and it spreads. Measured: the unknown version errored, the any version gave no error at all.
