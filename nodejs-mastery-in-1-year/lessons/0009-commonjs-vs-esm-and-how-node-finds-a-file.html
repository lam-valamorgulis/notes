CommonJS vs ESM, and how Node finds a file

Two module systems, one real difference — and it is not the syntax.

coreWeek 9 of 52. This lesson builds one domain-expert ability: say why it was built this way, and what that choice gives up. Week 9 in the plan · Glossary

Your win today: you will stop guessing at module errors. Given ERR_REQUIRE_ESM, ERR_MODULE_NOT_FOUND or ERR_PACKAGE_PATH_NOT_EXPORTED, you will read the message and know what happened — because you will know exactly when Node goes looking for a file, and where it looks.
Where you are Weeks 1–8 were about time: when your code runs. Weeks 9–12 are about place: where your code lives and how Node finds it. Same skill, different axis. Both are things you can trace instead of guess.

Start from the problem, not the syntax

One file gets too big. You want to split it. That is the whole problem.

To split code across files, a language needs to answer four questions. Nothing else. Read them and notice that three are easy:

  1. How do I name another file? Some kind of string.
  2. How does that file say what is public? Some kind of export.
  3. How does a name become a real file on disk? A set of lookup rules.
  4. When does that lookup happen? While the program runs, or before it runs?
The one choice that makes everything else

CommonJS looks up files while the program is running. ESM looks up every static import before any of your code runs. Almost everything you have to memorise follows from that one difference. There are exactly two exceptions: two lookup rules ESM changed on purpose. Both are labelled as conventions when they arrive, not smuggled in as logic.

That claim is worth testing rather than believing. Take the two systems in turn and see whether the differences really do fall out of the timing.

CommonJS — look it up while running

In CommonJS, require() is an ordinary function. Node wraps every file in a function before running it, roughly like this:

// What Node actually does to your .cjs file, simplified.
function (exports, require, module, __filename, __dirname) {
  // ...your file's code goes here...
}

That wrapper explains a lot at once. require, module and __dirname are not magic globals. They are arguments. That is why __dirname and __filename do not exist in the REPL, where there is no file. (require and module are there. The REPL sets them up for you.)

It also explains var. A top-level var in a Node file is not on globalThis. It is a local variable inside that function.

Now derive the rest. require() is a function call, so:

  • It can sit anywhere — inside an if, inside a loop, inside a function.
  • Its argument can be computed: require('./plugins/' + name).
  • It must be synchronous, because a function call has to return a value now. So it reads the file from disk and blocks while it does. On a server, that is fine only because it happens at start-up.
  • It returns whatever module.exports was at that moment — a snapshot.

That last point is the one that catches people out, so prove it rather than accept it:

counter.cjs

let n = 1;
setTimeout(() => { n = 99; }, 10);
module.exports = { n, get live() { return n; } };

use.cjs

const m = require('./counter.cjs');
setTimeout(() => console.log(m.n, m.live), 50);
// prints: 1 99

The value 1 was copied into the object when the file ran. Changing n later does nothing to it. The getter still sees the new value, because a getter runs when you read it. So CommonJS hands you an object, and normal JavaScript copying rules apply. There is no special "module" behaviour at all.

ESM — look everything up first, then run

ESM makes the opposite choice, and pays for it with restrictions you have probably felt without knowing why.

Node reads an ES module in three separate passes:

  1. Parse. Find every import in the file without running anything. Load those files. Repeat until the whole graph is known.
  2. Link. Connect each imported name to the exact slot in the file that exports it. No values yet — just wiring.
  3. Evaluate. Now run the code, deepest file first.

Pass 1 has to find the imports without running the file. That requirement forces the first two rules below on its own. The last two come from a separate design choice. ESM was built to work in a browser, over URLs. The table says so rather than pretending otherwise:

ESM ruleWhy it must be that way
import must be at the top levelAn import inside an if could not be found without running the if.
The path must be a literal string'./' + name has no value until the code runs. Pass 1 has not run anything.
File extensions are requiredConvention, not a consequence. Nothing about parsing first stops Node guessing — CommonJS is resolved statically too, and it guesses happily. ESM refuses because it is specified over URLs, to match the browser, where every guess is a network round trip. Remember this one.
No __dirnameConvention, not a consequence. Same reason: an ES module is named by a URL, and a URL need not be a file. Use import.meta.dirname.
…unless you use import()Dynamic import() is a function call, not a declaration. It runs during evaluation, like require(), so its path may be computed and it may sit anywhere. It returns a promise instead of a value.
The one escape hatch — and it proves the rule import('./x.mjs'), with brackets, like a function call, is a run-time load. So it may sit inside an if, and its path may be computed. It returns a promise, because loading is asynchronous. That is the whole trade: run-time freedom costs you the static graph and the live binding. Use it for a plugin you choose at start-up, and for nothing else.

Pass 2 is where the famous difference appears. Linking connects a name to a slot, not to a value. So when the other file changes what is in the slot, you see it:

counter.mjs and use.mjs

// counter.mjs
export let n = 1;
setTimeout(() => { n = 99; }, 10);

// use.mjs
import { n } from './counter.mjs';
setTimeout(() => console.log(n), 50);
// prints: 99

Same shape as the CommonJS example. Different answer. This is called a live binding. Nobody added it as an extra feature. You get it as soon as you decide to link before running.

A live binding is read-only for you You can see n change. You cannot write to it. n = 5 in the importing file is a TypeError. Only the file that owns the variable may change it.

How a name becomes a file

Three kinds of name, three different rules:

You writeCalledNode does
'./util.js'relativeJoins it to the current file's folder. One place, no searching.
'/opt/app/x.js'absoluteUses it exactly. No searching.
'lodash'bare specifierSearches. This is the one worth understanding.
'node:fs'builtinAnswered from inside Node. No disk is touched at all.
Why node:fs and not just fs They load the same object — require('node:fs') === require('fs') is true. But the prefix is not decoration. Newer built-in modules only exist with it. Verified on Node v24.14.0: 
require('test')        // MODULE_NOT_FOUND
require('node:test')   // works
The same is true of node:sqlite and node:sea. You will need node:test in week 35, so learn the prefix now. Use it in new code; expect the bare form in anything written before Node 16.

For a bare specifier, Node looks in node_modules in the current folder. Not there? It goes up one folder and looks again. It keeps going up to /node_modules — and then checks three legacy global folders: ~/.node_modules, ~/.node_libraries, and <node install>/lib/node. So the last folder in the list lives inside your Node installation, not at the root of the disk.

You do not have to believe that. Node will show you the list:

NODE_DEBUG=module node -e "require('lodash')"

The output prints the exact folders it checked, in order — up to /node_modules, then the three legacy global folders. Run it once inside a real project. It turns "module not found" into a list you can read instead of a mystery.

This is why a deep project can find a package it never installed A package in a parent folder's node_modules is visible to every folder below it. That is convenient, and it is also how a build works on your machine and fails in CI — where the parent folder does not exist.

The exports field blocks any path it does not list

Once Node has found the package folder, package.json decides what you may reach. The exports field lists the allowed entry points. Anything not listed is blocked, even though the file is right there on disk:

// node_modules/toy/package.json
{ "name": "toy", "exports": { ".": "./lib/main.js" } }
require('toy')             // works
require('toy/lib/secret')  // ERR_PACKAGE_PATH_NOT_EXPORTED

This applies to require as well as import. Before exports existed, every file in a package was public. The author had no say in it. So no file could ever be renamed safely. The field is the package author drawing a line around what they promise to keep.

Which system is this file? One line decides

FileTreated as
.mjsAlways ESM. No exceptions.
.cjsAlways CommonJS. No exceptions.
.jsDepends on the nearest package.json: ESM if it has "type": "module", otherwise CommonJS.
The rule that surprises everyone "type": "module" is not a switch for your project. It is a switch for every .js file under that package.json. Add it to an existing project and files you never touched change meaning. That is why the safe move in a mixed codebase is to rename the file to .mjs or .cjs, where the extension answers the question and nothing can override it.

Can require() load an ES module?

Yes — in modern Node, and this is a change worth knowing, because most tutorials still say no.

Verified on Node v24.14.0:

require('./m.mjs')     // works — returns the module
require('./tla.mjs')   // ERR_REQUIRE_ASYNC_MODULE

The rule is about timing again, exactly as you would now predict. require() must return a value immediately. Node can do that for an ES module as long as the whole graph is synchronous. Then one file in that graph uses top-level await. The module cannot finish synchronously. require() gives up with ERR_REQUIRE_ASYNC_MODULE.

Say the version out loud This changed. Older Node threw ERR_REQUIRE_ESM for any ES module. Synchronous require() of ESM arrived in Node 22.0 and was backported to 20.17, both behind --experimental-require-module. It is on by default from 20.19, 22.12 and 23.0. If Break 2 gives you ERR_REQUIRE_ESM, your Node is older than 20.19. If you are reading an answer online that says it is impossible, check the date before you believe it. Always check which Node version an answer was written for. You will still meet ERR_REQUIRE_ESM in two places: Node 18 and older, and bundlers that resolve modules themselves. When you see it, the first question is always which Node produced this?
Say it in the simplest words — the Feynman check

1 · In plain words A module system answers one question. You write the name of another file. When does the computer go and get it? CommonJS goes and gets each file at the moment it reaches that line. ESM reads your whole program first, collects every file it will need, fetches them all, and only then starts running.

Everything else people tell you to memorise comes from that one choice.

2 · One analogy Two ways to cook from a recipe. CommonJS is reading the recipe one line at a time and walking to the shop whenever an ingredient is named. ESM is reading the whole recipe first. You write one shopping list and go to the shop once. Only then do you start to cook.

…and where the analogy breaks The shopping picture makes ESM sound merely faster. Speed is the least interesting part. The real prize is what you come home with.

ESM knew the whole list in advance. So it can hand you a shelf instead of a bag. When the other file puts something new on that shelf, you see it. CommonJS handed you a bag holding whatever existed at the moment you asked. That is the live binding, and it is a difference in meaning, not in speed.

…and a second thing the picture hides The shopping trip sounds instant. It is not — ESM loading is asynchronous. So an ES module may not be finished at the moment somebody asks for it right now. That is exactly why require() of a top-level-await module fails. require has to return a value immediately. The shop is not next door.

3 · The sticking point People believe the difference is syntax — require or import, pick the one your project uses. It is not syntax. It is timing. Once you hold that, three confusing rules become obvious at the same moment.

  • You cannot put import inside an if. Nothing has run yet, so nothing could find it.
  • require() of a top-level-await module still fails. It cannot finish in time.
  • One line in package.json changes the meaning of files you never opened.

4 · Now you explain it back

In two or three sentences, say when CommonJS goes looking for a file. Say when ESM does. Then name one rule that follows from that difference. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — break it four ways, on purpose

Reading error messages is the actual skill this week. So produce them yourself, in a scratch folder, and write down what each one means. Six minutes each.

Set-up

mkdir -p mod-lab && cd mod-lab
npm init -y
printf 'export const hello = () => "hi";\n' > lib.mjs
printf 'export const slow = await Promise.resolve(1);\n' > tla.mjs

Break 1 — a bare specifier that does not exist

node -e "require('not-a-real-package')"
// then run it again and read the folder list:
NODE_DEBUG=module node -e "require('not-a-real-package')"

Write down: how many folders did it check, and what was the last one?

Break 2 — require a module that cannot finish in time

node -e "require('./tla.mjs')"
// ERR_REQUIRE_ASYNC_MODULE

Now delete the await from tla.mjs and run it again. It works. You have just shown that the error is about timing, not about ESM.

Break 3 — a missing file extension in ESM

printf 'import { hello } from "./lib";\n' > main.mjs
node main.mjs
// ERR_MODULE_NOT_FOUND — the message names the exact path it looked for

Then add .mjs to the import and watch it work. CommonJS would have guessed for you. ESM will not.

Break 4 — the exports door

mkdir -p node_modules/toy/lib
printf '{"name":"toy","exports":{".":"./lib/main.js"}}\n' > node_modules/toy/package.json
printf 'module.exports = "main";\n'   > node_modules/toy/lib/main.js
printf 'module.exports = "secret";\n' > node_modules/toy/lib/secret.js
node -e "console.log(require('toy'))"
node -e "console.log(require('toy/lib/secret'))"
// ERR_PACKAGE_PATH_NOT_EXPORTED — the file exists and is still refused
What to hand in A file called module-errors.md with four headings — one per error code. Under each, one sentence saying what happened and one saying how you fixed it. That file is worth more in six months than re-reading this lesson.

Remember this · the 20-second recap
  • A module system answers four questions. CommonJS and ESM differ on only one: when the lookup happens.
  • CommonJS looks up while running. So the path can be computed, require can sit anywhere, it blocks, and it gives you a copy.
  • ESM looks up before running, in three passes: parse, link, evaluate. So imports must be top level and literal, extensions are required, and you get a live binding.
  • A bare specifier like lodash searches node_modules upward to the root. See it with NODE_DEBUG=module.
  • The exports field blocks any path it does not list — ERR_PACKAGE_PATH_NOT_EXPORTED — for require too.
  • .mjs and .cjs always win. A plain .js is decided by "type" in the nearest package.json, which affects files you never opened.
  • Modern Node can require() an ES module, unless the graph uses top-level await.

If you remember one thing: the difference is not require versus import. It is whether Node looks for the file while running or before running. Every rule follows from that.
