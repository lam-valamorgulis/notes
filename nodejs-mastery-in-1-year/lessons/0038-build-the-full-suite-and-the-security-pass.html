The spine becomes something you would let a stranger deploy without watching them.

coreWeek 38 of 52. This lesson builds one domain-expert ability: defend your own work under questioning, and judge someone else's. Week 38 in the plan · Glossary

Your win today: two documents nobody assigned you, and a green build from a clean checkout. The documents are the part that changes how people treat you.
Where you are Weeks 35 to 37 gave you tests, reliable tests, and attacks. This week joins them into something a stranger can run, and adds the skill none of the previous weeks taught: writing down what you checked and what you chose not to.

Start from the problem — what does “ready” mean?

“It works” is not a claim anybody can check. Ready means something narrower and much harder:

The three questions behind “ready”

1. Can somebody who has never seen this get it green, first try?
2. Can you say what the tests prove, and what they do not?
3. Can you name the risks you accepted on purpose, and why?

Question 3 is the one that separates a professional from a careful person. A careful person fixes what they find. A professional writes down what they decided not to fix. The next person then inherits a decision, not a surprise.

Part 1 — green from a clean checkout

Your suite passing on your machine proves your machine works. The only test that counts is a fresh clone, on a machine that has none of your history.

cd $(mktemp -d)
git clone <your repo> spine && cd spine
npm ci                      # ci, not install — obeys the lockfile exactly
node --test
The five reasons this fails the first time A file you never committed — check git status in the clone, not in your working folder. A dependency you installed globally months ago. A .env file that is correctly ignored and quietly required. A path that only exists on your machine. A different Node version, which is why engines and a version file belong in the repo.

The runner already speaks the language continuous integration needs. Verified on Node v24.14.0:

NeedFlagVerified behaviour
Fail the build—A failing run exits 1; a passing run exits 0
Machine-readable output--test-reporter=junitPrints <testsuites> XML most CI tools display natively
Quiet log--test-reporter=dotPrints .... — one character per test
A coverage floor--test-coverage-lines=NExits 1 when coverage is below N
Reproduce a flake--test-concurrency=1Serial: two 400 ms files took 916 ms, not 464 ms

The coverage floor is worth setting up properly. It turns a number people argue about into a rule the machine enforces:

node --test --experimental-test-coverage --test-coverage-lines=90

ℹ  lib.js   |  66.67 |   100.00 |   50.00 | 2
ℹ all files |  66.67 |   100.00 |   50.00 |
# exit code 1 — the build fails. Without the flag, the same run exits 0.
Set the floor at what you have today Not at 90 because 90 sounds good. Measure, then set the floor one point below the current number. Now coverage can never fall, and nobody has to write pointless tests this afternoon. Raise it when you genuinely raise coverage.

Read that measured row once more, because it is week 35's lesson in one line. Branch coverage 100%, function coverage 50%. The file has no branches, so branch coverage is perfect and meaningless, while half the functions have never been called. One number is never the answer. The uncovered lines column — here, line 2 — is.

Part 2 — the security pass

This is a document, and it is the real deliverable of the week. Most engineers never write one, which is exactly why writing one is noticed.

It has three columns, and the third is the important one:

RiskStatusReasoning
Dangerous URL scheme (javascript:, data:)ClosedProtocol allow-list, http:/https: only. Test: rejects-javascript-scheme.
Prototype pollution via request bodyClosedMerge target is Object.create(null). Test asserts ({}).isAdmin stays undefined.
Regex denial of serviceClosedCodes limited to 32 characters before matching; pattern has no nested repeat.
Unbounded request bodyClosedBytes counted as received; socket destroyed past 1 MB. content-length not trusted.
Redirect to a private address (169.254.169.254)AcceptedWe send a 302; the browser fetches, not us. Revisit the moment we add link previews.
No rate limitingAcceptedBehind a gateway that limits per IP. If that ever changes, this becomes the top item.
No authentication on POST /linksAcceptedInternal service, private network. Not safe to expose publicly without auth.
What makes an “Accepted” row good Every one names the condition that would change the answer. “Behind a gateway” is a fact that can stop being true. Writing the trigger means the decision expires by itself instead of quietly rotting into a hole nobody remembers choosing.

Notice what the table is not. It is not a promise the service is secure. It is a record of what a specific person checked on a specific day, with the reasoning attached. That is a far more useful thing to hand someone, and a far more honest one.

Part 3 — judge a repository you did not write

This is the week's hardest exercise, and the closest thing to the job. Pick a real open-source Node service. Give yourself 30 minutes and write three specific findings.

You are not looking for style. You are answering one question: what breaks first, and who notices?

Look atAskFrom
The shutdown pathIs there a SIGTERM handler? Does it drain, or just stop?week 27
The error handlerDoes an unexpected error keep the process alive? Should it?week 28
Any await in a loopIs this serial on purpose, or by accident?week 7
The body parserIs there a size limit? Is content-length trusted?week 20
Any merge of request dataCan __proto__ get through?week 37
The testsIs there a sleep? A hard-coded port? An async test with no await?week 36

A finding is only useful in a particular shape. Compare:

// useless
"Error handling could be improved."

// a finding
"src/server.js:88 — the catch block logs and returns 500 for every error,
 including a validation failure. A client cannot tell a bad request from
 an outage, so retries hammer a server that will never accept the input.
 Split operational from programmer errors and map validation to 400."
The shape of a finding

Where (file and line) · what (the specific behaviour) · what it costs (who is hurt, and when) · what to do. Missing the third part is what makes a review sound like nagging.

Say it in the simplest words — the Feynman check

1 · In plain words A risk you have written down and decided not to fix is safe, in the way that matters. The next person inherits your decision instead of your blind spot.

So the job of a security pass is not to fix everything. It is to shorten the list of things nobody has looked at. Then to say why each remaining item is acceptable.

2 · One analogy A pre-flight checklist. The pilot is not repairing the aircraft. They are confirming that every item has been looked at by somebody, and signing their name to that.

…and where the analogy breaks A pre-flight checklist is fixed. Somebody else wrote it, and it is the same every flight. Your list has to be written by you, for this service, and it goes out of date.

That is why every “Accepted” row must name the condition that would change the answer. “We only redirect, we never fetch the URL” is fine today and wrong the day someone adds link previews. Without that trigger written down, an old decision quietly turns into a hole nobody remembers choosing.

3 · The sticking point People read “Accepted” as “we were lazy”, so they leave the row out. That is backwards. A risk in the table is being managed; the same risk left out is invisible.

Only one of the three states is actually bad, and it is Unknown — nobody looked, so nobody knows. Everything you move out of that column is real work, even when you fixed nothing.

4 · Now you explain it back

In two or three sentences, explain this. Writing down a risk you chose not to fix is safer than fixing it quietly. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — the whole week's deliverable

Requirements:

  1. Clean checkout, green first try. Clone into a temporary folder, npm ci, node --test. If it fails, that is the most valuable thing you will find this week. Fix the repo, not your machine.
  2. Continuous integration running the suite plus npm audit --audit-level=high.
  3. A coverage floor set one point below today's number, enforced with --test-coverage-lines. Confirm it fails when you lower a test.
  4. A coverage number you can defend. Write one paragraph: what the suite proves, and what it does not.
  5. SECURITY.md — the three-column table. Every Accepted row names its trigger.
  6. Ten clean runs of the suite in a row. Any failure is a flake to fix, not a retry to add.
  7. Three findings on somebody else's Node repository, each in the four-part shape.
The trap in requirement 4 “We have 88% coverage” is not defending a number, it is repeating one. Defending it sounds like: “88%. The redirect path, the 409 and the size limit are covered by integration tests. The uncovered lines are the fatal-error branch, which I could only test by killing the process, and the metrics endpoint. I judged both low risk, and here is why.”

One of those answers ends the conversation. The other starts a good one.

Judge a stranger's project out loud

Open a Node service you have never seen. Talk for five minutes, out loud, recorded.

Say what will break first, who notices, and what you would fix in the first week. Then listen back. Count how many times you said something that was true of any project. Those sentences are the ones an interviewer discounts entirely.

Remember this · the 20-second recap
  • Ready means three things. Green from a clean checkout, you can say what the tests prove, and you can name what you accepted.
  • A failing node --test exits 1 — the whole CI contract. --test-coverage-lines=N exits 1 below N too.
  • Measured: 66.67 line / 100.00 branch / 50.00 funcs — perfect branch coverage, half the functions never called.
  • Three states for a risk: Closed, Accepted, Unknown. Only Unknown is bad.
  • Every Accepted row names the condition that would change the answer, so it expires by itself.
  • A finding is where · what · what it costs · what to do. Drop the cost and it reads as nagging.
  • Defending a coverage number means naming the uncovered lines and why they are acceptable.

If you remember one thing: the security pass does not move risks to Closed — it moves them out of Unknown.
