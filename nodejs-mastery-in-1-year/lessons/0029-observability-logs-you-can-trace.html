Observability — logs you can trace

A log line you cannot tie to a request is nearly worthless during an incident.

depthWeek 29 of 52. This lesson builds one domain-expert ability: find one user's story inside forty requests a second. Week 29 in the plan · Glossary

Your win today: a request id on every log line, that nobody passes anywhere. And the case where it silently attaches the wrong id — which is worse than none.
Why this week is marked depth You can ship without it. You cannot debug without it. It is depth because nothing breaks until the first real incident, and then it is the difference between ten minutes and a whole afternoon.

Start from the problem — the incident

One user reports an error. No stack trace, no screenshot, no time. The service is handling 40 requests a second. Your logs look like this:

Error: could not resolve link
Error: could not resolve link
Error: could not resolve link
What is actually missing

Not detail. Identity. You cannot tell which lines belong to the same request. So you cannot reconstruct one user's story, and that story is the only thing that helps.

So the job is to put an id on every line. The obvious way to do that is to pass it as an argument. That falls apart immediately, because it must reach every function you call, including third-party ones.

AsyncLocalStorage — a variable that follows the request

It gives you a value that stays with a chain of async work, without being passed. Measured on Node v24.14.0:

await Promise.all([
  als.run({ requestId: 'req-A' }, () => deep(5)),     // 5 awaits + setTimeout
  als.run({ requestId: 'req-B' }, () => …),           // nextTick + setImmediate
]);

  through nextTick+setImmediate: req-B
  after 5 awaits + setTimeout : req-A

Two requests running at the same time, each keeping its own value through every kind of async hop. Nothing was passed as an argument.

Combine it with a structured logger and the id appears on its own:

als.run({ requestId: 'r-91', userId: 4 }, () => {
  log.info({ route: 'POST /links' }, 'request start');
  log.warn({ ms: 812 }, 'slow query');
});
log.info('outside any request');

{"level":30,…,"requestId":"r-91","userId":4,"route":"POST /links","msg":"request start"}
{"level":40,…,"requestId":"r-91","userId":4,"ms":812,"msg":"slow query"}
{"level":30,…,"msg":"outside any request"}

Both request lines carry r-91. The third does not, because it is not in a request. Neither call site mentioned an id.

The case where it attaches the wrong id

The context is captured when an async resource is created. Registering an event listener does not create one. So:

als.run({ requestId: 'req-C' }, () => {
  ee.on('plain', () => log(als.getStore()?.requestId));
  ee.on('bound', AsyncResource.bind(() => log(als.getStore()?.requestId)));
});

// emitted from outside any context
  plain listener      : undefined
  AsyncResource.bind  : req-C

// emitted from inside a DIFFERENT request
als.run({ requestId: 'req-D' }, () => { ee.emit('plain'); ee.emit('bound'); });
  plain listener      : req-D        <- the WRONG request
  AsyncResource.bind  : req-C        <- correct
Read the second block again A listener registered during request C, fired during request D, logged req-D. Not missing — wrong. Request C's work is now filed under request D's story.

A trace that lies is worse than a trace that is absent, because you will believe it. During an incident you will follow req-D's timeline and find an event that never belonged to it. Then you will conclude something false about the code.

And here is why it hides. When the listener is registered and emitted inside the same request, which is the normal case, it works perfectly. Measured: req-E, correct. The bug only appears for listeners that outlive the request that registered them.

The rule A callback stored somewhere and called later — an emitter listener, a cache entry, a queue handler, anything on a long-lived object — must be wrapped in AsyncResource.bind. A callback used immediately does not need it.

What it costs

200,000 async calls, three ways. Measured:

SetupTotalPer call
No AsyncLocalStorage at all20 ms0.10 µs
A new als.run around every call68 ms0.34 µs
All 200,000 calls inside one als.run17 ms0.09 µs
The third row is the one that matters Being inside a context costs nothing measurable. Only entering one costs, and that is 0.24 µs. You enter once per request, so the bill is a quarter of a microsecond per request — against week 40's 15 ms query, that is 0.0016%.

This matters because AsyncLocalStorage has an old reputation for being slow, from when it was built on async_hooks. Measure it before you believe that.

Why JSON logs, and how to keep pretty ones too

A pretty log is for a human reading one line. A JSON log is for a machine searching a million. In production you need the second, and it costs you nothing to have both:

node server.js | pino-pretty        # development: readable
node server.js                       # production: JSON, straight to the log system

The formatting is a separate process, so your service always emits JSON and never pays for prettiness. That also means you can pipe production JSON through pino-pretty locally when you are reading an incident.

diagnostics_channel — publish without knowing who listens

It solves one problem. You want to observe something. The code that does it must not depend on your logger, your metrics library, or anything else.

// in the data layer — knows nothing about logging
const ch = dc.channel('spine:query');
ch.publish({ sql, ms });

// somewhere else entirely — knows nothing about the data layer
dc.subscribe('spine:query', (msg) => log.info({ ...msg }, 'query'));

{"level":30,…,"requestId":"r-92","sql":"select url from links where code=$1","ms":14,"msg":"query observed by a subscriber"}
Look at that output again The publisher sent sql and ms. The line came out with requestId: r-92 on it, because the subscriber ran inside the request's context. The data layer never knew a request id existed, and the logger never knew the data layer existed.

And it is genuinely free when nobody is listening. One million publishes, measured:

guarded by hasSubscribers : 1 ms
unguarded                 : 2 ms

Two nanoseconds per publish with no subscriber. So you can leave the publish calls in production permanently and attach a subscriber only during an incident.

Say it in the simplest words — the Feynman check

1 · In plain words During an incident you do not need more detail. You need to know which log lines belong to the same request. Then you can read one user's story instead of forty mixed together.

AsyncLocalStorage gives you a value that stays with a chain of async work without being passed as an argument. Put the request id in it once, and every log line inside that request carries it.

2 · One analogy A wristband at a hospital. Nobody hands the patient's number to each department. It travels on the patient, and every note written anywhere gets the same number.

…and where the analogy breaks A wristband is on the patient, so it cannot end up on someone else. This can. The context is captured when an async resource is created, and registering an event listener does not create one.

I measured what happens then. A listener registered during request C and fired during request D logged req-D — not missing, wrong. Request C's work filed under D's story. And when the listener is registered and fired inside the same request, which is the normal case, it works perfectly. That is why the bug survives.

3 · The sticking point People avoid AsyncLocalStorage because they heard it is slow. Measure it. Being inside a context cost nothing — 200,000 calls took 17 ms with it and 20 ms without.

Only entering costs, at 0.24 µs, and you enter once per request. Against a 15 ms database query that is 0.0016% of the request. The reputation comes from the old async_hooks implementation, and it is worth checking a number before inheriting an opinion.

4 · Now you explain it back

In three sentences, explain how a request id reaches a log line in a function nobody passed it to. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — trace one request end to end

Requirements:

  1. Structured JSON logging with pino. pino-pretty in development only, as a separate process.
  2. A request id generated at the edge — or taken from an incoming x-request-id — and stored in AsyncLocalStorage once per request.
  3. The logger reads the id from the store. No function signature anywhere gains a requestId parameter.
  4. Trace one request end to end by its id alone: arrival, validation, cache, query, queue, response.
  5. Reproduce the wrong-id bug. Register a listener in one request, fire it in another, and watch the wrong id appear. Then fix it with AsyncResource.bind.
  6. One diagnostics_channel publisher in the data layer and a subscriber that logs it. The publisher must not import the logger.
  7. Measure your own als.run overhead and write the number down.
Requirement 5 is the whole week Everything else here works the first time. The wrong-id case is the one you will actually hit in production, in a queue handler or a cache callback, and it is the one that makes your traces lie. Build it on purpose now, while it is a five-line file.
The drill

“One user reports an error. No stack trace. Forty requests a second.”

Say exactly what you would query, in order, and what each step narrows down. Then answer the harder follow-up: what if the error happened in a background job, started by that request but running after the response was sent? That is where the request id has to be carried into the job payload, because the async context does not survive a queue.

Say it like an interviewer just asked

What this lesson left out on purpose OpenTelemetry is the standard for tracing across services, and it uses these same mechanisms underneath. Metrics and Prometheus answer a different question from logs — how often, not what happened. Log sampling matters once volume costs real money. Redacting secrets from structured logs is a security requirement, not a nicety. Correlation across services needs the id in a header, not just in memory.

Remember this · the 20-second recap
  • Incidents need identity, not detail. A line you cannot tie to a request is nearly worthless.
  • AsyncLocalStorage carries a value through await, setTimeout, nextTick and setImmediate, with nothing passed.
  • Measured: inside a context costs nothing (17 ms vs 20 ms). Entering one costs 0.24 µs, once per request.
  • A listener registered in request C and fired in request D logged req-D — wrong, not missing.
  • Wrap any callback that outlives its request in AsyncResource.bind. Registered and fired together works, which is why the bug hides.
  • Emit JSON always; pino-pretty is a separate process. diagnostics_channel lets the data layer publish without importing your logger, and the subscriber still picks up the request id.
  • Measured: 1M publishes with no subscriber took 2 ms. Leave them in permanently.

If you remember one thing: a wrong trace is worse than no trace, because you will believe it.
