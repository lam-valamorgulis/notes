Start from the problem — what makes a tool different from a script?

A script runs on your machine, on your files, while you watch. A tool runs on a stranger's machine, on files you have never seen, while nobody watches.

Everything that separates the two is about what happens when things go wrong. So build the tool by asking, for each part: what is the worst thing this could do to someone?

The rule for this week

A tool that does its job well and destroys data once is worse than useless, because people trusted it first.

The bug hiding in the obvious solution

A bulk renamer renames files. The obvious call is fs.rename. Try it:

const fs = require('node:fs');
// a.txt contains "A". b.txt contains "B". Both exist.
fs.renameSync('a.txt', 'b.txt');

What actually happened (Node v24.14.0):

a.txt gone | b.txt now contains: A

The original b.txt is gone. Not moved, not backed up — overwritten. No error, no warning, no exit code. The file that said "B" no longer exists anywhere.

This is not an accident. rename(2) is defined to replace the destination atomically. That is what you want when you write a temp file and swap it into place. It is exactly what you do not want when a batch rename happens to produce a name that already exists.

Why this reaches real users and not you You test on four files with obvious names. Nothing collides, so nothing is lost, and the tool looks finished. A stranger unzips nine hundred photos from a Linux server onto a Mac. The archive holds both IMG_0042.jpg and img_0042.JPG; on the Mac those are one name, so one photo is already lost at unzip time. Then your tool renames IMG_0043.jpg to photo_0043.jpg — a name that already exists — and rename destroys that one too. Your tool reported success.

The fix — ask the filesystem, do not ask yourself

The tempting fix is to check first:

// WRONG — looks careful, is not
if (!fs.existsSync(dest)) fs.renameSync(src, dest);

Between the check and the rename, anything can create dest. That gap is a race condition, and it is the same shape of bug as every other check-then-act. On your laptop it never fires. On a machine where a sync client is also writing, it does.

The correct move is to make the filesystem refuse, in one operation. fs.link fails with EEXIST if the target exists — verified:

link(x, y) -> EEXIST   // the target already existed, so it refused
// RIGHT — one atomic operation that cannot overwrite
try {
  fs.linkSync(src, dest);   // fails if dest exists
  fs.unlinkSync(src);       // only now remove the original
} catch (err) {
  if (err.code === 'EEXIST') /* report the collision, skip this file */;
  else throw err;
}

Read the order carefully. The original is removed only after the new name exists. If the process dies between the two lines, you have two names for one file — untidy, and nothing is lost. Do it the other way round and a crash loses the file entirely.

The honest limit of this fix link only works within one filesystem. Across a mount point it fails with EXDEV — but so does rename, so this is not a price you pay for choosing the safer call. The real fix there is copy-then-verify-then-delete. link does have one limit rename does not: you cannot hard-link a directory. It fails with EPERM, so skip anything that is not a file before you try.
Say it in the simplest words — the Feynman check

1 · In plain words A script is something you run while you are watching. A tool is something a stranger runs while nobody is watching. Everything that makes the second one harder is about the moments when things go wrong. A name already exists. A folder cannot be written to. The program crashes halfway through.

The tool has to survive all of those without destroying anything.

2 · One analogy Moving into a new flat. rename is putting your box down in a spot without looking, and whatever was there is crushed. link then unlink is different. You put the box in the new room first. You check it is really there. Only then do you clear the old room.

…and where the analogy breaks With boxes you would see the crushed thing. Here you see nothing at all — no error, no warning, exit code 0, and a report saying the job succeeded. That silence is the whole danger, and the analogy cannot show it.

The other break: with a box you could look first and then decide. In a filesystem, looking first is a race condition. Something can create the file in the gap between your look and your move. You cannot look. You have to make the filesystem refuse.

3 · The sticking point People believe --dry-run makes a tool safe. It does not. A dry run tells the user what the tool intends to do. Say the plan is “rename a onto b”. The dry run prints that plan, and hides the destruction inside it.

--dry-run is a preview, not a guard. The guard is the operation that cannot overwrite. You need both, and they are not the same thing.

4 · Now you explain it back

In two or three sentences, explain why if (!fs.existsSync(dest)) fs.renameSync(...) looks careful but is not, and what you would do instead. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — bulk-rename

One tool, published, that you would let someone point at their photo folder.

Requirements. Every one is testable, and every one comes from weeks 9 to 11:

  1. bulk-rename <pattern> <replacement> [dir], parsed with util.parseArgs.
  2. --dry-run prints the plan and changes nothing. It is the default; renaming needs --go.
  3. The plan goes to stdout. Progress, warnings and collisions go to stderr.
  4. A name collision is reported and skipped, never overwritten. Use link + unlink.
  5. Exit 0 on success, 1 on bad arguments, 2 if any file was skipped. Set process.exitCode — never call process.exit().
  6. bin, files and exports set so a stranger can npm i -g it.
  7. --help prints usage to stdout and exits 0. No arguments at all prints the same text to stderr and exits 1. That difference is the whole of week 10 in two lines.

The shape — fill in the middle yourself

#!/usr/bin/env node
const { parseArgs } = require('node:util');
const fs   = require('node:fs');
const path = require('node:path');

let opts;
try {
  opts = parseArgs({
    options: { 'dry-run': { type: 'boolean' }, go: { type: 'boolean' } },
    allowPositionals: true,
  });
} catch (err) {
  console.error('bad arguments:', err.message);
  process.exitCode = 1;
  return;
}

const [pattern, replacement, dir = '.'] = opts.positionals;
const commit = opts.values.go === true
            && opts.values['dry-run'] !== true;   // safe by default; --dry-run always wins

let skipped = 0;
for (const name of fs.readdirSync(dir)) {
    const full = path.join(dir, name);
  if (!fs.lstatSync(full).isFile()) continue;   // link cannot take a directory

  const next = name.replaceAll(pattern, replacement);
  if (next === name) continue;

  console.log(`${name} -> ${next}`);           // the plan, on stdout
  if (!commit) continue;

  try {
    fs.linkSync(path.join(dir, name), path.join(dir, next));
    fs.unlinkSync(path.join(dir, name));
  } catch (err) {
    if (err.code === 'EEXIST') {
      console.error(`skipped ${name}: ${next} already exists`);   // stderr
      skipped++;
    } else {
      throw err;                                // a real bug — let it crash
    }
  }
}
if (skipped) process.exitCode = 2;

Now prove it. Build a folder designed to break your tool, in a temporary directory so you cannot damage anything real:

cd $(mktemp -d)
printf 'one\n'   > IMG_1.txt
printf 'two\n'   > IMG_2.txt
printf 'DO NOT LOSE ME\n' > photo_2.txt      # the collision

# run it as `node /path/to/bulk-rename.js` until you npm i -g it below
# 1 · dry run by default — nothing changes
bulk-rename IMG photo .
ls                                            # all three files still there

# 2 · commit, and watch the collision be refused
bulk-rename IMG photo . --go
echo "exit was $?"                            # 2
cat photo_2.txt                               # DO NOT LOSE ME  ← still there

# 3 · the plan is clean data, the warnings are not in it
bulk-rename IMG photo . 2>/dev/null | head
The test that matters Step 2 is the whole week. photo_2.txt must still say DO NOT LOSE ME. Now go back, swap link + unlink for a plain fs.renameSync, and run it again. Watch the file's contents change. Do that once, deliberately, so you never do it by accident.

Then ship it — the week 11 loop, for real this time:

npm pack --dry-run          # read the file list before you upload it
npm publish --access public
npm i -g @yourname/bulk-rename
bulk-rename --help

Say it like an interviewer just asked

What this lesson left out on purpose Undo — writing a log you can replay backwards — is the right next feature and is genuinely harder than the rename itself, so it is left as an exercise rather than taught badly. Concurrency is skipped too: renaming files one at a time is correct here, and the moment you do them in parallel you get a whole new class of collision. Watching a folder with fs.watch is not in this course — its behaviour differs by operating system in ways that would take a week of their own.

Remember this · the 20-second recap
  • A script runs while you watch. A tool runs on a stranger's files while nobody watches.
  • fs.rename onto an existing name destroys it silently — no error, exit code 0.
  • if (!exists) rename() is a race condition. Never check then act.
  • Use link (fails EEXIST) then unlink. Order it so a crash loses nothing.
  • --dry-run is a preview, not a guard. You need the safe operation as well.
  • Destructive actions should need a flag. Safe should be the default.
  • Plan on stdout, warnings on stderr, honest exit code, npm pack --dry-run before you publish.

If you remember one thing: make the filesystem refuse, in one operation — never look first and then act.
