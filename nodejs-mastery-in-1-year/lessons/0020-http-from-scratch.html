Start from the problem — what is a request, to Node?

A framework hands you req.body as an object, and it feels like the body was always there. It was not. HTTP arrives as bytes on a socket, over time.

So Node cannot give you an object. It gives you the two things it actually has:

What you getWhat it really isVerified prototype chain
reqA Readable stream of body bytes, with the headers already parsedIncomingMessage → Readable → Stream → EventEmitter
resA writable-shaped object you push bytes intoServerResponse → OutgoingMessage → Stream → EventEmitter
A precise detail that catches people req instanceof Readable is true. But res instanceof Writable is false — verified. ServerResponse goes through OutgoingMessage, not stream.Writable. It has write, end and cork, so it behaves like one and works in pipeline. A type check against Writable will still fail.

Once you accept that req is a stream, everything else this week follows. The headers arrived; the body has not. It is still coming, and you decide what to do about that.

Routing is just two strings

There is no magic in a router. It reads two properties and decides:

const http = require('node:http');

const server = http.createServer((req, res) => {
  const url = new URL(req.url, `http://${req.headers.host}`);
  const route = `${req.method} ${url.pathname}`;

  if (route === 'GET /health')      return sendJson(res, 200, { ok: true });
  if (route === 'GET /items')       return listItems(req, res, url.searchParams);
  if (route === 'POST /items')      return createItem(req, res);

  sendJson(res, 404, { error: 'not found' });
});

function sendJson(res, status, body) {
  const text = JSON.stringify(body);
  res.writeHead(status, {
    'content-type': 'application/json',
    'content-length': Buffer.byteLength(text),   // bytes, not characters — week 14
  });
  res.end(text);
}

Buffer.byteLength, not text.length. Week 14's rule reaches all the way here. One Vietnamese character is three bytes, and a wrong content-length truncates the response.

Failure 1 — the request that never ends

Write to the response and forget end():

const server = http.createServer((req, res) => {
  res.write('partial');
  // no res.end()
});

What the client sees (Node v24.14.0):

client hung, then: AbortError — the response never completed

The server logs nothing. No error, no warning, no slow query. The connection is simply held open forever, and the client waits until something else gives up.

Why this is the hardest bug in the lesson Every other failure leaves a trace. This one leaves nothing — the request is not slow, it is unfinished. Every early return in a handler is a chance to create it, which is exactly why frameworks end the response for you. Writing this by hand once teaches you what they are doing.

Failure 2 — the body you accepted without asking how big it was

The obvious way to read a body:

// WRONG — the client decides how much memory you use
let body = '';
req.on('data', (c) => { body += c; });
req.on('end', () => handle(JSON.parse(body)));

Nothing limits that. A client can send a gigabyte and you will hold a gigabyte. The fix is to count as you go and refuse early:

const LIMIT = 1_000_000;                       // 1 MB
let size = 0;
const chunks = [];

req.on('data', (c) => {
  size += c.length;                            // bytes, from week 14
  if (size > LIMIT) {
    res.writeHead(413).end('too large');
    req.destroy();                             // stop reading, cut the connection
    return;
  }
  chunks.push(c);
});
req.on('end', () => {
  if (res.writableEnded) return;               // we already refused
  handle(Buffer.concat(chunks).toString('utf8'));
});

The real behaviour (Node v24.14.0):

POST 500 KB  -> received 500000 bytes
POST 3 MB    -> connection cut: EPIPE

The 3 MB request never finished uploading. req.destroy() stopped it partway, and the client saw the connection close. That is the point: you refused before holding the data, not after.

Read the check carefully res.writableEnded in the end handler is not decoration. Without it, a request that trips the limit tries to respond twice, and the second attempt throws ERR_STREAM_WRITE_AFTER_END. Every early exit in a handler needs an answer to “has this response already been sent?”

Headers go out once, and then they are gone

You can change a status code and headers freely — right up until the first byte of the body leaves. After that, they are on the wire and cannot be taken back.

res.writeHead(200);
res.write('some data');       // headers are now SENT
// something fails here
res.writeHead(500);           // ERR_HTTP_HEADERS_SENT

This is why an error handler must always ask res.headersSent first. If they are already gone, the only honest move is to destroy the socket. The client then sees a broken response, rather than a successful one containing an error.

The rule that avoids the whole problem Do all the work that can fail before you write anything. Build the whole response in memory, then send it in one go. Stream the response only when the body is genuinely too big to hold — and then accept that a mid-stream failure cannot be turned into a clean 500.
Say it in the simplest words — the Feynman check

1 · In plain words A request is not a parcel that arrives complete. The label arrives first — the method, the path, the headers — and your code starts running immediately.

The contents are still being delivered while you work. You decide how much of it you are willing to accept. You must also say clearly when you have finished replying. If you never say you have finished, the other side waits forever.

2 · One analogy A phone call. The caller says who they are and why they rang — that is the headers. Then they start telling you the long story, which is the body. You have to say “goodbye” and put the phone down, or the line stays open.

…and where the analogy breaks On a real call, silence is obvious. Somebody says “hello? are you there?” and hangs up. Here nothing does.

A handler that forgets res.end() produces no error, no log line, and no slow query. The request is not slow — it is unfinished, which monitoring built around latency cannot see. And unlike a phone, you cannot interrupt a caller who talks too long.

You have to count the words as they arrive and hang up yourself. Otherwise the caller chooses how much of your memory to use.

3 · The sticking point People think res is like a return value: build it, send it, done. It is not. It is a stream that opens the moment you first write to it.

That single misunderstanding causes two bugs at once. An early return that skips end() leaves the connection open forever. And a failure after the first write cannot become a 500, because the 200 is already on the wire. The rule that avoids both: finish all the work that can fail before you write one byte.

4 · Now you explain it back

In two or three sentences, explain why forgetting res.end() is harder to find than a slow query. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — a router, then break it three ways

No framework. Weeks 18 and 14 are both in here.

Requirements:

  1. Routes on method plus pathname. Query strings parsed with URL, never by hand.
  2. JSON responses with a correct content-length, using Buffer.byteLength.
  3. A 1 MB body limit that refuses with 413 and calls req.destroy().
  4. A GET /download route that streams a large file with pipeline, never readFileSync.
  5. One error handler that checks res.headersSent before deciding what to do.
  6. Correct status codes throughout: 200; 201 with a Location header; 400, 404, 409, 413 and 500.

Then cause all three failures on purpose and watch what the client and the logs do:

# 1 · the hang — comment out res.end() in one route
curl -m 5 http://localhost:3000/broken      # curl times out. Server logs NOTHING.

# 2 · the oversized body
head -c 3000000 /dev/zero | curl -X POST --data-binary @- http://localhost:3000/items

# 3 · headers already sent — throw after the first write
curl -v http://localhost:3000/late-error    # a 200 that is cut off mid-body

Now count your open sockets while the hang is running:

lsof -p $(pgrep -f "node server.js") | grep -c TCP

Fire ten hung requests and watch that number climb and never come down. That is the leak, and it is the reason the missing end() matters more than it looks.

What to hand in The socket count before and after ten hung requests. One pair of numbers explains why this failure kills a server slowly instead of quickly.
Scenario

A service becomes unresponsive after about six hours. CPU is near zero, memory is flat, and no request in the logs took longer than 40 ms. Restarting fixes it for another six hours.

Say what you would measure first, what you expect to find, and which line of code you would go looking for.

Remember this · the 20-second recap
  • Headers arrive first and your handler runs. The body is still coming.
  • req is a real Readable. res is not a Writable — it goes through OutgoingMessage and only implements the interface.
  • Forgetting res.end() holds the socket open forever, with no error and no log line.
  • An unlimited body means the client chooses your memory. Count bytes and refuse with 413 plus req.destroy().
  • Check res.writableEnded before responding twice, or you get ERR_STREAM_WRITE_AFTER_END.
  • Headers cannot be recalled after the first body byte. Check res.headersSent in every error handler.
  • Use Buffer.byteLength for content-length, never string.length.

If you remember one thing: do all the work that can fail before you write one byte. After that, you cannot change your mind.
