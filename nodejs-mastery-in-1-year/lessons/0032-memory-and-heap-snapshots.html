Memory and heap snapshots

Find a leak and name the thing that held the reference. This is the debugging skill with no ready answer online.

Where you are Week 31 was about time. This week is about space, and the tool is different — a profile is a tally over time, a snapshot is a photograph of one instant.

Start from the problem — a leak in a garbage-collected language

JavaScript frees memory for you. So how can it leak?

Because the garbage collector has exactly one rule, and it is not “is this still needed?”. It is “can this still be reached?”. Reachable means a chain of references leads to the object from a root. A global, the stack, or a live closure.

The definition that makes leaks findable

A leak in Node is not memory the collector failed to free. It is memory that is still reachable and that you no longer need. The collector is working perfectly. Your code is holding on.

That reframes the whole job. You are not looking for a bug in V8. You are looking for the reference. There is always exactly one thing at the end of it, called the retainer.

“Memory went up” is not a leak

Before you investigate anything, rule out the three normal explanations:

What you seeProbablyHow to tell
Memory rises, then drops sharplyNormal. That is a GC.The sawtooth pattern.
Memory rises and settles at a plateauNormal. Caches and pools filling.It stops rising.
Memory rises to the limit, GC runs constantly, then it diesCould be a leak — or a heap that is simply too small.Raise the limit. If it just dies later, it is a leak.
Memory rises steadily and never comes back downA leak.Compare across two GCs.

Watch v8.getHeapStatistics().used_heap_size, not process.memoryUsage().rss. RSS includes buffers, native allocations and memory the OS has not reclaimed yet, so it is noisy. Used heap is what your JavaScript is actually holding.

Two snapshots, and the difference between them

One snapshot tells you what exists. That is rarely enough — plenty of things legitimately exist. Two snapshots tell you what grew, and growth is the signal.

const v8 = require('node:v8');
v8.writeHeapSnapshot('./before.heapsnapshot');
// ...do the work you suspect, several times...
v8.writeHeapSnapshot('./after.heapsnapshot');

Load both into Chrome DevTools → Memory → Load, then choose Comparison. Sort by #Delta. Verified on Node v24.14.0, with 200,000 objects retained:

before: heap used  3.4 MB | snapshot file  4.4 MB
after:  heap used 43.5 MB | snapshot file 54.4 MB

Forty megabytes of growth, and the snapshot file grew by fifty. That is the whole diagnosis so far: something is holding 200,000 objects. Now you need to know what.

The retainer path — the only screen that matters

Click any object in a snapshot and DevTools shows Retainers. That is the chain of references keeping it alive, read from the object back to a root.

Object
 └─ in array of Array
     └─ in store of Object
         └─ in module.exports of Module        ← the root

Read it bottom to top and it becomes a sentence. A module exports an object, which has a property called store, which is an array, which holds this object. That sentence names the line of code to change.

This is the skill, and it is the only part that cannot be automated Anything can tell you memory is growing. Only the retainer path tells you which of your own references is the one to remove. Learning to read that chain is the entire value of this week.

Four leaks, and they are nearly all of them

ShapeLooks likeFix
A growing collectionA Map or array that only ever gets set and pushA size limit, or a TTL, or an LRU.
A forgotten listeneremitter.on() per request, never off()Remove it, or use once. Week 18's warning fires here.
A closure holding too muchA small callback keeping a huge buffer alivePull out only the field you need before closing over it.
A timer that never stopssetInterval with no clearIntervalClear it, and unref() anything that should not hold the process open.
The closure one is the sneakiest 
function handler(bigBuffer) {
  const id = bigBuffer.id;
  return () => console.log(id);      // looks like it holds one number
}
A closure captures the scope, not the variables it happens to mention. In some engines that callback keeps the whole bigBuffer alive even though it only reads id. This is week 2's “the room cannot be cleared while any key exists”, showing up thirty weeks later as a production leak.
Say it in the simplest words — the Feynman check

1 · In plain words The computer throws away anything you can no longer get to. It does not ask whether you still want it. It only asks whether there is any path from your program to that thing.

So a leak is not the cleaner failing to do their job. It is you still holding one end of a string tied to something you thought you had thrown away.

2 · One analogy A cleaner who takes away anything not attached to the building. Furniture bolted down stays. So does a huge box, if one thin string still runs from it to a hook on the wall.

…and where the analogy breaks A cleaner could see the string and ask you about it. The collector cannot, and neither can you, because the string is usually not where you would look.

The room is your whole process, and the hook can be anywhere.

An array you forgot. A listener nobody removed. A closure that captured more than it uses. That is why the answer is a tool and not care. You take two photographs of the room and compare them. The tool traces the string back to the hook for you. Nobody finds these by reading code.

3 · The sticking point People see memory rising and call it a leak. Rising memory is normal — caches fill, pools warm up, the collector waits until it is worth running.

The signal is not “it went up”. It is “it went up and never came back down across two collections”. Chasing the first thing wastes a day tuning something that was working. The opposite mistake is worse. A slow leak looks completely normal for hours, right until the process is killed.

4 · Now you explain it back

In two or three sentences, explain why a garbage-collected language can still leak. Use the word reachable. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — plant three leaks, find all three

Add three deliberate leaks to a copy of the spine, one at a time. Find each one from the snapshots alone.

  1. A growing Map. Cache every request by URL, never evict.
  2. A forgotten listener. process.on('SIGTERM', ...) inside the request handler.
  3. A closure holding a buffer. Keep a callback that mentions one field of a large object.

For each one, in this order:

1. Snapshot before.
2. Run 10,000 requests.
3. Snapshot after.
4. Compare, sort by #Delta, write down the retainer path.
5. Fix it. Repeat 1–3 and prove the delta is gone.
A measurement trap I hit while writing this lesson My first version of the leak test reported no growth at all — 3.4 MB before and 3.4 MB after, with 200,000 objects supposedly retained. Adding one line that read store.length made the growth appear.

I could not reproduce that effect reliably enough to explain it. So this lesson does not claim a mechanism. The lesson it does teach is the safe one: a single measurement that says “no leak” is not evidence. Change one thing, measure again, and be suspicious of a result that is exactly what you hoped for.

What to hand in Three retainer paths, written out as sentences, and the before-and-after delta for each. The paths matter more than the fixes — the fix is usually one line, and finding it is the whole job.
Scenario

RSS climbs about 40 MB an hour and never comes down. The service is restarted nightly, so nobody has ever seen it fail. A colleague suggests raising --max-old-space-size and moving on.

Say what raising the limit actually buys, what one measurement would tell you whether this is a leak at all, and what you would do in the first ten minutes.

Say it like an interviewer just asked

What this lesson left out on purpose How V8's collector works — generational collection, scavenge against mark-compact — is genuinely interesting and does not change what you do. WeakMap and WeakRef hold references that do not keep an object alive, and are the right tool for a cache keyed by object; worth reading about once the four shapes above are familiar. Native memory leaks in a C++ addon do not appear in a heap snapshot at all, and need different tools.

Remember this · the 20-second recap
  • The collector asks “is this reachable?”, never “is this needed?”
  • A leak is memory still reachable that you no longer want. The collector is fine; your code is holding on.
  • Watch used_heap_size, not rss. RSS is noisy.
  • Rising memory is normal. Rising and never returning across two collections is the signal.
  • One snapshot shows what exists. Two show what grew. Sort the comparison by #Delta.
  • The retainer path is the only screen that matters. Read it backwards as a sentence.
  • Four shapes cover nearly all of them: growing collection, forgotten listener, fat closure, uncleared timer. Be suspicious of any measurement that says exactly what you hoped.

If you remember one thing: you are not looking for a bug in the collector. You are looking for the reference you forgot you were keeping.
