The http module from first principles

Node ships a built-in http module — no install, no framework. A server is one function: it receives every request as req and replies through res.

hello.js

const http = require('http');

const server = http.createServer((req, res) => {
  res.writeHead(200, { 'Content-Type': 'text/plain' });
  res.end('hello from raw Node\n');
});

server.listen(3000, () => console.log('listening on http://localhost:3000'));

Run node hello.js, then in another terminal curl http://localhost:3000. That callback runs on every request. It runs on the event loop's single thread, so keeping it fast is the most important thing.

Routing — deciding what to do by method + URL

A "route" is just a decision based on req.method and req.url. No framework needed — an if is enough to understand how every framework works underneath.

function sendJson(res, status, data) {
  res.writeHead(status, { 'Content-Type': 'application/json' });
  res.end(JSON.stringify(data));
}

Async handlers — read a real file without blocking

Here is where weeks 1–3 become useful. To read a file inside a handler, use the async API (fs/promises), never readFileSync. A sync read would freeze every other request.

Say it in the simplest words — the Feynman check

1 · In plain words Every request that arrives at your server is handled by the same single worker. If one request asks that worker to sit and wait, everybody else waits too. If it asks the worker to hand the job away and come back later, everybody else keeps getting served. That is the entire difference between a server that survives and one that freezes.

2 · One analogy One till in a shop. A customer paying by card is fine. The card machine does the waiting, so the cashier serves the next person. A customer who asks the cashier to count a jar of coins is not fine. The queue stops until the counting is done.

…and where the analogy breaks A real cashier serves one customer from start to finish. Your one thread does not. It runs a slice of request 1, then a slice of request 7, then finishes request 1. Every await hands control back.

So a handler can sit half-done while another runs. Two requests can read the same variable between two await lines. Keep the till picture for who does the work, and throw it away for the order it happens in.

3 · The sticking point People translate “async” as fast and “sync” as slow. Both are wrong, and the mistake is expensive.

An await on a 2-second database query is slow and completely harmless. A tight for loop finishing in 200 ms is fast and froze every other request. The question is never how long it takes. It is whether the single thread was occupied.

4 · Now you explain it back

In two or three sentences, explain why a 2-second database query is safe. Then say why a 2-second for loop is not, though both take 2 seconds. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Three things you have not been taught yet This build uses async, await and Promise.all. You learn all three properly next week, in Lesson 5. That ordering is deliberate: it is much easier to want them after you have felt the problem they solve. For today, read them like this and no deeper:
  • await x — “hand the waiting away, then carry on here when the answer arrives”.
  • async before a function — “this function is allowed to use await”.
  • Promise.all([…]) — “start all of these, tell me when every one is finished”.

Build it for real — the full server

Create these two files. Then run node server.js.

data.json

{ "users": ["ada", "grace", "linus"] }

server.js

const http = require('http');
const fs = require('fs/promises');

function sendJson(res, status, data) {
  res.writeHead(status, { 'Content-Type': 'application/json' });
  res.end(JSON.stringify(data));
}

const server = http.createServer(async (req, res) => {
  // route 1: instant response
  if (req.method === 'GET' && req.url === '/') {
    return sendJson(res, 200, { message: 'hello from raw Node' });
  }

  // route 2: slow, but NON-blocking (thread stays free for 2s)
  if (req.method === 'GET' && req.url === '/slow') {
    setTimeout(() => sendJson(res, 200, { done: true }), 2000);
    return;
  }

  // route 3: read a real file asynchronously
  if (req.method === 'GET' && req.url === '/file') {
    try {
      const text = await fs.readFile('./data.json', 'utf8');
      return sendJson(res, 200, JSON.parse(text));
    } catch (err) {
      return sendJson(res, 500, { error: 'could not read file' });
    }
  }

  sendJson(res, 404, { error: 'not found' });
});

server.listen(3000, () => console.log('listening on http://localhost:3000'));

Try each route: curl localhost:3000/, curl localhost:3000/file, curl localhost:3000/slow. You've built a real, multi-route JSON API from scratch.

Measure it — the latency tester

Now prove non-blocking is real with numbers. This tester fires 10 requests to /slow at the same time and times the total. Node has a built-in fetch, so no installs.

tester.js (keep server.js running, then node tester.js)

const N = 10;

(async () => {
  const start = Date.now();
  await Promise.all(
    Array.from({ length: N }, () =>
      fetch('http://localhost:3000/slow').then((r) => r.text())
    )
  );
  console.log(`${N} concurrent /slow requests took ${Date.now() - start} ms`);
})();

Each /slow request takes 2 seconds. But because the thread never waits, all 10 overlap — so the total is just over 2000 ms, not 20000. Ten 2-second waits happened at the same time on one thread.

The blocking trap, measured

Swap the /slow handler for a blocking version and run the same tester:

if (req.method === 'GET' && req.url === '/slow') {
  const end = Date.now() + 2000;
  while (Date.now() < end) {}          // busy-wait: freezes the one thread
  return sendJson(res, 200, { done: true });
}

Now the tester reports roughly 20000 ms, about 10× slower. The single thread is captured by each busy-wait in turn, so the requests cannot overlap. Same code shape, 10× the latency. That number is why "never block the event loop" is the first rule of Node.

One more real habit (full version in week 27) A real server also shuts down cleanly. On SIGTERM you call server.close() to stop taking new requests and let requests already running finish. We'll do graceful shutdown properly when we harden the one API we build from week 21, in week 27 — just know it exists.

Remember this · the 20-second recap
  • A Node server is one function: http.createServer((req, res) => …), then server.listen(port).
  • A route is just a decision on req.method + req.url — frameworks only make this tidier.
  • Inside a handler, use async I/O (fs/promises, await) so one slow request never freezes the others.
  • Ten async 2-second requests finish in ~2s (they overlap); ten blocking ones take ~20s (they stack) — measured, not claimed.
  • A synchronous CPU loop in a handler blocks every user, because they all share one thread.
  • You have built a real multi-route JSON API from scratch. It is a throwaway. The service you harden for the rest of the year starts in week 21.

If you remember one thing: keep every request handler fast and async, and one thread will serve everyone at once.
