Background work — queues, retries, idempotency

Slow work does not belong in a request. And a retry can charge a customer twice.

coreWeek 42 of 52. This lesson builds one domain-expert ability: design work that survives being run twice. Week 42 in the plan · Glossary

Your win today: you will charge a test customer 9,998 cents for a 4,999 cent order — with no bug in your code, and no retry you wrote. Then you will fix it in four lines.
Where you are Weeks 40 and 41 gave the spine a database and a cache. Both are things a request waits for. This week is about the work a request should not wait for at all.

Start from the problem — what does a slow request cost?

Not just the user's patience. While a request runs it holds three things. A socket, a slot in your concurrency limit, and often a pool connection from week 40. Eight hundred milliseconds of work is eight hundred milliseconds of holding all three.

Same 800 ms task, two designs. Measured on Node v24.14.0:

DesignOne request20 at once
Do it in the request842 ms, status 200817 ms until the last response
Queue it, return a job id3 ms, status 20221 ms until the last response
A queue does not make work faster Those 20 jobs still take 16 seconds to process. Nothing sped up. What changed is that nobody is holding a socket, a connection or a spinner while it happens.

This matters because people reach for a queue expecting speed and get confused when total throughput is unchanged. A queue moves work off the request path and lets you control its rate separately. That is the benefit, and it is a big one.

The test for whether work belongs in a request

Does the user need the result to continue? If yes, it stays. If they only need to know you accepted it, queue it. An email, a PDF, a webhook, a thumbnail.

The promise a queue actually makes

You want “run this job exactly once”. No queue gives you that. What you get is at-least-once, and the reason is worth understanding, because it explains the whole rest of the lesson.

A worker takes a job, does the work, then tells the queue it is done. Between those last two steps it can die. A deploy, an out-of-memory kill, a network partition, or the SIGKILL from week 27.

The queue now knows one thing only: no acknowledgement arrived. It cannot tell these apart:

What really happenedWhat the queue sees
The worker died before doing the workNo acknowledgement
The worker did the work, then diedNo acknowledgement
The worker did the work and acknowledged, but the ack was lostNo acknowledgement

Only one choice is safe: redeliver. Losing a job is worse than repeating one — usually. Watch what “repeating one” means with a real database:

run 1: worker died before acknowledging
queue cannot know the work was done, so it redelivers...
charged total: 9998 cents   <- the customer paid TWICE for one job
There is no bug in that code The job did exactly what it was told, twice, because the queue did exactly what it promised. You cannot fix this by writing the job more carefully. The delivery guarantee is the thing you have to design around.

Idempotency — the only real answer

Idempotent means running it twice has the same effect as running it once. With at-least-once delivery this is not a nice property. It is the requirement.

The mechanism is a key the job carries, and a uniqueness rule the database enforces. You already have both — this is week 40's unique constraint and week 40's transaction, doing a new job:

create table processed_jobs (idempotency_key text primary key, charged_at timestamptz default now());

async function run(job) {
  try {
    await client.query('BEGIN');
    await client.query('INSERT INTO processed_jobs(idempotency_key) VALUES($1)', [job.key]);
    await client.query('INSERT INTO charges(user_id, cents) VALUES($1,$2)', [job.userId, job.cents]);
    await client.query('COMMIT');
  } catch (e) {
    await client.query('ROLLBACK');
    if (e.code === '23505') return 'already done — nothing to do';   // week 40's code
    throw e;
  }
}

Same crash, same redelivery. Measured:

run 1: worker died before acknowledging
run 2: already done — nothing to do
charged total: 4999 cents   <- correct
The transaction is the whole trick — read it again The key and the charge are inserted in one transaction. So either both happened or neither did.

Write the key first and commit separately, and a crash between them leaves a key with no charge. The job is now marked done, and the customer was never charged. That is worse than the double charge, because nothing ever detects it.

Where does the key come from? It must be stable across retries, so it cannot be generated inside the job. Use something from the work itself: charge:order-1042. If the client supplies it, your HTTP endpoint becomes safe to retry too. That is the same problem one layer up.

Retries — and the ones you must not make

Retry with exponential backoff and jitter, exactly as in week 8. Measured:

attempt 1: upstream 503 -> retry in 104 ms
attempt 2: upstream 503 -> retry in 186 ms
attempt 3: ok  (after 292 ms)

The jitter is not decoration. Without it, every worker that failed at the same moment retries at the same moment. You have rebuilt the spike from week 41.

The harder question is what to retry. Retrying a permanent failure is not persistence, it is a loop:

FailureRetry?Why
503, timeout, connection resetYesOperational. It may be fine in a second.
429 rate limitedYes, after Retry-AfterThey told you when.
400 invalid email addressNoIt will be invalid forever. Dead-letter it.
404, 403NoNothing about waiting changes the answer.

That is week 28's taxonomy again, deciding a new question. Operational errors are worth retrying; the others are not.

The dead-letter path, and who looks at it

Every queue needs a maximum attempt count and somewhere for jobs that exhaust it. Measured:

attempts made : 3
dead-lettered : {"attempts":3,"reason":"invalid email address"}
// without a max, this job retries forever and never leaves the queue

A job that retries forever is not resilience. It is a job consuming a worker slot permanently. Behind it, a queue grows until the process runs out of memory.

A dead-letter queue nobody reads is a bin This is the part almost everybody skips. Store the job payload, every attempt, and the last error. Then alert on the queue being non-empty, and name the person who looks. Without that last step you have built a place for failures to be silent, which is worse than not having one.

What the user sees while it runs

Moving work to a queue changes your API, and the HTTP for it already exists:

POST /reports
202 Accepted
Location: /jobs/8f3a
{ "jobId": "8f3a", "state": "waiting" }

GET /jobs/8f3a
200 { "state": "active" }
200 { "state": "completed", "result": "/reports/8f3a.pdf" }
200 { "state": "failed", "reason": "..." }

202 means “accepted, not finished” — which is exactly true, and different from 200. The Location header tells the client where to look without you inventing a convention.

The failure the client must handle A job can fail after you returned 202. So failed has to be a real state in your status response, and the client needs to do something with it. This is the most commonly skipped part of moving work to a queue, and it is why users end up staring at a spinner that never resolves.
Say it in the simplest words — the Feynman check

1 · In plain words A worker does a job, then tells the queue it finished. If it dies between those two steps, the queue only knows one thing: no acknowledgement arrived.

It cannot tell whether the work was done or not. Losing a job is usually worse than repeating one, so it sends the job again. That is called at-least-once, and every queue works this way.

2 · One analogy Posting a letter with no delivery confirmation. If you hear nothing back, you cannot tell whether it never arrived or the reply got lost. So you send it again.

…and where the analogy breaks A second letter is harmless. A second job charges someone twice. I measured it against a real database. One 4,999 cent order, one crash before the acknowledgement, and the customer paid 9,998 cents.

And there was no bug in that job. It did exactly what it was told, twice, because the queue did exactly what it promised. You cannot write the job more carefully to avoid this. The delivery guarantee is a fact you design around, not a defect you fix.

3 · The sticking point People try to make delivery exactly-once. You cannot. The failure lives in the gap between doing the work and reporting it, and no protocol removes that gap.

So you make the job safe to repeat instead. It carries a stable key. The database refuses a second row with it — the same unique constraint that gives you a 409. The key and the work go in one transaction, so either both happened or neither did. Commit them separately, and a crash between them marks the job done without doing it.

4 · Now you explain it back

In three sentences, explain why a queue cannot promise to run your job exactly once. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — move the slow work off the request

Requirements:

  1. Pick the spine's slowest route and move it to a BullMQ job. Return 202 with a Location header.
  2. A GET /jobs/:id endpoint with waiting, active, completed and failed as real states.
  3. Exponential backoff with jitter, and a maximum attempt count.
  4. Retry only operational failures. A 400 goes straight to the dead-letter path.
  5. A dead-letter store holding the payload, the attempts and the last error. Plus an alert, and a named person who reads it.
  6. Run the same job twice on purpose. Prove the side effect happened once. This is the week's real deliverable.
  7. Kill the worker mid-job with SIGKILL, restart it, and prove the same thing.
  8. Make requirements 6 and 7 automated tests.
Requirement 7 is the one that finds the real bug Running a job twice in a test is easy, and it usually passes. Killing the worker mid-transaction is what exposes the version where the key was committed separately from the work. That failure is silent — the job is marked done and nothing happened — so a test is the only way you will ever see it.
The drill — five minutes, out loud

“A retry sent the confirmation email twice. Design the fix.”

Do not start with the email. Start by saying why the retry happened and why the queue was right to retry. Then give the idempotency key you would use, say where the record of it lives, and say what happens if the send succeeds but recording it fails. That last question is the whole interview.

Say it like an interviewer just asked

What this lesson left out on purpose Job priorities, rate limiting and repeatable jobs are all in BullMQ and worth reading about. The outbox pattern is the proper answer to “write to the database and enqueue atomically”, and it deserves real study. Kafka and other log-based systems solve a different problem from a work queue. Exactly-once processing is achievable with careful transactional design, and the word still hides a lot. Saga and compensating transactions handle work that spans services.

Remember this · the 20-second recap
  • Work stays in the request only if the user needs the result to continue. Otherwise, queue it.
  • Measured: 842 ms inline versus 3 ms and a 202. The work still takes 16 s — a queue moves it, it does not speed it up.
  • Queues are at-least-once. A missing acknowledgement has three possible causes and the queue cannot tell them apart.
  • Measured: one 4,999 cent order, one crash → 9,998 cents charged, with no bug in the job.
  • Fix the job, not the delivery. A stable key, a unique constraint, and the key plus the work in one transaction.
  • Retry operational failures with jittered backoff; never a 400. A dead-letter queue needs a maximum attempt count, an alert and a named person, or it is a bin.
  • failed must be a real state in your job status, because a job can fail after you returned 202.

If you remember one thing: you cannot make delivery exactly-once, so you make the job safe to repeat.
