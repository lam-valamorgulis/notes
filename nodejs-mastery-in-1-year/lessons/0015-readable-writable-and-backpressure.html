Readable, Writable and backpressure

The one signal that stops a fast producer drowning a slow consumer — and what happens when you ignore it.

coreWeek 15 of 52. This lesson builds one domain-expert ability: explain it from first principles, with no jargon and no notes. Week 15 in the plan · Glossary

Your win today: you will explain backpressure without saying “Node just handles it”. You will also measure the cost of ignoring it: 172 MB against 84 MB of memory, for exactly the same work.
Where you are Week 14 was what a chunk is. This week is where chunks come from, and why the thing producing them has to be told to slow down.

Start from the problem — the two sides run at different speeds

You are copying a file to a network socket. Reading from a local disk is fast. Writing to a network is slow. Say the disk gives you 100 MB a second and the network takes 10 MB a second.

What happens to the other 90 MB, every second?

There are only three possible answers. There is no fourth:

  1. Throw it away. Correct programs cannot do this.
  2. Keep it in memory. Works for a second. After ten seconds you are holding 900 MB.
  3. Tell the reader to stop reading.
This is the whole idea

Backpressure is answer 3. It is the slow side telling the fast side to wait. Every stream API in Node exists to make that message travel.

So streams are not really about “reading a file in pieces”. They are about the message that travels backwards, from the slow end to the fast end.

How Node sends that message

Node had to put the signal somewhere. It chose the return value of write:

const ok = writable.write(chunk);
// true  = keep going
// false = stop. I will tell you when I am ready.

When it returns false, you wait for the drain event, then carry on. That is the entire protocol. Two things: a boolean, and an event.

The threshold is highWaterMark. Verified on Node v24.14.0:

createWriteStream('/dev/null').writableHighWaterMark   // 65536

w.write(Buffer.alloc(1000))     // true   — under the mark
w.write(Buffer.alloc(100000))   // false  — over it
w.writableLength                // 101000 — bytes now waiting
The return value is advice, not a lock Node does not stop you writing after false. The write still succeeds. The data still queues. highWaterMark is not a limit — it is the point at which the stream starts asking you to stop. Whether anything listens is entirely up to your code.

Measure the cost of not listening

Write 128 MB into a sink that takes 5 ms per chunk. Once ignoring the signal, once honouring it.

const slow = new Writable({
  highWaterMark: 64 * 1024,
  write(chunk, enc, cb) { setTimeout(cb, 5); },   // a slow network, in one line
});

// A — ignore the signal
for (let i = 0; i < 2000; i++) slow.write(fresh64KB());

// B — honour it
(function pump() {
  while (i < 2000) {
    i++;
    if (!slow.write(fresh64KB())) return slow.once('drain', pump);
  }
})();

The real output (Node v24.14.0):

ignore  -> peak RSS 172 MB | queued 125 MB
honour  -> peak RSS  84 MB | queued   0 MB

Same data, same sink, same result on the other end. Twice the memory, and 125 MB sitting in a queue that did nothing but wait.

Why this is worse than it looks 128 MB is a small file. The queue grows with the input, so the same code on a 10 GB file tries to hold most of 10 GB. The program does not slow down first and crash later. It looks completely fine, and then the process is killed for using too much memory.
A trap I fell into while measuring this My first version of that benchmark wrote the same Buffer object 2000 times. Memory barely moved, and I nearly wrote down the wrong conclusion. The queue was holding 2000 references to one 64 KB buffer, not 2000 copies. A fresh buffer per write is what makes the measurement real. When a benchmark tells you something surprising, suspect the benchmark first.

Two ways to read, and why both exist

ModeYou writeWho decides the pace
Flowingr.on('data', fn)The source. Chunks arrive as fast as it can produce them. You must call r.pause() yourself to slow it.
Pausedr.read(), or for await…ofYou. Nothing arrives until you ask.

Adding a 'data' listener switches a stream into flowing mode immediately. That is why the naive copy loop leaks memory: the source starts pushing and nothing is telling it to stop.

What to write in real code Neither of those, most of the time. Use pipeline, which wires the signal for you, or for await…of, which is paused mode with pleasant syntax: 
for await (const chunk of readable) {
  // the loop body IS the backpressure — nothing is read until you come round again
}
You learn pipeline properly in week 16. Know the manual protocol first, so the helper is a convenience and not a mystery.
Say it in the simplest words — the Feynman check

1 · In plain words Two people are moving boxes. One takes them off a fast truck. The other carries them slowly up the stairs.

If the fast one never looks up, boxes pile up in the hallway. Nothing is lost, but the hallway fills. Backpressure is the slow one saying “wait”, and the fast one actually stopping.

2 · One analogy A tap and a bucket with a small hole. Open the tap fully and the bucket overflows. The right amount to open the tap is however much the hole lets out. Only the bucket knows that number.

…and where the analogy breaks An overflowing bucket makes a mess you can see, and the water goes away. Here nothing spills and nothing goes away.

The extra data stays inside your process, in memory, forever growing. It is silent right up to the moment the operating system kills you for using too much. And the bucket does not get bigger when the file does. The queue grows with the input. So the same code that survives a 100 MB file dies on a 10 GB one.

3 · The sticking point People believe highWaterMark is a limit. It is not. Node never refuses a write.

It is the point where write() starts returning false — a request, not a rule. The queue keeps growing however many times it is ignored. That is why “I used streams” does not mean “my memory is safe”. Using a stream and honouring its signal are two different things, and only the second one saves you.

4 · Now you explain it back

In two or three sentences, explain what write() returning false means. Then say what happens if you ignore it. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — see your own memory climb

One file, two runs, two numbers. Save as bp.js.

const { Writable } = require('node:stream');
const mode = process.argv[2];              // 'ignore' or 'honour'

const slow = new Writable({
  highWaterMark: 64 * 1024,
  write(_chunk, _enc, cb) { setTimeout(cb, 5); },
});

const TOTAL = 2000;
let i = 0, peak = 0;
const track = () => {
  const mb = process.memoryUsage().rss / 1048576;
  if (mb > peak) peak = mb;
};
const fresh = () => Buffer.alloc(64 * 1024, 0x61);   // a NEW buffer each time

if (mode === 'ignore') {
  for (; i < TOTAL; i++) { slow.write(fresh()); track(); }
  console.log(`ignore -> peak ${peak.toFixed(0)} MB | queued ${(slow.writableLength/1048576).toFixed(0)} MB`);
} else {
  (function pump() {
    while (i < TOTAL) {
      i++; track();
      if (!slow.write(fresh())) return slow.once('drain', pump);
    }
    console.log(`honour -> peak ${peak.toFixed(0)} MB | queued ${(slow.writableLength/1048576).toFixed(1)} MB`);
  })();
}

Predict both numbers before you run it. Write them down. Then:

node bp.js ignore
node bp.js honour

Then change one thing. Set TOTAL to 8000 and run both again. The honour number should barely move. The ignore number should roughly quadruple. That is the whole point: one of them scales with the input and one does not.

What to hand in A four-cell table: ignore and honour, at 2000 and at 8000 chunks. The shape of those four numbers is the lesson.

Remember this · the 20-second recap
  • Two sides of a stream run at different speeds. There are only three options, and only one is correct: tell the fast side to wait.
  • The signal is write() returning false, and the drain event saying you may continue.
  • highWaterMark (64 KB by default) is the point where asking starts, not a limit. Node never refuses a write.
  • Ignoring it queues data in your process. Measured: 172 MB against 84 MB, with 125 MB stuck in the queue.
  • The queue grows with the input, so the same code survives a small file and dies on a big one.
  • Adding a 'data' listener starts the source immediately. for await…of and pipeline do not.
  • Using a stream and honouring its signal are two different things.

If you remember one thing: the data goes forward, and the permission to send goes backwards. A stream is that second arrow.
