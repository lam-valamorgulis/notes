Operational versus programmer errors

One kind you handle. The other you crash on. Mixing them up is how services corrupt data quietly.

coreWeek 28 of 52. This lesson builds one domain-expert ability: say why it was built this way, and what that choice gives up. Week 28 in the plan · Glossary

Your win today: a rule that tells you what to do with any error in about two seconds. And a demonstration that an uncaughtException handler keeps a broken process alive — which is the single most dangerous line in most Node codebases.
Where you are Week 6 was about where an async error goes. This week is about what to do with it once you have caught it — and when catching it is the wrong move.

Start from the problem — “handle your errors” is bad advice

Take two errors that both reach the same catch:

  • ECONNREFUSED — the database is restarting.
  • TypeError: cannot read properties of undefined — you have a bug.

The first one means the world outside misbehaved, and your program is fine. Retry, or return a 503. The second means your program is not what you think it is. Its state may already be wrong, and continuing means acting on assumptions you have just proved false.

Treating those the same is the mistake. So you need a name for the difference:

The two categories

An operational error is an expected failure in a correct program. You handle it and carry on. A programmer error is a bug. You crash, because a program in an unknown state is more dangerous than a restart.

The test — one question, two seconds

“Did I anticipate this when I wrote the code?”

Notice that the category is not a property of the error object. It is a property of your intent. The same ENOENT is operational when a user asks for a missing file. It is a programmer error when your own config file has vanished.

Marking the difference in code

Since it is intent, you have to say so. One base class and a flag:

class AppError extends Error {
  constructor(message, { code, status = 500, cause } = {}) {
    super(message, { cause });        // keeps the original stack — see below
    this.name = 'AppError';
    this.code = code;                 // week 21's stable client-facing code
    this.status = status;
    this.isOperational = true;        // the whole point of the class
  }
}

Then the top-level handler has something to ask:

function onError(err, req, res) {
  if (err.isOperational) {
    return sendError(res, err.status, err.code, err.message);   // week 21
  }
  logger.fatal({ err }, 'programmer error — restarting');
  res.destroy();                       // this request is not getting an answer
  shutdown('programmer-error');         // week 27's graceful path
}
cause keeps the trail — verified new Error(msg, { cause: original }) preserves the original error and its stack: 
wrapped.message      // 'could not save link'
wrapped.cause.message // 'connection refused'
wrapped.cause.stack   // 'at low (...)'  ← still there
Wrap freely to add context. Never wrap by copying the message into a new error and throwing that away — that is how a stack trace stops naming the line that broke.

The most dangerous line in most Node codebases

process.on('uncaughtException', (err) => {
  logger.error(err);        // and then... nothing
});

It looks responsible. It is the opposite. Watch what it actually does:

The real output (Node v24.14.0):

handler ran: boom
...and the process is STILL ALIVE 100ms later
exit code: 0

Registering that handler overrides Node's decision to exit. A bug threw, nobody knows what state anything is in, and the process carries on serving traffic and reports success.

What “unknown state” actually costs Consider a request that threw halfway through:
  • A database transaction is open and will never be committed or rolled back. That row is locked.
  • A module-level cache was half-updated, so every later request reads a value that never existed.
  • A counter was incremented but the work it counted never happened.
None of that appears in a log. The service keeps answering, and the wrong numbers spread. A restart costs you seconds. Corrupt data costs you a week, and you may not find out for months.
The correct use — log, then exit 
process.on('uncaughtException', (err) => {
  logger.fatal({ err }, 'uncaught exception');
  // give the log one tick to flush, then go
  setTimeout(() => process.exit(1), 100).unref();
});
The handler exists so you can record why, not so you can continue. Anything that restarts you — a container platform, systemd, pm2 — then gives you a fresh, correct process. Verified: an uncaught throw exits with code 1, even if you had set process.exitCode = 0.
Say it in the simplest words — the Feynman check

1 · In plain words Things go wrong in two ways. Somebody outside gave you something bad — that is normal, you deal with it and carry on.

Or you were wrong about something. Then you do not know what else you were wrong about. Carrying on means acting on beliefs you just proved false. Better to stop and start again from a known state.

2 · One analogy A pharmacist. A prescription with bad handwriting is normal: you refuse it and ask again. But noticing you may have mislabelled a bottle is different. You stop the whole counter, because you no longer know which bottles are right.

…and where the analogy breaks A pharmacist feels the difference and stops on instinct. Your program feels nothing. Both errors arrive at the same catch as the same shape of object, with no marking.

So nothing can infer the category for you. That is why the class with the flag exists. The worst case has no equivalent in a pharmacy. A Node process with an uncaughtException handler keeps serving customers after realising it mislabelled the bottle. The handler quietly cancelled the decision to stop.

3 · The sticking point People add uncaughtException to make the service more reliable. It does the opposite, and the output shows why. The process stays alive, at exit code 0.

Uptime is not the goal. Correctness is. A restart costs seconds and gives you a process you can trust. Continuing gives you a service that answers every request quickly, and some answers are wrong. No error anywhere tells you which ones.

Build it for real — an error taxonomy for the spine

Requirements:

  1. An AppError base class with code, status and isOperational.
  2. Named subclasses for the spine's real failures: ValidationError (400), NotFoundError (404), ConflictError (409), UpstreamError (503).
  3. Every deliberate failure throws one of those. Nothing throws a bare Error.
  4. One top-level handler: operational errors get week 21's error body, everything else logs and triggers week 27's shutdown.
  5. uncaughtException and unhandledRejection handlers that log and exit. Never continue.
  6. Config validated at boot. A missing required value crashes before the server listens.

Then prove the difference. Add two routes and watch what happens to the process:

# operational — the server must survive and answer
curl -s -o /dev/null -w "%{http_code}\n" -X POST localhost:3000/links -d 'not json'   # 400
curl -s localhost:3000/health                                                        # still 200

# programmer — the server must NOT survive
curl -s localhost:3000/boom      # route does: undefined.foo
curl -s localhost:3000/health    # connection refused — it exited, and that is correct
Requirement 6 is the one people skip, and it is the cheapest A missing DATABASE_URL discovered on the first request is an outage at 3am. The same mistake discovered at boot is a container that never starts, which the deploy catches and rolls back automatically. Move failures earlier and they get cheaper. This is the same reasoning as week 9's parse-before-run.

Scenario

A service has 100% uptime for six months. Then an audit finds that about 0.3% of orders have a total that does not match their line items. The logs are clean. The code has an uncaughtException handler that logs and continues.

Explain how the two facts are connected, and say why the clean logs are evidence for your theory rather than against it.

Remember this · the 20-second recap
  • Operational: an expected failure in a correct program. Handle it and carry on.
  • Programmer: a bug. Log it and crash, because unknown state is worse than a restart.
  • The test: did I anticipate this when I wrote the code?
  • The category is your intent, not a property of the error. Mark it yourself with a flag.
  • An uncaughtException handler keeps the process alive — verified, at exit code 0.
  • Use it to log and exit, never to continue. Uptime is not the goal; correctness is.
  • Wrap errors with { cause } — the original stack survives. Validate config at boot, because a failure that happens earlier is a cheaper failure.

If you remember one thing: a restart costs seconds and corrupt data costs a week. Crashing is the safe option, not the dramatic one.
