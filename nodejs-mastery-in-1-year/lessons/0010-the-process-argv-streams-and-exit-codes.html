The process — argv, streams and exit codes

How to write a program that behaves properly inside a shell, and one line that silently throws your output away.

coreWeek 10 of 52. This lesson builds one domain-expert ability: predict how it behaves in a case you have never seen. Week 10 in the plan · Glossary

Your win today: your program will work correctly inside a pipeline — right stream, right exit code, no lost output. You will also reproduce a bug yourself that silently deletes 99.9% of your output and leaves no error behind.
Where you are Week 9 was how Node finds your code. This week is how your program talks to the world outside it. Next week you package it; week 12 you ship it.

Start from the problem — what does a shell actually give you?

A shell runs your program and gives it exactly four things. Not more:

  1. A list of words — the command line, split up. In Node this is process.argv.
  2. Three open files — numbered 0, 1 and 2. Called stdin, stdout and stderr.
  3. A set of environment variables — process.env.
  4. One number back when you finish — the exit code.

That is the entire contract. A program is "well behaved" when it uses all four the way the shell expects. Most bad command-line tools break the same three rules, so take them one at a time.

Three of the four get a section below. The fourth is process.env. It is held back until week 27, where configuration and secrets have a real service to live in. For today, know only two things. It is a plain object of strings. A missing variable reads as undefined, not an error.

Why there are two output streams, not one

This looks like a historical accident. It is not. Derive it.

A shell lets you connect one program's output to the next program's input:

myTool data.csv | sort | head -20

For that to work, what leaves myTool must be only the data. If a progress message like Reading 400 rows… went down the same channel, sort would try to sort it. The friendly message would corrupt the data.

So you need a second channel that goes to the human instead of to the next program. That is stderr. The rule follows on its own, and it is not a style preference:

The rule

stdout is for the answer. stderr is for everything else: progress, warnings and errors. Anything you would delete if a machine were reading goes there.

Use this quick test on any line you print. If somebody piped this into another program, would this line be part of the data? If no, it goes to stderr.

Reading the command line without a library

process.argv is a plain array, and the first two entries are always the same:

// node rename.js --dry-run --name bob a.txt
process.argv[0]  // '/path/to/node'      — the runtime
process.argv[1]  // '/path/to/rename.js' — your script
process.argv.slice(2)  // ['--dry-run','--name','bob','a.txt'] — yours

Parsing that by hand is where the bugs live, so Node now ships a parser. util.parseArgs is built in — no dependency:

const { parseArgs } = require('node:util');

const { values, positionals } = parseArgs({
  options: {
    'dry-run': { type: 'boolean' },
    name:      { type: 'string' },
  },
  allowPositionals: true,
});

Run with --dry-run --name bob a.txt, that gives you exactly:

{"values":{"dry-run":true,"name":"bob"},"positionals":["a.txt"]}
Why start here and not with a library Libraries like commander and yargs are good, and you may well use one later. Start without one for a week, so you know what the library is doing for you. A dependency you can rebuild yourself is a choice. A dependency you cannot is a risk.

The line that silently deletes your output

Here is the part of this lesson that is worth the whole week. This is not a rumour — the numbers below came from running it.

big.js

const line = 'x'.repeat(200);
for (let i = 0; i < 300000; i++) console.log(i + ' ' + line);
process.exit(0);   // ← this line

Run it two ways. The reader is made slow on purpose, because a real one often is:

node big.js | (sleep 0.3; cat) | wc -l
// 320          ← with process.exit(0)

# now delete the process.exit line and run again
node big.js | (sleep 0.3; cat) | wc -l
// 300000       ← without it

320 lines out of 300,000 arrived. Over 99.9% of the output vanished. No error. No warning. Exit code 0, so every script around it believed the job succeeded.

Why it happens — and why it hides

Derive it from what you already know about the event loop.

When stdout is a terminal or a file, Node writes synchronously on Linux and macOS. That is a platform rule, not something you can derive. The bytes are gone by the time console.log returns.

When stdout is a pipe, Node on Linux and macOS writes asynchronously. The data is queued. The real writing happens later, on the event loop.

Windows is the other way round: pipes there are synchronous, terminals are not. This whole bug is a POSIX bug. Learn the rule, then check it with the one-liner below rather than trusting your memory.

You can confirm which one you have:

node -e "console.log(process.stdout._handle.constructor.name)" | cat
// Pipe

Now process.exit() does exactly what its name says: it ends the process immediately. It does not drain queues. It does not wait for the event loop. Every queued write is thrown away, with no message at all.

This is why the bug reaches production At small volume it looks fine — but the reason is not the one people give. The same script with 20,000 lines and a fast reader printed all 20,000, because cat emptied the pipe as fast as Node filled it, so Node's own queue never grew. Give those same 20,000 lines a slow reader and only 320 arrive — the same 320 as at 300,000 lines. That number is the size of the operating system's pipe buffer, about 64 KB. The bug appears when the reader is slower than the writer, which describes production and does not describe your laptop.
The fix is to stop calling it Set process.exitCode instead, and let the program end on its own. Node exits when there is no work left, and by then the queue has drained. 
process.exitCode = 1;   // good — a wish, honoured on the way out
process.exit(1);        // dangerous — an order, obeyed instantly
Keep process.exit() for the one case it is right: you must stop now and losing buffered output is acceptable.

The number you give back

The exit code is how the shell, CI, and every wrapper script learn whether you succeeded. Get it wrong and a failing job is reported as a pass.

You writeShell seesMeaning
nothing0Success. This is the default, so silence means "it worked".
process.exitCode = 33Your own failure code. Output still drains.
process.exit(4)4Same number, but the process stops immediately.
an uncaught throw1Node's generic failure. Fine, but it tells the caller nothing.

Those four rows were run and checked, not remembered. The dangerous default is the first row. A tool catches its own error and prints a message. Then it ends normally. It reports success while having done nothing.

Say it in the simplest words — the Feynman check

1 · In plain words Print to a screen and the letters are already gone. The print command has finished delivering them. Print into another program and they are not gone. They go into a waiting line. Something else delivers them a moment later. process.exit() stops your program that same instant. Anything still in the waiting line is thrown away, and nobody is told.

2 · One analogy Printing to the screen is handing a letter straight to the person. Printing into a pipe is dropping it in a postbox: it has left your hand, but it has not arrived. process.exit() is setting fire to your own outbox on your way out of the building.

…and where the analogy breaks A burnt postbox is obvious — there is smoke, and somebody complains. This failure is completely silent. There is no error and no warning. The exit code is still 0. So every script around yours is told the job succeeded.

And one more break, which explains the number 320. The postbox is not yours — it belongs to the operating system, and whatever reached it does get delivered. What burns is the pile still on your own desk, inside your process. That is why a little output survived and almost none of it did.

3 · The sticking point People read process.exit(0) as “finish now”. It does not mean finish. It means stop, and those are different words. Finishing would mean delivering what you already promised to deliver.

The confusion survives because the two behave identically on a laptop, where output is small and goes to a terminal. It only separates under load — which is the definition of a bug that reaches production.

4 · Now you explain it back

In two or three sentences, explain why process.exit(0) can lose output inside a pipeline. Then say why it never does when you run the program by hand. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — a tool that survives a pipeline

Write wordfreq.js. It counts word frequency. It must obey all four parts of the shell contract.

Requirements — every one of these is testable:

  1. Reads a file when given a path; reads stdin when the path is missing and input is piped in.
  2. Counts to stdout, one word count per line. Nothing else on stdout.
  3. Prints Read N lines… to stderr, so a pipeline never sees it.
  4. Supports --top N and --min-length N through util.parseArgs.
  5. Exits 0 on success, 1 on a bad argument, 2 when the file is missing — using process.exitCode, never process.exit().

The skeleton — fill in the middle yourself

#!/usr/bin/env node
const { parseArgs } = require('node:util');
const fs = require('node:fs');

let opts;
try {
  opts = parseArgs({
    options: { top: { type: 'string' }, 'min-length': { type: 'string' } },
    allowPositionals: true,
  });
} catch (err) {
  console.error('bad arguments:', err.message);  // stderr
  process.exitCode = 1;                          // not process.exit
  return;
}

const file = opts.positionals[0];
const input = file
  ? fs.createReadStream(file)
  : process.stdin;          // stdin is a Readable stream

// ... count words, then:
// console.log(word, n)          → the answer, stdout
// console.error('Read', n, 'lines') → the note, stderr
You have not been taught streams yet — here is the bridge Requirement 1 needs you to read from process.stdin, and a stream is week 15. Week 5 deliberately told you to skip for await…of until then, so you are not missing something you should have learned. Use this one line and treat it as a black box: 
const text = await new Response(input).text();
It works on a file stream and on process.stdin — verified on Node v24.14.0. It reads the whole input into memory before counting. That is fine for a book and completely wrong for a 4 GB log. Week 15 is where you learn why, and what to do instead. Knowing that this line has a limit is enough for today.

Now prove each requirement. A build with no proof is a build you hope works:

# 1 · works as a source in a pipeline
node wordfreq.js book.txt | sort -k2 -rn | head -5

# 2 · the note went to stderr, so the data stayed clean
node wordfreq.js book.txt 2>/dev/null | head -3

# 3 · works as a sink, reading stdin
cat book.txt | node wordfreq.js | head -3

# 4 · the exit code is honest
node wordfreq.js no-such-file.txt; echo "exit was $?"   # 2

# 5 · nothing is lost under a slow reader — the week's real test
node wordfreq.js big.txt | (sleep 0.3; cat) | wc -l
One test you must run in a real terminal process.stdout.isTTY is true when output goes to a terminal, and undefined when it is piped or captured. Use it to decide whether to print colour. Check it in your own terminal window — many tools that capture output will report undefined in both cases, which makes the test look broken when it is not.

Remember this · the 20-second recap
  • A shell gives your program four things: argv, three streams, env (week 27), and one number back.
  • stdout is the answer; stderr is everything else. Test: would a machine reading this want the line?
  • process.argv.slice(2) is your part. Parse it with the built-in util.parseArgs, not a dependency.
  • To a terminal or file, writes are synchronous. To a pipe, they are queued.
  • process.exit() discards that queue. Measured: 320 of 300,000 lines survived, with exit code 0.
  • It hides while the reader keeps up, so no queue ever builds. It appears the moment the reader falls behind.
  • Use process.exitCode = n and let Node leave on its own.

If you remember one thing: process.exit() means stop, not finish — and to a pipe those are very different.
