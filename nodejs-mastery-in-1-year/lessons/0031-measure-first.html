Measure first

A performance claim with no measurement behind it is an opinion. Learn the tools before you touch the code.

coreWeek 31 of 52. This lesson builds one domain-expert ability: debug a problem that has no ready answer online. Week 31 in the plan · Glossary

Your win today: a CPU profile of your own service, read without any tooling but Node. You will name the hot function from the raw file — 31 samples in one function, 22 in another — and know exactly where the time went.
Where you are Week 22 told you whether the CPU is the problem. This week tells you which function. Those are different questions and they need different tools.

Start from the problem — you cannot see time

A request takes 200 ms. Where did it go? You cannot look. So you have two honest options:

  • Instrument. Add timers around the code and record how long each part took. Accurate, and you only measure what you already suspected.
  • Sample. Interrupt the program many times a second and write down which function is running. You learn where time went without deciding in advance.
Why sampling wins for finding a bottleneck

Instrumenting can only confirm or deny a guess you already had. Sampling can surprise you, and the whole reason you are profiling is that your guess was wrong.

That is what a profiler is. It is not magic. It is a timer. About a thousand times a second it asks “what are you doing right now?” and keeps a tally. Functions that appear often were running often.

The whole tool is one flag

node --cpu-prof --cpu-prof-dir=./prof server.js

On exit, Node writes a .cpuprofile file. Verified on Node v24.14.0:

prof/CPU.20260828.150044.32055.0.001.cpuprofile   9195 bytes

You can open that in Chrome DevTools. But open it in a text editor first, once, because it is plain JSON and it will stop being magic:

{
  "nodes":   [ { "id": 1, "callFrame": { "functionName": "slowPath", "url": "..." } }, ... ],
  "samples": [ 1, 1, 4, 1, 7, 4, 1, ... ],       // which node was running, per tick
  "timeDeltas": [ 1021, 998, 1004, ... ]          // microseconds between ticks
}

That is it. A list of functions, and a list of which one was running at each tick. Counting the ticks is the entire analysis:

const p = JSON.parse(fs.readFileSync(profileFile));
const byId = new Map(p.nodes.map(n => [n.id, n]));
const tally = new Map();
for (const s of p.samples) {
  const name = byId.get(s).callFrame.functionName || '(anonymous)';
  tally.set(name, (tally.get(name) || 0) + 1);
}

The real output (Node v24.14.0):

    31 samples  pbkdf2Sync
    22 samples  slowPath
     1 samples  (program)
  total samples: 59

Two functions account for 53 of 59 samples — 90% of the CPU time. Nothing else is worth looking at until those two are dealt with.

Self time and total time are different questions

MeasureMeansUse it to find
Self timeTicks where this function was on top of the stackThe function actually burning CPU.
Total timeTicks where this function was anywhere on the stackWhich request path is expensive.
Sorting by the wrong one wastes an afternoon Sort by total and the top of your list is always main and your HTTP handler, because everything happens inside them. True, and useless. Sort by self to find the code to change; use total afterwards to find out who calls it.

Reading a flame graph

A flame graph is the same data drawn as boxes. Two rules and you can read any of them:

  • Width is time. A wide box was running for a long time. Nothing else about the width means anything.
  • Height is the call stack. A box sits on the function that called it. Height is not a problem — deep is normal.

So you are looking for wide plateaus, especially wide boxes with nothing on top. A wide box with nothing above it is self time: that function was running, not waiting for someone it called.

The x-axis is not time passing Frames are sorted alphabetically, not chronologically. A flame graph tells you where time went, never when. If you need the order of events, that is a trace, not a profile — a different tool answering a different question.
Say it in the simplest words — the Feynman check

1 · In plain words You cannot watch a program the way you watch a person. So instead you take a photograph a thousand times a second. Each photo shows what it was doing at that moment.

Afterwards you count the photos. Whatever appears in most of them is where the time went. You never measured anything directly, and you still get the answer.

2 · One analogy Walk the factory floor every minute and write down what each person is doing. That is how you learn where the day went. Nobody fills in a timesheet, and by the end of the day you know exactly where the hours went.

…and where the analogy breaks A factory walk-round would notice somebody waiting — standing by a machine, doing nothing. A CPU profiler does not. It only sees what is running.

Take a request that waits 190 ms of its 200 ms on a database. In a CPU profile it looks almost empty. You can stare at it and conclude “nothing is slow”. That is why week 22 comes first. A profiler answers “which function is burning CPU”. It is the wrong tool entirely if the answer is “none of them”.

3 · The sticking point People treat a profile as a list of slow functions, and start optimising from the top. But the top is usually sorted by total time, and the top of that list is always main.

Everything happens inside main, so it is 100% of the total time and 0% of the problem. Self time is the column that names code you can change. Sort by the wrong one and you rewrite a function that was only ever waiting for the one below it.

4 · Now you explain it back

In two or three sentences, explain the difference between self time and total time. Then say which one you sort by first. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — profile the spine, then fix one thing

Requirements:

  1. Load-test the spine under --cpu-prof and produce a profile.
  2. Write your own tally script. Do not use a GUI for this step — read the JSON yourself once.
  3. Name the top three functions by self samples, with their percentage.
  4. Write your prediction down before you look. Then compare, and record whether you were right.
  5. Change one thing. Re-profile. Report p50, p95 and p99 before and after.
  6. If it did not improve, keep the old code and write down what you learned.
# 1 · profile under load
node --cpu-prof --cpu-prof-dir=./prof spine.js &
autocannon -c 20 -d 30 http://localhost:3000/links
kill -TERM %1        # the profile is written on exit — week 27's handler matters here

# 3 · your tally
node tally.js prof/*.cpuprofile
Requirement 4 is the actual exercise Writing the prediction down first is not ceremony. It is the only way to find out whether your mental model of your own service is correct — and the answer is usually no. A profile that confirms what you already believed taught you nothing. The value is in the surprise, and you only get the surprise if you committed to a guess first.
Requirement 6 is the discipline Most optimisations do not help. Keeping a change that did not measure better, because you already wrote it, is how codebases get complicated for no reason. Reverting a change you spent an hour on is a skill, and it is easier when you decided the rule in advance.
Scenario

A colleague reports that a route is slow and proposes replacing JSON.parse with a faster library. They have not profiled.

Say what you would ask for before agreeing, what you expect the profile to show, and why JSON.parse is a suspicious first guess in particular.

Remember this · the 20-second recap
  • A profiler samples: it asks what is running about 1000 times a second and counts. It does not time anything.
  • Sampling can surprise you. Instrumenting can only confirm a guess you already had.
  • node --cpu-prof writes a .cpuprofile. It is plain JSON — read it once by hand.
  • Self time names the function to change. Total time names the path that is expensive.
  • Sorting by total puts main at the top: 100% of the time, 0% of the problem.
  • Flame graph: width is time, height is the stack, and the x-axis is not the clock.
  • A CPU profile cannot see waiting — an I/O-bound request looks almost empty in one. Predict before you look, and report p50, p95 and p99, never an average alone.

If you remember one thing: a profile that confirms what you already believed taught you nothing. Write the guess down first.
