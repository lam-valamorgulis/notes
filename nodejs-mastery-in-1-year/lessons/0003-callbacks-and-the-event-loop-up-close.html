Callbacks & the event loop, up close

Predict exactly when your code runs — the skill that separates confident Node devs from guessers.

Your win today: given a mix of ordinary code, setTimeout, setImmediate, Promise.then, and process.nextTick, you'll say the exact output order — and explain why. This is the most-tested Node.js interview topic, and after today it's just mechanics you can trace by hand.
Where you are Lesson 1: Node doesn't wait — it uses callbacks. Lesson 2: a callback is a function (a closure). Now: when, precisely, does each callback run? That answer is the event loop.

The call stack — one thing at a time

Your single thread has one call stack: a to-do list of function calls. Calling a function pushes it on top; returning pops it off. Only the function on top is running. Because there's one stack, only one thing runs at any instant.

function greet() { console.log('hi'); }
function start() { greet(); console.log('done'); }
start();
// stack: start → greet (runs, pops) → back in start → done → pops
// prints: hi, then done

Key rule: the event loop can only give you a new callback when the stack is empty. That's why a long synchronous task freezes everything — it never lets the stack empty, so no callback gets a turn. (That's the "never block the event loop" rule, now with a mechanism.)

So where do async callbacks go?

When you call setTimeout(fn, 0) or fs.readFile(path, fn), fn does not run now. Node registers it with the timer system or the OS and returns immediately. Later, when the timer fires or the file is ready, fn is placed on a queue. The event loop takes callbacks off the queue and pushes them onto the stack — but only once the stack is empty.

Two queues, not one: macrotasks and microtasks

Here's the part that trips people, and the part interviewers probe. There isn't one queue — there are two, with different priority:

  • Macrotask queue (also called the task/callback queue): setTimeout, setImmediate, and I/O callbacks.
  • Microtask queue: Promise callbacks (.then/.catch/.finally) and process.nextTick — where nextTick has even higher priority than promises.
The one rule that decides all ordering

After the current synchronous code finishes — and after every single macrotask — the event loop drains the entire microtask queue before running the next macrotask.

So the priority order is: (1) all synchronous code now → (2) all microtasks (nextTick before Promise) → (3) one macrotask → drain microtasks again → next macrotask, and so on.

The canonical example — trace it, don't guess

This exact shape appears in interviews constantly. Predict the order out loud, then check.

order.js

console.log('1: sync');

setTimeout(() => console.log('2: setTimeout'), 0);

Promise.resolve().then(() => console.log('3: promise'));

process.nextTick(() => console.log('4: nextTick'));

console.log('5: sync');

Output:

1: sync
5: sync
4: nextTick
3: promise
2: setTimeout

Trace: both console.logs are synchronous, so 1 and 5 run first. The stack is now empty, so microtasks drain — nextTick (4) before Promise (3). Only then does the single macrotask, the timer (2), get its turn. Every order question is just this rule applied.

The reliable rule people miss At the top level, setTimeout(fn,0) vs setImmediate(fn) order is not guaranteed. But inside an I/O callback, setImmediate always runs before setTimeout — because you're already past the poll (I/O) phase, and "check" (setImmediate) comes next. That's a favourite interview follow-up.

The event loop phases (the honest picture)

The loop isn't one queue — each turn passes through ordered phases. You don't need to memorise them, just know they exist and that microtasks drain between each:

  1. timers — setTimeout / setInterval callbacks whose time is up.
  2. pending callbacks — some deferred system callbacks.
  3. poll — wait for and run I/O callbacks (the main event, where most work happens).
  4. check — setImmediate callbacks.
  5. close — cleanup callbacks (e.g. a socket closing).

Build it for real — the order predictor

Prove the "setImmediate beats setTimeout inside I/O" rule yourself. Save as io-order.js and run it a few times with node io-order.js.

io-order.js

const fs = require('fs');

// Top level: order is NOT guaranteed — may flip between runs.
setTimeout(() => console.log('top: timeout'), 0);
setImmediate(() => console.log('top: immediate'));

// Inside an I/O callback: immediate ALWAYS wins.
fs.readFile(__filename, () => {
  setTimeout(() => console.log('io: timeout'), 0);
  setImmediate(() => console.log('io: immediate'));
});

Run it several times. The two top: lines may swap order between runs, but io: immediate will always print before io: timeout. You've just demonstrated the event loop phases with your own eyes.

Remember this · the Feynman summary
  • Your one thread has one call stack; a callback only runs when the stack is empty.
  • Async callbacks wait in queues. There are two: microtasks (process.nextTick, then Promise) and macrotasks (setTimeout, setImmediate, I/O).
  • The master rule: run all sync code, then drain all microtasks, then one macrotask, then drain microtasks again — repeat.
  • So order = sync → nextTick → Promise → timers/immediate.
  • Inside an I/O callback, setImmediate always beats setTimeout(0).
  • Too many process.nextTick calls can starve the loop so macrotasks (like new requests) never get a turn.

If you remember one thing: microtasks always cut in line before the next macrotask — sync, then microtasks, then one macrotask, repeat.

Sources: Node.js official documentation — "The Node.js Event Loop, Timers, and process.nextTick()"; "Don't Block the Event Loop". Microtask/macrotask behaviour follows the JavaScript job-queue model plus Node's libuv phases.
