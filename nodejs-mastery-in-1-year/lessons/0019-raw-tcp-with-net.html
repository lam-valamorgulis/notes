Raw TCP with net

You will rarely write raw TCP. Writing it once is how message boundaries stop being a mystery.

depthWeek 19 of 52. This lesson builds one domain-expert ability: explain a bug that only happens under load. Week 19 in the plan · Glossary

Your win today: two messages arriving as one string, on purpose — and the reason it works perfectly on your machine and breaks in production.
Why this week is marked depth You will almost never open a TCP socket by hand. But every framing bug you meet — in a database driver, a message broker, a websocket library — is this bug. One afternoon here makes all of them obvious. That is a good trade, and it is why the week exists.

Start from the problem — TCP has no messages

You send two things. You expect two things. That expectation has no basis:

What TCP actually promises

Every byte you send arrives, in order, exactly once. That is all. It says nothing about where one message ends and the next begins, because it has no idea you have messages.

TCP is a pipe for bytes. write() is not “send this message” — it is “add these bytes to the pipe”. Grouping is your problem, and the network is free to regroup as it likes.

Watch it happen — three measurements

A server that assumes one write gives one data event. Measured on Node v24.14.0:

c.write(JSON.stringify({ msg: 'hello' }));
c.write(JSON.stringify({ msg: 'world' }));

server got one chunk: "{\"msg\":\"hello\"}{\"msg\":\"world\"}"

Two writes, one event. JSON.parse on that string throws immediately, and the error will say something unhelpful about position 15.

Now the same two writes, 50 milliseconds apart:

server got one chunk: "{\"msg\":\"slow1\"}"
server got one chunk: "{\"msg\":\"slow2\"}"
This is why the bug reaches production Slow, it works. Fast, it breaks. In development you type one message at a time and everything is fine for months. Under load, messages arrive close together, get merged into one segment, and the parser fails on traffic that is completely valid.

A bug that only appears when you are busy is the worst kind. The conditions that cause it are the conditions where you can least afford to debug.

And it goes the other way too. One large write:

c2.write(Buffer.alloc(200000, 0x61));      // one write, 200 KB

one 200000-byte write arrived as 4 chunks, 200000 bytes total

So a single message can arrive in pieces, and several messages can arrive as one piece. Both directions, in the same connection. Any code that treats a data event as a message is wrong twice over.

The fix — say how long the message is, before you send it

If the pipe will not tell you where a message ends, put that information in the bytes. Four bytes of length, then that many bytes of body:

function encode(obj) {
  const body = Buffer.from(JSON.stringify(obj));
  const head = Buffer.alloc(4);
  head.writeUInt32BE(body.length);            // week 14's Buffer, doing real work
  return Buffer.concat([head, body]);
}

The decoder keeps a buffer and only acts when it has a whole message. Both waiting conditions matter:

function makeDecoder(onMessage) {
  let buf = Buffer.alloc(0);
  return (chunk) => {
    buf = Buffer.concat([buf, chunk]);
    for (;;) {
      if (buf.length < 4) return;                 // partial HEADER — wait
      const len = buf.readUInt32BE(0);
      if (buf.length < 4 + len) return;           // partial BODY — wait
      onMessage(JSON.parse(buf.subarray(4, 4 + len)));
      buf = buf.subarray(4 + len);                // keep the remainder
    }
  };
}

Tested against both failures at once. Three messages in one write, then two more split in the middle of a length header. Measured:

messages decoded in order: a, b, c, d, e
count: 5
The three details that make this correct The for(;;) loop, because one chunk may hold several messages — return after the first and the rest sit there until more data happens to arrive.

The partial header check. Two bytes of a four-byte length is a real case, and it is where hand-written decoders break.

Keeping the remainder. The leftover bytes are the start of the next message, not rubbish to discard.

Read the length before you trust it readUInt32BE can return 4 billion. If you allocate that, a stranger has just decided how much memory your process uses. Cap it — reject any frame longer than your limit and close the socket. This is week 20's body limit, at a lower layer and with the same reasoning.

What HTTP does about this, and why it matters

HTTP runs on TCP, so it has exactly this problem. It solves it twice:

MechanismHow the end is found
HeadersA delimiter — a blank line, \r\n\r\n
Body, usuallyA length — content-length
Body, streamingChunked encoding — a length before every chunk, then a zero

That is the same pair of choices you have: a delimiter, or a length. A delimiter is readable but needs escaping, since the terminator can appear in the data. A length needs no escaping but must be read carefully, which is the decoder above.

And it explains something from week 20. content-length is how the server knows the body has ended. A client that lies about it, or keeps sending, is attacking the framing itself. That is why you count the bytes you actually receive.

Say it in the simplest words — the Feynman check

1 · In plain words TCP promises that every byte you send arrives, in order, exactly once. It promises nothing at all about grouping, because it does not know you have messages.

So two things you sent can arrive as one, and one thing you sent can arrive as four. If you want message boundaries, you have to put them in the bytes yourself.

2 · One analogy Pouring two jugs of water into one pipe. Everything comes out, in order, and there is no line in the water showing where the first jug ended.

…and where the analogy breaks With water you would never expect a line. With a socket you get one most of the time, and that is what makes this dangerous.

I measured both. Two writes sent immediately arrived as a single chunk: {"msg":"hello"}{"msg":"world"}. The same two writes 50 ms apart arrived as two. So the naive code passes every test you write by hand, and fails once traffic gets busy. That is exactly when messages arrive close enough together to be merged.

3 · The sticking point People fix the merge and forget the split. A single 200 KB write arrived as 4 chunks. So a decoder that handles glued messages, but assumes each chunk starts a new one, is still broken.

The nastiest case is a chunk that ends inside the length header — two bytes of a four-byte number. That is why the decoder checks twice. First that it has a whole header, then that it has a whole body. Miss the first check and you read a length out of half a number.

4 · Now you explain it back

In 30 seconds, explain why two JSON messages arrived as one string. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — a TCP chat server

Requirements:

  1. A chat server with net. Several clients, messages broadcast to everyone else.
  2. Write the broken version first. One data event treated as one message.
  3. Send two messages with no gap and watch them glue. Keep that output — it is the evidence.
  4. Send one 200 KB message and watch it split. Keep that too.
  5. Add length-prefix framing. Handle a chunk holding several messages, and one ending mid-header.
  6. Cap the frame length and close the socket on anything larger. Test it with a lie.
  7. Write the decoder as a Transform stream from week 16, so it composes with pipeline.
Requirement 7 is where this connects back A framing decoder is a Transform: bytes in, objects out. Written that way it gets backpressure for free, and you will recognise the shape in every protocol library you read afterwards.
The drill — 30 seconds

“Two JSON messages arrived as one string.”

Explain the cause without saying “buffering”. Then answer the follow-up that always comes: “but it works in staging.” The answer to that one is in the 50 ms measurement.

Say it like an interviewer just asked

What this lesson left out on purpose Nagle's algorithm and setNoDelay control some of the merging you just saw, and are worth reading about. UDP keeps message boundaries and drops the delivery guarantee — the exact opposite trade. TLS sits on top of TCP with the same framing questions. Protocol buffers and MessagePack are what people use instead of JSON once the frame count is high. Websockets are a framing protocol over HTTP, and will now look familiar.

Remember this · the 20-second recap
  • TCP promises every byte, in order, exactly once — and nothing about grouping.
  • Measured: two fast writes arrived as one chunk. The same two, 50 ms apart, arrived as two.
  • That timing dependence is why the bug survives development and appears under load.
  • Measured: one 200 KB write arrived as 4 chunks. Messages merge and split.
  • Fix it with a length prefix — 4 bytes, then the body. The decoder must loop, check for a partial header as well as a partial body, and keep the remainder.
  • Cap the frame length, or a stranger's 4-byte number decides your memory use.
  • HTTP does both: a blank line ends the headers, content-length ends the body.

If you remember one thing: write() means “add these bytes to the pipe”, never “send this message”.
