Child processes and cluster

Use every core on the machine — and discover which line of your code was quietly assuming there was only one.

coreWeek 24 of 52. This lesson builds one domain-expert ability: predict how it behaves in a case you have never seen. Week 24 in the plan · Glossary

Your win today: the spine API running on every core. And a bug you create on purpose — the moment you cluster, your in-memory state stops working, and you will see exactly which line caused it.
Where you are Week 23 was one process, many threads. This is many processes. They solve different problems, and knowing which is which is the point of the week.

Start from the problem — one process uses one core

Your machine has ten cores. Verified with os.availableParallelism(). One Node process runs your JavaScript on one thread, so nine of them are idle.

Week 23 fixed that for one kind of work — a CPU-bound function you can hand to a thread. But a web server's problem is different. It is not one heavy function; it is thousands of light requests, and there is no single thing to move.

For that, you do not want another thread. You want another whole copy of your server, and the operating system to share the incoming connections between them.

The two tools, in one line each

Worker threads: one process, many threads, for one heavy job. Cluster: many processes, one per core, for many small requests.

How several processes share one port

Two programs cannot normally listen on port 3000. cluster gets round it by not letting the workers listen at all:

  1. The primary process creates the listening socket.
  2. It forks N workers, each a full copy of your program.
  3. When a worker calls listen(), cluster intercepts it. The worker does not open a port — it asks the primary for connections.
  4. The primary hands each accepted connection to a worker. On Linux and macOS the default is round-robin.
const cluster = require('node:cluster');
const os = require('node:os');

if (cluster.isPrimary) {
  const n = os.availableParallelism();
  for (let i = 0; i < n; i++) cluster.fork();

  cluster.on('exit', (worker, code) => {         // a worker died
    console.error(`worker ${worker.process.pid} exited (${code}) — replacing`);
    cluster.fork();
  });
} else {
  require('./server.js');                        // your normal server, unchanged
}

Your server code does not change at all. That is the appeal, and it is also the trap.

The bug you get for free

Fork two workers. Have each one increment a module-level counter and report it.

let counter = 0;        // module-level state
counter++;
process.send(counter);

The real output (Node v24.14.0):

worker reports counter = 1
worker reports counter = 1

Not 1 and 2. Each worker has its own memory. A fork is a separate process with a separate heap. Nothing in your code said “share this”, and nothing does.

Everything in memory is now wrong This is not a corner case. It breaks a specific list of things you almost certainly have:
  • Sessions in memory. A user logs in on worker 1 and is logged out on worker 3.
  • An in-memory cache. Ten copies, ten different answers, ten times the memory.
  • A rate limiter counting in a Map. Your limit of 100 is now effectively 1000.
  • Anything from week 21's in-memory store. The spine's links exist on one worker only.
None of these throw. They give wrong answers, intermittently, depending on which worker took the request.

That is why week 21 stored links in memory on purpose. It was correct for a single process, and this week is the lesson that collects the debt. The fix is week 40: state that is shared has to live outside the process.

Cluster, or several containers?

Most teams today run one Node process per container and let the orchestrator run N containers. That does the same job. So when is cluster the right answer?

clusterN containers
MemoryLower — one machine, shared OS page cacheHigher — N copies of everything
Restart on crashYou write it (cluster.on('exit'))The orchestrator does it
ScalingBounded by one machine's coresAcross machines
DeploysAll workers togetherRolling, one at a time
Best forOne box you own; a CPU-bound serviceAnything with an orchestrator
The honest recommendation If you already have Kubernetes or a similar platform, use it and skip cluster — two layers of process management is one too many. Learn cluster anyway, because it forces the shared-state bug into the open on your laptop, where it is cheap. Meeting it for the first time in production is a bad day.

child_process — the other three ways

FunctionUse it forWatch out
spawnA long-running program with streamed outputThe default. Arguments are an array, so no shell parsing.
execFileA short program whose whole output you wantBuffers the output. Set maxBuffer.
forkAnother Node script, with a message channelWhat cluster uses underneath.
execAvoid.Runs a shell string. Any user input in it is a command injection.
One rule that prevents a whole class of vulnerability exec('convert ' + filename) with a filename of a.jpg; rm -rf / runs both commands. spawn('convert', [filename]) cannot — the arguments never touch a shell, so a semicolon is just a character in a filename. Use spawn or execFile, and pass arguments as an array. This comes back in week 37.
Say it in the simplest words — the Feynman check

1 · In plain words Your program uses one core, and the machine has ten. So you run ten copies of the program and let the operating system share the incoming work between them.

Your code does not change. But each copy has its own memory. Anything you were remembering inside the program is now remembered ten separate times, differently.

2 · One analogy One shop counter becomes ten counters with one queue. Ten times the customers served, and no change to how any one assistant works.

…and where the analogy breaks Ten real assistants share one till and one stock room. These do not. Each has a private copy of everything. Its own till, its own stock list, its own memory of who just came in.

So a customer served by assistant 3 is a stranger to assistant 7. Nothing announces this. The shop looks identical from outside, and it simply gives the wrong answer sometimes, depending on which counter you reached.

3 · The sticking point People read “your code does not change” and hear “nothing changes”. The code does not change; its assumptions do.

Every place that kept something in memory silently became wrong. Sessions, caches, rate limits, counters, the whole of week 21's store. And none of it throws. It returns wrong answers, intermittently. That is the hardest kind of bug to trace, because the same request works on the next try.

Build it for real — cluster the spine, then find what broke

Requirements:

  1. A cluster.js that forks availableParallelism() workers and replaces any that dies.
  2. Every response carries an X-Worker-Pid header, so you can see which one answered.
  3. Prove all workers are serving: 100 requests should hit several different pids.
  4. Find the break. Create a link, then GET it repeatedly. It should 404 most of the time.
  5. Kill one worker with kill -9 under load, and prove no requests fail.
  6. Write down every piece of state in the spine that is now wrong. That list is week 40's job sheet.
# 3 · are all workers really serving?
for i in $(seq 1 100); do curl -sI localhost:3000/health | grep -i x-worker-pid; done | sort | uniq -c

# 4 · the break — create once, read many
curl -s -X POST localhost:3000/links -d '{"url":"https://example.com"}'
for i in $(seq 1 20); do curl -s -o /dev/null -w "%{http_code} " localhost:3000/links/abc123; done
# expect a mix of 200 and 404 — the link exists on ONE worker

# 5 · kill a worker under load and watch the error count
autocannon -c 20 -d 20 http://localhost:3000/health &
sleep 5; kill -9 $(pgrep -f "node server.js" | head -1)
What to hand in The mixed 200/404 output from step 4, and your list from step 6. That list is the honest inventory of what “stateless” really means, written by you about your own code.
Scenario

After moving to four instances, users report being randomly logged out. It happens roughly three times in four. Nothing was changed in the auth code, and no errors appear in the logs.

Say what the fraction tells you, name the cause, and give two fixes — one quick, one correct.

Say it like an interviewer just asked

What this lesson left out on purpose Sticky sessions — routing a user to the same worker every time — is the “quick fix” from the drill, and it is a trap worth knowing and avoiding, because it makes every worker a single point of failure. Zero-downtime reloads with cluster are real and fiddly; the orchestrator normally does it better. Sharing state properly is week 40 and week 41.

Remember this · the 20-second recap
  • Worker threads = one process, many threads, for one heavy job. Cluster = many processes, for many small requests.
  • The primary owns the listening socket and hands connections to workers. Your server code is unchanged.
  • Each worker has its own memory. Verified: two workers, both reporting counter = 1.
  • Sessions, caches, rate limits and in-memory stores all silently become wrong. Nothing throws.
  • Always handle cluster.on('exit') and fork a replacement.
  • If you already run an orchestrator, use N containers instead. Two layers of process management is one too many.
  • Use spawn or execFile with an argument array. exec takes a shell string and is a command injection.

If you remember one thing: clustering does not change your code — it changes what your code was allowed to assume.
