Process more data than the machine has RAM, in flat memory, and prove it with a graph.

coreWeek 17 of 52. This lesson builds one domain-expert ability: predict how it behaves in a case you have never seen. Week 17 in the plan · Glossary

Your win today: a tool that processes a file larger than your machine's memory and never grows past a flat line. Measured on a 191 MB file: 67 MB streaming against 657 MB with readFileSync.
This week assembles weeks 14 to 16 — and adds one thing Buffers and chunk boundaries from week 14. Backpressure from week 15. Transform and pipeline from week 16.

The one new idea is restartability. A job that runs for an hour will eventually be interrupted. A job you cannot resume is a job you run twice.

Start from the number that decides everything

Read a whole file into a string and your memory cost is the file size. Read it in chunks and your cost is one chunk, whatever the file size.

That is not a small saving. It is a different shape:

ApproachMemory for a 191 MB fileMemory for a 20 GB file
readFileSync657 MB (measured)The process is killed.
Streaming67 MB (measured)67 MB. Same number.

Note that 657 MB is more than three times the file. A JavaScript string is UTF-16, so ASCII text roughly doubles when decoded. The raw bytes are held at the same time. “It is only a 191 MB file” is not a safe thought.

The bug that ruins the first attempt

Week 14 taught that a chunk boundary can cut a character in half. The same cut also lands in the middle of a line, and that breaks records.

Take a CSV of 2000 rows and split each chunk on newlines, treating every piece as a row:

// WRONG — each chunk is treated as if it were whole
r.on('data', (c) => {
  for (const line of c.toString().split('\n')) {
    const cols = line.split(',');
    // ...
  }
});

The real output (Node v24.14.0, 64-byte chunks):

naive  -> malformed rows: 1093 | example: "3,c"

More than half the rows are damaged. The example is the row 3,customer-3,21 cut after two characters of the name. It still has commas in it, so it still parses. It is just wrong.

Why this is worse than a crash A broken row does not throw. It parses into something with the wrong number of columns, or the right number and wrong values. The job finishes, reports success, and writes bad data. Silent corruption at scale is the worst outcome in this whole course, and it is two lines of code away.

The fix — carry the remainder

Keep whatever came after the last newline, and put it in front of the next chunk:

let rest = '';
r.on('data', (c) => {
  const parts = (rest + c.toString()).split('\n');
  rest = parts.pop();            // the unfinished last piece — keep it
  for (const line of parts) handle(line);
});
r.on('end', () => { if (rest) handle(rest); });   // the final line

The real output:

carry  -> malformed rows: 0

That is the same shape as week 14's StringDecoder and week 16's flush. All three are the same idea: hold back the unfinished piece until the rest arrives. Once you see it once, you see it everywhere.

Do not write this by hand in real code node:readline does it for you, correctly, and handles \r\n too: 
const rl = readline.createInterface({ input, crlfDelay: Infinity });
for await (const line of rl) { /* one whole line, always */ }
Write it by hand once, this week, so you know what readline is protecting you from. Then use readline forever.
Say it in the simplest words — the Feynman check

1 · In plain words You can read a book two ways. Carry the whole book, or read one page and put it down. Carrying the whole book gets harder as the book gets bigger. Reading a page at a time costs the same for every book.

2 · One analogy Emptying a swimming pool. One way is to find a container as big as the pool. The other is a bucket you carry back and forth. The bucket takes longer, and it works for a pool of any size.

…and where the analogy breaks Water does not care where you cut it. Your data does. Fill a bucket from a pool and you get water. Fill a chunk from a file and you can get half a row.

That is the real difficulty and the analogy hides it completely. Streaming is not just “the same job with less memory”. It is the same job with the boundaries in the wrong places. Every unfinished piece has to be carried to the next bucket by hand.

3 · The sticking point People think the risk of streaming is running out of memory. It is not — that is the risk of not streaming.

The risk of streaming is silent corruption. A cut record still parses. It has commas in it. Nothing throws, the job reports success, and the wrong number reaches a report. Measured on a 2000-row file: 1093 damaged rows and zero errors.

4 · Now you explain it back

In two or three sentences, explain why processing a file in chunks can corrupt records. Then say what you carry between chunks to prevent it. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — bigcount

A tool that reads a log or CSV of any size and reports totals, in flat memory.

1 · Make a file bigger than you want to hold

node -e "
  const fs=require('fs');
  const w=fs.createWriteStream('huge.csv');
  w.write('id,name,amount\n');
  let i=0;
  (function pump(){
    while(i++ < 4000000){
      if(!w.write(\`\${i},customer-\${i%997},\${i%13*7}\n\`)) return w.once('drain',pump);
    }
    w.end();
  })();
  w.on('finish',()=>console.log((fs.statSync('huge.csv').size/1048576).toFixed(0),'MB'));
"

Note that the generator itself honours backpressure. Writing four million lines without that is week 15's bug, on the way in.

Requirements. Every one is testable:

  1. Reads the file with pipeline, never readFileSync.
  2. Splits lines correctly — zero malformed rows. Prove it by counting.
  3. Reports total rows, total amount, and the top 5 names by amount.
  4. Peak memory stays flat as the file grows. Print it at the end.
  5. Prints progress to stderr every 500,000 rows, so stdout stays clean data (week 10).
  6. Resumable. --from-line N skips the first N rows and carries on.

The shape

const { pipeline } = require('node:stream/promises');
const readline = require('node:readline');
const fs = require('node:fs');

const totals = new Map();
let rows = 0, sum = 0, peak = 0;

const rl = readline.createInterface({
  input: fs.createReadStream(file),
  crlfDelay: Infinity,
});

for await (const line of rl) {          // backpressure is the loop itself
  rows++;
  if (rows <= skip) continue;           // --from-line
  const [, name, amount] = line.split(',');
  // ...accumulate...
  if (rows % 500000 === 0) {
    const mb = process.memoryUsage().rss / 1048576;
    if (mb > peak) peak = mb;
    console.error(`${rows} rows, ${mb.toFixed(0)} MB`);    // stderr
  }
}
The requirement that will catch you Requirement 3 says top 5 names. There are 997 distinct names, so a Map is fine. Now imagine 40 million distinct names. Your accumulator is not flat any more — the file streams, but the totals do not. Streaming the input does not make a program constant-memory. The state you keep has to be bounded too, and that is the part people forget.

Prove every requirement

# 2 · zero malformed rows
node bigcount.js huge.csv 2>/dev/null | grep malformed        # 0

# 4 · flat memory — run on a file 4x bigger and compare
node bigcount.js huge.csv 2>&1 >/dev/null | tail -1

# 5 · stdout is clean data, so a pipeline can read it
node bigcount.js huge.csv 2>/dev/null | head -3

# 6 · resume gives the same answer as one whole run
node bigcount.js huge.csv --from-line 2000000

Then, for the graph: sample process.memoryUsage().rss every 500,000 rows, write the numbers to a file, and plot them. A flat line is the deliverable. A rising line means something in your accumulator grows with the input, and you should find it before moving on.

What to hand in The memory graph, and the two malformed-row counts — naive and carried. Those three artefacts are the whole of weeks 14 to 17 in one page.
Scenario

A nightly aggregation streams a 30 GB log and has worked for months. Traffic doubles. Now it is killed by the memory limit. The code still uses pipeline throughout, and nothing about the reading changed.

Say where the memory is going, why pipeline did not protect them, and what you would measure first.

What this lesson left out on purpose Parallel processing of one file — splitting by byte range across workers — is real and belongs with week 23, where there are workers to give it to. Compressed input is one more pipeline stage and needs no new idea.

Remember this · the 20-second recap
  • Reading a file whole costs the file size. Streaming costs one chunk, whatever the size.
  • Measured on 191 MB: 657 MB with readFileSync, 67 MB streaming.
  • A chunk boundary cuts records as well as characters. Measured: 1093 of 2000 rows damaged, with no error.
  • Fix it by carrying the remainder into the next chunk. Same idea as StringDecoder and flush.
  • In real code use node:readline with crlfDelay: Infinity. Write it by hand once, then never again.
  • Streaming the input is not enough. The state you accumulate must be bounded too.
  • A job that runs for an hour needs to be resumable, or you will run it twice.

If you remember one thing: the danger of streaming is not running out of memory. It is a cut record that still parses.
