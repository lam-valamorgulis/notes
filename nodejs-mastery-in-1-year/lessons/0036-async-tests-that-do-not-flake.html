Async tests that do not flake

A test that passes when it should fail is worse than no test. Here is how that happens.

coreWeek 36 of 52. This lesson builds one domain-expert ability: make a system behave the same way twice. Week 36 in the plan · Glossary

Your win today: you will write a test that shows a green tick while asserting something false. Then you will find the one line in the output that gives it away.
Where you are Week 35 said coverage measures execution, not verification. This week is the same disease, one level deeper: a test that runs, asserts, and still proves nothing.

Start from the problem — what makes a test lie?

Everything in this course since week 3 has been about one fact. Your code does not finish when the function returns. It finishes later, on a queue.

A test runner has to decide when your test is over. It cannot read your mind. So it uses a rule:

The rule the runner uses

The test is over when the function returns, or when the promise it returned settles. Anything your test starts but does not hand back is outside the test.

That is the whole bug. An assertion that runs after the test ended is an assertion the test never saw.

Watch a false assertion pass

Three tests. Two of them are wrong on purpose. Verified on Node v24.14.0:

test('A — assertion in a callback that nobody awaits', () => {
  setTimeout(() => {
    assert.strictEqual(1, 2);      // this is FALSE
  }, 10);
});                                 // the function returned. the test is over.

async function boom() { throw new Error('should fail the test'); }

test('B — forgot the await', () => {
  boom();                           // no await, no return
});

test('C — awaited properly', async () => {
  await assert.rejects(boom, /should fail/);
});

Now the output. Read the ticks first, then read the rest:

✔ A — assertion in a callback that nobody awaits (0.380042ms)
✔ B — forgot the await (0.083333ms)
✔ C — awaited properly (0.336750ms)

ℹ Error: Test "B — forgot the await" generated asynchronous activity after
  the test ended. This activity created the error "Error: should fail the test"
  and would have caused the test to fail, but instead triggered an
  unhandledRejection event.

ℹ Error: Test "A — assertion in a callback that nobody awaits" generated
  asynchronous activity after the test ended. ... "AssertionError: 1 !== 2"

✖ t36b.test.js (51.062458ms)
ℹ tests 4   ℹ pass 3   ℹ fail 1
Look at what actually failed Every named test has a ✔. 1 !== 2 is right there in the output, and test A still passed.

The ✖ is on the file. That is why tests 4 but only three were written — the file counts as the fourth. Node caught the escaped error and failed the run. But it could not blame a test, because that test was already over.

Node saves you here. Not every runner does, and not every escaped error lands in time. Do not rely on it. The lesson is the sentence Node printed: would have caused the test to fail.

The habit that removes this whole class of bug Return or await everything. If a line in a test starts work, the test must hold on to it. An async test that has no await in it is worth a second look, every time.

The second cause: real time

A test that waits for a real timer is slow and unreliable. A retry with a 60-second backoff cannot be tested by waiting 60 seconds. So do not wait. Move the clock.

test('fake clock fires a 60s timer instantly', (t) => {
  t.mock.timers.enable({ apis: ['setTimeout'] });
  let fired = false;
  setTimeout(() => { fired = true; }, 60_000);

  assert.strictEqual(fired, false);
  t.mock.timers.tick(60_000);        // move time forward by hand
  assert.strictEqual(fired, true);
});
✔ fake clock fires a 60s timer instantly (0.931ms)

Sixty seconds of behaviour, checked in under a millisecond. Date works the same way:

t.mock.timers.enable({ apis: ['Date'], now: 0 });
Date.now();            // 0
t.mock.timers.tick(5000);
Date.now();            // 5000
Why this beats a shorter timeout The tempting fix is to make the timeout configurable and set it to 5 ms in tests. That tests a different system — one with a 5 ms backoff. The fake clock tests the real 60-second value. You want the production number in the assertion.

The third cause: a sleep pretending to be a wait

This is the single most common flaky test in any codebase:

startTheJob();
await sleep(100);                       // "it'll be done by then"
assert.strictEqual(job.status, 'done');

It passes on your laptop. It fails on continuous integration, where the machine is slower and busy. Then someone changes 100 to 500 and the suite gets slower forever, and it still fails sometimes.

The fix is to wait for the thing, not for the clock:

// best — the code tells you when it is done
await startTheJob();
// or
await once(job, 'done');                // events/once, from week 18

// acceptable when you truly cannot observe it — poll, with a deadline
async function until(fn, ms = 2000) {
  const deadline = Date.now() + ms;
  while (Date.now() < deadline) {
    if (await fn()) return;
    await sleep(10);
  }
  throw new Error('condition never became true');
}

until is fast when the job is fast, and it fails with a real message when the job never finishes. A sleep is slow always and lies sometimes.

The fourth cause: tests that can see each other

You need to know exactly what runs at the same time as what. Measured, not assumed:

LevelDefaultMeasured
Tests inside one fileone at a time, in order1-start 1-end 2-start 2-end
Test filesparallel, separate processespids 40143 and 40144, both start at the same millisecond
Two 400 ms filesparallel464 ms total
Same two, --test-concurrency=1serial916 ms total

So the rule that matters: your test files run at the same time, in different processes. Anything outside the process is shared between them.

The things two test files fight over A hard-coded port. A database or a table. A file on disk, especially a fixture one test writes and another reads. An environment variable. A row with a fixed id.

All four produce the same symptom: passes alone, fails in the suite, or fails only sometimes. That symptom is a shared resource until proven otherwise.

The fixes follow from last week. Use listen(0) for a port the operating system picks. Use a unique name per test for anything on disk, and a fresh row rather than a fixed id. Then no two files can collide.

Mocks, and when to reach for one

test('mock.method records calls and restores after', (t) => {
  const svc = { save(x) { return 'real:' + x; } };
  t.mock.method(svc, 'save', (x) => 'fake:' + x);

  assert.strictEqual(svc.save('a'), 'fake:a');
  assert.strictEqual(svc.save.mock.callCount(), 1);
  assert.deepStrictEqual(svc.save.mock.calls[0].arguments, ['a']);
});

test('the mock was restored automatically', () => {
  const svc = { save(x) { return 'real:' + x; } };
  assert.strictEqual(svc.save('a'), 'real:a');       // ✔ — no leak
});

t.mock restores itself when the test ends. That matters. A mock that leaks into the next test is a flake that looks like a bug in that other test.

Mock the boundary, not your own code Mock the third-party HTTP call, the clock, the random number. Do not mock your own function to make your own test pass — at that point the test is checking that you wrote the mock correctly.
Say it in the simplest words — the Feynman check

1 · In plain words A test runner has to decide when your test is finished. It uses a simple rule. The test is over when the function returns, or when the promise you gave back settles.

So anything your test starts but does not hand back happens after the test. An assertion in there can be false and the test still shows a green tick. Nobody was watching by then.

2 · One analogy An exam invigilator who collects the papers at the bell. Whatever you write after the bell is not marked. It can be brilliant or wrong — it does not count, because the paper is already gone.

…and where the analogy breaks An invigilator sees you still writing and tells you to stop. Node partly does this too. It noticed the late error and failed the file, printing “would have caused the test to fail”.

But it could not fail the test, because that test was already marked as passed. So the analogy breaks in the direction that matters. The mark stays green, and the complaint appears elsewhere in the output, where nobody looks. Other runners do not complain at all.

3 · The sticking point People read a green tick as “the assertion passed”. It really means “nothing failed while I was watching”. Those are different claims, and an empty test satisfies the second one.

That is why a missing await is so dangerous. It does not break anything visibly. It quietly moves the check outside the window, and you keep the reassurance without the safety.

4 · Now you explain it back

In two or three sentences, explain this to a teammate. Their test passed, even though the assertion inside it was false. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — break a test, then fix it

Requirements:

  1. Write a test that shows ✔ while asserting 1 === 2. Keep it. Name it clearly.
  2. Find the line in the output that reveals it. Write down the exact wording.
  3. Fix it so the same assertion now fails the test. Both versions stay in the file, one skipped.
  4. Take the spine's retry or cleanup timer and test it with t.mock.timers. Assert on the production interval, not a shortened one.
  5. Replace every sleep in your suite with an awaited signal or the until helper.
  6. Run the suite ten times in a row. Any failure at all is a flake, not bad luck.
for i in $(seq 1 10); do node --test || echo "FLAKE on run $i"; done
If it flakes, do not retry it The industry answer is to mark it flaky and rerun it automatically. That converts a real race condition in your code into a slower test suite, and hides the bug.

A flaky test is usually telling the truth: the system really is non-deterministic. Find the shared thing. It is almost always a port, a row, a file, or a clock.

Diagnose from the symptom alone

A colleague says: “This test passes when I run the file on its own. It fails about one time in five when the whole suite runs. It never fails on my machine, only on continuous integration.”

Give the two most likely causes, and one command each that would confirm or clear them. You have every fact you need in this lesson.

Remember this · the 20-second recap
  • A test ends when the function returns or the returned promise settles. Everything else is outside it.
  • So a false assertion in a stray callback shows ✔. Verified: 1 !== 2 printed, test passed, and Node failed the file instead.
  • Return or await everything. An async test with no await deserves a second look.
  • t.mock.timers.tick(60_000) tests a 60-second timer in under a millisecond, at its real value.
  • Never sleep and hope. Await the signal, or poll with a deadline that fails loudly.
  • Test files run in parallel, in separate processes. Ports, rows, files and env vars are shared.
  • Never auto-retry a flake. It is usually telling the truth about a race in your code.

If you remember one thing: a green tick means “nothing failed while I was watching” — not “the assertion passed”.
