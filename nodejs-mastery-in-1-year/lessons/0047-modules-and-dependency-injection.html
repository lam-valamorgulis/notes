Modules and dependency injection

Understand what Nest is for before learning its syntax. Injection is the point; decorators are packaging.

coreWeek 47 of 52. This lesson builds one domain-expert ability: judge a framework by what it removes, not what it adds. Week 47 in the plan · Glossary

Your win today: a number for what dependency injection is worth. Swapping one dependency by hand costs one rebuild per level. With a container it costs one line, at any depth.
Where you are You have built the spine from raw http for 26 weeks. That was on purpose — you now know what a framework is doing for you. This module is about deciding whether that trade is worth making.

Start from the problem — who builds your objects?

Here is dependency injection, with no jargon at all:

The whole idea, in one sentence

An object does not build the things it needs. It is handed them. Something else decides what to hand it.

That is it. No decorators, no annotations, no framework. This is dependency injection:

// NOT injected — the service decides, and you cannot change it
class LinkService {
  constructor() { this.store = new PgLinkStore(); }
}

// injected — the caller decides
class LinkService {
  constructor(store) { this.store = store; }
}

The second version can be given a real store, a fake one, or one that fails on purpose. The first cannot, ever, without editing it. Everything else in this lesson is machinery for doing that at scale.

Wire it by hand first, and find where the pain is

A small chain: a controller uses a service, the service uses a store, a clock and a metrics counter. Wired by hand, the composition root is honest and readable:

function buildApp() {
  const store   = new PgLinkStore();
  const clock   = new Clock();
  const metrics = new Metrics();
  const service = new LinkService(store, clock, metrics);
  return new RedirectController(service);
}

Nothing wrong with that. It is five lines and you can read every one. The pain appears in a test, when you want a fake store:

const service    = new LinkService(new FakeStore(), new Clock(), new Metrics());
const controller = new RedirectController(service);      // rebuilt, just to reach the store

The controller has nothing to do with the store. It still has to be rebuilt, because it sits between you and the thing you wanted to change. Now measure how that scales:

Verified at depth 5 — swapping the leaf really does require rebuilding all five levels above it. The container version is one line whatever the depth:

const moduleRef = await Test.createTestingModule({ imports: [AppModule] })
  .overrideProvider(PgLinkStore).useClass(FakeStore)      // the entire swap
  .compile();

const controller = moduleRef.get(RedirectController);

This is the real argument, and it is a narrow one A container is a machine that knows how to build your object graph, so you can replace one node without touching the rest. That pays off when the graph is deep and you swap things often — which describes a test suite exactly.

On a three-class service you will not feel it. Anyone telling you Nest is always better is selling something.

What it costs — say this part out loud too

The hand-wired buildApp() has one enormous virtue: you can read it. Every construction, in order, in one place. Delete a line and something breaks immediately and obviously.

With a container that page does not exist. The graph is assembled from decorators spread across many files, at run time, by rules you have to know. When it goes wrong you get this. Measured on NestJS 12.0.1:

Nest can't resolve dependencies of the Svc (?). Please make sure that the
argument Clock at index [0] is available in the BadModule module.

Potential solutions:
- Is BadModule a valid NestJS module?
- If Clock is a provider, is it part of the current BadModule?
- If Clock is exported from a separate @Module, is that module imported within BadModule?
That is a good error message, and it is still the cost Nest names the class, the argument, the index and the module, then offers three fixes. It is genuinely excellent — and you need it, because the answer is no longer visible in the code.

Hand-wired, that failure is a missing argument at a construction you can see. This is the trade: less code to change, more machinery to understand. Anyone who claims a framework is free has not paid this bill yet.

How a provider is actually resolved

Follow the steps, because “magic” is just a lookup you have not read:

  1. Nest reads the constructor's parameter types, recorded by the compiler under emitDecoratorMetadata.
  2. For each type, it looks for a matching provider in the module that owns the class.
  3. Not there? It looks at what that module imports — and only at what those modules export.
  4. Found: it builds that provider first (recursively), then caches it. Providers are singletons per module scope by default.
  5. Not found anywhere: the error above.
The module boundary in one sentence A module says what it needs (imports) and what others may use (exports). Everything else in it is private. That is the buy: a real boundary you cannot accidentally reach through, which plain require never gives you.
Say it in the simplest words — the Feynman check

1 · In plain words An object does not build the things it needs. It is handed them, and something else decides what to hand it.

That one change lets you give a service a real database in production and a fake one in a test. The service itself never changes. A container is just a machine that does the handing, so you do not write it out by hand.

2 · One analogy A kitchen where ingredients are delivered rather than grown on site. The cook does not care where the eggs came from, so you can send different eggs without retraining the cook.

…and where the analogy breaks In a kitchen you can see the deliveries arrive. With a container the deliveries are arranged by rules in other files. No single page lists them.

Hand-wired, there is one function with every construction in it, in order, and you can read it in ten seconds. With a container that page does not exist. That is why Nest's error names the class, the argument, the index and the module, then suggests three fixes. The answer is no longer visible in the code.

3 · The sticking point People think the container is what gives them injection. It is not. Injection is the constructor taking its dependencies as arguments, and that works in plain JavaScript with no library at all.

The container only removes the wiring, and it earns its keep by how much wiring there is. Measured: swapping one leaf by hand costs one rebuild per level. That is 6 constructions at depth 5 and 11 at depth 10. The container costs one line at any depth. On a three-class service you will not feel it.

Build it for real — the same service twice

Requirements:

  1. Build a small service wired by hand, with one buildApp() composition root. Four or five classes, at least three levels deep.
  2. Build the same service again with Nest's container.
  3. Swap one leaf dependency for a fake in both. Count the lines that changed. That number is the lesson.
  4. Make the chain deeper and count again. Plot the two numbers if it helps.
  5. Break it on purpose: remove a provider from a module and read Nest's error properly.
  6. Trace one resolution by hand, in writing: constructor types → own providers → imports → exports → cache.
  7. Write both lists. What Nest made easier, and what it made harder. Neither list may be empty.
The drill

“Why NestJS and not Express?”

A feature list is the wrong answer. Give a real trade-off with a number on each side: what it removes, what it charges, and the size of team or codebase where the trade flips. Then name a project where you would not use it, and say why.

Say it like an interviewer just asked

What this lesson left out on purpose Custom providers — useValue, useFactory, injection tokens — are how you inject anything that is not a class, and you will need them for configuration. Injection scopes beyond the default singleton (request-scoped and transient) exist and have a real performance cost. Circular dependencies and forwardRef are a sign of a design problem more often than not. Dynamic modules are how configurable modules are built.

Remember this · the 20-second recap
  • Dependency injection is one idea: an object is handed what it needs instead of building it. No library required.
  • A container only removes the wiring. It earns its keep by how much wiring there is.
  • Measured: a hand swap costs one rebuild per level — 6 at depth 5, 11 at depth 10. The container costs 1 line, any depth.
  • The cost is real. No single page shows the object graph now. That is why Nest's resolution error must name the class, the argument, the index and the module.
  • Resolution order: constructor parameter types → the module's own providers → its imports → what those export → cache. Singletons by default.
  • A module declares what it needs and what others may use. Everything else is private — a boundary require never gives you.
  • Both lists must be non-empty. A framework that only made things easier is one you have not used long enough.

If you remember one thing: injection is the constructor argument — the container is only the machine that fills it in.
