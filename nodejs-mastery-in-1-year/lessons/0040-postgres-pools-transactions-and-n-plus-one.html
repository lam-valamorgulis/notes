Postgres — pools, transactions, and N+1

Most Node latency lives in the database. Learn the pool before you learn an ORM.

coreWeek 40 of 52. This lesson builds one domain-expert ability: find where the time actually goes when a service is slow. Week 40 in the plan · Glossary

Your win today: you will make a service where the queries are fast, the CPU is idle, and users still wait half a second. Then you will find the queue that did it.
Where you are The spine has kept its data in memory since week 21. That was on purpose — it kept the HTTP, concurrency and reliability lessons clean. Now it gets real persistence, and a new place for time to disappear.

Start from the problem — what is a connection?

A database connection is a TCP socket plus a session on the server. That session holds memory, a transaction state, and often a whole process on the Postgres side. It is expensive to make and it is not free to hold.

So you cannot open one per request. And you cannot share one, because a transaction on it belongs to whoever started it. That leaves one answer:

What a pool actually is

A small, fixed set of connections, and a queue of people waiting for one. It is the bounded-concurrency limiter from week 8, applied to sockets.

That is the whole idea, and it means the pool has the same failure mode as any queue. When the queue is long, the wait is long — and none of that wait appears in your query timings.

Watch a fast query become a slow request

Twenty requests arrive together. Each one needs a connection for 100 ms. Measured:

SetupTotal timeAverage waitWorst waitFailed
Pool of 20, query 100 ms103 ms0 ms0 ms0
Pool of 4, query 100 ms509 ms203 ms407 ms0
Pool of 4, query 500 ms2,511 ms1,004 ms2,008 ms0
Pool of 4, query 500 ms, 1 s connect timeout1,004 ms252 ms503 ms12 of 20
Row 2 is the one that ruins an afternoon The query still takes 100 ms. Your database dashboard is calm. Your query log says 100 ms. The user waited 507 ms, and 407 ms of that is not in any log you are reading.

This is why “the database is fine, it must be Node” is such a common wrong conclusion. The database is fine. The queue in front of it is not.

Row 3 shows the amplification. The query got 5x slower, and the worst wait got 5x worse on top of that. A queue does not add the extra time — it multiplies it across everyone still waiting.

Row 4 is the trade you get to choose. With connectionTimeoutMillis, 12 of 20 requests failed in one second instead of every request waiting two. That is usually the better outcome, and it is never the default.

Why connectionTimeoutMillis is not optional Without it, a slow database turns into an unbounded queue in your process. Requests pile up, memory grows, and your health check still passes because the event loop is idle. With it, you fail fast, return 503, and let the load balancer route around you.

This is week 28 again: an operational error you report is far better than an operational error you absorb.

The drill, answered by the table above

“The API hangs under load, but CPU is idle.”

Idle CPU means nothing is computing. So everything is waiting. The pool queue is the first suspect, and the check is one line: log pool.totalCount, pool.idleCount and pool.waitingCount every few seconds. A non-zero waitingCount ends the argument.

Transactions — and the one mistake everybody makes

A transaction is not on the pool. It is on one connection. That single fact is the source of the most common Postgres bug in Node code:

// BROKEN — three different connections, three separate transactions
await pool.query('BEGIN');
await pool.query('INSERT ...');      // probably a different connection
await pool.query('COMMIT');          // commits nothing you inserted

Each pool.query takes a connection, runs, and gives it back. Your BEGIN and your INSERT can land on different sessions. The right shape checks out one connection and keeps it:

const client = await pool.connect();
try {
  await client.query('BEGIN');
  const { rows } = await client.query(
    'INSERT INTO links(code, url) VALUES($1, $2) RETURNING id', [code, url]);
  await client.query('INSERT INTO audit(link_id) VALUES($1)', [rows[0].id]);
  await client.query('COMMIT');
} catch (err) {
  await client.query('ROLLBACK');     // the path people forget to test
  throw err;
} finally {
  client.release();                   // finally, ALWAYS. a leak here empties the pool
}

Rollback really does undo the work. Measured on PostgreSQL 18.3:

  inside the transaction : 101
  after rollback         : 100
The missing finally is a slow-motion outage A path that returns without release() loses one connection permanently. With a pool of 10, the tenth time that path runs your service stops answering — hours after the deploy, with no error and no crash, and every request waiting on waitingCount.

Let the database enforce what matters

The spine's rule from week 21 is that a code is unique. You could check with a SELECT first. That check is a lie under load: two requests can both read “free” before either writes.

A unique constraint cannot be raced. Measured:

create table links (..., code text not null unique, ...);

// insert a code that already exists:
  code       : 23505
  constraint : links_code_key
  message    : duplicate key value violates unique constraint "links_code_key"

23505 is the Postgres code for a unique violation. That is your 409, and now it is exact:

catch (err) {
  if (err.code === '23505' && err.constraint === 'links_code_key') {
    return conflict('code_taken');          // 409, the week 21 decision
  }
  throw err;                                 // anything else is not yours to swallow
}
Check err.constraint, not just err.code A table can have several unique constraints. Matching only 23505 means a duplicate on a different column also returns “code taken”, which sends the client to fix the wrong field.

N+1 — the bug that hides inside clean code

const users = await db.query('select id, name from users limit 100');
for (const u of users.rows) {
  u.links = await db.query('select code from links where user_id = $1', [u.id]);
}

It reads perfectly. It is 101 queries. Measured against PostgreSQL 18.3 with 200,000 rows:

ApproachQueriesTimePlus 1 ms network each way
The loop10022.3 ms122.3 ms
One query with = ANY($1)11.7 ms2.7 ms
Difference13.3x45.7x
Read the last column, not the middle one Those timings came from Postgres running in the same process, so the round trip was free. Add just 1 ms of network — a generous number for the same data centre — and the gap goes from 13x to 46x. On a database in another region, every one of those 100 round trips costs 20 ms or more.

N+1 is not mainly a database problem. It is a round-trip problem, and the fix is always the same: fetch the set in one query.

Turn on query logging and the shape is unmistakable — the same statement, a hundred times, with only the parameter changing. That is the whole detection method, and it is faster than any profiler.

Read a query plan, and learn what an index is worth

The same query, on 200,000 rows, before and after adding an index. Measured:

explain analyze select code from links where user_id = 777;

-- no index
Seq Scan on links  (cost=0.00..4166.00 rows=10) (actual time=0.105..13.822 rows=10)
  Filter: (user_id = 777)
  Rows Removed by Filter: 199990
  Buffers: shared hit=1666
Execution Time: 13.927 ms

-- after: create index links_user_id_idx on links(user_id);
Bitmap Heap Scan on links  (cost=4.37..42.17 rows=10) (actual time=0.091..0.106 rows=10)
  Recheck Cond: (user_id = 777)
  ->  Bitmap Index Scan on links_user_id_idx  (actual time=0.075..0.075 rows=10)
        Index Cond: (user_id = 777)
  Buffers: shared read=2
Execution Time: 0.130 ms

13.927 ms to 0.130 ms — 107 times faster. You do not need to read the whole plan to get value from it. Three lines tell you almost everything:

LineWhat it means
Seq ScanEvery row was read. Fine on a small table, fatal on a large one.
Rows Removed by Filter: 199990Work done and thrown away. This is the number to hate.
Index Scan / Bitmap Index ScanThe index was used.
actual timeWhat really happened. cost is only the planner's guess.
An index does not mean the index is used The same query on a 100-row table kept its Seq Scan after the index was created. The planner was right: reading 100 rows is cheaper than reading an index and then the rows.

So an index you added on a nearly-empty development database may do nothing, and prove nothing. Test query plans against realistic data volumes, or you are testing the wrong system entirely.

Say it in the simplest words — the Feynman check

1 · In plain words A database connection is expensive, so you keep a small fixed number of them and share. That means there is a queue: when all of them are busy, the next request waits.

The waiting happens before any query is sent, so it appears in no query log and no database dashboard. Your queries stay fast while your users get slow, and nothing in the obvious places explains it.

2 · One analogy Four checkouts in a shop. Each one still takes two minutes. Twenty people arrive at once, and the last person waits eight minutes for a two-minute checkout.

…and where the analogy breaks In a shop you can see the line. In a service the line is invisible. It is a list of promises inside your own process, and every part of your monitoring says things are healthy.

The CPU is idle, the event loop is free, the health check passes, and the query log reports 100 ms. Measured: a pool of 4 with 20 requests gave a worst wait of 407 ms. The query itself took 100 ms. You have to log pool.waitingCount on purpose, because nothing else will ever show you that queue.

3 · The sticking point People make the pool bigger. Sometimes that is right. Often it just moves the queue to the database. That has its own connection limit, and gets slower with every session it keeps alive.

The real question is why a connection is held so long. A 500 ms query made the worst wait 2,008 ms. Five times slower held the queue five times longer, on top of the slowdown itself. Fix the query, or fail fast with a connect timeout, before you raise the pool size.

4 · Now you explain it back

In three sentences, explain how every query can be fast and every request still slow. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — give the spine a database

Requirements:

  1. Move the spine's storage to Postgres with node-postgres. One pool for the whole process, created once — never per request.
  2. Set max and connectionTimeoutMillis explicitly, and write down why you chose each number.
  3. A unique constraint on code. Map 23505 plus the constraint name to your 409, and keep the week 35 test that proves it.
  4. One real transaction with a tested rollback path. Prove the row count returns to what it was.
  5. Log totalCount, idleCount and waitingCount every 5 seconds.
  6. Create an N+1 on purpose. See it in the query log, then fix it with one query, and record both timings.
  7. Run explain analyze on your slowest query, against realistic data volume. Add the index and record the before and after.
Do not reach for an ORM yet An ORM is a good tool that hides exactly the three things this week is about: how many queries ran, when a connection was held, and what the plan was. Learn to see them first. Then an ORM is a convenience rather than a blindfold — and you will be able to tell when it is generating an N+1 for you.

Remember this · the 20-second recap
  • A pool is N connections and a queue — week 8's bounded concurrency, applied to sockets.
  • Measured: pool of 4, 20 requests, a 100 ms query → 407 ms worst wait, invisible in every query log.
  • Log waitingCount. Idle CPU plus a hanging API means a queue, and this is the first one to check.
  • Set connectionTimeoutMillis. Measured: 12 of 20 failed in 1 s instead of everyone waiting 2 s.
  • A transaction lives on one client, never the pool, and release() goes in finally. A unique constraint cannot be raced: 23505 plus err.constraint is your 409.

If you remember one thing: your users spend that time waiting for a connection, and no query log records it.
