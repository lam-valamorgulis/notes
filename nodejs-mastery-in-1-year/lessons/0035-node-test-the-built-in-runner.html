Start from the problem — what is a test for?

Not “to check the code works”. You can check that by running it. A test earns its keep for one reason:

The only thing a test is really for

A test tells you when a future change breaks something you already decided was correct. It is a message to whoever edits this code next — usually you, having forgotten.

That reframes what to test. Not every line, and not the things you are confident about. The decisions — the ones somebody might undo without noticing they were decisions.

The runner is built in

There is nothing to install. Verified on Node v24.14.0:

const { test, describe, mock } = require('node:test');
const assert = require('node:assert');

describe('the built-in runner', () => {
  test('plain assertion', () => {
    assert.strictEqual(1 + 1, 2);
  });

  test('async test', async () => {              // just return a promise
    const v = await Promise.resolve(42);
    assert.strictEqual(v, 42);
  });
});
node --test a.test.js

Remember week 9: node:test is prefix-only. require('test') is MODULE_NOT_FOUND. That is not a typo people expect.

Why this matters more than it sounds A test framework used to be a dependency, a config file and a transpiler step. Now it is a flag. That removes the most common reason a project has no tests: the setup was the hard part, and the setup no longer exists.

Coverage, and what it does not mean

node --test --experimental-test-coverage

ℹ file      | line % | branch % | funcs % | uncovered lines
ℹ all files | 100.00 |   100.00 |  100.00 |

100% coverage. Now look at what that number actually claims:

Coverage measures execution, not verification A line is “covered” if a test ran it. Not if a test checked it. This passes with 100% coverage and tests nothing: 
test('creates a link', async () => {
  await createLink('https://example.com');    // every line ran
});                                            // nothing was asserted
So 90% coverage means “90% of lines were executed by something”. It is a floor, and a low one.

Use coverage the way it is actually useful: look at the uncovered lines column. Those are lines no test has ever run, so nobody knows whether they work. That list is worth reading. The percentage is not worth arguing about.

The number that means more than coverage Branch coverage, not line coverage. A line with an if is fully line-covered when only the true side ever ran. Your if (err.isOperational) from week 28 is exactly that shape, and the branch that crashes the process is the one nobody tests.
Say it in the simplest words — the Feynman check

1 · In plain words A test is not there to prove the code works today. You can see that by running it.

It is a note left for whoever changes this code next, saying “this behaviour was on purpose”. If they break it, the note shouts. Most of the time that person is you, months later, having forgotten why.

2 · One analogy A smoke alarm. It does nothing at all on a normal day. You are not paying for what it does today. You are paying for the one night it wakes you up.

…and where the analogy breaks A smoke alarm reacts to smoke, whatever caused it. A test only reacts to the exact thing you thought of.

So a house full of alarms can still burn down through a door nobody put one on. That is what a coverage number hides. It counts how many rooms have an alarm, not whether any is switched on. A test can run every line and check nothing at all, and coverage reports that as 100%.

3 · The sticking point People treat coverage as a score to raise. It measures execution, not verification. A line counts as covered if a test ran it, never if a test checked it.

So chasing 90% produces tests that call functions and assert nothing. The number goes up while the safety does not. The useful part of the report is the uncovered lines column, because those are lines nobody has ever run.

4 · Now you explain it back

In two or three sentences, explain how a test suite can have 100% coverage and still prove nothing. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — cover the spine's decisions

Requirements:

  1. Tests for the five rows in the table above. Start from DECISIONS.md, not from the code.
  2. Both an integration test (real HTTP against a server on port 0) and a unit test for validation.
  3. Every test asserts something. Grep your own tests for one with no assert.
  4. Run coverage. Read the uncovered lines column and write down what is in it.
  5. Pick the most dangerous uncovered line and test it. Say why you picked that one.
  6. The suite runs from a clean checkout with one command: node --test.

The integration shape — port 0 is the trick

test('duplicate code returns 409', async (t) => {
  const server = createServer();
  await new Promise(r => server.listen(0, r));      // 0 = any free port
  const port = server.address().port;
  t.after(() => server.close());                     // always cleans up

  const body = JSON.stringify({ url: 'https://a.test', code: 'abc' });
  await fetch(`http://localhost:${port}/links`, { method: 'POST', body });
  const second = await fetch(`http://localhost:${port}/links`, { method: 'POST', body });

  assert.strictEqual(second.status, 409);
  const json = await second.json();
  assert.strictEqual(json.error.code, 'code_taken');   // the stable code, not the message
});
Two details in there that stop this suite rotting listen(0) lets the operating system pick a free port. A hard-coded 3000 means two test files cannot run at once, and the suite fails on a machine where something else is on 3000.

Assert on json.error.code, not the message. Week 21 said clients must branch on the code and never the wording. A test is a client — assert on the message and you have made your own error text impossible to improve.

What to hand in The test file, the coverage output, and one line saying which uncovered line you chose and why. That last one is the judgement being practised.

Remember this · the 20-second recap
  • A test exists to tell you when a future change breaks a decision you already made.
  • So test the decisions, not the lines. DECISIONS.md is your list.
  • node --test is built in. No dependency, no config. It is node:test — the prefix is required.
  • Coverage measures execution, not verification. A test with no assertion still counts as covered.
  • Read the uncovered lines column. Do not argue about the percentage.
  • Branch coverage beats line coverage. The untested branch is usually the error path.
  • listen(0) for a free port, and assert on the error code, never the message.

If you remember one thing: coverage counts the rooms with an alarm, never whether one is switched on.
