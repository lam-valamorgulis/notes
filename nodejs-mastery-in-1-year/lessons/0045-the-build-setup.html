The build setup

Mostly a one-time cost. But a stack trace pointing at compiled JavaScript wastes hours.

depthWeek 45 of 52. This lesson builds one domain-expert ability: make the tooling tell you the truth about where an error happened. Week 45 in the plan · Glossary

Your win today: you will turn on source maps, watch the stack trace stay wrong, and find the flag nobody mentions.
Why this week is marked depth You configure this once and then never think about it again. It is here because the failure mode is expensive and silent: everything works, and every error report points at the wrong file for the life of the project.

Start from the problem — Node does not run your code

You write src/lib.ts. Node runs dist/lib.js. Those are different files with different line numbers, and Node has never heard of the first one.

What a build actually creates

A second copy of your program. Everything at run time — stack traces, breakpoints, coverage — describes that copy, not the one you edit.

So an error report reads like this. Measured on Node v24.14.0:

Error: the real error, thrown on this line
    at boom (…/dist/lib.js:4:11)
    at boom (…/dist/lib.js:3:16)
    at boom (…/dist/lib.js:3:16)

dist/lib.js:4. To act on that you must open a generated file and find line 4. Then work out which line you wrote produced it. At 3am, with a production incident, that is minutes you do not have.

Source maps — and the step everybody misses

A source map is a file saying “line 4 of the output came from line 3 of the input”. Turn it on:

"sourceMap": true

Rebuild, run again, and measured:

    at boom (…/dist/lib.js:4:11)      // …exactly the same.
The map was generated. Node just did not read it. dist/lib.js.map existed, and dist/lib.js ended with //# sourceMappingURL=lib.js.map. Everything was in place.

Node does not use source maps unless you ask it to, because resolving them costs work on every stack trace. Generating the map and using the map are two separate decisions, and only one of them is in tsconfig.json.

node --enable-source-maps dist/main.js

Error: the real error, thrown on this line
    at boom (…/src/lib.ts:3:9)
    at boom (…/src/lib.ts:2:25)
    at boom (…/src/lib.ts:2:25)

src/lib.ts:3 — the line you wrote, in the file you wrote. Line 3 is the throw, and line 2 is the recursive call. The whole trace is now readable.

In production, use the environment variable NODE_OPTIONS=--enable-source-maps works identically and needs no change to your start command — verified. That matters when the process is launched by a container image, a process manager, or a platform you do not control.

moduleResolution — it decides when you find the bug

This setting tells TypeScript how to work out what an import refers to. Picking the wrong value does not break the build. It moves the failure to production.

The same missing extension, under two settings. Measured:

import { boom } from './lib';         // no .js — legal in TypeScript, illegal in Node ESM

// moduleResolution: "nodenext"
src/main.ts(1,22): error TS2835: Relative import paths need explicit file extensions
  in ECMAScript imports when '--moduleResolution' is 'node16' or 'nodenext'.
  Did you mean './lib.js'?

// moduleResolution: "bundler"
(compiles clean)

// …then, at run time:
Error [ERR_MODULE_NOT_FOUND]: Cannot find module '…/dist/lib'
  code: 'ERR_MODULE_NOT_FOUND'
Same code, same bug, two very different afternoons nodenext names the file, the line, the reason and the fix, before anything runs. bundler compiles happily and hands you a crash on start-up.

So the rule is simple: if Node runs the output, use nodenext. bundler is correct only when a bundler will rewrite the imports for you, and a Node service has no bundler.

A change worth knowing about On TypeScript 7.0.2 the old node10 value is gone: error TS5108: Option 'moduleResolution=node10' has been removed. If you copy a tsconfig.json from an old blog post, that is the error you will get.

The other module error, and it reads strangely

Compile to CommonJS inside a package marked "type": "module", and Node treats the output as an ES module:

ReferenceError: exports is not defined in ES module scope

Nothing about that message mentions your configuration, which is why it costs people an hour. It means the compiler and the package disagree about what kind of module this is. The two settings must match:

package.jsontsconfig.jsonOutput
"type": "module""module": "nodenext"ES modules — import at run time
no type field"module": "commonjs"CommonJS — require at run time
"type": "module""module": "commonjs"exports is not defined

This is week 9's rule, now with a build in the middle. The .js extension plus the type field decide, and TypeScript must be told the same thing separately.

Type checking and transpiling are two different jobs

This surprises people, so here is the proof rather than the claim. A file that cannot possibly type-check:

const n: number = "this is definitely not a number";
console.log('but it RAN, and printed:', n);

// tsc --noEmit
src/broken.ts(1,7): error TS2322: Type 'string' is not assignable to type 'number'.

// tsx src/broken.ts
but it RAN, and printed: this is definitely not a number
Why they can be separated at all Transpiling one file needs only that file — delete the types, emit JavaScript, done. Type checking needs every file the program can reach, because a type may be defined anywhere.

That is why a runner like tsx starts instantly without understanding your program. It is also why the type check belongs in a separate command.

So run them separately, and put each where it belongs:

"scripts": {
  "dev":        "tsx watch src/main.ts",              // no build step at all
  "typecheck":  "tsc --noEmit",                        // the real check — CI runs this
  "build":      "tsc",                                 // check AND emit, for production
  "start":      "node --enable-source-maps dist/main.js"
}
The failure this arrangement invites tsx ignores type errors, so a broken type can sit in your branch all day while everything appears to work. The type check must be a CI step, not something you remember to run. Week 38's workflow already has a place for it.

And tsx has one more benefit worth naming: it applies source maps automatically. The stack trace above pointed at src/lib.ts:3:9 in development with no flag and no build.

Say it in the simplest words — the Feynman check

1 · In plain words Node never runs the file you wrote. It runs a second copy that a compiler produced, with different line numbers. It has never heard of your original.

So every stack trace describes the copy. A source map is a small file that translates back. It says which line of the output came from which line of the input.

2 · One analogy A translated book with a table matching each page to the original's page. The table is useless unless the reader knows to look at it.

…and where the analogy breaks A reader who ignores the table still notices they have the wrong page. Node does not. It prints a confident, well-formatted stack trace pointing at a file you never wrote, and nothing indicates anything is missing.

I measured this. With "sourceMap": true, the .map file existed and the //# sourceMappingURL comment was in the output — and the trace still said dist/lib.js:4:11. Only node --enable-source-maps changed it to src/lib.ts:3:9. Generating a map and using one are two separate decisions, and only one of them lives in tsconfig.json.

3 · The sticking point People think moduleResolution is a detail. It decides when you find out about a broken import. The same missing .js extension produced TS2835 at compile time under nodenext, naming the fix. Under bundler it compiled completely clean, then crashed on start-up with ERR_MODULE_NOT_FOUND.

Same code, same bug, two very different afternoons. If Node runs the output, use nodenext. bundler is right only when a bundler rewrites the imports, and a Node service has none.

4 · Now you explain it back

In three sentences, explain why turning on source maps did not fix the stack trace. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — a setup that tells the truth

Requirements:

  1. A tsconfig.json for Node ESM: "module": "nodenext", "moduleResolution": "nodenext", "strict": true, "sourceMap": true.
  2. "type": "module" in package.json, matching. Break the match on purpose once and read the error.
  3. tsx watch for development. No build step in the loop.
  4. tsc for production, and tsc --noEmit as a separate command that CI runs.
  5. Throw an error on purpose from production code and read the trace. If it names a .js file, you are not finished.
  6. Add --enable-source-maps, or NODE_OPTIONS, and check the same trace again.
  7. Drop the .js from one import. Confirm nodenext catches it before anything runs.
  8. Ship the .map files with your build, or step 6 does nothing in production.
Requirement 8 is quietly easy to miss A Docker build that copies only dist/**/*.js, or a bundler configured to drop maps, leaves you with the flag enabled and no maps to read. Everything looks configured and the traces are wrong anyway — the exact failure this whole lesson is about, one layer further out.
The drill

“It compiles but crashes at run time with a module error. Name two causes.”

You have both, measured. Say the error each one produces, and then say which moduleResolution value would have caught the first at compile time. The follow-up is “so why would anyone use bundler?” — and there is a good answer.

Say it like an interviewer just asked

What this lesson left out on purpose Node's own type stripping lets recent versions run .ts files directly, and it is moving fast enough to be worth checking against your version rather than a blog post. Project references matter in a monorepo. esbuild and swc are the transpilers underneath most fast tooling. Bundling a server is sometimes worth it for start-up time and image size. Path aliases are convenient and need matching configuration in three places, which is its own small trap.
