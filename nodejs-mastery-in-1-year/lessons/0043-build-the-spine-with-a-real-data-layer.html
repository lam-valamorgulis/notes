Build — the spine with a real data layer

Postgres, a cache and a queue in one service. Then take each one down while load is running.

coreWeek 43 of 52. This lesson builds one domain-expert ability: say what your service does when a dependency dies, and prove it. Week 43 in the plan · Glossary

Your win today: a table with a row for every dependency, saying exactly what happens when it dies. Most engineers cannot produce that for a service they have run for two years.
Where you are Three weeks gave you three pieces separately. This week runs them together and then breaks them one at a time, because a dependency you have never seen fail is a dependency whose failure behaviour you are guessing at.

Start from the problem — which dependencies are actually required?

Every service has a list, and almost nobody writes it down. Yet each dependency is in one of two categories, and the difference decides how your service should behave:

KindWhen it diesIn the spine
RequiredYou cannot answer. Say so clearly and fast: 503.Postgres
OptionalYou answer anyway, slower or with less. Never fail.Redis, the queue
The rule that follows

An optional dependency that can fail your request is a bug. A required one that fails slowly instead of quickly is also a bug. Both are only visible if you actually turn them off.

Four things in that table are worth stopping on. Three of them surprised me while measuring.

1. The cache is the entire performance story

Warm 14 ms, cold 70 ms. A five-fold difference from one thing being warm. Any load test that starts with a warm cache measures the wrong system. It is not the one you have on the morning after a deploy.

2. A cold cache is slower than no cache

Cold with Redis: 70 ms. Redis switched off entirely: 39 ms. Adding a cache made the first request slower, because a miss costs a lookup, the database, and a write back.

What that means for a deploy Restart your service and it is briefly worse than a service with no cache at all — and that is the exact moment traffic arrives at a cold instance. Combine it with the stampede from week 41 and you have the standard deploy-time latency spike, fully explained.

3. Optional really is optional

Redis down: 60 out of 60 succeeded. Queue down: same. Both down: same. That is what a correctly built optional dependency looks like, and you cannot claim it without the row.

4. The warm cache hid a total database outage

This is the row that matters most. Postgres was completely down, and every request returned 302. Your dashboards are green. Your health check passes. The service is broken and looks perfect.

The most dangerous row in the table A cache that serves through an outage is a real benefit and a real hazard. Traffic on cached keys is fine; the first request for anything else gets a 503. So the outage is invisible until it is partial, and by then nobody connects the two.

The fix is not to remove the cache. It is that your health check must touch Postgres, so the service reports unhealthy even while it is still answering. Serving traffic and being healthy are different claims.

Make degradation visible

If a request was served in a degraded way, say so. One response header costs nothing and turns an invisible state into a graph:

res.writeHead(302, {
  location: url,
  'x-degraded': degraded.join(',') || 'none'      // cache-read,cache-write,queue
});

Now “Redis has been down for two hours and nobody noticed” becomes a line on a dashboard. The same information belongs in your structured logs and in a counter you can alert on.

The shape of every optional dependency call Try it, catch it, record that you degraded, carry on. Never let the catch be empty — an empty catch is how a dependency dies silently for a fortnight. 
try { await cacheSet(k, v); }
catch (e) { degraded.push('cache-write'); metrics.degraded.inc({ dep: 'redis' }); }

The failure that is not covered by any of this

Every row above used a dependency that failed immediately — connection refused. The harder case is a dependency that is slow, and it is far more common.

A Redis that answers in 5 seconds is worse than a Redis that is down. Down, you skip it in a millisecond. Slow, you wait — for an optional dependency you did not need.

Every optional call needs its own timeout Without one, “optional” is only true for one failure mode. Set a cache timeout far below your response budget — a cache that takes longer than the database is worth nothing.

The same applies to Postgres, where the timeout is connectionTimeoutMillis from week 40. Measured there: 12 of 20 requests failed in one second, instead of every request waiting two.

Say it in the simplest words — the Feynman check

1 · In plain words Every service depends on other things. Each one is either required or optional. Required means you cannot answer at all without it. Optional means you can still answer, just slower or with less.

You have to decide which is which, and then prove the service behaves that way. The only way to prove it is to turn each one off while traffic is running.

2 · One analogy A shop needs its till to take money. It does not need the music playing. If the speakers break you keep selling; if the till breaks you put a sign on the door.

…and where the analogy breaks Broken speakers are obvious. A broken optional dependency is silent. The code that hides it is an empty catch block, and it hides the failure perfectly.

Worse, the analogy misses the row that surprised me most. With a warm cache, Postgres was completely down and all 60 requests still returned 302. That is a shop with a broken till, selling from memorised prices. It works until the first item nobody memorised — and by then nobody links that 503 to the database.

3 · The sticking point People treat “it still works when Redis is down” as the finish line. It is only true for one failure mode: Redis being gone. A Redis that answers in five seconds is worse than one that is down.

Down, you skip it in a millisecond. Slow, you wait five seconds for something you did not need. So optional is not a property of your architecture diagram. It is a property of having set a timeout on every optional call.

4 · Now you explain it back

In three sentences, explain the danger of a service that keeps working during a database outage. Say why it can be in more trouble than one returning 503. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — run all three, then break all three

Requirements:

  1. Postgres, Redis and the queue running together in the spine, under load from autocannon.
  2. An x-degraded header, a log line, and a counter for every degraded path.
  3. A timeout on every optional call, set below your response budget. Write the numbers down.
  4. A health check that touches Postgres, so it can report unhealthy while still serving cached traffic.
  5. Kill each dependency in turn, with load running. Record status codes, latency and what degraded. That table is the deliverable.
  6. Run the Postgres row twice: once with a cold cache, once warm. Explain the difference in one sentence.
  7. Add a slow dependency, not just a dead one. Put 5 seconds of delay into Redis and see whether “optional” survives it.
  8. Draw the dependency diagram from memory, then check it against the code. What you left out is what you do not really know.
Requirement 8 is the one that pays off in interviews Drawing it from memory, then diffing against reality, finds the parts you have been carrying as a vague feeling. Those are exactly the parts that collapse when somebody asks a follow-up question.
The drill — five minutes at a whiteboard

“Walk me through a request, from socket to database and back.”

Start at accept(), not at your route handler. Name every queue the request waits in — the event loop, the pool, and the cache lookup. Say where the response bytes go when the client is slow to read, which is week 15. Finish with which dependency you would remove first if you had to simplify, and why.

Say it like an interviewer just asked

What this lesson left out on purpose Circuit breakers are the standard next step once you have timeouts, and they are worth learning properly. Bulkheads — separate pools per dependency so one cannot starve another — are the same idea for resources. Chaos engineering is this week's exercise made continuous and automatic. Distributed tracing is how you see a request across services rather than inside one. Read replicas and failover change what “Postgres is down” even means.
