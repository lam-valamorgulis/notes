First principles — concurrency is not parallelism

These two words get mixed up, and the difference is a great interview answer.

  • Parallelism = literally doing things at the same instant, on multiple CPU cores. That needs multiple threads or processes (weeks 22–25).
  • Concurrency = many tasks in progress at once, taking turns on one worker. One thread, many jobs "still running."

From weeks 1–4 you know Node's single thread hands slow I/O to the OS and stays free. So it can have hundreds of network requests running at once. That is concurrency, even though your JavaScript runs on one thread.

You do not need parallelism to fetch 300 URLs together. You need concurrency, and the combinators below are how you express it.

Say this one out loud

Concurrency is dealing with many things at once (one thread, many I/O operations still running). Parallelism is doing many things at the same instant (many cores). Node gives you huge concurrency on one thread for free; parallelism needs worker threads or cluster.

The four combinators — pick by what "done" means

Each takes an array of promises and returns one promise. They differ only in when they settle and how they treat failure.

CombinatorSettles when…On failureUse it when…
Promise.allall fulfilfail-fast: rejects the instant any one rejectsyou need every result and any failure ruins the batch
Promise.allSettledall settlenever rejects; each item reports fulfilled or rejectedyou want partial results — some may fail and that's OK
Promise.racethe first one settlesthe first to settle wins, even if it's a rejectionpicking a winner between two racers. Not a real timeout — racing stops you waiting, it does not stop the request. See week 8.
Promise.anythe first one fulfilsignores rejections; if all fail it rejects with an AggregateError, whose .errors holds every reasonredundancy ("first mirror to answer wins")

Promise.all returns results in input order, not finish order. That is why it is the default for "fetch these three things and use all of them":

const [user, orders, prefs] = await Promise.all([
  getUser(id), getOrders(id), getPrefs(id),
]);   // all three run concurrently; array order matches input order
The all vs allSettled trap (they will ask this) Promise.all is fail-fast: one rejection rejects the whole call and you lose the results that did succeed. If you're fetching 300 URLs and one connection fails, all throws away the other 299. Careful: fetch does not reject on a 404 — it resolves with res.ok === false, and you have to throw yourself. When some failures are acceptable and you want every outcome, use allSettled and inspect each item's status. 
const results = await Promise.allSettled(urls.map(fetchJson));
const ok   = results.filter((r) => r.status === 'fulfilled').map((r) => r.value);
const bad  = results.filter((r) => r.status === 'rejected').map((r) => r.reason);
// you keep the 299 good ones AND a list of the failures

The problem Promise.all hides — the flood

Here's the trap that separates junior from senior. This looks harmless:

const results = await Promise.all(urls.map((u) => fetch(u)));   // 500 URLs?

urls.map(u => fetch(u)) starts every request immediately. With 500 URLs, that's 500 connections opening in the same tick. The consequences are real and bad:

  • the target server rate-limits you (HTTP 429) or bans your IP;
  • you exhaust file descriptors / sockets and get EMFILE or ECONNRESET;
  • memory spikes holding 500 still-running responses;
  • everything gets slower, not faster — you've built a denial-of-service against yourself.

The fix is a concurrency limit. Process the jobs so at most N run at any moment. Think of a pool of N workers pulling jobs from a shared queue.

Build the concurrency-limited runner from scratch

This is the pattern to own. The idea: start N "runners." Each runner loops — grab the next job index, do it, repeat — until the jobs run out. Because JavaScript is single-threaded, i = next++ can't be interrupted, so no two runners ever grab the same job. No library needed.

pool.js

async function mapWithConcurrency(items, limit, worker) {
  const results = new Array(items.length);
  let next = 0;                          // the shared cursor into the job list

  async function runner() {
    while (next < items.length) {
      const i = next++;                  // claim a job index (atomic: single thread)
      results[i] = await worker(items[i], i);
    }
  }

  // start N runners; they drain the same queue in parallel-still-running
  const pool = Array.from({ length: Math.min(limit, items.length) }, runner);
  await Promise.all(pool);               // wait for every runner to finish
  return results;                        // in the SAME order as items
}

Read it slowly, because it's small but packed with ideas:

  • next is shared by all runners; next++ hands each runner a unique index.
  • A runner awaits its job, so while it waits the thread is free. Another runner's await can be running too. That is how you get up to N concurrent, never more.
  • When a runner's job finishes, its while loop grabs the next index. When indices run out, that runner ends.
  • Promise.all(pool) resolves when all N runners have drained the queue.
  • Results land in results[i], so the output order matches the input — like Promise.all, but with bounded concurrency.

Use it:

const urls = [ /* ...500 URLs... */ ];
const bodies = await mapWithConcurrency(urls, 10, async (url) => {
  const res = await fetch(url);
  return res.text();
});   // at most 10 fetches ever still running
In real projects you'd use a library — but know the pattern Libraries like p-limit or p-map do exactly this in one line. Use them in production. But interviewers ask you to write the pool from scratch, because it proves you understand why unbounded Promise.all is dangerous and how a queue fixes it. Say it in the simplest words — the Feynman check

1 · In plain words Node can have hundreds of jobs still running at once, because nearly all of them are only waiting. That is not the same as doing hundreds of things in the same instant. And “still running” is not free — start five thousand together and something downstream falls over.

2 · One analogy One person posting letters. They can easily have 500 letters travelling through the postal system at the same time — that is concurrency. They cannot write 500 letters in the same second — that would be parallelism, and it needs more than one person.

…and where the analogy breaks The post office does not collapse when you post 5,000 letters. A real API does. The picture captures “many still running, one worker” very well.

It completely hides the fact that the other side has limits too: connection pools, rate limits, file handles. Your own process runs out of sockets long before the post office runs out of vans.

3 · The sticking point Promise.all looks like the tool for “do all of these together”, so people hand it the whole array. But it is not a concurrency control. Every request fired the moment you built the array with .map(). The flood happened before Promise.all ever saw them. The limit belongs where the promises are created, never where they are awaited.

Build it for real — flood vs pool, measured

Prove the pool matters with numbers. This starts a tiny local server that handles only a few requests at a time. Then it hits the server both ways.

race.js (one file — starts a server, then sends many requests to it)

const http = require('http');

// A fragile server: each request takes 200ms; it "overloads" past 10 at once.
let inFlight = 0, maxSeen = 0;
http.createServer((req, res) => {
  inFlight++; maxSeen = Math.max(maxSeen, inFlight);
  setTimeout(() => { inFlight--; res.end('ok'); }, 200);
}).listen(3000, run);

async function mapWithConcurrency(items, limit, worker) {
  const out = new Array(items.length); let next = 0;
  async function runner() { while (next < items.length) { const i = next++; out[i] = await worker(items[i], i); } }
  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, runner));
  return out;
}

async function run() {
  const urls = Array.from({ length: 100 }, () => 'http://localhost:3000');

  // pooled: at most 10 still running
  maxSeen = 0;
  await mapWithConcurrency(urls, 10, (u) => fetch(u).then((r) => r.text()));
  console.log('pooled  → peak concurrent on server:', maxSeen);   // ~10

  // flood: all 100 at once
  maxSeen = 0;
  await Promise.all(urls.map((u) => fetch(u).then((r) => r.text())));
  console.log('flooded → peak concurrent on server:', maxSeen);   // ~100

  process.exit(0);
}

Run node race.js. The pooled run keeps the server's peak at about 10; the flood pushes it to about 100 in one burst. On a real API, that difference is the line between "polite client" and "rate-limited / banned." Same jobs, same results — controlled vs uncontrolled.

Remember this · the 20-second recap
  • Concurrency = many jobs still running on one thread; parallelism = many cores at the same instant. Node gives huge concurrency for free; parallelism needs workers/cluster (weeks 22–25).
  • Promise.all — all fulfil, results in input order, fail-fast (one rejection loses the whole batch).
  • allSettled — never rejects; each item is fulfilled or rejected. Use it for partial results.
  • race — first to settle wins (good for timeouts). any — first to fulfil wins, ignores failures (good for redundancy).
  • urls.map(u => fetch(u)) inside Promise.all starts all requests at once — a flood that gets you rate-limited or crashes. Cap it with a concurrency limit.
  • The pool: N runners share a cursor next++. Each does a job then grabs the next, so at most N run at once and results stay in order. next++ is safe because JS is single-threaded.

If you remember one thing: never fire an unbounded Promise.all over a big list. Run it through a pool, so at most N are ever running.
