Month 2 · Lesson 7 · Async model

Doing many things at once — safely

The four Promise combinators, and the pattern that keeps 500 requests from becoming a flood: a concurrency limit.

Your win today: you'll know exactly when to reach for Promise.all, allSettled, race, or any — and you'll be able to write, from memory, a concurrency-limited runner that processes 500 jobs N-at-a-time. That runner is a favourite live-coding question and the engine of tomorrow's build.
Where you are Lessons 5–6 gave you one async operation at a time. Real work is rarely one thing — it's "fetch these 300 URLs," "resize these 1,000 images." Today is about running many promises together without either doing them one-at-a-time (slow) or all-at-once (a self-inflicted denial-of-service). Lesson 3 of 4.

First principles — concurrency is not parallelism

These two words get mixed up, and the difference is a great interview answer.

  • Parallelism = literally doing things at the same instant, on multiple CPU cores. That needs multiple threads or processes (Month 6).
  • Concurrency = many tasks in progress at once, taking turns on one worker. One thread, many jobs "in flight."

From Month 1 you know Node's single thread hands slow I/O to the OS and stays free. So it can have hundreds of network requests in flight at the same time — that's concurrency — even though your JavaScript runs on one thread. You don't need parallelism to fetch 300 URLs together; you need concurrency, and the combinators below are how you express it.

Say this one out loud

Concurrency is dealing with many things at once (one thread, many I/O operations in flight). Parallelism is doing many things at the same instant (many cores). Node gives you huge concurrency on one thread for free; parallelism needs worker threads or cluster.

The four combinators — pick by what "done" means

Each takes an array of promises and returns one promise. They differ only in when they settle and how they treat failure.

CombinatorSettles when…On failureUse it when…
Promise.allall fulfillfail-fast: rejects the instant any one rejectsyou need every result and any failure ruins the batch
Promise.allSettledall settlenever rejects; each item reports fulfilled or rejectedyou want partial results — some may fail and that's OK
Promise.racethe first one settlesthe first to settle wins, even if it's a rejectiontimeouts ("whichever finishes first — the work or a timer")
Promise.anythe first one fulfillsignores rejections; rejects only if all failredundancy ("first mirror to answer wins")

Promise.all returns results in input order (not finish order), which is why it's the default for "fetch these three things and use all of them":

const [user, orders, prefs] = await Promise.all([
  getUser(id), getOrders(id), getPrefs(id),
]);   // all three run concurrently; array order matches input order
The all vs allSettled trap (they will ask this) Promise.all is fail-fast: one rejection rejects the whole call and you lose the results that did succeed. If you're fetching 300 URLs and one 404s, all throws away the other 299. When some failures are acceptable and you want every outcome, use allSettled and inspect each item's status. 
const results = await Promise.allSettled(urls.map(fetchJson));
const ok   = results.filter((r) => r.status === 'fulfilled').map((r) => r.value);
const bad  = results.filter((r) => r.status === 'rejected').map((r) => r.reason);
// you keep the 299 good ones AND a list of the failures

The problem Promise.all hides — the flood

Here's the trap that separates junior from senior. This looks innocent:

const results = await Promise.all(urls.map((u) => fetch(u)));   // 500 URLs?

urls.map(fetch) starts every request immediately. With 500 URLs, that's 500 connections opening in the same tick. The consequences are real and painful:

  • the target server rate-limits you (HTTP 429) or bans your IP;
  • you exhaust file descriptors / sockets and get EMFILE or ECONNRESET;
  • memory spikes holding 500 in-flight responses;
  • everything gets slower, not faster — you've built a denial-of-service against yourself.

The fix is a concurrency limit: process the jobs in a controlled way so at most N run at any moment. Think of a pool of N workers pulling jobs from a shared queue.

Build the concurrency-limited runner from scratch

This is the pattern to own. The idea: start N "runners." Each runner loops — grab the next job index, do it, repeat — until the jobs run out. Because JavaScript is single-threaded, i = next++ can't be interrupted, so no two runners ever grab the same job. No library needed.

pool.js

async function mapWithConcurrency(items, limit, worker) {
  const results = new Array(items.length);
  let next = 0;                          // the shared cursor into the job list

  async function runner() {
    while (next < items.length) {
      const i = next++;                  // claim a job index (atomic: single thread)
      results[i] = await worker(items[i], i);
    }
  }

  // start N runners; they drain the same queue in parallel-in-flight
  const pool = Array.from({ length: Math.min(limit, items.length) }, runner);
  await Promise.all(pool);               // wait for every runner to finish
  return results;                        // in the SAME order as items
}

Read it slowly, because it's small but dense:

  • next is shared by all runners; next++ hands each runner a unique index.
  • A runner awaits its job, so while it waits the thread is free — another runner's await can be in flight too. That's how you get up to N concurrent, never more.
  • When a runner's job finishes, its while loop grabs the next index. When indices run out, that runner ends.
  • Promise.all(pool) resolves when all N runners have drained the queue.
  • Results land in results[i], so the output order matches the input — like Promise.all, but throttled.

Use it:

const urls = [ /* ...500 URLs... */ ];
const bodies = await mapWithConcurrency(urls, 10, async (url) => {
  const res = await fetch(url);
  return res.text();
});   // at most 10 fetches ever in flight
In real projects you'd use a library — but know the pattern Libraries like p-limit or p-map do exactly this in one line. Reach for them in production. But interviewers ask you to write the pool from scratch, because it proves you understand why unbounded Promise.all is dangerous and how a queue fixes it. Tomorrow's build wires retries and timeouts onto this exact runner.

Build it for real — flood vs pool, measured

Prove the pool matters with numbers. This spins up a tiny local server that can only handle a few requests at a time, then hits it both ways.

race.js (one file — starts a server, then hammers it)

const http = require('http');

// A fragile server: each request takes 200ms; it "overloads" past 10 at once.
let inFlight = 0, maxSeen = 0;
http.createServer((req, res) => {
  inFlight++; maxSeen = Math.max(maxSeen, inFlight);
  setTimeout(() => { inFlight--; res.end('ok'); }, 200);
}).listen(3000, run);

async function mapWithConcurrency(items, limit, worker) {
  const out = new Array(items.length); let next = 0;
  async function runner() { while (next < items.length) { const i = next++; out[i] = await worker(items[i], i); } }
  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, runner));
  return out;
}

async function run() {
  const urls = Array.from({ length: 100 }, () => 'http://localhost:3000');

  // pooled: at most 10 in flight
  maxSeen = 0;
  await mapWithConcurrency(urls, 10, (u) => fetch(u).then((r) => r.text()));
  console.log('pooled  → peak concurrent on server:', maxSeen);   // ~10

  // flood: all 100 at once
  maxSeen = 0;
  await Promise.all(urls.map((u) => fetch(u).then((r) => r.text())));
  console.log('flooded → peak concurrent on server:', maxSeen);   // ~100

  process.exit(0);
}

Run node race.js. The pooled run keeps the server's peak at about 10; the flood pushes it to about 100 in one burst. On a real API, that difference is the line between "polite client" and "rate-limited / banned." Same jobs, same results — controlled vs uncontrolled.

Remember this · the Feynman summary
  • Concurrency = many jobs in flight on one thread; parallelism = many cores at the same instant. Node gives huge concurrency for free; parallelism needs workers/cluster (Month 6).
  • Promise.all — all fulfil, results in input order, fail-fast (one rejection loses the whole batch).
  • allSettled — never rejects; each item is fulfilled or rejected. Use it for partial results.
  • race — first to settle wins (good for timeouts). any — first to fulfil wins, ignores failures (good for redundancy).
  • urls.map(fetch) inside Promise.all starts all requests at once — a flood that gets you rate-limited or crashes. Cap it with a concurrency limit.
  • The pool: N runners share a cursor next++; each does a job then grabs the next, so at most N run at once and results stay in order. next++ is safe because JS is single-threaded.

If you remember one thing: never fire an unbounded Promise.all over a big list — run it through a pool so at most N are ever in flight.
