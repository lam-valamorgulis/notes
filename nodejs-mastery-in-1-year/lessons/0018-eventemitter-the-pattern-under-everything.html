EventEmitter — the pattern under everything

Learn one small object properly, and four things you already use stop being magic.

coreWeek 18 of 52. This lesson builds one domain-expert ability: explain it from first principles, with no jargon and no notes. Week 18 in the plan · Glossary

Your win today: you will write your own EventEmitter in about thirty lines. Then you will see that streams, sockets, servers and the process itself are all the same object underneath — proven by printing their prototype chains.
Where you are Weeks 14–17 used streams and never asked what a stream is. It is this. Everything in weeks 18–21 is built on the small object below, so this is the highest-leverage hour in the module.

Start from the problem — who calls your function?

Week 1 established that Node does not wait. It registers a callback and gets called back. That works when there is exactly one answer coming.

A socket is not like that. It produces data, then more data, then maybe an error, then a close. Several kinds of thing, several times each, in an order nobody knows in advance.

A single callback cannot express that. So you need three things:

  1. A way to say which kind of thing you care about — a name.
  2. A way to register a function for that name.
  3. A way for the producer to say “this happened” and run everyone who asked.

That is the entire design. Node calls it EventEmitter, and it is small enough to write yourself.

Write it yourself — the whole thing

class MyEmitter {
  constructor() { this.listeners = new Map(); }

  on(name, fn) {
    if (!this.listeners.has(name)) this.listeners.set(name, []);
    this.listeners.get(name).push(fn);
    return this;                              // so calls can chain
  }

  off(name, fn) {
    const list = this.listeners.get(name) || [];
    const i = list.indexOf(fn);
    if (i !== -1) list.splice(i, 1);
    return this;
  }

  once(name, fn) {
    const wrapper = (...args) => { this.off(name, wrapper); fn(...args); };
    return this.on(name, wrapper);            // remove first, then call
  }

  emit(name, ...args) {
    const list = this.listeners.get(name);
    if (!list || list.length === 0) return false;
    for (const fn of [...list]) fn(...args);  // copy: a listener may remove itself
    return true;
  }
}

Two lines in there are the ones that matter, and both are there because of a bug:

  • once removes the wrapper before calling fn. Do it the other way round and a listener that emits the same event again recurses forever.
  • emit loops over a copy of the list. Without the copy, a listener that removes itself shifts the array while you walk it. The next listener is then skipped.

The fact that surprises people — emit is synchronous

Look at your own emit. It is a for loop. There is no timer, no queue, no promise. So every listener runs to completion before emit returns.

The real output (Node v24.14.0):

console.log('before emit');
e.emit('go');
console.log('after emit');

before emit
  listener ran
after emit
Why this matters more than it looks “Event” sounds asynchronous. It is not. A slow listener blocks the emitter, and a listener that throws propagates the throw straight back into whoever called emit — often deep inside Node's own code, which is why those stack traces look so strange. This is week 1's rule again: an event handler runs on the same one thread as everything else.

The error event is not an ordinary event

One name is special. If you emit 'error' and nobody is listening, Node does not shrug — it throws the error:

const e = new EventEmitter();
e.emit('error', new Error('boom'));
// throws: Error: boom

Verified. Uncaught, that ends the process.

This looks harsh, and it is the same reasoning as week 6's unhandled rejection. An error nobody agreed to handle means the program is in a state its author never planned for. Crashing loudly beats continuing quietly.

The rule this gives you Attach an error listener to every emitter you keep. Every socket, every stream, every child process. A missing one turns a recoverable network hiccup into a dead server, and the stack trace will point at Node's internals rather than at your code.

The warning that is usually a real bug

Add eleven listeners for one event and Node prints:

MaxListenersExceededWarning: Possible EventEmitter memory leak detected.
11 x listeners added to [EventEmitter]. MaxListeners is 10.

Verified: defaultMaxListeners is 10, and the warning fires when the eleventh is added.

Ten is a convention, not a law. Nothing breaks at eleven. The number was chosen because almost no correct program needs more than ten listeners on one event. So passing it is usually evidence of a real leak. Something adds a listener per request and never removes it.

The wrong fix, and why people reach for it setMaxListeners(100) makes the warning go away. It does not make the leak go away. Ask “what adds a listener, and what removes it?” first. Raise the limit only when you can say why a number above ten is correct here — for example, a long-lived emitter with a genuinely fixed set of twenty subscribers.

The payoff — four things are the same thing

Print the prototype chain of an HTTP request and response. Verified on Node v24.14.0:

req: IncomingMessage -> Readable -> Stream -> EventEmitter -> Object
res: ServerResponse  -> OutgoingMessage -> Stream -> EventEmitter -> Object

Both end at EventEmitter. So do sockets, so do file streams, and so does process itself. That is why process.on('SIGTERM'), stream.on('data'), server.on('connection') and socket.on('error') all feel the same. They are the same method.

A detail worth having, because it catches people out Notice that res is not a Writable. Its chain goes through OutgoingMessage, not stream.Writable, so res instanceof Writable is false. It has write, end and cork, so it behaves like one and works in pipeline. But a type check against Writable will fail, and that surprises people who trusted the name.
Say it in the simplest words — the Feynman check

1 · In plain words Sometimes you want to be told when something happens. It can happen many times, in many different ways. So you leave your phone number next to a label: “ring me on data”.

Anyone can leave a number. When the thing happens, the owner rings every number on that label, one after another. That is all an EventEmitter is: a list of names, and a list of functions under each name.

2 · One analogy A noticeboard in an office. You pin your name under a heading you care about. When something happens, whoever is announcing it reads the names under that heading and tells each person in turn.

…and where the analogy breaks A real announcer would carry on down the list. One person talking at length would not stop them. Node does not. emit is a for loop. Each listener runs to the end before the next one starts. The announcer is stuck until the last one finishes.

So one slow listener holds up every other listener and the code that emitted. And if a listener throws, the throw travels back to whoever called emit. That is usually a line inside Node itself. It is why the stack trace looks like it has nothing to do with you.

3 · The sticking point The word “event” makes people expect something asynchronous. It is not. There is no queue and no timer anywhere in emit.

That single wrong expectation causes two real bugs. People put slow work in a handler and wonder why throughput dropped. The handler blocks the event loop like any other function. And people write emitter.emit('x'); doNext(); expecting doNext to run first — it never does.

4 · Now you explain it back

In two or three sentences, explain what emit actually does when it is called. Then say what happens if one listener is slow. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — your own emitter, then three proofs

1 · Write it

Type the class above from scratch — do not copy it. Then check it against Node's:

const e = new MyEmitter();
e.once('go', () => console.log('once fired'));
e.emit('go'); e.emit('go');          // must print once, not twice

const f = () => { e.off('x', f); console.log('removed myself'); };
e.on('x', f); e.on('x', () => console.log('I must still run'));
e.emit('x');                          // both lines must print

That second test is the one people fail. If your emit does not copy the array, the second listener is skipped.

2 · Prove it is synchronous

console.log('A'); e.emit('go'); console.log('C');
// listener prints 'B'. Predict the order, then run it.

3 · Make the leak, then find it

const server = http.createServer((req, res) => {
  process.on('SIGTERM', () => res.end());   // a listener per request, never removed
  res.end('ok');
});

Send eleven requests and watch the warning appear. Then run it again with node --trace-warnings and read the stack — it names the line that added the listener. That is how you find one of these in a real service.

What to hand in Your MyEmitter, with both tests passing, and the --trace-warnings stack from the leak. The second one is the artefact — it is the technique, not the bug, that you keep.

Remember this · the 20-second recap
  • An EventEmitter is a map from a name to a list of functions. That is the whole design.
  • emit is a for loop, so it is synchronous. Listeners finish before it returns.
  • A slow listener blocks the emitter. A throwing listener throws into whoever called emit.
  • once must remove the wrapper before calling. emit must loop over a copy.
  • Emitting 'error' with no listener throws. Attach an error listener to every emitter you keep.
  • defaultMaxListeners is 10 — a convention. The warning at eleven usually means a real leak.
  • Streams, sockets, servers and process all inherit from it. One object explains all four.

If you remember one thing: “event” does not mean asynchronous. emit is a for loop on the same one thread.
