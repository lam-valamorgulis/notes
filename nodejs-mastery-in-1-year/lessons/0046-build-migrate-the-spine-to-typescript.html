Your win today: a bug list. Seven real crashes, found without running the service — and the exact order to turn the compiler up so each one appears.
Where you are Week 44 taught the four parts of the type system worth knowing. This week applies them to a whole service, and the deliverable is not the typed code. It is the evidence.

Start from the problem — how do you migrate without stopping?

The migration that fails is done as one branch, all at once, over three weeks. Meanwhile other people keep shipping. It ends in a merge nobody can review.

The rule that makes this safe

Every commit compiles and every commit has a green suite. If a step cannot be done that way, it is too big a step.

That is possible because TypeScript can read JavaScript. You can turn the checker on before renaming a single file — and that is where the first surprise is.

Step 1 — check the JavaScript, rename nothing

Two ordinary .js files from a link shortener: a store and an HTTP server. No types anywhere. Turn on allowJs and checkJs with strict, and compile. Measured with TypeScript 7.0.2:

Do this first, on any JavaScript codebase Thirteen findings from a configuration file. No rename, no rewrite, no risk. If someone is unconvinced that TypeScript is worth it, this is the demonstration — and it takes ten minutes.

Step 2 — rename, and type your own data

Now look at what those 13 errors have in common. Every single one comes from a type somebody else wrote — http, process, Error. The compiler knows those.

It knew nothing about the store's own data, because new Map() is Map<any, any>. So this code passed cleanly:

function bump(code) {
  const l = links.get(code);
  l.hits += 1;                // l is any. no error. crashes on an unknown code.
  return l.hits;
}

Rename store.js to store.ts and give the Map a type — the only real change:

type Link = { code: string; url: string; hits: number; createdAt: number };
const links = new Map<string, Link>();

store.ts(14,3):  error TS18048: 'l' is possibly 'undefined'.
store.ts(15,10): error TS18048: 'l' is possibly 'undefined'.
This is the whole argument for actually migrating checkJs alone found 13 bugs in other people's types and 0 in your own logic. The bug in bump only became visible once Map<string, Link> told the compiler what get returns.

So “we turned on checkJs, that is enough” is a real improvement and a fraction of the value. The compiler can only check the parts you have described.

Step 3 — the flag strict does not include

One bug was still hiding, in a function that reads perfectly:

const newest = all.sort((a, b) => b.createdAt - a.createdAt)[0];
return { count: all.length, total, newestCode: newest.code };

On an empty store, all[0] is undefined. Verified at run time:

TypeError: Cannot read properties of undefined (reading 'code')

And strict: true does not catch it. Indexing an array gives you Link, not Link | undefined. There is a separate flag, and it is not in strict:

"noUncheckedIndexedAccess": true

store.ts(22,50): error TS18048: 'newest' is possibly 'undefined'.
Turn it on, and expect noise Every arr[i] and every obj[key] becomes possibly undefined, which is honest and occasionally tiresome. It catches the empty-array bug, which is one of the most common crashes in any JavaScript service. Turn it on last, once the rest compiles.

Keep this list as you go, not afterwards Write the row when you fix the error, while you still remember why the code was wrong. Reconstructing it a week later produces “various type errors”, which persuades nobody and teaches you nothing.

The any that gets you through the week

Migrating produces pressure to silence the compiler. Three tools, in order of honesty:

EscapeWhat it meansAcceptable?
// @ts-expect-error + a reason“This is wrong, I know, here is why”Yes. It also errors if the problem is ever fixed.
x! non-null assertion“I promise this is not null”Only where you can point at the check.
as any“Stop checking, and everything downstream too”Almost never. Never at a boundary.
Why @ts-expect-error beats @ts-ignore @ts-ignore silences the line forever, including after you fix the underlying problem. @ts-expect-error fails to compile when the error goes away, so it cleans itself up and tells you the workaround is no longer needed.
Say it in the simplest words — the Feynman check

1 · In plain words TypeScript can check plain JavaScript. So the first step of a migration renames nothing — you turn the checker on and read what it says.

On two small files it found 13 real problems that way. Then you rename files and describe your own data, and it finds a different kind of problem. The compiler can only check the parts you have described to it.

2 · One analogy A spelling checker knows every word in its dictionary. It cannot check a name it was never told. So it stays silent on the one spelled wrong.

…and where the analogy breaks A spelling checker is silent about the unknown name. TypeScript is worse than silent. It reports the file as clean, because any means “stop checking” rather than “I do not know”.

I measured exactly that. With checkJs alone, links.get(code).hits += 1 produced no error, because new Map() is Map<any, any>. Only after writing Map<string, Link> did the compiler say 'l' is possibly 'undefined'. Same code, same flags — the only thing that changed was that I had told it what the Map holds.

3 · The sticking point People treat strict: true as the maximum setting. It is not. noUncheckedIndexedAccess is a separate flag, and without it arr[0] has the element type rather than “element or undefined”.

So the empty-array crash — one of the most common in any JavaScript service — passes strict cleanly. I measured it: all.sort()[0].code compiled fine and threw Cannot read properties of undefined at run time.

4 · Now you explain it back

In three sentences, explain why turning on checkJs is a real win but not the same as migrating. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words is the part that proves it.

Build it for real — migrate the spine

Requirements:

  1. Step 1 first. allowJs, checkJs, strict, rename nothing. Record the error count and read every one.
  2. Fix those without renaming. Commit. Green suite, compiling, before any rename happens.
  3. Migrate leaf files first — the ones nothing imports. Then work up. One file per commit.
  4. Every commit compiles and every commit is green. If a step cannot be, split it.
  5. Type your own data, not just the function signatures. That is where step 2's bugs live.
  6. Turn on noUncheckedIndexedAccess last, and fix the array-index bugs it finds.
  7. Keep the bug list as you go. Bug, how it was found, what it would have done in production.
  8. Grep for any, as, ! and @ts-. Each survivor gets a one-line defence in a comment, or gets deleted.
The drill

“Was TypeScript worth it here?”

Answer with the bug list, and for each row say what it would have cost in production and whether a test would have caught it. That second question is the honest part. Some of them a test would have caught easily — say so. The persuasive rows are the ones no reasonable test suite would ever have reached.
