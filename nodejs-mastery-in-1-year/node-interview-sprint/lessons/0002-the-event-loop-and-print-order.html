The event loop and print order

One rule decides the order of every callback in Node. Learn the rule, and you never memorise an output again.

sprintDay 1 of 7. This lesson builds one domain-expert ability: predict how it behaves in a case never seen before. Day 1 in the plan · Glossary

Your win today: you can read any mix of sync code, setTimeout, Promise and process.nextTick, and say the print order. You also know the one pair whose order is not fixed, and you say so.

Start from the problem

Work finishes at unpredictable times. A timer fires, a socket delivers bytes, a promise resolves.

Only one thread can run your JavaScript. So something must decide which waiting callback runs next.

You could run them in arrival order, with one flat queue. That fails for a simple reason.

A timer that is due and a socket that has data are not the same kind of work. Mixing them into one queue makes both worse.

So Node uses several queues, visited in a fixed order. One pass over all of them is called a tick of the event loop.

The phases, and the two queues that jump the line

libuv defines the phase order. It is a design decision, not a law of computing. Learn it as a convention.

PhaseWhat it runsYou meet it as
timersCallbacks whose time has comesetTimeout, setInterval
pending callbacksSome system errors held overRarely, in socket errors
pollNew I/O, and waiting for moreFile reads, incoming requests
checkCallbacks booked for right after pollsetImmediate
closeClose eventssocket.on('close')

Two queues sit outside those phases and are drained between every step.

  • The process.nextTick queue. Node's own queue. It is drained first.
  • The microtask queue. Promises and queueMicrotask. Drained second.

Both are drained completely, not one item at a time. A nextTick callback that queues another nextTick keeps the loop waiting.

The one rule — say this out loud

"Run the current synchronous code to the end. Then drain process.nextTick completely. Then drain microtasks completely. Only then move to the next phase."

Work the rule on real code

Here is the program. Read it, predict the order, then look.

console.log('1 sync start');
setTimeout(() => console.log('2 setTimeout 0'), 0);
setImmediate(() => console.log('3 setImmediate'));

Promise.resolve().then(() => {
  console.log('4 promise then');
  process.nextTick(() => console.log('5 nextTick inside then'));
});

process.nextTick(() => console.log('6 nextTick'));

(async () => {
  console.log('7 async fn body');
  await null;
  console.log('8 after await');
})();

queueMicrotask(() => console.log('9 queueMicrotask'));
console.log('10 sync end');

The measured output, on Node v24.14.0:

1 sync start
7 async fn body
10 sync end
6 nextTick
4 promise then
8 after await
9 queueMicrotask
5 nextTick inside then
3 setImmediate
2 setTimeout 0

Now derive it, line by line, using only the one rule.

OrderWhy it lands there
1, 7, 10All synchronous. An async function body runs at once, up to its first await.
6The nextTick queue is drained first, before any promise.
4, 8, 9Microtasks, in the order they were queued. await null queued one at line 8.
5Queued during microtask draining. The checkpoint runs again before the loop moves on.
3, 2Phases, at last. And this pair is the interesting one.
Trap — the pair with no fixed order In the main module, setTimeout(…, 0) against setImmediate is a race. It depends on how long the process took to start. Measured over 20 runs on Node v24.14.0: setImmediate ran first 17 times and setTimeout ran first 3 times. Saying "it is not deterministic here" is the correct answer, and it beats guessing.

Inside an I/O callback the answer is fixed. You are already past the timers phase, and check comes next.

Measured — Node v24.14.0, 2026-08-28 Inside an fs.readFile callback, over 10 runs, setImmediate ran before setTimeout(…, 0) every single time.

The one place the rule looks broken

At the top level of the main file, the module system changes the answer. This surprises almost everybody.

console.log('sync');
process.nextTick(() => console.log('nextTick'));
Promise.resolve().then(() => console.log('promise'));
Measured — Node v24.14.0, 2026-08-28 Saved as .cjs, that file printed sync nextTick promise on every run. Saved as .mjs, it printed sync promise nextTick on every run. Same code, opposite order.

The reason is the loader. An ES module is evaluated inside a promise job already.

So microtasks queued at the top level are still being drained when your module body ends. The nextTick queue is reached after that.

Inside a function, a handler or a callback, the normal rule holds in both module systems. The flip only affects top-level code in the main file.

Say it in the simplest words — the Feynman check

1 · In plain words Node keeps several lists of jobs to do. It walks the lists in a fixed order, again and again.

Two of the lists are special. They are emptied completely before Node is allowed to move to the next list.

2 · One analogy A nurse doing ward rounds in a fixed route. Room by room, same order, every round.

But before leaving any room, the nurse must clear the emergency tray by the door. Only when the tray is empty do they walk on.

…and where the analogy breaks A real nurse would stop refilling the tray and move on. Node will not.

If a nextTick callback keeps adding another nextTick, the tray never empties. The loop never reaches the next room, and your server stops answering. That is a real way to hang a service.

3 · The sticking point People think setTimeout(fn, 0) means "run this next". It does not. It means "run in the timers phase, at the earliest".

Every nextTick and every promise callback goes first. Zero is a floor on the delay, never a promise about position.

4 · Now you explain it back

In two or three sentences, say why process.nextTick beats a resolved promise. Then say why both beat setTimeout(fn, 0). Send it to me and I will tell you where the gap is. Do not skip this. Saying it in your own words is the part that proves it.

The three sentences that answer most follow-ups

They askYou say
"nextTick or setImmediate?"Names are backwards. nextTick runs sooner. setImmediate waits for the check phase.
"When would you use nextTick?"Almost never. To let a caller attach a listener before you emit an event.
"Can you starve the loop?"Yes. A nextTick that queues another nextTick never lets a phase run.
"Is await a microtask?"Yes. The code after await is queued as a microtask, even for await null.
"Does setTimeout(fn, 0) mean zero?"No. It is a minimum delay, and it is clamped to at least one millisecond.

Remember this · the 20-second recap
  • One rule: finish the sync code, drain process.nextTick, drain microtasks, then move a phase.
  • Phase order is timers → pending → poll → check → close. It is a convention from libuv.
  • Both special queues are drained completely, so they can starve the loop.
  • An async function body runs synchronously up to its first await.
  • setTimeout(fn, 0) is a minimum delay, never a position in the queue.
  • In the main module, setTimeout against setImmediate is a race — 17 to 3 over 20 runs.
  • Inside an I/O callback, setImmediate always wins. Poll is done, so check is next.

If you remember one thing: never memorise an output. Derive it from the one rule, out loud.
