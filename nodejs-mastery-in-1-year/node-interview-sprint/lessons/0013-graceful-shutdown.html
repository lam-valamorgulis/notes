Graceful shutdown

The question that separates a script from a service. Every deploy kills your process. What happens to the requests already inside it?

sprintDay 5 of 7. This lesson builds one domain-expert ability: say why it was built this way, and what that choice gives up. Day 5 in the plan · Glossary

Your win today: you can say the five steps of a graceful shutdown, in order. You can explain why process.exit() is the wrong tool. You have a number for the keep-alive problem.

Start from the problem

You deploy. The platform sends your process a SIGTERM.

Node's default handler for SIGTERM is simple. It ends the process at once.

Right now some requests are half-done. A database write is in flight. A response is half-written to a socket.

All of them die. The user sees a connection reset, not an error page.

The question to hold on to

A shutdown is not "stop". A shutdown is "stop taking new work, then finish the work you already took". Those are two different instructions, and Node gives you only the second one for free.

Derive the five steps

If the goal is "drop nothing", each step follows from the one before it.

#StepWhy it has to come here
1Fail the readiness checkThe load balancer must stop sending you new requests first.
2server.close()Stop accepting new connections. It does not cut existing ones.
3server.closeIdleConnections()Keep-alive sockets sitting idle would otherwise hold you open.
4Close the pool, the queue, the cacheOnly after the last request finished using them.
5Set process.exitCodeLet the loop drain on its own. Never force it.

Add one backstop. A timer that force-exits if the drain takes too long.

Without it, one stuck request holds the deploy forever. Give it a real number, not a guess.

const server = http.createServer(handler);

let shuttingDown = false;

function shutdown(signal) {
  if (shuttingDown) return;          // two signals must not run this twice
  shuttingDown = true;
  ready = false;                     // 1 · readiness check now fails

  const hard = setTimeout(() => {    // the backstop
    console.error('drain timed out, forcing exit');
    process.exit(1);
  }, 10_000);
  hard.unref();                      // do not keep the loop alive on its own

  server.close(async () => {         // 2 · no new connections
    await pool.end();                // 4 · close what the requests were using
    process.exitCode = 0;            // 5 · let the loop finish naturally
  });

  server.closeIdleConnections();     // 3 · release idle keep-alive sockets
}

process.on('SIGTERM', () => shutdown('SIGTERM'));
process.on('SIGINT',  () => shutdown('SIGINT'));

The three signals worth naming

SignalWho sends itCan you handle it?
SIGTERMDeploys, orchestrators, killYes. This is the one that matters.
SIGINTYou, pressing Ctrl-CYes. Handle it the same way.
SIGKILLThe last resort, or an out-of-memory killNo. The kernel ends you. No code runs.
Trap — you cannot handle SIGKILL There is no handler, no cleanup, and no final log line. Every platform sends SIGTERM first and waits a grace period. If you have not finished by then, SIGKILL arrives. So your drain timeout must be shorter than the platform's grace period, or your backstop never runs.

Why process.exit() is the wrong tool

process.exit() stops the event loop immediately. Nothing pending gets a chance to finish.

That includes your own writes. Writing to a pipe or a file is asynchronous, and the queued bytes are simply lost.

Measured — Node v24.14.0, 2026-08-28 A program wrote 300,000 lines into a slow pipe, then called process.exit(0). Only 320 lines arrived. The process reported exit code 0. It claimed success while losing more than 99.8% of its output.

That is the worst kind of failure. It is silent, and it looks like a success.

Use process.exitCode instead. It records what the exit code will be.

The process then ends on its own, once nothing is left to do. Every pending write completes first.

Say this, word for word

"I set process.exitCode and let the loop drain. process.exit() stops the loop on the spot, so queued writes are thrown away — and the process still reports success."

The keep-alive problem, with a number

Here is the part almost nobody mentions, and it makes the answer sound real.

server.close() waits for every open connection to end. That includes idle keep-alive connections.

An idle connection is doing nothing. It is just held open in case another request comes.

So your shutdown waits on a socket with no work in it. It waits until keepAliveTimeout expires.

Measured — Node v24.14.0, 2026-08-28 With idle keep-alive clients connected, server.close() took 3540 ms. Adding server.closeIdleConnections() brought it down to 538 ms. Node's default keepAliveTimeout is 5000 ms, which is where the wait came from.

The fix is one line. closeIdleConnections() ends sockets with no request on them.

Sockets that are mid-request are left alone. That is exactly the split you want.

Say it in the simplest words — the Feynman check

1 · In plain words Closing a service is two separate jobs. Stop letting new people in. Then finish serving the people already inside.

Node only gives you the second job for free. The first job is code you have to write yourself.

2 · One analogy Closing a shop at the end of the day. You lock the front door first.

Then you serve every customer still standing at the till. Only when the last one leaves do you turn off the lights.

…and where the analogy breaks A shop can ask people to leave. Your server cannot rush a request that is already running.

And a shop has no equivalent of the idle keep-alive socket. That is a customer standing inside the door, buying nothing, who keeps the shop open for five seconds. Measured: 3540 ms of shutdown that closeIdleConnections() cut to 538 ms.

3 · The sticking point People think server.close() closes connections. It does not close a single one.

It stops the listening socket, and then waits. Reading the name as an instruction rather than as a request is where the mistake starts.

4 · Now you explain it back

In two or three sentences, say what server.close() actually does. Then say why an idle connection makes it slow. Send it to me and I will tell you where the gap is. Do not skip this. Saying it in your own words is the part that proves it.

The follow-up questions, and the short answers

They askYou say
"Why fail the readiness check first?"So the load balancer stops routing to me before I stop accepting.
"What if a request never finishes?"A backstop timer force-exits. It must be shorter than the platform's grace period.
"Two SIGTERM signals arrive. What happens?"A guard flag. Running the drain twice closes the pool while requests still use it.
"Does this work with cluster?"Each worker drains itself. The primary stops replacing workers during a shutdown.
"How do you test it?"Send load, send SIGTERM mid-flight, and assert zero failed responses.

Remember this · the 20-second recap
  • A shutdown is two jobs: stop taking new work, then finish the work you took.
  • Order: readiness check, server.close(), closeIdleConnections(), close the pool, set process.exitCode.
  • server.close() closes no connections. It stops the listener and waits.
  • Idle keep-alive sockets hold you open. Measured 3540 ms, cut to 538 ms.
  • process.exit() throws away queued writes. Measured 320 of 300,000 lines, exit code 0.
  • SIGTERM and SIGINT are handleable. SIGKILL is not, so your backstop must fire first.

If you remember one thing: set process.exitCode and let the loop drain. Never call process.exit() in a service.
