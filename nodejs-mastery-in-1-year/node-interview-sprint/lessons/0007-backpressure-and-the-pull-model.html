Day 3 of 7 · Lesson 7 · Streams and memory

Backpressure — the pull model

The stream question every backend interview asks. Answer it with a number, and you sound like someone who has shipped this.

sprintDay 3 of 7. This lesson builds one domain-expert ability: explain it from first principles, with no jargon and no notes. Day 3 in the plan · Glossary

Your win today: you can explain backpressure without saying "it just handles it". You name where the extra bytes go, you name the boolean, and you give a measured number.

Start from the problem

You read a file from a fast local disk. You write it to a slow place.

Slow means a network socket, a remote disk, or another process. The reader produces 100 MB a second. The writer accepts 10 MB a second.

Ask the only question that matters. Where do the other 90 MB go?

They cannot vanish. They cannot go to the writer, because the writer is full. So they sit in memory.

Node calls that memory the internal buffer of the writable stream. It has no size limit of its own.

The whole problem in one sentence

A fast producer and a slow consumer always create a queue. The only question is whether anything tells the producer to stop.

Derive the answer, do not memorise it

The producer needs a signal. Two signals, in fact.

It needs "you are going too fast, pause". And it needs "I have caught up, carry on".

Node puts the first signal in a place people miss. stream.write() returns a boolean.

SignalHow Node sends itWhat the producer must do
Slow downwrite() returns falseStop calling write(). Call readable.pause().
Carry onThe 'drain' event firesCall readable.resume() and continue.

That pair is the whole mechanism. Everything else is convenience built on top of it.

What highWaterMark really is

highWaterMark is the threshold where write() starts returning false. The default is 65536 bytes for a byte stream.

It is not a hard limit. Node will not refuse a write, and it will not throw.

If you keep calling write() after it returned false, every byte still goes into the buffer. The buffer grows past the mark, and keeps growing.

Trap — the silent failure Ignoring the return value of write() never produces an error. There is no warning and no exception. The only symptom is memory. The process gets bigger and bigger, and one day the container is killed. This is why the bug reaches production so often.

The numbers

The same copy job was run twice. Once ignoring the boolean, once honouring it.

Measured — Node v24.14.0, 2026-08-28 Ignoring backpressure: peak RSS 172 MB, with 125 MB sitting in the queue. Honouring it: peak RSS 84 MB, with 0 queued. Same input, same output, half the memory.

The second number is even more useful in an interview.

Measured — Node v24.14.0, 2026-08-28 A 191 MB file cost 657 MB of peak memory through readFileSync. The same file streamed cost 67 MB. That is roughly ten times less.

Notice that 657 MB is far more than 191 MB. A file read into a string is not stored at one byte per byte.

The code, both ways

Here is the version that leaks. It looks completely normal.

// WRONG — the return value is thrown away every time.
readable.on('data', (chunk) => {
  writable.write(chunk);        // returns false sometimes. Nobody looks.
});

Here is the version that honours the signal.

// RIGHT — pause on false, resume on 'drain'.
readable.on('data', (chunk) => {
  const ok = writable.write(chunk);
  if (!ok) readable.pause();     // stop pulling
});

writable.on('drain', () => readable.resume());   // start again

And here is what you would actually ship. It does the same thing for you.

import { pipeline } from 'node:stream/promises';

await pipeline(readable, writable);   // backpressure and cleanup, both handled
Say it in the simplest words — the Feynman check

1 · In plain words One person fills buckets fast. Another empties them slowly. Somebody has to shout "stop".

In Node the shout is a false coming back from write(). The "carry on" is an event called 'drain'. If nobody listens, the buckets pile up in memory.

2 · One analogy A supermarket checkout. The scanner is fast and the person bagging is slow.

Items pile up on the little shelf between them. The cashier watches the shelf and pauses when it fills. That pause is backpressure.

…and where the analogy breaks A real shelf is a fixed size. Items fall off, and everybody sees the problem at once.

Node's shelf has no size limit. Nothing falls off and nothing errors. highWaterMark is only the point where Node says "this is getting full". It never refuses a write, so the failure is invisible until the process is killed.

3 · The sticking point People think highWaterMark caps the buffer. It does not cap anything.

It is only the threshold that flips the return value to false. Enforcement is entirely your job, or pipeline's job. Nothing in Node stops a determined producer.

4 · Now you explain it back

In two or three sentences, say what happens to the bytes when a writer is slower than a reader. Then say which single value tells you to stop. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words proves it.

The follow-up questions, and the short answers

They askYou say
"What is backpressure?"A slow consumer telling a fast producer to pause, so the queue between them stays small.
"How does Node send that signal?"write() returns false. The 'drain' event says you may continue.
"What is highWaterMark?"The threshold where write() starts returning false. Not a cap.
"What happens if you ignore it?"Nothing errors. Memory grows until the process is killed by the host.
"So should I write this by hand?"No. Use pipeline. I write it by hand only to show I know the mechanism.
"Does a bigger highWaterMark help?"It trades memory for fewer pauses. It never fixes a consumer that is simply too slow.

Remember this · the 20-second recap
  • A fast producer and a slow consumer always make a queue. The queue lives in your memory.
  • write() returns false when the buffer passes highWaterMark. That is the "stop" signal.
  • The 'drain' event is the "carry on" signal. Pause the reader, resume on drain.
  • highWaterMark is a threshold, not a cap. Node never refuses a write.
  • Ignoring the boolean never errors. The only symptom is memory, and then a killed container.
  • Measured: 172 MB peak with 125 MB queued, against 84 MB peak with 0 queued.
  • Measured: a 191 MB file cost 657 MB via readFileSync and 67 MB streamed.

If you remember one thing: the bytes have to go somewhere, and by default that somewhere is your heap.
