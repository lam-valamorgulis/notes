Kata 4 — the service that hangs

Ten minutes. No code to write. You debug out loud, and the order you check things in is the whole score.

sprintDay 5 of 7. This lesson builds one domain-expert ability: debug a problem in it that has no ready answer online. Day 5 in the plan · Glossary

Your win today: you can take a vague production complaint and turn it into an ordered search. Out loud, in ten minutes, naming the number you would collect at every step.
A kata is a performance, not an exam Debugging out loud is a performance skill, not a knowledge skill. You already know the causes from Lesson 13 and Lesson 14. What you are training here is doing it while a stranger watches and says nothing helpful. So run this kata twice. The first run finds the gaps. The second run is the one that tells the truth.

The brief, exactly as they will give it

The task · 10 minutes on the clock

"Our Node service stops answering under load. CPU is not pegged. Find the cause, out loud."

That is all they say. They will not add facts unless you ask for them. Every question you ask is part of the score.

Set a timer for ten minutes now. Talk the whole time. Do not scroll past this line until it rings.

The one thing they are grading

They are not grading whether you guess the cause. They are grading your search order.

A good search order removes half the possibilities with each answer. A guess removes none.

The sentence that scores highest

"Before I guess a cause, here is the first number I would collect. And here is what each answer rules out."

Trap — "CPU is not pegged, so it is not CPU" This is the trap hidden inside the brief. A blocked event loop is one thread. On an eight-core machine, one fully busy thread is about one eighth of total CPU — near 12%, which looks idle on a dashboard. That is arithmetic, not a measurement. So "CPU is low" does not rule out a blocked loop. It is the first thing you must say out loud.

The talking script — what to say, in order

StepSay this out loud
1 · Define "hangs""Are requests slow, or do they never answer? Does the health check still pass?"
2 · Kill the trap"Low CPU does not rule out a blocked loop. One busy thread on eight cores looks like 12%."
3 · Name the first number"So my first measurement is event loop delay, not a profile and not a log."
4 · Branch"If the delay is high, it is blocked. If it is flat, the loop is fine and I am waiting on something."
5 · Go one level"Blocked, so now I profile and sort by self time." Or: "Not blocked, so I count in-flight work."
6 · Say the guard"Then I add the measurement to the service, so nobody has to guess next time."

The decision tree, worked

Branch A — is the event loop blocked?

This is always the first question. One number answers it.

The cheapest version is a heartbeat. A timer that reports how late it fired.

const EVERY = 50;
let last = Date.now();

setInterval(() => {
  const now = Date.now();
  const late = now - last - EVERY;     // how much later than promised
  last = now;
  if (late > 20) console.log('heartbeat late by', late, 'ms');
}, EVERY).unref();                     // unref, so it never holds the process open
Measured — Node v24.14.0, 2026-08-28 In the parent course, that 50 ms heartbeat ran 3 ms late under heavy I/O and 155 ms late under a single CPU burst. Re-run while writing this lesson against a 200 ms synchronous burst, it printed late by 193 ms, on all three runs.

Those two numbers are the whole branch. 3 ms means not blocked. 155 ms means blocked.

The built-in version is better in production, because it keeps a histogram.

const { monitorEventLoopDelay } = require('node:perf_hooks');

const h = monitorEventLoopDelay({ resolution: 20 });
h.enable();

// read it whenever you like — these are nanoseconds
console.log('max', Math.round(h.max / 1e6), 'ms', ' mean', Math.round(h.mean / 1e6), 'ms');
Measured — Node v24.14.0, 2026-08-28 With resolution: 20, an idle loop reported a max of 21 to 27 ms across three runs. After one 300 ms synchronous burst the same max read 308 to 318 ms.
Say this honestly, it earns points The idle reading is not zero. With resolution: 20 the floor is about 20 ms, because that is how often it samples. So you compare against your own baseline, never against zero. Saying that out loud shows you have actually read the number, not just the API name.

Branch B — blocked. Which function?

Now, and only now, profile. Run under --cpu-prof while the load is on.

Sort by self time, not total time. Total time is sorted by the call stack.

The top of a total-time list is always main. It is 100% of the time and 0% of the problem.

Self time names code you can actually change. The usual suspects are worth naming out loud.

Blocking causeHow it hides
JSON.parse on a large bodyFast in testing, slow on the one big payload in production.
A synchronous fs callreadFileSync in a hot path, usually loading config per request.
A loop over a large arrayFine at 100 rows. Not fine at 100,000.
Synchronous crypto or compressionLooks like a library call, runs on your one thread.
A huge regular expressionCatastrophic backtracking on one unusual input.

Branch C — not blocked. What are we waiting on?

The loop is idle and requests still do not finish. So you are waiting, and something is full.

Resource causeThe number that proves it
Exhausted connection poolPool waiting count above zero. Every request queues for a free connection.
Unbounded Promise.allIn-flight request count equals the whole input list. The upstream throttles you.
No socket timeoutOpen sockets grow and never fall. One dead upstream holds them forever.
process.nextTick loopLoop delay is high but the CPU profile is nearly empty. Phases never run.
Downstream is simply slowYour latency matches theirs. Not your bug, and say so plainly.
The one that fits both branches A process.nextTick callback that queues another nextTick starves the loop with almost no CPU work. Loop delay is high, and the profile shows nothing worth optimising. If those two numbers disagree, say that out loud — it is the strongest single observation in this kata.

Branch D — is it memory?

If the hang gets worse over hours and a restart fixes it, suspect memory.

Watch used_heap_size, not rss. The signal is memory that never returns across two collections.

Then two heap snapshots, sorted by delta, and read the retainer path backwards.

Measured — Node v24.14.0, 2026-08-28 Heap used went from 3.4 MB to 43.5 MB with 200,000 objects retained. It returned to 3.4 MB once the reference was released. That return is what proves it was a held reference.
Say it in the simplest words — the Feynman check

1 · In plain words A hang has only a few possible causes. So do not guess which one it is.

Ask questions in an order where every answer throws away half the list. Four questions is enough to reach one cause.

2 · One analogy A doctor does not guess the illness from the door. They take a temperature first.

One cheap number splits the possibilities in two. Then the next test splits what is left.

…and where the analogy breaks A doctor's tests are slow and expensive, so they must ration them. Yours take seconds and cost nothing.

And the doctor has a patient who can describe the symptom. A hung process tells you nothing at all. Every fact you get, you have to go and measure. So there is no excuse for guessing first.

3 · The sticking point People hear "CPU is not pegged" and delete the whole blocked-loop branch. That is the trap in the brief.

A blocked loop is one thread. On eight cores that is about 12% of total CPU, which looks idle. Low CPU rules out nothing.

4 · Now you explain it back

In two or three sentences, say which number you collect first and why. Then say what a high reading rules out. Send it to me and I will tell you where the gap is. Do not skip this. Saying it in your own words is the part that proves it.

What they ask next

Follow-upThe short answer
"Loop delay is flat. Now what?"Then I am waiting, not computing. I count in-flight requests and pool waiters.
"Delay is high, profile is empty."A nextTick or microtask loop. It starves phases without burning CPU.
"Can you measure this in production?"Yes. monitorEventLoopDelay is cheap and safe to leave on.
"Why self time, not total time?"Total time is sorted by the stack, so main is always first and always useless.
"How do you stop it happening again?"Export loop delay as a metric, and alert on it. Guessing is now unnecessary.
Trap — jumping to a fix "It is probably a slow query, I would add an index" sounds decisive and scores badly. It names a fix for a cause nobody has shown. Naming the number you would collect first is worth more than naming a fix. If you truly must guess, say "my guess is X, and here is the measurement that would prove me wrong".

Remember this · the 20-second recap
  • They grade your search order, not your guess. Each answer must remove half the tree.
  • First measurement is always event loop delay. Measured: 3 ms under I/O, 155 ms under a CPU burst.
  • "CPU is not pegged" rules out nothing. One blocked thread on eight cores is about 12%.
  • Blocked → profile with --cpu-prof and sort by self time. Total time always names main.
  • Not blocked → count what is in flight. Pool waiters, unbounded Promise.all, sockets with no timeout.
  • High delay with an empty profile means a process.nextTick loop starving the phases.
  • Finish with the guard: export loop delay as a metric, so nobody guesses next time.

If you remember one thing: naming the number you would collect first beats naming a fix.
