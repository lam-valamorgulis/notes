Worker threads versus cluster

"Node is single-threaded, so how do you use eight cores?" There are two answers, and they solve different problems.

sprintDay 6 of 7. This lesson builds one domain-expert ability: predict how it behaves in a case never seen before. Day 6 in the plan · Glossary

Your win today: you can hear "use more cores" and ask the right question back. Is the work CPU-heavy, or is it just more requests? Then you pick the matching tool and say what it costs.

Start from the problem

One thread runs your JavaScript. The machine has eight cores.

So seven cores sit idle. That looks like an obvious waste, and interviewers always ask about it.

But "use more cores" hides two different problems. They need different tools.

The problemWhat is actually stuck
One request needs heavy mathsThe thread is held. Every other request waits behind it.
Many requests, each one cheapNothing is held. You simply want more capacity.

The first is a blocking problem. The second is a throughput problem.

Node ships one tool for each. They are not interchangeable.

Derive the first tool — worker threads

Take the blocking problem. You want the heavy maths off the main thread.

It must stay inside one process, because the result comes straight back into this request.

So you need a second JavaScript thread in the same process. That is worker_threads.

Now ask what those two threads share. Sharing a heap would need locks, and JavaScript has no locks.

So each worker gets its own V8 isolate and its own heap. Nothing is shared by accident.

If nothing is shared, values must travel as messages. A message is copied, not referenced.

Measured — Node v24.14.0, 2026-08-28 Starting one worker took 16 ms. A thousand message round trips took 25 ms in total. So a worker is cheap to talk to, and not free to create.

Copying is where the surprise lives. A big buffer costs real time to copy.

Measured — Node v24.14.0, 2026-08-28 Copying a 50 MB buffer to a worker took 28 ms. Transferring the same buffer took 2 ms. After the transfer the source buffer was left empty.

Transfer is the escape hatch. You pass the memory to postMessage in a transferList.

// Copy — safe, and 28 ms for 50 MB.
worker.postMessage({ buf });

// Transfer — 2 ms, and `buf` is empty here afterwards.
worker.postMessage({ buf }, [buf.buffer]);

That trade is the whole idea. Copying is safe and slow. Transfer is fast and takes the memory away.

Derive the second tool — cluster

Now take the throughput problem. Every request is cheap, and you just want more of them served.

You do not need shared memory at all. Each request is independent.

So the simplest answer is more whole processes, one per core. That is cluster.

One question remains. Eight processes cannot each bind port 3000.

So the primary process binds the port, and the workers share that one listening socket. That is the only thing they share.

Measured — Node v24.14.0, 2026-08-28 Two cluster workers each incremented an in-memory counter once. Each one then reported counter = 1. Not 2. They have separate memory, and there is no shared state.

That number is the whole warning. Anything you kept in a variable now exists eight times.

  • An in-memory cache becomes eight caches, each with different contents.
  • A rate limit of 100 becomes a real limit of 800.
  • A session in memory only works if the same worker gets the request.
  • A scheduled job runs eight times, once per worker.

The fix is always the same. Move the shared state out, into Redis or the database.

Say it in the simplest words — the Feynman check

1 · In plain words A worker thread is a second desk in the same room. You pass notes across, and each note is photocopied.

A cluster worker is a whole second office. Same front door, but a different room, different desk, different filing cabinet.

2 · One analogy A restaurant with one very slow dish. You can hire a second chef just for that dish, in the same kitchen.

Or you can open a second restaurant with the same phone number. One fixes a slow dish. The other serves more people.

…and where the analogy breaks Two chefs in one kitchen share the fridge. Two worker threads share almost nothing.

Every value you hand over is copied, and a 50 MB copy cost 28 ms. So a worker is not a free extra hand. It is a separate worker you must post things to.

3 · The sticking point People add cluster to fix a slow endpoint. It does not help at all.

Say one request holds the thread for two seconds. Eight processes means eight requests can each be stuck for two seconds. Latency is unchanged. Only throughput moved.

4 · Now you explain it back

In two or three sentences, say why cluster does not fix a slow endpoint. Then say what it does fix. Send it to me and I will tell you where the gap is. Do not skip this. Saying it in your own words is the part that proves it.

The decision, in one question

Say this, word for word

"First I ask whether the thread is held or whether I just want more capacity. Held means CPU work, and that is a worker thread. More capacity means cluster, or more containers. If the work is heavy and can wait, I take a third option and put it on a queue."

Say the third option out loud. It is the answer that separates strong candidates.

Heavy work that does not need an answer in this request should leave the request entirely.

Trap — "we use cluster, so we scale" cluster multiplies your process, and it multiplies every mistake in it. A leak leaks eight times faster. A cron job fires eight times. An in-memory rate limit becomes eight times looser. Say the shared-state consequence out loud, unprompted. It is the part interviewers listen for.
Drill · 4 minutes, out loud

The interviewer says: "Our API has eight cores and one Node process. Response time is fine, but we max out at 400 requests a second. What do you do?"

Answer out loud before reading on. A good answer names this as a throughput problem, not a blocking one. It reaches for cluster or more containers. Then it immediately lists what breaks: in-memory caches, rate limits and scheduled jobs.

Remember this · the 20-second recap
  • Two problems hide under "use more cores": the thread is held, or you want more capacity.
  • worker_threads is for CPU work. Separate isolate, separate heap, messages are copied.
  • Measured: worker start 16 ms, 1000 round trips 25 ms, a 50 MB copy 28 ms, a transfer 2 ms.
  • A transfer is fast because it moves the memory. The source is left empty.
  • cluster is for throughput. Processes share the listening socket and nothing else.
  • Measured: two cluster workers each reported counter = 1. Caches, limits and jobs all multiply.
  • The third answer is often best: put heavy work on a queue and out of the request.

If you remember one thing: cluster gives you more of the same speed. It never makes one request faster.
