The data layer — pool, transaction, cache, queue

Four pieces sit in almost every production Node service. Each one solves a real problem, and each one charges a price.

sprintDay 6 of 7. This lesson builds one domain-expert ability: say why it was built this way, and what that choice gives up. Day 6 in the plan · Glossary

Your win today: you can name all four pieces, say what problem each one solves, and say what it costs. You can also say what breaks when each one is set up wrong.

Start from the problem — connections are expensive

A database connection is not cheap. Opening one means a TCP handshake, then authentication, then session setup.

That takes milliseconds. A request that reads one row should take much less.

So opening a connection per request is wasteful. The connection costs more than the query.

The obvious fix is to keep one connection open forever and reuse it. That fails too.

One connection serves one query at a time. Node has many requests in flight at once.

So you need a small, fixed set of open connections. That is a pool.

The pool, in one sentence

"A pool keeps a fixed number of connections open, and puts a queue in front of them. When all of them are busy, the next request waits."

The pool, and the failure that looks like a hang

Read that last word again. The request waits. It does not fail.

That is the whole trap. An exhausted pool does not raise an error you can see.

It shows up as latency. Every request sits in the queue, waiting for a free connection.

From outside, the service looks hung. CPU is low. Memory is fine. Nothing is logged.

Trap — the pool you never sized Three things exhaust a pool: a query that got slow, a connection that was never released, and a transaction held open across a slow network call. All three look identical from outside. Always measure the wait time for a connection as its own metric. Without it you cannot tell a slow database from an empty pool.

Now the size. Instinct says a big pool serves more requests. Instinct is wrong here.

The database has a fixed number of cores and disks. Beyond that point, more connections only add contention.

Two hard limits also apply, and both matter in an interview.

  • Your pool size times your process count must stay under the database limit.
  • Under cluster, eight workers with a pool of 10 open 80 connections, not 10.

That second point connects straight to Lesson 16. It is a favourite follow-up.

Transactions — atomic, and therefore short

Some work must happen completely or not at all. The spine API has one such case.

Creating a short link writes a row and reserves a code. A half-finished version is worse than a failure.

A transaction gives you that. Everything inside it commits together, or none of it does.

The price is a lock, and a connection held for the whole transaction.

Trap — the transaction that waits on the network Never hold a transaction open across a call to another service. A payment API taking 800 ms means a row locked for 800 ms, and one pool connection gone for 800 ms. Under load, that alone empties the pool. Do the network call first, then open a short transaction to write the result.

The rule is easy to say and easy to defend. A transaction should touch the database and nothing else.

Cache — the read you stop doing

Look at the spine API's shape. A short link is written once and read many thousands of times.

Every read is the same query, for the same row, returning the same answer. That is waste.

So you keep the answer somewhere faster. That is a cache.

Redis is the usual choice in Node, because it is shared across every process.

An in-memory cache is faster but is not shared. Under cluster you get one cache per worker.

The cost is honest and you should say it plainly. A cache can be wrong.

The questionThe answer you can defend
What do you cache?Reads that repeat and change rarely. The redirect lookup, not the click count.
What TTL?The longest you can accept being wrong. Say the number and the reason.
How do you invalidate?Delete the key on write. TTL is the safety net, not the plan.
What if the cache is down?Fall through to the database. A cache must never be required.
What is the real risk?Stale data, and a cold cache after a restart hitting the database at once.

Queue — the work you move off the hot path

Back to the spine API. Every redirect should also count a click.

Writing that count inside the redirect makes every read a write. The fast path now depends on the database.

But nobody is waiting for the count. The user wants the redirect.

So you push a message and return. Something else counts it later. That is a queue.

BullMQ on Redis is the usual answer in Node. Name it, then say what it costs.

What a queue buysWhat it charges
The hot path stops waiting for slow workThe answer is no longer instant, and you must say so in the API
Retries with backoff, handled for youDelivery is at least once, so a job can run twice
A burst is absorbed instead of droppedA growing queue is a real failure you must alarm on
A bad job is parked in a dead-letter queueSomebody must look at that queue, or it is just a bin

At-least-once delivery is the part interviewers push on. Say the fix before they ask.

Say this, word for word

"Queues give at-least-once delivery, so I make the job idempotent. Each job carries a key. Running it twice with that key has the same effect as running it once."

Say it in the simplest words — the Feynman check

1 · In plain words Four small ideas. Keep a few phone lines open instead of dialling every time. That is the pool.

Do related writes together or not at all. That is the transaction. Remember popular answers. That is the cache. Write down slow jobs and do them later. That is the queue.

2 · One analogy A small clinic. Four doctors, one waiting room, and a receptionist who remembers common answers.

Anything that takes an hour goes into the afternoon list instead of holding the queue. Patients with quick questions keep moving.

…and where the analogy breaks A waiting room is visible. Everyone can see the queue growing, and someone reacts.

An exhausted connection pool is invisible. It raises no error and writes no log. It only shows up as latency, which is why you must measure the connection wait time as its own number.

3 · The sticking point People think a bigger pool means more speed. Past a small number it means less.

The database has a fixed number of cores and disks. Extra connections add contention, not capacity. And under cluster, eight workers with a pool of 10 open 80 connections.

4 · Now you explain it back

In two or three sentences, say why an exhausted pool looks like a hang. Then say which one number you would measure to prove it. Send it to me and I will tell you where the gap is. Do not skip this. Saying it in your own words is the part that proves it.

All four side by side

PieceThe problem it solvesWhat it costsWhat breaks when it is wrong
Pool Connections are slow to open, and one serves one query. A fixed ceiling, and a queue in front of it. Exhaustion shows as latency with no error and low CPU.
Transaction Related writes must all happen, or none of them. Locks, and one connection held for its whole life. Held across a network call, it empties the pool.
Cache The same read repeats thousands of times. The answer can be stale, and you must invalidate it. Wrong data, or a cold cache flooding the database.
Queue Slow work sits on a path where nobody is waiting. Delivery is at least once, so jobs must be idempotent. A growing queue, duplicate work, or an ignored dead-letter queue.
Drill · 5 minutes, out loud

The interviewer says: "Your API gets slow every afternoon. CPU is at 20%, memory is flat, and no errors are logged. Where do you look?"

Answer out loud before reading on. A good answer treats "slow with no errors" as a waiting problem. It names the pool first, then the number that proves it: the time a request spends waiting for a connection. It also names the usual causes — a slow query, a leaked connection, or a long transaction.

Remember this · the 20-second recap
  • A pool keeps a few connections open and queues the rest. Exhaustion looks like a hang, not an error.
  • Pool size must be small, and pool size times process count must stay under the database limit.
  • A transaction is atomic, so it holds a lock and a connection. Keep it short.
  • Never hold a transaction across a network call. That single mistake empties the pool.
  • A cache removes a repeated read. It costs staleness, so invalidate on write and keep a TTL.
  • A queue moves slow work off the hot path. Delivery is at least once, so jobs must be idempotent.
  • Measure the connection wait time. Without it you cannot tell a slow database from an empty pool.

If you remember one thing: each of the four buys speed and charges correctness. Say the price out loud, unprompted.
