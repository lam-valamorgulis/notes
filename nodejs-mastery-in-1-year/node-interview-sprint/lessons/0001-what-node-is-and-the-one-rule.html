What Node is, and the one rule

The first question of almost every Node interview. Own it, and the next ten minutes feel easy.

sprintDay 1 of 7. This lesson builds one domain-expert ability: explain it from first principles, with no jargon and no notes. Day 1 in the plan · Glossary

Your win today: you can answer "what is Node.js?" in about forty seconds. You name V8, libuv, and the one rule. You never say the words "Node is single-threaded" without finishing the sentence.

Start from the problem, not from the answer

Ten thousand people click your site in the same second. Most requests need something slow.

Slow means a database read, another company's API, or a file on disk. To a CPU that runs billions of operations a second, a few milliseconds is a very long wait.

The classic answer is one thread per request. A thread is a worker with its own memory, often one or two megabytes.

Here is the waste. While that worker waits for the database, it stands still. It holds memory and a slot and does nothing.

Ten thousand waiting requests means ten thousand mostly idle workers. You run out of memory long before you run out of work.

The question Node asked

What if there is one worker who never stands still? Hand the slow job to the operating system, take the next request, and come back when the answer arrives.

Derive the machine from that one question

If one worker must never wait, three things have to exist. Each one follows from the question, not from a design meeting.

What must existWhy it followsWhat Node calls it
Something that runs the JavaScriptThe CPU only understands machine code, not textV8, Google's engine
Something that talks to the operating systemV8 alone cannot open a file or a socketlibuv, a C library
A queue and a loop over itAnswers arrive later, so something must deliver themThe event loop

That is the whole runtime. Say it as one sentence and you have answered the question.

Say this, word for word

"Node is Google's V8 engine taken out of the browser. Beside it sits libuv, a C library that talks to the operating system. One thread runs my JavaScript. Slow work is handed away, and its result comes back as a queued callback."

The one rule, and the number that proves it

One thread runs your JavaScript. Nothing else can run while it is busy.

So a slow wait is free, and a slow calculation is not. That difference is the whole rule.

Measured — Node v24.14.0, 2026-08-28 A heartbeat set to fire every 50 ms was watched under two kinds of load. Under heavy I/O it ran 3 ms late. Under a single CPU burst it ran 155 ms late. Same process, same timer, two very different answers.

Say that number in an interview and you stop sounding like someone who read a blog post.

The honest part most candidates get wrong

"Node is single-threaded" is only half true. Say the half that is true.

Your JavaScript runs on one thread. Underneath, libuv keeps a pool of extra threads.

That pool handles file system work, DNS lookups, and some crypto calls. Network sockets do not use it, because the operating system already has a non-blocking way to wait on those.

The pool holds four threads by default. That number is a convention, not a law. It is set by UV_THREADPOOL_SIZE.

Measured — Node v24.14.0, 2026-08-28 Eight slow crypto.pbkdf2 calls were started at once. With the default they finished in two waves: four around 54–66 ms, then four around 109–119 ms. With UV_THREADPOOL_SIZE=8 all eight finished in one wave, 54–68 ms. 
// The measurement above. Run it yourself — it takes ten seconds.
import crypto from 'node:crypto';
const t0 = Date.now();
for (let i = 1; i <= 8; i++) {
  crypto.pbkdf2('secret', 'salt', 200000, 64, 'sha512', () => {
    console.log('task', i, 'done at', Date.now() - t0, 'ms');
  });
}
Say it in the simplest words — the Feynman check

1 · In plain words Node has one person doing the work. That person never sits and waits for anything.

When a job needs waiting, they hand it to someone else and take the next job. When the answer comes back, it joins a queue and gets picked up.

2 · One analogy A café with one barista and no seats behind the counter. You order, the barista starts the machine, and immediately serves the next person.

The machine works on its own. When a cup is ready, the barista calls the name. One person serves a long line, because nobody stands still.

…and where the analogy breaks A real barista can hand a cup over while the grinder runs. The Node thread cannot do two things at once, ever.

And the analogy hides the failure. If one customer asks the barista to count every bean in the shop, the whole line stops. That is a CPU burst, and it is the one thing Node cannot hand away.

3 · The sticking point People hear "asynchronous" and think "parallel". It is not. Only one piece of your JavaScript ever runs at a time.

Async means the waiting overlaps, not the running. Two database reads can be in flight together. Two for loops cannot.

4 · Now you explain it back

In two or three sentences, say why a slow database read costs Node nothing. Then say why a slow loop costs it everything. Send it to me and I will tell you where the gap is. Do not skip this. Reading the block above feels like understanding. Saying it in your own words proves it.

The follow-up questions, and the short answers

They askYou say
"Is Node single-threaded?"My JavaScript is. libuv keeps a pool of four threads underneath for files, DNS and some crypto.
"So Node is faster than Java?"No. It is cheaper per waiting connection. On raw CPU work it loses.
"When is Node the wrong tool?"When the work is CPU-heavy per request. Video encoding, big image work, heavy maths.
"What do you do if you need that anyway?"A worker thread, a separate process, or a different service. Day 6 covers the choice.
"Is Node a framework?"No. It is a runtime. NestJS is a framework that runs on it.
Trap — the memorised sentence with no mechanism "Node is non-blocking and event-driven, so it is very fast" is a slogan. It says nothing about who does the waiting. Always finish with where the wait actually happens: the operating system holds it, and the callback is queued. That one extra clause is the difference between a junior answer and a senior one.

Remember this · the 20-second recap
  • Node is V8 plus libuv. An engine that runs JavaScript, and a C library that talks to the operating system.
  • One thread runs your JavaScript. Nothing else runs while it is busy.
  • Waiting is handed to the operating system. The result comes back as a queued callback.
  • A slow wait is free. A slow calculation blocks every other request.
  • Measured: a 50 ms heartbeat was 3 ms late under I/O and 155 ms late under one CPU burst.
  • libuv keeps a pool of four threads for files, DNS and some crypto. Sockets do not use it.
  • "Async" means the waiting overlaps. It does not mean two pieces of your code run together.

If you remember one thing: Node makes waiting free and leaves thinking exactly as expensive as it was.
