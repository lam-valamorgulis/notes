The async ladder — callbacks, promises, await

Three rungs, thirty years apart. Each one fixed something real and gave something up. Say both halves and you sound senior.

sprintDay 2 of 7. This lesson builds one domain-expert ability: explain it from first principles, with no jargon and no notes. Day 2 in the plan · Glossary

Your win today: you can walk the ladder from callbacks to await in about sixty seconds. For each rung you name what it fixed and what it cost. You never say "await waits" without adding "but the thread does not".

Start from the problem

Day 1 gave us the rule. One thread runs your JavaScript, so nothing may sit and wait.

That creates an awkward question. If a function cannot wait for its answer, how does it return one?

It cannot. So it must not try. Instead you hand over a piece of code to run later, when the answer exists.

In 2009 JavaScript had exactly one way to do that. Pass a function as an argument.

The whole reason callbacks exist

A callback is not a design choice. It is the only tool the language had for saying "call me back later".

Rung 1 — callbacks, and the error-first rule

const { readFile } = require('node:fs');

readFile('a.txt', 'utf8', (err, data) => {     // error first, always
  if (err) return console.error(err);
  console.log(data.length);
});

The first argument is the error. That is a convention, not a language rule. Node chose it, and every Node API follows it.

It works. But it has three faults, and you should be able to name all three.

FaultWhat goes wrong
NestingThree dependent steps means three levels of indent. Ten steps is unreadable.
No compositionA callback is not a value. You cannot return it, store it, or put it in an array.
Errors by hopetry/catch does not reach inside. If you forget if (err), the failure is silent.

The second fault is the deepest one. Everything on rung 2 follows from fixing it.

Rung 2 — a promise is a value

Here is the idea in one line. Do not hand over the code. Hand back an object that stands for the future result.

Now the future result is a normal value. You can return it from a function.

You can store it in a variable, put it in an array, and pass it to another function.

const { readFile } = require('node:fs/promises');

const p = readFile('a.txt', 'utf8');   // p is a value, right now
const all = [p, readFile('b.txt', 'utf8')];   // so it goes in an array

That single change buys composition. Promise.all only exists because a promise is a value.

It also buys real error routing. A rejection travels down the chain until something catches it.

Two ways to get promises from old code util.promisify wraps any error-first function. node:fs/promises is the ready-made promise version of node:fs. Both were checked on Node v24.14.0 and read the same file to the same length.

What did rung 2 cost? A new vocabulary, and chains that still read sideways rather than downward.

Rung 3 — await is syntax over rung 2

This is the sentence that matters. async and await add no new capability.

An async function returns a promise. await unwraps one. That is all.

What it buys is enormous anyway. The code reads top to bottom, and try/catch works again.

async function load() {
  try {
    const a = await readFile('a.txt', 'utf8');
    const b = await readFile('b.txt', 'utf8');
    return a.length + b.length;
  } catch (err) {
    console.error('one of the reads failed:', err.message);
    throw err;
  }
}

And the cost? Two traps, both very common in review.

  • Accidental queueing. Two await lines in a row run one after the other. If they do not depend on each other, that is wasted time.
  • The forgotten await. The call still runs. The error escapes your try. Lesson 5 measures exactly what happens.

The proof that await does not block

This is the question that catches people. Say the answer with a measurement.

const t0 = Date.now();
const beat = setInterval(() => console.log('  heartbeat at', Date.now() - t0, 'ms'), 50);

async function slowJob() {
  await new Promise(r => setTimeout(r, 200));   // 200 ms of waiting
  console.log('slowJob done at', Date.now() - t0, 'ms');
}
await slowJob();
clearInterval(beat);
  heartbeat at 51 ms
  heartbeat at 102 ms
  heartbeat at 153 ms
slowJob done at 202 ms

The heartbeat fired three times during the await. The thread was free the whole time.

await pauses this function. It hands control back to the event loop.

Say it in the simplest words — the Feynman check

1 · In plain words A callback says "here is my phone number, ring me when it is done". You give away a piece of your code.

A promise flips it round. You keep something instead: an object that will hold the answer. Because you keep it, you can pass it around. await is a shorter way to open it.

2 · One analogy A cloakroom ticket. You hand over your coat and get a small numbered ticket.

The ticket is not the coat. But you can pocket it, or hand it to a friend. You can collect three tickets and fetch all the coats at once. Later you swap the ticket for the coat, or for a note saying it was damaged.

…and where the analogy breaks A cloakroom ticket does nothing until you use it. A promise has already started the work the moment it exists.

And a lost ticket only costs you a coat. A promise nobody ever opens can carry a rejection that crashes the process. Lesson 5 is entirely about that difference.

3 · The sticking point People read await as "stop the program here". It does not. It stops this function only.

Everything else keeps running. Measured above: a 50 ms heartbeat fired three times during a 200 ms await. Nothing else was frozen.

4 · Now you explain it back

In two or three sentences, say what a promise gave you that a callback could not. Then say what await added on top. Send it to me and I will tell you where the gap is. Do not skip this. Saying it in your own words is what proves you own it.

Two await lines, or one Promise.all?

This is the most common review comment on async code. Learn to spot it in one glance.

// Slow. b does not need a, but it waits for it anyway.
const a = await getUser(id);
const b = await getSettings(id);

// Fast. Both start now, both are awaited together.
const [a, b] = await Promise.all([getUser(id), getSettings(id)]);

The rule is one question. Does the second call need the first one's result?

If yes, two await lines is correct. If no, it is a bug you can measure.

Trap — "async makes it parallel" It does not. async changes what a function returns, nothing else. Two await lines run one after the other, exactly like sync code. Parallelism only appears when you start both promises before awaiting either. That is what Promise.all does, and it is why it exists.
Drill · 3 minutes, out loud

The interviewer says: "Why did the language add promises? Callbacks already worked."

Answer out loud before reading on. A weak answer says "callback hell". A strong answer says a promise is a value, so it can be returned, stored and combined. Then it names Promise.all as the thing that becomes possible.

Remember this · the 20-second recap
  • A callback was the only tool the language had for "call me back later".
  • Error-first is a convention Node chose. It is not a language rule.
  • A promise is a value standing for a future result. That is the whole leap.
  • Because it is a value, it composes. Promise.all exists only for that reason.
  • async/await adds no new power. It is syntax over promises.
  • await pauses one function, never the thread. Measured: a heartbeat fired three times during a 200 ms wait.
  • Two await lines run in sequence. Start both promises first to overlap them.

If you remember one thing: a promise is a value, and that single change is what bought everything else.
