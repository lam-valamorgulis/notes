Kata 3 — errors per hour in a 50 GB log

Twenty minutes. An empty file, a blank editor, no library. Talk the whole time.

The brief, exactly as they will give it

The task · 20 minutes on the clock

"We have a 50 GB application log. Each line starts with a timestamp. Count how many ERROR lines there are in each hour. The machine has 8 GB of RAM."

That is all they say. The RAM number is the whole question. They want to see whether you notice it.

A sample of the input. Assume many millions of lines like these.

2026-08-28T00:00:00Z ERROR request 0 finished
2026-08-28T01:00:00Z WARN  request 1 finished
2026-08-28T02:00:00Z ERROR request 2 finished

Set a timer for twenty minutes now. Do not scroll past this line until it rings.

The one decision the whole kata turns on

There are two shapes of answer. Only one of them can work.

ShapeMemory it needsVerdict
Read the file, then split itGrows with the file — 50 GB and moreFails immediately
Read line by line, keep a tallyGrows with the number of hoursWorks at any size

Say that difference out loud before you type. It is the point of the question.

The sentence that wins this kata

"My memory must depend on the number of distinct hours, not on the size of the file. A year of logs is under nine thousand keys. That fits anywhere."

The talking script — what to say while you type

Silence loses this kata. They cannot grade what they cannot hear.

StepSay this out loud
1 · Frame it"50 GB against 8 GB of RAM. So nothing that holds the file can work."
2 · Name the shape"I will stream it line by line and keep one counter per hour."
3 · Justify the tool"I use readline, because a chunk boundary cuts rows and letters."
4 · Show the key"The hour is the first thirteen characters. That is my map key."
5 · Bound the memory"The map holds one entry per hour. A year is under nine thousand."
6 · Offer the extras"Shall I add gzip input, or the shell one-liner I would really use?"
The opening — say it before your first keystroke

"Let me state my assumptions first. The file is far bigger than memory, so I will never hold it. I will stream it line by line with readline, and keep a map of one counter per hour. That makes memory depend on the number of hours, not on the file. Is that the scope you want, or would you rather I focus somewhere specific?"

Reference solution

Fourteen lines. Every one of them earns its place.

import { createReadStream } from 'node:fs';
import { createInterface } from 'node:readline';

const counts = new Map();
const rl = createInterface({
  input: createReadStream(process.argv[2]),
  crlfDelay: Infinity,          // treat \r\n as one line ending
});

for await (const line of rl) {
  if (!line.includes(' ERROR ')) continue;    // cheap filter first
  const hour = line.slice(0, 13);             // "2026-08-28T14"
  counts.set(hour, (counts.get(hour) ?? 0) + 1);
}

for (const [hour, n] of [...counts].sort()) console.log(hour, n);

The measured output looks like this.

2026-08-28T00 1191
2026-08-28T01 1191
2026-08-28T02 8334
2026-08-28T03 1190

Why each line is safe

LineWhat it buys you
createReadStreamBytes arrive in small chunks. The file is never held whole.
createInterfaceHolds partial bytes and partial rows. Yields only complete lines.
crlfDelay: InfinityA Windows line ending counts as one break, not two.
for awaitApplies backpressure for free. The stream pauses while you work.
includes firstSkips most lines before any slicing. Cheap test before costly work.
slice(0, 13)One small string per line, and it is thrown away straight after.
MapOne entry per hour. This is the only thing that survives the loop.

The proof — memory does not follow the file

The same program was run on two files. One is twenty times bigger than the other.

Measured — Node v24.14.0, 2026-08-28 On a 9.5 MB log it held 24 hour keys and peaked at 61 MB RSS. On a 190 MB log it held the same 24 keys and peaked at 85 MB. Twenty times the data, almost the same memory.

Now the version that fails, on the same 190 MB file.

Measured — Node v24.14.0, 2026-08-28 readFileSync plus split('\n') on the same 190 MB log peaked at 588 MB. Scale that to 50 GB and the process is killed long before it finishes.
Say it in the simplest words — the Feynman check

1 · In plain words You are counting, not collecting. A counter for each hour is tiny, however many lines you read.

So read one line, add one to a number, and throw the line away. The file can be any size at all.

2 · One analogy Counting cars at a junction with a clicker. You do not write down every number plate.

You keep one clicker per hour. At the end of the day you have twenty-four numbers on one small card.

…and where the analogy breaks A clicker is safe because the number of hours is fixed. Your key is not always fixed.

Group by hour and the map stays small forever. Group by request id and the map grows with the file, and you are back to holding 50 GB. The safety comes from the key, not from streaming.

3 · The sticking point People think "streaming" is the answer by itself. It is only half.

Streaming bounds the input you hold. It says nothing about the result you build. A streamed read into an unbounded map still runs out of memory.

4 · Now you explain it back

In two or three sentences, say what this program's memory actually depends on. Then say which change would break it. Send it to me and I will tell you where the gap is. Do not skip this. Saying it in your own words is the part that proves it.

What they will ask next

Assume you finish. The follow-ups are the real interview.

Follow-upThe short answer
"How much memory does this use?"One entry per hour. Measured: 61 MB on a 9.5 MB file, 85 MB on 190 MB.
"Group by request id instead."Then the map grows with the file. I would need a database or a disk sort.
"The file is gzipped."Put createGunzip() between the read stream and readline.
"Why not split('\n')?"It needs the whole file as one string. Measured: 588 MB for a 190 MB file.
"Why readline and not manual chunks?"A chunk boundary cuts rows and multi-byte letters. readline handles both.
"Can you make it faster?"Split the file by byte range across workers, then merge the maps.
"What would you really do?"Say it honestly: grep and awk in a shell. Then explain when Node wins.
Trap — the answer that sounds clever and is wrong Do not reach for worker_threads in the first minute. This job is I/O-bound, not CPU-bound, so more threads mostly add copying. Mention parallel byte ranges only as an optimisation after measuring. Reaching for it early tells the interviewer you did not think about where the time actually goes.

Remember this · the 20-second recap
  • The RAM number in the brief is the question. Say it out loud before you type.
  • Memory must follow the number of hours, never the number of bytes.
  • readline gives whole lines, and it fixes both the row and the letter boundary.
  • for await applies backpressure for free. The stream pauses while you work.
  • Measured: 61 MB on a 9.5 MB log, 85 MB on a 190 MB log, same 24 keys.
  • Measured: readFileSync plus split peaked at 588 MB on that 190 MB log.
  • Streaming bounds the input. It does not bound an unbounded result map.
