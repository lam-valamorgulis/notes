Operational versus programmer errors, and a real leak

Two production questions with one thing in common. Both are answered badly by candidates who have never been paged at three in the morning.

sprintDay 5 of 7. This lesson builds one domain-expert ability: debug a problem in it that has no ready answer online. Day 5 in the plan · Glossary

Your win today: you can sort any error into two buckets, and say what each bucket does to the process. You can also say how you find a leak, with a number for the heap.

Part one — start from the problem

An error reaches the top of your program. Nobody caught it.

Should the process die, or should it keep serving?

Both answers are correct. They are correct for different errors, and telling them apart is the whole skill.

Derive the split

Ask one question about the error. Did you expect this could happen, and did you write a plan for it?

If yes, it is an operational error. The outside world failed in a way you already knew about.

Your code is still correct. Your assumptions still hold. So handle it and keep serving.

If no, it is a programmer error. It is a bug in your code.

Now you do not know what else is wrong. A lock may be held. A transaction may be open.

You cannot reason about the process any more. So end it, and let the platform start a clean one.

Operational — handle itProgrammer — crash
An upstream returned 503Cannot read properties of undefined
A request timed outA function called with the wrong argument
The JSON body was malformedAn invariant you believed was broken
The disk was fullA promise rejection nobody handled
A connection was refusedA typed field that is suddenly undefined
Say this, word for word

"An operational error is the world failing in a way I planned for, so I handle it and keep serving. A programmer error means my process state is now unknown, so the safe move is to crash and restart."

The trap that turns a crash into a zombie

Somebody sees crashes in the logs. They add a handler to stop them.

process.on('uncaughtException', (err) => {
  console.log('handler saw:', err.message);   // and then… nothing
});

setTimeout(() => {
  console.log('still running 100 ms after the throw');
}, 100);

throw new Error('programmer error');
Measured — Node v24.14.0, 2026-08-28 That program printed handler saw: programmer error, then printed still running 100 ms after the throw, then exited with code 0. Registering the handler kept the process alive, and the exit code said everything was fine.

Look at what that costs you. The bug is still there.

The request that threw is half-done. Whatever it held is still held.

And the exit code is 0, so nothing alerts. Your monitoring reports a healthy service.

A crash is loud, fast and safe. A zombie is silent, slow and wrong.

The one correct use of uncaughtException Treat it as a last-chance logger, never as recovery. Log the error with its stack, flush the log, then exit with a non-zero code. Same for unhandledRejection. The handler exists so the error is not lost, not so the process survives it. 
process.on('uncaughtException', (err) => {
  logger.fatal({ err }, 'uncaught exception — exiting');
  logger.flush?.();
  process.exitCode = 1;          // non-zero, so the platform notices
  setTimeout(() => process.exit(1), 1000).unref();   // backstop only
});

Part two — memory that grows

Now the second production question. Memory is rising. Is it a leak?

Rising memory is normal. V8 grows the heap when it is cheaper than collecting.

So "memory went up" proves nothing on its own. You need a different signal.

The signal that means leak

Memory that rises and never returns across two collections. Not memory that rises. The collector asks "is this reachable?", never "is this needed?". So a leak is memory you still hold and no longer want.

Watch used_heap_size, not rss. RSS is noisy.

RSS includes buffers, the thread pool, and memory the operating system has not taken back yet.

Finding it — two snapshots and one screen

One snapshot shows what exists. It cannot tell you what is new.

Two snapshots show what grew. Take one, do the suspect work many times, take another.

Compare them sorted by delta. Then open the retainer path for the biggest growth.

The retainer path is the chain of references keeping those objects alive. Read it backwards and it becomes a sentence.

That sentence points at one line of your code. This is the part no tool can do for you.

Measured — Node v24.14.0, 2026-08-28 Heap used went from 3.4 MB to 43.5 MB with 200,000 objects retained. After the reference was released it went back to 3.4 MB. That return is the proof it was a held reference, not a collector problem.
The four shapesWhat it looks like
Growing collectionA Map used as a cache with no eviction and no size limit.
Forgotten listenerA handler added per request, never removed. Node's MaxListeners warning fires.
Fat closureA closure captures its whole scope, so a small callback holds a large buffer.
Uncleared timerA setInterval nobody clears, holding everything it references.
Say it in the simplest words — the Feynman check

1 · In plain words Some failures are part of the job. A slow network, a bad request, a full disk. You planned for those, so you deal with them and carry on.

Other failures mean your own code is wrong. Now you do not know what else is broken, so the safe move is to stop and start fresh.

2 · One analogy A restaurant. A customer sending a dish back is expected, so you cook another one and the evening continues.

The chef fainting is not expected. You do not keep serving. You close the kitchen, because nobody knows what is half-cooked.

…and where the analogy breaks The restaurant knows the chef fainted. Your process does not know what it half-did.

And a real kitchen cannot prop the chef up in a chair and pretend. Your code can. That is uncaughtException with no exit. I measured it. The process was still running 100 ms after the throw, and it exited with code 0. It looked healthy to every alert you have.

3 · The sticking point People think crashing is the failure. It is not. Crashing is the safe choice when the state is unknown.

The unsafe choice is carrying on with a process you can no longer reason about. Crashing is loud, fast and recoverable. A zombie is silent and wrong.

4 · Now you explain it back

In two or three sentences, say which errors you handle and which you crash on. Then say why a zombie is worse than a crash. Send it to me and I will tell you where the gap is. Do not skip this. Saying it in your own words is the part that proves it.

The follow-up questions, and the short answers

They askYou say
"So you like your service crashing?"On a bug, yes. A clean restart beats an unknown state.
"How do you restart it?"The platform does it. That is what a non-zero exit code is for.
"Where does unhandledRejection fit?"Same rule. Log it, then exit non-zero. Never swallow it.
"Memory grows 40 MB an hour. Restart nightly?"That buys time and answers nothing. It fails later, under more traffic.
"Which number tells you it is a leak?"used_heap_size not returning across two collections. RSS is too noisy.
Drill · 4 minutes, out loud

The interviewer says: "A teammate added an uncaughtException handler that logs and continues. Crashes stopped. Are you happy?"

Answer out loud before reading on. A strong answer says the crashes did not stop, only the reporting did. It names the unknown state, the half-done request, and the exit code of 0 that stops anyone being paged. Then it offers the correct version: log, flush, exit non-zero.
