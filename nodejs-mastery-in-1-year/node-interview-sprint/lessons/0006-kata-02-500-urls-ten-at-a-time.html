That is all they say. The limit is given. Everything else — the timeout, the retry policy, the shape of the result — is a decision they are watching you make.

Before you type: sixty seconds of talking

The opening — say it before your first keystroke

"Let me state my assumptions. I will write a pool of ten workers pulling from one shared list. Not batches of ten. I will keep results in input order."

Batches or a pool? Say why you chose

Most candidates write batches. It is the obvious idea, and it is worse.

Step 1 — the pool, on its own

Write this first, with nothing else. It is the part they are really grading.

async function mapWithLimit(items, limit, worker) {
  const results = new Array(items.length);
  let next = 0;                                  // the shared cursor

  async function runOne() {
    while (next < items.length) {
      const i = next++;                          // claim an index, then release
      results[i] = await worker(items[i], i);
    }
  }

  const runners = Array.from({ length: Math.min(limit, items.length) }, runOne);
  await Promise.all(runners);
  return results;
}

Three things to say about it while you type. Each is one sentence.

  • next++ is safe. One thread runs this, so no two workers can claim the same index.
  • Order is kept. Results go to results[i], not to a push.
  • Math.min matters. Ten workers over three items would leave seven doing nothing.
Measured — Node v24.14.0, 2026-08-28 Over 500 items with a limit of 10, peak concurrency was exactly 10, and all 500 results came back in input order. The same 500 items through Promise.all peaked at 500.

Step 2 — the timeout, and why a race is not one

The obvious idea is Promise.race against a timer. Do not do it, and say why.

A race decides when you stop waiting. The request is still open, still holding a socket.

With 500 URLs that leaks connections until the process dies. A real timeout must abort the request.

const res = await fetch(url, { signal: AbortSignal.timeout(300) });

That closes the socket. The rejection arrives with err.name === 'TimeoutError', which you can tell apart from your own AbortError.

Step 3 — the retry, and the two rules

const sleep = (ms) => new Promise(r => setTimeout(r, ms));

async function fetchWithRetry(url, { retries = 3, timeoutMs = 300 } = {}) {
  for (let attempt = 0; ; attempt++) {
    try {
      const res = await fetch(url, { signal: AbortSignal.timeout(timeoutMs) });

      if (res.status >= 400 && res.status < 500) {
        return { url, ok: false, status: res.status };   // never retry a 4xx
      }
      if (!res.ok) throw new Error('HTTP ' + res.status); // 5xx → retry
      return { url, ok: true, body: await res.text() };

    } catch (err) {
      if (attempt >= retries) return { url, ok: false, error: err.name };
      const backoff = 50 * 2 ** attempt;                 // 50, 100, 200 ms
      await sleep(backoff + Math.random() * backoff);    // jitter
    }
  }
}
RuleSay this
Never retry a 4xxThe request is wrong. Sending it again cannot change the answer.
Only retry safe methodsA retried POST can charge a card twice. GET is safe.
BackoffA failing service needs room to recover. Doubling gives it room.
JitterWithout it, 500 clients retry in the same millisecond and fail together.
Return, do not throwOne dead URL must not lose the other 499 results.

Putting it together, and the measured result

const out = await mapWithLimit(urls, 10, (url) => fetchWithRetry(url));

console.log('ok    :', out.filter(r => r.ok).length);
console.log('failed:', out.filter(r => !r.ok).length);

Say it in the simplest words — the Feynman check

1 · In plain words You have 500 jobs and you want ten happening at once. Do not cut the list into groups of ten.

Instead hire ten workers and give them one shared list. Each worker takes the next job whenever it is free.

2 · One analogy Ten checkouts in a supermarket, with one queue feeding all of them. When a till frees up, the next person goes there.

The alternative is a separate queue per till. Then one slow customer holds up nine people who could have been served.

…and where the analogy breaks Supermarket tills are real, separate people. Your ten workers are not parallel at all.

They are ten async functions on one thread. The overlap is in the waiting, never in the running. If the worker did heavy CPU work instead of a fetch, the pool would buy you nothing.

3 · The sticking point People worry that next++ needs a lock. It does not, and saying why earns you a point.

One thread runs your JavaScript, and next++ has no await in the middle. So nothing can interleave between reading and writing. In a threaded language this exact line would need a lock.

4 · Now you explain it back

In two or three sentences, say why a pool beats fixed batches. Then say why the pool cannot help CPU-heavy work. Send it to me and I will tell you where the gap is. Do not skip this. It is the answer to the follow-up, and the follow-up is where the round is decided.

What they will ask next

Follow-upThe short answer
"Why not batches of ten?"Batches wait for the slowest in each group. A pool never leaves a worker idle.
"Why not Promise.race for the timeout?"A race stops me waiting. It does not close the socket. That leaks connections.
"Why jitter?"Without it, every client retries at the same instant and knocks the service over again.
"Would you use a library?"Yes, p-limit, and undici for connection reuse. I wrote it by hand to show the mechanism.
"How do you pick ten?"From the other service's limit, not from a feeling. I would measure and tune it.
"What if the list were 10 million?"I would stream the input rather than build an array. That is Day 3.
"How do you test the concurrency?"Count live workers in the fake worker and assert the peak never passes the limit.

Remember this · the 20-second recap
  • A pool, not batches. Batches wait for the slowest item in every group.
  • Ten workers share one cursor. next++ needs no lock, because one thread runs it.
  • Write to results[i] to keep input order. Never push.
  • A timeout must abort the request. Promise.race leaks the socket.
  • Never retry a 4xx. Retry 5xx and network errors, with backoff and jitter.
  • Return a result per URL. One dead URL must not lose the other 499.
  • Measured: the pool peaked at 10 in flight, unbounded Promise.all peaked at 500.

If you remember one thing: they are grading the narration as much as the code.
