Kata 1 — predict the print order

Five minutes. A whiteboard, or paper. No editor, no Node, no notes. Talk the whole time.

The brief, exactly as they will give it

The task · 5 minutes on the clock

"Here is a small Node file. Tell me what it prints, and in what order."

That is all they say. They will not tell you it is CommonJS. They will not tell you the file read is fast. Both of those are decisions you must make out loud. 
// order.cjs — CommonJS. Assume the file read succeeds.
const { readFile } = require('node:fs');

console.log('A');

setTimeout(() => {
  console.log('B');
  process.nextTick(() => console.log('C'));
  Promise.resolve().then(() => console.log('D'));
}, 50);

readFile(__filename, () => {
  console.log('E');
  setTimeout(() => console.log('F'), 0);
  setImmediate(() => console.log('G'));
  process.nextTick(() => console.log('H'));
});

Promise.resolve().then(() => console.log('I'));

process.nextTick(() => console.log('K'));

(async () => {
  console.log('M');
  await null;
  console.log('N');
})();

console.log('L');

Set a timer for five minutes now. Do not scroll past this line until it rings.

The talking script — what to say while you write

Silence loses this kata. They cannot grade what they cannot hear.

Say these five things, in this order. Each one is a whole sentence out loud.

StepSay this out loud
1 · Frame it"I will use one rule: sync to the end, drain nextTick, drain microtasks, then move a phase."
2 · Sort the lines"Let me split these into sync, nextTick, microtasks, timers, poll and check."
3 · Walk it"First pass: A, then M because an async body runs to its first await, then L."
4 · Flag the risk"The 50 ms timer is well after the file read, so poll wins. If it were zero, I would call it a race."
5 · Read it back"So: A M L K I N E H G F B C D. Shall I justify any group?"
The opening — say it before your first mark on the board

"Before I trace this, let me state the rule I am using. Run the synchronous code to the end. Then drain the process.nextTick queue completely. Then drain microtasks completely. Only then advance one phase of the loop. I will apply that at every step and say which bucket each line goes in."

Say it in the simplest words — the Feynman check

1 · In plain words Do not try to order thirteen things at once. Sort them into four boxes first.

Sync goes in box one. Everything waiting at the checkpoint goes in box two. Then the phases, in their fixed order. Inside each box, source order decides.

2 · One analogy Sorting post. You do not walk to thirteen houses in a random order and hope.

You sort the pile into streets first. Then you walk one street at a time, in the order you always walk them.

…and where the analogy breaks Post sorting is done once, at the start. This sorting is not.

Every callback you run can drop new letters into boxes you have already emptied. That is what H, C and D are. You must re-check the checkpoint after every single callback.

3 · The sticking point People read the file top to bottom and try to answer top to bottom. The file's order is almost irrelevant.

Source order only decides ties inside one box. Across boxes it decides nothing. Reading top to bottom is exactly how M ends up in the wrong place.

4 · Now you explain it back

In two or three sentences, explain why G comes before F. Both were queued in the same callback. Send it to me and I will tell you where the gap is. Do not skip this. It is the part that turns a memorised answer into a rule you can reuse.

What they ask next

Assume you get the order right. The follow-ups are the real interview.

Follow-upThe short answer
"What if the timer were 0 instead of 50?"Then the timer and the file read race, and I would say so rather than guess.
"What if this were an ES module?"Top-level order flips: I before K. I measured that. Inside callbacks nothing changes.
"Why does G beat F?"We are in poll. Check is the very next phase. Timers is a whole lap away.
"Could H starve the loop?"Only if it queued another nextTick each time. One is harmless.
"Does any of this matter in real code?"Rarely for order. It matters a lot for starvation and for blocking the thread.
Trap — the confident wrong answer A candidate who says "setImmediate always runs before setTimeout" scores worse than one who says "in the main module that races, inside a callback it is fixed". Naming the uncertainty is a senior move. Guessing to sound sure is the fastest way to lose the round.

Score yourself

Run it twice today

Run 1: five minutes, out loud, on paper. Run 2, later in the day: same puzzle, no notes, no scrolling back.

Tick honestly. Anything unticked after run 2 is tomorrow's warm-up.
  • I stated the rule before tracing anything.
  • I sorted into buckets instead of reading top to bottom.
  • I never went silent for more than about ten seconds.
  • M is in the sync group, not after L.
  • K before I, because nextTick drains first.
  • H right after E, from the checkpoint inside the callback.
  • G before F, and I said why in one sentence.
  • I named the 50 ms timer as the thing that made poll safe to put first.
  • I said what would change if the timer were zero.

Remember this · the 20-second recap
  • Sort into buckets first. Sync, checkpoint, then the phases in order.
  • Source order decides ties inside a bucket, and nothing across buckets.
  • The checkpoint runs again after every callback, not only at the start.
  • An async body is synchronous up to its first await.
  • Inside a poll callback, setImmediate beats setTimeout by a whole lap.
  • Say "this pair races" when it does. Naming uncertainty scores higher than guessing.
  • Run it twice. The second run is the one that tells the truth.

If you remember one thing: they are grading the narration as much as the answer.
