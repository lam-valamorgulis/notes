Day 3 of 7 · Lesson 8 · Streams and memory

pipeline versus pipe, and the chunk trap

Two stream bugs that never raise an error. One leaks file descriptors. The other corrupts your data quietly.

sprintDay 3 of 7. This lesson builds one domain-expert ability: predict how it behaves in a case never seen before. Day 3 in the plan · Glossary

Your win today: you can say why pipeline exists, in one sentence, with a measured fact. And you can explain why a chunk boundary breaks both lines and letters.

Problem one — the sink fails halfway

You copy a big file to a network target. Halfway through, the target rejects a write.

The writable stream errors. Ask the question that matters. What happens to the reader?

Nothing happens to it. It is a separate object. It still holds an open file descriptor.

It may also keep reading, because nobody told it to stop. In a server that runs this per request, you leak a descriptor every time.

Measured — Node v24.14.0, 2026-08-28 After the sink errored, pipe left the source with destroyed: false. The same failure through pipeline gave destroyed: true.

Derive why pipe cannot fix this

Look at what pipe is. It is a method on one readable stream.

It knows about its own source and one destination. It forwards data and it honours backpressure. That is all.

It does not own the chain. With three streams there are three pipe calls, and none of them can see the whole line.

So no single pipe call has the information needed to tear everything down. It is not a bug. It is a missing job.

Say this, word for word

"pipe forwards data between two streams. pipeline owns the whole chain, so it can destroy every stream when any one of them fails."

// pipe — no owner. A sink error leaves the source open.
source.pipe(gzip).pipe(sink);
sink.on('error', handle);       // source and gzip are still alive

// pipeline — one owner for the whole chain.
import { pipeline } from 'node:stream/promises';
await pipeline(source, gzip, sink);   // any failure destroys all three

The promise form also gives you one try/catch instead of an error listener on every stream.

Problem two — a chunk is not a line

You read a CSV file and process it row by row. The obvious code looks correct.

// WRONG — splits each chunk on its own.
for await (const chunk of createReadStream('rows.csv')) {
  for (const line of chunk.toString('utf8').split('\n')) {
    process(line);
  }
}

A chunk is a fixed number of bytes. The default is 65536.

Your rows are not 65536 bytes long. So a boundary lands in the middle of a row, again and again.

That row becomes two fragments. Both look like valid rows to your code. Neither is one.

Measured — Node v24.14.0, 2026-08-28 Naive per-chunk splitting damaged 1093 of 2000 CSV rows, with no error at all. Carrying the remainder damaged 0. The exact count changes with chunk size. With a 128-byte chunk the same 2000 rows produced over 2000 broken fragments.

The worse half — a chunk is not even a letter

A boundary can also land inside a single character. UTF-8 uses one to four bytes per character.

Take the word 'việt'. It is 4 characters and 6 bytes.

const s = 'việt';
s.length                          // 4  — characters
Buffer.from(s, 'utf8').length     // 6  — bytes
// bytes: 76 69 e1 bb 87 74   — the letter ệ takes three bytes

Now cut at byte 3 and decode each half on its own. That is exactly what per-chunk toString does.

head.toString('utf8')    // "vi�"   — one replacement character
tail.toString('utf8')    // "��t"  — two more
head + tail              // "vi���t" — three, and ệ is gone forever

The letter cannot be recovered by joining the strings afterwards. The decoding already threw the bytes away.

The fix, derived

The last piece of a chunk is not a finished row. So do not treat it as one.

Keep it. Glue it to the front of the next chunk. That is the whole pattern.

// RIGHT — carry the remainder across the boundary.
let rest = '';
for await (const chunk of createReadStream('rows.csv')) {
  const parts = (rest + chunk.toString('utf8')).split('\n');
  rest = parts.pop();          // the last piece is unfinished — keep it
  for (const line of parts) process(line);
}
if (rest) process(rest);        // the final row has no newline after it

That fixes the rows. It does not fix the letters, because chunk.toString() already destroyed them.

For text, do not write this at all. Use the tool that solves both problems.

// BEST — readline handles rows and multi-byte letters, in constant memory.
import { createInterface } from 'node:readline';

const rl = createInterface({
  input: createReadStream('rows.csv'),
  crlfDelay: Infinity,          // treat \r\n as one line ending
});

for await (const line of rl) process(line);
Say it in the simplest words — the Feynman check

1 · In plain words Node hands you the file in blocks of a fixed size. It counts bytes, and it counts nothing else.

It does not know where your rows end. It does not know where your letters end. Both get cut in half, and neither cut raises an error.

2 · One analogy A long letter cut into pieces with a ruler, every ten centimetres. The cuts land in the middle of words.

If you read each piece on its own, you get half-words. If you keep the last half-word and join it to the next piece, you get the letter back.

…and where the analogy breaks With paper you can always see the cut and tape it back. With bytes you cannot.

Once you call toString() on half a letter, the broken bytes become a replacement character. Joining the strings afterwards does not bring the letter back. The information is already gone.

3 · The sticking point People believe a chunk is a "piece of text". It is a count of bytes, and the count was chosen by highWaterMark.

Nothing about it lines up with your data. And because both failures are silent, the code looks correct in review and in a small test file.

4 · Now you explain it back

In two or three sentences, say why joining two decoded halves does not repair a split letter. Then say what you would use instead. Send it to me and I will tell you where the gap is. Do not skip this. Saying it in your own words is the part that proves it.

The follow-up questions, and the short answers

They askYou say
"Why pipeline over pipe?"pipe forwards data. pipeline owns the chain, so it destroys every stream on failure.
"What breaks with pipe?"Measured: the source stayed destroyed: false. In a server that is a leaked descriptor per request.
"Is pipe ever fine?"For a short script that exits anyway. Never in a long-running service.
"Why not split each chunk?"A chunk is a byte count. Boundaries land inside rows and inside letters.
"How do you fix the rows?"Carry the last fragment into the next chunk. Or use readline.
"And the letters?"readline, or setEncoding, or StringDecoder. All three hold partial bytes.
