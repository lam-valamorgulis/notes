Day 2 of 7 · Lesson 5 · Async under pressure

Async errors, and the four combinators

The most common silent failure in production Node. Learn to spot it in someone else's code in five seconds.

sprintDay 2 of 7. This lesson builds one domain-expert ability: judge someone else's work in it, and say what is wrong and why. Day 2 in the plan · Glossary

Your win today: you can read a pull request and find the missing await in five seconds. You can say what each of the four combinators does with the losers. And you know why process.exitCode beats process.exit().

Start from the problem

An error in synchronous code is loud. It throws, the stack unwinds, and something catches it or the process dies.

An async error has no stack to unwind. By the time it happens, the function that started it has already returned.

So the error has nowhere to go. It has to be carried somewhere instead.

A promise carries it. The rejection sits inside the promise object, waiting for someone to look.

And that is the whole danger. If nobody looks, nobody knows.

Say this out loud

A synchronous error interrupts you. An async error waits for you. If you never open the promise, the failure is silent.

The missing await — measure it, do not guess

This is the bug. It is three characters, and it defeats a try/catch completely.

async function save() { throw new Error('db is down'); }

try {
  save();                      // ← no await
} catch (err) {
  console.log('caught:', err.message);
}
console.log('still running');

Predict the output before you read on. Most people get it wrong.

Measured — Node v24.14.0, 2026-08-28 The catch block never ran. The process printed still running, then crashed with an unhandled rejection and exit code 1. 
still running
Error: db is down
    at save (…)
Node.js v24.14.0
# exit code: 1

Why? Because save() returned a promise, and a promise is a value.

try only catches what is thrown inside its block. Nothing was thrown. A rejected promise was created and dropped.

Adding await fixes it. await turns a rejection back into a throw.

The five-second review rule Scan every line that calls an async function. If the result is not awaited, returned, or given a .catch(), that line is a bug. This one check finds most async faults in a pull request.

The forEach one is worth saying out loud. It is the classic interview trap.

// Broken. forEach does not wait, and it drops every promise.
items.forEach(async (item) => { await save(item); });
console.log('all saved');            // a lie — nothing is saved yet

// Correct, one at a time.
for (const item of items) await save(item);

// Correct, all at once.
await Promise.all(items.map(save));

process.exitCode, not process.exit()

When a service must fail, it should fail with a non-zero code. There are two ways, and only one is safe.

process.exit() stops the process immediately. Pending work is thrown away.

process.exitCode only sets the number. The process still finishes what it was doing.

// A: setTimeout(…, 10) then process.exitCode = 1
set exitCode, work carries on
pending timer ran
# exit code: 1

// B: setTimeout(…, 10) then process.exit(1)
calling process.exit(1) now
# exit code: 1
// the pending timer never ran
Measured — Node v24.14.0, 2026-08-28 Both files exited with code 1. Only the exitCode version let the pending timer run. process.exit() killed it.

In a real service that pending work is a log write, a flush, or a reply to a user. Day 5 makes this the centre of graceful shutdown.

The four combinators, and what happens to the losers

Now that a promise is a value, you can combine several. There are four ways, and interviewers ask about all four.

Here is the measured behaviour. Three jobs: one succeeds at 30 ms, one fails at 10 ms, one succeeds at 50 ms.

CombinatorSettles whenMeasured resultThe losers
Promise.allFirst rejection, or all succeedrejected: b failsKeep running
Promise.allSettledEvery one has settledfulfilled, rejected, fulfilledNone — all reported
Promise.raceFirst to settle, either wayrejected: b failsKeep running
Promise.anyFirst to succeedaKeep running
The sentence that wins this question None of the four cancel anything. A combinator only decides when you stop waiting. The other promises keep running to the end. Measured: Promise.all rejected at 0 ms, and the two other jobs still finished at 61 ms and 90 ms.

That is why a race against a timer is not a timeout. The slow request is still open.

A real timeout needs AbortController or AbortSignal.timeout, which the kata uses.

Why unbounded Promise.all kills a service

Here is the code everybody writes first. It looks perfect.

const results = await Promise.all(urls.map(fetch));   // 500 URLs

All 500 requests start in the same millisecond. Nothing limits them.

Four things break, and you should be able to list them.

  • Sockets and file descriptors. The operating system has a limit, and you hit it.
  • Memory. Every response body is held until the last one arrives.
  • The other service. You just sent it 500 requests at once. It rate-limits you, or falls over.
  • The result. One rejection loses all 500, because Promise.all returns nothing on failure.

The fix is a limit. Ten at a time, never more. That is Kata 2, and you write it from an empty file.

Say it in the simplest words — the Feynman check

1 · In plain words A normal error shouts at you. An async error puts a note in a box and walks away.

If you never open the box, you never see the note. The program carries on as if everything worked.

2 · One analogy A letter delivered to your door. A sync error is someone knocking and shouting until you answer.

An async error is a letter in the box. It is definitely there. But it changes nothing until you go and open the box.

…and where the analogy breaks An unopened letter is harmless. An unopened rejection is not.

Node watches for promises nobody opened. When it finds one, it crashes the process. Measured: exit code 1, with the stack printed. So the letter you ignore eventually burns the house down.

3 · The sticking point People believe try/catch covers everything inside its braces. It does not.

try catches what is thrown. Calling an async function without await throws nothing. It creates a value and drops it, and the catch block is never reached.

4 · Now you explain it back

In two or three sentences, say why a missing await defeats a try/catch. Then say what await actually does to a rejection. Send it to me and I will tell you where the gap is. Do not skip this. It is the difference between knowing the rule and being able to use it in review.

Drill · 4 minutes, out loud

The interviewer shows you this and asks what is wrong: users.forEach(async u => { await email(u); }); res.end('sent');

Answer out loud before reading on. A complete answer says forEach drops every promise, so res.end runs before any email is sent. It names the two fixes. And it adds that any failure becomes an unhandled rejection that can crash the process.

Remember this · the 20-second recap
  • A sync error interrupts you. An async error waits in the promise until opened.
  • A missing await defeats try/catch. Measured: the catch never ran, exit code 1.
  • Review rule: every async call must be awaited, returned, or given a .catch().
  • forEach with async drops every promise. Use for…of or map plus Promise.all.
  • No combinator cancels anything. Measured: all rejected at 0 ms, losers still finished at 61 and 90 ms.
  • process.exitCode lets pending work finish. process.exit() throws it away.
  • Unbounded Promise.all over 500 URLs opened 500 at once. A pool held exactly 10.

If you remember one thing: a rejected promise nobody opened is a crash waiting for a quiet moment.
