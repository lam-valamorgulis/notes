Webhooks Are a Hint, Not a Guarantee

The collector pays at 14:07. One message tells Game Locker about it. That message can arrive twice, arrive out of order, arrive late, or never arrive at all — and if your handler is slow enough for long enough, Shopify stops sending it altogether and does not tell you.

Your win today: list the three promises Shopify does not make, quote the retry rule including the condition most people miss, and explain why the handler must do nothing except verify, enqueue and answer 200.
Sources Quotes read from shopify.dev on 2026-08-06. Deeper mechanics: Main L02. The four streams for a stock integration: stockinstore L16.

1. One door, and it opens late

Walk the online sale from Shopify's side and notice how little reaches Game Locker before the end.

14:06:10 add to cart → Game Locker hears NOTHING 14:06:40 checkout opens → Game Locker hears NOTHING 14:07:00 PAYMENT TAKEN Shopify decrements ITSELF: available 1 → 0 14:07:01 orders/create fires ─────────────────────────────► the FIRST signal Two facts to hold together: 1. this webhook is the ONLY entry point for online sales 2. Shopify has ALREADY decremented its own stock before you hear a word about it So Game Locker is never asked for permission. It is only ever TOLD, afterwards.
Why "already decremented" matters so much It means Game Locker must not push that new number back to Shopify. Shopify did it. Pushing it again is the echo loop in §5 — one sale, stock down by two. The whole reliability of the return path depends on remembering that this message is news, not an instruction.

2. The three promises Shopify does not make

You might assumeWhat the docs actually say
"Each event arrives once" "Shopify minimizes duplicate deliveries, but your app might receive the same webhook more than once, for example after a network timeout or a retry."
"Events arrive in order" "Shopify doesn't guarantee ordering within a topic, or across different topics for the same resource." — see L06
"Every event arrives" "Webhook delivery isn't always guaranteed, and your app can miss or mishandle events for other reasons, such as handler failures or downtime."
The single sentence that reframes all three

"A webhook is a hint that something happened. It is fast and usually right, and it is not a record. So I use it for speed and I keep a separate, slower path that tells me the truth — and I never let the fast path be the only one."

3. The retry ladder, and the clause people miss

Read this one exactly, because there is a condition inside it that changes the risk.

shopify.dev, Deliver webhooks through HTTPS — quoted

"If Shopify receives no response or an error, it retries 8 times over the next 4 hours. After 8 consecutive failures, the subscription is automatically deleted if it was configured using the Admin API."

WHAT THAT MEANS IN PRACTICE your endpoint is broken at 10:00 │ ├─ retry 1 … retry 8, spread over about 4 hours │ └─ 14:00 subscription DELETED · no order webhooks arrive after this · nothing announces it · the shop looks quiet, not broken · every online order from now on is invisible to Game Locker And the clause matters: the automatic deletion is stated for subscriptions CONFIGURED USING THE ADMIN API. If yours are declared in the app configuration instead, VERIFY the behaviour rather than assuming it is the same.
Why this failure is worse than an outage An outage is loud — requests fail, someone notices. This is silent. After four bad hours the store stops receiving orders into Game Locker and every dashboard looks calm, because there is no traffic to fail. Mia finds out days later when she cannot work out why the counter and the platform disagree about a whole weekend. The only defence is monitoring that alarms on the absence of expected traffic — a Saturday with zero online orders is not good news for a card shop.

4. Therefore the handler does almost nothing

Given retries punish slowness, and eight failures cost you the subscription, the handler's job is to be fast and boring.

THE ONLY ACCEPTABLE SHAPE webhook arrives │ 1. VERIFY the HMAC ← reject anything unsigned │ 2. seen this X-Shopify-Webhook-Id before? │ → yes: return 200, do nothing │ 3. WRITE IT TO A QUEUE ← durable, survives a crash │ 4. RETURN 200 ← fast, always │ ▼ the WORKER does the real work, later ├── retries with backoff ├── idempotent by ORDER ID ├── ordered per card (L06) └── dead-letters after N attempts TWO REASONS THIS IS NOT NEGOTIABLE: 1. a slow handler becomes a FAILED handler, and eight of those can cost you the subscription 2. work that must be retried has to live somewhere that survives the request. A crash mid-handler loses the order with nothing to replay.
The detail that makes step 3 real "Write it to a queue" means durable, not an in-memory list. If the process dies between the 200 and the work, the order must still exist somewhere. This is the same reasoning as the outbox pattern in stockinstore L08 §4: never let an acknowledgement outrun a durable write.

5. The echo loop

Now the bug that eats a weekend. It only exists because inventory is the one two-way field, and it only appears under load — which is the worst combination.

THE NAIVE DESIGN Shopify sale ──► webhook ──► GL decrements ──► GL pushes ▲ stock to │ Shopify └──────────────────────────────────────────────┘ the push looks like a CHANGE, so something reacts to it again… THE SYMPTOM stock oscillates 4 → 3 → 4 → 3 or one sale drops stock by 2 and it only happens when things are BUSY, which makes it miserable to reproduce THE FIX — every write records WHERE IT CAME FROM ├── "this came from Game Locker" → never echo back └── "this came from a Shopify sale" → apply ONCE, keyed by order id
MechanismWhat it does
Idempotency key"Order 1234 already applied" is a row, checked before applying. Written first — see L04 §5.
Origin markingShopify's inventory mutations accept a referenceDocumentUri. Stamp your own origin on every write, so the adjustment history is readable six weeks later when someone asks why stock went to −3.
Do not trust the platform to tell youShopify's docs do not state whether an inventory_levels/update caused by your own write is distinguishable from any other. Verify it; do not design around an assumption. Marking your own writes works either way.
Worth raising before you are asked Almost nobody mentions echo loops in an interview, because you generally learn about them by having one in production. Naming it unprompted is a strong signal — and if the interviewer has lived through one, you have just described their worst week back to them.

6. Hint plus backstop

Put the three broken promises next to their cover. This table is the whole argument for Lesson 9.

What can go wrongWhat covers it
Same webhook twiceX-Shopify-Webhook-Id, then the order id
Out of orderX-Shopify-Triggered-At plus per-card ordering
Arrives 40 minutes lateAbsolute writes, so late is not wrong. L08
Never arrivesOnly the nightly read-back. Nothing else can see silence
Subscription deletedOnly an alarm on missing traffic. Nothing fails, so nothing else notices

Read the bottom two rows. Both are invisible to every mechanism inside the fast path. That is the structural reason a webhook can never be your only route — not because webhooks are unreliable, but because no fast path can detect its own silence.
