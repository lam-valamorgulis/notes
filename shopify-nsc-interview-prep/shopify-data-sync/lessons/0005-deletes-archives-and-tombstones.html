Deletes, Archives and Tombstones

Every other write in this system can be undone by writing again. Delete cannot. It is the only verb in the sync with no inverse — and the only one that can destroy a shop's data because an SFTP connection dropped at 2am.

Your win today: name the five ways to say "this card is gone" and what each one does to the URL and to old orders, explain why absence is not a message, and describe the guard that stops an empty feed deleting a catalogue.
Sources Every platform fact on this page was read from shopify.dev or help.shopify.com on 2026-08-06 and is quoted. Two things could not be verified and are labelled as such rather than guessed. No other page in this repo covers deletion, so nothing here is a retelling.

1. Why this is the dangerous lesson

Compare delete with everything else the sync does.

WriteWrong value writtenHow you recover
QuantitySays 3, truth is 1Write 1. Fixed in one second.
PriceSays $4, truth is $480Write $480. Fixed.
TitleWrong set nameWrite the right one. Fixed.
DeleteDeleted a card that still existsYou do not. "Deleted products can't be restored."

So the whole lesson follows from one asymmetry: every other write is a hypothesis you can correct. A delete is a commitment. Design accordingly.

2. The five ways to say "gone"

People think there are two — hide it or delete it. There are five, and they differ in ways that matter to a card shop.

WayWhat Shopify's docs sayReversible?
1. Quantity 0
still ACTIVE		 The product stays published. The page loads and shows sold out. Yes — write a number.
2. UNLISTED
API 2025-10 and later		 "The product is active but you need a direct link to view it. The product doesn't show up in search, collections, or product recommendations." Yes.
3. DRAFT "The product isn't ready to sell and is unavailable to customers on sales channels and apps." Yes.
4. ARCHIVED "The product is no longer being sold and isn't available to customers on sales channels and apps." The admin moves it to an Archived tab. Yes — you can unarchive.
5. productDelete "Permanently deletes a product and all its associated data, including variants, media, publications, and inventory items." No. "Deleted products can't be restored."
The one most candidates have never heard of UNLISTED is newer than most people's knowledge — the docs mark it as available in API version 2025-10 and later. It is a genuinely useful middle setting: the product is still buyable by anyone with the link, but it is invisible to search, collections and recommendations. For a card shop that is exactly the shape of "this exists, I just do not want it in the browse experience".

3. What happens to old orders

This is the first question an interviewer asks after "would you delete it?", and the documented answer is reassuring — with one exception.

RecordDocumented effect of productDelete
Completed orders"Previously completed orders that included this product aren't affected. The product information in completed orders is preserved for record-keeping."
Refunds"Existing refunds for this product remain valid and processable."
Draft orders ⚠"Existing draft orders that reference this product will retain the product information as stored data, but the product reference will be removed."
Why the draft-order row matters to this shop A card shop uses draft orders more than a normal retailer — a customer asks Mia to put four cards aside, and she builds a draft order to send them a payment link. If the sync deletes one of those products before they pay, the text survives but the link to the product is gone. Mia will discover it when the collector asks why the total changed. Worth naming, because it is the failure that looks smallest and embarrasses the merchant most.

4. What happens to the URL — and the honest gap

A card shop's product pages earn search traffic. Someone types "Base Set Charizard near mint" into Google. So the URL is not a detail; it is the shop's marketing.

WHAT THE DOCS ACTUALLY SAY ABOUT REDIRECTS help.shopify.com, URL redirects: "You can redirect only from broken URLs." Redirects only work for URLs that return 404 errors. And it names the ways to MAKE a product 404: · set the product to DRAFT status · remove it from all sales channels SO THE CHAIN IS: product must 404 → becomes eligible → you add a redirect ⚠ NOT DOCUMENTED, DO NOT GUESS: what URL an ARCHIVED product returns. The ProductStatus docs say archived products are not available to customers on sales channels — but no page states the HTTP status of the old URL. VERIFY THIS ON A REAL STORE BEFORE RELYING ON IT.
The order of operations people get backwards You cannot add the redirect first and then remove the product — a redirect from a URL that still works does nothing, because redirects only apply to broken URLs. So the sequence is: make it 404, then redirect. And for a bulk removal, that means the redirect list has to be built and submitted as a second step, not as part of the same write. Migration L08 makes the same point about a domain move.

Here is the actual decision table. The question is never "should we delete?" — it is "why is this card gone?"

The default to state plainly

"My default is that the sync never deletes. It sets quantity to zero, or it changes status. Deletion is a human decision made in the Shopify admin, or a rare explicit job with a human approving the list. There is exactly one case where the sync may delete on its own: a record it created by mistake and that has no orders against it."

6. Absence is not a message

Now the deeper problem, and the reason the lesson is called "tombstones".

Suppose Game Locker hard-deletes its own row when a card is written off. The next sync run reads Game Locker's cards and sends them to Shopify. What does it see?

THE ROW IS SIMPLY NOT THERE. And "not there" is indistinguishable from: · this card never existed · this card is not in scope for this run · the query was filtered slightly differently today · the read failed halfway and returned fewer rows A DELETION IS AN EVENT. AN EMPTY SPACE IS NOT. So the sync cannot act on it — and Shopify keeps the card listed and sellable, forever, with nobody noticing.
The fix, and the name for it Game Locker keeps the row and marks it: deleted_at, plus why. That is a tombstone — a record whose job is to say "this used to exist and is now gone". The sync then has an event it can act on, and it can act once, idempotently, exactly like every other write in Lesson 4.

The tombstone also carries the reason, which is what makes section 5's table usable. "Gone" is not actionable. "Gone because it was a fake" is.

ApproachWhat the sync can do
Hard delete in Game LockerNothing. It cannot tell removal from absence.
Compare against a snapshot of the last runDetect the gap — but a partial read now looks like a mass deletion. Dangerous without §7.
Tombstone with a reasonApply the right one of the five endings, once, and log why.

7. The 2am empty file

This is the failure that has destroyed real catalogues, and it is the strongest reason for the guard below.

02:00 the nightly job starts. 02:00 it reads the store's card list — which for a shop on a third-party till means a CSV EXPORT. 02:00 the transfer drops after the header row. The job receives a VALID, EMPTY file. Well-formed. Parses cleanly. Zero rows. 02:01 the sync reasons, correctly by its own rules: "Game Locker has 0 cards. Shopify has 12,000. Therefore 12,000 cards were deleted." 02:02 it starts deleting. 08:30 Mia opens her shop's website. There is nothing in it. And it is NOT RECOVERABLE, because "Deleted products can't be restored."
Every ingredient here is normal The transfer dropped — normal. The file parsed — normal, it was well-formed. The comparison was arithmetically right. The sync followed its rule exactly. There is no bug to fix. And note how ordinary the ingredient is: a file is the least trustworthy input there is, because a truncated file is still a valid file. An API that returns zero results at least did so deliberately. That is why the protection cannot be "write better code"; it has to be a rule that refuses to act on an implausible instruction.

The deletion budget

BEFORE APPLYING ANY REMOVALS, ASK ONE QUESTION: how many rows would this run remove? under 2% of the catalogue → proceed 2% to 10% → proceed, and ALARM over 10% → STOP. Do nothing. Alarm loudly. Wait for a human to approve. AND ALWAYS: · a run that received ZERO rows removes NOTHING, ever. An empty read is treated as a FAILED read, not as an instruction. · removals are applied SLOWEST, never first. If something is wrong, you want to find out while there is still a catalogue left.
Why a percentage and not a fixed number A fixed threshold like "never delete more than 500" is wrong at both ends of the range. For a shop with 300 cards it permits wiping everything; for a shop with 200,000 it blocks an ordinary clear-out. The budget has to scale with the store, which for a multi-tenant platform means per store, not per job. Harbour City Cards and a 200,000-card shop cannot share a threshold.
This is the same idea as full-snapshot versus delta feeds stockinstore L02 §5½ shows that a delta feed can silently miss a sell-out, so full snapshots are safer for quantities. This lesson is the other edge of the same knife: a full snapshot is the only thing that can tell you something disappeared — and that same power is what lets a truncated snapshot wipe a store. Snapshots make deletion detectable and make it dangerous, in one step.
