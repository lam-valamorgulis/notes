Absolute Writes, and Why Replay Must Be Safe

Every message in this system will be sent twice at some point. Not because of a bug — because retrying is how distributed systems survive. So the only question worth asking about a write is: what happens if it lands twice?

Your win today: name the four ordinary things that cause a replay, fill in the lost-versus-duplicate table from memory, and explain compareQuantity as a stop sign rather than a fix — then say which two keys you deduplicate on and why they are different.

Deeper treatment of the same mutations, from the platform side: POS L03 §5. The interview framing: Game Locker L03 §4.

1. Replay is normal, not exceptional

Candidates treat duplicate messages as an edge case. They are a Tuesday. Here are the four ordinary causes, and none of them is a defect.

#What happensWhy it duplicates
1Our push to Shopify times outWe do not know if it landed. Retrying is the only safe move — so we may write twice.
2Shopify sends the same webhook twiceDocumented: "your app might receive the same webhook more than once, for example after a network timeout or a retry."
3A deploy lands mid-batchThe job restarts. Items already done get done again.
4Support clicks "re-sync store 17"Somebody is fixing a problem. The tool must not create a worse one.
The reframe

"I do not design to prevent duplicate messages, because I cannot. I design so that a duplicate is boring. If replaying a write is harmless, then every retry, every deploy and every support re-sync is safe — and that is what makes the whole system recoverable rather than fragile."

2. Two ways to write a number, and only one survives a replay

Shopify offers both, and choosing wrong is the difference between a sync that heals itself and one that drifts forever.

inventorySetQuantitiesinventoryAdjustQuantities
MeansAbsolute. "This is now 7."Delta. "Add −1 to whatever is there."
Message lostNothing. The next push corrects it.Permanent drift. The −1 is gone for good.
Message duplicatedNothing. The same value written twice.Double decrement. An oversell you caused yourself.
Use forThe recurring sync. Game Locker knows the true count.One known event, applied exactly once, with a key.

Read the middle two rows as a 2×2 and the choice makes itself. An absolute write is naturally idempotent: doing it again changes nothing. A delta is naturally the opposite — it is a function of what it finds, so repeating it repeats its effect.

Why this is the highest-value fact in the sub-course Nearly every other reliability tool here — retries, queues, reconciliation, support re-syncs — depends on replay being safe. Pick delta writes and you have to make every one of those tools exactly-once, which is very hard. Pick absolute writes and they are all free. One decision, made in the first week, decides how much of the rest is hard.

3. compareQuantity — the stop sign

inventorySetQuantities takes a compareQuantity next to the new value. Shopify applies the write only if the stored quantity still matches what you thought it was. If it changed underneath you, the mutation returns a userErrors entry instead of silently overwriting.

The two numbers look alike and come from opposite places. This is the detail people get wrong:

FieldMeansComes from
quantityThe new value you want storedGame Locker — its own count
compareQuantityWhat you believe Shopify holds right nowShopify — your read, a moment earlier

Read a write out loud as one sentence and it stops being confusing: "make it 0, but only if it is still 1."

The sentence that lands this in an interview compareQuantity is not a fix. It is a stop sign. It does not know the right answer — it only turns a silent wrong write into a visible error your worker can handle. The re-read is what finds the truth.

There is also ignoreCompareQuantity: true to bypass the check. Know it exists, and know that reaching for it is a decision to accept overwriting other writers.

4. Saturday 14:05, with both roads out

Tom sold the Charizard at the counter this morning on Binder POS. The midday CSV import has just run, so Game Locker now holds 0 — and Shopify still holds 1, because it has not been told yet. The push that fixes that is starting right now, and in the same second an online shopper pays.

Note how the card got here Game Locker did not learn about the counter sale as it happened. It learned at the import, which is gap A and is not yours. Everything in this lesson is about gap B — getting that now-correct number into Shopify safely. Worth holding both in mind: this lesson makes your half reliable, and your half was already working from information that was hours old.

5. Two different deduplication keys, doing two different jobs

This is where careful candidates separate themselves. "Use an idempotency key" is not one decision — it is two, and they protect against different things.

X-Shopify-Webhook-IdThe order id
Answers"Have I seen this delivery before?""Have I already applied this business event?"
CatchesShopify re-sending the identical webhookThe same sale reaching us by any route
MissesThe same sale arriving on a different topic, or found by the reconcilerNothing about the sale — but it does not tell you a delivery was a repeat
Where it livesThe webhook receiver, before the queueThe worker, before applying the change
USE BOTH. THEY ARE CHEAP AND THEY GUARD DIFFERENT DOORS. webhook arrives │ ├─ seen this X-Shopify-Webhook-Id? → drop, return 200 │ (a pure repeat delivery) ▼ enqueue │ ▼ worker ├─ "order 1234 already applied"? → skip │ (the sale, by any route) ▼ apply once, record the key FIRST
Why the order-id key must be written first Record "order 1234 applied" before or with the change, not after. If you apply the decrement and then crash before recording the key, the retry applies it again — and you have built the exact double-decrement that absolute writes were meant to protect you from. The key and the effect must land together, or the key must land first.

6. The same rule, applied to prices

Inventory is the loud case, so it gets the attention. But the reasoning transfers, and saying so shows the principle is understood rather than memorised.

QuestionPrices at Harbour City Cards
Absolute or delta?Absolute. "This card is now $482." Never "add $2".
Replay safe?Yes. Writing $482 twice is writing $482.
Do we need compare-and-set?Less urgently — Shopify does not decrement prices by itself. But Mia might edit compareAtPrice, which is why L03 keeps last_pushed.
How many go per night?~3,000 of 12,000 moved. Push the diff, not everything — one bulk operation. See Main L18.
The judgement, not the rule A price write is not free. It costs API budget and it invalidates caches. Sending all 12,000 rows when 3,000 moved is not merely wasteful — it makes the nightly job four times longer, which makes it four times more likely to be interrupted by a deploy. Efficiency here buys reliability, not just speed.

7. What you would build, in one picture

GAME LOCKER SHOPIFY ─────────── ─────── counter sale ──┐ stock recount ─┤ nightly price ─┴─► CHANGE LOG ──► PUSH WORKER ──► Admin API what changed, │ absolute writes when, and │ + compareQuantity by whom │ + reference to │ our own origin rejected writes ◄────┘ go back for a RE-READ, not a retry of the same stale number THREE PROPERTIES TO SAY OUT LOUD: 1. every push is REPLAYABLE (change log + absolute) 2. every push is REFUSABLE (compareQuantity) 3. a refusal triggers a RE-READ (not a louder retry)

Property three is the one people forget. A rejected write means your information is old. Retrying the same numbers harder will be rejected again, forever. The correct response to a rejection is to go and look.
