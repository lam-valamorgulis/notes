Clocks, Order and Staleness

"Latest wins" sounds like a conflict rule. It is really an assumption — that you can tell which change was later. Three systems have three clocks, Shopify promises no ordering at all, and both of those facts break the rule before you have written a line of it.

Your win today: quote what Shopify actually promises about webhook ordering, name the header that lets you order events anyway, and state the rule that makes all of this manageable — never compare one system's clock to another system's clock.
Sources Read from shopify.dev on 2026-08-06 and quoted below. Nothing in this repo covers clock disagreement, so this lesson is new rather than a retelling.

1. The assumption hiding inside "latest wins"

Someone will propose this rule, and it sounds reasonable:

"If Game Locker and Shopify disagree, take whichever one changed most recently." To run that rule you need to answer: which change was later? Which needs: a time for change A a time for change B and the two times to be COMPARABLE The third one is where it falls over.

Game Locker's timestamp comes from Game Locker's servers. Shopify's comes from Shopify's. And any time that came off the counter till came from a PC in a shop. Nobody guarantees those agree. The first two will usually be close, and "usually close" is exactly the property that produces a bug you cannot reproduce. The third may be wrong by hours and nobody in the shop would ever notice.

Why the clocks disagreeTypical size
Ordinary clock drift between machinesMilliseconds to seconds
Time sync correcting a drifted clock — time can move backwardsWhatever the drift was
Two servers in one cluster stamping the same eventMilliseconds — enough to reverse the order of two fast writes
A queue holding a message before it is stampedSeconds to minutes
A shop PC's clock that nobody has ever checkedMinutes to hours. A till only has to print a receipt, so a wrong clock goes unnoticed for years
The failure this creates is the nastiest kind It works in testing, because your test writes are seconds apart. It works in staging. It fails on release Saturday, on one card, when two changes land inside the same second — and by the time anyone looks, both systems agree on a value and there is nothing left to inspect. A rule that is right 99.9% of the time is not a rule. It is a coin flip you have hidden from yourself.

2. What Shopify actually promises about order

Not "usually in order". Read it exactly:

shopify.dev, About webhooks — quoted

"Shopify doesn't guarantee ordering within a topic, or across different topics for the same resource."

And the example the docs themselves give is the one that shows how strange it can get: a products/update can arrive before the products/create for the same product.

WHAT THIS MEANS FOR HANDLERS NOT ordered within one topic: inventory_levels/update qty 3 ← sent first inventory_levels/update qty 1 ← sent second … may arrive in either order. NOT ordered across topics for the same resource: products/create ← may arrive AFTER products/update THEREFORE a handler that assumes "the newest message I received is the newest thing that happened" is wrong. Not occasionally. By design.

The same page also states delivery itself is not assured: "Webhook delivery isn't always guaranteed, and your app can miss or mishandle events for other reasons, such as handler failures or downtime." That is Lesson 7.

3. The header that fixes ordering — within Shopify

Shopify does not leave you stuck. Each delivery carries metadata headers, and one of them is the event time.

HeaderWhat it is for
X-Shopify-TopicWhich topic this delivery is
X-Shopify-Hmac-Sha256Verify it really came from Shopify
X-Shopify-Webhook-IdDetect and skip a repeated delivery — see L04 §5
X-Shopify-Event-IdCorrelate deliveries caused by the same merchant action
X-Shopify-Triggered-AtWhen the event happened. Shopify recommends using this, or the payload's updated_at, to order events and to spot stale payloads

It is an ISO 8601 timestamp with very fine precision — for example 2026-04-28T12:43:11.254245052Z.

Why this header is safe to trust and your own clock is not Every X-Shopify-Triggered-At comes from Shopify's clock. So comparing two of them is comparing one clock with itself, which is a valid comparison. Comparing one of them against a Game Locker timestamp is comparing two different clocks, which is not. The header solves ordering inside Shopify. It does not solve conflict between the systems.

4. The rule that makes all of this manageable

Memorise this one

"Never compare one system's clock to another system's clock. Compare Shopify's timestamps with Shopify's timestamps to order its events. Between the two systems, do not use time at all — use ownership."

This is why Lesson 3 exists, and the connection is worth saying out loud in an interview because most people never make it:

"WHO WINS?" HAS TWO POSSIBLE ANSWERS By TIME "whoever changed it last" needs comparable clocks → you do not have them fails silently and rarely → worst kind of bug By OWNERSHIP "the field's owner, always" needs no clock at all fails the same way every time → testable, explainable to a merchant, and boring Ownership is not a stylistic preference. It is what you use BECAUSE cross-system time is unusable.

The third clock is the worst one, and it arrives in a file

Shopify at least hands you X-Shopify-Triggered-At and admits it does not guarantee order. The counter till gives you neither.

Time signalHow much you can trust it
Shopify's X-Shopify-Triggered-AtGood. One clock, compared with itself, and the platform tells you to use it this way.
Game Locker's own version numberBest. No clock at all — see §8.
A timestamp in a row of the till's CSVWeakest of all. It comes from a shop PC's clock, there is no delivery metadata around it, and the file itself carries no ordering — rows are in whatever order the export produced.
What this means in practice Do not use the till's timestamps to decide anything about Shopify. Use them for one thing only: ordering the till's own rows against each other, if you must, and even then prefer the file's row order plus the import batch number. The moment you compare a till timestamp with a Shopify timestamp you have compared two clocks that have never agreed and never will — and one of them belongs to a machine whose only job is printing receipts.
Which is another argument for ownership over time Three clocks make "latest wins" three times worse, not one and a half times. And it is why the import should be treated as a statement of current state, not as a stream of timed events: "as of this export, store 17 holds these quantities". A state you can apply with an absolute write. A pile of events you cannot order is much harder to use.

5. Per-card ordering is enough

Once you accept messages can arrive out of order, the instinct is to force global order — one queue, one worker, strictly sequential. Resist it, and know why.

Global orderingOrdering per card
GuaranteeEvery message in the shop, in orderMessages about one card, in order
ParallelismOne at a time. 12,000 cards behind one laneAs many lanes as you like
One slow messageBlocks everythingBlocks that one card only
Correctness gainedNone you needed. Card A's order never mattered to card BAll of it

The reason is simple once stated: two different cards have no relationship. There is no rule connecting the Charizard's stock to a Pikachu's. So the only ordering that ever mattered is within one card — and that is cheap.

How you get it Key the queue by the thing that must stay in order — the inventory item, or the variant. Everything with the same key goes to the same lane and is handled in sequence; different keys run in parallel. This is the standard partitioned-queue shape, and Main L12 §5 covers the messaging side of it.

6. The staleness guard

Ordering per card handles messages that arrive out of sequence inside your queue. The staleness guard handles the ones that arrive late from outside.

STORE, PER CARD, THE TIME OF THE LAST EVENT YOU APPLIED. (Shopify's clock, from X-Shopify-Triggered-At.) a message arrives │ ├─ triggered_at OLDER than what I already applied? │ → DROP IT. It is news about a past I have moved on from. │ └─ NEWER? → apply it, and store its triggered_at WHY THIS IS SAFE FOR ABSOLUTE WRITES: the newest message contains the whole truth, so discarding an older one loses nothing at all. WHY IT WOULD BE FATAL FOR DELTA WRITES: each delta carries a piece of the truth. Drop one and it is gone forever — Lesson 4, the same reason.
The link back to Lesson 4 Notice that the staleness guard is only allowed to exist because the writes are absolute. Choosing inventorySetQuantities in Lesson 4 is what makes "just drop the old message" a safe sentence in Lesson 6. One early decision keeps paying. That kind of chain is worth pointing out in an interview — it shows you see the design as connected rather than as a list of tips.

7. What the staleness guard cannot catch

Be honest about the limits, because an interviewer will look for them.

CaseWhy the guard misses itWhat actually covers it
Two events with the same timestampNeither is older. The guard has no opinion.Ownership decides. Or, for quantity, compareQuantity — the loser is rejected and re-reads.
A counter sale versus an online saleThey come from different clocks, so the timestamps are not comparable at all.Nothing time-based. Both are real; the collision is handled, not ordered. L09.
A message that never arrivesNothing to compare. Silence has no timestamp.The nightly read-back. L09.
A card whose updated_at moved but whose value did notLooks newer, is not different.last_pushed from L03 — compare values, not times.
The trap in row four A common shortcut is "only sync cards whose updated_at changed". It is tempting and it leaks, because updated_at moves for reasons that are not real changes — a no-op save, a tag reorder, an app touching the record. You end up pushing thousands of rows that were already correct, burning API budget and invalidating caches for nothing. Timestamps tell you something happened. Only values tell you what.

8. Game Locker's own ordering, without clocks

One more piece. Shopify's events can be ordered by its header, but what orders Game Locker's own pushes when two staff edit the same card in the same second?

NOT A TIMESTAMP. A VERSION NUMBER. each card row carries version: 41 any change increments it → 42, 43, 44 … The push carries the version it was built from. The change log is ordered by version, not by time. WHY THIS IS BETTER THAN A CLOCK: · it cannot go backwards · it does not need two machines to agree · "42 is after 41" is true with no assumptions · a gap (41 → 43) is a VISIBLE missing event, which a timestamp gap never is

The last line is the real prize. With timestamps, a lost event leaves no trace. With a version sequence, a hole in the numbers is evidence — and evidence is what makes a sync auditable rather than merely hopeful.

9. The rules, collected

#Rule
1Never compare one system's clock to another's. Between systems, use ownership.
2Order Shopify's events by X-Shopify-Triggered-At — its clock against itself.
3Order your own events by a version number, not a timestamp.
3½Never let a till timestamp decide anything about Shopify. Treat the import as a statement of current state, not a stream of timed events.
4Order per card, never globally. Two cards have no relationship.
5Drop messages older than the last one applied for that card — safe only because writes are absolute.
6Never decide "did this change?" from a timestamp. Compare values.
