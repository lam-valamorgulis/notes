The Conflict Cases

Every way three systems can disagree, on one page. For each: how it looks from outside, how you notice it, and the rule that settles it. If a bug does not match a row here, you have found a new case and it belongs on this page.

Why a taxonomy and not a troubleshooting list: in production you do not get told which case you are in. You get "stock is wrong". This page turns that into a question with thirteen possible answers, each with a different fix — which is much faster than reasoning from scratch at 2am.

The thirteen cases

#CaseWhat you observeHow you noticeThe rule
1 Stale read
the ordinary one		 Website shows 1, shop has 0. Nothing has failed. Lag metric. Or a customer. Push on the change, not the batch. Then accept a residual gap and name it. And check case 11 — the stale number may have arrived stale. L01
2 Write–write on one field Two systems set the same field to different values. compareQuantity rejection, or last_pushed mismatch. Ownership decides. Never a timestamp. L03
3 Two doors sell the last unit
of three		 Two paid orders, one card. Only the unfulfillable report — both systems end up agreeing on 0. Cannot be designed away. Shrink the window, hold the last copy back, apologise by procedure. L09
4 Echo loop Stock oscillates 4→3→4→3, or one sale drops it by 2. Only under load. Adjustment history, if you stamped an origin. Otherwise guesswork. Mark the origin of every write. Never echo your own. L07 §5
5 Duplicate delivery One sale applied twice. Two rows for one order id — if you checked. Dedupe on X-Shopify-Webhook-Id and the order id, key written first. L04 §5
6 Out-of-order arrival An older value lands on top of a newer one. Compare X-Shopify-Triggered-At against the last applied. Order per card; drop anything older. Safe only because writes are absolute. L06
7 Lost message Nothing at all. Silence. Only the nightly read-back. No fast path sees its own silence. Reconcile, classify, heal the explainable. L09
8 Subscription deleted A quiet Saturday. No errors, no traffic. Only an alarm on the absence of expected traffic. Monitor for missing volume, not just for failures. L07 §3
9 Delete versus update A card is removed on one side and edited on the other. A tombstone arriving after a value change, or the reverse. Removal wins over an edit — but never a hard delete. Status change plus quantity 0. L05
10 Phantom deletion
the 2am empty file		 A whole catalogue disappears. Deletion budget refusing to proceed — if you built one. An empty read is a failed read. Per-store budget. Removals applied last. L05 §7
11 Upstream lag
gap A — not yours		 The website is a day stale even though your sync ran in two seconds. Only by measuring the till → platform hop separately. Your own metrics all look green. Not a code fix. Automate and shorten the import, and report the number. L11 §3
12 Held, not sold
the kiosk		 A kiosk customer and a website customer are both offered the same card. An order for a card that is physically spoken for but was never marked. Write it as committed, not as available. One of the eight states. L02 §4
13 Noisy neighbour One shop's urgent message waits hours. Nothing failed. Per-store lag. A platform average hides it completely. One lane per store, round-robin. Backfill in its own low lane. L10

The four that are invisible without a specific tool

Most cases announce themselves somehow. These four do not, and each needs one purpose-built detector. If any of them is missing from a design, the design has a hole regardless of how good the rest is.

CaseIts only detector
3 — two doors sell the last unitThe unfulfillable orders report. Stock reconciliation cannot see it, because both systems agree afterwards.
7 — lost messageThe nightly read-back. Silence produces no error to catch.
8 — subscription deletedAn alarm on missing traffic. Nothing fails, so nothing else notices.
11 — upstream lagTiming the till → platform hop on its own. Every metric you own reads green, because your half really is fast. The only way to see it is to measure a hop that is not yours.

The decision tree for "stock is wrong"

"The website has the wrong number." 0. How OLD is the newest counter-sale data we have? older than the disagreement → CASE 11. The number was stale before it reached us. Nothing downstream can fix that. current → continue. 1. Is there a PENDING message that would fix it? YES → this is LAG, not a conflict. Go to L08. NO → continue. 2. Is Shopify HIGHER than we believe exists? YES → suspicious. A hand edit, a failed decrement, a return processed once, or our own bad write. DO NOT push down — you would erase the evidence. Alarm. (L09 §4) NO → continue. 3. Did a write get REJECTED for this card recently? YES → case 2 or 3. Re-read and look for a second sale. NO → continue. 4. Is the number OSCILLATING? YES → case 4, echo loop. Check origin marking. NO → continue. 5. Was there ever a message for this change at all? NO → case 7, lost message. And check case 8: is the subscription still alive? YES → you have a new case. Add it to this page.

The seven rules that cover eleven of the thirteen

#RuleKills case
1Ownership per field, never a timestamp between systems2, 9
2Absolute writes with compareQuantity5, 6, and half of 2
3Mark the origin of every write4
4Never delete from the sync; tombstones and a budget9, 10
5Read back nightly, classify, heal the explainable7
6Per-store lanes and per-store metrics13
7Write held stock as committed, not as available12
Cases 3 and 11 are the ones no rule of yours kills Two doors selling the last unit cannot be removed by any design, because both writes are correct. And case 11 is not yours at all: the till reaching the platform is a hop you own neither end of, so the only honest move is to measure it and report it. Seven rules, eleven cases, one you cannot design away and one you do not control — that count is a better answer than a list of thirteen fixes, and it points at where the remaining work is: making the window small, promising less inside it, telling the merchant which gap is really hurting them, and handling the outcome like a professional.
