Kata 02 · Debug & fix · ~20 min

Debug the Double-Charge

The other live-coding format: they show broken code and ask you to find the bug and fix it, thinking out loud. This one hides a real async race condition — the kind that actually ships.

Do this first: read the broken code below. Cover the answer. Say out loud what you think is wrong and how you'd prove it, then fix it. Debugging out loud is the skill being scored — narrate your hunt, not just the fix.

The scenario (what the client tells you)

Bug report "Our sync worker sometimes creates the same order twice in the ERP, but only under load on sale days. Under light traffic it never happens. Here's the worker — can you find it?"

"Only under load" and "only sometimes" is the classic fingerprint of a race condition. Say that out loud — naming the bug class before reading every line is a senior move.

The broken code

async function handleOrder(order) { // Has this Shopify order already been synced to the ERP? const existing = await db.mappings.findByShopifyId(order.id); if (!existing) { // Not seen before -> create it in the ERP, then record the mapping. const erpId = await erp.createOrder(order); await db.mappings.insert({ shopifyId: order.id, erpId }); } else { await erp.updateOrder(existing.erpId, order); } } // Many events for the same order can be in flight at once. queue.process('orders', handleOrder);

Step 1 — Say the hunt out loud

  • "It only happens under load → concurrency, not logic. Two runs of handleOrder for the same order overlap."
  • "There's a check-then-act gap: both read findByShopifyId, both see null, both call erp.createOrder. That's the classic read-then-write race (a TOCTOU bug)."
  • "So the same order gets created twice before either mapping row is written."

Step 2 — How would you prove it?

Say this — it shows you fix by evidence, not by guessing:

  • Add a log with the order id and a worker id around the check and the create; under load you'll see two creates for one order id with no mapping in between.
  • Or reproduce: fire the same order event twice concurrently in a test and assert erp.createOrder was called once.

Step 3 — Fix it (try before revealing)

There are a few valid fixes. Say the trade-offs. Then reveal the model answer.

Why each fix works — the ranking to say out loud

FixStrengthWhat to say
Unique constraint on shopifyId + upsert / catch duplicateStrongest — the database enforces it no matter how many workers race."I make the mapping's shopifyId unique. The second insert fails, I catch it and switch to update. The DB is the source of truth, so this holds even across multiple worker machines."
Idempotency key sent to the ERPStrong — the ERP itself refuses the duplicate create."If the ERP accepts an idempotency key, two creates with the same key produce one order. Best when you don't fully trust your own dedupe."
Per-order lock (advisory lock / mutex on order id)Works, but adds coordination and can bottleneck."A lock keyed on the order id serializes same-order events. Correct, but I'd prefer the DB constraint — less to go wrong."
In-memory Set of seen idsWeak — the trap answer."Tempting, but it dies with the process and doesn't work across multiple workers. Not safe for production."
Trap: "just add an in-memory cache of processed ids." It looks like a fix and works on one machine in light testing — exactly why it's dangerous. It fails the moment you scale to more than one worker or restart the process. Name it, then reject it out loud.
"It only breaks under load, so it's a concurrency bug — a check-then-act race. Two workers both see no mapping and both create. I fix it at the database with a unique constraint on the Shopify id and an upsert, because that's the one place the guarantee holds across every worker."
