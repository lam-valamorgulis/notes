Kata 04 · Build from blank · ~25 min

NestJS Orders Module

The JD lists NestJS. This kata proves you can lay out a clean module — controller, service, DTO, dependency injection — from a blank file, the way a senior structures backend code.

Do this first: cover the model answer. Set a timer. This kata is about structure and boundaries, not clever logic — narrate why each piece exists and where the responsibility lines are.

The prompt

Task "Build a NestJS orders module with an endpoint to create an order and one to fetch an order by id. Validate the input. Keep it clean."

Step 1 — Clarify out loud

  • "Where does the real work live? In the service — the controller only handles HTTP. That separation is the point of NestJS."
  • "How do I validate input? A DTO with class-validator decorators plus a global ValidationPipe."
  • "How does the controller get the service? Dependency injection through the constructor — never new Service()."

Step 2 — Say the plan

orders.module.ts -> wires controller + service together orders.controller.ts -> HTTP layer only (routes, status codes) orders.service.ts -> business logic (talks to DB / ERP) dto/create-order.dto.ts -> shape + validation of the request body

Step 3 — Build it (open your editor)

What the interviewer is really checking

SignalWhat shows it
Layer separationController has no business logic. It calls the service and returns. Logic lives in the service.
Dependency injectionService is injected via the constructor with private readonly. You never construct it yourself — Nest's container does, which makes it testable (you can inject a fake).
Validation at the edgeA DTO with decorators + ValidationPipe rejects bad input before it reaches your logic. You do not hand-check fields inside the service.
Correct HTTP semanticsCreate returns 201; a missing order returns 404 (NotFoundException), not a 200 with null.
Trap: putting DB calls or validation if-checks in the controller. The controller is the HTTP boundary only. Business logic in the controller is the #1 thing that makes a NestJS reviewer wince — it kills testability and reuse.
"NestJS pushes you toward clean boundaries: the controller speaks HTTP, the service holds the logic, DTOs validate the edge, and dependency injection wires it together — which is also what makes each piece unit-testable in isolation."
