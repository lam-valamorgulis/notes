Idempotent ERP Sync Worker

Kata 01's webhook handler pushed a job on the queue. This is the other half — the worker that pulls the job and writes it to the ERP exactly once in effect, even though the same job can arrive twice.

Do this first: cover the model answer. 25-minute timer. Clarify out loud, say your 3-step plan, then type it from blank while narrating the reliability decisions. This is the heart of the whole role.

The prompt

Task "Write the worker that consumes orders-create jobs and writes each order into the ERP. Assume the queue delivers at-least-once — the same job can arrive more than once."

Step 1 — Clarify out loud

  • "Delivery is at-least-once, so I must make the write safe to run twice. Two defences: dedupe on the webhook id, and an idempotent create-or-update keyed on a mapping."
  • "Does the order already exist in the ERP? I keep a mapping table — Shopify id → ERP id — to decide create vs update."
  • "What if the ERP write fails? I throw so the queue retries; I do not swallow the error."

Step 2 — Say the plan

1. Seen this webhookId before? -> yes: ack and stop (dedupe). 2. Look up the mapping (shopifyId -> erpId). 3. No mapping -> create in ERP, save mapping. Mapping exists -> update. (Record the webhookId as processed. Let failures throw -> queue retries.)

Step 3 — Build it (open your editor)

The traps this kata tests

TrapWhy it fails
Only dedupe, no idempotent writeThe dedupe row and the ERP write are two steps. If you crash between them, the retry is deduped away and the order is never written. You need the write itself to be safe, not just a dedupe gate.
Only idempotent write, no dedupeWorks, but every duplicate does a full ERP round-trip. Dedupe is the cheap fast-path; idempotency is the correctness guarantee. Use both.
Catching the ERP error and acking anywaySwallowing the error means a failed write is marked done — the order is silently lost. Let it throw so the queue retries.
Check-then-act on the mappingTwo workers can both see "no mapping" and both create (Kata 02's race). Rely on a DB unique constraint, not an if-check.
"At-least-once delivery plus an idempotent consumer gives an exactly-once effect. I dedupe on the webhook id as a cheap fast-path, but the real guarantee is the idempotent create-or-update on the mapped id — so a retry updates the same ERP record instead of making a second one."

Say how you'd test it

  • Process the same job twice → ERP create called once, one mapping row, second call is a no-op or an update.
  • ERP throws on first attempt → job is retried, not acked; second attempt succeeds.
