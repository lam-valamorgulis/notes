Retry & Dead-Letter

A sync worker that never gives up will hammer a broken ERP forever; one that gives up too easily loses data. This kata is the reliability layer between those two failures: bounded retry with backoff, then a dead-letter queue.

Do this first: cover the model answer. This kata is about what happens when the write keeps failing — the exact reliability instinct this role is hiring for. Narrate every decision.

The prompt

Task "Your ERP write can fail transiently (network blip) or permanently (a malformed order the ERP rejects). Make the worker resilient: retry the transient failures, but don't lose or infinitely retry the permanent ones."

Step 1 — Clarify out loud

  • "Two failure kinds. Transient (timeout, 503) → retry with backoff. Permanent (400 bad data) → retrying won't help, so send it to the dead-letter queue immediately."
  • "Retries need a cap (say 5) and exponential backoff with jitter, so I don't stampede a recovering ERP."
  • "After the cap, the message goes to a DLQ — not dropped — so a human can inspect and replay it. I alert on DLQ depth."

Step 2 — Say the plan

try the ERP write ├─ success -> ack, done ├─ permanent error (4xx bad) -> send to DLQ now (retry is pointless) └─ transient error (timeout/5xx) ├─ attempts < MAX -> wait backoff(attempt) + jitter, retry └─ attempts = MAX -> send to DLQ, alert

Step 3 — Build it (open your editor)

The traps this kata tests

TrapWhy it fails
Retrying a permanent (400) errorMalformed data will fail the same way every time. Retrying 5x just wastes 5x the calls and delays the DLQ. Detect permanent errors and DLQ them at once.
Fixed-delay retries with no backoffIf the ERP is down, every worker retrying every 1s becomes a stampede that stops it recovering. Back off exponentially.
Backoff with no jitterWithout jitter, all workers retry at the same instants — a synchronized thundering herd. Add randomness.
No cap — retry foreverOne poison message blocks the worker and fills logs forever. Cap attempts, then DLQ.
Dropping the message after max retriesSilently discarding = data loss. The DLQ keeps it for inspection and replay. Losing an order is the one unforgivable outcome.
"I split failures into transient and permanent. Transient ones retry with exponential backoff and jitter, capped at five attempts, so I never stampede a recovering ERP. Permanent ones and anything past the cap go to a dead-letter queue — never dropped — and I alert on DLQ depth so I find out before the client does."

Note: managed queues (SQS, RabbitMQ, BullMQ) give you retry + DLQ as config. Knowing the mechanism — as in this kata — is what lets you configure them correctly and explain them.
