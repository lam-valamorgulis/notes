Kata 01 · Build from blank · ~25 min

Build a Shopify Webhook Handler

The single most common live-coding task for a Shopify backend role. If you can build this smoothly, out loud, you have shown the core ingestion skill.

Do this first, before scrolling: cover the model answer below. Set a 25-minute timer. Clarify out loud, say your plan, then type it from a blank file, narrating. Only then diff against the model.

The prompt (this is all the client gives you)

Task "Write an HTTP endpoint that receives Shopify orders/create webhooks. Make it production-ready."

That is deliberately vague — like the real thing. The senior move is to clarify what "production-ready" means here before you type.

Step 1 — Clarify out loud (do not skip)

Say these questions aloud, then state your assumptions. This alone separates you from most candidates.

  • "Do we need to verify the webhook is really from Shopify?" (Yes — always. HMAC.)
  • "What should the handler do with the order — write to the ERP now, or hand off?"
  • "What's the volume? Could we get a burst on a sale day?"
  • "Is it okay if the same webhook arrives twice?" (It will — delivery is at-least-once.)
Assumptions to state, then build on Verify HMAC on the raw body. Do not do the ERP write inline — Shopify times out at 5 seconds, so I ack fast and push to a queue. Assume duplicates can arrive, so I record the webhook id for dedupe. A worker (out of scope for this kata) drains the queue.

Step 2 — Say the plan (3 steps, before typing)

1. Enable rawBody. Verify HMAC-SHA256 in a GUARD. Reject (401) if bad. 2. Controller returns 200 fast (inside Shopify's ~5s budget). 3. Inject the queue; enqueue the event. Dedupe via jobId = X-Shopify-Webhook-Id.

NestJS shape: a CanActivate guard does the HMAC check, the @Controller stays thin, and the queue is injected with @InjectQueue (@nestjs/bullmq). Verification in a guard is reusable across every webhook route.

Step 3 — Build it (now open your editor)

Type from blank while narrating. When you are done — or the timer ends — reveal the model answer and diff.

The traps this kata is really testing

TrapWhy it fails in production
Verifying HMAC on the parsed body instead of the raw bytesJSON re-serialization changes the bytes, so the signature never matches. In NestJS you must pass rawBody: true and read req.rawBody — the default parsed @Body() will not verify.
Doing the ERP write inline before returning 200If the ERP is slow, you blow Shopify's ~5s timeout. Shopify then retries, and now you have duplicates and a pile-up. Ack fast, work async.
Assuming exactly-once deliveryShopify delivery is at-least-once and can retry up to ~8 times over ~4 hours. Without dedupe + idempotent writes, you double-apply orders.
Comparing the HMAC with ===String compare can leak timing. Use a constant-time compare (crypto.timingSafeEqual).
Returning 500 on a transient downstream hiccupA 500 makes Shopify retry the whole delivery. Once the event is safely queued, return 200 even if later processing might fail — retries belong to the worker, not the webhook.

Say how you'd test and monitor it (bonus senior points)

  • Test: a request with a bad HMAC returns 401; a valid one returns 200 and enqueues exactly one message; the same webhook id twice enqueues once.
  • Monitor: count of rejected (bad HMAC) requests, enqueue failures, and endpoint latency (must stay well under 5s).
