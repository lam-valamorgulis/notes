Lesson 2 · Theme architecture · The current generation

Horizon & Theme Blocks

Horizon is the newest theme architecture. One new folder — blocks/ — changes who controls the page, and it changes how you build. This is the lesson that marks you as current rather than out of date.

Your win: answer "What is the difference between Dawn and Horizon?" with an architectural answer, not a visual one.

Builds directly on L1 — you need Dawn's section-local blocks fresh in mind for the contrast to land. L3 then shows both themes calling the same cart endpoints in two different ways.

1. The one idea: blocks stopped belonging to sections

In Dawn, a block is declared inside one section's schema and lives only there (L1 §5). In Horizon, a block is its own Liquid file in a top-level blocks/ folder, and any section can accept it.

That is the whole architectural shift. Everything else in this lesson follows from it.

DAWN (Online Store 2.0) HORIZON (theme blocks) ────────────────────────── ──────────────────────────── sections/rich-text.liquid blocks/text.liquid <- one file schema.blocks: [heading, text] blocks/heading.liquid <- one file ^ these live HERE only ^ reusable EVERYWHERE sections/image-banner.liquid sections/any-section.liquid schema.blocks: [heading, text] schema.blocks: ^ COPIED — duplicated [{ "type": "@theme" }] ^ accepts all of them flat: 1 level, cannot nest nested: blocks inside blocks

2. What Horizon actually is

Shopify announced Horizon on 21 May 2025 as "a new collection of free themes designed to enhance your Shopify store" — ten themes, free in the Theme Store. The important sentence for an interview is the architectural one: "Horizon themes are built with theme blocks."

Shopify now documents three theme architecture versions. Being able to place any theme on this ladder is the fast way to sound current:

VersionExampleWhat it supports
Theme blocks (latest)the Horizon familyEverything in 2.0, plus theme blocks — reusable, nestable blocks
Online Store 2.0DawnSections on every page, dynamic sources, template creation, app blocks, filtering, predictive search
Vintageolder free themesSections on the home page only; no template creation, no app blocks, no filtering. Free vintage themes get security fixes only

Note what Horizon is not: it is not a rewrite away from Liquid. Horizon states the same four principles as Dawn — web-native and evergreen, lean and purposeful, server-rendered ("HTML must be rendered by Shopify servers using Liquid"), and functional over pixel-perfect. The rendering model did not change. The composition model did.

3. Writing a theme block

A theme block is one .liquid file in blocks/: markup, then a {% schema %}. The schema supports three keys worth knowing — settings, blocks (its own children), and presets (ready-made configurations a merchant can pick).

<!-- blocks/heading.liquid -->
<h2 class="heading" {{ block.shopify_attributes }}>
  {{ block.settings.text }}
</h2>

{% schema %}
{
  "name": "Heading",
  "settings": [
    { "type": "text", "id": "text", "label": "Heading text" }
  ],
  "presets": [{ "name": "Heading" }]
}
{% endschema %}

Inside the file you read your own settings from the block object. One hard rule to remember: "Theme blocks cannot access variables created outside the block." A block is a sealed unit — unlike a snippet, you cannot pass it arbitrary parameters. If it needs a value, that value must come from its own settings or from global objects.

4. How a section accepts blocks

Two pieces: declare what you accept in the schema, then render whatever the merchant configured.

<!-- sections/flexible-section.liquid -->
<div class="section">
  {% content_for 'blocks' %}
</div>

{% schema %}
{
  "name": "Flexible section",
  "blocks": [
    { "type": "@theme" },
    { "type": "@app" }
  ]
}
{% endschema %}

The two identifiers are the part to memorise:

  • {"type": "@theme"} — accept every theme block in blocks/ (except private ones, see §6).
  • {"type": "@app"} — accept app blocks, the ones installed apps provide (reviews widgets, custom forms).

You can also list specific types instead of @theme when a section should only take certain blocks.

content_for 'blocks' vs content_for 'block' The plural form, {% content_for 'blocks' %}, renders whatever the merchant arranged in the theme editor — a dynamic, reorderable area. The singular form renders one fixed block that the merchant cannot remove, and it requires a type and an id: 
{% content_for "block", type: "button", id: "static-block-1" %}
Extra parameters you pass here (for example color: "red") are readable inside that block. Use the singular form when the design requires a block to always be present — a buy button that must never be deleted.

5. Nesting — and the two limits

Because a block can declare its own blocks array, theme blocks nest inside other theme blocks. That is how Horizon builds a card that contains an image, a heading, a price, and a button, each independently editable and reorderable.

Two limits to state confidently:

  • 300 theme blocks per theme. "A theme can contain at most 300 theme blocks" — and that counts every .liquid file in blocks/, including AI-generated ones and files no section references.
  • You cannot mix the two block systems in one section. Section blocks "cannot coexist with theme blocks in the same section." A section either uses the old local blocks or the new theme blocks — never both.
The trap: the 300 limit counts files, not usage Deleting a block from every template does not free a slot. The file still counts. On a theme where merchants have been generating blocks with Shopify's AI prompt feature, unused files accumulate quietly. If a theme starts refusing new blocks, count the files in blocks/ before you debug anything else.

6. Private blocks — the underscore convention

Real Horizon has 112 files in blocks/, and most of them start with an underscore: _card.liquid, _slide.liquid, _product-card.liquid, _cart-summary.liquid.

The underscore is a deliberate convention, not a naming style. A block whose file name starts with _ is excluded from the block picker for any section or block that accepts @theme. The merchant never sees it in the "add block" list.

Why you want that: a _slide block is meaningless on its own — it only makes sense inside a slideshow. So the slideshow section declares {"type": "_slide"} explicitly as a child, while a generic section accepting @theme never offers it. You get reuse without flooding the merchant's picker with fragments.

7. What else changed: one stylesheet, a component base class, and DOM morphing

Horizon keeps the no-framework, server-rendered approach, but it organises the front end differently from Dawn. From the real repository:

ConcernDawn 15.3.0Horizon
CSSMany small component-*.css files, requested by each sectionOne large base.css (~54 KB) as the primary stylesheet
JS structureEach file calls customElements.define() itselfA shared component.js base class the others extend
DOM updatesinnerHTML replacement of section fragmentsmorph.js — patches the existing DOM in place
ToolingNo build step, no package manifest in the themejsconfig.json, package.json, and .d.ts type definitions for editor support
blocks/ folderAbsent112 files

The morphing change is the one with real user-visible consequences, and it is a strong thing to raise unprompted. Replacing a section's innerHTML destroys and rebuilds every node inside it: focus is lost, a half-typed quantity is wiped, CSS transitions restart. Morphing compares the new HTML against the live DOM and changes only what differs, so component state survives and rows can animate in and out. You will see both approaches side by side in L3.

8. Which one should a client be on?

A senior answer is a trade-off, not a recommendation:

  • New store, merchant wants to control layout → Horizon. Theme blocks are the reason it exists, and nesting means far fewer developer requests for small layout changes.
  • Existing heavily customised Dawn theme → stay. There is no migration path that converts section blocks into theme blocks; moving means rebuilding sections. The gain must justify a rebuild.
  • Vintage theme → plan to move. Sections only work on the home page, and the free vintage themes receive security fixes only.

The honest engineering point: theme blocks push power to the merchant, which reduces small tickets but widens the range of layouts a merchant can create — including broken ones. Guard rails belong in your block settings and presets.
