Lesson 4 · Theme architecture · Discounts

Discounts on the Storefront

"Add a discount box to the cart drawer" sounds like a one-hour ticket. It is the request most likely to go wrong, because the theme can apply a code but cannot decide whether it worked.

Your win: answer "How would you add a discount code field to the cart drawer, and how do you know if the code was valid?" — including why a successful response does not mean a successful discount.

Continues straight from L3: the discount parameter lives on /cart/update.js, and the same bundled section rendering repaints the cart. For discount logic that runs inside Shopify's checkout, see the main course's L24 — Shopify Functions.

1. The one idea: the theme displays discounts, it does not decide them

Discounts are calculated by Shopify — on the cart, and finally at checkout. Your theme does two things and no more: it submits a code, and it renders what Shopify says the result is. It never computes a discount amount itself.

Every mistake in this lesson comes from breaking that rule — computing a saving in Liquid, trusting a cart total as final, or treating an HTTP 200 as "the code worked".

Why the boundary is strict A discount depends on things the theme cannot see: customer eligibility, usage limits, per-customer caps, combination rules, and shipping address. Two of those are unknown until checkout. So the cart is an estimate — which is exactly why Dawn labels the cart total "Estimated total" rather than "Total".

2. The four kinds of discount, and the three classes

Two different questions, often confused. First, where the discount came from. Liquid tells you this through discount_application.type, which has four possible values:

typeMeaning
discount_codeThe customer entered a code
automaticApplied by Shopify with no code, when conditions match
manualAdded by staff on a draft order
scriptFrom a Shopify Script — the legacy engine, sunset June 2026 (see L24)

Second, what the discount acts on. These are the three discount classes, and they decide both stacking and calculation order:

ClassApplies toOrder of calculation
ProductSpecific items or collections1st — against individual items
OrderThe cart subtotal2nd — against the subtotal already reduced by product discounts
ShippingShipping cost3rd — last

The sequence matters for a question you will be asked: "the client says 20% off plus £10 off gives the wrong number." It does not — product discounts apply first, then the order discount applies to the reduced subtotal, not the original. The maths is right; the expectation is wrong.

Recall — cover the pageName the four type values and the three classes. In what order do the classes calculate?

3. What Liquid gives you — and the deprecated trap

Discounts appear at two levels, and you must render both or the numbers look wrong:

LevelPropertyUse it for
Cartcart.cart_level_discount_applicationsOrder-level discounts, shown near the totals
Cartcart.discount_applicationsAll discount applications on the cart
Lineline_item.line_level_discount_allocationsDiscounts applied directly to that line
Lineline_item.discount_allocationsAll allocations touching that line

A discount_application carries title (the customer-facing name), total_allocated_amount, type, value and value_type (fixed_amount or percentage), target_type (line_item or shipping_line), and target_selection (all, entitled, or explicit).

The trap: the deprecated price properties silently miss most discounts Four line_item properties are deprecated, and the reason is what makes this dangerous — they only ever included Shopify Scripts discounts, so they exclude automatic discounts and discount codes entirely:
DeprecatedUse instead
line_item.priceline_item.final_price
line_item.line_priceline_item.final_line_price
line_item.total_discountline_item.line_level_total_discount
line_item.discountsline_item.discount_allocations
cart.discountscart.discount_applications

This is the highest-value bug in the lesson. An old theme using item.price shows the undiscounted price while the cart total is discounted — the customer sees prices that do not add up to the total. Since Scripts were sunset in June 2026, these properties now miss essentially everything.

For the "was" price, pair original_price with final_price (or original_line_price with final_line_price) and only show a strike-through when they differ. Do not calculate a percentage saved yourself — read total_allocated_amount.

4. Applying a code from the cart

There is no dedicated discount endpoint. You use the discount parameter on /cart/update.js from L3:

ValueEffect
"SAVE10"Apply one code
"SAVE10,FREESHIP"Apply several — comma separated
""Remove all discounts
There is no "remove one code" call The parameter replaces the whole set. To remove a single code you send the codes you want to keep. That means the theme must track the currently applied codes and rebuild the list on every change — which is exactly what Horizon does (§6), reading them back out of the rendered DOM.

5. The trap that defines this lesson: a bad code still returns 200

Submitting a nonsense code does not fail the request. You get a normal cart back. If you treat the response as success, your UI reports "Discount applied!" and nothing changed.

The real check is a discount_codes array on the cart response, where each entry has a code and an applicable boolean. Horizon's cart-discount.js does precisely this:

const data = await response.json();

if (
  data.discount_codes.find((discount) => {
    return discount.code === discountCodeValue && discount.applicable === false;
  })
) {
  discountCode.value = '';
  this.#handleDiscountError('discount_code');   // "Invalid discount code"
  return;
}
Be honest about this one in an interview discount_codes[] and its applicable flag are not documented in the Cart AJAX API reference — the reference just says the response is "the JSON of the cart". But Shopify's own Horizon theme relies on the field in production, and it is annotated in the source as { code: string; applicable: boolean }. Saying "this is how Shopify's own theme does it, though the field isn't in the reference docs" is a stronger answer than pretending it is documented.

There is a second, subtler failure. A shipping discount code can come back applicable: true and still show nothing in the cart — because shipping discounts only take effect once there is a shipping address, at checkout. Horizon handles this by comparing the discount pills in the newly rendered HTML against the codes it already had: if the rendered list did not grow but the cart says the code is applicable, it shows "Discount not applicable for shipping". Its own comment explains the reasoning — it checks "the liquid logic compared to the cart payload to assess whether we leveraged a valid shipping discount code."

6. Dawn has no discount field. Horizon does.

This is the cleanest example of the Dawn↔Horizon difference in the whole sub-course, and it is a fact worth stating plainly because clients ask for this feature constantly.

Dawn 15.3.0Horizon
Discount code input in cartNone. Codes are entered at checkoutYes — cart-discount.js, with removable pills
Displays discountsYes — cart-level and line-levelYes
Invalid-code handlingn/aChecks applicable, clears input, shows an error
Repaint after changen/amorphSection, so the input keeps focus

Dawn's display code is small and worth copying as the reference pattern. Cart level, in sections/main-cart-footer.liquid:

{%- if cart.cart_level_discount_applications.size > 0 -%}
  <ul class="discounts list-unstyled" role="list"
      aria-label="{{ 'customer.order.discount' | t }}">
    {%- for discount in cart.cart_level_discount_applications -%}
      <li class="discounts__discount discounts__discount--position">
        {{- 'icon-discount.svg' | inline_asset_content -}}
        {{ discount.title | escape }}
        (-{{ discount.total_allocated_amount | money }})
      </li>
    {%- endfor -%}
  </ul>
{%- endif -%}

And line level, in sections/main-cart-items.liquid:

{%- for discount in item.line_level_discount_allocations -%}
  <li class="discounts__discount">
    {{- 'icon-discount.svg' | inline_asset_content -}}
    {{ discount.discount_application.title | escape }}
  </li>
{%- endfor -%}

Three things to notice. The title is always run through | escape — a merchant types the discount name, so it is untrusted input. The amount uses the | money filter rather than manual formatting, because currency formatting is a platform concern. And an allocation reaches its parent through discount.discount_application.title — the allocation is the amount on this line, the application is the discount itself.

Horizon's apply call is the L3 pattern with a discount parameter added:

const allDiscountCodes = [...existingDiscounts, discountCodeValue];

const config = fetchConfig('json', {
  body: JSON.stringify({
    discount: allDiscountCodes.join(','),      // the FULL set, every time
    sections: [this.dataset.sectionId],        // bundled section rendering
  }),
});
const response = await fetch(Theme.routes.cart_update_url, { ...config });

7. Stacking: what actually combines

Two limits customers hit, worth knowing exactly:

  • A customer can use at most 5 product or order discount codes and 1 shipping discount code on the same order.
  • Multiple shipping discounts cannot combine with each other.

Which combinations are allowed universally: product + free shipping; product + product on separate items; order + free shipping. Stores meeting eligibility requirements can also combine product + order, and order + order. Shopify Plus merchants can stack multiple product discounts on the same line item using tags.

Discounts do not combine by default "Discounts don't automatically combine. You must manually configure each discount's combination settings." So when a client reports "my two discounts won't stack", the first thing to check is not your code — it is the combination settings on each discount in the admin. Automatic discounts and codes can combine, but only if each one is configured to combine with the other's class. When an automatic discount conflicts with a customer's code, Shopify applies the best discount or combination.

8. Applying a discount by link

You do not always need a form. Shopify supports a shareable discount URL:

https://shop.example.com/discount/SAVE10
https://shop.example.com/discount/SAVE10?redirect=/collections/fresh-finds

The default destination is the store's home page; the optional redirect parameter sends the customer somewhere else. The discount "applies automatically to your customer's next checkout cart, or to any active carts they have open" — and the 5-code limit still applies. This is the right tool for an email campaign or an influencer link, and it needs no theme code at all. Knowing it saves you from building a form where a URL would do.

9. Where the theme stops

Three things you cannot do from a theme, and what to reach for instead:

RequirementWhere it belongs
Custom discount logic ("buy 3 of any shirt, cheapest free")A Discounts Function — see L24
Creating or editing discounts programmaticallyThe Admin GraphQL API — see L1
Showing the final shipping discount in the cartNot possible — no address yet. Set the expectation instead

That last row is the honest answer to a common request. If a client insists the cart must show the exact final total including a shipping discount, the correct response is that Shopify cannot know it before checkout — so the design needs to say "estimated", as Dawn does.

Say it like this

"The theme displays discounts; it never decides them. To apply a code from the cart I use the discount parameter on /cart/update.js — comma-separated for several codes, an empty string to clear them all. There is no remove-one call, so I send the full set I want to keep and track the applied codes in the UI. The critical part is validation: an invalid code still returns a normal 200 with a normal cart, so I check the discount_codes array on the response for my code with applicable: false — that field isn't in the reference docs, but Horizon relies on it in production. Shipping codes have a second failure: they can be applicable and still show nothing, because shipping discounts need an address, so they only bite at checkout. For display I read cart.cart_level_discount_applications and line_item.line_level_discount_allocations, and I avoid item.price, line_price, total_discount and cart.discounts — they're deprecated because they only ever included Shopify Scripts discounts, so they miss codes and automatic discounts entirely. Worth knowing: Dawn ships no discount field at all, Horizon does; classes calculate product, then order, then shipping; a customer can use five product-or-order codes plus one shipping code; and discounts don't stack unless each one is configured to combine."
