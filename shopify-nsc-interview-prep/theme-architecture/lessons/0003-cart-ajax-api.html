Lesson 3 · Theme architecture · The cart

The Cart AJAX API

Five endpoints run every cart interaction on a Shopify storefront. Knowing the paths is junior-level. Knowing which identifier to send, what the API will not validate, and how to repaint the page in one round trip is the senior answer.

Your win: answer "How does add-to-cart work in a Shopify theme, and how does the cart drawer update without a page reload?" — and name the trap in update.js.

Uses the Section Rendering API from L1 §8, and closes the Dawn↔Horizon comparison from L2 §7 with the real code from both themes.

1. The one idea: the cart is one server-side object you mutate over HTTP

The cart does not live in JavaScript. It lives on Shopify's servers, attached to a cart token. Your theme's JavaScript sends small POST requests that mutate it, and Shopify replies with the new cart as JSON. There is no client-side cart state to keep in sync — there is one authoritative object and a series of requests against it.

That framing matters because it explains the traps later in this lesson: anything that assumes a stable local view of the cart (a line position, a quantity you believe is available) can be wrong by the time your next request lands.

2. The five endpoints

Every path is prefixed with an optional locale — /{locale}/cart/add.js — which is why themes read the URLs from window.routes instead of hard-coding them (§5).

EndpointMethodPurposeKey parameters
/cart/add.jsPOSTAdd one or more variantsitems: array of { id, quantity }; optional properties, selling_plan, parent_id
/cart.jsGETRead the whole cartnone
/cart/change.jsPOSTChange one existing lineid or line; plus quantity, properties, selling_plan
/cart/update.jsPOSTChange several lines, the note, attributes, or a discountupdates, note, attributes, discount
/cart/clear.jsPOSTEmpty the cartnone

Add returns the added line items. The other four return the full cart object — items, token, note, attributes, item_count, currency, totals, and cart_level_discount_applications. All money values come back in the customer's presentment currency.

There are also three shipping-rate endpoints. Shopify's recommended pair is asynchronous: POST /cart/prepare_shipping_rates.json to start the calculation (it returns null), then GET /cart/async_shipping_rates.json to collect the result. The synchronous GET /cart/shipping_rates.json exists but is "subject to throttling".

3. change.js vs update.js — the distinction they will test

They look interchangeable. They are not, and the differences cause real bugs.

change.jsupdate.js
How many linesOne at a timeSeveral at once
Existing items only?Yes — "only items already in your cart can be changed"No — adds a new line if the variant_id is not in the cart
Validates stock?YesNo — see the trap below
Can also setproperties, selling_plannote, attributes, discount
Remove a linequantity: 0quantity 0 in updates
The trap worth memorising: update.js can oversell Shopify documents plainly that update.js "doesn't validate the quantity on variants that are already in the cart. This means that it's possible to add more inventory than is available." So a "set quantity to 99" control built on update.js will happily put 99 in the cart when 3 exist, and the customer only discovers it at checkout. Use change.js for quantity edits on existing lines — it validates — and keep update.js for multi-line updates, notes, attributes, and discount codes.

A second trap in the same family: add.js is more forgiving than people expect. If the requested quantity exceeds stock, it adds the maximum available rather than failing. So a successful response does not mean you got the quantity you asked for — read the returned line item if the number matters.

4. line vs key — the positional bug

change.js accepts two ways to identify a line:

  • line — the 1-based position in the cart.
  • id — a variant id, or better, the line item key (a string like 40053432:8b1f...).

Position is fragile. Remove line 2 and everything below shifts up by one, so a queued request that says "line 3" now edits a different product. Shopify's own guidance points the same way for update.js: using the line item key is recommended over variant_id when the cart holds several identical variants — because the same variant added with different properties, prices, or selling plans becomes separate line items, and a bare variant id cannot tell them apart.

Practical rule Prefer the line item key. Reach for line only where the docs require it — with selling_plan, where you must identify by line and always send quantity. And send cart writes one at a time: the cart is a single server-side object and change.js only accepts one line per request, so firing several in parallel invites lost updates and stale positions. Queue them, or disable the control while a request is in flight — which is exactly what Dawn's loading state does.

5. Never hard-code the URLs

Because the paths carry a locale prefix, a hard-coded /cart/add.js breaks on a multi-language store. Themes publish the routes from Liquid into a global. Dawn's layout/theme.liquid does exactly this:

window.routes = {
  cart_add_url:    '{{ routes.cart_add_url }}',
  cart_change_url: '{{ routes.cart_change_url }}',
  cart_update_url: '{{ routes.cart_update_url }}',
  cart_url:        '{{ routes.cart_url }}',
  predictive_search_url: '{{ routes.predictive_search_url }}'
};

Then the JavaScript uses routes.cart_change_url. Saying this in an interview is a small detail that signals you have shipped on a real multi-market store.

6. Bundled Section Rendering — the whole point

Here is the part that turns a working cart into a good one. A naive implementation needs two round trips: POST the change, then fetch the re-rendered cart markup. Bundled section rendering collapses that into one.

Add two parameters to add, change, update, or clear:

ParameterMeaning
sectionsComma-separated section ids to re-render — maximum 5
sections_urlThe page path to render them in the context of. Must start with /. Defaults to the Referer header

The response then carries an extra sections key: an object of section id → rendered HTML, alongside the usual cart JSON. One request, updated cart and fresh markup for the cart drawer, the header count bubble, the totals, and the live region.

Two failure behaviours that differ A section that fails to render does not fail the request — that section simply comes back as null, so your code must handle a missing section instead of assuming HTML. But an invalid sections_url that does not start with / returns HTTP 400 for the entire request — the cart change included. Build the value from window.location.pathname and it is always correct.

Why the context parameter exists at all: a section renders differently depending on the page it sits on. Without sections_url, Shopify falls back to the Referer header, which you should not depend on.

7. The real Dawn implementation

This is Dawn 15.3.0's quantity update, close to verbatim. Read it as the canonical pattern:

updateQuantity(line, quantity, event, name, variantId) {
  this.enableLoading(line);                    // block further input

  const body = JSON.stringify({
    line,
    quantity,
    sections: this.getSectionsToRender().map((section) => section.section),
    sections_url: window.location.pathname,    // always starts with "/"
  });

  fetch(`${routes.cart_change_url}`, { ...fetchConfig(), ...{ body } })
    .then((response) => response.text())
    .then((state) => {
      const parsedState = JSON.parse(state);

      if (parsedState.errors) {                // roll the input back
        quantityElement.value = quantityElement.getAttribute('value');
        this.updateLiveRegions(line, parsedState.errors);
        return;
      }

      this.classList.toggle('is-empty', parsedState.item_count === 0);

      this.getSectionsToRender().forEach((section) => {
        const elementToReplace =
          document.getElementById(section.id).querySelector(section.selector)
          || document.getElementById(section.id);
        elementToReplace.innerHTML = this.getSectionInnerHTML(
          parsedState.sections[section.section],   // HTML from the same response
          section.selector
        );
      });
    });
}

And the list of what it repaints — note it is exactly four, inside the limit of five:

getSectionsToRender() {
  return [
    { id: 'main-cart-items',      section: ..., selector: '.js-contents' },
    { id: 'cart-icon-bubble',     section: 'cart-icon-bubble',     selector: '.shopify-section' },
    { id: 'cart-live-region-text',section: 'cart-live-region-text',selector: '.shopify-section' },
    { id: 'main-cart-footer',     section: ..., selector: '.js-contents' },
  ];
}

Three details worth stealing:

  • The selector field solves the wrapper problem from L1 §8. Dawn does not inject the whole returned section; getSectionInnerHTML parses it and pulls out just .js-contents, so shopify-section wrappers never nest.
  • The error path rolls the input back to its previous value with getAttribute('value'). The server rejected the change, so the visible number must not keep the value the customer typed.
  • cart-live-region-text is an accessibility section. It exists so a screen reader announces the change. It is easy to drop when writing a custom cart, and noticing it is a strong senior signal.

Add-to-cart follows the same shape in product-form.js, with one difference: it sends a FormData built from the real <form> and appends sections and sections_url to it, deleting the JSON Content-Type header so the browser sets the multipart boundary itself. Both JSON and FormData are supported by the API.

8. How Horizon does the same thing

Horizon calls the identical endpoint with the identical parameters — the API is shared. What changed is the last step:

// Horizon — same request shape as Dawn
const body = JSON.stringify({
  line: line,
  quantity: quantity,
  sections: Array.from(sectionsToUpdate).join(','),
  sections_url: window.location.pathname,
});
fetch(`${Theme.routes.cart_change_url}`, fetchConfig('json', { body }));

// ...but the DOM update morphs instead of replacing
morphSection(this.sectionId, parsedResponseText.sections[this.sectionId], {
  mode: this.isDrawer ? 'hydration' : 'full',
});

Dawn assigns innerHTML, which destroys and rebuilds every node in the section. Horizon's morphSection (from @theme/section-renderer) compares the new HTML against the live DOM and changes only what differs. The practical wins: a quantity input keeps focus and its typed value, transitions do not restart, and removed rows can animate out. Horizon also falls back to sectionRenderer.renderSection(...) when a response arrives without section HTML — the null case from §6.

The transferable idea Both themes make the same request. The quality difference is entirely in how the response is applied to the DOM. When you are asked to improve a janky custom cart, the fix is usually not the network call — it is replacing wholesale innerHTML replacement with a targeted update.

9. Line item properties and cart attributes

Two extra mechanisms, and two naming rules that are easy marks in an interview:

  • Line item properties — per-line custom data (engraving text, a gift note), sent as properties. A property whose name starts with a single underscore (_source) is private, but you must hide it in your Liquid yourself — it is a convention the theme enforces, not the platform.
  • Cart attributes — cart-wide data, sent as attributes. A name starting with a double underscore (__internal) is automatically hidden and, notably, does not affect caching.
  • properties is replace-not-merge on change.js: sending it overwrites the entire object. And once set, properties cannot be emptied — to clear them you remove the whole line item.

One more small fact with real consequences: items that differ in price, properties, or selling plan become separate line items even for the same variant. That is precisely why the line item key beats a variant id (§4).

Also worth knowing: clear.js zeroes the items but "does not remove cart attributes or the cart note." If a client reports "I emptied the cart but my gift message is still there", that is the reason.

Say it like this

"The cart lives on Shopify's servers, keyed by a cart token, and the theme mutates it over five endpoints — add.js, cart.js, change.js, update.js, clear.js. I read the URLs from window.routes rather than hard-coding them, because the paths carry a locale prefix. For a quantity edit I use change.js, not update.js: change.js handles one existing line and validates stock, while update.js explicitly does not validate quantity on variants already in the cart, so it can oversell. I identify the line by its line item key, not by line position, because positions shift when a line is removed and the same variant with different properties becomes separate line items. Then the key move is bundled section rendering: I send sections — up to five — plus sections_url from window.location.pathname, and the response comes back with both the new cart JSON and the re-rendered HTML, so one round trip updates the drawer, the header count, the totals, and the accessibility live region. Dawn applies that HTML by parsing out an inner selector and assigning innerHTML; Horizon morphs the DOM instead, so focus and typed input survive. And I handle a null section, because a failed section does not fail the request — though a sections_url not starting with a slash returns 400 for the whole thing."
