Dawn Theme Architecture

Dawn is the reference theme for Online Store 2.0. Before you can explain what Horizon changed, you must be able to draw Dawn's seven folders from memory and say what each one owns.

Your win: answer "Walk me through the architecture of a Shopify theme." — the folders, how a URL becomes a page, and where the JavaScript lives.

This sub-course starts here because Dawn is the shape almost every live theme still has. Lesson 2 shows what Horizon replaced; Lesson 3 covers the Cart AJAX API that both themes use.

1. The one idea: Shopify renders the HTML, not your JavaScript

A Shopify theme is server-rendered. Shopify's servers run your Liquid files and send finished HTML to the browser. Dawn's own stated principle is that "HTML must be rendered by Shopify servers using Liquid," and that "business logic and platform primitives such as translations and money formatting don't belong on the client."

This is the fact that explains every other choice in the theme. There is no React, no Vue, and no build step. JavaScript is added only where the server cannot help — a drawer opening, a quantity changing. Shopify calls this "JavaScript-only-as-needed".

Why an interviewer cares Many candidates describe a theme like a single-page app. It is the opposite. If you say "server-rendered Liquid, progressive enhancement, no framework" in your first sentence, you have already shown you know the platform rather than just the syntax.

2. The seven folders

Only one thing is required: a layout folder containing theme.liquid. Everything else is optional — though a real theme uses all of it. Subdirectories other than the ones listed are not supported.

FolderWhat it ownsIn Dawn 15.3.0
layout (required)The outer HTML shell every page renders inside2 files
templatesWhat renders for each page type (product, collection, cart…)16 files
sectionsReusable, merchant-editable content modules54 files
snippetsReusable Liquid fragments, rendered anywhere37 files
assetsCSS, JavaScript, images, fonts185 files
configTheme settings schema and their saved values2 files
localesTranslated strings51 files

Note what is absent: Dawn has no blocks/ folder. That single missing folder is the whole difference between Dawn's architecture and Horizon's — Lesson 2 picks that up.

3. How a URL becomes a page

Four steps, always in this order. Learn to say them as a chain:

GET /products/blue-shirt │ ├─ 1. TEMPLATE templates/product.json "which sections, in what order?" │ ↓ (a JSON file listing section ids + their settings) ├─ 2. SECTIONS sections/main-product.liquid each one renders its own markup │ ↓ a section may render snippets, and may accept blocks ├─ 3. SNIPPETS snippets/product-variant-picker.liquid reused fragments │ ↓ └─ 4. LAYOUT layout/theme.liquid wraps the result {{ content_for_header }} ← Shopify injects scripts here {{ content_for_layout }} ← the template output lands here

The two Liquid objects in step 4 are the ones to memorise. In Dawn's layout/theme.liquid they sit at lines 46 and 317: {{ content_for_header }} (Shopify's own scripts — app embeds, analytics) and {{ content_for_layout }} (the rendered template). Leave either one out and the theme breaks.

4. JSON templates are the Online Store 2.0 change

Before Online Store 2.0, a template was a .liquid file with hard-coded markup, and only the home page could have sections. Online Store 2.0 introduced sections on every page, driven by JSON templates. A JSON template holds no markup at all — it is a list of section ids and their saved settings:

{
  "sections": {
    "main": {
      "type": "main-product",
      "settings": { "enable_sticky_info": true }
    },
    "recommendations": {
      "type": "product-recommendations",
      "settings": {}
    }
  },
  "order": ["main", "recommendations"]
}

Because the merchant edits that JSON through the theme editor, they can reorder, add, and remove sections on any page without a developer. Your job shifts: you build the section, and expose the right {% schema %} settings so the merchant can drive it.

Sections vs snippets — the distinction they will test A section has a {% schema %}, so it is merchant-editable and appears in the theme editor. A snippet has no schema — it is a plain reusable fragment you {% render %} from code, and the merchant never sees it. If a merchant must be able to change it, it is a section. If only developers touch it, it is a snippet.

5. Dawn's blocks are section-local

Dawn does have blocks, but they are declared inside a section's own schema and belong only to that section. These are section blocks, and they carry two hard limits: they "only support a single level of hierarchy, and cannot be nested," and they cannot be mixed with theme blocks in the same section.

{% schema %}
{
  "name": "Rich text",
  "blocks": [
    { "type": "heading",  "name": "Heading",  "settings": [] },
    { "type": "text",     "name": "Text",     "settings": [] }
  ]
}
{% endschema %}

So in Dawn, a "heading" block written for the rich-text section cannot be reused by the image-banner section. You copy it. That duplication is exactly the problem theme blocks were created to solve.

6. Where the JavaScript lives: web components

Dawn has no framework, so it uses the browser's own component system — custom elements. Each interactive piece is a class registered with customElements.define(), and the matching Liquid renders that tag. Real examples from Dawn 15.3.0:

Custom elementWhat it does
<product-form>Intercepts the add-to-cart submit and posts it with fetch
<cart-items>Quantity changes and line removal on the cart page
<cart-drawer>The slide-out cart
<variant-selects>Switching variant updates price, media, and availability
<quantity-input>The plus/minus stepper
<predictive-search>Live search suggestions as you type
<modal-dialog>, <slider-component>Dialogs and carousels

The pattern is always the same: the server sends real HTML, and the custom element upgrades it in place. If the JavaScript fails to load, the markup still works — the form still posts, the links still navigate. That is progressive enhancement, and it is why Dawn supports old browsers "through progressive enhancement—not polyfills."

7. CSS is split per component and loaded by the section that needs it

Dawn does not ship one big stylesheet. It ships many small ones, and each section asks for only the files it uses. The top of sections/main-cart-items.liquid really looks like this:

{{ 'component-cart.css'       | asset_url | stylesheet_tag }}
{{ 'component-cart-items.css' | asset_url | stylesheet_tag }}
{{ 'component-totals.css'     | asset_url | stylesheet_tag }}
{{ 'component-price.css'      | asset_url | stylesheet_tag }}
{{ 'component-discounts.css'  | asset_url | stylesheet_tag }}

The benefit is that a product page never downloads the cart's CSS. The cost is 185 files in assets/ and many requests. Horizon takes the opposite trade — Lesson 2 shows why.

8. The Section Rendering API

Because sections are server-rendered units, Shopify can re-render one of them on request. That is the Section Rendering API, and it is the mechanism behind every "the page updated without reloading" feature in a Shopify theme.

ParameterReturnsLimit
?section_id=The rendered HTML directlyone section
?sections=A JSON object pairing each section id with its HTMLup to 5 sections

You can append it to any page URL — /collections/featured?sections=main-collection-product-grid. One real limit to remember: you cannot pass section settings through the API. If the section already exists in the template, its saved settings apply; otherwise its defaults are used.

The trap: fetching HTML you then have to unwrap The API returns the section wrapped in its own <div class="shopify-section">. If you drop that whole string into a container that is already a section wrapper, you nest wrappers and the CSS breaks. Dawn handles this by parsing the returned HTML and pulling out only the inner selector it cares about — you will see that exact code in Lesson 3.
Say it like this

"A Shopify theme is server-rendered Liquid — Shopify's servers produce the HTML, so business logic and money formatting stay off the client. The structure is seven folders, and only layout/theme.liquid is strictly required; it must contain content_for_header and content_for_layout. A request resolves template → sections → snippets → layout. Online Store 2.0 made templates JSON, so sections work on every page and merchants can reorder them. Dawn's blocks are section-local: one level deep, not nestable, not reusable across sections. Interactivity is plain web components — product-form, cart-items, variant-selects — upgrading server HTML in place, with per-component CSS loaded by whichever section needs it. And because sections are server-rendered units, the Section Rendering API can re-render up to five of them, which is how the cart updates without a page reload."
