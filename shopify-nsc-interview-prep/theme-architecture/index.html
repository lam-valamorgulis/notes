The Map — Theme Architecture

One page that connects this sub-course into a story: how a Shopify theme is built, what changed between Dawn and Horizon, and how the cart updates without a page reload.

The main course looks at Shopify from the server — apps, webhooks, ERP sync. This sub-course turns around and looks at the storefront: the theme itself. Four lessons, in order. First Dawn, the Online Store 2.0 baseline almost every live theme still follows. Then Horizon, the newer theme-block architecture, and exactly what it changed. Then the Cart AJAX API, where the two themes make the same request and apply the answer in two different ways. Finally discounts, the surface where the theme's limits show most clearly. Read it as one argument: Shopify renders the HTML and decides the prices, so the interesting engineering is in composition and in how you repaint the page.

The big picture — how it all connects

The whole sub-course answers one question: "If Shopify's servers render the HTML, what is actually left for a theme developer to design?" The answer is two things — composition (which reusable units exist, and who can rearrange them) and repainting (how a page updates after the shopper acts). Lesson 1 sets the vocabulary with Dawn. Lesson 2 shows Horizon changing the composition rules. Lesson 3 shows both themes repainting the cart. Lesson 4 pushes on the boundary until it shows: the theme can ask for a discount, but only Shopify decides what it is worth.

One thread runs through all four: the Section Rendering API. Lesson 1 introduces it as a consequence of sections being self-contained server-rendered units. Lesson 3 shows its real use — the bundled sections parameter that lets a single cart request return both new cart JSON and fresh HTML. Lesson 4 reuses that same call with one more parameter.

And one warning repeats: in both cart lessons, the request succeeding is not the same as the request working. update.js will happily oversell stock (L3) and will happily accept an invalid discount code (L4), returning a clean 200 both times. Knowing which field to check instead is what separates a working cart from a correct one.

Chapter 1 Learn the baseline before the news

Start with Dawn theme architecture (L1). It sets every word you need later: the seven folders and the one that is actually required, the template → sections → snippets → layout chain, the two Liquid objects theme.liquid cannot live without, and the JSON template that let merchants reorder sections on any page. It also introduces the two ideas the rest of the sub-course builds on — that blocks in Dawn are trapped inside one section, and that a section can be re-rendered on its own through the Section Rendering API.

They will push here
  • Walk me through the architecture of a Shopify theme.
  • What is the difference between a section, a snippet, and a block?
  • There is no framework — so how does the cart drawer actually open?
  • Why is per-component CSS a good idea, and what does it cost?

Chapter 2 Then say precisely what changed

Horizon & theme blocks (L2) is the lesson that dates you as current. The whole shift is one sentence — a block became its own file — and everything else follows: any section opts in with @theme, blocks nest inside blocks, and merchants gain far more control. It also gives you the two limits worth stating without being asked (300 block files, counted even when unreferenced; and no mixing the two block systems in one section), the underscore convention for private blocks, and the three-rung architecture ladder that lets you place any theme a client shows you.

They will push here
  • What is the difference between Dawn and Horizon? (Answer architecturally, not visually.)
  • Why would you name a block file _slide.liquid?
  • A client is on a heavily customised Dawn theme — should they move to Horizon?
  • What stops a merchant building a broken layout once blocks are theirs to arrange?

Chapter 3 Prove it on the hardest surface: the cart

The Cart AJAX API (L3) is where the two chapters meet. Five endpoints, one server-side cart, and a set of traps that separate people who have shipped a cart from people who have read about one: update.js does not validate stock and will oversell; line positions shift under you, so the line item key is the safer identifier; and a sections_url without a leading slash fails the entire request while a broken section merely returns null. Then the payoff — the same request in Dawn and in Horizon, differing only in how the response is applied to the DOM, which is nearly always where a janky custom cart is actually broken.

They will push here
  • How does the cart drawer update without a page reload?
  • change.js or update.js for a quantity stepper — and why?
  • Why not identify the line by its position?
  • The quantity input loses focus every time it updates. What is wrong?

Chapter 4 Find the edge of what a theme may decide

Discounts on the storefront (L4) takes the most ordinary-sounding request in Shopify theme work — "put a discount box in the cart drawer" — and shows why it is the one most likely to ship broken. The theme can submit a code through the same /cart/update.js call from Chapter 3, but it cannot judge the result: an invalid code comes back as a perfectly normal 200 with a perfectly normal cart. The lesson gives you the field to check instead, the deprecated price properties that silently hide every modern discount, the stacking rules and code limits, and the plainest Dawn↔Horizon contrast in the sub-course — Dawn ships no discount input at all, Horizon ships one. It closes on the boundary itself: what belongs in a Function or the Admin API instead, and the one thing a cart genuinely cannot know.

They will push here
  • How do you know the discount code was valid? (Not from the status code.)
  • The line prices don't add up to the cart total. What did the previous developer use?
  • The client's two discounts refuse to stack. Where do you look first?
  • Can the cart show the final total including a shipping discount? Why not?
