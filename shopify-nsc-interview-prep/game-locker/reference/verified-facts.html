Verified Facts About Game Locker

Every checkable fact this course rests on, with where it came from and how much to trust it. No lesson re-argues a fact. Lessons cite a row here instead.

Why this page exists: the first version of this course was written from Game Locker's public website and the job description. Then a real integration discovery arrived — written against a live Game Locker tenant. It corrected six things the course taught and added eighteen facts the course did not have. This page is the ledger. It is also where the honest gaps live, so they never quietly turn into claims.

1. How to read the labels

LabelMeansHow you may use it

The rule that matters most on this page The discovery this page draws from corrected itself in public — several of its early claims were retracted by their own author within three weeks. A "10.8% coverage" figure was withdrawn as a dev-tenant artefact. A "buy price is a computable percentage of market price" claim was tested and failed. A source that retracts is more trustworthy, not less. But it means the retractions travel with the facts. Where a row below replaces an earlier claim, the earlier claim is shown struck through, because knowing what is not true is what stops you asserting it in a room.

2. Provenance, and why it is not named here

The discovery is an engineering audit written inside an agency, about a delivery project, for a client who is a Game Locker customer. It names that client, six people, budget figures, an internal communications hold, and a client complaint.

None of that is in this course. This folder is published to a web host, and the course exists to prepare for an interview at Game Locker — who is the vendor in that story. So the split is fixed:

KeptRemoved

Two labels are used for the sources: D1 (the original discovery, 2026-07-07, later superseded) and D2 (the current state of record, 2026-07-31). Exact locators live outside this repository, in the session notes for 2026-08-17.

How you are allowed to say you know this

"I've read a detailed integration discovery written against your platform — a live tenant, the Shopify sync, the buy-rule pricing, the credit ledger."

Not "I built it". Nothing on that project is assigned to you. B01 and B05 both work this line properly, because getting it wrong is the fastest way to lose the room.

3. Corrections — where this course was wrong

Six rows. Each one is a thing a previous version of this course would have had you say out loud.

WasIsLabel
"~145 million cards, 18+ games" /catalogue/metrics returns totalItems.count = 1,122,612 across 19 games, MTG alone 869,531, and newItems.count = 201 per day. Treat 145M as a marketing figure about cards ever printed; 1.12M is the number a system has to hold verified
"daily repricing from global price feeds" Right, and now exact. Their change log reads "Changes will be reflected on Inventory tomorrow at 6.00 am" — so it is a nightly batch that publishes at 06:00. On one sampled day 38,715 MTG rows updated, 403 were data corrections, and 389 of 38,309 price moves were ≥30%. Against ~869,531 MTG cards that is ~4.4% moving on a given day and ~0.04% moving hard verified
"they have a direct Shopify integration" Proven at the strongest tier available. Shopify's Product.events log carries appTitle "Game Locker", attributeToApp true, and messages like "Game Locker created a new product: …". App attribution is written by Shopify, not by the app, so it cannot be faked by naming conventions. There is no public App Store listing — it is a custom or unlisted app verified
"Game Locker is the system of record and Shopify is a channel hanging off them" True for catalogue and price. False for inventory. Their own team: "you would also never need to read/update inventory from our side, as we are synced with your Shopify products, so you just need to manage stock updates from that end and it syncs with us." So stock is written in Shopify and flows back. This is the single biggest correction on the page — see §7 reported, corroborated twice
"condition × language × finish — the three-option cap is the constraint that decides the model" They use one option axis: Condition: [NM, LP, MP, HP, DMG] → 5 variants. Foil is a separate product, title suffix - Foil, tag Variant: Foil. Language is not modelled at all. They spend one of their three slots and leave two unused verified
"card attributes go to metafields and metaobjects" Attributes arrive as tags: LocationId: …, Magic: The Gathering, Rarity: mythic, Set: …, Variant: Foil. Exactly two product metafields exist — custom.external_card_id and custom.external_location_id — and neither has a metafield definition. Every variant metafield is [] verified
"Game Locker lacks a buy list feature" It has a full one. Columns Buylist ID, Customer name, Submitted at, Buylist status, Total qty, Channel, Payment ref, Payment status, Quoted buy price, Profit %. Tabs All / Quoted / Reviewed / Completed, plus "Create a buylist". Buylists are orders with orderType=buy. What it lacks is a customer-facing one verified
Why the metafield miss is worth understanding The audit first reported "no GameLocker metafields exist" and was wrong. It had queried metafieldDefinitions — but an app can write metafields without defining them, so a definitions query returns nothing while the data sits on the product. It had also filtered on product_type:*Single* when the real type is Magic: The Gathering TCG. Two misses, one root cause: querying the schema instead of reading the rows. That is a genuinely useful Shopify lesson and A02 teaches it.

4. The API surface

#FactLabel
F1 Base https://api.gamelocker.co, on AWS API Gateway, region ap-southeast-2 (Sydney). An unauthenticated call returns 403 {"message":"Missing Authentication Token"} with x-amz-apigw-id headers — the API Gateway signature verified
F2 Auth is AWS Cognito. Authorization: Bearer <id-token>, a JWT. User pool ap-southeast-2_<pool>, app client <app-client-id>. The claim custom:company carries the tenant. iat → exp = 86400s, so a token lives 24 hours verified
F3 access-control-allow-origin is locked to https://shop.gamelocker.co. A browser on any other origin is blocked, so a third party integrates server-side or not at all verified
F4 One endpoint serves two surfaces. GET /inventory/search powers both the buy list and the full card page. Filter params include buyCashPriceFilter.criteria=gte, buyCashPriceFilter.min, the same pair for credit, plus locationId, limit, sortBy. Each item returns buyCashPrice, buyCreditPrice, sellPrice, marketPrice, condition, variant, rarity, image, description (oracle text) and extendedAttributes (mana cost, types, colours, artist) verified
F5 GET /catalogue/metrics returns catalogue scale and a per-day product-run summary — the source of every number in §3 row 1 verified
F6 No external API keys. The Cognito app client has USER_PASSWORD_AUTH enabled but is configured with a secret the vendor does not hand out — a login probe returned NotAuthorizedException: configured with secret but SECRET_HASH was not received. The secret is not in the front-end bundle. Their admin site has no self-serve API-key page verified
F7 Their stated policy: no external API key access "at this time", and if ever, read access only, for authenticated accounts, for security reasons. A later, warmer statement from a second person: "we need an API… we just don't have the resources for it. So we'll get to it." So it is a capacity deferral, not a product refusal reported
F8 A non-API data route exists: the admin panel offers "Download weekly catalogue updates (CSV)", plus a "Top movers" filter and filters for newly added, data correction, image updates and duplicates removed verified
Read this API as a design, not a list A 24-hour token, a tenant in a JWT claim, CORS pinned to one origin, and one search endpoint feeding two very different screens. That is a coherent set of choices for a multi-tenant SaaS whose only intended client is its own front-end. It is not an integration platform, and it was never trying to be. A07 rebuilds exactly this shape, and B04 is about what you do when you are on the outside of it.

5. The data model, as actually built

Observed on a dev tenant: 214 products, all one game, all tagged with one location. This is the most useful table in the course for A02.

What comes across

titleCard name, then the set in parentheses, then - Foil if foil. The sample has a double space before the dash — real systems have blemishes
productTypeThe game: Magic: The Gathering TCG. Not "MTG Single"
vendorThe location or environment name, not a real vendor. Do not build logic on it
tagsLocationId: … · Magic: The Gathering · Rarity: mythic · Set: … · Variant: Foil. Rarity casing is inconsistent across products (mythic in one place, R in another) — never branch on it

What does not come across — and what each absence costs

MissingConsequence
Buy price — cash and credit, per conditionA customer-facing buy list cannot quote. This is the one field the whole integration waits on
All variant metafields ([] on all five)This is the empty slot the buy price would occupy — and where it must land, because each condition is its own variant with its own cardId. A product-level field cannot express NM versus DMG
Collector number, mana cost, colours, artist, legality, printingsAll present in the API's extendedAttributes, all dropped by the sync. A rich card page needs another source
SEO title and descriptionEvery card publishes with no SEO metadata
Per-variant imagesimage: null on every condition; one shared product image
barcode, compareAtPrice, unitCostAll null
The one-sentence version

Everything needed to render a card is already in Shopify — name, set, rarity, foil, image, oracle text, five conditions. The only thing missing is the price you would pay the customer.

The SKU trap

This one silently corrupts four fifths of your data The SKU is {cardId}_{locationId} and each condition has its own cardId. The product-level custom.external_card_id equals the NM variant only. So code that reads the card id from the product and applies it to all five variants looks correct, runs without error, and mismatches LP, MP, HP and DMG every single time. Always parse the id per variant.

6. The pricing engine

The most interesting subsystem in the platform, and the one A03 is built around.

#FactLabel
P1 Buy price is derived, not stored. It is computed from activeBuyRule. A card with no matching rule returns blank — observed as activeBuyRule: __UNSET__ → —/— verified
P2 Three rule types, not one: Sell, Buy, and Stop buy. "Stop buy" can halt buying — for example when the shop is already well stocked. A global Price rounding control sits above all rules verified
P3 A rule is a filter plus two percentages. Observed: Market ≥ $5 · Condition LP · Rarity All · Print variants Foil · Stock Any → cash 10% / credit 15%, matching 746,555 items. A second active rule matched 2,830 verified
P4 The buy price does not reproduce from the market price the API exposes. Under that 10%/15% rule, a real card with marketPrice A$34.02 returned cash A$3.03 / credit A$4.54. The rule predicts A$3.40 / A$5.10. The cash:credit ratio is exact (2:3), so the rule is being applied — but the implied base is ~A$30.28, not A$34.02. They price off a figure they do not publish verified (n=1)
P5 A rule filtered to one condition inverts what a customer expects. With the rule set to LP only, a Near Mint card — the better card — gets no offer, while a played copy gets one. This is a straight consequence of the rule model, not a bug in it verified
P6 The retail condition ladder is a clean multiplier: observed 100 / 80 / 60 / 40 / 37 % of NM, and an exact 100/80/60/40/40 on an older system. Foil does not follow the ladder verified for retail
P7 If the buy ladder followed the retail ladder, a sync would only need to carry NM cash and NM credit per card rather than ten values inference — n=3, and the ladder measured was a retail ladder, not a buy ladder
P8 Their own admin banner flags its own coverage holes, e.g. "Missing buy price automations — Magic: The Gathering ≤$4.99". Five automations existed in total on the sampled tenant verified
P9 "Buy-rule coverage is 10.8% — 18,077 of 167,311 rows" — retracted by its own author: a dev-tenant figure produced by one test rule, never a production measurement. Do not quote it retracted
Why P4 is the best single fact on this page It is a failed prediction, reported honestly. Someone had a clean theory — buy price is a percentage of market price, so we can compute it ourselves and skip the vendor. They tested it on one real card and it was off by four dollars. The ratio matching exactly while the base did not is the interesting part: it says the rule engine works as documented and the input is different from what the API shows. Probably a different market figure — a low or median or trend price — and possibly rounding on top. In an interview, "we tested our own assumption and it failed, here is what the failure told us" is worth more than any correct guess.

7. The sync, and who owns inventory

#FactLabel
S1 The Game Locker Shopify app creates and publishes products. Proven by Shopify's own event log, not by naming conventions verified
S2 The sync is two-way and moves fulfilment in both directions. Their words: "the Shopify integration is two-way updating. So if we update inventory on Shopify, it updates inventory in GameLocker." reported, twice, by two people
S3 Shopify is the inventory writer. "you would also never need to read/update inventory from our side… you just need to manage stock updates from that end and it syncs with us." So accepting a trade-in means increment stock in Shopify and let it flow back reported
S4 The sync carries sell price only. Buy price is absent from Shopify entirely verified
S5 locationId is baked into every SKU, and the portal now shows a "Multi-store (Early access)" badge. Which location a trade-in increments is genuinely undecided verified
S6 A card the shop does not currently stock has no Shopify variant to increment. Inventing one breaks the {cardId}_{locationId} contract, because the id is theirs, not yours verified as a consequence
S7 The dev tenant syncs one game only — 214 MTG products. Pokémon, Yu-Gi-Oh, Lorcana and One Piece all return 0. The catalogue spans 19 games, so production breadth is unproven gap
S3 flips the course's original story The first version of this course said Game Locker is the system of record and Shopify is a channel hanging off it. For catalogue and price that is right. For inventory it is backwards: their own guidance is to write stock in Shopify. So the ownership matrix in A04 is not "Game Locker owns everything and pushes". It is split by field — catalogue and price out of Game Locker, stock authored in Shopify and mirrored back. Get this wrong in an interview and you will confidently describe their product backwards.

8. The customer ledger — the money risk

#FactLabel
L1 Game Locker holds store credit. Its /customers screen columns are: Name · Email/Shopify Customer ID · Mobile Number · Transactions · Credit Balance · Total Spending · Total Sold verified at schema level
L2 The ledger is keyed to the Shopify Customer ID. It is a full customer record, tracking both what each customer has spent and what they have sold to the shop verified
L3 Issuing Shopify-native store credit alongside this creates a second ledger for the same money — one balance spendable at the counter and online. That is a double-spend, not a display bug verified as a consequence
L4 The dev tenant has 0 customers, so this is schema evidence, not observed balances. Whether production balances are authoritative there is not established gap

Why L1–L3 matter more than they look. Trade-ins happen at the counter, through Game Locker. So the shop's credit balance has lived there for years, across two different inventory systems. Moving it to Shopify is not an automation task — it is a ledger migration. A06 is built on this.

9. The buy list, as the platform already has it

#FactLabel
B1 Buylists are orders with orderType=buy — the same object as a sale, with the direction flipped verified
B2 Lifecycle: Quoted → Reviewed → Completed, exposed as tabs alongside All, plus a "Create a buylist" action for staff verified
B3 Columns include Channel, Payment ref, Payment status, Quoted buy price and Profit %. So it tracks whether the customer has been paid, and the margin on the trade — it is a payout pipeline, not just a queue verified
B4 A buylist with Channel = "Shopify" was observed once, quoted at A$14.67 cash. On a later visit it was gone — 0 rows in every tab, the tenant appears to have been reset. So what a Shopify-channel buylist actually does was never inspected gap
B5 The write path was never called. POST /orders/new is inferred from observed routes only, deliberately not exercised because it would mutate a live tenant gap

10. The gaps, collected

Kept together on purpose. In an interview these are worth more than the facts, because naming the edge of your knowledge is the thing that makes the rest of it credible.
