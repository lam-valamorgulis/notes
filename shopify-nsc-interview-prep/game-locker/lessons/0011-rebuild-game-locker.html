Part A · Lesson A07 · The capstone

Rebuild Game Locker

Eight modules, in NestJS and Postgres. Not a tutorial — a specification, where every module's acceptance test is a behaviour someone observed in the real system. Ends with one thing you actually run.

Your win today: draw the eight modules and their dependency order from memory, name the three hard problems in the whole platform, and write the pricing evaluator with its rounding — then prove it against four real values, including the one that does not reproduce.

This lesson assumes A01 through A06. Every fact is a labelled row in verified-facts, which doubles as the acceptance-test list.

1. What you are building, in one paragraph

A multi-tenant SaaS that game shops run their business on. It holds a catalogue of about 1.12 million card items across 19 games, growing by ~200 a day. It ingests a market price feed nightly and publishes derived prices at 06:00. Each tenant configures rules that turn market prices into what they sell for and what they will pay. It tracks stock per location, orders in both directions, and a credit ledger of money owed to customers. It pushes the catalogue into each tenant's Shopify store and mirrors stock back. And it exposes one tenant-scoped API that its own front-ends consume.

The sentence that shows you understand the shape

"It's a pricing engine with a catalogue attached, not a catalogue with prices attached. Everything hard about it comes from prices being derived rather than stored."

2. The three genuinely hard problems

Most of this system is ordinary CRUD. Say that out loud — it shows judgement. Then name the three parts that are not.

#The hard problemWhy it is hard
1 Derived prices at 1.12M scale A price must reflect a rule the instant the rule changes, and also be materialised for a sync that cannot evaluate rules a million times. Two representations of the same truth, with a defined staleness
2 Two systems writing one stock number The counter sells a card and so does the website, out of one physical pile. Neither is wrong to write. Choosing an owner — the tool that solves every other field — does not work here
3 One credit balance, two places to spend it It is money you owe. In store and online both decrement it, and a lost decrement is not a bug report, it is a loss

Everything else — cards, sets, users, tenants, search, reports — is a well-understood problem you can staff and schedule. These three are where an experienced engineer earns their salary, and where a rebuild goes wrong.

Build order

Dependency order, not importance order. Each step is demonstrable before the next begins.

StepModulesDemo you can show
1catalogue + api skeletonSearch cards by name in one tenant, get nothing from another tenant's data
2pricingAuthor a rule, get a live buy quote. Change the rule, quote changes instantly
3inventoryStock per location, and the sku identity holds
4repriceA nightly run that writes snapshots and reports how many rows moved
5buylist + ledgerQuote, review, complete, and a credit balance that reconciles

Pricing at step 2, before inventory. That is deliberate and worth defending: pricing is the hard part and the reason the product exists. Build the risky thing while there is still time to be wrong about it.

Three tables carry the whole design market_price is the only stored price. If a second price column appears anywhere that is not price_snapshot, the derived model has leaked and you now have two truths.

credit_entry is append-only and credit_account.balance is a cache. The balance must be rebuildable by summing entries, because the question is always "how did it get there".

sync_outbox exists so a push is replayable rather than fire-and-forget. Without it, a failed sync is invisible and unrecoverable.

5. Multi-tenancy — decide it on day one

Notice which tables carry tenant_id and which do not.

Shared across tenantsPer tenant
Whatgame, card_set, card, printing, sku, market_priceRules, stock, orders, customers, credit, sync links
WhyA card is the same card in every shop. Storing it per tenant would multiply 1.12M rows by every customer you winPrices, stock and money are opinions and possessions, never shared
The one that bites Shared reference data plus per-tenant everything else means every query that touches both must be filtered, and the filter is easy to forget on a join. One missing WHERE tenant_id = ? shows a shop its competitor's stock or its competitor's margins. Enforce it below the query layer — Postgres row-level security, or a repository base class that refuses to build a statement without a tenant scope. Do not rely on remembering. The real system carries the tenant in a JWT claim (custom:company), which is the right instinct: the tenant should arrive with the request, not be passed around as an argument someone can drop.

6. Module notes worth writing down

pricing — the evaluator is a pure function

Everything in A03 §9, with one addition: keep the evaluator pure. Rules and market price in, prices out, no database access inside. That is what makes it testable against the real observed values in §8 below, and it is what lets the same code serve a live API call and a million-row batch.

// pure. no I/O. this is the whole product, in one function.
quote(input: {
  market: Decimal,
  sku: { condition: Condition, finish: Finish, rarity: string },
  stockQty: number,
  rules: PriceRule[],
  setting: PricingSetting,
}): { sell?: Money, cash?: Money, credit?: Money, ruleId?: string, reason?: NoOfferReason }

Note reason. "No offer" has two causes — the shop declined and we have no market price — and they must be distinguishable even though the customer sees one message. Someone will ask how many cards fall in each bucket, and you want to answer without a migration.

reprice — the job that must finish

RuleWhy
Only re-evaluate skus whose market price moved, or that have stock, or whose tenant edited a rule~96% of the catalogue did not move. Evaluating it all is almost entirely wasted work
Write the whole run to price_snapshot, then hand the changed set to the syncThe sync should push differences, not everything
Record how many rows moved and by how muchThat count is your best health signal. A sudden zero, or a sudden million, both mean the feed broke
A rule edit invalidates its matched set, not the whole catalogueAn owner changing one rule at 4pm should not trigger a full run

Two of those are worth arguing about vendor = location name is a misuse of the field, and you should say so while also saying you would keep it. It is load-bearing for someone's saved filters by now. Add the proper LocationId: tag alongside and treat vendor as legacy.

Buy price must go on the variant, not the product. Each condition is a separate variant with its own id, so a product-level field cannot express "NM cash price" and "DMG cash price" at once. This is not a preference — a product-level field makes per-condition quoting impossible.

api — one endpoint, two screens

The real system serves both the buy list and the full card page from a single /inventory/search. That is a good decision and worth copying, but it has a cost you should name: the buy list needs ten prices per card and the card page needs one. Serve both from one endpoint and either the card page over-fetches or the buy list under-fetches.

Solve it with a field-selection parameter rather than two endpoints. Two endpoints drift; a projection parameter cannot.

7. What you would do differently — and say so

An interviewer asking you to describe their system is also asking whether you can critique it without being rude. Four things, each with the reason it was probably done that way.

They didI wouldBut their choice makes sense because
Card attributes as tags Metafields with definitions, so they are typed and filterable properly Tags work on every Shopify plan, need no definition step, and every search app indexes them. Metafields need setup per store — across hundreds of tenants that is a support burden
Two metafields with no definitions Define them, so they are visible and typed An app can write undefined metafields with no setup at all. It is invisible to a definitions query, which is a real trap — but it is also zero-friction
vendor holding a location name A tag, and leave vendor for a real vendor It was probably the only free top-level field that shows up in Shopify's default filters
Only one of three option slots used Nothing. This is correct Foil is a physically different printing, not a state of the same card. Splitting it into products is more right than a variant axis, and it keeps two slots free
The move that lands Give the reason before the criticism. "Tags work on every plan and need no per-store setup, which across hundreds of merchants is a real support saving — I'd still want definitions for the filterable ones, because rarity casing is already inconsistent and you can't safely branch on it." That is a colleague talking. "You should have used metafields" is a candidate talking.

8. The runnable proof

Not the whole platform. One function, and the four real numbers it has to face. This is a ninety-minute exercise and it is the highest-value ninety minutes in Part A, because it ends with you having tested a claim about their system.

The evaluator

type Condition = 'NM' | 'LP' | 'MP' | 'HP' | 'DMG';
type RuleType  = 'sell' | 'buy' | 'stop_buy';

interface PriceRule {
  id: string;
  type: RuleType;
  priority: number;            // lower wins
  active: boolean;
  filter: {
    marketMin?: number; marketMax?: number;
    conditions?: Condition[];
    finishes?: ('normal' | 'foil')[];
    rarities?: string[];
    stockMin?: number; stockMax?: number;
  };
  cashPct?: number;            // buy only
  creditPct?: number;          // buy only
}

interface Setting { roundingMode: 'none' | 'nearest' | 'down' | 'up'; roundingStep: number; }

type NoOffer = 'no_market_price' | 'stop_buy' | 'no_matching_rule';

function matches(r: PriceRule, market: number, sku: Sku, stockQty: number): boolean {
  const f = r.filter;
  if (f.marketMin  !== undefined && market   <  f.marketMin) return false;
  if (f.marketMax  !== undefined && market   >  f.marketMax) return false;
  if (f.stockMin   !== undefined && stockQty <  f.stockMin)  return false;
  if (f.stockMax   !== undefined && stockQty >  f.stockMax)  return false;
  if (f.conditions && !f.conditions.includes(sku.condition)) return false;
  if (f.finishes   && !f.finishes.includes(sku.finish))      return false;
  if (f.rarities   && !f.rarities.includes(sku.rarity))      return false;
  return true;
}

function round(v: number, s: Setting): number {
  if (s.roundingMode === 'none' || !s.roundingStep) return r2(v);
  const n = v / s.roundingStep;
  const k = s.roundingMode === 'down' ? Math.floor(n)
          : s.roundingMode === 'up'   ? Math.ceil(n)
          :                             Math.round(n);
  return r2(k * s.roundingStep);
}
const r2 = (v: number) => Math.round(v * 100) / 100;

// The finding from A03 §7, encoded as a seam.
// KNOWN WRONG by ~11% on the one card ever tested. When someone runs the
// 200-row experiment, THIS is the only function that changes.
function pricingBase(market: number): number {
  return market;
}

function quoteBuy(
  market: number | null, sku: Sku, stockQty: number,
  rules: PriceRule[], setting: Setting,
): { cash: number; credit: number; ruleId: string } | { noOffer: NoOffer } {
  if (market === null) return { noOffer: 'no_market_price' };

  const active = rules.filter(r => r.active);

  // 1. the veto runs FIRST. it is not a competitor.
  if (active.some(r => r.type === 'stop_buy' && matches(r, market, sku, stockQty)))
    return { noOffer: 'stop_buy' };

  // 2. then the buy rules
  const buys = active
    .filter(r => r.type === 'buy' && matches(r, market, sku, stockQty))
    .sort((a, b) => a.priority - b.priority);

  if (buys.length === 0) return { noOffer: 'no_matching_rule' };

  const rule = buys[0];
  const base = pricingBase(market);
  return {
    cash:   round(base * (rule.cashPct!   / 100), setting),
    credit: round(base * (rule.creditPct! / 100), setting),
    ruleId: rule.id,
  };
}

The tests that matter

const LP_FOIL_OVER_5: PriceRule = {
  id: 'r1', type: 'buy', priority: 10, active: true,
  filter: { marketMin: 5, conditions: ['LP'], finishes: ['foil'] },
  cashPct: 10, creditPct: 15,
};
const NO_ROUNDING: Setting = { roundingMode: 'none', roundingStep: 0 };

it('refuses a card with no matching rule', () => {
  const nmFoil = { condition: 'NM', finish: 'foil', rarity: 'rare' };
  expect(quoteBuy(34.02, nmFoil, 0, [LP_FOIL_OVER_5], NO_ROUNDING))
    .toEqual({ noOffer: 'no_matching_rule' });
});
// ^ THE INVERSION. The Near Mint card — the BETTER card — gets nothing,
//   because the rule is filtered to LP. Real observed behaviour.

it('stop_buy beats a matching buy rule', () => {
  const stop: PriceRule = { id: 'r0', type: 'stop_buy', priority: 999,
                            active: true, filter: { finishes: ['foil'] } };
  const lpFoil = { condition: 'LP', finish: 'foil', rarity: 'rare' };
  expect(quoteBuy(34.02, lpFoil, 0, [LP_FOIL_OVER_5, stop], NO_ROUNDING))
    .toEqual({ noOffer: 'stop_buy' });
});
// ^ note the priority: 999. The veto wins ANYWAY. That is the point.

it('applies the rule at the documented ratio', () => {
  const lpFoil = { condition: 'LP', finish: 'foil', rarity: 'rare' };
  const q = quoteBuy(34.02, lpFoil, 0, [LP_FOIL_OVER_5], NO_ROUNDING) as any;
  expect(q.credit / q.cash).toBeCloseTo(1.5, 5);   // 15/10 = 2:3. PASSES.
});

it('DOES NOT reproduce the real observed price — and that is the finding', () => {
  const lpFoil = { condition: 'LP', finish: 'foil', rarity: 'rare' };
  const q = quoteBuy(34.02, lpFoil, 0, [LP_FOIL_OVER_5], NO_ROUNDING) as any;

  expect(q.cash).toBe(3.40);      // what OUR rule maths gives
  expect(q.credit).toBe(5.10);

  const REAL_CASH = 3.03;         // what the live API actually returned
  const REAL_CREDIT = 4.54;

  expect(q.cash).not.toBe(REAL_CASH);
  expect(REAL_CREDIT / REAL_CASH).toBeCloseTo(1.5, 2);   // ratio still 2:3!
  expect(REAL_CASH / 0.10).toBeCloseTo(30.28, 1);        // implied base != 34.02
});
Why that last test is the point of the whole lesson

It is a test that asserts your own model is wrong, and pins down exactly how. The ratio passes, the absolute value fails, and the implied base is off by 11% — so the rule engine is right and the input is different. That is a finding, written as code, that will not rot.
