When the Vendor Will Not Give You an API

A real integration that went through six designs in four weeks, because the platform on the other side had no key to give. Which constraint killed which design — and the two blockers that were never the vendor's fault at all.

Your win today: name the four technical constraints a closed platform imposes and what each one forbids · walk the six designs and say which constraint killed which · and explain the difference between a capacity deferral and a product refusal, because reading one as the other costs weeks.
Read this before you use any of it Every name, company, person, budget and ticket number is removed on purpose, and stays removed. What is teachable here is the shape of the problem: constraint → design → death → next design. If you tell this story in an interview, tell it as "I read a detailed integration discovery against a closed platform" and keep it structural. The moment it becomes gossip about a named project you have stopped being an engineer talking about architecture. See verified-facts §2.

1. The setup, in five lines

PieceWhat it was
The platformA closed, multi-tenant inventory system. Holds the catalogue, the pricing rules, the stock and the customer credit ledger
The storefrontShopify. The platform already syncs products and prices into it, two-way for stock
The featureLet a customer, at home, list cards they want to sell, see an instant per-condition offer, and submit the batch for a shop to review and pay out
The catchThe offer price exists only inside the platform, computed live from rules. It is not in Shopify, and there is no external API access
The clockA fixed go-live, roughly three months out

That is a completely ordinary brief. Everything difficult about it comes from the last two rows.

2. The wall, described technically

"No API" is a vague phrase. Here is what it actually looked like, and it is worth learning as a checklist, because each item forbids something different.

ConstraintObservedWhat it forbids
CORS is pinned access-control-allow-origin allowed exactly one host — the platform's own front-end Any browser call from your domain. So server-side or nothing
Tokens are human and short A staff login produced a JWT lasting 24 hours Unattended servers. A 24-hour token means a human logging in daily forever
The app client holds a secret you do not have A login probe returned configured with secret but SECRET_HASH was not received. The secret was not in the front-end bundle Self-refreshing. Even with a password you cannot mint a token from a server
No self-serve key page The admin site had no developer or API-key screen anywhere Solving it yourself. It becomes a human ask to the vendor, on their timeline
The order of that list is the useful part Each row rules out one escape route, and they compound. CORS pushes you server-side. The short token means the server needs to refresh. The missing secret means it cannot refresh. The missing key page means you cannot fix that yourself. Four findings, and the fourth one converts an engineering problem into a scheduling problem — which is a much worse kind, because you no longer control it.

One honest nuance on CORS

"CORS forces a server-side design" is weaker than it sounds The previous inventory vendor at that same shop shipped a browser widget that called its own API directly from the page. So a closed API is a choice about who they will CORS-enable, not a law of the problem. The correct framing is: "this vendor has not enabled cross-origin access for us" — which is a request you can make, not a wall you have to route around. Stating it the strong way sounds authoritative and quietly closes a door that was never locked.

3. Six designs, and what killed each

Four weeks. Six architectures. This is the actual value of the case study — not the answer, the sequence.

dead D1 · Live server-side validation and write-back

Storefront posts to an App Proxy path → HMAC verified → a hosted function re-validates every line against the platform's live search endpoint → posts the approved batch into the platform's own buy list, which already has a review pipeline.

Killed by: the missing app-client secret. There is no way for a server to hold a credential.

What survives from D1, and it is a lot The App Proxy plus HMAC plus server-side re-validation pattern is right no matter which design wins. Every later option still needs it, because every later option needs a secret in a server — and a secret cannot live in theme JavaScript. So this was never wasted design work; it was unbuilt infrastructure sitting in front of options 3 to 6. Knowing the difference between "that design died" and "that design's plumbing is still required" is a senior distinction.

live D2 · The platform pushes prices as Shopify metafields

No live call at all. The platform writes cash and credit buy prices onto Shopify variant metafields as part of the sync it already runs. The storefront reads them like any other product field.

Not killed. This became the sanctioned pricing path, and the read side is trivial.

Why it worksWhat it actually depends on
The sync already exists and already writes products. Adding one field is smallThe field must be variant-level, because each condition is a separate variant. A product-level field cannot express NM versus DMG
Removes every credential problem at onceA vendor delivery date you do not control
Prices become as fast as any other Shopify readProducts existing on the store at all — see §4

option D3 · A file exported from the review tool, uploaded by a human

Once staff approve a batch, generate a file and have someone upload it into the platform by hand.

Not killed, and never validated. Cheap to build, permanently expensive to operate, because it puts a human step in the money path forever.

The kill-check nobody ran Does the import screen exist, and what fields does it need? It probably needs the platform's own per-condition card id — which lives in the platform and is exactly what a task tool will not have. That check is ten minutes on a screen the shop's staff use daily, and it was never done. Before you design to an interface, open it. This is the cheapest possible way to kill or confirm an option, and it kept getting deferred in favour of harder questions.

live D4 · The client's existing task tool as the staff review queue

A submission creates a task in the tool the shop's buying team already works in. Staff price, adjust and approve there. Status flows back to the customer's account page.

Not killed — the destination was confirmed as the decision. But half of it could not ship as designed, for a reason that has nothing to do with the vendor. See §4.

live D5 · Submit, and we will quote you

The customer submits a list with no instant price. The shop responds after a human review.

Not killed. Lowest build cost, and the realistic shape for a first release.

But it is not zero-dependency, and the question was never asked It still needs a Shopify custom app, an App Proxy subpath, and hosting stood up from scratch, because writing into the task tool needs a token. And commercially: the approved designs all show instant per-condition quotes, and the old site already advertised a choice of cash or store credit. Nobody asked whether launching without instant quotes was acceptable. That is a one-sentence question with a three-month consequence, and four weeks of architecture happened without it.

option D6 · Push approved buy-ins through the stock sync that already exists

Skip the file and the write API entirely. Accepting a trade-in means incrementing stock in Shopify, which the existing two-way sync already carries back into the platform.

Not killed. The only option with zero unbuilt vendor dependency. And the most under-explored.

What blocks itType of problem
It bypasses the platform's buy-list reporting — margin per trade, payment status, customer lifetime soldCommercial. And never quantified — nobody asked which reports break
A card the shop does not stock has no variant to increment, and the SKU embeds the platform's own card idTechnical, and real
Which location's stock rises, now that the platform runs multi-storeUndecided
The pattern across all six

"Only one of the six was killed by the vendor. Two were blocked by questions nobody had asked, and two by things we hadn't checked on screens we could open."

4. The two blockers that were never the vendor's fault

This is the part that makes the case study worth telling, and it is the part everyone misses while arguing about credentials.

BlockerThe shape of itWhere it appeared in the plan
The catalogue did not exist The production store had zero card products. The old store had over ten thousand. Every pricing design assumed products to hang prices on Nowhere. No ticket, no estimate, no meeting recap
There was no backend at all The repository was a theme. No app manifest, no serverless config, no functions directory, no hosting. Every remaining option needed all three Nowhere. It was assumed to exist because a design had used it
and a third — the account page could not host the feature The live store had moved to Shopify's new customer accounts, so the theme's own account page is unreachable dead code there. The approved status design was drawn against the old capability Nowhere. A platform change nobody re-checked
The lesson, and it is the most useful sentence in this lesson The blocker is almost never the thing in the ticket. Four weeks of attention went to a vendor credential — the visible, dramatic, external obstacle. Meanwhile the release was going to fail because a store had no products in it and the team had nowhere to run a server. Both were discoverable in an afternoon and neither was anybody's assigned job to notice.

Which gives you a habit worth naming out loud in an interview:

Before designing anything, verifyHow
The data the design reads exists, in the environment it will run inQuery production, not the dev store. Count rows
The runtime the design needs existsLook for the app manifest, the hosting config, the deploy step
The platform capability the design assumes is still trueRe-check the feature flags on the actual store. Platforms move
The screen you plan to integrate with opensOpen it

5. Deferral or refusal? Learn to tell

The single most expensive misreading in the whole story.

The vendor's answer, structurally: we do not support external API keys at this time, and if we ever did it would be read access only, for authenticated accounts, for security reasons — and we do not have capacity for the next two months. Happy to talk about what you are trying to build and other ways to achieve it.

That got recorded internally as "the vendor refused; the API is dead". Then weeks later a second person at the same vendor said, in effect: you are right, you need an API, we just do not have the resources. We will get to it.

SignalRefusalDeferralWhich was present
Time qualifierAbsent — "we don't do that""at this time", "not until after September"Deferral
Reason givenPolicy or product directionCapacityDeferral
Alternatives offeredNone"happy to discuss other ways"Deferral
Later statementsHardenSoftenDeferral
And the sharpest bit: the refusal may have been to the wrong question The original ask was for a credential to create and read buy-list orders — write access. The vendor's answer specifically volunteered that read access is the only thing they would ever consider. A narrow, read-only ask was never cleanly made. Weeks of re-architecture followed a "no" to a question nobody had narrowed. Before you accept a refusal, check whether the thing refused is the smallest thing you actually need.

6. The failure mode that has nothing to do with vendors

Two phrases circulated as project facts: "blocked until September" and "the interim solution is a file export".

Neither had a human author. Both appeared only in an AI-generated meeting recap email. What the humans on that call actually said was that the integration was live on a dev store, that one metafield was outstanding, and — hedged with "might" and "probably" — that a file export could be where things end up.

A summary is a source with a confidence level, not a fact A recap turned a hedged option into the decision, and a late field into a blocked project. Both then got repeated by people who had not been on the call. This will happen to you constantly from here on. The defence is cheap and boring: when a claim matters, go to the transcript, the ticket, or the system. And when you write the summary, keep the hedges — "suggested, not decided" is two extra words that save a fortnight.

Two more method traps from the same story

TrapWhat happenedThe rule
Querying the schema instead of the rows An audit concluded "the sync writes no metafields" because metafieldDefinitions returned nothing. But an app can write metafields without defining them — the data was sitting on the products all along Absence in a schema query is not absence of data. Read the rows
Trusting a filter the API silently ignores A count query filtered on metafield:… returned the maximum, and so did a deliberately nonsensical key. The filter was being discarded, not applied Test your query with an input that must return zero. If nonsense returns everything, your filter is not running
Reading a permission error as an answer An installed-apps query returned access-denied, so nobody could tell whether the vendor's app was installed but idle. "No writes observed" got reported as "not installed" Permission denied means you do not know. It is not evidence of absence

7. The playbook

What to actually do, in order, next time a closed platform is on the other side.

1 MAP THE WALL, precisely CORS? token life? can a server self-refresh? is there a key page? Each answer forbids one escape route. Write down which. 2 NARROW THE ASK before accepting a no Do you need write, or only read? Ask for the smallest thing. A "no" to a big ask is not a no to a small one. 3 CLASSIFY THE NO time qualifier + capacity reason + alternatives offered = DEFERRAL Get a week number. Do not re-architect around a maybe. 4 FIND THE DATA PATH THAT ALREADY EXISTS Is there a sync? a scheduled export? a file download? A shipping integration beats a promised endpoint. 5 VERIFY THE FOUNDATIONS — before designing Does the data exist in PRODUCTION? Is there a runtime? Is the platform capability still true? Does the screen open? This is where the real blockers are. 6 BUILD AGAINST A CONTRACT, NOT A PROMISE Stub the missing field. Build the whole flow. Swap the stub when the real thing lands. 7 KEEP THE HEDGES IN YOUR OWN WRITING "suggested, not decided" — four words, saves a fortnight.

Step 6 is the one that rescues a schedule. The buy price was missing, so build everything with a stubbed price and one function that fetches it. Then the vendor's delivery date stops being a blocker and becomes a swap.

Why step 4 matters more than it looks Three data routes already existed and were treated as second-class next to the API nobody could have: a two-way sync that was live and working, a metafield push the vendor had already offered, and a weekly catalogue file download sitting in the admin panel. An integration that ships beats an endpoint that is promised. Look for the path already running before you ask for a new one.

8. How to tell this in an interview

You are interviewing at a company whose platform is the closed one in this story. So the framing matters as much as the content.

DoDo not
Keep it structural — constraints, designs, what killed whatName the client, the people, the money, or the tickets
Say "I read a detailed integration discovery against your platform"Imply you built it. You did not
Give their design decisions their reasons before critiquingPresent their API as a mistake. It is coherent for its purpose
Lead with the blockers that were our fault, not theirsMake it a story about a vendor being difficult
Offer the read-only-ask observation as a questionTell them their own team got it wrong
The version that lands

"The thing that stayed with me is that only one of six designs was blocked by your side. Two were blocked by questions nobody had asked, and two by things nobody had checked on screens we could already open. I'd want to be the person who runs those checks in week one."

That answer does four things at once. It shows you read carefully. It takes responsibility rather than assigning blame. It names a habit you would bring. And it is completely safe to say, because there is nothing confidential in it.
