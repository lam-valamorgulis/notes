Lesson 5 · Game Locker · Storefront

Themes for Game Stores

One theme, many merchants, each wanting something different — and it has to be fast on a phone in a shop with bad reception. This is the JD's first bullet, and it is a different problem from building one store well.

Your win today: explain how you serve many stores from one theme codebase without forking, design the singles search and filter experience down to the exact filter.* parameters, and name the three Core Web Vitals with their thresholds and the specific things that make a Shopify card store slow.

Ties to your 24-hour plan: block 13. Read TA L01 (Dawn) and TA L02 (Horizon) first — this lesson does not re-teach sections and blocks, it applies them.

1. The sentence in the JD that changes the problem

"Work with our marketing team and customers to build their desired front ends."

Their customers are game stores. So you are not building a storefront — you are building a storefront product that many merchants use, each with their own logo, colours, opening hours, tournament schedule and opinions.

The naive approach fails predictably:

THE FORK TRAP Store A wants a tournament calendar → copy the theme, add it Store B wants it too, but on the homepage → copy, add it there Store C wants a buylist page → copy, add it SIX MONTHS LATER · 12 theme copies, each slightly different · a bug fix must be applied 12 times, by hand · nobody knows which store has which version · onboarding store 13 means choosing a parent to copy THIS IS THE PROBLEM ONLINE STORE 2.0 EXISTS TO SOLVE. It is also why the JD names sections, blocks and JSON templates specifically rather than just saying "Liquid".

2. The rule: variation becomes configuration

Every difference between merchants must land in one of these, in order of preference:

MechanismUse forWho changes it
Theme settings (settings_schema.json)Colours, fonts, logo, shop-wide togglesThe merchant, in the theme editor
Section settingsPer-instance choices: heading text, how many products, which collectionThe merchant
Blocks inside sectionsRepeatable, reorderable pieces — a row of features, a list of games stockedThe merchant, by drag and drop
JSON templatesWhich sections appear on which page type, and in what orderThe merchant
Theme blocks (Horizon-era)Blocks that can nest and be reused across sections, without the section declaring each oneThe merchant, more freely
A code branchNothing, ideally. The last resortYou, forever
The line to say

"With many merchants on one theme, my rule is that a merchant difference has to become a setting, not a branch. The moment I fork for one store I have signed up to maintain two codebases forever — and the fix I ship next month has to be applied twice, by hand."

The question to ask them "When a store wants something the shared theme doesn't do, where do you currently draw the line between adding a theme setting and doing custom work for that one store?" — this is the real operational tension in their business, and asking it shows you have already worked out what the hard part is.

3. What a card store's storefront actually needs

Generic theme knowledge is not enough here. A card store has page types most themes never consider:

Page / featureWhy it is unusual
Singles searchThousands of near-identical products. Search and filtering carry the whole experience — browsing collections by hand does not work at this catalogue size. Section 4 goes deep on this.
Faceted filteringSet, rarity, condition, language, finish, price. Driven by the metafields and metaobjects from Lesson 2 — the data model decides whether this is possible. Section 4.
Condition availability on the product pageBecause condition is an option, Shopify already knows stock per condition. "Damaged — sold out" comes free. Getting the data model right is what makes the UI easy.
A 30-line cartNormal for collectors. Puts real pressure on cart rendering and on the Cart AJAX API.
Buylist / "we buy cards"Usually not commerce at all — a form or a link into Game Locker. Worth knowing it is not a product page.
Events and tournamentsContent, not products. Often the single most-visited page for a local store.
Preorders for upcoming setsSelling stock that does not exist yet — the one case where overselling is intentional and must not be blocked.
The preorder exception Everything in Lesson 3 is about preventing oversell. Preorders invert it: the store deliberately sells 200 booster boxes it will not have for six weeks. So "continue selling when out of stock" must be a per-product decision the sync respects, not a global setting the sync overwrites every night. A sync job that blindly enforces "available = what we physically hold" will silently kill every preorder. Raising this unprompted is a strong signal, because it is the kind of thing you only think of if you have modelled real stock.

4. Search and filtering — the page a card store lives on

Section 3 gave this one table row. It deserves a whole section, because it is where the data model, the theme and the performance work all meet. It is also the answer that separates "I have built Shopify stores" from "I have built this kind of Shopify store".

Two mechanisms, often confused

SearchFiltering
What it doesFree text across the catalogueNarrows a list that already exists
The URL/search?q=lightning+bolt?filter.v.option.condition=Near+Mint

They stack, and that is the point. A collector searches "lightning bolt", then filters what came back. collection.filters and search.filters return the same filter object, so you write the facet UI once as a snippet and render it on both templates.

Every card attribute maps to an exact filter parameter

This is the payoff from Lesson 2. Each modelling decision there becomes a URL here.

You never hand-write these. Liquid gives you value.url_to_add and value.param_name. Knowing the shape matters for debugging, and for linking a filtered view from a newsletter.

The closed list that decides your metafield types Only seven metafield types can become a storefront filter: single_line_text_field, list.single_line_text_field, metaobject_reference, list.metaobject_reference, number_integer, number_decimal, boolean.

So multi_line_text_field, rich_text_field, json and date cannot be filters. Picking multi_line_text_field for rarity because "it might get long one day" permanently breaks the rarity facet, and the repair means re-typing the field across every product.

The good news is the load-bearing one: metaobject_reference is on that list. That single fact is what makes Lesson 2's "set is a metaobject" safe. If metaobject references were not filterable, the most important filter on a card site would be impossible, and set would have to go back to being free text.

filter.p versus filter.v — the distinction that catches people

p is product level. v is variant level. For a card that split is not cosmetic:

ONE CARD, TWO LEVELS PRODUCT "Lightning Bolt · Modern Horizons 3 · #161" ├─ set → filter.p.m.card.set (product level) └─ rarity → filter.p.m.card.rarity (product level) VARIANTS ├─ NM / English / Foil $22.00 qty 1 ├─ LP / English / Normal $4.50 qty 3 └─ DMG / Japanese / Normal $1.20 qty 1 └─ condition, language, finish, price, availability → all filter.v.* (variant level) "NM, English, under $20" is THREE variant filters. "Mythic rares from MH3" is TWO product filters.
The question worth asking out loud When you combine two variant filters, does one single variant have to satisfy both? If not, the card above could appear under "Near Mint and under $20" — the NM copy is $22 and the $4.50 copy is Lightly Played, so no such variant exists.

I would test this on a real store before trusting the facet, and I would say so in the interview. "I would verify it rather than assume" is a stronger answer than a confident wrong one, and this is exactly the bug that produces angry customer emails.

AND or OR — filter.operator

WhereLogicWhat the collector means
Across filter groupsAlways AND"From MH3 and Near Mint"
Inside one group, operator ORAny of the values"Near Mint or Lightly Played"
Inside one group, operator ANDAll of the values"Legal in Modern and in Commander"

Both live in the same URL shape — filter.v.option.condition=Near+Mint,Lightly+Played, or the parameter repeated. Only filter.operator tells you which one it is, and it returns AND or OR for boolean and list filters. Filters that can use AND are product tags, list.single_line_text_field and list.metaobject_reference.

So a "formats legal in" list metafield can be an AND filter, and a theme that hard-codes "any of these" labels will describe it wrongly. Read filter.operator and label accordingly.

The Liquid you actually write

Three filter types, three cases. Handle all three or a facet silently renders as nothing.

{%- for filter in collection.filters -%}
  <fieldset>
    <legend>{{ filter.label }}
      {%- if filter.active_values.size > 0 %} ({{ filter.active_values.size }}){% endif -%}
    </legend>

    {%- case filter.type -%}

      {%- when 'list' -%}
        {%- for value in filter.values -%}
          <label>
            <input type="checkbox"
                   name="{{ value.param_name }}"
                   value="{{ value.value }}"
                   {% if value.active %}checked{% endif %}
                   {% if value.count == 0 and value.active == false %}disabled{% endif %}>
            {{ value.label }} ({{ value.count }})
          </label>
        {%- endfor -%}

      {%- when 'price_range' -%}
        <input type="number" name="{{ filter.min_value.param_name }}">
        <input type="number" name="{{ filter.max_value.param_name }}"
               max="{{ filter.range_max | money_without_currency }}">

      {%- when 'boolean' -%}
        {{ filter.true_value.label }} / {{ filter.false_value.label }}

    {%- endcase -%}
  </fieldset>
{%- endfor -%}
PropertyWorth knowing
filter.typelist, price_range, boolean. That is the whole set.
filter.presentationimage, swatch or text. list filters only. A set logo as an image facet is a real use here.
value.countHow many results. nil for price_range.
filter.operatorAND or OR. nil for price_range.
filter.range_maxHighest price in the current results — the slider's top end.
value.url_to_add / url_to_removeShopify builds the URL. Pagination parameters are dropped, which is correct — page 7 of the old filter is meaningless.

Disable at zero — do not hide A collector who sees "Damaged (0)" learns something true: you have none. A collector who sees the Damaged option disappear thinks the site is broken, or worse, does not notice and assumes you never stock it. Shopify's own example disables rather than hides, and on a catalogue of near-identical products the counts are half the information on the page.

The 100-value ceiling — the real card-store filter problem

A filter group can display up to 100 values, and Shopify's UX guidance is to show about 10 with a "show more". Now count the sets in a trading card game.

WHY "SET" BREAKS AS A GLOBAL FACET /collections/all-singles the Set filter would need ~900 values → past the 100-value ceiling → and unusable even if it fitted /search?q=lightning+bolt the Set filter now has ~30 values → fits comfortably → and it is the list the collector actually wanted to see THE FIX IS NOT A BIGGER FACET. IT IS NARROWING THE LIST FIRST.

So the design conclusion is: set is navigation, not a facet, until the list is already small. Three ways to narrow first, and they combine:

  • Search first. A card name cuts 900 sets down to 30. This is why a card store is search-led rather than browse-led.
  • Scope by collection. One collection per game, and often per block or era. Inside it the set list stays under the ceiling.
  • A set index page. Sets get their own landing pages — which you get almost free once set is a metaobject, and which is worth far more for SEO than a checkbox in a sidebar.

Search itself, and where it stops being enough

The storefront search URL, with every part that matters:

/search?q=lightning+bolt
       &type=product
       &options[prefix]=last

ParameterWhat it doesThe card-store call

Predictive search — the numbers, and the one setting nobody changes

Predictive search is GET /search/suggest.json (or /search/suggest with section_id for rendered HTML). The documented example debounces input by 300ms.

ParameterValuesDefault
resources[type]product, page, article, collection, queryquery,product,collection,page
resources[limit]1 to 1010
resources[limit_scope]all or eachall
resources[options][unavailable_products]show, hide, lastlast
resources[options][fields]author, body, product_type, tag, title, variants.barcode, variants.sku, variants.title, vendortitle, product_type, variants.title, vendor
The specific, checkable point to make in the interview variants.sku and variants.barcode are searchable — but they are not in the default field list. A card SKU can carry the set code, the collector number and the condition. Adding variants.sku to resources[options][fields] is what lets someone type MH3-161 and land on the exact printing.

Almost no theme changes that setting, because on a fashion store nobody searches by SKU. On a card store, the SKU is how the trade talks about a card. That is a one-line change with a large effect, and naming it shows you have thought about this catalogue rather than a generic one.
Two limits that shape the UI The cap is 10 results, and "Lightning Bolt" has around 30 printings. So a dropdown that lists products is the wrong shape here — it will show ten near-identical rows and hide the rest. The useful suggestion is the card, and the printing list belongs on the search results page.

Also: product variants are only returned when the query matches terms in the variant title. Typing "Lightning Bolt NM" gets you nothing extra from "NM" unless that string is in the variant title. Condition belongs in the facets, not in the search box.
The honest verdict — say this

"Shopify's native search plus Search & Discovery filters is the right tool for one store's own site at a few thousand SKUs, and I would not replace it early. Where it runs out is the card-specific stuff: nicknames like 'bolt', set codes, collector numbers, and ranking thirty near-identical printings sensibly. For the marketplace — searching across many sellers' stock — I would expect a dedicated search index rather than Shopify's product search, because at that point it is a search problem rather than a storefront one."

Making the filtered page fast

This is the same conversation as the next section, so it belongs here rather than there:

  • Every filter click is a new URL and a new server render. Do not full-page reload. Fetch the new URL, and swap only the results grid using section rendering.
  • Push the new URL with the History API. The filter state must stay in the URL, because a filtered view is a shareable thing — a newsletter can link "NM Modern Horizons 3 rares under $20" directly.
  • Paginate. The next section lists unpaginated collections as a top cause of slow pages. A filtered singles list is exactly that case.
  • Render value.count. It costs nothing extra and stops people clicking into empty results, which is the most common wasted interaction on a facet.

5. Performance — the JD asks for it, so be precise

The JD wants "clean, responsive, and fast loading front end code" and "a good eye for responsive design and performance". Vague answers about "optimising images" are weak. Use the actual metrics.

The three Core Web Vitals

MetricMeasuresGoodWhat breaks it on Shopify
LCP

INP replaced FID as the responsiveness metric. Saying "INP" rather than "FID" is a small, cheap currency signal.

What actually makes a Shopify store slow

In rough order of how much damage they do in practice:

  1. Apps and third-party scripts. Usually the single biggest cost, and the least controlled. Each one adds JS that runs on every page. The honest engineering position: audit whether each app earns its weight, and audit the tag manager for tags nobody remembers adding.
  2. Too many sections on a template. Shopify's own guidance is explicit about this — high section counts lower performance. Every section is Liquid to render and usually CSS and JS to ship.
  3. Unpaginated collections. Loading hundreds of products at once. On a card store with thousands of near-identical singles this is fatal, and pagination is the documented fix.
  4. Inefficient Liquid. Loops inside loops, repeated expensive lookups. It shows up as server-side Liquid render time before the browser gets anything at all.
  5. Images. Wrong size, no width/height, not lazy-loaded below the fold, hero image not preloaded.
  6. Fonts. Blocking, or swapping late and causing layout shift.
The senior move: measure before you optimise Two tools, two purposes, and knowing the difference matters. Shopify's Web Performance report in the admin uses Core Web Vitals from real visitors — that is field data, and it is the truth about your actual customers. PageSpeed Insights / Lighthouse is a lab test on a simulated device — repeatable, good for catching regressions, but not evidence of what real users experience. Optimising the lab number while the field number stays bad is a classic waste of a week.

The card-store-specific performance answer

Two things matter here that would not on a normal store:

  • Search and filter results, not the homepage. Collectors arrive at a search result or a filtered collection. That is the page to optimise, and it is the one that is hardest — many products, many filters, prices that change.
  • The cart. Thirty lines, each with a quantity control. A cart that re-fetches and re-renders the whole page on every quantity change will feel broken. This is where bundled section rendering earns its place — update the cart section and the header count in one request, rather than reloading the page.
WHY BUNDLED SECTION RENDERING MATTERS ON A 30-LINE CART NAIVE: change quantity → POST /cart/change.js → then reload the whole page → 30 lines re-rendered, images re-requested → feels slow exactly when the order is big BETTER: change quantity → POST /cart/change.js with `sections=cart-items,cart-footer,header` → Shopify returns THOSE SECTIONS' HTML → swap them in. One request. No reload. ⚠ AND REMEMBER FROM TA L03: update.js does NOT check stock, and line positions move under you. On a site where most lines have quantity 1, that is not a small detail.

6. Responsive, in a shop

"A good eye for responsive design" has a specific meaning for this customer base:

  • Phones dominate. Collectors check prices on a phone, often while standing in a shop comparing to what is on the shelf.
  • Bad reception is normal. Inside a shop, on a phone, on mobile data. This is the reason performance and responsive are the same conversation here rather than two.
  • Dense data on a small screen. A card listing has set, condition, language, finish and price. Squeezing five attributes into a phone-width row without it becoming unreadable is the actual design problem, and it is harder than a fashion product card.
  • Tap targets. Condition selectors are small. On a phone, a mis-tap buys the wrong condition at the wrong price.
A concrete answer if they ask "how do you approach responsive?" Do not say "mobile first" and stop. Say: "I design the dense case first — a card row with five attributes and a price on a narrow screen — because if that reads well, the desktop layout is easy. The other way round, you end up shrinking a desktop table into something unreadable." That is a real opinion, and it is specific to their products.

7. Liquid facts worth having exactly right

Theming may be your comfort zone, but comfort zones produce vague answers. A few precise ones:

ThingThe precise version
render vs include{% render %} is the current tag. {% include %} is deprecated — it leaked the parent scope, which made snippets unpredictable. render takes an isolated scope, so a snippet only sees what you pass it.
Section vs snippetA section is merchant-configurable and appears in the editor with settings and blocks. A snippet is a code-level partial with no settings and no editor presence.
Section vs theme blockSections are the OS 2.0 unit. Theme blocks (Horizon-era) can nest and be reused across sections without each section declaring them — more merchant freedom, less duplicated schema.
JSON templateDeclares which sections a page type has and their order, so the merchant can rearrange them. Replaced the old fixed .liquid templates.
Metafields in LiquidReached through product.metafields.namespace.key. This is how the card data from Lesson 2 reaches the page.
Filters in Liquidcollection.filters and search.filters return the same filter object, so one snippet serves both templates. Three types to handle: list, price_range, boolean.
Where the theme's authority endsIt can submit a discount code; only Shopify decides what it is worth. See TA L04.
