The Matching Key & Idempotency

You will run the import more than once. That is not a risk to manage — it is a certainty to design for. One decision, made in the first hour, is what makes the second run a repair instead of a disaster.

Your win today: choose a matching key and defend it, and know Shopify's own documented answer — a custom ID held in an id-type metafield, which productSet can look up and upsert against.

Ties to your mission: this is the lesson that separates a migration that can be fixed from one that has to be deleted and started again. It is also the question a senior interviewer asks second, right after "how would you move the products?".

1. The second run is not optional

Name the reasons an import runs twice. There are more than people expect:

  • The test run on a development store, then the real one.
  • You find a mapping bug at record 8,000 of 12,000 — fix, run again.
  • The API returned errors for 340 records. You retry only those.
  • The client keeps trading during the project, so late data arrives after your snapshot.
  • The cutover slips a week, so you re-run to pick up the delta.

So the real question is not "how do I write these records?" It is: given a source record, how do I find the Shopify record it already became?

THE ONLY QUESTION THAT MATTERS ON RUN 2 NO MATCHING KEY WITH A MATCHING KEY ─────────────── ─────────────────── run 1: create 12,431 products run 1: create 12,431 products run 2: create 12,431 products run 2: look up each source id ───────────────────── → found? UPDATE 24,862 products ✗ RUINED → missing? CREATE ───────────────────── the store must be wiped and 12,431 products ✓ FINE rebuilt from zero run 2 is a REPAIR, not a disaster ⇒ "idempotent" just means: running it twice leaves the same result as running it once.
The word to use, and what it really means Idempotent. An operation you can repeat with no extra effect. Setting a value is idempotent; adding to a value is not. Creating a record is not idempotent — unless you can first ask "does it already exist?", and that question needs a key. This is the same idea as absolute versus delta inventory writes in POS Lesson 3, one level up.

2. Four candidate keys, scored

KeyUnique?Stable?Who owns itVerdict
Handle (the URL slug) Yes, per store No — changes when the title changes; Shopify may de-duplicate it Shopify Fine for a one-shot CSV import. It is the CSV's own match column. Weak as a long-term key.
SKU Not enforced Usually The client Tempting and often wrong. Real catalogues contain blank SKUs and duplicated SKUs. Check before trusting it.
Shopify ID in your own mapping table Yes Yes You Works, but the knowledge lives in your database. Lose it and the link is gone. Nobody else can use it.
Legacy ID stored on the record (a custom ID) Yes — enforced Yes Shopify holds it, you set it The answer. Shopify built a feature for exactly this. Section 3.
Run this query before you trust a SKU SELECT sku, COUNT(*) FROM variants GROUP BY sku HAVING COUNT(*) > 1 — plus a count of blanks. Every catalogue you are handed claims its SKUs are unique. Roughly none of them are. Finding out on run 2 means duplicate products that have already been ordered from.

3. Shopify's own answer: the custom ID

This is the part most candidates do not know, and it is documented plainly. Shopify has a first-class concept for "the ID this record has in your other system":

shopify.dev · Working with custom IDs A custom ID gives you "a reliable unique identifier to match resources across multiple shops and/or systems (e.g. ERPs, CRMs, PIMs)." It is named as being for developers who need "a mapping of identifiers to manage data migration and synchronization with Shopify."

It uses the id metafield type, and — this is the good part — "ID metafield types are automatically configured to have unique values."

Read that last sentence again. You do not have to enforce uniqueness yourself. Pick the id metafield type, and Shopify rejects a duplicate for you. Your legacy primary key becomes a unique index inside Shopify.

THE CUSTOM ID — WHERE THE MAPPING LIVES THEIR SYSTEM SHOPIFY ┌───────────────┐ ┌─────────────────────────────┐ │ product_id │ │ Product gid://…/Product/998 │ │ = 55231 │──────────────▶│ │ └───────────────┘ mapping │ metafield │ lives HERE │ namespace: "legacy" │ not in your │ key: "product_id" │ database │ type: id ← unique │ │ value: "55231" │ └─────────────────────────────┘ benefits over your own mapping table: · survives your service being rebuilt or lost · visible in the admin, so support staff can trace a record · the NEXT developer can find it without asking you · uniqueness is enforced by the platform, not by your code

Then the lookup happens inside the mutation itself. productSet takes an identifier argument, and the docs describe the behaviour exactly:

shopify.dev · Working with custom IDs "When the identifier argument includes a custom ID, it first looks up a matching record. If one exists, the mutation updates it. Otherwise, it attempts to create a new record."

And the contrast that matters: productUpdate "looks up a matching record and updates it. Unlike productSet, it doesn't create a new product if no match is found."

That is a true upsert, server-side, with no read-before-write of your own. One call per record, safe to repeat.

Field of ProductSetIdentifiersDocumented asWhen to use it
customId"Custom ID of product to upsert."Migrations and syncs. Takes a namespace, key and value.
handle"Handle of product to upsert."When the source has no stable ID and the slug is all you have.
id"ID of product to update."When you already hold the Shopify ID — an update, not a lookup.
The support is narrower than you would hope Custom-ID lookup covers products, variants, collections, customers, orders and locations. But custom-ID create-or-update is documented for products and customers only — productSet, productUpdate and customerSet. So for orders you get to find by legacy ID but not to upsert by it, and your importer needs a "does this order already exist?" read of its own. Do not design as if the feature is everywhere.
Cover the screen Which metafield type is automatically unique? Which two resources support create-or-update by custom ID? And what does productUpdate do that productSet does not?

4. The trap inside productSet

productSet is the right tool and it is also the most destructive mutation in a migration, because of how it treats lists.

shopify.dev · productSet For list fields — collections, metafields, variants — it creates new entries, updates existing ones, and deletes entries not included in the input. For other field types it "Updates only the included fields. Any omitted fields will remain unchanged."
TWO KINDS OF "OMITTED" IN ONE MUTATION plain field omitted list field omitted ─────────────────── ────────────────── vendor: (not sent) variants: [A, B] ← C not sent ↓ ↓ vendor UNCHANGED ✓ variant C DELETED ✗ ⇒ a retry that sends a PARTIAL variant list does not "update what it knows about". It DESTROYS the rest. the fix: for each product, always send the COMPLETE variant list, or use a narrower mutation instead.
How this bites in practice Your importer batches variants for speed and sends a product's variants in two calls of 500. The second call does not add 500 — it deletes the first 500 and leaves the last 500. The counts in your reconciliation report look plausible, so nobody catches it until a customer cannot buy a size that exists in the warehouse.

5. The other two upserts you need

MutationUpsert behaviourThe limit that shapes your batching
metafieldsSet "Metafield values will be set regardless if they were previously created or not." 25 metafields per call, and a total payload under 10 MB. Also has compareDigest for compare-and-set since 2024-07.
inventorySetQuantities Absolute write — sets the number rather than adjusting it. name accepts only available or on_hand; reason is required; compareQuantity "will only update the quantity if the persisted quantity matches" and errors otherwise.
A free audit trail you should always use inventorySetQuantities takes referenceDocumentUri — documented as a URI "that represents why the inventory change happened, identifying the source system and document that caused this adjustment." Put your migration run ID in it. Months later, when someone asks why a count changed on cutover night, the answer is in the platform instead of in your logs.

6. The dry run

A matching key lets you do the single most valuable thing in a migration: run it twice on purpose, before it counts.

THE RUN SEQUENCE THAT DE-RISKS EVERYTHING 1. dev store · run 1 → create N records, capture counts 2. dev store · run 2 → SAME input, SAME code, no changes ──────────────────────────────── count MUST be identical. if it doubled → the key is broken. STOP. Fix the key, not the importer. 3. dev store · run 3 → change 10 records at source, re-run, confirm exactly 10 changed 4. live store · run 1 → the real thing, now boring step 2 costs one hour and is the difference between "we re-ran it" and "we rebuilt the store".

Notice what step 2 tests. Not whether the data is right — whether the identity is right. Those fail differently and step 2 only catches the second one, which is the one that cannot be repaired later.

8. Say it like an interview

Read this next

Primary source — 15 minutes shopify.dev · Working with custom IDs — short and directly on target. Read the support table carefully: notice that lookup and create-or-update have different coverage. Then skim productSet and find the sentence about list fields being deleted. Those two pages are most of this lesson.
Remember this
  • The import always runs more than once. Test run, bug fix, retry, late data, slipped cutover.
  • The real question is "how do I find the record this already became?" — that is the matching key.
  • Do not trust SKUs until you have counted blanks and duplicates yourself.
  • Shopify's answer is a custom ID: your legacy key in an id-type metafield, and "ID metafield types are automatically configured to have unique values."
  • productSet with identifier.customId is a real upsert — looks up, updates if found, creates if not. productUpdate never creates.
  • Create-or-update by custom ID is products and customers only, even though lookup covers more.
  • productSet deletes list entries you omit — variants, metafields, collections. Always send the complete list.
  • metafieldsSet caps at 25 per call and 10 MB.
  • Run it twice on a dev store with identical input. If the count doubles, the key is broken — stop there.
If you remember one thing: put their primary key in an id metafield on the Shopify record, so the mapping lives in the platform rather than in your database — and the migration becomes re-runnable by anyone, forever.
