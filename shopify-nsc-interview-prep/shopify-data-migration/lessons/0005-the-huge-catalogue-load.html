Lesson 5 · Shopify Data Migration · Scale

The Huge Catalogue Load

At a certain size the problem stops being the API and becomes the calendar. There is a documented daily limit on creating variants — and it can turn a two-week import into a nine-month one. Almost nobody knows it exists.

Your win today: name the daily variant creation limit, do the arithmetic that turns it into a delivery date, and say which plan is exempt — then choose the product shape that avoids the wall in the first place.

Ties to your mission: a platform-scale catalogue — auto parts, trading cards, books, industrial fasteners — is the case where a competent migration plan still fails. Not because of your code. Because of a number in the docs.

1. The wall nobody plans for

You can write 40,000 products in an afternoon. You cannot necessarily write 400,000 variants in a month, and the reason is a throttle that has nothing to do with rate limits.

shopify.dev · API limits Once a store reaches 50,000 product variants: "After this threshold is reached, no more than 1,000 new variants can be created per day." And: "These additional limits don't apply to stores on the Shopify Plus plan."
help.shopify.com · Adding variants For stores with 500,000+ total variants: "You can add up to 10,000 new variants in a day before the limit is reached." Same exemption: "If you're on the Shopify Plus plan, then the daily rate limit for uploading variants doesn't apply to your store."
Read those two boxes again — they do not agree One page puts the threshold at 50,000 variants with a cap of 1,000 per day. The other puts it at 500,000 variants with a cap of 10,000 per day. Both were read on 2026-08-03. They are describing throttles at different tiers, and no single page reconciles them.

So the professional move is not to memorise one number and quote it at a client. It is to say: "there is a documented daily throttle on new variants for non-Plus stores, the published thresholds differ between two Shopify pages, so before I commit to a date I will measure the actual rate on the actual store." That answer is stronger than a confident wrong number — and being confidently wrong here is a missed delivery date.

2. The arithmetic that changes a project

This is the calculation to do in the first meeting, on paper, in front of the client.

SAME DATA, THREE VERY DIFFERENT PROJECTS catalogue: 300,000 variants ┌─────────────────────────────────────────────────────────┐ │ Shopify Plus no daily variant throttle │ │ → paced only by the API │ │ → DAYS │ ├─────────────────────────────────────────────────────────┤ │ non-Plus, 10,000/day 300,000 ÷ 10,000 │ │ → 30 days │ ├─────────────────────────────────────────────────────────┤ │ non-Plus, 1,000/day 300,000 ÷ 1,000 │ │ → 300 DAYS ✗ project is dead │ └─────────────────────────────────────────────────────────┘ the code is identical in all three rows. the PLAN is not. ⇒ "which plan are they on?" is a TECHNICAL question, asked before the estimate — not a sales question.
Say it this way

"Before estimating a large catalogue load I ask which plan the store is on, because non-Plus stores have a documented daily throttle on creating new variants and Plus is exempt. At the low end of the published figures, a 300,000-variant catalogue is three hundred days of imports. That is a plan question, not a code question, and it has to be answered before anyone promises a launch date."

3. Shape before volume

Before counting records, decide the product shape — because shape is what generates the variant count, and the variant count is what hits the wall.

LimitDocumented asThe design it forces
Options per product"Products support a maximum of three options each"Pick your three axes deliberately. Everything else becomes a metafield — filterable and displayable, but not a purchase choice.
Variants per product"You can create up to 2,048 variants for a product."Raised from 100 in October 2025. Rarely the wall now — but 3 axes × wide value lists multiply fast.
Media per product"You can have up to 250 media items, such as images, per product."Holds even at 2,048 variants. So a per-variant image is impossible past 250 variants — plan a per-option-value image instead.

All three from help.shopify.com · Adding variants, read 2026-08-03.

THE SHAPE DECISION — WHERE EACH ATTRIBUTE GOES a buyer must CHOOSE it to buy → OPTION (max 3) a buyer wants to FILTER by it → METAFIELD + filter it describes the whole product → METAFIELD it is a set of related products → METAOBJECT + reference worked example — a card catalogue: condition → OPTION 1 (buyer chooses: Near Mint / Played) language → OPTION 2 (buyer chooses) finish → OPTION 3 (buyer chooses: Foil / Normal) set, rarity, artist, release year → METAFIELDS (filter and display only) get this wrong and you either run out of options or you generate variants nobody will ever buy.
Every unnecessary axis multiplies Options multiply, they do not add. Three axes of 10 values each is 1,000 variants per product. Add a fourth axis of 5 and you would need 5,000 — over the 2,048 cap and straight into the daily throttle. Moving one attribute from an option to a metafield can cut the whole job by 80%.
Cover the screen Three numbers: options per product, variants per product, media items per product. Then the test that decides whether an attribute is an option: what must be true for a buyer?

4. The catalogue is not the product list

The most effective way to load a huge catalogue is to load less of it.

A platform-scale source catalogue is a reference database — every card ever printed, every part ever made. The merchant's Shopify store only needs what that merchant actually sells. Those are very different numbers, often by a factor of a hundred.

Question to askWhy it shrinks the job
Do we import items with zero stock and no sales history?Usually the majority of a reference catalogue. Import on first stock movement instead.
Can items be created on demand, when first stocked?Turns a one-time load into a trickle that never hits a daily cap.
Does the storefront need to be searchable across the full catalogue?If yes, that is a search problem, not an import problem — and Shopify is the wrong place to hold 145 million rows.
What is the reference data versus the sellable data?Reference stays in their system; only sellable items become Shopify products. This is the single biggest lever you have.
Say it this way

"I would push back on importing the whole catalogue. A platform catalogue is a reference database; a Shopify store only needs the items the merchant actually stocks. So I would import what has stock or sales history, and create the rest on first stock movement. That usually removes an order of magnitude of work, and it keeps me under the daily variant throttle instead of fighting it."

5. Images are the slow part

People plan for the products and are surprised by the media. Two routes, and the docs are clear about which to use when:

RouteDocumented asUse when
fileCreate by URL "Provide a URL and Shopify handles downloading, processing, and storing the file." The default for a migration. The old site is still up, so its image URLs work. You transfer no bytes yourself.
stagedUploadsCreate Recommended for "Large files", "Files on your server" not publicly reachable, "Unreliable networks", and "Bulk imports" The old site is already dark, the files are private, or you are pushing from a local archive.

Caps to respect: images 20 MB and 4472 × 4472 px (20 MP); videos 1 GB and 10 minutes; 3D models 500 MB. And a volume limit that catches migrations of media-rich catalogues: "Apps can create up to 1,000 videos for each store in a week."

The dependency nobody writes down Pulling images by URL means the old site must stay online through the whole import. If the client cancels their old hosting on cutover day — a very normal thing to do to save money — every image not yet fetched is gone, and the source is gone with it. Put "old platform stays up until images are verified" in writing, with a date.

6. Make it resumable, then walk away

A load that runs for days will be interrupted. Machine restarts, deploys, a mistake at record 200,000. Resumability is not a nice extra at this size — it is the design.

THE RESUMABLE LOADER source ──▶ ┌──────────────┐ ──▶ Shopify │ for each │ │ record: │ 1. is it already done? │ │ (check YOUR ledger first — │ ledger row: │ cheaper than asking Shopify) │ src_id │ 2. upsert by custom ID │ shopify_id │ 3. write the ledger row │ status │ │ error │ crash anywhere → restart │ run_id │ → skips everything already done └──────────────┘ the ledger is not extra work. it IS: · the resume mechanism · the retry queue (WHERE status = 'error') · the reconciliation report from Lesson 1 · the audit trail when someone asks "what happened to SKU X?" one table, four jobs.

Notice how the Lesson 3 decision pays off here. Because every record carries a custom ID, a restarted loader can be safely dumb: attempt the upsert again and Shopify updates instead of duplicating. Resumability comes free from idempotency.

Order of passes at scale Split into passes rather than one giant job, and run them in this order: 1) products and variants (plain fields), 2) metafields, 3) collections and publishing, 4) media, 5) inventory. Inventory goes last because it is the only number that must be true at the moment of go-live — everything else can be written a week early.

Remember this

  • The two published thresholds disagree (50,000 variants → 1,000/day; 500,000 variants → 10,000/day). Measure on the real store; do not quote one number.
  • Do the arithmetic before the estimate. 300,000 variants is days on Plus, 30 days at 10,000/day, and 300 days at 1,000/day.
  • 3 options, 2,048 variants, 250 media items per product. Media stays 250 even with 2,048 variants.
  • Options multiply. Moving one attribute to a metafield can cut the job by most of its size.
  • The catalogue is not the product list. Import what has stock or sales history; create the rest on first stock movement.
  • Pull images by URL with fileCreate — but then the old site must stay online until every image is verified.
  • Keep a ledger row per record. It is the resume mechanism, the retry queue, the reconciliation report and the audit trail at once.
  • Inventory is the last pass — the only number that must be true at go-live.
If you remember one thing: at scale the constraint is the calendar, not the code — so ask which plan the store is on before you promise a date.
