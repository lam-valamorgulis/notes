Lesson 7 · Shopify Data Migration · The familiar case

Shopify → Shopify

Moving between two Shopify stores feels like the easy version. It is the case with the least official guidance and one structural fact that breaks more things than any platform difference: every ID changes.

Your win today: explain the export / import asymmetry (you can export orders as a CSV and there is no order CSV import), and list what breaks because IDs do not survive a store-to-store move.

Ties to your mission: store consolidation, a move between regions or plans, splitting one store into several, or leaving a shared Plus organisation. Common work, and clients assume it is trivial because "it is the same platform."

Honesty about sources on this page Shopify publishes guides for moving to Shopify from named platforms. It publishes no dedicated Shopify-to-Shopify guide — the closest advice is "develop, or hire a Shopify Partner to create, a custom migration solution using the Shopify API." So this lesson is assembled from the export and import pages plus what is structurally true of the API. Claims that are documented are quoted. Claims that are inference are labelled as inference. Treat the labelled ones as things to verify on the actual store.

1. The asymmetry that shapes everything

Shopify lets you take more out than you can put back in. That sounds like a complaint; it is really a design clue.

WHAT COMES OUT vs WHAT GOES IN RECORD EXPORT (CSV) IMPORT (CSV) verdict ────── ──────────── ──────────── ─────── products ✓ yes ✓ yes round trip works customers ✓ yes ✓ yes round trip works orders ✓ YES ✗ NO ONE WAY ONLY gift cards ✓ yes ✗ no API only metafields ✗ not in CSV — API only, both ways metaobjects ✗ not in CSV — API only, both ways files/media ✗ not in CSV — API only ⇒ the order CSV export exists for HUMANS — accounting, analysis, a spreadsheet. It is not an import format. Re-importing order history is still orderCreate. (Lesson 6)

So the CSV route is a trap on this job specifically. It covers the two easy record types and none of the ones that actually make a Shopify store what it is.

The right export tool for a Shopify source Use bulkOperationRunQuery, not the admin CSV exports. You get metafields, metaobject references, publication status, inventory per location and media — none of which appear in a CSV. Mechanics are in main-course Lesson 18. This is the one migration where both sides of the job are a bulk operation.

Export limits worth knowing when you are working in the admin: exports of up to 50 orders download immediately, 51 or more are emailed; an export under 100,000 items "might complete in under an hour", while 400,000 items "might take around 4 hours." Source: help.shopify.com · Exporting orders, read 2026-08-03.

2. Every ID changes. That is the whole lesson.

A Shopify ID is issued by a store. Store B has never seen store A's numbering, so nothing keeps its identity across the move. This is structural, not a limitation you can configure away.

THE ID RESET STORE A STORE B ───────── ───────── Product/8801 ──────▶ Product/44219 ← new ProductVariant/551 ──────▶ ProductVariant/990 ← new Customer/2077 ──────▶ Customer/8814 ← new Order/91043 ──────▶ Order/60022 ← new Location/33 ──────▶ Location/71 ← new Metaobject/17 ──────▶ Metaobject/5 ← new files.shopify CDN url ────▶ a DIFFERENT url ← new everything that stored one of those numbers is now pointing at nothing — or worse, at the WRONG record.

Say it this way

"The hard part of a Shopify-to-Shopify move is not the data, it is the identity. Every product, variant, customer and order gets a new ID on the destination store, so everything that stored one of those IDs breaks at once — reference metafields, theme settings, app data, and every third-party integration keyed on a variant. I plan that as a second pass with its own mapping table, and I treat the integration re-mapping as the largest line item in the estimate, not an afterthought."

3. The two-pass shape this forces

Because references cannot be written before their targets exist, the job splits in a way a platform-to-Shopify migration does not.

WHY IT IS TWO PASSES, NOT ONE PASS 1 — create the records, references left EMPTY ───────────────────────────────────────────────── products ──▶ customers ──▶ orders each one carries a custom ID: legacy.store_a_id = "8801" ← Lesson 3 build a mapping: store A id → store B id PASS 2 — fill in every reference, using the mapping ────────────────────────────────────────────────── reference metafields ("related products" → new IDs) metaobject entries (re-link to new records) theme settings (re-pick products by hand or by script) collections (rule-based ones re-evaluate; manual ones re-list) pass 1 without pass 2 gives you a store that looks complete and has quietly lost every relationship in it.

The custom ID from Lesson 3 is what makes pass 2 possible at all. If store B's records carry store A's IDs in an id-type metafield, the mapping is a query rather than a file you must not lose.

4. What still does not move

Same platform on both sides does not rescue bucket 3 from Lesson 2:

  • Customer passwords — still one-way hashes, still not portable. Passwordless sign-in still saves you.
  • Reviews — they live in a review app, so the app's own export/import is the route, not Shopify's.
  • Analytics history — store B starts empty. Your reconciliation report becomes the archive.
  • Saved payment methods — the same narrow gateway support from Lesson 6 applies. Subscriptions are the risk.
  • Discount code usage history — codes can be recreated; how many times each was used is not order data you are importing.
  • App subscriptions and configuration — reinstall and reconfigure, and re-do any app-specific data mapping.
The mistake clients make on this job Because both sides are Shopify, clients price it as a copy. Then the first honest estimate lands and looks unreasonable. The way out is to explain where the cost is before quoting: the second pass and the integration re-mapping, not the record copy. Show the ID-reset diagram. It is the fastest way to make an invisible cost visible.

6. Say it like an interview

Read this next

Primary source — 10 minutes help.shopify.com · Exporting orders — read the field list of the order export and ask: could I rebuild these orders on another store from this file alone? Work out what is missing. That exercise gives you the asymmetry in section 1 first-hand, and it is a better answer in an interview than repeating it from a lesson.
Remember this
  • Shopify publishes no dedicated Shopify-to-Shopify guide — its advice is a custom API solution or a Partner.
  • Orders export as CSV but cannot be imported as CSV. The export is for humans; re-import is still orderCreate.
  • CSV exports carry no metafields, metaobjects or media — use bulkOperationRunQuery for a Shopify source.
  • Every ID changes. Products, variants, customers, orders, locations, metaobjects and CDN URLs all get new identities.
  • Everything that stored an ID breaks: reference metafields, theme settings, app databases, 3PL and ERP and feed integrations.
  • The job is two passes — create the records, then fill in every reference using a store A → store B mapping.
  • A custom ID makes pass 2 a query instead of a file you must not lose.
  • Bucket 3 still applies: passwords, reviews, analytics history and saved cards do not move just because both sides are Shopify.
If you remember one thing: on a store-to-store move you are not migrating data, you are re-establishing identity — and that is where the whole cost lives.
