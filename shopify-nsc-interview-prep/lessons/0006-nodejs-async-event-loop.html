Node.js Async & The Event Loop

The question every Node interview asks. Get the mental model right and the rest of the day is easy.

Your win today: confidently answer "Explain how Node handles many requests on a single thread." — out loud, with the words event loop, non-blocking I/O, and microtask queue.

Ties to your mission: the NSC role is a Node backend that talks to Shopify all day. A Shopify sync is almost all I/O — many API and DB calls. This lesson is why Node is the right tool for that job.

1. The bridge from what you already know

In a theme you wrote {{ product.title }} and Shopify's server did the waiting for you. On the backend, your Node process does the waiting: it calls the Shopify Admin API, waits for JSON, calls the database, waits again. A single order sync can fire dozens of these calls. The whole game is: how does one Node process stay busy while all that waiting happens?

2. One thread, one event loop

Your JavaScript runs on one main thread. There is no thread per request like a classic Java or PHP server. Instead Node uses an event loop: a loop that runs your code, and when your code asks for something slow (a network call, a file read), it hands that off and moves on to other work. When the slow thing finishes, its callback is queued to run later.

The one-line rule Node is single-threaded for your JS, but not single-tasking. One thread can juggle thousands of in-flight I/O calls because it never sits and waits for any of them.
Picture a coffee shop with ONE barista The barista (your one thread) takes your order, starts the espresso machine (hands off the slow I/O), and instead of standing and watching it brew, immediately serves the next customers. When a coffee is ready the machine dings, and the barista hands it over. One barista clears a long queue fast — because they never stand still waiting. "Never stand and wait" = non-blocking I/O. "Who do I serve next?" = the event loop. A CPU-heavy task is like the barista being forced to hand-grind beans for 3 minutes: now the whole queue is stuck — that's "blocking the loop".

3. Non-blocking I/O and the libuv thread pool

Non-blocking I/O means an I/O call returns straight away; a callback or Promise fires when the data is ready. Under the hood a C library called libuv does this. Network sockets use the operating system's async features. Some work that has no async OS option — file reads, DNS, some crypto — runs on a small libuv thread pool (4 threads by default) so it still does not block your main thread.

Say this to sound precise "Node's main thread runs my JS. Slow I/O is offloaded — network I/O to the OS, file and DNS work to libuv's thread pool — so the loop keeps serving other requests."

4. Call stack, microtasks, macrotasks

Three pieces decide what runs next:

  • Call stack — where your current function runs, top to bottom. Node runs this to the end first.
  • Microtask queue — Promise .then/await continuations and process.nextTick. Node drains all of these before anything else.
  • Macrotask queue — timers (setTimeout), I/O callbacks. Node takes one per loop turn.

The key ordering fact interviewers want: after the current code finishes, microtasks run before the next macrotask.[1] So a resolved Promise callback always beats a setTimeout(…, 0).

+-----------------------------+ | CALL STACK | <- your JS runs (one thread) +--------------+--------------+ | stack empties v +-----------------------------+ | MICROTASK QUEUE (drain ALL)| <- Promise .then / await, nextTick +--------------+--------------+ | only then... v +-----------------------------+ | MACROTASK QUEUE (take ONE) | <- setTimeout, I/O callbacks +--------------+--------------+ | run one, then back to top +----------> (one "tick" of the loop)

              5. Great for I/O, bad for CPU
              
  
              Because waiting is free, Node shines when the work is I/O-bound — exactly a Shopify integration: fan out many Admin API and database calls, and the one thread stays busy handling whichever reply lands first.
              
  
              The flip side: a CPU-bound task (parsing a giant CSV, resizing images, heavy crypto) runs on the main thread. While it runs, the event loop is frozen — every other request waits. This is "blocking the loop", and it is the classic Node failure.
              
  
              
    The fix (name all three)
    Move CPU work off the loop: 1) worker threads for in-process parallelism; 2) push the job onto a queue for a background worker (make the job idempotent so retries are safe); 3) a separate service in a language better suited to the crunch.
  
              
  
              And to use every CPU core for normal traffic, run many Node processes — cluster / horizontal scaling behind a load balancer.
              

  
              5½. See it: worker threads unblock the main thread — optional deep-dive (skip if short on time)
              
  
              A request needs a heavy CPU calculation (say, hashing a big file). On the main thread it would freeze everyone. With a worker thread, the crunch moves to a separate thread — the main thread keeps serving. Step through it.
              
  
              
    
              

              // main thread
const w = new Worker('./hash-worker.js', { workerData: text });
w.on('message', result => res.json({ hash: result }));   // reply when done

// hash-worker.js  (runs on its OWN thread)
const { workerData, parentPort } = require('worker_threads');
parentPort.postMessage(heavyHash(workerData));            // crunch, then send back

                    Press “Step ▶”. R1 needs heavy work; R2 and R3 are quick.
                    
    
                    
      
      
      
    
                    
  
                    
  
                    
    Contrast: without a worker thread
    If the main thread ran heavyHash itself, it would be stuck on R1 the whole time — R2 and R3 would sit frozen until it finished. That is blocking the loop. The worker thread is what keeps the main thread free.
  
                    
  
                    
    In practice
    Creating a worker per request is costly — use a pool of reusable workers (e.g. the piscina library). Main and worker talk by passing messages (postMessage), not shared variables — so there are no race conditions.
  
                    

  
                    6. Common async mistakes
                    
  
                    
  
                    
    
                    MistakeWhy it hurtsFix
                    
    
                    Blocking the loop with CPU work or fs.readFileSyncEvery other request stallsAsync APIs; worker threads; a queue
                    
    
                    await inside a loop when calls are independentSerial: 50 calls take 50×await Promise.all(items.map(fetchOne))
                    
    
                    Unhandled promise rejectionCan crash the processAlways await/.catch; try/catch
                    
    
                    Firing thousands of calls at onceShopify throttles youBatch / concurrency limit (see rate limits)
                    
  
                    
  
                    
  
                    The async/await point that reads senior: know when to go parallel. Independent Shopify reads should run together with Promise.all; only chain with sequential await when one call needs the result of the last.
                    
  
                    // Slow: 50 sequential round trips
for (const id of ids) { await getProduct(id); }

// Fast: all in flight at once, one wait
const products = await Promise.all(ids.map(id => getProduct(id)));
                    
  
                    See the difference at a glance — same 50 calls, ~100 ms each:
                    
  
                    
    
                    Sequential await in a loop — one call finishes before the next starts
                    ≈ 5000 ms (50 waits)
                    
    
                    Promise.all — all 50 fired at once, you wait a single time
                    ≈ 100 ms
                    
  
                    
  
                    Parallel wins because the waiting overlaps. (But mind Shopify's rate limit — cap concurrency; don't fire 10,000 at once.)
                    

  
                    One more example: blocking vs non-blocking
                    
  
                    Both "wait" for 2 seconds, but only one freezes every other request:
                    
  
                    // ❌ BLOCKING: a CPU loop holds the one thread for 2s — the whole server is frozen
const end = Date.now() + 2000;
while (Date.now() < end) {}          // nobody else gets served
console.log('done');

// ✅ NON-BLOCKING: the thread is free for 2s — other requests run meanwhile
setTimeout(() => console.log('done'), 2000);   // just a timer on the macrotask queue
                    
  
                    The first is "blocking the loop" — the classic Node mistake. The second lets the one thread keep serving everyone while the timer counts down.
                    

  
                    7. Streams for large payloads
                    
  
                    Do not load a huge Shopify export or CSV fully into memory — that spikes RAM and can crash the process. Streams process data in small chunks as it arrives, keeping memory flat. Pipe the download straight into a parser and into the database.
                    

  
                    7½. See it: streaming keeps memory flat — optional deep-dive (skip if short on time)
                    
  
                    Loading a 2 GB file all at once spikes memory and can crash. A stream reads it in small chunks — process each, then drop it — so memory never holds more than one chunk. Step through and watch the memory bar barely move.
                    
  
                    
    
                    

                    // stream: download → parse → database, chunk by chunk
readStream(bigFile)          // emits small chunks
  .pipe(parseChunks())       // handle one chunk at a time
  .pipe(writeToDatabase());  // memory stays flat, even for 2 GB

    Backpressure (the senior detail)
    If the database is slower than the file arrives, the stream pauses the source until the destination catches up — so chunks never pile up in memory. pipe() handles this for you. It is why streaming a huge Shopify / bulk-operation export never runs out of RAM.

    Say it like this (memorise the shape)
    
                                  "Node runs my JavaScript on a single thread using an event loop. Slow I/O is non-blocking — it's offloaded to the OS or libuv's thread pool — so one thread can handle thousands of in-flight requests. It's bad for CPU-heavy work, because that blocks the loop — so I move heavy work to worker threads, a background queue, or a separate service."
