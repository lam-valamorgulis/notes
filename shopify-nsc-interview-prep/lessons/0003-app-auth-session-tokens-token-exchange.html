App Auth: Session Tokens & Token Exchange

Every Shopify app must prove who it is and get permission for a shop. Know the modern flow and you skip the trap most people fall into.

Your win today: confidently answer "How does a Shopify app authenticate and get an access token?" — the modern token-exchange flow, out loud, in under a minute.

Ties to your mission: before your backend can call the Admin API for a shop, it needs an access token for that shop. Auth is the gate in front of every integration you'll build here.

1. The problem auth solves

Your app talks to many shops. For each one it must answer two questions: "who are you?" (this request really comes from my app) and "what are you allowed to do?" (this shop granted my app permission to read orders, write products, and so on). The output of solving both is an access token — the per-shop credential your server sends on every Admin API call.

2. The modern flow: session token → token exchange

The recommended setup today is session tokens + token exchange, used by embedded apps (apps that render inside the Shopify admin). It relies on Shopify managed installation, which handles the install and permission grant for you — no OAuth redirects.

  • App Bridge (Shopify's JS library for embedded apps) gives your frontend a session token — a short-lived JWT that proves the request came from your app inside the admin.
  • Your backend takes that session token and does a token exchange: it swaps the JWT for an access token for that shop.
  • Now your server calls the Admin API with the access token. No redirect pages, no bouncing the user around.
One-line rule Session token = proof of identity (short-lived JWT). Access token = the key to the Admin API. Token exchange turns the first into the second.
How the backend knows the token is real (the follow-up) Before it trusts a session token, the backend verifies the JWT signature using the app's client secret — if the signature does not match, the token is rejected. It also checks the standard claims: aud (the token was issued for this app's client ID), iss/dest (it came from the right shop), and exp (it has not expired). Only a token that passes all of these is exchanged for an access token.

4. Online vs offline access tokens

Token exchange can return two kinds of access token, and choosing right is a favourite follow-up question.

Offline tokenOnline token
LifetimeLong-lived (no expiry by design)Short-lived, tied to a login
Tied toThe shopA specific logged-in user
Use it forWebhooks, background jobs, syncActions a user does in the UI
WhyRuns when no user is presentRespects that user's permissions
Rule of thumb For an ERP/CRM sync — which runs on a timer and reacts to webhooks with no human watching — use an offline token. Reach for an online token only for actions inside a user's session.

5. Access scopes

An access token is only as powerful as its access scopes — the permissions your app requests, like read_products, write_orders, read_customers. You declare them for the app (configured via the Shopify CLI). Ask for the least you need; requesting write_ everything is a red flag in a security-minded interview.

6. The legacy flow: authorization code grant

Before token exchange, apps used the authorization code grant — the classic OAuth redirect flow: send the merchant to Shopify, they approve, Shopify redirects back with a code, and you swap the code for a token. It works, but the redirects hurt the user experience inside an embedded admin.

When it's still required Standalone (non-embedded) apps — apps that do not render inside the Shopify admin — can't use App Bridge, so they can't get a session token. They still need the authorization code grant. For embedded apps, prefer token exchange.

7. Storing tokens safely

An access token is a long-lived key to a merchant's store data — treat it like a password.

  • Per shop: store one token record per shop domain; never share tokens across shops.
  • Encrypted at rest: keep tokens in your database, encrypted — never in client code, logs, or page markup.
  • Server-side only: the Admin API access token must never reach the browser. That is the whole point of keeping the Admin API on the server.
