Lesson 27 · Domain · Closes a JD gap

Payment & Fulfillment Integrations

The JD says "integrate Shopify with ERP, CRM, payment gateways, and fulfillment platforms." Your ERP/CRM sync is covered in Lesson 11. This lesson covers the other two — same reliability patterns, a few domain-specific rules.

Your win today: talk about payment and fulfillment integrations like someone who has shipped them — the idempotency rule for money, what you must never store, and how fulfillment/tracking flows back to Shopify.

Ties to your mission: this is a named JD responsibility. The good news — the core is the same shape you already know: webhook → queue → idempotent write. The new part is the domain rules that make money and shipping safe.

1. The one rule that carries over: idempotency, but stricter for money

Everything from Lesson 11 still holds — at-least-once delivery, dedupe, idempotent writes. For payments the stakes are higher: a duplicate write is not a cosmetic bug, it is a double charge or a double refund. So the idempotency key stops being "nice" and becomes mandatory, end to end.

"With money, idempotency is not optional. Every charge or refund call carries an idempotency key — usually derived from the order or the event id — so a retry after a timeout can never charge the customer twice."
Trap: a payment request times out. The junior retries blindly — and the first request had actually succeeded, so now the customer is charged twice. The fix is an idempotency key: the gateway recognizes the repeat and returns the original result instead of charging again.

2. Payment gateways — what to say

TopicThe senior answer
Never store card dataYou never touch raw card numbers. The gateway (Stripe, Adyen, PayPal, Shopify Payments) tokenizes them; you store the token / payment intent id, not the PAN. This keeps you out of heavy PCI-DSS scope.
Idempotency keysEvery create-charge / refund call sends a unique key. Retries with the same key are safe no-ops that return the original outcome.
Async by webhookYou do not block waiting for "payment succeeded." The gateway sends a webhook (e.g. payment_intent.succeeded) later. Same pattern as Shopify: verify signature, ack fast, update state from the event.
Verify gateway webhooks tooGateways sign their webhooks (Stripe uses a signing secret + timestamp to stop replay). Verify exactly like you verify Shopify's HMAC. Never trust an unverified "payment done" call.
Reconcile money dailyA scheduled job compares the gateway's records against your orders. The mechanic: compare the gateway's charge list vs your local orders by idempotency key; alert and repair on any mismatch. Money is the one place you always run reconciliation — a missed webhook must never leave an order "paid" in the gateway but "unpaid" in your system.

3. Fulfillment platforms — what to say

Fulfillment is the flow after payment: get the order to a warehouse / 3PL, get tracking back to Shopify, keep the customer informed. Shopify models this with fulfillment orders.

Order paid ──► Shopify FULFILLMENT ORDER created │ ▼ (you or a fulfillment service claims it) ┌─────────────────────────────────────────────┐ │ Your integration / 3PL / warehouse (WMS) │ │ picks, packs, ships │ └───────────────┬───────────────────────────────┘ │ ships + gets a tracking number ▼ Write fulfillment back to Shopify (mark shipped + tracking number + carrier) ──► Shopify emails the customer the tracking link, order shows "Fulfilled"
TopicThe senior answer
Fulfillment ordersThe modern Shopify model. One order can split into several fulfillment orders (different locations / 3PLs). You act on fulfillment orders, not the raw order.
Two-way flowDown: send the order to the warehouse. Up: write the tracking number + carrier back to Shopify so it notifies the customer. Inventory is the two-way case — same echo-loop and conflict care as Lesson 11.
Webhooks to listen forfulfillment_orders/* and fulfillments/create|update. React to these instead of polling.
Fulfillment service appsIf the warehouse is a registered fulfillment service, Shopify can route requests to it directly. Know the term; you may build one.
Partial & failed shipmentsReal orders ship in parts and sometimes fail. Your integration must handle partial fulfillment and a re-ship, not assume one order = one shipment.

4. The mental model to keep it simple

Do not memorize four different integrations. Memorize one shape and the domain rule that bends it:

One shape, four uses Webhook → verify signature → ack fast → queue → idempotent write → reconcile. ERP/CRM: the write is a record. Payments: the write is money, so idempotency is mandatory and you reconcile daily. Fulfillment: the write is two-way (tracking up, orders down) and can be partial.
