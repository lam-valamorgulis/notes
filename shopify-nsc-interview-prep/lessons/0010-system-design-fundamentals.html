Lesson 10 · Day 2 · System design

System Design Fundamentals

The highest-weighted round. You don't need to memorise systems — you need one repeatable method you can run out loud on any question.

Your win today: answer "Give me a repeatable way to design any backend system" — a 7-step framework plus the building blocks, so you never freeze when the whiteboard is blank.

Ties to your mission: system design is the top-weighted part of this interview. This lesson is the template; the next lesson (Shopify ↔ ERP sync) is the worked example you'll actually be asked.

1. The mindset: it's a conversation, not a quiz

A system design question has no single right answer. The interviewer is watching how you think: do you ask before you build, do you reason about scale, do you name the trade-offs? A junior starts drawing boxes. A senior starts asking questions, then thinks out loud, then commits to a design and defends it. You already do this when you scope a theme build — same instinct, bigger canvas.

The three habits that read as "senior" Ask clarifying questions first. Think out loud the whole time. Always name the trade-off ("I'll use a cache here — faster reads, but now I own cache invalidation"). Do these three and you look experienced even on an unfamiliar problem.

2. The 7-step framework (say each step out loud)

Run these seven steps in order. Narrating the step names alone already structures the whole answer.

#StepWhat you say / do
1Clarify requirements + scaleAsk: which features are in scope? Read-heavy or write-heavy? How many users / requests per second? How much data? Latency target? Consistency need?
2Sketch the API / contractName the few endpoints or operations. "createOrder, getOrder, a webhook in, a sync out." This pins down inputs and outputs.
3Data modelList the main entities and their relationships. Pick a store type per entity (relational vs document vs key-value).
4High-level componentsDraw the boxes: client → load balancer → services → cache / queue / database.
5Scale each partWalk box by box: how does each one handle 10x traffic? Add replicas, caching, a queue, sharding where needed.
6Find the bottleneckName the part that breaks first under load (usually the database or a single hot service) and fix that one.
7State the trade-offsClose by naming what you gave up: cost, complexity, consistency, latency. This is the closing sentence interviewers remember — it wins the round.
Time budget In a 40-minute round, spend the first 5–8 minutes on step 1. Rushing past requirements is the number one way people design the wrong system beautifully.

2½. Worked micro-example: steps 1–4 on a URL shortener

Before you run this on the hard Shopify ↔ ERP question in the next lesson, watch the method once on a tiny system: a URL shortener (long URL in, short code out). Here are the first four steps, said out loud.

StepWhat I say for a URL shortener
1. Clarify + scale"Turn a long URL into a short code, and redirect the short code back. It's very read-heavy — maybe 100M redirects/day but only ~1M new links/day. Redirect latency must be low. A stale read is fine, so I don't need strong consistency."
2. API / contract"POST /urls with { longUrl } returns { shortCode }. GET /{shortCode} returns a 302 redirect to the long URL."
3. Data model"One record: shortCode (primary key) → longUrl. Lookups are single-key and huge in volume, so a key-value store fits better than a relational schema."
4. High-level components"Client → load balancer → stateless service → a cache for hot short codes → the key-value store. Redirects hit the cache first, so most reads never touch the database."
Then steps 5–7 continue Scale each part (cache soaks up the read spikes; the write path is tiny), name the bottleneck (the key-value store under redirect load — fix with caching and replicas), and close on trade-offs (a cache means a small staleness window, which is fine here). That is the same shape you will run in full on the Shopify ↔ ERP sync next.

3. The building blocks (one-line "when to use")

These are the LEGO pieces. Know what each one buys you and its one cost, so you can drop it into any design and defend it.

BlockUse it when…The cost / catch
Load balancerYou have more than one service instance and need to spread traffic.One more hop; needs health checks.
Stateless services + horizontal scalingYou want to add capacity by adding identical boxes.No local state — sessions/data must live elsewhere.
Cache (Redis)The same reads are hot and repeated; you can tolerate slightly stale data.You now own invalidation and a consistency window.
Message queueWork can be async; you need to absorb spikes and decouple producers from consumers.Eventual, not instant; you must design idempotent consumers.
Database replicasReads far outnumber writes; you want read scale.Replica lag — reads can be slightly behind the primary.
ShardingOne database can't hold the data or the write load.Cross-shard queries and re-sharding are painful.
CDNYou serve static assets / media to users far from your servers.Caching rules and purges to manage.

Memorise this shape. Almost every backend design is a variation of it: spread traffic, keep services stateless, cache hot reads, push slow work to a queue, scale the database last and most carefully.

4. Consistency: strong vs eventual, and CAP

This is where interviewers separate people who memorised words from people who understand them.

  • Strong consistency — after a write, every read sees the new value immediately. Simple to reason about; harder and slower to scale. Use it for money, inventory counts, anything where a stale read is wrong.
  • Eventual consistency — reads may be briefly stale, but all copies converge soon. Cheaper and more available; you must design for the gap. Use it for feeds, caches, analytics, cross-system sync.
CAP theorem in one plain paragraph A distributed system wants three things: Consistency (every read sees the latest write), Availability (every request gets an answer), and Partition tolerance (it keeps working when the network between nodes breaks). Networks do break, so you must tolerate partitions — that part is not optional. So the real choice is: during a partition, do you stay consistent (reject some requests) or stay available (serve possibly-stale data)? That's the whole theorem. See the glossary.

        5. Back-of-the-envelope estimation

        You don't need exact numbers — you need the right order of magnitude, to know if this is a one-box problem or a fleet problem. Reason like this, out loud:

        Requests per second (rps):
  daily requests / seconds-in-a-day
  1 day ≈ 86,400 s ≈ 100,000 s  (round for speed)

  Example: 5M requests/day
    5,000,000 / 100,000 ≈ 50 rps average
    peak ≈ 2–10x average → plan for ~100–500 rps

Storage:
  rows/day × bytes/row × retention
  Example: 1M orders/day × 2 KB × 365 days
    ≈ 730 GB/year → fits one DB now, plan sharding later
        The estimation move that impresses Round hard (a day ≈ 100,000 seconds), state your assumption, then multiply for peak. Finish with the conclusion: "so ~500 rps at peak — a small stateless fleet behind a load balancer handles that; the database is the part I'd watch."

        6. How to talk in the room

        • Ask first. "Before I design — is this read-heavy or write-heavy? What scale? What's the latency target?" Never assume scale; it changes everything.
        • Think out loud. Narrate the 7 steps. Silence reads as being stuck; narration reads as being in control.
        • Name the trade-off every time you add a box. "Cache here: faster reads, but a staleness window I have to manage."
        • Drive to a bottleneck. Interviewers love "the database is the first thing that breaks, so here's how I'd scale it." That's the senior move.
        The trap that reads as "junior" Jumping straight to boxes and over-engineering for scale you were never given — sharding and multi-region for a system that serves 50 requests per second. Match the design to the numbers you asked for in step 1. Simpler-but-right beats complex-but-guessed.
        Say it like this (memorise the shape)

        "I run the same seven steps on any design. First I clarify the requirements and the scale — reads vs writes, requests per second, data size, latency and consistency needs. Then I sketch the API, then the data model, then the high-level components: client, load balancer, stateless services, a cache for hot reads, a queue for slow work, and a database with replicas. Then I scale each part and name the bottleneck — usually the database. And I close on trade-offs: what I gained, and what I gave up in cost, complexity, or consistency."
