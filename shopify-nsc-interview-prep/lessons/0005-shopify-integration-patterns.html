Shopify Integration Patterns

ERP, CRM, fulfillment. The heart of the NSC job is keeping Shopify and an external system in step — reliably, at scale, without losing data.

Your win today: confidently answer "How would you integrate Shopify with an ERP, CRM, or fulfillment system?" — with a real, named pattern, not a vague answer.

Ties to your mission: this is the core backend work at NSC. It also sets up the Day-2 system-design set piece (Lesson 11), so learn the shape well here.

1. The one job: keep two systems in sync

An ERP, CRM, or warehouse (WMS) each holds its own copy of products, orders, inventory, or customers. Your app's job is to make sure both sides agree — and to keep agreeing as data changes all day. There is a standard three-part pattern for this. Say all three parts and you sound senior.

2. The standard three-part pattern

  • Initial bulk import — one big first load. Use bulk operations to pull all existing data at once as a file, instead of thousands of small calls.
  • Ongoing event sync — after the first load, react to changes. A webhook fires, you put it on a queue, a worker transforms it and pushes it to the external system.
  • Scheduled reconciliation — a reconciliation job runs on a timer, re-reads the source of truth, and fixes any drift from missed or wrong events.
The core three vs the nice-to-say details Must keep (the spine): bulk import → event sync → reconciliation. If you only remember three things, remember these, in this order. Nice to say (extra credit): the bulk-operation limits, idempotency and the DLQ, the two rate limits, and id mapping. These make you sound senior — but they are detail hung on the spine, not the spine itself.

3. Why bulk for the first load

A store can have hundreds of thousands of products or orders. Looping normal API calls would burn your rate limit for hours. Bulk operations run a GraphQL query asynchronously in the background and hand you the whole result as a JSONL file.[1] You start it, poll until it is done, then download and import the file.

mutation {
  bulkOperationRunQuery(query: """
    { products { edges { node { id title } } } }
  """) {
    bulkOperation { id status }
    userErrors { field message }
  }
}

The query must include a connection (here products). You poll the returned operation until status is COMPLETED, then fetch its JSONL url.

Know the limits (say a number) Bulk query results stay available for 7 days. The query must include at least one connection field, allows up to 5 connections, and a max nesting depth of 2. There is also bulkOperationRunMutation for large writes back to Shopify.

4. Ongoing sync: webhook → queue → transform → push

After the import, you keep up with changes through events. A webhook tells you an order was created or a product changed. The senior move is: acknowledge fast, process later. Return 200 within the 5-second timeout, drop the job on a queue, and let a worker do the real work: transform Shopify's shape into the ERP's shape, then write it.

Why the queue matters The queue absorbs traffic spikes (a flash sale), lets you retry safely, and keeps the webhook handler fast so Shopify does not time out and retry you. Never call the slow ERP directly from the webhook handler.

5. Make it reliable: idempotency, retries, rate limits

Webhooks can arrive twice and jobs can be retried, so every write must be idempotent — running it once or five times gives the same result. Dedupe on a stable id (Shopify's X-Shopify-Webhook-Id, or the order id) before you write.

Watch both rate limits, not just Shopify's:

The failure juniors forget A write that keeps failing after retries must not vanish. Send it to a dead-letter queue (DLQ) so you can inspect and replay it. "Retry a few times, then DLQ" is the line they want to hear. (A poison message just means a job that keeps failing no matter how many times you retry it.)

6. Mapping ids and two-way sync

Each side has its own id for the same thing. You must store the link. Keep a mapping table in your database (Shopify id ↔ ERP id), or store the external id on the Shopify resource with metafields. Without this map you cannot tell an update from a new record.

If data flows both ways (Shopify ⇄ ERP), you need a rule for conflicts. Two common ones:

  • Source of truth — pick which system owns each field (e.g. ERP owns price and stock, Shopify owns product copy). Cleanest.
  • Last-write-wins — the newest change wins, using timestamps. Simple, but can lose an edit.
Say it like this (memorise the shape)

"I'd use a three-part pattern. One: an initial bulk import with bulk operations, which returns a JSONL file, so I don't fight the rate limit. Two: ongoing sync — a webhook lands, I verify it, ack fast, put it on a queue, and a worker transforms and pushes it to the ERP. Three: a scheduled reconciliation job that re-reads Shopify to fix drift. I make every write idempotent, dedupe on the webhook id, respect both Shopify's and the ERP's rate limits, keep a Shopify-to-ERP id mapping, and send poison messages to a dead-letter queue. For two-way sync I define a source of truth per field."
