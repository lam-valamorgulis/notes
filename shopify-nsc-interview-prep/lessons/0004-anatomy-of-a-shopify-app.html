Anatomy of a Shopify App

You have built themes that live inside a store. Now build the app that sits beside the store and drives it over the API.

Your win today: confidently answer "Walk me through how you'd build and structure a Shopify app." — name the parts, draw the flow, sound like you have shipped one.

Ties to your mission: NSC builds Node.js + Shopify apps. This is the whiteboard question that opens the Shopify deep-dive. If you can name the parts and draw the request flow, you pass the first filter.

1. The bridge from what you already know

A theme runs inside Shopify: Shopify renders your Liquid and serves the page. An app is different — it is your own service that lives on your own server and talks to the store through the Admin API. The merchant clicks a link in their Shopify admin, and your app opens like a page inside that admin. Same store you know from Liquid — now you own the code and the data around it.

2. Two ways to slice an app

Interviewers like to hear you place an app on two axes. First, who can install it. Second, where its UI renders.

One-line rule Public vs custom = who installs it. Embedded vs standalone = where the screen lives. Most modern apps are public and embedded. An embedded app uses App Bridge, Shopify's JS library, to get session tokens and to navigate inside the admin.

3. The moving parts of a real app

When they ask "how would you structure it", list these five parts — each has a job:

  • The embedded admin UI — a React front-end rendered inside the Shopify admin via App Bridge. It shows settings and status to the merchant.
  • A Node backend service — your server. It authenticates requests, calls the Admin API, and serves the UI.
  • A database — stores shop records, access tokens, sessions, and your own app data. This is your source of truth for app state.
  • Webhook endpoints — HTTP routes that receive webhooks from Shopify (order created, app uninstalled) and hand the work off fast.
  • Background workers + a queue — a queue holds jobs; workers process them off the request path (syncs, exports, slow API calls).
If you remember one thing The five parts are: embedded UI, Node backend, database, webhook endpoints, and workers + a queue. If you can list these five and say what each one does, you can answer the whole "how would you structure it" question.

4. How Shopify CLI scaffolds this

You do not build all of this by hand. The Shopify CLI creates a working app in one command. The Remix template is the app template it scaffolds — it wires up App Bridge, auth, a webhook setup, and an example admin page for you.[1] You declare your access scopes (like read_products) in config, and the CLI opens a tunnel so you can preview the app on a dev store.

# scaffold a new app with the Shopify CLI
npm init @shopify/app@latest

# run it against a dev store (opens a secure tunnel)
shopify app dev
Say this to sound current Shopify now recommends the React Router template for new apps; the Remix template is the older default and still widely used. Either way the shape is the same — CLI scaffold, App Bridge, auth, webhooks. Naming both shows you follow the platform.

5. One admin request, end to end

This is the flow to draw. The merchant opens your app page inside the admin:

  1. App Bridge attaches a short-lived session token (a signed JWT) to the request to your backend.
  2. Your backend does token exchange: it swaps that session token for an access token for the shop (this is "Shopify managed installation" — no redirects).
  3. You store or reuse the access token from your database.
  4. Your backend calls the Admin GraphQL API with that token to read or write store data.
  5. Your backend returns data; the embedded UI renders it. Slow work is pushed to the queue instead of blocking the response.
The catch juniors miss The session token is not the API token. It only proves the request came from your embedded app. You must exchange it for an access token before you can touch the Admin API. Mixing these up is a classic red flag.

6. Hosting and the theme touch-point

Hosting in one line: your Node backend is a normal web service — deploy it anywhere that runs Node (a container on Fly, Render, Heroku, AWS) behind HTTPS, with the database and a worker process alongside.

Theme app extensions in one line: they let your app add front-end blocks to the storefront through the theme editor without editing the merchant's theme code, so nothing breaks and the code is removed cleanly on uninstall. (The Storefront API, Shopify Functions, and Plus features build on this same app.)
