Event-Driven & Messaging: Kafka vs RabbitMQ vs SQS

Every backend interview asks this. You need one clear answer for each tool, plus a real pick for a Shopify sync.

Your win today: confidently answer "When do you use Kafka vs RabbitMQ vs SQS?" — and back it with a concrete choice for a Shopify↔ERP sync.

Ties to your mission: the JD lists "Kafka / RabbitMQ / SQS" and event-driven systems. This is a breadth question — they want to hear you reason, not recite.

1. Why put a queue between services?

A message queue is a buffer that sits between a producer (who makes work) and a consumer (who does it). You reach for one for three reasons:

  • Decouple services. The producer drops a message and moves on. It does not wait for the consumer, and it does not care if the consumer is slow or down right now.
  • Absorb spikes. If 10,000 orders land in a minute, the queue holds them. Your consumer drains them at a safe rate instead of falling over.
  • Retry safely. If processing fails, the message stays in the queue and is tried again — no lost work.
Request/response vs event-driven Request/response = service A calls service B and waits (tight coupling; if B is down, A fails). Event-driven = A emits an event and forgets; whoever cares reacts later. This is event-driven architecture — looser coupling, easier to scale.

2. Kafka vs RabbitMQ vs SQS

These three are not the same tool with different logos. They are three different shapes.

ThroughputVery high (millions/sec)High, but lower than KafkaHigh; near-infinite scale, zero tuning

Kafka is a log: it keeps events around, so many consumers can read the same stream and you can replay from any point. RabbitMQ is a classic broker: rich routing and per-message acknowledgements, great for spreading tasks to workers. Amazon SQS is a fully managed queue: Standard gives at-least-once delivery and huge throughput; FIFO gives ordering plus exactly-once within a 5-minute dedup window — outside that window, and end-to-end, you still make the consumer idempotent, because true exactly-once is not real.

3. Pub/sub vs work queue

Two delivery shapes, and the difference matters:

WORK QUEUE (compete) PUB/SUB (fan-out) producer --> [ queue ] producer --> [ topic ] | | | | | | v v v v v v W1 W2 W3 sub-A sub-B sub-C each message -> ONE worker each message -> EVERY subscriber
  • Work queue: each message is handled by exactly one worker. Add workers to go faster. (RabbitMQ, SQS.)
  • Pub/sub: each message goes to every subscriber (fan-out = one event copied to every subscriber). Good for "one event, many reactions". (Kafka topics; on AWS, SNS in front of SQS.)

4. Delivery guarantees

GuaranteeMeaningRisk
At-most-onceDelivered zero or one timeCan lose messages
At-least-onceDelivered one or more timesCan duplicate messages
Exactly-onceDelivered once, no dup, no lossCostly and hard; narrow support
The safe default (say this) Real exactly-once end-to-end is expensive and rare. The common, robust choice is at-least-once delivery + idempotent consumers: assume you may see a message twice, and make processing safe to repeat (e.g. de-dup on an order id). You get no data loss without paying for true exactly-once.

5. Dead-letter queues and ordering

A dead-letter queue (DLQ) catches messages that keep failing after several tries. Instead of blocking the queue or losing the message, you park it in the DLQ, alert, and inspect it later. Pair every real queue with a DLQ and a retry-with-backoff policy.

Ordering costs you throughput. Kafka orders within a partition, and SQS FIFO orders within a message group — both trade some parallelism for order. Only ask for ordering where you truly need it (e.g. "update" must not overtake "create" for the same order).

6. The pick for a Shopify↔ERP sync

Concrete scenario: Shopify fires order webhooks; you must push each order into an ERP that is sometimes slow or down. What queue?

Say it like this (memorise the shape)

"My webhook handler just validates and drops the order onto a queue, then returns 200 fast. My default is SQS — it's fully managed, gives at-least-once delivery, and I add a DLQ plus backoff for free, so a flaky ERP never loses an order. I make the consumer idempotent on the order id, so retries and duplicate webhooks are safe. If the same order needs strict ordering I use SQS FIFO with the order id as the group key — but FIFO's exactly-once only holds within a 5-minute dedup window, so I keep the consumer idempotent regardless, because true end-to-end exactly-once isn't real. I'd reach for Kafka only if we needed to replay the event history or stream to analytics and several teams; for one point-to-point sync that's operational overkill. RabbitMQ would fit if I needed rich routing and wasn't committed to AWS."

Why SQS wins here: the JD is AWS-heavy, the job is a simple point-to-point sync, and "zero ops + DLQ + at-least-once + idempotent consumer" is the lowest-risk answer. Naming when you'd switch to Kafka (replay/streaming) is what makes it sound senior.
