Shopify's Two APIs & Rate Limits

The most common Shopify deep-dive opener. You already know this domain from Liquid — now see it from the server.

Your win today: confidently answer "What's the difference between the Admin API and the Storefront API, and how do Shopify's rate limits work?" — out loud, in under a minute.

Ties to your mission: the JD names "Shopify Admin API, Storefront API" in the must-have list. This is a core, expected question for the deep-dive round.

1. The bridge from what you already know

As a theme developer you wrote {{ product.title }} and {{ cart.item_count }} in Liquid. Shopify's server rendered those for you. A backend app does the same thing without Liquid: it asks Shopify's APIs for that data directly, over HTTP, and gets JSON back. Same store, same objects — different door.

There are two main doors, and picking the right one is the first thing an interviewer checks.

2. Admin API vs Storefront API

PurposeManage the store (back office)Build the buying experience
Typical callerYour backend app / integrationA headless site, custom cart, mobile app
Reads/writesProducts, orders, customers, inventory, fulfillment, discountsProducts, collections, carts, checkout start

One-line rule Admin API = staff/back-office actions. Storefront API = shopper-facing actions. An ERP or CRM integration lives almost entirely on the Admin API.

3. GraphQL is now the primary API

As of the recent API versions, Shopify treats the GraphQL Admin API as primary and the REST Admin API as legacy — new development should use GraphQL.[1] Why GraphQL wins for integrations:

  • Ask for exactly what you need — one request returns just the fields you list, no over-fetching.
  • One round trip — fetch a product and its variants and its inventory in a single call.
  • Typed schema — the API is self-documenting; tooling autocompletes fields.
  • Bulk operations — for huge datasets, run an async bulk operation instead of thousands of calls.
The catch (say this to sound senior) GraphQL isn't magically faster. A careless query can be expensive (high query cost) or cause N+1 work on the server. You still design queries deliberately.

4. Rate limits — the part they probe

This is where juniors get vague and seniors get specific. Shopify uses a leaky bucket, but the two APIs measure it differently:

GraphQL Admin API — calculated query cost

Every field you request has a point cost. You spend from a 1000-point bucket that refills 50 points per second (standard plans).[1] The response tells you your exact budget in extensions.cost:

"extensions": {
  "cost": {
    "requestedQueryCost": 3,
    "actualQueryCost": 3,
    "throttleStatus": {
      "maximumAvailable": 1000.0,
      "currentlyAvailable": 997,
      "restoreRate": 50.0
    }
  }
}

How you handle it (the senior answer):

  • Read throttleStatus.currentlyAvailable and slow down before you hit zero.
  • Request only the fields you need — smaller queries cost fewer points.
  • Use retry with backoff on the throttled error, and cursor-based pagination for big lists.
  • For very large jobs, switch to bulk operations so you don't fight the bucket at all.

REST Admin API — request bucket

REST counts requests, not cost: a bucket of ~40 requests that refills ~2 per second (standard). Simpler, but you can't fetch related data in one call, so you make more of them. Another reason GraphQL wins for integrations.

Storefront API

Also cost-based, but scaled for shopper traffic and measured per IP / uncached request. Point: it's built to be called a lot from clients, unlike the Admin API.
