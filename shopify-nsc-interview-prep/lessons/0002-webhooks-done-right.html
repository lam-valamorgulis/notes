Webhooks Done Right

This is the classic "show me you can build backend integrations" question. Get the four rules right and you sound senior instantly.

Your win today: confidently answer "How do you build a reliable Shopify webhook handler?" — with the four rules, out loud, in under a minute.

Ties to your mission: the JD is a Shopify + Node.js backend role syncing store data to other systems (ERP/CRM). Webhooks are how that sync starts. This is a guaranteed question.

1. What a webhook is (and why it beats polling)

A webhook is an HTTP POST that Shopify sends to your server the moment something happens — an order is created, a product is updated, a customer is deleted. You subscribe to a topic (like orders/create) and give Shopify a URL. Shopify calls that URL with the event data as JSON.

The alternative is polling: your app asks "any new orders?" every minute, forever. Polling wastes rate-limit budget, adds delay, and misses nothing only if you never stop. Webhooks flip it: Shopify pushes the event to you the instant it happens. Push beats pull for freshness and cost.

Say this Webhooks are push; polling is pull. I use webhooks for near-real-time events and keep polling only as a backup safety net.

2. The four rules of a reliable handler

Almost every webhook bug comes from breaking one of these four rules. Memorise them as a list — interviewers love a numbered answer.

Rule 1 — Verify HMAC on the RAW body

Anyone can POST to your URL. To prove a request is really from Shopify, you verify its HMAC. Compute HMAC-SHA256 over the raw request body using your app's client secret, then compare the result to the X-Shopify-Hmac-SHA256 header. If they do not match, reject with 401.

The #1 mistake You must hash the raw bytes of the body, before any JSON parsing. If your framework auto-parses the body (e.g. express.json()), the re-serialized JSON differs from the original bytes and the HMAC will never match. Capture the raw body first.

Rule 2 — Respond 200 inside the 5-second budget

Shopify has a 1-second connection timeout and a 5-second total timeout. If you do not return 200 OK in time, Shopify treats it as a failure and retries. So your handler must be fast: verify, accept, and reply. Do not call the ERP, resize an image, or run a long database job before you answer.

Rule 3 — Be idempotent (dedupe on the webhook id)

Shopify may deliver the same event more than once (that is normal for at-least-once delivery). Your handler must be idempotent: processing the same event twice has the same effect as once. Use the X-Shopify-Webhook-Id header as the idempotency key — store seen ids and skip any you have already handled.

Rule 4 — Do the real work asynchronously via a queue

Because of Rule 2, the handler cannot do slow work inline. So it pushes a job onto a queue (SQS, RabbitMQ) and returns 200 at once. A separate worker picks up the job later and does the heavy lifting: transform the data, call the ERP, retry on failure. This is the "ack fast, process later" pattern.

3. Retries and auto-removal

If your endpoint fails or times out, Shopify retries up to 8 times over roughly 4 hours with growing gaps (backoff). This is why idempotency matters — a retry of an event you already processed must not create a second order in your ERP.

The scary part If deliveries keep failing, Shopify eventually auto-removes the subscription. Then you silently stop receiving that event. Monitor delivery failures, and use reconciliation (next section) so a removed subscription does not quietly break your sync.

4. Ack fast, process later — the flow

Shopify event (orders/create) | v POST + X-Shopify-Hmac-SHA256 + X-Shopify-Webhook-Id +----------------------------+ | Your webhook endpoint | | 1. verify HMAC (raw body) | | 2. dedupe on webhook-id | | 3. enqueue job | | 4. return 200 (< 5s) | +----------------------------+ | v [ Queue: SQS / RabbitMQ ] --(on repeated failure)--> [ DLQ ] | v +----------------------------+ | Worker (background) | | transform + retry/backoff | +----------------------------+ | v [ ERP / CRM sync ]

The queue also gives you a dead-letter queue (DLQ): after a worker fails a job too many times, the message goes to the DLQ so you can inspect it instead of losing it.

5. The ack-then-enqueue handler (pseudo-code)

app.post('/webhooks/orders-create',
  rawBody(),                         // keep the raw bytes
  (req, res) => {
    const digest = hmacSha256(req.rawBody, CLIENT_SECRET);
    if (!safeEqual(digest, req.header('X-Shopify-Hmac-SHA256')))
      return res.status(401).end();  // Rule 1: not from Shopify

    const id = req.header('X-Shopify-Webhook-Id');
    if (seen.has(id)) return res.status(200).end(); // Rule 3: dedupe

    queue.enqueue({ id, topic: 'orders/create', body: req.rawBody });
    seen.add(id);
    return res.status(200).end();    // Rule 2 + 4: ack fast, work later
  });

Notice what the handler does not do: it never talks to the ERP. That job belongs to the worker.

Senior talking point — the in-memory Set is a demo shortcut In production the dedupe store must be shared and durable — a unique key in Postgres or Redis — not an in-memory Set, or a restart or a second instance re-processes events. The const seen = new Set() above only works for one process that never restarts; say this out loud when you show this code.

6. Reconciliation — the safety net

Webhooks can be missed: your server was down, a subscription was auto-removed, or a rare event never arrived. So a mature integration also runs a scheduled reconciliation job. On a timer (say hourly), it re-reads the source of truth from Shopify's Admin API — "give me all orders changed since the last sync" — and fixes anything the webhooks missed. Webhooks give speed; reconciliation gives correctness.

7. How this feeds an ERP/CRM sync

Put it together and you have the exact system this job builds: Shopify emits an event, your endpoint verifies and enqueues it, a worker maps Shopify fields to the ERP's shape and calls the ERP API with its own retries, and a nightly reconciliation job repairs any gaps. Loose coupling, survives spikes, safe to retry.
