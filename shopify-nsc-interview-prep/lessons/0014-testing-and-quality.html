Testing & Quality

Your win today: confidently answer "How do you test a backend plus Shopify integration?" — the test pyramid, how you mock Shopify, and how you prove idempotency — out loud, in under a minute.

Ties to your mission: the JD wants a senior who ships safe code. You do not need to be a testing expert — you need a clear mental model and the right vocabulary. That is what this lesson gives you.

1. The test pyramid — and why it is a pyramid

The test pyramid is a simple rule for how many of each kind of test to write. Many small tests at the bottom, fewer big tests at the top.

/\ / \ few → End-to-end (E2E): whole system, real browser/HTTP /----\ / \ some → Integration: your code + DB / queue / HTTP /--------\ / \ many → Unit: one function, no I/O, milliseconds /------------\

Why this shape? It is about speed, cost, and how clearly a failure points at the bug:

  • Unit tests are fast (milliseconds) and cheap. When one fails, you know exactly which function broke.
  • Integration tests are slower and need real dependencies (a database, a queue). They catch bugs at the seams between parts.
  • E2E tests are slowest and most brittle. One failure can mean anything, and they are painful to debug. So you keep only a few, for the most important flows.
The anti-pattern to name The "ice-cream cone": mostly slow E2E and manual tests, few unit tests. It is slow, flaky, and expensive to keep. Saying you avoid this shows you have felt the pain.

2. What to UNIT test

Unit tests are for pure logic — code that takes input and returns output with no database, no network, no clock. In a Shopify integration, the highest-value unit tests are:

  • Business rules — "apply this discount", "is this order eligible for sync", "which tier is this customer".
  • Data transforms — turning a Shopify order into your internal shape, formatting money, mapping statuses.
  • The ERP mapping — the function that converts a Shopify product/order into the exact fields the ERP or CRM expects. This is where silent bugs hide, so test it hard: missing SKU, null address, a currency you did not expect.
Why this matters for you The mapping layer is your code, not Shopify's. It is easy to test (input JSON → expected object) and it is exactly where integration bugs live. If you only unit test one thing, test the mapping.

3. INTEGRATION tests — the seams

Integration tests check that your code works with a real dependency, not a fake. They are slower, so you write fewer of them, but they catch what unit tests cannot:

DependencyWhat the integration test proves
DatabaseYour query, schema, and migration actually work. Run against a real Postgres in Docker, not a mock.
QueueA job you push to the queue is picked up and processed once. Retries and the dead-letter path behave.
HTTP / APIYour client sends the right request and parses the real response shape (headers, pagination, errors).

A common, cheap way to get a real database in tests is a throwaway container (for example Testcontainers, or a Postgres service in CI). The test spins it up, runs, and throws it away.

4. Testing a Shopify integration WITHOUT hitting Shopify

This is the part interviewers love, because it separates people who have done it from people who have not. You never call the real Shopify API in a test — it is slow, rate-limited, and not repeatable. Instead:

a) Mock the Admin API

Intercept the outgoing HTTP call and return a canned response. In Node you use a tool like nock (intercepts at the HTTP layer) or msw (Mock Service Worker). Your code thinks it called Shopify; really it got your fixture.

// Mock the Admin API with nock — no real network call
nock('https://my-shop.myshopify.com')
  .post('/admin/api/2026-07/graphql.json')
  .reply(200, { data: { order: { id: 'gid://shopify/Order/123' } } });

const result = await syncOrderToErp('123');
expect(result.erpId).toBe('ERP-123');

b) Use recorded webhook fixtures

Save a real Shopify webhook body once as a JSON file (a "fixture"). Then your tests feed that fixture to your handler again and again. No waiting for Shopify to send a real event.

c) Test your HMAC verification with a known secret and body

Your webhook endpoint must verify the HMAC signature. You can test this fully offline: take a known secret, a fixed raw body, compute the expected signature yourself, and assert your verifier accepts it — and rejects a tampered body.

const secret = 'test_secret';
const body = '{"id":123}';
const good = crypto.createHmac('sha256', secret)
  .update(body).digest('base64');

expect(verify(body, good, secret)).toBe(true);   // real signature passes
expect(verify(body, 'AAAA', secret)).toBe(false); // fake signature fails

5. Testing IDEMPOTENCY and RETRIES

Shopify can send the same webhook more than once, and your queue will retry failed jobs. So your handler must be idempotent: running it twice must have the same single effect as running it once.

The test is beautifully simple — send the same webhook twice and assert one effect:

const event = loadFixture('order-created.json'); // same X-Shopify-Webhook-Id

await handleWebhook(event);
await handleWebhook(event); // duplicate delivery

const rows = await db.orders.count({ shopifyId: 123 });
expect(rows).toBe(1); // exactly one order, not two
Say the mechanism, not just the word Idempotency is usually done with an idempotency key — store the X-Shopify-Webhook-Id, and skip the work if you have seen it. Testing retries is the same idea: run the job twice and assert the outcome is identical.

6. TDD in one paragraph

Test-Driven Development (TDD) is a loop: red → green → refactor. First write a small failing test (red). Then write the least code to make it pass (green). Then clean up the code while the test stays green (refactor). Repeat. The point is not the tests themselves — it is that writing the test first forces you to design a clear, testable interface and gives you a safety net to refactor without fear.

7. Coverage — a target, not a rule

Coverage is the percent of your code lines that tests run. A common target is around 80%. But the senior point is this:

Say it like this (the mature take)

"I aim for about 80% coverage, but I test behavior, not lines. 100% coverage can still miss the bug that matters, and testing the last few lines is usually wasted effort. I put my tests where the risk is — the ERP mapping, HMAC verification, and idempotency."

8. Tests run in CI on every push

None of this helps if tests only run on your laptop. They must run in CI/CD automatically on every push and every pull request. A red build blocks the merge. That is how the team keeps quality without trusting memory.

The full 30-second answer (memorise the shape)

"I follow the test pyramid: many unit tests for pure logic like my ERP mapping and data transforms, some integration tests for the database, queue and HTTP, and a few end-to-end tests for the critical flows. I never call the real Shopify API in tests — I mock the Admin API with nock or msw, replay recorded webhook fixtures, and test HMAC verification with a known secret and body. I prove idempotency by sending the same webhook twice and asserting one effect. I aim for around 80% coverage on behavior, and everything runs in CI on every push."
