Design: Shopify ↔ ERP/CRM Sync at Scale

The one system design question you are most likely to get for this role. This is a full worked answer — run it end to end.

Your win today: design a system that keeps Shopify and an ERP/CRM in sync at scale, end to end — ingestion, queue, workers, reconciliation, idempotency, rate limits, and failure recovery, all named out loud.

Ties to your mission: the JD is a Shopify backend role, and "keep Shopify in sync with an ERP/CRM" is the classic design prompt for it. This lesson combines the 7-step framework from Lesson 10 with the Shopify facts from Day 1 (webhooks, rate limits, bulk operations).

2. Architecture (the whole flow)

Three data paths, one system: real-time events (webhooks), a safety net (reconciliation), and a first fill (bulk import).

  1. Real-time: Shopify webhook → ingestion endpoint (verify HMAC, return 200 fast) → message queue → worker pool (transform → write to ERP).
  2. Safety net: a scheduled reconciliation job re-reads Shopify and compares against the ERP to catch any missed or dropped events.
  3. First fill: a one-time bulk import (bulkOperationRunQuery → JSONL) to load all historical data without hitting rate limits.

Why the queue is the heart of this The webhook must return 200 within Shopify's 5-second timeout (that 5s is the total window — roughly the first second goes just to connecting, so you really have very little time to work). You cannot write to a slow ERP inside that window. So the endpoint does the minimum — verify, enqueue, ack — and the queue absorbs spikes and feeds workers at a rate the ERP can take. The queue is your shock absorber and your backpressure valve.

3. Reliability (the part they push on)

Webhooks are at-least-once: Shopify retries on failure (about 8 times over ~4 hours), so the same event can arrive more than once, and events can arrive out of order. You design for all of that.

  • Idempotency: dedupe on X-Shopify-Webhook-Id (plus a per-resource idempotency key). Store seen IDs in a dedupe table; if it's already there, skip. Every ERP write is "create-or-update on the mapped id," never a blind insert.
  • Retries with exponential backoff: if the ERP write fails, the worker retries with growing delays instead of hammering it.
  • Dead-letter queue: a message that keeps failing (bad data, "poison message") moves to a DLQ after N attempts, so it stops blocking the line. A dashboard + alert lets a human inspect and replay it.
  • Ordering: global ordering is hard and usually unnecessary. Keep per-resource order (all events for order #1001 processed in sequence) by partitioning the queue on the resource id, or by using the event timestamp so an older update can't overwrite a newer one.
The trap juniors fall into Trying to make the pipeline "exactly-once." You can't guarantee exactly-once delivery. You accept at-least-once delivery and build idempotent consumers — that gives exactly-once effect at the ERP. Say this sentence and you sound senior.

3½. Kata — type the ingestion handler from a blank file

This is the most likely live-coding task for this role. Open a blank file and type the ingestion handler from memory: verify HMAC on the raw body → dedupe check → enqueue → return 200. Then compare to the model.

Your task (cover the model) Write a handler that (1) reads the raw body, (2) verifies the X-Shopify-Hmac-SHA256 header and rejects with 401 if it fails, (3) skips if the X-Shopify-Webhook-Id is already in the dedupe table, (4) enqueues the event, (5) returns 200 fast — with no ERP write inside the request. 
import crypto from 'crypto';

// The HMAC must be computed on the RAW body bytes, not parsed JSON.
app.post('/webhooks/orders',
  express.raw({ type: 'application/json' }),
  async (req, res) => {
    const hmac = req.get('X-Shopify-Hmac-SHA256') || '';
    const digest = crypto
      .createHmac('sha256', process.env.SHOPIFY_SECRET)
      .update(req.body)                 // req.body is a Buffer (raw)
      .digest('base64');

    // constant-time compare — reject spoofed calls
    const ok = hmac.length === digest.length &&
      crypto.timingSafeEqual(Buffer.from(hmac), Buffer.from(digest));
    if (!ok) return res.sendStatus(401);

    const webhookId = req.get('X-Shopify-Webhook-Id');
    if (await seenBefore(webhookId)) return res.sendStatus(200); // dedupe → no-op

    await markSeen(webhookId);
    await queue.enqueue(JSON.parse(req.body.toString())); // hand off to workers
    return res.sendStatus(200);         // ack fast; ERP write happens off-queue
  });

4. Rate limits on BOTH sides

Two systems, two limits. Name both.

  • Shopify (reads): the Admin GraphQL API uses calculated query cost — a 1000-point bucket refilling 50 points/sec on standard plans. Read extensions.cost.throttleStatus and back off before you hit zero. For big pulls (reconciliation, initial load), use bulk operations so you never fight the bucket.
  • ERP (writes): the ERP has its own limits and can be slow. Batch writes where the ERP supports it, and let the queue apply backpressure — workers pull only as fast as the ERP can accept, so a spike in Shopify events never overruns the ERP.
One line to remember The queue protects the ERP from Shopify's spikes; bulk operations and backoff protect you from Shopify's rate limits. You respect both buckets, from both directions.

5. Data mapping (how records match)

You need to know which Shopify record equals which ERP record — otherwise updates create duplicates. Keep a mapping store.

  • A DB table: shopify_id ↔ erp_id (plus entity type, last-synced timestamp, and a hash of the last payload to skip no-op writes).
  • Or, for the reverse lookup, store the ERP id back on Shopify as a metafield so the record carries its own link.

This mapping is what makes writes idempotent: a repeated event resolves to the same erp_id and updates the same record instead of creating a new one. It's also how you decide create vs update on every incoming event.

-- dedupe + mapping, the two tables that make it safe
webhook_dedupe(webhook_id PK, received_at)          -- skip if seen
id_map(entity, shopify_id, erp_id, last_hash,       -- match + no-op skip
       last_synced_at, UNIQUE(entity, shopify_id))

5½. Two-way sync & conflicts

Two-way sync (e.g. inventory changing on both sides) raises the two hardest follow-ups. A senior answer names both problems and a concrete fix for each.

(a) Prevent echo loops

The danger: a Shopify → ERP write triggers an ERP change event → which writes back to Shopify → which fires another Shopify webhook → and round it goes forever. Two ways to break the loop:

  • Tag the write origin. When you write to a side because of a sync, mark that write (a metafield, a header, or a source: "sync" flag). When an event comes back carrying your own tag, skip it — you caused it, so it is not real news.
  • Skip if the content hash is unchanged. Store a hash of the last payload you wrote in the mapping table (the last_hash column). Before writing, hash the incoming record; if it matches what is already stored, it is a no-op — do not write, so no new event fires and the loop dies.

(b) Resolve conflicts (both sides changed)

When Shopify and the ERP both change the same field before a sync catches up, you need a rule chosen up front:

  • Source of truth per field. Declare which system owns each field — for example Shopify owns price and product content; the ERP owns inventory and cost. The owner always wins; the other side only reads that field.
  • Newest wins (timestamp or version). Where no single owner fits, keep an updated_at or a version number per record and let the most recent change win (last-write-wins). A version number is safer than a clock, because clocks on two systems drift apart.
Say it like this "For two-way sync I stop echo loops by tagging the sync origin and by skipping no-op writes with a content hash. For conflicts I declare a source of truth per field — Shopify owns content, the ERP owns inventory — and fall back to newest-version-wins where there is no clear owner."

6. Scale & ops

  • Horizontal workers: the worker pool is stateless — add workers to drain the queue faster on sale days. This is horizontal scaling in action.
  • Partition by shop / entity: if you serve many shops, partition the queue by shop id (fairness, isolation) and keep per-resource ordering inside a partition.
  • Monitoring + alerting: track queue lag (how far behind are we?), error rate, retry rate, and DLQ depth. Alert when lag or DLQ crosses a threshold.
  • DLQ dashboard: a place to see, inspect, and replay poison messages by hand.

7. Failure modes + recovery

What breaksWhat happens / how you recover
ERP is down (e.g. 2 hours)Workers fail the write and retry with backoff; messages stay safely in the queue (it buffers). Nothing is lost. Shopify already got its 200, so it does not retry. When the ERP returns, workers drain the backlog. Messages that never succeed land in the DLQ for replay.
A webhook is missed / droppedThe scheduled reconciliation job re-reads Shopify (via bulk ops), compares against the ERP using the mapping table, and re-syncs anything missing. This is why you never rely on webhooks alone.
Duplicate events arriveThe dedupe table (X-Shopify-Webhook-Id) and idempotent create-or-update mean the second copy is a no-op. No double orders.
Poison message (bad data)After N failed retries it moves to the DLQ so it stops blocking the queue. Alert fires; a human inspects and replays after a fix.
Our ingestion endpoint is downShopify retries the webhook (~8x over ~4h). If still missed, reconciliation catches it later. Two safety nets.
Say it like this (the whole design in 6 sentences)

"Shopify sends webhooks to an ingestion endpoint that verifies the HMAC and returns 200 within the 5-second timeout, then pushes the event onto a message queue. A pool of stateless workers pulls from the queue, transforms each event, looks up the record in a mapping table, and does an idempotent create-or-update into the ERP. Because delivery is at-least-once, I dedupe on the Shopify webhook id and make every write idempotent, so duplicates and retries are safe. I respect rate limits on both sides — bulk operations and backoff for Shopify reads, batching and queue backpressure for ERP writes. A scheduled reconciliation job re-reads Shopify to catch any missed events, and a one-time bulk import loads the history. Failures are contained: the queue buffers when the ERP is down, poison messages go to a dead-letter queue, and monitoring on queue lag and DLQ depth tells me when to act."
