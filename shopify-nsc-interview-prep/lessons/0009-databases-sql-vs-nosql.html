Databases: SQL vs NoSQL

Where the data lives. Choose wrong and every feature above it fights the storage forever.

Your win today: confidently answer "SQL or NoSQL — how do you choose, and how do you model the data?" — with a concrete example.

Ties to your mission: an NSC backend syncs Shopify with an ERP. That means orders, money, and id mappings — data where getting storage right is the whole job.

1. Two families, one question

There are two main choices. The interview question is never "which is better" — it is "which fits this data, and why". Answer with the shape of the data, not with a favourite.

Relational (SQL)Document (NoSQL)
ExamplesPostgreSQL, MySQLMongoDB
SchemaFixed, enforcedFlexible, per document
ShapeTables + rows, joinedNested JSON documents
StrengthRelationships + ACIDVaried data, fast simple reads

2. Relational: PostgreSQL / MySQL

A relational database stores data in tables with a fixed schema (defined columns and types). You connect tables with joins and foreign keys. Its superpower is the ACID transaction: a group of writes that all succeed or all roll back — nothing half-done.

Pick relational when The data is structured and highly related, and correctness matters: orders, payments, money, inventory. If losing or duplicating a row means real money lost, you want ACID. This is the default choice for an ERP sync.

3. Document: MongoDB

A document database stores denormalized JSON-like documents. There is no fixed schema, so each record can differ. You often keep related data inside one document, so a common read is a single lookup with no join.

Pick document when The data is varied or changing shape, or you need simple high-scale reads of self-contained records: product catalogs with different attributes, activity logs, CMS content, user sessions.
The catch "Flexible schema" does not mean "no thinking". You still design documents around how you read them. And MongoDB has transactions now, but relational databases are still the safer home for money.

4. Indexing

An index is a second data structure that makes reads on a column fast — like the index at the back of a book. The trade: every write must also update the index, and it uses disk. So index the columns you filter or join on, and do not index everything.

One-line rule Indexes speed reads, and cost you writes and storage. Add them where your queries actually search.

Why an index is fast (the book analogy)

Without an index, to find WHERE email = 'gina@x.com' the database must check every row — a full table scan. A million rows = a million checks. An index is a separate sorted structure (a B-tree) that maps values → row locations, so the DB jumps to the match instead of scanning.

Like a book's index To find "photosynthesis" without the index at the back, you would read every page (full scan). With the index you look it up alphabetically → "page 142" → jump straight there. It works because the index is sorted. Same as a phone book: sorted by last name, so finding "Smith" is fast — but finding someone by their phone number would mean scanning every entry, because it is not sorted by number. That is why you index the column you search by.

      5. The N+1 query problem

      This one shows up in every backend interview. The N+1 query problem is when you run one query per item in a loop: fetch 100 orders (1 query), then loop and fetch each order's customer (100 more). That is 101 trips to the database for data you could have gotten in one.

      // BAD — N+1
const orders = await getOrders();          // 1 query
for (const o of orders) {
  o.customer = await getCustomer(o.userId); // N queries
}

// GOOD — one batched query
const ids = orders.map(o => o.userId);
const customers = await getCustomersIn(ids); // 1 query (IN / JOIN)

      Fixes: a SQL JOIN, a single IN (...) query, or a batching layer like DataLoader that collects the ids and fetches them together. Same idea in GraphQL resolvers.

        6. Normalization vs denormalization
        
  
        Normalization = store each fact once, join to read it. Less duplication, safe writes — the relational default. Denormalization = copy data together so a read is one lookup. Faster reads, but every copy must be kept in sync, or they drift. Relational leans normalized; document leans denormalized. Choose by whether you read more or write more.
        

  
        7. Transactions and consistency
        
  
        A transaction groups writes so they are all-or-nothing (the "A" in ACID). Moving stock from Shopify to the ERP, or writing an order and its payment, should be one transaction — you never want the order saved but the payment lost. Relational databases give you this by default; that is why money lives there.
        

  
        7½. ACID, letter by letter
        
  
        ACID is the set of four guarantees a relational transaction gives you. Classic interview question — know each letter with one concrete example.

    The happy path
    If both steps succeed, COMMIT saves them together (Durability — survives a crash), the balances still add up (Consistency), and other transactions never saw the half-done state (Isolation). Atomicity is the "all-or-nothing" that makes the rest possible.
  
            
  
            
    Isolation, one level deeper
    Isolation has levels — Read Committed → Repeatable Read → Serializable (higher = safer, slower). They prevent anomalies: a dirty read (reading another transaction's uncommitted data), a non-repeatable read (a row changes between two reads), and a phantom read (new rows appear between two reads). PostgreSQL defaults to Read Committed. Read Committed (the Postgres default) stops dirty reads but still allows non-repeatable and phantom reads — that is the trade for speed.
  
            

  
            8. Concrete example — the id mapping table
            
  
            Here is the real NSC problem. Shopify has its own product ids; the ERP has different ids. You need a mapping so a sync in either direction can find the match. This is small, highly related, and must be exact — a textbook relational table.
            
  
            CREATE TABLE product_id_map (
  id          BIGSERIAL   PRIMARY KEY,
  shopify_id  BIGINT      NOT NULL,
  erp_id      VARCHAR(64) NOT NULL,
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (shopify_id),   -- one Shopify product maps once
  UNIQUE (erp_id)        -- one ERP product maps once
);

-- fast lookups when the ERP pushes a change
CREATE INDEX idx_product_map_erp ON product_id_map (erp_id);
            
  
            Why relational fits perfectly: the UNIQUE constraints stop duplicate mappings (a data guarantee a document store won't enforce for you), the index makes lookups by erp_id fast, updated_at supports reconciliation, and updates run inside a transaction. You change this table over time with a migration.
            

  
            
    Say it like this (memorise the shape)
    
            "I choose by the shape of the data. Structured, highly related, money-critical data — orders, payments, id mappings — goes in a relational database like PostgreSQL for ACID transactions and constraints. Varied or fast-changing data with simple reads can go in a document store like MongoDB. I index the columns I filter or join on, watch for N+1 by batching with a JOIN or DataLoader, and keep money-critical writes inside transactions. For a Shopify-to-ERP id mapping, I use a relational table with unique constraints — it has to be exact."
