DevOps & Cloud: Docker, CI/CD, AWS

You don't need to be an SRE. You need to sound credible about how backend code ships and runs.

Your win today: speak confidently about Docker, CI/CD, and cloud — enough breadth to answer any "how do you deploy?" question without freezing.

Ties to your mission: the JD names Docker, CI/CD, and AWS. This is the area you're lightest on, so the goal is breadth, not depth — clear one-liners you can defend.

1. Docker: image vs container

Docker packages your app plus everything it needs (runtime, libraries, config) so it runs the same on your laptop, in CI, and in production. Two words you must not mix up:

  • Image = the built, read-only template. Like a class.
  • Container = a running instance of an image. Like an object.

A tiny Dockerfile for a Node backend is only a few lines:

FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
CMD ["node", "server.js"]
Why it matters (the one-liner) "It works on my machine" stops being an excuse. The image is the same everywhere, so dev, CI, and prod all run identical code and dependencies.

For local dev, docker-compose starts your app plus its dependencies (Postgres, Redis, a queue) with one command, so a new developer is running in minutes.

If you remember one thing Image = the built template. Container = a running copy of that image. Same image runs the same on laptop, CI, and prod.

2. CI/CD: the pipeline

CI/CD means every push runs an automated pipeline before code reaches users. A typical order:

push --> [ lint ] --> [ test ] --> [ build image ] --> [ deploy ] | | | | style/ unit & docker build to staging format integration + push to registry then prod
  • Lint — catch style and obvious mistakes.
  • Test — unit and integration tests must pass.
  • Build image — build the Docker image and push it to a registry.
  • Deploy — ship the image to an environment (staging, then production).

Why it matters: bugs are caught early and automatically, releases are small and repeatable, and shipping stops being manual and risky. Tools: GitHub Actions, GitLab CI, CircleCI.

If you remember one thing Every push runs lint → test → build → deploy automatically, so failures are caught before code reaches users.

3. The 12-factor essentials

The 12-factor app is a checklist for apps that run well in the cloud. You don't need all twelve — know these four:

FactorRuleWhy
ConfigKeep config and secrets in env vars, not codeSame image, different settings per environment; no secrets in git
StatelessProcesses hold no local stateAny instance can serve any request; enables horizontal scaling
LogsWrite logs to stdout as a streamThe platform collects and ships them; app doesn't manage files
DisposabilityStart fast, shut down cleanlySafe to kill, restart, and scale instances at any time
Stateless is the key idea If a process keeps no session or file state locally, you can run many copies behind a load balancer and add or remove them freely. Shared state goes in a database, a cache (Redis), or object storage.

4. AWS core services for a Node backend

Learn these five cold — they cover most Shopify-integration backends. One line each:

ServiceWhat it is
Fargate (ECS)Run Docker containers with no servers to manage
RDSManaged relational database (Postgres / MySQL)
S3Object storage for files, images, backups
SQSManaged message queue (see Lesson 12)
CloudWatchLogs, metrics, and alarms
Also know the name (don't over-study) EC2 = raw virtual servers you manage yourself. Lambda = run a function on demand, scales to zero, event-driven. Secrets Manager = store and rotate secrets (DB passwords, API keys). Recognise them, place them in one line — you don't need more.
If you remember one thing Containers on Fargate, data in RDS, files in S3, background work through SQS, logs and metrics in CloudWatch. One sentence, five services.

Why Fargate over EC2? Fargate means no server patching — AWS manages the underlying machines, so you just run the container.

5. Observability and safe deploys

Observability is how you understand a running system. Three pillars:

  • Logs — what happened (events, errors).
  • Metrics — numbers over time (request rate, error rate, latency).
  • Traces — follow one request across services to find the slow step.

Two safe deploy strategies:

  • Rolling — replace instances a few at a time, so the app stays up during the release.
  • Blue-green — run two full environments (old = blue, new = green), switch all traffic at once, and roll back instantly by switching back.

Why blue-green over rolling? Blue-green gives instant rollback (flip traffic back), but it costs about 2x infrastructure because you run two full environments.

If you remember one thing Observability = logs, metrics, traces. Safe deploys = rolling (replace a few at a time) or blue-green (switch all at once, roll back instantly).
