API Design & Architecture

You spent years calling other people's APIs. Now you design one that other people — and machines — must trust.

Your win today: confidently answer "How do you design a clean, scalable API?" — with real terms, in under two minutes.

Ties to your mission: at NSC you sit in the middle. You consume Shopify's GraphQL Admin API, and you expose your own API to an ERP and a frontend. Both sides judge you by the API you design.

1. Where your API lives

Picture the shape of the job. Data flows through your server. You are not just a client and not just a store — you are the bridge.

ERP / Frontend ───▶ YOUR API ───▶ Shopify Admin API (GraphQL) (they consume (you design (you consume your endpoints) this layer) their schema)

So you make two kinds of choices at once: how you call Shopify, and how you publish your own endpoints. Good design on both sides is what "scalable" really means here.

If you remember one thing Validate at the edge, use one error shape, and version so you never break clients. Every other rule in this lesson hangs off those three habits.

To keep it concrete, we carry one endpoint through the whole lesson: POST /v1/orders, which creates an order. Watch its version, its DTO, its 201, its error shape, and its idempotency key show up in each bucket below.

The rest of the lesson is three buckets. Each answers one job: shape the contract, guard the edge, then survive scale & change.

Bucket 1 — Shape the contract

REST vs GraphQL · status codes · DTOs · one error shape. This is the promise your API makes to every caller.

REST vs GraphQL — when to choose each

You already know REST vs GraphQL from Lesson 1. The senior move is picking on purpose, not by habit.

Pick REST whenPick GraphQL when
Simple resource CRUD (orders, products)Clients need many shapes of the same data
Easy caching by URL, wide toolingYou want one round trip for nested data
An ERP that expects plain endpointsA rich frontend that over-fetches on REST
The honest answer You consume Shopify as GraphQL (their choice). For the API you expose, REST is the safe default for an ERP integration — predictable, cacheable, easy to secure. So our carried example is a plain REST endpoint, POST /v1/orders. Offer GraphQL only if a client truly needs flexible queries.

Resources and status codes

Design URLs around nouns, not verbs: GET /v1/orders/123, not /getOrder. Let the HTTP method be the verb. Then return the right status code — clients branch on it. Our POST /v1/orders returns 201 Created on success.

CodeMeaningUse it for
200OKA read or update that worked
201CreatedA POST that made a new resource — e.g. POST /v1/orders

Validate input with DTOs

Never trust the request body. A DTO (Data Transfer Object) is a typed, validated shape for input. In NestJS you use a class plus class-validator and a validation pipe, so a bad field is rejected with a 400 before it ever reaches your business logic. This keeps garbage out of your database and your Shopify calls. Here is the DTO for our carried endpoint:

export class CreateOrderDto {          // the shape of POST /v1/orders
  @IsString()  customerId: string;
  @IsInt() @Min(1)  quantity: number;
  @IsString()  sku: string;
}
Say this "Validation lives at the edge. A DTO defines what a valid request looks like; the pipe enforces it. My services only ever see clean, typed data."

One error shape, everywhere

The fastest way to look junior is a different error format on every endpoint. Pick one JSON shape and return it for every failure. Include a machine code, a human message, per-field details, and a request id for tracing. When POST /v1/orders gets a bad body, it returns a 400 in exactly this shape:

{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request could not be validated.",
    "details": [
      { "field": "quantity", "issue": "must be at least 1" }
    ],
    "requestId": "req_01HZY8..."
  }
}

Now every client writes one error handler, and every log line has a requestId you can grep. That is scalability of people, not just servers.

Bucket 2 — Guard the edge

Validation, authentication vs authorization, idempotency, rate limiting. This is how you keep bad, unauthorised, and duplicate calls out — before they touch your logic.

Authentication vs authorization

Two words, often confused. Authentication = who are you? (prove identity, e.g. an API key or JWT). Authorization = what are you allowed to do? (check permissions/scopes). You always do both: first confirm the caller, then confirm the caller may perform this exact action. Before POST /v1/orders runs, you authenticate the caller, then check it holds the "orders:write" scope.

Idempotency for writes

Networks fail. A client sends POST /v1/orders, times out, and retries — did it create one order or two? Make writes idempotent. The client sends an idempotency key (a unique id). You store it; if you see the same key again, you return the first result instead of doing the work twice. Now a retry is safe. This is the same discipline that makes duplicate Shopify webhooks harmless.

Step through the retry on our carried endpoint:

POST /v1/orders Idempotency-Key: key_abc │ ▼ server creates order #5001, stores key_abc → order #5001, returns 201 │ ✗ the 201 response is lost — client's network times out │ ▼ client RETRIES the same POST with the SAME Idempotency-Key: key_abc │ ▼ server sees key_abc already used → returns the STORED 201 (order #5001) │ RESULT: one order, not two. The retry is safe.

Rate-limit your own API

Shopify limits you; you should limit your callers too. A shared store like Redis counts requests per client and returns 429 Too Many Requests with a Retry-After header when they go over. This protects your server and, indirectly, protects the Shopify quota you all share.

Bucket 3 — Survive scale & change

Versioning, pagination, OpenAPI. This is how the API grows and changes without breaking anyone who already depends on it.

Versioning

Once someone depends on your API, you cannot change it freely. Put a version in the path (/v1/… — that is the v1 in POST /v1/orders) or a header. Add fields freely; never change or remove one inside a version. This is exactly how Shopify ships dated API versions so your app does not break overnight.

Pagination — cursor vs offset

Offset (?page=5)Cursor (?after=abc)
HowSkip N rows, take M"Give me rows after this marker"
Big listsSlow; skips/repeats on insertsStable and fast
Used bySmall admin tablesShopify, and you should too
Why cursors win With offset, if a row is inserted while you page, you can see a row twice or miss one. A cursor points at a stable position, so paging a changing list stays correct. Shopify's GraphQL uses cursor pagination for this reason.

Document with OpenAPI

Write the contract as an OpenAPI spec. NestJS can generate it from your DTOs and decorators — including our CreateOrderDto. It gives you live docs (Swagger UI), typed client SDKs, and a shared source of truth so the ERP team and frontend team stop guessing.

Say it like this (memorise the shape)

"I design resource-based endpoints with correct status codes and one consistent error shape. Input is validated at the edge with DTOs. I version the API so I never break existing clients, paginate with cursors like Shopify does, and make writes idempotent with an idempotency key so retries are safe. Auth is two layers — authenticate the caller, then authorize the action — and I rate-limit callers with a 429. I document everything with OpenAPI."
