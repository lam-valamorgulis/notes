Shopify Functions

Custom backend logic that runs inside Shopify's checkout — the modern replacement for Shopify Scripts. This is how you change payment, delivery, and discount behavior at the payment step.

Your win: answer "What are Shopify Functions, and how would you hide a payment method for some orders?"

Ties to your mission: this is the "behavior" door from L23, and it is the heart of the "checkout/payment is painful" problem the client named. Builds on L1 (GraphQL).

1. The one idea: your code runs inside Shopify's checkout

A Shopify Function is a small piece of your own logic that Shopify runs on its servers at key moments — like when it calculates discounts or shows payment options. You do not host it; Shopify runs it, compiled to WebAssembly (Wasm), and you write it in Rust or JavaScript. Because it runs inside the buying flow, it must be fast — a slow function can block a customer's purchase.

The input → logic → operations picture Every Function works the same way: Shopify sends your code an input (a GraphQL query result — the cart, the customer, the options). Your code runs and returns a list of operations (do this: hide that payment method, apply this discount). You never mutate Shopify's data directly — you return instructions, and Shopify applies them.

2. Functions replaced Scripts (say the dates)

The old tool was Shopify Scripts (Ruby, Plus-only). It was sunset on June 30, 2026 — any still-published Scripts were switched off. So today, Functions are the only way to do this kind of checkout logic. (The old Script Editor stays read-only until July 30, 2026, just to look up old logic.)

3. The Function APIs (map from old Scripts)

Function APIWhat it doesOld Script
DiscountsCreate custom discounts on products or the cartLine item scripts
Cart TransformBundle, merge, or modify cart line itemsLine item scripts
Cart & Checkout ValidationBlock checkout under conditions (e.g. over a limit)Line item scripts
Delivery CustomizationHide, rename, reorder delivery options (max 25/store)Shipping scripts
Payment CustomizationHide, rename, reorder payment methods (max 25/store)Payment scripts

There are more (fulfillment constraints, location rules, pickup points), but these five cover almost every real request.

4. Worked example — hide "Cash on Delivery" over $500

The Function runs at the target cart.payment-methods.transform.run. It reads the cart total and returns a paymentMethodHide operation for the payment method you do not want shown. In JavaScript it looks like this (simplified):

// Payment Customization Function — target: cart.payment-methods.transform.run
export function cartPaymentMethodsTransformRun(input) {
  const total = parseFloat(input.cart.cost.totalAmount.amount);
  if (total < 500) {
    return { operations: [] };          // nothing to change
  }
  // Find the "Cash on Delivery" option Shopify passed us
  const cod = input.paymentMethods.find(
    (m) => m.name.includes("Cash on Delivery")
  );
  if (!cod) return { operations: [] };

  return {
    operations: [
      { paymentMethodHide: { paymentMethodId: cod.id } }   // instruction, not a mutation
    ],
  };
}

You also write an input query (GraphQL) that tells Shopify exactly what data to pass in — here, the cart total and the payment methods. Keep the query small: less input means a faster function.

5. Availability — where Plus matters

SetupWho can use it
A public app (from the App Store) that contains FunctionsAny plan
A custom app that contains Function APIsShopify Plus only

So if the client is on Plus and wants a bespoke payment rule, you build a custom app with a Payment Customization Function. On a lower plan, they must use a public app instead. This connects straight to L25.

The trap: a slow or heavy Function Functions run in the live purchase path. If yours is slow, calls a big external API, or asks for huge input data, it hurts checkout for real customers. Keep the input query minimal, keep the logic simple, and do heavy work elsewhere (a webhook worker — see L2), not inside the Function.
