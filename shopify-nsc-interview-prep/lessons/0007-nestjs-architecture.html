NestJS Architecture

The framework most Node teams reach for. Learn the shape once and you can read any Nest codebase on day one.

Your win today: confidently answer "Why NestJS, and how is a Nest app structured?" — out loud, naming Module, Controller, Service, and dependency injection.

Ties to your mission: many Node + Shopify teams (likely NSC) build on NestJS. Knowing its structure and request lifecycle shows you can drop into their codebase fast.

1. What NestJS is

NestJS is an opinionated TypeScript framework that sits on top of Express (or Fastify). Express gives you routing and not much else, so every team invents its own folder layout. Nest gives you one agreed structure — modules, controllers, providers, decorators — plus built-in dependency injection. Everyone's Nest app looks the same, which is exactly what a team wants.

If you remember one thing Express is a library; Nest is a framework. Nest trades some freedom for structure, testability, and a shared vocabulary across the whole team.

2. Why teams use it

  • Structure — the same layout in every feature, so new engineers move fast.
  • Testability — dependency injection lets you swap real services for fakes in tests.
  • Batteries included — validation, config, guards, interceptors, and both REST and GraphQL come built in.

4. Dependency injection

A controller does not build its own service with new. It just asks for one in its constructor, and the framework supplies it. That is dependency injection. The payoff is testing: in a unit test you inject a fake Shopify service, so the test never makes a real API call.

// orders.module.ts — the module wires a controller + service
import { Module } from '@nestjs/common';
import { OrdersController } from './orders.controller';
import { ShopifyOrdersService } from './shopify-orders.service';

@Module({
  controllers: [OrdersController],
  providers:   [ShopifyOrdersService],   // injectable
})
export class OrdersModule {}

// orders.controller.ts — the service is injected, not created
@Controller('orders')
export class OrdersController {
  constructor(private readonly orders: ShopifyOrdersService) {}

  @Post('sync')
  sync(@Body() dto: SyncOrdersDto) {
    return this.orders.sync(dto);   // controller stays thin
  }
}

4½. Dependency injection, deeper

The rule: a class never builds its own dependencies with new. It declares what it needs in the constructor, and a container (Nest's injector) creates those dependencies and hands them in. The class just says "I need a ShopifyService" — it does not care how one is built. (This flip — the framework, not your class, decides how dependencies are made — is called inversion of control.)

Analogy: welded in vs plugged in A class that does new ShopifyService() inside itself is like a car with the engine welded in — you cannot swap it, and you cannot test the car with a dummy engine. DI plugs the engine in from outside through the constructor — so you drop in the real engine in production, or a test dummy in a unit test. Same car, swappable parts.

Without DI vs with DI

❌ Without DI (welded / coupled)✅ With DI (Nest)
class OrdersService {
  private shopify =
    new ShopifyService(); // welded in
  // can't swap → hard to test
}
 
@Injectable()
class OrdersService {
  constructor(
    private shopify: ShopifyService,
  ) {}   // handed in → mock in tests
}

    Three pieces that make DI work in Nest
    1) @Injectable() marks a class as providable. 2) the module's providers: [...] registers it. 3) a constructor parameter asks for it by type. The container matches the type and injects a single shared instance (a singleton by default). The exception: a provider marked request-scoped (@Injectable({ scope: Scope.REQUEST })) is built fresh for each request instead of shared — use it only when you truly need per-request state, since it costs some performance. In a test you override step 2 with { provide: ShopifyService, useValue: mockShopify } — same slot, fake engine.
  
      

  
      5. The request lifecycle (say it in order)
      
  
      When a request comes in, Nest runs it through a fixed pipeline. Interviewers love this list in order (see Guard / Pipe / Interceptor / Filter):
      
  
        request
     |
     v
  [ middleware ]        raw request setup (logging, body)
     |
     v
  [ guard ]            auth: allow or reject
     |
     v
  [ interceptor pre ]   before: start timer, transform
     |
     v
  [ pipe ]             validate + transform the input (DTO)
     |
     v
  [ ROUTE HANDLER ]     your controller method runs
     |
     v
  [ interceptor post ]  after: shape the response
     |
     v
  [ exception filter ]  only if something threw -> error shape
     |
     v
  response
      
  
      
    Memory hook
    M-G-I-P → handler → I-F. Middleware, Guard, Interceptor, Pipe, then the handler, then Interceptor and Filter on the way out.

      6. DTOs, validation, and config
      
  
      A DTO (Data Transfer Object) is a class that describes the shape of an incoming request body. Add class-validator decorators, turn on the global ValidationPipe, and Nest rejects bad input before it reaches your handler — no manual checking.
      
  
      export class SyncOrdersDto {
  @IsString()  shopDomain: string;
  @IsInt()     since: number;
}
      
  
      For environment settings (API keys, the Shopify shop domain, database URL) use ConfigModule: it loads .env once and injects a typed config service anywhere you need it — no scattered process.env reads.
      

  
      7. One line on testing
      
  
      Because everything is injected, a Nest test builds a small testing module and provides mock versions of the services. You test your controller and service logic with zero real network or database calls — fast and reliable.

      // orders.service.ts — holds the business logic
@Injectable()
export class OrdersService {
  create(dto: CreateOrderDto) {
    // real work lives here
    return { id: 1, ...dto };
  }
}

// orders.controller.ts — thin: no logic, just delegates
@Controller('orders')
export class OrdersController {
  constructor(private readonly orders: OrdersService) {}

  @Post()
  create(@Body() dto: CreateOrderDto) {
    return this.orders.create(dto);
  }
}

// orders.module.ts — wires the two together
@Module({
  controllers: [OrdersController],
  providers:   [OrdersService],
})
export class OrdersModule {}
