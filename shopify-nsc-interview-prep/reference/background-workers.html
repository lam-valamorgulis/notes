Background Workers

How a Node backend does slow, heavy, or deferred work without blocking web requests — the backbone of webhooks, bulk processing, and the ERP sync.

The core idea: the web server does only the fast part of a request and hands the slow work to a separate worker process via a durable queue.

The problem it solves

A Node web server's one job is to answer HTTP requests fast. But much real work is slow or heavy: processing a webhook (call the ERP + DB), parsing a giant bulk-operations JSONL file, sending emails, generating reports, the nightly sync.

  • Do it inside the HTTP handler → the request hangs; a Shopify webhook times out at 5s.
  • Heavy work also blocks the single-threaded event loop, so other requests stall too.

A background worker moves that work out of the request/response cycle.

The architecture: producer → queue → worker

Web app (producer) Worker (consumer) ┌─────────────────┐ enqueue job ┌──────────────┐ ┌───────────────┐ │ webhook handler │ ─────────────► │ QUEUE │ ► │ worker.js │ ► DB / ERP │ returns 200 fast │ │ (Redis/SQS) │ │ (separate proc)│ └─────────────────┘ └──────────────┘ └───────────────┘
  1. Producer — the web app. Does the fast bit (verify, return 200), then puts a job on a queue.
  2. Queue — a durable store between them (Redis via BullMQ, or SQS/RabbitMQ). Durable = jobs survive a crash.
  3. Worker — a separate process (node worker.js, own container) that pulls jobs and does the slow work.

Code (BullMQ — common Node choice)

// ---- producer: in the web app, after verifying the webhook & sending 200 ----
const { Queue } = require('bullmq');
const orderQueue = new Queue('order-sync', { connection: { host: 'localhost', port: 6379 } });

await orderQueue.add('process-order',
  { webhookId, payload },                                   // job data
  { attempts: 5, backoff: { type: 'exponential', delay: 1000 } });  // retry 1s,2s,4s...

// ---- worker.js: a SEPARATE process you run on its own ----
const { Worker } = require('bullmq');
new Worker('order-sync', async (job) => {
  await processOrderEvent(job.data);                        // transform + idempotent ERP upsert
}, { connection: { host: 'localhost', port: 6379 }, concurrency: 5 });  // 5 at a time
// jobs that fail all 5 attempts → the "failed" set = your dead-letter queue

Production must-haves

  • Retries with backoff — transient failures (ERP briefly down) retry with growing delays.
  • Dead-letter queue — jobs that keep failing go there for inspection, not lost.
  • Idempotency — queues are at-least-once, so the same job can run twice. Dedupe / upsert.
  • Concurrency cap — process N at a time so you don't overload the ERP or DB.
  • Independent scaling — add worker processes when the queue backs up, without touching the API.

Two flavors

TypeTriggered byExample
Queue / job workeran event (a job is added)process a webhook, send an email, parse a bulk file
Scheduled / cron workera clockhourly reconciliation, nightly bulk export
Two traps to avoid (1) A setTimeout inside the web process is NOT a real background worker — that work is lost on restart and still shares the event loop. Use a durable queue + separate process. (2) A queue worker is for I/O-heavy, deferrable work. For CPU-heavy work (parsing, crypto, image math) use Node worker_threads or a separate service, so the event loop never blocks.
Say it like this

"I keep the web server fast by doing only the quick part in the request — verify and return 200 — then push a job to a durable queue. A separate worker process consumes it and does the slow work: calling the ERP, parsing bulk files, sending email. It retries with backoff, sends poison jobs to a DLQ, processes idempotently because queues are at-least-once, and scales independently of the API. For CPU-heavy work I'd use worker threads so the event loop never blocks."
