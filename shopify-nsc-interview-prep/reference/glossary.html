Glossary

Shopify

Admin API
The server-side API to manage a store: products, orders, customers, inventory, fulfillment. GraphQL is the primary version; REST is now legacy. Your backend app uses this.
Storefront API
A customer-facing GraphQL API to build shopping experiences (headless sites, custom carts): read products/collections, create carts, start checkout.
Access token
The credential your app uses to call the Admin API for a shop. Offline = long-lived, one per shop, for background work (webhooks, scheduled syncs, bulk jobs) — the default for integrations. Online = tied to a logged-in staff user, short-lived, carries the user's identity (associated_user) and that user's permissions — use it for user-triggered actions in the admin where "who did this?" and least-privilege matter. Memory hook: online = a human is watching; offline = a robot is working. Not the same as the session token (browser→backend) or the client secret (signs/verifies).
Session token
A short-lived JWT that proves a request came from your embedded app inside the Shopify admin. You exchange it for an access token.
Token exchange
The current recommended way to get an access token: swap a session token for an access token with no redirects (part of "Shopify managed installation").
Authorization code grant
The legacy OAuth redirect flow to install an app and get a token. Still required for standalone (non-embedded) apps.
Access scopes
Permissions the app requests, e.g. read_products, write_orders. Configured via Shopify CLI.
Webhook
An HTTP POST Shopify sends your server when an event happens (order created, product updated). You must verify HMAC, respond 200 fast, and be idempotent.
HMAC verification
Proving a webhook is really from Shopify: compute HMAC-SHA256 of the raw body with your app secret, compare to the X-Shopify-Hmac-SHA256 header.
Calculated query cost
The GraphQL rate-limit model: each requested field costs points. You have a 1000-point bucket that refills 50 points/second (standard). Response includes extensions.cost.throttleStatus.
Leaky bucket
The rate-limit algorithm behind Shopify's APIs: requests draw from a bucket that refills at a steady rate; overflow is throttled.
Bulk operations
Async Shopify GraphQL jobs to read or write very large datasets without hitting per-request rate limits. Result delivered as a file.
Metafields / Metaobjects
Custom structured data attached to Shopify resources (metafields) or standalone custom records (metaobjects).
Shopify Plus
The enterprise tier: higher limits, checkout customization (Functions), Flow automation, B2B, multiple stores.
Shopify Functions
Server-side customizations (discounts, checkout, shipping) that run on Shopify's own infrastructure.
Embedded app / App Bridge
An app rendered inside the Shopify admin. App Bridge is Shopify's JS library that provides session tokens and navigation for it.

Node.js / Backend

Process
A running program with its own memory. Your Node app is a process. Run several (often one per CPU core) to use the whole machine — see cluster / horizontal scaling.
Thread
A single sequence of execution inside a process; it runs instructions one after another. A process has one or many, and threads in the same process share memory (which risks race conditions). Node runs your JavaScript on one thread.
CPU core
A core runs one thread at a time. More cores = more threads truly in parallel. One process on one thread can't use extra cores — hence worker threads or multiple processes.
Event loop
The single-threaded loop that runs your JS and schedules async callbacks. It is why Node handles many connections without a thread per request.
Non-blocking I/O
I/O calls return immediately; a callback/promise runs when the data is ready, so the one thread is never stuck waiting.
Async / await & Promises
A Promise is an object for a future value. async/await is syntax that makes promise code read top-to-bottom.
process.nextTick / queueMicrotask / setImmediate
Three ways to defer a callback, by priority. process.nextTick = run before the event loop continues (highest priority; can starve the loop if overused). queueMicrotask = run on the Promise microtask queue (after nextTick, before timers). setImmediate = run on the next loop iteration, yielding to I/O first (safest for "soon but don't block"). Order each turn: sync → nextTick → microtasks/Promises → one timer/I/O.
Worker threads
Extra threads for CPU-heavy work (image processing, crypto) so the main event loop stays responsive.
Cluster / horizontal scaling
Running many Node processes or instances behind a load balancer to use all CPU cores and handle more load.
NestJS
An opinionated Node framework built on Express/Fastify: modules, providers, decorators, and dependency injection — structure that scales for teams.
Dependency injection (DI)
The framework supplies a class's dependencies instead of the class creating them. Makes code testable (you can inject fakes).
Module / Service / Controller
Nest building blocks: a module groups a feature; a controller handles HTTP routes; a service (provider) holds business logic.
Guard / Pipe / Interceptor / Filter
Nest request-lifecycle hooks: guard = auth check, pipe = validate/transform input, interceptor = wrap responses/logging, filter = handle errors.
REST vs GraphQL
REST exposes many resource endpoints; GraphQL exposes one typed endpoint where the client asks for exactly the fields it needs.

System Design

Idempotency
An operation that has the same effect whether it runs once or many times. Essential for safe retries and duplicate webhooks.
Idempotency key
A unique id (usually a UUID) sent with a request so the server processes it only once, even if it arrives twice. Main job: make a client retry a POST safely when the outcome was uncertain (timeout / lost response / double-click) — the server remembers the key and returns the first result instead of redoing the work (no double charge or double order). Two sides of one idea: a client sends a key on outbound POSTs; a server dedupes on an incoming id like Shopify's X-Shopify-Webhook-Id. Keys usually expire (e.g. 24h).
Message queue
A buffer between a producer and a consumer so work is done asynchronously and survives spikes. Examples: SQS, RabbitMQ.
Event-driven architecture
Services talk by emitting and consuming events instead of calling each other directly. Looser coupling, easier scaling.
Kafka
A distributed log for high-throughput event streaming. Consumers read at their own pace; events are retained so you can replay.
RabbitMQ
A classic message broker: queues, routing keys, acknowledgements. Great for task/work queues.
Amazon SQS
A fully managed queue. Standard = high throughput, at-least-once. FIFO = ordered, exactly-once processing.
Dead-letter queue (DLQ)
Where a message goes after it fails processing too many times, so it can be inspected instead of lost.
Retry with backoff
Re-attempting failed work with growing delays (e.g. 1s, 2s, 4s) to avoid hammering a struggling service.
Caching (Redis)
Storing fetched/computed data in fast memory to cut latency and reduce load on the database or an external API.
Load balancer
Distributes incoming traffic across many instances of a service.
Horizontal vs vertical scaling
Horizontal = add more machines. Vertical = make one machine bigger. Horizontal is how you scale stateless services.
CAP theorem / eventual consistency
During a network partition you must trade consistency vs availability. Eventual consistency = replicas converge over time, not instantly.
Reconciliation job
A scheduled sync that re-reads the source of truth (e.g. Shopify) to fix any events that were missed or processed wrong.
ERP (Enterprise Resource Planning)
The system that runs a business's internal operations — inventory, orders, purchasing, finance/accounting, warehouse, fulfillment. The "operations brain". Examples: SAP, Oracle NetSuite, MS Dynamics, Odoo. A common Shopify integration target.
CRM (Customer Relationship Management)
The system for managing customers and sales relationships — contacts, leads, deals, support, marketing history. The "relationship brain". Examples: Salesforce, HubSpot, Zoho.
Source of truth
For each data type, the one system that is authoritative; the others follow it. In a Shopify sync, inventory is usually mastered by the ERP, the order is created in Shopify then pushed to the ERP, and the customer often lives in the CRM. Deciding this up front stops systems from overwriting each other.

Data / DevOps

ACID
Atomicity, Consistency, Isolation, Durability — the safety guarantees of relational database transactions.
SQL (PostgreSQL / MySQL)
Relational databases: fixed schema, joins, transactions. Best for structured, highly related data (orders, payments).
NoSQL (MongoDB)
Document databases: flexible schema, denormalized documents. Best for varied or rapidly changing data and simple high-scale reads.
Index
A data structure that makes reads on a column fast — at the cost of slightly slower writes and more storage.
N+1 query
Accidentally running one query per item in a loop. Fix with a join, an IN query, or batching (DataLoader).
Migration
A versioned, repeatable change to the database schema, checked into source control.
Docker (container vs image)
Packages an app plus its dependencies so it runs the same everywhere. An image is the built template; a container is a running instance of it.
CI/CD
Continuous Integration = auto build + test on every change. Continuous Delivery/Deployment = auto ship to an environment.
Env vars / secrets
Configuration and credentials kept out of code and injected at runtime (12-factor config).
Observability
Logs, metrics, and traces that let you understand and debug a running system in production.

Project & Delivery

Agile
A way of working: deliver software in small increments, get feedback, and adjust — instead of one big batch at the end.
Scrum
An Agile framework built on fixed sprints, with roles (product owner, scrum master, developers) and events (planning, standup, review, retrospective).
Kanban
An Agile method of continuous flow: a board (To do → In progress → Done) with WIP limits; you pull the next task when free. Good for support/ongoing work.
Sprint
A short, fixed time-box (usually 1–2 weeks) in which a Scrum team delivers a working increment.
Daily standup
A short daily sync: what I did, what I will do next, and what is blocking me. Not a deep planning meeting.
Backlog
The ordered list of work still to do. The product owner prioritises it; the team pulls from the top.
Story points
A relative size estimate (not hours) for a task, based on effort and uncertainty. Used to plan how much fits in a sprint.
WIP limit
A cap on how many tasks are "in progress" at once, so the team finishes work instead of starting too much.
Retrospective
A short team meeting at the end of a sprint to reflect: what to keep, what to improve.
MVP (minimum viable product)
The smallest version that delivers real value, shipped early to learn from real use before building more.
Spike
A short, time-boxed piece of research to reduce uncertainty before you commit to an estimate or approach.
