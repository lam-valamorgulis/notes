Webhook → ERP Worker

The three code pieces that make up the webhook side of a Shopify↔ERP sync: verify (Express & NestJS), then transform, then write idempotently.

Use this for: the coding-flavoured parts of the system-design answer. You won't write code live, but being able to describe exactly these steps is what makes the design sound real.
Shopify event ─► [1] verify HMAC (raw body) ─► return 200 fast ─► queue ─► [3] worker: [transform] ─► ERP (idempotent, mapping table)
Two directions of auth — don't confuse them Inbound (Shopify → you): receiving the webhook is verified by HMAC (your client secret). No access token is used to receive it. Outbound (you → Admin API): when the worker calls Shopify back — fetch the full record, update inventory, push to the ERP — it authenticates with the shop's offline access token. It must be offline because webhooks fire with no user logged in and are processed later on a worker; an online token would fail (user-bound + short-lived).

1. Verify — Express (raw body)

Trap: express.json() parses and discards the raw bytes, but HMAC needs the exact bytes. Grab the raw Buffer for the webhook route.

const express = require('express');
const crypto = require('crypto');
const app = express();

app.post(
  '/webhooks/shopify',
  express.raw({ type: 'application/json' }),   // req.body is a raw Buffer, not parsed JSON
  (req, res) => {
    const hmacHeader = req.get('X-Shopify-Hmac-SHA256');

    const digest = crypto
      .createHmac('sha256', process.env.SHOPIFY_API_SECRET)  // the client secret
      .update(req.body)                                       // the RAW bytes
      .digest('base64');

    const valid =
      hmacHeader &&
      crypto.timingSafeEqual(Buffer.from(digest), Buffer.from(hmacHeader));
    if (!valid) return res.status(401).send('invalid hmac');

    // Verified → ACK FAST, process later
    const event = JSON.parse(req.body.toString('utf8'));
    queue.enqueue({
      topic: req.get('X-Shopify-Topic'),
      webhookId: req.get('X-Shopify-Webhook-Id'),
      payload: event,
    });
    res.sendStatus(200);   // return 200 in < 5s; the worker does the real work
  }
);
Trap A global app.use(express.json()) eats the raw body before your route sees it, so HMAC always fails. Scope express.raw to the webhook route, or capture the raw body via the verify callback of express.json.

2. Verify — NestJS guard

Same logic, but as a reusable guard that runs before the handler.

Step A — enable raw body (main.ts)

const app = await NestFactory.create(AppModule, { rawBody: true }); // exposes req.rawBody (Buffer)

Step B — the guard

@Injectable()
export class ShopifyWebhookGuard implements CanActivate {
  canActivate(ctx: ExecutionContext): boolean {
    const req = ctx.switchToHttp().getRequest();
    const hmacHeader = req.headers['x-shopify-hmac-sha256'] as string;
    const rawBody: Buffer = req.rawBody;               // available because rawBody: true
    if (!hmacHeader || !rawBody) throw new UnauthorizedException();

    const digest = crypto
      .createHmac('sha256', process.env.SHOPIFY_API_SECRET)
      .update(rawBody)
      .digest('base64');

    const ok = crypto.timingSafeEqual(Buffer.from(digest), Buffer.from(hmacHeader));
    if (!ok) throw new UnauthorizedException('invalid hmac');
    return true;
  }
}

Step C — attach it

@Post('webhooks/shopify')
@UseGuards(ShopifyWebhookGuard)
handle(@Req() req) {
  const event = JSON.parse(req.rawBody.toString('utf8'));
  this.queue.enqueue({
    topic: req.headers['x-shopify-topic'],
    webhookId: req.headers['x-shopify-webhook-id'],
    payload: event,
  });
  // returning normally = 200
}
Why a guard Verification is a cross-cutting concern. As a guard it lives in one testable class and protects every webhook route — instead of being copy-pasted into each handler.

3. Transform + worker (idempotent write)

Split into a pure transform (easy to unit-test) and the worker that decides create-vs-update using the mapping table.

Pure transform — Shopify order → ERP shape

// PURE: no I/O, so it's trivial to unit test with a fixture.
// Order WEBHOOK payloads are snake_case (REST-style); GraphQL/bulk are camelCase + MoneyBag.
function toErpOrder(o) {
  return {
    externalId: String(o.id),          // Shopify order id — the link back
    orderNumber: o.name,               // "#1001"
    placedAt: o.created_at,
    currency: o.currency,
    total: Number(o.total_price),      // Shopify sends money as strings — cast carefully
    customer: {
      email: o.email,
      firstName: o.customer?.first_name ?? null,   // may be missing → default
      lastName: o.customer?.last_name ?? null,
    },
    lines: (o.line_items ?? []).map(li => ({
      sku: li.sku,
      name: li.name,
      quantity: li.quantity,
      unitPrice: Number(li.price),
    })),
  };
}

Worker — runs off the queue, must be idempotent

async function processOrderEvent(job) {
  const { payload, webhookId } = job;

  // 1. Idempotency guard — dedupe on the webhook id
  if (await alreadyProcessed(webhookId)) return;

  // 2. Transform
  const erpOrder = toErpOrder(payload);

  // 3. Mapping table decides CREATE vs UPDATE (shopify_id <-> erp_id)
  const mapping = await db.mappings.findByShopifyId(payload.id);

  // 4. Write to the ERP — upsert / idempotency key so a retry never duplicates
  if (mapping) {
    await erp.updateOrder(mapping.erpId, erpOrder);
  } else {
    const created = await erp.createOrder(erpOrder, { idempotencyKey: String(payload.id) });
    await db.mappings.save({ shopifyId: payload.id, erpId: created.id });
  }

  // 5. Record success (so step 1 skips a duplicate next time)
  await markProcessed(webhookId);
  // If any step throws, DON'T swallow it — let the queue retry with backoff, then DLQ.
}
The mapping table is the backbone shopify_id ↔ erp_id lets the worker tell "new → create" from "seen → update", so replaying an event updates one record instead of creating duplicates. Dedupe on webhookId catches exact duplicate deliveries; the upsert-by-shopify_id catches events that arrive via a different path (e.g. the reconciliation job).

The mapping table schema

The table the worker's db.mappings calls hit. The two UNIQUE rules make the database itself block duplicates — idempotency enforced at the storage layer.

CREATE TABLE sync_mappings (
  id                 BIGSERIAL   PRIMARY KEY,
  shop_domain        TEXT        NOT NULL,           -- multi-tenant: one row per shop
  entity_type        TEXT        NOT NULL,           -- 'order' | 'product' | 'customer'
  shopify_id         TEXT        NOT NULL,           -- 'gid://shopify/Order/1001'
  erp_id             TEXT        NOT NULL,           -- 'ERP-55'
  shopify_updated_at TIMESTAMPTZ,                    -- last-write-wins / stale-write guard
  version            INTEGER     NOT NULL DEFAULT 0, -- conflict detection (two-way sync)
  sync_status        TEXT        NOT NULL DEFAULT 'synced', -- 'synced' | 'pending' | 'error'
  last_error         TEXT,
  last_synced_at     TIMESTAMPTZ,
  created_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at         TIMESTAMPTZ NOT NULL DEFAULT now(),

  UNIQUE (shop_domain, entity_type, shopify_id),   -- one Shopify record ↔ one row
  UNIQUE (shop_domain, entity_type, erp_id)        -- ...unique in BOTH directions
);

CREATE INDEX idx_map_shopify ON sync_mappings (shop_domain, entity_type, shopify_id);
CREATE INDEX idx_map_erp     ON sync_mappings (shop_domain, entity_type, erp_id);
CREATE INDEX idx_map_status  ON sync_mappings (sync_status) WHERE sync_status <> 'synced';

Idempotent upsert — the same event twice yields one row, not two:

INSERT INTO sync_mappings (shop_domain, entity_type, shopify_id, erp_id, shopify_updated_at)
VALUES ($1, 'order', $2, $3, $4)
ON CONFLICT (shop_domain, entity_type, shopify_id)
DO UPDATE SET erp_id = EXCLUDED.erp_id,
              shopify_updated_at = EXCLUDED.shopify_updated_at,
              updated_at = now();
Why the columns earn their place shop_domain = multi-tenant scoping · entity_type = one table for all record types · shopify_updated_at / version = last-write-wins + conflict detection · sync_status / last_error = retry/DLQ dashboard · the two UNIQUE keys = idempotency enforced by the DB · indexes = fast per-webhook lookups. (In Prisma: a model SyncMapping with @@unique([shopDomain, entityType, shopifyId]).)

The reliability trio

Three concepts turn an at-least-once pipeline into one that is exactly-once in effect.

ProblemAnswerHow
Same webhook arrives twiceIdempotencyDedupe on X-Shopify-Webhook-Id + upsert by the Shopify id (never a blind INSERT).
Which ERP record is this?Mapping tableA table in your DB: shopify_id ↔ erp_id. Found → update; not found → create + save mapping.
Write fails after all retriesDead-letter queueMove the poison message to a DLQ: safe, not lost, doesn't block the queue. Alert → inspect → fix → replay.
Retries vs DLQ — the deciding question is "is it worth trying again?" Transient failures (ERP briefly down, timeout) → retries with backoff usually fix them. Permanent / poison failures (malformed data, a bug) → retries never help → send to the DLQ, so one bad message can't loop forever or block everything behind it.
Say it like this

"Duplicates → idempotency: dedupe on the webhook id and upsert by the Shopify id. 'Which ERP record?' → a mapping table (shopify_id ↔ erp_id) that also decides create vs update. A write that keeps failing after backoff → a dead-letter queue: safe, not lost, not blocking, then alerted and replayed."

Say-it checklist

  • Hash the raw body with the client secret; compare to X-Shopify-Hmac-SHA256; reject on mismatch.
  • Return 200 in under 5 seconds, then process on a queue.
  • Worker is idempotent: dedupe on X-Shopify-Webhook-Id.
  • Transform is a pure function (unit-tested); the write is an upsert keyed by the Shopify id.
  • On failure, let it throw → queue retries with backoff → DLQ.
