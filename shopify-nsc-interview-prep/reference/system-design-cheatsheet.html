System Design Cheat Sheet

A calm framework, the building blocks, the delivery guarantees, and the one diagram you must be able to draw: Shopify syncing to an ERP.

How to use this: the interviewer wants to hear your process, not a memorized answer. Follow the 7 steps out loud. Narrate every choice as a trade-off.

1. The 7-step framework (say each step out loud)

  1. Clarify. Ask about scope, scale, read/write mix, and what "done" means. Never start drawing first.
  2. API. Define the few key endpoints or events. This pins down the contract.
  3. Data. Pick the data model and store(s). Name the source of truth.
  4. Components. Draw the boxes: clients, load balancer, services, queue, DB, cache.
  5. Scale. Show how it grows: stateless services, replicas, sharding, CDN.
  6. Bottlenecks. Name what breaks first (hot DB, slow external API, queue backlog) and how you watch for it.
  7. Trade-offs. State what you chose and what you gave up. This is what makes you sound senior.
Tip Spend real time on step 1. A minute of good clarifying questions saves you from designing the wrong thing for ten minutes.

2. Building blocks — one line on "when"

BlockWhat it doesWhen to reach for it
Load balancerSpreads traffic across instancesAny time you run more than one instance
Stateless serviceHolds no local state; any instance serves any requestSo you can scale horizontally — just add more

DB shardingSplits data across machines by keyOne DB can no longer hold the write load or size
CDNServes static assets from the edgeImages, JS/CSS, anything cacheable close to the user

3. Delivery guarantees

GuaranteeMeaningRisk
At-most-onceDeliver 0 or 1 timeCan lose messages
At-least-onceDeliver 1 or more timesCan duplicate messages
Exactly-onceDeliver exactly 1 timeHard and costly to guarantee end-to-end
The default answer

"I use at-least-once delivery plus idempotent consumers. That gives me exactly-once effect without the cost of true exactly-once delivery. Duplicates are safe because processing the same event twice changes nothing."

4. The diagram: Shopify ↔ ERP sync

Draw this from memory. It answers "design a system that keeps our ERP in sync with Shopify."

┌──────────────────────────┐ Shopify events ───────▶│ Ingest / webhook endpoint│ (order, product, │ 1. verify HMAC (raw body)│ inventory) │ 2. return 200 in < 5s │ └────────────┬─────────────┘ │ enqueue ▼ ┌───────────────────┐ │ Message queue │ (buffers spikes, │ (SQS / RabbitMQ) │ survives retries) └─────────┬─────────┘ │ ┌─────────────┴─────────────┐ ▼ ▼ ┌───────────────┐ ┌───────────────┐ │ Worker 1 │ │ Worker N │ (idempotent, │ dedupe on │ ... │ scale out │ dedupe on │ webhook-id │ │ under load │ webhook-id) └───────┬───────┘ └───────┬───────┘ └─────────────┬──────────────┘ ▼ ┌───────────────┐ │ ERP │ (write / update) └───────────────┘ BULK IMPORT (backfill): bulkOperationRunQuery ──► JSONL ──► load into ERP RECONCILIATION (safety): scheduled re-read of Shopify ──► compare ──► fix gaps
Why each piece is there Queue = ack fast + absorb spikes. Idempotent workers = safe retries and duplicate webhooks. Bulk import = cheap first load. Reconciliation = catches anything missed. Name all four when you draw it.

Reconciliation — the correctness safety net

Webhooks are best-effort: your server may be down, or Shopify gives up after ~8 retries over ~4h. A scheduled job re-reads Shopify (the source of truth) and fixes drift.

  • Incremental (frequent, e.g. hourly): query records with updatedAt ≥ lastRun — a high-water mark / checkpoint — and upsert through the same idempotent path as the webhook worker. Overlap the window a little; idempotency makes re-processing safe.
  • Full (rare, e.g. weekly): compare the whole dataset — often via a bulk operation — to catch deletes and deep drift. An incremental "updated since" query cannot see deletions (a deleted record just stops appearing).
Say it like this

"Webhooks for speed, reconciliation for correctness. A scheduled job re-reads Shopify since my last checkpoint and upserts through the same idempotent path, so overlapping the window is safe. Incremental hourly; a periodic full pass via a bulk operation catches deletes and deep drift."

Two-way sync & conflicts

Best strategy: avoid it. Give each field a single source of truth so it's one-way, not two-way — then there is nothing to conflict.

DataMasterDirection
Inventory / priceERPERP → Shopify
Description / imagesShopifyShopify → ERP
Order (placed)ShopifyShopify → ERP
Fulfillment / trackingERPERP → Shopify

If a field truly must be two-way, resolve conflicts with: last-write-wins on updatedAt, version numbers (to detect a clash), field-level merge (different fields changed = no real conflict), source-of-truth priority, or flag for a human on critical data.

Don't forget the echo loop Your write to Shopify fires a webhook that would bounce back to the ERP and loop forever. Break it: skip no-op changes, recognize your own writes (an origin marker), and apply an incoming update only if its updatedAt is newer than what you have (stale-write guard).
Say it like this

"First I avoid true two-way by giving each field one owner — inventory and price from the ERP, content from Shopify. For fields that must be bidirectional I use last-write-wins on updatedAt, or versioning to detect a clash, and flag critical ones. The key extra step is breaking echo loops: I skip no-op changes and ignore my own writes so a push doesn't bounce back forever."

5. Rough estimation numbers

You do not need exact figures. You need numbers that are the right size, fast.

FactNumber to remember
One day in seconds~86,400 (round to ~100,000)
One modern server, simple requests~a few thousand req/s
Read from memory / cachesub-millisecond to ~1 ms
Read from SSD~0.1 ms
Round trip within a datacenter~0.5 ms
Round trip across regions / internettens to ~150 ms
1 million requests/day~12 req/s average (but plan for peak > average)
Estimation move Convert "per day" to "per second" by dividing by ~100,000. Then compare to "one server does a few thousand/s" to decide how many servers you need. Always multiply the average by a peak factor (3x–10x).
