Shopify Backend Cheat Sheet

1. Admin API vs Storefront API

One-line rule Admin API = staff / back-office. Storefront API = shopper. An ERP, CRM, or inventory sync lives almost entirely on the Admin GraphQL API.

2. Rate limits

GraphQL Admin — calculated query cost

Every field has a point cost. You spend from a 1000-point bucket that refills 50 points/second (standard plans). Read your live budget in extensions.cost:

"extensions": {
  "cost": {
    "requestedQueryCost": 3,
    "actualQueryCost": 3,
    "throttleStatus": {
      "maximumAvailable": 1000.0,
      "currentlyAvailable": 997,
      "restoreRate": 50.0
    }
  }
}

Handle it like a senior:

  • Read throttleStatus.currentlyAvailable; slow down before it hits zero.
  • Request only the fields you need — smaller query, fewer points.
  • Retry with backoff on the throttled error; use cursor pagination for big lists.
  • Huge jobs → use bulk operations, not the live bucket.

REST Admin (legacy) & Storefront

Trap GraphQL is not magically free. A careless query has high cost or causes N+1 work on Shopify's side. Design queries on purpose.

3. Webhooks — the 4 rules

  1. Verify HMAC. Compute HMAC-SHA256 of the raw request body with your app's client secret. Compare to header X-Shopify-Hmac-SHA256. Never parse the body before verifying.
  2. Return 200 within 5 seconds. Do the real work later.
  3. Ack fast, then queue. Push the event onto a queue, reply 200, let a worker process it.
  4. Be idempotent. The same event can arrive twice.
Shopify event (e.g. orders/create) │ POST + headers: X-Shopify-Hmac-SHA256, X-Shopify-Webhook-Id ▼ ┌────────────────────────────┐ │ 1. Verify HMAC (raw body) │ mismatch → reject (401) └─────────────┬──────────────┘ ▼ ┌────────────────────────────┐ │ 2. Return 200 (< 5 sec) │ do NOT process inline └─────────────┬──────────────┘ ▼ ┌────────────────────────────┐ │ 3. Enqueue the event │ push to a queue (SQS / RabbitMQ) └─────────────┬──────────────┘ ▼ ┌────────────────────────────┐ │ 4. Worker processes it │ idempotent; dedupe on Webhook-Id └─────────────┬──────────────┘ ▼ your DB / ERP / CRM (+ reconciliation job re-reads Shopify to catch any misses)
ConcernWhat Shopify does / what you do
RetriesShopify retries ~8 times over ~4 hours if you do not return 200.
DedupeUse header X-Shopify-Webhook-Id as the idempotency key; skip if already seen.
Missed eventsRun a reconciliation job that re-reads Shopify to catch anything dropped.
Say it like this

"I verify the HMAC on the raw body, return 200 in under five seconds, then push the event to a queue. A worker processes it idempotently, deduping on the webhook id. Shopify retries about eight times over four hours, and a nightly reconciliation job re-reads Shopify so nothing is lost."

5. Bulk operations — the flow

A bulk operation is a job, not a request: you start it, Shopify runs it in the background, and you download a file. Use it for large imports/exports so you never fight the rate-limit bucket. Full lesson: L18.

1. START bulkOperationRunQuery(query: "...") → job created (no first: args inside) 2. WAIT currentBulkOperation { status url } → CREATED → RUNNING → COMPLETED 3. DOWNLOAD GET the `url` once COMPLETED → one JSONL file (url expires in 7 days) 4. SORT stream the file line by line → re-group children by __parentId
  • JSONL = one record per line, not a nested object.
  • Children (line items) are flattened onto their own lines with a __parentId pointing to the parent — you rebuild the shape as you stream.
  • Stream it line by line so memory stays flat even for gigabytes.
  • Know when it's done: poll currentBulkOperation, or use the bulk_operations/finish webhook.
  • bulkOperationRunMutation = the same idea for bulk writes.
Say it like this

"Bulk operations are async jobs. I start with bulkOperationRunQuery, poll currentBulkOperation (or use the finish webhook) until COMPLETED, download a JSONL file, and stream it — re-grouping children by __parentId. It avoids the rate-limit bucket and keeps memory flat, so it's right for big exports and the initial ERP import."

6. Plus & Functions

  • Shopify Plus: the enterprise tier — higher limits, checkout customization, Flow automation, B2B, multiple stores.
  • Shopify Functions: your server-side customizations (discounts, shipping, checkout logic) that run on Shopify's own infrastructure.

7. The standard integration pattern

This is the answer that ties it all together — the shape of almost every Shopify ↔ external-system sync.

1. BULK IMPORT (one time / periodic) bulkOperationRunQuery ──► JSONL file ──► load into your DB → gives you the full current state without hammering the bucket. 2. WEBHOOK SYNC (real-time) Shopify event ──► verify HMAC ──► 200 fast ──► queue ──► worker (idempotent) ──► your DB / ERP → keeps you up to date as things change. 3. RECONCILIATION (safety net) scheduled job ──► re-read Shopify (Admin API) ──► compare ──► fix gaps → catches any webhook that was missed or processed wrong.
Say it like this (the whole pattern)

"I seed my database with a bulk operation to get the full current state cheaply. Then I keep it fresh with webhooks — verify HMAC, ack in under five seconds, queue, and process idempotently. Finally I run a reconciliation job on a schedule that re-reads Shopify and fixes anything the webhooks missed. Bulk for backfill, webhooks for real-time, reconciliation for correctness."
