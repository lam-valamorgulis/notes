Find-in-Store Query API

The read-path endpoint the product-page widget calls thousands of times: "which stores near me have this SKU, right now?" — fast, cached, and honest about freshness.

Do this first: cover the model answer. 25-minute timer. Clarify, plan, then type it from blank while narrating the latency and caching decisions. Maps to Lesson 4.

The prompt

Task "Write the public endpoint GET /find-in-store?sku=&lat=&lng=&radius=&limit= that returns the nearest stores with that SKU's availability state. It's called from the shopper's browser on the product page; keep it under ~100 ms."

Step 1 — Clarify out loud

  • "This is a read hint, not the buy-time guarantee — so it can be cached and slightly stale (the strict check is at checkout, Kata 03)."
  • "I read a pre-computed availability table — the threshold/prediction maths already ran on the write side (Lesson 3). No availability calculation in the request."
  • "Nearest-stores is a geospatial query — spatial index, not a distance loop over every store."
  • "It's a public browser endpoint — public per-merchant key, CORS, rate limit; return a state + age, not a bare number."

Step 2 — Say the plan

1. Cache key = (sku, coarse area e.g. postcode/geohash). Hit -> return (a few ms). 2. Miss -> single-flight rebuild: geospatial KNN over locations JOIN pre-computed availability, LIMIT N, on a read replica. 3. Cache the result with a short TTL; return state + updated-age per store.

Step 3 — Build it (open your editor)

The traps this kata tests

TrapWhy it fails
Computing availability in the requestCouples every page view to your heaviest logic and the write DB. Pre-compute on write; read a stored state.
Distance loop over all storesDoesn't scale. Use a spatial index (PostGIS GiST + <-> KNN, or Redis GEO).
Caching on exact lat/lngEvery shopper gets a unique key → ~0% hit rate. Round to postcode/geohash so an area shares one entry.
No single-flight on missA hot SKU expiring lets thousands of requests rebuild the same key at once (thundering herd).
Returning a bare quantityLoses the honesty rule. Return a state (in_stock / call_to_confirm / …) and an age.
Reading the write primaryProduct-page traffic then competes with ingestion. Read a replica.
"Display is a cached hint, so I read a pre-computed availability table off a replica, find nearest stores with a spatial index, and cache on (SKU, coarse area) with a short TTL and single-flight rebuild. I return a state and an age, never a bare number — the guarantee happens at checkout, not here."

Say how you'd test it

  • Second identical request in the same area → served from cache (fast, no DB).
  • Store with no coordinates → excluded, query doesn't crash on NULL.
  • No stores in radius → widen once, then "ships from warehouse", never an empty crash.
  • Concurrent misses on one key → one rebuild, others wait (single-flight).
