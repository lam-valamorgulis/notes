Click & Collect Reservation + Re-check

The moment of truth: turn a soft "likely in stock" hint into a hard guarantee at checkout, without ever letting two shoppers reserve the same last unit.

Do this first: cover the model answer. 25-minute timer. Clarify, plan, then type it from blank while narrating the concurrency decisions. Maps to Lesson 5 and Lesson 3 §6.

The prompt

Task "Write reserveForPickup(orderRef, locationId, lines[]) where each line is { sku, qty }. Reserve all lines at the chosen store atomically — all or nothing — so concurrent checkouts can't oversell. Give each hold a TTL so an abandoned order frees the stock."

Step 1 — Clarify out loud

  • "The product-page number was a cached hint; here I re-check the live count and reserve in one atomic step."
  • "I don't decrement on_hand — the POS owns it. I raise reserved, which lowers available immediately."
  • "The guard is a single conditional UPDATE: 0 rows means not enough → the whole order fails and I offer another store."
  • "Every hold gets an expires_at so an abandoned checkout releases it; releasing is as atomic as taking."

Step 2 — Say the plan

BEGIN for each line: UPDATE inventory_levels SET reserved = reserved + qty WHERE (location,sku) AND on_hand - reserved - buffer >= qty if 0 rows -> ROLLBACK, return {ok:false, badSku} (offer another store) INSERT reservations(... status='active', expires_at = now + TTL) COMMIT -> {ok:true}

Step 3 — Build it (open your editor)

The traps this kata tests

TrapWhy it fails
SELECT the count, then UPDATECheck-then-act race: two buyers both read "1 left" and both reserve. The check and the write must be one statement.
Decrementing on_handYou don't own it — it's the POS's number. Raise reserved instead; on_hand drops later via the feed.
Reserving line-by-line without a transactionPartial reservation: 2 of 3 lines succeed, then line 3 fails and you've locked stock for an order that can't complete. All-or-nothing.
No TTLAn abandoned order locks the unit forever — phantom out-of-stock. Every hold expires.
Forgetting to release on collect/cancelreserved leaks upward; available shrinks. Release (decrement) atomically when the hold ends.
"The guard is a single conditional UPDATE that checks availability and raises reserved in one atomic step, so the row lock serialises concurrent buyers — zero rows means refuse. All lines commit in one transaction (all-or-nothing), each hold carries a TTL, and I raise reserved rather than touch on_hand because the POS owns the physical count."

Say how you'd test it

  • Two concurrent reservations for the last unit → exactly one succeeds, the other gets ok:false.
  • 3-line order where line 3 is short → whole order rolls back, nothing reserved.
  • Reservation expires → sweep sets status='expired' and decrements reserved.
  • Collect → status='consumed', reserved decremented, no double-subtract with the feed.
