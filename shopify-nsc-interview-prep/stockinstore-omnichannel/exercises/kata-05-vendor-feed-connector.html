The Vendor Feed Connector

The Track B counterpart to Kata 01. Same domain, different destination — and the change of destination changes almost every decision.

Do this first: cover the model answer. 30-minute timer. Clarify out loud, say your plan, then type it from a blank file while narrating why a relay is not an ingest. Maps to Lesson 12, with the mapping step from Lesson 13.

The prompt

Task "Write the worker that relays a batch of stock readings from a retailer's POS into a third-party vendor's HTTP API. Each reading is { sourceItemCode, sourceStoreCode, quantity, uom, measuredAt }. The vendor accepts up to 500 items per call, rate-limits you, and occasionally returns 5xx. You cannot read back what the vendor currently believes. Make it correct and cheap."
The sentence in the prompt that is the whole kata "You cannot read back what the vendor currently believes." Everything you design differently from Kata 01 follows from that clause. If you don't notice it, you will write an ingest and get an ingest's score.

Step 1 — Clarify out loud

  • "I can't inspect the destination, so I send absolute quantities, never deltas — a lost delta is permanent silent drift, a lost absolute heals on the next send."
  • "I can't inspect the destination, so I keep a shadow table of what I last successfully sent, hashed, and only write it on a 2xx."
  • "sourceItemCode and sourceStoreCode are the source's names — I must map them to canonical ids first, and an unmappable row is quarantined, never dropped."
  • "uom means quantities may be cases, not eaches — I convert before sending, or I'm wrong by the case size."
  • "Rate limits and 5xx mean a client-side token bucket, retry with full jitter, honour Retry-After, and a dead-letter queue after N attempts."
  • "And I'll want a scheduled full reconciliation, because the event path always drops some messages — but that's outside this function."

Step 2 — Say the plan

For each reading: 1. MAP sourceItemCode -> sku, sourceStoreCode -> locationId (quarantine on miss) 2. CONVERT quantity x uom_factor -> canonical eaches 3. GUARD drop if measuredAt < shadow.source_ts (staleness) 4. SUPPRESS drop if hash(payload) == shadow.sent_hash (vendor already knows) Then, per batch of <=500 survivors: 5. TAKE from the token bucket 6. POST with a CONTENT-DERIVED idempotency key 7. on 2xx -> write shadow rows (ONLY here) on 429 -> sleep Retry-After, retry on 5xx -> full-jitter backoff, retry up to N then -> dead-letter with the payload and the error

Step 3 — Build it (open your editor)

The traps this kata tests

TrapWhy it fails
Relaying the POS's delta straight throughOne dropped HTTP call and that SKU's count is wrong forever, with no error message. The most expensive bug in Track B.
Writing the shadow row before the send succeedsChange suppression then skips that row permanently — you believe the vendor knows something it never received.
Comparing only the quantity for suppressionPrice, active flag or trading hours may ride along in the payload. Hash the whole payload you actually send.
A random uuid() idempotency keyA retry generates a new key, so the vendor sees a second distinct request. Derive the key from the content, sorted.
Ignoring Retry-After and using your own backoff on a 429The server knows its own recovery window. Your exponential guess either hammers them or wastes minutes.
Retrying without jitterEvery worker retries in lockstep after an outage and re-DOSes the vendor at the moment it recovers.
Dropping an unmappable rowStock silently disappears. Quarantine with an alert so a human can add the mapping — invisible gaps are worse than loud ones.
Forgetting the UoM factorA case-pack source reports 1 when 6 are on the shelf, or the reverse. Silent 6× error in either direction.
"The destination is a system I can't inspect or repair, so every decision changes: absolute sends instead of deltas, a shadow table instead of a SELECT, a derived idempotency key instead of a random one, and quarantine instead of a dropped row. Kata 01 wrote into my own database and could be repaired with one UPDATE. This one can only be repaired by re-sending — which is exactly why absolute state and the shadow table are not optional."

Say how you'd test it

  • Same batch sent twice → one effect at the vendor (derived idempotency key), and no second shadow write.
  • Vendor returns 500 for the whole batch → no shadow rows written, batch retried, eventually dead-lettered.
  • Vendor returns 429 with Retry-After: 2 → waits ~2 s, not the exponential guess.
  • Unchanged reading re-sent → zero HTTP calls (suppression), and a metric increments.
  • Older measuredAt arrives after a newer one → dropped by the staleness guard.
  • Unknown sourceItemCode → quarantined with an alert; the rest of the batch still sends.
  • A case-pack source with uom_factor = 6 → the vendor receives 6× the reported number.
