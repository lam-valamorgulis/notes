Kata 01 · Build from blank · ~25 min

Idempotent Inventory Upsert

The write-path heart of the platform: a normalise worker that takes one stock reading from any source and writes it safely — duplicates, out-of-order arrivals, and full-vs-delta feeds all handled.

Do this first: cover the model answer. 25-minute timer. Clarify out loud, say your plan, then type it from a blank file while narrating the reliability decisions. Maps to Lesson 2.

The prompt

Task "Write the worker that applies one normalised stock reading { eventId, source, locationId, sku, onHand, measuredAt, feedKind } to the inventory_levels table. The feed delivers at-least-once, readings can arrive out of order, and feedKind is 'delta' or 'full'."

Step 1 — Clarify out loud

  • "At-least-once → I dedupe on eventId for exactly-once application."
  • "Out of order → a staleness guard: only accept a reading whose measuredAt is newer than what I hold, so an old poll can't overwrite a fresh webhook."
  • "The POS owns on_hand, so I replace the value, never add a delta."
  • "For a full snapshot I must zero SKUs that dropped off; for a delta I must not. So I need the feed kind."

Step 2 — Say the plan

1. Seen this eventId? -> yes: return (dedupe, no-op). 2. Upsert on (locationId, sku): SET on_hand = new WHERE new.measuredAt > stored. 3. Record eventId as processed (same transaction as the upsert). 4. (full-snapshot batch only, separately) zero any SKU not seen in this batch.

Step 3 — Build it (open your editor)

The traps this kata tests

TrapWhy it fails
Blind INSERT or add-a-deltaDuplicates create phantom stock, and adding deltas drifts from the POS truth. The POS owns on_hand — replace it.
No staleness guardA slow poll landing after a fresh webhook moves stock backwards in time. Guard on measuredAt.
Treating a full feed like a deltaA SKU that dropped off a full snapshot means "0 left." Leave it and you show a sold-out item as in stock.
Dedupe row and upsert in separate transactionsCrash between them and you either lose the write or re-process. Commit both together.
Strict > on equal timestampsSecond-granularity feeds emit same-second readings; a strict > drops the legit later one. Use >= and rely on dedupe for true duplicates.
"Duplicates are killed by the eventId dedupe; ordering is handled by a measuredAt staleness guard; POS truth is respected by replacing on_hand rather than adding; and full-vs-delta is the one flag that decides whether an absent SKU means zero or unchanged. Miss any one and you either oversell or wipe stock."

Say how you'd test it

  • Same eventId twice → one effect (dedupe).
  • Older measuredAt after a newer one → ignored (no backwards move).
  • Full snapshot missing a previously-present SKU → that SKU goes to 0.
  • Delta feed missing a SKU → that SKU is unchanged.
