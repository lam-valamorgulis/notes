inventory_levels(location_id, sku, on_hand, reserved, version,
                 updated_at TIMESTAMPTZ, source, PK (location_id, sku))
  -- reserved = authoritative running counter (for the atomic guard)

  -- state: in_stock | low | likely | out_of_stock | call_to_confirm

  -- LEDGER (one row per hold); status: active | consumed | expired | cancelled

Consistency split

  • Strongly consistent (one island): the reservation — atomic guarded UPDATE on the primary, on a single (location, sku) row.
  • Eventually consistent (everything else): availability display, sync, analytics, POS/ERP write-back — feeds lag, so display is a hint with an age.
  • CAP/PACELC: under a partition the reservation picks consistency, the read path picks availability; in normal operation the read path also picks latency (fast+stale) over freshness.
  • Reservation DB = primary + synchronous cross-AZ standby, automatic failover; strong-consistent writes stay in-region.

The three "pairs people confuse"

PairDifference
on_hand vs availableon_hand = raw physical count; available = on_hand − reserved − buffer (what you can sell).
idempotency vs staleness guardDedupe on event id = exactly-once application; timestamp/version guard = ordering (drop older).
delta vs full feedDelta: absent = unchanged. Full snapshot: absent = 0 (sold out) — you must zero it.
