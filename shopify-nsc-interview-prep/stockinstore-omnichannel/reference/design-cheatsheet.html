Cheat Sheet — "Design stockinstore"

One page to skim before the interview. The seven steps, the architecture in words, and the decisions that win. Full detail in Lesson 10.

Lead with the constraint: "I don't own the stock and can't fully trust the number — it's external, uncertain, and stale — so the whole design manages that uncertainty without overselling."

The seven steps

1. CLARIFY retailers/stores/SKUs? feed types? which features? freshness/latency? traffic? cost/SLA? 2. ARCHITECT three paths: write (ingest→availability), read (find-in-store), order (reserve→allocate) 3. FLOWS walk stock-in, shopper-read, buy — one hard thing each: idempotent upsert / fast cached read / atomic reserve 4. RELIABLE at-least-once → idempotent; outbox; reconciliation; strong consistency only for the reservation 5. SCALE 3 workloads on 3 axes; multi-tenant (retailer_id + RLS); SLIs vs SLOs; cost 6. BREAK stale feed, dup event, full-feed gap, store reject, abandoned hold, spike, hot key, noisy tenant 7. SUMMARISE ~90s, then take the "why?" follow-ups

The three paths (say each in one line)

PathWhat it doesThe one hard thing
Write (L2–L3)POS/ERP feeds → verify → enqueue → normalise → idempotent upsert → availability engine computes a safe stateIdempotent, version-guarded upsert; full-vs-delta zeroing
Read (L4)Widget asks "nearest stores with SKU X"; geospatial + pre-computed availability, cached on a replicaPre-compute on write; ~100 ms; state + age, not a number
Order (L5–L6)C&C: carry store → re-check → atomic reserve → pickup order → notify. Ship-from-Store: score stores → allocate → reassignAtomic guarded reservation; fairness in allocation

Decisions that win

  • Availability = on_hand − reserved − buffer, gated by a per-store/per-SKU threshold, decayed by trading hours (down only).
  • Source of truth per fact: POS owns on_hand, platform owns reserved+availability, Shopify owns the order+catalogue.
  • One strong-consistency island: the reservation — a single guarded UPDATE ... WHERE on_hand-reserved-buffer >= qty on the primary.
  • Outbox so a DB write and its event commit together; reconciliation because feeds and webhooks drop.
  • Shopify facts: HMAC + X-Shopify-Webhook-Id dedupe; ~8 retries/4h then Admin-API subs auto-remove; PICK_UP fulfillment order + committed; fulfillmentOrderMove to reassign.
  • Scale: reads = cache/edge/replica; writes = workers/partitions; orders = per-row consistency; multi-tenant with RLS + per-tenant limits.
  • Degrade gracefully: lose a feature, not the site (reservation stays on; availability/cache/allocation/notify fall back).
"Manage the uncertainty, never oversell: pre-compute a safe availability hint on the write side and serve it fast and cached; make the purchase the strict, atomic guarantee; glue it with idempotent events, an outbox, and reconciliation; keep strong consistency to one row; and degrade gracefully so a failure loses one feature, not the platform."
