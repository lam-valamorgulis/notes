Webhooks, Write-Back & Reconciliation

Stock went out to the vendor. Now the sale has to come back to the till and the ledger. Four webhook streams, two signature schemes, and one three-way reconciliation nobody builds until it's too late.

Your win today: draw the four webhook streams in a Track B integration instead of the one most people draw. Verify two different signature schemes correctly. Write back to the POS/ERP idempotently, split stock from finance, and build the three-way reconciliation — POS vs vendor vs Shopify — with a documented winner per fact.

This is Lesson 7 (queues, idempotency, the outbox) and Lesson 8 §5 (write-back) applied to a three-party integration. The reliability rules are unchanged. What changes is that there are now three systems that can each be right and disagree.

1. Four streams, not one

┌──────────────────┐ │ SHOPIFY │ └────┬────────┬────┘ ① orders/create │ │ ② the vendor's app fulfillment │ │ subscribes directly order events │ │ (their subscriptions, ▼ ▼ their endpoint) ┌────────────────────┐ ┌──────────────┐ │ YOUR SERVICE │◄── ③ ──│ stockinstore│ │ (the connector │ order │ SaaS │ │ + write-back) │ alloc- │ │ └─────────┬──────────┘ ated, └──────────────┘ │ pickup ④ write-back ready │ ▼ ┌────────────────────┐ │ POS / ERP │ stock movement + the sale └────────────────────┘ ① Shopify → you HMAC: X-Shopify-Hmac-Sha256 ② Shopify → vendor not yours — but you must know it exists (see §2) ③ vendor → you HMAC: the VENDOR's own header and secret ④ you → POS/ERP whatever the POS accepts: API, file, or a queue Most people draw ① only. Stream ② is the one that causes the arguments, because two apps are reacting to the same order and neither knows it.
Why stream ② matters even though you don't own it The vendor's app has its own webhook subscriptions on the same shop. So an order triggers your handler and their handler at the same time, in an order nobody controls. If both write to the POS, you double-count. If both notify the store, staff get two tasks. The integration design must state, per event, which party acts — and the answer must be "exactly one." Get that list agreed in discovery (L18) and write it into the runbook.

2. Two signature schemes, verified properly

Shopify signs with its own header and your app's shared secret. The vendor signs with theirs. Using the wrong verifier on the wrong stream is a real, common bug, and it looks like "webhooks aren't arriving."

import crypto from 'node:crypto';

/** Shopify: HMAC-SHA256 over the RAW body, base64, in X-Shopify-Hmac-Sha256. */
export function verifyShopify(rawBody: Buffer, headerHmac: string, secret: string): boolean {
  const digest = crypto.createHmac('sha256', secret).update(rawBody).digest('base64');
  const a = Buffer.from(digest);
  const b = Buffer.from(headerHmac || '');
  // length check FIRST: timingSafeEqual throws on a length mismatch
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}

/** The vendor: same idea, THEIR header, THEIR secret, possibly hex not base64,
 *  and often a timestamp inside the signed string to stop replay. Read their docs. */
export function verifyVendor(rawBody: Buffer, sigHeader: string, tsHeader: string, secret: string) {
  const skewMs = Math.abs(Date.now() - Number(tsHeader) * 1000);
  if (!Number.isFinite(skewMs) || skewMs > 5 * 60_000) return false;   // reject replays
  const signed = `${tsHeader}.${rawBody.toString('utf8')}`;
  const digest = crypto.createHmac('sha256', secret).update(signed).digest('hex');
  const a = Buffer.from(digest), b = Buffer.from(sigHeader || '');
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
Three ways this goes wrong (1) The body was parsed before you hashed it. Express's JSON middleware re-serialises the body, so key order and whitespace change and the HMAC never matches. Capture the raw bytes on the webhook route only. (2) A plain === comparison. Use a constant-time compare, with a length check first, because timingSafeEqual throws when lengths differ. (3) The wrong verifier. A vendor payload checked against Shopify's secret fails silently and looks like a delivery problem — log which scheme ran, on every request.

3. Shopify's delivery rules you must design around

RuleWhat it forces you to build
Response timeout is 5 seconds1Ack first, process later. Verify, enqueue, return 200. Never call the POS inside the handler — an on-premise till can take longer than 5 s on its own.

// The reconciler that stops a silent outage becoming permanent.
const REQUIRED = [
  'orders/create', 'orders/cancelled',
  'fulfillment_orders/order_routing_complete',
  'fulfillments/create', 'fulfillments/update',
  // mandatory compliance topics the app must implement (L17)
  'customers/data_request', 'customers/redact', 'shop/redact',
];

export async function reconcileSubscriptions(shop: string) {
  const live = await admin.listWebhookSubscriptions(shop);      // what Shopify has
  const have = new Set(live.map(s => s.topic));
  for (const topic of REQUIRED) {
    if (!have.has(topic)) {
      await admin.createWebhookSubscription(shop, topic, CALLBACK_URL);
      log.warn({ shop, topic }, 'webhook subscription was MISSING — recreated');
      metrics.subscriptionRecreated.inc({ topic });             // alert on this, always
    }
  }
}
Alert on the repair, not just the failure A recreated subscription means you were deaf for a while. That metric going above zero is an incident with a blast radius — every event in that window is lost and must be recovered by reconciliation (§6), not by hoping. Teams that only alert on 5xx never notice the window.

4. The write-back: two different facts, two different rules

"Write back to the POS" is really two jobs with different correctness requirements. Conflating them is why finance and inventory teams end up with different numbers.

-- The write-back ledger. Insert-only. The unique index IS the idempotency.
CREATE TABLE pos_writeback (
  id             BIGSERIAL PRIMARY KEY,
  retailer_id    TEXT NOT NULL,
  kind           TEXT NOT NULL,          -- 'stock_movement' | 'sale'
  idempotency_key TEXT NOT NULL,         -- derived, never random
  payload        JSONB NOT NULL,
  status         TEXT NOT NULL DEFAULT 'pending',  -- pending|sent|failed|dead
  attempts       INT  NOT NULL DEFAULT 0,
  last_error     TEXT,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  sent_at        TIMESTAMPTZ
);
CREATE UNIQUE INDEX ON pos_writeback (retailer_id, kind, idempotency_key);

Insert first, send from a worker. That is the outbox from Lesson 7, and it is what stops the dual-write problem: the webhook handler does one local transaction (mark the event seen, insert the outbox row) and returns 200 well inside the 5-second budget. The POS call happens later, retried, with the unique index guaranteeing that a replayed webhook cannot create a second financial record.

Derive the idempotency key; never generate one uuid() as an idempotency key is not idempotency — a retry produces a new key and a second record. Derive it from the facts: sale:{order_id}, or move:{fulfillment_id}:{line_id}. Then the same event, replayed a hundred times, collides on the unique index a hundred times and inserts once.

5. Ordering: what actually needs it

Webhooks arrive out of order. Most of your handlers do not care, and knowing which ones do is the whole skill.

  • Doesn't need ordering — stock relays (absolute values, timestamp-guarded), notifications, cache invalidation. Last write wins is correct.
  • Needs ordering per key — a lifecycle: created → fulfilled → refunded. A refund processed before the sale it refunds produces nonsense in the ledger. Partition the queue by order_id so one order's events are handled in sequence.
  • Needs a state machine, not just ordering — the honest answer for the write-back. Rather than trusting arrival order, record the state you believe and reject impossible transitions: a refunded event for an order you never marked sold goes to a review queue instead of the ledger. That survives out-of-order delivery and a replay from six weeks ago.

6. Three-way reconciliation

Three systems hold overlapping facts. Each can be right and they can still disagree. Reconciliation is a scheduled job that finds the disagreements and knows who wins.

FactPOS/ERPVendorShopifyWinner
Physical on_hand at a storeAuthoritativeDerived from your feedOnly if you publish it therePOS. Everything else is a copy — repair the copies, never the POS.
Reserved for a pickup orderDoesn't knowAuthoritativeIts own committed, separatelyVendor. Don't model it; don't reconcile against a number you don't own.
The order and its moneyA copy, via your write-backA copyAuthoritativeShopify. If the POS disagrees, the POS is wrong.
Fulfilment stateCopyDrives itAuthoritative recordShopify for the record, the vendor for the workflow.
The identifier mapping———You. The one fact nobody else can adjudicate (L13).

Three cheap daily jobs, each with an owner and a threshold:

  1. Stock drift (POS ↔ what we sent). Full snapshot from each source, diffed against the shadow table. Output: rows corrected. Trending up means the event path is leaking.
  2. Order completeness (Shopify ↔ write-back ledger). Every pickup order fulfilled yesterday should have exactly one sale row and the right number of stock_movement rows. Missing rows are lost revenue records; duplicates are double-counted revenue. Both are alerts, not report lines.
  3. Store list (registry ↔ Shopify locations ↔ vendor stores). A shop opened, closed, or was renamed in one system only. This is a five-minute job that prevents a whole class of "no stock at that shop" tickets.
The reconciliation that pays for itself the fastest Order completeness. Stock drift is self-healing on the next feed, but a missing or duplicated financial record is found by an accountant weeks later with no way to reconstruct the truth. Build job 2 first, even if it is the least interesting.

7. Failure modes

What breaksHow you handle it
Webhooks stop arrivingSuspect subscription deletion after 8 consecutive failures over ~4 h. The subscription reconciler recreates them and alerts; then run reconciliation to recover the missed window.
HMAC never matchesThe body was parsed before hashing, or the wrong scheme ran. Capture raw bytes on webhook routes; log which verifier was used.
The same order is written back twiceDerived idempotency key plus the unique index makes the second insert a no-op. If it happened, the key was random — that is the bug.
Two apps both act on one orderStream ② . Agree per event which party acts, exactly one, and put the list in the runbook. Symptoms are duplicate POS records or duplicate store tasks.
Refund arrives before the saleState machine rejects the impossible transition and routes it to review, instead of writing nonsense to the ledger.
POS is down for a dayOutbox rows stay pending and drain when it returns. Alert on outbox age, not just depth — 50 rows an hour old is fine, 3 rows a day old is not.
Handler is slow, Shopify times out5-second budget. Verify, mark seen, insert outbox, return 200. Everything else is a worker's job.
A replayed webhook from weeks agoseen_events on X-Shopify-Webhook-Id makes it a no-op. Keep those ids long enough to cover a vendor replay — days, not minutes.
Vendor's webhook has no signature at allRaise it. Meanwhile: allow-list their source IPs, use a long unguessable callback path, and treat the payload as a hint — re-fetch the authoritative record from Shopify or the vendor's API instead of trusting the body.
Say it like this (closing the loop in 6 sentences)

"I draw four webhook streams, not one: Shopify to me, Shopify to the vendor's app, the vendor to me, and me to the POS. The second one is the one people forget, and it's why I agree per event which single party acts — otherwise two apps react to the same order and the till gets the sale twice. On Shopify's stream I verify HMAC-SHA256 over the raw body with a constant-time compare, de-duplicate on X-Shopify-Webhook-Id because delivery is at-least-once, route on X-Shopify-Topic, and ack inside the 5-second timeout by verifying, inserting an outbox row and returning 200 — the POS call happens in a worker. I run a subscription reconciler at boot and daily, because Shopify deletes a subscription after 8 consecutive failures over about four hours, and a recreated subscription is an incident with a lost window, not a tidy-up. The write-back is two facts, not one: a stock movement, which the next POS feed will repair anyway, and a sale, which nothing repairs — so its idempotency key is derived from the order id, never generated, and the unique index on the outbox is what actually enforces once-only. And I schedule three-way reconciliation with a documented winner per fact: the POS owns physical stock, the vendor owns reservations, Shopify owns the order and the money, and I own the mapping — with order completeness built first, because stock drift heals itself and a missing financial record does not."
