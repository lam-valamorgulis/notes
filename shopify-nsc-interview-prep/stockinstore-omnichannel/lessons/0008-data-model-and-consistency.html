Data Model & Consistency

Now put all the tables on one page and answer the hard question: which parts of this system can be eventually consistent, and which parts must be strongly consistent — and why getting that split right is the whole game.

Your win today: lay out the full schema, decide the source of truth for each fact, place the one island of strong consistency (the reservation) inside a sea of eventual consistency, and explain the transactional outbox that stops a database write and an emitted event from drifting apart.

This gathers the tables introduced across Lessons 2–6 into one model, and answers the consistency questions an interviewer asks once they've seen the pieces.

1. The schema on one page

Everything the platform stores. retailer_id is on every row — this is a multi-tenant system serving many retailers (Lesson 9).

retailers(retailer_id PK, name, plan)

locations(location_id PK, retailer_id, name, geog POINT, timezone,
          daily_capacity, active)                 -- geog: PostGIS point (L4)

-- SKU is a VARIANT-level code in Shopify (may be null/duplicate), so it is
-- unique only WITHIN a retailer, never globally.
products(retailer_id, sku, title, barcode, active,
         PRIMARY KEY (retailer_id, sku))

-- canonical raw stock (write path, L2). reserved is the AUTHORITATIVE running
-- counter (see §3); version guards against stale/out-of-order writes (§4).
inventory_levels(location_id, sku, on_hand, reserved, version INT,
                 updated_at TIMESTAMPTZ, source, PRIMARY KEY (location_id, sku))

-- computed, read-optimised availability (L3 → L4 reads this)
--   state: 'in_stock' | 'low' | 'likely' | 'out_of_stock' | 'call_to_confirm'
--   qty_shown: the safe number to display = max(0, on_hand - reserved - buffer)
availability(location_id, sku, state, qty_shown, computed_at TIMESTAMPTZ,
             PRIMARY KEY (location_id, sku))

-- the LEDGER of holds (L5): one row per hold, with a TTL. The sum of active
-- rows must equal inventory_levels.reserved (reconciled periodically).
--   status: 'active' | 'consumed' | 'expired' | 'cancelled'
reservations(id PK, retailer_id, location_id, sku, qty, order_ref,
             status, expires_at TIMESTAMPTZ, created_at TIMESTAMPTZ)

-- what we allocated / order lifecycle (L5, L6)
allocations(id PK, order_ref, location_id, sku, qty, method, status)
            -- method: PICK_UP | SHIPPING ; status: reserved..fulfilled

-- identity mapping: each source's codes → canonical (L2)
id_map(entity, source, source_code, canonical_id,
       UNIQUE(entity, source, source_code))

-- reliability tables (L2, L7) — both are append-heavy; see retention in §6
event_dedupe(event_id PK, received_at TIMESTAMPTZ)       -- idempotency
feeds(source PK, retailer_id, mode, kind, last_seen_at TIMESTAMPTZ) -- push/pull/file; delta/full
outbox(id PK, aggregate, payload, published_at TIMESTAMPTZ NULL)    -- see §4
Why reserved appears to live in two places (it doesn't) inventory_levels.reserved is an authoritative running counter — a single number so the concurrency guard can be one atomic row update (§3). The reservations table is the ledger — one row per hold, carrying the TTL, order reference, and status for audit and expiry. They are not two sources of truth for the same fact: the counter is the fast aggregate, the ledger is the detail, and both are written in the same transaction. A periodic reconciliation asserts inventory_levels.reserved == SUM(qty of active reservations) and repairs any drift.

2. Source of truth — decide it per fact

The most important design statement in the whole system. Different facts are owned by different systems; naming the owner prevents fights and duplicates.

FactSource of truthWhy
Physical on-hand stockThe store's POS/ERPYou don't control the shelf; you receive its count and never invent it.
Reservations & availabilityYour platformThese are your computation; only you know what you've promised.
The order & its fulfilment stateShopifyCheckout, payment, and fulfillment orders live there (L5).
Product catalogue / priceShopify (usually)The storefront owns what's for sale and at what price.
Say it like this "I declare a source of truth per fact: the POS owns physical stock, my platform owns reservations and computed availability, Shopify owns the order and the catalogue. Each system only reads the facts it doesn't own. That single rule kills most sync bugs before they happen."
How the rule is enforced (not just declared) Two mechanics turn "source of truth" from a wish into a guarantee. (1) Replace, don't add. An inbound POS reading sets on_hand to the reported number — it never adds a delta — because the POS owns that field. So even after you write a fulfilment back to the store, the next feed that reflects it is a harmless no-op, not a second decrement. (2) Version guard. Each inventory_levels row carries a version (or you compare updated_at); a write with an older-or-equal version is ignored, so a slow full feed can't clobber a newer delta. When both sides change the same fact, the owner wins: the POS wins on_hand, the platform wins reserved — they don't fight because they own different fields.

3. Eventual consistency — with one strong-consistency island

The platform is eventually consistent by nature: store feeds lag, so your availability is always a little behind the shelf, and that's acceptable (Lesson 3 made availability a hint with an age). But one operation cannot be eventually consistent:

The island: the reservation must be strongly consistent Two shoppers must never both reserve the last unit. The reservation is two writes — increment the counter and insert a ledger row — done in one transaction, and the guard is a single conditional update on the (location_id, sku) row: 
BEGIN;
  -- take the hold only if enough is really free; the row lock serialises buyers
  UPDATE inventory_levels
     SET reserved = reserved + :qty
   WHERE location_id = :loc AND sku = :sku
     AND (on_hand - reserved - :buffer) >= :qty;     -- 0 rows ⇒ sold out ⇒ ROLLBACK, refuse
  INSERT INTO reservations(...);                      -- the ledger row, same transaction
COMMIT;

Zero rows updated means "not enough" — you roll back and refuse. Everything around this (display, sync, analytics) can be eventually consistent; the reservation is the one place you pay for strong consistency, and you pay it on a single row, so it stays cheap.

Releasing a hold is just as atomic as taking one When a reservation is collected, cancelled, or hits its TTL, you must set its ledger status and decrement inventory_levels.reserved in the same transaction. Skip the decrement and the counter leaks upward forever — available stock silently shrinks (a phantom out-of-stock). Expiry is a guarded write, not a background afterthought.

In CAP terms — which applies during a network partition — the reservation chooses consistency (refuse rather than risk a double-sell) while the read path chooses availability (serve a possibly-stale hint rather than fail). And in normal operation (PACELC's "else" branch) the read path also favours latency over freshness: it's a hint with an age, so a stale-but-fast answer beats a slow-but-fresh one. One consequence: availability reads may come from a read replica, but the reservation transaction must always run on the primary — a replica's lag would let two buyers take the last unit.

4. The dual-write problem & the outbox

A worker often must do two things: write to the database and emit an event (Lesson 7). If it writes the row, then crashes before emitting, the event is lost and downstream never reacts (a reservation created but no cache invalidation, no notification). Two writes to two systems can't be made atomic directly — this is the dual-write problem.

The fix: transactional outbox In the same database transaction as the business write, insert a row into an outbox table. A separate publisher polls SELECT ... WHERE published_at IS NULL ORDER BY id (backed by a partial index — §6), emits each event per aggregate in order, then sets published_at. Because the business row and the outbox row commit together, you never write one without the other. If the publisher crashes after emitting but before marking published, it re-emits on restart — at-least-once, which is fine because consumers are idempotent (Lesson 7). (Change-data-capture on the outbox table is an alternative to polling.)
The trap juniors fall into "Write the row, then publish the event" in two steps. A crash between them silently drops the event, and the bug is invisible until a customer doesn't get their "ready to collect" message. The outbox makes the write-and-emit atomic; a plain two-step does not.

5. Closing the loop: stock & finance back to the POS/ERP

When a Ship-from-Store or Click & Collect order is fulfilled, the store just sold a unit through the online channel. The store's own POS/ERP must learn about it, or its stock count and its books will be wrong. stockinstore "integrates with your POS/ERP to keep accurate stock and finance records."

  • Stock: the fulfilment reduces the store's real on-hand; you write that movement back so the POS doesn't keep showing the sold unit. The next inbound feed then reports the already-reduced number, and because feeds replace on_hand (never add — §2), that feed is a no-op, not a second decrement. This is why you don't double-count the sale across the two directions.
  • Finance: the sale (revenue, tax, the fulfilling store's credit) is recorded in the ERP so the store gets attribution and the books reconcile.
  • Idempotent write-back: keyed on the order/allocation id, so a retried write-back doesn't double-count the sale.

6. Indexing & storage choices

  • (location_id, sku) primary key on inventory_levels and availability — the natural lookup and the upsert conflict target.
  • Spatial index (GiST) on locations.geog for the Lesson-4 "near me" query.
  • Index on reservations.expires_at (partial, WHERE status = 'active') so the TTL sweep (Lesson 5) finds expired holds cheaply.
  • Partial index ON outbox (id) WHERE published_at IS NULL so the publisher's poll only scans unpublished rows.
  • Multi-tenancy model: this is the shared-schema, row-discriminator design (one retailer_id column on every row) — the simplest of the three options (vs schema-per-tenant, DB-per-tenant). Enforce it with Postgres row-level security so a forgotten WHERE retailer_id can't leak across tenants; trade-offs are in Lesson 9.
  • Retention: event_dedupe and outbox are append-heavy. Keep event_dedupe for a bounded window (e.g. daily partitions dropped after the max replay window, ~24–48 h); delete or archive outbox rows soon after published_at is set. Left unbounded they bloat and slow the hot paths they protect.
  • SQL for the canonical model (relational, transactional — reservations need ACID). A high-volume append-only event log can live in a store tuned for writes; the deeper SQL-vs-NoSQL trade-off is your round-1 lesson. Don't force everything into one engine.
Say it like this (the data & consistency story in 6 sentences)

"I keep one canonical model — locations, products, raw inventory_levels, a computed availability table the read path serves, reservations with a TTL, allocations for the order lifecycle, plus id-mapping and reliability tables — all tagged with retailer_id for multi-tenancy. The key statement is source of truth per fact: the POS owns physical stock, my platform owns reservations and availability, Shopify owns the order and catalogue, and each system only reads what it doesn't own. The platform is eventually consistent because feeds lag, and that's fine for display, but the reservation is a strong-consistency island — one atomic guarded update on a single row so two buyers can't take the last unit. Where a worker must write and emit an event, I use a transactional outbox so the row and the event commit together and neither is lost. When an order is fulfilled I write the stock movement and the sale back to the store's POS/ERP, idempotently, so their stock and finance stay correct. In CAP terms the read path favours availability and the reservation favours consistency, and knowing which side each operation sits on is the whole design."
