Lesson 2 · Architecture · The input problem

Inventory Ingestion & Multi-Source Sync

Stock lives in dozens of store systems you do not control, in dozens of formats. This lesson is how you pull it in, normalise it, and store it safely — the foundation everything else reads from.

Your win today: design the ingestion pipeline that turns many messy POS/ERP feeds into one clean, canonical stock view — and explain the three ways stock arrives (push, pull, and file), why every write must be idempotent, and how you keep the number fresh without hammering anyone.

Builds on Lesson 1 (the hard problem: stock is external and uncertain) and on your round-1 "Shopify ↔ ERP sync" design. This is that design, pointed at a fleet of stores instead of one ERP.

1. The canonical model: what you are actually storing

Before pipelines, define the target. Everything you ingest normalises into one core fact:

The atom of the whole system inventory_level = (location_id, sku, on_hand, updated_at, source) — "how many of this SKU are at this location, as last reported, by whom." Every feed, in every format, becomes rows of this shape. Get this atom right and the rest of the system has firm ground. (This is the raw number; the safe-to-sell number is computed on top of it in Lesson 3.) 
-- the canonical target every feed normalises into
locations(location_id PK, retailer_id, name, lat, lng, timezone, active)
products(sku PK, retailer_id, title, barcode)          -- catalogue
inventory_levels(
  location_id, sku,
  on_hand      INT,          -- raw count the source reported
  updated_at   TIMESTAMPTZ,  -- when the SOURCE measured it (UTC), not when we saved it
  source       TEXT,         -- which POS/ERP/feed it came from
  PRIMARY KEY (location_id, sku)
)

Two column choices carry weight. updated_at is the source's measurement time, not your insert time — you need it to reject stale updates that arrive out of order (an older reading must never overwrite a newer one). And it is TIMESTAMPTZ stored in UTC: your stores span time zones, so a naive TIMESTAMP would corrupt both the staleness guard below and the "feed age" and trading-hours maths in Lesson 3. Convert to locations.timezone only for display and for the trading-hours decay, never for comparison.

2. Three ways stock arrives

Different stores can feed you differently. A good answer names all three and when each fits.

ModeHow it worksWhen it fitsFreshness
Push (webhook / API)The POS calls your endpoint when stock changes. You verify, enqueue, ack fast.Modern POS with outbound webhooks. Best case.Near real time (seconds).
Pull (poll their API)You call the POS/ERP API on a schedule and diff against what you have.Systems with a read API but no webhooks.Minutes (your poll interval).
File drop (batch)The store uploads a CSV/JSONL to SFTP/S3 on a schedule; you parse and load it.Old or offline systems; nightly full exports.Hours (often nightly).
The senior framing "I support push, pull, and file ingestion behind one normalisation layer, because a franchise will have a mix — a few modern stores push in real time, most poll, and the legacy ones drop a nightly file. The freshness of each store's data depends on its mode, and I surface that (a 'last updated' age) rather than pretending all stock is equally fresh."

3. The pipeline (one shape for all three modes)

No matter how stock arrives, it flows through the same stages. This is the diagram to draw.

MANY SOURCES ONE CANONICAL VIEW ┌──────────────┐ push ┌───────────────┐ │ Store A POS │─────►│ │ │ (webhook) │ │ │ └──────────────┘ │ │ enqueue ┌──────────┐ ┌──────────────┐ pull │ INGESTION │───────────►│ Queue │ │ Store B ERP │◄─────│ EDGE │ (raw feed │ (per- │ │ (poll API) │─────►│ │ events) │ source │ └──────────────┘ │ • auth/verify │ │ partition) ┌──────────────┐ file │ • adapter per │ └────┬─────┘ │ Store C │─────►│ source type │ │ │ (SFTP CSV) │ │ • ack fast │ ▼ └──────────────┘ └───────────────┘ ┌─────────────────┐ │ NORMALISE │ │ WORKER │ │ • map to SKU │ │ • map to │ │ location_id │ │ • unit/format │ │ • drop if stale │ └───────┬─────────┘ │ idempotent upsert ▼ ┌───────────────────────────┐ reconciliation (scheduled) ─── repair ──►│ inventory_levels (canon) │ re-reads each source, fixes drift └───────────────────────────┘
  1. Ingestion edge — one endpoint per mode. A source adapter knows the quirks of that POS/ERP (auth, field names, units). It authenticates the feed, does the minimum, and enqueues the raw event. For push it must ack fast — the same acknowledge-first discipline as Shopify webhooks (Shopify's own timeout is 5 seconds; a store's POS may allow more, so treat "reply fast, process off the queue" as the principle).
  2. Queue — buffers bursts and decouples ingestion speed from database speed. Partition it for fairness and isolation — so one store dumping a huge file cannot starve the real-time feeds. If you also want strict per-location ordering, partition on (source, location_id) so all events for one store's SKU land in the same partition with one in-order consumer. But note you should not rely on ordering: the timestamp guard in step 5 makes out-of-order arrival safe anyway, so partitioning is really about fairness, not correctness.
  3. Normalise worker — the brain. It maps the source's product code to your canonical sku, its store code to your location_id, converts units (see §4), drops readings older than what you already have, then does an idempotent upsert into inventory_levels.
  4. Reconciliation — a scheduled job that re-reads each source's full stock and repairs anything the event stream missed. Non-negotiable, because feeds drop events. It depends on the source being able to give a full snapshot; a push-only POS with no bulk export cannot be reconciled this way, so for those you lean harder on the event stream and on feed-age alerts. Bound its cost — a full re-read of 40 stores hits the same rate limits §6 warns about, so schedule it off-peak and stagger stores.
How you actually authenticate a push feed Same mechanism as a Shopify webhook: the source signs the raw body with a shared secret using HMAC-SHA256 and sends the signature in a header; you recompute it over the raw bytes and compare with a constant-time check (reject on mismatch). Add a timestamp or nonce in the signed payload and reject old ones, so a captured request cannot be replayed. Never trust source IP or an unsigned "store id" field alone — both are easy to spoof.

4. The mapping problem (why normalisation is hard)

Two stores rarely agree on identifiers. Store A calls it SHOE-RED-42; Store B calls the same shoe 0042-RD; your catalogue calls it SKU 1001. If you do not map these to one canonical SKU, "who has this shoe?" returns nothing. Mapping is the unglamorous core of ingestion.

  • SKU / barcode mapping — a lookup table from each source's product code (or barcode/GTIN) to your canonical sku. Barcodes are the most reliable join key across systems.
  • Location mapping — from each source's store code to your location_id.
  • Unit-of-measure (UoM) conversion — sources count differently. One reports eaches (a "12" means 12 items); another reports cases (a "1" means one case of 12); weight-based items report kilograms. If you skip this, a case-pack source shows 1/12th of the real stock (undersell) or an each-pack source multiplied by the case size (oversell). Store a per-source, per-SKU multiplier and convert to a single unit before the upsert.
  • Unmapped items — a feed row you cannot map does not silently vanish. It lands in a quarantine / dead-letter table with an alert, so a human can add the missing mapping. Silent drops are how stock quietly goes wrong.
The trap juniors fall into Assuming all sources speak your identifiers. They do not. Without a mapping layer (source code → canonical SKU/location), Find in Store shows "no stock" for products that are actually on the shelf — because the feed row never matched anything. Always name the mapping table and the quarantine path for rows that do not map.

5. Safe writes: dedupe key + staleness guard

Feeds retry. Polls overlap. The same reading arrives twice. So every write must be safe to repeat. You never blind-insert a stock row; you upsert on the primary key (location_id, sku), and you only accept the write if it is newer than what you have.

-- upsert with a staleness guard (PostgreSQL)
INSERT INTO inventory_levels (location_id, sku, on_hand, updated_at, source)
VALUES ($1, $2, $3, $4, $5)
ON CONFLICT (location_id, sku) DO UPDATE
  SET on_hand    = EXCLUDED.on_hand,
      updated_at = EXCLUDED.updated_at,
      source     = EXCLUDED.source
  WHERE EXCLUDED.updated_at >= inventory_levels.updated_at;  -- reject only OLDER readings
Two different jobs — don't confuse them The WHERE clause is a staleness guard: it stops an older reading (a slow poll that lands after a fresh webhook) from moving stock backwards in time. It is not true idempotency — a genuine re-send stamped with a new send-time would still pass it. For exact-once application, dedupe on a source event id (a per-event key from the feed) in a seen-events table, exactly like X-Shopify-Webhook-Id. Real systems use both: the event-id dedupe kills duplicates, the timestamp guard handles ordering.
Two subtle bugs in the guard (1) Clock skew. The guard trusts each source's clock. When one (location_id, sku) is fed by two sources with drifting clocks, a laggy clock can wrongly win or lose. Prefer a single authoritative source per location; where you can't, add a monotonic sequence number from the feed instead of leaning on wall-clock time. (2) Equal timestamps. Feeds with one-second granularity emit many readings sharing the same second — a strict > would drop the legitimate later one. Using >= (above) lets a same-timestamp reading through; pair it with the event-id dedupe so a true duplicate is still a no-op.

5½. Full snapshot vs delta feeds (the silent-oversell bug)

The upsert above only touches SKUs that appear in the feed. That is correct for a delta feed (it only sends what changed, so a SKU that is absent means "unchanged"). It is dangerous for a full snapshot feed (a nightly file listing everything the store has). If yesterday the store had SHOE-RED-42 and today's full file no longer lists it, the real answer is "0 left" — but the upsert leaves the old positive count in place forever. The product shows in stock at a shop that sold out. This is one of the most common real oversell bugs.

The fix: know the feed type, and zero the missing Tag each feed as delta or full. For a full snapshot, stamp every row you write with a batch id, then in one statement set on_hand = 0 for any row of that (source, location) not seen in this batch. For a delta feed, never do this — absent means unchanged. Getting this one distinction wrong causes either phantom stock (full feed, not zeroed) or wiped stock (delta feed, wrongly zeroed).

6. Freshness without hammering

You want fresh stock, but you cannot poll every store's API every second — you would blow their rate limits and yours. Balance it:

  • Prefer push where a store supports it — zero polling, seconds-fresh.
  • Adaptive polling for pull sources — poll fast-moving stores/SKUs more often, slow ones less. Or poll only what changed (a "since" cursor) instead of the full catalogue.
  • Backpressure via the queue — workers pull only as fast as the database accepts, so a nightly full-file drop from 40 stores does not overwhelm writes.
  • Track feed age — store updated_at per row and expose "last updated N minutes ago." A stale feed is a first-class signal the availability engine (L3) uses, and an ops alert when a store goes silent.
Shopify's side of this — two designs, know Shopify's model Shopify already has a real multi-location inventory model: an InventoryItem has an InventoryLevel per Location, and each level tracks distinct quantity states — on_hand, available, committed, reserved, incoming, damaged, safety_stock — where on_hand = available + committed + reserved + …. That gives you two design choices. (A) Serve the widget from your own API: keep availability in your database and let the Find-in-Store widget read it directly; Shopify never sees per-store stock. Simplest, and the usual pattern. (B) Model each physical store as a Shopify Location and publish per-store quantities into Shopify with inventorySetQuantities / inventoryAdjustQuantities (bulk operations for the first big load), under the calculated-cost budget. If you pick (B), write the raw on_hand and let Shopify compute available from its own committed/reserved — do not push your already-reduced number into available, or you double-count Shopify's own reservations.

Say it like this (the ingestion design in 6 sentences)

"Stock arrives from many store systems three ways — push webhooks, polled APIs, and batch file drops — so I put a source adapter per system behind one normalisation layer. The edge verifies the feed's HMAC signature and acks fast, then enqueues raw events onto a queue partitioned for fairness so one noisy store can't starve the others. A normalise worker maps the source's product and store codes to my canonical SKU and location, converts units, then writes to a single inventory_levels table keyed on location and SKU. Because delivery is at-least-once, I dedupe on the source event id for exact-once application, and I add a source-timestamp staleness guard so an out-of-order older reading can't move stock backwards. I track whether each feed is a delta or a full snapshot, and for full snapshots I zero any SKU that dropped off, so a sold-out item doesn't stay phantom in-stock. Rows that won't map go to a quarantine table with an alert instead of vanishing, and a scheduled reconciliation re-reads each source that supports a full export to repair drift, while feed-age alerts catch the ones that don't."

The exact confusions to be ready for when the client asks "why?" three times deep. Cover each answer, say it out loud, then scroll.

The read path: what "6 lines of code" really is The vendor's "6 lines" is just a loader (the legacy ScriptTag snippet; modern themes use a theme app extension). At runtime the widget calls your API: GET /v1/availability?shop=…&sku=RUN-RED-9&lat=…&lng=…&radius=25 with a public, read-only key (never the Admin token — it runs in the shopper's browser). Your API answers from a precomputed availability view, nearest stores first, returning a status (in_stock / low / call) not a raw count, plus each store's feed age ("14 h ago"). It must fail fast and never block add-to-cart. That "14 h ago" is the same updated_at the write path wrote — the read path is honest about the write path's freshness.

Q2. Staleness guard vs event-id dedupe — why you need both

They answer two different questions, and neither can do the other's job.

MechanismQuestion it answersProblem it solves
Staleness guard (WHERE EXCLUDED.updated_at >= …)"Is this reading newer than what I have?"Out-of-order arrival
Event-id dedupe (a seen_events table)"Have I already processed this exact event?"Duplicate delivery

Two different events (a fresh webhook + a slow poll) have different event ids, so dedupe waves both through — only the guard knows one is older. And the guard uses >= on purpose (to let legitimate same-second readings through), so a true duplicate with an equal timestamp passes the guard — only dedupe kills it. A duplicate is harmless for a pure state write, but doubles any side effect (emit an event, append a ledger, decrement a counter) or any delta ("sold 2") — that is the real bug dedupe prevents.

Order of operations in the worker Check seen_events for the event id → if seen, stop (dedupe kills copies). If new, record the id and run the guarded upsert (the guard then picks the freshest of the genuinely-distinct readings).

Q3. Why is the guard needed at all — doesn't the queue keep things in order?

No — a queue does not guarantee your writes land in order, even from one source. Standard queues are best-effort; even Kafka only orders within a partition. Two things reorder the writes regardless: parallel workers (you run several for throughput) and retries (a failed message is re-injected after newer ones). A single (location, sku) can also have two sources (a webhook plus a reconciliation poll).

enqueued :02 on_hand = 8 (measured 10:00:02) <- in-order enqueue enqueued :05 on_hand = 5 (measured 10:00:05) W1 grabs :02 -> slow DB / GC pause ... W2 grabs :05 -> finishes first, writes 5 (correct so far) W1 wakes up -> writes 8 (OLDER reading lands LAST) no guard : final = 8 -> oversell 3 pairs with guard : :02 >= :05 is false -> rejected -> stays 5 (correct)
The principle (the senior answer) Don't make correctness depend on ordering — make each write safe regardless of arrival order. The guard makes the write commutative: throw the same readings in any order and you still land on the freshest. That is why partitioning is for fairness (one noisy store can't starve others), not correctness — the guard owns correctness.

Q4. Full vs delta feeds — the batch-id zero sweep (and the nuance)

It all turns on one question: when a SKU is missing from the feed, what does missing mean? A full snapshot = "everything I have right now", so missing = 0. A delta feed = "only what changed", so missing = unchanged. Same absence, opposite meaning. The plain upsert only touches SKUs that appear — correct for delta, but for a full feed it leaves a sold-out shoe's old count sitting there forever (phantom in-stock).

Fix — full feeds only, two steps:

-- step 1: upsert every row in today's file, stamping THIS batch id
--   blue  -> batch_id = 8842,  green -> batch_id = 8842
--   red   -> NOT written (absent), so it KEEPS yesterday's id 8841

-- step 2: zero anything this store didn't send tonight
UPDATE inventory_levels
SET on_hand = 0
WHERE source = 'store-C-csv' AND location_id = 'store-C'   -- scope! or you wipe other stores
  AND batch_id <> 8842;                                 -- "old batch = not seen tonight"
The nuance — it's not "no batch id", it's "not THIS batch id" Every row always carries a batch id — the one from whenever it was last written. The sold-out red shoe isn't blank; it still has yesterday's id (8841). So the test is batch_id <> 8842 (an older batch), not IS NULL. And never run this sweep on a delta feed — there, absent blue and green mean "nothing changed", so zeroing them wipes real stock.

Q5. Which clock does the guard compare — measurement time, not write time

If worker A already stored the row with updated_at = 10:00 and worker B brings an event with updated_at = 9:55, the guard checks 9:55 >= 10:00 → false → rejected. Correct. The trap: "10:00" is the source's measurement time (when the POS counted), not the wall-clock moment a worker ran the write. Worker B might physically execute at 10:01, after A — irrelevant. The guard compares the two updated_at values the source stamped, so the freshest reading wins no matter who commits last. It only engages because both writes hit the same (location_id, sku) row, so ON CONFLICT fires and the WHERE arbitrates.

Q6. Partitioning the ingestion queue — why, and what "key on (source, location_id)" means

A queue splits its stream into partitions (parallel lanes). The only ordering guarantee is: messages within one partition are processed in order (one consumer per lane); across lanes there is none. The partition key is the dial that picks what stays ordered — partition = hash(key) % N, so same key → same lane → ordered; different keys → different lanes → parallel.

Keying on (source, location_id) means "put every event about one store's feed in the same lane", so each store's own timeline stays in order while different stores run in parallel. Its real payoff is fairness/isolation: a store dumping a 500k-row nightly file floods only its own lane, so it can't block another store's real-time webhook in a different lane.

Partition keyWhat stays orderedParallelism
source onlya whole feed (all its stores)low
(source, location_id)one store's whole streammedium — one lane per store
(source, location_id, sku)one single row's streamhigh — one lane per SKU
Fairness, not correctness Correctness only ever needs per-row order (location_id, sku), and the staleness guard already delivers that whatever the arrival order. So partition ordering is a nice-to-have, never the mechanism — and it isn't airtight anyway (a retry, a consumer-group rebalance, or two sources feeding one row can still reorder). Say it as: "I partition for fairness so a batch store can't starve a real-time one; I don't lean on partition order for correctness — the timestamp guard makes out-of-order writes safe."

9. The two workers in code — poll-with-cursor (pull) and SFTP/CSV loader (file)

Both reuse the idempotent write from Kata 01 — applyReading() (dedupe on eventId + the guarded upsert) and zeroMissingAfterFullSnapshot() — so each worker only owns its transport quirks. TypeScript + PostgreSQL, same as the kata.

Worker A — poll-with-cursor (a PULL / delta source)

Poll the POS read API on a schedule, fetch only what changed since last time (a since cursor), apply each reading, and advance the cursor only after the page is durably written. A cursor feed is a delta, so it never zeroes.

// PULL: poll a POS API for changes since a saved cursor, normalise, apply.
async function pollOnce(db: Db, api: PosApi, loc: StoreConfig): Promise<void> {
  // 1. Where did we stop last time? (null on the very first run)
  let since = await loadCursor(db, loc.source, loc.locationId);
  let page: PosPage;

  do {
    // 2. Fetch ONLY the delta since the cursor. Back off on 429/5xx (respect Retry-After).
    page = await withRetry(() => api.getInventoryChanges(loc, { since, limit: 500 }));

    // 3. Normalise + apply each row. applyReading is idempotent, so if a re-poll
    //    overlaps the last page, the dedupe + staleness guard absorb the repeat.
    for (const raw of page.items) {
      const reading = normalise(raw, loc);       // source codes -> sku/location, unit convert
      if (!reading) { await quarantine(db, raw, loc, 'unmapped'); continue; }  // never drop
      await applyReading(db, reading);           // Kata 01: dedupe + guarded upsert
    }

    // 4. Advance the cursor ONLY after the page is durably applied. Crash before this
    //    and we simply re-poll from the old cursor next run — at-least-once, and safe.
    since = page.nextCursor;
    await saveCursor(db, loc.source, loc.locationId, since);
  } while (page.hasMore);
}
The one decision that makes it crash-safe Advance the cursor after the page is written, never before. If the worker dies mid-page the cursor still points at the old spot, so the next run re-fetches that page — and because applyReading is idempotent, re-applying it changes nothing. Advance the cursor first and a crash would skip unapplied changes forever (silent stock loss). Poll cadence is adaptive (fast-movers more often), and backoff uses jitter so many stores don't retry in lockstep.

Worker B — SFTP/CSV batch loader (a FILE / full source)

Pull the nightly file, stream-parse it (files can be huge), apply each row under one batchId, quarantine what won't map, then — because a nightly file is a full snapshot — zero the SKUs that dropped off.

// FILE: pull a nightly CSV over SFTP, stream it, apply under a batchId, then zero the missing.
async function loadNightlyFile(db: Db, sftp: SftpClient, loc: StoreConfig): Promise<void> {
  const batchId = await newBatchId(db, loc.source, loc.locationId);   // one id per load
  const path = loc.dropPath;                                         // e.g. /out/stock.csv

  try {
    // 1. STREAM the file — never buffer a 500k-row file into memory.
    const rows = parseCsvStream(sftp.createReadStream(path));        // async iterable

    // 2. Apply each row under this batchId. Same guarded upsert as Kata 01, plus it
    //    stamps last_batch_id = batchId (Kata 01's column) so step 4 can find what
    //    this file did NOT touch.
    let seen = 0;
    for await (const raw of rows) {
      const reading = normalise(raw, loc);
      if (!reading) { await quarantine(db, raw, loc, 'unmapped'); continue; }
      await applyReadingWithBatch(db, reading, batchId);
      seen++;
    }

    // 3. GUARD: a truncated or empty drop must NOT reach the zero sweep, or it would
    //    wipe the whole store. No rows -> treat as a failed drop, not "everything sold out".
    if (seen === 0) throw new Error(`empty/truncated file for ${loc.locationId}`);

    // 4. FULL snapshot only: zero any SKU at this store not written by this batch
    //    (it dropped off the file = sold out). A DELTA feed SKIPS this step.
    await zeroMissingAfterFullSnapshot(db, loc.source, loc.locationId, batchId);

    // 5. Archive the file so it can't be loaded twice.
    await sftp.rename(path, `${path}.done.${batchId}`);
  } catch (err) {
    // Poison file (corrupt/unparseable) or a mid-file failure: alert, don't half-trust it.
    // Re-running later converges — the upsert is idempotent and the sweep is keyed on the
    // batchId — so a partial load self-heals on the next successful run.
    await deadLetterFile(db, loc, path, err);
    throw err;
  }
}

// the guarded upsert, plus last_batch_id so the full-snapshot sweep can find absent SKUs
async function applyReadingWithBatch(db: Db, r: StockReading, batchId: string): Promise<void> {
  await db.query(
    `INSERT INTO inventory_levels(location_id, sku, on_hand, updated_at, source, last_batch_id)
     VALUES ($1,$2,$3,$4,$5,$6)
     ON CONFLICT (location_id, sku) DO UPDATE
       SET on_hand = EXCLUDED.on_hand, updated_at = EXCLUDED.updated_at,
           source = EXCLUDED.source, last_batch_id = EXCLUDED.last_batch_id
     WHERE EXCLUDED.updated_at >= inventory_levels.updated_at`,
    [r.locationId, r.sku, r.onHand, r.measuredAt, r.source, batchId]);
}
The bug that wipes a whole store Skipping the seen === 0 guard. If tonight's file is empty (an SFTP hiccup, a truncated upload) and you run the zero sweep anyway, every SKU is "not in this batch" — so you set the entire store to on_hand = 0 and it shows sold out of everything. Always prove the snapshot actually arrived before you let it zero anything.
Why these two are the same worker in different clothes Strip the transport away and both do the same thing: normalise → (quarantine if unmapped) → applyReading. The pull worker adds a cursor; the file worker adds a batchId + zero sweep. The safe write in the middle is identical — which is exactly why "one normalisation layer behind three transports" (§3) is the right shape. Push (webhook) is the third: verify HMAC, enqueue, and the same applyReading runs off the queue.
