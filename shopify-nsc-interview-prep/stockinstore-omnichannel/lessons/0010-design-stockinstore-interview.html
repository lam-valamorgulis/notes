System-Design Interview: "Design stockinstore"

The whole course in one answer. This is the rehearsal script for "design an omnichannel stock and click-and-collect platform" — run it end to end, out loud, then handle the follow-ups.

Your win today: deliver the full design in seven moves — clarify, draw the architecture, walk the three flows, defend reliability, scale it, break it, and summarise — and answer the deep "why?" follow-ups without hesitating. Everything here is a synthesis of Lessons 1–9.

This mirrors your round-1 "Shopify ↔ ERP sync" design, pointed at the omnichannel domain. Same seven-step shape; new content.

1. Clarify first (never skip)

Ask before you draw. The answers reshape the design, and asking is the senior signal.

AskWhy it changes the design
How many retailers, stores, SKUs? Franchise?Sets multi-tenancy, the number of feeds, and whether sources are heterogeneous (many POS types).
How do stores feed stock — webhook, API, file?Push/pull/file each have different freshness and different ingestion code (L2).
Which features — Find in Store, C&C, Ship from Store?Read-only display is far simpler than reservations + allocation. Scope it.
Freshness & latency targets?Near-real-time display vs strict buy-time; the product-page latency budget (L4).
Traffic shape — sale-day spikes?Drives queueing, caching, and horizontal scaling (L7, L9).
Cost / SLA budget?Decides how much cache, replica, and redundancy you buy, and how often reconciliation full-reads run (they cost API budget).

Lead with the core constraint. Before the boxes, name the one hard truth (from Lesson 1): "I don't own the stock and can never fully trust the number a store gives me — it's external, uncertain, and often stale. So the whole design is about managing that uncertainty without overselling." Every choice below is a response to that sentence.

Working assumptions for this answer ~30 retailers; a franchise with ~400 stores across 3 POS types + head-office ERP; Find in Store + Click & Collect + Ship from Store; near-real-time display (seconds–minutes), strict at purchase; heavy product-page reads with sale-day spikes. Must never oversell a Click & Collect pickup.

2. The architecture (one whiteboard)

Two separate queues: an ingestion queue (edge → normalise worker, on the write path) and an order/event queue (fed by Shopify webhooks, on the order path). They don't share capacity — that's why a feed flood never slows checkout.

3. Walk the three flows

  1. Stock in (write path). POS/ERP feeds arrive push/pull/file → verify + enqueue → normalise (map codes, convert units) → idempotent, version-guarded upsert into inventory_levels → the availability engine recomputes a safe state — available = on_hand − reserved − buffer, gated by a threshold, then decayed for staleness — and stores it. Reconciliation re-reads full snapshots to repair drift. (L2, L3)
  2. Shopper read (read path). The widget asks "nearest N stores with SKU X" → a geospatial query (PostGIS KNN) joined to the pre-computed availability → served from cache/edge on a read replica, under ~100 ms. Display is a hint with an age. (L4)
  3. Buy (order path). Click & Collect: carry the chosen store to checkout → re-check + atomic reserve → Shopify pickup order (PICK_UP fulfillment order, committed) → pick task → notify → fulfil + release. Ship from Store: the OMS scores stores (coverage × proximity × fairness) and places the work with fulfillmentOrderMove, reassigning on rejection. (L5, L6)

4. Reliability (the part they push on)

  • At-least-once everywhere → idempotent consumers keyed on event id; the timestamp/version guard handles ordering. Exactly-once effect, not exactly-once delivery. (L7)
  • Transactional outbox so a DB write and its event can't drift apart. (L8)
  • Reconciliation re-reads sources to catch missed events; Shopify webhooks can be dropped and even auto-removed after prolonged failure, so never rely on the stream alone. (L2, L7)
  • Strong consistency only where needed — the reservation is one atomic guarded row update on the primary; everything else is eventually consistent. (L8)

5. Scale, watch, and cost

Three workloads, three axes: reads scale with cache + edge + replicas; writes with more queue workers + per-source partitions; orders stay correct because contention is normally isolated to one (location, SKU) row — with a hot SKU at one store handled as a genuine hotspot (tiny lock, retry on the row), not scaled away. Multi-tenant: retailer_id everywhere with row-level security, per-tenant rate limits and queue partitions so no retailer is a noisy neighbour, and outbound calls respect Shopify's per-shop API budget. (L9)

Observability: "how do I know it's healthy?" — I watch a few SLIs against SLOs and page on error-budget burn: feed age per store, queue depth vs lag, DLQ depth, read p95, reservation-reject rate, and a lagging "availability accuracy" that ties back to the core promise. Cost: strong consistency is confined to one cheap row; a split shipment costs an extra parcel (so I prefer one store); and reconciliation full-reads run off-peak to bound API spend. (L9, L6, L2)

6. Break it (failure modes)

Name the top ones and the defence for each: stale feed → conservative availability + alert; duplicate event → idempotent no-op; SKU off a full feed → zero it; store rejects → reassign, capped; abandoned reservation → TTL release; spike → queue + workers; hot product → single-flight cache; one tenant floods → per-tenant limits. (L2, L3, L5, L6, L7, L9)

Say it like this (the whole design, ~90 seconds — lead with the constraint)

"The one hard truth is that I don't own the stock and can't fully trust the number a store gives me — it's external, uncertain, and stale — so the whole design manages that uncertainty without overselling. I split the system into a write path, a read path, and an order path. On the write path, POS/ERP feeds arrive by webhook, poll, or file; I verify, enqueue, normalise, and do an idempotent, version-guarded upsert into a canonical inventory table. An availability engine then turns each raw count into a safe state — on_hand minus reserved and a buffer, gated by a threshold, decayed for staleness. On the read path, the Find-in-Store widget asks 'nearest stores with this SKU'; I answer with a geospatial query joined to the pre-computed availability, served from cache and a read replica under about a hundred milliseconds, as a hint with an age. On the order path, buying turns the hint into a guarantee: Click & Collect carries the chosen store to checkout, re-checks, and reserves atomically on a single row, then places a Shopify pickup order, sends a pick task, and notifies the customer. Ship from Store scores candidate stores on coverage, proximity, and fairness, places the work with fulfillmentOrderMove, and reassigns if a store can't deliver. It's glued together by events with at-least-once delivery, so consumers are idempotent, a transactional outbox keeps writes and events in step, and reconciliation repairs anything the stream drops. The only strongly-consistent operation is the reservation — one atomic guarded update on the primary — everything else is eventually consistent because feeds lag. It's multi-tenant with retailer_id and row-level security, the three workloads scale on separate axes, I watch SLIs against SLOs, and every component degrades gracefully so a failure loses one feature, not the platform."

7. The deep follow-ups (drill these)

They ask…Crisp answer
"Two shoppers, one last unit — what stops a double-sell?"A single guarded UPDATE ... WHERE on_hand - reserved - buffer >= qty on the primary; 0 rows ⇒ refuse. Row lock serialises them. (L5/L8)
"The POS number is 6 hours old — what do you show?"Decay it by the store's rolling sell rate × trading hours since the reading — decay only ever lowers, never raises, because I can't see returns/restock until the next feed; gate on threshold; fall back to 'call to confirm' when too stale. The strict reservation at purchase is the real guarantee. (L3)
"A store's POS feed dies for a day."That store degrades to 'call to confirm' + alert; reconciliation repairs on recovery. Other stores are unaffected. (L3/L2)
"(Separately) your ingest endpoint is down for hours — what about the webhooks?"Shopify retries ~8×/4h, then auto-removes Admin-API-created subscriptions (app-specific ones aren't removed), so I detect the removal and re-subscribe, then reconcile the gap. (L7)
"The widget is public browser JS — how is your API secured?"Public, read-only endpoint; per-merchant public key (no secrets in the browser); CORS to the storefront origin; per-key and per-IP rate limits because it's scrapeable. (L4)
"How do a DB write and its event stay in sync?"Transactional outbox — event row committed in the same transaction; a relay publishes at-least-once. (L8)
"One store has 2 of 3 items — how do you fulfil?"Prefer one store that has all 3; else split — fulfillmentOrderMove a subset, Shopify leaves the rest in a remainingFulfillmentOrder. (L6)
"Why not just push all stock into Shopify and use its inventory?"You can (model each store as a Location), but your source of truth is external POS stock Shopify can't see, so you own availability + reservation and use Shopify for the order. (L2/L5/L8)
"A viral product page — does stock sync slow down?"No — reads run on cache + replica, writes on a separate worker pool; the paths don't share capacity. (L4/L9)
