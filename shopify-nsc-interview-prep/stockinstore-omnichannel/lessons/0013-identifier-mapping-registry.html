Identifier Mapping & the Mapping Registry

Three systems, three sets of names for the same shoe and the same shop. The mapping between them is the least glamorous part of the integration and the one that decides whether it works.

Your win today: build the mapping registry — a real, versioned, auditable table that joins Shopify ↔ POS/ERP ↔ vendor identifiers. Learn Shopify's own identifier traps (SKU is not unique, GID vs legacyResourceId, no store-code field on Location), the four-step match ladder, and why 97% mapping coverage is a failing grade.

This is Lesson 2 §4 promoted to its own lesson, because in Track B it is a bigger share of the work. In the build-it track you own both ends of the join. Here you own neither, and there are three namespaces instead of two.

1. Three namespaces, one shoe

The same physical red shoe, size 42, sitting on a shelf in Geelong, has at least four names and the shop has three:

THE SAME RED SHOE, SIZE 42 SHOPIFY POS / ERP VENDOR (stockinstore) ─────────────────────── ─────────────────────── ─────────────────────── ProductVariant.id ItemCode "0042-RD" product_ref "SKU1001" gid://shopify/…/44821 ProductID 88213 store_ref "VIC-GEE" ProductVariant.sku Barcode "0093672841003" "SHOE-RED-42" StoreCode "GEE" ProductVariant.barcode OutletID 17 "9336728410034" (UoM: CASE of 6) InventoryItem.id Location.id gid://shopify/Location/72 Location.legacyResourceId 72 ▲ ▲ ▲ └────────────┬───────────┴──────────────┬───────────┘ │ │ ┌──────────────────────────────────────┐ │ THE MAPPING REGISTRY │ ← you own this │ canonical sku · canonical location│ │ + one row per (namespace, external) │ └──────────────────────────────────────┘ Notice the barcode: Shopify has 9336728410034, the POS has 0093672841003. Same barcode. Different length, leading zero, different check-digit handling. That single row is a week of someone's life if you don't plan for it.
The rule that makes this tractable Never map namespace-to-namespace. Map every namespace to one canonical identifier that you own. Three systems mapped pairwise is 6 mappings; three mapped to a hub is 3. Add a fourth system (a second POS after an acquisition) and pairwise becomes 12 while the hub becomes 4.

2. Shopify's own identifier traps

You will be asked to join "on the SKU." Here is why that sentence hides four problems.1

TrapWhat Shopify actually saysWhat it does to you
SKU is not uniqueProductVariant.sku is "a case-sensitive identifier for the product variant in the shop" — the docs do not state a uniqueness requirement, and Shopify does not enforce one.Your join on SKU can return two variants. A merchant with a duplicated or blank SKU silently breaks one product. Check for duplicates before you trust the join, and report them as data defects.
SKU is case-sensitiveStated on the field itself.shoe-red-42 and SHOE-RED-42 are two different SKUs to Shopify but the same thing to a human and often to a POS. Normalise on the way in — and record that you normalised.
GID vs legacyResourceIdid is "a globally-unique ID"; legacyResourceId is "the ID of the corresponding resource in the REST Admin API", typed UnsignedInt64.Two different values for the same object. Store the GID as the key and the numeric id only as a convenience — a vendor or a CSV that carries 72 instead of gid://shopify/Location/72 will not join, and the failure looks like "no stock" rather than an error.
Location has no store-code fieldThe object exposes id, legacyResourceId, name, address, isActive, fulfillsOnlineOrders, localPickupSettingsV2 — and nothing for the retailer's own store code.The retailer's GEE lives nowhere in Shopify by default. You either keep it in your registry or put it in a metafield on the location. Do not match on name; someone will rename "Geelong" to "Geelong (Westfield)" on a Friday.
SKU is required for fulfillment servicesThe sku docs note it is "required in order to connect to a fulfillment service."If the vendor's app registers as a fulfillment service (L15), blank SKUs are not a data-quality nag — they are a hard blocker. Find them in discovery.
The trap juniors fall into Treating sku as a primary key because it looks like one. It is a free-text field a merchant types. It can be blank, duplicated, have trailing whitespace, differ in case, or be reused after a product is deleted. Your registry needs its own key, and SKU is just one of the columns you match on.

3. The registry, as a real schema

One canonical table per entity, plus one alias table per entity. The alias table is where every external namespace lands.

-- ---------- canonical: the hub. Yours. Never a vendor's id. ----------
CREATE TABLE canon_product (
  retailer_id  TEXT NOT NULL,
  product_key  TEXT NOT NULL,          -- your own opaque key, e.g. 'p_01H8Z…'
  title        TEXT,
  uom          TEXT NOT NULL,          -- the unit YOU store in: 'EACH'
  active       BOOLEAN NOT NULL DEFAULT TRUE,
  PRIMARY KEY (retailer_id, product_key)
);

CREATE TABLE canon_location (
  retailer_id  TEXT NOT NULL,
  location_key TEXT NOT NULL,
  name         TEXT,
  lat          NUMERIC, lng NUMERIC,
  timezone     TEXT NOT NULL,          -- stores span zones (L2 §1)
  active       BOOLEAN NOT NULL DEFAULT TRUE,
  PRIMARY KEY (retailer_id, location_key)
);

-- ---------- aliases: one row per (namespace, id type, external value) ----------
CREATE TABLE product_alias (
  retailer_id   TEXT NOT NULL,
  namespace     TEXT NOT NULL,   -- 'shopify' | 'pos:retail-express' | 'vendor'
  id_type       TEXT NOT NULL,   -- 'variant_gid' | 'sku' | 'barcode' | 'item_code'
  external_id   TEXT NOT NULL,   -- stored EXACTLY as the source sends it
  external_norm TEXT NOT NULL,   -- normalised form used for matching (§4)
  product_key   TEXT NOT NULL,
  uom_factor    NUMERIC NOT NULL DEFAULT 1,  -- source unit → canonical unit
  confidence    TEXT NOT NULL,   -- 'exact' | 'barcode' | 'normalised' | 'manual'
  approved_by   TEXT,            -- who accepted a non-exact match, and when
  valid_from    TIMESTAMPTZ NOT NULL DEFAULT now(),
  valid_to      TIMESTAMPTZ,     -- NULL = current. Never DELETE a mapping.
  PRIMARY KEY (retailer_id, namespace, id_type, external_id, valid_from)
);
CREATE UNIQUE INDEX one_current_alias
  ON product_alias (retailer_id, namespace, id_type, external_norm)
  WHERE valid_to IS NULL;        -- at most one live mapping per external id

Five design choices in there earn their keep:

  • Both external_id and external_norm. You match on the normalised value but you must be able to echo back the exact string the source sent, or you cannot debug anything or write back to the POS.
  • valid_from / valid_to instead of DELETE. Store codes get reused. A SKU gets retired and reissued. If you delete the old row you lose the ability to explain last month's orders. Close it, don't kill it.
  • The partial unique index. It enforces "one live mapping per external id" while still allowing history. Without it, two overlapping mappings send the same shelf stock to two products.
  • confidence + approved_by. A machine-guessed match and a human-confirmed match are not the same fact, and you will be asked which is which.
  • uom_factor on the alias, not the product. The same shoe can arrive in eaches from one store and cases of 6 from another. The factor belongs to the source, so it lives on the alias row.

4. The match ladder — four rungs, then a human

Matching is a ladder, tried in order. Each rung is weaker than the one above, and the rung you used is recorded as confidence.

#RungHowTrust
1Explicit idThe source sends the Shopify variant GID or a previously-agreed key. Direct lookup.Highest. Auto-accept.
2Barcode / GTINNormalise (strip spaces, pad to 13 or 14 digits, decide once about the check digit) then match. Barcodes are assigned by the manufacturer, so they survive both systems.High. Auto-accept if exactly one hit.
3Exact SKUByte-for-byte match, case included.High only if the SKU is unique in both systems. Auto-accept when the hit count is 1; quarantine when it is 2+.
4Normalised SKUUppercase, trim, collapse inner whitespace, strip a documented separator set. Deterministic and written down.Medium. Queue for human approval, don't auto-accept.
—Fuzzy / title similarityLevenshtein on titles, "looks like" matching.Never automatic. Use it only to suggest to a human, and store the result as manual with the approver's name.
Why fuzzy matching is a trap, not a shortcut A fuzzy match that is 99% accurate on 50,000 SKUs mislabels 500 products. Each one sends a customer to a shop for the wrong item, or shows a product out of stock that is on the shelf. Both are worse than an honest gap, because a gap is visible on a report and a wrong match is not. Suggest, never decide.

5. Normalisation, written down once

Normalisation is only safe if it is deterministic and documented, because you will re-run it and it must give the same answer.

// The normaliser is a pure function. Version it; log the version on the alias row.
export const NORM_VERSION = 3;

export function normSku(raw: string): string {
  return raw
    .normalize('NFKC')          // full-width characters from a Japanese POS export
    .trim()
    .toUpperCase()
    .replace(/\s+/g, ' ');      // collapse inner whitespace only — do NOT delete it
}

export function normBarcode(raw: string): string {
  const digits = raw.replace(/\D/g, '');            // strip spaces, dashes
  if (digits.length === 0) return '';
  // UPC-A (12) → EAN-13 by left-padding. Decide ONE canonical width and stick to it.
  if (digits.length === 12) return '0' + digits;
  if (digits.length === 13) return digits;
  if (digits.length === 14) return digits.replace(/^0+/, '').padStart(13, '0'); // GTIN-14
  return digits;                                     // record, flag, let a human look
}
The leading-zero disaster (this is not hypothetical) A retailer sends a nightly CSV. Someone opens it in Excel to check it. Excel reads the barcode column as a number and drops the leading zero: 0093672841003 becomes 93672841003. Saved. Now that store's entire barcode column fails to match. The fix is threefold: never match on raw barcodes, always pad to a canonical width, and reject a file whose barcode column has changed length distribution since yesterday. Add the last check as a feed-level guard, not a per-row one.
Why replace(/\s+/g, ' ') and not replace(/\s/g, '') Deleting all whitespace merges genuinely different SKUs: AB 12 and A B12 both become AB12. Collapsing runs of whitespace fixes formatting noise without inventing collisions. Every normalisation step must be checked for "does this create a collision that didn't exist?" — and the answer belongs in a test.

6. Coverage is the project's real progress bar

"We're integrated" is not a status. Mapping coverage is, and it is the number you report weekly.

-- coverage, weighted by what actually matters: stock, not row count
SELECT
  l.location_key,
  COUNT(*)                                             AS feed_rows,
  COUNT(a.product_key)                                 AS mapped_rows,
  ROUND(100.0 * COUNT(a.product_key) / COUNT(*), 2)    AS pct_rows_mapped,
  -- the honest one: how much STOCK is invisible?
  ROUND(100.0 * SUM(CASE WHEN a.product_key IS NULL THEN f.qty ELSE 0 END)
              / NULLIF(SUM(f.qty), 0), 2)              AS pct_units_unmapped
FROM feed_staging f
JOIN canon_location l ON l.location_key = f.location_key
LEFT JOIN product_alias a
       ON a.retailer_id = f.retailer_id
      AND a.namespace   = f.namespace
      AND a.external_norm = f.external_norm
      AND a.valid_to IS NULL
GROUP BY l.location_key
ORDER BY pct_units_unmapped DESC;      -- worst store first
97% is a failing grade — say the number out loud 50,000 SKUs at 97% coverage means 1,500 products are invisible in Find in Store. Nobody gets an error. The widget just says "not available nearby" and the customer leaves. Compare that to a broken deploy, which everyone notices in ten minutes. Set the acceptance bar as a number in the contract — ≥99.5% of units mapped, and a named owner for the remainder — and put the unmapped list in front of the retailer's merchandising team every week, because only they can fix it.

Weight by units, not rows. A thousand unmapped end-of-line SKUs with one unit each matter far less than fifty unmapped best-sellers with two hundred units each. The pct_units_unmapped column is the one that predicts complaints.

7. Diagnosing "the widget says no stock"

This is the single most common support ticket in Track B. It has six possible causes and they are cheap to separate in this order.

"Product X shows no stock at store Y, but it's on the shelf" │ ▼ 1. Is store Y in canon_location and active? ──── no ──► location never mapped / deactivated │ yes ▼ 2. Did a feed arrive for Y recently? ──── no ──► connector / source problem (L12) (MAX(source_ts) for that location) │ yes ▼ 3. Was product X in that feed at all? ──── no ──► POS didn't report it: wrong POS store, item not stocked │ yes ▼ 4. Did that feed row map to a product_key? ──── no ──► MAPPING GAP ← most common │ yes ▼ 5. Did we send it? (shadow table, L12 §5) ──── no ──► suppressed / DLQ / 4xx │ yes ▼ 6. We sent qty > 0 and the vendor shows 0 ─────────► vendor-side: threshold, buffer, reservation, or their bug → ticket Steps 1–5 are yours and take minutes. Only step 6 is a vendor conversation, and by then you can attach exactly what you sent and when.

8. Failure modes

What breaksHow you handle it
Two Shopify variants share one SKUThe join returns 2 rows. Quarantine both, alert as a data defect, and ask the merchant to fix the catalogue. Never pick one arbitrarily — you will pick wrong for half the orders.
Blank SKU on a variantExcluded from matching entirely (never match blank to blank). Report it; it is also a hard blocker if the vendor registers as a fulfillment service.
A store code is reused for a new shopThe old alias is closed with valid_to, a new row opens. History still explains old orders. This is exactly why you never DELETE.
Excel strips leading zeros from a barcode columnCanonical padding in normBarcode, plus a feed-level guard that rejects a file whose barcode length distribution shifted overnight.
New products arrive daily and are unmapped for a dayAuto-map rungs 1–3 on arrival, on a schedule, not only at onboarding. An integration that only maps once is out of date the week it launches.
A case-pack source is mapped without a UoM factorYou report 1 when 6 are on the shelf (undersell) or 6 when 1 is (oversell). uom_factor is mandatory on every alias row; default 1 must be a decision, not an omission.
Someone edits the registry by hand in productionEvery change goes through the same code path with approved_by and a timestamp. An unaudited mapping change is indistinguishable from a bug three weeks later.
Vendor renames a store referenceTheir side of the alias closes and reopens. Because the hub key never changed, nothing downstream moves — that is the payoff for not mapping pairwise.
Say it like this (mapping in 6 sentences)

"Identifier mapping is where integrations actually fail, so I treat it as a real component with a schema, not a spreadsheet. I map every namespace — Shopify, each POS or ERP, and the vendor — to one canonical key I own, because a hub scales linearly while pairwise mappings explode as systems are added. I keep both the raw external id and a normalised form, with a versioned pure-function normaliser, and I never delete a mapping — I close it with a valid_to so history still explains last month's orders. Matching is a ladder: explicit id, then barcode, then exact SKU, then normalised SKU, and fuzzy matching only ever suggests to a human, because a 99%-accurate guess on fifty thousand SKUs is five hundred wrong products with no error message. I watch Shopify's own traps: SKU is case-sensitive and not enforced unique, the GID is not the legacyResourceId, and Location has no field for the retailer's store code, so that lives in my registry or a metafield — never in the location's name. And I report coverage weighted by units, not rows, because 97% of fifty thousand SKUs is fifteen hundred products that silently show 'not available nearby' and nobody ever gets an alert."
