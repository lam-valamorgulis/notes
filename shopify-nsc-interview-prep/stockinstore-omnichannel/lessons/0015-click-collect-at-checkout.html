Click & Collect at Checkout (Integration POV)

"Does Click & Collect work on our plan?" has three different correct answers, depending on which of the three layers you mean. Getting that answer wrong is how a project gets re-scoped in week six.

Your win today: separate C&C into its three layers — pre-checkout store choice, the checkout delivery method, and post-checkout fulfilment — and give the plan answer for each. Learn the scope trap that breaks "always pick the narrowest scope", and the 2026 change that invalidates one line of code in most integrations: ship and pickup can now be in one order.

The build-it version of this is Lesson 5, where you own the reservation. Here the vendor reserves, and your job changes shape completely — the hard part is no longer atomicity, it is not double-counting.

1. C&C is three layers, not one feature

LAYER 1 · BEFORE CHECKOUT LAYER 2 · IN CHECKOUT LAYER 3 · AFTER CHECKOUT ────────────────────────── ───────────────────── ──────────────────────── shopper picks a store on the shopper picks "Pick up" order → delivery group → PDP or in the cart as the delivery method fulfillment order with deliveryMethod = PICK_UP owner: the VENDOR's widget owner: SHOPIFY │ + your cart attribute (native local pickup) ▼ (L14 §7) staff pick it │ plan gate: none for a widget plan gate: native local ▼ (vendor may impose one) pickup = all plans; fulfillmentOrderLineItems CHECKOUT-STEP UI PreparedForPickup extensions = PLUS ONLY │ ▼ "Ready For Pickup" customer notified │ ▼ fulfillmentCreate → fulfilled Three layers, three owners, three different plan answers. Most "we can't do C&C on this plan" claims confuse layer 2's Plus gate with layer 1 or 3, which have no such gate.

The distinction that makes you sound senior There are two independent gates: Shopify's and the vendor's. Shopify lets a Basic store do local pickup. stockinstore's own Click & Collect app targets Shopify Plus. So "can we do Click & Collect on Basic?" splits into: the platform, yes; this vendor's C&C product, no. A retailer on Basic can still ship the feature — with native local pickup, the vendor's Find-in-Store widget for stock visibility, and pickup fulfilment handled through Shopify. Say that, and you have turned a blocker into a scoped option.

Vendor plan requirements and packaging change. Re-read the vendor's own page and the app listing at the start of every project, and put the date next to the claim in your notes — exactly as this course does.

3. What the order actually looks like

Layer 3 is Shopify's model, and it is the part you must be precise about because your write-back depends on it.

# One order, its delivery groups, and the fulfillment orders they produce.
query PickupOrder($id: ID!) {
  order(id: $id) {
    name
    attributes { key value }              # ← your cart-attribute store code (L14 §7)
    fulfillmentOrders(first: 10) {
      nodes {
        id
        status                            # OPEN = a to-do, not "done"
        requestStatus
        deliveryMethod { methodType }     # PICK_UP | SHIPPING | ...  ← iterate, never assume
        assignedLocation { name location { id } }
        lineItems(first: 50) { nodes { id totalQuantity } }
      }
    }
  }
}
A fulfillment order is a to-do list, not a completed job status: OPEN means "someone still has to do this." It is not "fulfilled." This trips people up because the object is named for the noun, not the state. Marking pickup ready and then fulfilling are two separate later steps — see §4.

4. The pickup fulfilment sequence, with exact mutations

  1. Order placed with pickup. Shopify creates a fulfillment order whose deliveryMethod.methodType is PICK_UP, assigned to the pickup location.
  2. Store staff pick the item. This happens in the vendor's store-collection screen, in Shopify POS, or in the retailer's own tool — whichever the project chose.
  3. Mark it ready. fulfillmentOrderLineItemsPreparedForPickup, taking FulfillmentOrderLineItemsPreparedForPickupInput!. This marks the line items ready and sends the customer a "Ready For Pickup" notification.1
  4. Customer collects. Someone confirms the handover.
  5. Fulfil. fulfillmentCreate closes it out; stock and finance write-back follows (L16).
The scope trap — this breaks a rule you learned in Lesson 11 fulfillmentOrderLineItemsPreparedForPickup requires the write_merchant_managed_fulfillment_orders access scope.1 Pickup at the retailer's own shop is merchant-managed, so the narrower write_assigned_fulfillment_orders — which covers fulfillment orders assigned to a registered fulfillment service — is not enough. "Always pick the narrowest scope" is right as a principle and wrong as a shortcut: the correct scope is determined by who owns the location, not by which name sounds smaller. Check the mutation's documented scope, every time.
Three fulfillment-order scope families, one decision read/write_assigned_fulfillment_orders — fulfillment orders assigned to your app acting as a fulfillment service, which gets its own dedicated Shopify location. read/write_merchant_managed_fulfillment_orders — orders fulfilled from the merchant's own locations, which is what a retail store is. read/write_third_party_fulfillment_orders — an external service's. So the question to answer first is architectural: is the vendor registered as a fulfillment service, or operating on the merchant's own locations? The scope list follows from that answer, not the reverse.

5. The 2026 change: ship and pickup in one order

Shopify Plus and Enterprise merchants can now let a customer choose shipping and store pickup in one checkout, instead of placing two orders. It is in feature preview, effective 2026-04-23, and the changelog marks it "Action required" for app developers.1

What changed, and what didn't No new API fields and no breaking schema change. What changed is the combinations your data can now hold: "Checkouts can have multiple deliveryGroups: each group represents how different items are to be fulfilled", and "orders can contain fulfillment order with different delivery methods (SHIPPING and PICK_UP) within the same order." The required action is blunt — find and remove any logic that "assumes a single delivery method per order." 
// ✘ The line that is now a bug. It was correct for years.
const isPickup = order.fulfillmentOrders.nodes[0].deliveryMethod.methodType === 'PICK_UP';
if (isPickup) notifyStore(order);           // silently wrong on a mixed order

// ✔ Iterate every fulfillment order and act per group.
for (const fo of order.fulfillmentOrders.nodes) {
  switch (fo.deliveryMethod?.methodType) {
    case 'PICK_UP':  await notifyStore(fo);         break;   // one store, some lines
    case 'SHIPPING': await routeToWarehouse(fo);    break;   // other lines, elsewhere
    default:         await logUnhandled(fo);        break;   // fail loud, not silent
  }
}
Why this deserves a paragraph in your integration audit The old code does not crash. It reads the first fulfillment order, decides the whole order is a pickup or a shipment, and gets it half right. Half an order gets notified to a store; the other half is never routed. Nothing errors. Every integration written before this change has that assumption somewhere — in the write-back, the store notification, the finance record, or a reporting query. Grep for [0] on fulfillmentOrders and for any single isPickup boolean hanging off an order.

6. Who reserves? The double-count problem

In Lesson 5 you built the reservation yourself, and the hard part was atomicity. In Track B the vendor reserves. The hard part becomes arithmetic.

FactWho owns it in Track BYour rule
Physical on_hand at a storeThe POS/ERPRelay it as an absolute number (L12). Never subtract anything from it first.
Reserved for a pickup orderThe vendorDo not model it. Do not send a reduced figure. Their engine subtracts it.
Shopify's committed / reservedShopifyIf you publish stock into Shopify locations at all, write raw on_hand and let Shopify compute available itself.
The order and its fulfillment ordersShopifyRead them; don't duplicate their state in your database.
The double-count bug, concretely Shelf has 5. One pickup order for 1 is in flight. The vendor reserves 1 and shows 4 — correct. Your connector "helpfully" subtracts the open order too and sends 4. The vendor reserves 1 from that and shows 3. Now the last two units are invisible; at scale a store looks empty while stock sits on the shelf. Send the raw physical count. Subtracting is the engine's job, and there is exactly one engine.

7. Notifications: two senders, one customer

The customer can now receive "your order is ready" from two places — Shopify's own notification triggered by fulfillmentOrderLineItemsPreparedForPickup, and the vendor's store-collection tooling. Decide which one owns that message, in writing, before launch.

  • Shopify owns it — the vendor's tool calls the mutation, Shopify emails the customer. One template, merchant-branded, one place to edit. Usually the right answer.
  • The vendor owns it — richer content (a map, opening hours, a QR code), but a second sender and a second template to maintain. Then Shopify's notification must be turned off, or the customer gets two emails.
  • Both fire — the default if nobody checks. Two "ready to collect" emails, sometimes with different wording. It looks broken because it is.

8. Failure modes

What breaksHow you handle it
"Pick up" never appears at checkoutLocal pickup must be enabled per location, and the location must be active and able to fulfil online orders (isActive, fulfillsOnlineOrders, localPickupSettingsV2). Check the location, not the plan.
Vendor's C&C app needs Plus, retailer is on AdvancedDon't declare it impossible. Native local pickup + the Find-in-Store widget + Shopify-side pickup fulfilment covers the core journey. Scope the gap explicitly and price the plan upgrade as an option.
Marking ready fails with an access errorThe scope trap: pickup at the merchant's own store needs write_merchant_managed_fulfillment_orders. Re-request scopes and have the merchant re-approve — that is a merchant action, so plan for it.
Mixed ship + pickup order handled half-rightIterate every fulfillment order and switch on deliveryMethod.methodType. Audit for fulfillmentOrders[0] and for any order-level isPickup flag.
Stock looks lower than the shelfDouble-count: something is subtracting reservations twice. Send raw on_hand; exactly one system reserves.
Customer gets two "ready" emailsTwo notification owners. Pick one; disable the other. Decide before launch, not after the first complaint.
Order arrives with no store codeThe widget didn't write the cart attribute, or the shopper reached checkout another way (a saved cart, a direct link, a draft order). Fulfilment needs a documented fallback: read the pickup location off the fulfillment order's assignedLocation.
Store rejects a pickup order (item damaged, not found)This is the vendor's allocation problem in Track B, but you own the write-back and the customer-facing outcome. Confirm in discovery: does the vendor reroute, cancel, or hand it back? Then make sure your POS write-back matches whichever it does.
Pickup enabled at a location that never fulfilsCustomers choose a store that ignores its queue. Availability engines cannot fix an ops problem — this belongs in the store-readiness checklist in L18.
Say it like this (C&C in the integration case, 6 sentences)

"I split Click & Collect into three layers, because 'does our plan support it?' has a different answer for each. Layer one is the pre-checkout store choice — the vendor's widget plus a cart attribute, no Shopify plan gate. Layer two is the checkout delivery method: native local pickup works on all plans, and only checkout UI extensions for the information, shipping and payment steps are Shopify Plus only — so the common claim that C&C needs Plus usually confuses those two. Layer three is fulfilment: Shopify creates a fulfillment order with deliveryMethod.methodType = PICK_UP, staff pick it, then fulfillmentOrderLineItemsPreparedForPickup marks it ready and sends the customer Shopify's 'Ready For Pickup' notification, and fulfillmentCreate closes it. Two traps I check every time: that mutation needs write_merchant_managed_fulfillment_orders because a retail store is a merchant-managed location — so 'pick the narrowest scope' is decided by who owns the location, not by which name sounds smaller — and since 2026 a single order can contain both SHIPPING and PICK_UP fulfillment orders on Plus and Enterprise, so any code reading fulfillmentOrders[0] is now silently half-wrong. And I remember the second gate is commercial, not technical: stockinstore's own Click & Collect app targets Shopify Plus while their Find in Store app runs on Basic, so on a lower plan I scope the journey around native local pickup instead of calling it impossible."
