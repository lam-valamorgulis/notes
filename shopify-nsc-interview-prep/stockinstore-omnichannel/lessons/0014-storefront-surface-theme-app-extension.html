The Storefront Surface: Theme App Extensions in Depth

The vendor ships the widget. You decide where it goes, what context it gets, when it refreshes, and whether it slows every product page in the shop. Those four decisions are yours, and three of them are usually got wrong.

Your win today: know the exact difference between an app block and an app embed block (different target values, different theme support, different way merchants turn them on), recite the real extension limits, solve the variant-change problem that makes a widget show stock for the wrong size, and hold a third-party widget to a performance budget you can defend.

Deepens connection point 4 from Lesson 11. The read path it talks to is Lesson 4, except the API belongs to the vendor now.

The sentence that settles the "why is the widget not showing?" ticket Both block types are off after install. An app block is disabled until a merchant adds it to a section; an app embed block is deactivated until a merchant switches it on under Theme settings → App embeds. So "I installed the app and nothing happened" is not a bug — it is the documented default, and it is a step in your rollout plan.1
Which one does a Find-in-Store button want? An app block, targeting section. It belongs inside the product section, under the variant picker, positioned by the merchant. An app embed block cannot be placed per-section — it is global. If a vendor only ships an app embed block for a per-product feature, they are asking the shopper's browser to find the right DOM node and inject into it, which breaks the first time the theme changes. That is a question worth asking during vendor selection.

2. The real limits (know these before you promise anything)

LimitValueWhy you care
Total extension size10 MBEnforced. A vendor bundling a map library and icon fonts can hit it.
Number of blocks30Plenty for one vendor, tight if several apps' features live in one extension.
Locale files100, each max 15 KBMulti-region retailers translate the widget's strings. 15 KB per locale is small.
Liquid content100 KB across all filesLiquid is for markup and settings, not logic. If a vendor's block is near this, something is wrong.
CSS (suggested)100 KB compressedSuggested, not enforced — but it is the number to quote when the widget's CSS is 400 KB.
JavaScript (suggested)10 KB compressedThe one to hold a vendor to. 10 KB is a deliberate signal: a storefront widget should be small.

The CSS and JS numbers are suggested, and vendors exceed them. That is exactly why they are useful to you: they turn "the widget feels heavy" into "Shopify's suggested budget is 10 KB compressed for JavaScript; yours is 180 KB — can we get a slim build?" A number changes that conversation.

3. What a block actually looks like

You will read the vendor's block, not write it. Reading it tells you what context it receives — which is the root of most widget bugs.

Read selected_or_first_available_variant again That value is rendered once, on the server, when the page is built. It is the variant that was selected when the HTML was generated — usually the first available one. The moment the shopper picks a different size, that data-variant-id is stale. Everything in §4 follows from this one line.
Settings are your lever Every settings entry is something a merchant can change in the theme editor without a developer. Search radius, whether to show "low stock", the button label. During rollout, the ability to change the radius per store network without a deploy is worth more than it looks. When you evaluate a vendor's block, read its settings array — it tells you what is configurable and, by omission, what needs a support ticket.

4. The variant-change problem

This is the integration bug the retailer will find on day one, and it is nobody's fault in particular — which is why it lands on you.

SERVER RENDER SHOPPER ACTION WIDGET STATE ───────────────────── ─────────────────── ───────────────── product page built variant = 42 (first available) data-variant-id="44821" ────────────────────────────────────────► shows stock for 42 ✔ correct shopper clicks size 45 theme JS updates: • price • images • ?variant=44822 in URL • the add-to-cart form │ ▼ nothing told the widget ──────► STILL shows 42 ✘ wrong, and silent The customer drives to a shop for a size 45 that was never there. The widget did exactly what it was told. Bridging this gap is YOUR job.

Three ways to close it, best first:

  1. The vendor's widget listens for the theme's variant event. Ask in vendor selection: "which variant-change signal does the widget subscribe to?" If the answer is a specific documented event, good.
  2. You bridge it with a few lines in the theme, because Dawn-style themes publish variant changes and most themes also update ?variant= in the URL. This is the realistic answer.
  3. Hide the widget on multi-variant products. Ugly, but honest, and better than lying about stock. A legitimate temporary state during rollout.
// A defensive bridge: listen for the theme's own signal, and fall back to the URL.
// Placed in the theme (or an app embed block) because it is glue, not vendor code.
(function () {
  const el = document.getElementById('sis-find-in-store');
  if (!el) return;

  function refresh(variantId) {
    if (!variantId || String(variantId) === el.dataset.variantId) return;
    el.dataset.variantId = String(variantId);
    // whatever the vendor documents — a method, or a custom event they listen for
    window.stockinstore?.refresh?.({ variantId });
  }

  // (a) Themes that publish a variant-change event (Dawn-family pub/sub, custom events…).
  //     Confirm the exact event name against the theme you are on — it is theme-specific.
  document.addEventListener('variant:change', (e) => refresh(e.detail?.variant?.id));

  // (b) Fallback that works on nearly every theme: the URL's ?variant= parameter.
  let last = new URL(location.href).searchParams.get('variant');
  const check = () => {
    const now = new URL(location.href).searchParams.get('variant');
    if (now !== last) { last = now; refresh(now); }
  };
  window.addEventListener('popstate', check);
  // history.replaceState doesn't fire an event, so poll cheaply as a last resort
  setInterval(check, 500);
})();
Why the fallback is not embarrassing There is no single cross-theme variant-change event in Shopify. Dawn-family themes use their own publish/subscribe module; other themes dispatch their own custom events; some only update the URL. A bridge that tries the documented event and watches ?variant= is not sloppy — it is the honest response to a platform where the theme, not Shopify, owns that moment. Write down which theme you verified it against, because a theme upgrade can change it.

5. Performance: a third-party script on every product page

The widget is now in the critical path of the retailer's best-converting pages. Hold it to numbers.1

Metric"Good" thresholdHow the widget breaks itThe fix you ask for
LCP — largest contentful paint≤ 2.5 sA blocking <script> in head, or a synchronous stylesheet, delays the hero image.defer the JS; never let the widget's fetch gate first paint.
CLS — cumulative layout shift≤ 0.1The widget renders after the API answers, pushing the add-to-cart button down. The worst case is a shopper tapping the wrong thing.Reserve the space: a fixed min-height skeleton from first paint.
INP — interaction to next paint≤ 200 msA heavy widget script busy on the main thread when the shopper taps a size.Smaller bundle, no synchronous work on load, lazy-load the map.

All three are assessed at the 75th percentile of page loads, split by mobile and desktop — so "it's fast on my laptop" is not an answer. Mobile at p75 is the bar.

Four things to insist on, in order of value (1) Reserve the space. A skeleton with the widget's final height removes its entire CLS contribution for one line of CSS — the highest-value fix here. (2) defer, never blocking. (3) Lazy-load below the fold. If the locator map is below the fold, load it on intersection, not on page load. (4) Time-box the request. A 2-second client-side timeout with a graceful empty state; the vendor's slow day must not become the retailer's slow day (L17).
Measure it, don't assume it Compare the same product page with the app embed activated and deactivated — that toggle is a genuine A/B switch that needs no code. Run both through a lab tool and check field data, because a widget that is fine on a fast connection can be the worst thing on the page over 3G. Do this before the rollout meeting, so the number is yours and not the vendor's.

6. The browser talks to the vendor, not to you

A storefront widget calls the vendor's API directly from the shopper's browser. Three consequences:

  • The key in the theme is public. Anything in a block's Liquid or a JS asset is readable by anyone. It must be a read-only, per-shop, rate-limited key. If a vendor hands you a key that can write, escalate — that is a security defect, not a configuration choice.
  • CORS is the vendor's to configure. Their API must allow the shop's domain. Every extra domain — a second market, a custom checkout domain, a staging store — needs adding. A launch that works on *.myshopify.com and fails on the live domain is almost always this.
  • The response is public data. Whatever the widget can read, a competitor can read at scale. So the widget should return a state and an age ("in stock", "low", "updated 8 minutes ago") rather than an exact count — the same conclusion as Lesson 4, now for a commercial reason as well as a trust one.

7. Carrying the chosen store forward — the cart-attribute bridge

The shopper picks "Geelong" on the product page. Checkout happens later, in Shopify, where your widget does not exist. How does the store choice survive?

// Persist the shopper's choice on the CART, so it lands on the ORDER.
await fetch('/cart/update.js', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    attributes: {
      'Pickup store':      'Geelong',
      'Pickup store code': 'VIC-GEE'   // the code YOUR systems join on (L13)
    }
  })
});
// cart.attributes → order.attributes: fulfilment can read the store code off the
// order with no app call and no webhook. See the POS sub-course for this pattern.
Why this matters even when the vendor handles pickup Two reasons. One: it gives you a copy of the shopper's intent inside Shopify, so when the vendor and Shopify disagree you have a third record that neither side controls. Two: it is your escape hatch. If the vendor is ever replaced (L19), the store code is already on every historical order in a format you own. Cheap to add on day one, impossible to back-fill later.

8. Failure modes

What breaksHow you handle it
Widget doesn't appear at allExpected default: app blocks are disabled and app embeds deactivated after install. Check the theme editor first — the Apps picker inside the section, or Theme settings → App embeds.
Appears on one template, not anotherApp blocks live in sections. A different product template, or a section that doesn't accept app blocks, has no block. Add it per template.
Disappears after a theme changeBlock placement is theme-specific data. Duplicating or replacing a theme does not carry it. Add "re-add the app block" to the theme-deploy checklist — this catches teams every single time.
Shows stock for the wrong sizeThe variant-change gap (§4). Bridge the event, or hide the widget on multi-variant products until you can.
Works on the preview domain, fails liveCORS on the vendor's side, or a per-domain key. Enumerate every domain — live, myshopify.com, markets, staging — during discovery.
Product page gets slower after launchMeasure with the app embed on and off. Ask for the deferred, smaller build; quote the 10 KB suggested JS budget. Reserve space to kill the CLS contribution.
Add-to-cart button jumps as the widget loadsPure CLS. Fixed min-height skeleton. Highest value for the least code on this whole page.
Vendor API is slow or downClient-side timeout, graceful empty state, never block add-to-cart. Detailed in L17.
Vintage theme, no app blocksApp embed blocks do support vintage themes; a per-product inline button generally does not. Either upgrade the theme or accept a ScriptTag-era integration and its fragility. Say which, in writing.
Say it like this (the storefront surface in 6 sentences)

"The vendor ships the widget, but placement, context, refresh and performance are mine. I use a theme app extension app block targeting section for a per-product Find-in-Store button, because it drops into the product section from the theme editor with no theme-code edits and cleans up on uninstall — app embed blocks target head, compliance_head or body and are for global or floating things, and they're the only one of the two that supports vintage themes. Both are off after install, so 'I installed it and nothing happened' is the documented default and a step in my rollout plan, not a bug. The bug that always bites is the variant change: the block renders selected_or_first_available_variant once on the server, so switching size silently leaves the widget showing the first size's stock — I bridge the theme's variant event with a ?variant= fallback, because there is no single cross-theme event. I hold the widget to real numbers: reserve its space so it contributes no layout shift, defer the script, time-box the request, and quote Shopify's suggested 10 KB compressed JavaScript budget against LCP 2.5 s, CLS 0.1 and INP 200 ms at the 75th percentile on mobile. And I persist the chosen store as a cart attribute so it flows to order.attributes — that gives fulfilment the store code with no app call, and it means the data is mine if the vendor is ever replaced."
