Ship from Store & the OMS Fairness Allocation

Built from first principles: start from what is unavoidably true, then let the allocation design fall out of it — instead of memorising "the four factors."

Your win today: derive the Order Management System (OMS) allocator from scratch — show why a decision is forced, why "nearest store with stock" must fail, and how coverage, proximity, fairness, a single-shipment preference, a reservation, and a bounded reroute loop each fall out of one irreducible fact.

Same domain as before — it reuses the reservation from Lesson 5 and the availability signal from Lesson 3 — but we rebuild the reasoning from the ground up. Nothing here is "because the pattern says so"; every piece is derived from a fact.

1. First principles: what is unavoidably true?

Before any design, write down only what cannot be argued with. Everything else is derived from these six facts.

#Irreducible fact
F1An order is a set of line items that must reach one customer, one address.
F2Stock is scattered — it sits across many stores (and maybe a warehouse); each location holds only some items, in some quantity.
F3A parcel ships from exactly one location. You cannot post one box from two shops.
F4Every physical action costs: distance costs money and time; each parcel has a fixed pick-pack-postage cost; each store has finite labour per day.
F5A stock number is an estimate (Lessons 2–3), not a guarantee — the chosen store might not really have it.
F6Stores also serve walk-in customers; online-picking labour is a shared, finite resource, not free.
Why start here "The four scoring factors" is an answer. Memorise the answer and you can't defend it when the interviewer changes the question. Derive it from F1–F6 and you can re-derive it live, and justify every weight. That is what "first principles" buys you.

2. A decision is forced — so "allocation" must exist

Put F1, F2 and F3 together. The order needs many items (F1); those items are scattered (F2); but each parcel leaves from one place (F3). So for every line item you are forced to answer: which location ships it? That forced question is allocation. It is not a feature someone added — it is the unavoidable consequence of scattered stock and single-origin parcels.

From first principles F2 (scattered) + F3 (one origin per parcel) → you must choose an origin per line item → allocation exists. And F4 (near is cheaper) + F2 (stores sit near customers) → using a store as the origin can beat a distant warehouse — which is exactly what "Ship from Store" is.

Three consequences the interviewer expects you to name — notice each is a corollary of F2/F4, not a separate idea:

  • Faster, cheaper delivery — a store near the customer means a short parcel journey (F4: distance costs).
  • Fewer lost sales — if the warehouse is out but three stores have it, the order still ships; the whole network is your inventory (F2).
  • Sell stock that would be marked down — a slow-moving item in one store fills an online order instead of being cleared (a business use of F2).

3. Kill the obvious answer — by derivation, not assertion

The first idea everyone has is: "ship from the nearest store that has it." Don't just say it's wrong — show that the facts force it to fail:

The naive rule assumes……but a fact breaks it
the nearest store has everythingF2: it may hold only 1 of 3 items → a split you never planned.
picking one store is freeF4 + F6: the nearest store then gets every order and its finite, shared labour saturates while others sit idle.
the stock number is trueF5: "nearest that has it" may be a stale estimate → the store rejects it.
The trap juniors fall into Optimising one factor (distance) as if the others had zero cost. The moment you accept F4 and F6 — that labour is finite and shared — a single greedy rule is provably wrong, because it externalises the very costs that sink the client's store staff.

4. Derive the cost function — the factors fall out

If a decision is forced (§2) and every action costs (F4), then the right decision is the one with the lowest total cost. So enumerate the real costs — and each cost becomes a scoring factor:

Real cost (from a fact)Becomes the factor
A cancelled order loses the whole sale (F1 — the customer wanted it)Coverage — can this store fill the order at all?
Distance costs money + time (F4)Proximity — near = cheaper, faster
Labour is finite and shared (F4 + F6)Fairness / capacity — spread load, respect the daily limit
Some stock is worth clearing; some stores have cut-offs (business facts)Business rules — tunable boosts / limits

Now a problem: these costs are in different units — kilometres, parcels, labour-hours, dollars. You can't compare them directly. So convert each into one common currency — a weighted score — and pick the highest. The weights are the business's judgement about how many kilometres a parcel is worth, made explicit and tunable.

// score one candidate store for an order (higher = better). Illustrative model.
function scoreStore(store, order) {
  if (!coversAnyLine(store, order)) return -Infinity;         // F2: useless candidate

  const coverage  = fractionOfUnitsInStock(store, order);     // 0..1 — F1: fulfil at all
  const proximity = 1 / (1 + shippingDistanceKm(store, order.dest)); // F4: near = higher
  const capacity  = remainingDailyCapacity(store);            // 0..1 — F4+F6: fairness
  const clearance = clearanceBoost(store, order);             // business rule, tunable

  return  W_COVERAGE  * coverage       // prefer one store that has everything
        + W_PROXIMITY * proximity      // prefer close (cost + speed)
        + W_FAIRNESS  * capacity       // spread load; don't overload one shop
        + W_CLEARANCE * clearance;     // business rule, tunable
}
// pick argmax; if the top store can't cover all lines, allocate the rest to the
// next-best store(s) — a SPLIT (see §5).
Why a transparent weighted score, not a black box Because the weights encode business trade-offs that change (peak season, a struggling store, a clearance push). A linear, weighted score is easy to explain to the client and easy to tune one weight at a time. A machine-learned black box hides exactly the judgement the client needs to control.

5. Derive the objective order — one shipment or many?

The factors say what to measure; now derive what to prioritise, purely from the relative sizes of the costs in F1 and F4:

From first principles → the objective, in order 1. Fulfil at all. A cancelled order loses the whole sale (F1) — bigger than any shipping cost. So coverage is a gate, not a tiebreak. 2. Fewest parcels. Each extra parcel is a fixed pick-pack-postage cost (F4) that usually dominates a little extra distance — so one slightly-farther store that covers everything beats two near stores that split it. 3. Then least distance + balanced load. Only once fulfilment and parcel-count are settled do proximity and fairness break the tie.

This is why splitting is a last resort, not a default: from F3, more origins = more parcels = more fixed cost. Split only when no single store covers the order.

6. Fairness is not kindness — it's internalising a hidden cost

Why does "fairness" deserve to be a first-class term and not a nice-to-have? Because of F6. A cost function that ignores capacity is blind to a real cost — the finite, shared labour of store staff — so it will happily pile every order on the cheapest store until that uncounted cost explodes (staff burn out, walk-in service suffers). Fairness is just putting that externalised cost back into the equation.

  • Capacity-aware — each store has a realistic daily online-pick limit; as it fills, its score drops so work flows elsewhere (F6 as a term in the score).
  • Load spreading — among stores with similar coverage and proximity, rotate (weighted round-robin) so no one shop is always chosen.
  • Protect the shopfloor — a store busy with walk-ins can defer or decline online picks; the OMS routes around a saturated store, never piles on.
The senior framing "Fairness is the client's biggest concern because it protects their people. In cost terms, store labour is a finite shared resource (F6); if my allocator doesn't price it, it externalises it onto the busiest shop. So capacity is a first-class term in the score, exactly alongside stock and proximity — which is what stockinstore means by a 'fairness system.'"

7. The input is an estimate → close the loop

F5 says every allocation is made on an estimate. So an allocation can be wrong the instant a store tries to act on it. A one-shot "decide and hope" design is therefore impossible — the system must be closed-loop: decide → try → if it fails, decide again.

score candidates ─► pick best ─► reserve at that store ─► ask store to fulfil ▲ │ │ accepts ──┴──► pick/pack/ship ─► FULFIL │ rejects / can't └──────────── re-score & reroute ◄──────────────────┘ (release old reserve, (capped: after N tries, escalate) reserve new store)

Two things fall straight out of the facts:

  • A reservation is mandatory (F5 + concurrency). Between deciding and the store acting, a Click & Collect buyer (Lesson 5) could take the unit. So the decision must be committed atomically — the guarded reserve from Lesson 5 — or your allocation is undercut a second later.
  • The reroute loop must be bounded (F4: each attempt costs time). Retrying forever can flap an order between stores and never ship it. So cap attempts, then escalate to a human or the warehouse, and record why each store rejected.

8. Map the decisions onto Shopify (the "how")

Everything above is platform-agnostic. Now bind each derived decision to a concrete Shopify mechanism — this is where the OMS meets the platform.

order placed ─► Shopify order routing creates FULFILLMENT ORDER(s) per location │ ▼ YOUR OMS scores candidates (coverage × proximity × fairness) §4 │ decision ▼ fulfillmentOrderMove(id, newLocationId) ── place work at the chosen store (or fulfillmentOrdersReroute to let Shopify pick per routing settings) │ reserve at that store (Lesson 5); Shopify → committed ▼ store ACCEPTS ─► pick / pack ─► hand to carrier ─► FULFIL (+ tracking) │ store REJECTS / can't ─► reroute to next-best ─► (repeat, capped) §7
  • Shopify creates fulfillment orders at a location when the order is placed (its built-in routing). Recall from Lesson 5: a fulfillment order is a to-do, not "fulfilled".
  • Your OMS overrides the choice with fulfillmentOrderMove(id, newLocationId) — reassigning the unfulfilled line items to your scored winner. The platform enforces F5 for you: the move fails if the destination doesn't stock the item, and if only some lines are stocked there, the rest stay in a remainingFulfillmentOrder — the split from §5 falls out of the API itself.
  • Or reroute with fulfillmentOrdersReroute to let Shopify pick an alternative location per the shop's routing settings (include/exclude lists) — handy on rejection when you just need "anywhere else that has it."
  • Reserve at the chosen store (Lesson 5's guarded update) so a Click & Collect buyer can't undercut the allocation a second later; Shopify also moves the quantity to committed at that location.
  • Fulfil when the parcel is handed to the carrier, attaching tracking — which fires the customer's "shipped" notification.

9. Failure modes (each is a fact biting back)

What breaksRoot factHow you handle it
Store rejects the order (busy / not really there)F5Reroute to next-best (fulfillmentOrderMove / fulfillmentOrdersReroute); release the old reserve, reserve the new store.
No single store has the whole orderF2Split across the fewest stores; a subset fulfillmentOrderMove leaves the rest in a remainingFulfillmentOrder.
Destination doesn't stock the itemF5The move fails by design — your candidate list was stale. Re-read availability, re-score, pick a store that truly has it.
All good stores at capacityF6Fairness caps push work to farther stores; if the whole network is saturated, fall back to the warehouse or queue the order + alert ops.
Carrier cut-off missedF4Factor the store's daily cut-off into the score; past it, prefer a store that can still ship today or set next-day expectations.
Reassignment flapping (bounced between stores)F4 + F5Cap reroute attempts; after N tries, escalate to a human / warehouse; log each rejection reason.
Say it like this (allocation from first principles, in 6 sentences)

"Stock is scattered across stores and each parcel ships from one place, so for every line item a choice of origin is forced — that is allocation. 'Ship from the nearest store with stock' must fail, because a store may hold only part of the order, its finite shared labour saturates if it gets everything, and the stock figure is only an estimate. So I score each candidate on the real costs — coverage, proximity, capacity/fairness, and business rules — turning different units into one weighted, tunable number, and I prioritise fulfil-at-all, then fewest parcels, then distance and load. Fairness is a first-class term because store labour is a finite shared resource; if I don't price it, my allocator externalises it onto the busiest shop, which is exactly what the client fears. Because the input is an estimate, the system is closed-loop: reserve at the chosen store, and if it rejects or can't deliver, reroute to the next-best with a capped retry so an order never flaps forever. On Shopify this is fulfillmentOrderMove to my scored winner (or fulfillmentOrdersReroute), where partial moves leave a remainingFulfillmentOrder so a split falls straight out of the API."
