Lesson 12 · Track B · The thing you actually build

The Vendor Stock-Feed Connector

In Track B the vendor owns the availability engine. You own the pipe that feeds it. This lesson builds that pipe properly — as a relay with two failure surfaces, two rate limits, and one audit trail.

Your win today: design and code the connector — the small service that moves stock from the retailer's POS/ERP into the vendor's API. Name the one rule that makes a relay safe (send absolute state, never deltas), keep a shadow table so you can always answer "what did we send?", and size your batches against real Shopify and vendor rate limits.

Builds on Lesson 11 (the responsibility split) and on Lesson 2 (ingestion into your own database). The concerns rhyme, but a relay is not the same as an ingest — this lesson is about the difference.

1. What a connector is, and why it exists

The vendor says "we do the integration." They mean they integrate their logic. Nobody at the vendor has credentials to the retailer's till system in Ballarat. So somebody writes a small service that reads that till system and calls the vendor's API. That service is the connector, and it is yours.

The one-sentence definition A connector is a service you own that reads stock from a system you don't own, and writes it to an API you don't control. It owns no business logic. Its whole job is to be correct, cheap, and observable while sitting between two things that can both fail.

That "between two things" is the whole lesson. In Lesson 2 you ingested into your own database, so you controlled the destination — you could pick the schema, add a column, run a repair query. Here the destination is a vendor's HTTP API with its own rules, its own rate limit, and its own opinion about what a stock update means. You cannot fix their side. So you design for it.

2. An ingest has one failure surface. A relay has three.

Lesson 2 (build it): ingestLesson 12 (integrate): relay
Source can failYesYes

Read the last two rows again. In a relay you can lose track of what the destination believes. That single fact drives two design decisions below: absolute sends (§4) and the shadow table (§5).

4. Absolute state, not deltas — the rule that saves you

Two ways to tell a vendor that stock changed:

Delta ("adjust by −1")Absolute ("set to 4")
A lost message means…Permanent drift. The count is wrong forever, silently.Nothing. The next send repairs it.
A duplicated message means…Double-applied. Stock is now wrong by one.Nothing. Setting 4 twice is still 4.
Out-of-order arrival means…Wrong result — order matters.Last write wins; guard with a timestamp.
Needs idempotency to be safe?Yes, absolutelyIt is naturally idempotent
Recovery after an outageReplay every missed event in orderSend the current state once
The rule When you relay across a boundary you don't control, send absolute state. A delta is a differential equation that needs every step; an absolute value is self-healing. This is the same choice Shopify itself exposes — inventorySetQuantities (absolute) vs inventoryAdjustQuantities (delta) — and for a cross-system feed you want the absolute one.1

Deltas are not always wrong. A till that reports "sold 1" is naturally a delta, and asking a 15-year-old POS to compute a full count may not be possible. The fix is to convert as early as you can: apply the delta to your own shadow count, then send the resulting absolute number onward. The delta lives inside one system; the absolute crosses the boundary.

The trap Relaying the POS's delta straight to the vendor because "it's less data." One dropped HTTP call, and that store's count for that SKU is wrong until a human notices. There is no error message. Availability quietly lies for weeks. This is the most expensive bug in this lesson.

5. The shadow table — your own memory of the vendor

You do not own the vendor's database, so you keep a small local record of what you last told them. It is not a copy of their state; it is a log of your side of the conversation.

-- one row per (location, sku): what we last successfully sent
CREATE TABLE vendor_feed_state (
  retailer_id   TEXT        NOT NULL,
  location_id   TEXT        NOT NULL,   -- canonical, ours
  sku           TEXT        NOT NULL,
  sent_qty      INT         NOT NULL,   -- the absolute number we sent
  sent_hash     TEXT        NOT NULL,   -- hash of the whole payload we sent
  source_ts     TIMESTAMPTZ NOT NULL,   -- when the SOURCE measured it (UTC)
  sent_at       TIMESTAMPTZ NOT NULL,   -- when we got a 2xx back
  attempts      INT         NOT NULL DEFAULT 0,
  last_error    TEXT,
  PRIMARY KEY (retailer_id, location_id, sku)
);
CREATE INDEX ON vendor_feed_state (retailer_id, sent_at);   -- for the staleness report

Four things this one table buys you:

  1. Change suppression. If the new payload hash equals sent_hash, skip the call. A nightly full file of 50,000 rows where 300 changed becomes 300 API calls, not 50,000. This is usually the difference between fitting inside the rate limit and not.
  2. An answer to "what did we send?" When the retailer says the widget is wrong, you can prove your side in one query instead of arguing with the vendor.
  3. A staleness report. MAX(sent_at) per location tells you a store went quiet, before a customer finds out.
  4. A resend path. After a vendor outage, select the rows whose source_ts > sent_at and replay only those.
Why a hash and not just the quantity Stock is not the only field you send. Price, active flag, and store trading hours may ride along. Comparing only sent_qty would skip a call when the quantity is unchanged but the price moved. Hash the full payload you actually send, and compare that.

6. The connector in code

Node + TypeScript, framed the way a NestJS service would be. One adapter per source, one client for the vendor, one worker that joins them.

// ---------- the only shape the rest of the connector knows about ----------
type StockReading = {
  retailerId: string;
  locationId: string;      // canonical, already mapped (L13)
  sku: string;             // canonical, already mapped (L13)
  onHand: number;          // absolute, already unit-converted
  sourceTs: Date;          // when the SOURCE measured it, UTC
  source: string;          // 'retail-express' | 'store-c-sftp' | ...
};

// ---------- one adapter per POS/ERP: the only place quirks are allowed ----
interface SourceAdapter {
  readonly source: string;
  /** Full snapshot of everything this source knows. Used for reconciliation. */
  snapshot(retailerId: string): AsyncIterable<StockReading>;
  /** Parse one inbound push into readings. Throws on a bad signature. */
  parsePush(rawBody: Buffer, headers: Record<string, string>): StockReading[];
}

// ---------- the worker: normalise → suppress → send ----------
async function relay(readings: StockReading[]) {
  for (const batch of chunk(readings, VENDOR_BATCH_SIZE)) {
    const toSend: StockReading[] = [];

    for (const r of batch) {
      const prev = await state.get(r.retailerId, r.locationId, r.sku);

      // (a) staleness guard — never move stock backwards in time
      if (prev && r.sourceTs < prev.source_ts) { metrics.stale++; continue; }

      // (b) change suppression — the vendor already knows this
      if (prev && prev.sent_hash === hashPayload(r)) { metrics.unchanged++; continue; }

      toSend.push(r);
    }
    if (toSend.length === 0) continue;

    await bucket.take(costOf(toSend));              // §7 client-side rate limit
    await sendWithRetry(toSend);                     // §8 retry + DLQ
  }
}

async function sendWithRetry(readings: StockReading[], attempt = 0): Promise<void> {
  // one stable key per batch: safe for the vendor to de-duplicate on
  const idempotencyKey = sha256(readings.map(r =>
    `${r.locationId}|${r.sku}|${r.onHand}|${r.sourceTs.toISOString()}`).sort().join('\n'));

  try {
    await vendor.setInventory({ idempotencyKey, items: readings.map(toVendorShape) });
    await state.markSent(readings);                  // shadow table, only on 2xx
    metrics.sent += readings.length;
  } catch (err) {
    if (isRetryable(err) && attempt < MAX_ATTEMPTS) {
      // full jitter: random between 0 and the capped exponential delay
      const cap   = Math.min(30_000, 500 * 2 ** attempt);
      const delay = Math.random() * cap;
      if (err.status === 429 && err.retryAfterMs) await sleep(err.retryAfterMs);
      else await sleep(delay);
      return sendWithRetry(readings, attempt + 1);
    }
    await deadLetter.put({ readings, err: String(err), attempt });   // never silently drop
    metrics.dead += readings.length;
  }
}
Three details a reviewer looks for (1) state.markSent runs only after a 2xx — if you write the shadow row optimistically, a failed send makes you believe the vendor knows something it doesn't, and change suppression then hides the truth forever. (2) The idempotency key is derived from the content, sorted, so a retry of the same batch produces the same key. (3) Retry-After from a 429 beats your own backoff maths — the server knows better than you do.

7. Two rate limits, one budget

A connector can be throttled at both ends. Size it against the real numbers.

SideThe real limitWhat it means for the connector
Shopify GraphQL Admin API1Cost-based leaky bucket: 100 points/second (Standard), 200 (Advanced), 1000 (Plus), 2000 (Enterprise). A single query may not exceed 1,000 points regardless of plan.If you also read products/locations from Shopify, that read competes with every other app on the store. Cache the catalogue; don't re-read it per SKU.
Shopify bulk operations1No max-cost or rate limit like single queries.The right tool for the first full catalogue load, and for a monthly full reconciliation. Not for incremental updates.
The vendor's APIWhatever their contract says — often requests/minute plus a max batch size.Get this in writing during discovery (L18). It sets your batch size and your worst-case catch-up time.
The POS/ERPOften the weakest link: an on-premise box, sometimes single-threaded.Poll gently, off-peak, staggered per store. A connector that DOSes the till system gets switched off by the retailer.
The catch-up sum you should be able to do out loud 50 stores × 20,000 SKUs = 1,000,000 rows. Vendor accepts 500 items per call at 60 calls/minute → 30,000 items/minute → ~33 minutes for a full push. That is your disaster-recovery time, and it decides whether a full resend is a routine tool or a weekend. Ask for the numbers, then do this sum before you promise anything.

8. When to send: three triggers

  • Event-driven — a push arrives, you relay within seconds. Best freshness, spiky load.
  • Micro-batch — collect for 5–30 seconds, then send one call per location. Usually the right default: it collapses a burst of ten changes to one SKU into a single send, and it fits batch-oriented vendor APIs.
  • Scheduled reconciliation — a full snapshot per source on a timer (nightly is typical). This is the only thing that repairs silent drift, and it is not optional. Compare the snapshot against the shadow table and send only the differences, so a nightly full run costs almost nothing when nothing changed.
The trap Shipping only the event path because it demos well. Feeds drop messages; a vendor has maintenance windows; an adapter gets deployed with a bug for six hours. Without scheduled reconciliation, every one of those leaves permanent wrong stock, and the first person to notice is a customer standing in a shop.

10. Failure modes

What breaksHow you handle it
Vendor returns 429Honour Retry-After; back off with full jitter; the queue absorbs it. Never drop the reading — a throttle is a delay, not a failure.
Vendor is down for an hourRetries fail, batches land in the DLQ. When it recovers, resend from the shadow table where source_ts > sent_at — absolute sends mean you send current state, not a backlog of history.
Vendor changes a field name4xx spike, isolated to one payload shape. Contract test against their sandbox in CI catches it before production. Pin the API version if they offer one.
POS clock is wrongThe staleness guard trusts source_ts, so a skewed clock can pin stock at an old value. Alert when a reading's source_ts is in the future or absurdly old; prefer a monotonic sequence number where the source offers one.
Shadow table and vendor disagreeOnly reconciliation finds this. Re-send the location in full, then investigate. If the vendor exposes a read API, diff it weekly.
Connector deployed with a mapping bug4xx or "unknown sku" from the vendor. Quarantine those rows, alert, keep the rest flowing. Never let one bad SKU stop a store's feed.
Someone reruns yesterday's fileThe staleness guard rejects older source_ts; the hash suppresses unchanged rows; the idempotency key makes a true duplicate a no-op. Three layers, on purpose.
A store closesIts feed stops, so feed age grows and looks like a fault. Deactivate the location in your registry (L13) so it drops out of the alert and out of the vendor's store list.
Say it like this (the connector in 6 sentences)

"The connector is the one service I really build in an integration: it reads stock from the retailer's POS or ERP and writes it into the vendor's API. I treat it as a relay, not an ingest, because the destination is a system I can't inspect or repair — so I always send absolute state rather than deltas, since a lost delta is permanent silent drift while a lost absolute heals on the next send. I keep a small shadow table of what I last sent per location and SKU, hashed, which gives me change suppression, a staleness report, proof of what I sent, and a clean resend path after an outage. I respect rate limits at both ends — Shopify's GraphQL Admin API is a cost-based bucket at 100 points a second on a standard plan, and the vendor has their own cap — so I micro-batch, back off with jitter, and honour Retry-After. I run three triggers: event-driven for freshness, micro-batch as the default, and a scheduled full reconciliation that repairs drift, because feeds always drop messages. And I watch five numbers — feed age per location, 4xx versus 5xx send rate, suppression ratio, dead-letter depth, and reconciliation drift — so a broken store surfaces to me before it surfaces to a customer."
