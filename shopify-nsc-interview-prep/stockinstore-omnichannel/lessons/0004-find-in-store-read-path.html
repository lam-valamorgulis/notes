Find in Store & Store Locator: the Read Path

The shopper asks one question on the product page — "which shops near me have this, right now?" — and expects an answer before they lose interest. This is a latency problem, not a stock problem.

Your win today: design the read path that answers "who near me has SKU X available?" in well under a second — the geospatial "near me" query, joined to the availability signal from Lesson 3, served from a cache within a strict latency budget, behind the "six lines of code" widget.

Builds on Lesson 3 (the availability signal you are about to serve) and Lesson 2 (the data you are reading). Ingestion is the write path; this is the read path, and the two are designed separately.

1. The one query

Find in Store and Store Locator are the same query with a different filter. Both start from the shopper's location and a product, and return nearby stores:

What the widget actually asks your API "Given SKU X and location (lat, lng), return the N nearest stores, each with its distance and its availability state." Store Locator is the same call without a SKU (just "nearest stores"), or with the SKU used only to label stock status. One endpoint serves both.

So the answer is a join of two things you must compute fast: proximity (which stores are near) and availability (does each have it, per Lesson 3). The whole lesson is how to make that join cheap.

2. The geospatial part — "near me"

"Nearest stores to a point" is a classic geospatial query. Do not compute distance to every store in a loop — that does not scale and it is slow. Use a spatial index.

  • PostGIS (Postgres): store each location as a geography(Point), add a GiST spatial index, and let the database find nearest neighbours. Two operators do the work: ST_DWithin(geog, point, meters) filters to a radius, and the <-> KNN operator orders by true distance using the index.
  • Redis GEO: for a hot, in-memory read path, GEOSEARCH … BYRADIUS … ASC returns nearby members ordered by distance in microseconds.
  • Cheap approximation: a bounding-box filter (lat/lng between ±δ) to shrink the set, then exact distance on the survivors. Works without PostGIS, but a real spatial index is better.
-- nearest 5 stores within 50 km that have this SKU, with availability
-- (PostGIS; :lat/:lng from the shopper, :sku the product)
SELECT s.location_id, s.name, s.lat, s.lng,
       ST_Distance(s.geog, ST_MakePoint(:lng, :lat)::geography) AS metres,
       a.state, a.qty_shown
FROM   locations s
JOIN   availability a ON a.location_id = s.location_id AND a.sku = :sku
WHERE  s.active
  AND  ST_DWithin(s.geog, ST_MakePoint(:lng, :lat)::geography, 50000)   -- 50 km radius
ORDER  BY s.geog <-> ST_MakePoint(:lng, :lat)::geography                -- KNN, index-ordered
LIMIT  5;
Note what this query reads It reads an availability table, not raw inventory_levels. The Lesson-3 engine (threshold, buffer, prediction) has already been applied and the result stored, so the read path does no availability maths at request time — it just reads a pre-computed state. Pushing the expensive work off the request is the core read-path move.

3. The latency budget (why this is a read problem)

This call happens on the product page, often on load, for every visitor. It must feel instant. Put a number on it so you can defend the design:

LayerTarget (p95)Why
Whole page feels instant< ~300 msAbove this, shoppers notice and bounce.
Your availability API< ~100 msIt's one of several things the page waits on; keep your slice small.
Cache hita few msMost reads should never touch Postgres at all.
The trap juniors fall into Running the availability calculation (threshold + prediction) inside the request. That couples every product-page view to your heaviest logic and to the write-side database. Pre-compute availability when stock changes (write path), store the result, and let the read path serve a simple lookup. Reads and writes have opposite shapes — many fast reads, fewer heavy writes — so you optimise them separately.

4. Caching — the technique that makes it fast

The same popular product in the same city is queried thousands of times. Cache the answer.

Start simple — what the Redis cache even is Picture two places the answer can live. Postgres is a big filing cabinet: it holds the truth, but opening it and searching takes ~30 ms. Redis is a sticky note on your desk — a plain key → value store kept in memory (RAM), so reading it takes ~1 ms. The cache is just this: before doing the slow filing-cabinet work, check the sticky note. If the answer is already there, hand it back; if not, do the work once and write it on the note for next time.
shopper: "stores near postcode 2026 with SKU 1001?" │ ▼ ┌─────────────────────────────────┐ │ Redis — is this key saved yet? │ │ key = avail:1001:postcode:2026 │ └───────────────┬─────────────────┘ │ ┌─────────────┴──────────────┐ HIT (~1ms) MISS (first time, or after expiry) │ │ ▼ ▼ return the saved ask Postgres (~30ms), answer instantly SAVE it in Redis, then return (every later shopper now HITs)

HIT = the answer was on the note (fast). MISS = it wasn't, so one request rebuilds it. That is the whole idea. Everything below is just detail: which answer to save (the key), how long to keep it (the TTL), and when to tear the note up (invalidation).

  • What to cache: the result of "(SKU, coarse area) → nearby stores + availability." Round the shopper's location to a coarse grid or use their postcode as the key, so nearby shoppers share one cache entry instead of each getting a unique lat/lng.
  • Where: an in-memory cache (Redis) in front of Postgres, and an edge/CDN cache for the truly hot, coarse queries.
  • TTL: short — seconds to a couple of minutes. Availability is already a hint (Lesson 3), so a slightly old hint is acceptable; the strict check happens at purchase, not on the product page.
  • Invalidation: when the availability of a SKU at a store changes materially (crosses a threshold, or a reservation is taken), evict or update the entries that include it. A short TTL is the safety net for anything you miss.
Worked example — the cache key A shopper at (−33.8908, 151.2743) searching SKU 1001 becomes key avail:1001:postcode:2026 (or a geohash prefix). The next shopper in postcode 2026 asking for 1001 hits the same cached answer — a few milliseconds, no database. Only when that entry expires (say 60 s) or is invalidated does one request rebuild it and re-populate the cache for everyone.

5. Where the data lives (read/write split)

Draw the two paths as separate flows meeting at one store of pre-computed availability.

WRITE PATH (Lesson 2 + 3) READ PATH (this lesson) POS/ERP feeds ─► ingest ─► inventory_levels product page │ │ widget availability engine (L3) ▼ │ ┌──────────┐ miss ┌──────────┐ ▼ │ Cache │─────────►│ availability ┌──────────────┐ read │ (Redis / │◄─────────│ + PostGIS │ availability │◄────────│ edge) │ rebuild │ (read │ │ (state per │ └────┬─────┘ │ replica) │ │ loc × sku) │ │ hit (ms) └────────────┘ └──────────────┘ ▼ N nearest stores + availability state
  • Pre-computed availability is written by the engine when stock changes, and only read here.
  • Read replica: serve the geospatial rebuild query from a read replica so heavy read traffic never competes with ingestion writes.
  • The widget never talks to the write side. It only ever reads cache → replica. This isolation is what keeps a viral product page from stalling your stock sync.

6. The widget → your public API

"Six lines of code" means a small script on the merchant's product page that calls your API with the SKU and the shopper's location. Because it runs in the shopper's browser on the merchant's domain, three things matter:

  • It is a public, read-only endpoint — no secret keys in the browser. Scope it to read availability only. Identify the merchant with a public, per-merchant key in the URL, not a secret.
  • CORS must allow the merchant's storefront origin to call it from the browser.
  • Rate limiting / abuse protection — a public endpoint is scrapeable, so throttle per key and per IP, and never return more store detail than the widget needs.
GET /v1/find-in-store?sku=1001&lat=-33.89&lng=151.27&radius=50000&limit=5
    &key=pub_merchant_abc            // public merchant key, not a secret

200 OK   (served from cache in a few ms)
{
  "sku": "1001",
  "stores": [
    { "id": "bondi",     "name": "Bondi",     "distance_km": 1.2,
      "state": "in_stock",    "qty_shown": 4, "updated_min_ago": 3 },
    { "id": "randwick",  "name": "Randwick",  "distance_km": 3.8,
      "state": "call_to_confirm" },
    { "id": "city",      "name": "Sydney CBD", "distance_km": 6.1,
      "state": "out_of_stock" }
  ]
}

Notice the response carries the state and an age (updated_min_ago), not a bare number — so the widget can show "In stock (updated 3 min ago)" or "Call to confirm," honouring the honesty rule from Lesson 3.

8. Deep-dive Q&A — the read model, and the cache entry's life cycle

Two questions the read path always draws out. Cover each answer, say it out loud, then scroll.

Q1. Is availability a separate table, and what's its key?

Yes — availability is its own table, and its primary key is (location_id, sku), the same grain as inventory_levels. One row = "the answer for this product at this store." The two tables are a read model / write model split (CQRS-lite):

inventory_levels (WRITE model)availability (READ model)
Holdsraw feed truth: on_hand, reserved, version, updated_at, sourcecomputed answer: state, qty_shown, computed_at
Written byingestion workers (feeds)the availability engine (Lesson 3)
Read bythe engine, reconciliationthe hot read path (the widget)
KeyPK (location_id, sku)PK (location_id, sku) — 1:1 twin

Why separate: computing state means combining on_hand − reserved − buffer, the per-SKU threshold, and the feed age (a stale feed → call_to_confirm) — the heavy write-side logic. Do it once when stock changes and store the finished state, so the hottest path (every product-page view, and geospatial) is a cheap indexed lookup, never a recomputation. The query returns a state enum (in_stock | low | likely | out_of_stock | call_to_confirm), not the raw number — hiding the count and encoding policy.

retailers (retailer_id PK) │ 1 ┌───────────┴────────────┐ │ * │ * ┌────────┴─────────┐ ┌─────────┴──────────────┐ │ locations │ │ products │ │ location_id PK │ │ (retailer_id, sku) PK │ │ geog (POINT) │ │ barcode, title │ │ active, timezone │ └─────────┬──────────────┘ └────────┬─────────┘ │ 1 (by sku) │ 1 │ │ (location_id, sku)│ │ * │ * ┌──────┴────────────────────────┴──────┐ │ inventory_levels ── WRITE model │ │ PK (location_id, sku) │ │ on_hand, reserved, version, updated_at│ └──────────────┬────────────────────────┘ │ 1 : 1 (engine computes) ▼ ┌───────────────────────────────────────┐ │ availability ── READ model │ │ PK (location_id, sku) ◄ query JOINs │ │ state, qty_shown, computed_at │ └───────────────────────────────────────┘
Two indexes, two jobs The query touches two indexes doing different things: the GiST index on locations.geog finds the nearby stores (via ST_DWithin + the <-> KNN order), and the PK (location_id, sku) on availability resolves this product's answer at each of those stores. Neither can do the other's job. Column order matters: (location_id, sku) suits this query (look up per location after the spatial step); if your dominant access were "one SKU across all stores" you'd want a (sku, location_id) index — same uniqueness, different traversal.

Q2. "One request rebuilds it and re-populates the cache for everyone" — what does that mean?

The coarse key (avail:1001:postcode:2026) makes every shopper in postcode 2026 asking for SKU 1001 share one cache entry. "Rebuild" = run the real PostGIS + availability lookup on the read replica (~tens of ms). After one rebuild you SET the result back, so the next thousand shoppers read it in a few ms and never touch the database. The DB cost is paid once per key per TTL window, amortised across everyone in that area.

key = avail:1001:postcode:2026 TTL = 60s t=0.0s shopper A -> GET -> MISS -> rebuild (PostGIS on replica, ~30ms) -> SET key = result, EX 60 t=0.3s shopper B -> GET -> HIT -> ~2ms, no DB t=12s shopper C -> GET -> HIT -> ~2ms, no DB ... (hundreds in postcode 2026 served from this ONE entry) t=45s reservation taken for 1001 nearby -> INVALIDATE -> DEL key (event-based) t=45.1s shopper D -> GET -> MISS -> one rebuild -> SET -> HITs resume t=105s 60s after the last rebuild -> entry EXPIRES on its own (time-based safety net)

Two independent triggers remove the entry, and you want both: TTL expiry (time-based — the safety net; a hint can't be more than 60s stale) and invalidation (event-based — evict the moment availability materially changes: crosses a threshold, or a reservation is taken, so you never show sold-out stock as in-stock). Invalidation keeps it correct; TTL keeps it bounded.

The word "one" is the trap — cache stampede By default it is not one rebuild. When a hot key expires, many shoppers miss in the same millisecond and all rebuild at once — a burst of identical expensive queries (the "cache miss storm" in §7). To make "one request rebuilds for everyone" literally true you add a single-flight lock (one rebuilds, the rest wait then read the fresh value) or stale-while-revalidate (serve the slightly-old value while one background request refreshes). 
// single-flight: exactly one rebuild repopulates the shared entry
async function getAvailability(key: string) {
  const hit = await redis.get(key);
  if (hit) return JSON.parse(hit);                          // fast path (a few ms)

  // MISS: only ONE request should rebuild. Take a short lock.
  const gotLock = await redis.set(`${key}:lock`, '1', 'NX', 'PX', 5000);
  if (!gotLock) { await sleep(50); return getAvailability(key); }  // wait -> read fresh entry

  try {
    const result = await queryReplica(key);                 // the expensive rebuild, ONCE
    await redis.set(key, JSON.stringify(result), 'EX', 60); // re-populate for everyone
    return result;
  } finally {
    await redis.del(`${key}:lock`);
  }
}
Why the coarse key is the biggest lever "For everyone" only works because the key is a postcode/geohash, not exact lat/lng. Exact coordinates give every shopper a unique key → ~0% hit rate → you rebuild on every request. Rounding the key is the single biggest lever on hit rate — it's what turns one rebuild into thousands of cheap hits.

Q3. How do locations and products know each other?

They don't link directly — the ERD in Q1 has no line between them. They meet only through inventory_levels, a junction (bridge) table that resolves a many-to-many relationship: one location stocks many products, one product sits in many locations. A relational DB can't store M:N directly, so you keep one row per pair.

locations inventory_levels products ──────────── ───────────────────── ───────────────────── location_id PK ◄─────── location_id (retailer_id, sku) PK sku ──────────────► sku on_hand, reserved, ... barcode, title PK = (location_id, sku)

The PK (location_id, sku) is literally one id from each side glued together: a location_id → every product that store stocks; a sku → every store carrying that product; both → the one row with its on_hand. Because it also carries data (on_hand, reserved) it's an associative entity, not just a pure link.

The precise detail — how sku reaches products: products's key is (retailer_id, sku), but inventory_levels has no retailer_id column, so sku alone can't identify a product (it's only unique within a retailer). The missing retailer_id comes from the location:

SELECT ...
FROM   inventory_levels i
JOIN   locations l ON l.location_id = i.location_id    -- borrow retailer_id from the store
JOIN   products  p ON p.retailer_id = l.retailer_id    -- now the full product key matches
                  AND p.sku         = i.sku;

So the two sides connect only through inventory_levels, and the retailer scope flows via the location. (Strict schemas either add retailer_id onto inventory_levels for a clean composite FK, or make sku globally unique.)

Where the link is actually created — ingestion The linking row is born in Lesson 2's mapping step: the normalise worker turns a store's own codes (0092-RED at store MEL-03) into a canonical sku + location_id via id_map, then writes one inventory_levels row. If the mapping fails there is no linking row — which is exactly why Find in Store shows "no stock" for a product that's really on the shelf.

Q4. Cache key: geohash vs postcode?

Both do the same job — coarsen the shopper's location so nearby people share one entry (§4). They differ in how they draw the "area":

PostcodeGeohash prefix
Key looks likeavail:1001:postcode:2026avail:1001:geohash:r3gx2
How the area is drawnthe region's own postcode boundarya grid cell; a longer prefix = a smaller cell (tunable)
Good whenthe shopper types a postcode; matches delivery/pickup zones; human-readableyou have precise lat/lng (geolocation); want uniform, country-agnostic cells
Weaknessuneven sizes (dense city vs huge rural); boundaries don't match "within 50 km"arbitrary squares; shoppers just across a cell edge get different keys (fragmentation)

Both trade exact precision for hit rate, and both share the same edge problem: the truly-nearest store can sit just across a boundary, so neither zone perfectly matches "5 nearest within 50 km." That is acceptable because availability is a hint — and the query still runs a real ST_DWithin radius from a representative point.

The key and the query point MUST match Whatever you key on, run the query from a canonical point for that key — the postcode centroid, or the geohash cell centre — not the shopper's exact lat/lng. If two shoppers share postcode:2026 but you compute distances from each one's precise coordinates, they would serve each other slightly-wrong cached answers. One key = one query = one stored answer.

Q5. Why an edge/CDN cache in front of Redis?

Redis is fast but lives in one region — your origin. A shopper on another continent still pays the network round-trip to that region for a Redis hit. An edge/CDN cache (Cloudflare, Fastly, CloudFront) stores the HTTP response at a PoP (point of presence) near the shopper, so the hottest, coarsest queries are answered ~10–30 ms away and your origin does zero work.

browser ──→ CDN / edge PoP ──miss──→ your API ──→ Redis ──miss──→ Postgres (near (~10-30ms hit, (region (~1ms hit) (replica, shopper) a coarse cacheable GET) round-trip) ~30ms) ▲ ▲ most viral, coarse per-region hot queries stop HERE queries stop HERE
  • What's cacheable at the edge: only a stable, shareable GET. The URL must carry the coarse key (postcode/geohash + a rounded radius) and the public merchant key — never exact lat/lng, or every URL is unique and edge hit rate is ~0. Same coarsening idea as the Redis key, applied to the URL.
  • How it's controlled: Cache-Control: public, s-maxage=60 on the response tells the CDN to keep it 60 s. Layer the TTLs (edge ~30–60 s, Redis ~60 s) so staleness stays bounded top to bottom.
  • Invalidation is weaker here: you can purge a CDN entry, but it is eventually consistent across PoPs — so at the edge you lean on the short TTL, and keep the precise threshold/reservation invalidation at the Redis layer.
  • Safe because it's public: the endpoint is a public, read-only availability hint (§6), so there is nothing user-specific to leak. Never edge-cache anything keyed to a person, and don't cache errors for long.
One sentence for the interview "I layer caches by how coarse and hot the query is: the CDN absorbs the viral, coarse queries near the user; Redis absorbs the per-region hot ones; the read replica handles the rest — each layer has a short TTL so a stale hint is bounded, and the widget shows the age anyway."
