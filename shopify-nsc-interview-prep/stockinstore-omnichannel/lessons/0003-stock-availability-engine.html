Lesson 3 · The signature problem

The Stock Availability Engine

You have a raw number from a store's POS. It may be stale, may not count what's reserved, may be wrong. The question is not "how many are there?" It is "what do I dare tell the customer?"

Your win today: explain the difference between on-hand and available-to-promise, and describe the four levers that turn an untrusted raw count into a safe availability signal — thresholds, safety buffers, prediction, and a "call to confirm" fallback — so you never send a customer to an empty shelf.

This is the lesson that makes you sound like you know the domain, not just the platform. It builds on Lesson 2's canonical inventory_levels and feeds the read path in Lesson 4.

1. On-hand is not available

The number the POS reports is quantity on hand — what the system thinks is physically there. It is not what you can safely sell. The value you actually publish is available-to-promise (ATP):

The core equation available = on_hand − reserved − safety_buffer, then gated by a threshold and adjusted for staleness. Everything in this lesson is one of those terms. If any term is missing, you will oversell.
  • on_hand — the raw count from ingestion (Lesson 2).
  • reserved — units promised to Click & Collect / Ship-from-Store orders that are not yet picked (Lesson 5). If you don't subtract these, two customers claim the same unit. A reservation must expire (a hold with a TTL) — otherwise a customer who never collects leaves the unit reserved forever, hiding real stock as a phantom out-of-stock.
  • safety_buffer — a cushion you hold back because you don't fully trust the count.
  • threshold — a floor below which you say "not available here" even if the raw number is 1 or 2.
This is Shopify's real model — use its words Shopify's own inventory splits on_hand into named states: on_hand = available + committed + reserved + damaged + safety_stock + quality_control. So your "ATP" is Shopify's available, your "reserved" maps to Shopify's reserved/committed, and your "safety_buffer" maps to Shopify's safety_stock. Saying "I compute an available-to-promise number — Shopify's available state — by holding back safety_stock and subtracting reserved and committed" tells the interviewer you know the platform, not just the theory.

2. Lever 1 — Thresholds (per store, per SKU)

A raw "1 in stock" is the most dangerous number in retail. It is exactly the case most likely to be wrong (the last one was sold, misplaced, or is a display model). So you set a threshold: only show "available" when the count is at or above it.

stockinstore makes this configurable by store and by individual SKU, and that granularity matters:

SituationThreshold choiceWhy
High-theft small item, busy storeHigher (e.g. show available only at ≥ 3)Counts drift fast; 1–2 is unreliable.
Big, tracked item (fridge)Lower (even 1 is fine)Hard to lose; count is trustworthy.
Store with a flaky nightly feedHigher across the boardData is old, so demand more headroom.
Say it like this "Thresholds are per store and per SKU because trust in the number isn't uniform — a well-tracked appliance in a quiet store can show available at 1, but a small high-theft item in a busy store shouldn't show available until there are several, because the raw count there is the least reliable."

3. Lever 2 — Safety buffer

Even above the threshold, hold a little back. If on-hand is 10 and your buffer is 2, you promise 8. The buffer absorbs the sales that happened since the last feed but haven't reached you yet. It trades a few "sorry, sold out" moments for far fewer "drove to the shop and it wasn't there" moments — and the second failure is the one that loses a customer for good.

4. Lever 3 — Prediction (the "close to real-time" trick)

Feeds are periodic; sales are continuous. Between two feed updates the true count moves — usually down from walk-in sales, but it can also go up (customer returns, a delivery received, an inter-store transfer, a cancelled layby). stockinstore names "an algorithm that predicts stock availability" for exactly this gap. Because you cannot see the up-moves until the next feed, the safe design is a one-directional one: the prediction may only ever lower the shown number, never raise it. That is a deliberate safety choice, not a claim that stock physically only falls — the real guarantee comes from the strict reservation at purchase (§6).

So you decay a stale count toward zero, using how fast that store/SKU normally sells and how many trading hours have passed since the reading:

// predicted available between feed updates (illustrative, explainable model)
function predictedAvailable(level, now, salesRatePerTradingHour, buffer, threshold) {
  // Count only hours the store was OPEN — a feed from 6pm close read at 8am is
  // 14h old on the clock but sold ZERO overnight. Use locations.timezone + hours.
  const openHours  = tradingHoursBetween(level.updated_at, now, level.location);
  const likelySold = Math.round(salesRatePerTradingHour * openHours); // not ceil — see note
  const predicted  = level.on_hand - level.reserved - likelySold - buffer;
  return predicted >= threshold ? predicted : 0;                       // gate on threshold
}
// salesRatePerTradingHour = a rolling per-store, per-SKU velocity you keep from
// history (e.g. avg units sold per open hour over the last N weeks).
Worked example (trace it out loud) on_hand = 10, reserved = 0, buffer = 2, threshold = 3, sells 2 per trading hour, reading is 4 trading hours old.
likelySold = round(2 × 4) = 8 → predicted = 10 − 0 − 8 − 2 = 0 → 0 < threshold 3 → the widget shows "Out of stock". The same feed at 1 trading hour old: likelySold = 2 → predicted = 6 → shows "In stock (6)". Older reading, more conservative — automatically.
Three traps in this small function (1) Wall-clock age. Using real elapsed time zeroes overnight-stale feeds that actually sold nothing — decay against trading hours (needs locations.timezone + opening hours). (2) Math.ceil. Ceil is over-aggressive — a 30-minute-old feed at 0.1 sales/hour would "predict" 1 sold and wrongly drop the count; use round (or floor). (3) Magic sell rate. The rate isn't a guess — it's a rolling velocity computed per store and SKU from sales history, and it degrades to "call to confirm" when you have no history.

5. Lever 4 — The honest fallback

Some stores simply cannot give reliable (or any) data. Do not fake it. stockinstore shows customisable text like "call store to confirm" for these. Being honest about uncertainty is better than a confident lie that ends at an empty shelf. The availability signal is therefore not just a number — it is a state:

AVAILABILITY STATE (what the widget actually shows) feed fresh + count ≥ threshold ............► "In stock" (green) feed fresh + count in low band ............► "Low stock" (amber) feed stale but predicted ≥ threshold ......► "Likely in stock" (amber) count < threshold OR predicted 0 ..........► "Out of stock" (grey) no reliable feed for this store ...........► "Call to confirm" (neutral)

6. Preventing oversell at the moment of truth

Availability display is a hint. The guarantee happens at purchase. When a customer actually chooses Click & Collect at a store, you re-check and reserve against the live count. "Atomic" is not hand-waving — it is one conditional write that both checks and reserves, so two buyers can never both claim the last unit:

-- reserve N only if enough is really available; returns 0 rows if not (→ refuse)
UPDATE inventory_levels
   SET reserved = reserved + $qty
 WHERE location_id = $loc AND sku = $sku
   AND (on_hand - reserved - $buffer) >= $qty      -- the check and the write, together
RETURNING reserved;

The WHERE and the SET execute as one atomic row update, so concurrent checkouts are serialised on that row — no "check-then-write" race. (Equivalently: SELECT … FOR UPDATE to lock the row, verify, then update.) If it returns no row, there isn't enough — you refuse and offer another store.

Two different jobs, two different strictness levels Browse-time availability (Find in Store): fast, cached, approximate — a threshold-and-prediction hint across many stores. Buy-time availability (checkout reservation): slow-path, strict, atomic — the guarded update above for one store, or refuse. Confusing these two is the classic mistake.
Watch the pickup handoff — don't subtract twice When the store picks the order, two things happen: the POS on_hand drops (the item physically leaves) and your reserved must be released. If you drop on_hand (via the next feed) but forget to clear reserved, you subtract the same unit twice and hide stock. Release the reservation the moment the pick is confirmed, and treat the short window between "picked" and "next feed" as expected. Reservations that are never picked up hit their TTL and release automatically (§1).

7. How you'd defend the design

They ask…You answer…
"Why not just show the POS number?"Because it's on-hand, not available: it ignores reservations, staleness, and count error. Showing it oversells and sends customers to empty shelves.
"Isn't a buffer just lost sales?"It's a trade. A few 'sold out online' moments cost far less than a wasted trip to the store, which loses trust and the customer. I tune the buffer per store/SKU to balance it.
"Your prediction could be wrong."Yes — so it only ever reduces the count, never inflates it, and it degrades gracefully to 'call to confirm.' It's a conservative hint, backed by a strict reservation at purchase.
"A store's feed died. Now what?"Feed age crosses a limit → I stop trusting the number: widen buffer, then fall back to 'call to confirm,' and alert ops. I never keep showing a frozen count as if it's live.
Say it like this (the availability engine in 5 sentences)

"The number from the POS is on-hand, not available-to-promise, so I compute available = on_hand − reserved − buffer — in Shopify's own words, its available state after holding back safety_stock and reserved — gated by a per-store, per-SKU threshold. The threshold protects me from the least trustworthy numbers, a raw 1 or 2 in a busy store, while a well-tracked item can show available at 1. Because feeds are periodic and sales continuous, I decay a stale count downward by the store's rolling sell rate times the trading hours since the reading — one-directional, as a safety choice, since I can't see returns or restock until the next feed. Where a store can't give reliable data I show 'call to confirm' rather than guess. And I keep browse-time availability (fast, cached, approximate) separate from buy-time availability (a strict, atomic guarded update that reserves or refuses), because display is a hint and the reservation is the guarantee."

8. Deep-dive Q&A — how the engine is triggered (not push/poll/file)

A common mix-up worth nailing. Cover each answer, say it out loud, then scroll.

Q1. Does the availability engine read stock via push, poll, or file?

No. Push / poll / file are the ingestion transports (Lesson 2) — how external POS/ERP data reaches your inventory_levels table. The availability engine sits one step after that, entirely inside your system: it reads inventory_levels, computes the state, and writes the availability row. It never calls a POS.

EXTERNAL (POS / ERP) INSIDE YOUR SYSTEM ┌──────────────────────┐ │ push / poll / file │ ── feed the WRITE model ──► └──────────┬───────────┘ ▼ ingestion worker ──► inventory_levels (on_hand, reserved) ← WRITE model (L2) │ engine reacts to THIS changing ▼ availability engine (compute state) ← THIS lesson │ ▼ availability (state, qty_shown) ← READ model → widget (L4)

So whether a reading arrived by push, poll, or file, once it lands in inventory_levels the same internal trigger drives the engine — the transport is invisible to it. Push/poll/file only decide when on_hand changes and how fresh it is; the engine reacts to the result, not the pipe it came through.

Q2. So what actually triggers the engine to rewrite an availability row?

"When stock changes" is slightly loose. The engine fires when any input to the availability formula (on_hand − reserved − buffer, gated by threshold, adjusted for staleness) changes:

TriggerWhere it comes from
on_hand changeda new reading was applied — the one that came via push/poll/file
reserved changeda reservation was taken / released / expired (Lesson 5) — a customer action, no external feed
config changeda threshold or safety buffer was retuned
time passedthe feed aged → decay / flip to call_to_confirm — no data arrived at all
Two triggers have no external feed — that's the proof it's internal A reservation change and the time-based staleness decay both rewrite availability with nothing coming in from a POS. If the engine "worked via push/poll/file", neither could ever happen — yet they're the two that most often prevent an oversell. The time one needs a scheduled sweep / TTL that re-evaluates aging entries, because you can't be event-triggered by "a reading that never arrived".
How the trigger is delivered reliably Two designs: inline — recompute availability in the same transaction that writes inventory_levels (simple, always consistent, but coupled); or event-driven — write inventory_levels + an event to the transactional outbox in one transaction, a relay publishes it, the engine consumes it (Lesson 7). The outbox avoids the dual-write problem: emit the "changed" event separately from the DB write and a crash between them leaves availability silently stale forever.
