Click & Collect / BOPIS Order Flow

A browse becomes a promise. The customer picks a store, pays, and expects the item to be waiting. This is where a soft "likely in stock" hint must become a hard guarantee — without overselling.

Your win today: trace the whole Click & Collect flow end to end — carry the chosen store from product page to checkout, re-check and reserve the stock atomically at purchase, create the Shopify order as a pickup, send the store a pick task, notify the customer when it's ready, and release the reservation on collection — and name what happens when the store hasn't actually got it.

This is where Lesson 3's browse-vs-buy split becomes real, and where Lesson 4's hint is cashed in. BOPIS = Buy Online, Pick up In Store.

1. The whole flow in one picture

Draw this. The interviewer wants to see you move state through the system without losing or double-selling a unit.

PDP ──► choose store ──► CART ──► CHECKOUT ──► pay │ (carry store id through every step) │ │ ▼ │ (a) RE-CHECK availability at chosen store │ (b) RESERVE atomically ── fail ─► offer another store │ │ ok │ ▼ │ create SHOPIFY ORDER (pickup) │ Shopify → fulfillment order (PICK_UP), │ inventory moves to "committed" at that store │ │ │ ▼ │ PICK TASK ─► store staff (Collection Manager) │ │ picked & set aside │ ▼ │ mark "prepared for pickup" ─► NOTIFY customer │ │ (email / SMS: "ready") │ ▼ │ customer COLLECTS ─► fulfil order │ │ │ ▼ └───────────────────────────────► RELEASE reservation; on_hand drops via next feed (never collected → TTL expires → release + restock + refund)

2. Carry the chosen store through every step

The store the shopper picked on the product page must survive all the way to checkout, or the reservation reserves at the wrong shop. stockinstore explicitly "passes the selected Click & Collect store between PDP, Store Locator & Checkout." Concretely, you attach the chosen location_id to the cart (a cart attribute / line-item property), so it rides through to the order.

The trap juniors fall into Treating store choice as UI state that lives only on the product page. If it's not attached to the cart, the customer changes pages, the choice is lost, and you either reserve nowhere or guess. Bind the location_id to the cart as soon as it's chosen, and re-confirm it on the checkout screen.

3. The moment of truth: re-check, then reserve

The product page showed a hint (Lesson 4, from cached availability). At checkout you must turn it into a guarantee. Two steps, in order:

  1. Re-check the live availability for each line item at the chosen store — quantity included (2 requested, is there 2?). The cached hint may be minutes old; this reads fresh.
  2. Reserve atomically — the single guarded update from Lesson 3 §6, which checks and reserves in one statement so two shoppers can't both take the last unit:
-- reserve every line item for this order at the chosen store, all-or-nothing
BEGIN;
  -- for each line item (qty q, sku): reserve only if enough is really available
  UPDATE inventory_levels
     SET reserved = reserved + :q
   WHERE location_id = :loc AND sku = :sku
     AND (on_hand - reserved - :buffer) >= :q;      -- 0 rows affected ⇒ not enough
  -- if ANY line item failed, ROLLBACK the whole order and offer another store
COMMIT;
-- write a reservation row per line with an EXPIRES_AT (TTL) so an abandoned order frees stock
Why a reservation and not an immediate stock decrement You cannot decrement the store's real on_hand — that number lives in the store's POS, not in your database (Lesson 1). So you hold a reservation in your own system: it lowers available immediately (Lesson 3's equation subtracts reserved) so no one else can claim the unit, while the real on_hand only drops later, when the store picks the item and the next feed reports it. The reservation is your bridge across that gap.

4. Creating the order on Shopify (how pickup is represented)

Once reserved, the order is placed. Know exactly how Shopify models a pickup, because the interviewer may ask:

  • Local pickup at checkout. Shopify's checkout shows a Pickup tab listing store locations that have local pickup enabled; the buyer's chosen store becomes the pickup location on the order.
  • Fulfillment orders. After checkout, Shopify's order routing creates one or more fulfillment orders, each assigned to a location, each with a deliveryMethod.methodType — for pickup it is PICK_UP (shipping is SHIPPING). Read the delivery method from this field — do not infer it from shipping lines or the address.
  • The committed state. When the order is placed, Shopify moves that quantity into the committed inventory state at the assigned location automatically (you don't set committed via the API — order creation and fulfilment drive it).
Two integration levels — say which you're choosing (A) Lean on Shopify native pickup: if each store is a Shopify Location with its stock in Shopify (design B from Lesson 2), Shopify's own local pickup, fulfillment orders, and committed state do much of this for you. (B) Your own Click & Collect layer (what stockinstore does): because your source of truth is external POS stock that Shopify can't see, you run your own reservation and your own Store Collection Manager, and use the Shopify order + fulfillment-order APIs as the record and the pick/notify hooks. Naming which level you're at shows you understand the boundary.

5. Pick, prepare, notify

The store now has work to do, and the customer is waiting for one message: "it's ready."

  • Pick task to the store. Subscribe to Shopify's fulfillment_orders/order_routing_complete webhook to know the pickup fulfillment order exists, then surface it to store staff (stockinstore's Store Collection Manager) as a pick list.
  • Prepared for pickup. When staff have picked and set the order aside, you mark the fulfillment order's line items prepared for pickup; Shopify fires fulfillment_orders/line_items_prepared_for_pickup. That transition is your trigger to notify the customer.
  • Notify. Send the "ready to collect" email/SMS — with the store, hours, and what to bring. This is the payoff moment of the whole feature.
  • Collected. When the customer picks it up, you fulfil the fulfillment order. That is the real hand-over: the item has left the shelf.

6. The order/reservation state machine

Every Click & Collect order is a small state machine. Knowing the states — and the exits — is what stops stock leaking.

RESERVED ──pick──► PREPARED ──collect──► FULFILLED ✓ │ │ (on_hand drops via feed; │ │ release reservation) │ └── customer never comes ──► EXPIRED │ (release + restock) └── reserve fails / store rejects ──► CANCELLED (release + refund + offer alt store)
Don't subtract the same unit twice When the order is collected, two things must line up: your reserved is released and the store's on_hand drops (via the next feed). Release the reservation the moment you fulfil, and treat the short window until the next feed as expected — otherwise on_hand − reserved counts the sold unit twice and hides stock (the same handoff trap from Lesson 3 §6).

Say it like this (the Click & Collect flow in 6 sentences)

"The store the shopper picks on the product page is bound to the cart so it survives to checkout. At checkout I turn the soft availability hint into a hard guarantee in two steps: re-check the live count for every line item at that store, then reserve atomically with a single guarded update so two buyers can't take the last unit. I hold a reservation in my own system rather than decrementing the store's on-hand, because that real number lives in the POS and only drops when staff pick the item and the next feed reports it. The order is placed as a Shopify local pickup, which creates a PICK_UP fulfillment order at the store and moves stock to Shopify's committed state; I pick up the pick task from the order-routing webhook and surface it to store staff. If the store hasn't really got it I reassign the fulfillment order to another store or refund — availability is a hint, and the pick is the truth."

8. Deep-dive Q&A — the reservation guarded write, under concurrency

The "two shoppers, one last unit" question, in slow motion. Cover each answer, say it out loud, then scroll.

Q1. Read the guarded reserve line by line

UPDATE inventory_levels
   SET reserved = reserved + :q
 WHERE location_id = :loc AND sku = :sku
   AND (on_hand - reserved - :buffer) >= :q     -- the CHECK and the WRITE, one statement
RETURNING reserved;                              -- the success signal

on_hand − reserved − buffer is the available-to-reserve amount (raw stock, minus what's already held for other pending orders, minus a safety buffer you never sell). The WHERE matches the row only if that is still >= :q; if it matches, reserved goes up in the same statement. The result is your yes/no: 1 row back (rowcount 1) → reserved, confirm the order; 0 rows back → refuse ("out of stock") gracefully. The whole point is that the check and the write are one statement — no gap for another order to slip through (no "time-of-check to time-of-use" race).

Q2. Two orders at once — same store, same SKU. What happens?

Setup: on_hand = 5, reserved = 3, buffer = 0 → available = 2. Order X wants 2, order Y wants 2, both fire together.

t0 X: UPDATE ... -> grabs the ROW LOCK on (loc, sku) first t0 Y: UPDATE ... -> wants the same row -> BLOCKS, waits for X t1 X: (5 - 3 - 0) >= 2 -> TRUE -> reserved = 5, RETURNING 5, COMMIT (available is now 5 - 5 = 0) t2 Y: unblocks. READ COMMITTED RE-READS the fresh row (reserved = 5) and RE-EVALUATES the WHERE: (5 - 5 - 0) >= 2 -> FALSE -> 0 rows -> REFUSE Y result: exactly 2 reserved. X wins, Y refused. NO oversell.

Two mechanisms combine, and both are worth naming:

  • Row-level lock. Two UPDATEs on the same row are serialised — the second blocks until the first commits. "At the same time" becomes "one after the other" for that row, and you wrote no locking code; the UPDATE takes the lock.
  • The re-check on unblock (EvalPlanQual). Under READ COMMITTED (Postgres default), a blocked UPDATE does not use its stale snapshot when it wakes — it re-reads the freshly-committed row and re-runs the WHERE against it. So Y is judged against the reality X left behind, not the world when Y arrived. That is why this single statement is safe without SERIALIZABLE or an explicit SELECT … FOR UPDATE.
Why the naive "check then write" oversells If you split it — SELECT available in app code, decide, then UPDATE — both orders read "2 available" before either writes, both decide "enough", and both run an unconditional UPDATE reserved += 2 → reserved climbs 3 → 5 → 7 against on_hand 5 → oversold by 2. The fused guarded write kills this because Y's guard is re-evaluated after X's write, under the lock.
The honest scale caveat (raise it unprompted) This serialises all reservations for one (location, sku) on a single hot row. For a normal store that is fine. For one viral SKU it becomes a contention hotspot — then you'd queue or shard reservations per key. And this only reserves: you still convert reserved → sold on fulfilment and release it on a TTL/expiry, or reserved leaks upward and slowly chokes real availability.

Q3. What does "placed as a local pickup → PICK_UP fulfillment order → committed" mean?

Three separate Shopify mechanics stacked into one line:

  • Placed as a local pickup — Shopify's built-in local pickup delivery method. Enabled per location; at checkout the customer picks "Pick up" and a store, and the order is tagged as a pickup order at that store (not a shipping order).
  • Creates a PICK_UP fulfillment order — an Order is the customer's purchase; a Fulfillment Order is the work instruction ("fulfil these line items from this location, by this method"). One order can split into several. Each carries deliveryMethod.methodType — PICK_UP (customer collects) or SHIPPING (posted). You read that field to know it's a pickup task and surface it to store staff — never infer it from the address.
  • Moves stock to committed — see the table below.

Shopify tracks inventory in buckets (Lesson 2 §6): on_hand = available + committed + reserved + …. available = free to sell; committed = on a placed but unfulfilled order. Placing the order moves the quantity available → committed; the physical on_hand does not drop until the item is actually picked/collected.

Stage (store MEL-03, SKU 1001)on_handavailablecommitted
before the order550

Two phases: at placement available↓ and committed↑ (so Shopify won't sell the unit again) — on_hand unchanged, because the shoes are still on the shelf. At fulfilment committed clears and on_hand↓, because the item has physically left. committed is just Shopify's own word for "reserved".

The nuance for stockinstore (design A vs B) All of the above is Shopify-native and fully applies only when the store's stock lives in Shopify (each store a Shopify Location — design B). In stockinstore's world (design A) the real stock is in the store's POS, which Shopify can't see — so Shopify's committed reflects only what Shopify knows, and your own reserved counter (§3) is the real oversell guard. You still let Shopify create the Order + PICK_UP fulfillment order, because that's your record and your pick/notify hooks (the webhooks in §5).

Q4. A "fulfillment order" is created — is the order fulfilled yet?

No. This is Shopify's most confusing name. A fulfillment order is a request / to-do — "these line items need to be fulfilled from this location, by this method." A fulfillment is the completion record — "these items were handed over." They are two different objects:

Fulfillment OrderFulfillment
Isthe to-do / work ticketthe "done" record
Created whenthe order is placed (order routing)later, when you fulfil (fulfillmentCreate)
Starts asstatus OPEN (unfulfilled)doesn't exist yet
Inventory effectcommitted +1 (a promise)on_hand −1, committed −1

The trap is the word "order": a fulfillment order is an order to fulfil (a work order), not "an order that has been fulfilled." At the moment order routing creates it, the order is UNFULFILLED — only creating a fulfillment flips it to FULFILLED and drops on_hand.

order placed → order routing creates a FULFILLMENT ORDER status: OPEN (unfulfilled) committed +1 │ ← the order is NOT fulfilled here → staff mark "prepared for pickup" status: still OPEN (no inventory change) │ ← still NOT fulfilled — just "ready", your cue to notify → customer collects → you FULFIL it a FULFILLMENT is created on_hand -1, committed -1 fulfillment order → CLOSED, order → FULFILLED
Two pre-fulfilled states, not one There are two states before "fulfilled": OPEN (just created) and prepared for pickup (picked and set aside). Both are still unfulfilled — the item is spoken for, maybe even bagged, but it hasn't left the shop. "Prepared for pickup" is your cue to notify the customer, never a signal that stock moved. Only the final fulfil at collection is "done".
