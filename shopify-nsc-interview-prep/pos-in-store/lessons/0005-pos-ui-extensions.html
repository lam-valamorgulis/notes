POS UI Extensions: Code That Runs on the Till

Everything so far has been about data moving between systems. This is the one lesson where your code runs on the shop counter — in Preact, on an iPad, in front of a customer, sometimes with no network.

Your win today: name the three kinds of extension target (tile, action, block), say which API can write to the POS cart, and explain why the Connectivity API exists — it is the offline constraint from Lesson 1 showing up as a function call.

Ties to your mission: Lesson 2 called this Pattern C and told you not to claim it. This lesson gives you enough real mechanism to discuss it credibly while still saying you have not shipped one — which is a much stronger position than vagueness.

1. What it actually is

A POS UI Extension is your code rendering inside the Shopify POS app. Not a webview bolted on — Shopify renders it as native components, so it looks and performs like the rest of the till, on both iOS and Android.

The stack is specific and worth knowing precisely:

PieceWhat it is
LanguageTSX or JSX files — TypeScript or JavaScript
FrameworkPreact-based code
ConfigurationTOML files
Renderingremote-dom — "Shopify's library for building cross-platform user interfaces"
Why remote-dom matters conceptually Your code does not own the screen. It describes a UI, and that description is sent to the native app, which draws it with real native widgets. This is the same idea behind checkout UI extensions: you get expressiveness, Shopify keeps control of look, performance, and accessibility. It also explains the constraint — you cannot drop arbitrary HTML or a CSS framework in there. You compose from Shopify's components.

3. The API surface

Shopify groups the APIs into three families. The grouping itself is informative:

FamilyAPIsWhat the family is for
Contextual Cart, Cart Line Item, Customer, Draft Order, Order, Product The commerce objects in front of the staff member right now.
Platform Connectivity, Device, Navigation, PinPad, Print, Scanner, Storage The physical shop — hardware, network, and the device itself.
Standard Action, Locale, Product Search, Session, Toast Extension plumbing — lifecycle, language, search, feedback.

The Platform family is the one that gives the game away. Scanner, PinPad, Print, Device — you are not writing a web app. You are writing software for a machine with a barcode scanner, a card reader, and a receipt printer attached, held by someone standing up.

4. Read versus write, one last time

The distinction from Lesson 1 reappears in the API design itself:

APIDocumented capabilityRead or write
Cart API "Add, remove, and modify cart items, apply discounts, and manage cart properties" Write. This is real power — your code changes what the customer is about to pay.
Cart Line Item API "Read and interact with the currently selected cart line item in detail views" Read-only. Inspect the selected line, do not mutate it here.
A write API in front of a paying customer The Cart API can apply a discount. That means a bug in your extension does not produce a stack trace on a dashboard — it produces a wrong price at the counter, with a queue behind. There is no "refresh the page" and no staged rollout to 1% of carts.

So the safe-design instinct here is stricter than on the web: validate before you write, make the effect visible to the staff member before it is committed, and never let a failed network call leave the cart half-changed.

5. The Connectivity API is Lesson 1 coming back

Lesson 1 said offline is a constraint, not a feature — a till must keep selling when the network drops. That constraint appears in this API surface twice, and noticing it is the mark of someone who understands the domain rather than the docs:

  • Connectivity API — so your extension can ask whether it currently has a network. Its existence is the platform admitting the network is not reliable.
  • Storage API — so your extension can keep local state while offline and act on it later.
Worth saying out loud in an interview

"I would design an extension offline-first: check the Connectivity API before any call that needs the network, degrade to something honest rather than a spinner, and use the Storage API to hold intent until the connection returns. On a till, 'try again later' is not an option — someone is waiting."

7. The prerequisite nobody mentions

This needs an app, not a theme A POS UI Extension lives inside a Shopify app — a project with a shopify.app.toml and an extensions/ directory. It is not something you add to a theme.

That is why Lesson 2 told you not to claim this: every repo you maintain is a theme, not an app. Knowing exactly where the boundary is — and saying so plainly — reads as far more credible than implying broader experience and being found out on a follow-up.
One repo at your agency is an app project Your team has shipped a POS UI Extension — an inventory-transfer app that lets shop staff move stock between locations from the till. You did not write it, but you can read it, and Lesson 8 goes through it properly: the two targets in its manifest, the Navigator that is not a router, Direct API Access (the extension has no backend at all), and a severity-ranked review of what is wrong with it.

That changes what you can honestly say. Read this lesson for the shape, then Lesson 8 for the reality, and use the stronger script below.

The honest sentence, one more time, because it is worth having ready:

The honesty script

"I haven't shipped a POS UI Extension myself. I know the shape — Preact and TSX rendered through remote-dom into native components, targets for tiles, actions and blocks, and an API surface that includes the scanner, pin pad and printer. My agency has shipped one and I've read that codebase closely, so I can talk about how it's really put together. I'd be learning the toolchain, not the concepts."
