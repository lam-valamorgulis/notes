Inside a Real POS Extension

Lesson 5 gave you the shape of a POS UI Extension from the documentation. This lesson opens a shipped one — an inventory-transfer app built by the team at the agency you work for — and reads it the way a reviewer would.

Your win today: explain Direct API Access — why this extension calls the Admin API 33 times and its own backend zero times — walk the six-mutation write path that ships a transfer, and name the one bug that makes a till say "Transfer received" when nothing was received.

Ties to your mission: Lesson 5 ended with an honesty script that said "no repo you work in is an app project." That sentence is now out of date, and this lesson is why. You still have not written a POS extension — but one exists at your agency, you have read it closely, and being able to critique real code is a stronger interview position than either vagueness or an overclaim.

About the source The app is a private client project, so the client, the repository, the app credentials and the developers are not named here. Every code sample below is real, quoted from the repository, and reduced only by removing logging and unrelated lines. Nothing has been invented to make a point.

1. What the app does

A retailer with many shops needs to move stock between them. Historically that is a back-office job: someone opens Shopify admin on a laptop, builds a transfer, and a staff member in the shop finds out later. This app moves that job onto the counter. A staff member taps a tile on the POS home screen, picks a destination shop, scans the items into a list, and sends the transfer — standing at the till, holding the stock.

That is the whole product. It is worth holding onto, because every technical decision below follows from it: the person using this is standing up, holding a scanner, and has a queue behind them.

2. The repo has two projects in it

The first thing to understand is the folder layout, because it maps exactly onto the "extensions live in an app, not a theme" rule from Lesson 5:

the-app/ ├── shopify.app.toml ← the APP manifest: scopes, webhooks, [pos] ├── app/ ← a REMIX web app (Node server) │ ├── shopify.server.js OAuth, session storage │ └── routes/ embedded admin pages ├── prisma/schema.prisma ← one table: Session ├── Dockerfile ← deployed to Google Cloud Run │ └── extensions/ └── inventory-transfer/ ← the POS UI EXTENSION (the real product) ├── shopify.extension.toml ├── api/ ← GraphQL calls └── src/ ← Preact screens

Two deployable things, one repository. The app/ directory is a Remix server that gets built into a Docker image and run on Cloud Run. The extensions/ directory is compiled and shipped to Shopify, and runs inside the POS app on the device. They are joined by shopify.app.toml, which declares the scopes both of them rely on:

[access_scopes]
scopes = "read_locations,write_inventory_transfers,write_locations,
          write_products,write_inventory_shipments,
          write_inventory_shipments_received_items,read_inventory"

[pos]
embedded = true

The [pos] embedded = true line is small and important: it is what makes this app eligible to render inside POS at all.

3. The backend that isn't there

Here is the finding that reframes the whole codebase. Search the extension for calls to the app's own Cloud Run backend and you find none. Search it for this instead:

const response = await fetch("shopify:admin/api/graphql.json", {
  method: "POST",
  body: JSON.stringify({ query, variables }),
});

…and you find it 33 times. That URL is not a real host. It is Direct API Access: a special scheme the extension runtime intercepts, attaches the merchant's credentials to, and forwards to the Shopify Admin GraphQL API. The extension talks to Shopify directly from the device.

WHAT YOU EXPECT WHAT THIS APP ACTUALLY DOES ┌──────────────┐ ┌──────────────┐ │ POS extension│ │ POS extension│ └──────┬───────┘ └──────┬───────┘ │ fetch │ fetch ▼ │ "shopify:admin/api/graphql.json" ┌──────────────┐ │ │ your backend │ ← auth, rate │ (runtime injects credentials) │ (Cloud Run) │ limits, caching │ └──────┬───────┘ │ │ Admin API │ ▼ ▼ ┌──────────────┐ ┌──────────────┐ │ Shopify │ │ Shopify │ └──────────────┘ └──────────────┘ The Cloud Run server still exists — but only to install the app.

So what is the Remix app for? Almost nothing. Its one substantive job is OAuth and session storage — an app must have a URL to be installed, and installation is what grants the access scopes that Direct API Access then uses. Open app/routes/app._index.jsx and you find the unmodified Shopify starter template, still containing the demo action that creates a product with a randomly chosen colour from ["Red", "Orange", "Yellow", "Green"]. Nobody deleted it, because nobody ever needed that page.

Why this is the most useful thing in the repo It answers a question people get wrong in interviews: "does a POS UI Extension need a backend?" The instinctive answer is yes — extensions are clients, clients need servers. The real answer is that for anything expressible as Admin API calls, no backend is needed, and this app is the proof. You need a backend when you need something Shopify does not store: your own database, a third-party system, a secret you cannot ship to a device, or work that must continue when the till is asleep.
The trade you are making Direct API Access means the scopes are exercised from the shop floor. This app holds write_products and write_inventory_transfers, and any code path in the extension can use them. There is no server in the middle to narrow what a device may do, to enforce a business rule, to rate-limit a stuck retry loop, or to keep an audit log. You trade a whole tier of control for the simplicity of deleting it.

That is a perfectly reasonable trade for an internal tool used by trained staff. Being able to say it is a trade is the part that reads as senior.

4. Two targets, and a router that is not a router

The extension manifest declares exactly the two targets Lesson 5 described:

[[extensions.targeting]]
module = "./src/Tile.jsx"
target = "pos.home.tile.render"

[[extensions.targeting]]
module = "./src/Modal.jsx"
target = "pos.home.modal.render"

The tile is 24 lines, and it is the entire entry point to the product:

const TileComponent = () => {
  const api = useApi();
  return (
    <Tile
      title="Inventory Transfers"
      onPress={() => { api.action.presentModal(); }}
      enabled
    />
  );
};

export default reactExtension("pos.home.tile.render", () => <TileComponent />);

Everything else hangs off the modal. Inside it, navigation works in a way that surprises web developers — there are no routes, no URLs and no path matching. You render every screen as a sibling inside a <Navigator>, each with a name, and you move between them by calling a function:

<Navigator>
  <Screen name="Home" title="Transfers"> … </Screen>
  <NewTransferModal />        {/* renders <Screen name="NewTransfer"> */}
  <CameraScannerScreen />     {/* renders <Screen name="CameraScanner"> */}
  <EditDraftTransfer />
  <ReceiveTransfer />
</Navigator>

// and to navigate:
api.navigation.navigate("NewTransfer");
Every screen is mounted all the time Because the screens are siblings rather than route matches, they all mount when the modal opens — including their useState, their useEffect and any fetch those effects trigger. Screens in this app defend themselves by bailing out early, for example if (!transfer) return null; at the top of the receive screen.

This is the single biggest mental adjustment coming from React web work. "The component is not on screen" does not mean "the component is not running."

5. The domain: a transfer is a state machine

Before the code makes sense, the Shopify object model has to. A transfer is not one record that changes a status field — it is two related objects, and knowing the split explains every mutation name in the app:

ObjectWhat it represents
InventoryTransferThe intent. Origin, destination, note, and the line items you plan to move.
InventoryShipmentThe physical event. What actually left, in a box. A transfer can have several.

That is why the receiving side accepts and rejects against a shipment, not against the transfer: you receive a box, and the box may not contain everything that was promised. The status flow the app drives looks like this:

DRAFT ──────────────► READY_TO_SHIP ──────────────► (in transit) │ inventoryTransfer │ inventoryShipment │ │ MarkAsReadyToShip │ CreateInTransit │ │ │ │ inventoryTransferDelete ▼ ▼ inventoryShipmentReceive (gone) │ ┌────────────────────┬─┴──────────────────┐ ▼ ▼ ▼ ACCEPTED REJECTED partial: per-line ACCEPTED + REJECTED

Notice how this lands on Lesson 3. A transfer in flight is exactly why incoming exists as one of the eight inventory states — stock that has left one location and not yet arrived at another has to live somewhere in the model, and it lives there.

6. The write path: six mutations, no transaction

This is the most instructive function in the codebase. A staff member fills in a transfer and taps Send. Here is what one tap does, stripped to the calls:

export async function updateDraftTransferToInProgress({ … }) {
  // Step 1 — update destination, note and line items
  const updateResult = await updateDraftTransfer({ … });   // ← itself 2–4 calls
  if (!updateResult) return null;

  // Step 2 — flip the status
  await fetch(…)  // mutation inventoryTransferMarkAsReadyToShip

  // Step 3 — create the physical shipment
  await fetch(…)  // mutation inventoryShipmentCreateInTransit
}

And updateDraftTransfer, the innocuous-looking first line, is itself a sequence:

ONE TAP ON "SEND" 1. inventoryTransferEdit set destination + note 2. fetchTransferDetails read back, to find items to remove 3. inventoryTransferRemoveItems remove the ones no longer wanted ⏸ await sleep(300) 4. inventoryTransferSetItems set the ones we keep ⏸ await sleep(500) 5. fetchTransferDetails read back again, to verify 6. inventoryTransferMarkAsReadyToShip 7. inventoryShipmentCreateInTransit Any one of these can fail. There is no rollback.
Partial failure is the real bug class here Suppose step 4 succeeds and step 7 fails — the wifi drops as the staff member taps, which is the ordinary case at the back of a shop. The function returns null, the UI reports a failure, and the staff member taps again. But the transfer has already been edited and marked ready to ship. The retry now runs against an object in a different state than the code assumed.

This is a distributed transaction wearing a plain async function. The fixes are known ones — make the sequence idempotent so replaying it is safe, drive it from a single source of truth you can re-read, or move the sequence server-side where you can retry it without a person standing there. This app does none of the three, which is a real risk and also an entirely normal state for a v1 internal tool.
Those sleep calls deserve their own note await new Promise(r => setTimeout(r, 300)) between two mutations is a timing guess standing in for a consistency guarantee. It is there because the developer saw a read return stale data after a write. 300ms usually wins the race on office wifi. It will lose it on a busy shop network, and when it loses, the failure is silent and the data is wrong.

The same instinct appears in the UI layer, where refreshing the list waits 2000ms with the comment "Delay to ensure server has processed the new transfer." If you ever want a single line to explain read-after-write consistency in an interview, this is it.

7. The bug worth remembering

Lesson 5 warned that on a till, failure is public. Here is that warning as a real defect, in the code that receives a shipment. First, the API helper:

const json = await response.json();

// the real path is json.data.inventoryShipmentReceive.userErrors
if (json?.data?.userErrors && json?.data?.userErrors?.length > 0) {
  console.error("errors", json.data.userErrors);
  return null;
}

return null;   // ← and success returns null too

Two faults stacked. The userErrors check reads the wrong path in the response, so it never fires. And both branches return null, so the function's return value carries no information at all. Now the caller:

const res = await mutateInventoryShipmentReceive(shipment.id, lineItems, type);

if (res?.userErrors) {          // res is ALWAYS null — dead code
  console.error(…);
}

And finally, how the staff member is told what happened:

} catch (error) {
  console.error("Error processing shipments:", error);
} finally {
  if (type === "ACCEPTED") {
    setBanner({ message: ALL_RECEIVED_BANNER_MESSAGE, variant: "confirmation" });
    onTransferReceived("ACCEPTED", transfer.name);
  }
  …
}
The green banner is in a finally block finally runs whether the try succeeded or the catch caught. So if every mutation fails — network down, scope missing, invalid quantity — the staff member still sees a green "Transfer received." The stock is not received. The error exists only in a console.error nobody will ever read, on a device with no console.

This is precisely the failure mode Lesson 5 described in the abstract: a bug at the counter does not produce a stack trace on a dashboard, it produces a confident wrong answer in front of a customer. Someone will discover it during a stock count weeks later.

The fix is not clever, and that is the point. Return the mutation result instead of null, read userErrors at the right path, and move the success banner out of finally into the success path.

Cover the screen Why does the extension not need a backend? What does finally do that try does not? And why is a 300ms sleep between two mutations a bug rather than a fix?

8. The hardware loop

The scanner is where this stops resembling web work. The API is a subscription — barcodes arrive as a stream of events, not as a function you call:

const { data } = useScannerDataSubscription();
const processedBarcodesRef = useRef(new Set());
const isNavigatingRef = useRef(false);

useEffect(() => {
  if (data && data.trim() !== ""
      && !processedBarcodesRef.current.has(data)   // not already handled
      && !isNavigatingRef.current) {               // not mid-navigation
    processedBarcodesRef.current.add(data);
    handleBarcodeScan(data);
  }
}, [data]);

Both useRef guards exist because of physical reality. A hardware scanner fires repeatedly while the beam is on a barcode, so the same value arrives many times in a second — hence the Set of already-processed codes. And a scan triggers navigation, so a second scan landing mid-transition would navigate twice — hence the navigation flag.

Why useRef and not useState A ref updates synchronously; state updates are batched and visible only on the next render. Two barcode events in the same tick would both see the old state and both pass the check. The ref is not a style preference here — it is the only one of the two that works.

The scan handler then does something genuinely thoughtful. Before adding the item, it checks that the variant is stocked at both ends:

const hasOriginLocation      = locationIds.includes(originLocationGid);
const hasDestinationLocation = locationIds.includes(destinationLocationGid);

if (!hasOriginLocation || !hasDestinationLocation) {
  // three distinct messages, depending on which side is missing
  setErrorMessage("Product variant is not tracked at destination location");
  …
}

That is domain knowledge in the UI. You cannot transfer stock into a location that does not track the item, and catching it at scan time — rather than at submit time, after twenty items — is the difference between a tool staff trust and one they work around.

9. Knowing what device you are on

A phone and a tablet need different layouts, and the extension has no CSS media queries. Its answer:

const deviceName = api?.device?.name || "";
const isMobile = MOBILE_KEYWORDS.some(k => deviceName.toLowerCase().includes(k));

// MOBILE_KEYWORDS = ["phone","android","ios","xiaomi","redmi","oppo","vivo",
//                    "oneplus","samsung","google","htc","lg","motorola", …]

The result picks between <PhoneTransferList> and <TabletTransferList>. It works, and it is fragile in an interesting way: api.device.name is the user-assigned device name, so an Android tablet named "Samsung Tab — Front Counter" matches "samsung" and renders the phone layout. A till named "Sony Store iPad" matches twice over. The honest description is a heuristic over a display string, and naming it as such is what a reviewer would want to hear.

10. Two generations of state in one repo

Read the folders in the order they were written and you can watch the team outgrow their first approach. Modal.jsx, the original, holds 18 separate useState calls in one component:

const [selected, setSelected]                 = useState("all");
const [transfers, setTransfers]               = useState([]);
const [cachedPages, setCachedPages]           = useState(new Set([0]));
const [endCursor, setEndCursor]               = useState(null);
const [hasNextPage, setHasNextPage]           = useState(false);
const [currentPage, setCurrentPage]           = useState(1);
const [isLoading, setIsLoading]               = useState(false);
const [successTransferName, …]                = useState(null);
const [successUpdateTransferName, …]          = useState(null);
const [successDeleteTransferName, …]          = useState(null);
// … eight more

Three of those are near-identical success banners, and resetting the list means setting six of them by hand — a block that is duplicated in four places. The newer screens/ folder replaces this with a small generic factory:

const [Provider, useStateContext, useDispatch] = createReducerContext(
  newTransferReducer, INITIAL_STATE, "NewTransferState",
);

What makes it good is what it exports. Not the raw state object, but one narrow hook per concern:

export function useSelectedVariants()   { return useStateContext().selectedVariants; }
export function useTransferQuantities() { return useStateContext().transferQuantities; }
export function useAppendVariant() {
  const dispatch = useDispatch();
  return (variant) => dispatch({ type: "APPEND_VARIANT", payload: variant });
}

The payoff shows up in the scanner, which sits several screens away from the transfer form and needs to add an item to it. With the old pattern that meant threading a setter down through props. With this, it is one line — const appendVariant = useAppendVariant(); — and the scanner needs to know nothing about how the list is stored.

The state/dispatch split, and why it matters more here createReducerContext creates two contexts, one for state and one for dispatch. A component that only dispatches subscribes to the dispatch context, which never changes, so it does not re-render when state changes. On a mid-range Android till rendering through remote-dom, avoided renders are worth more than they are in a browser.

Both generations are live at once — Modal.jsx still owns the list, the newer screens own the create flow, and EditTransfer.jsx (1213 lines) sits beside EditDraftTransfer.tsx (1201 lines) as an unfinished fork of one screen into two. That is what a mid-refactor codebase looks like, and reading one is a more useful skill than reading a clean one.

11. What you would raise in review

Pulled together, ordered by what would actually hurt. This table is the most interview-useful thing on the page — it is a worked example of reading someone else's code and forming a judgement:

FindingWhy it mattersSeverity
Success banner in a finally block; receive helper always returns null Staff are told stock arrived when it did not. Silent data divergence found weeks later at stock count. Critical
Six-mutation send path with no rollback or idempotency A drop mid-sequence leaves a transfer half-shipped, and the retry runs against unexpected state. Critical
setTimeout used as a consistency guarantee (300ms, 500ms, 2000ms) Works on office wifi, fails on shop wifi, fails silently. High
112 console.log calls shipping to production, several logging whole GraphQL responses Noise, measurable cost on a low-power device, and product and location data written to device logs. High
SQLite session store in a container on Cloud Run with --max-instances 10 The database is inside the container filesystem. Each instance gets its own; instances are disposable. Sessions vanish or diverge. The template's own README warns SQLite only works "if your app runs as a single instance." High
ENV SHOPIFY_API_SECRET= declared in the Dockerfile Empty today, so not a live leak — but it invites the next person to paste a secret into a layer that ships with the image. Medium
canEditDestination(status) ignores its argument and returns false Reads as a rule with logic behind it; is actually a constant. Misleads the next reader. Low
~1200-line edit screen forked into two ~1200-line near-copies Every future fix has to be made twice, and one of them will be missed. Medium
How to deliver this without sounding like a hostile reviewer Lead with the constraint the team was under, then the finding. "This is a v1 internal tool for trained staff, shipped fast, and that is the right call — the thing I would fix first is the success banner in finally, because it is the one that can quietly corrupt stock counts." You have shown judgement about severity, not just an ability to spot defects. Anyone can list problems; ranking them is the senior skill.

12. Saying it in an interview

The updated honesty script

"I have not written a POS UI Extension myself. My agency has shipped one — an inventory-transfer app that lets shop staff move stock between locations from the till — and I have read that codebase closely. So I can talk about how it is actually built: two targets, a tile and a modal; screens as siblings inside a Navigator rather than routes; and Direct API Access, where the extension calls the Admin GraphQL API straight from the device and the app's own server exists only to carry OAuth. I would be learning the toolchain, not the concepts."

That answer is stronger than either alternative. It is more credible than "I know the docs," and unlike an overclaim it survives every follow-up, because all of it is true and you can go deeper on any sentence.

If they ask what you would change

"Two things, in order. First, the receive flow reports success from a finally block, so a failed receive still shows a green banner — on a till, that is worse than an error, because the staff member walks away believing the stock arrived. Second, sending a transfer is six chained mutations with no rollback, so a dropped connection can leave it half-shipped. I would make that sequence idempotent, or move it server-side where it can be retried without someone standing at the counter waiting."

Primary source — 20 minutes shopify.dev · Direct API Access, then the inventory transfer mutations in the Admin API. Read them in that order. Direct API Access explains how this extension reaches Shopify with no backend; the mutation list explains why the send path needs six calls — there simply is no single mutation that does it.
Remember this
  • Direct API Access — fetch("shopify:admin/api/graphql.json") from the device. 33 calls in this app, zero to its own backend.
  • The app server exists for OAuth, not for data. Its admin page is still the untouched starter template.
  • Screens are siblings inside <Navigator>, moved between by api.navigation.navigate("Name"). All of them mount at once.
  • InventoryTransfer is the intent, InventoryShipment is the physical event. You receive against a shipment.
  • Sending is six mutations with no transaction. Partial failure is the real risk, not a failed call.
  • A success banner in a finally block lies to the staff member. The clearest example of "failure is public" you will find.
  • useRef, not useState, for scanner de-duplication — refs update synchronously, and barcodes arrive in bursts.
  • sleep(300) between mutations is a guess, not a guarantee. It loses the race on a slow network, silently.
If you remember one thing: this extension has no backend, and that is not a shortcut — Direct API Access means the till talks to Shopify itself. What it costs you is the tier where you would have put validation, rate limiting and an audit log.
