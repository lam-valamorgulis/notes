Lesson 1 · POS & In-Store · First principles

What a POS Actually Is

Twenty seconds at a shop counter, taken apart. Start with the physical till and the data falls out on its own — including the one question that organises every POS conversation you will ever have.

Your win today: define a POS in one sentence — a machine that creates an order, decrements inventory at a location, and records a payment — and then use the question "who owns the transaction?" to sort any POS setup into "nothing to sync" or "two systems of truth."

Ties to your mission: this is the foundation lesson. Lesson 2 covers how in-store stock reaches a storefront in code. But if you cannot say what a till does first, the integration patterns are just trivia.

1. Start with the shop, not the API

A POS — Point of Sale — is the till. A screen, a card reader, a cash drawer, a receipt printer, a barcode scanner. A person stands behind it.

A customer picks up a board game, walks over, hands it across. Staff scans the barcode, taps the card reader, hands back the game and a receipt. Twenty seconds.

Hold that picture. Everything in this sub-course is what those twenty seconds mean in data.

Why start here Candidates who begin from the API say vague things about "syncing inventory." Candidates who begin from the counter say precise things about what must be true the moment money changes hands. The second sounds like someone who has shipped this.

2. The three writes

The instant the card is tapped, three things must become true:

The definition — memorise this one

"A POS is a machine that creates an order, decrements inventory at a location, and records a payment."

Two words in there are doing heavy lifting.

"At a location." Online, stock is a single number. In retail it is a number per place — and the place matters, because a unit in Melbourne cannot be handed to someone standing in Sydney. Shopify's word for a place is a location; other systems say outlet, branch, or site.

"Writes." All three are writes. A widget that shows which shops have stock is a read and is not a POS. That distinction is the difference between a two-week theme ticket and a six-month programme, so it is worth being pedantic about it in a scoping conversation.

Cover the screen — say it out loud What are the three writes? Then: which word in the inventory write changes the whole architecture?

3. Why a shop is harder than a web checkout

Online checkout does the same three writes. But a physical shop breaks four assumptions the web quietly relies on:

The web assumesA shop reality
The customer waits patiently in a browser tabA human is standing in front of staff. Latency is social, and a queue is forming behind them.
Network is up; on failure, show an error and retryShop wifi drops. The till must keep selling anyway and catch up later.
Stock is "in the warehouse" — one numberStock is at this shop, and the real truth is the shelf, not the database.
Payment is a form post to a gatewayPayment is a physical card tap — hardware, drivers, and payment certification.

The second row is the deep one, so sit with it.

Offline is not a feature — it is a constraint A website that cannot reach the server shows a spinner and nobody loses money. A till that cannot reach the server must still take the payment, or the shop stops trading. So the till holds local state and reconciles when the network returns.

Which means a POS inherits every hard problem of eventual consistency — duplicate writes, conflicting updates, ordering — in a shop, with a queue, operated by someone who has not read your design doc.
The trap: promising real-time "We'll sync inventory in real time between the shops and the website" is the single most common wrong answer in this domain. It cannot be done reliably over shop wifi, and promising it means every stock discrepancy becomes a broken promise. The senior move is to pick a direction, accept a lag, state the lag out loud, and add reconciliation to catch drift.

4. So what is Shopify POS?

Shopify POS is Shopify's own till app, running on an iPad or a phone.

The app is not the interesting part. This is: it reads and writes the same data as your online store. Same product catalogue. Same inventory, tracked per location. Same customer records. Same orders.

So an in-store sale creates a normal Shopify order — the same shape as an online one, just recorded as coming from POS.

Say this in the interview

"Shopify POS is not an integration. It is the same backend with a different front end."

That sentence is worth more than any API detail, because it tells the interviewer you understand why choosing Shopify POS removes work rather than adding it. There is no sync to build. There is no second customer list. There is no reconciliation job. The integration problem does not get solved — it stops existing.

Shopify's own summary of what POS apps can do — custom discounts and loyalty, low-inventory alerts, real-time availability across stores, ship-from-store suggestions, custom payment flows, receipts, gift cards, analytics — is at shopify.dev · Build POS apps. Note how many of those are only possible because the till and the website share one data set.

5. The question that organises everything

Now the payoff. Ask this and any POS setup sorts itself into one of two worlds:

"Who owns the transaction?"

CASE A — SHOPIFY POS IS THE TILL one system of truth ┌──────────┐ ┌─────────────────────────┐ ┌──────────┐ │ website │───────►│ SHOPIFY │◄───────│ POS app │ │ (online) │ │ orders · inventory │ │ (in shop)│ └──────────┘ │ customers · payments │ └──────────┘ └─────────────────────────┘ nothing to sync — there is no second system your job: configuration + extensions CASE B — A THIRD-PARTY TILL TWO systems of truth ┌──────────┐ ┌───────────────┐ ?? ┌───────────────┐ │ website │───────►│ SHOPIFY │◄╌╌╌╌╌╌►│ 3rd-PARTY POS │ │ (online) │ │ online sales │ sync │ in-store sales│ └──────────┘ │ online cust. │ lag │ in-store cust.│ │ its own stock│ │ REAL shelf │ └───────────────┘ └───────────────┘ ▲ every hard problem lives HERE ↓ ↓ ↓ oversell split customer two reports history that disagree

Case A — Shopify POS is the till. Shopify owns the transaction. In-store and online sales land in the same place. Nothing to sync, because there is no second system.

Case B — a third-party till. That system owns in-store orders, in-store customers, and the real shelf count. Shopify knows only about online. You now have two systems of truth, and every difficult problem in this field descends from that one fact.

6. The oversell, minute by minute

Almost every POS interview question is this scenario wearing a disguise. Learn the timeline and you can answer most of them.

TimeWhat happensWhat each system believes
2:00One unit left in the Melbourne shop.POS: 1 · Shopify: 1 ✅
2:05A walk-in customer buys it. The till writes its three writes — locally.POS: 0 · Shopify: 1 ❌ drift starts here
2:06An online shopper adds it to their cart. The site says "in stock" — truthfully, according to Shopify.POS: 0 · Shopify: 1 ❌
2:07They check out. Shopify accepts the order and takes the money.POS: 0 · Shopify: 0 — but two units were sold and one existed
2:20The POS sync finally runs and pushes 0.Both say 0. The damage is already done and invisible.

The failure is not the sync being slow. The failure is that Shopify promised a unit it did not have. That reframing is the interview answer, because it points at where you can actually intervene:

  • Shrink the window — push stock changes on an event instead of a 15-minute batch. Helps, never eliminates. There is always some window.
  • Stop promising the last unit — hold a buffer, so Shopify shows 0 when the real count is 1. You lose a little revenue and buy accuracy. Usually the right trade.
  • Verify before you promise — re-check availability at checkout rather than at add-to-cart. Moves the check to the last possible moment.
  • Plan the apology — decide in advance what happens when it does go wrong: refund, substitute, or hold for restock. It will go wrong; a plan is part of the design, not an admission of failure.
The senior framing Two systems cannot be made consistent in real time over shop wifi. So do not design for consistency — design for a known, stated lag plus reconciliation to catch drift, and decide up front which system is allowed to be right about what. "Shopify owns sellable stock; the POS owns cost and production" is a real answer. "We'll sync both ways in real time" is not.

Remember this
  • A POS creates an order, decrements inventory at a location, and records a payment. All three are writes.
  • "At a location" changes the architecture — stock is a number per place, not one number.
  • Offline is a constraint, not a feature. A till must keep selling when the network drops, so it inherits eventual consistency.
  • Shopify POS is not an integration — it is the same backend with a different front end. Same catalogue, inventory, customers, orders.
  • "Who owns the transaction?" sorts everything: Case A = one truth, nothing to sync. Case B = two truths, all the pain.

If you remember one thing: ask "who owns the transaction?" — because that single answer tells you whether you are configuring a system or reconciling two of them.
