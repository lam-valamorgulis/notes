Three Ways In-Store Stock Reaches a Shopify Storefront

Most candidates say "POS" and mean four different things at once. This lesson gives you one sharp distinction and three named patterns — so you can say exactly which one a system uses, and why it matters to the back end.

Your win today: name the three ways a physical shop's stock can reach a Shopify product page — vendor drop-in, theme-woven widget, and native Shopify POS — and explain the one question that separates them: who owns the transaction?

Ties to your mission: this is the gap in your Shopify story. You have worked daily inside POS-integrated storefronts, but the integration layer was built by others. This sub-course closes the gap so that when an interviewer asks "how does in-store stock get onto the site?", you answer from mechanism, not from vibes.

1. The distinction that fixes everything

"POS integration" almost always turns out to be one of two completely different jobs. Getting this wrong is the fastest way to lose a systems-design conversation.

Stock visibilityPoint of sale
The question it answers"Is this on a shelf near me?""Take this customer's money, now, in the shop."
Direction of dataRead only. Stock levels flow out of the shop.Read and write. Orders, payments, and customers flow in.
If it breaksA widget shows stale or no stock. Annoying.You cannot sell. The shop stops.
Who owns the order recordNobody — no order exists yet.Whichever system rings up the sale. This is the whole game.
Say this out loud until it is automatic

"Showing in-store stock is a read. Selling in store is a write. The read is a widget problem; the write is a systems-of-truth problem."

Almost every "POS integration" you will meet on a Shopify theme is the read. It looks up stock and draws a list of shops. It never takes a payment. That is worth knowing before you over-claim in an interview — and worth asking about before you estimate a ticket.

2. The three patterns

Here is the whole landscape on one page. Notice where the boundary of your code sits in each — that boundary is what changes your job.

Read the diagram this way In A, the browser talks straight to the POS vendor and Shopify never learns anything. In B, you own a bridge that writes the shopper's store choice back into the Shopify cart. In C, there is no bridge at all, because there is only one system — Shopify is the POS.

3. Pattern A — vendor drop-in

The vendor ships a JavaScript bundle. Your theme's entire job is to hand it a settings object and an empty <div>. Here is a real one, trimmed:

{% comment %} @name: Retail Express Click and Collect {% endcomment %}
{% if template == 'cart' or template == 'product' %}
  {{ 'click-and-collect-es6.js' | asset_url | script_tag }}

  <script>
    function initCnc() {
      clickAndCollectSettings = {
        subdomain: '{{ shop.permanent_domain }}'.split('.', 1),
        apiPrefix: 'shopify.retailexpress.com.au',
        showQuantity: true,
        enableMap: true
      };
      {% if template == 'cart' %}
      window.cnc = new ClickAndCollectCart(clickAndCollectSettings);
      {% endif %}
      {% if template == 'product' %}
      window.cnc = new ClickAndCollectProduct(
        clickAndCollectSettings,
        '{{ product.selected_or_first_available_variant.id }}'
      );
      {% endif %}
    }
    document.addEventListener("DOMContentLoaded", function () {
      if (!document.getElementById('cnc-container')) {
        console.log('Click and Collect element not found.');
      } else { initCnc(); }
    });
  </script>
{% endif %}

That is the whole integration — 57 lines. Inside the vendor bundle, the request it builds is:

GET https://shopify.retailexpress.com.au
      /api/shopify_stores/{subdomain}/outlets
      ?variant_ids={variantId}&qty-{variantId}=1

Three things are worth naming out loud, because each is an interview answer:

  • The lookup key is the Shopify variant_id. That means the POS vendor holds its own mapping from Shopify variant → its internal stock code. You do not own that mapping, and when a variant is recreated it silently breaks. "Who owns the identity mapping?" is always a good question to ask.
  • The store's identity comes from shop.permanent_domain, split on the first dot. The vendor keys its whole tenant lookup off the *.myshopify.com subdomain — which is why this snippet needs no API key at all.
  • "Outlets" is the vendor's word for shops. Every POS vendor invents its own noun — outlet, location, store, branch, site. Match their vocabulary in the interview and you sound like you have done this.
This snippet is dead code — and that is the lesson In the repo I read it, nothing ever calls {% render 'click-and-collect' %}. The file sits there, the CSS sits there, the 35 KB vendor bundle sits there — all unreferenced. The live integration is Pattern B. Never describe an integration from the presence of a file. Grep for the render call. A snippet that is never rendered is documentation of a decision someone already reversed.

4. Pattern B — theme-woven widget

Here the vendor still ships a widget, but the theme feeds it and listens to it. Three snippets, all rendered from theme.liquid. First, the theme pushes its catalogue into the page:

<script type="application/json" id="sis-product-json-loaded">
  {
    "handle": "{{ product.handle }}",
    "id": {{ product.id }},
    "variants": [{% for variant in product.variants %}
      {
        "available": {{ variant.available }},
        "id": {{ variant.id }},
        "inventory_quantity": {{ variant.inventory_quantity }},
        "sku": {{ variant.sku | json }},
        "barcode": {{ variant.barcode | json }}
      }{% unless forloop.last %},{% endunless %}{% endfor %}
    ]
  }
</script>

This inverts Pattern A. Instead of the vendor pulling from Shopify's Admin API, the theme serialises the product — including per-variant sku and barcode, the keys a POS actually uses — straight into the HTML. Cheap, no API credentials, no rate limits. And it has a cost:

Exact stock levels become public inventory_quantity renders the real number into page source for anyone to read — including competitors, at scale, on every product. Shopify exposes this field in Liquid, so it is not a bug; it is a choice someone made. If an interviewer shows you this, the senior answer is: "publish available as a boolean, or bucket it — 'low stock' — unless the business has explicitly decided exact counts are fine to leak."

5. The bridge: how the back end ever finds out

Now the part that makes this a backend lesson. A shopper picks the Bondi store in a third-party widget. Checkout is Shopify's. Fulfilment reads Shopify orders. So how does "Bondi" survive?

Not a webhook. Not an app. Not a metafield. Here is the real code:

_stockinstore.clickcollect = {
  onStoreSelected: function (data) {
    if (data.selectedstore !== null) {
      sisGetCartToken(function (token) {
        if (token !== null) {
          sisUpdateCartAttributes(token, data.selectedstore.code, function () {});
        }
      })
    }
  }
}

var sisGetCartToken = function (pcallback) {
  fetch('/cart.js')
    .then(r => r.json())
    .then(data => pcallback.call(this, data.token))
    .catch(() => pcallback.call(this, null));      // ← swallows the error
}

var sisUpdateCartAttributes = function (token, storecode, pcallback) {
  fetch('/cart/update.js', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      attributes: { 'storeCode': storecode, 'orderIdentifier': token }
    })
  })
  ...
}

The chosen store is written into cart attributes. And cart attributes are the one channel that crosses checkout without any server-side code at all:

Verified against the docs, not from memory The Liquid cart object's attributes holds "additional attributes entered by the customer with the cart" (shopify.dev · cart). The Liquid order object also has attributes — "the attributes on the order… Attributes are collected with the cart" (shopify.dev · order). So a value written by POST /cart/update.js lands on the finished order, where any downstream system can read it.
The one-sentence answer to memorise

"A third-party store picker persists the shopper's choice as a Shopify cart attribute, and because cart attributes are carried onto the order, fulfilment can read the store code off the order without any app, webhook, or custom back end."

Cover the screen — answer from memory (1) Which HTTP call writes the store choice, and to what field? (2) Why does the value still exist after checkout? (3) In Pattern A, where would the same store choice have gone?
(3) is the interesting one: in Pattern A it goes nowhere. The browser-to-POS lookup is read-only, so a store choice made there is invisible to Shopify forever.

6. Four failure modes in nine lines

That bridge code is short, which makes it a perfect code-review exercise. A senior engineer should spot these unprompted:

#The flawWhat the shopper experiences
1.catch(() => pcallback(null)) then if (token !== null) — the write is skipped and nothing is logged or retried.Picks a store, sees a confirmation in the widget, and the order arrives with no store on it. Silent data loss.
2orderIdentifier stores the cart token captured at selection time. A cart token changes when the cart is emptied or recreated.The attribute now points at a cart that no longer exists — a stale foreign key written by the client.
3On reload, the store is recovered from a cookie (_SISSTORECODEINFO).Clear cookies, switch device, or open a private window and the choice is gone — even though the cart survived.
4The attribute keys are storeCode, not __storeCode.Shopify documents a __ prefix for private attributes that "don't affect page rendering" and improve caching. Un-prefixed keys forfeit that.

Flaw 4 is a genuinely obscure one worth remembering — see the attributes section of shopify.dev · cart. Naming it in an interview is a strong signal, because it shows you read platform docs rather than copying snippets.

Honest limit of what I verified Shopify's Cart AJAX API docs state that attributes takes key-value pairs, but they do not say whether a POST /cart/update.js merges with existing attributes or replaces the whole object. I did not find that documented. If a ticket depends on it, test it — do not assume. Saying "the docs don't specify, so I'd verify it in a dev store" is a better interview answer than a confident guess.

7. Pattern C — the one none of these use

Native Shopify POS removes the integration problem by removing the second system. Shopify holds the catalogue, the inventory, the customers, and the in-store transaction. There is no sync, because there is nothing to sync.

Where your code goes in that world is a POS UI Extension — it runs inside the till app itself, written in TSX/JSX with Preact, configured by TOML, rendered through Shopify's remote-dom library. The targets are named after where they appear:

TargetWhere it shows up
pos.home.tile.renderA tile on the smart grid — the POS home screen
pos.home.modal.renderThe modal that tile opens
pos.product-details.block.renderInline content on a native product screen
pos.cart.line-item-details.action.renderAn action on a cart line item

Targets and stack confirmed at shopify.dev · POS UI Extensions. Note the shape: tiles, actions, blocks — the same extension-target vocabulary as checkout extensibility, which you already covered in Lesson 23 of the main course.

Do not claim this one No repo you work in contains a Shopify app or a POS UI Extension — no shopify.app.toml, no extension targets, anywhere. Pattern C is knowledge you are learning here, not experience you have. The honest framing is: "I've maintained storefronts integrated with third-party POS systems; I know how POS UI Extensions work but I haven't shipped one." That sentence costs you nothing and protects you completely.

Remember this
  • Stock visibility is a read; point of sale is a write. Nearly every theme "POS integration" is only the read.
  • Pattern A — vendor drop-in: a config object plus an empty div; the browser calls the POS API directly; Shopify learns nothing.
  • Pattern B — theme-woven: the theme serialises its own catalogue into JSON for the widget, and you own the write-back.
  • The bridge is a cart attribute. POST /cart/update.js → cart.attributes → order.attributes. No app, no webhook.
  • Pattern C — native Shopify POS: one system, no sync; your code is a POS UI Extension (Preact/TSX) at targets like pos.home.tile.render.
  • A file is not an integration. Grep for the render call — dead snippets outlive the decisions that made them.
  • Exposing inventory_quantity publishes exact stock counts to anyone reading page source.
If you remember one thing: the question that sorts every POS conversation is "who owns the transaction?" — because that decides whether you are building a widget or a system of truth.
