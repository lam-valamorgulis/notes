Lesson 3 · POS & In-Store · The data model

Locations & Multi-Location Inventory

Lesson 1 said "inventory drops at a location." This is that sentence's data model — eight inventory states, three mutations, and the one distinction that decides whether your sync job is safe to retry.

Your win today: name Shopify's eight inventory states, explain why available is the only one a shopper can buy, and say which inventory mutation is idempotent — and therefore which one your webhook handler should use.

Ties to your mission: Lesson 1 ended with the oversell. This lesson shows Shopify already has a first-class answer to it built into the data model — and most candidates have never noticed it.

1. A Location is a place, and places can decline work

Shopify's Location is "a physical place where merchants manage and fulfill inventory — such as retail stores, warehouses, or fulfillment centers." A shop is a location. So is a warehouse. So is a factory's back room.

The fields that matter here are the ones that let a location say no:

FieldDocumented asWhy you care
fulfillsOnlineOrders"Whether this location can fulfill online orders."A shop can hold stock the website is not allowed to sell. This is the switch behind "shop-only stock."
localPickupSettingsV2"Local pickup settings for the location."Whether this shop offers Click & Collect at all, and on what terms.
isActive"Whether the location is active."A closed shop that still holds stock. Deactivating removes it from the pool.
inventoryLevels"A list of the quantities of the inventory items that can be stocked at this location."The join between a product and a place. The numbers live here.
hasUnfulfilledOrders"Whether this location has orders that need to be fulfilled."A cheap safety check before deactivating or migrating a location.

Field names and quotes from shopify.dev · Location.

The built-in answer to "shop stock vs web stock" People reach for tags, metafields, or a separate feed to stop the website selling shop-floor stock. The platform already has it: set fulfillsOnlineOrders to false. Knowing the built-in answer before proposing a custom one is precisely the instinct an interviewer is testing.

2. Where a stock number actually lives

Stock is never a property of a product. It is a property of a product at a place. Three objects express that:

WHERE A STOCK NUMBER ACTUALLY LIVES ┌────────────────┐ ┌────────────────┐ │ InventoryItem │ │ Location │ │ │ │ │ │ the *thing* │ │ the *place* │ │ (one per │ │ (shop, │ │ variant) │ │ warehouse) │ └───────┬────────┘ └───────┬────────┘ │ │ └───────────────┐ ┌───────────────┘ ▼ ▼ ┌────────────────────┐ │ InventoryLevel │ │ │ │ the NUMBERS for │ │ this item at │ │ this place │ │ │ │ available: 3 │ │ committed: 1 │ │ safety_stock: 1 │ │ on_hand: 5 │ └────────────────────┘ "3 in stock" is meaningless. "3 available of item X at location Y" is a fact.
Say it this way

"An InventoryLevel is the row where an InventoryItem meets a Location. Every stock number is scoped to that pair — which is why 'how many do we have?' is not a well-formed question in retail."

3. The eight states

Shopify does not store one number per location. It stores eight, and they mean different things:

StateDocumented asSellable?
available"The inventory that a merchant can sell"Yes — this is the only one
committed"The number of units that are part of a placed order but aren't fulfilled"No — already sold, still on the shelf
reserved"The on-hand units that are temporarily set aside"No
damaged"The on-hand units that aren't sellable or usable due to damage"No
safety_stock"The on-hand units that are set aside to help guard against overselling"No — deliberately
quality_control"The on-hand units that aren't sellable because they're currently in inspection for quality purposes"No
on_hand"The total number of units that are physically at a location"It is a total, not a bucket
incoming"The inventory that's on its way to a merchant's location"No — and it is not physically there

All quotes from shopify.dev · Inventory management apps, verified 2026-07-31.

Two structural points hold the whole model together:

  • on_hand is a total, not a bucket. It is what is physically in the building, made up of the other on-hand states. So available + committed + reserved + damaged + safety_stock + quality_control is what sits on the floor.
  • incoming is the odd one out — the docs call it the only state for quantities not physically present. It sits outside on_hand because it has not arrived. Never show it as buyable.
Why "committed" is the state that confuses people A unit that is committed is still on the shelf — someone bought it online and nobody has picked it yet. So a staff member counting the shelf will find it and think the system is wrong. It is not: the shelf holds 5, but only 3 are yours to sell. This is the single most common source of "the stock numbers are broken" tickets in retail.

4. safety_stock — the platform's own answer to the oversell

In Lesson 1 the fix for the oversell was: stop promising the last unit — hold a buffer so Shopify shows 0 when the real count is 1.

Shopify has a named state for exactly that, described in its own docs as units "set aside to help guard against overselling."

This is a strong interview moment

"Rather than invent a buffer in application code, I'd move units into safety_stock. The platform models it as a first-class state, so the buffer is visible in the admin, survives every integration, and does not have to be re-implemented by whoever touches this next."

The contrast is what makes it land. A custom buffer lives in one service and is invisible everywhere else. A safety_stock buffer is a property of the inventory itself.

Cover the screen Which single state can a shopper buy from? Which state is physically present but already sold? And which state is not physically present at all?

5. Three mutations — and only one is safe to retry

This is the part that matters most to a backend engineer, because it decides whether your sync job can be retried.

MutationWhat it doesRetry-safe?
inventoryAdjustQuantities "adjusts the inventory quantity … by the given delta" No. Relative. Running −1 twice removes two.
inventorySetQuantities "explicitly sets the quantity of inventory in the on_hand or available state" Yes. Absolute. Setting 5 twice still means 5.
inventoryMoveQuantities Moves quantities between available and unavailable states Depends — it is a transfer, so treat it like a delta.
DELTA vs ABSOLUTE — WHY THIS DECIDES YOUR DESIGN adjustQuantities(delta: −1) setQuantities(available: 4) ─────────────────────────── ────────────────────────── call 1 → 5 becomes 4 call 1 → available = 4 timeout! did it land? unknown timeout! did it land? unknown call 2 → 4 becomes 3 ✗ WRONG call 2 → available = 4 ✓ FINE a retry CORRUPTS the count a retry is a NO-OP ⇒ if the POS sends you "we sold one", do NOT translate that into a delta. Ask it for the new TOTAL and set it.
The classic bug this causes A POS webhook says "sold 1." Your handler calls inventoryAdjustQuantities(delta: −1). The response times out but the write succeeded. Your retry logic fires. Stock is now one lower than reality, silently and permanently — and it drifts further with every timeout, until someone does a manual count months later and nobody can explain the gap.

The fix is not better retry logic. It is choosing an absolute write, so a retry is harmless by construction.
When a delta is still the right call Deltas are not banned — they are correct when you genuinely have a stream of events and can guarantee exactly-once processing (a deduped queue with an idempotency key per event). If you cannot guarantee that, prefer absolute. And say the trade-off out loud in an interview: "deltas need exactly-once delivery; absolutes only need last-write-wins, which is much cheaper to guarantee."

6. What this means for a POS integration

Put the pieces together and the design of a stock sync almost writes itself:

  • Sync to available, not on_hand — unless you genuinely know the physical total. available is the number that gates selling.
  • Ask the POS for totals, not events — so you can use an absolute write and stop worrying about retries.
  • Do not fight committed — Shopify manages it from orders and fulfilment. If your job overwrites it, you will double-count.
  • Put the buffer in safety_stock — visible, portable, and not your code's private secret.
  • Use fulfillsOnlineOrders to keep shop-floor stock off the website, instead of filtering in the theme.

  • committed is sold but still on the shelf — the top cause of "your numbers are wrong" reports.
