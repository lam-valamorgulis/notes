Month 1 · Lesson 1 · First principles

What is Flutter, really?

Every pixel is yours. Understand that one sentence and the whole framework starts making sense — including the parts that will be asked about in a senior interview.

Your win today: a running Flutter app on your own machine, changed by you and hot-reloaded in under a second — plus a one-sentence answer to "what is a widget?" that is actually correct.
Versions used here — checked 2026-07-28 Flutter 3.44 stable (released 18 May 2026), Dart SDK 3.12.2. Source: Flutter — What's new. If your flutter --version says something newer, that is fine; nothing in this lesson is version-fragile.

The first idea: Flutter draws its own pixels

Most tools that promise "one codebase, two platforms" work by wrapping the platform's own controls. You write a description, and the tool creates a real iOS button or a real Android button underneath.

Flutter does not do that. Flutter asks the operating system for one thing — a blank canvas and a stream of events — and then paints every button, every letter, and every shadow itself, using its own rendering engine.

Say it like this

"Flutter doesn't use the platform's widgets. It gets a canvas from the OS and draws the whole interface itself."

This single design decision explains almost every trade-off you will meet this year:

Because Flutter draws everything…You getYou pay
The UI is not made of native controls Your screen looks identical on iOS and Android. What you design is what ships. You do not automatically inherit a platform's new look when the OS updates.
Nothing has to be translated to a platform control No "waiting for the platform to support it" — any design is achievable. You own the details: taps, focus, scroll physics feel right only if the framework got them right.
Layout and paint happen in Flutter's own engine Smooth animation is realistic, because there is no per-frame bridge crossing. The engine ships inside your app, so a Flutter app has a size floor of a few megabytes.
Accessibility is not free from the platform Flutter exposes a semantics tree to the OS screen readers on purpose. If you do not add semantics, a blind user gets nothing. (Month 11)

Here is the stack you are actually standing on. You will be asked to draw or describe this in a senior interview, so learn it now while it is only four boxes.

The second idea: a widget is a description, not a thing

This is the sentence that trips up everyone who comes to Flutter from another UI toolkit. In Flutter, a widget is an immutable description of part of the interface. It is not the pixels. It is not an object you keep a reference to and edit later.

class Greeting extends StatelessWidget {
  const Greeting({super.key, required this.name});

  final String name;                          // configuration, always final

  @override
  Widget build(BuildContext context) {        // "what should this look like now?"
    return Text('Hello, $name');
  }
}

Notice what is not there: no method to change the text later. If the name changes, Flutter does not edit this widget — it throws it away and builds a new Greeting. Widgets are cheap on purpose, so creating thousands of them per second is normal and fine.

The mental model in one line UI = f(state). You write a function from data to a description. Flutter runs that function whenever the data changes, compares the result to what is on screen, and updates only the difference. You never reach out and set a label's text by hand.

The framework keeps three parallel trees to make this cheap: the Widget tree (your descriptions, rebuilt constantly), the Element tree (the long-lived slots that remember), and the RenderObject tree (the things that measure and paint). You do not need that detail today — Month 8 is entirely about it — but the names are in the glossary now so they stop sounding mysterious.

Common trap "Widget" sounds like "the button on screen". It is not. The button on screen is a RenderObject, positioned inside an Element, described by a Widget. When you catch yourself wanting to "grab a widget and change it", that is the old mental model talking — change the data instead.

Set it up for real

I checked your machine: Flutter and Dart are not installed yet, and Android Studio is missing, but the Xcode command line tools are present. So here is the exact path from here.

1 · Install the Flutter SDK

Follow the official installer — do not use a random blog post, and do not install Flutter through Homebrew (the docs do not support that path):

  • docs.flutter.dev/get-started/install → choose macOS.
  • The Quick start path (/install/quick) installs Flutter through the VS Code Flutter extension and is the currently recommended route. The Custom setup path (/install/custom) downloads the SDK yourself and lets you pick target platforms.

2 · Check the machine, not your feelings

flutter --version        # confirm the SDK is on your PATH
flutter doctor -v        # the "is my computer ready?" report

flutter doctor will list a tick or a cross per platform. Expect it to complain about Android at first — that is correct, because Android Studio is not installed. Fix the crosses one at a time, in the order the tool prints them.

Hot reload: the loop that makes Flutter feel fast

With the app running, open lib/main.dart, change the text of the app bar, and save. In the terminal where flutter run is going, you can also type:

KeyWhat happensState kept?
rHot reload — new code is injected and the widget tree rebuilds.Yes — you stay on the same screen with the same data.
RHot restart — the app restarts from scratch with the new code.No.
qQuit the session.—

Hot reload works because debug builds compile Dart just in time. Release builds are compiled ahead of time to native machine code — faster and smaller, but with no hot reload. This is also why you must never judge performance in debug mode; a debug build can be several times slower than what your users get.

Remember this
  • Flutter draws every pixel itself. The OS gives it a canvas and events; Flutter paints the rest. That one fact explains the identical look, the app size, and the accessibility work.
  • Four layers: your Dart code → framework (Dart) → engine (C++, Impeller) → embedder (a real native app) → GPU.
  • A widget is an immutable description, not the thing on screen. Flutter throws widgets away and rebuilds them; that is cheap by design.
  • UI = f(state). You never edit the screen. You change data and re-describe the screen.
  • Three trees: Widget (descriptions), Element (long-lived slots that remember), RenderObject (measures and paints). Month 8 goes deep.
  • Debug is JIT-compiled (so hot reload works); release is AOT-compiled. Never measure performance in debug mode.
  • flutter doctor -v is the answer to almost every "it will not build" problem.

If you remember one thing: a widget is a recipe, not the cake. Change the ingredients, and let Flutter cook the pixels again.
