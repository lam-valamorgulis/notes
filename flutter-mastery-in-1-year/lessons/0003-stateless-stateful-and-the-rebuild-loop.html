Stateless, Stateful & the rebuild loop

What setState actually does — and why Flutter splits a stateful widget into two classes. This is the lesson that separates people who use Flutter from people who understand it.

Your win today: a working counter and a toggle written from memory, plus the ability to trace out loud the exact path from a finger tap to a changed pixel. That trace is a standard senior interview question.

Stateless: the pure function of the UI world

A StatelessWidget describes a piece of UI using only the values handed to it. Same inputs, same output, every time. Nothing inside it can change on its own.

class HabitTile extends StatelessWidget {
  const HabitTile({super.key, required this.habit, this.onTap});

  final Habit habit;              // configuration — final, immutable
  final VoidCallback? onTap;       // a function someone else gave us

  @override
  Widget build(BuildContext context) {
    return ListTile(
      title: Text(habit.title),
      trailing: Icon(habit.done ? Icons.check_circle : Icons.circle_outlined),
      onTap: onTap,                // we don't decide what happens — we report it
    );
  }
}

Notice the shape: it receives data and reports events upward through a callback. It does not own the truth about whether a habit is done. That is deliberate, and it is the pattern you will use for nearly every widget you write this year — data down, events up.

Stateful: why on earth are there two classes?

Some things must change over time and be remembered: a counter, a text field's contents, an animation's progress. For these you need a StatefulWidget, and it always comes as a pair:

class Counter extends StatefulWidget {           // 1. the widget: immutable config
  const Counter({super.key, this.start = 0});
  final int start;

  @override
  State<Counter> createState() => _CounterState();
}

class _CounterState extends State<Counter> {    // 2. the State: mutable, long-lived
  late int _count = widget.start;               // widget.x reads the config

  void _increment() {
    setState(() {                               // tell Flutter: my data changed
      _count++;
    });
  }

  @override
  Widget build(BuildContext context) {
    return TextButton(
      onPressed: _increment,
      child: Text('Tapped $_count times'),
    );
  }
}

The reason for two classes is the thing you learned in Lesson 1: widgets are thrown away and rebuilt constantly. If the counter lived in the widget, it would reset every time a parent rebuilt. So Flutter keeps the mutable part in a separate State object that is attached to the long-lived Element, not to the widget.

Say it like this

"The widget is disposable configuration; the State object is what survives. That is why they are two classes — one is rebuilt constantly, the other persists across rebuilds."

What setState really does

Here is the part most people get wrong. setState does not rebuild your widget immediately. It does two things: it runs your callback synchronously (so your data is updated right away), and it marks this element dirty so the framework rebuilds it on the next frame.

Three consequences worth memorising, because each one is a real bug you will otherwise write:

Because setState only schedules…What follows
Several setState calls in one event handlerCost one rebuild, not several. Flutter coalesces them into the next frame.
Reading a value right after setStateYour data is already updated (the callback ran synchronously). The screen is not yet.
Calling setState after the widget is goneAn error. Guard async completions with if (!mounted) return;.
Three traps that will bite you this month 1. Never call setState inside build. That marks the element dirty while building it — an infinite loop of frames.
2. Never start work in build. No network calls, no timers, no navigation. build can run many times per second and must be a pure description. Put one-time work in initState.
3. Always dispose what you create. Controllers, timers, stream subscriptions, focus nodes. A forgotten dispose is a memory leak that only shows up after a user has navigated around for ten minutes.

The State lifecycle — the five methods that matter

MethodWhen it runsWhat belongs here
initState()Once, when the State is created.Set up controllers, subscribe to streams, kick off the first data load. Do not use Theme.of(context) here.
didChangeDependencies()After initState, and again whenever an inherited widget it depends on changes.Work that needs context lookups, like reacting to a theme or locale change.
build()Every rebuild. Possibly 60+ times a second.Only describing the UI. Nothing else.
didUpdateWidget(old)When the parent rebuilds and hands this State a new widget of the same type.Compare widget.x with old.x and re-subscribe or reset if the input changed.
dispose()Once, when the widget is permanently removed.Cancel timers and subscriptions, dispose controllers. Mirror everything from initState.
Why didUpdateWidget exists The State object outlives the widget. So if a parent rebuilds with Counter(start: 10) where it previously passed start: 0, your State is not recreated and initState does not run again. If you only read widget.start in initState, you will silently ignore the new value. That is one of the most common "why is my widget showing stale data" bugs in Flutter.

Which kind of widget should this be?

Default to StatelessWidget. Reach for StatefulWidget only when the widget itself must remember something between rebuilds. And be honest about whose state it is:

The valueKind of stateWhere it goes
Which tab is selected; whether a password is visible; animation progressEphemeral (local)StatefulWidget + setState. Perfectly professional — do not reach for a library.
The signed-in user; the cart; cached server data; the themeApp (shared)A state manager. Riverpod in Month 4, BLoC in Month 5.

The test is one question: would another screen care about this value? If no, keep it local. Both terms are in the glossary, and Flutter's own docs draw the same line.

Your turn — build two things, then predict one

Exercise · 20 minutes

In your habit_lab project (or DartPad), write these from memory. Do not copy from above.

  1. A Counter with + and − buttons, which never goes below zero.
  2. A HabitToggle: a StatefulWidget holding one bool done, showing a tick or an empty circle, flipping on tap.
  3. Add print('build ran'); at the top of each build. Tap a few times and watch the console. Now predict before you look: when you tap the counter, does HabitToggle's build also run? Why or why not?
  4. Add a Timer.periodic in initState that ticks every second and calls setState. Then navigate away without disposing it, and read the error Flutter gives you. Then fix it in dispose.
Step 4 teaches you a lesson that no amount of reading will: Flutter tells you when you leak, if you are listening.

Say it like an interviewer just asked

Interview prep · Lesson 3

Question 2 below is asked in almost every Flutter interview, at every level. The difference between a mid and a senior answer is whether you mention the Element tree and the next frame. Answer out loud, about 60 seconds each.

  1. What is the difference between StatelessWidget and StatefulWidget?
  2. What exactly happens when you call setState?
  3. Why does a StatefulWidget need a separate State class at all?
  4. Walk me through the State lifecycle, and tell me where a network call belongs.
  5. When would you not use setState?
Read the primary source Required reading: Differentiate between ephemeral state and app state and the State class API docs. Flutter's API documentation is unusually good — the class-level comments are essentially short essays, and reading them is a habit worth building now.
Ask me to drill you on the rebuild loop until you can recite it without hesitating — it comes up again in Month 8 as the foundation of every performance fix. Or paste your counter code and I will review it like a senior colleague would.
Remember this
  • StatelessWidget: output depends only on its own fields. Data down, events up through callbacks.
  • StatefulWidget is two classes because the widget is thrown away on every rebuild and the State object must survive. The State lives with the long-lived Element.
  • setState does two things: runs your callback immediately, and marks the element dirty. The rebuild happens on the next frame.
  • Many setState calls in one handler = one rebuild. Flutter coalesces them.
  • build must be pure and fast. No network calls, no timers, never setState inside it.
  • Mirror initState in dispose. Everything you subscribe to or create must be cancelled or disposed.
  • didUpdateWidget is how you notice new configuration — initState will not run again just because the parent passed a new value.
  • Ephemeral state → setState. Shared state → a state manager (Months 4–5). Ask: would another screen care?

If you remember one thing: setState does not redraw anything — it marks your element dirty and asks for the next frame. Everything else in Flutter's performance story follows from that.
