Dart is deliberately boring — except in three places

If you have written JavaScript, Java, Swift, or Kotlin, most of Dart will feel familiar: curly braces, semicolons, classes, if/for. Dart's designers were not trying to be clever. That is a feature — the interesting ideas in Flutter are in the framework, not the syntax.

Three things are genuinely different, and all three exist because Flutter needs them:

The Dart featureWhy Flutter needs it
Sound null safety — a type cannot hold null unless you write ?A UI framework that rebuilds thousands of objects per second cannot afford null crashes found at runtime.
Named parameters with required and defaultsWidget constructors take a dozen options. Positional arguments would be unreadable.
const constructors — objects built at compile timeA const widget can be created once and reused forever, so Flutter can skip rebuilding it. const is a performance feature.

1 · Four ways to hold a value, and when each locks

var   count = 0;      // type inferred (int); can be reassigned
int   total = 0;      // type written out; can be reassigned
final name  = 'Lam';  // assigned once, when the line runs
const pi    = 3.14;   // assigned once, before the program runs
late  String token;   // "I promise to set this before anyone reads it"

The difference between final and const is when the value is decided, and that is the part people get wrong:

Say it like this

"final means I cannot reassign the variable. const means the value itself is fixed before the program even runs — which is why Flutter can reuse const widgets instead of rebuilding them."

2 · Sound null safety — two separate type universes

String  name = 'Lam';   // can NEVER be null. The compiler proves it.
String? nick;           // may be null. Starts as null.

print(nick.length);     // ✗ compile error — might be null
print(nick?.length);    // ✓ null if nick is null
print(nick ?? 'none');  // ✓ use a default instead of null
print(nick!.length);    // ✓ compiles — but crashes if it IS null

String and String? are different types. That is the whole idea: the compiler forces you to deal with "might be missing" at the moment you write the code, instead of at 2am when a user hits it.

The ! trap ! means "trust me, this is not null". It compiles, so it feels like a fix. It is not a fix — it is a runtime crash you have agreed to. Treat every ! as a small debt and prefer ??, a pattern match, or an early return. In a code review, a senior developer will ask about every one.

3 · Named parameters — the reason Flutter code looks like that

This is the single biggest "oh, that's why" of Dart for Flutter. Compare:

// positional — what do these mean?
buildCard('Water', 3, true, false);

// named — self-documenting at the call site
buildCard(title: 'Water', streak: 3, done: true, pinned: false);

Anything inside curly braces in a parameter list is a named parameter. Add required to force the caller to supply it, or give it a default:

Widget buildCard({
  required String title,      // must be provided
  int streak = 0,             // optional, defaults to 0
  bool done = false,
  VoidCallback? onTap,        // optional AND nullable
}) { ... }

Now read a real Flutter constructor. You already know every piece of it:

const Text(
  'Drink water',                       // one positional argument: the string
  style: TextStyle(fontSize: 18),      // named
  maxLines: 2,                         // named, has a default
  overflow: TextOverflow.ellipsis,     // named, an enum value
)
The Flutter convention Widgets take at most one positional argument — the obvious "main" one (the text, the child) — and everything else is named. When you write your own widgets in Lesson 5, follow the same rule and your code will look like framework code.

4 · A class shaped for Flutter

Flutter models are almost always immutable: every field final, a const constructor, and a copyWith to make a changed copy. Here is the model you will use in Lesson 5:

class Habit {
  const Habit({
    required this.title,
    this.done = false,
    this.streak = 0,
  });

  final String title;        // final everywhere = immutable object
  final bool done;
  final int streak;

  // derived value — computed, never stored
  String get label => done ? '$title ✓' : title;

  // the immutable "change": return a NEW Habit
  Habit copyWith({String? title, bool? done, int? streak}) => Habit(
        title: title ?? this.title,
        done: done ?? this.done,
        streak: streak ?? this.streak,
      );
}

Two things to notice, because both matter all year:

  • this.title inside the parameter list assigns the field directly. No constructor body needed.
  • label is a getter — computed on demand from other fields. Never store what you can derive; a stored copy is a second source of truth that will eventually disagree.
Say it like this

"I do not mutate state in Flutter, I replace it. copyWith returns a new object, so change detection is a simple comparison and there is no hidden shared mutation."

5 · Collections are how data becomes widgets

Almost every screen you build is "turn this list of data into a list of widgets". Dart has two pieces of syntax that make that read cleanly, and you will use them constantly:

final habits = [
  const Habit(title: 'Water', streak: 3),
  const Habit(title: 'Read', done: true),
];

// derive numbers instead of storing them
final doneCount = habits.where((h) => h.done).length;   // 1
final titles    = habits.map((h) => h.title).toList();  // [Water, Read]

// build a list of children with conditions and loops INLINE
final children = [
  const Text('My habits'),
  if (habits.isEmpty) const Text('Nothing yet'),        // collection-if
  for (final h in habits) Text(h.label),                // collection-for
];

map and where return a lazy Iterable, so call .toList() when a widget needs a real list. collection-if and collection-for are what let a widget tree stay one readable expression instead of a pile of helper methods.

Remember this
  • const is fixed before the app runs; final is fixed when its line runs. In Flutter, const is a performance feature, not just style.
  • String and String? are different types. Sound null safety means the compiler proves a non-nullable value is never null.
  • Every ! is a crash you agreed to. Prefer ??, a default, or an early return.
  • Curly braces in a parameter list = named parameters, with required or a default. This is why widget constructors are readable.
  • Models are immutable: final fields, const constructor, copyWith to make a changed copy.
  • Derive, do not store. A getter that computes "how many are done" can never disagree with the list; a stored counter can.
  • collection-if and collection-for are how data becomes a list of widgets in one readable expression.

If you remember one thing: Dart pushes you toward immutable data and compile-time guarantees — because a framework that rebuilds the world 60 times a second cannot afford surprises.
