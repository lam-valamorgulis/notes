Month 1 · Lesson 4 · The layout rule

Enough layout to build anything

One rule, three kinds of box, and about ten widgets. Learn the rule properly now and you will never again be confused by an overflow error — or by a widget that refuses to be the size you asked for.

Your win today: you can look at any layout error — "RenderFlex overflowed", "unbounded height", "my Container ignored my width" — and know why before you try a fix. Guessing at layout is the single biggest time-waster for new Flutter developers.

The rule. Learn it word for word.

Straight from the Flutter documentation

"Constraints go down. Sizes go up. Parent sets position."

The docs are unusually blunt about how much this matters: "Flutter layout can't really be understood without knowing this rule, so Flutter developers should learn it early on." (Understanding constraints)

Unpacked, one layout pass works like this:

  1. A widget receives constraints from its parent — just four numbers: minimum and maximum width, minimum and maximum height.
  2. It passes constraints down to each child (possibly different ones per child) and asks each child what size it wants to be.
  3. It positions its children, one by one.
  4. It tells its own parent what size it decided to be — within the constraints it was given.

Four limitations that follow from the rule

The docs spell these out, and each one explains a class of bug:

LimitationWhat it means in practice
A widget can only choose a size within the constraints its parent gave it.Your width: 500 can be silently ignored. The parent has the final say.
A widget cannot know or decide its own position.To move something, change its parent (add Padding, Align, Center).
Size and position depend on the whole tree.You cannot reason about one widget in isolation. Read upward when debugging.
If a child wants a different size and the parent has no alignment information, the child's size may be ignored.The docs' own advice: "Be specific when defining alignment."

Tight and loose constraints

Two words that appear in every layout discussion, defined by the docs like this:

  • Loose — the parent says "you can be smaller than this". Minimum is zero, maximum is a limit. Center passes loose constraints.
  • Tight — the parent says "you must be exactly this size". Minimum equals maximum. SizedBox.expand passes tight constraints.

So "why did my Container(width: 300) come out full width?" almost always has the same answer: something above it passed tight constraints, and tight constraints win.

The three kinds of box

Quoting the docs directly, because the categories are worth memorising:

Kind of boxExamples from the docsWhat to expect
Tries to be as big as possibleCenter, ListViewIt will fill whatever it is allowed to fill.
Tries to be the same size as its childrenTransform, OpacityIt is transparent to layout — the child decides.
Tries to be a particular sizeImage, TextIt has intrinsic content, so it asks for what it needs.

Container is the confusing one on purpose: its behaviour changes with its arguments. Given a child and no size, it matches the child (plus any padding). Given no child and no size, it tries to be as big as possible. This is why Container feels unpredictable until you know the rule — and why SizedBox, Padding, and DecoratedBox are often the clearer choice.

Row and Column: the two alignment axes

Column(
  mainAxisAlignment: MainAxisAlignment.spaceBetween,  // vertical, for a Column
  crossAxisAlignment: CrossAxisAlignment.start,       // horizontal, for a Column
  mainAxisSize: MainAxisSize.min,                     // only as tall as the children
  children: [ ... ],
)

For a Column the main axis is vertical and the cross axis is horizontal. For a Row they swap. Getting these two names straight removes about half of all layout frustration — when something will not move, you are usually setting the wrong axis.

The two errors you will see this month, and their fixes

1 · "A RenderFlex overflowed by N pixels"

Your Row or Column asked for more space than it was given. The yellow-and-black stripes are Flutter telling you the truth rather than silently clipping.

// ✗ a long title in a Row pushes past the edge
Row(children: [Text(veryLongTitle), Icon(Icons.star)])

// ✓ let the text take the space that is left, and shorten it
Row(children: [
  Expanded(child: Text(veryLongTitle, overflow: TextOverflow.ellipsis)),
  const Icon(Icons.star),
])

2 · "Vertical viewport was given unbounded height"

You put a scrolling widget inside a Column. The Column offers unbounded height; the ListView wants to be as big as possible; infinity is not a size Flutter can render.

// ✗ ListView inside a Column
Column(children: [Text('Habits'), ListView(children: tiles)])

// ✓ give the list a bounded height
Column(children: [
  const Text('Habits'),
  Expanded(child: ListView(children: tiles)),   // "take exactly what's left"
])
Debug it, do not guess at it Three tools, in order of usefulness: 1) the Widget Inspector in DevTools — select a widget and read the actual constraints it received; 2) debugPaintSizeEnabled = true to draw every box boundary; 3) wrap a subtree in LayoutBuilder and print(constraints) to see the exact four numbers. Read the constraints before changing code — otherwise you are just trying things.

Your turn — the layout that teaches the rule

Exercise · 25 minutes

Build this one screen. It is deliberately shaped so that every step forces the rule to show itself.

  1. A Scaffold with an AppBar titled "Habits".
  2. A body Column with 16px padding around it.
  3. At the top, a Row holding a long habit name on the left and a star Icon on the right. Make the name too long on purpose, see the overflow stripes, then fix it with Expanded and ellipsis.
  4. Below it, a ListView of ten Cards. Add it without Expanded first, read the unbounded-height error, then fix it.
  5. Pin a small circular badge to the top-right corner of the first card using Stack + Positioned.
  6. Finally, wrap the whole body in LayoutBuilder and print(constraints). Rotate the simulator and watch the numbers change.
Doing steps 3 and 4 the wrong way first is the point. Both errors will happen to you in real work — this is where you decide whether they cost you two seconds or twenty minutes.

Remember this
  • "Constraints go down. Sizes go up. Parent sets position." Word for word.
  • A constraint is four numbers: min and max width, min and max height.
  • Tight = min equals max ("be exactly this"). Loose = min is zero ("be up to this"). Tight constraints override your requested size.
  • Three kinds of box: as big as possible (Center, ListView), same size as child (Transform, Opacity), a particular size (Text, Image).
  • Container changes behaviour with its arguments. Prefer SizedBox, Padding, or DecoratedBox when you want predictability.
  • Expanded forces the child to fill the remaining main-axis space; Flexible does not (its fit defaults to FlexFit.loose).
  • Overflow = children asked for more than the parent gave. Unbounded height = a scroller inside a Column. Fix with Expanded.
  • To move a widget, change its parent. A widget cannot decide its own position.

If you remember one thing: a widget never decides its own size alone — it negotiates with its parent. Debug layout by reading upward, not by adding numbers until it looks right.
