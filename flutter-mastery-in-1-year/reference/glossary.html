Reference · Nomenclature

Glossary

Flutter's own vocabulary, defined once and used the same way in every lesson. Each entry has the precise definition, then a plain-English line, then the month where it becomes important.

Why a glossary matters here: most Flutter confusion is vocabulary confusion. "Widget", "context", and "state" all mean something narrower than they sound. Get these right and half the framework stops being mysterious. Definitions follow Flutter's official glossary and API docs.

The core three — the ones everything else rests on

Widget Month 1
An immutable description of part of a user interface. A widget is configuration, not the thing drawn on screen. Flutter creates a fresh widget object for every frame that needs one, which is cheap by design.
Plain English: a widget is a recipe, not the cake. Flutter reads the recipe and cooks the pixels.
Element Month 8
The instance of a widget at a location in the tree. Elements are long-lived: when a widget is rebuilt, Flutter reuses the existing element if the new widget has the same runtimeType and key, and updates it instead of recreating everything.
Plain English: the element is the actual slot in the tree. Widgets get thrown away and replaced; the element stays and remembers.
RenderObject Month 8
The object that does real layout and painting. It holds size and position, takes constraints from its parent, and paints to a canvas. Most widgets do not create one directly — they compose other widgets that eventually do.
Plain English: the render object is the thing that actually measures and draws. It is the bottom of the stack.

Building UI

StatelessWidget Month 1
A widget whose description depends only on its own configuration (its fields). Given the same inputs it always produces the same output. It has a build method and no mutable state.
Plain English: same input, same picture. Nothing inside it changes on its own.
StatefulWidget / State Month 1
A widget paired with a separate State object that survives rebuilds and can hold values that change. Calling setState marks the element dirty so Flutter rebuilds it on the next frame. Lifecycle methods: initState, didUpdateWidget, dispose.
Plain English: the widget is thrown away and rebuilt constantly; the State object is the part that remembers between rebuilds.
build method Month 1
The method that returns a widget tree describing this part of the UI. It must be fast and free of side effects, because Flutter may call it many times per second.
Plain English: build answers "what should this look like right now?" — nothing else. Never start a network call in it.
BuildContext Month 1
A handle to the location of a widget in the tree. It is how a widget looks up the tree for inherited things — Theme.of(context), MediaQuery.of(context), Navigator.of(context).
Plain English: context is your address in the tree. You use it to ask your ancestors for things.
Key Month 8
An identity marker Flutter uses when matching new widgets to existing elements. ValueKey, ObjectKey, UniqueKey, and GlobalKey are the common kinds. Keys matter most in lists whose items are reordered, inserted, or removed.
Plain English: a key is a name tag, so Flutter knows "this is the same item that moved" rather than "a different item appeared".
Constraints Month 1
Four numbers a parent passes to a child: minimum and maximum width, minimum and maximum height. The rule, quoted from the Flutter docs: "Constraints go down. Sizes go up. Parent sets position."
Plain English: the parent says how big you are allowed to be, you choose a size inside that, and the parent decides where you sit.
Sliver Month 2
A portion of a scrollable area. Slivers can compute their layout lazily based on what is currently visible, which is how Flutter scrolls very long content cheaply. Used through CustomScrollView, SliverList, SliverAppBar.
Plain English: a sliver is a scrolling piece that only does work for the part you can actually see.
Material / Cupertino Month 2
The two built-in design languages shipped with Flutter: Material (Google's, currently Material 3) and Cupertino (Apple's look). They are widget libraries, not requirements — you can draw anything you want.
Plain English: two ready-made sets of buttons and bars. You are free to ignore both.
Hot reload Month 1
Injecting changed Dart code into the running app and rebuilding the widget tree, while keeping the current app state. Different from hot restart, which throws state away, and from a full restart.
Plain English: save the file and the screen updates in under a second, without losing where you were.

State & architecture

State (app state vs ephemeral state) Month 3
Ephemeral (local) state belongs to one widget — a checkbox, the current tab, an animation value. App (shared) state is used by several parts of the app — the signed-in user, a cart, cached data.
Plain English: ask "would another screen care about this value?" If no, keep it local. If yes, it belongs in a state manager.
InheritedWidget Month 3
The framework's built-in way to pass data down the tree so descendants can read it with .of(context), and to rebuild only the widgets that depend on it. Theme and MediaQuery are InheritedWidgets. Provider and Riverpod build on this idea.
Plain English: the original "share data with everything below me" tool. All the popular state libraries are polished versions of it.
Provider (Riverpod) Month 4
In Riverpod, a provider is a declaration of a piece of state or a service, plus how to create it. Widgets read it with ref.watch (rebuild on change), ref.read (one-off read), or ref.listen (side effects).
Plain English: a named box that knows how to make its own contents, and tells whoever is watching when they change.
AsyncValue Month 4
Riverpod's type representing "loading, or data, or error" as one value, so a screen must handle all three states explicitly.
Plain English: one object that says which of the three situations you are in, so you cannot forget the error case.
Bloc / Cubit Month 5
From the bloc package. A Cubit exposes methods that emit new states. A Bloc receives events and maps them to states with on<Event>. Both expose a stream of states that the UI listens to via BlocBuilder.
Plain English: Cubit = call a method, get a new state. Bloc = send an event, a handler decides the new state. Bloc is more ceremony and a better audit trail.
Repository Month 6
A class that owns access to data for one area of the app, hiding whether the data came from the network, a cache, or a local database. The rest of the app depends on the repository, not on http or the database.
Plain English: one door to your data. Everything else knocks on that door and does not care what is behind it.
Offline-first Month 6
An approach where the local database is the source of truth for the UI, and the network syncs into it in the background. The app works with no connection and never shows a blank screen while loading.
Plain English: show what you already have instantly, then quietly catch up with the server.

Under the hood

Framework / engine / embedder Month 1
Three layers. The framework is Dart code (widgets, rendering, animation). The engine is mostly C++ (rasterising, text layout, Dart runtime). The embedder is the platform-specific shell that hosts it all on iOS, Android, web, or desktop.
Plain English: your Dart sits on a fast drawing engine, which sits inside a small native app that the phone knows how to launch.
Impeller Month 8
Flutter's rendering runtime, which precompiles its shaders to avoid the first-run shader compilation stutter that the older Skia backend suffered from.
Plain English: the newer drawing engine. Its main win is that animations do not stutter the first time you play them.
Isolate Month 3
Dart's unit of concurrency: its own memory and its own event loop, with no shared mutable state. Isolates communicate by passing messages. compute() runs one function in a short-lived isolate.
Plain English: a separate worker with its own memory. Use one for heavy work so the screen keeps drawing at 60 frames per second.
Event loop (microtask & event queue) Month 3
The scheduler inside an isolate. It drains the microtask queue completely, then takes one item from the event queue, and repeats. await schedules the continuation of your function onto this loop.
Plain English: one worker with a to-do list. Nothing runs at the same time as anything else — it just takes very short turns.
JIT / AOT Month 10
In debug builds Dart is compiled just in time, which is what makes hot reload possible. Release builds are compiled ahead of time to native machine code, which is faster and smaller but has no hot reload.
Plain English: debug mode is flexible and slow; release mode is fast and fixed. Never judge performance in debug mode.
Platform channel Month 9
The message-passing bridge between Dart and native platform code. You send a named method call with arguments across a MethodChannel; the native side replies asynchronously. Pigeon generates type-safe channel code for you.
Plain English: a phone line between your Dart code and the iOS or Android code, for things Flutter cannot do alone.
Tree shaking Month 10
The compiler removing code and assets that are provably never used, which shrinks the release build.
Plain English: unused code does not ship. This is why one big widget library does not automatically bloat your app.

Tooling & testing

pubspec.yaml Month 1
The project manifest: name, Dart and Flutter SDK constraints, dependencies, and assets. pubspec.lock records the exact resolved versions and should be committed for applications.
Plain English: the shopping list for your project. Edit it, then run flutter pub get.
flutter doctor Month 1
A command that inspects your machine and reports what is missing for each target platform (SDKs, licences, toolchains, connected devices).
Plain English: the "is my computer ready?" check. Run it whenever something will not build.
DevTools Month 8
Flutter's suite of debugging and performance tools: widget inspector, performance timeline, CPU profiler, memory view, and network view.
Plain English: the instrument panel. Month 8 is mostly learning to read it.
Widget test Month 7
A test that builds a widget tree in a test environment (pumpWidget), interacts with it via finders, and asserts on what is rendered — without a real device.
Plain English: a fake screen in memory. Fast, and enough to catch most UI bugs.
Golden test Month 7
A test that renders a widget to an image and compares it byte-for-byte against a stored reference image ("the golden").
Plain English: a saved screenshot the test compares against. Great for catching visual changes, annoying when fonts shift.
Flavor Month 10
A build variant with its own configuration, app identifier, icon, and backend — commonly dev, staging, and production, installable side by side on one device.
Plain English: the same app built three ways, so testing never touches real customer data.
