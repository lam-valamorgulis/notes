Variables & null safety

var count = 0;        // int, inferred
int total = 0;        // written out
final name = 'Lam';   // set once, at runtime
const pi = 3.14;      // set at compile time
late String token;    // promise: set before use
final means the variable cannot be reassigned. const is stronger: the value must be known before the program runs. In Flutter, const is a performance feature — a const widget is built once and reused, so Flutter can skip rebuilding it. late says "I will set this before anyone reads it". If you lie, you get a runtime error. 
String name = 'Lam';   // can never be null
String? nick;          // may be null

print(nick!.length);   // ! = trust me, not null
print(nick?.length);   // ?. = null if null
print(nick ?? 'none'); // ?? = default value
nick ??= 'none';       // assign only if null
This is sound null safety. A type without ? can never hold null, and the compiler proves it. ! is you overriding the compiler — every ! is a possible crash, so treat each one as a small debt.
Interview line: "null safety moves null errors from runtime to compile time."

Functions & parameters

int add(int a, int b) => a + b;

// named, optional + default
void greet(String who, {String greeting = 'Hi'}) {
  print('$greeting, $who');
}

// named + required
Widget card({required String title, int count = 0}) => ...;

greet('Lam', greeting: 'Hello');
=> is shorthand for a function whose body is one expression. Anything in curly braces in the parameter list is a named parameter — the caller writes its name. This is why Flutter code reads like Text('hi', style: ..., maxLines: 2): almost every widget parameter is named, which keeps a 12-argument constructor readable. 
// function stored in a variable
final onTap = () => print('tapped');

// function taking a function
void run(void Function() action) => action();

// typedef gives a name to a signature
typedef ItemBuilder = Widget Function(int index);
Functions are values in Dart. You pass them around constantly in Flutter: onPressed, onChanged, itemBuilder are all just functions you hand to a widget. Callback simply means "a function you give to someone else so they can call it later".

Classes & constructors

class Habit {
  final String title;
  final bool done;

  const Habit({required this.title, this.done = false});

  // named constructor
  Habit.empty() : title = '', done = false;

  // computed property (getter)
  String get label => done ? '✓ $title' : title;

  // copy with changes — the immutable update
  Habit copyWith({String? title, bool? done}) => Habit(
        title: title ?? this.title,
        done: done ?? this.done,
      );
}
this.title inside the constructor's parameter list assigns the field directly — no boilerplate. A const constructor (only possible when every field is final) lets Dart create the object at compile time. Flutter leans on this heavily. copyWith is the standard Dart way to "change" an immutable object: you do not edit it, you make a new one. You will write this method hundreds of times, and later generate it. 
class Money {
  final int cents;
  const Money(this.cents);

  // value equality, by hand
  @override
  bool operator ==(Object other) =>
      other is Money && other.cents == cents;

  @override
  int get hashCode => cents.hashCode;
}
By default, two Dart objects are equal only if they are the same object. Override == and hashCode together to get value equality (two objects with the same contents count as equal). This matters a lot later: state management rebuilds the UI when state "changes", and without value equality, an identical new object still looks like a change. Packages like equatable or freezed generate this for you.

Inheritance, mixins & interfaces

class Animal { void speak() {} }

class Dog extends Animal {          // inherit
  @override void speak() => print('woof');
}

class Robot implements Animal {     // contract only
  @override void speak() => print('beep');
}

mixin Swimmer { void swim() {} }    // reusable behaviour
class Duck extends Animal with Swimmer {}
extends = inherit the code. implements = promise the same methods, write them yourself. with = mix in behaviour from elsewhere (Dart has single inheritance, so mixins are how code is shared sideways). You meet all three in Flutter: extends StatelessWidget, with SingleTickerProviderStateMixin for animations, and implements for repository interfaces in Month 6.

Collections

final list = <String>['a', 'b'];
final set  = <int>{1, 2, 3};
final map  = <String, int>{'a': 1};

// transform, filter, reduce
final upper = list.map((s) => s.toUpperCase()).toList();
final done  = habits.where((h) => h.done).toList();
final count = habits.where((h) => h.done).length;
final any   = habits.any((h) => h.done);
final first = habits.firstWhere((h) => h.done,
    orElse: () => Habit.empty());
map/where return a lazy Iterable, not a List — call .toList() when you need a real list (for example to hand to a widget's children). In Flutter you use these constantly to turn data into widgets and to compute derived values (like "3 of 5 done") instead of storing them in state. 
final all = [...first, ...second];        // spread
final safe = [...?maybeNull];             // null-aware spread

final children = [
  const Text('always'),
  if (isLoggedIn) const Text('welcome'),  // collection-if
  for (final h in habits) HabitTile(h),   // collection-for
];
collection-if and collection-for are the reason Flutter layouts can stay declarative. You build a list of children with conditions and loops inline, with no temporary variables and no helper functions. Learn these two early — they show up in nearly every real widget tree.

Control flow

if (a > b) { ... } else if (...) { ... } else { ... }

for (final h in habits) { ... }
for (var i = 0; i < 10; i++) { ... }
while (going) { ... }

switch (status) {
  case Status.loading: return const Spinner();
  case Status.error:   return const ErrorView();
  case Status.ready:   return const HabitList();
}
With an enum, Dart checks that your switch covers every case — so adding a new status makes the compiler point at every place you must handle it. That is a feature, not a nuisance. Note there is no break needed in these arms in modern Dart.

Records & patterns (Dart 3)

// record: a lightweight, unnamed group of values
(int, String) pair = (1, 'one');
({int code, String msg}) named = (code: 404, msg: 'nope');
print(named.code);

// return two things without a class
(double lat, double lng) location() => (1.2, 3.4);
final (lat, lng) = location();      // destructure
A record groups a few values without declaring a class. Good for a quick return of two things; bad as your app's domain model (use a class with a name for that). Destructuring means pulling the pieces out into their own variables in one line. 
// pattern matching on shape and type
final message = switch (response) {
  Success(data: final d) => 'got $d',
  Failure(code: 404)     => 'not found',
  Failure(code: final c) => 'error $c',
};

if (json case {'name': final String name}) {
  print(name);                       // safely extracted
}
Patterns let you match a value's shape and pull data out at the same time. This is the modern Dart way to handle "one of several possible results", which is exactly what a network call is. You will use this heavily in Month 3 (result types) and Month 4 (AsyncValue).
Reference: dart.dev/language/patterns

Enums

enum Status { loading, ready, error }

// enhanced enum: fields + methods
enum Plan {
  free(0), pro(9), team(29);

  const Plan(this.price);
  final int price;

  bool get isPaid => price > 0;
}

print(Plan.pro.price);   // 9
An enum is a fixed set of named options. Use one instead of strings for anything with a known list of values — the compiler then catches typos and missing cases for you. Enhanced enums can hold data and behaviour, which removes a lot of switch statements.

Async — Future, Stream, await

Future<String> fetchName() async {
  final res = await http.get(url);   // wait, don't block
  return res.body;
}

// run several at once, wait for all
final results = await Future.wait([fetchA(), fetchB()]);

// a stream = many values over time
Stream<int> ticks() async* {
  for (var i = 0; ; i++) {
    await Future.delayed(const Duration(seconds: 1));
    yield i;                         // push a value out
  }
}

await for (final t in ticks()) print(t);
A Future is one value that arrives later. A Stream is many values arriving over time. await does not block the app — it says "pause this function, let the app keep drawing frames, and resume me when the value lands". async* + yield is how you write a stream by hand.
Interview line: "Dart is single-threaded per isolate; async work is scheduled on the event loop, not run on another thread."

Errors

try {
  await save();
} on SocketException catch (e) {
  // no internet — a specific, expected failure
} on FormatException catch (e, stack) {
  // bad data — keep the stack trace
} catch (e) {
  // anything else
} finally {
  // always runs
}

throw ArgumentError('title must not be empty');
Catch specific types first, general last. Always keep the second parameter (stack) when you plan to log — a crash report without a stack trace is nearly useless. Rule for the year: never write a bare catch (e) {} that does nothing. Silent failures are the hardest bugs to find in a shipped app.

Idioms you will see everywhere

// string interpolation
print('Hi $name, you have ${habits.length} habits');

// cascade: many calls on one object
final paint = Paint()
  ..color = Colors.blue
  ..strokeWidth = 2;

// ternary in a widget tree
Text(done ? 'Done' : 'Todo')

// private to the file: leading underscore
class _HabitTile extends StatelessWidget {}
$name inserts a variable; ${expression} inserts anything longer. The cascade .. means "call this on the same object and keep returning that object" — common in painting and configuration code. A leading underscore makes something private to its file. In Flutter, State classes and small local widgets are private by convention.
Style that senior reviewers notice Follow Effective Dart. The three that matter most day to day: prefer final over var; make fields final and objects immutable by default; and name things fully (selectedHabitIndex, not idx). Run dart format and fix every analyzer warning — Flutter's own lint set is your free code reviewer.
