The 12-Month Plan

One page that holds the whole year. Four phases, twelve monthly modules, one real build each. Tick each skill when you can do it — not when you have read about it.

How to use this: The Map tells the story; this page tracks what to tick off. Each month has a real build (the use case), a short skill list, one interview drill, and a deep dive that only exists because you have 15–20 hours a week. Your ticks are saved in this browser automatically.

Progress: 0 / 0 skills ticked

Pacing at 15–20 hrs/week Roughly: ~3 hrs on the lessons, ~2 hrs reading the official docs, ~10–12 hrs building the month's real project, and ~2 hrs of drills — saying answers out loud and doing timed exercises. This course is build-first on purpose. You learn Flutter's hard parts by hitting them in real code, then say them out loud until an interviewer cannot shake you.
Two goals, one year Half of this plan serves the senior interview (Months 1–9 depth, Month 12 system design). The other half serves freelance and contract work — Month 9 native integration, Month 10 release engineering, and Month 12 estimation. A developer who can ship to both stores alone is worth more than one who can only write widgets.
Versions used in this plan Checked 2026-07-28 against the official sources: Flutter 3.44 stable (released 18 May 2026), Dart SDK 3.12.2, flutter_riverpod ^3.4.1 (Riverpod 3.0), flutter_bloc 9.1.1, go_router 17.3.0. Flutter moves fast — re-check What's new each month.

Phase 1 · Months 1–3 · The Flutter mental model

Learn Dart, learn what a widget really is, learn why layout behaves the way it does, and learn to talk to a real API. By the end you can build a working multi-screen app.

M1Dart + widgets — your first real screen

Objective: understand that a Flutter widget is a description, not a thing on screen; write enough Dart to be dangerous; and make a screen that responds to taps.

Build: a habit-tracker screen — a list you can add to and tick off, with stats derived from state, built out of your own extracted widgets.

Drill: Live-build a counter, then a list with add and toggle. Then answer: "is a widget the thing I see on screen?"

Deep dive (extra hours): read Flutter architectural overview and draw the framework / engine / embedder stack from memory.

Primary: Install, Dart language tour, Understanding constraints. Lessons: 0001, 0002, 0003, 0004, 0005.

M2Layout, scrolling & adaptive UI in depth

Objective: build any screen from a design, at any size, without fighting the framework — including long scrolling screens and phone-versus-tablet differences.

Build: a pixel-accurate product / profile screen from a real design, responsive from a small phone to a tablet, with a custom scrolling app bar.

Drill: "This Column throws an overflow inside a ListView — fix it and explain why." Then: Expanded vs Flexible, out loud.

Deep dive: write a CustomMultiChildLayout or a small custom RenderObject once, just to feel the layout protocol from the inside.

Primary: Layout, Understanding constraints, Slivers, Adaptive & responsive design.

M3Async Dart, networking & real data

Objective: talk to a real API without lying to the user — every screen has loading, empty, error, and success states, and none of them crash.

Build: an API-backed list → detail app (real public API) with pull-to-refresh, search, proper error handling, and JSON parsed into typed Dart models.

Drill: Live-build a search screen that cancels stale requests. Then: "Dart is single-threaded — so how does it do two things at once?"

Deep dive: move a heavy JSON parse into an Isolate with compute() and measure the frame time before and after.

Primary: Async programming, Asynchrony support, Fetch data from the internet, Isolates.

Phase 2 · Months 4–6 · Architecture that scales

Stop writing screens and start writing systems. State management twice over — Riverpod and BLoC — then the architecture that holds a real app together.

M4State management I — Riverpod, deeply

Objective: manage app-wide state without prop-drilling or global mess, and make every piece of it testable.

Build: rebuild the Month 3 app on Riverpod — providers for repositories, AsyncNotifier for screen state, caching, pagination, and unit tests for every provider.

Drill: "Add pull-to-refresh and optimistic delete to this list." Then: "why is ref.watch in an event handler a bug?"

Deep dive: read Riverpod's own source for AsyncValue. Understanding that one type well is a senior-level answer on its own.

Primary: Riverpod docs (Riverpod 3.0 — flutter_riverpod ^3.4.1, riverpod_annotation ^4.0.5, riverpod_generator ^4.0.6).

M5State management II — BLoC, streams & the comparison

Objective: read, write, and critique BLoC code confidently, because most senior Flutter job ads still name it — and be able to argue when it is the right choice.

Build: the same feature again in flutter_bloc — events, states, Cubit vs Bloc, bloc_test — plus a written side-by-side comparison with your Riverpod version.

Drill: Convert a Cubit to a full Bloc live, and say what you gained. Then: "when is BLoC's boilerplate worth paying for?"

Deep dive: write the same feature a third time with plain ValueNotifier + InheritedNotifier, so you can prove no library is magic.

Primary: Bloc library docs (flutter_bloc 9.1.1, bloc ^9.0.0); Using streams.

M6Clean architecture, routing & offline-first

Objective: structure an app that a team could join tomorrow — clear layers, real routing, and data that survives losing the network.

Build: the spine app starts here — a feature-first, layered, offline-first app: go_router navigation with guards and deep links, a repository over a local database, and background sync.

Drill: "The user edits offline on two devices — what happens?" Then: draw your layers on a whiteboard and defend them.

Deep dive: read Flutter's own app architecture guide and compare it honestly to what you built.

Primary: Flutter app architecture, go_router 17.3.0, Persistence cookbook.

Phase 3 · Months 7–9 · Production engineering

The difference between a developer and a senior developer: tests that catch regressions, frames that never drop, and the ability to reach the native platform when Flutter alone cannot.

M7Testing at scale

Objective: change code with confidence. Tests that fail for real reasons, run fast, and run in CI on every push.

Build: a full test suite for the spine app — unit, widget, golden, and integration tests, with mocks, coverage reporting, and a GitHub Actions workflow that blocks a failing pull request.

Drill: Write a failing test for a reported bug, then fix it — live. Then: "your team has 20% coverage and no time. What do you test first?"

Deep dive: add a mutation-testing or flaky-test-detection pass and report what your "green" suite was actually missing.

Primary: Testing Flutter apps, Testing cookbook, mocktail, bloc_test.

M8Rendering internals & performance

Objective: know exactly what happens between setState and a pixel changing — then use that knowledge to kill jank with evidence, not guesses.

Build: take a deliberately janky screen (10,000 items, heavy images, rebuilds everywhere), profile it in DevTools, and fix it — with before/after frame times and app-size numbers written down.

Drill: "Scrolling this list stutters on a cheap Android phone — find out why." Then: "why is const on a widget a performance feature?"

Deep dive: read Inside Flutter and explain how Flutter keeps layout roughly linear-time.

Primary: Inside Flutter, Performance best practices, DevTools, Impeller.

M9Native interop & platform integration

Objective: stop being blocked by "Flutter cannot do that". Reach into iOS and Android yourself, and package what you build so others can use it.

Build: publish your own plugin on pub.dev (platform channels or Pigeon, both platforms) and wire push notifications, permissions, and deep links into the spine app end to end.

Drill: "We need a native SDK that has no Flutter package — how would you approach it?" Then: explain platform channel threading.

Deep dive: embed a native view (PlatformView) and describe honestly what it costs in performance.

Primary: Platform channels, Pigeon, C interop, Developing packages & plugins.

Phase 4 · Months 10–12 · Ship it, polish it, sell it

Everything that turns a working app into a released product — and everything that turns a good developer into someone a company hires as senior, or a client pays as a contractor.

M10Release engineering, CI/CD & going live

Objective: ship to the App Store and Google Play from an automated pipeline, then know within minutes when something breaks in production. This module is the heart of the freelance goal.

Build: take the spine app all the way live — dev/staging/prod flavors, signing, an automated pipeline, store listings, crash reporting, analytics, feature flags, and a staged rollout.

Drill: "Version 2.1 crashes for 3% of users. Walk me through the next 30 minutes." Then: explain your release process to a non-technical client.

Deep dive: add over-the-air-style config and an in-app update prompt; document your whole release runbook as if handing it to a client.

Primary: Deploy to iOS, Deploy to Android, Flavors, Continuous delivery.

M11Advanced UI — animation, custom painting, accessibility & i18n

Objective: build the interface quality that wins contracts, and make it usable by everyone, in every language you sell into.

Build: a polished animated onboarding flow, a custom-painted chart (no chart package), plus a full accessibility and localisation pass on the spine app.

Drill: "Make this transition feel expensive" — then justify every millisecond. Then: name three ways your app fails a blind user.

Deep dive: add a fragment shader or a Rive animation, and measure its cost on a low-end device.

Primary: Animations, CustomPainter, Accessibility, Internationalization.

M12Senior scope — system design, mocks & client work

Objective: perform at senior level in a room. Design a mobile system out loud, review other people's code, and scope and price real work.

Build: a capstone mobile system-design document (offline-first, authenticated, push-enabled, at scale) + four timed mock interviews + a written proposal and estimate for a realistic freelance brief.

Drill: "Design a WhatsApp-style offline-first chat app for 10 million users — mobile side." Then a 45-minute mock, recorded, then watch it back.

Deep dive: answer a real question in r/FlutterDev or the Flutter Discord every week this month. Teaching is the final test of understanding.

Primary: your own 12 builds; Flutter app architecture; Effective Dart; the communities in RESOURCES.md.
