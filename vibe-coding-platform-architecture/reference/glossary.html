Reference

Glossary

The vocabulary of this system. Every lesson uses these words with exactly these meanings — and so should you, out loud, in the interview.

How to use this page Each entry gives the plain-English meaning and the real file where it lives in the repo. If you can point at a file, you sound like someone who has read the code. If you cannot, you sound like someone who has read a blog post about it.

The agent core

Agent loop

The repeating cycle where a model is given tools, picks one, gets the result back, and then decides again. It keeps going until it decides it is finished or it hits a cap. In this repo the loop is not hand-written — it is what streamText does for you.

Lives in: app/api/chat/route.ts

Step

One turn of the agent loop: the model produces output, and if that output is a tool call, the tool runs and its result is fed back. Twenty steps is the hard cap here.

Lives in: stopWhen: stepCountIs(20) in app/api/chat/route.ts

Tool

A function the model is allowed to call, described in words so the model knows when to use it. Three parts: a description (plain text for the model), an inputSchema (a Zod schema the arguments must match), and an execute function (the real code that runs). This app has exactly four.

Lives in: ai/tools/*.ts

Tool description in Markdown

An unusual choice in this repo: each tool's description is a separate .md file, imported as a string rather than typed inline. A build rule turns .md files into raw text so they can be imported like code. The effect is that the words sent to the model are reviewable as prose in a pull request.

Lives in: ai/tools/*.md, enabled by next.config.ts

streamText

The AI SDK function that runs the model and the agent loop, and streams the output as it arrives instead of waiting for the whole answer. Given tools, it handles calling them and feeding results back automatically.

From the ai package (AI SDK v6)

System prompt

The standing instructions given to the model before the user says anything. Here it is a 148-line Markdown file that behaves like configuration: it sets the rules for loop prevention, which Next.js versions are safe, and a deliberate "frontend only unless asked" policy.

Lives in: app/api/chat/prompt.md

The streaming protocol

Data part key idea

A small, typed, named piece of structured state that the server pushes to the browser mid-answer — separate from the chat text. Example: data-run-command carrying { sandboxId, command, status: 'running' }. This is the backbone of the whole user interface. Instead of the UI guessing progress from text, the server states progress as data.

Defined in: ai/messages/data-parts.ts

Writer (UIMessageStreamWriter)

The object handed into every tool that lets the tool push data parts to the browser while it is still working. This is why a tool can report "uploading" and then "uploaded" during a single call, rather than going silent until it returns.

Passed into every tool from app/api/chat/route.ts

Dual return key idea

The pattern where every tool reports the same event twice, to two different audiences: once as a data part for the human's screen, and once as a returned string for the model's next step. The two are written for different readers and say different things. Missing this is the most common way to misread this codebase.

Visible in every file under ai/tools/

toolCallId as identity

Every data part is written with id: toolCallId. That identifier is what lets a later write replace an earlier one in the UI instead of appending a new row — how one command's card goes from "executing" to "running" to "done" in place.

NDJSON

"Newline-delimited JSON" — one complete JSON object per line. Used for the command log stream because a reader can act on each line as it arrives, without waiting for a closing bracket. Note this is a separate channel from the chat stream.

Lives in: app/api/sandboxes/[sandboxId]/cmds/[cmdId]/logs/route.ts

Structured output (Output.object)

Forcing the model to answer in a shape that matches a schema, instead of free text. Used to make the file generator return { files: [{ path, content }] } and to make the error summariser return a decision object.

Partial output stream

Reading a structured answer while it is still being written. The file generator uses this to start uploading finished files before the model has finished writing the later ones. This is what makes the file tree appear to fill up live.

Lives in: ai/tools/generate-files/get-contents.ts

The sandbox

Vercel Sandbox

A throwaway Amazon Linux 2023 virtual machine, created on demand, that the agent writes files into and runs commands in. It is the only thing in the system that touches a real filesystem. It dies on a timer (10 to 45 minutes).

Used via the @vercel/sandbox package

Ephemeral

Short-lived by design. The sandbox is not storage. When it expires, the generated app is gone. This is the single most important fact about the system's design, and the source of most of its trade-offs.

Stateless shell

Each command runs in a fresh shell with no memory of the previous one. You cannot cd into a directory and expect the next command to still be there. The system prompt and the tool description both warn the model about this repeatedly.

Detached command

A command started in the background so the caller is not blocked. Every command here is started detached; the wait argument then decides whether the tool waits for the exit code or returns immediately. This is how a dev server can keep running while the agent moves on.

Lives in: ai/tools/run-command.ts

Port exposure

Ports must be named when the sandbox is created, not later. Get this wrong and there is no way to preview the app without starting over — a genuine design constraint, and a good interview talking point.

The models layer

AI Gateway

One endpoint that fronts many model providers. Because of it, switching from Claude Opus to Grok is a string change, not an integration. The trade-off is a dependency on Vercel sitting in the request path.

Lives in: ai/gateway.ts

Provider options

Per-provider settings that cannot be expressed generically, so they leak through the common interface. Here: OpenAI gets reasoningEffort and serviceTier; Anthropic gets prompt caching and a beta header. Proof that "one interface for all models" is never quite complete.

Lives in: getModelOptions() in ai/gateway.ts

Prompt caching (cacheControl: ephemeral)

Telling the provider to remember the long unchanging part of the prompt so you are not charged full price to resend it every step. Matters here because a 148-line system prompt is resent on all 20 steps.

Reasoning effort

A dial for how much internal thinking the model does before answering. Higher means better decisions, more cost, more delay. Notably the file generator is hard-coded to low — speed chosen over deliberation for the sub-task.

The client

Shared chat instance

One single Chat object created in a React context and shared by every component that needs it. This is what lets the error monitor inject a message into the same conversation the user is typing into.

Lives in: lib/chat-context.tsx

Data-state mapper

The single switch statement that turns every incoming data part into a store update. It is the seam between the streaming protocol and the user interface — one function, one place, easy to find.

Lives in: useDataStateMapper() in app/state.ts

Auto-fix loop

The feature where errors printed by a background command are collected, summarised by a second model, and — if judged worth fixing — sent back into the chat as a new user message so the agent repairs its own work. The most interesting feedback loop in the codebase, and the most heavily guarded against runaway repetition.

Lives in: components/error-monitor/error-monitor.tsx

Remount key (urlUUID)

A fresh random value stored alongside the preview URL and used as the React key. Changing a key forces React to throw the old element away and build a new one — here, a deliberate way to force the preview iframe to reload even when the URL string has not changed.

Lives in: app/state.ts and app/preview.tsx

BotID

An invisible bot check that runs before either AI route does any work. Present because both routes are expensive: one spends model tokens, the other boots a virtual machine.

Lives in: checkBotId() in both API routes, wired by next.config.ts
