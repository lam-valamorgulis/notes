Reference

Next.js in this repo

Every Next.js feature this project actually uses, with the real file that uses it. Nothing here is a tutorial example.

Why this page exists Generic Next.js documentation teaches features in isolation. This page teaches only the features this codebase depends on, in the shape it uses them. If a feature is not on this page, the repo does not use it, and you can safely ignore it for this course.

The two halves: server and client

The single most important rule. Files in the App Router are server by default. The 'use client' marker at the top of a file moves it — and everything it imports — to the browser.

Runs on the serverRuns in the browser
app/layout.tsx app/chat.tsx
app/page.tsx (async) app/preview.tsx
app/actions.ts ('use server') app/state.ts
every app/api/**/route.ts lib/chat-context.tsx
every file under ai/ components/layout/panels.tsx
The rule that catches everyone Secrets are safe only on the server side of that table. The AI Gateway key and the whole ai/ folder never reach the browser. If you moved ai/gateway.ts into a 'use client' file, you would ship your API key to every visitor.

Routing and pages

Root layout — wraps every page

app/layout.tsx 
export const metadata: Metadata = { title, description, openGraph: {...} }

export default function RootLayout({ children }) {
  return (
    <html lang="en"><body>
      <Suspense fallback={null}>      // needed to read URL state
        <NuqsAdapter>                  // settings live in the URL
          <ChatProvider>               // one shared Chat object
            <ErrorMonitor>{children}</ErrorMonitor>
          </ChatProvider>
        </NuqsAdapter>
      </Suspense>
      <Toaster /><CommandLogsStream /><SandboxState />
    </body></html>
  )
}

Note the last three components sit outside children. They render nothing visible; they exist to run background work for the whole app life.

The page is an async Server Component

app/page.tsx 
export default async function Page() {
  const store = await cookies()                          // server-side read
  const banner = store.get('banner-hidden')?.value !== 'true'
  const horizontalSizes = getHorizontal(store)
  const verticalSizes = getVertical(store)
  // ...renders panels already at the user's saved sizes
}
The elegant bit The browser saves panel sizes with document.cookie (components/layout/panels.tsx). The server reads those cookies before rendering. So on reload the panels are already the right size — there is no visible jump. Server and client cooperating through a cookie.

Server Action — a function that runs on the server

app/actions.ts 
'use server'

export async function hideBanner() {
  const store = await cookies()
  store.set('banner-hidden', 'true', { httpOnly: true, ... })
  revalidatePath('/', 'layout')        // re-render with the new cookie
}

It is passed to a client component as a prop (onDismissAction={hideBanner}). The browser calls it like a normal function; Next.js turns that into a network request. One Server Action in the entire repo — worth knowing it is there, and how little it is used.

Route Handlers — the whole back end

A file named route.ts exports functions named after HTTP verbs. Six of them make up the entire API.

PathVerbDoes what
/api/chatPOSTRuns the agent loop, streams the answer
/api/errorsPOSTSummarises log errors into a decision
/api/modelsGETLists allowed models, cached 300s
/api/sandboxes/[sandboxId]GETSandbox status
/api/sandboxes/[sandboxId]/filesGETStreams one file's bytes
/api/sandboxes/[sandboxId]/cmds/[cmdId]/logsGETStreams logs as NDJSON

Dynamic segments: params is a Promise now

A folder named [sandboxId] makes that path piece a variable. In current Next.js you must await it.

app/api/sandboxes/[sandboxId]/files/route.ts 
export async function GET(
  request: NextRequest,
  { params }: { params: Promise<{ sandboxId: string }> }   // a Promise!
) {
  const { sandboxId } = await params
  const fileParams = FileParamsSchema.safeParse({
    path: request.nextUrl.searchParams.get('path'),
    sandboxId,
  })
  if (fileParams.success === false) { /* 400 */ }
}

Every handler validates its input with Zod before touching the sandbox. Never trust the path or the query string.

Streaming a response with ReadableStream

No WebSockets anywhere in this app. Long-lived HTTP responses do all the live updating.

app/api/sandboxes/[sandboxId]/cmds/[cmdId]/logs/route.ts 
return new NextResponse(
  new ReadableStream({
    async pull(controller) {
      for await (const logline of command.logs()) {     // async generator
        controller.enqueue(encoder.encode(JSON.stringify({...}) + '\n'))
      }
      controller.close()
    },
  }),
  { headers: { 'Content-Type': 'application/x-ndjson' } }
)
NDJSON in one line One complete JSON object per line, separated by \n. The reader can act on each line the moment it arrives, instead of waiting for a closing bracket. The matching browser-side reader is in components/commands-logs/commands-logs-stream.tsx.

Build configuration as architecture

The most unusual Next.js usage in the repo. It makes .md files importable as plain strings, so every prompt is reviewable prose instead of a string literal buried in TypeScript.

next.config.ts 
webpack(config) {                       // for production builds
  config.module.rules.push({ test: /\.md/, type: 'asset/source' })
  return config
},
turbopack: {                            // for dev — must match!
  rules: { '*.md': { loaders: ['raw-loader'], as: '*.js' } },
},
images: {
  remotePatterns: [{ hostname: 'vercel.com', pathname: '/api/www/avatar/**' }],
  dangerouslyAllowSVG: true,
  contentSecurityPolicy: "default-src 'self'; script-src 'none'; sandbox;",
}

Two build systems means the rule is written twice — once for Webpack, once for Turbopack. Miss one and it works in development but breaks in production, or the reverse.

TypeScript needs telling too, or the import will not type-check:

markdown.d.ts 
declare module '*.md' {
  const content: string
  export default content
}
Why allow SVG but lock it down? dangerouslyAllowSVG is on because avatars are SVG, and SVG can carry scripts. The matching contentSecurityPolicy with script-src 'none' is what makes it safe. Turning on the dangerous flag and adding the guard is the correct pairing — a good detail to name in an interview.

Settings live in the URL, not in state

An easy feature to miss, and a good one to talk about. Model choice, reasoning effort, and the auto-fix toggle are query parameters, handled by the nuqs library — not React state.

components/settings/use-settings.ts 
export function useModelId() {
  return useQueryState(
    'modelId',
    parseAsStringLiteral(SUPPORTED_MODELS.map((m) => m)).withDefault(DEFAULT_MODEL)
  )
}

What it buys: settings survive a reload, and a URL can be shared with a configuration already applied. What it costs: a `Suspense` boundary in the layout, an extra dependency, and settings become part of your public URL surface.
