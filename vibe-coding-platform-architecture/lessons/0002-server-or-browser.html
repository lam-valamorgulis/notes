Server or browser? The line that splits this app

Lesson 1 drew two columns and never explained how the code knows which column it is in. This is that explanation.

Your win today: point at any file in this repo and say, without hesitating, whether it runs on the server or in the browser — and why. This is the gap that blocks everything else in Next.js.

The default nobody tells you

In the App Router, every file is server code until something says otherwise. Layouts and pages are Server Components by default (Next.js docs). Server code never reaches the browser at all — not the source, not the secrets, nothing.

The one thing that moves code to the browser is a single line at the top of a file:

'use client'

Here is the whole repo, sorted:

app/layout.tsxapp/chat.tsx
app/page.tsx — and it is asyncapp/preview.tsx

all six app/api/**/route.tslib/chat-context.tsx
everything under ai/ 🔑components/layout/panels.tsx

It is a boundary, not a label

This is the part that trips people up. 'use client' does not mark one component. It declares a boundary between two module graphs. The official wording is worth reading twice:

From the Next.js documentation "Once a file is marked with 'use client', all of its imports and the components it directly renders are included in the client bundle. […] It does not apply to Server Components passed as children or other props."

So the marker spreads downward through imports — but it stops at children. That second half is what makes this repo's layout work at all.

The picture

Read the layout with that in mind

app/layout.tsx 
export default function RootLayout({ children }) {
  return (
    <html lang="en"><body>
      <Suspense fallback={null}>
        <NuqsAdapter>                             // client
          <ChatProvider>                          // client
            <ErrorMonitor>{children}</ErrorMonitor> // client, but children stay server
          </ChatProvider>
        </NuqsAdapter>
      </Suspense>
      <Toaster /><CommandLogsStream /><SandboxState />
    </body></html>
  )
}

Three client providers wrap the app, and yet app/page.tsx is still an async Server Component that reads cookies. No contradiction: the page is passed through the providers as children, so it never enters their import graph. This is the standard "interleaving" pattern, and this repo uses it correctly.

Notice the placement The providers wrap {children} — not <html>. The docs recommend rendering providers "as deep as possible in the tree" so more of the app can stay static server output. This repo follows that advice. Small detail, real signal.

The server reads cookies before it renders

Now the payoff. app/page.tsx is async — a Server Component can await things before producing any HTML:

app/page.tsx 
export default async function Page() {
  const store = await cookies()                            // server-only API
  const banner = store.get('banner-hidden')?.value !== 'true'
  const horizontalSizes = getHorizontal(store)             // saved panel sizes
  const verticalSizes = getVertical(store)
  // …renders the panels already at the user's saved sizes
}

And the browser half writes those cookies directly:

components/layout/panels.tsx 
'use client'

const onLayout = (sizes: number[]) => {
  document.cookie = `${HORIZONTAL_COOKIE}=${JSON.stringify(sizes)}`
}
Say it like this

"Panel sizes are stored in a cookie by the client and read by the server before the first render. So on reload the panels come back already sized — there is no layout jump. Server and client cooperating through a cookie, with no database involved."

That is a small feature, but it is the clearest example in the repo of why the server/client split is useful rather than just a rule to obey.

One Server Action, and only one

'use server' is the mirror image of 'use client': a function that always runs on the server, callable from the browser as if it were local.

app/actions.ts 
'use server'

export async function hideBanner() {
  const store = await cookies()
  store.set('banner-hidden', 'true', { httpOnly: true, ... })
  revalidatePath('/', 'layout')          // re-render with the new cookie
}

It is handed to a client component as a prop — onDismissAction={hideBanner} in page.tsx. Next.js turns that call into a network request for you.

Worth saying out loud in an interview There is exactly one Server Action in this entire repo, and it dismisses a welcome banner. Everything else uses Route Handlers. That is a deliberate shape: Server Actions suit small state changes, but this product needs streaming responses, and Route Handlers are the tool for that. Knowing when not to reach for the newer feature is the senior signal.

Why the boundary is a security boundary

.env.example in this repo has exactly one line:

AI_GATEWAY_API_KEY=

That key is read in ai/gateway.ts, which lives on the server side of the line. Two mechanisms keep it there:

  1. Nothing under ai/ is imported by any 'use client' file, so it never enters the client bundle.
  2. Next.js only exposes environment variables prefixed with NEXT_PUBLIC_. Anything else is replaced with an empty string in browser code.
The mistake this prevents Add 'use client' to the top of a file that imports ai/gateway.ts and you have just published your API key to every visitor. The second mechanism blunts the damage — the variable becomes an empty string — but the correct habit is to keep the import graph clean. For hard enforcement, the docs recommend the server-only package, which turns the mistake into a build error. This repo does not use it. That is a fair "what would you add?" answer.

Remember this
  • App Router files are server by default. 'use client' is what moves them.
  • 'use client' marks a module-graph boundary, and it spreads down through imports.
  • It does not spread to children — which is why a server page can sit inside client providers.
  • app/page.tsx is async and reads cookies before rendering; the client writes them with document.cookie. No layout jump.
  • Only NEXT_PUBLIC_ variables reach the browser; everything else becomes an empty string.
  • There is exactly one Server Action in the repo. Streaming work uses Route Handlers instead.
  • Providers wrap {children}, not <html> — deliberately as deep as possible.

If you remember one thing: 'use client' is a boundary that travels through imports but stops at children.
