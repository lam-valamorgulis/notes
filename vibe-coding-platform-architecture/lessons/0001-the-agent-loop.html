Chapter 1 · Lesson 1

The agent loop in one picture

Before any detail makes sense, you need the shape of the whole thing. This is the shape.

Your win today: draw this system on a whiteboard from memory in under three minutes, naming the real files. That single skill carries the first ten minutes of an architecture interview.

The whole system in one sentence

It is a chat endpoint that hands a language model four tools, and the only thing in the system that touches a real filesystem is a throwaway virtual machine.

That is genuinely it. Everything else — the file tree, the live preview, the log panel, the self-repairing errors — is built on top of those two facts. Hold them and the rest of the course is detail.

Why this framing matters Most people describe this app as "an AI that writes code". That description explains nothing and predicts nothing. Describing it as a tool-calling loop plus an ephemeral VM lets you correctly guess where the hard problems are: keeping the user informed while the loop runs, and coping with a machine that dies on a timer.

The four tools

The agent's entire vocabulary. Four functions, defined in ai/tools/. It cannot do anything else.

ToolWhat it doesFile
createSandbox Boots the virtual machine. Ports must be named now or never. create-sandbox.ts
generateFiles Writes the application's code into the machine. generate-files.ts
runCommand Runs one shell command. No memory between commands. run-command.ts
getSandboxUrl Returns the public URL for a port, for the preview pane. get-sandbox-url.ts

Notice what is missing: there is no "read file" tool, no "edit file" tool, no "list directory" tool. The agent writes whole files and runs commands. That absence is a design decision, and we will come back to what it costs in Chapter 3.

The picture

Walk it once, out loud

Read these seven steps aloud while tracing the diagram with a finger. Saying it is the practice; reading it is not.

  1. You type a prompt. app/chat.tsx posts it to /api/chat, along with your chosen model and reasoning effort.
  2. The route runs an invisible bot check and rejects unknown model ids. Both happen before any money is spent.
  3. streamText starts the agent loop with the system prompt and the four tools attached.
  4. The model picks a tool. The tool runs real work against the sandbox.
  5. While it works, the tool pushes data parts — small typed status objects — to the browser through the writer.
  6. The tool also returns a string. That string goes back into the loop as the model's next input. Step 4 repeats, up to twenty times.
  7. In the browser, one switch statement in app/state.ts turns each data part into a store update, and the panels re-render.

The idea most people miss

Look again at steps 5 and 6. Every tool reports the same event twice, to two different audiences:

ChannelAudienceShapePurpose
writer.write(...) The human Typed object Drive the user interface
return "..." The model Prose string Decide the next step

You can see both in a single tool. This is create-sandbox.ts, trimmed:

ai/tools/create-sandbox.ts 
const sandbox = await Sandbox.create({ timeout, ports })

writer.write({                          // → for the screen
  id: toolCallId,
  type: 'data-create-sandbox',
  data: { sandboxId: sandbox.sandboxId, status: 'done' },
})

return (                                // → for the model
  `Sandbox created with ID: ${sandbox.sandboxId}.` +
  `\nYou can now upload files, run commands, ...`
)

The object is for your eyes. The sentence is for the model's next decision. They carry the same news in two languages. We named this the dual return — it is the organising idea of the entire codebase, and Lesson 2 is devoted to it.

Common misreading People assume the UI is built by parsing the model's chat text — watching for "I created a sandbox" and reacting. It is not. The UI never reads the model's prose. It reads typed data parts written by the tool code. That separation is why the panels stay correct even when the model's wording changes or it switches provider.

Why exactly twenty steps?

One line caps the whole loop:

app/api/chat/route.ts 
stopWhen: stepCountIs(20),

A realistic successful run needs roughly six to eight steps: create sandbox, generate files, install, start server, get URL, report. Twenty leaves room for a few rounds of error fixing, then gives up.

This is the answer to the standard interview question "how do you stop an agent running forever?" The honest full answer has three layers, and only the first is code:

  1. A hard step cap — stepCountIs(20). Mechanical, cannot be argued with.
  2. A sandbox timer — the VM dies after 10 to 45 minutes regardless.
  3. Prompt instructions — the system prompt spends its opening section on "CRITICAL RULES TO PREVENT LOOPS", telling the model not to regenerate files it has already written.
Say it like this

"Three layers: a hard step cap in code, a wall-clock timeout on the sandbox, and prompt-level rules. The first two are guarantees; the third is a hope. I would not rely on the prompt alone."

That last sentence is the part that sounds senior. Noticing that prompt instructions are not a guarantee is exactly the judgement an interviewer is listening for.

Remember this
  • The system is a tool-calling loop plus a throwaway VM. Everything else is detail.
  • The agent has exactly four tools: create sandbox, generate files, run command, get URL.
  • There is no read-file or edit-file tool — it writes whole files and runs commands.
  • Every tool reports twice: a typed data part for the screen, a string for the model.
  • The UI never parses the model's prose. It reacts to typed data parts only.
  • The loop is capped by stepCountIs(20); the sandbox also dies on a timer.
  • Command logs travel on a separate NDJSON stream, not through the agent.

If you remember one thing: the tool talks to the human and the model at the same time, in two different languages.
