Six endpoints and one very long response

Lesson 1 said the logs "stream". This is what that actually means — and it is not a WebSocket.

Your win today: explain how a log panel updates live over plain HTTP, and why the browser needs a leftover buffer to read it. That buffer is the detail most engineers get wrong.

A file named route.ts is an endpoint

No router file, no app.get(...). In the App Router you create a folder, put a route.ts inside it, and export a function named after the HTTP verb. The folder path is the URL.

This entire product has six of them. That is the whole back end.

URLVerbReturnsValidates input?
/api/chatPOST Chat streamYes — model id checked against a list
/api/errorsPOST JSON decisionYes — linesSchema.safeParse
/api/modelsGET JSON, cached 300sNo input to validate
/api/sandboxes/[sandboxId]GET JSON statusNo
…/[sandboxId]/files?path=GET Raw bytesYes — FileParamsSchema.safeParse
…/cmds/[cmdId]/logsGET NDJSON streamNo
An honest inconsistency Look down that last column. The files route carefully validates with Zod before touching the sandbox. The logs and status routes take the path parameter and pass it straight into Sandbox.get(). Reading the code, my read is that this is drift, not a decision — the routes were written at different times. It is a good, specific answer to "what would you tighten up?"

Dynamic segments, and the change that catches everyone

A folder named [sandboxId] makes that piece of the path a variable. The thing to know: params is a Promise now. You must await it.

app/api/sandboxes/[sandboxId]/files/route.ts 
export async function GET(
  request: NextRequest,
  { params }: { params: Promise<{ sandboxId: string }> }   // ← a Promise
) {
  const { sandboxId } = await params
  const fileParams = FileParamsSchema.safeParse({
    path: request.nextUrl.searchParams.get('path'),   // query string
    sandboxId,                                        // path segment
  })
  if (fileParams.success === false) {
    return NextResponse.json({ error: 'Invalid parameters…' }, { status: 400 })
  }
  // …only now touch the sandbox
}

Two different sources of user input — the path and the query string — are validated together in one schema. That is the pattern worth copying.

Three shapes of response

Every endpoint here is one of three shapes. Knowing which shape you need is most of the design work.

ShapeBuilt withUsed for
Whole JSON, at once NextResponse.json(...) Model list, sandbox status, error decision
Raw bytes, streamed ReadableStream, no content type set Reading one file out of the sandbox
Many small objects, streamed ReadableStream + application/x-ndjson Live command logs

Streaming, on the server side

Here is the whole log endpoint. It is shorter than you would expect.

app/api/sandboxes/[sandboxId]/cmds/[cmdId]/logs/route.ts 
return new NextResponse(
  new ReadableStream({
    async pull(controller) {
      for await (const logline of command.logs()) {      // async generator
        controller.enqueue(
          encoder.encode(JSON.stringify({
            data: logline.data,
            stream: logline.stream,       // 'stdout' or 'stderr'
            timestamp: Date.now(),
          }) + '\n')                      // ← the newline is the protocol
        )
      }
      controller.close()
    },
  }),
  { headers: { 'Content-Type': 'application/x-ndjson' } }
)

Two things to notice.

for await ... of means command.logs() is an async generator — a source that produces values over time, which you can loop over as if it were a normal list. You will meet this again in the file generator.

That + '\n' is the entire protocol. One JSON object, then a newline. This is called NDJSON, and it exists so a reader can act on each object the moment it arrives instead of waiting for a closing bracket at the end.

Streaming, on the browser side — the hard part

Now the detail that trips up experienced engineers. The network does not hand you neat lines. It hands you arbitrary blocks of bytes, and a block can end in the middle of a JSON object.

And here is the repo doing exactly that:

components/commands-logs/commands-logs-stream.tsx 
const reader = response.body!.getReader()
const decoder = new TextDecoder()
let line = ''                                   // the leftover buffer
while (true) {
  const { done, value } = await reader.read()
  if (done) break

  line += decoder.decode(value, { stream: true })
  const lines = line.split('\n')
  for (let i = 0; i < lines.length - 1; i++) {  // note: length - 1
    if (lines[i]) {
      const parsed = logSchema.parse(JSON.parse(lines[i]))
      yield { data: stripAnsi(parsed.data), ... }
    }
  }
  line = lines[lines.length - 1]                // keep the tail
}

Three details, each doing real work:

  • length - 1 — never parse the final piece. Without a trailing newline it might be half an object.
  • { stream: true } — tells the decoder a multi-byte character may be split across chunks too, so it should wait rather than produce a broken character.
  • stripAnsi(...) — terminal output contains colour codes. They would render as garbage, so they are removed.
Say it like this

"Chunk boundaries and record boundaries are independent. So the reader accumulates into a buffer, splits on the newline, processes everything except the last piece, and carries that last piece forward. Getting this wrong gives you parse errors that only appear under load, which makes them horrible to debug."

Why not a WebSocket?

Streaming over plain HTTP instead of WebSockets
What it buys

No socket server to run, no connection state to manage, and it works on ordinary serverless functions. Every proxy and firewall already understands it. The data flows one way — server to browser — so a two-way channel would be unused capability.

What it costs

The browser cannot send anything back on the same connection. Reconnecting after a drop is your problem — and this repo does not attempt it. If the log stream breaks, the panel just stops updating silently.

What I would consider

Server-Sent Events would give automatic reconnection almost free, at the cost of a slightly stricter message format. For logs, that trade looks favourable. Worth saying — it shows you weighed it rather than accepted it.

Bonus: a hack the authors admitted to

The status endpoint has no real status call available, so it runs a pointless command and watches for a specific failure:

app/api/sandboxes/[sandboxId]/route.tsx 
/**
 * We must change the SDK to add data to the instance and then
 * use it to retrieve the status of the Sandbox.
 */
const sandbox = await Sandbox.get({ sandboxId })
await sandbox.runCommand({ cmd: 'echo', args: ['Sandbox status check'] })
return NextResponse.json({ status: 'running' })
// …catch: if error.json.error.code === 'sandbox_stopped' → { status: 'stopped' }

"Is it alive?" is answered by "try to talk to it and see if that fails." The comment is the maintainers' own note that the SDK should expose this properly.

Why this is gold in an interview A trade-off the authors already acknowledged in a code comment is far safer to raise than one you invented. You are agreeing with the maintainers, not second-guessing them. Quote the comment and say what you would do instead.

Remember this
  • A folder plus route.ts is an endpoint. The folder path is the URL. There are six.
  • params is a Promise — always await it.
  • Three response shapes: whole JSON, raw byte stream, NDJSON stream.
  • NDJSON = one JSON object per line. The \n is the whole protocol.
  • Chunk boundaries ≠ record boundaries. Keep a leftover buffer and never parse the last piece.
  • No WebSockets anywhere. Live updates are long-lived HTTP responses, one way only.
  • Only the files route validates its path input with Zod. Logs and status do not.

If you remember one thing: the network gives you bytes, not lines — the buffer is what turns bytes into records.

Curious what breaks without the buffer? Ask your teacher to walk you through a failing case byte by byte. It is the fastest way to make this permanent.
