Lesson 5 · Domain 3 · 20% of the exam

Claude Code Configuration & Workflows

This is likely your strongest area — you live in Claude Code every day. The goal here is not to learn new habits, but to turn "I just know how to do it" into exact, named answers the exam rewards: the right file, the right flag, the right scope.

Your win: for any config or workflow question, name the exact file and location (project vs user), the exact mechanism (@import, glob paths, context: fork, -p), and say why the other three options are worse — in one breath.

Domain 3 has 6 task statements. Most questions are scenario-based: they hand you a situation and ask for the best choice. The wrong options are usually real things that almost work — your job is to spot why they fall short.

1. The CLAUDE.md hierarchy — who sees what

Claude Code loads memory from several places at once. The exam tests whether you know which scope reaches which people.

LevelFileApplies toShared with team?
User~/.claude/CLAUDE.mdYou, in every project on your machineNo — never committed
Project.claude/CLAUDE.md or root CLAUDE.mdEveryone who works in this repoYes — via version control
DirectoryCLAUDE.md inside a subfolderAnyone editing files in that folderYes — if the folder is committed

~/.claude/CLAUDE.md is user-level: it holds your personal preferences. It is not shared with teammates through Git. .claude/CLAUDE.md (or a plain CLAUDE.md in the repo root) is project-level: it is committed, so every teammate who clones the repo gets it.

Classic diagnosis trap A new teammate is not receiving a coding standard you rely on. You put it in ~/.claude/CLAUDE.md. That is user-level — it lives only on your machine and is never committed. The fix is to move it to the project-level .claude/CLAUDE.md (or root CLAUDE.md) so it ships with the repo. "It works for me" is the tell that a rule is stuck in user scope.
Do this to verify Run /memory to see exactly which memory files are currently loaded and from where. When a question is about "why isn't this instruction taking effect", /memory is the diagnostic tool that confirms whether the file is even being read.

The same scope question, asked of settings

CLAUDE.md carries instructions. settings.json carries configuration — permissions, environment variables, hooks. It answers the same "who gets this" question, and it has three answers rather than two:

SourceFileReachesCommitted?
user~/.claude/settings.jsonYou, in every projectNo
project.claude/settings.jsonEveryone in this repoYes
local.claude/settings.local.jsonYou, in this repo onlyNo — git-ignored

The one that earns its keep is local: it is how you keep a personal permission or an experiment out of a file your teammates share, without giving up on having it. So the three-way split answers two questions at once — is this for me or the team, and is it for this project or all of them. Same shape as the three MCP scopes in Lesson 3, which is not a coincidence: it is Claude Code's standard answer to configuration scope, and recognising the pattern once saves you learning it three times.

2. Keep CLAUDE.md modular — @import and .claude/rules/

A giant single CLAUDE.md becomes hard to maintain. Two mechanisms keep it clean:

  • @import syntax — references an external file from inside CLAUDE.md, so you can split standards into focused files and import just the ones each package needs.
  • .claude/rules/ directory — holds topic-specific rule files as an alternative to one monolithic CLAUDE.md. Each file covers one subject (testing, security, style).

A modular project-level CLAUDE.md using @import:

# Project standards

@import ./.claude/rules/testing.md
@import ./.claude/rules/api-conventions.md
@import ./packages/payments/CLAUDE.md
Remember the split CLAUDE.md = always-loaded universal standards (rules that apply to the whole project, every session). Skills = on-demand, task-specific workflows (loaded only when invoked). Do not put a one-off workflow in CLAUDE.md, and do not put a universal standard in a skill.

3. Path-specific rules — conventions that follow the file

Files inside .claude/rules/ can carry YAML frontmatter with a paths field. paths takes glob patterns. The rule then loads only when Claude edits a file matching that glob. This saves context tokens: irrelevant rules stay out of the way until they are needed.

A path-scoped rule file — .claude/rules/react-tests.md:

---
paths: ["**/*.test.tsx"]
---

# React test conventions
- Use React Testing Library, never enzyme.
- One `describe` block per component.
- Name tests "renders / behaves" style.

The power of a glob is that it spans directories. Test files like Button.test.tsx sit next to their components all over the codebase. A single paths: ["**/*.test.tsx"] rule catches every one of them, wherever they live.

Why a per-directory CLAUDE.md is the wrong pick here A directory-level CLAUDE.md only applies inside one folder. Test files are scattered across many folders, so you would have to copy the rule into dozens of directories — brittle and easy to miss. A glob paths rule in .claude/rules/ is the correct tool for conventions that span the tree. Putting everything in the root CLAUDE.md and "hoping Claude infers when it applies" is also wrong — it wastes context on every file and relies on guessing.

Other real examples: paths: ["terraform/**/*"] for infrastructure files, paths: ["**/*.test.tsx"] for tests.

4. Slash commands and skills — scope decides sharing

Both custom slash commands and skills exist at two scopes, and the scope decides who gets them.

ThingProject scope (shared)User scope (personal)
Slash command.claude/commands/~/.claude/commands/
Skill.claude/skills/~/.claude/skills/

If a command or skill must reach every developer on clone or pull, it goes in the project directory (.claude/commands/ or .claude/skills/) and is committed. If it is just for you, it goes under ~/.claude/.

The /review command scenario A team wants a /review command available to everyone on clone. Correct: put it in .claude/commands/ in the repo. Wrong options and why: ~/.claude/commands/ is personal, so teammates never get it; putting the instructions in CLAUDE.md gives context, not a runnable command definition; and there is no .claude/config.json "commands" array — that file/field does not exist. Watch for made-up config fields — they are a favorite wrong answer.

Skill frontmatter you must recognize

A skill lives in a SKILL.md file with YAML frontmatter. Three fields show up on the exam:

  • context: fork — runs the skill in an isolated sub-agent context. The skill's output does not pollute the main conversation. Use it for verbose work (big codebase analysis) or exploratory work (brainstorming) where you only want the summary back.
  • allowed-tools — restricts which tools the skill may use while it runs. Limit it (e.g. to file writes only) to prevent destructive actions.
  • argument-hint — prompts the developer for the parameters the skill needs when they invoke it without arguments.
---
name: analyze-codebase
description: Deep structural analysis of the repo
context: fork                    # run in an isolated subagent
agent: Explore                   # which agent type to fork as
allowed-tools: Read, Grep, Glob  # comma-separated list, not a YAML array
argument-hint: "<path or module to analyze>"
---

Analyze the target and return only a summary...

Note the format of allowed-tools: the documented form is a comma-separated list (Read, Grep, Glob), not a bracketed YAML array. A small thing, but this domain is full of questions decided by exact syntax.

The frontmatter field pair most people miss — who is allowed to invoke it

The three fields above control how the skill runs. Two more control something different and just as testable: who may start it at all. By default both you and Claude can invoke a skill. Each field switches off one side:

FrontmatterYou can invoke itClaude can invoke itWhy you would want that
(neither field set)YesYesThe default — an ordinary skill
disable-model-invocation: trueYesNoThe skill has a real-world side effect — deploys, sends an email, moves money. A human must be the one to pull the trigger
user-invocable: falseNoYesThe skill is background knowledge Claude should reach for on its own. There is nothing for a human to "run"

This is Lesson 1's enforcement lesson showing up in configuration. "Do not deploy unless the human asks" written in a prompt is a request. disable-model-invocation: true is a guarantee — the model has no way to start that skill, however the conversation goes. When a scenario says "the agent must never trigger X on its own", it is asking for this field, not for firmer wording.

Say it like this

"context: fork runs the skill in an isolated sub-agent, so its verbose output never clutters my main conversation — perfect for codebase analysis or brainstorming. allowed-tools locks down what the skill can touch so it can't do damage, and argument-hint tells the developer what input to pass."

Personal customization without breaking the team Want your own tweak of a shared skill? Create a personal variant in ~/.claude/skills/ with a different name. It stays on your machine and does not affect teammates' shared skill.

5. Plan mode vs direct execution

Two ways to run a task, and the exam wants you to match the mode to the complexity.

Plan modeDirect execution
Use forComplex tasks: large-scale changes, several valid approaches, architectural decisions, many filesSimple, well-scoped changes
What it givesSafe exploration and design before touching code — prevents costly reworkSpeed — no planning overhead when the fix is obvious
ExampleRestructure a monolith into microservices; decide service boundaries firstAdd one validation check to a function; fix a single-file bug with a clear stack trace

You can also combine them: use plan mode to investigate and design, then direct execution to implement the agreed plan.

The Explore subagent helps here too: it isolates the noisy discovery output (reading many files) and returns a clean summary, so your main conversation context is preserved.

The microservices scenario You must split a monolith into microservices — dozens of files, real service-boundary decisions. Correct: enter plan mode to explore dependencies and design before changing anything. Wrong: "start direct and let the boundaries emerge" risks expensive rework; "direct execution with comprehensive upfront instructions" assumes you already know the final structure (you don't); "start direct, switch to plan if it gets complex" fails because the complexity is already stated — it is not emergent, so you plan from the start.

6. Iterative refinement techniques

When plain prose gets interpreted inconsistently, these techniques get better results:

  • Concrete input/output examples — the most effective way to communicate an expected transformation. Give 2–3 examples of input and the exact output you want.
  • Test-driven iteration — write the test suite first, then iterate by sharing the test failures with Claude.
  • The "interview pattern" — in an unfamiliar domain, ask Claude to ask you questions first. This surfaces considerations (cache invalidation, failure modes) before any code is written.
  • Batch vs sequential feedback — when problems interact, give all of them in a single message so Claude sees the whole picture. When problems are independent, fix them one at a time.
Quick rule Prose unclear → give examples. New domain → interview first. Multiple related bugs → one message. Multiple unrelated bugs → sequential.

7. Claude Code in CI/CD pipelines

Running Claude Code inside automation (a build or PR pipeline) needs non-interactive mode.

  • -p (or --print) — runs Claude Code non-interactively: it processes the prompt, writes the result to stdout, and exits without waiting for input. This is the fix for a pipeline that hangs waiting for interactive input.
  • --output-format — text (the default), json for a single result object, or stream-json for results as they arrive. It only takes effect together with -p, which is the detail worth remembering: --output-format json on its own does nothing, because an interactive session has no single result to serialise.
  • --json-schema — a JSON Schema used to validate the structured output, so a CI job can rely on the shape it parses. The documented form takes the schema itself, inline.
  • CLAUDE.md in CI — still loaded, so it gives the CI-invoked run its project context: testing standards, fixture conventions, review criteria.

A CI command that produces parseable review output:

claude -p "Review this PR diff for security issues" \
  --output-format json \
  --json-schema '{"type":"object",
                  "properties":{"findings":{"type":"array"}},
                  "required":["findings"]}'
Two more flags a production pipeline wants — and why --max-budget-usd <amount> puts a hard ceiling on what one run may spend on API calls (again, -p only). In CI this matters more than anywhere else, because nobody is watching: a prompt that sends the agent in circles on a pull request that runs on every push is exactly how a surprise bill happens. --permission-mode <mode> sets the permission stance for the session. A pipeline has no human to approve anything, so leaving the stance unstated is how you get either a hang or a job that quietly cannot do its work. Same idea as -p, one level up: state explicitly what a pipeline cannot ask a human for.

A note on how this domain is examined: notice that every wrong answer in the trap below is an invented flag. That is the single most common wrong-answer pattern in Domain 3, and it cuts both ways — a plausible-sounding flag you cannot place in the real reference is almost certainly the distractor, and if all four options look plausible, the real one is usually the plainest.

The hanging pipeline scenario A CI job runs claude "Analyze this PR for security" and hangs forever. Correct: add the -p flag so it runs non-interactively and exits. Wrong: a CLAUDE_HEADLESS env var (does not exist), a --batch flag (does not exist), and redirecting stdin from /dev/null (a Unix hack that hides the symptom instead of using the proper flag). Invented flags and env vars are the trap — -p/--print is the real answer.
Say it like this

"A CI run needs -p so Claude Code is non-interactive — it reads the prompt, prints to stdout, and exits instead of waiting. I add --output-format json (with a --json-schema) so the findings are machine-parseable for automated PR comments, and CLAUDE.md still supplies the project's review criteria."

Session context isolation for review

One senior-level point: the same session that generated code is less effective at reviewing its own changes than an independent review instance — it shares the same blind spots. When you re-run a review after new commits, include the prior review findings in context and tell Claude to report only new or still-unaddressed issues, so it does not repeat comments. Likewise, give it the existing test files so generated tests avoid duplicating scenarios.
