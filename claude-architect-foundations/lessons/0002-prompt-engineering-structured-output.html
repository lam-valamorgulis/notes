Prompt Engineering & Structured Output

The exam does not ask you to write prompts — it asks you to pick the technique that fixes a broken production system.

Your win: given a scenario — too many false positives, messy output, invented data, slow batch jobs, contradictory reviews — pick the one technique that actually fixes it, and say why the tempting alternative does not.

Domain 4 is a scenario-judgment domain. Every question hands you a failing system and four plausible fixes. Only one is best. Your job is to know the sharp edges of each tool: what it fixes, and what it does not.

1. Explicit criteria beat vague instructions

The most common review-bot problem: it flags too many things that are not real problems. These are false positives — the model reports an issue that is not actually an issue. When a bot cries wolf too often, developers stop trusting even its correct findings.

The wrong instinct is to add soft guidance like "be conservative" or "only report high-confidence findings." These vague words do not improve precision. The model has no shared definition of "conservative." Precision comes from explicit, categorical criteria that name exactly what to REPORT and what to SKIP.

Vague (does not help)Explicit criteria (fixes it)
"Check that comments are accurate.""Flag a comment ONLY when the claimed behavior contradicts the actual code behavior."
"Be conservative.""REPORT: bugs, security issues. SKIP: minor style, local project patterns."
"Only high-confidence findings.""Severity HIGH = data loss or auth bypass (example: ...). Severity LOW = naming. Report HIGH and MEDIUM only."
Do this Write specific review criteria that split issues into REPORT vs SKIP. Define each severity level with a concrete code example. If one whole category (say, "comment accuracy") is noisy, temporarily disable that category while you improve its prompt — one bad category poisons trust in the good ones.
Tempting but WRONG "Add 'be conservative, only report high-confidence issues' to the system prompt." This feels like a precision knob. It is not. General hedging words do not change what the model considers an issue. Precision needs categorical rules, not mood words.

2. Few-shot prompting for consistency

Few-shot means putting 2–4 worked examples right in the prompt, each showing an input and the exact output you want. It is the most effective technique when detailed written instructions still give inconsistent or badly-formatted results.

Why examples beat more instructions:

  • They show the exact output shape you want (for a code review: location, issue, severity, suggested fix) instead of describing it.
  • Good examples show the reasoning — why one action was chosen over a plausible alternative. This teaches judgment, not just format.
  • They help the model generalize to new, unseen patterns — not just copy the exact cases you listed.
  • They reduce hallucination in extraction tasks (informal measurements, documents with varied structure, inline citations vs a bibliography).
Pick the count on purpose Use 2–4 targeted examples aimed at the ambiguous cases — the ones where the model keeps guessing wrong. One example is too thin to show a pattern; a dozen wastes context. Choose examples that cover the confusing boundary, not the easy happy path.
Tempting but WRONG "Output is inconsistent, so let me write three more paragraphs of formatting rules." More prose is the weaker fix. When instructions alone keep failing, show the model 2–4 examples instead of telling it again in more words.

3. Structured output with tool_use and JSON schemas

When you need machine-readable output, do not ask the model to "return JSON" in plain text and hope. Define a tool with a JSON schema and let the model call it. tool_use with a schema is the most reliable path to schema-compliant output — it eliminates JSON syntax errors (missing commas, unquoted keys, broken brackets).

{
  "name": "extract_metadata",
  "description": "Extract invoice metadata from the document.",
  "input_schema": {
    "type": "object",
    "properties": {
      "invoice_number": { "type": "string" },
      "vendor_name":    { "type": "string" },
      "tax_id":         { "type": ["string", "null"] },
      "category": {
        "type": "string",
        "enum": ["services", "goods", "other"]
      },
      "category_detail": { "type": "string" }
    },
    "required": ["invoice_number", "vendor_name", "category"]
  }
}

tool_choice — who decides whether a tool runs

tool_choiceMeaningUse when
"auto"Model MAY call a tool, or may just reply with text.Tool is optional; a plain answer is sometimes fine.
"any"Model MUST call some tool, but it picks which one.Several extraction schemas exist and the document type is unknown.
{"type":"tool","name":"extract_metadata"}Model MUST call that one specific tool.You need a known step to run — e.g. metadata extraction before any enrichment step.
"none"Model CANNOT call any tool this turn, even though the tools are still defined.You want a plain-language turn — a summary, a question back to the user — without removing the tools from the request. Removing tools instead would change the request prefix and throw away your prompt cache (Lesson 4).

Read the four as two separate switches: must a tool run? (none = never, auto = model's choice, any and tool = yes) and who picks which one? (tool = you, everything else = the model). A question that says "the model keeps answering in prose when it should call the tool" is asking for any. A question that says "it calls the wrong tool first" is asking for tool.

One more knob on the same field Any tool_choice value can also carry disable_parallel_tool_use: true, which limits Claude to at most one tool call per response. By default Claude may ask for several tools in a single reply. Turn it off when the tools are not safe to run at the same time — two writes to the same record, or a step whose input depends on another step's output. Note the difference from tool_choice itself: that field controls whether and which, this one controls how many at once.
Ordering dependency — force the SPECIFIC tool on the FIRST turn, then release to "auto" When one tool must run before others (e.g. extract_metadata produces the DOI that lookup_citations needs) and the model sometimes calls them out of order, you need a hard ordering guarantee. Two knobs matter: which tool and when. "any" only sets when (a tool runs this turn) — the model still picks which, so it can call the wrong one first; and a system-prompt "prioritize X" is a suggestion the model already ignores under "auto". Tool ordering in the array is not a documented preference — do not rely on it. The only deterministic fix is {"type":"tool","name":"X"} on the first turn (forces that exact tool), then hand control back to "auto" so the enrichment tools can run with the first tool's output in context. Do not pin the specific tool on every call — that starves the other tools forever (right mechanism, wrong scope).

Add strict: true to guarantee the output matches the schema exactly (right field names, right types, required fields present). Two details that decide whether it actually works:

  • It goes on the tool, not on tool_choice. strict is a top-level field on the tool definition, sitting beside name, description, and input_schema. Putting it inside tool_choice is a common wrong guess — that field is about which tool runs, not about how its input is validated.
  • The schema must be closed. A strict tool's schema needs "additionalProperties": false and a required list. Without them there is nothing to be strict about — an open schema permits any extra field, so "matches the schema" would still allow surprises.
{
  "name": "extract_metadata",
  "strict": true,                       // top-level, next to name — NOT in tool_choice
  "input_schema": {
    "type": "object",
    "properties": { "invoice_number": { "type": "string" } },
    "required": ["invoice_number"],     // required list: needed by strict
    "additionalProperties": false       // closed schema: needed by strict
  }
}
What a schema cannot express — plan around this JSON-schema support is deliberately narrow, and the limits shape your data model. Supported: the basic types, enum, const, anyOf, allOf, $ref, and string formats such as date, date-time, email, uri, uuid. Not supported: recursive schemas (so a tree of unbounded depth cannot be described — flatten it to a list with parent ids), numeric bounds (minimum, maximum, multipleOf), and string-length bounds (minLength, maxLength). The architectural consequence is the same point as the strict trap below, one level deeper: range and business rules are your validation code's job, not the schema's. A schema can promise you a number in the right field; only your code can promise it is between 0 and 100.
Tempting but WRONG — the big one "We used strict, so the extracted data is guaranteed correct." No. strict guarantees the shape is valid, not the meaning. It stops syntax errors and wrong types. It does NOT stop semantic errors: line items that do not add up to the total, or a value placed in the wrong field. A schema cannot check business logic.

Two different ways to get structured output — and they answer different questions

Defining a tool is one route. There is a second, dedicated one: constrain the response itself with output_config.format, so the model's final answer is schema-valid JSON rather than a request to call something.

output_config: {
  format: {
    type: "json_schema",
    schema: { "type": "object",
              "properties": { "sentiment": { "type": "string" } },
              "required": ["sentiment"],
              "additionalProperties": false }
  }
}
// The first text block of the reply is valid JSON matching that schema.
tool_use + input_schemaoutput_config.format

They compose: a request can force a strict tool and constrain the final answer's shape. The judgment call the exam is really testing is whether there is an action to perform. If nothing needs executing and you only want a clean record back, wrapping it as a fake tool call adds a loop you do not need.

Three limits worth knowing before you design around it The parameter name moved. A bare top-level output_format is deprecated — the current field is output_config.format. A schema is compiled once. The first request using a new schema pays a one-time cost, then it is cached for about 24 hours — so a system that generates a fresh schema per request pays that cost every single time, which is an argument for a small fixed set of schemas over dynamically-built ones. Two ways the guarantee can still not hold: if stop_reason comes back max_tokens the JSON is truncated, and if it comes back refusal the output need not match the schema at all. Both are Lesson 1's point arriving here: check stop_reason before you parse. It is also incompatible with citations — asking for both returns an error.

Schema design to stop the model inventing data

  • Make a field optional / nullable when the source document may not contain it. Then the model returns null instead of fabricating a value. This is the single most important anti-hallucination move in extraction.
  • Use an enum for fixed categories, plus an "other" value and a free-text detail field for cases outside the list — so the category set stays extensible.
  • Add an "unclear" enum value so the model has an honest choice for ambiguous cases, instead of picking a wrong-but-confident label.
  • When a field is genuinely multi-valued or versioned — the same term appears with more than one value (contract amendments, revised figures, historical states) — give the schema room for a list of values, each with its source location and effective date. Forcing one slot makes the model flip-flop between the values with no indication of which applies; a versioned field stops that at the source and preserves the history downstream may need.
"tax_id": { "type": ["string", "null"] }
// Document has no tax ID  ->  model returns  "tax_id": null
// NOT a plausible-looking invented number.
Say it like this

"To guarantee the model never invents a missing field, I make that field nullable in the schema and instruct it to return null when the source lacks the value. A retry will not help here — you cannot retry data that simply is not in the document. tool_use with strict fixes syntax and shape; nullable fields fix fabrication."

Pattern — "the model is inconsistent," so fix the SCHEMA, not the behavior When structured extraction is inconsistent, first ask whether the schema can even represent the truth. If the real data is nullable (a field the source may omit) or multi-valued / versioned (a contract amendment: "30-day terms" → "45 days"), a schema that forces a single mandatory value makes the model misbehave by design — it invents or flip-flops. The senior fix is to redesign the data model to match reality (nullable field; or a list of values with source location + effective date), not to patch the symptom with "always take the most recent" (loses history downstream needs), a classifier that deletes superseded sections (amendments often change only a subset of clauses — risks stripping text still in force), or routing every document to manual review (expensive, and still no structured answer). Preserve, don't discard.
Normalize messy input formats AT extraction time When the source uses inconsistent formats (prices "$12" vs "12.00", dietary info as icons vs text), do the normalization inside the extraction call: define the target shape in the schema and put explicit normalization rules in the prompt ("prices as a decimal with two places", "dietary info as enumerated tags"). The model then extracts AND normalizes in one pass, using its understanding — it knows a leaf icon means vegetarian. Do not extract raw and clean up in downstream code: deterministic post-processing is brittle (it must anticipate every format permutation) and semantically blind (it cannot interpret an icon). Keep it a single call so cross-field links survive (which icon sits next to which item). Same timing rule as few-shot for varied structure: interpretation that needs the source and the model's understanding belongs at extraction time, not in post-processing.

4. Validation, retry, and feedback loops

Even with a valid schema, the meaning can be wrong. The fix is validation-retry: after your code checks the output and finds a problem, send a follow-up message that includes three things — the original document, the failed extraction, and the specific validation error. That guides the model to self-correct.

// Follow-up on a validation failure:
{
  "role": "user",
  "content": "Your extraction had an error. The line items sum to
  $1,180 but stated_total is $1,080. Re-extract using the original
  document below and fix the discrepancy.\n\n[original document]"
}
Tempting but WRONG "The field came back empty, so retry until the model fills it in." Retry is ineffective when the information is simply absent from the source. Retrying an absent value just invites hallucination. Retry helps for format / structural errors, not for missing data — for missing data, use a nullable field and accept null.
Design self-correction into the schema Ask for calculated_total alongside stated_total so your code can flag mismatches automatically. Add a conflict_detected boolean for inconsistent source data. Add a detected_pattern field to each finding so you can later analyze which false-positive patterns developers keep dismissing.

Keep the two error types straight: schema syntax errors (broken JSON, wrong type) are eliminated by tool_use. Semantic validation errors (values do not sum, wrong field) are caught by your validation code and fixed with a targeted retry.

5. Efficient batch processing

The Message Batches API processes many requests together for 50% cost savings. The trade-offs you must know cold:

  • Up to a 24-hour processing window. Most batches finish inside an hour — but "usually fast" is not a promise you can design an SLA on.
  • No guaranteed latency SLA — you cannot promise when a single request finishes.
  • Two size ceilings, and you hit whichever comes first: 100,000 requests or 256 MB per batch. Long documents hit the megabyte ceiling well before the request count — 10,000 large documents will not fit in one batch, so the submission itself has to be split.
  • Each entry is one complete Messages request, so there is no round-trip inside a batch item — see the note below on what that does and does not rule out.
"Tools work" and "no tool loop" are both true — here is why These two statements look contradictory and the distinction is the exam-relevant part. A batch entry is a full Messages request, so every request-level feature works: you can define tools, attach images, use prompt caching, ask for structured output. What you get back is one response — and if that response says tool_use, nobody is there to run the tool and send the result back. The batch is finished. So: tool definitions are supported; the agentic loop is not. The rule that follows is architectural — batch the single-shot steps (classify, extract, summarise) and keep any step that needs a loop on the real-time path.

So batch is right for non-blocking, latency-tolerant work: overnight reports, weekly audits, nightly test generation. It is wrong for a blocking workflow — like a pre-merge check where a developer is sitting and waiting for the result.

custom_id — the correlation key Each batch request carries a custom_id you set. The response echoes it, so you can match each answer back to its input. Results come back in ANY order — you must key by custom_id, never by position in the list. To handle failures, resubmit only the failed items (found by custom_id) with a fix — for example, chunk a document that blew past the context limit.

Worked example — handling context_length_exceeded batch failures

A 10,000-doc batch finishes; 300 (3%) fail with context_length_exceeded. That error is an input-size problem: the context window is a shared budget — input + output must fit together — and these 300 documents are simply too long to fit.

CONTEXT WINDOW (e.g. 200K tokens) = one fixed box
  [ system prompt ~1K | the DOCUMENT (input) -- the big one | output <= max_tokens ]

  A failed doc = 320K tokens  >  200K window  ->  context_length_exceeded
  input budget ~= window - max_tokens - overhead
  (raising max_tokens RESERVES MORE for output, leaving LESS room for input)
Name check — what the API actually calls this context_length_exceeded is the plain-language name for the failure, and the mock exam uses it, so recognise it. In the API you meet the same condition under two different names depending on where it surfaces, and the difference tells you which lever to reach for. A request that was too big to even start comes back in the batch results as an error of type invalid_request — the request was malformed for this model, so no amount of retrying the same payload helps; you must shrink the input. A conversation that outgrew the window while running surfaces instead as stop_reason: "model_context_window_exceeded" — that is Lesson 4's problem, and the lever there is trimming or summarising history, not chunking a document. Too big to start → chunk the input. Grew too big while running → manage the history.

Why raising max_tokens can't help: max_tokens caps the output, not the input. It doesn't shrink the oversized document, and raising it actually leaves less room for input. max_tokens ≠ context window.

The fix — chunk the oversized docs, extract per chunk, merge:

320K doc  ->  split into 4 chunks (~80K each)
   chunk 1 (80K) -> extract -> partial 1     each request ~= 80K input + 1K prompt
   chunk 2 (80K) -> extract -> partial 2       + 4K output ~= 85K  < 200K  (fits)
   chunk 3 (80K) -> extract -> partial 3
   chunk 4 (80K) -> extract -> partial 4
                    merge partials -> final record

Chunking fixes the actual cause and works regardless of window size — better than "use a bigger-context model", which only raises the ceiling (a truly outsized doc can still exceed it) and forces you to reprocess the 9,700 successes. And reprocess only the 300 failures (found by their custom_id in the results file), never the whole batch. Merge nuance: union list-type fields (all line items) and reconcile any scalar that appears in more than one chunk — prefer the chunk that actually contains it, or flag a conflict rather than silently picking (the surface-don't-pick rule).

How you call it — create → poll → retrieve The lifecycle is three moves: create the batch (messages.batches.create(requests=[...]), each request a custom_id + params); poll until processing_status == "ended" (messages.batches.retrieve(id)); then retrieve the results (messages.batches.results(id)), each carrying a status of succeeded / errored / canceled / expired. Up to 100,000 requests per batch; results kept for 29 days; all Messages-API features work (vision, tools, caching); no beta header. Not available on Bedrock, Vertex, or Foundry.
DO THIS — split a mixed workload by latency profile When one pipeline has two kinds of work with different urgency — e.g. archival monthly reports (no deadline) plus urgent exception reports with a 30-minute alert SLA — do not route them the same way. Send the non-urgent bulk to the Batch API (50% cheaper) and the latency-sensitive items to the real-time Messages API (fast). Routing urgent work through batch fails the SLA (batch can take up to 24h, and "flagging urgent" or "hourly batches" does not change the batch turnaround). Match each stream to the cheapest lane that still meets its deadline.
Tempting but WRONG "The manager wants both the blocking pre-merge check AND the overnight report on batch, for 50% savings — so move both." No. Batch the overnight report only. The pre-merge check blocks a waiting developer and batch has no latency SLA, so it stays real-time. (And batch results are still correlatable via custom_id — that is not a reason to avoid it for the report.)

Two more practical points the exam likes:

  • Compute your submission frequency from the SLA. With a 24-hour batch window, submitting every 4 hours lets you guarantee a 30-hour end-to-end SLA.
  • Refine the prompt on a small sample first, then run the large volume — so you maximize first-pass success before spending on the whole batch.

6. Multi-instance and multi-pass review

Two limits of a single model call, and their fixes.

Self-review is weak

A model that just generated something keeps its reasoning context from that generation. In the same session it is less likely to question its own decisions. A separate, independent review instance — one with no prior reasoning context — catches more subtle problems than "please double-check yourself" instructions or extended thinking do.

Attention dilution on large reviews

When one call reviews a huge change (say a PR touching 14 files), quality drops: findings become inconsistent or contradictory. The fix is multi-pass review — run focused per-file local passes, then a separate cross-file integration pass.

Tempting but WRONG "Just use a model with a bigger context window — then all 14 files fit and the problem goes away." A bigger window does not fix attention dilution. The files fitting is not the issue; spreading attention thin across them is. Split into focused passes instead. (Also wrong: forcing developers to split their PRs, or running 3 times and taking a consensus — consensus suppresses real bugs that only one run happened to catch.)
Do this Use an independent reviewer instance, not self-review. Split big reviews into per-file passes plus a cross-file pass. Ask each finding to self-report a confidence score so you can route low-confidence findings for extra checking (calibrated review routing).
Single call over 14 files ── attention diluted ── contradictory findings │ ▼ split [file 1 pass] [file 2 pass] ... [file 14 pass] + [cross-file integration pass] └──────────── focused, consistent findings ─────────────┘
