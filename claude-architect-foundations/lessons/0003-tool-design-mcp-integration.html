Tool Design & MCP Integration

The model can only be as good as the tools you hand it. This domain is about designing tools it can pick, use, and recover from — not about hosting servers.

Your win: confidently answer "An agent keeps calling the wrong tool — what's your first fix, and why not a routing layer?" — and know when to split one tool into three.
Scope note This lesson is about tool design and integration. Hosting, deploying, and networking MCP servers are out of scope for the exam and for this lesson. We focus on how tools are described, chosen, and how errors flow back.

1. The mental model: descriptions are the interface

A tool is a function the model can call — it has a name, a set of inputs, and a tool description: the plain-text explanation of what the tool does. The model does not read your code. It reads the description and the input schema, then decides which tool fits the user's request.

So the description is the interface. If two tools sound the same, the model guesses. If a description is vague, the model picks wrong. Most "the agent misbehaves" problems in this domain are really "the description was weak" problems.

Crisp answer

"The tool description is the primary mechanism the model uses to select a tool. When selection is unreliable, I fix the descriptions before I add machinery around the model."

2. Writing descriptions that route correctly

A good tool description tells the model four things:

  • Input formats — what the inputs look like (an order ID like #1024, an email, a URL).
  • Example queries — the kind of user request this tool answers.
  • Edge cases — what happens with no match, bad input, or partial data.
  • Boundary vs alternatives — when to use this tool instead of a similar one.

The classic failure is two tools with near-identical minimal descriptions:

// BAD — the model cannot tell these apart
get_customer:  "Retrieves customer information."
lookup_order:  "Retrieves order details."

When a user asks "where is my order?", the model may call get_customer because both descriptions are one vague line. The fix is to expand each description so the boundary is obvious:

// GOOD — inputs, examples, and a boundary line
get_customer:
  "Look up a customer profile by email or customer ID
   (e.g. cust_8891). Returns name, contact, and account status.
   Use for questions ABOUT a person. Do NOT use for order
   status — use lookup_order for anything about a specific order."

lookup_order:
  "Look up one order by order number (e.g. #1024) or order ID.
   Returns status, items, shipping, and totals. Use for
   'where is my order', 'what did I buy'. Do NOT use to fetch
   a customer profile — use get_customer for that."
WRONG first move Jumping straight to a routing layer (extra code that decides which tool to call before the model sees the request). That over-engineers the problem and throws away the model's own language understanding. The root cause was weak descriptions — fix those first.
Also WRONG as a first move Adding few-shot examples in the system prompt to patch the misrouting. It burns tokens on every call and does not fix the real problem: the tool itself still describes itself badly. Fix the description, which every caller sees for free.
Do this When descriptions overlap, also consider a rename. If analyze_content secretly means "extract results from a web page", rename it to extract_web_results and give it a web-specific description. A precise name is half the description.

3. When one tool is doing too much: split it

A single generic tool with a fuzzy job is hard to select and hard to use well. If analyze_document can summarize, pull data points, and fact-check, the model never knows which behavior it is asking for.

The fix is to split the generic tool into purpose-specific tools, each with a clear input/output contract:

analyze_document  (does everything, unclear)
        │  split into
        ▼
extract_data_points      in: document → out: list of fields
summarize_content        in: document → out: short summary
verify_claim_against_source  in: claim + source → out: supported / not

Now each tool has one job, one shape of input, one shape of output. Selection becomes reliable because the descriptions no longer overlap.

Rename vs split — which one? Rename when the tool does one thing but is labeled badly. Split when the tool genuinely does several different things. In the sample-question style: expanding descriptions is the cheapest first step; splitting is right when the tool really has multiple jobs.

4. Structured error responses (the isError flag)

When an MCP tool fails, it signals that with the isError flag — a boolean the tool sets to tell the agent "this call did not succeed". But a bare isError: true with the message "Operation failed" is almost useless. The agent cannot decide what to do next.

Give the agent enough metadata to make a recovery decision. The four error kinds it must tell apart:

Error kindExampleWhat the agent should do
TransientTimeout, service unavailableRetry (maybe after a short wait)
ValidationBad input format, missing fieldFix the input, then retry
BusinessPolicy violation (e.g. refund window closed)Do NOT retry — explain to the user
PermissionNot allowed / not authorizedDo NOT retry — escalate or stop

Return that as structured fields: an errorCategory (transient / validation / permission / business), an isRetryable boolean, and a human-readable description. For a business-rule violation, set isRetryable: false and include a customer-friendly explanation.

// A useful error object
{
  "isError": true,
  "errorCategory": "business",
  "isRetryable": false,
  "message": "Refund window closed. Orders can be refunded
              within 30 days; this order is 45 days old."
}
Which parts of that object are the protocol, and which are your design Worth separating, because only one part is fixed. The flag is the protocol. An MCP tool result carries isError; the equivalent on a Claude API tool_result block is spelled is_error — same meaning, different layer, and you will meet both spellings depending on which side you are writing. Everything else in that object is your own convention. errorCategory and isRetryable are not standard fields — they are a shape you choose and put inside the result content. That is the actual architectural lesson: the protocol gives you a single bit, failed or not, and one bit is not enough to decide what to do next. So you design the vocabulary that carries the recovery decision, and — this is the part that matters — you use the same vocabulary across every tool, so the agent learns one way to read failures instead of one per tool.
WRONG Returning a uniform {"isError": true, "message": "Operation failed"} for every failure. The agent cannot tell a timeout (retry) from a policy block (stop). It may retry forever on a business rule, or give up on a one-off timeout.
You cannot prompt your way to information the tool never emitted When the fix is "the error responses are information-free", the answer is to enrich the response at the source — not to add few-shot examples that "interpret error patterns", and not to add a second analyze_error tool (an extra round-trip for something the failing tool already knew). If every failure returns "Operation failed", there is no signal to interpret: few-shot teaches the model to read present-but-ambiguous data consistently, but it cannot conjure absent data. Before reaching for examples, ask: is the information present-but-ambiguous, or missing entirely? Present → prompting/few-shot can help. Missing → fix the source (emit errorCategory / isRetryable / cause). Blanket server-side retries are also wrong here — they retry permanent errors and hide the category the agent needs.
Do this — empty is not an error Distinguish an access failure (the query could not run — needs a retry decision) from a valid empty result (the query ran fine, there were simply no matches). "No orders found for this customer" is a success with an empty list, not an error. Marking it isError makes the agent retry a query that already worked.
In multi-agent flows Handle transient errors locally inside the subagent (retry there). Only pass up to the coordinator the errors that cannot be fixed locally — and when you do, pass up any partial results you already have, so the coordinator can still make progress.

5. Distributing tools across agents

More tools is not better. Giving one agent 18 tools instead of 4–5 makes selection worse: every extra tool adds decision complexity, and the model is more likely to pick the wrong one. Agents also misuse tools outside their specialty — a synthesis agent (whose job is writing the final answer) will try to run web searches badly if you hand it search tools.

Crisp answer

"Scoped tool access: give each agent only the tools its role needs. Add a small number of limited cross-role tools for specific high-frequency needs, and route anything complex through the coordinator."

Example: a synthesis agent should not get a full web-search tool. Give it a narrow verify_fact tool for the one thing it actually needs (quick fact checks), and send genuinely complex research back through the coordinator.

6. Forcing tool choice with tool_choice

You can control whether and which tool the model calls with tool_choice:

ValueMeaningUse when
"auto"Model decides: call a tool or just reply in textNormal case — the model chooses
"any"Must call some tool (no plain-text reply)You need an action, not chatter
{"type":"tool","name":"..."}Must call this exact toolGuarantee a step runs first
"none"Must not call any tool, though the tools stay definedYou want one prose turn — a summary, a clarifying question — without stripping the tools out of the request

Same field, same four values as Lesson 2 §3 — met here from the tool designer's side rather than the schema author's. The pairing worth remembering: "any" guarantees that a tool runs but not which; only the named form guarantees which.

Use the forced form to make sure a step happens in order — for example, force extract_metadata so it always runs before an enrichment step. Use "any" when you must guarantee the model performs an action rather than returning text.

Do this — constrain the tool, not just the choice Replace a dangerous generic tool with a narrow one. Instead of fetch_url (which can hit anything), give a load_document tool that validates the URL is a real document first. A constrained tool is safer than trusting tool_choice alone.

7. Integrating MCP servers into Claude Code

MCP (Model Context Protocol) is an open standard for connecting a model to external tools and data. An MCP server exposes tools (actions), resources (content it can read), and prompts. Claude Code connects to these servers and, at connection time, discovers the tools from every configured server at once — they are all available to the agent together.

Where servers are configured: scoping

There are three scopes, not two, and the one people forget is the default. You choose with claude mcp add --scope <local|user|project>; omit the flag and you get local.

local — the defaultprojectuser
Where it livesYour own settings, recorded per project.mcp.json in the repoYour global user config
Who gets itOnly you, only in this projectEveryone who clones the repoOnly you, in every project
Committed?NoYes — checked in with the codeNo
Reach for it whenTrying a server out on one projectThe whole team needs this toolingA personal server you want everywhere

The scope decision is really one question: who should get this server, and where? Team-wide and tied to this codebase → project, so it is version-controlled and arrives with a git clone. Just you, everywhere → user. Just you, just here → local, which is why it is the safe default: an experiment cannot leak into a teammate's setup or another project.

A project-scope server is not trusted automatically Because .mcp.json arrives from the repository, a server listed there is not connected to on sight — it sits as pending approval until you accept it. This is a deliberate security boundary, and it is worth being able to explain why: a committed config file is executable configuration written by whoever last pushed. Without the gate, cloning a repository would silently run whatever command its .mcp.json names. The trade-off to state out loud: project scope buys you team consistency, and pays for it with a one-time approval step per person.

Secrets: environment variable expansion

Never commit a token into .mcp.json. Instead use environment variable expansion — write ${GITHUB_TOKEN} and Claude Code fills in the real value from your environment at run time. The file stays safe to commit; the secret lives outside it.

// .mcp.json — safe to commit, no secret inside
{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" }
    }
  }
}
WRONG Pasting the literal token ("GITHUB_TOKEN": "ghp_abc123...") into .mcp.json and committing it. The secret is now in git history for everyone. Use ${GITHUB_TOKEN} instead.

MCP resources reduce exploratory calls

MCP resources expose ready-made content catalogs — issue summaries, documentation hierarchies, database schemas — that the agent can read directly. This cuts down exploratory tool calls: instead of the agent making ten calls to figure out the shape of a database, it reads the schema resource once.

Do this — help the agent prefer the better tool Enhance an MCP tool's description so the agent prefers it over a weaker built-in. If a Jira MCP server offers a real search tool, write its description so the agent uses it instead of falling back to Grep over local files that do not have the answer.
Community vs custom servers For a standard integration (Jira, GitHub, Slack), use an existing community MCP server — do not build your own. Reserve a custom server for team-specific workflows that no community server covers.

8. Built-in tools: Read, Write, Edit, Bash, Grep, Glob

Claude Code ships with built-in tools. Knowing which to reach for is a task statement in this domain:

ToolUse it for
GrepContent search inside files — function names, error messages, imports
GlobFile-path pattern matching — e.g. **/*.test.tsx
Read / WriteFull-file read / full-file write
EditTargeted change by matching a unique piece of text in the file
BashRun a shell command
Gotcha — Edit needs unique text Edit replaces text it can match uniquely. If the text you target appears several times, the edit fails because it does not know which one you mean. The fallback is Read the whole file, then Write it back with your change — it needs no match at all, so a repetitive file stops being a problem, and you can place the new code at the exact spot you want.
Two wrong escapes from a failed Edit When Edit can't find a unique anchor, two "fixes" are tempting and both are wrong. A very long old_string (30+ lines) is brittle — one whitespace or format difference breaks the match. replace_all mutates every occurrence of the pattern and corrupts the whole file (it is for renaming a symbol everywhere, never for a single insertion). And appending with Bash lands the code at the end of the file — wrong when the task says "insert between two functions." Check every option against all the stated constraints (here: unique-match impossible AND must land in a specific location); Read → Write is the only one that satisfies both.
Do this — understand a codebase incrementally Do not read every file up front. Start with Grep to find entry points, then Read to follow imports and trace the flow. To trace how a function is used across wrapper modules, first find its exported name, then Grep for that name everywhere it is called.
Understanding a subsystem's architecture — top-down from the root When the goal is to understand how a subsystem works (before changing it), not just locate a symbol, navigate top-down from the architectural root: analyze imports and class hierarchies to find the base class / interface, Read that to grasp the design, then trace only the specific implementations you care about. Structured and cheap on context. Avoid the three traps: (a) reading every file flat — 8,000 lines floods context and buries the relevant logic; (b) grepping keywords and reading bare line-ranges — that strips the class/method context you need to know what the code guards and how it fits (keyword search is for locating, not understanding); (c) prioritizing the largest files — size is a poor proxy for importance; the strategic base class is often small. Navigate by architecture, not by line count or keyword hits.

Finding all callers before deleting a function

Grep is a string tool, not a symbol tool: it matches the exact name you give it, not the function's identity. A function has one definition but can be re-exported or wrapped under a different name — calculateTax in the library becomes computeOrderTax in the orders module. At the call site the code says computeOrderTax(...), so the string calculateTax never appears there. Any search is only as complete as the list of names you feed it.

Do this — enumerate every exposed name, then Grep each Read the library and its wrapper modules to gather all the names the function is exposed under, then Grep for each name across the codebase. This searches for the call itself — a call site is found no matter how its file imported the function.
Tempting but leakier — tracing imports instead of names "Grep for files that import the library/wrapper, then read each to check usage." This searches a proxy (the import statement) instead of the target (the call), and the proxy has holes: it misses dynamic imports (await import(path)), re-export chains (a file imports the wrapper second-hand through another module), and indirect call chains — and it forces you to read every importing file by eye. Grepping the original name only is worse still: it misses every renamed call site. Reliability order: enumerate-all-names > trace-imports > original-name-only > read-the-docs (docs are stale and incomplete — never delete on documentation-level evidence).
