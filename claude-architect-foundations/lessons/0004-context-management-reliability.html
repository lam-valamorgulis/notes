Lesson 4 · Domain 5 · 15% of the exam

Context Management & Reliability

The judgment domain. There is no single doc that gives you the answer — you must reason about what happens when a long, multi-agent workflow slowly loses the facts it needs.

Your win: when the exam hands you a long-running agent that has started giving vague, inconsistent, or unsupported answers, you can name the exact failure — lost facts, lost position, lost provenance, or a silently swallowed error — and pick the fix that keeps the real facts alive.

This domain is about reliability over time. Short chats work fine. The problems here only show up in long conversations, big codebases, and multi-agent systems where context is summarized, trimmed, or passed between agents.

1. Why long context breaks — the two core failures

A model has a limited context window. As a conversation grows, something has to give. Two things go wrong, and the exam tests both.

Failure A — Progressive summarization loses hard facts

Progressive summarization means: as the chat gets long, you replace old turns with a short summary to save space. The danger: a summary tends to keep the gist and drop the numbers. Amounts, percentages, dates, order numbers, and what the customer clearly asked for all get squashed into vague words like "the customer had a billing issue."

WRONG — trusting the summary for facts "The customer wanted a refund and was unhappy about the price." That summary threw away $47.30, ordered on May 2, order #10842, and "promised a 20% discount by phone." Now the agent cannot act correctly, and it does not even know it lost anything.

Failure B — "Lost in the middle"

"Lost in the middle" is a known model behavior: the model reads the beginning and the end of a long input reliably, but it may skip or forget things buried in the middle. So even if a fact is technically in context, its position decides whether the model actually uses it.

LONG INPUT (what the model actually attends to) START ┃██████████┃ strong attention ✓ used ┃ ┃ MIDDLE ┃░░░░░░░░░░┃ weak attention ✗ often missed ┃ ┃ END ┃██████████┃ strong attention ✓ used Fix: put the key-findings summary at the START, add explicit section headers, don't hide the one fact that matters in paragraph 14 of 30.

2. Tool results are token hogs

Every tool result stays in context and eats tokens. The problem: a tool often returns far more than you need. An order lookup can return 40+ fields when your task only needs 5 (id, status, total, date, customer). Multiply that by many lookups across a long session and the useful facts get drowned in noise — which makes both failures above worse.

DO THIS — trim before it accumulates Trim each tool result down to the relevant fields before it lands in context, not after. Once 40 fields per call pile up over 30 calls, the damage is done — the window is full of noise and you are paying for all of it.

See the official tool-use guidance on shaping and trimming tool results before feeding them back to the model.[2]

Two API mechanisms for the same problem — and they are not the same

Everything above is something you do to the context. The API also offers two mechanisms that do it for you, and the exam-relevant point is that they work in opposite ways. Confusing them leads to picking the one that destroys the thing you needed.

Context editing — prunesCompaction — summarizes
What it doesRemoves old content outright: stale tool results, old thinking blocksReplaces earlier history with a summary of it
What survivesThe conversation's structure; the removed content is goneThe gist; the exact wording is gone
Right whenOld tool output is genuinely no longer relevant — you read the file three steps ago and acted on itThe conversation is genuinely approaching the window limit and you need the earlier meaning, not the earlier text
The costAnything you pruned is unrecoverable — so prune tool results, not factsSummarizing is exactly the lossy step §1 warned about

So the two mechanisms sharpen the lesson's core rule rather than replacing it: context editing is the automated version of "trim tool results" and is usually safe, because a verbose tool result is noise once you have acted on it. Compaction is the automated version of the very failure in §1 — it is the right tool when you are out of room, and it is still lossy, which is precisely why the case-facts block in §3 exists. Compaction handles the history; the facts block protects what compaction would blur.

The compaction trap — a silent state loss When compaction is on, the response carries a compaction block along with the text, and the API uses that block to stand in for the history it replaced. So on the next turn you must append the whole response content back to your message list — not just the text you pulled out of it. Code that does the natural-looking thing and appends only the extracted string silently throws the compaction state away: no error, no warning, and the conversation quietly loses the summary that was supposed to be holding its history. This is the same class of bug as Lesson 1's stop_reason trap — a reliability failure that looks like success — and it is worth recognising as a pattern, because that shape is most of this domain.
The stop reason that means "the whole conversation no longer fits" Distinguish two failures that both feel like "too big". max_tokens means this reply hit your output cap — the answer is truncated, and you raise the cap or stream. model_context_window_exceeded means the whole conversation no longer fits, and no output setting helps: you must reduce what you are sending — prune the tool results, compact the history, or move the durable facts to disk. That is this lesson's entire subject in one field value.

3. The "case facts" block — the single most important trick

Here is the pattern the exam rewards. Do not rely on the summarized history to carry the numbers. Instead, pull the hard, transactional facts out into a small, separate block and re-send that block with every prompt, outside the part that gets summarized.

A case facts block is a short, structured list of the facts that must never be lost: amounts, dates, order numbers, statuses, and clear customer promises. Because it lives outside the summary, summarization can never blur it.

┌─ CASE FACTS (verbatim, re-sent every prompt, never summarized) ─┐ │ order_id: #10842 │ │ order_date: 2026-05-02 │ │ amount: $47.30 │ │ status: shipped, not delivered │ │ customer_promise: "20% discount agreed by phone on May 5" │ └────────────────────────────────────────────────────────────────┘ + [ summarized conversation history ] ← gist only; safe to blur + [ new user message ]

Also: pass the complete conversation history in each API request so the model stays coherent — the API is stateless, so if you drop turns, the model simply never sees them. The case facts block is the safety net for the parts you do compress.

Where you put the block decides whether you keep your prompt cache The diagram above draws case facts first, because that is how you think about priority — and read literally, it is the most expensive possible arrangement. Here is the mechanism. Prompt caching is a prefix match: the request is assembled in a fixed order — tools, then system, then messages — and a cache entry is reused only up to the first byte that differs. Everything after that byte is reprocessed at full price. Now recall what the case-facts block is: a small piece of text that changes as the case develops. Put a changing thing at the front — in the system prompt — and every turn you invalidate the entire conversation behind it. You have built the perfect cache-buster and put it in the worst place.

The fix is placement, not abandonment. Keep the stable material at the front — the frozen system prompt, a tool list in a deterministic order — and put the volatile facts block late, in the messages, after the cached prefix. The rule generalises past this lesson: stable content first, volatile content last. Same reasoning explains why editing the system prompt mid-conversation is costly while appending an operator instruction as a later message is cheap — one rewrites the prefix, the other lands behind it.

Three habits that quietly destroy caching — audit for these All three put something that changes into the stable part of the prompt, which is the one sin that matters. (1) A timestamp or a generated id in the system prompt — "Current time: …" makes every single request a unique prefix, so nothing ever caches. (2) Serialising data without a fixed key order — the same facts rendered in a different order are different bytes. (3) Building the tool list per user or per request — tools render first, so varying them invalidates everything. The diagnostic is direct rather than guesswork: the response reports how many tokens were read from cache, and if that number stays zero across requests that ought to share a prefix, one of these three is the reason.
Crisp answer — how to stop long chats from losing facts

"Summaries drop numbers. So I extract the hard transactional facts — amounts, dates, order numbers, statuses, customer promises — into a persistent case facts block that I re-send verbatim with every prompt, outside the summarized history. I trim verbose tool results to only the relevant fields before they accumulate, and I put the key-findings summary at the start with clear section headers to beat lost-in-the-middle."

4. Escalation and ambiguity — knowing when to hand off

A support agent must know when to stop trying and bring in a human. The exam is picky about which signals justify escalation.

Good escalation triggers (real signals):

  • The customer explicitly asks for a human — this is a firm escalation trigger; do not ignore it, deflect with a capability list, or keep trying to self-solve over many turns. But escalate warm, not cold: first acknowledge the frustration, then take one minimal respectful step so the handoff is useful — offer the fix if you already have context and a resolution exists (see Q14-style cases), or ask one targeted question if you have zero context yet, so the human isn't handed a blank case (and you get a shot at first-contact resolution). A single acknowledging, context-gathering question is not "stalling"; silently running multiple lookups, or listing what the bot can do, is. Escalating instantly with zero context is a cold handoff — the human restarts from scratch.
  • A policy gap or exception — the policy is silent on this exact request (for example, policy covers price adjustments on your own site, but the customer asks for a competitor price match). Silence is not permission; escalate.
  • No meaningful progress — the agent is stuck and cannot move the case forward.

Bad triggers (unreliable proxies):

WRONG — escalate on sentiment "The customer sounds angry, so escalate." An angry customer with a one-click, in-policy fix does not need a human. Sentiment measures mood, not case complexity. Sentiment ≠ complexity.
WRONG — escalate on the model's self-reported confidence "The model says it's only 60% confident, so escalate." Self-reported confidence scores are poorly calibrated — the model is often confidently wrong or needlessly unsure. A raw confidence threshold routes the wrong cases.

When a lookup returns multiple customer matches, do not guess one by a heuristic ("probably the most recent"). Ask for more identifiers to disambiguate. Picking wrong here can expose the wrong person's data.

DO THIS — fix a mis-calibrated escalation rate If the agent escalates easy cases and tries to auto-handle policy exceptions, do not add a confidence threshold or a sentiment classifier. Add explicit escalation criteria with few-shot examples to the system prompt, showing side by side when to escalate vs when to resolve. That teaches the boundary directly.

5. Error propagation across multi-agent systems

In a coordinator-plus-subagents system, a subagent will sometimes fail. What it sends back decides whether the whole system recovers well or fails blindly.

Return structured error context. When a subagent (say a web-search agent) times out, it should report: the failure type, the query it attempted, any partial results it did get, and alternative approaches. That lets the coordinator decide intelligently — retry, route around it, or note the gap.

GOOD (coordinator can recover): { status: "error", type: "timeout", attempted_query: "2025 EV sales EU", partial_results: [ ...3 of 10 rows... ], alternatives: ["retry with narrower date range", "try cached source X"] } BAD (coordinator is blind): { status: "search unavailable" } ← hides everything { results: [] } ← empty, looks like success (LIE) throw → whole workflow dies ← one failure kills all

Also learn to tell two "empty" results apart:

  • An access failure (a timeout) — something broke; a retry decision is needed.
  • A valid empty result — the query ran fine and there genuinely are no matches. This is a real answer, not an error.
WRONG — the two silent anti-patterns (1) Swallowing the error: returning empty results as if the call succeeded. The coordinator now trusts a lie. (2) Killing the whole workflow on one subagent failure. One bad source should not take down everything.
The senior pattern Subagents do local recovery for transient problems (retry the flaky call themselves) and only propagate the errors they could not resolve, with what they attempted and any partial results. The final synthesis is then annotated with coverage notes: which findings are well-supported, and which topic areas have gaps because a source was unavailable.

6. Context in large codebase exploration

Long coding or exploration sessions have their own decay. Context degradation shows up as the agent giving inconsistent answers and starting to reference "typical patterns" instead of the specific classes and files it actually discovered earlier. When you hear "usually this kind of app has a UserService…", the real findings have fallen out of context.

Three tools to fight this:

  • Scratchpad files — write key findings to a file on disk. Files persist across context boundaries; the window does not. The agent re-reads the scratchpad instead of trying to remember. Two things make this reliable: (1) the same agent can re-read the file mid-session, on demand — so even inside one long session it fetches a fact fresh from disk rather than recalling it from a crowded window (no sub-agent required); and (2) the scratchpad keeps full detail, unlike a summary, which flushes the specifics out.
  • Subagent delegation — send the noisy, verbose exploration to a subagent so its 10,000 tokens of file-reading never touch the main context. The main agent keeps only the high-level understanding the subagent returns. This is the core reason subagents exist.[1]
  • /compact — a Claude Code command that shrinks the current context (it summarizes the session) to free room during a long exploration.
Tempting but wrong — for "agent forgets / contradicts itself in long sessions" When the symptom is inconsistent answers about things discussed earlier, three fixes look reasonable and all fail. A bigger context window / higher model tier only delays the problem — it does not cure attention degradation over a long, noisy context. Auto-clearing context on a timer throws away the valid findings the engineers are already tired of re-supplying. Pre-summarizing every file before exploration loses the detail that makes exploration useful, and it is done blind — before you know which files matter. The reliable fix keeps the findings and lets the agent re-fetch them accurately: a scratchpad file.
DO THIS — crash recovery for long agent runs Have each agent export its state to a known location — a manifest file. On resume after a crash, the coordinator loads the manifest and injects the recovered state back into each agent's prompt. Work already done is not repeated.

Worked example — resuming a crashed pipeline with manifests

A pipeline runs 28 documents through three agents and crashes after doc 12. Because each agent wrote a structured manifest to a known location as it worked (not only at the end), the progress is already on disk when the crash hits:

web_search.manifest    { status: complete, sources: [doc 1..28] }        // all found
doc_analysis.manifest  { status: in_progress,
                         completed: [ {doc 1, findings{...}} ... {doc 12, findings{...}} ],
                         next_doc_id: 13 }                                // <- resume point
synthesizer.manifest   { status: in_progress, patterns_so_far: [...], based_on_docs: [1..12] }

On resume the coordinator drives recovery (it stays the single hub):

COORDINATOR restarts
  1. read the 3 manifests from the known location
  2. compute state: sources done | extraction 1-12 done, resume at 13 | synthesis partial
  3. inject ONLY the relevant slice into each agent's prompt:
     -> doc_analysis: "Docs 1-12 already extracted (findings attached). Continue from 13."
     -> synthesizer:  "Patterns so far [...]; 12/28 extractions attached. Extend as docs arrive."
  4. pipeline continues at doc 13  (no work repeated)

This balances the three needs at once: fidelity (findings stored in a schema, exact), efficiency (compact reports, not the full conversation log), and coordinator control (the coordinator reads and injects, staying the orchestration hub). Two rules make it work: write the manifest incrementally (a report written only on completion is useless when the crash is mid-run), and inject only the relevant slice into each agent (doc-analysis needs "resume at 13", not the synthesizer's patterns) — which is why per-agent independent reload bloats each agent with noise it does not need.

7. Human review and confidence calibration

When you automate document extraction (pulling fields off invoices, forms, etc.), you decide which extractions a human must check. Doing this by a single overall accuracy number is a trap.

WRONG — trusting one aggregate accuracy number "We're at 97% overall, ship it." A single average hides the fact that you might be at 99% on typed invoices but 70% on handwritten receipts, or great on totals but poor on dates. The average masks a weak document type or field.

Do this instead:

  • Stratified random sampling — sample across each group (each document type, each field) rather than randomly across everything. This measures the true error rate inside high-confidence extractions and catches new kinds of errors the average hides. "Stratified" just means you sample each slice on purpose.
  • Field-level confidence scores, calibrated on a labeled validation set (data where you know the right answer), to route review attention to the fields most likely wrong.
  • Validate by document type and field before you let high-confidence extractions run without review.
  • Route low-confidence or ambiguous / contradictory-source extractions to humans first, so your limited reviewers spend time where it matters.
Confidence routing aims HUMANS — it is not a second model Field-level confidence routing spends your scarce human review budget on the riskiest extractions: the same extraction model self-reports a confidence per field, you calibrate a threshold on labeled data, and the low-confidence items go to your reviewers. This is not "have a second model re-check every extraction" — that is a different, more expensive approach (a second LLM pass) and it does not solve a human-capacity limit. When the constraint is "reviewers can only check 20%," the win is aiming a cheap signal (confidence) at an expensive resource (people) — triage, not duplication. Also remember: schema validation catches syntax only; a value of the right type in the wrong field is semantically wrong and passes validation, which is exactly why you need a confidence signal to find it.
Worked example — aiming beats random Say 10,000 extractions/day, 12% semantic errors (= 1,200 bad ones), and reviewers can check only 20% (2,000/day). First calibrate on a labeled set: you find field-confidence below 0.85 covers ~2,000 extractions (20% of volume) with a 45% error rate — so that low-confidence band holds 900 of the 1,200 errors (75%); the high-confidence 8,000 hold only 300. Now spend the same 2,000-review budget two ways:
StrategyWhich 2,000 you reviewErrors caught
Random 20%a random slice20% × 1,200 = 240
Confidence routingthe low-confidence 2,000900
Same human effort, ~3.75× more errors caught — purely by aiming. Random sampling is the right tool to measure the error rate (an unbiased ~12% estimate); confidence routing is the right tool to catch errors under a capacity limit. Different jobs.

8. Provenance and uncertainty in multi-source synthesis

When one agent merges findings from many sources, it must keep track of where each fact came from. Provenance means the source of a claim — which URL, which document, which excerpt.

WRONG — summarizing away the sources Compressing findings into a clean paragraph and dropping the claim-source mapping (which claim came from which source). Now no fact can be traced or checked. "Claim-source mapping" = a link from each statement to the exact source it came from — keep it.

The synthesis rules the exam wants:

  • Preserve and merge structured claim-source mappings — keep source URLs, document names, and excerpts attached to each claim through the merge.
  • Conflicting numbers from two credible sources? Do not silently pick one. Annotate the conflict with both values and both sources, and let the reader see it.
  • Require dates (publication or collection date) in structured outputs, so a 2023 figure and a 2025 figure are read as different times, not as a contradiction.
  • Render each content type in its right form — financial data as tables, news as prose, technical findings as structured lists — instead of flattening everything into one format.
  • Also require subagents to include metadata (dates, source locations) in their structured outputs, so provenance survives the hand-off.
WRONG — reconstructing attribution after the merge If the subagents already cite correctly and the binding is only lost at synthesis, the fix is to preserve the model's original claim-source mapping — not to reconstruct it later. Three reconstruction "fixes" are tempting and all fail: (1) post-hoc log analysis (keep full transcripts, add an agent to work out attributions afterwards) is fragile and expensive, and still loses bindings the synthesis step already merged; (2) semantic-similarity matching re-guesses the source from text overlap and attributes the wrong source when two sources say similar things; (3) source-ID prefixes injected into the prose get dropped, paraphrased, or hallucinated during summarization — because metadata hidden inside the text is just more text to rewrite. Rule of thumb: metadata that must survive summarization lives in a structured field OUTSIDE the prose, and you preserve the known mapping rather than re-derive a lost one.
Crisp answer — a source returns a number that conflicts with another

"I never arbitrarily pick one value. I keep the claim-source mapping intact through synthesis, annotate the conflict with both figures and their sources, and attach the publication dates — because a difference in time is not a contradiction. Financial data goes in a table, not buried in prose, so the conflict is visible."
