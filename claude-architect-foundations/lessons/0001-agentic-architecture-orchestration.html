Lesson 1 · Domain 1 · 27% of the exam

Agentic Architecture & Orchestration

This is the biggest domain on the exam, and it is about judgment: not just what an agent does, but why one design choice beats another.

Your win: confidently answer "How does an agentic loop decide when to stop, and when do you use a coordinator with subagents instead of one agent?" — and spot the tempting wrong answer every time.

Domain 1 is 27% of the exam — the largest slice. Almost every question is a short production story that asks for the MOST effective fix. So we will learn the fact, then learn why the plausible-looking wrong option is worse.

1. The agentic loop — how an agent actually runs

An agent is not one call to Claude. It is a loop. You send a request. Claude answers. You look at why Claude stopped. If Claude asked to use a tool, you run that tool, give the result back, and send again. You repeat until Claude is finished.

The single field that drives the whole loop is stop_reason. It tells you why the model stopped talking. The two values you must know:

  • tool_use — Claude wants to run a tool. You must run it and send the result back.
  • end_turn — Claude is done. This is your stop signal.
send request to Claude │ ▼ read stop_reason │ ┌──────┴───────────────┐ │ │ "tool_use" "end_turn" │ │ ▼ ▼ run the tool(s) STOP │ (task done) ▼ append tool_result to the conversation │ └──────────► send again (loop)

When Claude asks for a tool, the message contains a tool_use block: the tool name, a unique id, and the input. You run the tool, then you send back a tool_result block that carries the same id and the output. That result is appended to the conversation history, so on the next turn Claude can read what happened and reason about the next step.

// Claude's turn stopped with stop_reason: "tool_use"
{ "type": "tool_use", "id": "toolu_01A", "name": "get_customer",
  "input": { "email": "sam@shop.com" } }

// Your turn: run the tool, append the result with the SAME id
{ "type": "tool_result", "tool_use_id": "toolu_01A",
  "content": "{ \"customer_id\": \"cus_88\", \"verified\": true }" }

The loop is model-driven. Claude decides which tool to call, from the context and the tools you gave it. You do not write a fixed decision tree that says "first call A, then B, then C". You give good tools and a clear goal, and the model chooses the path.

Do this Stop the loop when stop_reason == "end_turn". That is the correct, reliable completion signal. Everything else is a guess.
Tempting but wrong "Read the assistant's text and stop when it sounds finished" (parsing natural language for phrases like "I'm done"). This is fragile — wording changes, languages differ, and the model may write a summary and still want another tool. The structured field stop_reason exists exactly so you never have to guess from prose.
Tempting but wrong "Just cap the loop at N iterations and stop there." An iteration cap is a good safety limit to stop runaway cost. But if you use it as the primary way to know the task is done, you will cut off real work halfway or keep spinning after Claude already said end_turn. The cap is a seatbelt, not the steering wheel.

The other stop_reason values — the ones that break a loop silently

tool_use and end_turn are the two that drive the loop. But the field has more values than that, and the difference matters architecturally: if you write the loop as "if tool_use, run the tool; otherwise we're done", then every other value silently becomes "done" — and a half-finished answer gets reported to the user as a finished one. There is no error and no exception. That is the worst kind of bug: a wrong answer that looks correct.

stop_reasonWhat actually happenedWhat the loop must do
tool_useClaude asked for a toolRun it, append tool_result, send again
end_turnClaude finished naturallyStop. This is the real completion signal
max_tokensThe answer hit your output cap mid-sentenceNot done. The text is truncated — raise max_tokens, or stream, and retry
pause_turnA long-running server-side tool (web search, code execution) paused the turnSend the conversation again with the assistant turn appended, so the server resumes. Do not add a "continue" message
stop_sequenceYour own custom stop string firedWhatever your design intends — it is your own signal
refusalSafety classifiers declined the requestRead stop_details for the category. Do not re-send the same prompt and hope
Why this is an architecture question, not trivia Each of these values needs a different recovery action, and only one of them means "finished". So the loop is not a two-way branch — it is a dispatch on a known set of values, with an explicit branch for anything unrecognised. On top of that, refusal means content can be empty: code that reaches straight for content[0].text crashes on that response. Check stop_reason before you read the content. Related: model_context_window_exceeded means the whole conversation no longer fits — a different problem from max_tokens, and the subject of Lesson 4.

2. Coordinator and subagents — hub and spoke

One agent cannot hold everything for a big job. So you use a coordinator (the hub) that talks to several subagents (the spokes). The subagents never talk to each other. All routing, error handling, and passing of information goes through the coordinator.

┌───────────────┐ │ COORDINATOR │ │ (the hub) │ └───┬───┬───┬───┘ delegates │ │ │ aggregates results ┌───────┘ │ └───────┐ ▼ ▼ ▼ ┌─────────┐ ┌─────────┐ ┌─────────┐ │subagent │ │subagent │ │subagent │ │ A │ │ B │ │ C │ └─────────┘ └─────────┘ └─────────┘ (isolated) (isolated) (isolated) no shared memory between spokes

The coordinator does four jobs:

  • Decompose — break the big task into smaller subtasks.
  • Delegate — send each subtask to the right subagent.
  • Aggregate — collect the subagent results into one answer.
  • Choose — decide which subagents to invoke for this query. A simple query may need one subagent; a complex query needs many. This is dynamic selection, not always running the full pipeline.
Key fact — isolation Subagents run with an isolated context. They do not automatically inherit the coordinator's conversation history. What a subagent knows is only what you put in its prompt. We come back to this in section 3.

The classic failure: narrow decomposition. Say the task is "research the creative industries." The coordinator only breaks it into visual-art subtasks. The report comes back with no music, no writing, no film. Each subagent did its assigned job perfectly. The root cause is the coordinator's decomposition — it never created the missing subtasks. The subagents cannot cover a topic they were never asked about.

Tempting but wrong When the creative-industries report misses music and film, it is tempting to blame the subagents ("the research agents are weak, give them better tools"). Wrong. The subagents completed exactly what they were handed. Fix the coordinator's decomposition, not the downstream workers.

To catch gaps, good coordinators use an iterative refinement loop: after the first synthesis, the coordinator checks the output for missing coverage, sends new targeted subtasks to fill the gaps, and re-runs synthesis until coverage is good enough.

3. Spawning subagents and passing context

The mechanism to spawn a subagent is the Task tool. For the coordinator to spawn anything, its allowedTools list must include "Task". If Task is missing from allowedTools, the coordinator simply cannot delegate.

Because subagents are isolated (section 2), you must put the context into the prompt. Pass the full prior findings directly — the web-search results, the document text, the earlier analysis. Do not assume the subagent can "see" what the coordinator saw.

// Coordinator spawns a subagent with the Task tool.
// Everything the subagent needs is IN the prompt — nothing is inherited.
Task({
  subagent_type: "fact_checker",
  prompt: `Verify these claims. Here are the source findings:
    - Claim: "Global music revenue grew 10% in 2024"
      Source: [full text of the search result, with URL]
    Return each claim as verified / unverified / false, with the URL.`
})

An AgentDefinition is the config that describes a subagent type: its description, its system prompt, and its tool restrictions (which tools that subagent is allowed to use). You give each subagent only the tools it needs — this is least privilege.

Two more habits the exam rewards:

  • Keep metadata attached. Use a structured format (like JSON) that separates the content from its metadata — source URL, document name, page number. That way attribution survives when context is passed between agents. Pasting raw text loses the source.
  • Write goal-based prompts. Tell the subagent the goal and the quality criteria, not a rigid step-by-step script. Then the subagent can adapt to what it finds. Over-scripted prompts break the moment reality differs from your steps.
Do this — real parallelism To run subagents in parallel, emit multiple Task tool calls in a single coordinator response. If you spread the calls across separate turns, they run one after another (sequential), not together.
Width, not depth Width is how many subagents run at once — that is where the speedup comes from. Depth is how many layers of agent-spawning-agent you stack — that is where debugging pain comes from. Once the work items are independent, one level of fan-out already runs all of them concurrently; extra layers below add no speed. So a slow sequential loop over 12 independent items is fixed by one coordinator fanning out to a few subagents, each taking a subset, then aggregating the results back at the coordinator before synthesis.
Indirection destroys the coordinator's debug view A coordinator can only monitor work it directly holds a handle to. Three shapes break that, and all three show up as exam distractors:
  • Nested spawning — a subagent spawns its own subagents. The coordinator sees one child and cannot see the grandchildren, their failures, or their partial output.
  • Recursive hierarchies — the same problem, repeated, and the run shape changes each time so there is nothing stable to instrument.
  • External queues / worker pools — the work leaves the agent system. The coordinator must now ask another system what succeeded and what it produced, instead of receiving results directly.
Each of these can be genuinely good engineering elsewhere. When the requirement says "preserve the ability to monitor and debug", they are costs, not features.
Timing — fan out AFTER you have well-scoped sub-questions, not before Parallel subagents are powerful only once the work has decomposed into scoped, independent sub-tasks — "find all test files", "trace the refund flow". Fanning out before you know where the subject lives is premature: the subagents explore blindly, duplicate each other, and miss cross-cutting flows that span their separate scopes. So: to understand where auth lives in an unfamiliar 800-file codebase, localize first (Grep entry points, follow real imports) — do not fan out yet. But once you've read enough to have concrete scoped questions (e.g. a 45-file module you've partly mapped), then delegate each scoped question to a fresh-context subagent while the main agent keeps the architectural overview. Same tool, opposite verdict — decided by whether you have scoped questions yet.

Worked example — scoped subagents scale exploration past one context window

An agent must find untested code paths across a 45-file payment module. After reading 8 files its context is filling up and answers are degrading — it has hit the single-context-window ceiling. But those 8 files gave it the module's shape (there is a PaymentProcessor, a RefundHandler, a charge/capture flow, a tests/ dir). That architectural overview is the asset — keep it. Now the main agent becomes a coordinator: it stays put holding the overview and spawns scoped subagents, each with its own fresh context, to do the heavy reading.

The trick: each subagent reads thousands of tokens of source, but that reading happens in its own isolated context and never touches the main context. Each returns only a distilled answer. So the main window stays small (overview + three short summaries) while you effectively cover ~30 more files. A subagent is a context firewall — that, not speed, is the core reason subagents exist.

Why the tempting alternatives fail here: clearing context (summary-then-/clear, or /clear-then-re-read) deletes the overview you built and makes you rebuild it; Grep for function names can't find an untested branch — a name is not coverage, you must read the path.

The rule: localize first, fan out second.

When NOT to spawn — the coordinator already has the context Subagents earn their cost only when they provide isolation (keep verbose/independent work out of the main context) or specialization. If the coordinator already holds the data and the task is straightforward — e.g. "summarize the findings you just gathered" — spawning a synthesis subagent forces it to re-ingest everything (transfer + processing + spawn latency) for a result the coordinator could produce directly. That is pure overhead. The fix is architectural: let the coordinator answer simple follow-ups itself, and reserve subagents for complex analysis. Note that prompt caching the repeated context only makes the needless spawn cheaper — it does not remove the spawn; removing it beats discounting it. The decision axis: does this work fit the actor's current context? Fits → answer directly. Exceeds it, or needs an isolated/specialized context → delegate.
Decomposing an unknown-cause investigation — adaptive, not pre-planned When the task is to find the root cause of an unknown failure (an intermittent 500 error, an unfamiliar bug) in a large codebase, the decomposition must be adaptive: read something, let what you find pick the next step, and generate investigation subtasks as the error path emerges. You cannot correctly pre-plan a route to a bug you have not found (a comprehensive up-front plan plans blind), a fixed pipeline executed regardless of findings wastes work on uninvolved layers and can skip the real path, and parallel workers across all layers are premature fan-out — you have no scoped subtasks yet, so you pay N× to search layers that are not the problem. Adaptive subtasks ≠ parallel sub-agents: follow the evidence first (that is the search), then delegate to sub-agents only once findings have localized the fault into scoped questions.

fork_session lets you create independent branches from one shared baseline. You analyze something once, then fork several sessions from that same starting point to explore different approaches in parallel, without each branch redoing the shared work.

Say it like this

"A coordinator uses the Task tool to spawn subagents, and it must have Task in its allowedTools. Subagents run in isolated context — they inherit nothing — so I pass all prior findings directly in the prompt, in a structured format that keeps source URLs attached. For real parallelism I emit several Task calls in one response. And I write prompts as goals plus quality criteria, not fixed steps, so the subagent can adapt."

4. Enforcement and handoff — when prompts are not enough

Here is the most tested idea in the whole domain. You can steer an agent two ways:

Prompt-based guidanceProgrammatic enforcement
HowSystem prompt, few-shot examples, instructionsHooks, prerequisite gates, code checks
GuaranteeProbabilistic — usually works, sometimes failsDeterministic — always works or blocks
Use whenStyle, tone, soft preferencesBusiness rules that MUST hold every time

The lesson: prompt instructions alone have a non-zero failure rate. If a rule must hold every single time — for example, verify identity before a financial action — you cannot rely on a prompt. You add a programmatic gate.

Prerequisite gate example. An agent must call get_customer (which returns a verified customer id) before it is allowed to call process_refund or lookup_order. You enforce this in code: the refund tool is blocked until a verified id exists. Now the ordering is guaranteed, not hoped for.

Tempting but wrong An agent skips the verification step 12% of the time and issues wrong refunds. The tempting fixes are "make the system prompt stronger" or "add few-shot examples." Both are still probabilistic — they lower the failure rate but never reach zero. For money, "usually" is a bug. The correct fix is a deterministic prerequisite gate that blocks the refund until identity is verified.

The other direction — when a hook is the wrong answer. The table above is only half the rule. A deterministic gate needs a condition you can write down completely. If you cannot enumerate the condition, code does not become more reliable than the model — it becomes reliably wrong on every case you failed to list.

The condition is…ExamplePut the decision in…
A bright line — a value you can compare, a tool you can nameRefund amount over $500; identity must be verified firstCode (hook / prerequisite gate)
Open-ended judgment — about intent, meaning, or progress"Does this customer actually need a human?"The model (clear criteria in the prompt)

Escalation triggers are judgment calls. Good criteria are written in plain language and cover the long tail: escalate when the customer asks for a human, when the issue needs a policy exception, or when the agent cannot make meaningful progress. Three weaker mechanisms show up as distractors:

  • A retry counter ("escalate after 3 failed tool calls") measures effort spent, not need. It fires too late for a customer who asked for a human on turn one, and too early when the three failures were just a flaky API.
  • Sentiment analysis is a proxy — it detects a symptom that often accompanies the condition. It misses the calm customer who needs a policy exception, and over-fires on people who write in capitals.
  • A rules engine mapping issue type to escalation only covers what you enumerated. Support work is mostly the cases you did not enumerate.
Tempting but wrong Do not confuse the trigger ("when do we escalate?") with the payload ("what do we send the human?"). They are independent decisions. A retry counter is sometimes defended as "the failures give the human more context" — but a failed tool call only tells the human that your tool broke, and you can build a full structured handoff at any escalation moment without burning three failures first.

Structured handoff to humans. When an agent escalates to a person, that person did not read the whole transcript. So the agent must hand off a structured summary: customer id, root cause, refund amount, recommended action. Do not dump the raw chat log. Give the human the decision-ready facts.

For a request with several concerns in it, decompose it into distinct items, investigate each in parallel with shared context, then synthesize one unified resolution — instead of answering only the first thing the customer mentioned.

5. Hooks — intercepting tool calls

A hook is code that runs automatically at a point in the loop. The one to know is PostToolUse: it runs after a tool returns, and it can transform the tool result before the model reads it.

Main use: data normalization. Different tools (or different MCP servers) return dates in different shapes — Unix timestamps, ISO 8601 strings, numeric status codes. A PostToolUse hook rewrites them all into one format, so the model always sees consistent data.

// PostToolUse hook: normalize any timestamp field to ISO 8601
// runs AFTER the tool returns, BEFORE Claude reads the result
function postToolUse(result) {
  if (result.timestamp)              // Unix seconds -> ISO
    result.timestamp = new Date(result.timestamp * 1000).toISOString();
  return result;
}

The hook that intercepts an outgoing tool call — before it runs — is PreToolUse. That is the one you use to block something: refuse any refund over $500 and redirect it to human escalation. This is the same deterministic idea from section 4, applied at the hook layer. Knowing which of the two to name is a common exam discriminator, and the rule is simply which side of the tool call you sit on:

HookRunsCan it stop the call?Use it for
PreToolUseBefore the tool runsYes — it can block or rewrite the inputGates and guardrails: block the refund, deny the write, require verification first
PostToolUseAfter the tool returns, before Claude reads the resultNo — the call already happenedShaping what the model sees: normalize dates, strip noise, redact secrets

The memory hook: "Pre" is the bouncer at the door — it can turn you away. "Post" is the translator inside — the guest is already in, it only cleans up what gets said. So a question that says "prevent", "block", or "must not happen" wants PreToolUse. A question that says "the model is confused by inconsistent data" wants PostToolUse.

Where hooks actually live — two different surfaces The example above is written as a plain function, which is the shape hooks take in the Agent SDK: an in-process callback you pass in your options. In Claude Code a hook is not a function at all — it is an external command declared in settings.json, matched to a tool by name, that receives the event as JSON on standard input: 
"hooks": {
  "PreToolUse": [
    { "matcher": "Bash",
      "hooks": [ { "type": "command", "command": "node ./scripts/check-bash.js" } ] }
  ]
}
Same idea — deterministic code at a fixed point in the loop — but a different mechanism, and the exam can ask about either. The Claude Code event set is wider than the two above: it also includes PostToolUseFailure, PreCompact, SessionStart, SessionEnd, and Stop. Because a hook is an ordinary command, its exit status is the deterministic signal — a non-zero exit from a PreToolUse hook is what actually blocks the call.
The rule of thumb Hooks give a deterministic guarantee. Prompt instructions are probabilistic. When a business rule must be guaranteed, choose the hook. When you just want soft guidance, a prompt is fine.

6. Task decomposition — fixed vs adaptive

How you split the work depends on whether the shape of the work is known in advance.

Fixed sequential pipelineDynamic adaptive decomposition
Also calledPrompt chainingOpen-ended investigation
Use whenThe steps are predictableThe steps depend on what you find
ExampleReview each file, then one cross-file passAdd tests to a legacy codebase: map structure, find high-impact areas, build a plan that adapts as you learn

Large code reviews: split the work into a per-file local-analysis pass for each file, plus a separate cross-file integration pass. This avoids "attention dilution" — one giant prompt trying to hold every file at once loses detail. Small focused passes catch more, and the extra integration pass catches the bugs that only appear between files.

7. Session state — resume, fork, or restart

Three ways to continue work, and the exam cares about picking the right one.

  • Named resumption — --resume <session-name> continues a specific earlier conversation, with its history intact. This is the CLI continuation you pick when you want one particular past session out of many and you know its name (Claude Code lets you name sessions with -n <name> or /rename).
    FlagTargetsUse when
    --continue (-c)The most recent session in this repoYou just want to pick up where you last left off — no session in mind
    --resume [value] (-r)A specific session. The value is a session ID, or a search term that filters the interactive picker; with no value you get the full pickerYou want a particular older session — even if it is not the most recent
    --session-id <uuid>A specific session by exact UUIDCorrect but cumbersome — you must hunt the UUID in the transcript files
    --fork-sessionNothing on its own — it modifies --resume or --continueYou want to branch instead of continue: same starting context, brand-new session ID, original left untouched
    The classic trap: if you have done other work since (e.g. worked on three other codebases), --continue resumes the wrong session, because "most recent" is no longer the one you want. Reach for --resume <name>. And remember: resuming reloads the old saved context — it does not teach the agent what changed on disk since; if files have changed, that old context may be stale (see the stale-context note below).
  • fork_session — branch from a shared baseline to explore divergent approaches side by side (same idea as section 3). It is always paired with a resume, on every surface: --fork-session alongside --resume on the CLI, resume: sessionId, forkSession: true in the TypeScript SDK, resume=session_id, fork_session=True in Python. The original session is left untouched, the fork gets its own new session ID, and you can create multiple forks from the same parent. The tell: fork is not a third way to continue — it is resume plus "don't write back to the original".
  • Fresh session with a summary — start new, and hand in a clean structured summary of the current state.

Resume vs. fork — the context-contamination trap

Everything in a session's context window is visible to the model at every step. So if you explore two mutually-exclusive approaches in one resumed thread (approach A, then approach B in the same conversation), the model's reasoning and proposed code for approach A is still sitting in context while it works on approach B. It anchors on what it already said — reusing A's assumptions, echoing A's design — so B is no longer an independent take. This is context contamination: the two explorations bleed into each other.

Forking removes the contamination. Each fork starts from the identical baseline but runs in its own isolated context, so neither branch can see the other's reasoning. That is why, for a fair "compare A vs. B from a shared starting point" task, fork beats resume-sequentially, which in turn beats any option that rebuilds yesterday's context by hand.

Keyword tells: "explore both / each approach", "compare", "in parallel" from a shared baseline → fork. "Continue / keep going" on one line of work → resume.

Two judgment calls that show up as questions:

  • Resuming after code changed? Tell the agent which files changed, so it re-analyzes just those (targeted). Do not force it to re-explore the whole project from scratch.
  • Resume or restart? If the old session holds stale tool results (old file contents, old API responses), a fresh session with a current structured summary is more reliable than resuming on top of outdated data. Stale context quietly poisons the reasoning.
Tempting but wrong "Always resume the old session — it has the most context." Not if that context is stale. Resuming on top of outdated tool results (files that changed, expired data) makes the agent reason from wrong facts. A fresh session seeded with an accurate summary beats a resumed session full of stale results.
