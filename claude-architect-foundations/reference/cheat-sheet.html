CCA-F Pattern Cheat-Sheet

The ~12 recurring principles the exam recycles. Each is "when you see this → pick this, and here's the trap." Read it as: the answer is almost always the one that fixes the cause at the right layer, preserves information, and doesn't over-engineer.

How to use this Match the scenario to a family below, then apply the rule. If two options both "work", pick the one that (1) fixes the root cause at the right layer, (2) preserves information rather than discarding/averaging it, and (3) is the simplest thing that works (no vector DB / queue / classifier / routing layer unless truly needed).

1 · Sessions & continuity

Reuse yesterday's expensive context; never rebuild by hand. The move depends on why you're continuing.

When you see…Answer
Compare 2+ approaches from one baselinefork (independent branches, no cross-contamination) Q1,Q32
Continue one specific past session out of many, by name--resume <name> (not --continue = most recent) Q10
Old context is pervasively stale (data changed, poisoning replies)Fresh session + structured summary + fresh tool calls Q38
Small, specific stale delta (2 files/functions changed)Resume + targeted delta ("these changed") Q46,Q53

TRAP Sequential exploration of A then B in one thread = context contamination. Manual re-typing of a summary = lossy.

2 · Schema design (structured extraction)

When the model is inconsistent, first ask: can the schema even represent the truth? Fix the data model, not the behavior.

ProblemFix
Model invents values for absent fieldsMake field nullable + instruct "return null if not stated" Q7
Same field has multiple/versioned values (amendments)List of values + source location + effective date Q8
Enum can't cover an open-ended, growing setenum + "other" + free-text detail field Q51
Values don't reconcile (totals, OCR)Capture calculated vs stated, flag mismatch for human Q21
Messy input formats (icons, "$12" vs 12.00)Schema + normalization rules in the prompt, one pass (not post-processing) Q37

TRAP strict:true guarantees shape, not meaning. Required fields force invention. Post-processing code is brittle & semantically blind.

3 · Preserve & surface — never collapse or fabricate

Keep the claim→source mapping and any uncertainty as structured data, outside the prose, end-to-end. Surface conflicts; don't invent a clean answer.

When you see…Answer
Citations lost during synthesisStructured claim-source mappings, preserved & merged (not reconstructed) Q6,Q26,Q56
Conflicting numbers from two sourcesAnnotate both + sources; add dates (a trend ≠ a contradiction) Q28,Q58
Tool succeeded partially / permanently failedDeliver partial value + be honest; never claim success that didn't happen Q21,Q24

TRAP Averaging different-methodology estimates, discarding older data, "most-recent-wins", or reconstructing via similarity all destroy the nuance.

4 · Few-shot: present-vs-absent diagnostic

Before choosing few-shot, ask: is the needed info present-but-ambiguous or absent?

Present but inconsistently interpreted/formattedFew-shot examples teach the pattern (split rules, formats, recall) Q18,Q29,Q37,Q55
Absent (tool emits no distinguishing info)Fix at the source — emit the data; few-shot can't conjure it Q25

TRAP "Add few-shot" is right for interpretation of present data, wrong when the info was never produced. Retry fixes rendering, not knowledge gaps Q11.

5 · Tool design & selection

The model picks tools by reading descriptions — descriptions ARE the interface. Match the fix to the cause.

Right tool ignored (thin description)Enrich the description (when to use, I/O) Q15,Q48
Overlapping / misleading nameRename to be specific
One tool doing many jobs (fuzzy output)Split into purpose-specific tools w/ I/O contracts Q50
Tool error handlingisError:true + message; add errorCategory + isRetryable + customer msg Q25,Q42,Q49
Must run tool X before others (ordering)tool_choice:{type:tool,name:X} on first turn, then release to auto Q47

TRAP Routing layer / removing tools / few-shot-in-prompt are worse than fixing the description. "any" forces a tool, not the tool. Don't pin a tool on every call. Empty result ≠ error.

6 · Orchestration & subagents

Subagents are context-isolated; the coordinator is the hub that forwards via the prompt.

Subagent got "no findings"Coordinator must forward output in the prompt (isolation) Q22,Q45
Coordinator reasons but never executes, no errorsTask missing from allowedTools Q52
Parallelize but stay observable/debuggableFlat, coordinator-managed fan-out (not queues/recursion/nested spawn) Q35
Resume a crashed pipelinePer-agent structured manifests → coordinator loads & injects Q39
Coordinator already has the context (simple summary)Answer directly — don't spawn (caching a needless spawn ≠ fix) Q36

7 · Decomposition & fan-out timing

Localize first, fan out second. Adapt to the unknown; don't pre-plan a route to a bug you haven't found.

Unknown subject in a big codebaseLocalize (Grep entry points, follow imports) — don't fan out yet Q27
Work exceeds one context, you have scoped questionsFan out scoped subagents; main keeps the overview Q30
Debug an unknown/intermittent failureAdaptive subtasks, follow the evidence (not plan/pipeline/blind fan-out) Q41
Understand a subsystem's architectureTop-down from the base class/interface, then trace specifics Q57
Find all callers before deleting a functionEnumerate all exposed names, Grep each (not import-tracing) Q2

8 · Context management (long/multi-topic sessions)

Agent gets inconsistent / forgets earlier findingsScratchpad file (re-read on demand); not bigger window / auto-clear / pre-summaries Q4
Verbose tool outputs (40+ fields) crowd contextPrune to relevant fields (keeps precision; not prose summary / vector DB) Q20
Long, multi-topic chat near the limitSummarize resolved topics, keep active thread verbatim Q40
Limited human review capacity, hidden errorsField-level confidence + calibrate → route low-confidence to humans Q17
Deciding what to auto-approveBreak down accuracy by segment — aggregate hides weak segments Q12

9 · Customer-support judgment

Frustrated customer, simple fix, you have contextAcknowledge + offer to complete or escalate (preserve choice) Q14
Frustrated, asks for human, you have no contextAcknowledge + one targeted question → warm escalate (not cold) Q44
Need a human (auth limit / policy exception)Structured handoff: who · what · why · recommended action Q19,Q31
When to escalateJudgment criteria (explicit request, policy gap, no progress) — not sentiment/retry-count/rules-engine Q33

RULE Honor the feeling + agency + capability. Sentiment ≠ complexity. Never exceed your authorization "and hope".

10 · Cost, latency & batch

Mixed workload: bulk + latency-sensitiveBatch the non-urgent bulk (50% off, ≤24h), real-time the SLA items Q13
Pick batch cadence for an SLAinterval + 24h ≤ SLA − margin (exactly-at-SLA fails 99.9%) Q54
context_length_exceeded on some docsChunk oversized input, merge; reprocess only failures via custom_id Q59
Batch results handlingMatch by custom_id (any order); resubmit only failed items with a fix

TRAP max_tokens = output cap, not the context window. Bigger model just raises the ceiling; chunking removes it.

11 · Agentic loop fundamentals

How the loop picks the next toolAppend tool_result → model reasons over context (no router/tree/plan) Q43
Varying query complexity, evolving distributionCoordinator reasons per query at runtime (not patterns/classifier) Q3
Delegating to a subagentGive goals + quality criteria, not rigid procedural steps Q9
Agent "forgets" earlier turnsAPI is stateless → pass the full messages array each request Q60

12 · File-editing built-ins

Edit can't find a unique match (repetitive file)Read → modify in memory → Write full file (no match needed) Q5

TRAP Long old_string = brittle; replace_all = corrupts; Bash append = wrong location. Check options against all constraints.

Two meta-habits that catch most misses

1. Don't over-engineer. Vector DBs, message queues, trained classifiers, routing layers, and second verification models are usually the wrong "sophisticated" answer — prefer the simplest fix at the source.
2. Name the precise reason. A right answer for a fuzzy reason will pick the wrong option elsewhere. Say which specific failure mode each distractor has.

Weakest domains to drill first: Extraction pipelines (schema design, few-shot, chunking) and Code exploration (localize-first, fork/resume, top-down understanding). Full explanations live in Lessons 1–4.
