Paging & versioning

Collections grow and clients multiply. Two ideas, one fear: things you don't control, attached to your API.

The win: after ~35 minutes you never ship an unbounded collection endpoint again, you can choose offset vs cursor paging with reasons, and you can evolve a live API without breaking clients you cannot see.

1. The time bomb: an unbounded collection

GET /orders returns "all orders." On launch day that is 50 rows — fine. Two years later it is 4 million rows, and that one endpoint now builds a 2 GB response, holds a database connection for a minute, and crashes the mobile app that tries to parse it. Nothing "broke" — the data just grew.

So the rule is absolute: every collection endpoint is bounded from day one. The only question is how you slice. There are two ways.

2. Slice 1 — offset paging

GET /orders?limit=20&offset=40        → SQL: ... LIMIT 20 OFFSET 40

"Skip 40 rows, give me the next 20." Dead simple, maps straight onto SQL, and the client can jump to any page number. Two real flaws:

  • The window drifts. Offset counts positions in whatever the list is right now. If rows are inserted or deleted while a user pages through, the window shifts under them — items repeat or silently disappear.
  • Deep pages are slow. OFFSET 100000 does not teleport: the database must walk and throw away 100,000 rows to find row 100,001. The cost grows with depth — page 5,000 can take seconds while page 1 is instant.

3. Slice 2 — cursor (keyset) paging

GET /orders?limit=20&after=eyJpZCI6OTA1fQ   → SQL: WHERE (created_at, id) < (…) ORDER BY created_at DESC, id DESC LIMIT 20

Instead of a position number, the server returns an opaque cursor with each page — a bookmark that encodes the last item you saw (its sort key, for example created_at + id). The next request says: "the 20 that come after this bookmark."

  • No drift. The bookmark points at an item, not a position. Inserts above it cannot shift your window — you continue exactly after what you saw.
  • No deep-page penalty. The database jumps to the bookmark through an index instead of counting rows — as fast on page 5,000 as on page 1. (The machinery behind that jump is the B-tree — a ★ leaf waiting in Domain 4.)
  • The trade: no "jump to page 7", and you need a stable, unique sort key (that is why the cursor carries id as a tie-breaker, not just the timestamp).
Rule of thumb

Admin table with page numbers and modest data → offset is fine. Infinite scroll, feeds, anything big or hot → cursor. This is why the big public APIs — GitHub, Stripe, Slack — are cursor-based.

4. Versioning: an API is a promise to strangers

The moment one stranger's code calls your API, every field name and behavior becomes a promise you cannot take back. You cannot see your callers. You cannot fix their code. Anything you change breaks someone, silently. Versioning is how you evolve anyway — but the best version is the one you never ship:

Safe forever (additive)Breaks someone (needs a version)
add a new optional response fieldrename or remove a field
add a new endpointchange a field's type or meaning
add an optional query parametermake an optional thing required

Teams that stay in the left column ship for years on v1. The matching client-side habit is called the tolerant reader: ignore fields you do not recognize, never depend on field order. Both sides bend so neither breaks.

5. When you must break: three places to put the version

StyleLooks likeTrade-off
URL GET /v2/orders Visible, easy to test in a browser, cache-friendly. "Impure" (the version is not part of the resource's identity) — nobody cares; it is the most common choice.
Header Accept: application/vnd.myapi.v2+json Clean URLs; but invisible, harder to test, easy to forget in one client out of five.
Date pin Stripe-Version: 2024-06-20 Each account pins the behavior-date it was built against; the server keeps translation layers from every old date. Best client experience, most server work.

Rule of thumb: stay additive on /v1 for as long as humanly possible; take URL versioning when you truly must break; admire Stripe's date-pinning from a distance until you have Stripe's problems.

Drill — the duplicate feed

Users report that the activity feed sometimes shows the same entry twice while they scroll. The feed is busy — new entries arrive every few seconds. The endpoint is GET /feed?limit=20&offset=N.

Diagnose the mechanism (why exactly does a duplicate appear?), then give the fix — including what the new request and response look like, and which column(s) the cursor must encode. Answer out loud before flipping the recall card.

6. Prove it

Lock it in — the blank-page rule Close this leaf in the tree tracker when you can, from a blank page: name offset paging's two flaws with their mechanisms, sketch a cursor request/response, list three additive vs three breaking changes, and place the three versioning styles.
Primary sources Markus Winand — "No Offset" (10 min) is the canonical case for keyset paging, with the SQL. Then Stripe — APIs as infrastructure: API versioning (15 min): how date-pinning works in production and why they chose it.

Anything unclear — how the cursor is encoded, why the id tie-breaker matters, when a breaking change is truly unavoidable? Ask your teacher — open a session and say /teach.

Remember this
  • Bound every collection endpoint from day one — unbounded lists fail by growth, not by bugs.
  • Offset paging counts positions: simple + page jumps, but the window drifts under inserts and deep offsets scan-and-discard.
  • Cursor paging bookmarks an item: no drift, index-fast at any depth; trade = no page jumps, needs a stable sort key + id tie-breaker.
  • An API field, once published, is a promise to code you cannot see.
  • Evolve additively (new optional fields, new endpoints) and you may never need v2; clients read tolerantly.
  • Must break? URL version is the pragmatic default; header is purist; date-pin is Stripe-grade.

If you remember one thing: offset says "give me rows 41–60 of whatever the list is now"; a cursor says "give me what comes after this bookmark" — and only the bookmark survives a changing list.
