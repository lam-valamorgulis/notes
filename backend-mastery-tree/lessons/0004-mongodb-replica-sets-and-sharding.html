MongoDB: replica sets & sharding

One database becomes many machines — first so it survives, then so it scales. Two different problems, two different machines.

The win: after ~40 minutes you can answer the two senior MongoDB questions cold: "an acknowledged write disappeared after a failover — how?" and "why is a timestamp a terrible shard key?" — plus the mechanism underneath each: elections by majority, and routing by key.

1. First, the unit: the document

Everything in MongoDB follows from one design decision: the document is both the read unit and the atomic unit. In SQL you model the data's shape (normalize, then join at read time). In MongoDB you model the application's queries — store together what is read together, so the hot path is one read instead of a 4-way join.

Three hard limits shape the choice: a document caps at 16 MiB; an unbounded embedded array is a slow-motion bug (every append rewrites a growing document, until the cap kills it in production); and a write to one document is always atomic — even across 20 fields — while a write to two documents never is, unless you pay for a multi-document transaction. Embedding buys atomicity for free; referencing spends it.

Feynman version — the pre-packed kit

SQL is a warehouse: every part in its own labeled bin, assembled at pickup time. MongoDB is a pre-packed kit: everything one job needs, in one box. Kits are fast to grab — but a kit that must hold "every part we might ever need" overflows the box. That overflow is your unbounded array.

The "transactions everywhere" smell MongoDB has real multi-document ACID transactions (since 4.0, sharded since 4.2, 60-second lifetime by default). But the docs themselves say transactions "should not be a replacement for effective schema design." If most operations need one, the document boundaries were drawn wrong — you rebuilt a relational schema inside a document store and now pay document-store prices for relational semantics.

2. Replica sets — copies, for survival

A replica set is a group of servers holding identical copies of the data. Exactly one member is the primary — it takes all writes. The others are secondaries: they copy the primary's changes and can take over if it dies. This is a high-availability machine, not a scaling machine — all writes still land on one node.

The copying mechanism is the oplog: a capped (fixed-size, ring-buffer-like) collection on every member, recording every change in idempotent form — an $inc is logged as "set field to the resulting value", so replaying an entry twice is harmless (lesson 0002's set-vs-add lens, living inside the database engine). Secondaries tail this log and apply it. Default size: 5% of free disk, clamped between 990 MB and 50 GB.

Feynman version — the newsroom

One editor-in-chief (primary) approves every story. Deputy editors (secondaries) keep their own complete copy of the paper by reading the chief's change log (oplog). If the chief collapses, the deputies vote and one takes over. The paper survives — but for a few seconds, nobody can approve new stories. And a deputy who was on holiday longer than the change log is long must re-copy the whole archive from scratch (initial sync): the oplog's length is the catch-up budget.

3. Elections — and the write that vanished

Members heartbeat each other every 2 seconds. When secondaries haven't heard from the primary for electionTimeoutMillis (default 10 s), they call an election — a Raft-style vote with terms and a simple rule: a candidate needs a majority of voting members, and voters refuse candidates whose copy of the data is behind their own. Median failover with defaults: ≤ 12 seconds, during which no writes are accepted anywhere.

The majority rule is also the split-brain defense: a primary that can only reach a minority of voters steps down on its own. Better no editor than two editors. And it explains the famous "why 3 nodes minimum": with 2 nodes, majority = 2, so losing either node means no primary — two nodes give worse write availability than one. With 3, any single failure is survivable.

Now the interview classic. Write concern is how many members must acknowledge a write before the driver returns "success":

Write concernMeaningSurvives failover?
w: 0fire-and-forget, no acknowledgment❌ no promise at all
w: 1the primary has it❌ can be rolled back
w: "majority"a majority have it, journaled on disk✅ never rolled back
Trap — acknowledged is not durable A w:1 write is acknowledged the moment the primary alone has it. If the primary crashes before any secondary copies that write, a new primary is elected without it. When the old primary rejoins, it sees history has moved on — and rolls the write back, dumping it to a file on disk. The client was told "success"; the database no longer contains the data. This is not a bug — it is exactly what w:1 promises. Anything you can't lose goes w:"majority" (the server default since MongoDB 5.0).

4. The read side: two dials, not one

Reads have two independent settings, and confusing them is a favorite interview probe:

  • Read preference picks the node: primary (default), secondary, nearest… A secondary read can be stale — replication is asynchronous, lag is usually milliseconds but unbounded under load.
  • Read concern picks the quality: local (default — may return data that is later rolled back!), majority (only majority-committed data, never rolled back), linearizable (primary double-checks it is still primary before answering — one document, one extra round trip).

So secondary + majority is a valid combination (a stale but durable read), and the default combination — primary + local — can return data that later vanishes. For "read my own write" across nodes, the tool is a causal consistency session: the driver threads a cluster timestamp through your operations, and a lagging secondary waits until it has caught up to your write before answering.

Pointer back up the tree "Point reads at secondaries to scale reads" is mostly a trap: secondaries already replay the full write load, and if your read capacity depends on them, you have silently spent your failover headroom. Read scaling is sharding's job. Secondary reads are for geography (nearest) and isolation (analytics on a hidden member).

5. Retryable writes — lesson 0002, built into the driver

During those ~10 seconds of election, what does your application see? In-flight writes fail with an ambiguous network error — the same ambiguity as lesson 0002: did it land or not? MongoDB's answer is the same answer too: an idempotency key, built in. Every single-document write carries a session ID + a counter (txnNumber). The driver retries once against the new primary; the new primary checks the ID against replicated history — if the first attempt already committed, it does not re-execute, it returns the stored result. Exactly-once effect, transparent to your code, on by default in all modern drivers.

6. Sharding — slices, for capacity

A replica set hits two walls that copies cannot fix: RAM (when the working set — hot data + indexes — outgrows memory, every read risks a disk fetch and latency falls off a cliff) and write throughput (all writes hit one primary, always). Sharding splits the data itself across many replica sets (shards), each owning a slice. Three moving parts:

  • Shards — each a full replica set, owning a range of the data.
  • Config servers — a replica set holding the map: which shard owns which range. The balancer runs on its primary, moving ranges (default size 128 MB) when shards differ by ≥ 3 range-sizes (~384 MB). Back these up like data — they hold the only map.
  • mongos — a stateless router your app talks to. It caches the map and forwards each query to the right shard(s).

Order of operations in real life: fix schema and indexes first, scale vertically second, shard third — every shard multiplies the operational surface.

7. The shard key — the highest-stakes schema decision

The shard key is the field whose values decide where every document lives and how every query routes. Three properties decide whether a key is good:

  1. Cardinality — many distinct values (a country key caps you at ~200 slices, some giant).
  2. Frequency — evenly used values (if 30% of documents share one value, that value is an unsplittable jumbo range pinned to one shard).
  3. Monotonicity — the killer. If the key only ever grows (timestamp, auto-increment, ObjectId — which is timestamp-prefixed), every insert lands in the last range, on one shard. You bought a 10-shard cluster with the write throughput of 1 shard.

The choice is a query-mix decision. Ranged keys keep order: range queries (ts between…) route to few shards — but monotonic/skewed keys hotspot. Hashed keys spread writes perfectly — but only equality queries route; ranges broadcast. The senior answer is often a compound key: {tenant_id: 1, ts: 1} — a coarse routing field first (targets real queries), the fine/monotonic field second (splits big tenants into multiple ranges).

Trap — the default _id "We'll just shard on _id." The default ObjectId begins with a timestamp — it is monotonic — so this is precisely the hot-shard trap with a different name. Hashed _id fixes the hotspot and sacrifices range routing. Interviewers plant this on purpose.

And why is this the highest-stakes decision? Because changing it means re-placing every document while writes continue. The escalation ladder: refineCollectionShardKey (4.4 — add suffix fields; can't fix a wrong first field), reshardCollection (5.0 — full live resharding: needs ~2× the collection's storage free, days of background work on big collections, and a ~2-second write-block at cutover). Possible now — but a project, not a command. Choose right the first time.

8. Targeted vs scatter-gather

If a query's filter contains the shard key (or a prefix of a compound key), mongos routes it to only the owning shard(s) — targeted. If not, mongos must broadcast to every shard and merge — scatter-gather. Its latency is the slowest shard's latency, and its total cost grows with shard count — so a scatter-gather-heavy workload gets worse as you scale out.

Trap — "a secondary index will fix it" Each shard indexes only its own data; there is no global secondary index. A non-shard-key query still visits every shard — the index only makes each shard's local search fast. The only routing field is the shard key. This is why the key is chosen from the real query filters, not from the data model diagram.
Drill — the multi-tenant order system

You are sharding an orders collection for a B2B SaaS: 2,000 tenants, a few of them huge; hot queries are "orders for tenant X in a date range" and "order by id". A teammate proposes sharding on {created_at: 1}.

What breaks with that key? Propose a better one and defend it against all three properties (cardinality, frequency, monotonicity) — and say what happens to the giant tenants. Answer out loud before the quiz.

9. Prove it

Lock it in — the blank-page rule Close the replica sets & elections and sharding & shard keys leaves in the tree tracker when you can, from a blank page: sketch a 3-node failover timeline with the w:1 rollback, explain w:majority via the majority rule, and design a compound shard key while naming the hot-shard trap.

Anything unclear — why the rollback isn't a bug, how mongos knows the map, what a jumbo chunk is? Ask your teacher — open a session and say /teach.

Remember this
  • Replication is for survival, sharding is for capacity. Replicas never add write throughput; shards never add durability.
  • The document is the read unit and the atomic unit — model for access patterns; unbounded arrays are the classic modeling bug.
  • Elections need a majority of voters — that's why 3 nodes minimum, why a minority primary steps down, and why 2 nodes are worse than 1.
  • w:1 writes can be rolled back after failover; w:"majority" writes never are. "Acknowledged" is only as strong as the concern you asked for.
  • Read preference picks the node; read concern picks the quality. The defaults (primary + local) can read data that later vanishes.
  • Shard keys live or die on cardinality, frequency, monotonicity — timestamps and ObjectId hotspot; hashed keys spread writes but broadcast range queries; compound keys are the senior answer.
  • No shard key in the filter → scatter-gather: every shard, slowest one sets the latency, worse as you grow.

If you remember one thing: majorities decide what survives a failover; the shard key decides where every byte lives — both are chosen up front, and both are brutal to change later.
