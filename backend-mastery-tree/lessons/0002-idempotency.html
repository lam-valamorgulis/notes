Domain 3 · API design · REST · Lesson 0002

Idempotency

The network will lie to you. This is the property that makes the lie harmless.

The win: after ~30 minutes you can answer any retry question cold — which operations are safe to re-send, why, and how to manufacture that safety for the one verb that doesn't have it (POST — the one that moves money).

1. The problem: networks fail ambiguously

Your client sends a request. It waits… timeout. Now answer this: did the server (a) never receive the request, or (b) receive it, process it fully, and the response got lost on the way back?

You cannot know. This is not a gap in your code — it is mathematically unsolvable over an unreliable channel (computer science calls it the Two Generals problem). No retry policy, no clever handshake, removes the ambiguity.

So backend engineering makes a judo move. If you cannot know whether the first attempt landed, stop trying to know — instead, make repeating harmless. Then the answer stops mattering: just send it again.

2. The definition, and the lens that explains everything

An operation is idempotent when doing it N times leaves the server in the same state as doing it once: 

f(f(x)) = f(x)
Feynman version — the elevator button

Pressing the elevator call button five times does what pressing it once does. Now compare two light switches: one labeled "set to ON" — flip it 10 times, the light is on. One labeled "toggle" — flip it 10 times and the result depends on how many times. Same finger, same switch — the difference is that one sets an absolute state and the other applies a relative change.

That is the deep pattern, and it explains every case in this lesson: "set X to 5" is idempotent; "add 1 to X" is not. Set vs add. Keep this lens.

3. The verb table, seen through the set-vs-add lens

VerbIdempotent?Why, via the lens
GET✅changes nothing at all
PUT✅"make the resource exactly this" — absolute
DELETE✅"make it gone" — absolute (gone twice = gone)
POST❌"add one to the collection" — relative
PATCH⚠️ depends{"email":"a@b.c"} sets → idempotent. "Append item to list" adds → not

This is why PATCH got the "not guaranteed" footnote in lesson 0001: idempotency is not a property of the word PATCH — it is a property of what your patch does.

Trap — state, not status codes Send DELETE /addresses/9 twice: the first returns 204 No Content, the second returns 404 Not Found. Different responses — still idempotent. The end state is identical (the resource is gone). Idempotency is a promise about server state, never about what the client sees. Interviewers love this edge.

4. The hard case: POST, and how the industry fixed it

The most money-critical operation in most systems — create the payment, create the order — is exactly the one verb with no retry safety. Timeout during checkout leaves two terrible options: retry and risk charging twice, or give up and risk losing the sale.

The fix is the idempotency key: the client generates a unique random token (a UUID) per logical operation — not per attempt — and sends it as a header: 

POST /payments
Idempotency-Key: 7f3d9a2e-4c1b-4e8a-9f60-2b8d1c5a7e33
Content-Type: application/json

{ "amount": 4999, "currency": "usd", "source": "card_..." }

The server keeps a table of key → stored response. First time it sees the key: process normally, store the result. Any repeat of the same key: do not re-execute — replay the stored response. The retry becomes indistinguishable from the original.

Stripe's payment API made this pattern famous, and it is now the standard for anything involving money. Notice what happened conceptually: the client reframed the operation from add to ensure-exists — the same set-vs-add lens from section 2.

Pointer down the tree The server side of this pattern — where keys are stored, when they expire, what happens when the retry arrives while the first request is still running — is its own leaf: idempotency keys, Domain 6 · Reliability. Here you own the client-side mechanism and the why.
Drill — the checkout timeout

Your checkout calls POST /payments. Five seconds pass — timeout. The user is staring at a spinner. Product wants you to "just retry automatically."

What exactly is unsafe about a blind retry? What two things must change (one on the client, one on the server) to make automatic retry correct? Answer out loud before flipping the recall cards.

Anything unclear — why the two status codes don't break idempotency, who generates the key, what happens if two retries race? Ask your teacher — open a session and say /teach.

Remember this
  • A timeout is ambiguous forever: you cannot distinguish "never arrived" from "response lost". Design for it.
  • Idempotent = N calls end in the same state as 1 call: f(f(x)) = f(x).
  • The lens: "set X to 5" is idempotent, "add 1 to X" is not — absolute vs relative.
  • GET, PUT, DELETE: idempotent by contract. POST: never. PATCH: depends on what the patch does.
  • Idempotency is about end state, not status codes — double DELETE returning 204 then 404 is still idempotent.
  • Idempotency key: one UUID per logical operation (not per attempt); server stores key → response and replays on repeats.

If you remember one thing: you can't stop the network from lying — you can only make the lie harmless, by turning "add" into "ensure-exists."
