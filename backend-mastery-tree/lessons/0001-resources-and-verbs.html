Domain 3 · API design · REST · Lesson 0001

Resources & verbs

Freeze the verbs. Let the nouns grow. Everything REST buys you comes from this one trade.

The win: after ~30 minutes you can look at any API endpoint and judge it — REST or RPC-in-disguise — and explain the mechanical cost of the wrong choice: what caches, browsers, and load balancers can no longer do for you.

1. The problem: every RPC API is a private language

Before REST, each API invented its own vocabulary. One team wrote getUser, another wrote fetchAccount, a third wrote user_load. Every name was made up, so every API had to be memorized. That is annoying for humans — but the real damage is for machines in the middle.

A cache, a proxy, or a load balancer sitting between the client and the server sees a call like POST /doStuff and knows nothing. Can it store the answer and reuse it? Can it safely send the request again after a timeout? No idea. Every call is an opaque mystery box, so the middle-machines must do the only safe thing: pass everything through, every time, and never retry.

2. The move: frozen verbs, growing nouns

Roy Fielding's 2000 idea was a compression trick. HTTP already ships with a tiny, fixed set of verbs whose meanings are standardized forever — GET, POST, PUT, PATCH, DELETE. So instead of inventing a new verb for every feature (getOrder, cancelOrder, refundOrder…), you model your system as nouns — resources, each with its own URL — and only ever apply the frozen verbs to them.

Feynman version — the warehouse

Every item sits on a shelf with an address (/orders/1042). The staff understand exactly five instructions: show me that shelf (GET), add a new item to this aisle (POST), replace the item on that shelf (PUT), change part of it (PATCH), empty the shelf (DELETE). You never teach the staff new words. You only add new shelves. That is why any robot — a cache, a browser, a CDN — can work in any warehouse on earth on day one.

3. Resources: nouns with URLs

Two URL shapes carry almost everything:

ShapeExampleMeaning
Collection/ordersthe set of all orders
Item/orders/1042one specific order

Nesting expresses ownership: /customers/88/addresses is the address collection belonging to customer 88. Keep nesting shallow — one level is usually enough.

4. The verb contract — this table is the whole leaf

Each verb carries two machine-readable promises:

  • Safe — calling it changes nothing on the server.
  • Idempotent — calling it 5 times leaves the same end state as calling it once. (This property gets its own lesson next — here you only need the column.)
VerbMeaningSafe?Idempotent?
GETread a resource✅✅
POSTcreate in a collection — the server picks the new ID❌❌
PUTfully replace the resource at a URL you name❌✅
PATCHchange part of a resource❌not guaranteed
DELETEremove the resource❌✅

5. Why this is mechanism, not style

"Use nouns, not verbs, in URLs" sounds like a style preference. It is not. The payoff is that dumb intermediaries can make smart decisions without understanding your app:

  • Caching. A cache builds its key from method + URL. In the RPC version, the product's identity ({"id": 7}) hides in the request body — which is not part of the cache key. The cache literally cannot tell two different lookups apart.
  • Retries. A load balancer sees a timed-out PUT → the contract says idempotent → safe to re-send. The same timeout on a POST? Re-sending might create a duplicate order, so it must not.
  • The browser itself. Refresh a page after a form POST and the browser shows a "resubmit?" warning dialog. That dialog exists because of this table.
Trap — the design smell A verb inside the URL path (/getOrder, /createUser, /updateCart) means you are writing RPC while wearing REST's clothes. Everything travels as POST, so to every machine in the middle, your reads and writes are indistinguishable — nothing cacheable, nothing retryable.

6. The honest grey area: actions that are not CRUD

Real systems have operations that do not map to create/read/update/delete: cancel an order, send an invoice. Two accepted answers:

  • Purist: turn the action into a noun — POST /orders/1042/cancellation. You are creating a cancellation. The verb table still applies.
  • Pragmatic: POST /orders/1042/cancel — a deliberate, documented exception. Most real APIs do this, and nobody dies.

What separates a designed API from an accreted one is not purity — it is knowing the exception is an exception, instead of making verbs-in-URLs the default habit.

Drill — judge and redesign

A team ships this API. Every endpoint is called with POST:

POST /api/getUserById       { "id": 42 }
POST /api/createUser        { "name": "…", "email": "…" }
POST /api/updateUserEmail   { "id": 42, "email": "…" }
POST /api/deleteUser        { "id": 42 }
What style is this really? Name one concrete thing generic infrastructure can no longer do. Then redesign all four as REST — method + URL each — before flipping the last recall card below.

Anything unclear — why the body is not in the cache key, when nesting URLs goes too far, whether PUT can create? Ask your teacher — open a session and say /teach.

Remember this
  • REST = frozen verbs, growing nouns: model the system as resources (URLs), apply only the five standard verbs.
  • Collection (/orders) vs item (/orders/1042) — two shapes carry almost everything.
  • Each verb makes two promises: safe (changes nothing) and idempotent (repeat = same end state).
  • Middle-machines read only the verb: GET → cacheable, PUT/DELETE → retryable, POST → hands off.
  • Caches key on method + URL — identity hidden in a POST body is invisible to every cache.
  • Verbs in the URL path = RPC in REST's clothes. Actions that aren't CRUD: make them a noun, or make a documented exception.

If you remember one thing: the verb is a promise, and infrastructure acts on the promise — not on your code.
