Kafka & event-driven architecture

A mailbox empties when read. A log doesn't. Nearly every Kafka guarantee falls out of that one difference.

The win: after ~45 minutes you can answer the two senior questions cold: "Kafka writes everything to disk — why is it fast?" and "a service must update its database AND publish an event — how do you make that reliable?" — plus the pattern names interviewers listen for: consumer groups, ISR, idempotent consumers, and the transactional outbox.

1. It is a log, not a queue

Kafka stores messages in topics, each split into partitions. A partition is an append-only log: an ordered, immutable sequence of records, each with an offset — a position number, unique within that partition. New records are only ever added at the end.

Here is the inversion that defines everything. In a classic queue (RabbitMQ, SQS), the broker tracks what each consumer received and deletes on acknowledgment — reading is destructive. In Kafka, the consumer owns its own position: it just says "give me records from offset N". The broker keeps no per-message, per-consumer state; a consumer's entire progress is one integer per partition. Data is deleted only by retention rules (age or size — default 7 days), never because someone read it.

Feynman version — the newspaper archive

Kafka is a newspaper archive with numbered pages, not a mailbox. The publisher keeps printing pages into a bound archive. Every reader keeps their own bookmark: "I'm up to page 4,812." Readers can re-read old pages (replay), a hundred readers can share one archive without extra copies (fan-out for free), and pages are shredded only when they get old — never because somebody read them.

That one picture buys the three things queues can't do: replay (rewind the offset, reprocess history after a bug), cheap fan-out (analytics, search-indexing, and billing all read the same topic independently), and slow consumers that hurt nobody (a lagging reader is just a bookmark far from the end — the broker does no extra bookkeeping).

2. Why it's fast, though everything hits disk

  • Sequential I/O only. Appends and range reads — never seeks into the middle to mutate. Sequential disk access is orders of magnitude faster than random access.
  • The OS page cache is the cache. Kafka writes to the filesystem and does not force a disk flush per message. Durability comes from replication across machines (section 5), not from one machine's disk platter.
  • Zero-copy. For plaintext connections, bytes move from page cache straight to the network socket (sendfile()), never entering the application. (TLS disables this — data must pass through user space to be encrypted. A nice interview footnote.)
  • Opaque batches, end to end. Producers ship compressed batches; the broker stores and serves them without deserializing anything. Work per record is tiny and constant.

And the deep reason, again: no per-message consumer state. A broker that tracks ack status per message per consumer (RabbitMQ) carries a data structure that grows with traffic. Kafka carries an integer.

3. Partitions: where ordering lives — and dies

Ordering is guaranteed only within one partition. Across partitions there is no order at all. This is a deliberate trade: partitions are the unit of parallelism, and total order and parallelism are fundamentally at odds.

The partition key decides placement: records with the same key go to the same partition — hash(key) % partitions. So the key is a design decision: the key names the thing whose events must stay in order. Key by order_id and every order's lifecycle (placed → paid → shipped) stays in sequence; different orders don't need mutual ordering, and shouldn't pay for it.

Feynman version — checkout lanes

A topic is a supermarket with several checkout lanes (partitions). Within one lane, strict order. Between lanes, no promise. The key is the rule "one family, one lane" — each family's items stay in order. A hot partition is one family arriving with 40 carts: their lane crawls, other lanes idle — and opening more lanes doesn't help, because the family must stay together.

Trap — "we use Kafka, so events are ordered" Anyone who says this without naming the partition key has a design bug. Two more edges: adding partitions later changes hash(key) % N, so a key's new records land in a different partition than its history — cross-boundary order is lost (and you can never reduce partition count). Plan partitions generously up front for keyed topics.

4. Consumer groups: parallelism with a ceiling

Consumers sharing a group.id form a consumer group: each partition is assigned to exactly one consumer in the group. Two different groups are fully independent (that's the pub/sub part). Two rules follow:

  • Max useful parallelism = partition count. A 13th consumer on a 12-partition topic stands idle. Partition count is a capacity decision, not a detail.
  • Progress = committed offsets. The group records "next offset to read" per partition. Commit after processing → a crash between processing and commit means reprocessing: at-least-once (the default posture). Commit before processing → a crash loses records: at-most-once. The commit's position in your loop is your delivery semantics.

When membership changes (deploy, crash, scale-out), the group rebalances — partitions are reassigned. Under the classic protocol this was stop-the-world: every consumer paused, and everything processed-but-uncommitted got reprocessed after. Mitigations worth naming: static membership (a restarted pod reclaims its old partitions — no rebalance on rolling deploys), cooperative assignment, and the modern broker-side protocol (Kafka 4.x, KIP-848) that moves only the partitions that must move, with no global pause.

5. The guarantees: ISR, acks, and the trap inside "all"

Each partition is replicated: one leader (takes all reads/writes), N−1 followers that copy from it. The ISR — in-sync replicas — is the set currently caught up with the leader. It is a dynamic set, and that dynamism hides the best trap in Kafka:

Trap — acks=all does not mean all replicas acks=all means "all in-sync replicas have it" — and the ISR can shrink to just the leader when followers lag. Then acks=all silently behaves like acks=1, still returning success. The missing piece is min.insync.replicas=2: with fewer than 2 replicas in sync, the broker rejects writes instead of lying. The canonical no-data-loss recipe: replication factor 3 + acks=all + min.insync.replicas=2 — survives one broker; refuses writes rather than lose data when two are down. That refusal is the durability-vs-availability dial, set per topic.

Producer retries create duplicates (send → broker appends → the ack is lost → retry appends again — lesson 0002's ambiguous timeout, on the produce side). The idempotent producer (default since Kafka 3.0) fixes exactly this with sequence numbers the broker checks. Transactions go further: atomic writes across partitions plus the consumer's offsets — "exactly-once" for pipelines where both ends are Kafka.

What exactly-once does not cover — say this in the interview: any side effect outside Kafka. A database write, an HTTP call, an email inside your handler is neither rolled back on abort nor deduplicated on replay. So the senior posture is: every consumer is idempotent anyway — upserts keyed by entity id, or a unique constraint on event_id in the sink. Exactly-once is an optimization, not a foundation.

6. Event-driven architecture: the patterns

Event vs command. An event is an immutable fact, past tense (OrderPlaced), broadcast with no expectation about who reacts. A command is an imperative addressed to one handler that may refuse (ReserveInventory). The test: if the producer is broken when nobody handles it, it was a command — even if you named it like an event.

Three patterns people mix up (a classic interview discriminator):

Publishing events about your database changes is notification / state transfer — a fine pattern, but not event sourcing; claiming otherwise is a known red flag. (And Kafka alone is usually not an event store: it can't read "all events for aggregate #123" or do append-if-version-matches.)

The dual-write problem — and the outbox

The single most useful pattern in this lesson. A service must update its database and publish an event. Two systems, no shared transaction — any ordering is broken: write DB then crash before publish = the event never happened, downstream diverges silently forever; publish then crash before commit = an event about a change that doesn't exist.

Two more names to recognize, one line each. Saga: a distributed workflow as a chain of local transactions with compensating actions (refund, release) instead of rollback — choreography (services react to each other's events; the flow exists nowhere) vs orchestration (one coordinator owns the state machine; the flow is explicit). Dead-letter queue: Kafka brokers have none built in — it's a consumer-side pattern (bounded retries → retry topics → DLQ topic with error headers), and retry topics break per-key ordering, which most teams discover in production.

The fork is the storage model — retained log vs delete-on-ack vs nothing — not a throughput benchmark. One currency note for interviews: since Kafka 4.0 (2025) ZooKeeper is gone — cluster metadata is itself a Raft-replicated event log (KRaft). Kafka's answer to "who manages the manager?" was the same answer it gives everyone else: an ordered, replicated log.

Drill — the checkout event

Your checkout service saves the order to Postgres, then publishes OrderPlaced to Kafka. A teammate wraps both in try/catch: "if the publish fails, we roll back the DB transaction — problem solved."

Find both crash windows that survive the try/catch. Then fix the design with the outbox — and say why consumers must dedupe afterwards. Answer out loud before the quiz.

Anything unclear — where the offset actually lives, what a rebalance does to in-flight work, why the relay can't just be a second thread? Ask your teacher — open a session and say /teach.

Remember this
  • Log, not queue: the consumer owns its offset; the broker deletes by age, never by "read". Replay and fan-out fall out for free.
  • Fast-on-disk = sequential I/O + page cache + zero-copy + opaque batches + no per-message consumer state. Durability = replication, not fsync.
  • Order lives only inside a partition. The key names the thing whose events must stay ordered; a hot key can't be fixed by adding partitions.
  • Group parallelism ceiling = partition count. Commit after processing = at-least-once; before = at-most-once.
  • acks=all means all in-sync replicas — pair it with min.insync.replicas=2 and RF=3 or it silently degrades to acks=1.
  • Exactly-once covers Kafka-in → Kafka-out only. Your DB write is not protected — make every consumer idempotent (lesson 0002, again).
  • DB + event = dual write, always broken. Fix: transactional outbox — event row commits with the business change; a relay publishes at-least-once; consumers dedupe by event id.

If you remember one thing: Kafka is a numbered archive readers bookmark themselves — and anything that must be true in two systems at once (DB + event) needs the outbox, because two commits are never one.
