Domain 6 · Architecture · Real-time · Lesson 0006

WebSockets at scale

One open phone line per user. Cheap per message — and it quietly breaks every stateless scaling rule you know.

The win: after ~45 minutes you can answer the two senior real-time questions cold: "design chat for 1M concurrent users" and "deploy new code without dropping 100k live connections" — with the load-bearing words: backplane, fan-out amplification, heartbeat sweep, jittered backoff, and resume-from-sequence.

1. The protocol, in two minutes

A WebSocket starts life as a normal HTTP GET with two special headers (Upgrade: websocket, a random Sec-WebSocket-Key). The server answers 101 Switching Protocols — and from that moment HTTP is over. The same TCP connection stops carrying request/response pairs and becomes a persistent, full-duplex byte pipe: both sides send whenever they want, with 2–14 bytes of framing per message instead of hundreds of bytes of HTTP headers.

Wire details worth owning: the unit you send is a message, possibly split into frames; ping/pong control frames test liveness (browsers answer pings automatically but give JavaScript no API to send them — so the server pings); a clean shutdown is a close-frame handshake with a code. Two codes to know: 1000 (normal) and 1006 (the TCP connection died with no close frame — what you see when networks just drop; it is synthesized locally, never sent).

The decision rule: client pushes frequent small messages (typing, cursors, game input, call signaling) → WebSocket. One-way feed (notifications, tickers, LLM token streaming — this is why AI products use SSE) → SSE, and "SSE down + normal POST up" is often the cheapest correct design. "WebSocket is always the modern choice" is a junior tell — choose per feature.

2. Why this breaks the stateless playbook

The whole HTTP scaling playbook assumes any request can go to any server. A WebSocket violates that premise: the connection is a living object in the memory of exactly one process on exactly one machine — a file descriptor, TCP buffers, TLS state, subscription lists. You cannot serialize a TCP connection and move it elsewhere. Five consequences:

  1. Routing: to push to user X, something must know which process holds X's socket. HTTP never needed this.
  2. Servers must talk to each other: user A (node 1) messages user B (node 2). This forces the backplane of section 3.
  3. Deploys disconnect users: killing a process hangs up on everyone it holds.
  4. Autoscaling half-works: new nodes only catch new connections; scale-in kicks users off.
  5. The capacity metric changes: HTTP capacity is requests/second; WS capacity is connections held (memory + file descriptors, even at zero traffic) and, separately, messages/second (CPU). Systems die of fd exhaustion at 20% CPU, and of event-loop saturation at 10% memory. Load-test both axes.
Feynman version — the hotel

An HTTP fleet is a bank-teller hall: any teller serves whoever is next; add tellers, the line shortens instantly. A WebSocket fleet is a hotel: each guest occupies one room in one building for the whole stay. A new tower doesn't help guests already checked in, you can't move a sleeping guest without waking them (reconnect), and delivering a package means first finding out which building and room. Capacity isn't customers-per-hour — it's rooms.

Trap — "WebSockets require sticky sessions" Repeated in a hundred blog posts, and wrong as stated. A pure WebSocket needs no stickiness: TCP pins the established connection to one backend by nature. Stickiness is needed only when multiple separate HTTP requests must reach the same node — the classic case is Socket.IO's long-polling fallback, where each poll is an independent request carrying a session id that lives in one node's memory ("Session ID unknown" otherwise). What a load balancer actually must do for WS: pass the Upgrade through on every hop, and have an idle timeout longer than your heartbeat interval — the default 60s on nginx and AWS ALB reaps quiet-but-healthy connections, and you will debug "mystery 1006 every 60 seconds" for a week. Making this distinction crisply is a strong senior signal.

3. Scaling out: the pub/sub backplane

With N nodes, the canonical pattern is: nodes never talk to each other directly — they meet on a message bus.

Around the backplane sit two registries. Connection registry ("which node holds user X?"): either don't track it (all nodes subscribe, each filters for local recipients) or a Redis set per user — with a TTL, because a crashed node never runs its disconnect handlers; stale entries are the classic bug. Presence ("is X online?"): deceptively hard because it is fan-out-heavy — debounce the flapping (mobile networks disconnect constantly; wait a few seconds before broadcasting "offline"), batch updates, and only push presence for users actually visible on screen.

4. Fan-out amplification — the actual hard part

Receiving a message is O(1). Delivering it is O(room size): 

outbound msgs/sec  =  msgs published/sec  ×  room size
10 senders/sec × 100,000 members × 1 KB  ≈  1,000,000 sends/sec, ~8 Gbps egress

Ten people typing melt a server, while ingest sits at 10 msgs/sec. Worse: in real products, activity grows with room size, so cost grows superlinearly. The toolbox, in the order you reach for it:

  • Serialize once. Encode the message one time and write the identical buffer to every socket — vs 50k JSON.stringify calls, often a 10–50× CPU difference.
  • Batch and conflate. Ship digests every 50–100 ms; for keyed state (cursor position, presence) drop superseded values — only the latest matters.
  • Interest management. Don't send what the client won't render (Discord's "lazy guilds": no member lists or presence for members not on screen).
  • Degrade by tier. Big rooms lose typing indicators and receipts first, keep messages. Fewer features at scale, by design.
  • Relay trees. Publisher → K relay processes → each serves a slice of subscribers. This is how Discord pushed one community past ~1M concurrent members.

5. The Node.js numbers

One Node process = one event loop. That is architecturally right for holding sockets — 100k idle connections are just epoll entries and heap objects, no thread-per-connection cost. It is wrong for anything synchronous: a broadcast loop over 100k sockets at ~10 µs each is one full second of frozen event loop — no reads, no writes, heartbeats stall, and your own liveness sweeper starts reaping healthy connections. Chunk big loops with setImmediate, move heavy serialization to worker threads, and alert on event-loop lag — it is the health metric for a Node WS tier.

Three budgets cap a process: file descriptors (1 per connection — raise ulimit; remember the proxy in front needs 2 per connection and can exhaust ephemeral ports first), memory (~50–100 KB per connection all-in with TLS → 100k ≈ 5–10 GB; the famous trap is permessage-deflate, whose per-connection zlib contexts and heap fragmentation are why Socket.IO disables it by default), and the event loop (the real limit once users are active). Planning figures: 10k–50k active connections per process; 600k+ idle has been demonstrated on tuned boxes, but that's a parking-garage benchmark, not production capacity. ws is the bare, fast protocol library; Socket.IO adds the things you'd otherwise rebuild badly on a deadline — reconnection with jittered backoff, heartbeats, rooms, and the Redis adapter. Node's cluster module doesn't change the story: workers are separate processes, so cross-worker delivery needs the same backplane pattern — "another process" is another process, across a socketpair or a datacenter.

6. Operational hardening — where seniors are separated

Heartbeats, because TCP lies by silence. If a peer vanishes without a close — laptop lid, tunnel, NAT expiry — the socket stays ESTABLISHED forever; you learn the truth only when you next write. (TCP keepalive defaults to two hours.) So the server sweeps: 

ws.isAlive = true; ws.on('pong', () => ws.isAlive = true);
setInterval(() => wss.clients.forEach(ws => {
  if (!ws.isAlive) return ws.terminate();   // peer is gone — no polite close
  ws.isAlive = false; ws.ping();
}), 30_000);

The interval must be shorter than every idle timeout on the path (that 60-second load-balancer default again) — heartbeats are liveness detection and keepalive traffic at once.

Reconnection, with jitter. A restart disconnects 100k clients in the same instant; if they all retry at t+1s, t+2s, t+4s, they arrive as synchronized waves that re-kill the recovering server. Backoff without jitter schedules the herd; it doesn't disperse it: 

delay = Math.random() * Math.min(30_000, 1000 * 2 ** attempt)   // "full jitter"

A full reconnect also re-authenticates (the token may have expired), resubscribes, and — the part juniors forget — resyncs missed state.

Delivery across reconnects. TCP's guarantees end at the disconnect boundary — exactly where real-time systems live. The standard stack: one writer per channel assigns a per-channel sequence number; the client tracks last_seq; on reconnect it sends RESUME(session, last_seq) and the server replays from a bounded buffer — or, if the gap is too old, the client does a full refetch from the database. Must-deliver messages get acks plus client-generated IDs so receivers dedupe: at-least-once delivery + idempotent processing (lesson 0002's answer, again — "exactly-once delivery" over a network is not a thing). Durability lives in the DB; the socket path is a best-effort accelerator over it.

Backpressure. send() never blocks — it queues in your process's memory, and bufferedAmount grows without bound; a handful of 2G phones in a big room can OOM the node serving everyone else. The senior insight is that the policy is per message class: conflate superseded state (cursors, presence — only the latest matters), shed niceties first (typing, receipts), and for must-deliver messages keep a bounded queue then disconnect — the client resumes from its sequence number, which converts an unbounded memory problem into the already-solved resume problem. A client 30 seconds behind a live feed is reading fiction; cutting it is honesty, not cruelty.

Deploys. "Zero-drop" really means paced, cheap, invisible reconnects: pull the node from the balancer, tell small random batches of clients "reconnect" (close code 1012) over minutes, let jitter and resume do the rest. The big architectural lever: split the connection tier from the logic tier — a thin gateway holds sockets and rarely deploys; business logic behind it deploys twenty times a day without touching a socket (Slack and Discord both do exactly this). Slack's marquee scaling move, Flannel, was an edge cache making reconnect cheap — because reconnects, not connections, were what crushed the backend. The numbers that make it real: Slack holds millions of sockets with ~16M channels served per host; Discord runs 12M+ concurrent users pushing 26M+ events/sec; WhatsApp famously held 2M+ TCP connections on one tuned Erlang box — density is a runtime story, which is why Node's answer is horizontal.

Drill — the Friday deploy

Your WS tier holds 100k live connections across 4 nodes. A critical fix must ship now. A teammate proposes the normal rolling deploy: kill node 1, wait for health check, next node.

Narrate what the users experience, what the reconnect storm does to nodes 2–4 and to your auth service, and then give the grown-up runbook — pacing, jitter, resume, and what close code you send. Answer out loud before the quiz.

Remember this
  • After the 101, HTTP is over: one persistent full-duplex TCP pipe, 2–14 bytes of framing. One-way feeds usually belong on SSE instead.
  • A connection is pinned state in one process — that single fact forces the registry, the backplane, the deploy dance, and the new capacity metric (rooms, not customers-per-hour).
  • Pure WS needs no sticky sessions; polling fallbacks do. What WS needs from the infrastructure: Upgrade passthrough and idle timeouts longer than the heartbeat.
  • Cross-node delivery = pub/sub backplane; it is a signal, not a source of truth — durability lives in the DB write.
  • The hard part is fan-out amplification: outbound = rate × room size. Serialize once, conflate, degrade niceties, relay trees.
  • Heartbeat sweep or half-open zombies accumulate; full-jitter backoff or reconnect waves re-kill the server; seq + resume + dedupe or messages silently vanish at every disconnect.
  • Slow client? Policy per message class: conflate state, shed niceties, bounded-queue-then-kick for must-deliver — resume makes the kick safe.

If you remember one thing: scaling WebSockets is not about holding connections — it's about surviving their loss: cheap reconnects, resumable state, and fan-out you did the math on.
