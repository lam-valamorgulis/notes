Glossary

The words a front-end tech lead uses. Learn them once here; every lesson uses the same meaning. Keep the real terms — don't translate them away.

Why a glossary matters: half of "sounding like a tech lead" is using the shared words correctly. When a term appears in a lesson, it means exactly what it means here.

Leadership & influence

Tech Lead (TL)
A senior engineer who owns the technical direction of a team and still writes code. Leads through influence and credibility, usually with no direct reports. The role this course targets.
Staff Engineer
A senior individual contributor (above senior, no reports) whose impact is broad — across teams or a whole domain. The common next step after Tech Lead on the technical track.
Lead by influence
Getting people to move in the same direction without the power to order them — by clear writing, technical credibility, and trust. The core skill of a Tech Lead.
RFC (Request for Comments)
A short written proposal for a change: the problem, the options, your recommendation, and the tradeoffs. People comment before it is decided. How a Tech Lead drives a decision on paper, not in a meeting fight.
ADR (Architecture Decision Record)
A short note that records one architecture decision and why it was made. So future engineers know the reason, not just the result.
Disagree and commit
Once a decision is made, everyone supports it fully — even those who argued against it. Lets a team move after a real debate instead of staying stuck.
Mentoring
Sharing your experience and advice. "Here's how I'd approach it." You give answers.
Coaching
Helping someone find their own answer by asking questions. You give questions, not answers — builds their skill.
Glue work
The essential, often invisible work that holds a team together (unblocking, docs, reviews, RFCs). Core tech-lead work — but make sure it is recognized.
Brag document (evidence log)
A running note of your leadership wins ("drove the state-management RFC", "cut LCP from 4s to 2s"). You need specifics for a promo case or Tech Lead interview.
Managing up
Deliberately building a good working relationship with your own manager: sharing context and making their job easier. A Tech Lead's decisions need air cover.
Two-way vs one-way door
A reversible decision (two-way door) vs a hard-to-undo one (one-way door). Decide fast on reversible things; go slow only on one-way doors.

Front-end architecture & rendering

CSR (Client-Side Rendering)
The browser downloads JavaScript and builds the page. Great for app-like screens; weaker for first-load speed and SEO.
SSR (Server-Side Rendering)
The server builds the HTML for each request, then the browser makes it interactive. Better first paint and SEO; more server cost.
SSG (Static Site Generation)
Pages are built once at build time and served as files. Fastest and cheapest for content that rarely changes.
ISR (Incremental Static Regeneration)
Static pages that quietly rebuild in the background on a schedule. SSG speed with fresher content.
RSC / streaming (React Server Components)
Components that render on the server and stream to the browser, sending less JavaScript. The modern React/Next.js direction.
Hydration
Attaching JavaScript behaviour to server-rendered HTML so it becomes interactive. Heavy hydration is a common cause of slow interactivity.
State management
How the app stores and shares data that changes (local state, context, a store, or server-cache libraries). One of the biggest architecture choices a Tech Lead owns.
BFF (Backend for Frontend)
A thin backend layer built to serve one front-end's exact needs. Where front-end and back-end contracts often meet.

Performance

Core Web Vitals
Google's three headline user-experience speed metrics: LCP, INP, and CLS. The shared, evidence-based way to talk about front-end speed.
LCP (Largest Contentful Paint)
How long until the biggest thing on screen appears. Measures loading feel. Aim under ~2.5s.
INP (Interaction to Next Paint)
How quickly the page responds after the user interacts. Measures responsiveness. Replaced the older "FID".
CLS (Cumulative Layout Shift)
How much the page jumps around while loading. Measures visual stability. Lower is better.
Performance budget
An agreed limit (e.g. "JS bundle under 200KB", "LCP under 2.5s") the team must stay within. Turns "make it fast" into a testable rule.
Code-splitting
Breaking the JavaScript into smaller pieces loaded only when needed. A main lever for faster first load.
Lighthouse / RUM
Lighthouse = a lab test in your browser. RUM (Real User Monitoring) = speed measured from real visitors. Trust RUM for the truth; use Lighthouse to debug.

Design systems

Design system
A shared set of components, patterns, and rules so every screen looks and behaves consistently. A Tech Lead's biggest consistency and speed lever.
Design tokens
Named design values (colors, spacing, font sizes) stored in one place and reused everywhere. Change once, update the whole product.
Atomic design
Brad Frost's model: build UI from small to large — atoms → molecules → organisms → templates → pages.
Storybook
A tool to build, view, and document components on their own, outside the app. Lets others use a component without reading your code.
Component library
The shipped, versioned package of reusable components teams install and use.

Quality & accessibility

Testing trophy / pyramid
Models for how much of each test type to write. The trophy (Kent C. Dodds) favours integration tests; the pyramid favours many small unit tests. A Tech Lead picks the mix that fits the team.
Testing Library
A tool that tests components the way a user uses them (by visible text and role), not by internal details. Tests that survive refactors.
E2E test (end-to-end, e.g. Playwright)
A test that drives the whole app in a real browser like a user would. High confidence, higher cost — use for key flows.
Visual regression test
A test that compares screenshots to catch unwanted visual changes.
Accessibility (a11y)
Building UI everyone can use, including people who use a keyboard only, a screen reader, or need high contrast. A quality baseline, not an add-on.
WCAG (Web Content Accessibility Guidelines)
The W3C standard for accessible web content, with levels A, AA, AAA. AA is the common legal and practical target.
POUR
The four WCAG principles: content must be Perceivable, Operable, Understandable, and Robust.
ARIA
Extra HTML attributes that describe UI to assistive tech when plain HTML is not enough. Rule of thumb: use semantic HTML first; reach for ARIA only when you must.
Semantic HTML
Using the right HTML element for the job (<button>, <nav>, <label>). Free accessibility and behaviour, before any ARIA.

Scaling & delivery

Monorepo
Many projects/packages living in one repository, with shared tooling (e.g. Nx, Turborepo). Easier sharing; needs good tooling to stay fast.
Micro-frontend
Splitting a front-end into independently built and deployed pieces owned by different teams. Solves team-scaling pain but adds real complexity — use with care.
Conway's law
Systems tend to copy the shape of the organization that builds them. You can shape the front-end by shaping the teams — on purpose.
Team Topologies
A model of four team types: stream-aligned, platform, enabling, and complicated-subsystem.
Tech debt
The future cost of a shortcut taken today. Some is wise; too much slows everything down.
DORA metrics
Four research-backed measures of delivery (from Accelerate): Deployment Frequency, Lead Time for Changes, Change Failure Rate, and Time to Restore. Talk about delivery with evidence, not vibes.
