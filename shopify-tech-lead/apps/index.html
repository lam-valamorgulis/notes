Apps & Integrations

You integrate Shopify by building an app. The app is the vehicle. The sync is the job.

The one win of this Track. By the end you will have a service you wrote, running against a real Shopify Dev store, that survives a duplicate webhook, a 429, a clock that runs backwards, and an ERP that goes down mid-batch — and a report that proves it survived.

The story of this Track

Chapter A1 builds the app itself: how Shopify identifies it, how the session token becomes an access token, and how a webhook proves it really came from Shopify. Chapter A2 adds only the backend the app actually needs — a NestJS module, a Postgres schema, one queue, and a way to run it locally. Nothing more; depth beyond the Project belongs in the Node course.

Chapter A3 is the discipline, and it is the most valuable material here. It starts from one question — who owns this field? — and follows every consequence: why a write must be absolute so replay is safe, why a webhook is a hint and not a guarantee, what a delete means when neither side agrees it happened, and how you prove the two systems match without trusting either of them.

Chapter A4 is the connectors you meet in real work: an ERP, a CSV dropped on an SFTP server, a vendor who will not give you an API at all. Chapter A5 is the Project, where you build the thing.

Read A1 and A2 while you build Steps 0 and 1. Do not wait until the reading is finished — hands-on time is the scarce resource, not reading time.

A note on where this material came from Several traps in this Track were learned from a real integration read against a live system. Every company, client, tenant and traceable number has been removed. The pattern survives; the source does not. That is deliberate and permanent.

A5 · The Project core

Five steps. Each one is built from a blank file while you say out loud what you are doing. Code lives in shopify-tech-lead/project/, inside the private learn repo. deploy-site.sh excludes that folder from the published site and aborts if anything secret-shaped is ever staged, so an .env holding a Shopify access token cannot reach the public copy. Lessons show code as text — they never link into project/, because the folder does not exist on the live site.

0
The Dev store, the Shape sample, and the generator Create a free Plus Dev store. Read the Client store for structure and scale only — counts, metafield namespaces, tag conventions, locations. Then write a generator that produces a synthetic catalogue of the same shape. ADR 0001 is the rule.
1
The Fake ERP Products, prices, stock per location, an order inbox — and switches to break it on purpose: return stale data, duplicate a webhook, go down for ten minutes, change a price mid-sync. You need to cause the failures, which is why you write this side yourself instead of using someone's sandbox.
2
Catalogue out — the bulk load, then keeping it fresh Get ~46,000 synthetic variants in without being throttled, then keep them current when only a few percent change per day. This is where the rate-limit model stops being theory.
3
Webhooks in, inventory back HMAC on the raw body. Answer 200 inside the timeout. Dedupe on X-Shopify-Webhook-Id. Then send inventory the other way and meet the trap: Shopify owns inventory while your ERP owns the catalogue, so ownership is split on the same product.
4
The queue, the dead-letter, and the proof Retries with backoff, a dead-letter queue you actually read, and a reconciliation report. Then break the ERP and prove the report catches it. A sync without a report is a sync you are only guessing about.

All ten katas from the old course became these steps. A drill you never run is not practice.

Reserved file numbers — do not renumber Lesson files in apps/lessons/ are numbered by Map order, not by the order they get written, and each Chapter owns a fixed block. A1 0001–0004 · A2 0005–0008 · A3 0009–0015 · A4 0016–0021 · A5 0022–0026. Step 0 is therefore 0022 even though it is the first file written. Renumbering later would break every cross-link, so the ranges are claimed up front.

The Chapters

A1 · What an app is

  • Anatomy of a Shopify app core Public, custom, and the app config. What Shopify sees when it looks at your app.
  • App auth: session tokens and token exchange core How an embedded app turns a browser session into a server-side access token.
  • Webhooks done right core HMAC on the raw body, the response deadline, retries, and dedupe.
  • Scopes, protected customer data, and the mandatory webhooks core What you are allowed to ask for, and what you must promise in return.
  • Distribution, billing and App Store review depth What changes the day a client decides to sell the integration. Custom apps cannot bill through Shopify at all — ask the resale question on day one.
  • Sales channel apps depth Publishing to a channel is ordinary; being one is a different app type. Now also the recommended read path for market-driven shipping.

A2 · The backend the app needs

Hard-scoped to the Project. Deeper Node work links out to ../../nodejs-mastery-in-1-year/.

  • The NestJS module shape for a sync service core Modules, providers, and the API surface your own service exposes.
  • A Postgres schema for a sync store core Mapping tables, last-seen watermarks, and why you store the remote id twice.
  • One queue, with retries and a dead-letter core Backoff, poison messages, and the queue you can actually inspect.
  • Run it: docker-compose, CI, and what to log core One command to start everything, and the three log lines that save you at 2am.
  • The Shopify CLI and the dev workflow depth Config as code, one command for a tunnel, and two deploys that succeed while silently doing nothing.

A3 · The sync discipline

The strongest material in the Course. Start here if you only read one Chapter.

  • Shopify alone, and what a second system adds core Why one system is easy and two is a design problem.
  • Ownership, per field not per record core The spine of the Track. Title from the ERP, inventory from Shopify, on the same product.
  • Absolute writes, safe replay, and tombstones core Send the value, never the change. Then deletes, archives, and the record that says "gone".
  • Webhooks are a hint — clocks, order and staleness core Out-of-order delivery, a clock that disagrees, and the update that overwrites a newer one.
  • The backlog core What happens after four hours down, and why "catch up fast" is the wrong instinct.
  • Reconciliation, and numbers that do not lie core Counting rows proves nothing. What to compare so a money bug cannot hide.
  • Store 17 of four hundred core One tenant is a script. Four hundred tenants is a different job.

A4 · Real connectors

  • Integration patterns: ERP, CRM, payments, fulfillment core The four shapes almost every brief turns out to be.
  • Set piece: design a Shopify ↔ ERP sync at scale core The whiteboard answer, start to finish, out loud.
  • The vendor stock-feed connector: CSV and SFTP core What half of real clients actually hand you. Boring, and it breaks in interesting ways.
  • Identifier mapping and the mapping registry core Their id, your id, Shopify's id. Where syncs die.
  • When the vendor will not give you an API core A real refusal, and the four routes left. Genericised — no company, no tenant.
  • Worked example: integrating a stock-availability SaaS depth One integration end to end, using stockinstore as the concrete case.
