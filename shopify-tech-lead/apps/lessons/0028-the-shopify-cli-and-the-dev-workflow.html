The Shopify CLI and the dev workflow

Config as code, one command for a tunnel, and a deploy that can silently do nothing.

Your win today. You know what the CLI actually gives you, and the two deploy behaviours that succeed while not doing what you asked.

How it works

Derive it: what does app development need that a normal project does not?

Three things, and the CLI exists for exactly these:

NeedBecauseCLI answer
A public URLShopify must reach you — webhooks, callbacks, the embedded app frameshopify app dev creates a tunnel
Config in the repoScopes, webhooks and extensions must be reviewable, not clicked in a dashboardTOML files, deployed with the app
ScaffoldingEvery extension type has a fixed file shapeshopify app generate extension

The commands that matter

shopify app dev                  # run locally + create a tunnel
shopify app generate extension   # scaffold: checkout_ui, POS, customer account,
                                 #           payments, functions, theme app ext
shopify app deploy               # push app config + extensions

The tunnel is the important one, and it is why Project Step 3 becomes possible at all. Note that the tunnel URL changes each time you restart — Shopify's own advice is to use a relative path for a webhook URI, such as uri = "/webhooks", so the subscription does not need updating on every restart.

Config as code, and what that buys

Your app's scopes, webhook subscriptions, URLs and extension declarations live in TOML in the repo. So a scope change is a reviewable diff rather than something a colleague clicked at 6pm and cannot remember. That is the whole argument, and it is a good one.

shopify.app.toml scopes · URLs · webhook subscriptions shopify.extension.toml one per extension: targets, capabilities, metafields, settings

Two deploys that succeed and do nothing

1 · analytics_queryable in a metafield definition Documented plainly: shopify.app.toml accepts capabilities.analytics_queryable, your app deploys without an error, and the capability is not set. You asked for a feature, the deploy went green, and you did not get it.

So: verify capabilities after deploy rather than trusting the exit code.
2 · More than 25 metafield definition changes in one deploy Declarative metafield definitions are capped at 25 changes — creation, update or deletion — per deploy. A larger schema change has to be split across deploys, which matters when you planned one release.

And a related trap from P2.1: definitions declared in TOML are read-only through the Admin API. You can query them; mutations error. So runtime code that creates definitions breaks the day someone moves them into config.

Dev stores, and the plan choice

Create dev stores in the Dev Dashboard, on any plan including Plus, at no cost. And the counter-intuitive recommendation from Project Step 0: for sync work, choose a non-Plus store. Plus multiplies your rate limits by ten, which hides the throttling problems you are trying to learn to handle.

Two dev-store limits worth remembering because they shape what you can demo: no real transactions — use the Bogus gateway — and Store Credit and Gift Cards are not supported at all.

Answer before reading on Your deploy is green. You added a metafield capability and thirty definition changes in the same release. What actually happened?

Probably neither of the things you wanted, and the deploy told you nothing.

The thirty definition changes exceed the documented cap of 25 per deploy, so that release could not apply all of them — a larger schema change has to be split. And if one of your capabilities was analytics_queryable, that one is documented as deploying without an error while not being set.

The lesson is the same one as bulk operations in P6.2 and reconciliation in A3.6: a green result is a statement about the operation, not about the outcome. Read back what you asked for and confirm it is there.

Where it hurts

Fails with no error — analytics_queryable Documented: deploys clean, capability not set. Verify capabilities after deploy.
Fails with no error — over 25 definition changes in a deploy A hard cap. Split the release, or discover mid-launch that half your schema is missing.
Fails with no error — an absolute webhook URI and a restarted tunnel The tunnel URL changes; the subscription still points at the old one. Shopify fails deliveries you never see. Use a relative uri.
Runtime code creating declarative definitions TOML-declared definitions are read-only through the Admin API. Code that created them at runtime starts failing the day they move into config.
Costs money — developing on a Plus dev store Ten times the rate limit hides every throttling problem. You ship to a Basic store and it falls over on day one.
Demoing store credit or gift cards on a dev store Not supported. Plan the demo around it rather than debugging it for an afternoon.
Judgement, not documentation — the CLI will not catch a deprecated field It scaffolds and deploys; it does not lint your GraphQL against the version you pinned. Validating queries against the schema in CI is what caught three already-deprecated fields while building this Course. That job is yours to add.

What you say to a client/PM

Explaining why config lives in the repo All the app's permissions and webhook settings live in a file in our code rather than being clicked in a dashboard. It means any change to what we can access shows up in a review, with a date and a name against it. Worth it for anything touching your customer data — you can always see what we asked for and when. Explains a developer convenience as an audit benefit, which is what the client actually values.
When a schema change needs splitting This one goes out over two releases rather than one. Shopify caps how many custom-field definitions can change in a single deploy at twenty-five, and we have thirty. Nothing's wrong — it's just two deploys instead of one, and I'd rather tell you now than have half of it land silently. A platform limit, stated as a scheduling fact rather than a problem, with the silent-failure risk named.

Remember this

  • Three needs: a public URL, config in the repo, scaffolding. That is what the CLI is for.
  • shopify app dev makes a tunnel, and its URL changes on restart. Use a relative webhook uri.
  • Config as code makes a scope change a reviewable diff. That is the real argument.
  • 25 declarative metafield changes per deploy. Bigger schemas split across releases.
  • analytics_queryable deploys clean and is not set. Verify capabilities after deploy.
  • TOML definitions are read-only via the Admin API. Runtime creation breaks when they move to config.
  • Dev on a non-Plus store for sync work. Plus hides the throttling.

If you remember one thing: a green deploy is a statement about the operation, not the outcome — read back what you asked for.
