Track 2 · A3 · Lesson 1

Shopify alone, and what a second system adds

One system has no sync problems. Every sync problem is created by the second one.

Your win today. You can name, from first principles, the four problems that appear the instant a client adds a second system — before you have seen their API. Every later Lesson in this Chapter solves exactly one of them.

How it works

Start from the simplest possible store

A merchant sells on Shopify and nothing else. A staff member edits a price in the admin. The storefront shows the new price. Someone buys the last unit; stock goes to zero and the product shows as sold out.

Ask the first-principles question: why does any of that work? Not "which feature makes it work" — why is it impossible for it to be wrong?

one system edit ──▶ [ the only copy ] ──▶ read │ └── there is nothing to disagree with

Because there is one copy of each fact. Not because Shopify is well built. A single copy cannot disagree with itself. There is no ordering question, because writes hit one place in one order. There is no staleness question, because there is no second reader with an older answer. There is no ownership question, because there is only one writer.

Say it as plainly as possible, the Feynman way: a fact stored once is always right. Correctness here is free, and it is free for a structural reason, not a technical one.

Now add the second system

The merchant buys an ERP. Their staff manage products there, because that is also where purchasing and accounting live. Now the same fact — this product's price — exists in two places.

two systems edit ──▶ [ copy A ] ─── some delay ───▶ [ copy B ] ──▶ read ▲ │ └──────── also edited here ────┘

Nothing has been badly built yet. No code has been written. And four problems already exist, purely from the arithmetic of having two copies:

#The problem, stated from first principlesSolved in
1Two copies can be edited. Which edit wins? A3.2 — ownership
2Copying can fail halfway. Is repeating it safe? A3.3 — absolute writes
3Copying takes time. Which copy is older, and how would you know? A3.4 — clocks and staleness
4Copies drift. How do you prove they agree? A3.6 — reconciliation

That is the entire Chapter. Not a list of Shopify features — four consequences of the number two.

Why the count of systems is the wrong count

It is tempting to say "we have two systems, so we have one sync". Wrong unit. The real unit is the field. In practice a single product has some fields owned by the ERP, some by Shopify, and possibly one owned by neither, which is the worst case.

So the honest description of a real integration is not "two systems, one sync". It is "about forty fields, each with its own answer to who decides". That reframing is what the next Lesson is built on, and it is the difference between a sync that works and one that mostly works.

Answer before reading on A client says: "just make Shopify and our ERP match." Why is that sentence not yet a specification? Say it out loud in one sentence.

Because "match" does not say what happens when they differ — and they will differ, on purpose, every day. Their staff edit the ERP; customers buy on Shopify. "Match" is a description of a good day. The specification is the answer for each field: who decides, which way it flows, and what happens when both changed. Until you have that, you have a wish.

Where it hurts

Costs money — "two-way sync" agreed as a phrase A client asks for two-way sync and everyone nods. Nobody asked which side wins. The first conflict resolves in whichever direction the code happened to run last, and it resolves against the client's money — a price, or a stock count that oversells. Turn the phrase into a per-field table before anyone estimates it.
Fails with no error — the field owned by nobody Both systems can edit it, and nobody decided which wins. Each sync run overwrites the other's value. It looks like flickering, and it is nearly impossible to reproduce on demand because the outcome depends on timing. Every field needs an owner, even if the owner is "Shopify, because we said so".
Counting systems instead of fields "One integration" sounds like one unit of work. Forty fields with three different flow directions is the real shape. Estimates built on the first number are wrong by a large multiple, and the discovery happens in week three.
Judgement, not documentation — a third system arrives later Marketplaces, a POS, a warehouse, a review app. Each one adds a copy and re-asks all four questions. Design the mapping and the ownership rules so that adding a system is a configuration change, not a re-think. A3.7 covers what actually breaks at scale.

Say it out loud

Explain this to a beginner

A client says "we just need a simple two-way sync between our warehouse system and Shopify". Explain why that sentence contains no actual requirement.

Say it out loud. Then read on.

Now compare with a plain-words answer

Because "two-way" does not say who wins.

With one system there is one copy of every fact, so it cannot disagree with itself. Correctness is free. The instant there is a second copy, four questions appear, and no code has been written yet: when both sides changed, whose change survives? If we send the same thing twice, is that safe? When they differ, which one is older? And how would we even know they had drifted apart?

"Two-way sync" answers none of those. Everyone nods, because it sounds like a description of something. It is a description of a good day.

And the unit is wrong too. It is never "two systems, one integration". It is forty fields, each needing its own decision. The warehouse might own how many there are; the shop owns the description and the photos; the price is argued over by both. Counting systems makes it sound like one piece of work. Counting fields tells you the truth.

The worst outcome is a field nobody was assigned. Both sides can edit it, so each run overwrites the other. It looks like flickering, it never reproduces on demand, and it can survive for years.

If you used any of these words, try again bidirectional · source of truth · conflict resolution · eventual consistency · last-write-wins. "Two-way does not say who wins" is the explanation, and it is the entire chapter in six words.

Build it

Task · 60 minutes no store needed

Turn a sentence into a specification. This is the single most valuable artefact in the Course.

  1. List every field that exists in both systems. Aim for the real number, which will be thirty to fifty, not five.
  2. Against each, write the direction: into Shopify · out of Shopify · both · neither.
  3. Circle every row marked "both". Those are your future bugs.
  4. For each circled row, either assign an owner or split the field in two.
  5. Count the rows. Show that number to whoever called it "one integration".

Proof it worked: you have a table with no "both" rows left, and a row count that changes the conversation about the estimate. If your table has five rows, you described the systems and not the fields.

Then plan for the third system · 20 minutes no store needed

A marketplace, a till, a warehouse, a reviews app — one of them arrives later, always. Write how your table grows when it does.

Proof it worked: your ownership table has a column per system rather than a single "external" column. Retrofitting that is painful; adding it now is free.

Remember this

  • One copy of a fact is always right. Correctness with one system is free, and free for a structural reason.
  • The second copy creates every sync problem. Four of them, before any code exists.
  • Which edit wins? Is a repeat safe? Which copy is older? Do they still agree? That is this whole Chapter.
  • The unit is the field, not the system. "Two systems, one sync" hides forty decisions.
  • A field owned by nobody flickers, and is nearly impossible to reproduce on demand.
  • "Make them match" is a description of a good day, not a specification.
  • Two good client questions: where do staff edit prices, and where does a sale reduce stock?

If you remember one thing: you are not synchronising two systems, you are deciding forty small arguments in advance.

Ask questions. Then "next" for ownership — the spine of this Track.
