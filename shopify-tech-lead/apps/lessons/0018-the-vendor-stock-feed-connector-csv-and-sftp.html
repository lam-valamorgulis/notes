Track 2 · A4 · Lesson 3

The vendor stock-feed connector: CSV and SFTP

What half of real clients actually hand you. Boring, and it breaks in interesting ways.

Your win today. A connector that treats a file drop as a legitimate integration rather than a workaround — and that refuses to import a truncated file instead of wiping a catalogue with it.

How it works

Derive it: a file is a snapshot with no metadata

An API answers questions. A file does not. It arrives, it contains rows, and everything you would want to know is absent:

You want to knowAn API tells youA file tells you
What changed?changed since XNothing. Diff it yourself
Is this complete?Pagination, a cursorNothing. It may be half-written
What was deleted?A tombstone or a flagAbsence — which carries no information
Is this newer than the last one?A timestamp per recordA filename and an mtime, both editable

So the connector's job is to manufacture the metadata a file does not carry. That is the whole design, and it is why "it's just a CSV" is the most misleading sentence in this trade.

A file feed IS a full-state snapshot — use that

Here is the one genuine advantage. A full file every day answers the deletion question that APIs make hard. If a SKU was in yesterday's file and is not in today's, it is gone. An absence inside a complete snapshot is information — unlike an absence inside a page of changes.

yesterday's file today's file conclusion ──────────────── ──────────── ────────── SKU-1 SKU-1 unchanged (or changed — diff the row) SKU-2 — DELETED. this is reliable. — SKU-3 new

That inference is only valid if today's file is complete. Which is exactly why the next section is the most important part of the Lesson.

Never trust the file until it passes the gate

A truncated upload plus "absence means deleted" equals a wiped catalogue. So every file passes a gate before a single row is applied:

GateRulePrevents
StabilitySize unchanged for N seconds before you open itReading a file still being uploaded
HeaderExact expected columns, or rejectA silent column reorder mapping price into stock
Row count sanityWithin ±X% of the last good fileA truncated file deleting the catalogue
FreshnessNot older than the last file processedAn old file being re-dropped, undoing a day
ChecksumIdentical to last time → skipRe-processing an unchanged feed

The row-count gate is the one that saves you. A feed that normally has 40,000 rows arriving with 300 is not a business event — it is a failed upload. Reject and alert. Never apply. Half a catalogue deleted at 3am is one of the few genuinely unrecoverable integration incidents.

Vendors do not send well-formed files

Assume all of this, because you will meet all of it:

  • Encoding. UTF-8 with a BOM, or Windows-1252 with a smart quote. Detect, do not assume.
  • A trailing summary row. "TOTAL, 40000" at the bottom, which parses as a product.
  • Numbers as text. "1,234" with a thousands separator, or "12.00 " with a trailing space.
  • Excel damage. A SKU like 0012345 silently losing its leading zeros, or becoming a date.
  • Duplicate keys. The same SKU twice, with different stock. Decide the rule — last wins, or reject the file — and write it down.
  • A changed column order with no version marker. This is why the header gate is exact-match, not permissive.

Then convert it into the shape from A3

Once it passes the gate, the file becomes ordinary. Diff against the previous good snapshot, turn the diff into absolute writes, emit tombstones for disappearances, and everything from Chapter A3 applies unchanged. Keep the previous good file — it is your only diff baseline and your only evidence when a vendor says they never sent that.

Answer before reading on Monday's feed has 40,000 rows. Tuesday's has 38,500. Your rule is "absence means deleted". Do you apply it?

Not automatically — 3.75% is exactly the ambiguous band. It could be a genuine seasonal delisting or a partial upload, and the file cannot tell you. So the honest design has three outcomes, not two: apply below a tight threshold, reject above a wide one, and hold for a human in between. Most connectors have only apply and reject, which forces you to set the threshold either dangerously loose or annoyingly tight. A hold state costs one notification and removes the dilemma.

Where it hurts

Costs money — applying a truncated file The worst incident in this Lesson. Absence means deleted, the upload failed halfway, and half the catalogue is archived overnight. Recovery means restoring from your previous snapshot, which only exists if you kept it.
Costs money — reading a file mid-upload Your watcher fires on file creation, not completion. You read 60% of a feed and treat it as complete. Identical damage to the above, from a race rather than a vendor error. Wait for a stable size, or require the vendor to upload to a temp name and rename.
Fails with no error — a reordered column Price and stock swap places. Every row parses. Every number is wrong. There is no error at any layer, and the store sells at stock levels and stocks at prices. Exact header matching is the only defence.
Fails with no error — Excel eating the SKU A vendor opens the file to check it and saves it. Leading zeros are gone, and long numeric SKUs become scientific notation. Your matching silently fails for those rows, which then look like new products. Validate the key format and reject rows that fail it.
The re-dropped old file A vendor re-uploads last week's file to "fix" something. Without a freshness gate you cheerfully roll the catalogue back a week. Track the last processed file's identity and timestamp, and refuse to go backwards.
Judgement, not documentation — SFTP has no delivery notification There is no webhook. You poll a directory, which means your freshness is bounded by your poll interval plus the vendor's schedule. And if the vendor's upload silently stops, you receive nothing — which looks exactly like "no changes today". Alert on the absence of a file, not only on bad files. This is the failure most connectors miss entirely.

Say it out loud

Explain this to a beginner

A supplier drops a stock file every night. Tonight's file has 200 rows instead of the usual 40,000. Explain what your connector must do, and why "apply it" and "reject it" are both wrong.

Say it out loud. Then read on.

Now compare with a plain-words answer

Applying it would set 39,800 products to zero stock, taking the shop offline. That is the catastrophe.

But rejecting it is not right either, because you do not actually know it is wrong. Maybe the supplier really did discontinue almost everything. Rejecting silently means if it was real, your stock is now days stale and nobody knows.

So there is a third outcome: hold it, and ask a person. That single extra state removes an impossible decision. You are no longer trying to pick a magic threshold that separates "suspicious" from "wrong" — you just say "this is unusual, a human should look", and the file waits.

The bigger idea: a file tells you almost nothing about itself. It does not say when it was made, whether it finished uploading, whether it is complete, or which rows changed. The connector's whole job is to manufacture the information the file does not carry — is it still being written, are the column headings exactly right, is the row count sane, is it fresh, is it byte-for-byte the same as yesterday's.

The upside of a full nightly snapshot is that it answers the deletion question that APIs make hard: anything absent is gone. But that is only true if the file is complete — which is precisely why the gates come first.

If you used any of these words, try again ETL · schema validation · sanity check · atomic write · checksum · quarantine. "Hold it and ask a person" is the explanation, and it is the design idea worth stealing.

Build it

Task · 2 hours Postgres + local SFTP

Build the five gates, then feed the connector five bad files.

  1. Stability: is the file still being written? Test with a half-uploaded file.
  2. Exact header: test with a renamed column and a reordered one.
  3. Row-count sanity: test with 200 rows instead of 40,000.
  4. Freshness: test with yesterday's file re-delivered.
  5. Checksum: test with a byte-identical repeat.
  6. Implement three outcomes: apply, hold, reject. Keep the last good file.

Proof it worked: the 200-row file went to hold, not apply and not reject, and a human was notified. Nothing was deleted. Then diff the held file against your last good one to show the human exactly what would have changed.

The rule, written down · 5 minutes no store needed

Put this in the connector's README: never let a short file delete anything.

Proof it worked: there is a test named after that sentence, and it fails if someone removes the gate.

Remember this

  • A file carries no metadata. The connector's job is to manufacture what the file does not say.
  • A complete snapshot answers the deletion question that APIs make hard — but only if it is complete.
  • Five gates before any row is applied: stability, exact header, row-count sanity, freshness, checksum.
  • Three outcomes, not two: apply, hold for a human, reject. A hold state removes the threshold dilemma.
  • Keep the last good file. It is your diff baseline and your evidence.
  • Assume encoding, summary rows, Excel damage and duplicate keys. All of them, every time.
  • Alert on a missing file. Silence looks exactly like "no changes today".

If you remember one thing: never let a short file delete anything — hold it and ask a human.
