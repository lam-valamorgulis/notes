Track 2 · A2 · Lesson 2

A Postgres schema for a sync store

Five tables. The interesting one is the one that stores what you last sent.

Your win today. A schema that can answer three questions instantly: what is this record called on the other side, did I already handle this message, and is what I sent still what they have.

How it works

Your database is not a copy of Shopify. Copying Shopify is a losing game — it is always newer than you. Your database holds the things only you know: the identity mapping, how far you have read, what you last sent, and what happened.

id_map "their id ↔ my id ↔ Shopify's id" watermark "how far have I read from each source" inbox "which messages have I already handled" shadow "what did I last successfully SEND" outbox_dead "what failed for good, and why"

1 · id_map — a hub, never pairwise

CREATE TABLE id_map (
  entity        text NOT NULL,          -- 'product' | 'variant' | 'location'
  local_id      uuid NOT NULL,          -- YOUR id. the hub.
  system        text NOT NULL,          -- 'erp' | 'shopify'
  external_id   text NOT NULL,
  PRIMARY KEY (entity, system, external_id),
  UNIQUE (entity, system, local_id)
);

Three systems, so the temptation is a table with erp_id and shopify_id side by side. Resist it. With n systems, pairwise mapping needs n(n−1)/2 relationships and every new system rewrites the table. A hub — your own id in the middle — needs n. Adding a marketplace later becomes an insert, not a migration.

Note the two constraints. The primary key stops one external id mapping to two locals. The unique stops one local mapping to two external ids in the same system. Both directions matter, and only writing one is the usual mistake.

2 · watermark — the highest value you actually saw

CREATE TABLE watermark (
  source        text PRIMARY KEY,       -- 'erp.items' | 'shopify.products'
  last_seen_at  timestamptz NOT NULL,   -- the SOURCE's clock. never ours.
  last_seen_id  text,                   -- tiebreak for equal timestamps
  updated_at    timestamptz NOT NULL DEFAULT now()
);

Two rules, both learned expensively. Store the source's timestamp, never your own — mixing clocks silently drops rows. And store the highest value you actually saw, not the time the scan started. Saving the start time loses every row that changed during the scan, permanently and invisibly. Re-reading a few rows next time is cheap.

last_seen_id earns its place the first time two records share a timestamp to the second. Without it you either skip one or loop on it forever.

3 · inbox — idempotency, made a database constraint

CREATE TABLE inbox (
  message_id   text PRIMARY KEY,        -- X-Shopify-Webhook-Id, or the ERP's key
  topic        text NOT NULL,
  received_at  timestamptz NOT NULL DEFAULT now(),
  handled_at   timestamptz
);

A primary key is a better idempotency check than an if statement, because two workers racing cannot both win. The insert fails for the loser. Note handled_at is nullable on purpose: "received" and "finished" are different states, and the gap between them is where crashed work hides.

4 · shadow — the table people leave out

CREATE TABLE shadow (
  entity      text NOT NULL,
  local_id    uuid NOT NULL,
  system      text NOT NULL,
  payload     jsonb NOT NULL,           -- exactly what we last SENT
  sent_at     timestamptz NOT NULL,
  PRIMARY KEY (entity, local_id, system)
);

This is the one that separates a sync from a script. It records what you last successfully sent — and it is written only after a confirmed success.

It buys three things. You can skip a write when nothing changed, which is most of the time. You can produce a real diff for reconciliation instead of comparing counts. And when someone asks "did we send the wrong price or did they change it after?", you can answer, which is otherwise unanswerable.

5 · outbox_dead — failures you can read

CREATE TABLE outbox_dead (
  id           bigserial PRIMARY KEY,
  entity       text NOT NULL,
  local_id     uuid,
  attempt      int  NOT NULL,
  error_code   text,                    -- 'THROTTLED' | userError code | HTTP status
  error_body   jsonb,
  failed_at    timestamptz NOT NULL DEFAULT now(),
  resolved_at  timestamptz
);

A dead-letter table you never read is a landfill. resolved_at is what makes it a work queue: unresolved rows are a number you can alert on.

Answer before reading on Your sync crashes after Shopify accepted a price update but before you wrote the shadow row. On restart, what happens — and is it a problem?

You resend the same price. That is fine, and it is fine because you send absolute values: setting the price to 12 twice leaves it at 12. This is why "shadow after success" is the safe ordering — writing shadow first would make you skip a write that never happened, and the wrong value would stay wrong forever. A duplicate write is cheap; a skipped write is permanent.

Where it hurts

Costs money — pairwise id mapping erp_id and shopify_id as columns on one row works with two systems and collapses at three. Adding a marketplace becomes a migration plus a backfill plus a re-test, instead of an insert.
Fails with no error — the watermark saved as "now" Using your own clock, or the scan's start time, drops rows changed during the scan. No error, no log line, no count mismatch unless you reconcile. This is the single most common cause of "a few products are just wrong".
Fails with no error — writing shadow before the send Write it first and a crash makes you believe you sent something you did not. The record is then skipped on every future run because "nothing changed". The wrong value is now permanent. Order matters: send, confirm, then record.
Only one unique constraint on id_map Guarding "one external id → one local" but not the reverse lets a local record acquire two Shopify products. Both directions, or you will find out by seeing duplicates in the admin.
No tiebreak on equal timestamps Two records with the same updated_at and a strict > filter means one is skipped forever. Use >= plus last_seen_id, and accept re-reading one row.
Judgement, not documentation — jsonb in shadow Storing the sent payload as jsonb is deliberate: the shape changes when Shopify changes, and you do not want a migration every quarter for a table that exists to be compared, not queried. Do not do this for data you filter on.

What you say to a client/PM

When a client asks whether you are "copying their data" Not really. We don't keep a second copy of your catalogue — Shopify stays the place to look. What we store is the plumbing: which record matches which, how far we've read, and what we last sent. That last one is what lets me tell you exactly what changed and when, if anything ever looks wrong. Answers the data-residency worry honestly, and turns the shadow table into a benefit the client can feel.
When asked why a few products are wrong and the rest are fine Almost always it's records that changed while we were mid-scan, and our bookmark moved past them. It's a known failure and it doesn't show up as an error — that's why we run a reconciliation that compares what we sent against what's there, rather than trusting counts. Give me the report and I'll tell you exactly which ones. Names the mechanism instead of promising to "look into it", which is what separates a lead from a developer in that conversation.

Remember this

  • Your database is not a copy of Shopify. It holds mapping, position, what you sent, and what failed.
  • id_map is a hub, not pairwise. Your id in the middle: n relationships instead of n(n−1)/2.
  • Constrain both directions on the mapping, or you will create duplicates.
  • Watermark = the source's clock, and the highest value you actually saw. Never your clock, never the scan's start.
  • Idempotency belongs in a primary key, not an if. Two racing workers cannot both insert.
  • shadow is written after a confirmed success. Before means believing in sends that never happened.
  • A dead-letter table needs resolved_at, or it is a landfill instead of a queue.

If you remember one thing: store what you last sent — it is the only way to answer "did we break it, or did they change it?"

Ask questions. Then "next" for the queue, and the throttle that returns HTTP 200.
