Track 2 · A5 · Project Step 3

Webhooks in, inventory back

The first step where data comes to you. That inverts everything about the setup.

Your win today. A receiver that proves a message came from Shopify, survives the same one arriving twice, and writes inventory back to the Fake ERP — with ownership deliberately reversed on the same product.

How it works

What changed: direction

Steps 0 to 2 were all outbound. Your code called Shopify, so localhost was fine — nothing needed to reach you. Step 3 is the first inbound step, and that single change inverts the networking requirement.

STEPS 0-2 (outbound) STEP 3 (inbound) your laptop ──▶ Shopify Shopify ──▶ your laptop localhost is fine localhost is UNREACHABLE you control the timing Shopify controls the timing you can retry you get 5 seconds, then 8 retries

So you need a public HTTPS URL that forwards to your machine. Three ways, in order of convenience:

ToolNotes
shopify app devShopify CLI creates a tunnel for you. Easiest, and the URL changes on each restart
cloudflared tunnel --url http://localhost:3000Free, no account for a quick tunnel
ngrok http 3000Same idea. A free account gives you a stable subdomain

Whichever you pick, the URL changes when the tunnel restarts. So do not hardcode it: read PUBLIC_BASE_URL from .env, and recreate the subscription on boot if the registered URL does not match. That is ten lines and it removes a whole category of "why is nothing arriving".

1 · Register the subscription

mutation CreateWebhook(
  $topic: WebhookSubscriptionTopic!
  $sub:   WebhookSubscriptionInput!
) {
  webhookSubscriptionCreate(topic: $topic, webhookSubscription: $sub) {
    webhookSubscription { id topic apiVersion { handle } uri }
    userErrors { field message }
  }
}

And to see what is already registered — run this first, or you will create duplicates:

query ListWebhooks {
  webhookSubscriptions(first: 50) {
    nodes { id topic apiVersion { handle } createdAt uri }
  }
}

2 · The receiver, in the only order that works

POST /webhooks/shopify 1. capture the RAW body ← before any JSON parsing 2. verify HMAC-SHA256(raw, secret) vs X-Shopify-Hmac-SHA256 mismatch → 401, and do not log the body 3. INSERT X-Shopify-Webhook-Id into inbox duplicate key → 200, and stop. already handled. 4. enqueue the id + topic 5. return 200 ← inside 5 seconds, always ── total work here: microseconds. no API calls. no ERP calls.

Step 1 is where most people fail. Your framework parses JSON before your handler runs, and a parsed-then-re-serialised body is a different byte string — so the HMAC never matches and the code looks correct. Capture raw bytes on this route specifically.

Step 3 is idempotency as a database constraint rather than an if. Two workers racing cannot both insert; the loser's insert fails and it returns 200. An if can be passed by both.

3 · Then do the work, outside the request

The queued job does what A3.4 requires: the webhook is a trigger, not data.

job(webhookId, topic): read the CURRENT value from Shopify ← never trust the payload map ids via the registry write to the Fake ERP, ABSOLUTE record in shadow, only after success advance the watermark to the highest seen

4 · Inventory back — and read this mutation choice carefully

Shopify gives you two, and the names are dangerously similar:

MutationSemanticsUse
inventorySetQuantitiesAbsolute. "This is now 12"This one
inventoryAdjustQuantitiesDelta. "Change by −3"Almost never. A retry applies it twice
mutation SetInventoryAbsolute($input: InventorySetQuantitiesInput!) {
  inventorySetQuantities(input: $input) {
    inventoryAdjustmentGroup {
      createdAt
      reason
      changes { name delta quantityAfterChange }
    }
    userErrors { field message code }
  }
}

Note what comes back: quantityAfterChange. That is Shopify telling you the resulting value, so you can record exactly that in shadow rather than recording what you hoped for.

5 · The point of this Step: ownership reverses

On the same product, in the same run:

title, description, price Fake ERP ──▶ Shopify (Step 2) inventory quantity Fake ERP ◀── Shopify (Step 3) ── ownership SPLITS INSIDE ONE PRODUCT. this is the whole lesson.

Build it that way deliberately, because it is the arrangement most real integrations have and the one that catches people. And note which direction you are writing: pull Shopify's available, and write it to the ERP's sellable field — never to its warehouse total.

6 · Then break it on purpose

Do thisProve
Change stock in the Shopify adminThe ERP follows within seconds
Replay the same webhook body twiceSecond one returns 200 and does nothing. Check the inbox row
Return a 301 from the route for a minuteShopify counts failures. Watch the retries arrive
Take the receiver down for 20 minutesRetries arrive with growing gaps. Count them
Set ERP_FAIL_MODE=downThe job fails, retries, and lands in the dead-letter — not lost
Sleep 6 seconds before returning 200It times out at 5. Confirm the deadline is real
Answer before you build Your handler verifies the HMAC, then does the ERP write, then returns 200. The ERP takes 4 seconds today. What breaks, and when?

Nothing — today. You are at 4 seconds against a 5-second budget, so it works, and it will keep working until the ERP has a slow afternoon. Then you cross 5 seconds, Shopify records a failure, and it retries — so you do the slow write again, still too slowly, eight times. After 8 consecutive failures your subscription is deleted, and from then on your app looks healthy and receives nothing.

That is the whole reason for enqueue-then-200. The 5 seconds is for acknowledging, never for working. And notice the failure is invisible: no error in your logs, because your handler completed fine — just slowly.

Where it hurts

Costs money — doing the work inside the request The scenario above. It works until it does not, then it deletes your own subscription and the app goes quiet while looking healthy. Enqueue, return 200, work behind it.
Fails with no error — HMAC on a parsed body Every delivery is rejected as unauthentic and the code reads as correct. Capture raw bytes on this route only.
Fails with no error — a stale tunnel URL The tunnel restarted, the subscription still points at the old URL, and nothing arrives. Shopify is failing deliveries you never see. Recreate the subscription on boot if the URL does not match.
Costs money — inventoryAdjustQuantities A delta. Retry it and the stock drifts permanently, in a direction nobody notices until a count is wrong. Use inventorySetQuantities.
Costs money — writing available into a warehouse total You are writing back now, so the oversell risk points the other way: the ERP's picking decisions get made on a sellable number that excludes reserved stock.
Fails with no error — duplicate subscriptions Register on every boot without listing first and you accumulate subscriptions on one topic. Each produces a separate delivery with its own Webhook-Id and the same Event-Id — so your inbox lets both through and you do the work twice.
Logging the payload to debug Order and customer payloads carry names, emails and addresses. Log the Webhook-Id, the topic and your decision — never the body.
Judgement, not documentation — pin the webhook's API version too A subscription carries its own version. Pin your calls and forget the subscription and you will one day parse a new payload shape with old code. Read it back from apiVersion { handle } and assert it matches your constant on boot.

What you say to a client/PM

When asked why inventory goes the opposite way to everything else Because that's where it actually changes. Your ERP decides what a product is and what it costs, but a sale happens in Shopify — so Shopify knows the quantity first, and we carry that back to you. It means one product has information flowing both ways at once, which sounds odd but is the arrangement that stops the two systems fighting. Explains a design that looks inconsistent by grounding it in where the event happens. Clients accept it immediately once "a sale happens there" is said aloud.
When asked how fast the update is Usually a few seconds. I won't say instant, because Shopify's own guidance is that a notification can arrive up to a day late — so alongside reacting to notifications we also re-check on a schedule. What I can promise is that a late or repeated message can't do any damage, which matters more than the speed. Refuses the wrong promise and replaces it with a better guarantee.

Remember this

  • Step 3 is the first inbound step. You need a public tunnel; localhost cannot receive.
  • Read the tunnel URL from config and recreate the subscription on boot if it changed.
  • List subscriptions before creating one, or you get duplicate deliveries you will process twice.
  • Order: raw body → HMAC → inbox insert → enqueue → 200. No API or ERP calls in the request.
  • inventorySetQuantities, never inventoryAdjustQuantities. Absolute, not delta.
  • Record quantityAfterChange in shadow — what happened, not what you hoped.
  • Ownership splits inside one product. Price flows out; quantity flows in. That is the Step.

If you remember one thing: the five seconds is for saying yes, never for doing the work — break that and Shopify eventually deletes your subscription and your app goes quiet while looking healthy.
