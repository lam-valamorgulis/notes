Anatomy of a Shopify app

An app is not a plugin. It is your server, which Shopify has agreed to trust.

Your win today. When a client describes what they want, you can say which kind of app it is — and what that choice costs them in review time, billing, and who is allowed to install it. Getting this wrong is a rebuild, not a refactor.

How it works

A Shopify app is code that runs on your infrastructure. Shopify never hosts your logic. What Shopify holds is a record — a client ID, a client secret, the scopes you asked for, and where to reach you.

Shopify Your infrastructure ┌────────────────────┐ ┌──────────────────────────┐ │ app record │ │ your server │ │ client id │──── trusts ──▶│ admin UI (embedded) │ │ client secret │ │ webhook receiver │ │ scopes │ │ your database │ │ URLs │ │ your jobs │ └────────────────────┘ └──────────────────────────┘ │ ▲ │ extensions run INSIDE Shopify │ ▼ │ ┌────────────────────────────────────────┐ │ │ theme app extension (the storefront) │ │ │ checkout UI extension (the checkout) │────────┘ │ Shopify Function (server-side) │ they call back to you │ POS UI extension (the till) │ └────────────────────────────────────────┘

So an app has two halves. Your server, which you deploy and can debug. And extensions, which run on Shopify's side, where you cannot attach a debugger and cannot deploy a hotfix in thirty seconds. That asymmetry decides a lot of designs.

This is the decision to get right on day one.

For the integration work this Course is about — one client, their ERP, their store — the answer is almost always custom. You are not selling a product; you are building one merchant's plumbing.

Answer before reading on A client wants an app that syncs their ERP to their one store, and they ask whether they will be charged monthly for it. Which distribution, and what is your answer about billing? Say it out loud.

Custom distribution — one store, no App Store review, faster to ship. And on billing: they pay you, not Shopify. A custom app cannot use the Billing API at all, so there is no Shopify invoice line for it. That is usually what a client wants to hear, and it is a useful thing to be able to say without checking.

The config is code

Scopes, webhook subscriptions, URLs and extension declarations live in your app's configuration file, in your repo, under version control. That matters more than it sounds: it means a scope change is a reviewable diff, not something a colleague clicked in a dashboard at 6pm and cannot remember.

Where it hurts

Costs money — picking custom, then needing to sell it A custom app cannot charge through Shopify. If the client later decides to resell the integration to other merchants, you are not adding a feature — you are changing distribution, which means App Store review, mandatory compliance webhooks, protected customer data approval, and a listing. Ask "will anyone else ever install this?" before you choose, and write the answer down.
The legacy trap: apps created in the Shopify admin Older apps made directly in a store's admin cannot be created any more. Existing ones keep working, but they cannot use App Bridge, cannot use app extensions, and cannot use the Billing API. If you inherit one and the ticket says "add a theme app extension", the honest answer is that the app itself has to be replaced first.
Fails with no error — the extension you cannot debug Your server has logs. A Shopify Function does not run on your server. When an extension misbehaves, the tools you reach for first are not there. Design so the decisions live where you can observe them, and keep the extension thin.
The 100 KB Liquid limit on theme app extensions Theme app extensions have file and content size limits, and Liquid is capped at 100 KB. An exception can be requested if your app uses custom distribution or has Built for Shopify status — but Shopify's own note is that increasing it can hurt performance. Plan to stay under it rather than plan to ask.
Judgement, not documentation — "app" means four different things A client says "app" and means an icon in their admin. A PM says "app" and means the project. You say "app" and mean a client ID plus a server. Agree what the word means in the first meeting, or three people will approve three different scopes of work.

Say it out loud

Explain this to a beginner

What is a Shopify app? And why does choosing "custom" or "public" on day one matter more than any code you write?

Say it out loud. Then read on.

Now compare with a plain-words answer

An app is just your own server, plus a record at Shopify saying "this server is allowed to do these specific things to this shop". That is it. Shopify holds the identity, the password, the list of permissions and the addresses to call. It does not hold your code — your code is wherever you put it.

Some small pieces are the exception: bits that appear inside Shopify's own screens run on Shopify's side, not yours. Which means when one of those goes wrong you cannot look at your logs and you cannot push a quick fix. So you keep them thin and put the thinking on your own server.

Now the day-one choice. "Custom" means built for one shop: no review queue, quick to ship — and it cannot take money through Shopify at all. "Public" means it can be sold and billed, and it has to pass review.

Here is why that is not a technical decision. If you build custom and later the client wants to sell it, you do not flip a switch. You need review, billing, the mandatory privacy handling, and the ability to serve many shops instead of one. Each is real work, and together it reads as a rebuild.

So ask on day one: will anyone else ever install this? The question is free now and expensive later.

If you used any of these words, try again OAuth client · embedded app · App Bridge · distribution model · multi-tenancy · extension surface. "Your own server, plus a record saying it is allowed to do these things" is the explanation.

Build it

Task · 30 minutes Partner account
  1. Create an app and find, in the dashboard, each of the four things Shopify holds: the client ID, the secret, the scopes, the URLs. Note that your code is in none of them.
  2. Write down which distribution you chose, and the answer to "will anyone else ever install this?" — even if the answer is "probably not".
  3. List what you would have to add to switch: review, the Billing API, the three compliance webhooks, serving many shops.

Proof it worked: the resale answer is written down with a date. That one recorded sentence is the difference between a decision and a default.

Keep the extension thin · 45 minutes Dev store

Build one small extension that renders inside Shopify, then deliberately put a bug in it.

  1. Try to debug it the way you would debug your own server. You cannot — no logs of yours.
  2. Move the logic to your server and leave the extension as a thin display layer.
  3. Break it again and fix it from your side.

Proof it worked: the second fix needed no extension deploy. That is the whole argument for keeping extensions thin, and you now have felt it rather than read it.

Remember this

  • An app is your server plus a trust record. Shopify holds the client ID, secret, scopes and URLs. It never hosts your logic.
  • Extensions run on Shopify's side. No logs, no fast hotfix. Keep them thin.
  • Custom for one client, public for a product. Custom skips review and cannot bill through Shopify.
  • Custom apps cannot use the Billing API. The client pays you directly.
  • Admin-created legacy apps cannot use App Bridge, extensions, or billing, and cannot be created any more.
  • Theme app extension Liquid caps at 100 KB. Exceptions exist; staying under is better.
  • Config is code. A scope change should be a reviewable diff, not a click nobody remembers.

If you remember one thing: choose distribution before you write a line, because changing it later is a different project, not a change request.
