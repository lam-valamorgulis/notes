Track 2 · A3 · Lesson 7

Store 17 of four hundred

One tenant is a script. Four hundred tenants is a different job.

Your win today. You know which four things break when a working single-store sync meets many stores — and which of them you should design for now versus deliberately ignore.

How it works

Derive it: what is actually per-store?

Your sync works for one store. Now four hundred. Ask what is shared and what is per store, because every bug at this scale is something shared that should not have been.

ThingShared or per store?What breaks if you get it wrong
Rate-limit budgetPer app and storeA global limiter throttles 399 stores to protect one
Access tokenPer storeRevoked individually, at any time, without telling you
WatermarkPer storeOne shared watermark skips data for everyone
Id mappingPer storeProduct 12 in one store is product 99 in another
Ownership rulesUsually sharedPer-store overrides multiply your test matrix
Plan tierPer storePlus gets 10× the bucket and skips one throttle

The rate-limit row is the one that surprises people, and it cuts both ways. The bucket is per app and store, so a global rate limiter is wrong — it makes 400 stores share one store's budget. But a per-process limiter is also wrong, because ten workers on the same store share that store's bucket. The correct shape: one budget per store, shared across all workers.

Then four things break

1. NOISY NEIGHBOUR one huge store starves 399 small ones 2. FAILURE ISOLATION one bad store's errors stop the loop for everyone 3. HEAD-OF-LINE store 17 is at the front and slow; 18-400 wait 4. FLEET BLINDNESS "is it working?" has 400 answers and you show one

1 · The noisy neighbour

One store has 400,000 variants; the rest have 2,000. A naive loop spends most of every cycle on it. Fix: work is scheduled per store with a cap on how much of a cycle any one store may consume, and big stores get their own cadence rather than being squeezed into the common one.

2 · Failure isolation

Store 17's token was revoked. A single try/catch around the whole loop means stores 18 to 400 never run. Every store must be an independent unit of work that can fail alone. This sounds obvious and is the most common real outage in multi-tenant syncs, because the single-store version had one loop and nobody re-thought it.

3 · Head-of-line blocking

Even with isolation, a strictly ordered queue lets one slow store delay the rest. Partition the work by store id so each store has its own lane. Then a slow store is slow only for itself.

4 · Fleet blindness

The four numbers from A2.4 — queue depth, dead-letters, rate-limit headroom, reconciliation drift — become four numbers per store. A single average hides everything: 399 healthy stores and one broken one averages to "fine". Report the worst store and the count of stores outside tolerance, never the mean.

What to build now, and what not to

Being honest about this is part of the skill. Most of the above is wasted effort on a single-store project, and the guessed abstractions get deleted.

Do now, even for one storeDo not build until you need it
Store id as a parameter, never a global or an env varA scheduler with fairness policies
Watermark and mapping keyed by storePer-store ownership overrides
One unit of work = one store, able to fail aloneSharding across databases
Metrics tagged with the storeA per-store dashboard

The left column costs almost nothing today and is painful to retrofit, because it means touching every query. The right column is real engineering that should be driven by a real second store.

Answer before reading on You add a global rate limiter set to Shopify's documented bucket, to "be a good citizen". You run 400 stores. What have you built?

A bottleneck 400 times too small. The bucket is per app and store, so each store had its own budget and you have just made them queue for a single shared one. Throughput collapses to roughly one store's worth for the whole fleet, and it looks like a Shopify problem in your metrics — headroom appears fine per call, while the queue grows forever. The limiter must be keyed by store, and shared across workers within that store.

Where it hurts

Costs money — a global rate limiter As above. Every store waits for every other store. The symptom is a growing queue with healthy per-call metrics, which sends you looking in the wrong place for days.
Costs money — one try/catch around the whole fleet Store 17 fails and stores 18 to 400 stop syncing. Wrong prices and wrong stock across hundreds of merchants, from one revoked token.
Fails with no error — the averaged dashboard 399 healthy and 1 broken averages to healthy. The broken store's merchant finds out before you do. Report the worst, and the count outside tolerance.
Fails with no error — a token revoked without notice A merchant uninstalls or rotates. Your calls fail for that store only. With per-store isolation this is a small, visible event; without it, it is an outage. Treat auth failure for one store as a first-class state, not an exception.
A shared watermark One last_seen_at row for all stores means the fastest store's progress hides every slower store's gap. Data is skipped for most of the fleet, silently. Key it by store from the first line — this is the cheapest thing on the list and the worst to retrofit.
Plan differences are invisible in code A Plus store gets roughly 10× the bucket and is exempt from the extra variant throttle. If your limiter assumes one tier, you either throttle Plus stores unnecessarily or overrun small ones. Read the plan and let the limiter adapt.
Judgement, not documentation — resist per-store rules Somebody will ask for a per-store exception to an ownership rule. Each one doubles the test matrix and none can be removed later. Push hard for one set of rules with configuration, not per-store behaviour, and record every exception you are forced to accept.

What you say to a client/PM

When asked to move from one store to many The sync logic doesn't change much — what changes is the plumbing around it. Each store needs its own credentials, its own place-marker, and its own share of Shopify's rate limit, and one store failing mustn't stop the others. That's the real work, and it's mostly invisible from the outside, which is why it looks smaller than it is. Sets the expectation that a re-platform to multi-tenant is not a small change, and says why it looks like one.
When a PM asks "is the fleet healthy?" I won't give you an average, because 399 fine and one broken averages to fine. What I'll report is the number of stores outside tolerance and which ones. Today that's two, both waiting on the merchant to reinstall. Refuses the misleading metric and replaces it with an actionable one, in the same breath.

Remember this

  • The rate-limit bucket is per app and store. One budget per store, shared across workers within it.
  • A global limiter is a bottleneck 400× too small. A per-process one over-runs a single store.
  • One store = one unit of work that can fail alone. One try/catch around the fleet is the classic outage.
  • Partition queues by store, or one slow store delays everyone.
  • Never average fleet health. Report the worst store and the count outside tolerance.
  • Watermark and mapping keyed by store from day one. Cheap now, painful to retrofit.
  • Plan tier changes the limits. Plus gets roughly 10× the bucket and skips the extra variant throttle.

If you remember one thing: pass the store id as a parameter from the very first line — everything else on this list can wait, and that one cannot.
