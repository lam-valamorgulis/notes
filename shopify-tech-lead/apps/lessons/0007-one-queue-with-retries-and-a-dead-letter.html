Track 2 · A2 · Lesson 3

One queue, with retries and a dead-letter

The most dangerous response Shopify sends you is a 200 that means "no".

Your win today. A worker that reads its own rate-limit budget from every response, slows down before it is told to, and separates "try again" from "this will never work" instead of retrying both forever.

How it works

The fact that changes your error handling

REST returns 429 Too Many Requests when you are throttled. GraphQL returns 200 OK with the failure inside the response body:

{
  "errors": [
    { "message": "Throttled",
      "extensions": { "code": "THROTTLED" } }
  ],
  "extensions": {
    "cost": {
      "requestedQueryCost": 202,
      "actualQueryCost": null,
      "throttleStatus": {
        "maximumAvailable": 1000,
        "currentlyAvailable": 186,
        "restoreRate": 50
      }
    }
  }
}

So if (response.ok) is not an error check on the GraphQL Admin API. A throttled request is HTTP 200. A validation failure is HTTP 200. A partial success with userErrors is HTTP 200. You must read the body, every time, on three levels:

LevelWhereMeans
TransportHTTP statusDid the request arrive at all
Queryerrors[]Malformed, unauthorised, or THROTTLED
Businessdata.*.userErrors[]Shopify understood you and refused

Verified 2026-08-23: the extensions.cost shape, throttleStatus fields, the 1,000-point bucket with a 50/second restore in the documented example, and that a throttled GraphQL request returns 200 OK with a THROTTLED error in the body while REST returns 429 — Migrate to GraphQL from REST and the GraphQL Admin API reference.

Every response tells you your remaining budget

throttleStatus arrives on successful responses too. That is the important part: you never have to be throttled to know you are close. Read currentlyAvailable after each call and pause when it drops below the cost of your next query.

a well-behaved worker loop: if (available < nextQueryCost + margin) sleep( (nextQueryCost - available) / restoreRate ) send read extensions.cost.throttleStatus ← on success as well available = currentlyAvailable ── this is a SPEED LIMITER, not error handling. Being throttled means the limiter failed.

The point is worth stating plainly: retrying on 429 is recovery. Reading throttleStatus is prevention. Most integrations only do the first and spend their lives at the limit.

Classify before you retry

ClassExamplesDo
Transient5xx, timeout, connection resetRetry with exponential backoff and jitter
ThrottledTHROTTLED, or REST 429Wait for the budget. Honour Retry-After on REST. Not a failure — a queue
TerminaluserErrors, bad scope, invalid fieldDo not retry. Dead-letter it immediately
PoisonAnything that fails the same way N timesDead-letter with the full error body

Retrying a terminal error is the most common waste in a sync. A product rejected for a missing required field will be rejected identically eight times, burning rate-limit budget that the valid records needed.

Jitter, and why

Plain exponential backoff makes every failed job retry at the same moment, because they all failed at the same moment. The retry storm then reproduces the outage. Add randomness: delay = base · 2^attempt · (0.5 + random·0.5). This costs one line and prevents a self-inflicted second incident.

Answer before reading on Your worker retries on any non-2XX. It processes 40,000 variant updates, 900 of which have a missing required field. What does the run look like, and what is the real cost?

It looks like a slow success. The 900 bad records each fail 8 times — 7,200 wasted calls — and every one of those consumed rate-limit budget the other 39,100 needed. So the run takes far longer, and if the budget runs out you also start failing valid records, which then look broken too. Meanwhile the 900 genuinely bad records are still not in a list anyone can read. Terminal errors must dead-letter on the first attempt.

Where it hurts

Costs money — treating HTTP 200 as success The single most expensive habit on this API. A throttled call, a validation failure and a partial success all return 200. Code that checks only the status silently drops real failures and reports a clean run.
Costs money — retrying terminal errors Eight attempts at something that can never succeed, multiplied by every bad record, spent out of the same budget your good records need. Classify first, retry second.
Fails with no error — no jitter Synchronised retries after an outage reproduce the outage. Your monitoring shows recovery, then a second spike you caused. Nothing identifies you as the cause.
Fails with no error — the unread dead-letter queue Failures go somewhere, so the main path looks healthy. Nobody looks. Alert on the count of unresolved dead-letter rows, not on the existence of the table.
Concurrency multiplies against one bucket The rate limit is per app and store. Ten workers on one store share one bucket, so scaling workers does not scale throughput — it just distributes the throttling. The budget has to be shared state, not per-process.
A single query may not exceed 1,000 points That ceiling applies regardless of plan and is checked before execution, from the requested cost. A query that asks for too much per page fails at every bucket level, so no amount of waiting helps. Reduce the page size instead.
Judgement, not documentation — one queue, not five Splitting into per-entity queues feels tidy and gives you five independent things competing for one rate-limit bucket, with no shared view of priority. One queue with a priority field is easier to reason about and easier to drain.

What you say to a client/PM

When asked why the sync is "slow" It's not slow, it's paced. Shopify gives us a budget of API calls and we deliberately stay under it — if we push through, they start rejecting us and everything takes longer. Your plan sets the budget, so a higher plan genuinely makes this faster if that ever matters. Reframes pacing as deliberate, and names the one lever the client actually controls.
When 900 products did not sync They were rejected, not delayed — each has a specific reason and I've got the list. I don't retry those, because they'd fail identically and eat the capacity the working records need. Send me the list back with fixes and they'll go through on the next run. Separates "failed" from "not tried yet", which is the distinction that makes a client trust the report.
When a PM suggests "just run more workers to speed it up" It won't help — the limit is per store, not per worker. Ten workers share the same budget, so I'd get the same throughput and more throttling. If we need it faster, the levers are fewer calls per product or a higher Shopify plan. Kills a plausible-sounding suggestion with a mechanism, then offers the two real options. Never just say no.

Remember this

  • GraphQL returns 200 when throttled. if (response.ok) is not an error check.
  • Check three levels: HTTP status, errors[], and userErrors[].
  • throttleStatus comes back on success too. Use it to slow down before you are told to.
  • Classify: transient, throttled, terminal, poison. Only the first two are worth retrying.
  • Never retry a userError. It will fail identically and spend budget the good records need.
  • Add jitter. Synchronised retries recreate the outage you just recovered from.
  • The bucket is per app and store. More workers redistribute throttling; they do not add throughput.

If you remember one thing: read the rate-limit budget on every response and stay under it — being throttled means your speed limiter already failed.
