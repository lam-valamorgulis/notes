Track 2 · A2 · Lesson 4

Run it: docker-compose, CI, and what to log

One command to start it. And the four numbers that tell you whether it is actually working.

Your win today. A sync you can start from a clean machine in one command, a test suite that never touches Shopify, and a dashboard that answers "is it healthy?" without you reading a single log line.

How it works

One command, from nothing

cp .env.example .env     # then fill it in
docker compose up -d     # Postgres + Redis
npm install
npm run generate         # the synthetic catalogue
npm run dev

The measure of this is not elegance. It is: could someone who has never seen the repo run it in ten minutes, and can you still run it in six months? The docker-compose.yml in the Project deliberately declares no volumes, so docker compose down -v returns you to a clean state — which is what you want constantly while learning, and rarely later.

One detail that saves an afternoon: give Postgres a healthcheck. Without it the app starts before Postgres accepts connections and the first run fails with ECONNREFUSED, which reads like a configuration error and is not.

Three test layers, and only one is allowed near Shopify

LayerTestsTalks toRuns
UnitOwnership rules, conflict resolution, watermark mathsNothingEvery save
IntegrationReal Postgres, real queue, a fake ShopifyDocker onlyEvery push
ContractThat your queries are still validThe schema, not a storeNightly, and on version bumps

CI must never need a Shopify store. A pipeline that depends on a live store is a pipeline that fails when someone else's token expires.

The contract layer is the one people skip and then regret. Validate your GraphQL documents against the schema for your pinned version, in CI. This Course found two deprecated fields that way — ShopPlan.displayName and Market.enabled — in queries that looked obviously correct. A quarterly version bump becomes a red build instead of a production surprise.

What to log — and what not to

Structured, one object per line, with a correlation_id threaded from the webhook that started the work through every retry. Without that thread, a failure at 2am is unreadable.

Always logNever log
The message id, the entity, the attempt numberThe access token, or any part of it
The remaining rate-limit budget on each callWhole webhook payloads — they carry personal data
Decisions: "skipped, shadow matched"Customer names, emails, addresses
Every terminal error with its full bodyStaff names from event feeds

That last one is real, not theoretical. Shopify's Product.events messages contain staff full names and email addresses in plain text. Anything that logs those events wholesale is quietly building a staff PII store inside your log retention.

The four numbers

Logs explain a problem. These tell you a problem exists:

1. queue depth ── going up and not coming down = falling behind 2. unresolved dead-letters ── a work list, not a metric to admire 3. rate-limit headroom ── the min of currentlyAvailable over a window 4. reconciliation drift ── records where shadow ≠ Shopify

Number 4 is the only one that measures correctness. The first three can all look perfect while the data is wrong, which is exactly how a broken sync survives for months.

Answer before reading on Queue depth is zero, no dead-letters, plenty of rate-limit headroom, and no errors in the logs for a week. Can you tell the client the sync is healthy?

No. Every one of those is true of a sync that is doing nothing — a deleted webhook subscription, a watermark stuck in the future, a filter that matches no rows. All three "green" signals measure effort, not outcome. Only reconciliation drift distinguishes "working" from "idle", which is why it is the number you put in front of a client.

Where it hurts

Costs money — a token in the logs Log the request headers "just for debugging" and the access token is now in your log store, your log vendor, and any backup of either. It grants read and write to the whole store. This is not recoverable by deleting a log line, exactly like a secret in git history.
Costs money — payloads in the logs An order webhook contains a name, an email and an address. Logging payloads wholesale turns your logging system into a customer-data store, with all the privacy obligations from A1.4 and none of the intent.
Fails with no error — green dashboards on an idle sync The scenario above. Nothing measures whether work happened, only whether errors did. This is the most common way a sync is broken for months.
Fails with no error — no healthcheck on Postgres The app starts before the database is ready and dies on the first query. The message points at connection settings, which are fine. Minutes lost every time a new person clones the repo.
CI that needs a real store It passes until someone's token expires, a dev store is deleted, or a rate limit hits during a build. Then the pipeline is red for a reason unrelated to the change, and people start ignoring red pipelines.
No correlation id One webhook produces a receive line, three retry lines and a dead-letter line, in a log shared with thousands of others. Without a shared id you cannot assemble the story, and the incident takes an hour instead of a minute.
Judgement, not documentation — do not alert on everything An alert that fires weekly and is always ignored is worse than no alert, because it trains people to dismiss the channel. Alert on two things: unresolved dead-letters above a threshold, and reconciliation drift above a threshold. Everything else is a dashboard.

What you say to a client/PM

When a client asks "how do we know it's working?" Not from the absence of errors — a sync that's doing nothing has no errors either. We run a nightly check that compares what we sent against what's actually in Shopify and reports the differences. If that number is zero, it's working. That's the one I'd put on a report. Gives them a single number that means something, and pre-empts the false comfort of a quiet log.
When asked to add "just a bit of extra logging" to debug a live issue I'll add it around the decision, not the payload. Order and customer payloads have names and emails in them, and once those are in our logs they're subject to the same privacy rules as a database. I can get you the same answer without that. Says yes to the need and no to the method, with a reason that is about their liability rather than your preference.
When a PM asks why tests do not run against the real store Because then a build fails when someone's token expires or we hit a rate limit — nothing to do with the code being tested. We test the logic against a fake Shopify, and separately we validate our queries against Shopify's real schema every night. That second one already caught two fields Shopify had deprecated. Has a concrete win to point at. An argument with evidence ends the conversation.

Remember this

  • One command from a clean machine. Declare a Postgres healthcheck, or the first run fails misleadingly.
  • Three test layers. Unit needs nothing, integration needs Docker, contract needs the schema. CI never needs a store.
  • Validate your GraphQL in CI. That is how two deprecated fields were caught in this Course.
  • Thread a correlation_id from the webhook through every retry, or logs are unreadable.
  • Never log tokens or payloads. A token in a log is as unrecoverable as a secret in git history.
  • Four numbers: queue depth, unresolved dead-letters, rate-limit headroom, reconciliation drift.
  • Only drift measures correctness. The other three look perfect on a sync that does nothing.

If you remember one thing: no errors is not the same as working — only a comparison against reality tells you the sync is alive.
