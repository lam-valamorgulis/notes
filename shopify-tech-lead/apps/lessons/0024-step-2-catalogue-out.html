Track 2 · A5 · Project Step 2

Catalogue out

46,000 variants into a store that only lets you make two requests a second.

Your win today. The whole synthetic catalogue in your Dev store, loaded by a bulk operation rather than 10,000 separate calls — and a second run that changes almost nothing and finishes in seconds.

How it works

Where you push — answer this before anything else

Read this twice You push to your own Dev store. Never to a client store. A client store has real customers, real orders and live sales channels; 10,000 fake products there is an incident, not a mistake you quietly undo. The Project has exactly one SHOPIFY_SHOP_DOMAIN variable and no second one, on purpose — there is no supported way for this code to write to a store that is not yours.

If the Dev store does not exist yet, that is Step 2's first task, and it takes about two minutes:

  1. Dev Dashboard → Stores → Create store. Pick a non-Plus plan. You want the small rate-limit bucket: 40 requests with a 2/second leak, not Plus's 400 and 20/second. Throttling is the lesson.
  2. Create a custom app on that store and install it.
  3. Copy the Admin API access token — it starts with shpat_ — into project/.env along with the store's *.myshopify.com domain.

Three ways to push, and why only one survives this volume

The bulk import flow

1. stagedUploadsCreate ── reserve a slot, get a URL + form params │ 2. POST the JSONL to that URL ── the `file` field goes LAST in the form │ 3. bulkOperationRunMutation ── pass the mutation as a STRING ( mutation: "...", stagedUploadPath: "tmp/uploads/x.jsonl" ) │ 4. wait ──┬── poll bulkOperation(id:) (2026-01 and higher) └── or subscribe to bulk_operations/finish │ 5. download the result JSONL from `url` ── and READ IT. Per-line userErrors live here, nowhere else.

Verified 2026-08-23 against Bulk import data with the GraphQL Admin API: JSONL capped at 100 MB · must finish within 24 hours or it is stopped and marked failed · the mutation is limited to one connection field · in 2026-01 and higher an app may run 5 concurrent bulk mutation operations per shop, where older versions allowed only one of each type · poll with bulkOperation(id:) on 2026-01+, or currentBulkOperation before that. All three mutations in this Lesson were run through the schema validator before being written down.

Which mutation to run in bulk

productSet is the one you want, because it is an upsert: give it a stable identifier and it creates the product the first time and updates it every time after. That is what makes the load re-runnable, and re-runnable is the whole point.

The docs contradict themselves here — check it yourself The bulk-import guide's argument table lists "Valid values: productCreate, collectionCreate, productUpdate, productUpdateMedia" for the mutation argument. The same page's own Limitations section says you "can supply any GraphQL Admin API mutation ... except bulkOperationRunMutation and bulkOperationRunQuery themselves". Those cannot both be true, and productSet is not in the four-value list.

Do not resolve this by reasoning. Resolve it by running it — one product, in a bulk operation, on your Dev store. If it is refused, fall back to productCreate for the first load and productUpdate afterwards, and keep your own mapping table so you know which is which. Finding out now costs ten minutes. Finding out during a client's cutover costs the weekend.
Before you read on Your bulk operation reports status: COMPLETED. Nothing errored. Are all 10,000 products in? Say why or why not.

No — COMPLETED only means the operation ran to the end. Each individual line can still have failed with its own userErrors, and those live only in the result JSONL at url. An import that "completed" with 4,000 silent per-line failures looks exactly like a success from the outside. Download the result and count it.

Then make it re-runnable

Run the whole load a second time. Almost nothing has changed, so almost nothing should be written. That means filtering on your watermark — the highest updatedAt you actually saw — and pushing only what moved. On the real store this Course sampled, roughly a few percent of rows change on a given day. A sync that re-pushes everything nightly works right up until the catalogue grows, and then it stops finishing before morning.

Where it hurts

Costs money — productSet deletes what you omit productSet treats the input as the whole desired state. Leave a variant out of the list and it is removed, not ignored. Send a partial product and you delete the rest of it. This is correct behaviour and it is the single most expensive surprise in the mutation. Send complete objects, always.
Fails with no error — COMPLETED is not "worked" Per-line userErrors appear only in the downloaded result file. Never treat the operation status as the outcome. Count the successes and compare them to the line count you uploaded.
Fails with no error — the form field order When you POST the JSONL to the staged URL, the file field must be last in the multipart form. Put it earlier and the upload is rejected or silently wrong, and the error you get points nowhere near the cause.
100 MB, and your file is bigger than you think The generated catalogue is already about 25 MB as plain records. Wrapped as productSet variables — every variant, every option, every metafield — it grows well past that. Chunk the upload and count bytes as you write, rather than discovering the cap at 99%. On 2026-01+ you may run five operations at once, so chunking costs you little.
One connection field The mutation you hand to bulkOperationRunMutation may contain only one connection. A productSet selection asking for both variants and media is rejected. Keep the selection set tiny — you only need the id and the errors.
Judgement, not documentation — the 24-hour clock A bulk operation that exceeds 24 hours is stopped and marked failed. Nothing tells you at hour 23. If a load is big enough that this is even conceivable, it is too big: split it.
Your Dev store is slower than the client's, and that is the point The store this catalogue was modelled on is Plus, which multiplies the buckets by ten and is exempt from the extra variant throttle entirely. Your non-Plus Dev store is not. Expect the load to behave worse for you than for the real store. That gap is the experiment, not a problem to fix.

Say it out loud

Explain this to a beginner

You are loading 10,000 products. Explain why you do not make 10,000 API calls — and why productSet is dangerous if you send an incomplete object.

Say it out loud. Then read on.

Now compare with a plain-words answer

Because 10,000 separate requests means 10,000 chances to be told you are going too fast, plus 10,000 round trips. Instead you write everything into one file, hand the file over, and let Shopify work through it. One conversation instead of ten thousand.

The catch is knowing when it actually worked. The job reports finished and tells you how many lines it processed — both of which measure effort, not success. The individual failures are written in a results file you have to go and fetch. Skip that and a load that lost 400 products looks identical to a perfect one.

On the dangerous mutation: some operations set the whole state of a thing rather than editing part of it. So if you send a product with only its title filled in, you have not "updated the title" — you have said "this product consists of a title and nothing else", and the rest is removed.

Absolute writes are what make retries safe, but absolute has to mean complete. Half a truth is more destructive than a change, because it deletes.

If you used any of these words, try again bulk operation · JSONL · staged upload · whole-state mutation · partial update. "One conversation instead of ten thousand, and the truth is in the results file" is the explanation.

Build it

Task · 3 hours Dev store
  1. Run the full five steps: stagedUploadsCreate → upload → bulkOperationRunMutation → poll → download the results.
  2. Put 20 deliberately invalid products in your 10,000. Count the failures from the results file.
  3. Compare what the status and line count told you against what the file told you.
  4. Now send a productSet with only the title filled in. Look at what happened to the rest.
  5. Confirm your domain variable points at your Dev store and there is no second one anywhere in the code.

Proof it worked: your loader reports "9,980 succeeded, 20 failed" from the results file, not "COMPLETED". And you have erased a product's fields with a partial payload once, on purpose, so you will never do it by accident.

The limits, in code · 30 minutes Dev store

Put the five limits where your loader can enforce them: 100 MB · 24 hours · one connection field · 5 concurrent (2026-01+) · 250-item arrays. Then keep the results file as your id mapping.

Proof it worked: your loader refuses to build a file over 100 MB rather than finding out from Shopify, and your mapping table was populated for free from the results.

Remember this

  • You push to your own Dev store. Never a client store. One domain variable, no second one.
  • Bulk operation, not 10,000 calls. stagedUploadsCreate → upload → bulkOperationRunMutation → poll → download the results.
  • COMPLETED is not "worked". Per-line userErrors live only in the result JSONL. Count them.
  • productSet deletes what you omit. It sets whole state. Always send complete objects.
  • Limits: 100 MB JSONL · 24 hours · one connection field · 5 concurrent on 2026-01+.
  • The file form field goes last. Out of order fails in a way that points nowhere.
  • The docs disagree about which mutations bulk accepts. Test it on your Dev store; do not reason about it.

If you remember one thing: a load that reports success is not a load that worked — the truth is in the results file, and reading it is the job.

Ask questions. Say "write the pusher" when the Dev store exists and the .env is filled, and we build it together against real limits.
