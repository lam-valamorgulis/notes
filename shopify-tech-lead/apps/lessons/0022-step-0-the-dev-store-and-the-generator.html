Track 2 · A5 · Project Step 0

The Dev store, the Shape sample, and the generator

Before you sync anything, you need somewhere safe to sync to, and data worth syncing.

Your win today. A Dev store you own, a one-page record of what a real store's data actually looks like, and a script that turns that record into a catalogue big enough to hurt. Nothing after this works without it.

How it works

You need two things that pull in opposite directions. Realistic data, and a store you can destroy. A client's store gives you the first and forbids the second. A blank Dev store gives you the second and none of the first.

So you split them. Read the real store for its shape. Generate the volume yourself.

Client store ──read only──► Shape sample ──► generator ──► Dev store (real, live) (counts, field (your code) (yours, names, tags — break it no content) freely) What crosses the first arrow: "1 option axis, 5 values, 2 metafield namespaces, 3 locations, ~40k products" What NEVER crosses it: a title, a SKU, a price, a customer, an order

1 · Create the Dev store

In the Dev Dashboard: Stores → Create store, then pick a plan. The plan choice matters, and the obvious answer is wrong.

PlanREST bucket / leakGood for
Basic / Grow / Advanced40 requests, 2/secondThis Project. You meet real 429s
Plus400 requests, 20/secondTrack 1 P5 only — checkout, B2B, Flow

Choose a non-Plus plan. Plus multiplies your rate limits by ten, which sounds generous and is actually a trap: it hides the throttling problem this whole Track exists to teach. Create a second, Plus Dev store later when Track 1 needs one. Dev stores cost nothing.

Verified 2026-08-23: dev stores can be created on any plan including Plus at no cost, and cannot process real transactions — Dev stores. Bucket sizes — REST rate limits.

2 · Install a custom app on it and take the token

You need an Admin API access token, the kind that starts with shpat_. Ask for the smallest set of scopes that makes your queries run. The Shape sample query below needs exactly these, and no more:

read_products
read_orders
read_marketplace_orders
read_locations
read_inventory
read_markets_home

Put it in project/.env, which is gitignored and cannot be published. Pin the API version in the same file — 2026-07 is the latest stable today. Never let a client library pick "latest" for you.

Before you read on Why is pinning the API version a line item in an estimate, not a detail? Say the answer out loud before you continue.

Because a new stable version lands every quarter, each one is supported for a minimum of 12 months, and an unpinned or retired version makes Shopify fall forward to the oldest version it still serves — silently changing your app's behaviour on a day you did not choose. Version 2026-07 is accessible until 16 July 2027.

Verified 2026-08-23: quarterly releases, 12-month minimum support, 9-month overlap, and the fall-forward rule — About Shopify API versioning.

3 · Take the Shape sample

Run this against the Client store, read-only. It answers "what shape is a real catalogue?" without copying a single piece of content.

query ShapeSample {
  shop {
    name
    plan { publicDisplayName partnerDevelopment shopifyPlus }
  }
  productsCount        { count precision }
  productVariantsCount { count precision }
  locationsCount       { count precision }
  ordersCount          { count precision }
  locations(first: 50) {
    nodes { id name isActive shipsInventory }
  }
  productMetafieldDefs: metafieldDefinitions(first: 100, ownerType: PRODUCT) {
    nodes { namespace key type { name } validationStatus }
  }
  variantMetafieldDefs: metafieldDefinitions(first: 100, ownerType: PRODUCTVARIANT) {
    nodes { namespace key type { name } }
  }
}

Then page through products for the structural facts — how many option axes, how many variants each, which tag prefixes repeat, what productType and vendor are actually used for:

query TagAndTypeShape($cursor: String) {
  products(first: 250, after: $cursor) {
    pageInfo { hasNextPage endCursor }
    nodes {
      productType
      vendor
      tags
      hasOnlyDefaultVariant
      variantsCount { count }
      options { name optionValues { name } }
    }
  }
}

Both queries validated against the 2026-07 Admin schema on 2026-08-23. The first one initially used plan { displayName }, which the validator rejected as deprecated in favour of publicDisplayName. That is the value of validating instead of trusting: a field that "obviously exists" had already moved.

4 · Write the record, then the generator

Write the answers into project/tools/shape-sample.md as numbers and names only. Then write project/tools/generate-catalogue.ts so it reads that file and produces a catalogue of the same shape at the same scale, with invented titles and SKUs.

Type it from a blank file. Its whole job is: read the shape, loop, emit products whose structure matches and whose content does not exist anywhere real.

Where it hurts

Permission confusion — the expensive one Your client said you may download product data to practise. They did not say you may publish it. This Course is rsynced to a public site, and a public git history cannot be un-published. Those are two different permissions and only one was granted. This is why the catalogue is generated, not copied — the reasoning is written down in ADR 0001.
Fails with no error — the Plus dev store Pick Plus and everything works beautifully. You will build a sync that has never been throttled, ship it to a Basic-plan client, and watch it fall over on day one. There is no error message for "your test environment was too generous".
Fails with no error — precision Every *Count field returns a precision next to the number, and it has two values. AT_LEAST means "a limit was imposed and reached" — so your "40,000 products" is really "at least 40,000", which is a different number to size a migration against. And EXACT is not a promise of freshness either: the docs say plainly that "a write may not be reflected instantaneously". In a sync, a count you read one second after writing can legitimately disagree with what you wrote. Build your reconciliation around that instead of being surprised by it. Verified 2026-08-23 — CountPrecision. Several count queries also take a limit argument, which is what triggers AT_LEAST when it is hit.
The metafield trap you will meet for real A live integration can write metafields that have no metafield definition. The data is there, the admin shows nothing, and it is not properly queryable or validated. If metafieldDefinitions comes back empty while products clearly carry custom data, you have found this — not an absence of data. Chapter P2 is this trap in full.
Not in the docs — Store Credit and Gift Cards Dev stores do not support them. Any lesson touching store credit can be taught but not demonstrated here. Plan around it rather than debugging it for an afternoon.
Scope creep on the token It is tempting to grant write_products now "to save time later". Do not. This token can reach a store, and Step 0 only reads. A read-only token cannot cause a bad afternoon.

What you say to a client/PM

When a client offers you a copy of their live data I'd rather not take a copy of the real catalogue. What I need is its shape — how many products, how many variants each, which custom fields you use. I'll build test data that matches that shape. You get the same confidence, and your customer data never leaves your systems. This is the rare answer that is both safer for them and easier for you. It also signals that you think about data handling before someone makes you.
When a PM asks why you need a test store at all Because the failure I need to find is throttling, and it only appears at volume. On a small test set the sync looks perfect. I'd rather find it this week on a store nobody uses than in week one of go-live. Ties the cost of the environment to a specific risk. "Best practice" persuades nobody; a named failure does.
When someone asks for a date and you have not measured yet I can give you a range now and a number after I've loaded the real volume. The reason I'm careful is the throttle: Shopify caps new variants once a store passes half a million, and I need to know if you're near that line. Same work, very different timeline either side of it. A range plus the reason for the range. Chapter R3 drills this sentence pattern on its own, because it is the one you will need most.

Remember this

  • Shape crosses, content does not. Counts, field names and tag conventions are safe to record. Titles, SKUs, prices, customers and orders are not.
  • Pick a non-Plus Dev store. 40 requests with a 2/second leak, not 400 and 20/second. You want the 429s.
  • Pin the API version. 2026-07 is current, accessible until 16 July 2027. Unpinned means Shopify falls forward and your behaviour changes on a day you did not pick.
  • Smallest scopes that work. Step 0 reads. A read-only token cannot ruin a day.
  • Read precision, not just count. AT_LEAST is not EXACT, and sizing off the wrong one is how estimates die.
  • Empty metafieldDefinitions plus visible custom data means undefined metafields, not missing data.
  • Validate every query before you trust it. plan { displayName } was already deprecated when this Lesson was written.

If you remember one thing: you are allowed to copy a store's shape, never its contents — and the generator is what makes that a practical rule rather than a pious one.
