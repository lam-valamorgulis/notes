Track 2 · A5 · Project Step 1

The Fake ERP

Build the other side of the sync yourself, so you can cause its failures instead of waiting for them.

Your win today. A small service that behaves like every ERP you will ever integrate with — and a set of switches that make it lie, stall, repeat itself, and change its mind mid-batch, on demand.

How it works

A sync needs two systems. Shopify is one. The other has to exist before you can write a single line of sync code.

You could point at someone's public sandbox. Do not. The entire skill you are building is handling failure, and you cannot ask a stranger's API to go down at 14:32 on a Tuesday. So you write this side. Not because it is realistic — because it is controllable.

┌─────────────────── Fake ERP ───────────────────┐ │ │ │ GET /items?updatedSince=&cursor= │ the read path │ GET /items/:id │ │ GET /stock?locationId= │ │ POST /orders (Shopify → ERP) │ the write path │ │ │ ── failure switches ────────────────────── │ │ ERP_FAIL_MODE = stale | duplicate | │ │ down | price-mid-sync │ │ ERP_FAIL_RATE = 0.0 .. 1.0 │ └────────────────────────────────────────────────┘ ▲ │ │ your sync service ▼ └──────── Postgres ──────┘

What it owns, and what it does not

This is the decision that matters most, and it is the one most integrations get wrong. Write it down before you write code:

FieldOwnerDirection
title, description, product typeFake ERPERP → Shopify
priceFake ERPERP → Shopify
SKU / identityFake ERPERP → Shopify
inventory quantityShopifyShopify → ERP
ordersShopifyShopify → ERP

Look at that table again. Ownership is split down the middle of a single product. The ERP owns its title and price; Shopify owns how many there are. That is not a contrived teaching example — it is the most common real arrangement, and it is where two-way syncs go wrong. Chapter A3 is this idea in full.

The endpoints, and why each one is shaped that way

GET /items?updatedSince=<ts>&cursor=<c> — the workhorse. Two rules. It returns absolute values, never "price went up by 2". And it is cursor-paged, not page-numbered, so rows changing mid-scan cannot make you skip or repeat one.

POST /orders — the write path, and the one that must be idempotent. Send the same order twice and the second call returns the first result rather than creating a duplicate. Give it a client-supplied key so you can prove that.

The failure switches — the actual point of Step 1

SwitchWhat it doesThe bug it lets you cause
staleServes data from N seconds agoYou overwrite Shopify with an older truth
duplicateReturns the same item twice in one pageDouble-processing, if you are not idempotent
down503s for N secondsThe backlog, and whether your retry is polite
price-mid-syncChanges a price between page 1 and page 3A batch that is internally inconsistent
Cover the table and answer You run a full catalogue scan. Page 1 has item A at $10. Between page 1 and page 3, the ERP changes A to $12. Your scan finishes and writes everything it collected. What is now in Shopify, and is it wrong? Say it out loud.

Shopify has $10. Whether that is wrong depends on something you have not built yet: if your next scan picks A up again because its updatedAt moved, the system is eventually consistent and $10 was merely temporary. If your scan filters on updatedSince using the time the scan started, you may never see the change at all, and $10 is permanent. Same code, one line different, and one version quietly sells at the wrong price forever. That single line is why price-mid-sync exists.

Build it

Type it from a blank file. NestJS, Postgres, in project/fake-erp/. Smallest thing that satisfies all of the above:

  • An items table: id, sku, title, price, updatedAt, and a soft-delete flag.
  • A stock table keyed by (itemId, locationId).
  • An orders inbox with a unique constraint on the client-supplied key.
  • A middleware that reads the two failure switches and misbehaves accordingly.
  • A seed command that loads the synthetic catalogue from Step 0.

Do not add authentication beyond a static bearer token from .env. It is not the lesson, and a real vendor's auth gets its own treatment in Chapter A4.

Where it hurts

Costs money — deltas instead of absolutes An ERP that sends "price +2" instead of "price is 12" cannot be replayed. Re-run the batch after a crash and you add 2 twice. Absolute values make replay harmless, which is the entire foundation of a sync you can restart with confidence. Build the Fake ERP absolute from the first line, so you never learn the other habit.
Fails with no error — page-numbered paging ?page=3 over a table being written to will skip and repeat rows, and nothing in the response tells you. Cursors are not a nicety. Shopify itself deprecated page-based pagination in the REST Admin API at version 2019-07 for exactly this reason.
Fails with no error — the watermark you save too early Save updatedSince as "when the scan started" and any row changed during the scan is lost forever. Save it as "the highest updatedAt I actually saw" and you re-read a few rows next time. Re-reading is cheap. Losing a row is invisible and permanent.
Soft delete is not the same as gone If the ERP hard-deletes a row, your sync sees an absence, and an absence is indistinguishable from "not in this page". You cannot tell "deleted" from "unchanged" without a marker. Give the Fake ERP a soft-delete flag now; Chapter A3 covers tombstones in full.
Judgement, not documentation — clock skew If your sync filters on the ERP's updatedAt but stores its watermark using your clock, a difference of a few seconds between the two machines silently drops rows. Nothing warns you. Use one clock — the source's — and never mix them. This is engineering judgement, not a documented Shopify rule.
Making the fake too clever The temptation is to build a beautiful little ERP. Resist it. Every hour spent here is an hour not spent on the sync, which is the part you were actually rejected for. If it serves items, tracks stock per location, accepts orders idempotently, and can be told to misbehave, it is finished.

Say it out loud

Explain this to a beginner

Why build a fake ERP instead of practising against a real one? And why cursors rather than page numbers?

Say it out loud. Then read on.

Now compare with a plain-words answer

Because the skill you are learning is handling failure, and a real system will not fail on demand. You need to be able to make it time out on Tuesday afternoon, return a corrupt row, go slow, duplicate a record, or lie about a timestamp — whenever you want. Control beats realism here.

So you write the other side yourself, with switches for breaking it. Then every failure lesson becomes something you actually experience rather than read.

On cursors: think about reading a list of names on a whiteboard while somebody is adding and removing names. You read the first ten, then ask for "the next ten" by position. But three names above were deleted while you were reading, so everything shifted up — and you have just skipped three names and re-read three others. Nothing errored.

A cursor says "carry on from this record" instead of "give me positions 11 to 20". The data can shift underneath you and you still pick up in the right place.

Same family of thinking as the rest: absolute values so a retry is harmless, and a position marker set to the highest value you actually saw rather than the time the scan started. Re-reading a few records is cheap. Losing one is permanent.

If you used any of these words, try again keyset pagination · offset pagination · watermark · idempotent · fault injection. "Somebody is adding and removing names while you read the list by position" is the explanation.

Build it

Task · 3 hours Postgres
  1. Build the fake ERP: products, prices, stock per location, an order inbox.
  2. Make the ownership split explicit: the ERP owns title and price; Shopify owns quantity. Encode that so the ERP cannot write quantity even if you ask it to.
  3. Expose changes as absolute values, never deltas.
  4. Paginate with cursors. Then add an offset-based endpoint too, purely to break it.
  5. Add failure switches: timeout, slow, corrupt row, duplicate row, wrong timestamp.

Proof it worked: you can turn any failure on from a config value. Then run the offset endpoint while deleting rows mid-scan and watch it skip and repeat records silently — that is the bug you now know by sight.

The watermark test · 30 minutes Postgres

Write a scan that sets the watermark to the highest updatedAt it actually saw. Then write a variant that sets it to the scan's start time. Write a record during each scan.

Proof it worked: one version re-read harmlessly and the other lost a record forever. Keep both as a regression test — this failure has no error message anywhere.

Remember this

  • You write the other side so you can break it. Control beats realism when the skill being learned is failure handling.
  • Ownership splits inside one product. The ERP owns title and price; Shopify owns quantity. That split is normal, and it is where syncs break.
  • Absolute values, never deltas. Absolutes make replay safe. Deltas make a retry a bug.
  • Cursors, never page numbers. Page numbers over changing data skip and repeat rows silently.
  • Watermark = highest updatedAt you actually saw, not when the scan began. Re-reading is cheap; a lost row is permanent and invisible.
  • Soft delete, so "gone" is a value. An absence cannot be told apart from "not on this page".
  • One clock — the source's. Mixing two machines' clocks drops rows with no warning.

If you remember one thing: build the failures in on day one. A sync is not code that moves data, it is code that survives the data moving badly.

Ask questions. Unsure how to shape the failure middleware, or which tables you actually need? Ask before you build — this one is worth getting right.
