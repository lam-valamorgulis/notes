Track 2 · A1 · Lesson 2

App auth: session tokens and token exchange

Three kinds of token, and picking the wrong one breaks your sync months later.

Your win today. You can say which token your background sync must use, and why using the other one means the sync dies the day a staff member leaves the company.

How it works

Two different questions

Authentication in a Shopify app answers two questions that people constantly merge:

QuestionAnswered byLives for
Is this browser request really from a logged-in merchant in my embedded app? Session tokenSeconds
May my server call the Admin API for this store? Access tokenLong, or until uninstall

Token exchange is the bridge: your embedded app front end holds a short-lived session token, sends it to your server, and your server exchanges it for a real access token.

embedded app in the admin iframe │ session token (short-lived, proves "a merchant is here, now") ▼ your server │ token exchange ▼ Shopify ──▶ access token (shpat_…) ──▶ store it, use it for the Admin API

If the app is not embedded, there is no iframe and no session token, so you use the authorization code grant instead — the classic redirect-and-callback flow.

The three token types

TypePrefixUse it when
Offline — the defaultshpat_ Background work. Webhooks, scheduled jobs, your sync. It persists beyond any person's session
Onlineshpat_ You need to respect one staff member's permissions, or attribute an action to them
Delegateshppa_ A subsystem needs narrow access without your app's full credentials

Offline and online tokens look identical — both start shpat_, whatever grant produced them. You cannot tell them apart by looking. Only your own records know which one you stored.

Expiring offline tokens, and the 2027 deadline

Offline tokens come in two flavours. Non-expiring ones grant access until the app is uninstalled or the secret is revoked. Expiring ones are refreshable, and Shopify keeps exactly one refreshable expiring offline token per app and store.

The refresh behaviour has a sharp edge worth reading twice. When your app obtains a new expiring offline token, older ones for the same app and store are retired. A retired token stays valid until its expires_in runs out, so requests already in flight can finish — but its refresh token is invalidated immediately.

Verified 2026-08-23: token types and prefixes, the one-refreshable-token rule, retirement behaviour, and the January 2027 migration requirement for public apps still on non-expiring offline tokens (which does not apply to custom apps or merchant-created apps) — Access tokens.

Answer before reading on Your nightly ERP sync uses an online access token, taken when the store owner installed the app. Nine months later the sync stops. Why?

An online token is tied to a person's session and that person's permissions. It was never meant to outlive them. The moment the session ends — or that staff member's permissions change, or they leave — the background job has no valid identity. Nothing in your code changed, and nothing logged an obvious cause. Background work uses offline tokens. This is the single most common auth mistake in integration work.

Where it hurts

Fails with no error — online token on a background job The scenario above. It works in testing, works for months, then stops for a reason that is organisational rather than technical. Offline is the default precisely because it is almost always what you want.
Costs money — the January 2027 migration Public apps still using non-expiring offline access tokens must migrate to expiring ones by January 2027. Custom apps and merchant-created apps are exempt. If you build a public app today on non-expiring tokens, you have booked yourself an unpaid migration with a hard date.
Fails with no error — the refresh token dies before the access token Obtain a new expiring offline token and the old one's refresh token is invalidated immediately, while the old access token keeps working until it expires. So a second worker holding the old token appears fine, then fails permanently the first time it tries to refresh. Two processes racing to refresh is how you build that bug.
You cannot tell offline from online by looking Both are shpat_. If your database column is called access_token and nothing records which grant produced it, you cannot audit your own system. Store the type next to the token.
Judgement, not documentation — one token, many stores Access tokens are per app and store. A sync serving many stores holds many tokens, and each can be revoked independently by its own merchant. A single global token variable in your config is fine for the Project and wrong for anything real.

Say it out loud

Explain this to a beginner

There are two kinds of token and they do completely different jobs. Explain both. Then explain why a nightly sync must never use the kind tied to a person.

Say it out loud. Then read on.

Now compare with a plain-words answer

One is a visitor badge. It proves that a shop owner is looking at your screen inside Shopify right now. It is short-lived and it does not let you do anything to the shop — it only proves who is standing there.

The other is a key to the building. It lets your server actually read and change things in the shop, whether anyone is watching or not.

You swap the badge for a key when you need one.

Now the important part. Keys come in two flavours: one belongs to the shop, and one belongs to a specific member of staff. Your nightly sync must use the shop's own key, because the staff one dies with that person. They go on holiday, they leave the company, their session expires — and your sync, which has nothing to do with them, stops. At 3am, silently, for a reason that looks like nothing.

So: a background job needs its own identity, never a borrowed one. That is precisely why the shop-level kind exists.

And a practical annoyance: two of these look identical from the outside — same prefix, no way to tell them apart by looking. So record which kind you stored, yourself, when you store it.

If you used any of these words, try again session token · access token · token exchange · authorization code grant · offline versus online · JWT. "A visitor badge versus a key to the building" is the explanation.

Build it

Task · 60 minutes Dev store
  1. Get a session token in your embedded app. Try to call the Admin API with it directly. It does not work — confirm that yourself.
  2. Exchange it for an access token. Call the Admin API. It works.
  3. Store the token with a column recording which type it is, because shpat_ covers both offline and online. (Delegate tokens are shppa_.)
  4. Now get an online token and use it for a background job. Log out of that staff account. Run the job again.

Proof it worked: the job using the online token broke when the person logged out, and the offline one did not. Your sync uses offline, and your database can tell you which is which without guessing from the prefix.

The refresh detail · 20 minutes no store needed

Write down the rule for refreshable expiring offline tokens: one per app and store, and issuing a new one retires the old — the old refresh token stops working.

Proof it worked: your token storage has room for exactly one per store, not a growing list. Code that keeps old tokens "just in case" will eventually use a retired one.

Remember this

  • Session token ≠ access token. One proves a merchant is in your iframe right now; the other lets your server call the Admin API.
  • Token exchange turns a session token into an access token. Non-embedded apps use the authorization code grant instead.
  • Offline is the default and the right choice for sync. It outlives any person's session.
  • Online tokens are tied to a staff member. Never use one for a background job.
  • Offline and online both start shpat_. Delegate tokens start shppa_. Record the type yourself.
  • One refreshable expiring offline token per app and store. A new one retires the old; the old refresh token dies immediately.
  • Public apps on non-expiring offline tokens must migrate by January 2027. Custom and merchant-created apps are exempt.

If you remember one thing: a sync must have its own identity, not a borrowed one — offline tokens exist so no person's departure can take your integration down.
