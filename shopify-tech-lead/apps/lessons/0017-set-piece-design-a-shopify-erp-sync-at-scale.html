Track 2 · A4 · Lesson 2 · set piece

Set piece: design a Shopify ↔ ERP sync at scale

The whole answer, in five stages, in the order you should say it.

Your win today. A structure you can deliver out loud in eight minutes, to a client or an interviewer, that never gets lost and never skips the part that matters.

How it works

Everything in Chapters A1 to A3 is now one answer. The value is not the content — you have that. It is the order, because under pressure people start with the database schema and never reach the interesting part.

Stage 0 · Ask four questions first (60 seconds)

Never design before this. It is also the strongest signal you can send about how you work.

QuestionWhat it changes
How many products and variants?Bulk versus per-record. Whether throttles apply
Which fields does each side own?The entire conflict design
Can the ERP tell me what changed since a timestamp?Incremental versus nightly full scan
How does the ERP signal a deletion?Whether you need a full comparison at all

Stage 1 · Ownership, out loud (90 seconds)

Start here, not with architecture. It is the part that decides correctness.

ERP owns ──▶ title · description · price · SKU identity Shopify owns ◀── inventory quantity · orders · SEO · handle split ──▶ tags: ERP owns its prefix only, never the list excluded anything a human decides ad hoc — say so out loud

Say the sentence that shows you understand it: "ownership splits inside a single product — the ERP owns its title and price while Shopify owns its quantity."

Stage 2 · The flow, both directions (2 minutes)

CATALOGUE IN ERP change → webhook or poll (changed-since) → collapse to affected ids → read CURRENT values from the ERP ← never trust the payload → map ids via the registry → write to Shopify, ABSOLUTE and COMPLETE → record in shadow, only after success → advance watermark to the HIGHEST seen INVENTORY BACK Shopify inventory webhook → read current level per location → write to ERP, absolute → same shadow, same watermark discipline FIRST LOAD bulk operation. staged upload → run → poll → DOWNLOAD RESULTS (COMPLETED is not "worked": per-line userErrors live in the result file)

Stage 3 · What goes wrong, unprompted (2 minutes)

This is the stage that separates a senior answer from a competent one. Volunteer the failures before you are asked.

FailureDesign that handles it
Duplicate webhookInbox table, message id as primary key
Out-of-order deliveryRead current value; ordering stops mattering
ThrottledRead throttleStatus on every response and stay under it. GraphQL returns 200 when throttled
Crash mid-batchAbsolute writes make re-running free
Deletion in the ERPTombstone; archive in Shopify, never delete
Clock skewOne clock per source, the source's own. Never compare across systems
Long outageCollapse the backlog, drain by damage, and check whether the subscription was deleted
Silent driftNightly three-way reconciliation with the denominator published

Stage 4 · How you know it works (60 seconds)

Close on measurement, because it is the part nobody else mentions.

Four numbers: queue depth, unresolved dead-letters, rate-limit headroom, reconciliation drift. Then the sentence that lands: "only the last one measures correctness — the other three look perfect on a sync that is doing nothing."

Stage 5 · What you would not build (30 seconds)

Naming your own scope limits reads as judgement, not as gaps.

  • No per-store rule overrides — one rule set with configuration.
  • No custom queue — one queue with a priority field.
  • No multi-tenant scheduler until there is a second store, but the store id is a parameter from line one.
  • No auto-fix of fields a human owns; report the difference instead.
Say the whole thing out loud, now Close this page and deliver the five stages from memory in under eight minutes. Not reading — saying. Where did you get lost? That gap is your next re-read.

Almost everyone loses stage 3. It is the longest list and the only one that is not a narrative. Fix it by remembering the question behind it rather than the table: for each of duplicate, out-of-order, throttled, crashed, deleted, skewed, backlogged, drifted — what handles it? Eight words, in that order. The answers you already know.

Where it hurts

Costs money — designing before asking Present a beautiful design built on a wrong volume assumption and you have to withdraw it. Four questions first costs a minute and never has to be taken back.
Starting with the schema Tables are concrete, so they are where nervous people start. But the schema is a consequence of the ownership decisions, so leading with it means presenting an answer before its question. Lead with ownership.
Fails with no error — never mentioning failure A design that only describes the happy path sounds complete and reads as inexperienced. The listener does not know what is missing — they just do not feel confident. Volunteering stage 3 is the single biggest upgrade to how this answer lands.
Not saying how you would know it works Almost nobody reaches measurement. Ending there makes the whole answer feel operational rather than theoretical.
Judgement, not documentation — say the numbers you actually verified If you quote a limit, be able to say when you checked it. "One connection field per bulk mutation, 100 MB, 24 hours — I checked that this month" is far stronger than a confident number with no date. And where two doc pages disagreed, say that too; it is a better answer than picking one.

Say it out loud

Explain this to a beginner

You are asked to design a Shopify-to-ERP sync, out loud, with no preparation. What do you do before designing anything, and what do you volunteer that nobody asked for?

Say it out loud. Then read on.

Now compare with a plain-words answer

Before designing: ask four things. How much data. Who decides each field. Can their system tell me what changed since last time. And how do I find out something was deleted.

Those four answers change the entire design. Present a beautiful architecture built on a wrong volume assumption and you have to withdraw it — which is far worse than having asked. Asking costs a minute.

What you volunteer: the ways it breaks. A design that only describes the happy path sounds complete and reads as inexperienced, because the listener cannot tell whether you know what is missing or simply have not thought about it. Naming eight failure modes and giving a one-line answer to each is what separates someone who has run one of these from someone who has read about them.

Then you close on how you would know it works — the numbers you would watch, and the fact that only the drift number measures correctness. Almost nobody gets that far, and ending there makes the whole answer sound operational rather than theoretical.

One discipline throughout: lead with who owns each field, not with database tables. Tables are concrete so nervous people start there, but the tables are a consequence of the ownership decisions. Starting with the schema means presenting an answer before you have made the decision it depends on.

If you used any of these words, try again system design · non-functional requirements · CAP · architecture diagram · SLO. "Ask four things, then volunteer how it breaks" is the explanation.

Build it

Task · 45 minutes, recorded a voice recorder

The deliverable here is a recording, not code. That is deliberate — this skill only exists out loud.

  1. Set a timer for 15 minutes. Record yourself designing the sync.
  2. Stage 1: ask the four questions aloud, and answer them with assumptions you state.
  3. Stage 2: ownership. Stage 3: flow. Stage 4: the failure list, unprompted. Stage 5: the four numbers. Stage 6: what you are explicitly not covering.
  4. Listen back. Mark where you reached for the schema too early.

Proof it worked: in the recording you asked before designing, and you volunteered failures without being asked. If you started with tables, record it again — that is the habit this task exists to break.

The numbers rule · 10 minutes no store needed

Write down every limit you might quote, with the date you personally checked it.

Proof it worked: you can say "one connection field per bulk mutation, 100 MB, 24 hours — I checked that on this date". Quoting a limit you cannot date is the thing that gets caught, and this Course's own throttle number moved 10× in three weeks.

Remember this

  • Five stages: ask · ownership · flow · failures · measurement · scope limits.
  • Four questions first: volume, ownership, changed-since, deletions.
  • Lead with ownership, not the schema. The schema is a consequence.
  • Volunteer the failures. Eight of them, and each has a one-line answer you know.
  • Close on the four numbers, and that only drift measures correctness.
  • Name what you would not build. Stated limits read as judgement.
  • Date your facts. "I checked this month" beats a confident undated number.

If you remember one thing: ask four questions before you design, and volunteer the failure list before anyone asks for it.
