The NestJS module shape for a sync service

Four modules, one rule: only one of them is allowed to know what Shopify is.

Your win today. A folder structure where you can answer "where does this code go?" without thinking — and where swapping the ERP for a different vendor touches one module instead of forty files.

How it works

A sync service does four jobs, and they change for different reasons. That is the whole basis for splitting them up — not tidiness, but rate of change.

The one rule worth enforcing

domain imports nothing from shopify. Dependencies point inward. The domain module works on your own types — an item, a price, a stock level at a location — and never on a ProductSetInput.

This sounds like architecture pedantry until the day Shopify releases a new API version and changes a field shape. With the rule, you edit one module. Without it, "which files know about Shopify?" has the answer "all of them", and a quarterly version bump becomes a project.

Enforce it mechanically, not by discipline. A lint rule that fails the build on a forbidden import is worth more than a paragraph in a README that nobody reads twice.

Where the API version lives

Exactly one place: a constant in the shopify module, read from the environment. Never let a client library default to "latest". Shopify ships a new stable version every quarter, so "latest" means your app's behaviour changes on a schedule someone else controls.

What the service exposes

Keep your own HTTP surface tiny. It is not a public API — it is an operations console:

POST /webhooks/shopify/:topic   receive, verify, enqueue, 200
POST /webhooks/erp              same, from the other side
GET  /health                    is the process alive
GET  /ready                     can it reach Postgres, Redis and Shopify
POST /admin/resync              force a run for one item or one range
GET  /admin/reconcile           the report, on demand
Answer before reading on A ticket says "when the ERP price is missing, fall back to the last known price". Which module? And where does the temptation put it?

It belongs in domain — it is a business rule about what the correct value is. The temptation is to write it in shopify, right where you are about to send the price, because that is where you are already typing. Do that a dozen times and the rules are scattered through the module that changes for entirely unrelated reasons. When someone asks "what is our fallback policy?", the answer should be one file, not a search.

Where it hurts

Costs money — business rules inside the API client Every rule written next to the API call is a rule you must re-verify at each quarterly version bump, because it lives in the file you are changing. This is the difference between a version upgrade being an afternoon and being a sprint.
Fails with no error — a second place that knows the API version A client library defaulting to "latest" while your constant says 2026-07 means two code paths on two versions. Both work. They disagree about a field shape, occasionally, in one direction. Pin it once, pass it everywhere.
The ingest module that decides things It is tempting to have the CSV reader skip rows it thinks are bad. Now "what counts as bad?" has two answers — one in the CSV path, one in the webhook path — and they drift. Ingest normalises. Domain decides.
ops built last is ops never built Reconciliation and replay are the tools you need at the worst possible moment. Build the endpoints early and empty, then fill them in. A replay tool written during an incident is written badly.
Judgement, not documentation — do not build for many stores yet Multi-tenancy changes every one of these modules, and guessing at it now produces abstractions you will delete. Build for one store, but keep the store identity as a parameter rather than a global. Chapter A3 covers the real multi-store shape.

Say it out loud

Explain this to a beginner

Exactly one part of your codebase is allowed to know that Shopify exists. Explain why that rule is worth enforcing with a linter rather than good intentions.

Say it out loud. Then read on.

Now compare with a plain-words answer

Because Shopify changes on somebody else's schedule and your business rules do not.

Split the code by how often it changes. There is a part that reads from the other system, a part that holds the actual rules — who wins a conflict, what counts as valid — a part that talks to Shopify, and a part that runs the thing. Shopify releases a new version every three months. Your rules change when the business changes its mind.

If Shopify's shapes leak into the rules, then every quarterly platform change becomes a change to your business logic. That is how a small version bump turns into a scary release.

Now why a linter. Because this boundary is broken accidentally, always. It is 6pm, you need one field, the Shopify object already has it, and importing it is one line. Nobody decides to break the architecture — they just need one field. Good intentions do not survive that moment; a build failure does.

The same reasoning gives you the other rules. The version is pinned in one constant, because "latest" means your behaviour changes quarterly without you touching anything. And the reader normalises but never judges, because a reader that quietly drops bad rows creates a second, competing definition of "bad".

If you used any of these words, try again hexagonal architecture · ports and adapters · anti-corruption layer · dependency inversion · bounded context. "Split by how often it changes, and Shopify changes quarterly while your rules do not" is the explanation.

Build it

Task · 60 minutes no store needed
  1. Create the four modules: ingest, domain, shopify, ops.
  2. Add a lint rule that fails the build if anything in domain imports from shopify.
  3. Break it on purpose. Import a Shopify type into a domain file and confirm CI goes red.
  4. Grep for the API version string. There must be exactly one occurrence.
  5. Expose only ops endpoints: health, ready, resync, reconcile. No public API.

Proof it worked: CI went red on the deliberate violation. A rule that cannot fail is a comment. And your version grep returns one line — two paths on two versions is a miserable bug to find.

The reader/decider split · 30 minutes no store needed

Find one place where your reader filters or rejects a row. Move that decision into domain and have the reader pass everything through, normalised.

Proof it worked: there is exactly one definition of "bad row" in the codebase. Two definitions means the answer to "why was this skipped?" depends on which file you read.

Remember this

  • Four modules: ingest, domain, shopify, ops. Split by rate of change, not by tidiness.
  • domain never imports from shopify. Enforce it with a lint rule, not with good intentions.
  • Only shopify knows GraphQL, the cost budget, and the API version.
  • Pin the API version in one constant. "Latest" means your behaviour changes quarterly on someone else's schedule.
  • ingest normalises, domain decides. A reader that filters rows creates two competing definitions of "bad".
  • Your HTTP surface is an ops console, not a public API. Health, ready, resync, reconcile.
  • Build ops early and empty. A replay tool written mid-incident is written badly.

If you remember one thing: exactly one module is allowed to know what Shopify is — that boundary is what makes the quarterly upgrade an afternoon.
