Track 2 · A1 · Lesson 3

Webhooks done right

Five seconds, eight retries, and then your subscription is deleted.

Your win today. A receiver that proves the message came from Shopify, answers inside the deadline, survives the same message arriving twice, and does not quietly unsubscribe itself after a bad afternoon.

How it works

something happens in the store │ ▼ Shopify POSTs to your URI │ X-Shopify-Hmac-SHA256 base64 HMAC-SHA256(raw body, client secret) │ X-Shopify-Webhook-Id unique per DELIVERY → dedupe on this │ X-Shopify-Event-Id same per merchant ACTION → correlate on this ▼ your receiver: 1. verify HMAC on the RAW body ── before parsing, before trusting 2. dedupe on X-Shopify-Webhook-Id ── or be idempotent 3. enqueue ── do not process here 4. return 200 ── within 5 seconds, total │ └─ anything not 2XX (3XX included) = failure → 8 retries over 4 hours, interval growing each time → after 8 consecutive failures the subscription is DELETED (if it was configured using the Admin API)

1 · Verify on the raw body

The signature is a base64-encoded HMAC-SHA256 of the raw request body, keyed with your app's client secret, in the X-Shopify-Hmac-SHA256 header. Compute it, compare, reject on mismatch.

"Raw" is load-bearing. Most frameworks parse JSON for you before your handler runs, and a parsed-then-re-serialised body is a different byte string — different key order, different whitespace. The HMAC then never matches and the cause is invisible in the code you are reading. Capture the raw bytes for this route specifically.

Note the boundary: HMAC verification applies to HTTPS delivery only. Google Cloud Pub/Sub and Amazon EventBridge deliveries do not require it, because the transport already establishes the sender.

2 · Two different ID headers

HeaderUnique perUse it to
X-Shopify-Webhook-IdDeliveryDeduplicate
X-Shopify-Event-IdMerchant actionCorrelate deliveries from the same cause

If you have more than one subscription on the same topic, you get a separate delivery per subscription — each with a different Webhook-Id but the same Event-Id. Dedupe on the wrong header and you throw away work you were supposed to do.

3 · Enqueue, do not process

Shopify allows a one-second connection timeout and a five-second timeout for the whole request. That budget is for acknowledging receipt, not for doing the work. Store the payload, return 200, process asynchronously. Then add a reconciliation job that periodically re-reads from the API to catch what you missed — Shopify's own guidance recommends exactly that pattern, which tells you how much they expect you to miss.

4 · Failure is a countdown

No response or an error means 8 retries over the next 4 hours, with the interval growing each time. After 8 consecutive failures the subscription is automatically deleted — and warning emails go to your app's emergency developer email address.

The qualifier that matters Automatic deletion applies to subscriptions configured using the Admin API (shop-specific). App-specific subscriptions declared in your app configuration are not managed that way — Shopify's recovery guidance says you do not need to re-subscribe if your app uses app-specific subscriptions. Which style you chose decides whether an outage costs you a resubscribe script.

Answer before reading on Your receiver returns a 301 redirect to a tidier URL. Deliveries look fine in your access log. What is Shopify recording?

Failures. Any response outside the 200 range, including 3XX, is treated as an error. Your access log shows 301s and looks healthy; Shopify's counter climbs toward eight, and then your subscription is gone. A redirect is one of the few ways to fail while appearing to succeed on your own side.

Where it hurts

Fails with no error — the parsed body Your middleware parses JSON before the handler. You HMAC the re-serialised object. It never matches, and the code looks correct. Every webhook is rejected as unauthentic. Capture raw bytes on this route.
Fails with no error — a 3XX response As above. Non-2XX means failure, and redirects count. Terminate the webhook path exactly where you say it terminates.
Costs money — secret rotation has a one-hour tail Rotate your app's client secret and it can take up to an hour for the HMAC digest to be generated with the new secret. Verify against the new secret immediately and you reject real deliveries for that hour, burning retries. Accept both secrets during the overlap.
Costs money — the subscription deletes itself Eight consecutive failures and it is gone. Your app then looks healthy and receives nothing, which is worse than crashing. Watch the failure rate: Shopify calls anything over 0.5% higher than average.
Webhooks can arrive a day late Shopify's own guidance is to compare the webhook's timestamp with the current time if being a day late would cause problems. So a webhook is not just unreliable in whether it arrives — it is unreliable in when. Chapter A3 builds on exactly this.
Dedupe on the wrong header Two subscriptions on one topic produce two deliveries with one Event-Id. Deduping on Event-Id silently drops the second, which some other part of your system was waiting for.
Coming change — Events, in developer preview Shopify is previewing Events on the unstable API version, described as becoming the primary subscription mechanism as topic coverage grows. Note the header is Shopify-Hmac-Sha256 — no X- prefix. Do not hardcode one header name in a shared verifier.

What you say to a client/PM

When a client says "so it updates instantly" Usually within seconds, yes. But a webhook is a notification, not a guarantee — it can be delayed, and occasionally it doesn't arrive. So alongside it we run a check that re-reads from Shopify on a schedule and fixes anything that drifted. Without that, one missed message means one wrong stock number forever. Sets the expectation before the first miss, and sells the reconciliation job as insurance rather than extra scope.
When the integration silently stopped and the client asks what happened Our endpoint failed eight times in a row, so Shopify removed the subscription — that's designed behaviour, not a bug. I've fixed the endpoint, recreated the subscription, and backfilled the gap. I'm also adding an alert on the failure rate so we hear about it from monitoring rather than from you. Names the mechanism, does not hide behind it, and closes with the thing that stops the same conversation happening twice.
When a PM asks why you need a queue "just to receive a message" We get five seconds total to answer, and that's the whole budget. If we do the work inside those five seconds, a slow day means timeouts, and enough timeouts means Shopify stops sending. So we accept the message, say yes immediately, and do the work behind it. A hard number and a named consequence. "Best practice" would have lost this argument.

Remember this

  • HMAC the RAW body with your client secret, before parsing. A re-serialised body never matches.
  • 1 second to connect, 5 seconds total. Enqueue and return 200; never process inline.
  • Any non-2XX is a failure — 3XX included. A redirect fails while your own log looks fine.
  • 8 retries over 4 hours, then the subscription is deleted if it was configured via the Admin API. App-specific subscriptions are not.
  • Webhook-Id to dedupe, Event-Id to correlate. Two subscriptions on one topic means two deliveries, one Event-Id.
  • Secret rotation has an up-to-one-hour tail. Accept both secrets during the overlap.
  • Always add a reconciliation job. Shopify's own docs recommend it, which tells you how much you will miss.

If you remember one thing: a webhook is a hint that something changed — never proof, and never the only way you find out.
