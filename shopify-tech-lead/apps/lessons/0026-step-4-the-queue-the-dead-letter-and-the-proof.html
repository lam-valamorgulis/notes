The queue, the dead-letter and the proof

Break it on purpose, then prove the report catches it. This is the step that changes what you can honestly claim.

Your win today. A sync that survives every failure you can cause — and a nightly report that names exactly which records are wrong. After this you can say "I built one, and here is how I know it works."

How it works

Three things, and the third is the point

1. THE QUEUE retries, backoff with jitter, one shared budget per store 2. THE DEAD-LETTER terminal failures, readable, with resolved_at 3. THE REPORT ← the only thing that measures CORRECTNESS 1 and 2 make it survive. 3 makes it provable.

Everything up to now could be wrong without you knowing. Step 4 is where that stops being true.

1 · The queue: classify before you retry

ClassDetected byDo
Transient5xx, timeout, connection resetRetry, exponential backoff with jitter
Throttlederrors[].extensions.code === "THROTTLED" — inside an HTTP 200Wait for budget. Not a failure, a queue
Terminaldata.*.userErrors[], bad scope, invalid fieldDead-letter on the first attempt. Never retry
PoisonN identical failuresDead-letter with the full error body

Write the three-level check as one function and use it everywhere:

// HTTP status → errors[] → userErrors[]. All three, every call.
function classify(res, body) {
  if (!res.ok)                                    return 'transient';
  if (body.errors?.some(e => e.extensions?.code === 'THROTTLED'))
                                                  return 'throttled';
  if (body.errors?.length)                        return 'terminal';
  const ue = findUserErrors(body.data);
  if (ue.length)                                  return 'terminal';
  return 'ok';
}

And the speed limiter, which is prevention rather than recovery:

// throttleStatus arrives on SUCCESSES too. Use it to never be throttled.
const { currentlyAvailable, restoreRate } = body.extensions.cost.throttleStatus;
if (currentlyAvailable < nextCost + MARGIN) {
  await sleep(((nextCost - currentlyAvailable) / restoreRate) * 1000);
}

Jitter is one line and prevents a second outage. Without it, every job that failed at the same moment retries at the same moment, and your recovery reproduces the incident:

const delay = base * 2 ** attempt * (0.5 + Math.random() * 0.5);

2 · The dead-letter, made readable

The outbox_dead table from A2.2, and the one column that matters:

ColumnWhy
error_code, error_bodyThe actual Shopify message, not your paraphrase
attemptDistinguishes "tried once, terminal" from "tried eight times"
resolved_atMakes it a work queue instead of a landfill. Unresolved rows are a number you alert on

Then one endpoint: GET /admin/dead-letters, grouped by error_code. Grouping is what turns 900 failures into "three problems", which is the difference between a list and an action.

3 · The report — the three-way compare

Fake ERP shadow Shopify (source) (what we sent) (what's there) │ │ │ ├── A ─────────┤ │ source ≠ shadow → WE ARE BEHIND │ ├──── B ───────────┤ shadow ≠ Shopify → SOMEONE ELSE WROTE IT └────── C ────────────────────────┘ source ≠ Shopify → conflict

Compare by consequence, not everything: inventory and price nightly, existence nightly, text weekly. Read the Shopify side with a bulk query, not a paged loop — a nightly full compare is exactly what bulk operations are for.

And the output rule: always publish the denominator.

BAD "3 differences" ← out of how many? BAD "99.99% in sync" ← not actionable GOOD "compared 46,367 variants · 3 differences · here they are: SK000412-M price shadow 24.99 shopify 19.99 → type B SK001877-L stock shadow 4 shopify 0 → type B SK003001-XS price source 12.50 shadow 11.00 → type A"

Zero differences out of zero records looks exactly like a pass. Printing the denominator is the only thing that separates them.

5 · The four numbers, on one page

GET /admin/health queue depth ................ 0 ← rising and not falling = behind unresolved dead-letters .... 3 ← a work list rate-limit headroom (min) .. 812/1000 ← how close you got reconciliation drift ....... 3 / 46,367 with the list └─ the ONLY one that measures correctness

Alert on exactly two: unresolved dead-letters above a threshold, and drift above a threshold. Everything else is a dashboard. An alert that fires weekly and is always ignored trains people to ignore the channel.

Answer before you build Row 8: you set the watermark to now(), skipping a batch of real changes. Queue depth is zero, no dead-letters, plenty of headroom, no errors anywhere. Which of the four numbers moves?

Only reconciliation drift. The other three are all measuring effort — how much work you did and how well it went — and you did no work, perfectly. Drift is the only one comparing against reality, so it is the only one that can distinguish "nothing needed doing" from "we skipped everything".

That is why drift is the number you put in front of a client, and why "no errors this week" is not a status report. Run row 8 deliberately and watch three green numbers sit next to a broken sync — it is the most useful ten minutes in the Project.

Where it hurts

Costs money — retrying terminal errors Eight attempts at something that can never succeed, spending the budget the valid records needed. If enough bad records exist, you start failing good ones too — and those look broken as well.
Costs money — treating HTTP 200 as success Throttles, validation failures and partial successes all return 200 on GraphQL. One classify() function, used everywhere, is the fix.
Fails with no error — no jitter Everything that failed together retries together. Your recovery causes the second spike, and nothing points at you as the cause.
Fails with no error — the unread dead-letter table Failures go somewhere, so the main path looks clean. Nobody looks. Alert on the count of unresolved rows, not on the table existing.
Fails with no error — a report with no denominator Zero out of zero is indistinguishable from a pass. Publish both numbers or the report proves nothing.
Costs money — auto-fixing every difference A type B difference means a human or another app wrote that field. Silently overwriting starts a fight where your sync and a person take turns. Auto-fix only where ownership is unambiguous; queue the rest.
Comparing money as floats 10.10 and 10.1 are equal. A naive compare reports drift every single night, and a report that cries wolf is worse than no report. Integer minor units, same currency.
Judgement, not documentation — where to stop You could keep hardening this forever. The bar is the ten rows above passing and the report naming the differences. Past that you are polishing, and the remaining gap is real production pressure, which you cannot manufacture. Stop, and go and say you built it.

What you say to a client/PM

The one number that means "it works" Every night we compare what we sent against what's actually in Shopify, field by field, for prices and stock. The report says "we checked 46,367 values and found 3 differences, here they are". If I only told you no errors had happened, that would sound reassuring and prove almost nothing — a sync that's stopped has no errors either. Gives the number, the denominator, and pre-empts the weaker metric someone will otherwise ask for.
When 900 records did not sync They were rejected, not delayed — each has a specific reason and I've grouped them into three problems rather than 900 lines. I don't retry those, because they'd fail identically and use up the capacity the working records need. Fix the three and they'll go through on the next run. Separates "failed" from "not tried yet", and turns a scary number into three tasks.
Now that the Project runs — the sentence this Step buys you I've built one end to end. It syncs a catalogue out and inventory back, and I deliberately broke it ten different ways — stale data, duplicate messages, the other system down, a killed process mid-batch — to check the report catches each one. What I haven't had is a real merchant's data wrong on a Monday morning with someone on the phone. That's the part I can't manufacture. Specific enough that only someone who did it could say it, and it still names the remainder honestly. That combination is the whole point of the Project.

Remember this

  • Classify before retrying: transient · throttled · terminal · poison. Only the first two are worth a retry.
  • One classify() function checking HTTP status, errors[], then userErrors[].
  • Read throttleStatus on successes and slow down before you are refused.
  • Jitter is one line and prevents your recovery from causing the next outage.
  • resolved_at makes the dead-letter a queue, not a landfill. Group by error code.
  • Three-way compare, and always publish the denominator. Zero out of zero looks like a pass.
  • Run all ten break-it rows. Rows 6 and 8 are the ones where the expected result is silence.

If you remember one thing: three of the four numbers measure effort — only reconciliation drift measures whether the data is right.

Ask questions. When the ten rows pass, say "review the project" and I will read it as a reviewer would — then we update R5.1, because the honest answer to "have you done this?" will have changed.
