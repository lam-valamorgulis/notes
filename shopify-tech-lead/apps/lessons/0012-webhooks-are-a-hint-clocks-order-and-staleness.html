Track 2 · A3 · Lesson 4

Webhooks are a hint: clocks, order and staleness

A webhook tells you something changed. It does not tell you what it is now.

Your win today. You stop trusting webhook payloads as data, stop comparing two machines' clocks, and can explain to a client why "instant" and "reliable" are different promises.

How it works

Derive it: what can a message actually prove?

A webhook arrives carrying a product payload. Ask what that payload proves. It proves the product looked like that at the moment Shopify built the message. Between then and your handler reading it, there was a network, a queue, possibly a retry, possibly four hours of retries.

So a webhook payload is a photograph of the past, with no guarantee about how old the photograph is. It answers "did something change?" reliably. It answers "what is the value now?" not at all.

T0 something changes T1 Shopify builds the payload ← the photo is taken here T2 network, queue, retries... ← unknown duration. can be HOURS T3 your handler reads it ← you are looking at T1 T4 you write it somewhere ← you may be writing STALE data

That gives the rule the whole Chapter turns on: a webhook is a trigger, not a source. Use it to know that you should act. Then read the current value from the API before you act on it.

The cost is one extra read. What it buys is that a delayed webhook becomes harmless: a four-hour-old notification triggers a fresh read and writes the correct value. Use the payload as data instead, and that same delayed message overwrites good data with a four-hour-old number.

Order is not guaranteed either

Two changes to the same product, one second apart. Two webhooks. Nothing promises they arrive in that order — different retries, different paths.

sent: [price → 10] then [price → 12] arrived: [price → 12] then [price → 10] payload-as-data → final price 10. WRONG, permanently. payload-as-hint → read current: 12. RIGHT, both times.

Notice that "read the current value" fixes out-of-order delivery for free. You did not need sequence numbers, or ordering guarantees, or a state machine. Handling both messages the same way produces the right answer, because the API is the authority and the API has one value.

The clock problem

Now the subtler one. To sync incrementally you filter on "changed since X". That requires comparing timestamps — and the timestamps come from machines you do not control.

ClockOwned bySafe to compare with
Shopify's updatedAtShopifyOther Shopify timestamps
The ERP's updatedAtThe vendorOther ERP timestamps
Your server's now()YouNothing else

The rule: one clock per source, and it is the source's own. Store the ERP's timestamp as the ERP watermark. Store Shopify's as the Shopify watermark. Never mix, and never use your own clock as a watermark for someone else's data. A few seconds of drift between two machines silently drops every row that changed inside the gap.

And never compare across sources. "The ERP value is newer than the Shopify value" is a sentence with no reliable meaning. That is why "newest wins" is not a conflict rule — the comparison it depends on is not available to you. Use ownership instead, from A3.2. Ownership needs no clock.

Late is normal, not exceptional

Shopify's own guidance is to compare a webhook's timestamp with the current time if receiving it up to a day late would cause problems in your app. Read that again: the platform tells you to design for a day.

Verified 2026-08-23: the day-late guidance and the recommendation to pair webhooks with a periodic reconciliation job that re-reads from the API — Troubleshoot webhooks and Verify webhook deliveries. Delivery mechanics — 1-second connect, 5-second total, 8 retries over 4 hours — are in A1.3.

Answer before reading on You take a watermark by writing down the time your scan started, then scan for two minutes. A product is edited 30 seconds in. What happens to it, and when do you find out?

It depends where it sat in the scan. If you had already passed it, you never saw the edit — and your next scan filters on "changed since the scan started", which is after the edit. So it is skipped forever. You find out when a customer or the client notices one wrong price, with no error anywhere. The fix is one line: store the highest updatedAt you actually saw, not the start time. You then re-read a few rows, which is free, instead of losing one, which is permanent.

Where it hurts

Costs money — using the webhook payload as data A retried webhook from four hours ago overwrites the current price with an old one. Both the message and your code are working exactly as written. The store sells at the wrong price until someone notices.
Fails with no error — out-of-order delivery Two edits, delivered backwards, and the older value wins permanently. Nothing logs a problem because nothing failed. Reading the current value on every trigger makes this impossible.
Fails with no error — the watermark from your own clock Your server's clock is 4 seconds ahead of the ERP's. Every scan silently skips 4 seconds of changes. Over a year that is thousands of rows, spread randomly, with no pattern anyone can reproduce.
Fails with no error — the watermark set to the scan's start As above. Everything edited during the scan is lost, every scan, forever.
Equal timestamps with a strict greater-than Two rows share updatedAt to the second. > skips one forever; >= without a tiebreak loops on it. Use >= plus the last id you saw, and accept re-reading one row.
"Newest wins" as a conflict rule It requires comparing two clocks you do not own. It resolves, in practice, to "whichever machine drifted further". Use ownership, which needs no clock at all.
Judgement, not documentation — the extra read costs budget Reading the current value on every trigger doubles your API calls. That is real against the rate limit from A2.3. The mitigation is batching: collect triggered ids for a few seconds, then read them in one query. Do not fix it by trusting the payload.

Say it out loud

Explain this to a beginner

A webhook arrives saying the price is £20. Explain why you should not write £20 anywhere. Then explain what "one clock per source" means.

Say it out loud. Then read on.

Now compare with a plain-words answer

Because the message is a photograph of the past, and you do not know how old it is. It was taken when the change happened. Since then it may have queued, been retried, or overtaken another message. Two edits can genuinely arrive in the wrong order.

So the message is worth exactly one thing: "something about this item changed — go and look." You throw the contents away and read the current value. One extra call, and late delivery, duplicate delivery and out-of-order delivery all stop mattering. You do not need to sequence anything, because you always read the end state.

That is a remarkable amount of complexity deleted by one habit.

On clocks: each system keeps its own time, and its timestamps mean "when I changed it". Those numbers are not comparable across systems — different clocks, different meanings, different drift. So when you record how far you have got through someone else's data, you use their clock and their values, never your own now().

And this is exactly why "newest wins" fails as a rule: you cannot reliably say which is newest. Use ownership instead, which needs no clock at all.

If you used any of these words, try again eventual consistency · clock skew · causal ordering · read-your-writes · watermark. "A photograph of the past, of unknown age" is the explanation.

Build it

Task · 60 minutes Dev store

Make out-of-order delivery harmless, by testing that it is.

  1. Write a handler that uses the payload value. Make two quick edits, then deliver the two webhooks in reverse order.
  2. Check what value you stored. It is the older one.
  3. Rewrite the handler to ignore the payload and read current.
  4. Deliver them backwards again. Then deliver one twice. Then deliver one two hours late.

Proof it worked: all three abuses produce the correct final value, and you wrote no sequencing code at all. That is the payoff.

Break the watermark on purpose · 45 minutes Postgres
  1. Set your watermark to now() at the end of a scan.
  2. Write a record in the source during the scan.
  3. Run the next scan. Prove that record is skipped, permanently.
  4. Change the watermark to the highest updatedAt you actually saw, from the source's clock. Repeat.

Proof it worked: the first version lost a record forever with no error; the second re-read a few records harmlessly. A re-read is free; a skip is permanent. Always bias the watermark backwards.

Remember this

  • A webhook is a trigger, not a source. The payload is a photo of the past, of unknown age.
  • Read the current value before acting. One extra call makes late and out-of-order delivery harmless.
  • Order is not guaranteed. Two edits can arrive backwards; reading current fixes it with no sequencing.
  • One clock per source, and it is the source's own. Never your now() for someone else's data.
  • Never compare timestamps across systems. That is why "newest wins" is not a rule — use ownership.
  • Watermark = highest updatedAt seen, never the scan's start. Re-read is free; a skip is permanent.
  • Shopify says design for a day late. Pair every webhook with a scheduled re-read.

If you remember one thing: never trust a timestamp you did not generate, and never trust a payload to still be true.
