The Map · Client / PM phrasebook

Talking to a client about Shopify

Every sentence that used to sit inside a Lesson, on one page, in Lesson order.

Why this page exists Every Lesson used to carry a block called What you say to a client/PM. That block was removed on 2026-08-23, because this Course is now about building Shopify integrations, not about talking about them. The sentences themselves are still good, so they all live here instead — unchanged, grouped by Lesson, each linking back to the Lesson that explains why the sentence is true.

Use it the way you would use a phrasebook: find the situation, read the sentence, say it out loud. For the situational ones — buying ten seconds, saying no, disagreeing upward — use the Client / PM phrasebook instead. This page is organised by topic; that one is organised by moment.

P1 · The shape of Shopify

P1.1 — The Shopify object model, end to end

When a client says "just sync our stock number" I need to be precise about which number. Shopify keeps stock per location, and it separates "physically here" from "available to sell" — the difference being items already sold but not yet shipped. If your system's number includes those, sending it straight across would re-sell them. Which number is it? One question that prevents the most expensive failure in the project. Ask it before agreeing to anything.
Explaining why "one product" is not one thing In Shopify a product is really a folder. The things customers buy are the variants inside it — each size and colour has its own price, its own code and its own stock. So when we say "10,000 products", the number that actually matters for how long anything takes is the variant count, which is usually four or five times bigger. Corrects the unit before it appears in an estimate. Clients count products; the work scales with variants.

P1.2 — The two APIs and the rate limit model

When asked "how many API calls per second can we do?" It doesn't work as a number of calls. Shopify gives us a budget and charges each request by how much data it asks for, so one big request can cost as much as a hundred small ones. What that means practically: the way to go faster is to ask for less, not to ask more often. And your plan sets the budget size. Corrects the mental model and immediately gives the lever that actually works. Ends the "can't we just parallelise it?" conversation early.
When someone proposes a quick fix on REST I'd rather not add new REST code. Shopify marked it legacy in October 2024, and new apps have had to be GraphQL-only since April 2025 — so anything we write there is work we'll redo. It's the same effort in GraphQL today. Two dates make this unarguable. Vague "it's deprecated" invites a debate.

P1.3 — API versioning and the quarterly upgrade

When quoting the build, before anyone asks One thing to build into your budget: Shopify releases a new version of their API every three months, and each one is supported for about a year. So the integration needs a small maintenance slot roughly quarterly. It's a few hours if we keep up. It's a fortnight if we leave it two years, which is what usually happens. Raising it unprompted makes it a platform fact rather than a later surprise. Clients accept costs they were warned about.
When a client says their existing integration "works fine, don't touch it" I'd check one thing first. Shopify retires API versions after about a year, and when yours retires they don't fail your requests — they quietly serve a newer version instead. So an integration that hasn't been touched in two years is running on a version nobody picked, and it changed without telling anyone. It might genuinely be fine. I'd rather know than assume. Describes a real mechanism instead of implying the previous developer was careless. That keeps the client on your side.

P2 · Custom data

P2.1 — Metafields, definitions, and the cost of skipping them

When a client asks "can Shopify store our custom product data?" Yes, and there are two ways. Simple extra fields on a product — a care instruction, a fabric, a supplier code — are straightforward. If the data has several parts that belong together, like a size chart with rows and columns, that's a slightly different mechanism but still built in. What I need from you is the list of fields and their types, because defining them properly up front is what makes them editable and searchable later. Answers yes, distinguishes the two mechanisms without naming either, and asks for the one input that prevents the expensive mistake.
When you inherit an integration that skipped definitions The data is all there, but it was saved without telling Shopify what it means — so your team can't see or edit it in the admin, and it can't be used for filtering. Fixing it is straightforward but not instant: we declare the fields properly, then check every existing value matches the type we declared. I'd do it before adding anything new on top. Describes the symptom in the client's terms — "you can't see or edit it" — rather than as a technical omission.

P2.2 — Metaobjects, and when data does not belong on the product

When a client describes data with parts That sounds like a thing in its own right rather than a label on a product. So I'd set it up once, as its own record, and have the products point at it. Then when a measurement changes you edit it in one place and every product that uses it updates. If we put it on each product instead, you'd be editing it forty times. Explains normalisation with no jargon and in terms of the client's future editing effort, which is what they actually care about.
When asked whether the team will be able to edit it themselves Yes, as long as we set it up as yours rather than as our app's. That's a decision at build time — the two look identical afterwards, but only one lets your team manage it in the admin. I'll set it up as yours by default unless it's purely internal plumbing. Surfaces a build-time decision that is invisible later and expensive to reverse. Clients rarely know to ask.

P3 · Inventory, locations and the till

P3.1 — Three ways in-store stock reaches the storefront

First conversation There are three ways to do this and they cost very differently. If your shop stock is already in Shopify, it's nearly free — the website already knows. If it lives in a separate till system, we either ask that system every time someone loads a page, which makes your pages depend on its speed, or we copy the numbers over every few minutes and say how fresh they are. Where does your shop stock live today? Three options with their real costs, then one question that decides it. The client leaves knowing why the answer differs.
When pushing back on exact numbers I'd show "in stock" or "low stock" rather than a count. Shop floors are never accurate to the single item — things get held, damaged, or sit in a fitting room. If we say "2 left" and someone drives over for it, being wrong costs you that customer. Bands answer the question they actually have, which is whether it's worth the trip. Grounds a technical recommendation in a physical reality the client knows better than you do. Very hard to argue with.

P3.2 — Locations and multi-location inventory

During discovery Can I get a list of your physical locations, and separately what Shopify shows? They're often different — warehouses appear, apps create their own, and locations that were closed are usually still there. I need to know which ones actually hold stock you'd sell online, because that's the set I'll sync. Pre-empts a discrepancy the client does not know exists, and frames it as normal rather than as their mistake.
When totals do not match Shopify's total is higher than ours by a consistent amount, which points at a location we're not including rather than updates we're missing. There's a location in your account that's marked inactive but still holds stock. Do you want it in scope or excluded? Either is fine — I just need it to be a decision rather than an accident. Distinguishes a missing place from missing updates, which is the diagnosis that saves a day, and asks for a decision instead of guessing.

P3.3 — The till: POS, the retail order, and UI extensions

When a client is about to open their first shop Before that goes live I need to check what our integration does with shop sales. They arrive as orders like any other, but they're already complete — the customer has walked out with the item. Right now our warehouse feed would treat them as things to pick. That's a small change, but it has to happen before the shop opens rather than after. Raises a failure before it happens, with the timing that matters. This is the single most valuable habit in integration work.
When asked for a feature on the till We can put it on the till in three ways: a tile on the home screen, a button that opens a full-screen step-by-step, or a small block inside an existing screen. The thing I'd hold us to is speed — there's a customer waiting at a counter, so if it takes two seconds staff will stop using it. Which of the three fits the moment they'd need it? Gives real options in plain terms, and sets a performance constraint using the customer at the counter rather than a millisecond target.

P4 · The storefront

P4.1 — Liquid or headless: the client conversation

When asked "should we go headless?" Three questions decide it for me. Is your storefront doing something genuinely unusual, beyond showing a catalogue? Will you have front-end developers on staff permanently, not just for the build? And does your team need to change pages without asking a developer? If it's no, no, yes — which is most businesses — a theme is the right answer, and we can still build one fully custom section for the page that needs it. Three questions, an honest default, and a middle option so "no" does not sound like a refusal.
When the client has already decided and you disagree I'll build it, and I want one thing on the record first: this needs a front-end developer available every quarter, permanently — for Shopify's API versions, for security updates, and for the apps we'll be replacing by hand. If that resource exists, headless is a good fit. If it doesn't, the site will freeze about a year from now. Which is it? Does not fight the decision. Names the one condition that makes it work and hands the risk back, in writing.

P4.2 — Dawn, Horizon and theme blocks

Explaining the value of a modern theme The practical difference is how much your team can change without me. Layout changes — moving a band, adding a promo to another page, reordering things — become something you do yourself in the editor. What you'd still come to me for is a genuinely new kind of content band. So over a year, fewer small tickets and more of your budget going to real work. Describes the change in terms of the client's own future workload, not in terms of theme architecture.
When asked for four slightly different versions of the same band Let me build one with a few options instead. It'll take a little longer than the first one and much less than the fourth, and after that you can add it anywhere yourself and choose the layout each time. If I build four separate ones, the fifth request is another job. Names the cost of the alternative rather than arguing for reuse in the abstract.

P4.3 — The Cart AJAX API

When a customer reports "the cart let me buy 50 and then wouldn't" That's a known behaviour of one of Shopify's cart endpoints — it doesn't check stock when you change the quantity of something already in the cart, so the limit only applies at checkout. I'm switching us to the endpoint that does check, so customers see the real limit in the cart instead of after they've entered their card. Names it as a platform behaviour, not a mystery, and describes the fix by where the customer experiences it.
When asked to add a "remove this discount" button Slightly awkward, and worth knowing why. Shopify's cart takes the full list of discount codes, not add-one or remove-one. So to remove one, we send all the others. It works fine — it just means the cart has to know every code currently applied, which is a thing I need to keep track of properly. Explains an odd bit of extra work with the reason, so it does not look like padding an estimate.

P4.4 — Discounts on the storefront

When the numbers do not add up on the cart page Nothing's charging twice — the discount is applied once and correctly. The line prices are being read from an older field that doesn't include discount codes, while the total does. So the gap you're seeing is the discount. It's a display fix, and I'd like to do it soon, because customers seeing inconsistent numbers at the cart is the worst place for it. Kills the scary theory first, explains the real cause in one sentence, then argues for urgency on the customer's behalf rather than the code's.
When asked to show a "you saved X%" calculation Happy to show it, and I'll take the numbers from Shopify rather than working them out in the page. If the theme does its own maths, it'll eventually disagree with what's actually charged — usually on a promotion, which is exactly when you'd least want it. Says yes, and defends "no arithmetic in the theme" with the moment it would fail.

P4.5 — Hydrogen, Oxygen and building headless

Before a headless build Before we commit, can I list your installed apps? Anything that shows something on your storefront — reviews, upsells, a store locator — mostly stops working when we leave the theme, so each becomes a custom build and then something I maintain forever. That list is usually the biggest number in the quote, and it's the one nobody expects. Names the largest hidden cost and asks for the one artefact that quantifies it.
On an existing headless site you have been asked to take over Give me a day before I quote. I need to know when this was last upgraded — Shopify retires API versions after about a year, and a custom storefront that's been untouched for two is running on a contract nobody chose. It might be fine. I'd rather know than assume, because it changes whether this is maintenance or a rebuild. Uses the verified fall-forward mechanism from P1.3 to justify a paid discovery day, rather than guessing at the state.

P5 · Checkout, money and Plus

P5.1 — Shopify Plus, and Markets

When asked "do we need Plus?" It depends which piece. Changing the checkout page itself — the payment and shipping steps — that's Plus only. Everything after the order is placed works on your current plan. And the server-side logic, like custom discount rules, doesn't need Plus at all. Tell me which of the three matters most and I'll tell you whether it's an upgrade conversation. Splits one question into three answers, which is honest and usually saves the client money.
When a client mentions selling internationally One thing to check early: how many markets are set up in your Shopify account? These can multiply fast — I've seen a store with over two hundred, one per country, created automatically by a cross-border app. It matters because prices and availability can be set per market, so if we're syncing prices I need to know which one we're writing to. Turns an invisible configuration detail into a specific question before it causes a whole country to sell at the wrong price.

P5.2 — Checkout extensibility

On inheriting a store with old checkout customisations Before we plan anything new, I need to check something with a deadline attached. Shopify has retired the old way of customising the order confirmation page — for stores on your plan that happened in August 2026. So any tracking or upsell script there has either stopped or is about to. There's a report in your admin that lists exactly what you have. Can I run it today? Leads with the dated risk, not with the new work, and asks for one concrete thing. Deadlines get attention that "technical debt" never will.
When a client wants to change the payment step and is not on Plus That specific page is Plus-only — Shopify doesn't allow app content on the payment and shipping steps below that plan. What I can do on your plan is everything after the order is placed, plus the server-side rules like custom discounts. If the payment-step change is genuinely important, that's a plan conversation, and I'd want to be sure it's worth it before you upgrade for one message. Says no with the reason, immediately says what is possible, and declines to upsell a plan for a small feature. That last part buys a lot of trust.

P5.3 — Shopify Functions

Explaining what a Function is, without jargon Normally when something happens in your store, Shopify tells our server and our server responds. This is the opposite: we put a small piece of our logic inside Shopify, and Shopify runs it itself. That means it's instant and it can't be affected by our server being slow or down — which matters, because this runs while a customer is checking out. Explains it by contrast with the thing the client already understands, and lands on the benefit they care about.
When the rule needs data from another system One constraint worth knowing: that logic runs inside Shopify and can't reach out to your loyalty system while the customer is there. So we copy each customer's tier into Shopify ahead of time and the rule reads it from there. Practically that means a tier change takes a few minutes to affect discounts rather than being instant. Is that acceptable? States the constraint, gives the workaround, names the exact cost in the client's terms, and asks. Four sentences and no jargon.

P5.4 — Flow: when automation replaces your code

When the request is a Flow workflow I don't think you should pay me for this one. Shopify has a built-in automation tool that does exactly this — when an order is over an amount, tag the customer and send an email. I'll set it up with you now, and you'll be able to change the amount yourself later without asking me. Let's spend the budget on something it can't do. Turning down work you could bill for is the single most trust-building thing you can do with a client, and it costs you almost nothing.
When a client asks for "an app" and means a sync Worth checking what you picture here. If you're expecting screens in your Shopify admin, that's real design and build work. If what you actually want is the two systems staying in step, it can run entirely in the background with nothing to look at — which is faster and cheaper. Is there anything you'd want to click? Finds out whether an expensive part of the scope is wanted at all, before it is in a quote.
When automatic changes appear that nobody can explain Before I dig into our code, can I look at your Flow workflows? Automations built there are invisible to us, and something changing tags or inventory on its own is very often a workflow somebody set up months ago and forgot. Checks the cheap explanation first. Saves a day roughly one time in three.

P6 · Getting data in and out

P6.1 — The matching key, and custom IDs

Explaining why you need a stable code from them I need one code per product that never changes for the life of that product. Not the name — your team edits those, and if I match on a name, editing it creates a duplicate. Whatever your ERP uses internally is usually perfect. I'll store it against each Shopify product so anyone can see which is which. Explains the requirement through the failure it prevents, and offers the answer they already have.
When duplicates have already appeared These are duplicates from name changes — the previous integration matched products by name, so editing a title made it look like a new product. I'm switching to your product codes, which don't change. Then I'll merge the existing duplicates, and I'll need your team to tell me which of each pair to keep, because both may have sales against them. Names the cause, states the fix, and is honest that cleanup needs the client's decisions rather than pretending it is automatic.

P6.2 — Three ways to push it, and bulk operations

When asked how long an import takes The upload is quick; the queue on Shopify's side is what takes time, and I won't have a real number until I've run it once at your volume. What I can tell you is that it's restartable and that I'll give you a count of what succeeded and what didn't — because a job finishing isn't the same as every row working. Refuses a made-up number, offers restartability, and sets the expectation that there will be a failure list.
When someone suggests just using a CSV That's the right tool if you're doing it by hand occasionally. For something we run repeatedly I'd rather use the API route, because it tells me exactly which rows failed and why. With a spreadsheet import, a bad row tends to disappear quietly, and we find out from a missing product. Respects the suggestion, then distinguishes it by error visibility rather than by sounding more technical.

P6.3 — The huge catalogue load, and the throttle that starts at 500,000

When asked for a timeline on a large catalogue I'll give you a range today and a number after one test load. The reason I'm careful is that Shopify limits how fast new variants can be created once a store gets large, and that limit is different on your plan than on others — I've also seen the published figure change. So I'd rather measure it on a test store like yours than quote something I'd have to walk back. Explains the caution with a specific, verifiable mechanism. "It depends" with a reason is a strong answer; "it depends" alone is not.
When the client says "we have 80,000 products" The number I actually need is variants — every size and colour counts separately, and that's what Shopify limits. If those 80,000 average four variants each, we're really talking about 320,000. Worth getting exactly right before I put a date on anything, because the arithmetic changes a lot. Corrects the unit before it enters an estimate, and shows the arithmetic so it does not look like hedging.

P6.4 — The cutover and the proof

Agreeing the plan, a week before Two things I need from you before the date. First, a freeze on editing products for the window — a few hours, announced to your team. Second, I want us to agree now what would make us stop and revert. My suggestion: any price difference in your top fifty sellers, or more than one percent overall. Deciding that today is much better than deciding it at two in the morning. Asks for the freeze and pre-agrees the abort criteria in the same conversation, when everyone is calm and reasonable.
During the cutover, when asked to just push through We agreed a stop line last week and this is inside it, so we're going ahead — but I'm putting these twelve products on a list with a name and a date against them, and they'll be in the handover note. What I'm not going to do tonight is change any code to fix them. Tired changes on a live store is how a small problem becomes a big one. Uses the pre-agreed line as the authority, and refuses the one genuinely dangerous action while still saying yes.
The morning after Here's the record: 40,120 variants expected, 40,120 loaded, 0 failed. Prices compared on all of them, 12 differences, all long-tail and on the list. Stock compared, no differences. I also checked ten products by hand against your old system, including your three bestsellers. Reconciliation runs again tonight and I'll send the result. Numbers with denominators, the hand-check named, and the next checkpoint stated. This is what "it worked" sounds like when it is evidence rather than a feeling.

P6.5 — What a migration is, and what never moves

First meeting, unprompted Three things I want to flag now rather than later. Customer passwords can't move between platforms — everyone will need to set a new one, or sign in with a code we email them, so that needs a communication plan. Second, anything living in your current apps — reviews, loyalty points — is a separate export each, and I need the app list this week. And third, we need redirects from every old URL, or you lose your search traffic on day one. Three items, all of which are cheap now and expensive later. Delivering them unprompted is the difference between a supplier and a lead.
When asked to migrate ten years of orders Let me ask what they're for. If it's so customers can see what they bought, we can bring across the items, dates and totals and that works well. If it's for accounting or tax, I'd keep the old system readable instead — a recreated order isn't the original transaction, and making it accurate enough for an audit is a project on its own. Which one matters? One question that can remove the largest and least valuable chunk of a migration from the scope entirely.

P6.6 — Orders, money, and the Shopify → Shopify replatform

Before importing any orders One thing I want to be careful about. When we recreate old orders, if we don't send the exact price paid, the system can fill in today's price instead — so an order from 2019 would show what the item costs now. Nothing would look broken; the numbers would just be wrong. So I'll send every price explicitly and then check ten old orders by hand against your current system before we sign it off. Explains a silent failure in the client's own terms and commits to the specific check that catches it. This is the sentence that makes a client trust the whole migration.
When asked to quote a Shopify-to-Shopify move as "simple" It's simpler in one way — the data shapes match, so there's no translation. But every product, customer and order gets a brand new ID in the new store, so everything that references anything has to be re-mapped. And every app has to be reinstalled and its data exported separately. That's the actual work, and it's the part that looks invisible from outside. Concedes the genuine advantage first, which makes the rest credible rather than defensive.

P7 · Shipping, delivery and tax

P7.1 — Shipping rates and delivery profiles

When a client asks for different shipping on heavy items That's a separate shipping profile, which is a bigger change than it sounds. Once those products are in their own profile they stop using your normal rates entirely — so we have to set up every country and every rate again for them. Worth doing if the economics are really different. If it's just "a bit more", a weight-based band on your existing rates is far less to maintain. Names the real cost — duplicated configuration and a doubled test matrix — and offers the cheaper option. Most clients take the band.
When customers in one country cannot check out That's almost always configuration rather than a bug, and it's usually one of two things: those products are in a separate shipping profile that doesn't list that country, or the country isn't in any zone. I can check both in about ten minutes. Nothing is broken — there's just no rate for that combination, and checkout won't let someone through without one. Reassures, names the two likely causes specifically, and gives a time. "No rate exists" is a much calmer explanation than "checkout is broken".

P7.2 — Carrier-calculated rates: your server inside checkout

Before agreeing to live carrier rates I can do it, and I want to flag one thing about how Shopify treats us. The busier your store gets, the less time it gives us to answer — down to three seconds on a big day. So I won't call the courier while the customer is waiting; I'll fetch their prices in the background and answer instantly from what we already have. Slightly less current, and it can't fall over on your biggest day. Names the counter-intuitive constraint, states the design, and prices the trade-off in one sentence the client can actually weigh.
When asked what happens if your service goes down Shopify has a built-in fallback and we use it deliberately: if we can't answer confidently we tell it to use your own configured rates instead. So the customer always sees a shipping option and can still check out — the price is just your standard one rather than the live courier quote. That's much better than showing them nothing. Explains fail-open in the client's terms — "they can still check out" — rather than as a status code.
When the client wants rates to depend on something Shopify does not send That one's a problem, and it's worth knowing why. Shopify caches our answers for fifteen minutes and the cache is keyed on the cart, the addresses and the weights — not on the customer or the time. So a rule based on who the customer is would simply not get asked most of the time; they'd get whoever's rate was cached first. We'd need a different mechanism for that. Refuses on a specific mechanism rather than "that's not possible", and the mechanism is checkable — which is what makes the no credible.

P7.3 — Tax: what Shopify does, and where you must not guess

Any tax question at all That's one for your accountant rather than me. What I can tell you is the mechanical part: Shopify calculates the tax at checkout, once it knows the customer's address, and I make sure that number reaches your other systems unchanged. What I never do is work tax out myself — if I did and it were wrong, that's your liability. Declines cleanly, states what you do own, and gives the reason in terms of their risk rather than your caution. Nobody pushes back on this.
When asked to show tax earlier in the journey Shopify deliberately removed the tax fields from the cart, because tax needs the full address to be right. So anything I showed before checkout would be an estimate, and I'd want it labelled as one. If it's about European customers seeing inclusive prices, that's a different and better-supported thing — a per-market price presentation setting rather than a calculation. Explains the platform's reasoning, offers the legitimate alternative, and separates "display convention" from "calculation" — which is the distinction that matters.
When they want their own tax engine I checked, and that route isn't open to us — Shopify's tax platform is invitation-only for tax software companies. So the options are Shopify's own tax calculation, or one of the tax apps they've already approved. Worth your accountant picking between those two rather than me. A specific, checkable reason for a no, and it hands the remaining choice to the right person.

P8 · After the sale

P8.1 — Returns, refunds and order editing

When asked for automatic refunds I can do that, and I'd want a limit on it before we switch it on. Refunds move real money out of your account, and if our logic is wrong it's wrong repeatedly and quietly. My suggestion: refund automatically up to a value you're comfortable losing to a bug, and anything above that goes to a person. What's that number for you? Says yes, names the specific risk, proposes the control, and hands them the one decision only they can make.
On restocking One question per return type, and it matters more than it sounds. When someone returns something faulty, do you want it back in sellable stock? I'd say no — otherwise the website will sell it and nobody can ship it. But for a change of mind, yes. I need that rule per reason code, not one setting for everything. Turns an invisible technical flag into a question about their warehouse, which they can answer confidently.
When an order needs changing after payment I can edit a paid order, and Shopify lets me build the change as a draft first so someone can see the new total before it's applied. I'd keep that step even when it's tempting to automate — this is the one operation where the customer already has a receipt that says something different. Explains a deliberate slowdown by naming what the customer is holding. Nobody argues with that.

P8.2 — Payments, and what you must never touch

When a client says "we need a payments integration" Let me find out which of three things you mean. If you want to accept cards, that's a settings job and I'm not needed. If your provider already has a Shopify app, we install it. If you want to offer your own payment method to other Shopify merchants, that's a regulated build with PCI obligations, a five-day settlement duty and fraud responsibility — that's a product, not a feature. Which is it? Three options, and two of them are free. Clients regularly discover they wanted the free one.
When asked to hide a payment method for some customers That one's genuinely doable and reasonably small — Shopify has a payment customisation function for reordering and hiding methods, and it doesn't need Plus. What I can't do is influence which payment succeeds; that's between the customer, their bank and the gateway. Says yes to the real request, and draws the boundary at the thing that is not yours.
When someone asks you to store card details No — and not because of a preference. Card data carries PCI obligations that neither of us wants to take on, and Shopify and your gateway already hold it. If the goal is charging a customer again later, that's a saved payment method held by the gateway, and I can work with the token rather than the card. Refuses in one word, gives the reason, and immediately offers the legitimate route to what they actually wanted.

P8.3 — Draft orders: selling outside the storefront

When asked for phone or wholesale ordering That's a draft order — your team builds the order, then either emails the customer a link to pay, or marks it paid if they've already transferred the money. Same mechanism handles quotes and wholesale invoices. Two things I need from you: who's allowed to change a price, and by how much. Names the mechanism once for all four use cases, then asks the control question before it becomes a problem.
On quote expiry Shopify won't expire a quote — a draft order sits there until someone acts on it. So if you want 30-day validity, I build that, and I'd also want a rule for what happens when an expired quote is accepted anyway. Do we block it, or re-price it? Names a platform gap, offers to fill it, and asks for the business rule rather than choosing one.

P9 · Other ways to sell

P9.1 — B2B: companies, catalogs and price lists

When B2B enters the conversation Worth flagging early, because it changes something we already built. Right now our sync writes one price per product. B2B prices don't live there — each business customer gets their own price list, so writing the normal price won't change what they pay. I need to add price lists to what we sync and to what we check nightly. Otherwise your wholesale margin drifts and our report says everything is fine. Names the invisible failure precisely, and asks for the work before it becomes a margin problem. This sentence is the whole value of the Lesson.
When scoping B2B I'd treat this as a second way of selling rather than a pricing feature. Business customers get their own prices, their own product visibility, their own tax settings, payment on terms rather than by card, and optionally an approval step before an order is accepted. A1 · What an app is

A1.1 — Anatomy of a Shopify app

When a client asks "will this be in the App Store?" It doesn't need to be. Since it's only for your store, we build it as a custom app — that skips Shopify's review queue, so we ship sooner. The trade-off is that nobody else can install it, and it can't bill through Shopify. If you ever want to sell it to other retailers, tell me now, because that's a different build. Gives the recommendation, the benefit, the cost, and the one question that would change the answer. That shape works for almost every technical choice.
When a PM asks why the storefront part is riskier than the admin part The admin part runs on our server, so I can read logs and deploy a fix in minutes. The storefront part runs inside Shopify, where I can't. So I'm keeping the logic on our side and the storefront piece as thin as possible. It'll look like less work than it is. Explains a design choice by naming what you lose, not by naming a pattern. "Thin extension, fat service" means nothing to a PM; "I can't read the logs" does.

A1.2 — App auth: session tokens and token exchange

When a client offers to "just send you an API key" That works for a custom app on your store, and I'll take it — but two things. It can read and write your whole store, so it goes in our secrets manager, never in email or Slack. And if it's ever rotated, the sync stops until we update it, so tell me before you rotate rather than after. Accepts the offer, states the handling rule, and pre-agrees the one operational thing that will otherwise cause a 2am incident.
When someone asks why the sync must not run "as" a staff member If we tie it to a person's login, it breaks when they leave or when their permissions change — and it breaks quietly, months later. The sync gets its own identity that doesn't belong to anyone. It's also better for you: nobody's departure takes the integration down. Frames a technical rule as a staffing risk, which is a thing the other person actually owns.

A1.3 — Webhooks done right

When a client says "so it updates instantly" Usually within seconds, yes. But a webhook is a notification, not a guarantee — it can be delayed, and occasionally it doesn't arrive. So alongside it we run a check that re-reads from Shopify on a schedule and fixes anything that drifted. Without that, one missed message means one wrong stock number forever. Sets the expectation before the first miss, and sells the reconciliation job as insurance rather than extra scope.
When the integration silently stopped and the client asks what happened Our endpoint failed eight times in a row, so Shopify removed the subscription — that's designed behaviour, not a bug. I've fixed the endpoint, recreated the subscription, and backfilled the gap. I'm also adding an alert on the failure rate so we hear about it from monitoring rather than from you. Names the mechanism, does not hide behind it, and closes with the thing that stops the same conversation happening twice.
When a PM asks why you need a queue "just to receive a message" We get five seconds total to answer, and that's the whole budget. If we do the work inside those five seconds, a slow day means timeouts, and enough timeouts means Shopify stops sending. So we accept the message, say yes immediately, and do the work behind it. A hard number and a named consequence. "Best practice" would have lost this argument.

A1.4 — Scopes, protected customer data & compliance

When a client offers full admin access "to make it easier" I'd rather take less. The sync only needs products, inventory and locations — no customers, no orders. That means if our credentials ever leaked, nobody's personal data is exposed, and it keeps us out of a whole category of privacy obligations. It's not extra work for you; it's a shorter list. Turns "least privilege" into two things a client cares about: their customers' exposure, and less paperwork.
When a client asks for a customer name on the sync dashboard I can, but I want you to know what it costs before you decide. Adding a name moves us into a higher tier of Shopify's customer-data rules — extra approval and a data protection review. If support just needs to find an order, an order number does the job with none of that. Which do you want? Never refuse outright and never comply silently. Price it, offer the cheaper option, hand back the decision.
When someone promises a client "deletions happen within 24 hours" I need to correct that before it's in writing. If the customer has ordered in the last six months, Shopify holds the deletion request for six months before it reaches us — the merchant still needs those records for returns and tax. We have 30 days to act once it arrives. Let's say that instead. Catching a wrong promise before it is written down is worth more than anything you will build that week.

A1.5 — Distribution, billing and App Store review

On day one One question that shapes the build: will anyone other than you ever install this? If it's only ever yours, we build it as a custom app — faster, no Shopify review. If there's a real chance you'd sell it to suppliers or peers, I'd build differently from the start, because retrofitting that is significant work rather than a feature. Gets the decision on the record when it is free, which is the entire point.
When resale comes up later Genuinely possible, and I want to be straight that it's a new project rather than an add-on. The sync itself barely changes. What's new is Shopify's app review, billing — a custom app can't charge through Shopify at all — and making it work for many stores at once with separate credentials and separate rate limits. When asked why a few products are wrong and the rest are fine Almost always it's records that changed while we were mid-scan, and our bookmark moved past them. A2.3 — One queue, with retries and a dead-letter

When asked why the sync is "slow" It's not slow, it's paced. When 900 products did not sync They were rejected, not delayed — each has a specific reason and I've got the list. When a PM suggests "just run more workers to speed it up" It won't help — the limit is per store, not per worker. A2.4 — Run it: docker-compose, CI, and what to log

When a client asks "how do we know it's working?" Not from the absence of errors — a sync that's doing nothing has no errors either. Gives them a single number that means something, and pre-empts the false comfort of a quiet log.
When asked to add "just a bit of extra logging" to debug a live issue I'll add it around the decision, not the payload. Says yes to the need and no to the method, with a reason that is about their liability rather than your preference.
When a PM asks why tests do not run against the real store Because then a build fails when someone's token expires or we hit a rate limit — nothing to do with the code being tested. Has a concrete win to point at. An argument with evidence ends the conversation.

A2.5 — The Shopify CLI and the dev workflow

Explains a developer convenience as an audit benefit, which is what the client actually values.
When a schema change needs splitting This one goes out over two releases rather than one. Nothing's wrong — it's just two deploys instead of one, and I'd rather tell you now than have half of it land silently. A3 · The sync discipline

A3.1 — Shopify alone, and what a second system adds

The first meeting, when they say "we want them to match" I want to turn that into something we can build. For each piece of information — the title, the price, how many you have — one system needs to be the one that decides, and the other follows. Where do your staff actually edit prices? And where does a sale reduce stock? Those two answers give us most of it. Converts a wish into a specification using two questions the client can definitely answer, without a single technical term.
When asked why this is harder than it sounds On its own, Shopify can't be wrong — there's only one copy of each number. The moment there are two copies, they can disagree, and most of my work is deciding what should happen when they do. That's not complexity I'm adding; it comes with having two systems. Explains the difficulty as a property of their situation rather than of your work. It is also simply true, which is why it lands.

A3.2 — Ownership, per field not per record

Filling in the table, in the room I'll go field by field and I only need one answer each: if these two systems disagree tomorrow morning, which one would you believe? For the title? For the price? For how many you have left? "Which would you believe" is answerable by anyone. "Which is the source of truth" gets a confident nod and no information.
When both sides insist they own tags Then let's not share it. Your ERP tags start with a marker — I only ever touch those, and I never delete anything else. Marketing's tags are invisible to me. You both keep what you need and neither of you can overwrite the other. Removes the conflict instead of adjudicating it. This is the most reusable move in integration work.
When a client asks you to sync warehouse stock into Shopify I want to check one thing first, because this is where oversells come from. Is the number in your ERP everything in the warehouse, or only what's available to sell online? A3.3 — Absolute writes, safe replay and tombstones

When a client asks what happens if the sync crashes mid-run We just run it again. Every update we send is a complete statement — "this price is 14.99" — rather than an instruction like "add two". So sending it twice changes nothing. That's deliberate, and it's why a failed run isn't an incident. Turns a scary question into a designed-for answer, with a concrete example the client can picture.
When you discover the vendor hard-deletes records There's a gap I need to flag. When you remove a product from your ERP, nothing tells us — it just stops appearing, which looks identical to "unchanged". So deleted items would stay on sale. Two options: ask them for a deleted-items flag, or we compare full lists nightly, which is slower and costs more. I'd push for the flag. Names the invisible failure, gives two costed options, and states a preference. That is the shape of every good escalation.
When someone asks you to delete products that leave the catalogue I'd rather archive them. Deleting destroys the product's web address and its history, so if it comes back next season it comes back as a new page with no search ranking. Archived is invisible to customers and reversible in one click. Frames a reversibility argument in terms of SEO and next season, which are things the client already worries about.

A3.4 — Webhooks are a hint: clocks, order and staleness

When a client asks for "real-time" sync Usually a few seconds, and I'll build for that. But I won't promise instant, because Shopify's own guidance is that a notification can arrive up to a day late. So the design is: react immediately when we're told, and also check on a schedule so nothing can be missed. "Fast, and definitely correct" rather than "instant". Refuses the wrong promise, gives the right one, and cites the platform rather than your own caution.
When one product had a stale price for a day Found it — a notification arrived late and we'd been trusting the values inside it rather than checking the current ones. I've changed it so a notification just tells us to go and look. A late message is now harmless instead of harmful. The nightly check will correct anything else from the same cause. Explains the class of bug, not just the instance, and says what will catch the rest. Clients forgive a fixed cause far more easily than a fixed symptom.

A3.5 — The backlog

During recovery, when asked "how long until it's caught up?" Stock and prices will be right within about twenty minutes — I'm doing those first because they're the ones that cost you money. Descriptions and images will trail behind for an hour or two. I'm deliberately not pushing at full speed, because Shopify would start rejecting us and the whole thing would take longer. Two timelines instead of one, ordered by the client's risk, plus the reason for the pace. Nobody argues with this.
When the queue is empty after a long outage I need to be straight with you: the queue is empty because Shopify stopped sending, not because we're caught up. After enough failures it removes the subscription — that's designed behaviour. I've recreated it and I'm now re-reading everything that changed during the window, so nothing is lost. It'll take longer than a normal catch-up. Says the uncomfortable thing first. A client who later discovers you reported "caught up" will not trust the next report.

A3.6 — Reconciliation, and numbers that do not lie

When asked for one number that proves it works Every night we compare what we sent against what's actually in Shopify, field by field, for prices and stock. The report is "we checked 46,000 values and found 3 differences, here they are". If I only told you the product count matched, that would look reassuring and prove almost nothing. Gives the number, gives the denominator, and pre-emptively dismisses the weaker metric someone will otherwise ask for.
When a price is wrong and it is not your fault We sent 14.99 on Tuesday and I can show you that. It's 12.99 now, and we didn't change it — so someone edited it in the admin, or another app did. That's worth a decision: if staff need to override prices there, I'll stop overwriting that field. If not, I should be putting it back. Turns "who broke it" into "what should the rule be". Only possible because the shadow table exists.
When asked to make the sync fix everything automatically For prices and stock, yes — your ERP owns those, so I'll correct them. For anything your team edits in Shopify, I'd rather show you the difference than silently overwrite their work. Otherwise we get a tug-of-war where a person changes something and it reverts overnight. Says yes to most of it, and gives a vivid reason for the exception.

A3.7 — Store 17 of four hundred

When asked to move from one store to many The sync logic doesn't change much — what changes is the plumbing around it. Each store needs its own credentials, its own place-marker, and its own share of Shopify's rate limit, and one store failing mustn't stop the others. That's the real work, and it's mostly invisible from the outside, which is why it looks smaller than it is. When a PM asks "is the fleet healthy?" I won't give you an average, because 399 fine and one broken averages to fine. What I'll report is the number of stores outside tolerance and which ones. Today that's two, both waiting on the merchant to reinstall. Refuses the misleading metric and replaces it with an actionable one, in the same breath.

The checkpoint That's the shape of it — three parts. Before I go into how a price actually travels, does that much make sense, or shall I go back over any of it? Explicitly offers going back, which makes it safe to admit confusion. "Any questions?" gets "no" from a room that is completely lost.
Closing — measurement And the way you'll know it's working isn't the absence of errors — a sync doing nothing has no errors either. Every night we compare what we sent against what's actually in Shopify and report the differences. If that number is zero, it's working. That's the number I'd put in front of you. Ends on something they can hold and ask for. It also quietly demonstrates you have thought past go-live, which most people have not.

R1.2 — The design conversation: whiteboard for a client, not a grader

Serving both audiences at once At a high level: your ERP owns prices, Shopify owns stock, and we move each one direction only so they can't fight. That's the whole design. Happy to go deeper on how we handle their system being temporarily down, if that's useful. Complete for the decision-maker, with an explicit door for the technical person. Nobody is bored and nobody is short-changed.
When you genuinely do not know I don't know yet, and I don't want to guess at it. What I'd do is load a sample at your real volume and measure — that's about half a day and it turns a guess into a number. Can I do that before we commit to a date? "I don't know" plus a concrete plan and a cost reads as rigour. "I don't know" alone reads as unpreparedness. The difference is the next sentence.
When someone proposes a worse design That could work. The thing I'd want to check is what happens when two people edit the same product in both systems on the same day — with that approach I think we'd get a flicker. Want me to try it and see, or shall we design around it now? Does not reject, names one specific consequence, and offers two ways forward. You get the better outcome without anyone being corrected.

R1.3 — Design a stock-availability platform: domain and engine

Explaining the design in one pass We keep a count per item per location, and crucially we keep when we last heard it. Then before we show anything, we take off whatever's promised to customers coming to collect, hold back a small buffer because shop floors are never exact, and check the number isn't too old. What comes out is "available", "low", "not available", or "we can't confirm right now" — rather than a count we can't stand behind. Describes the whole engine in four sentences with no jargon, and the fourth outcome makes the honesty visible.
When the client asks why the site says no and the shelf says yes Two reasons, both deliberate. One of those three is promised to someone who's on their way to collect it. And we hold back two per shop, because a shop floor is never accurate to the item — things get held, damaged, or left in a fitting room. So we're not reporting your stock, we're answering whether a customer can actually get it. The buffer is yours to set if two feels too cautious. Explains a confusing behaviour as two intentional decisions, and hands them the dial. The last sentence turns a complaint into a setting.

R1.4 — Allocation, data model, consistency and failure at scale

When asked why orders do not always go to the nearest shop Nearest sounds right but it buries your busiest shops — they'd get almost every order, their staff would stop serving walk-in customers, and their stock would empty while your quieter shops sat full. So we score each shop on distance, how much stock it has, and how much it's already handled today. Those weights are yours to set, and I'd rather you owned them than me. Names three specific consequences of the obvious rule, then hands over the controls. The last sentence is what makes them trust the first three.
When a shop complains they are getting too many orders That's a real problem and it's a setting, not a rebuild. Each shop has a daily cap and a weighting. I can lower theirs today. Worth deciding together where that work should go instead, because it has to land somewhere — that's the trade-off rather than a fix. Responds to a complaint with an immediate action and an honest statement that the work moves rather than disappears.

R2 · Owning the work

R2.1 — Owning ambiguous scope

Asking the one blocking question One thing I need before I start, because it's expensive to get wrong. Does anyone on your team edit product titles or descriptions directly in Shopify? If they do, and I set this up with the ERP as the source, their edits would get overwritten every night. Everything else I can make a sensible call on and tell you what I chose. One question, the consequence spelled out, and an explicit promise to decide the rest yourself. That last clause is what makes the question welcome rather than annoying.
Stating decisions, at the start Three calls I've made so I could get moving. Product details sync once a day, stock every few minutes. I'm matching products on your ERP product code. And if your ERP is unreachable we hold the last known values rather than blanking anything. All three are easy to change — flag any that don't match how you work. Shows initiative and stays correctable. Three specific decisions with an open door reads as ownership; asking about all three reads as needing supervision.
When the ambiguity is really a disagreement between two people I've hit something I shouldn't decide. Your buying team wants prices controlled in the ERP; the marketing team is currently setting promotional prices in Shopify. Both are reasonable, and whichever we pick means the other loses something. I'll keep working on the parts that don't depend on it — can the two of them agree by Thursday? Refuses to arbitrate a business decision in code, keeps working, and asks for a dated resolution. This is the highest-value sentence in the Lesson.

R2.2 — Estimating, pacing, and holding two projects

The estimate itself Three days if their system can tell me what's changed since a given time. Eight if it can't, because then I have to compare full lists every night, which is a different piece of work. I'll know which within an hour of seeing their API docs — can you get me those? Range, reason, and the exact thing that collapses the uncertainty, framed as a request. The client can now do something to shorten their own project.
Naming the client's part in the timeline Two things on your side are on the critical path: the API credentials from your ERP vendor, and a decision on who owns product descriptions. If both land this week we're on for the 14th. If the credentials take three weeks — which happens — the date moves by that much, and I'd rather we both see that now. Makes their dependencies visible before they cause a delay, without blaming anyone for something that has not happened yet.
Re-estimating early Something's changed and I want to tell you today rather than in three weeks. Their API can't tell me what's changed since a timestamp, so we're on the eight-day path, not the three-day one. Nothing's gone wrong — this was the unknown I flagged, and it resolved the expensive way. Ties the revision back to a risk you already named, which turns bad news into a demonstration that your process works.

R2.3 — Communicating with a busy client

The four-line decision message Need a call from you before Thursday. Do we send historical orders across, or keep the old system readable as an archive? Sending them is about two weeks and the money won't be exactly right; the archive is a day and keeps the numbers accurate. I'd do the archive. If I don't hear by Thursday I'll plan for the archive and we can revisit. Ask, two costed options, a recommendation, a dated default. Answerable in five seconds with "agreed".
Following the default through Didn't hear back, so as flagged I've gone with the archive. Nothing is lost — if you want the full order history later, it's still possible, it's just the two-week version. Wanted to make sure you knew the choice was made. No reproach, and it restates that the decision is reversible. This is the message that makes a client comfortable with you using defaults again.
Escalating an irreversible one I've asked twice about who owns product pricing and I don't want to guess, because whichever way I build it, the other team's work gets overwritten and there's no undo. I've paused that piece and I'm working on inventory instead, so nothing is idle — but the go-live date moves by however long this takes. Who should I be asking? Names the irreversibility, shows you kept working, states the cost, and asks for a person rather than an answer. That last part is often what actually unblocks it.

R2.4 — The integration project: discovery to rollout

Setting up discovery on day one Before I design anything I want two days to look at the actual data in both systems — how many variants, how well they match up, which fields are actually filled in, and how much changes daily. I'm not doubting what you've told me; it's that these numbers decide the whole approach, and I'd rather find a surprise now than in week six. I also need one name: who decides when something's ambiguous? Asks for the audit and the decision-maker together, and frames the audit as protecting the project rather than checking their claims.
Presenting an uncomfortable audit result Here's what I found. 94% of your products match between the two systems — but the 6% that don't include eleven of your top hundred sellers, so it matters more than the number suggests. Most have blank supplier codes. I need either those filled in, or a rule for what we do without one. It's a day or two of someone's time and it saves us a lot later. Leads with the weighted framing, names the cause, and asks for a specific, bounded action rather than presenting a problem.
Arguing for the awkward store early For the second group of stores I'd like to include the one with the older till system, rather than saving it for last. If it's going to cause problems I want to find them while we still have time and attention for it. Leaving it to the end means discovering it when everyone thinks we're finished. Gives the reason in terms of when attention is available, which is a scheduling argument rather than a technical one — and therefore lands with a PM.

R2.5 — Build vs buy, lock-in, and the exit

The recommendation I'd buy it. You could build it — the inventory part isn't the hard bit — but you'd be building the collection flow, the store locator and the staff screens, then maintaining them forever, and customers don't choose you because those are bespoke. Two conditions though: I want it behind one piece of our code so we could swap it, and I want written confirmation you can export your own data whenever you like. A clear recommendation with two conditions that cost nothing and preserve every option. This is what a lead sounds like on a commercial question.
The question they did not ask One thing worth asking them before you sign: if you left in three years, could you take your data with you, and in what format? It's a much easier conversation now than later. Vendors answer it happily pre-sale and much less happily afterwards. Offers a piece of commercial advice a developer is not expected to give, which is exactly why it lands.
When the client wants to build for the wrong reason I'll build it if you want it. The question I'd want answered first is who maintains it in two years — because this touches stock and customer promises, so it can't be left unowned. If there's a name, building is fine. If there isn't, buying is genuinely the safer call even though it feels like less control. Does not refuse. Names the one condition and is honest that buying feels worse and usually is not.

R2.6 — Agile delivery as a senior

Standup, with a blocker Delta load is working end to end. Today I'm on inventory write-back. Still blocked on the ERP credentials — I chased on Tuesday, nothing yet. If they land tomorrow the date holds; after that it starts moving. Progress, plan, blocker, and the consequence of the blocker. Four clauses and the last one is what gets it acted on.
Refusing an unready ticket I don't want to put a number on this one yet — it'd be a guess and it'd end up in the plan. What I can do this sprint is the read-only half: pull their data, log exactly what we'd change, write nothing. That's three days I'm confident about, it's demonstrable, and it answers the two questions that decide the rest. Refuses and immediately offers something valuable of the same size. Almost impossible to argue with, and it keeps the sprint full.
At the demo Before I show you it working, I want to show you it failing. I'm going to turn the ERP off mid-sync. You'll see it retry, then give up on the ones that can't work, and then the report tells us exactly which records need attention. That's the part I'd want to see if I were you. Demonstrating failure handling is the single most confidence-building thing you can do in a review, and almost nobody does it.

R3 · The sentences

R3.1 — Buying thinking time, and saying "I don't know yet"

A hard technical question you can answer, but need a moment for Let me take that in two parts. First, whether it's possible — yes. Second, what it costs — that depends on one thing, which is whether their system can tell us what changed since a timestamp. "In two parts" buys the pause and structures the answer. You now have a scaffold instead of an open field.
A number you genuinely do not have I don't know yet, and I don't want to guess — a number I invent today becomes the plan. Give me half a day to load a real sample and I'll have a proper answer. What I can commit to now is that timing. Refuses, gives a method, gives a cost, and commits to something concrete. This is the strongest available answer and it should be automatic.
When you have over-explained and lost the room I'm overcomplicating this. The short version: their system decides prices, Shopify decides stock, and each one only travels one direction. That's it. Resets cleanly and usually lands better than the original attempt. Self-correcting in public reads as confidence, not as weakness.

R3.2 — Saying no without sounding negative

Not possible That specific page is Plus-only — Shopify doesn't allow app content on the payment and shipping steps below that plan. What I can do on your plan is everything after the order is placed, plus the server-side rules. If that page genuinely matters, it's a plan conversation, and I'd want to be sure it's worth it for one message. Names the platform rule, offers the alternative, and declines to upsell them. That last part is what makes the no trustworthy.
Possible but unwise I can build it. Before you decide — that number includes stock that's already been sold but not shipped, so sending it across would let customers buy things you can't ship. I'd use the sellable figure instead. Same work, and it won't oversell. Shall I do that? Yes, then the consequence, then the better version, then a question. They get to choose and the right thing is the easy choice.
Possible but not now Yes — about three days. Where would you like those three days to come from? Right now they'd have to come out of the reconciliation report, and I'd keep the report if it were me, because it's how we'd catch anything going wrong quietly. Never refuses, makes the cost unavoidable, and gives a recommendation. This is the most reusable sentence in the Chapter.

R3.3 — A range, not a number

The estimate Three working days if their API can tell me what's changed since a given time. Eight if it can't, because then I'd have to compare the full catalogue every night, which is a different piece of work. I'll know within an hour of seeing their documentation — can you get me that? All four slots, the unit stated, and it ends by giving the client something they can do to shorten it.
When they want one number I'll give you a firm number on Thursday. To get there I need their API docs and half a day to run a test load. If you need a single figure today, I'd have to quote the bad case — eight days — because I can't promise the good one yet. I'd rather give you the real number on Thursday. Offers the commitment, then shows what insisting actually costs them. Most people choose Thursday.
When the range collapses badly Update on the estimate, today rather than in three weeks. Their API can't do changed-since, so we're on the eight-day path. Nothing's gone wrong — this was the unknown I flagged, and it resolved the expensive way. Ties it back to a named risk. The same news delivered without that reference sounds like a slip; with it, it sounds like the process working.

R3.4 — Disagreeing upward, and the senior narrative

Disagreeing with a PM under time pressure I want to hit that date too. The one thing I'd worry about is that without the checking report we can't tell a working sync from a stopped one — they look identical. Your call, but I'd keep a half-day version that just compares prices and stock, and drop the rest. Agrees, one concern, and a cheaper version of your own position so they can say yes without losing their constraint.
Overruled, and moving on Understood, we'll go without it. I've written the concern down so if stock numbers look odd later we know where to check first. On to the inventory piece. Accepts cleanly, records once, and changes subject in the same breath. The last three words are what stop it sounding grudging.
The thirty-second narrative Six years on Shopify. The first three were deep in themes and storefronts, so I know where that platform hurts and what breaks in a real shop. Then more front end, and increasingly the integration side — how Shopify talks to the systems behind it. That's what I'm focused on now, and it's where I want to keep going. Direction, specificity, and it ends on where they are heading. Thirty seconds and no technology list.

R4 · Mentoring and pressure

R4.1 — Mentoring and code review, both directions

When asked how you would mentor a junior Mostly by giving them the question rather than the answer. If they've written something that breaks on a retry, I don't say "use absolute values" — I ask "what happens if this runs twice?" They get there themselves, and next time they ask themselves. And if I find myself asking the same question three times, I write it down as a rule, because at that point it's our process failing, not them. Concrete, has an example, and the last sentence shows you think about systems rather than about people's shortcomings. That is what a lead sounds like.
When asked how you handle criticism of your own work If they're right, "good catch, I'll fix it" and no explanation — the explanation is just me protecting myself. If I disagree I say why and ask whether it changes their view, because it often turns out they know a constraint I don't. The reviews I've learned most from were the uncomfortable ones. Specific behaviours rather than a claim about being open-minded. Anyone can claim the attitude; describing the actual sentences is evidence.

R4.2 — Confident problem-solving under pressure

First response to a live problem Let's stop it getting worse first — I'll pause the sync so nothing else gets overwritten. Then give me two product codes that are wrong and I'll trace exactly what we sent and when. I'd rather see it than guess at it. Mitigation, then method, in two sentences. It also converts the client into someone supplying evidence rather than watching.
Mid-investigation, asked "what's causing it?" Two possibilities and I don't want to guess between them yet. Either we sent the wrong value, or we sent the right one and something else changed it afterwards — and our record of what we sent will tell us which. Ten minutes. Refuses to name a cause, shows the method, and gives a time. All three reduce the client's anxiety more than a confident guess would.
Asking for the room Give me twenty minutes on my own with this and I'll come back with either a cause or a much better question. It's paused, so nothing's getting worse while I do. Names what you will return with — including the honest possibility that it is a better question. And it reminds them the bleeding has stopped.

R5 · Interviews

R5.1 — The experience gap: talking about what you have not built

The direct question Not in production, no. What I have done is build one end to end — a service syncing a fake ERP with a Shopify dev store, with switches to make the other side fail on purpose so I could handle it rather than hope. What I haven't had is a real merchant's data wrong on a Monday morning with someone on the phone. That's the part I can't practise. Three parts, no hedging, and it ends on the honest remainder. The last sentence is what makes the first two credible.
When they push on the difference Fair — a dev store isn't production. The rate limits and webhooks are real, so I've hit real throttling and real duplicate deliveries. What's missing is scale, real money, and the pressure. I'd want to be paired with someone who's done a live cutover before I ran one alone. Concedes the point precisely, states exactly what does transfer, and asks for the support you would actually need. That request is a strength, not a weakness.
Turning the gap into a question for them Can I ask how you'd want that handled? If something's quietly wrong at nine in the morning, do you want me to pause the sync and investigate, or fix forward? I'd default to pausing — but I'd rather know your preference now than guess on the day. Converts the topic from your history into how you would work together. It also shows you have thought about the failure they were worried about, which is the underlying question.

R5.2 — What a Shopify tech-lead interview actually probes

Opening a design answer Two questions before I design anything, because they change the answer. Can the ERP tell me what's changed since a given time? And how does it tell me something was deleted? If the answer to the first is no, this is a nightly full comparison rather than an incremental sync — different piece of work. Demonstrates the habit rather than describing it, and shows you know which unknowns are load-bearing.
Volunteering a failure The bit I'd want to get right is what happens when the same webhook arrives twice — which it will. Without handling that, a duplicate delivery becomes a duplicate order. So I'd make the message id a primary key and let the second insert fail, rather than checking first, because two workers can both pass a check. Unprompted, specific, and it includes why the naive version is wrong. This single answer moves you from assessed to consulted.
A limit, dated The extra variant throttle kicks in at half a million variants on the store, then caps new ones at ten thousand a day, and Plus is exempt. I checked that this month — and worth saying, that number had changed since I last looked, so I'd re-check before quoting it in a proposal. The fact, the date, and the habit. The last clause is worth more than the number.

R5.3 — The full mock

When you scored well but the gap is real I can talk through all of that, and I want to be straight about the difference between talking and having done it. I've built a sync end to end against a dev store — real rate limits, real webhooks, deliberate failures. What I haven't done is a live cutover with real money moving. That's the piece I'd want support on first time. Uses the honesty from R5.1 rather than letting fluency imply experience. Fluency without that sentence is exactly what reads as overselling.
When you are asked something you scored 0 on I don't have that one at my fingertips. What I'd do is check Shopify's documentation and note the date, because these limits move — I've seen one change by a factor of ten in three weeks. I'd rather look it up than give you a number I half-remember. Turns a genuine gap into a demonstration of the right habit. Far stronger than a half-remembered fact delivered confidently.

A5 · The Project

A5.1 — The Dev store, the Shape sample, and the generator

When a client offers you a copy of their live data I'd rather not take a copy of the real catalogue. What I need is its shape — how many products, how many variants each, which custom fields you use. I'll build test data that matches that shape. You get the same confidence, and your customer data never leaves your systems. This is the rare answer that is both safer for them and easier for you. It also signals that you think about data handling before someone makes you.
When a PM asks why you need a test store at all Because the failure I need to find is throttling, and it only appears at volume. On a small test set the sync looks perfect. I'd rather find it this week on a store nobody uses than in week one of go-live. Ties the cost of the environment to a specific risk. "Best practice" persuades nobody; a named failure does.
When someone asks for a date and you have not measured yet I can give you a range now and a number after I've loaded the real volume. The reason I'm careful is the throttle: Shopify caps new variants once a store passes half a million, and I need to know if you're near that line. Same work, very different timeline either side of it. A range plus the reason for the range. Chapter R3 drills this sentence pattern on its own, because it is the one you will need most.

A5.2 — The Fake ERP

When a client asks who owns a field For each field we need one system that decides, and the other one follows. Your ERP should own titles and prices — that's where your staff edit them. Shopify should own stock, because that's where the sale happens and it changes by the second. Two systems both deciding the same field is the one arrangement I'd push back on. "Who decides" is the question a non-engineer can answer. "Source of truth" makes people nod without understanding. Ask the version they can answer.
When a PM asks why you are building a fake version of their system I need their system to fail on demand — go down, send stale data, repeat a record. I can't ask the real one to do that on a schedule. Half a day of fake ERP buys me every failure test, and it means the first time we see those bugs isn't in production. Names the cost, names what the cost buys. Never justify work with "good practice" when you can justify it with a bug you will otherwise ship.
When a vendor says "just poll our API every hour" That works, and I want to check one thing first: does your API tell me what changed since a timestamp, and does it page with a cursor? If it's page numbers, I'll miss records whenever your data changes during my scan. It's a quiet failure — nothing errors, the numbers just drift. Two specific questions instead of a general worry. Vendors answer specific questions; they deflect general concerns.

A5.3 — Catalogue out

When a client asks how long the initial load takes The upload itself is quick. What takes the time is the queue on Shopify's side, and I can't promise a number until I've run it once against real volume. What I can promise is that it's restartable — if it fails at 80% we don't start again from zero. Restartability is the thing a client actually cares about and rarely knows to ask for. Offering it unprompted is what a lead sounds like.
When someone says "the import finished, so we're done" The job finished, but each row can fail on its own and those errors are in a separate results file. Give me twenty minutes to reconcile the counts before we tell anyone it worked. This is the sentence that prevents the worst kind of go-live: the one everybody has already celebrated.
When a PM asks why you are testing on a smaller plan than the client has Their store is Plus, which gets ten times our rate limit and skips one throttle completely. If I build against those limits I'll never see the throttling bugs. Testing somewhere stricter means the client's store is the easy case, not the surprise. Reframes "worse environment" as deliberate margin. That is a lead's argument, not a developer's excuse.

A5.4 — Webhooks in, inventory back

When asked why inventory goes the opposite way to everything else Because that's where it actually changes. Your ERP decides what a product is and what it costs, but a sale happens in Shopify — so Shopify knows the quantity first, and we carry that back to you. It means one product has information flowing both ways at once, which sounds odd but is the arrangement that stops the two systems fighting. Explains a design that looks inconsistent by grounding it in where the event happens. Clients accept it immediately once "a sale happens there" is said aloud.
When asked how fast the update is Usually a few seconds. I won't say instant, because Shopify's own guidance is that a notification can arrive up to a day late — so alongside reacting to notifications we also re-check on a schedule. What I can promise is that a late or repeated message can't do any damage, which matters more than the speed. Refuses the wrong promise and replaces it with a better guarantee.

A5.5 — The queue, the dead-letter and the proof

The one number that means "it works" Every night we compare what we sent against what's actually in Shopify, field by field, for prices and stock. The report says "we checked 46,367 values and found 3 differences, here they are". If I only told you no errors had happened, that would sound reassuring and prove almost nothing — a sync that's stopped has no errors either. Gives the number, the denominator, and pre-empts the weaker metric someone will otherwise ask for.
When 900 records did not sync They were rejected, not delayed — each has a specific reason and I've grouped them into three problems rather than 900 lines. I don't retry those, because they'd fail identically and use up the capacity the working records need. Fix the three and they'll go through on the next run. Separates "failed" from "not tried yet", and turns a scary number into three tasks.
Now that the Project runs — the sentence this Step buys you I've built one end to end. It syncs a catalogue out and inventory back, and I deliberately broke it ten different ways — stale data, duplicate messages, the other system down, a killed process mid-batch — to check the report catches each one. What I haven't had is a real merchant's data wrong on a Monday morning with someone on the phone. That's the part I can't manufacture. Specific enough that only someone who did it could say it, and it still names the remainder honestly. That combination is the whole point of the Project.
Reading these does nothing. Saying them does. Pick three and say them out loud now.
