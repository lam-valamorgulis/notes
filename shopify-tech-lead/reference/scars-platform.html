Reference · Track 1

Scars — Platform

Every "Where it hurts" from Track 1, on one page. Read before a client call.

How to read this Red = costs money. Purple = fails with no error. Dashed = not documented, engineering judgement. All facts verified against shopify.dev on 2026-08-23 unless noted.

The object model

Writing on_hand into available They differ by exactly what is already sold. Overwrite one with the other and you re-sell boxed items. The most common cause of overselling in an integration. → P1.1
Assuming one order is one shipment An order can hold several FulfillmentOrders, one per location. Model the fulfillment order, not the order.
A missing InventoryLevel is absence, not zero A variant not stocked at a location has no level there. You cannot write to a level that does not exist.
tracked: false No meaningful quantity, and writes do nothing useful. Check it before trusting or setting a number.
Mapping an ERP item to a Shopify product Prices, SKUs and stock are on the variant. Works only while every product has one variant, then breaks permanently.

APIs, limits and versions

Retrying a query over 1,000 points The single-query ceiling is checked before execution, on every plan. Waiting never helps — reduce the page size. → P1.2
Porting REST error handling to GraphQL REST throttles with 429; GraphQL throttles with 200 OK and a THROTTLED error in the body. A status-code check silently stops noticing.
Over-asking in a query The bucket must hold the requested cost before running. Fields you never read still reserve capacity.
No API version pinned Requests go to the oldest supported version, which moves quarterly. Behaviour changes on Shopify's schedule. → P1.3
Fall forward A retired pinned version is silently served by a newer one. Nothing errors. "It hasn't errored" is not evidence of health.
Two versions in one codebase Your constant says one thing, a client library defaults to another. Both work, and disagree about one field, sometimes.
Webhook subscriptions carry a version too Easy to pin your calls and forget the subscriptions. Upgrade both together.

Custom data

Metafields with no definitions Stored and inert: not editable in the admin, not validated, not filterable. Fixing it later means creating definitions and reconciling every existing value. → P2.1
The 10,000-byte Function cliff Function input queries do not return metafield values over 10,000 bytes — the Function gets null. Stored fine, Admin API fine. Small test products pass; real ones do not.
analytics_queryable in TOML Documented: it deploys without error and the capability is not set. Verify capabilities after deploy.
Mutating a TOML-declared definition via the API Declarative definitions are read-only through the Admin API. Queries work; mutations error.
TOML only creates app-owned metaobjects Merchant-owned definitions must be created via GraphQL. The deploy succeeds and you get the wrong kind. → P2.2
An id stored at the wrong level Verified on a live store: a product-level external id that actually identified only one variant. Every lookup matched that one and silently mismatched the rest.

Inventory, locations, the till

Inactive locations excluded by default locationsCount includes them; locations() does not. Verified on a live store: count 4, list 3. The hidden one was inactive and flagged for online orders. → P3.2
Treating "active" as "can ship" Separate properties. A location can be active and fulfil nothing.
A store locator built from the location list It will include warehouses and app-created fulfillment-service locations. Customers get offered places they cannot visit.
Publishing shelf stock as available Held, damaged and display items are on the shelf and not for sale. Customers travel for nothing. → P3.1
An unlabelled cache Twenty-minute-old availability shown as current. Usually right. When wrong, someone made a journey.
Treating a retail order as unfulfilled A shop sale arrives created and fulfilled. Downstream systems create picking work for goods already carried out. → P3.3
Assuming every order has a customer or an address Retail orders are often anonymous with no shipping address. Failures cluster in one shop and look like a shop problem.

Storefront

update.js for quantity changes Shopify documents it: no quantity validation on items already in the cart. It can oversell. Use change.js. → P4.3
Sending one discount code to "add" one The parameter is whole-state. One code sent removes every other code. An empty string clears all.
Addressing cart lines by variant id The line key identifies a line, not a variant. One variant can occupy two lines.
Summing deprecated price fields price, line_price and discounts include Scripts discounts only. "The line prices don't add up to the total" is always this — the gap is the discount. → P4.4
title versus product.title on an order One is historical, the other current. A receipt on the wrong one rewrites history after a rename.
Costs money — headless with no permanent front-end team The build lands, the agency leaves, and nothing changes for two years because every content edit needs a developer. The merchant ends up worse off than with a theme they could edit. → P4.1
Costs money — losing the app ecosystem Apps that inject storefront UI stop working. Each one becomes a custom build and a permanent maintenance item. Enumerate the client's installed apps before recommending headless, and price the replacements.
Fails with no error — headless "for speed" Speed problems are usually third-party scripts and images, which follow you into any stack. The rebuild ships, the score does not move, and nobody can explain why.
Underestimating the editing story "The merchant can edit content" is a feature you must build, and it competes with a theme editor that Shopify improves for free. Budget it explicitly or it becomes support tickets.
Judgement, not documentation — the recommendation is usually a theme Most Shopify stores sell a catalogue of products, which is exactly what themes are for. Recommending a theme can feel like the unambitious answer. It is usually the correct one, and being willing to say so is a mark of seniority rather than of caution.
Costs money — bespoke sections per page Each one is a permanent maintenance item and none is reusable. The client keeps paying for variations of something they already own, and every theme update multiplies the work. → P4.2
Costs money — hardcoded content in a section Text or images baked into Liquid instead of exposed as settings means every wording change is a deploy. The merchant loses self-service and you gain a queue of trivial tickets.
Fails with no error — assuming a feature is present A reference theme may simply not ship something you expected. Building on the assumption produces code that silently does nothing on that theme. Grep before you assume.
Section settings with no sensible defaults A merchant adds your section and sees an empty band. They conclude it is broken. Give every setting a default that renders something reasonable.
Judgement, not documentation — composability has a limit Exposing every possible setting produces a section a merchant cannot understand and can easily break. There is a real trade-off between flexibility and usability, and the right answer depends on the team who will use it. Ask who edits the store before deciding how many knobs to expose.

Checkout, Plus, Markets

Script tags past their sunset Thank you / Order status script tags: sunset 28 Aug 2025 for Plus, 26 Aug 2026 for non-Plus. The feature simply stops. → P5.2
React checkout components not migrated 2025-07 is the last version supporting them. Blocked from updating after 1 Oct 2026.
checkout.liquid blocking Function APIs A store still carrying old checkout customisations must migrate before it can use Functions. The migration is a prerequisite, not a competing task. → P5.3
Costs money — designing a Function that needs external data live There is no network access inside a Function. Discovering this after committing to a feature means redesigning it as sync-then-read, which is a different project.
Fails with no error — no debugger and no logs of your own It does not run on your infrastructure, so the tools you reach for first are absent. Keep Functions small and pure, and test the logic outside Shopify.
Forgetting the merchant configures it You ship a type, not an instance. A Function with its rules hardcoded is one no merchant can adjust, so every change becomes a deploy.
Judgement — over-asking in the input query The input query runs before your logic on every affected customer interaction. Requesting data you do not use is a cost you pay forever.
Getting the Plus gate wrong in either direction Checkout steps need Plus. Thank you / Order status do not. Functions do not. Market overrides need Advanced. → P5.1
A hardcoded market count Verified on a live store: 205 markets, 8 publications. Code looping per market does 25× the work of code looping per channel.
Writing a base price over a market override Both are real prices. One country sells wrong while every other market looks perfect.
Costs money — building what Flow does free A tagging rule or a notification, coded, deployed and maintained forever, when a merchant-editable workflow would have done it. The client pays twice: once to build, then again every time the rule changes. → P5.4
Costs money — hardcoding a threshold the business owns Any number the business might revise belongs in configuration or in Flow, never in a deploy. This is the most common source of trivial recurring tickets.
Fails with no error — two automations doing the same job Your app tags customers and a merchant builds a Flow workflow that tags them differently. Both run. Nothing errors, and the tag flickers. Before writing any automation, ask what workflows already exist.
Reaching for Flow inside checkout Flow reacts to events. It does not run in the request path, so it cannot decide a price or block a checkout step. That is a Function. Confusing the two produces a design that works in testing and is always a beat too late in production.
Building screens for a sync A server-only app needs no merchant UI. Building an admin interface for something nobody opens is budget spent on nothing, and it is surprisingly common because "an app" implies a screen.
Judgement, not documentation — a workflow is a dependency you cannot see Merchant-built workflows are invisible from your codebase. A behaviour you cannot explain may be a workflow somebody built last year. When debugging odd automatic changes, check Flow before reading your own code.

Migration

Costs money — matching on handle or title A title edit creates a duplicate product. Sales and inventory split across two records, and reconciliation reports drift on both. This is the most common cause of duplicate products in an integrated store. → P6.1
Costs money — a custom ID with no uniqueness guarantee The definition must be set up so values are unique. Without it, two products can carry the same identifier and your lookups return an arbitrary one. Verify the definition, not just the values.
Fails with no error — expecting productUpdate to create With a custom ID it looks up and updates, and does nothing useful when there is no match. A first import written on it silently imports nothing. Use productSet when you need create-or-update.
Fails with no error — an id stored at the wrong level Verified on a live store: a product-level external id that actually identified only one of that product's variants. Every lookup matched that variant and silently mismatched the rest.
Assuming create-or-update everywhere Lookup covers many resource types; create-or-update covers products and customers. A design that assumes upsert-by-custom-id for collections or orders will need rewriting.
Judgement, not documentation — pick the namespace and key once, forever A metafield key cannot be renamed without a migration, and your identifier is the last thing you want to migrate. Choose the namespace and key deliberately at the start, write it down, and never let a second convention appear alongside it.
The omitted line price Omit a price on an imported order and the platform can fill in the variant's current price. Counts match, line items match, and the customer's history is wrong. → P6.6
Emails about 2016 orders Creating orders can fire customer notifications. Confirm and disable before any bulk order import. Test on a Dev store with a real inbox.
Orders dated today Omit the date and a decade of history collapses onto the migration day. Every cohort report becomes meaningless.
Treating COMPLETED as success Per-line userErrors live only in the downloaded results file. objectCount counts processed, not succeeded. → P6.2
The file form field out of order It must be last in the multipart form. Earlier, the upload fails in a way that points nowhere.
Quoting a limit from memory The daily variant throttle changed by 10× between two checks three weeks apart. Date every limit. Current: threshold 500,000 variants, then 10,000/day, Plus exempt. → P6.3
Sizing from productsCount Verified returning exactly 10,000 with precision: AT_LEAST — a floor, not a value. Even EXACT is not a freshness promise.
The login surprise Passwords never move between platforms. On go-live morning every returning customer fails to sign in, and nothing is broken. → P6.5
No redirects Every old indexed URL becomes a 404. Traffic dies silently. The highest-value, least glamorous task in a migration.
No written stop condition for a cutover At 2am the pressure runs one way. Agree the abort criteria while everyone is calm. → P6.4

Shipping, delivery and tax

A custom delivery profile with an incomplete zone list Moving variants into a new profile removes them from the default one. Forget a country and those products have no rate at all there — checkout is impossible, and every other product works, so nobody suspects configuration. → P7.1
Fails with no error — a missing variant weight Weight-based rates treat a blank weight as zero, so a heavy item falls into the cheapest band and you ship at a loss.
Free shipping built as a discount It is a conditional rate of zero. Rates and discounts combine and report differently.
Costs money — calling a carrier live inside the rate handler Their latency sits inside your budget and there is no retry mechanism. Pre-compute; serve a lookup. → P7.2
Costs money — designing for the 10-second timeout It is dynamic per shop-and-app pair: 10 s under 1,500 RPM · 5 s to 3,000 · 3 s above. The busier the store, the less time you get — so it fails on the biggest day. Design for 3 seconds.
Costs money — an empty array when you meant "I'm broken" Empty array = "no rates from me", and the customer may see no shipping option at all. To fall back to the store's own rates you must return 4xx or 5xx. Two meanings, one loses the sale.
Fails with no error — the 30-second error cache Success caches for 15 minutes; an error for 30 seconds. A failing endpoint receives roughly 30× the load of a healthy one — your outage amplifies itself.
Fails with no error — a rate depending on something outside the cache key The key is variant IDs, box weight and dimensions, quantities, carrier service ID, origin, destination, item weights and signatures. Customer tags and time of day are not in it, so Shopify serves a cached rate and never calls you.
Fails with no error — a dynamic service_code A timestamp or session id makes every response a new shipping option. Dynamic data goes in metafields.
A cross-domain redirect on the callback 30x is followed only within the same domain. A load balancer redirecting elsewhere silently triggers backup rates.
Costs money — recalculating tax anywhere A rate you looked up will be wrong for some jurisdiction, product type or exemption you did not know about. Read Shopify's number; never derive one. → P7.3
Fails with no error — exemption as a boolean Exemption is jurisdiction-scoped — a long enumeration, including the EU reverse-charge rule. A customer exempt in one state modelled as globally exempt stops being charged anywhere, until an audit.
Promising tax in the cart Storefront Cart API tax and duty fields are deprecated as of 2025-01 — deliberately, because tax needs the full checkout context.
Scoping a custom tax engine The Tax Platform is invitation-only to selected tax software companies. Not available to you.
Judgement — never answer a tax question, even when you know An answer from you creates reliance, and if it is wrong the liability is theirs. "That's one for your accountant" has no downside.

After the sale

Costs money — a refund with no idempotency key Optional from 2026-01, required from 2026-04. On older versions a retried refund pays the customer twice; on current versions the call is rejected. Either way, code written before 2026-04 needs changing. → P8.1
Costs money — calculating the refund amount yourself Discounts, proportional tax and prior partial refunds all affect it. Call suggestedRefund and refund from its answer.
Costs money — the wrong refund mutation returnRefund takes no restocking input. Use it for a change-of-mind return and the stock never comes back — you have quietly written off sellable inventory. refundCreate is the one with restocking.
Fails with no error — restocking a faulty item The reverse mistake. A damaged item restocked becomes phantom stock: Shopify sells it, nobody can ship it. Overselling caused by a refund.
Fails with no error — committing an order edit nobody looked at The CalculatedOrder draft phase exists so a human can check. Skip it and an automated edit changes what a customer paid — correctly per your code, wrongly per the customer.
Refunds and drafts arriving in the ERP as orders A refund is an amendment; a draft order is a quote. Anything consuming order webhooks that treats either as a sale reports revenue that never existed.
Costs money — resolving a payment session after 3 minutes Shopify re-runs confirmation and may refund or void a payment you already took. Money out, no error anywhere. Use paymentSessionPending rather than holding the session open. → P8.2
Fails with no error — resolving before confirmation arrives Shopify fails Resolve and Reject until it has sent the confirmation result to your confirm-session URL. Code that assumes success marks the order paid internally while Shopify does not.
Costs money — a non-2xx on the confirmation callback It is retried, and if it keeps failing the customer must start their payment again. An abandoned checkout caused by your endpoint, at the last possible moment.
Costs money — scoping a payments app as "an integration" It carries PCI obligations, a 5-day settlement duty, fraud responsibility judged at Shopify's sole discretion, pricing rules, and a 7-day merchant exit right. Those are commercial commitments, not tickets.
Judgement — never store a card number, for any reason Someone will ask you to keep card details "so we can charge them later". The answer is no, and it is not a preference.
Costs money — no price validation on draft orders Arbitrary line prices are a feature. Your code is the only guard, so a bug or a careless staff member can sell a £500 item for £5 and it looks like a legitimate order. → P8.3
Costs money — complete when you meant invoice Completing marks an order paid with no money moving. The merchant ships goods nobody paid for, and their reports show revenue that never arrived.
Judgement — a quote needs an expiry someone enforces Shopify keeps a draft order forever. Nothing expires it and nothing warns anyone, so a two-year-old quote at last year's prices is still completable.

Other ways to sell

Costs money — syncing only the variant price for B2B B2B prices live in price lists, not on the variant. Your sync writes a price nobody in B2B pays, and reconciliation confirms it perfectly. Wholesale margin drifts invisibly. → P9.1
Costs money — treating "order created" as "order confirmed" B2B orders can require merchant review. Push those to a warehouse and you ship goods on an unapproved order.
Fails with no error — a product invisible to one company location Catalogs control visibility as well as price. A B2B customer reporting a missing product is usually a catalog question, and nothing errors.
Costs money — payment terms ignored downstream A B2B order may be payable in 30 days. An ERP treating every order as paid-on-placement reports revenue and chases nothing.
Costs money — uninstall deletes every selling plan in 48 hours All plans, policies and associations gone. Products survive. If your app holds no backup, a merchant's change of mind is unrecoverable. → P9.2
Costs money — committing inventory at creation for a consumable A twelve-month subscription reserves twelve cycles of stock now. The storefront shows sold out while the warehouse is full. Commit at fulfilment instead — but then nothing stops over-subscription, so the merchant needs a subscriber report.
Fails with no error — three stacking price overrides Market override, B2B price list and a subscription pricing policy can all apply. "What does this cost?" has no single answer, and reconciling against the variant price proves nothing.
Judgement — a contract outlives your code A twelve-month subscription taken today is still billing after your next two refactors and several API version bumps.
Fails with no error — a domain allow-list for extension CORS Customer account UI extensions run in a Web Worker with a null origin, so an allow-list matches nothing. You need Access-Control-Allow-Origin: *, and the failure looks like an empty panel. → P9.3
Costs money — quoting extensions before checking the account version Legacy customer accounts support no UI extensions at all. Query CustomerAccountsV2 first, or the real project turns out to be an account migration.
Costs money — the login surprise on migration day Passwords never transfer. Every returning customer fails to sign in on go-live morning and nothing is broken. One-time email codes plus a communication plan, agreed in advance.

Conversion, content and risk

Fails with no error — the filter that was never created Storefront filters must be created in the admin first. The data exists, the filter does not, and nothing errors. Debugging theme code for this wastes a day. → P10.1
Fails with no error — undefined metafields cannot be filtered Same root cause as P2.1. An integration that skipped definitions has produced data that can never become a filter.
Explaining AND/OR backwards to a client AND between filter groups, OR within one. So selecting two colours widens the results. Clients expect narrowing and report it as a bug.
Judgement — the docs describe the price sort directions as inverted Shopify's own page describes price-ascending as "high to low". Test both directions rather than trusting the description; this one is visible to every customer.
Costs money — a headless rebuild for speed The scripts and images follow you, and you add a hosting layer to tune. The score does not move and nobody can explain why. Measure first — the cause is usually apps. → P10.2
Fails with no error — scripts from apps nobody uses Uninstalled and unused apps can leave script tags loading on every page view. Nothing errors; the site is just heavier.
Starting with theme JavaScript, or blaming Liquid Scripts and images first, always. Liquid renders on Shopify's infrastructure before the browser sees anything, so it is almost never the finding.
Costs money — estimating content without multiplying by locales Four languages makes every content number four times bigger, including the human checking it. The single most common content underestimate. → P10.3
Costs money — no redirects after a migration Old URLs become 404s. Search traffic dies silently and the cause is invisible in your logs. Menus break the same way when handles change.
Fails with no error — an integration writing untranslated content Your sync writes an English title and markets that previously showed a translation now show English. Only a customer in that market sees it.
Storing a file URL in a text metafield Use file_reference. A URL string does not survive the file being replaced, and nothing tells you it has rotted.
Costs money — auto-cancelling on a risk signal A false positive cancels a genuine order and refunds a real customer. They experience being accused of fraud, and you lose them permanently. Queue it for a human. → P10.4
Costs money — computing your own risk score Same rule as tax: read Shopify's assessment, never derive one. A homemade score is a liability wearing a number.
Fails with no error — tracking that stopped at a sunset date Script tags on Thank you and Order status are sunset — 26 Aug 2026 for non-Plus. They may still download and do nothing, so the client believes they have attribution data they do not have.
Judgement — never explain a risk score to a customer Explaining the signals teaches someone how to evade them, and it is not your assessment to defend.

Headless

Costs money — not pricing the app replacements Theme app extensions mostly stop working, so every storefront-rendering app becomes a custom build plus permanent maintenance. Enumerate the installed apps before quoting. → P4.5
Costs money — no permanent front-end owner The build lands, the agency leaves, and nothing changes for two years because every edit needs a developer. The merchant ends up worse off than with a theme.
Assuming checkout rules relax, or that the Storefront API sees everything Checkout is still Shopify's — Plus gates and sunset dates all still apply. And the Storefront API is channel-scoped, so a missing product is usually a publication or catalog question, not a query bug.
Fails with no error — expecting tax in the Storefront cart Those fields were deprecated as of 2025-01. The constraint is not a theme limitation, so headless does not escape it.
