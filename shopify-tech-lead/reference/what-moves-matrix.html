What-moves matrix

Per record type: moves cleanly, moves with loss, or never moves.

Use this in the first meeting Walk the client down the third column. Everything in "never moves" is a communications or scope decision, not a task — and raising them on day one is the difference between a plan and a crisis.

Moves cleanly

RecordNotes
Products, variants, pricesMechanical. Count variants, not products
CollectionsManual ones move; automated ones need their rules rebuilt
Customers (identity only)Name, email, addresses — never credentials
Inventory levelsPer location. Check sellable vs shelf first
Metafield valuesOnly after the definitions exist. Definitions are per store

Moves with loss — each needs a decision

RecordWhat is lostDecision needed
OrdersThe gateway's transaction record, that day's tax calculation, the old platform's discount engineWhat are they for? Customer visibility → fine. Accounting → keep an archive instead
DiscountsRule semantics differ between platformsRebuild, or accept different behaviour
Content pages, blogsFormatting, embedded widgetsWho re-checks each page
Gift cardsRules vary. Not supported on dev stores at allHow balances are honoured
Saved payment methodsGateway-dependent, often impossibleWhether customers re-enter cards
Reviews, loyalty, subscriptionsEach lives in an app, each has its own export — or noneEnumerate installed apps in week one

Never moves

ThingConsequence
PasswordsHashed with the old platform's secret. Every customer sets a new one or signs in with an emailed code. This is a communications project
Shopify record IDs (even Shopify → Shopify)Every product, variant, customer and order gets a new id. All references must be re-mapped
Platform-specific featuresNot a data task — a scope decision. Escalate immediately
SEO authority on old URLsNeeds redirects. Without them, traffic dies silently
Order numbers matching old receiptsStore the original in a metafield and make support able to search it, or accept the mismatch knowingly
App configurationEvery app reinstalled and reconfigured by hand

Order imports — always send these explicitly

Every default is a lie about the past Line item price — omitted, the platform can use the variant's current price. The date — omitted, the order imports as today. Fulfilment state — defaults to unfulfilled, so a decade of shipped orders looks like a backlog. Tax and discounts — recalculated by today's rules.

And check what emails fire before any bulk order import. Test on a Dev store with a real inbox.

The four numbers to measure before designing

variant count both sides ── clients say products. counts can be capped match rate both ways ── report by row AND weighted by units sold blank rate per field ── a field that exists is not a field that is filled change rate per day ── decides whether incremental is worth building

Verified 2026-08-23 where marked: gift cards and store credit unsupported on dev stores; productsCount can return AT_LEAST; metafield definitions are per store. Not re-verified today: the forced import order between products/customers/orders, whether orders can be CSV-imported, orderCreate scope and token requirements, per-minute order caps on dev and trial stores, and the exact backdating field. Check those before planning against them.
