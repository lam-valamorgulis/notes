Scars — Apps & Integrations

Every "Where it hurts" from Track 2. The page to read before designing a sync.

How to read this Red = costs money. Purple = fails with no error. Dashed = engineering judgement, not documented. Verified against shopify.dev on 2026-08-23 unless noted.

The app itself

Picking custom distribution, then needing to sell it A custom app cannot use the Billing API. Reselling means changing distribution: App Store review, compliance webhooks, protected-data approval, a listing. Ask "will anyone else ever install this?" first. → A1.1 → A1.5
Inheriting an admin-created legacy app Cannot use App Bridge, app extensions, or the Billing API, and cannot be created any more. "Add a theme app extension" means replacing the app first.
Online token on a background job Tied to a person's session and permissions. Works for months, then stops when they leave or their permissions change. Nothing logged. Background work uses offline tokens. → A1.2
Public app on non-expiring offline tokens Must migrate to expiring tokens by January 2027. Custom and merchant-created apps are exempt.
The refresh token dies before the access token Obtaining a new expiring offline token invalidates the old refresh token immediately while the old access token keeps working. A second worker looks fine, then fails permanently on its first refresh.
Offline and online look identical Both start shpat_. Delegate tokens start shppa_. Store the type next to the token or you cannot audit your own system.

Webhooks

HMAC on a parsed body Middleware parses JSON before your handler; you sign the re-serialised object. It never matches and the code looks correct. Capture raw bytes on that route. → A1.3
A 3XX response Any non-2XX is a failure, redirects included. Your access log shows healthy 301s while Shopify's counter climbs to eight.
Secret rotation has an up-to-one-hour tail It can take up to an hour for the HMAC digest to use a new client secret. Verify against the new one immediately and you reject real deliveries. Accept both during the overlap.
The subscription deletes itself 8 consecutive failures and it is gone — if configured via the Admin API. App-specific subscriptions are not. Watch the failure rate; Shopify calls anything over 0.5% higher than average.
Deduping on Event-Id Two subscriptions on one topic produce two deliveries, two Webhook-Ids, one Event-Id. Dedupe on Webhook-Id; correlate on Event-Id.
Webhooks can arrive a day late Shopify's own guidance is to compare the timestamp to now if a day's delay would matter. Always pair with a scheduled re-read.

Privacy and scopes

One name field moves you to privacy level 2 Level 1 excludes name, address, phone and email. Include any one and you need field-specific approval plus data protection reviews. Teams walk into this via a support dashboard. → A1.4
The 30-day compliance clock nobody owns You return 200 and a human has 30 days to actually delete. An acknowledged-but-uncompleted request looks identical to a completed one. Track them with a due date.
customers/redact timing If the customer ordered within six months, the request is withheld for six months. Only with no recent order does it arrive after 10 days. Never promise a client fast deletion.
Scope creep is permanent Adding a scope is easy; removing one means merchants re-approve. Ask for what today's feature needs.

Backend and the queue

Treating HTTP 200 as success on GraphQL The most expensive habit on this API. Throttles, validation failures and partial successes all return 200. Check three levels: HTTP status, errors[], userErrors[]. → A2.3
Retrying terminal errors 8 attempts at something that can never succeed, spending budget the good records needed. Classify first: transient · throttled · terminal · poison.
No jitter Synchronised retries recreate the outage you just recovered from. Nothing identifies you as the cause.
Concurrency against one bucket The limit is per app and store. Ten workers on one store share one budget. More workers redistribute throttling; they do not add throughput.
Business rules inside the API client Every rule next to an API call is a rule you must re-verify at each quarterly version bump. → A2.1
Pairwise id mapping erp_id and shopify_id as columns works with two systems and collapses at three. Use a hub — your id in the middle. → A2.2
Writing shadow before the send A crash then makes you believe in a send that never happened. The record is skipped forever as "unchanged" and the wrong value is permanent. Send, confirm, then record.
A token or a payload in the logs A token in a log store is as unrecoverable as a secret in git history. Order payloads contain names, emails and addresses. Note: Product.events messages contain staff full names and emails in plain text — verified on a live store. → A2.4
Green dashboards on an idle sync Zero queue depth, no dead-letters, no errors — all true of a sync doing nothing. Only reconciliation drift measures correctness.

The sync discipline

Costs money — "two-way sync" agreed as a phrase A client asks for two-way sync and everyone nods. Nobody asked which side wins. The first conflict resolves in whichever direction the code happened to run last, and it resolves against the client's money — a price, or a stock count that oversells. Turn the phrase into a per-field table before anyone estimates it. → A3.1
Fails with no error — the field owned by nobody Both systems can edit it, and nobody decided which wins. Each sync run overwrites the other's value. It looks like flickering, and it is nearly impossible to reproduce on demand because the outcome depends on timing. Every field needs an owner, even if the owner is "Shopify, because we said so".
Counting systems instead of fields "One integration" sounds like one unit of work. Forty fields with three different flow directions is the real shape. Estimates built on the first number are wrong by a large multiple, and the discovery happens in week three.
Judgement, not documentation — a third system arrives later Marketplaces, a POS, a warehouse, a review app. Each one adds a copy and re-asks all four questions. Design the mapping and the ownership rules so that adding a system is a configuration change, not a re-think. A3.7 covers what actually breaks at scale.
Overwriting sellable stock with warehouse stock Both numbers right, mapping wrong, result is overselling. The most expensive ownership mistake available. → A3.2
Per-record ownership "The ERP owns products" quietly claims the quantity field. One nightly run resets every stock level.
The shared tag list Writing the list wholesale deletes the marketing team's tags. They add them back; you delete them tonight. Own a prefix, never the list.
Deltas instead of absolute values A retry applies it twice. Absolute writes are what make replay, backlogs and repair possible at all. → A3.3
Partial payload to a whole-state mutation "Absolute" must also mean complete. Three of five variants sent means two deleted.
A hard-deleted source row An absence carries no information — deleted, unchanged, next page and source error look identical. Products stay live and sellable for months.
Using the webhook payload as data A four-hour-old retry overwrites the current price with an old one. A webhook is a trigger, not a source. → A3.4
The watermark from your own clock, or the scan's start Both silently drop every row changed during the scan. Highest updatedAt you actually saw, from the source's clock.
An empty queue after a long outage It looks like a clean recovery and means the subscription was deleted and every event is gone. → A3.5
Draining a backlog at full speed, in arrival order Spends the whole budget on obsolete history while live changes queue behind it. Collapse to ids, re-read current, drain by damage.
Count-only reconciliation Every price off by a cent, or every stock level a week old, passes perfectly. → A3.6
Zero differences out of zero records An empty comparison set reports a clean pass. Always publish the denominator.
A global rate limiter across many stores The bucket is per app and store. A global limiter is a bottleneck 400× too small, with healthy per-call metrics and a queue that grows forever. → A3.7
One try/catch around the whole fleet Store 17's revoked token stops stores 18 to 400. The classic multi-tenant outage.
Averaged fleet health 399 healthy and 1 broken averages to healthy. Report the worst and the count outside tolerance.

Connectors

Treating a checkout-time integration like an async one Adding retries inside checkout multiplies the delay. The loss is invisible — abandoned carts raise no tickets. → A4.1
No fail-open / fail-closed decision Undecided means the code decides by throwing. Fail open on information, fail closed on a promise.
Applying a truncated file Absence means deleted, the upload failed halfway, and half the catalogue is archived overnight. Row-count sanity gate, and a hold-for-human state. → A4.3
A reordered CSV column Price and stock swap places. Every row parses. Every number is wrong. Exact header matching is the only defence.
SFTP has no delivery notification If the vendor's upload silently stops, you receive nothing — which looks exactly like "no changes today". Alert on the absence of a file.
A reused SKU A retired code reused eighteen months later updates the old product, on its existing URL and history. Tombstone retired keys. → A4.4
Cached Shopify variant ids A product option change can destroy and recreate variants. Treat the Shopify id as a cache you can re-resolve.
Coverage measured by row count "97% of 50,000" hides 1,500 invisible products, possibly including bestsellers. Report coverage weighted by units sold too.
Costs money — designing before asking Present a beautiful design built on a wrong volume assumption and you have to withdraw it. Four questions first costs a minute and never has to be taken back. → A4.2
Starting with the schema Tables are concrete, so they are where nervous people start. But the schema is a consequence of the ownership decisions, so leading with it means presenting an answer before its question. Lead with ownership.
Fails with no error — never mentioning failure A design that only describes the happy path sounds complete and reads as inexperienced. The listener does not know what is missing — they just do not feel confident. Volunteering stage 3 is the single biggest upgrade to how this answer lands.
Not saying how you would know it works Almost nobody reaches measurement. Ending there makes the whole answer feel operational rather than theoretical.
Judgement, not documentation — say the numbers you actually verified If you quote a limit, be able to say when you checked it. "One connection field per bulk mutation, 100 MB, 24 hours — I checked that this month" is far stronger than a confident number with no date. And where two doc pages disagreed, say that too; it is a better answer than picking one.
Costs money — reserving stock you cannot confirm Accepting a pickup order while the vendor is unreachable means promising an item that may not be there. The customer drives to the shop. That is worse than losing the sale, because it costs the client the customer. → A4.6
Costs money — shelf stock treated as sellable Damaged units, held items and display stock are on the shelf and not for sale. Publish the shelf number as availability and you send people to collect things that are not available.
Fails with no error — a cache with no label Five-minute-old availability shown as if live. Nothing errors and the number is usually right. When it is wrong, a customer has made a journey. Label the freshness on the page.
Fails with no error — a shop with no Shopify location Shopify cannot express per-shop inventory for a shop that is not a location. Availability for it is silently absent, which looks like "out of stock everywhere". Audit locations against real shops during discovery.
Synchronous third-party calls in a collection grid As above. Latency multiplied by the number of cards, on a page the customer is watching. Batch it, defer it, or move it to the product page.
Judgement, not documentation — the vendor's plan gates matter too A vendor's own product tiers can require a particular Shopify plan for some features while others work on any plan. So "does this need Plus?" can have a different answer per feature. Confirm it with the vendor per feature, in writing, before you scope.

Patterns from a closed vendor platform

Company, client and tenant removed on purpose. The pattern is the lesson. → A4.5

Two ledgers for the same money A vendor holding a customer credit balance, plus store credit issued in Shopify. Both real, neither aware of the other, and a customer can spend it twice. Find this before go-live.
Recomputing a derived value A price computed from hidden rules is not reproducible from what is exposed. Read their number or show nothing. A formula fitted to one example is a guess with a decimal point.
Assuming the system of record owns everything They may own the catalogue while Shopify owns inventory, flowing back to them. Establish ownership per field even when one system is obviously the master.
Identity that encodes a location A key fusing item and location works for one location and breaks all at once when the second arrives, usually mid-rollout.
No published limits means no promised throughput You cannot discover a closed platform's rate limits responsibly on someone's production system. Say what you measured and that it is not a commitment.

Distribution, billing and the dev workflow

Costs money — assuming compliance webhooks are optional Required for every App Store app regardless of whether it collects personal data. "We don't store customers" is not an exemption. → A1.5
Fails with no error — a stale emergency developer contact It is where webhook failure warnings are sent. Stale, and the warnings that precede your subscription being deleted go nowhere. Then the app silently receives nothing.
Requiring merchants to paste code into a theme App Store expectations are explicit: use theme app extensions. An install process involving copied snippets is both a review problem and a support burden forever.
Not detecting development stores Without the partnerDevelopment check plus SHOP_UPDATE, a store that converts to a paid plan keeps free access indefinitely.
Judgement — ask the resale question on day one "Will anyone else ever install this?" costs nothing to ask at the start and is expensive to answer late, because a custom app cannot bill through Shopify at all.
Costs money — developing on a Plus dev store Ten times the rate limit hides every throttling problem. You ship to a Basic store and it falls over on day one. → A2.5
Fails with no error — an absolute webhook URI and a restarted tunnel The tunnel URL changes; the subscription still points at the old one. Shopify fails deliveries you never see. Use a relative uri.
Fails with no error — analytics_queryable in a metafield definition shopify.app.toml accepts capabilities.analytics_queryable, your app deploys clean, and the capability is not set. Verify capabilities after every deploy.
Fails with no error — over 25 metafield definition changes in one deploy Declarative definitions are capped at 25 changes per deploy — create, update or delete. Split the release, or discover mid-launch that half your schema is missing.
Runtime code creating declarative definitions TOML-declared definitions are read-only through the Admin API. Code that created them at runtime starts failing the day they move into config.
Judgement — the CLI will not catch a deprecated field It scaffolds and deploys; it does not lint your GraphQL against the version you pinned. Validating queries against the schema in CI is what caught three already-deprecated fields in this Course.
