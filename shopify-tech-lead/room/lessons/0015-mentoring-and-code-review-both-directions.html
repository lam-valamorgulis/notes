Track 3 · R4 · Lesson 1

Mentoring and code review, both directions

Reviewing a junior's work, and taking a hard review of your own.

Your win today. A review comment format that gets the fix without costing the author anything — and a way to receive criticism that makes people want to review your work.

How it works

Derive it: what is a review comment for?

Not to demonstrate that you spotted something. Its only purpose is a change in the code, or a change in what the author knows. So any comment that produces neither is noise, however correct it is.

That single test cuts most bad review habits immediately. "This could be cleaner" produces neither. "Nit: naming" produces neither. A question with no suggestion often produces neither.

The comment format

1. SEVERITY say it, so the author knows what to do 2. WHAT the specific thing 3. WHY the consequence, not the principle 4. WHAT INSTEAD a concrete suggestion ── all four, in two sentences.
SeverityMeans
BlockingMoney, data loss, or security. Cannot merge
Should fixA real bug or a maintenance problem. Fix before merge
ConsiderA better option. Author's choice
Note / learningNo change wanted. Just information

Stating severity is the single highest-value habit in review. Without it, a junior treats every comment as blocking and a senior treats every comment as optional — and both are wrong.

WeakStrong
"This should be idempotent."Blocking: if this webhook arrives twice we'd create two orders. Add the message id as a primary key on the inbox table and let the insert fail on the duplicate.
"Why did you do it this way?"Consider: is there a reason for the delta rather than the absolute value? A retry would double it. Happy to be wrong if there's a constraint I'm missing.
"Nit: naming."Note: we tend to call this a watermark elsewhere in the repo — worth matching so it's greppable. Not blocking.

Mentoring: give the shape, not the answer

The instinct is to supply the fix, because it is faster. But the goal is that they can do the next one without you — so give them the question you would ask yourself.

Instead ofAsk
"Use the absolute value here.""What happens if this runs twice?"
"You need to check the precision field.""How do you know that count is exact?"
"Add a reconciliation job.""How would we find out if this were quietly wrong?"

Three questions that transfer. And a practical rule: if you have asked the same question twice, write it down somewhere shared. A repeated review comment is a missing rule, a missing lint check, or a missing paragraph in a document — the third time is a failure of the system, not of the person.

Receiving review: the two responses that matter

Drill these Good catch — you're right, I'll fix it.
I did it that way because [reason]. Does that change your view, or is there something I'm still missing? The first is short and complete; do not add justification to a valid catch. The second disagrees while genuinely leaving room to be wrong.

What to avoid: explaining why you did it wrong. It reads as defensiveness and lengthens the thread for no benefit. "You're right, I'll fix it" is a stronger response than a correct explanation.

Answer before reading on A junior's pull request sends stock deltas instead of absolute values. Write the comment.

Something close to: "Blocking: if this job retries — and it will — the delta gets applied twice and the stock number drifts permanently. Send the absolute value instead: 'stock is 12', not 'add 3'. Then a retry is harmless and we can re-run the whole thing any time."

Check it against the four parts: severity stated, the specific thing, the consequence rather than the principle, and a concrete alternative. It also teaches the general rule in its last sentence, so the author can apply it next time without you.

What you did not write: "this isn't idempotent". Correct, unhelpful, and it requires the author to already know what you know.

Where it hurts

Costs money — no severity on a blocking comment A real bug worded as a suggestion gets merged. The author was not being careless; they were reading your tone correctly. Say "blocking".
Comments that produce no change and no learning Every one spends the author's attention and your credibility. Apply the test before posting: what does this comment change?
Citing a principle instead of a consequence "This isn't idempotent" requires them to already know why that matters. "A retry would double the stock" does not.
Fails with no error — the same comment three times You are patching a systemic gap by hand, forever. The third occurrence means it belongs in a rule, a lint check or a document.
Explaining why you did it wrong When receiving review, justification reads as defensiveness. Fix it and move on, or disagree with a reason — not both.
Judgement, not documentation — review the code, and read the person Twenty comments on a junior's first pull request is technically thorough and practically demoralising. Pick the three that matter, say the rest in a five-minute conversation, and note the pattern for next time.

What you say to a client/PM

When asked how you would mentor a junior Mostly by giving them the question rather than the answer. If they've written something that breaks on a retry, I don't say "use absolute values" — I ask "what happens if this runs twice?" They get there themselves, and next time they ask themselves. And if I find myself asking the same question three times, I write it down as a rule, because at that point it's our process failing, not them. Concrete, has an example, and the last sentence shows you think about systems rather than about people's shortcomings. That is what a lead sounds like.
When asked how you handle criticism of your own work If they're right, "good catch, I'll fix it" and no explanation — the explanation is just me protecting myself. If I disagree I say why and ask whether it changes their view, because it often turns out they know a constraint I don't. The reviews I've learned most from were the uncomfortable ones. Specific behaviours rather than a claim about being open-minded. Anyone can claim the attitude; describing the actual sentences is evidence.

Remember this

  • A comment must produce a code change or a learning. Anything else is noise.
  • Four parts: severity · what · why (as a consequence) · what instead.
  • Always state severity. Blocking · should fix · consider · note.
  • Give the question, not the answer — "what happens if this runs twice?"
  • The same comment three times is a missing rule, not a careless person.
  • "Good catch, I'll fix it" — no justification when they are right.
  • Pick three comments on a first pull request, not twenty.

If you remember one thing: state the consequence, not the principle — "a retry would double the stock" teaches, "this isn't idempotent" does not.

Ask questions. Then "next" for debugging while someone watches.
