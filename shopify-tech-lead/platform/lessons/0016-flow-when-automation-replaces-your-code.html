Flow: when automation replaces your code

Knowing when not to write an app is a tech-lead skill. This is the main place to use it.

Your win today. A test for whether a client's request needs code at all — and the move that makes your app more valuable by doing less.

How it works

Flow is trigger → condition → action

Shopify Flow is an automation platform for building workflows: something happens, a condition is checked, an action runs. Tag a customer after a big order. Notify someone when stock is low. Hide a product when it sells out.

TRIGGER CONDITION ACTION "order created" → "total > $500" → "tag customer VIP" "stock changed" → "quantity < 5" → "send a notification" a merchant builds this. no developer, no deploy, no maintenance.

The first-principles observation: a large share of what clients ask developers for is exactly this shape. If it is, then writing code for it is worse than not writing it — because code has a maintenance cost forever and a merchant-built workflow does not.

The test, before you estimate anything

AskIf yes
Is it "when X happens, do Y"?Probably Flow
Does the decision need only data already in Shopify?Probably Flow
Will the merchant want to tweak the thresholds themselves?Definitely Flow
Does it need to run during checkout, in the request path?Not Flow — that is a Function
Does it need external data, or complex state over time?Not Flow — that is your app

That third row is the one that should change your instinct. A threshold hardcoded in your app is a deploy every time the business changes its mind. The same threshold in a Flow workflow is a merchant editing a number. You have given away work and made the client more capable, which is what a lead is for.

Then the better move: make your app a Flow citizen

Rather than competing with Flow, plug into it. Three integration points:

You buildWhich means
TriggersYour app emits an event that starts a merchant's workflow
ActionsFlow calls your app to do something when conditions are met
TemplatesPre-built workflows a merchant installs from Flow's template library

The leverage here is real. Any trigger you build immediately composes with every action Flow already has — email, Slack, SMS, tagging, inventory — so you get a large amount of functionality without building any of it. Shopify's own framing is that this saves you building and maintaining direct integrations with many other apps.

Two extras worth knowing: a public app gets a "Works with Flow" badge on its App Store listing, and merchants can discover your templates and tasks inside Flow even without your app installed — which is distribution you do not have to buy.

The third option nobody mentions: an app with no interface

Between "a Flow workflow" and "a full app" there is a shape that fits integration work exactly. A server-only app runs entirely in the background with no merchant-facing UI — useful for syncing data between Shopify and external systems, running scheduled tasks, or responding to webhooks. Shopify notes these are typically distributed as custom apps on a single store rather than through the App Store.

That is precisely the Project in this Course, and precisely most ERP integration work. If a client asks for "an app" and means "keep these two systems in step", they do not need screens — and not building screens is a large saving nobody will ask you for.

Answer before reading on A client asks for an app that tags customers as VIP when they spend over $500, and emails the account manager. They mention the threshold "might change to $750 later". What do you build?

Nothing. This is trigger, condition, action, on data already in Shopify, with a threshold the client has told you will change. A Flow workflow does all of it, the merchant edits $500 to $750 themselves, and there is no code to maintain. Quoting for an app here would be quoting for something worse than the free alternative. The right answer is to build the workflow with them in twenty minutes and spend the budget on something Flow genuinely cannot do — and saying that out loud is what makes a client trust the next estimate you give.

Where it hurts

Costs money — building what Flow does free A tagging rule or a notification, coded, deployed and maintained forever, when a merchant-editable workflow would have done it. The client pays twice: once to build, then again every time the rule changes.
Costs money — hardcoding a threshold the business owns Any number the business might revise belongs in configuration or in Flow, never in a deploy. This is the most common source of trivial recurring tickets.
Fails with no error — two automations doing the same job Your app tags customers and a merchant builds a Flow workflow that tags them differently. Both run. Nothing errors, and the tag flickers. Before writing any automation, ask what workflows already exist.
Reaching for Flow inside checkout Flow reacts to events. It does not run in the request path, so it cannot decide a price or block a checkout step. That is a Function. Confusing the two produces a design that works in testing and is always a beat too late in production.
Building screens for a sync A server-only app needs no merchant UI. Building an admin interface for something nobody opens is budget spent on nothing, and it is surprisingly common because "an app" implies a screen.
Judgement, not documentation — a workflow is a dependency you cannot see Merchant-built workflows are invisible from your codebase. A behaviour you cannot explain may be a workflow somebody built last year. When debugging odd automatic changes, check Flow before reading your own code.

Say it out loud

Explain this to a beginner

A client asks for a feature. What question tells you the best thing to build is nothing?

Say it out loud. Then read on.

Now compare with a plain-words answer

The question is: can you say the request as "when X happens, do Y"?

If you can, and both X and Y are things Shopify already knows about, then the shop owner can build it themselves with a drag-and-drop tool. No code. No deploy. No bug. No maintenance. Nobody to call in two years when it needs a small change — they just change it.

Your code, by comparison, has to be written, reviewed, deployed, kept working through platform changes, and edited by a developer every time the business changes its mind. If the thing being decided is a number the business might want to adjust — a spend threshold, a tag rule — putting it in your code is the worst possible place for it.

There are two limits. It cannot make a decision while a customer waits at checkout; that needs the other tool. And it can only see things Shopify knows, so anything involving your own system needs you.

The clever move is not choosing between them. It is making your app usable inside that drag-and-drop tool, so the shop owner can wire your thing into their own workflows without asking you. Then one piece of work you did composes with everything the tool can already do.

And a debugging habit: those workflows are invisible from your code. When a store does something inexplicable, check whether a human wired it up before you go hunting in your own logs.

If you used any of these words, try again event-driven · trigger · low-code · orchestration · composability · declarative automation. "The shop owner can build it themselves and change it without you" is the explanation.

Build it

Task · 30 minutes Dev store

Delete some of your own future work.

  1. Take your current backlog. Rewrite each item as "when X happens, do Y" if you can.
  2. For every item where X and Y are both Shopify-only, build it in Flow instead. Time yourself.
  3. Find any threshold hardcoded in your code that the business might change. Move it out.

Proof it worked: at least one backlog item is now done with no code, and one hardcoded number no longer needs a deploy to change. If nothing on your backlog fits the pattern, check again — "email someone when an order is tagged" fits and gets written in code constantly.

Make your app a citizen · 60 minutes Dev store

Add one trigger from your app, so the merchant can start their own workflows from something only your system knows.

Proof it worked: your one trigger now composes with every action Flow already has — email, tag, webhook, everything. You wrote one thing and got a hundred combinations you did not have to build.

Remember this

  • Flow is trigger → condition → action, built by the merchant, with no deploy and no maintenance.
  • "When X happens, do Y" on Shopify-only data is Flow, not code.
  • A threshold the business might change belongs in Flow or config, never in a deploy.
  • Flow cannot run in the request path. Checkout-time decisions are Functions.
  • Build triggers, actions and templates — your trigger composes with every action Flow already has.
  • A server-only app has no UI and is the right shape for most sync work. Do not build screens nobody opens.
  • Merchant workflows are invisible from your code. Check Flow before debugging your own.

If you remember one thing: ask whether the request is "when X, do Y" — if it is, the best code you can write is none.
