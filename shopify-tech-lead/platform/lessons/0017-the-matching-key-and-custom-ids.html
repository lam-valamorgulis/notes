Track 1 · P6 · Lesson 1

The matching key, and custom IDs

Shopify's own documented answer to "how do I find this record again?" — and most integrations never use it.

Your win today. You can look up and upsert any product by your own identifier, with no mapping table lookup and no round trip.

How it works

Derive it: whose id do you have?

You are importing 40,000 products from an ERP. You have their ids. Shopify wants its ids, which do not exist yet for the first import and which you must remember afterwards. So the naive loop is: look up my mapping table, find the Shopify id, then write. One extra step per record, and a mapping table you must never lose.

Ask whether that step is necessary. It is only necessary because Shopify does not know your identifier. So tell it your identifier and the problem disappears.

WITHOUT WITH A CUSTOM ID their id their id │ │ ▼ your mapping table lookup ▼ productSet(identifier: { customId: ... }) Shopify id │ │ ▼ ▼ write created or updated. one call.

What a custom ID actually is

A metafield with a definition, whose value is unique, used as an identifier. Once a resource carries it, Shopify gives you dedicated lookup queries:

query findProduct {
  productByIdentifier(identifier: {
    customId: { namespace: "custom", key: "id", value: "1234" }
  }) {
    title
    handle
  }
}

There are matching queries for other resource types — customerByIdentifier, orderByIdentifier, and similar ByIdentifier queries for collections and product variants.

Upsert in one call

mutation UpsertProductByCustomId(
  $input: ProductSetInput!
  $identifier: ProductSetIdentifiers
) {
  productSet(input: $input, identifier: $identifier) {
    product { id title }
    userErrors { field message }
  }
}

# variables
{
  "input":      { "title": "Summer sandals" },
  "identifier": { "customId": { "namespace": "custom", "key": "id", "value": "12345" } }
}

ProductSetIdentifiers accepts exactly three things — customId, handle, or id. So identity is a first-class argument, not something you resolve beforehand.

The distinction that matters: which mutations create

MutationWith a custom ID
productSetLooks up a match. Updates it if found, creates it if not
productUpdateLooks up a match and updates it. Does not create if no match
customerSetCreate-or-update, as with productSet

So lookup by custom ID is broad — products, customers, orders, collections, variants — while create-or-update is narrow: products and customers. For anything else you can find a record by your own id but must still create it the ordinary way.

This does not replace your mapping table

Be clear about what you have and have not solved. A custom ID removes the lookup round trip and gives you a mapping that survives losing your database. It does not remove the need for your own registry from A4.4, because you still need the hub for three or more systems, and you still need tombstones for retired keys.

Use both: the custom ID is the identity written into Shopify; the registry is the identity you own.

Answer before reading on You use handle as your identifier instead of a custom ID, because it is already there and needs no setup. What breaks, and when?

The first time a merchant edits a product title. A handle is derived from the title, so it changes — and your next run cannot find the product, creates a duplicate, and now two live products compete for the same sales. Nothing errors, because creating a product is a perfectly valid outcome. The whole point of a custom ID is that it is a value nobody has a reason to edit, whereas a handle is a side-effect of content someone edits for a living. handle is offered as an identifier because it is occasionally the right tool for a one-off import — never for an ongoing sync.

Where it hurts

Costs money — matching on handle or title A title edit creates a duplicate product. Sales and inventory split across two records, and reconciliation reports drift on both. This is the most common cause of duplicate products in an integrated store.
Costs money — a custom ID with no uniqueness guarantee The definition must be set up so values are unique. Without it, two products can carry the same identifier and your lookups return an arbitrary one. Verify the definition, not just the values.
Fails with no error — expecting productUpdate to create With a custom ID it looks up and updates, and does nothing useful when there is no match. A first import written on it silently imports nothing. Use productSet when you need create-or-update.
Fails with no error — an id stored at the wrong level Verified on a live store: a product-level external id that actually identified only one of that product's variants. Every lookup matched that variant and silently mismatched the rest.
Assuming create-or-update everywhere Lookup covers many resource types; create-or-update covers products and customers. A design that assumes upsert-by-custom-id for collections or orders will need rewriting.
Judgement, not documentation — pick the namespace and key once, forever A metafield key cannot be renamed without a migration, and your identifier is the last thing you want to migrate. Choose the namespace and key deliberately at the start, write it down, and never let a second convention appear alongside it.

Say it out loud

Explain this to a beginner

Your warehouse system and Shopify both hold the same 10,000 products. Every night you have to update them. Explain how you know which Shopify product is which, and why matching by name is a bug waiting to happen.

Say it out loud. Then read on.

Now compare with a plain-words answer

Both systems gave the same shirt a different reference number, because neither knew about the other. So every night you have to answer "which one of these is that one of those?" ten thousand times.

The tempting shortcut is to match on something you can see in both — the name, or the web address. It works on day one. Then a marketing person improves a product title, and now that title matches nothing. Your nightly job decides it is a new product and creates a duplicate. Sales and stock split across two records, and every report is quietly wrong from then on.

So you never match on anything a human is allowed to edit.

The good move is to write your own reference number into Shopify, in a proper labelled field that Shopify is told about and told to keep unique. From then on you can look a product up by your number instead of Shopify's. The question "which record is this?" stops needing a lookup at all, because you are asking in your own language.

One sharp edge: there are two similar-looking operations, and only one of them will create a product it cannot find. The other quietly does nothing. A first import written on the wrong one imports nothing and reports success.

If you used any of these words, try again natural key · surrogate key · upsert · idempotency · external identifier · join. "You never match on something a human is allowed to edit" is the explanation, and it is the whole lesson.

Build it

Task · 45 minutes Dev store

Create a duplicate product on purpose. This is the single most valuable mistake to have already made.

  1. Write a small sync that matches products on title. Run it. Fine.
  2. Edit one product's title in the admin, the way a marketer would.
  3. Run the sync again. Watch it create a duplicate.
  4. Now define a custom ID metafield, with uniqueness set up, and write your own reference into it.
  5. Rewrite the sync to look up by that instead. Edit the title again. Run it again.

Proof it worked: after the change, editing the title does nothing at all to the sync. Before the change it produced a duplicate you can still see in the admin. Keep both products as evidence.

The mutation that silently does nothing · 20 minutes Dev store
  1. Using a custom ID that does not exist yet, call productUpdate.
  2. Check whether anything was created. Check whether you got an error.
  3. Now call productSet with the same identifier.

Proof it worked: one created the product and one did not, and you can say which is which without checking. Write it in your notes: lookup is broad, create-or-update is products and customers only. And keep your mapping table anyway — a custom ID complements it, it does not replace it.

Remember this

  • A custom ID is a unique, defined metafield used as an identifier. Tell Shopify your id.
  • productByIdentifier, customerByIdentifier, orderByIdentifier and similar for collections and variants.
  • productSet creates when there is no match. productUpdate does not.
  • Lookup is broad; create-or-update is products and customers only.
  • ProductSetIdentifiers takes customId, handle, or id.
  • Never match on handle or title for an ongoing sync. Both change when content is edited.
  • A custom ID complements your mapping registry, it does not replace it.

If you remember one thing: write your own identifier into Shopify, and the question "which record is this?" stops needing a lookup.
