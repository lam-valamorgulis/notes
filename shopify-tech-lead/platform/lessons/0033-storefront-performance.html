Track 1 · P10 · Lesson 2

Storefront performance

The cause is almost always apps, and the fix is almost never a rebuild.

What is verified here, and what is not The Shopify-specific facts on this page are verified and linked. The diagnostic order and the priorities are engineering judgement, not documentation — Shopify publishes no ranked list of causes. Treated as advice, not as fact.
Your win today. When a client says "the site is slow, should we go headless?", you can find the real cause in an afternoon and usually save them the rebuild.

How it works

Derive it: what can actually make a Shopify storefront slow?

Shopify hosts the page and serves it from a CDN. So the things you and the merchant control are a short list — and that is genuinely useful, because it makes diagnosis finite:

Shopify's side hosting, CDN, Liquid rendering ← not yours ───────────────────────────────────────────────────────── THE MERCHANT'S SIDE third-party scripts apps, tag managers, chat, tracking ← usually the answer images oversized, wrong format, no lazy load theme JavaScript too much, or blocking fonts render-blocking, too many weights section count how much is on the page at all

Note what is missing from that list: Liquid. Rendering happens on Shopify's infrastructure, before the browser is involved. So "Liquid is slow" is almost never the finding, which is exactly why "go headless for speed" usually does not help — you would carry every item in the lower box with you and add a hosting layer to tune.

The diagnostic order

#CheckWhy here
1Count the third-party scripts. View source, list every external domainHighest hit rate by a wide margin. Each app adds requests, and apps outlive their usefulness
2Check image sizes and formats on the heaviest pageUsually the largest bytes. Often a 3000px image in a 400px slot
3Count theme sections on the home pageMerchants add sections over years and never remove them
4Look for render-blocking fonts and CSSCheap to fix, visible improvement
5Only then look at theme JavaScriptWhere developers want to start, and rarely the biggest win

Step 1 is not glamorous and it is where the answer usually is. Ask which installed apps the merchant still actually uses. An uninstalled app can leave script tags behind; an unused one certainly does.

Two Shopify-specific facts that matter here

FactConsequence
Theme app extensions cap Liquid at 100 KBA hard limit on how much an app can inject. Exceptions exist for custom distribution or Built for Shopify status, and Shopify notes raising it can hurt performance
Script tags on Thank you / Order status are sunset28 Aug 2025 for Plus, 26 Aug 2026 for non-Plus. Old tracking scripts there have already stopped — which is a performance and a functionality finding

Both come from P5.2 and A1.1. The second one is worth checking on any inherited store: you may find dead scripts still being downloaded.

The headless question, answered properly

From P4.1, restated because this is where it gets asked: a headless rebuild that carries the same third-party scripts will be slower, not faster, because you have added a hosting layer you now have to tune and lost the theme editor.

So the honest sequence is: measure, fix the top two causes, measure again. If the site is still slow after removing unused apps and fixing images, you have evidence for a bigger conversation. If it is not — and it usually is not — you saved the client a rebuild, and that is a better outcome than winning the argument.

Performance as a correctness requirement, not a nice-to-have

Two places in this Course where slow is broken, both verified:

WhereWhy slow = broken
POS extensionsShopify's own documentation says extensions "run in the context of key merchant workflows, so always prioritize performance". There is a customer at a counter — see P3.3
Carrier rate callbacksThe timeout shrinks as traffic grows: 10 s → 5 s → 3 s. Slow does not degrade, it fails to backup rates — see P7.2
Answer before reading on A client says a competitor's site feels faster and asks for a quote to go headless. What do you do first, and what do you say?

First: measure, and count the scripts. View source on their busiest page and list every external domain being loaded. That is an afternoon, not a project.

What you say: "Before I quote a rebuild, give me an afternoon to find out why it's slow. In my experience it's usually apps loading their own scripts, and images that are bigger than the space they're shown in — both fixable in the theme this month. If I rebuild it headless and we carry the same scripts across, it'll be slower, not faster, because we've added a hosting layer to manage. If the measurement says otherwise, you'll have real evidence for the bigger decision."

Notice the structure: you refuse the expensive thing, offer a cheap diagnostic, and commit to supporting the expensive thing if the evidence supports it. That is not caution — it is the only version of this conversation where the client can trust your eventual answer.

Where it hurts

Costs money — a headless rebuild for speed The scripts and images follow you, and you add a hosting layer to tune. The score does not move and nobody can explain why. Measure first.
Fails with no error — scripts from apps nobody uses Uninstalled and unused apps can leave script tags loading on every page view. Nothing errors; the site is just heavier. Audit installed apps against what the merchant actually uses.
Fails with no error — dead checkout scripts still downloading Script tags on Thank you and Order status pages are sunset — 26 Aug 2026 for non-Plus. They may still load and do nothing. A functionality bug wearing a performance costume.
Starting with theme JavaScript Where developers want to begin and rarely the biggest win. Scripts and images first, always.
Blaming Liquid Rendering happens on Shopify's infrastructure before the browser sees anything. It is almost never the finding, and saying so early stops a wrong project.
Judgement, not documentation — a score is not the goal A client will bring a Lighthouse number. Improving a score and improving revenue are correlated but not the same, and some score fixes are cosmetic. Ask what they actually want — faster pages, or a higher number — and if it is the number, say plainly that you will optimise for the number.

Say it out loud

Explain this to a beginner

A client says their Shopify shop is slow and asks you to rebuild it. Explain what you look at, in order, and why "the theme code" is near the bottom.

Say it out loud. Then read on.

Now compare with a plain-words answer

Because Shopify already built the page before the customer's browser saw anything. That part happens on Shopify's own machines, and it is fast. So the slowness is almost always things added to the page, not the page itself.

So you look in this order: other people's scripts, then images, then how many things are on the page, then fonts, and only then the shop's own JavaScript.

The answer is usually the first one. Every app the shop installed adds its own code to every page — reviews, chat, popups, loyalty, wishlists. And the really annoying part: apps that were removed can leave their code behind, still downloading on every single page view, doing nothing at all.

Which is why the cheapest fix in this whole subject is usually uninstalling something, not writing anything.

And why "let's rebuild it from scratch to make it fast" usually makes it worse: those scripts and images follow you to the new site, and now you also own the hosting to tune. Same weight, more work.

One exception worth naming: in a couple of places slow genuinely is broken — the shop till, where there is a queue of real customers, and the live shipping-price call, where your time limit shrinks as the shop gets busier.

If you used any of these words, try again Core Web Vitals · LCP · render-blocking · TTFB · Lighthouse score · critical rendering path. "Shopify built the page before the browser saw it, so it is the things added on top" is the explanation.

Build it

Task · 60 minutes a real store

Count before you quote. This is the whole job.

  1. Load a product page and list every third-party script, with its size.
  2. Match each script to an installed app. Anything you cannot match is a leftover from an uninstalled app — write those down separately.
  3. List the images and their real dimensions versus displayed dimensions.
  4. Count the sections on the page.
  5. Only now look at the theme's JavaScript.

Proof it worked: you found at least one script from an app nobody uses. That is a free win requiring no code, and it is the finding a client remembers. If you started with the theme's JavaScript, start again — that ordering is exactly the mistake.

The conversation, in writing · 20 minutes no store needed

A client brings you a Lighthouse number. Write the one-page reply: what the number measures, what you measured, which fixes are cosmetic and which change what customers experience.

Proof it worked: your reply separates improving a score from improving revenue. They correlate; they are not the same. And nothing in your reply blames Liquid, because Liquid renders before the browser is involved and is almost never the finding.

Remember this

  • Shopify hosts and renders the page. The controllable causes are a short, finite list.
  • Diagnostic order: third-party scripts → images → section count → fonts and CSS → theme JavaScript.
  • Scripts from apps are the usual answer. Audit installed apps against what is actually used.
  • Liquid is almost never the finding. It renders before the browser is involved.
  • Headless for speed usually makes it worse — the scripts follow you, plus a hosting layer to tune.
  • Theme app extension Liquid caps at 100 KB, and raising it can hurt performance.
  • In POS extensions and carrier callbacks, slow is broken — one has a queue, the other a shrinking timeout.

If you remember one thing: measure and count the scripts before quoting anything — the cheapest fix is usually uninstalling an app nobody uses.
