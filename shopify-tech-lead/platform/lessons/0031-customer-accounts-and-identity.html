Track 1 · P9 · Lesson 3

Customer accounts and identity

There are two versions, and the old one supports none of this. Check first.

Your win today. You check which account version a store uses before scoping, and you know the three approvals a customer-facing extension needs before it can go live.

How it works

Derive it: what is a customer account for?

Order history, order status, profile editing, and taking action on an order. That is genuinely all — which means it is the one surface where the customer returns after buying. Everything valuable there is post-purchase: returns, loyalty, subscriptions, tracking.

First, the fork in the road

Check this before you scope anything There are two versions of customer accounts. Customer account UI extensions are only supported on the new version. Legacy customer accounts do not support them at all.

Query the CustomerAccountsV2 object to find out which a merchant is on. Ten seconds, and it is the difference between a feature being buildable and not existing.

So the first question on any customer-account request is not "what should it do" — it is "which version are they on". Scoping a loyalty panel for a store on legacy accounts is scoping something impossible.

What you can extend

Two connections worth noticing. The order index showing invoiced draft orders ties straight to P8.3 — a B2B buyer sees their invoices here. And the profile page carrying company information ties to P9.1.

The shape is the same as every other extension

Polaris, and three parts: targets (where you appear), target APIs (what data you can reach), web components (what you render). Preact TSX plus a TOML config, scaffolded with shopify app generate extension. If you have read P3.3 or P5.2, this is the third time — the pattern is deliberate.

# shopify.extension.toml
[[extensions.targeting]]
target = "customer-account.order-status.block.render"
module = "./src/OrderStatusBlock.tsx"

[[extensions.targeting]]
target = "customer-account.profile.block.render"
module = "./src/ProfileBlock.tsx"

[[extensions.targeting]]
target = "customer-account.page.render"        # a whole new page
module = "./src/LoyaltyPage.tsx"

[extensions.capabilities]
api_access     = true
network_access = true                          # needs Partner Dashboard approval

[extensions.capabilities.collect_buyer_consent]
customer_privacy = true

Three approvals, and they are the schedule risk

WhatApproval needed
Accessing customer data at allProtected customer data access must be approved before it can go live
Calling your own backendnetwork_access = true and a request in the Partner Dashboard
Collecting buyer consentDeclared as a capability

All three work fine in development and block you at launch. That is a schedule risk, not a technical one: request them at the start of the build, not the end. And remember from A1.4 that touching a name, address, phone or email puts you at privacy level 2 — which is exactly what a customer account extension does by definition.

The CORS trap

Documented, specific, and invisible until it fails UI extensions run in a Web Worker with a null origin. So if your extension fetches from your backend, your server must return Access-Control-Allow-Origin: *. A normal allow-list of domains will not match, because there is no origin to match.

And the alternative worth considering first: if the data is not truly dynamic, use metafields instead of a network call. Shopify says so explicitly, and it removes the approval, the CORS problem and the latency at once.

The migration fact nobody plans for

From P6.5: passwords never move between platforms. Modern customer accounts can sign a customer in with a one-time code sent to their email, which removes the password problem entirely — and turns a technical dead end into a communications plan. Raise it in the first meeting.

Answer before reading on A client wants a loyalty points balance shown in their customers' accounts. Points live in an external loyalty system. Name the four things you must establish before giving an estimate.

1 · Which account version are they on? Query CustomerAccountsV2. On legacy accounts, UI extensions do not exist and the answer is "not possible without migrating first" — which is a different project.

2 · Has protected customer data access been approved? Showing a balance against a named customer is customer data. It works in development and blocks at launch.

3 · Network access, or metafields? If points can be synced periodically into a metafield, you avoid the Partner Dashboard request, the CORS work and the latency. If they must be live, you need network_access plus approval, and your server must send Access-Control-Allow-Origin: *.

4 · What shows when the loyalty system is down? A points balance is information, so fail open — hide the panel. Same rule as A4.1.

Three of those four are approvals and version checks rather than code. That is what makes this area's estimates go wrong.

Where it hurts

Costs money — scoping extensions for legacy accounts Legacy customer accounts support none of this. Discovering it after quoting means the real project is an account migration. Query CustomerAccountsV2 first.
Costs money — approvals requested at the end Protected customer data access and network access both work in development and block go-live. Request them on day one.
Fails with no error — a domain allow-list for CORS Extensions run with a null origin. An allow-list matches nothing. You need Access-Control-Allow-Origin: *, and the failure looks like an empty panel.
A network call where a metafield would do Every network call adds an approval, a CORS surface, latency and a failure mode. Shopify's own advice is to prefer metafields when the data is not truly live.
Fails with no error — checkout metafields after upgrading The latest extension version replaces checkout metafields with order metafields. Code reading the old location finds nothing after an upgrade.
Costs money — the login surprise on migration day Passwords never transfer. Every returning customer fails to sign in on go-live morning, and nothing is broken. One-time email codes plus a communications plan is the fix.
Judgement, not documentation — this is privacy level 2 by definition A customer account extension shows a named customer their own data, so you are handling name and email whether you meant to or not. Assume level 2 and its data-protection review from the start rather than discovering it during app review.

Say it out loud

Explain this to a beginner

You build a panel for a shop's account area. It works locally. Live, it is blank and there is no error. Explain the most likely cause.

Say it out loud. Then read on.

Now compare with a plain-words answer

Your panel runs in a heavily locked-down box, and that box does not tell your server who it is. Where a browser normally says "I am calling from shop.example.com", this says nothing at all.

So if your server is set up to allow calls from a list of approved addresses, the check compares your list against nothing, and nothing is never on a list. The call is refused and the panel draws empty. No crash, no message — just blank.

The fix is to allow any origin for that endpoint, because there is no origin to allow.

But before any of that, there is a bigger question people skip: there are two versions of Shopify's account system, and the older one cannot run add-on panels at all. So if the shop is on the old one, everything you just planned is unavailable, and the real project is upgrading their accounts first. Check the version before quoting, not after.

And a design instinct worth having: every network call from one of these panels adds an approval to request, a security surface, latency and a way to fail. If the data could just be stored on the product instead, store it there. Fewer moving parts, no approval.

If you used any of these words, try again null origin · CORS preflight · Web Worker sandbox · UI extension target · protected customer data. "The box does not tell your server who it is, so your approved-addresses list matches nothing" is the explanation.

Build it

Task · 20 minutes, before anything else the actual store

The cheapest question in this Lesson, asked in the right order.

  1. Query CustomerAccountsV2 on the store.
  2. If it is legacy, stop. Write down that UI extensions are unavailable and the real project is an account upgrade.
  3. Then request all three approvals on day one: protected customer data, network access, buyer consent.

Proof it worked: you know the account version and it is written down with a date. Both approvals work in development and block go-live, so asking on day one is the entire trick.

Then produce the blank panel on purpose · 60 minutes Dev store
  1. Build a small panel that fetches from your own backend.
  2. Configure your backend with a domain allow-list. Load the panel. It is blank.
  3. Switch to Access-Control-Allow-Origin: *. Load it again.
  4. Now rebuild the same panel reading a metafield instead of calling out at all.

Proof it worked: you have seen the silent blank panel and fixed it, and the metafield version needed no approval, no CORS and no network. Prefer that whenever the data is not truly live. And remember passwords never migrate — one-time email codes plus a communications plan.

Remember this

  • Two versions. Legacy supports no UI extensions. Query CustomerAccountsV2 before scoping.
  • Four surfaces: order index, order status, profile, and full new pages.
  • The order index lists invoiced draft orders; the B2B profile carries company information.
  • Three approvals — protected customer data, network access, buyer consent. Request on day one.
  • Null origin means Access-Control-Allow-Origin: *. An allow-list matches nothing.
  • Prefer metafields over a network call. It removes an approval, CORS and latency together.
  • Passwords never migrate. One-time email codes plus a communications plan.

If you remember one thing: check the account version first — on legacy accounts, everything in this Lesson is unavailable.
