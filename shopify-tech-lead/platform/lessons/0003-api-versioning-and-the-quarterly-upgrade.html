API versioning and the quarterly upgrade

Why "we upgrade every quarter" belongs in every estimate you ever give.

Your win today. You can tell a client, in one sentence, why their integration has a permanent maintenance cost — and defend it as a feature of the platform rather than a flaw in your build.

How it works

The schedule, and the only three numbers you need

RuleValue
New stable versionEvery 3 months, at the start of the quarter, 5pm UTC
Support per versionAt least 12 months
Overlap between consecutive versionsAt least 9 months

Version names are dates: 2026-07, 2026-10, 2027-01. So you always have around nine months to move, which is generous — and which is exactly why teams leave it until it is urgent.

2026-07 released 1 Jul 2026 ──────────────▶ accessible until 16 Jul 2027 2026-10 released 1 Oct 2026 ──────────────▶ accessible until 16 Oct 2027 2027-01 released 1 Jan 2027 ──────────────▶ accessible until 16 Jan 2028 ~9 months of overlap. plenty of time, right up until it isn't.

Fall forward: the behaviour that decides everything

Here is the mechanism that makes an unpinned version dangerous. If your app targets a version that is no longer accessible, Shopify does not reject the request. It falls forward and serves the oldest accessible stable version.

you request a retired 2026-10 │ ▼ Shopify serves 2027-01 instead │ └── your code did not change. the API's behaviour DID. nothing errored. nothing logged. field shapes moved.

That is the whole risk in one picture: the failure mode of ignoring versions is not an error, it is a silent behaviour change on a date you did not choose. And if you send no version at all, requests go to the oldest supported stable version — which also moves quarterly.

Verified 2026-08-23: quarterly releases at 5pm UTC, minimum 12 months of support, at least 9 months of overlap, the fall-forward rule, that omitting a version defaults to the oldest supported one, and the accessible-until dates above — About Shopify API versioning. The latest stable version as of this date is 2026-07.

So: pin it, once

One constant, read from configuration, used by every call. Never let a client library default to "latest" — and never let a second code path hold a different value. Two paths on two versions both work, and disagree occasionally, in one direction, about one field.

The upgrade, as a routine rather than an event

StepWhat
1Read the release notes for the new version. Not the whole changelog — the one version's notes
2Validate every query and mutation against the new schema. This is the step that finds the problems
3Change the one constant in a branch. Run the test suite
4Run against a Dev store on the new version before production
5Ship. Note the date you did it

Step 2 is the whole value, and it can be automated. This Course validated its own queries against the schema and found two already-deprecated fields — ShopPlan.displayName (use publicDisplayName) and Market.enabled (use status) — in queries that looked obviously correct. Two for two on the first attempt. A CI job doing that turns a quarterly upgrade into a red build you fix in an afternoon.

For a custom app there is a second tool: a REST endpoint that lists the deprecated calls your app has made in the past 30 days, with migration steps and deadlines. It only covers custom apps, and it only covers REST — but if you have inherited a REST codebase, it is a free work list.

Answer before reading on A client's integration has worked untouched for two years. No deploys, no errors. How many versions have passed, and what is the state of that app?

Eight versions. And if the version was pinned, that pin retired around a year ago — so every request has been falling forward to whatever the oldest accessible version is now, and has done so through several rollovers. The app is not "stable"; it is running on an API contract nobody chose, which changed silently at least twice. The absence of errors proved nothing, because fall-forward is designed not to error. This is the strongest argument you will ever have for a maintenance retainer, and it is entirely honest.

Where it hurts

Costs money — no version pinned Requests go to the oldest supported version, which moves every quarter. Your app's behaviour changes on Shopify's schedule. The bug reports arrive weeks later, uncorrelated with any deploy of yours, which makes them expensive to diagnose.
Fails with no error — fall forward A retired pinned version is served by a newer one instead of failing. Field shapes move, defaults change, nothing logs. This is the reason "it hasn't errored" is not evidence of health.
Fails with no error — two versions in one codebase Your constant says one thing, a client library defaults to another. Both work. They disagree about one field, sometimes. This can survive for months and is miserable to find.
The upgrade treated as a project Left for nine months, it becomes an unbudgeted sprint with several breaking changes at once. Done quarterly with schema validation in CI, it is an afternoon. The work is identical; only the batching differs.
Deprecated but still working A deprecated field keeps returning data, so nothing forces you to act. Then it is removed. Treat a deprecation warning as a dated task, not as information.
Judgement, not documentation — webhook payloads are versioned too It is easy to pin your API calls and forget that webhook subscriptions carry a version as well. Upgrade both together, or you will parse a new payload shape with old code.

What you say to a client/PM

When quoting the build, before anyone asks One thing to build into your budget: Shopify releases a new version of their API every three months, and each one is supported for about a year. So the integration needs a small maintenance slot roughly quarterly. It's a few hours if we keep up. It's a fortnight if we leave it two years, which is what usually happens. Raising it unprompted makes it a platform fact rather than a later surprise. Clients accept costs they were warned about.
When a client says their existing integration "works fine, don't touch it" I'd check one thing first. Shopify retires API versions after about a year, and when yours retires they don't fail your requests — they quietly serve a newer version instead. So an integration that hasn't been touched in two years is running on a version nobody picked, and it changed without telling anyone. It might genuinely be fine. I'd rather know than assume. Describes a real mechanism instead of implying the previous developer was careless. That keeps the client on your side.

Remember this

  • New stable version every 3 months. Supported at least 12 months, with at least 9 months of overlap.
  • Latest stable is 2026-07 as of this Lesson, accessible until 16 July 2027.
  • Fall forward: a retired version is silently served by a newer one. It does not error.
  • No version specified means the oldest supported one, which also moves quarterly.
  • Pin it once, in one constant. Two paths on two versions is a miserable bug.
  • Validate every query against the new schema in CI. That step found two deprecated fields here on the first try.
  • Webhook subscriptions are versioned too. Upgrade both together.

If you remember one thing: "it hasn't errored" is not evidence of health, because falling forward is designed never to error.
