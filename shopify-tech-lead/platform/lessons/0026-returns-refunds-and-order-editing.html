Track 1 · P8 · Lesson 1

Returns, refunds and order editing

Changing a paid order changes what someone was charged. Shopify now forces you to be idempotent.

Your win today. You can refund correctly, restock deliberately, and explain why editing a paid order is a different class of operation from everything else in this Course.

How it works

Derive it: what makes post-purchase different?

Everything before checkout is a proposal. A cart can be wrong and nothing has happened. After payment, the order is a record of a completed financial event — the same category as an imported historical order in P6.6.

So changing it is not an update. It is amending a financial record and moving money, and three separate things move at once:

one refund touches THREE systems of record MONEY a transaction back to the payment method STOCK restock — or deliberately not TAX proportional tax reversal, calculated by Shopify get one right and the other two wrong and nothing errors.

A refund has two halves, and people forget the second

Shopify's own framing: a refund has transaction records of money returned and the line items included, with restocking instructions. Two halves. The money half is obvious; the stock half is where integrations go wrong.

Always calculate before you refund

Do not compute a refund amount yourself. Ask Shopify what it should be, then create the refund from that answer:

query SuggestRefund($orderId: ID!, $lineItems: [RefundLineItemInput!]) {
  order(id: $orderId) {
    suggestedRefund(refundLineItems: $lineItems) {
      amountSet             { shopMoney { amount currencyCode } }
      maximumRefundableSet  { shopMoney { amount } }
      shipping {
        amountSet            { shopMoney { amount } }
        maximumRefundableSet { shopMoney { amount } }
      }
      refundLineItems { quantity restockType lineItem { id } }
      suggestedTransactions { amountSet { shopMoney { amount } } kind }
    }
  }
}

This is the same rule as tax in P7.3: read the platform's number, never derive one. The suggestion accounts for discounts already applied, proportional tax, and what has already been refunded — three things you would get wrong by hand.

Refunding less than the calculated amount You may refund less than suggested, for line items or shipping. But know what that does: an order adjustment is created automatically to account for the discrepancy in the store's financial reports. So a partial refund is not silent — it leaves an accounting artefact, which is correct and which the merchant's accountant will see.

Two refund mutations, and the difference is restocking

MutationMoneyRestocking
refundCreateYesYes — you specify restock behaviour per line item
returnRefundYesNo restocking input at all — purely financial

Pick deliberately. A customer returning a faulty item should be refunded without restocking; a change-of-mind return usually restocks. Choosing the wrong mutation means either phantom stock you cannot sell or real stock that never comes back.

The breaking change you need to know about

Dated, and already in force The refund mutation's idempotency key was optional as of API version 2026-01, and is REQUIRED as of 2026-04, supplied with the @idempotent directive.

So on any current version, a refund without an idempotency key is rejected. Shopify made the discipline from A3.3 mandatory for exactly the reason that Lesson gives: a retried refund must not pay a customer twice. Code written against 2026-01 and not touched since will fail on upgrade.

Order editing: begin, mutate, commit

Editing a paid order is a three-phase transaction, and the middle phase is not live:

1. orderEditBegin(id) → returns a CalculatedOrder a DRAFT. the real order is untouched 2. mutate the CalculatedOrder orderEditAddVariant orderEditSetQuantity orderEditAddCustomItem orderEditAddLineItemDiscount 3. orderEditCommit(id, ...) → NOW the order changes 
mutation Begin($id: ID!) {
  orderEditBegin(id: $id) {
    calculatedOrder { id originalOrder { name } }
    userErrors { field message }
  }
}

mutation Commit($id: ID!, $notify: Boolean, $staffNote: String) {
  orderEditCommit(id: $id, notifyCustomer: $notify, staffNote: $staffNote) {
    order { id name totalPriceSet { shopMoney { amount currencyCode } } }
    userErrors { field message }
  }
}

The draft phase is the useful part: you can add, remove and price things, read the recalculated totals, and show a human the result before committing. Anything that changes what a customer paid should have a human look at it first — and this API is built to allow that.

Note notifyCustomer on the commit. Editing an order can email the customer. Decide that explicitly rather than accepting a default.

Verified 2026-08-23: a refund's two components and the calculate-then-create flow, that you may refund less and that an order adjustment is created automatically for the discrepancy — Refund. The refundCreate versus returnRefund restocking difference, and the idempotency key being optional from 2026-01 and required from 2026-04 via @idempotent — Refund — GraphQL Admin. The order-edit mutation set — CalculatedLineItem. All three operations above were validated against the 2026-07 schema. Scopes: write_order_edits, read_order_edits, read_orders.

Answer before reading on Your integration refunds an order. The call times out — but it actually succeeded. Your retry logic fires. What happens on 2026-01, and what happens on 2026-07?

On 2026-01, where the idempotency key is optional and you did not send one: the customer is refunded twice. Real money, out of the merchant's account, and the only signal is a second transaction that looks deliberate.

On 2026-07, where the key is required: if you sent one, the retry is recognised and does nothing — correct. If your code predates the requirement and sends no key, the call is rejected outright and no refund happens at all. That is a different bug, and a much better one: it fails loudly instead of paying twice.

The lesson underneath is the whole of A3.3, now enforced by the platform: a write that moves money must be safe to repeat, and Shopify stopped trusting developers to remember.

Where it hurts

Costs money — a refund with no idempotency key On older versions, a retried refund pays the customer twice. On current versions the call is rejected. Either way, code written before 2026-04 needs changing.
Costs money — calculating the refund amount yourself Discounts already applied, proportional tax, and prior partial refunds all affect it. Use suggestedRefund and refund from its answer.
Costs money — the wrong refund mutation returnRefund takes no restocking input. Use it for a change-of-mind return and the stock never comes back — you have quietly written off sellable inventory.
Fails with no error — restocking a faulty item The reverse. A damaged item restocked becomes phantom stock: Shopify will sell it, and nobody can ship it. Overselling caused by a refund.
Fails with no error — committing an order edit nobody looked at The draft phase exists so a human can check. Skip it and an automated edit changes what a customer paid, correctly according to your code and wrongly according to the customer.
Costs money — an unexpected customer email notifyCustomer on the commit, and the notify option on a refund, both send mail. A bulk correction run with notification on emails every affected customer about an order they had forgotten.
Refunds arriving in your ERP as new orders A refund is not an order. Anything consuming order webhooks must handle a refund as an amendment — otherwise your ERP sees revenue where money left the account.
Judgement, not documentation — decide who may refund automatically Shopify will let your app refund without a human. Almost no client should allow that unconditionally. Agree a ceiling — an amount, or a rule — in writing, and put anything above it in a queue for a person. This is a business control, not a technical one, and offering it unprompted is what a lead does.

Say it out loud

Explain this to a beginner

A refund looks like one action: give money back. Name the three things it actually moves, and explain why Shopify now refuses a refund that does not carry a safety key.

Say it out loud. Then read on.

Now compare with a plain-words answer

A refund moves money, stock and tax, all at once. Get the money right and the stock wrong and nothing errors — you have just either lost a sellable item or created one that does not exist.

On the safety key: imagine your code sends a refund and the connection drops before you hear back. Did it happen? You do not know. So you try again — and if the first one did go through, you have now paid the customer twice, with your client's money.

The key is just a note saying "this is that same refund, not a new one". Shopify sees the key already used and does nothing instead of paying again.

It used to be optional. It is now required. Read that as what it is: the platform decided it could not rely on developers to make money-moving operations safe to repeat, so it stopped asking.

Two more. Do not work out the amount yourself — discounts, proportional tax and earlier partial refunds all change it, so ask Shopify what it should be and refund from that answer. And there are two refund operations where only one can put stock back, so choosing the wrong one quietly writes off inventory you could have sold.

If you used any of these words, try again idempotency key · at-least-once delivery · restocking behaviour · order adjustment · proportional tax allocation. "A note saying this is that same refund, not a new one" explains the key completely.

Build it

Task · 60 minutes Dev store

Double-refund yourself on purpose, then make it impossible.

  1. Place a test order. Refund part of it without an idempotency key, then send the exact same request again.
  2. Look at the order's financial history. Note what happened, and whether anything warned you.
  3. Add the @idempotent key and repeat. Send it three times.
  4. Now call suggestedRefund on an order that has a discount and a prior partial refund. Compare its number with the one you would have calculated.

Proof it worked: with the key, three sends produce one refund. And suggestedRefund disagreed with your own arithmetic — which is exactly why you never do it yourself.

Stock, both wrong ways · 30 minutes Dev store
  1. Use returnRefund for a change-of-mind return. Check the stock afterwards.
  2. Use refundCreate with restocking for the same case.
  3. Now restock a damaged item and follow what happens when someone buys it.
  4. Finally, run an order edit: begin, change the draft, commit — and check the notifyCustomer flag before committing.

Proof it worked: you produced both failure directions — sellable stock written off, and phantom stock that Shopify will sell and nobody can ship. And your bulk-correction code sets the notification flag explicitly, because a bulk run with it on emails every affected customer.

Remember this

  • A refund moves money, stock and tax at once. Get one right and the others wrong and nothing errors.
  • Calculate first. suggestedRefund accounts for discounts, proportional tax and prior refunds.
  • Refunding less creates an order adjustment automatically in the store's financial reports.
  • refundCreate takes restocking input; returnRefund does not. Choose deliberately.
  • The idempotency key is REQUIRED from 2026-04 via @idempotent. Optional from 2026-01.
  • Order editing is begin → mutate a draft → commit. Keep a human on the commit.
  • Both refunds and edits can email the customer. Set that flag explicitly, especially on a bulk run.

If you remember one thing: Shopify now requires an idempotency key on refunds — the platform stopped trusting developers to make money-moving writes safe to repeat.
