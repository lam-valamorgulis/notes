Track 1 · P7 · Lesson 1

Shipping rates and delivery profiles

Five nested objects between a product and a price at checkout. Miss one and the rate disappears.

Your win today. You can answer "why is no shipping rate showing?" by walking the chain, and you know why "we ship heavy items differently" is a whole extra profile rather than a setting.

How it works

Derive it: what does a shipping price depend on?

A customer at checkout needs a number. Ask what it can possibly depend on, from first principles:

WHAT is being shipped ── a sofa costs more than a card FROM where ── which warehouse or shop TO where ── which country HOW MUCH of it ── weight, or cart value

Four inputs. So Shopify's model is four nested groupings, plus the rate itself — and that is exactly the object chain:

Delivery profile shipping settings for a GROUP OF VARIANTS │ e.g. one for heavy items, one for fragile ├── Profile items which products and variants are in it │ └── Location group a set of locations that ship to the SAME zones │ e.g. "Americas" ships to Canada and Germany │ └── Delivery zone a group of COUNTRIES │ └── Delivery method the static or carrier-calculated rate │ static rates can be CONDITIONAL └── Rate the number the customer sees

Feynman version: a profile answers "which things", a location group answers "from where", a zone answers "to where", and a method answers "how much". All four must line up or the customer sees nothing.

The profile is the part people miss

Every store has a default profile containing everything. You create a second profile when a group of variants needs genuinely different shipping — heavy goods, fragile goods, items that only ship from one warehouse.

Once a variant is in a custom profile it is no longer covered by the default one. So the classic failure is: someone creates a "Bulky items" profile, adds products to it, and forgets to configure a zone for one country. Those products now have no rate at all in that country, while every other product is fine.

Rate types

TypeBased onNotes
FlatNothing. A fixed priceSimplest, and what most stores should start with
Weight-basedCart weight bandsNeeds weights on every variant. A missing weight counts as zero
Price-basedCart total bandsThis is how "free shipping over $100" is built
Carrier-calculatedA live call to a carrier or your appP7.2 — a different job entirely

Static rates support conditions: a rate that applies only when the cart total is at or above a threshold, or the weight is within a band. That is the mechanism behind free shipping — it is a conditional rate of zero, not a discount.

Local pickup and local delivery

These are separate delivery methods, not shipping rates. A location can offer local pickup (the customer collects) or local delivery (you drive it). Both connect back to P3.2: a location is only usable for online orders when it is configured with shipping rates, local pickup, or local delivery.

One documented limitation worth knowing For subscription checkouts, if the customer chooses local pickup or local delivery, that method applies to the entire order. Mixed delivery methods are not supported — so a cart with a one-time item and a subscription cannot have one collected and the other shipped.

Reading it all in one query

query DeliveryProfiles {
  deliveryProfiles(first: 10) {
    nodes {
      id name default
      activeMethodDefinitionsCount
      productVariantsCount { count }
      profileLocationGroups {
        locationGroup { id locations(first: 10) { nodes { name } } }
        locationGroupZones(first: 20) {
          nodes {
            zone { id name countries { code { countryCode } } }
            methodDefinitions(first: 20) {
              nodes {
                id name active
                rateProvider {
                  __typename
                  ... on DeliveryRateDefinition {
                    price { amount currencyCode }
                  }
                  ... on DeliveryParticipant {
                    carrierService { id formattedName }
                    percentageOfRateFee
                    fixedFee { amount currencyCode }
                  }
                }
              }
            }
          }
        }
      }
    }
  }
}

Read the nesting — it is the model. And note rateProvider is a union: a DeliveryRateDefinition is a static price; a DeliveryParticipant is a carrier service, optionally with a markup (percentageOfRateFee, fixedFee) applied on top of whatever the carrier returns.

Costs money — this whole model is being replaced. Verified 2026-08-23. Shopify is rolling out market-driven shipping, which moves shipping configuration into each market so a merchant can tailor rates per market — across regions, POS locations and B2B company locations. As part of that rollout, deliveryProfile and deliveryProfiles are being deprecated for merchant-owned shipping configuration. Every merchant is expected to be on the new model by July 2027.

What still works: profiles your own app creates and manages are unchanged — keep using deliveryProfile / deliveryProfiles for those. What breaks is reading or writing the merchant's profiles.

What to do: detect the model with the marketDrivenShipping field on ShopFeatures, then branch. Writers move to marketCreate / marketUpdate (needs read_markets and write_markets). Readers either become a sales channel and use Contextual Product Feeds — Shopify's recommended path — or read the Markets API directly. Audit your code for deliveryProfile, deliveryProfiles, deliveryProfileCreate, deliveryProfileUpdate and deliveryProfileRemove: anything touching a profile your app did not create is a merchant-profile interaction and needs changing.

A Market-driven shipping feature preview is available on development stores, so you can test the new path before merchants start opting in. Turn it on and run your integration against both models. Upgrade your app for market-driven shipping
So read the rest of this Lesson with one correction in mind The chain below — profile → location group → zone → method → rate — is still the right mental model, and it is still what you will find on essentially every store today. But the place that configuration lives is moving from a delivery profile to a market. Learn the chain, then check marketDrivenShipping before writing anything.

Answer before reading on A client says "customers in Germany can't check out — it says no shipping available. But it works for everyone else." Walk the chain and name the four things to check, in order.

In order, cheapest first:

1 · Which profile are those products in? If they are in a custom profile, the default profile's Germany zone does not help them. This is the answer most of the time.
2 · Does that profile have a location group containing a location that can ship? A location needs shipping rates, local pickup or local delivery configured to fulfil online orders at all.
3 · Is Germany in a zone on that location group? A zone is a list of countries; Germany may simply be absent.
4 · Does that zone have an active method whose conditions the cart meets? A weight-based rate with bands 0–5 kg gives nothing to a 6 kg cart. A price-based rate starting at $50 gives nothing to a $30 cart.

Notice that step 4 is the only one that depends on the cart. Steps 1 to 3 are configuration, which is why "it works for everyone else" is a strong hint the answer is step 1 or 3.

Where it hurts

Costs money — a custom profile with an incomplete zone list Moving variants into a new profile removes them from the default one. Forget a country and those products have no rate at all there — the customer cannot check out, and every other product looks fine, so nobody suspects configuration.
Fails with no error — a missing variant weight Weight-based rates need a weight on every variant. A blank weight is treated as zero, so a heavy item can silently fall into the cheapest band and you ship it at a loss.
Costs money — free shipping built as a discount A conditional rate of zero and a shipping discount code behave differently, combine differently, and report differently. If the client means "free over $100 for everyone", that is a conditional rate, not a discount.
Fails with no error — a location that cannot fulfil online orders A location must be configured with shipping rates, local pickup or local delivery to be usable online. In the profile it looks present; at checkout it contributes nothing.
Assuming one rate per order When more than one rate is available the customer chooses. So your fulfilment logic must read what they picked, not assume the cheapest or the only one.
Mixed delivery methods on a subscription checkout Documented as unsupported: pickup or local delivery applies to the whole order. A cart mixing a subscription and a one-time item cannot split methods.
Judgement, not documentation — profiles multiply your test matrix Every profile × location group × zone × condition is a case that can be wrong on its own. Two profiles is not twice the testing, it is closer to four times. Push back on a third profile unless the shipping economics genuinely differ, and keep a written list of the country-and-cart combinations you actually tested.

Say it out loud

Explain this to a beginner

A customer reaches checkout and is told there are no shipping options. The shop definitely ships to their country. Explain what has actually gone wrong.

Say it out loud. Then read on.

Now compare with a plain-words answer

Almost nothing has "gone wrong". A chain of four things has to line up, and one link is missing.

The chain is: a set of products → the places they ship from → the countries you ship to → the prices you charge. Break any link and the customer sees nothing at all.

So the country being covered is only the third link. Maybe the product was moved into its own shipping set, and that set has no prices. Maybe the warehouse it ships from is not in any group. Maybe the group covers the country but nobody added a price.

The trap that makes this common: moving a product into its own shipping set takes it out of the normal one. It does not belong to both. So someone sets up special rates for one bulky item, and that item quietly stops being shippable everywhere else.

Which is why "no shipping available" is a configuration question, not a bug. You walk the chain and find the missing link — and you do it in that order, because starting anywhere else wastes an hour.

If you used any of these words, try again delivery profile · location group · zone · rate method · fulfilment eligibility. "Four things have to line up and one link is missing" is the explanation. Learn the real names after the idea, not before.

Build it

Task · 45 minutes Dev store

Break shipping four different ways, then read the chain backwards to find each break.

  1. Set up shipping normally and confirm a rate appears at checkout.
  2. Break link one: move a variant into a custom profile with no rates. Check out with it.
  3. Break link two: remove the location from its group.
  4. Break link three: delete the zone covering your test address.
  5. Break link four: delete the rate but keep the zone.
  6. Each time, the customer sees the same "no shipping available". Write down the query that told you which link it was.

Proof it worked: four different causes, one identical symptom, and one query that distinguishes them. Keep the query — it turns an hour of guessing into a minute.

The silent money one · 20 minutes Dev store
  1. Set up a weight-based rate with bands.
  2. Create a heavy product and leave its variant weight blank.
  3. Check out and look at the shipping price offered.
  4. Then set up "free shipping" as a conditional rate of zero, and separately as a discount. Compare how each reports.

Proof it worked: the blank weight was treated as zero, so the heavy item fell into the cheapest band and would have shipped at a loss. Nothing warned you. Now add a check to your sync that refuses to write a variant with no weight when weight-based rates are in use.

Remember this

  • Profile → location group → zone → method → rate. All four must line up or the customer sees nothing.
  • A profile groups variants. Moving a variant into a custom profile removes it from the default one.
  • Four rate types: flat, weight-based, price-based, carrier-calculated.
  • Free shipping is a conditional rate of zero, not a discount. They behave differently.
  • A blank variant weight counts as zero and silently falls into the cheapest band.
  • A location needs rates, pickup or local delivery configured to fulfil online orders at all.
  • The customer picks the rate when several are offered. Read what they chose.

If you remember one thing: "no shipping available" is almost never a bug — it means one link in the profile → group → zone → method chain does not cover that cart.
