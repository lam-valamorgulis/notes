Track 1 · P1 · Lesson 1

The Shopify object model, end to end

One diagram you will reuse all year. Stock is not on the product, and that is the whole lesson.

Your win today. You can draw the chain from product to a stock number at a named place, and explain why "how many do we have?" needs three objects to answer.

How it works

Derive it: what is actually being sold?

A shop sells "a t-shirt". But you cannot ship "a t-shirt" — you ship a medium in black. So the sellable thing is the variant, and the product is a grouping for presentation.

Push once more. The variant is what a customer chooses. But the same physical item might sit in a warehouse and in two shops, with different quantities. So the quantity cannot live on the variant either — a single number cannot describe three places.

Product a group for display. NOT sellable. └── ProductVariant the sellable thing. price, SKU, options. └── InventoryItem the stockable thing (1:1 with the variant) └── InventoryLevel ONE PER LOCATION ← the quantity lives here └── Location a real place "how many do we have?" = sum of InventoryLevels across Locations "how many here?" = one InventoryLevel

Feynman version: the product is the poster, the variant is the thing, the inventory item is the thing-as-stock, and the level is that stock in one place. Four objects because the question "how many" is meaningless without a place.

Quantities are plural

Even one inventory level has several numbers, and they are not interchangeable:

NameRoughly means
availableCan be sold right now
on_handPhysically there, including what is already promised
committedSold but not yet shipped
incomingOn its way to this location
reserved, damagedHeld back, not sellable

This is the source of the overselling mistake from Track 2: an ERP's "stock" is usually on_hand, and Shopify sells available. Writing one into the other is how you promise items that are already sold.

The order side

Order the customer's request to buy ├── LineItem what they chose └── FulfillmentOrder work to be done FROM ONE LOCATION ├── FulfillmentOrderLineItem └── Fulfillment an actual shipment, with tracking one Order can have SEVERAL FulfillmentOrders ── because its items may ship from different places

That last line is the part people miss. An order is not one shipment. Split it across a warehouse and a shop and you get two fulfillment orders, each with its own location and status. Anything that assumes one order equals one shipment breaks the first time a cart spans two locations.

And a FulfillmentService — a third-party warehouse — automatically gets its own Location when it is created. So "locations" in a real store is not just shops and warehouses; some are apps.

Verified 2026-08-23: Order contains an array of FulfillmentOrders; a FulfillmentOrder is items fulfilled from the same location and there can be more than one per order per location; a FulfillmentService always has its own automatically created Location; active Locations can fulfil online orders when configured with shipping rates, local pickup or local delivery — Apps in order management and About fulfillment services. The product → variant → inventoryItem → inventoryLevel → location chain and the named quantities were validated against the 2026-07 Admin schema on the same date.

The query that proves it

query ObjectModel {
  products(first: 1) {
    nodes {
      id title
      variants(first: 1) {
        nodes {
          id sku
          inventoryItem {
            id tracked requiresShipping
            inventoryLevels(first: 10) {
              nodes {
                location { id name }
                quantities(names: ["available","on_hand","committed",
                                   "incoming","reserved","damaged"]) {
                  name quantity
                }
              }
            }
          }
        }
      }
    }
  }
}

Read the nesting: to get from a product to a number you pass through variant, inventory item, inventory level and location. That nesting is the model.

Answer before reading on A client says "the product page says 5 in stock but we have 8 in the shop". Name three different explanations, using the right object names.

One: the shop's Location is not stocking that variant, so its InventoryLevel is absent — the 5 is from another location. Two: on_hand is 8 but available is 5, because 3 are committed to orders not yet shipped. Three: the shop is not a Location at all, so its stock is invisible to Shopify entirely. All three look identical to a client, and the object names are what let you tell them apart in one query instead of a day of guessing.

Where it hurts

Costs money — writing on_hand into available The two differ by exactly the amount already sold. Overwrite one with the other and you re-sell items that are boxed and waiting to ship. This is the single most common cause of overselling in an integration.
Costs money — assuming one order is one shipment Code that fulfils "the order" fails or double-ships when an order has two FulfillmentOrders from two locations. Model the fulfillment order, not the order.
Fails with no error — the missing InventoryLevel A variant not stocked at a location has no level there, rather than a level of zero. Code expecting a row gets nothing and often treats it as zero — which is right by accident, until you try to write to a level that does not exist.
Fails with no error — tracked: false A variant with tracking off has no meaningful quantity, and writes to it do nothing useful. Check tracked before trusting or setting a number.
Treating the product as the sellable unit Prices, SKUs, barcodes and stock are all on the variant. A design that maps an ERP item to a Shopify product works only while every product has exactly one variant, and then breaks permanently.
Judgement, not documentation — locations are not all shops Fulfillment services create their own locations, so a "location count" mixes real places with apps. Never assume the list of locations equals the list of shops; check what each one is before building a store locator on it.

Say it out loud

Explain this to a beginner

A shop sells t-shirts. Why does Shopify need four separate things just to answer "how many do we have?"

Say it out loud, to someone who has never opened Shopify. No object names. Then read on.

Now compare with a plain-words answer

You cannot post "a t-shirt" to someone. You post a medium black one. So the thing a customer really buys is the medium black one, and "t-shirt" is just the folder it sits in. The folder is the product. The medium black one is the variant.

Now that same medium black shirt might be sitting in a warehouse and in two shops. If I asked you "how many do we have?" and you handed me one number, you would have thrown away the part I needed — where. So the count cannot be written on the shirt. It has to be written once per place.

That is why there are four. The product is the poster on the wall. The variant is the actual shirt. The inventory item is that shirt thought of as stock. The inventory level is that stock in one named place. Four things, because "how many" is a meaningless question until you say "how many where".

If you used any of these words, try again object model · entity · one-to-one relationship · hierarchy · normalised · granularity · SKU-level. Every one of them names the shape instead of explaining it. A beginner learns nothing from "it is a normalised hierarchy". They learn everything from "you cannot post a t-shirt, you post a medium black one".

Build it

Task · 20 minutes no store needed

A client says: the product page says 5 in stock but we have 8 in the shop. Block 01 gave three explanations. Now make them distinguishable.

  1. Write one GraphQL query that returns enough to tell all three apart. Start from the query in block 01 and cut everything you do not need.
  2. Next to each field you kept, write which of the three explanations that field rules out.
  3. Find the case your query cannot settle, and write down why. (There is one. The shop that is not a Location at all does not appear in any inventory level, so its absence looks the same as a variant simply not being stocked there.)

Proof it worked: your query returns, for one variant, every InventoryLevel with its location { name } and the available, on_hand and committed quantities — and you can point at one field per explanation. If you cannot say which field settles which case, you have copied the query rather than read it.

Then, once the Dev store exists · 10 minutes Dev store
  1. Pick one variant. Set its on_hand to 8 at one location.
  2. Read available for the same level. It is also 8.
  3. Place an order for 3 of that variant and do not fulfil it.
  4. Read both numbers again.

Proof it worked: on_hand is still 8, available is now 5, and committed is 3. You have just reproduced the overselling bug on purpose. An ERP that sends its "stock" number sends the 8.

Remember this

  • The variant is the sellable thing. The product is a grouping for display.
  • Product → Variant → InventoryItem → InventoryLevel → Location. The quantity lives at the level.
  • "How many" is meaningless without a place. Total stock is a sum across locations.
  • available ≠ on_hand. They differ by what is committed. Confusing them oversells.
  • One order can have several FulfillmentOrders, one per location. Model that, not the order.
  • A missing InventoryLevel is absence, not zero, and you cannot write to a level that does not exist.
  • Fulfillment services create their own Locations. Not every location is a shop.

If you remember one thing: stock is not a property of a product — it is a number attached to a variant at a place.
