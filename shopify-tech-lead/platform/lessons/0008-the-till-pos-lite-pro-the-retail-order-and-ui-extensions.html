The till: POS, the retail order, and UI extensions

What changes when the sale happens in a shop, and how your code runs on the counter.

Your win today. You know why an in-shop sale is still an Order, what is different about it, and the three places your own code can appear on a till screen.

How it works

Derive it: a shop sale is still an order

A customer buys in a shop. No cart, no checkout page, no shipping address, payment by card terminal. Ask whether Shopify needs a new concept for that.

It does not. The sale creates an Order, at a Location, drawing down that location's InventoryLevel — exactly the objects from P1.1. What differs is which fields are populated:

Online orderRetail order
Shipping addressPresentUsually absent
CustomerUsually attachedOften anonymous
FulfilmentLater, from a locationImmediate — they walk out with it
LocationAssigned by routingThe shop, definitively

That third row is the one that breaks integrations. A retail order is created and fulfilled in the same instant, so anything downstream that expects "order created, then fulfilled later" sees both at once — or sees a fulfilled order it never saw unfulfilled. And the second row breaks anything that assumes an order has a customer.

Your code on the till: three target types

POS UI extensions are built with Polaris and have three interconnected parts — targets (where you appear), target APIs (what data you can reach there), and web components (what you can render). The targets:

TargetAppearsUse for
TileThe smart grid — the POS home screenStatus at a glance, quick actions, starting a workflow
ActionA menu item button on native screens, opening a modalFull workflows, forms, multi-step processes
BlockInline within native POS screensMetrics, instructions, printed receipt content

Extensions render as native components, work identically on iOS and Android, and are scaffolded with shopify app generate extension — TOML config plus Preact-based TSX.

Verified 2026-08-23: the three target types and their uses, the targets/target-APIs/web-components structure, Polaris as the basis, Preact + TSX + TOML, native rendering and iOS/Android parity, and Shopify's own instruction that extensions "run in the context of key merchant workflows, so always prioritize performance" — Extending Shopify POS with UI extensions and the POS UI extensions reference.

What I did not verify The specific feature split between POS Lite and POS Pro, and which POS capabilities require a particular Shopify plan. Those are commercial tiers that change, and I did not confirm them today. Check the current tier before promising a POS feature to a client — this is exactly the kind of fact that goes stale between a proposal and a build.

Performance is a correctness requirement here

A slow web page is annoying. A slow till has a queue of customers and a staff member who will stop using your feature. Shopify says it in the documentation, which is unusual. Treat a POS extension's latency budget as tighter than a storefront's, not looser.

Answer before reading on Your ERP integration listens for order webhooks and creates a picking task for the warehouse. The client opens a shop with Shopify POS. What goes wrong?

You create picking tasks for items that already left the shop in a customer's hand. A retail order arrives created and fulfilled in the same moment, and your handler only checks that an order exists. The warehouse gets work for goods that are gone, and stock gets decremented twice if the picking flow also adjusts inventory. The fix is to branch on how the order was placed and on its fulfilment state — not to assume every order needs fulfilling. Anything that consumes orders must be told that shops exist before the first shop opens.

Where it hurts

Costs money — treating a retail order as unfulfilled Picking tasks, packing labels or fulfilment API calls for goods already handed over. In the worst case stock is decremented twice and the shop shows as out of stock.
Fails with no error — assuming every order has a customer Retail orders are often anonymous. Code reading order.customer.email throws or silently skips, and the failures cluster in one shop, which makes them look like a shop problem rather than a code problem.
Fails with no error — assuming a shipping address exists Same shape. Address-based logic — tax, routing, region rules — has nothing to work with on an in-shop sale.
A heavy extension on the till A network call on a tile render, or a modal that loads slowly, means a queue. Staff stop using it, and the client concludes the feature does not work. Cache aggressively and render something immediately.
Judgement, not documentation — the till may be offline Shops have bad connectivity. Design extensions to degrade to something useful rather than to a spinner, and never make completing a sale depend on your extension succeeding.

What you say to a client/PM

When a client is about to open their first shop Before that goes live I need to check what our integration does with shop sales. They arrive as orders like any other, but they're already complete — the customer has walked out with the item. Right now our warehouse feed would treat them as things to pick. That's a small change, but it has to happen before the shop opens rather than after. Raises a failure before it happens, with the timing that matters. This is the single most valuable habit in integration work.
When asked for a feature on the till We can put it on the till in three ways: a tile on the home screen, a button that opens a full-screen step-by-step, or a small block inside an existing screen. The thing I'd hold us to is speed — there's a customer waiting at a counter, so if it takes two seconds staff will stop using it. Which of the three fits the moment they'd need it? Gives real options in plain terms, and sets a performance constraint using the customer at the counter rather than a millisecond target.

Remember this

  • A shop sale is an ordinary Order at a Location, drawing down that location's InventoryLevel.
  • Retail orders are created and fulfilled at once. Anything expecting "later" breaks.
  • Often no customer and no shipping address. Code that assumes either will fail in one shop only.
  • Three POS targets: Tile (home grid), Action (menu item plus modal), Block (inline).
  • Polaris, Preact, TSX, TOML, native rendering, identical on iOS and Android.
  • Performance is a correctness requirement — there is a queue of customers.
  • Confirm POS Lite versus Pro and plan requirements before promising a feature. Commercial tiers move.

If you remember one thing: a retail order arrives already finished — tell every downstream system that before the first shop opens.
