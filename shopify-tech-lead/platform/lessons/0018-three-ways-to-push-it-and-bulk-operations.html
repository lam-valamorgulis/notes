Three ways to push it, and bulk operations

One at a time, a spreadsheet, or a job. The third one is the only one that scales.

Your win today. You can pick the right import route from the record count alone, and you know the five limits that decide whether a bulk job will finish.

How it works

Derive it: what does volume change?

Writing one record is a request. Writing 40,000 is a schedule, because the rate limit is a budget over time. So the routes are not three styles — they are three different answers to "how do I spend a budget?"

CSV is a merchant tool. It exists so a shop owner can update prices in a spreadsheet. It is not an integration route, and treating it as one means giving up error visibility and control.

What I did not verify today The specific CSV import rules — the file size cap, that Handle is the match column, whether blank columns overwrite while omitted ones do not, and whether an import can be cancelled — live in Shopify's merchant help documentation rather than on shopify.dev, and I did not re-check them for this Lesson. Verify them there before relying on any of it, and prefer a bulk operation regardless.

The bulk flow, and where people stop too early

1. stagedUploadsCreate reserve a slot → URL + form parameters 2. POST the JSONL the `file` field goes LAST in the form 3. bulkOperationRunMutation mutation passed as a STRING + stagedUploadPath 4. wait poll bulkOperation(id:) [2026-01+] or subscribe to bulk_operations/finish 5. DOWNLOAD THE RESULTS ← most people stop at step 4

Step 5 is not optional. COMPLETED means the job ran to the end, not that the rows worked. Per-line userErrors exist only in the results file at url. An import that "completed" with 4,000 silent row failures is indistinguishable from a success unless you download and count.

Verified 2026-08-23: the staged-upload flow, the 100 MB JSONL cap, the 24-hour limit, the single-connection-field restriction, five concurrent bulk mutations on 2026-01 and higher against one of each type before, bulkOperation(id:) versus currentBulkOperation, the bulk_operations/finish webhook option, and bulkOperationCancel — Bulk import data with the GraphQL Admin API. The 250-item input array limit — Shopify API limits.

The docs contradict themselves — test it yourself The bulk-import guide's argument table lists "Valid values: productCreate, collectionCreate, productUpdate, productUpdateMedia" for the mutation argument. The Limitations section on the same page says you can supply any Admin API mutation except the two bulk ones. Both cannot be true, and productSet — the upsert you actually want — is not in the four-value list.

Settle this by running one product through a bulk operation on your own Dev store, not by reasoning about it. If productSet is refused, fall back to productCreate for the first load and productUpdate afterwards, keeping your own mapping so you know which is which.
Answer before reading on Your bulk import reports status: COMPLETED, objectCount: 40000, and no errors anywhere in your logs. How many products are in the store?

Unknown. objectCount counts objects processed, not objects succeeded, and every row can fail on its own with a userError that appears only in the results file. So the honest answer is that you cannot tell from any of those three signals — you have to download the results and count successes. This is the same lesson as the reconciliation Chapter in Track 2: every "green" indicator here measures effort, not outcome.

Where it hurts

Costs money — treating COMPLETED as success Thousands of silently failed rows, and a client told the import worked. The gap is discovered by a customer or by a reconciliation weeks later, when the cause is much harder to trace.
Costs money — a CSV import for an integration No per-record error visibility, no control over pacing, and rules that differ from the API's. A route designed for a human doing it once, used for a machine doing it nightly.
Fails with no error — the file form field out of order It must be last in the multipart form. Earlier and the upload is rejected or wrong, with an error that points nowhere near the cause.
Fails with no error — a JSONL that grew past 100 MB productSet variables with every variant, option and metafield are far bigger than the source records. Count bytes while writing and chunk, rather than discovering the cap at 99%. Chunking is cheap now that five operations can run at once.
Two connection fields in the mutation Only one is allowed. A selection set asking for both variants and media is rejected. Keep the selection to the id and the errors.
A job that could take more than 24 hours It is stopped and marked failed, with no warning at hour 23. If that is even conceivable, the job is too big. Split it.
Judgement, not documentation — reuse the results file The results JSONL contains the created ids next to your input. That is your mapping table for free, and the cheapest moment to record it. Discard the file and you will pay for those ids again with a lookup pass.

What you say to a client/PM

When asked how long an import takes The upload is quick; the queue on Shopify's side is what takes time, and I won't have a real number until I've run it once at your volume. What I can tell you is that it's restartable and that I'll give you a count of what succeeded and what didn't — because a job finishing isn't the same as every row working. Refuses a made-up number, offers restartability, and sets the expectation that there will be a failure list.
When someone suggests just using a CSV That's the right tool if you're doing it by hand occasionally. For something we run repeatedly I'd rather use the API route, because it tells me exactly which rows failed and why. With a spreadsheet import, a bad row tends to disappear quietly, and we find out from a missing product. Respects the suggestion, then distinguishes it by error visibility rather than by sounding more technical.

Remember this

  • Three routes: one at a time, CSV, bulk. CSV is a merchant tool, not an integration route.
  • Five steps, and step 5 is downloading the results. Per-line errors live only there.
  • COMPLETED and objectCount both measure effort, not success.
  • 100 MB · 24 hours · one connection field · 5 concurrent on 2026-01+ · 250-item arrays.
  • The file form field goes last. Out of order fails misleadingly.
  • The docs disagree about which mutations bulk accepts. Test one product; do not reason.
  • Keep the results file — it is your mapping table for free.

If you remember one thing: the import is not finished until you have downloaded the results and counted them.

Ask questions. Then "next" for the throttle that only starts at half a million.
