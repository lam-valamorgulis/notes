Track 1 · P5 · Lesson 5 · core

Bundles and cart transform Functions

One line becomes several — so price and inventory stop matching what your sync wrote.

Your win today. You know the three ways a bundle can be composed, and why a bundle silently invalidates a price reconciliation that was passing yesterday.

How it works

Derive it: what is a bundle, really?

A customer buys "the shampoo and soap set". But the warehouse does not stock a set — it stocks shampoo and it stocks soap. So a bundle is a thing that exists at the moment of buying and does not exist at the moment of picking.

Which means something has to translate between them. Somewhere between the customer clicking and the warehouse packing, one line has to become two.

That translation is the whole subject, and it is where your integration breaks — because your sync wrote one price against one product, and by the time checkout has finished there are two lines with different numbers.

Three ways a bundle gets composed

Shopify composes bundles during calculation in two shapes — expand and merge — and the expand shape comes from two different sources. So there are three cases, and they are named in the API:

NameWhat happensWhere it comes from
BUNDLES_STATIC_EXPANDA parent variant expands into its component linesA fixed bundle definition
BUNDLES_DYNAMIC_EXPANDA parent variant expands into component linesA cart transform Function's expand operation
BUNDLES_DYNAMIC_MERGESeparate lines are merged into one bundle lineA cart transform Function's merge operation
EXPAND cart: [ Hair & Skin Bundle x1 ] after: [ Shampoo x1 ] [ Soap x1 ] one line became two MERGE cart: [ Shampoo x1 ] [ Soap x1 ] after: [ Hair & Skin Bundle x1 ] two lines became one Either way: what the customer chose is not what the warehouse picks, and the prices are recomputed in between.

Notice that expand and merge run in opposite directions but cause the same problem for you: the lines that come out are not the lines that went in.

The fixed kind: an async operation, not a mutation

A fixed bundle is created with productBundleCreate. The part people miss is that it does not return a product — it returns a productBundleOperation with an id and a status, which you then poll.

mutation ProductBundleCreate($input: ProductBundleCreateInput!) {
  productBundleCreate(input: $input) {
    productBundleOperation { id status }
    userErrors { message field }
  }
}

The first response comes back with status: "CREATED", which means the operation was created — not the bundle. Same shape as a bulk operation, and the same trap: a clean response is a statement about the request, not about the outcome.

Each component carries a quantity, a productId, and optionSelections naming which options of that component the bundle exposes. If two components both have an option you want to present as one choice — every component has a "scent" — you use consolidatedOptions to map them into a single bundle option.

The Function kind: your code, at checkout, with no network

A cart transform Function is a Function like any other, so everything in P5.3 applies: it runs inside Shopify while a customer waits, it cannot reach anything, it has no logs of its own, and its input query drops metafield values over 10,000 bytes.

Which produces a specific and common design failure: "the Function will check our ERP to decide what goes in the bundle". It cannot. Anything it needs must already be in Shopify before the customer arrives.

Verified 2026-08-23: the three composition names (BUNDLES_STATIC_EXPAND, BUNDLES_DYNAMIC_EXPAND, BUNDLES_DYNAMIC_MERGE), that expand takes a parent variant into component lines and merge takes separate lines into one bundle, the productBundleCreate mutation returning a productBundleOperation to poll, component optionSelections and consolidatedOptions, and that subscription contract calculation needs withMerchandiseCustomizations: true to expand a bundle — Add a product fixed bundle and Edit subscription contracts with bundles.

Answer before reading on Your nightly reconciliation compares every variant's price against the ERP and passes. A finance report says margin is down on bundles. Explain how both can be true.

Because your reconciliation compares the price on the parent variant, and nobody pays that. The bundle's pricing is applied during composition, when the parent expands into components. So you are checking a number that is correct and irrelevant — the same failure shape as B2B price lists in P9.1, where the price lives somewhere other than the variant. Bundles are the next override layer that reconciliation forgets, after markets, price lists and subscription pricing policies.

Where it hurts

Costs money — reconciling the parent variant's price Nobody pays it. The bundle's price is applied when the parent expands. Your check passes forever while margin drifts, exactly like the B2B price-list trap in P9.1.
Fails with no error — inventory against a bundle that does not exist as stock The warehouse holds shampoo and soap, not sets. Writing stock against the parent variant writes a number for something nobody picks, and the real components go unmanaged.
Costs money — designing a Function that checks an external system A cart transform Function is a Function: no network access. "It will look up our ERP to build the bundle" has to become sync-then-read, and finding that out after promising the feature means a redesign.
Fails with no error — treating productBundleCreate as synchronous It returns a productBundleOperation with status: CREATED, meaning the operation exists. Code that reads the bundle immediately finds nothing and concludes the mutation failed.
Fails with no error — the 10,000-byte input-query cliff From P5.3: a metafield value above that arrives as null in a Function input query. A bundle rule stored in a large JSON metafield works in the Admin API and is invisible to the Function.
One set of lines in, a different set out Expand and merge run in opposite directions and both mean the lines leaving checkout are not the lines that entered. Anything downstream matching on line count or line identity will disagree with the order.
Forgetting the flag on subscription contracts Editing a subscription contract that contains a bundle needs withMerchandiseCustomizations: true, or the parent is not expanded and the calculation runs against the wrong lines.
Judgement, not documentation — decide who owns the component list A bundle's components are merchandising; its stock is operations. Those are usually different people and often different systems. Decide which side owns the component list before either starts writing it, or you have created a field owned by nobody — see A3.2.

Say it out loud

Explain this to a beginner

A customer buys one thing: "the shampoo and soap set". Explain why that single purchase makes both the price check and the stock count in your nightly sync wrong.

Say it out loud. Then read on.

Now compare with a plain-words answer

Because the set is not a real thing in the warehouse. Nobody has a shelf of sets. They have shampoo and they have soap, and somebody puts one of each in a box when an order comes in.

So there are two different views of the same purchase. The customer bought one item. The warehouse picks two. And somewhere in between, Shopify turns the one into the two.

The price goes wrong because your sync wrote a price against the "set" — but the customer's actual charge is worked out during that turning-one-into-two step. So you can check the set's price every night, find it perfectly correct, and never once look at what anyone paid.

The stock goes wrong for the mirror-image reason. Your sync wrote a stock number against the set, which is a number for something that does not physically exist. Meanwhile the shampoo and soap — the things that actually run out — had their numbers written by nobody.

So both checks pass and both are looking at a thing that is not what happened. That is why this is dangerous rather than merely annoying: it is a failure that makes your monitoring more confident, not less.

If you used any of these words, try again bundle parent · component variant · cart transform · expand operation · merge operation · SKU decomposition. "Nobody has a shelf of sets" is the explanation. If you reached for "the parent variant is expanded into its components", you have named the mechanism and explained nothing.

Build it

Task · 90 minutes Dev store

Make your own reconciliation pass while the money is wrong.

  1. Create a fixed bundle with productBundleCreate. Poll the operation — do not read the product straight away.
  2. Give the bundle a price that is not the sum of its components.
  3. Buy it. Look at the order lines: the bundle expanded.
  4. Run your price reconciliation. Watch it pass.
  5. Now extend it to compare the price a customer actually paid, and watch it find the gap.

Proof it worked: the first run said everything was correct and the second did not. Add bundles to your ownership table as another price-override layer, after markets, B2B price lists and subscription pricing policies.

The stock half · 45 minutes Dev store
  1. Set stock on the bundle parent to 100 and on one component to 1.
  2. Try to buy two bundles.
  3. Write down which number actually constrained the sale.
  4. Now fix your sync: write stock to the components, and stop writing anything to the parent.

Proof it worked: you can say which number Shopify honoured, from testing rather than reasoning. And your sync no longer writes a stock figure for something that does not exist on a shelf.

Hit the Function walls · 90 minutes Dev store
  1. Build a cart transform Function with an expand operation.
  2. Try to call your own server from inside it. There is no network.
  3. Put the bundle rule in a metafield just over 10,000 bytes. The Function receives null.
  4. Then build a merge operation and watch two lines become one.

Proof it worked: you hit both walls and you have seen composition run in both directions. Now check every downstream consumer that matches on line count — both directions break it.

Remember this

  • A bundle exists when buying and not when picking. Something has to translate, and that is where your numbers break.
  • Three composition names: BUNDLES_STATIC_EXPAND (fixed definition), BUNDLES_DYNAMIC_EXPAND and BUNDLES_DYNAMIC_MERGE (cart transform Function).
  • Expand and merge run in opposite directions and cause the same problem: lines out are not lines in.
  • productBundleCreate is asynchronous. It returns a productBundleOperation to poll; CREATED describes the operation.
  • Reconcile what was paid, not the parent's price. Bundles are a price-override layer, like markets and B2B price lists.
  • Write stock to components, never the parent. The parent is not a thing on a shelf.
  • A cart transform Function has no network access and the 10,000-byte metafield cliff. Everything it needs must already be in Shopify.

If you remember one thing: a bundle makes your price and stock checks pass while both are measuring something nobody bought — so reconcile against what was paid and what was picked.
