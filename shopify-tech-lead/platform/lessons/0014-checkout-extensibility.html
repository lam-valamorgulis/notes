Checkout extensibility

What you may change on checkout, what is permanently closed, and two deadlines you need this week.

Your win today. You know which parts of checkout are open to you, and you can warn a client about two dated cut-offs before they find out the hard way.

How it works

Two dated cut-offs, checked today

Read these two dates first 1 · Script tags on the Thank you and Order status pages. Sunset for Plus stores on 28 August 2025, and for non-Plus stores on 26 August 2026.

2 · React-based checkout UI components. API version 2025-07 is the last version to support them. Later versions use Polaris web components, and you are blocked from updating your extension after 1 October 2026 if you have not migrated.

Both dates are close enough to act on. If you inherit any checkout customisation, establish which side of them it sits on before you touch anything else.

And the broader position: checkout.liquid is now unsupported for the Information, Shipping and Payment steps, and checkout.liquid plus additional scripts were sunset for the Thank you and Order status pages on 28 August 2025. Stores still using it there must move to Shopify Extensions in Checkout.

There is a helpful thing most people do not know about: the Shopify admin contains a report identifying a store's current checkout customisations, with guidance on mapping each one to Extensions in Checkout. On an inherited store, that report is the fastest possible audit.

Derive it: why did Shopify close the checkout?

A checkout is where money moves. Arbitrary merchant Liquid and arbitrary third-party scripts on that page means arbitrary code between a customer and their card details — unauditable, unbounded in performance cost, and impossible for Shopify to guarantee.

So the model changed from "edit the page" to "declare where you want to appear and what you want to do". You get defined slots and a defined API, and Shopify keeps the guarantees. Feynman version: you no longer get to rewrite the shop's cash register — you get to bolt approved attachments onto it.

Structure of a checkout UI extension mirrors POS extensions: targets (where you appear), target APIs (what data you can reach), and web components (what you render). Scaffold with shopify app generate extension --template checkout_ui.

One dependency worth knowing: a merchant with checkout.liquid customisations must upgrade to Extensions in Checkout before they can use Function APIs. So an old checkout blocks new server-side work, not just new UI work.

Answer before reading on You inherit a non-Plus store whose Order status page has a custom tracking script added years ago, and the client wants a new custom discount rule. What do you tell them, and in what order?

The urgent thing first: that script stopped being supported for non-Plus stores on 26 August 2026, so it either has already stopped working or is about to. That is not a nice-to-have, it is a live breakage — and it is why nothing else should be scheduled ahead of it. Second, the discount rule needs Functions, and a store still carrying checkout.liquid customisations must migrate to Extensions in Checkout before it can use Function APIs. So the migration is not a competing priority to their request — it is a prerequisite for it. Run the admin's customisation report first to see the full list.

Where it hurts

Costs money — a script-tag customisation past its sunset Order tracking, analytics or a post-purchase upsell that simply stops. Nothing errors on the merchant's side; the feature is just gone, and revenue attributed to it disappears quietly.
Costs money — a React-based extension not migrated After 1 October 2026 you are blocked from updating the extension. So the first urgent fix you need to ship is the moment you discover it, which is the worst possible timing.
Fails with no error — checkout.liquid blocking Function APIs A client asks for a custom discount and the work looks unrelated to their old checkout. It is not: the migration is a prerequisite. Discovering this mid-sprint turns a small feature into a project.
Promising checkout-step UI on a non-Plus store Information, shipping and payment steps are Plus only. The Thank you and Order status pages are not. Get the plan and the exact page before you agree to anything.
Building on post-purchase without checking access It is in beta: unrestricted on a dev store, but a live store needs an access request. So it works perfectly in development and cannot ship. Request access before you build.
Judgement, not documentation — checkout is not a place for third-party latency Whatever the platform permits, an extension that waits on an external service is sitting between a customer and their payment. Apply the rule from A4.1: fail open on information, fail closed on a promise, and never retry inside checkout.

Say it out loud

Explain this to a beginner

Shopify used to let developers change the checkout page freely, and stopped. Explain why a company would deliberately take capability away from its own developers.

Say it out loud. Then read on.

Now compare with a plain-words answer

Because checkout is where the money happens, and it was the one page anybody could put arbitrary code on.

Think about what that means at scale. One badly written addition slows the page down, and a slower checkout means fewer completed purchases across every shop that has it. One broken addition and people cannot pay at all. And because the code was custom per shop, Shopify could not improve checkout without risking breaking thousands of shops in ways it could not see.

So they closed it and reopened it as a set of specific, sandboxed slots. You can add your thing, but only in defined places, and Shopify keeps control of the page around it. You lose freedom; the whole platform gets faster and harder to break.

The part that matters to you is that this came with calendar deadlines. Old customisations stop working on published dates. So on any shop you inherit, the first thing to do is find out what checkout customisation it already has and when that stops working — before you promise anything at all. There is a report in the admin that tells you.

If you used any of these words, try again extensibility · sandbox · sunset · deprecation · UI extension target · Checkout Extensibility. "It was the one page anyone could put arbitrary code on, and it is where the money happens" explains the whole decision.

Build it

Task · 20 minutes any store you inherit

This is the single highest-value twenty minutes in the chapter, and almost nobody does it.

  1. Open the admin's checkout customisation report on a store you did not build.
  2. Write down every customisation it lists.
  3. Next to each, write the date it stops working. Script tags on Thank you and Order status: 28 Aug 2025 for Plus, 26 Aug 2026 for non-Plus. React checkout components: 2025-07 is the last supporting version, blocked from updating after 1 Oct 2026.
  4. Mark anything using checkout.liquid, because that also blocks Function APIs until it is migrated.

Proof it worked: you have a dated list. If any date is in the past, you have found live broken tracking that the client believes is working — and you found it before quoting, not after.

Then build one · 45 minutes Dev store

Add one checkout UI extension to a Thank you page — available on every plan except Starter, so you do not need Plus to practise this.

Proof it worked: your extension renders on Thank you, and you can state from memory which surfaces need Plus (the checkout steps) and which do not (Thank you and Order status).

Remember this

  • Script tags on Thank you / Order status: sunset 28 Aug 2025 for Plus, 26 Aug 2026 for non-Plus.
  • 2025-07 is the last API version supporting React checkout components. Blocked from updating after 1 Oct 2026.
  • checkout.liquid is unsupported for information, shipping and payment; sunset on Thank you and Order status from 28 Aug 2025.
  • The admin has a report listing a store's checkout customisations. Run it on any inherited store.
  • Checkout-step UI is Plus only. Thank you and Order status are all plans except Starter.
  • Old checkout.liquid customisations block Function APIs. The migration is a prerequisite, not a competing task.
  • Post-purchase is in beta — free on a dev store, access request for a live one.

If you remember one thing: on any inherited store, run the admin's checkout customisation report before you promise anything — there are dated cut-offs already behind us.
