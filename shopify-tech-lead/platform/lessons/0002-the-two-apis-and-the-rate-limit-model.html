The two APIs and the rate limit model

REST is legacy. And the limit is a budget you spend, not a number of requests you make.

Your win today. You can explain why "how many requests per second?" is the wrong question, and answer the right one — which is "what does my query cost?"

How it works

Which API, settled

DateWhat happened
1 October 2024The REST Admin API became a legacy API. New feature work goes to GraphQL
1 April 2025All new public apps submitted to the App Store must be built exclusively with the GraphQL Admin API

So the decision is made for you: build on the GraphQL Admin API. REST still works and you will meet it in older codebases, but nothing new should be written against it.

Verified 2026-08-23 — the deprecation changelog, and the "legacy as of October 1, 2024" banner on the REST Admin API reference. That same REST resource is genuinely useful once: for a custom app it lists the deprecated calls your app has made in the past 30 days.

Derive the rate limit: why counting requests cannot work

Imagine limiting an API by requests per second. One request asks for a product's title. Another asks for 250 products, each with 100 variants, each with inventory at 10 locations. Counting both as "one request" is absurd — the second is thousands of times more work.

So the limit is on cost, not count. Each field has a point value, and your query's cost is the sum of what it could return.

Two consequences fall straight out of that table. Asking for more scalar fields on an object you already fetched is free — so fetch generously within an object. And first: 250 costs far more than first: 10, so page size is your main cost lever.

Every response tells you where you stand

"extensions": {
  "cost": {
    "requestedQueryCost": 3,
    "actualQueryCost": 3,
    "throttleStatus": {
      "maximumAvailable": 1000,
      "currentlyAvailable": 997,
      "restoreRate": 50
    }
  }
}

That arrives on successful responses, which is what makes prevention possible rather than just recovery. Read currentlyAvailable and slow down before you are refused.

REST, for when you meet it

REST counts requests, using a leaky bucket: 40 requests with a 2/second leak, and ×10 for Plus — 400 with 20/second. Over the limit returns 429 plus a Retry-After header saying how many seconds to wait. Current usage is in the X-Shopify-Shop-Api-Call-Limit header as 32/40.

The difference that catches people REST signals throttling with 429. GraphQL signals it with 200 OK and a THROTTLED error in the body. Code ported from REST to GraphQL that checks only the status code silently stops noticing throttles. See A2.3.

Verified 2026-08-23: cost-based limiting, the field cost table, the requested-versus-actual refund, the 1,000-point single-query ceiling, the 250-item input array limit, and the 500,000-variant / 10,000-per-day throttle with the Plus exemption — Shopify API limits. REST bucket sizes, leak rates, the ×10 Plus multiplier, Retry-After and the call-limit header — REST Admin API rate limits.

Answer before reading on Your query asks for first: 250 products with variants and inventory levels, and it fails immediately with a cost error. You wait a minute and retry. What happens, and what should you do?

It fails again, identically. The 1,000-point single-query ceiling is checked before execution against the requested cost, so it is not about how full your bucket is — waiting changes nothing. The fix is to make the query smaller: fewer items per page, or fewer nested connections. This distinction matters because "throttled" and "too expensive" both look like a rate-limit problem and only one of them is fixed by patience.

Where it hurts

Costs money — retrying a too-expensive query A query over 1,000 points fails at every bucket level and on every plan. Retrying it forever spends real time and never succeeds. Reduce the page size instead.
Fails with no error — porting REST error handling to GraphQL Your REST code checked for 429. The GraphQL version returns 200 when throttled, so the check never fires and throttled calls are silently treated as successes. Data quietly does not arrive.
Fails with no error — over-asking and paying for it The bucket must hold the requested cost before the query runs. A query selecting fields you do not use reserves capacity you then cannot spend, and the refund arrives too late to help the call that was queued behind it.
Building on REST today It is legacy as of October 2024, and new public apps have been GraphQL-only since April 2025. Anything new written on REST is a migration you have scheduled for yourself.
Assuming a single restore rate Restore rate scales with plan tier. A limiter with a hardcoded number either throttles a Plus store unnecessarily or over-runs a Basic one. Read restoreRate from the response.
Judgement, not documentation — the bucket is per app and store So many workers on one store share one bucket, while many stores each have their own. A global limiter is a bottleneck; a per-process one over-runs a store. See A3.7.

What you say to a client/PM

When asked "how many API calls per second can we do?" It doesn't work as a number of calls. Shopify gives us a budget and charges each request by how much data it asks for, so one big request can cost as much as a hundred small ones. What that means practically: the way to go faster is to ask for less, not to ask more often. And your plan sets the budget size. Corrects the mental model and immediately gives the lever that actually works. Ends the "can't we just parallelise it?" conversation early.
When someone proposes a quick fix on REST I'd rather not add new REST code. Shopify marked it legacy in October 2024, and new apps have had to be GraphQL-only since April 2025 — so anything we write there is work we'll redo. It's the same effort in GraphQL today. Two dates make this unarguable. Vague "it's deprecated" invites a debate.

Remember this

  • Build on GraphQL. REST is legacy since 1 Oct 2024; new public apps GraphQL-only since 1 Apr 2025.
  • The limit is a cost budget, not a request count. Scalars are free; objects cost 1; a mutation costs 10.
  • Connections are sized by first. Page size is your main cost lever.
  • The bucket must hold the requested cost before running, and refunds the difference after.
  • 1,000 points is a hard ceiling per query, checked before execution. Waiting never fixes it.
  • Input arrays cap at 250 items. The extra variant throttle starts at 500,000 variants; Plus is exempt.
  • REST throttles with 429; GraphQL throttles with 200. Read the body.

If you remember one thing: to go faster, ask for less — not more often.
