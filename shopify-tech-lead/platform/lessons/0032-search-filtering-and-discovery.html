Track 1 · P10 · Lesson 1

Search, filtering and discovery

Filters must be created in the admin before any code can use them. That surprises everyone.

Your win today. You know why a filter you can see in the data does not appear on the storefront, and you can explain AND-versus-OR filter logic to a client who thinks their filters are broken.

How it works

Derive it: what does a filter need to know?

To filter a collection you need a field, its possible values, and which of them a customer picked. Two of those three are merchant decisions, not code decisions — which field is worth filtering on, and how to present it. So Shopify puts filter definition in the admin:

The thing that catches people Filters must be created in the Shopify admin before they can be applied. Having the data is not enough.

So "we have colour on every product but the colour filter doesn't show" is almost never a code problem — nobody created the filter. Check the admin before you debug anything.

Two methods, and one is legacy in practice

MethodVerdict
Storefront filteringRecommended. Merchants create filter groups from existing product data. Works on collections and search results
Tag filteringFiltering a collection into subsets using product tags. Older approach

Storefront filters can be built on: availability, category, price, product tags, product type, vendor, variant options, and metafields.

That last one connects straight to P2.1: a metafield with no definition is not filterable. So "we can't filter on fabric" and "the integration wrote metafields without definitions" are the same bug seen from two ends.

AND between filters, OR within one

colour = red, blue → red OR blue size = M → and M result: (red OR blue) AND (M) ── never "red AND blue". a product is not two colours.

This is the single most common client confusion about filters. "Why do I get 40 results when I picked two colours?" — because picking two colours widens the result, it does not narrow it. Applied filters appear in the URL as parameters, which makes them shareable and testable.

Storefront search, and the parameters worth knowing

ParameterDoes
qThe query. The only one needing user input
typeRestrict to certain resource types
unavailable_productsWhere sold-out products appear. Defaults to last, and the default is changeable in Search Settings in the Search & Discovery app
prefixlast by default — partial match on the final term. "winter snow" also matches "snowshoe", "snowboard". none disables it
sort_byrelevance (default), price-ascending, price-descending
A documentation inconsistency — test this yourself Shopify's own page describes price-ascending as sorting "from high to low" and price-descending as "from low to high". Those descriptions look inverted. The names almost certainly mean what the names say, but do not take either on trust — run both on a Dev store and see. It is a thirty-second check and a customer-visible mistake if you guess.

Also worth knowing: for both price sorts, non-product results are pushed to the end of the results array.

The search form posts to action="/search". Populate that action from the routes object rather than hardcoding it, so multi-language stores get the right URL — the same discipline as market awareness in P5.1. Every parameter except q should be a hidden input.

The app that changes the answers

The Shopify Search & Discovery app lets merchants customise product recommendations and search results. Its settings affect storefront search and the Ajax Product Recommendations API.

That means a merchant can change your search results without touching your code, and there will be no trace of it in your repository. When results look wrong, check that app's settings before reading any Liquid — the same reflex as checking Flow in P5.4.

Answer before reading on A client says: "our integration writes a fabric field on every product, but customers can't filter by fabric." Name the two things to check, in order.

1 · Does the metafield have a definition? An undefined metafield is stored but not filterable — the exact trap in P2.1. If the integration wrote values without creating definitions, the data is there and unusable, and this is the likely answer.

2 · Has the filter been created in the admin? Even a properly defined metafield is not a filter until a merchant makes it one. Nothing in code creates it.

Both are configuration, and neither produces an error anywhere. This is why "we have the data" and "customers can filter on it" are two entirely separate statements — and why the answer is usually a ten-minute admin change rather than a build.

Where it hurts

Fails with no error — the filter that was never created The data exists, the filter does not, and nothing errors. Debugging theme code for this wastes a day. Check the admin first.
Fails with no error — undefined metafields cannot be filtered Same root cause as P2.1. An integration that skipped definitions has produced data that can never appear as a filter.
Explaining AND/OR backwards to a client Selecting two colours widens the results. Clients expect narrowing and report it as a bug. Get the explanation right the first time or you will have it three times.
Fails with no error — the Search & Discovery app changing results A merchant can reorder or boost results with no trace in your code, and it also affects the Ajax recommendations API. Results "changing on their own" is usually this.
Trusting the documented sort directions The docs' descriptions of price-ascending and price-descending appear inverted. Test both rather than guessing — this one is visible to every customer.
Hardcoding /search Multi-language stores need the localised route. Use the routes object, exactly as with any other market-aware URL.
Judgement, not documentation — partial matching cuts both ways prefix=last is on by default, so "snow" matches "snowboard". Helpful for discovery, and it produces surprising results on short queries or product codes. If a client searches by SKU, test that specifically — a three-character code with prefix matching can return most of the catalogue.

Say it out loud

Explain this to a beginner

The shop has fabric recorded on every product. Customers still cannot filter by fabric, and nothing is broken. Explain. Then explain why ticking two colours shows more results, not fewer.

Say it out loud. Then read on.

Now compare with a plain-words answer

First part: having the information and offering it as a filter are two separate jobs. Somebody has to go into the admin and say "make fabric a filter". Until then the data sits there, complete and unusable, and nothing errors because nothing is wrong. Developers lose a day in theme code over this. Check the admin first.

(And if the field was never properly declared to Shopify in the first place, it can never become a filter at all — same root cause as the inert field lesson.)

Second part: within one filter, the options are alternatives. Ticking red and blue means "red or blue" — you have asked to see both, so you get more. Across different filters they combine: red plus size medium means "red and medium", which narrows.

Customers expect every tick to narrow, so they report the widening as a bug. Explain it correctly the first time or you will explain it repeatedly.

If you used any of these words, try again faceted search · disjunctive within facet · conjunctive across facets · indexed attribute. "Within one filter the options are alternatives; across filters they stack" is the explanation.

Build it

Task · 45 minutes Dev store + theme
  1. Add a fabric metafield with a proper definition to ten products.
  2. Do not create the filter. Try to filter. Confirm nothing errors and nothing works.
  3. Create the filter in the admin. Try again.
  4. Now add the same data as an undefined metafield on another field and try to make that filterable. It cannot be.
  5. Tick two colours, then colour plus size, and record the result counts.

Proof it worked: you have the counts written down proving OR-within and AND-across, and you produced the "we have the data but cannot filter" state twice — once fixable in the admin, once needing the data rewritten with a definition.

Two things to test rather than trust · 25 minutes Dev store
  1. Sort by price ascending and descending. Look at the actual order. Shopify's own docs describe these two as if inverted, so test rather than believe.
  2. Search a short term and a product code. prefix=last is on by default, so "snow" matches "snowboard" — check what that does to your SKUs.
  3. Open the Search & Discovery app and reorder a result. Confirm your code shows no trace of why.
  4. Confirm your search URL uses the localised route object, not a hardcoded /search.

Proof it worked: you have a dated note on which sort direction does what, and you know to check the merchant's app before debugging your own code when "results changed on their own".

Remember this

  • Filters must be created in the admin first. Having the data is not enough.
  • An undefined metafield is not filterable. Same root cause as P2.1.
  • AND between filters, OR within one. Two colours widens; colour plus size narrows.
  • Filterable on: availability, category, price, tags, product type, vendor, variant options, metafields.
  • prefix=last is the default — partial matching on the final term. Test it against SKUs.
  • Test the price sort directions. The documented descriptions appear inverted.
  • The Search & Discovery app changes results with no trace in your code. Check it first.

If you remember one thing: "we have the data" and "customers can filter on it" are two different statements, and the gap between them is an admin setting.
