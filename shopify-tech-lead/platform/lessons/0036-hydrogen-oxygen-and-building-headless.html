Hydrogen, Oxygen and building headless

The decision lesson is P4.1. This one is what you inherit once the decision goes the other way.

Read P4.1 first, and be honest about this page P4.1 teaches the decision, and the decision is usually "stay in the theme". This Lesson covers what changes when it genuinely is headless — at the level of consequences, not implementation. Framework specifics move fast and are not verified here; check the current Hydrogen documentation before building.
Your win today. You know which platform features you lose the moment the storefront leaves Liquid — and which of them the client has not thought about.

How it works

Derive it: what is actually different?

One thing: you render the page instead of Shopify. Every consequence follows from that single change.

THEME HEADLESS Shopify renders YOU render Shopify hosts + CDN you host (Oxygen, or anywhere) Liquid objects give you data Storefront API gives you data theme editor = merchant control you build the editing story theme app extensions work they mostly do not checkout is a link away checkout is a HANDOFF you must get right

The Storefront API is not the Admin API

This trips people who arrive from integration work. They are different APIs with different purposes, and the distinction matters for a reason that has already appeared in this Course:

Admin APIStorefront API
ForManaging the storeBuilding a buying experience
Called fromYour serverThe storefront, often the browser
SeesEverything you have scopes forWhat is published to that channel

And a verified consequence from P7.3: tax and duty fields were deprecated in the Storefront Cart API as of 2025-01, because they need the full checkout context. So a headless build cannot show a reliable tax figure in its own cart either — the constraint follows you.

What you lose, ranked by how much it hurts

LostConsequence
Theme app extensionsThe largest one. Reviews widgets, upsells, store locators, loyalty panels — each becomes custom work, and then permanent maintenance. Enumerate the client's installed apps and price the replacements before quoting
The theme editorMerchant self-service disappears unless you build an editing story. It competes with something Shopify improves for free
Hosting and scalingYours now, including the sale-day spike
Search, filtering, recommendations out of the boxYou wire them up — and remember from P10.1 that filters must still be created in the admin first
Liquid's market awarenessThe routes object handled localised URLs for you. Multi-market routing is now your problem

What stays Shopify's

Checkout. That is the important one — you do not build checkout, you hand off to Shopify's. Which means every constraint in P5.2 still applies: the Plus gate on checkout-step extensions, the sunset dates, the checkout.liquid prerequisite for Function APIs. Going headless does not free you from checkout rules; it only changes what leads into it.

Also still Shopify's: tax calculation, payment processing, order records, inventory, and every limit in the rate limits card.

The two questions that decide whether it will survive

QuestionWhy it is fatal if the answer is no
Is there a permanent front-end developer?A custom storefront is a dependency, not a build. Quarterly API versions, security updates, and every app replaced by hand. Without an owner it freezes within about a year
Can the merchant change content without a developer?If not, every copy change becomes a ticket. The theme editor was doing that for free
Answer before reading on A client is already headless and asks you to add a reviews widget "like the one on their old theme". What is the honest answer?

That the widget was almost certainly a theme app extension, and those do not work here — so this is not installing an app, it is a build.

Concretely: the reviews app can probably still store and serve the review data through its API, but the part that rendered on the page was theme-side. So the work is a custom component reading that app's API, styled to match, handling its empty and error states — and then maintained by you forever, including when that app changes its API.

Then say the sentence that is genuinely useful: "and this will happen again with the next app. It's worth listing which apps you rely on for storefront display, because each one is this same conversation." That turns one ticket into a planning conversation, which is the tech-lead move.

Where it hurts

Costs money — not pricing the app replacements Theme app extensions mostly stop working. Every storefront-rendering app becomes a custom build plus permanent maintenance. Enumerate the installed apps before quoting.
Costs money — no permanent front-end owner The build lands, the agency leaves, and nothing changes for two years because every edit needs a developer. The merchant ends up worse off than with a theme.
Fails with no error — headless "for speed" From P10.2: the scripts and images follow you, and you add a hosting layer to tune. Measure first; the cause is usually apps.
Fails with no error — expecting tax in the Storefront cart Deprecated as of 2025-01. The constraint is not a theme limitation, so headless does not escape it.
Assuming checkout rules relax Checkout is still Shopify's. Plus gates, sunset dates and the checkout.liquid prerequisite all still apply.
Forgetting the Storefront API sees only published products It is channel-scoped. A product missing from a headless storefront is often a publication or catalog question — see P9.1 — not a query bug.
Judgement, not documentation — inherit before you recommend If you are asked to take over an existing headless build, spend a day finding out who maintained it and when it was last upgraded. An unowned custom storefront on a retired API version is a much bigger commitment than the brief will say, and the honest answer may be that it needs replacing rather than extending.

Say it out loud

Explain this to a beginner

In one sentence: what is actually different when you build a Shopify shop headless? Then name the thing that stays Shopify's no matter what.

Say it out loud. Then read on.

Now compare with a plain-words answer

One thing changes: you draw the pages instead of Shopify drawing them. Every other difference is a knock-on effect of that.

Because you draw the pages, apps can no longer put their own bits on them — so they stop working. Because you draw the pages, the shop owner loses the visual editor. Because you host the pages, you own the hosting.

And the thing that does not change: checkout is still Shopify's. Every rule about what you can and cannot do at checkout applies exactly as before. Every feature that needs the top plan still needs it. Every deadline for retiring old checkout customisation still lands on you. People expect headless to be an escape from those rules and it is not.

One more that catches people: the interface a headless site reads from only sees products that have been published to it. So "the product is missing from our new site" is usually a publishing question, not a broken query.

If you used any of these words, try again rendering layer · edge runtime · channel scoping · publication · decoupled architecture. "You draw the pages instead of Shopify" is the whole thing, and everything else follows from it.

Build it

Task · 90 minutes Dev store

Build the smallest possible headless page and hit the three walls on purpose.

  1. Render one product from the Storefront API. Nothing else.
  2. Wall one: unpublish that product from the channel your site uses. The query returns nothing. Confirm it is not a query bug.
  3. Wall two: try to read tax or duty from the cart. Those fields were deprecated as of 2025-01. Confirm headless does not escape it.
  4. Wall three: install any app that renders into the theme. Confirm it does not appear on your page, and write down what rebuilding it would take.

Proof it worked: you hit all three walls yourself. Now you can answer "can we go headless?" from experience rather than from a blog post — and the third wall is the one that decides the budget.

Before taking over someone else's headless build · 1 day no store needed

Find out two things and write them down: who maintained it, and when it was last upgraded.

Proof it worked: you have dates. An unowned custom storefront is a liability you are about to inherit, and one day of asking is cheap compared with finding out later.

Remember this

  • One change: you render instead of Shopify. Everything else is a consequence.
  • Theme app extensions mostly stop working. The biggest and least expected cost.
  • Checkout stays Shopify's. Every checkout rule and Plus gate still applies.
  • Storefront API is channel-scoped. A missing product is often a publication question.
  • Tax in the Storefront cart was deprecated in 2025-01. Headless does not escape it.
  • Two survival questions: a permanent front-end owner, and merchant self-service.
  • Headless for speed is usually wrong. Measure first — see P10.2.

If you remember one thing: the expensive part of headless is not the build, it is replacing and then maintaining every app that used to render itself into the theme.
