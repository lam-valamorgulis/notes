Shopify Functions

Your logic, running inside Shopify's backend. No URL, no server, no network call.

Your win today. You can explain what a Function is by what it is not — not a webhook, not an API call, not something you can reach — and why that difference decides where you can use one.

How it works

Derive it: why could a webhook never do this?

Shopify needs to decide a discount while a customer sits in a cart. Could it ask your server? Only by making the customer wait on your latency and your uptime, on the most important page in the funnel. For a decision that must happen every time, in the request path, that is unacceptable.

So the model inverts. Instead of Shopify calling out to you, you ship code into Shopify and Shopify runs it. No network hop, no uptime dependency, no timeout.

WEBHOOK FUNCTION Shopify ──HTTP──▶ your server your code lives INSIDE Shopify after the fact during the customer journey you can retry there is no retry — it runs or it doesn't your uptime matters your uptime is irrelevant you can log to your system you cannot attach a debugger

Shopify's own wording is worth remembering: "Shopify Functions are never invoked directly by URL or otherwise. Shopify invokes them as needed within the customer journey." There is no endpoint. That single sentence explains every constraint below.

Anatomy: an input query, then logic

1. run.graphql you declare what data you need │ ▼ 2. Shopify runs that query and hands you input.json │ (shape matches your query exactly) ▼ 3. your logic pure transformation, no I/O │ ▼ 4. output shape defined by the Function API schema

Both the input and output shapes come from the schema of a Function API — one per capability. Each target your extension implements can have its own input query, so you request only what that target needs.

Language: anything that compiles to WebAssembly. Rust is recommended and strongly preferred — which in practice means the tooling, examples and performance guidance assume it. JavaScript compiles too, and you should expect a rougher path.

The lifecycle, and who configures what

StepWho
Write and deploy an app containing the functionYou
Install the app and configure the function — create a discount from your new typeThe merchant
Execute it during the customer journeyShopify

The middle row matters for design. You are not shipping a discount; you are shipping a discount type the merchant then configures. So your function must read its configuration from somewhere — and that is what metafields, app-owned metaobjects, and input variables are for in an input query.

Answer before reading on A client wants a discount that depends on the customer's loyalty tier, which lives in an external loyalty system. Can a Function do it?

Not by asking the loyalty system — a Function has no network access and cannot call out. So the design has to move the data before the moment of decision: your app syncs each customer's tier into a metafield, and the Function's input query reads that metafield. The tier is then slightly stale, and that is the trade-off you must name to the client. And watch the size limit: a Function input query does not return metafield values larger than 10,000 bytes — it receives null instead, while the Admin API still returns the value in full. So keep whatever the Function reads small and deliberate.

Where it hurts

Costs money — designing a Function that needs external data live There is no network access. Discovering this after committing to a feature means redesigning it as a sync-then-read, which changes the freshness guarantee you promised.
Fails with no error — the 10,000-byte input cliff Metafield values above that limit arrive as null in a Function input query. Stored fine, returned fine by the Admin API, invisible only to the Function, only for large values. Small test products pass; real ones do not.
Fails with no error — no debugger, no logs of your own It does not run on your infrastructure, so the tools you reach for first are absent. Keep functions small and pure, and put anything you need to observe on the configuration side where you can see it.
Forgetting the merchant configures it You ship a type, not an instance. A function with its rules hardcoded is one no merchant can adjust, and every change becomes a deploy. Read configuration from metafields or input variables.
A checkout.liquid store cannot use Function APIs Merchants with old checkout customisations must migrate to Extensions in Checkout first. That makes the migration a prerequisite for a feature that looks unrelated.
Judgement, not documentation — over-asking in the input query The input query runs before your logic every time, on every affected customer interaction. Requesting data you do not use is work Shopify does on every cart. Trim run.graphql to exactly what the logic reads, and keep the per-target queries genuinely separate.

What you say to a client/PM

Explaining what a Function is, without jargon Normally when something happens in your store, Shopify tells our server and our server responds. This is the opposite: we put a small piece of our logic inside Shopify, and Shopify runs it itself. That means it's instant and it can't be affected by our server being slow or down — which matters, because this runs while a customer is checking out. Explains it by contrast with the thing the client already understands, and lands on the benefit they care about.
When the rule needs data from another system One constraint worth knowing: that logic runs inside Shopify and can't reach out to your loyalty system while the customer is there. So we copy each customer's tier into Shopify ahead of time and the rule reads it from there. Practically that means a tier change takes a few minutes to affect discounts rather than being instant. Is that acceptable? States the constraint, gives the workaround, names the exact cost in the client's terms, and asks. Four sentences and no jargon.

Remember this

  • Your code runs inside Shopify. Never invoked by URL — Shopify calls it during the customer journey.
  • No network access, no retry, no logs of your own. Keep functions small and pure.
  • Anatomy: run.graphql input query → logic → output, both shapes from a Function API schema.
  • Any language compiling to Wasm; Rust is strongly preferred.
  • You ship a type, the merchant configures an instance. Read config from metafields, app-owned metaobjects or input variables.
  • Input queries drop metafield values over 10,000 bytes — the Function gets null.
  • All plans except Starter, but a checkout.liquid store must migrate first.

If you remember one thing: a Function cannot reach anything — so any external data it needs must already be inside Shopify before the customer arrives.
