Metafields, definitions, and the cost of skipping them

You can write a metafield without a definition. Almost everything then quietly stops working.

Your win today. You can answer "can Shopify store this?" for almost anything a client asks — and you will never again write a metafield without its definition.

How it works

Derive it: what does a platform do with a field it does not know about?

A metafield is a custom field on a Shopify resource. You can create one with a namespace, a key and a value, and it will be stored. Ask the first-principles question: what can Shopify do with a value whose meaning it has never been told?

Almost nothing. It cannot render an editor, because it does not know the type. It cannot validate, because it has no rules. It cannot offer it as a filter, because it does not know the values are comparable. So the value sits there, correct and inert.

The definition is where you tell Shopify what the field means. That is the whole idea:

Without a definitionWith a definition
StoredYesYes
Readable by APIYesYes
Editable in the adminNoYes, with a proper editor
ValidatedNoYes, by type and rules
Usable for filtering, smart collectionsNoYes, via capabilities

Feynman version: a metafield without a definition is a note in a language nobody has taught the building. It is stored perfectly and useful to nobody but the code that wrote it.

Found on a real store This Course sampled a live Plus store and found 169 metafield definitions — 85 on products, 84 on variants. Every one reported validationStatus: ALL_VALID. So a well-run store does define them. The failure mode below is what an integration does when nobody checks.

Four kinds of ownership, and you must know which you are writing

KindNamespaceWho controls it
Merchant-ownedAny non-reserved, e.g. customThe merchant and every installed app
App-ownedThe reserved $app (GraphQL) / app (TOML)Your app. View-only in the admin by default
Shopify-reservedshopify-- and standard definitionsShopify controls the structure; the merchant owns the values
App-dataTied to your app installationYour app. Completely hidden from the admin

The practical rule: put your app's own bookkeeping in the app-reserved namespace, so nothing else can change it. Put anything the merchant should edit in a merchant-owned namespace. And app-owned definitions can only be declared in the app-reserved namespace, which is deliberate — it lets Shopify guarantee the same shape on every shop your app is installed on.

One number I could not settle. The definitions page lists an app-scoped limit of 128 metafield definitions per owner type. The limits page says each app can create up to 256 per resource type, and the same for merchants. These may be describing declarative-versus-API definitions, but neither page says so. Do not design against either number without testing it on your own store. Reported here rather than resolved, because guessing which page is right is exactly how the variant-throttle mistake happened.

Answer before reading on Your integration writes a 40 KB JSON blob of product specifications into a metafield, and a Shopify Function needs to read one value from it to apply a discount. It works in testing with small products. What happens on the real catalogue?

The Function receives null. Shopify Functions input queries do not return metafield values larger than 10,000 bytes — the value is still stored, and the Admin API still returns it in full, so every check you make from outside says the data is fine. Only the Function sees nothing, and only for large products. That is a size-dependent, silent, environment-specific failure: the worst combination available. Keep anything a Function reads well under 10 KB, and put the bulk elsewhere.

Where it hurts

Costs money — writing metafields with no definitions Your integration writes them, the API reads them back, and every test passes. Then the merchant cannot see or edit the data, it is not filterable, and nothing validates it. Months later the fix means creating definitions and reconciling every existing value against the new type.
Fails with no error — the 10,000-byte Function cliff As above. The value is stored, the Admin API returns it, and the Function gets null. Small products work, big ones do not, and nothing logs anything.
Fails with no error — analytics_queryable in TOML Shopify's own documentation states that capabilities.analytics_queryable in shopify.app.toml deploys without an error but the capability is not set. You ask for a feature, the deploy succeeds, and you do not get it. Verify capabilities after deploy rather than trusting a green deploy.
Mutating a declarative definition through the API Definitions declared in TOML are read-only through the Admin API. You can query them; mutations return an error. If your code creates definitions at runtime and someone later moves them to TOML, that code starts failing.
More than 25 definition changes in one deploy A hard cap. A big schema change has to be split across deploys, which matters when you planned a single release.
Writing into a namespace you do not own custom is merchant-owned, so the merchant and every other app can change your values. Fine for data the merchant should edit; wrong for your app's internal bookkeeping. Use the app-reserved namespace for that.
Judgement, not documentation — an id stored at the wrong level Verified on a real store: an external id written at product level actually identified only one of that product's variants. Anything parsing it product-level matched that variant and silently mismatched the others. Store an identifier at the level it identifies.

What you say to a client/PM

When a client asks "can Shopify store our custom product data?" Yes, and there are two ways. Simple extra fields on a product — a care instruction, a fabric, a supplier code — are straightforward. If the data has several parts that belong together, like a size chart with rows and columns, that's a slightly different mechanism but still built in. What I need from you is the list of fields and their types, because defining them properly up front is what makes them editable and searchable later. Answers yes, distinguishes the two mechanisms without naming either, and asks for the one input that prevents the expensive mistake.
When you inherit an integration that skipped definitions The data is all there, but it was saved without telling Shopify what it means — so your team can't see or edit it in the admin, and it can't be used for filtering. Fixing it is straightforward but not instant: we declare the fields properly, then check every existing value matches the type we declared. I'd do it before adding anything new on top. Describes the symptom in the client's terms — "you can't see or edit it" — rather than as a technical omission.

Remember this

  • A metafield without a definition is stored and inert. Not editable, not validated, not filterable.
  • Four ownerships: merchant-owned, app-owned ($app), Shopify-reserved (shopify--), and app-data (hidden from the admin).
  • App-owned definitions only exist in the app-reserved namespace. That is what guarantees the same shape on every shop.
  • 64 KB for most types, 128 KB for json, 128 list items (1,024 for metaobject references).
  • Functions see null above 10,000 bytes. Stored fine, API fine, Function blind.
  • TOML definitions are read-only via the Admin API, and capped at 25 changes per deploy.
  • analytics_queryable in TOML deploys silently without taking effect. Verify capabilities after deploy.

If you remember one thing: never write a metafield without its definition — the data will look fine and everything built on it will not work.

Ask questions. Then "next" for when data does not belong on the product at all.
