Track 1 · P4 · Lesson 3 · depth

The Cart AJAX API

Shopify documents, in its own caution box, that one endpoint lets you oversell.

Your win today. You know which cart endpoint can silently put more items in a cart than exist, why the line item key is not the variant id, and how the discount parameter destroys what you did not send.

How it works

The endpoints, and what each one is for

EndpointDoesWatch for
/cart/add.jsAdd items404 Cannot find variant if the variant is not available on the online store channel
/cart/update.jsSet quantities, attributes, note, discountsDoes not validate quantity on items already in the cart
/cart/change.jsChange quantity, properties, selling planOne line item at a time, and only items already present

The documented overselling caution

This is not folklore. Shopify's own reference carries a caution:

Shopify's own words "The update.js endpoint doesn't validate the quantity on variants that are already in the cart. This means that it's possible to add more inventory than is available."

So a quantity stepper built on update.js will happily set a line to 50 when 3 exist. Nothing errors. The customer proceeds to checkout believing they have 50, and the problem surfaces at the worst possible moment — or after payment.

The mitigation is to use change.js for adjusting an existing line, and to re-read the cart after every write rather than trusting your local state. Which leads to the next point.

The line item key is not the variant id

"items": [
  {
    "id":         39897499729985,
    "variant_id": 39897499729985,
    "key":        "39897499729985:b1fca88d0e8bf5290f306f808785f744",
    ...
  }
]

The key identifies a line, not a variant. The same variant can appear on two lines — different properties, different selling plan — and only the key distinguishes them. Target a line by variant_id and you may change the wrong one, or merge two lines the customer meant to keep separate. Always address lines by key.

Discounts on the cart, and the destructive parameter

Discount support was added to /cart/update.js on 21 May 2025. The shape is simple and sharp-edged:

SendResult
{ discount: 'CODE' }That code is applied
{ discount: 'CODE1,CODE2' }Both applied
{ discount: '' }All discounts removed

Read that as whole-state, exactly like productSet in Track 2: the parameter sets the complete set of codes. There is no remove-one call. To remove one of three, you send the other two. Send one code to "add" it and you have silently deleted the other two.

Verified 2026-08-23: the update.js quantity-validation caution, the 404 Cannot find variant error, change.js handling one line item at a time and only existing items, the line item key format, and the discount parameter including comma separation and empty-string removal — Cart API reference. Discount support added 21 May 2025 — changelog.

Answer before reading on Your cart page has a quantity input. A customer types 50 for an item with 3 in stock, and your code calls update.js. What does the customer see, and where does it go wrong?

They see a cart with 50, a subtotal for 50, and no error at all — because update.js does not validate quantity on an item already in the cart. Everything looks correct right up to checkout, where availability is enforced. So the failure lands at the moment of highest intent, which is the worst place to put it. Use change.js for the adjustment, re-read the returned cart, and render from that response rather than from what you asked for. Then the customer sees 3 immediately and can decide, instead of discovering it after entering their card details.

Where it hurts

Costs money — update.js for quantity changes Documented by Shopify: no quantity validation on items already in the cart. Overselling, discovered at checkout. Use change.js.
Costs money — sending one discount code to "add" one The parameter is whole-state. One code sent means every other code removed. The customer loses a discount they had, silently, and blames the shop.
Fails with no error — addressing lines by variant id Two lines with the same variant and different properties. You change the wrong one, or merge them. Both are plausible-looking outcomes with no error. Use the key.
Fails with no error — rendering from your request, not the response Every cart write returns the resulting cart. Render from that. Render from what you asked for and your UI shows a cart the server does not have.
change.js handles one line at a time A "clear cart" or bulk-edit built on it becomes a sequence of calls. Sending them all at once invites a race where the last response is not the final state — send them in order and render the last response.
Judgement, not documentation — concurrent cart writes Shopify publishes no explicit guidance on concurrent cart requests, so treat this as engineering judgement rather than a documented rule: serialise your cart writes. Two in flight and the cart you render depends on which returns last.

Say it out loud

Explain this to a beginner

There is a cart endpoint that can sell items the shop does not have. Explain how that is possible, and what you use instead.

Say it out loud. Then read on.

Now compare with a plain-words answer

There are two different ways to change a cart, and they check different things.

One of them is for adding things, and it checks stock properly. The other one is for rewriting the whole cart at once — and for items that are already in the cart, it does not re-check the quantity. Shopify says so in its own documentation. So if you use the rewriting one to bump a quantity from 1 to 50, nothing stops you at 50 when there are only 3.

The fix is to use the endpoint meant for changing an existing line, one line at a time. Slower to write, does the check.

Two more things about carts that catch people. First, the identifier for a line is not the identifier of the product — the same product can sit on two separate lines, so you have to address the line. Second, several of these calls replace the whole state rather than editing part of it. There is no "remove one discount" call; you send the full set you want, and sending an empty one clears them all.

Which gives one habit that covers all of it: always draw the cart from what came back, never from what you sent. What you asked for and what happened are not the same thing.

If you used any of these words, try again idempotent · declarative state · optimistic UI · race condition · payload · PUT versus PATCH. "It rewrites the whole cart and does not re-check what was already in it" is the explanation.

Build it

Task · 30 minutes Dev store + theme

Oversell on purpose. It takes five minutes and you will never forget it.

  1. Set a variant's stock to 3.
  2. Add 1 to the cart normally.
  3. Now use update.js to set that line's quantity to 50.
  4. Look at the cart. Then do the same thing with change.js.

Proof it worked: one call accepted 50 and one refused it. You have reproduced a documented overselling path with your own hands, and you can now say which endpoint is safe for which job without looking it up.

Then the two traps · 25 minutes Dev store + theme
  1. Get the same variant onto two separate cart lines. Confirm the line keys differ and the variant id does not distinguish them.
  2. Apply two discount codes, then try to remove only one. Observe there is no such call.
  3. Fire two cart writes at once and render from what you sent. Then render from what came back.

Proof it worked: rendering from the request produced a cart that disagreed with Shopify; rendering from the response did not. That is the bug that shows up as "the cart shows the wrong thing sometimes" and is almost impossible to reproduce on a fast connection.

Remember this

  • update.js does not validate quantity on items already in the cart. Shopify documents this. It can oversell.
  • Use change.js to adjust an existing line. One line at a time, existing items only.
  • The line item key identifies a line, not a variant. One variant can occupy two lines.
  • The discount parameter is whole-state. No remove-one call; an empty string clears everything.
  • Render from the response, never from what you asked for.
  • A missing or unavailable variant returns 404 Cannot find variant, including when it is not on the online store channel.
  • Serialise cart writes. Undocumented, but concurrent writes make the rendered cart depend on response order.

If you remember one thing: the cart is whole-state and only loosely validated — send complete sets and always render what came back.
