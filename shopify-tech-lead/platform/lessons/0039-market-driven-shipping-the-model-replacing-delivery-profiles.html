Market-driven shipping: the model replacing delivery profiles

Shipping configuration is moving out of delivery profiles and into markets. Every merchant, by July 2027.

Your win today. You know which of the two shipping models a store is on, you can detect it in one field, and you know which of your own code has to change.

How it works

Why this Lesson exists, honestly This slot was originally going to be about Managed Markets. While researching it on 2026-08-23 I found something more urgent that I could verify: the delivery profile model taught in P7.1 is being deprecated. That is a live change to something the Course already teaches, so it wins the slot. Managed Markets stays on the gap list until I can verify it properly.

Derive it: why would Shopify move shipping into markets?

P5.1 established what a market is: a group of buyers you treat differently. Currency, prices, which products they can see, which website they land on, language — all already overridable per market.

Now ask the obvious question. If everything else about how you sell to a group of buyers lives in one place, why is shipping configured somewhere else entirely?

It should not be. Which is why it is moving. Shipping options are being moved into each market, so a merchant configures rates per market — across regions, POS locations and B2B company locations — and gets more predictable rates at checkout.

OLD delivery profile -> location group -> zone -> method -> rate a parallel structure, with its own idea of geography NEW market -> shipping configuration one place per group of buyers, alongside currency, prices, catalogue visibility and language

So this is not a new feature bolted on. It is a correction: shipping was the last thing configured outside the market model, and now it is not.

What is being deprecated, and what is not

This distinction is the whole Lesson, and getting it wrong means either panicking about nothing or missing a real break.

Your app…Action
Only creates and manages its own app-owned delivery profiles, and never reads merchant onesNo change. Keep using deliveryProfile / deliveryProfiles. Your integration keeps working.
Reads merchant delivery profiles — to surface rates, or sync with an external systemUpdate your read path.
Creates or modifies the merchant's delivery profilesUpdate your write path.

So the deprecation is specifically of deliveryProfile and deliveryProfiles for merchant-owned shipping configuration. App-owned profiles are untouched.

To find out which case you are in, audit your own GraphQL for deliveryProfile, deliveryProfiles, deliveryProfileCreate, deliveryProfileUpdate and deliveryProfileRemove. Anything that targets a profile your app did not create is a merchant-profile interaction, and that is the test — not the mutation name.

Detecting which model a merchant is on

You cannot assume, because merchants opt in over time and both models exist at once. There is one field for it: marketDrivenShipping on ShopFeatures.

So your code branches:

read ShopFeatures.marketDrivenShipping | |-- true -> write via marketCreate / marketUpdate | (needs read_markets AND write_markets) | |-- false -> write via deliveryProfiles (legacy) Once every merchant is on the new model (July 2027), the legacy branch can be deleted.

The two read paths, and why one is recommended

For reading merchant shipping configuration there are two options, and Shopify has a preference.

Option A — Contextual Product Feeds. Recommended, if your app is a sales channel or can become one. Shopify states it has several advantages over reading the Markets API directly. See A1.6 for what becoming a channel involves.

Option B — the Markets API. If Option A is not a fit, read from Markets directly. The markets query needs read_markets; mutations need read_markets and write_markets.

Test it before merchants arrive

There is a Market-driven shipping feature preview for development stores. Select it when creating a dev store, or enable it on an existing one from the developer dashboard. That means you can run your integration against both models today, before any merchant opts in — which is the entire point of a feature preview and almost nobody uses one.

Verified 2026-08-23: that market-driven shipping moves shipping options into each market across regions, POS locations and B2B company locations; that deliveryProfile and deliveryProfiles are being deprecated for merchant-owned shipping configuration while app-owned profiles are unchanged; the three action cases; the audit list of five operation names; the marketDrivenShipping field on ShopFeatures; that writers move to marketCreate / marketUpdate needing read_markets and write_markets; that readers should prefer Contextual Product Feeds if they are or can be a sales channel; that all merchants are expected on the new model by July 2027; and that a feature preview is available on development stores — Upgrade your app for market-driven shipping and markets.

Answer before reading on Your app creates its own delivery profile for a special "bulky items" rate, and separately reads the merchant's profiles to sync rates into an ERP. Which half breaks, and what do you do about each?

The app-owned profile is fine — keep using deliveryProfiles for it, unchanged. The reading half breaks, because it targets profiles your app did not create. So you branch on ShopFeatures.marketDrivenShipping and, on the new model, read from the Markets API — or become a sales channel and use Contextual Product Feeds, which is the recommended path. One app, two answers, and mixing them up means either rewriting something that was fine or missing the part that breaks.

Where it hurts

Costs money — assuming all delivery profile use is deprecated App-owned profiles are unchanged. Rewriting them is work you did not need to do, and it is the most likely over-reaction to this announcement.
Fails with no error — assuming which model a merchant is on Both exist at once while merchants opt in. Guessing means writing to the wrong place, and shipping configuration failing to appear is not an exception you will see — it is a checkout with no shipping option, which is P7.1's symptom.
Costs money — auditing by mutation name instead of by ownership The test is whose profile you are touching, not which operation you called. Anything targeting a profile your app did not create is a merchant-profile interaction, however you got there.
Costs money — discovering the market scopes late Writing through markets needs read_markets and write_markets. Adding a scope means re-consent from every merchant, as in A1.4 — so add it in the same release, not after.
Fails with no error — not using the feature preview You can enable market-driven shipping on a development store today. Skip it and your first contact with the new model is a live merchant who opted in, which is the most expensive possible place to find a gap.
Treating July 2027 as far away It is the date the legacy branch can be deleted, not the date to start. Merchants opt in before then, individually and without telling you.
Judgement, not documentation — this changes the shape of a shipping estimate Under the old model, shipping was one configuration to get right. Under the new one it is a configuration per market, and a store with many markets — P5.1 records one real store with 205 — is a very different amount of work. Ask how many markets before quoting shipping work.

Say it out loud

Explain this to a beginner

Shopify is moving shipping settings out of one place and into another. Explain why — and why some code that uses the old place is completely fine.

Say it out loud. Then read on.

Now compare with a plain-words answer

A shop already keeps a lot of settings per group of customers: what currency they see, what prices they pay, which products they are even shown, which language, which website. All in one place per group.

But shipping was configured somewhere else entirely, in its own structure with its own idea of geography. So a shop owner setting up a new country had to do part of the job in one place and part in another, and the two could disagree.

Moving shipping in with everything else means one place per group of customers. That is the whole reason.

On the code that is fine: there are two different things using the old structure. Some apps create their own shipping setup — a special rate for oversized items, say — and that is theirs to manage. Other apps read or change the shop owner's setup. Only the second kind is affected, because only the second kind is touching the thing that moved.

So the question is not "do I use the old thing?" It is "whose settings am I touching?"

If you used any of these words, try again delivery profile · market-driven · deprecation · app-owned versus merchant-owned · feature flag. "The shop owner had to do half the job in one place and half in another" explains the move. "Whose settings am I touching?" explains who is affected.

Build it

Task · 45 minutes your own codebase

Audit yourself. This is twenty minutes that decides whether you have any work at all.

  1. Grep for all five: deliveryProfile, deliveryProfiles, deliveryProfileCreate, deliveryProfileUpdate, deliveryProfileRemove.
  2. For every hit, answer one question: did my app create that profile?
  3. Sort the hits into two lists: app-owned (no change) and merchant-owned (must change).
  4. Split the merchant-owned list into reads and writes.

Proof it worked: you have four lists and you can say the size of the actual job. If your merchant-owned list is empty, you are done — write that down with the date so you do not re-audit in six months.

Then branch on the field · 60 minutes Dev store
  1. Read ShopFeatures.marketDrivenShipping and log it at start-up next to the API version.
  2. Create a dev store with the Market-driven shipping feature preview on — or enable it on an existing one from the developer dashboard.
  3. Run your integration against both a preview store and a normal one.
  4. For writes, implement the marketCreate / marketUpdate branch, and add read_markets and write_markets in the same release.

Proof it worked: the same code handles both stores, and your logs say which model each one is on. That log line is what stops the eventual "it broke for one client" from being a mystery.

The estimate question · 10 minutes no store needed

Add one line to your shipping-work estimate template: how many markets does this store have?

Proof it worked: the question is in the template. Shipping used to be one configuration; it is becoming one per market, and P5.1 records a real store with 205 of them.

Remember this

  • Shipping is moving into markets — per region, POS location and B2B company location. All merchants by July 2027.
  • deliveryProfile / deliveryProfiles are deprecated for merchant-owned configuration only. App-owned profiles are unchanged.
  • The test is ownership, not the operation name. Anything touching a profile your app did not create is affected.
  • Detect the model with ShopFeatures.marketDrivenShipping. Never assume — both exist at once.
  • Writers move to marketCreate / marketUpdate, needing read_markets and write_markets.
  • Readers should prefer Contextual Product Feeds if they are or can become a sales channel; otherwise read the Markets API.
  • A feature preview exists on dev stores. Test both models before a merchant opts in.

If you remember one thing: the question is not "do I use delivery profiles?" but "whose delivery profiles am I touching?" — and the answer decides whether you have any work at all.
