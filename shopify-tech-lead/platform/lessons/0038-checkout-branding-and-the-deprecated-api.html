Checkout branding, and the API that is already deprecated

The answer to "can we restyle checkout?" — plus a worked example of reading a deprecation notice properly.

Your win today. You can answer the restyling question with the plan gate and the mechanism, and you have seen why "it is in the docs" and "it is current" are different claims.

How it works

Derive it: what can you change about a page you do not own?

P5.2 established why checkout was closed: it is where the money happens, and it was the one page anyone could put arbitrary code on. So the answer to "can we restyle checkout?" cannot be "yes, write CSS".

What you get instead is a controlled vocabulary. Shopify defines the things that can vary — colours, type, spacing, corners, imagery, which components are visible — and you supply values. You are filling in a form, not writing a stylesheet. That is deliberate: Shopify can keep improving checkout because it knows every possible variation in advance.

The CheckoutBranding object has two halves:

FieldWhat it holds
designSystemThe foundations — colour roles, typography scales, spacing units. Set these once and they apply throughout.
customizationsSpecific components and areas — sections, dividers, interactive elements, visibility.

The split matters more than it looks. The design system is where you make broad changes consistently; customizations are where you override one thing. Doing everything through customizations produces a checkout that looks fine and cannot be adjusted later without touching twenty places.

Different colour schemes can be defined for different contexts, which is how contrast and accessibility stay correct across checkout states rather than being something you hand-check.

The plan gate, which is more generous than people assume

CheckoutBranding requires access to checkout branding settings and the shop must be on a Plus plan or a Development store plan.

That second half is the useful part. You can build and rehearse the whole thing on a dev store without Plus — which, per P5.1, is exactly why "do we need Plus?" has to be answered per feature. Here the answer is "yes for a live shop, no to learn it".

Now read the deprecation notice, because this is the real lesson

Look at how you would actually use it. The query is checkoutBranding, taking a required checkoutProfileId. The mutation is checkoutBrandingUpsert, taking a CheckoutBrandingInput and a required checkoutProfileId, where passing null resets to default.

Both are marked Deprecated in 2026-07.

Read that carefully, because it is a pattern worth internalising. The object is documented, current and fully described. The ways in are deprecated. So a search that lands you on the object page shows you something that looks completely healthy, and the deprecation is on the query and mutation pages you did not open.

This is the same shape as P1.3's falling forward: nothing errors, nothing warns you in the place you looked, and the signal is somewhere adjacent. Before building on any surface, check the deprecation state of the operations, not just the type.

Verified 2026-08-23: that CheckoutBranding requires access to checkout branding settings and the shop must be on a Plus plan or a Development store plan; that it exposes designSystem (colour roles, typography scales, spacing units) and customizations (sections, dividers, interactive elements, visibility); that different colour schemes can be defined per context; and that the checkoutBranding query and the checkoutBrandingUpsert mutation are both marked Deprecated, both take a required checkoutProfileId, and that passing null to the input resets settings to default — CheckoutBranding.

Answer before reading on A client on the Basic plan asks you to match checkout to their brand. Give the three-part answer.

One: what is possible — colours, type, spacing, imagery and component visibility, through a defined set of values rather than free CSS. Two: what it costs — checkout branding needs Plus on a live shop, so this is a plan upgrade conversation before it is a development one. Three: what could go wrong — the API surface for it is already deprecated, so before committing I would confirm the current supported route and put the date on the answer. That third part is what separates a real answer from a confident one.

Where it hurts

Costs money — building on the deprecated operations The checkoutBranding query and checkoutBrandingUpsert mutation are both marked Deprecated in 2026-07. Building on them without checking the current route is signing up for a rewrite you were told about in advance.
Fails with no error — reading the object page and stopping The CheckoutBranding object page looks entirely current. The deprecation is on the query and mutation. Check the operations, not the type — this is the same silence as falling forward in P1.3.
Costs money — promising checkout styling on a non-Plus live shop It needs Plus for a live store. Dev stores can do it, which makes the demo work and the go-live fail — the worst possible ordering.
Doing everything through customizations The design system exists so broad changes stay consistent. Override component by component and the next adjustment touches twenty places, which is how a "quick branding tweak" becomes a day.
Fails with no error — passing null without meaning to Passing null to the input resets settings to default. A partial payload that nulls a section is not "leave it alone" — it is "put it back", which is the same whole-state trap as productSet in P6.2.
Hand-checking contrast Colour schemes can be defined per context precisely so accessibility holds across checkout states. Setting one scheme and eyeballing the rest produces unreadable text in a state nobody tested.
Judgement, not documentation — this is usually not your decision Checkout appearance is a designer's call and a brand call. Your job is to say what is possible, what it needs, and what the risks are. A developer choosing the colour roles is a developer who will be asked to change them repeatedly.

Now compare with a plain-words answer

Documentation describes what exists. It does not promise that what exists is what you should build on.

Here is the exact situation. There is a page describing the thing that holds all the checkout appearance settings. It is detailed, it is current, and reading it you would have no idea anything was wrong.

But the two doors into that thing — the one for reading the settings and the one for changing them — are both marked as being on their way out. And those marks are on different pages. So you can read the main page carefully, understand it correctly, and start building on something you were warned about on a page you never opened.

The general habit: the thing and the way in are documented separately, and they can be in different states. So before building, check the state of the operations you will actually call, not just the object you read about.

And this is the same shape as the version problem. Nothing errors. Nothing warns you where you were looking. The signal exists, one page sideways.

If you used any of these words, try again deprecated · sunset · API surface · type versus operation · breaking change. "The thing and the door into it are documented separately and can be in different states" is the explanation.

Build it

Task · 30 minutes no store needed

Build the habit this Lesson is really about.

  1. List every Shopify operation your integration calls — queries and mutations, not types.
  2. Open each one's own reference page and record whether it is marked deprecated.
  3. Write today's date next to the list.
  4. Add this check to your CI alongside the schema validation from A2.4, so it cannot go stale.

Proof it worked: you found at least one deprecation you did not know about. This Course found three already-deprecated fields that way, every one inside a query that looked obviously correct.

Then actually brand a checkout · 60 minutes Dev store
  1. On a dev store — which qualifies without Plus — set the design system first: colour roles, typography, spacing.
  2. Only then add one customization for a single component.
  3. Now change the brand colour once, in the design system, and confirm it moves everywhere.
  4. Send a partial input that nulls one section. Watch it reset to default rather than stay put.

Proof it worked: one edit changed the whole checkout, and you have personally reset a section by passing null. That is the whole-state trap again, and it is cheaper to meet here than on a live shop.

The client answer · 15 minutes, recorded a voice recorder

Record the three-part answer to "can we restyle checkout?" — what is possible, what plan it needs, and the fact that you would confirm the current route before committing.

Proof it worked: the third part is in there. Saying "let me confirm the supported route and come back with the date I checked" is the R5.3 habit, and it is the part that makes the first two trustworthy.

Remember this

  • You get a controlled vocabulary, not CSS. Shopify defines what can vary; you supply values.
  • Two halves: designSystem for broad consistent foundations, customizations for specific overrides. Lead with the design system.
  • Needs Plus or a Development store plan. So you can learn it free and cannot ship it free.
  • The checkoutBranding query and checkoutBrandingUpsert mutation are both deprecated in 2026-07 — while the object page looks current.
  • Check the deprecation state of operations, not types. They are documented separately and can differ.
  • Passing null resets to default. A partial payload is not "leave it alone".
  • Define colour schemes per context so accessibility holds across checkout states.

If you remember one thing: "it is documented" and "it is the current way in" are different claims — so check the deprecation state of the operations you will actually call.
