Founding Engineer

How a real software product gets made inside a startup — from no idea at all, to strangers paying for it.

The goal. Any early startup can hand you a vague idea, and you can take it all the way to a live product with paying users — alone if you have to — and say why each decision was right. Read MISSION.md for the full version.

The big picture

Start with what a startup is. Steve Blank's definition does the work: a startup is a temporary organisation searching for a repeatable business model, while a company is a permanent one executing a model it already has.1 Search and execute are opposite jobs. Almost every mistake in this course comes from doing the second one while you are still in the first.

Searching costs money, and the money runs out. That is the whole shape of the problem: a fixed timer, and a guess you have to test before it stops. So the person who turns the guess into something real is not a code monkey. They are the constraint. That is the founding engineer's job, and it is where this course starts.

From there the course follows the order the work actually happens in, as three Tracks.

Track 1 — Find. You cannot build the right thing before you know what hurts. So first you learn to run a conversation without poisoning it: the Mom Test — talk about their life, not your idea, because any question about the future comes back as a polite guess. Then choosing which problem is worth a year of your life, using frequency, pain, who holds the budget, and whether you can find these people at all. Then the part nobody teaches: the kill rule, written down before you start, so you know in advance what evidence would make you stop. Without it, the runway makes the decision for you.

Track 2 — Build. Now the engineering, but with the objective function changed. You stop asking "how long will this take?" and start asking "how much time is this worth?" — appetite instead of estimate, because a fixed-scope overrun has no limit and a fixed-time one does. You learn cutting to the MVP, and to say out loud what you left out on purpose. You learn why the stack should be boring: you get about three novel choices, and a database is a terrible place to spend one. And you build a walking skeleton — thin, ugly, deployed on day one — then go fast everywhere except the places where a failure loses data or loses trust. That line is the quality boundary, and knowing where it sits is most of the craft.

Track 3 — Live. A product nobody uses has taught you nothing. You get the first ten users by hand, one at a time, because every normal channel multiplies a stock you do not have yet. You set the first price, because charging is a test and not a reward. You pick the one metric that matters for the stage you are in and ignore the other thirty. And you learn keeping it alive alone: backups you have actually restored, errors that reach your phone, a deploy you are not afraid of on a Friday.

Twelve ideas. Four per Track. That is the 20% core, and nothing else gets taught until those are solid — the rest is queued in the depth queue below, in the open, so you can always see what is being deliberately skipped.

1 Sourced: Steve Blank, "What's A Startup? First Principles." and "Search versus Execute". Checked 2026-08-23.

Track 1 — Find 4 core

  • F1 The job is not writing code core Why the role exists at all. The runway is a timer, so the scarce thing is learning per month, not lines per week.
  • F2 The Mom Test core Talk about their life, not your idea. Ask about the last time it happened, never about what they would do. Includes the evidence ladder: rank an answer by what it cost the person to say it.
  • F3 Choosing which problem to build core Four filters — frequency, pain in hours or money, who signs, can you reach them. Score each 0 to 5 and multiply, so a single 0 takes the whole score to zero.
  • F4 The kill rule core Write the evidence that would make you quit, while you are still calm about the idea. A number, a date, an action — and three paths out, not two.

Track 2 — Build 4 core

  • B1 Appetite, not estimate core Fix the time, vary the scope, because a fixed-scope overrun has no limit. Includes the sentence to say when you accept an appetite, so it does not become a deadline.
  • B2 Cutting to the MVP core Two tests — removal and answer — then say out loud what is missing on purpose. A human doing it by hand is a valid implementation.
  • B3 Boring stack and innovation tokens core You get about three novel choices. The real argument is failure modes you already understand — so ask "have I run this in production?"
  • B4 The walking skeleton and the quality boundary core Deploy end to end on day one, then go fast on anything you could fix in an afternoon. The axis is reversibility, not how bad it feels.

Track 3 — Live 4 core

  • L1 The first ten users, by hand core Every channel multiplies a stock you do not have yet, so at zero they all return zero. Fetch users one at a time, and log the refusals — they name the real problem.
  • L2 The first price core Charging is a test, not a reward. Never ask "would you pay?" — say "it is $X, shall I send the link?" and then be quiet.
  • L3 The one metric that matters core One number per stage: empathy, stickiness, virality, revenue, scale. Growth before stickiness fills a leaking bucket at full price.
  • L4 Keeping it alive alone core Three things only: a backup you have restored, errors that reach your phone, a deploy you are not scared of. Plus the list you skip on purpose.
